## 1. What's actually being asked of me here

Task 9.1 is mine — well, Priya's, but I was the one who signed off on it being gated last time, so I'm not going to wave it through without doing the thinking Priya would have done. Four bullets:

(a) what a participant/facilitator sees on delivery-time cessation
(b) what a participant sees on a rejected subscription attempt
(c) whether (a) and (b) are visually distinguishable from ordinary network flakiness — **they must not be**
(d) what the facilitator's readiness grid shows to distinguish "stale" from "accurate" for a given participant

I read the backend mechanism first (`staleness-signal.ts`). It's exactly what it should be: one close code, `STALE_SIGNAL_CLOSE_CODE = 4000`, used for every server-initiated close whose cause must not be disclosed — a rejected subscription and the 90-minute force-expiry both resolve to the same wire event. Task 9.2 already caught and fixed a real regression here (two distinct close codes that should have been one), and there's a named test guarding it. Good. That means the hard part — not leaking cause-of-revocation on the wire — is already done and already has a net under it. My job is narrower and, in some ways, harder: don't let the *client* leak it back in through a door the wire protocol didn't leave open.

## 2. The thing I actually worry about

The non-goal in design.md is precise: "Disclosing the cause of revocation to the affected connection... telling a removed connection why its events stopped would itself be a surveillance-adjacent behavior." That's a wire-protocol statement. It says nothing about UI, because at the time it was written there was no UI — I checked, and there still isn't. `SessionLobbyPage.tsx` is the only live-session-adjacent frontend surface that exists today, and it's pre-session only (waiting-for-facilitator). There is no WebSocket client anywhere in `packages/frontend/src`. No readiness grid component exists either — "readiness grid" today is a backend concept (`vote_readiness_update`, `evaluateSessionSubscriberAccess`) with no rendering surface.

So this isn't "add a banner to an existing live-session screen." This is the *first* frontend WebSocket work in this codebase, full stop. That changes what I'm worried about, because a design built from scratch has more places to accidentally reintroduce the disclosure the backend just spent a whole change eliminating.

A close code is binary — it either discloses or it doesn't, and that's checkable in a unit test. A UI has three ways to leak the same information that a close-code test will never catch:

- **Wording.** If the banner for "you were revoked" and the banner for "the network blipped" use even slightly different copy — one says "refresh," the other says "reconnecting..." — a curious participant now has a tell. This is the most obvious failure mode and the one 9.1(c) already names directly. I don't think anyone building this in good faith gets this wrong on the first pass. I think they get it wrong on the *second* pass, when someone reasonably wants to make the network-hiccup case less alarming ("we'll auto-retry") and the revocation case more final ("please sign back in") — two genuinely different technical situations that a well-meaning engineer will want to word differently, and that's exactly the drift I have to block.
- **Timing.** A rejected subscription attempt fails essentially instantly (the server never grants the subscription). A genuine network flake has whatever latency the network gives it — could be instant, could be five seconds of a spinner before the close event fires. If revocation is *always* fast and flakiness is *usually* slow, a participant who gets an instant banner has learned something, even if the banner text is identical. This is the one I don't have a clean answer for yet, because I don't know how the frontend intends to distinguish "close event received" from "connection attempt never completed" at the state-machine level — those may need to collapse into the same visual state with the same minimum-display-time floor, the way the reveal path already uses a timing floor elsewhere in this codebase (`timing-oracle.ts`, `CONTENT_TIMING_FLOOR_MS` — worth reusing the pattern, possibly not the module, since that one's server-side for a different reason).
- **Visual/behavioral asymmetry.** A retry-with-backoff on the network case but a hard "you must re-navigate to rejoin" on the revocation case is the same leak as wording, just moved into behavior instead of text. If the UI *does* different things (auto-reconnect vs. force a manual rejoin) for the two cases, that's disclosure, full stop — regardless of what the banner says. This means the client cannot special-case "was this close code 4000" vs. "was this a raw network error" and branch on it. It has to treat both as one undifferentiated bucket at the state-machine level, not just at the render level. That's a stronger constraint than "same banner" — it's "same code path."

I want that last point on the record because it's the one most likely to get quietly relaxed by an engineer who's trying to build a good reconnection UX (which is a legitimate goal!) and doesn't realize that a smarter reconnect strategy for ordinary flakiness is itself a disclosure surface if the revocation path doesn't get the identical smarter strategy.

## 3. Ritual constraints this has to respect (BRD, Section 8)

This isn't a generic "handle WebSocket errors" ticket — it lands inside a specific ritual with specific rules, and I want the design held against them explicitly:

- **OR-2.2 / OR-4.4** — the facilitator's readiness grid shows locked-in status "and nothing more," and it is facilitator-only; participants never see other participants' readiness. Bullet (d) asks what the grid shows to distinguish "stale" from "accurate" *for a given participant*. That's new information density on a screen that OR-2.2 explicitly constrains to be minimal. Whatever indicator we add (a per-row "last known state" marker, greyed-out row, a small icon) has to earn its place against "and nothing more" — it can't turn into a mini status console. And it has to be facilitator-only exactly like the rest of the grid; a stale/accurate distinction is itself a piece of information about a specific participant's connection, so it inherits OR-4.4's audience restriction, not just the readiness values themselves.
- **OR-3.5 / OR-3.6** — reveal must land on all participants simultaneously and participants get zero visibility into others' state pre-reveal. If a participant's connection silently dropped and got revoked mid-vote, and the UI shows *that specific participant* something different from what a merely-flaky participant sees, that's a second disclosure vector layered on top of §2 above — this time visible to the affected participant themselves, which OR-3.5's simultaneity guarantee doesn't obviously cover (it's about the reveal event, not about connection health), but the spirit of "no participant learns something about the mechanics of their own standing relative to others mid-session" runs the same direction.
- **The no-manager-surveillance thread, extended once more.** Every WebSocket change so far in this codebase has had to re-answer "does this leak something to someone who shouldn't see it" one more time in a slightly different place — HTTP payloads, then close codes, then (per the reauth change) audit trace names. This is the same question asked of pixels instead of protocol. I don't think that's a coincidence; I think it's what happens when a system is built around a genuine trust boundary instead of a cosmetic one. Good — that means the discipline that already worked three times should work a fourth time. I'd rather this Design stage treat "no disclosure via UI" as a first-class requirement with its own scenario coverage, the same way `websocket-session-authorization/spec.md` gave the wire protocol its own scenarios, rather than a stray sentence in a component's code comment that nobody re-checks after the fact.

## 4. Relationship to issue #33 — deliberately not touching it

#33 is about the *reauthorization* flow specifically — the facilitator readiness grid not yet distinguishing revocation from network flakiness *during reauth* (my own sign-off on `websocket-connection-reauthorization` named this as still open, and Rachel — via that champion-signoff — was right that it's "half the guarantee, not all of it"). This change's bullet (d) sounds adjacent but isn't the same ask: 9.1(d) is about the *delivery-time authorization* staleness signal (rejected subscription / force-expiry), not the reauth grace-period/token-refresh lifecycle #33 covers. If this design produces a generic "stale participant indicator" component for the readiness grid, #33 should consume it rather than duplicate it — but that's a note for whoever picks up #33 next, not a reason to expand this change's scope to solve #33 now. I want the Propose stage to state explicitly that this change's readiness-grid indicator is deliberately generic enough to also represent a not-yet-reauthorized connection, without this change being the one that wires that second case up. If it can't be made generic without meaningfully complicating this change, don't force it — leave a clean seam and let #33 do its own job.

## 5. What "same generic treatment" concretely has to produce

Reading 9.1's four bullets together, I think the actual deliverable is:

1. One client-side connection-health state (not per-cause) with values something like: `connected`, `unknown/reconnecting` — a single bucket covering both a raw close/error event and the 4000 code — no third value that a curious client could branch on. Two things I left implicit that Marcus's review rightly said needed to be explicit:
   - **Recovery is silent.** When a genuinely-flaky connection comes back, the state reverts to `connected` with no distinct "you're reconnected" acknowledgment — no toast, no transition treatment. This is deliberate, not an oversight: an explicit "reconnected" event that can only ever fire for the recoverable case would itself be the same disclosure this document exists to prevent, since a revoked connection would never produce one. Should have said so the first time rather than leaving it to be inferred.
   - **Initial-connection failure folds into the same bucket.** A participant whose very first subscription attempt is rejected (never had a good connection to lose) is not a different case from mid-session staleness — it's bullet (b) of 9.1, and it gets the same `unknown/reconnecting` state and the same banner. Worth saying in as many words, since this is greenfield frontend WebSocket code with no prior pattern to match against, and an engineer building the state machine from scratch could otherwise reasonably invent a separate "couldn't connect" path without realizing it reopens the same disclosure risk.
2. One rendered treatment for that "unknown/reconnecting" state, shown identically to a participant or facilitator regardless of underlying cause: plain language, no blame, no urgency escalation. My own sketch — **"Your view may be stale. Refresh to continue."** — was never more than a placeholder to react to, and I want that stated explicitly now that Priya has: it is not implementation-ready copy and nobody downstream should treat it as approved. Priya's own first pass, offered on the same non-final basis: **"Your view may be out of date. Refresh to continue."** (participant-facing) and **"Last known state may not be current."** (facilitator grid tooltip, deliberately duller register — a fact to note, not a problem to solve). Neither of us is signing off on wording in isolation; Priya wants both strings seen in their actual layout (banner in context, tooltip on the actual grid) before sign-off, and that's the right bar. The *constraint* that it's one string per state, applied identically regardless of cause, is what I can commit to now — the string itself is not this document's call to make.
3. A facilitator-only per-participant grid marker for "last known state may be stale" — visually minimal (per OR-2.2), not a second information channel, and itself gated to facilitator-only the same as the rest of the grid. Marcus's review sharpened this into a concrete bound, and I want it stated as a requirement rather than left as prose: the marker adds at most one new visual state to the grid's existing three (connected+locked-in, connected+not-locked-in, disconnected+no-vote, per `redis-session-model.md`), introduces no new color/icon language beyond what the grid already uses, and — this is the part I'd have missed — is **cause-blind**, not just visually minimal: it must not let a facilitator distinguish "stale because revoked" from "stale because flaky" from "stale because not-yet-reauthorized" (#33's case). That last clause is the same disclosure discipline from §2 applied to this surface, not a separate concern, and it should have been explicit in my first draft.
   The marker also needs a defined lifecycle, which I hadn't specified: if a participant never reconnects, does the marker persist indefinitely or collapse into the existing `disconnected_no_vote` state? Agreed with Marcus that Design needs to state a TTL or fallback, not leave it open-ended — OR-2.2's "and nothing more" budget is a footprint constraint, and an indefinite fourth state is a bigger footprint than a transient one. One addition of my own: whatever that TTL is, it has to apply identically regardless of cause, for the same reason the initial timing floor does (§2) — a marker that collapses to "disconnected" faster for revoked connections than for flaky ones is a timing leak in a new location.
4. A single reconnection/recovery behavior applied uniformly regardless of cause (see §2's timing/behavior point) — this is the part most likely to be treated as "just an engineering detail" and it isn't; it's a disclosure boundary exactly as load-bearing as the close code itself.

I'm treating #3 and #4 as needing explicit scenario coverage at Design stage, not left implicit.

## 6. Open questions I'm carrying into Propose

Two of these have moved out of this section since the first draft — Marcus's review is right that they were already decisions, not questions, and I was hedging procedurally rather than actually being uncertain:

- **Shared implementation — now a requirement, not a question.** A single client-side connection-health module is the sole implementation of the `connected`/`unknown-reconnecting` state machine, consumed by both the participant view and the facilitator grid. No second implementation may be built independently, including by #33's later work — #33 must consume this module, not fork it. I was already arguing for this; framing it as "open" was me being more cautious than the reasoning warranted.
- **Retry-strategy symmetry — now a testable acceptance condition, not a research question.** The client's reconnection state machine must not branch on close-code value (4000 vs. raw network error/close) or on connection-attempt outcome type. Retry count, backoff schedule, and jitter must be identical code paths for both causes, verifiable by a test that forces both a 4000 close and a simulated network drop through the same handler and asserts identical retry timing. This is Marcus's rewrite of my original bullet, and it's a strict improvement — "need the reconnection strategy specified" wasn't buildable on its own.

Remaining, genuinely still open:

- **Timing floor.** Does the "unknown/reconnecting" banner need a minimum-display or minimum-delay-before-showing floor to prevent instant-vs-eventual timing from leaking cause? Yes — and I want to lock in the *existence and uniform application* of the floor as a requirement now, even though the exact millisecond value is legitimately a Design-stage decision that may need real latency data. Priya's review adds a second, independent justification for the same floor that I hadn't considered: ordinary conference-room wifi flakes constantly, and a marker that flickers on/off with every two-second hiccup trains facilitators to ignore it by session three, which defeats the point of having it. Disclosure-timing and visual-noise are different justifications that likely converge on the same number — I want both reasons on record so neither gets forgotten if someone tries to trim the floor down later purely for "responsiveness."
- **Grid marker visual design.** Still needs an actual mock, not prose — both Priya and Marcus independently said the same thing and I agree. Marcus's bound (at most one new visual state, no new color/icon language, cause-blind — see §5.3 above) and Priya's register guidance (§7 below) give Design something concrete to design against and be checked against, rather than "visually minimal" being a judgment call made once and never revisited.
- **Grid marker lifecycle during an active vote.** New question from Priya, and a good one: if a participant goes stale *during* an active vote rather than pre-session or idle, does their row freeze at last-known-state, or change visually? A row that silently flips from "not yet voted" to "may be stale" mid-reveal-countdown is a different cognitive event for a facilitator than the same change showing before voting starts. Design needs to state which moments in the session lifecycle this marker can appear during, not just what it looks like at rest.
- **Confirm with Priya** whether either of our copy sketches (§5.2) is acceptable or whether she wants different wording once she's seen both in actual layout — still the standing blocker per 9.1's own text, and per Marcus's review this needs to carry into Propose with the same teeth tasks.md 9.1/9.3 already gave it: *a filed draft that does not resolve all four bullets does not close this task; "filed" and "signed off" are not the same completion condition.* Propose should restate that language directly rather than paraphrase it.

## 7. Facilitator-experience additions (from Priya's review)

My first draft was written entirely from the disclosure-boundary side and said almost nothing about what a facilitator running a live session actually experiences when this fires. That's Priya's half of task 9.1, not mine, and I'm folding her points in rather than restating my own reasoning around them:

- **Visual register: "uncertain," not "broken."** The marker should read closer to a hollow/dimmed version of the existing not-locked-in state than a new icon or color — if it looks like an error, a facilitator will start treating it like one during the session (narrating it out loud, which is its own problem — next bullet). See §8 for a tension this creates with Marcus's constraint that Design needs to resolve, not me.
- **Not an outlier-flagging signal.** A facilitator seeing "participant X is possibly stale" is one short step from treating that as a reason to call on them ("are you still there?"), which is the wrong move for the same reason unprompted outlier flagging is already advisory-not-prescriptive elsewhere in this system — arguably more so here, since "your connection might be flaky" is a more awkward thing to surface to a room than a vote difference. Concretely: no click-to-ping, no auto-generated chat message, nothing that turns a quiet facilitator-only signal into a spoken moment unless the facilitator chooses to make it one. This lines up directly with the no-manager-surveillance thread already flagged in §3 — same instinct, applied to a new surface.
- **First-session support is a tooltip, not a tutorial.** A one-line hover tooltip is enough ("last known state may not be current" is Priya's draft); it needs to be self-explanatory to a first-time facilitator without requiring they've read documentation first, since the first session for a new team is already the hardest one to run.
- **Usability test, not just OR compliance.** Priya wants to be in the room (virtual is fine) when this is tested against real facilitator judgment calls specifically for "does this read as an alarm," not just checked against OR-2.2/OR-4.4. Right call — carry it forward as a testing-stage commitment, not something dropped once Design produces a mock that technically satisfies the written requirements.

## 8. Pushing back / flagging tensions rather than silently resolving them

Two things from the reviews I'm not just folding in quietly:

1. **Priya's and Marcus's visual guidance point in slightly different directions, and I'm not picking a side here.** Priya wants the marker to read as a dimmed/hollow version of the *not-locked-in* state — implying "still connected, just uncertain." Marcus's acceptance condition says the marker must not introduce color/icon language beyond what the grid already uses for *disconnected*. Those are two different existing states with two different implications, and collapsing them into one instruction without noticing the difference would be worse than leaving it visible. This is a real design decision, not a contradiction to average away — it's Priya's call on the register (she owns the facilitator-experience half of 9.1) constrained by Marcus's budget (no new color/icon vocabulary, cause-blind), and Design should resolve it explicitly against a mock, not have me guess at it in a notes document.
2. **Session-history footnotes for stale-connection events — I'm not carrying this forward as proposed.** Priya suggested (flagged explicitly as non-blocking, to her credit) that session history could someday note something like "participant X's connection was interrupted during topic 3." I want to name why I'm hesitant rather than let it sit as an innocuous "flag for later": a record that ties connection-stability events to a *named individual* across sessions is exactly the kind of data the ritual's core design refuses to collect on purpose — session data must not be surfaceable in a way that allows comparison of individual engineers across teams or over time, and that isn't a guideline I get to soften because a given data point feels harmless. A connection hiccup isn't a performance signal today, but a per-person history of them, accumulated over months, starts to look like one whether or not that's the intent. If this is ever pursued, it needs its own review against that constraint specifically — aggregated and unattributed at minimum, probably scoped to session-level ("a stale-connection event occurred during topic 3," no participant name) rather than participant-level. I'm not blocking Priya's ask to *name the question*, which she already did carefully by calling it speculative scope creep herself — I'm declining to let "not a blocker" imply "safe to build later without another look."
