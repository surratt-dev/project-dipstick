# Implementation Summary — `websocket-staleness-signal`

Implemented by: Marcus Oyelaran (Full Stack Engineer), following `design.md` and `tasks.md` as finalized after design/task review incorporation.

## What was built

**Group 0 — shared close-code constants.** `STALE_SIGNAL_CLOSE_CODE` (4000) and `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (4001) relocated to `packages/shared/src/types/ws-close-codes.ts` as runtime `export const` values, re-exported from `packages/shared/src/index.ts`. `packages/backend/src/realtime/staleness-signal.ts` and `connection-token-refresh.ts` now import from `@dipstick/shared` and re-export under their original names, so every existing backend import site (`websocket-routes.ts`, `connection-reauthorization.ts`, both test files) kept working unmodified. All 449 pre-existing backend tests pass unchanged.

**Group 1 — `packages/frontend/src/realtime/connectionHealth.ts`.** The full three-state machine (`connected` / `unknown-reconnecting` / `reauth-required`) per Decisions D1–D5, D1a–D1g:
- `useConnectionHealth(connect)` owns the WebSocket lifecycle: initial connect, close/error classification, message inspection, the 2000ms timing floor (with the D3a early-recovery cancellation), full-jitter exponential backoff via the exported pure `computeRetryDelay`, and silent recovery.
- `connect` is captured via `useRef` with an empty-deps setup effect (D1d); message handling uses `addEventListener` exclusively, never `.onmessage =` (D1e); teardown unconditionally closes the socket and clears both timers, covering unmount-mid-retry and React 18 StrictMode's double-invoke (D1g).
- The one narrow exception to the non-disclosure invariant — checking `event.code === REAUTH_GRACE_EXPIRED_CLOSE_CODE` — is the only close-code comparison anywhere in the module. `reauth-required` is sticky/terminal (D1c): entry synchronously clears any pending retry timer and a state check gates out all subsequent close/error events, closing both races the security review flagged.
- Exhaustiveness is enforced via an exported `assertExhaustiveConnectionHealthState(state: never)` helper, used in every switch over `ConnectionHealthState` across all three components (task 1.2's convention, matching `ws-event-dispatcher.ts`).
- `FakeWebSocket` (`realtime/__tests__/fake-websocket.ts`) is a hand-rolled `EventTarget`-based test double per D1f — no new dependency.
- 23 tests in `connectionHealth.test.ts` plus 4 grep-based structural tests in `connectionHealth.grep.test.ts` (task 1.9's non-disclosure invariant, extended in Group 3/4 to also scan `ConnectionStatusBanner.tsx` and `FacilitatorReadinessGrid.tsx`).

**Group 3 — `ConnectionStatusBanner.tsx`.** Calls `useConnectionHealth` directly (D6). Renders one fixed placeholder string per state (`unknown-reconnecting` / `reauth-required`), nothing for `connected`. Rendered-output-identity tests confirm byte-for-byte identical output regardless of underlying cause, and that the two non-connected states differ from each other. A plain-language check confirms no exclamation, "error" wording, or alarm-red styling.

**Group 4 — `FacilitatorReadinessGrid.tsx`.** A minimal readiness grid (not feature-complete — Non-Goals) calling `useConnectionHealth` directly for the facilitator's own connection (D6/D7). The marker overlays every row simultaneously when the facilitator's own state is `unknown-reconnecting`, composes with (never suppresses) `disconnected-voted`'s existing "ready" treatment, introduces no new color/icon language (neutral placeholder per the D10/4.7 gate), has no independent TTL (lockstep with connection health), has no click/ping/auto-notify affordance, and is excluded entirely when the facilitator's own state is `reauth-required` (superseded by the same top-level treatment `ConnectionStatusBanner` renders). The hover tooltip (`"Last known state may not be current."`) is wired via the native `title` attribute. `facilitator-row-fixture.ts` provides the test-local four-state row fixture (task 4.0a), independent of Group 5's host-level stub. 11 tests in `FacilitatorReadinessGrid.test.tsx`, including the cross-surface import check (4.12).

**Group 5 — minimal host surfaces.** `SessionConnectionHost.tsx` (participant) and `FacilitatorConnectionHost.tsx` (facilitator) build a same-origin `ws(s)://.../ws/sessions/:sessionId` connection from the route's `sessionId` param and wire it to the banner / grid respectively. Mounted at new routes `/session/:sessionId/live` and `/session/:sessionId/facilitator` in `App.tsx`, both behind `ProtectedRoute`, so they're reachable via `npm run dev` for manual verification and available for issue #19's E2E work. `vite.config.ts` gained a `/ws` proxy entry with `ws: true` (task 5.1a) — without it, the dev server couldn't reach the backend's WS route at all.

**Group 7 — final sweep.** Re-ran the 1.9 grep checks across all three source files (7.1); ran the four disclosure-boundary hard-gate tests explicitly — retry-symmetry (1.4), reauth-required no-retry (1.11), both sticky-state race tests (1.14/1.15), and the cause-blindness test (4.4) — all pass (7.2); confirmed no `process.env`/config/feature-flag surface reaches the timing floor, backoff, or jitter (7.3); confirmed no session-history/trend-continuity code was added (7.4 — this change touches no database or history-recording path at all); ran the full frontend suite alongside the pre-existing 168 tests, all passing (7.5).

## A gap worth flagging, not fixed here

`packages/frontend`'s `build` script (`vite build`) does not type-check — confirmed by injecting a deliberate type error and observing a clean build. The CI "Type Check" job runs `npm run build`, which for the frontend workspace is this same non-type-checking `vite build`, so **no TypeScript error in `packages/frontend/src` is currently caught by CI**. This is a pre-existing condition, not something introduced by this change (`git status` before this work began was clean; several pre-existing test files — `AuthContext.test.tsx`, `ProtectedRoute.test.tsx`, `MemberManagement.test.tsx`, `App.test.tsx`, `TeamPage.test.tsx` — already fail `tsc --noEmit` under this repo's strict `tsconfig.base.json`, e.g. `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`). All new *production* source added by this change (`connectionHealth.ts`, `ConnectionStatusBanner.tsx`, `FacilitatorReadinessGrid.tsx`, `SessionConnectionHost.tsx`, `FacilitatorConnectionHost.tsx`) was verified clean under `tsc --noEmit -p packages/frontend/tsconfig.json`; the test-support module `fake-websocket.ts` was also fixed to be clean. New `*.test.ts(x)` files were not scrubbed for `noUncheckedIndexedAccess`/`exactOptionalPropertyTypes` compliance, consistent with the rest of this repo's existing test suite. Task 1.2's "compile-time regression test" is therefore implemented as a runtime proxy (calling `assertExhaustiveConnectionHealthState` directly and asserting it throws) rather than a `// @ts-expect-error`-based compile check, since no typecheck harness currently runs against `packages/frontend` for either CI or `vitest` to enforce it either way. Not fixed here as it's outside this change's scope — flagging for whoever picks this up next.
