## Context

`websocket-delivery-time-authorization` closed the wire-protocol leak: every server-initiated close whose cause must not be disclosed — a rejected subscription and the 90-minute absolute-lifetime force-expiry — resolves to the single `STALE_SIGNAL_CLOSE_CODE` (4000, `packages/backend/src/realtime/staleness-signal.ts`). That change's own task 9.3 left a hard gate open, carried here verbatim: this capability "MUST NOT be used for a real pilot team's first live session" until the client-visible signal exists, is unambiguous, and has Priya Nair's (Facilitator SME) sign-off. Issue #19 (full-stack E2E) is also blocked behind this gate.

There is no frontend WebSocket client anywhere in `packages/frontend/src` today, and no readiness-grid rendering surface — "readiness grid" is currently a backend-only concept (`vote_readiness_update`, `evaluateSessionSubscriberAccess`, and the `connection_status` field documented in `requirements/design/redis-session-model.md`). `SessionLobbyPage.tsx` is the only live-session-adjacent frontend surface, and it is pre-session only. This is the first frontend WebSocket work in this codebase: there is no existing pattern to lean on, and — per `exploration-notes.md` §2 — no existing pattern to accidentally deviate from either, which is precisely why the constraints below are written as explicit requirements rather than left to engineering judgment.

**Constraints this design is held against** (from `proposal.md`, `exploration-notes.md` §2–3, and the ritual's BRD Section 8):

- A close code is binary and unit-testable. A UI can leak the same cause-of-revocation information three ways a close-code test never catches: **wording** (different copy for "revoked" vs. "flaky" is a tell), **timing** (an instant-fail-vs-eventual-fail asymmetry is a tell even with identical copy), and **behavior** (a smarter retry strategy applied to only one cause is a tell regardless of what the banner says).
- OR-2.2 / OR-4.4: the facilitator's readiness grid is minimal ("and nothing more") and facilitator-only. Any new grid state inherits both constraints.
- The no-manager-surveillance thread: this is the same trust-boundary question already re-answered for HTTP payloads, close codes, and audit trace names, now asked of pixels.

**Stakeholders:** Priya Nair (Facilitator SME) owns the facilitator-experience requirements and holds two hard sign-off gates (copy, and the visual-register mock) plus a usability-test commitment carried into the testing stage. Marcus Delgado (BA) supplied the acceptance-condition tightening this design implements directly (shared-module requirement, retry-symmetry test, grid-marker bound, and — at Propose review — the requirement that this design account for `websocket-connection-reauthorization`'s 4001/`reauth_required` signal pair rather than silently folding it into the disclosure-blind bucket). Issue #33 (facilitator grid distinguishing revocation from flakiness during the *reauthorization* flow specifically) and issue #32 (the reauthorization spec's own tracked item for the client-visible UX of its re-authentication prompt, spec.md:11/178) are both deferred consumers of the module this change builds — neither is built or wired up here.

**A second wire contract this design must account for, not just SEC-25's:** `websocket-connection-reauthorization` (SEC-25/SEC-26) closes connections two ways. The SEC-25 sweep reuses `STALE_SIGNAL_CLOSE_CODE` (4000) — the same disclosure-blind code the delivery-time mechanism uses, and the one this design's `unknown-reconnecting` bucket exists to render without leaking cause. The SEC-26 silent-refresh path uses a *different*, deliberately distinct pair — `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (4001) and an in-band `reauth_required` message — that the reauthorization spec itself states is legitimately disclosed to the client it happens to (spec.md:107-121) and that requires a full top-level page navigation to recover from, never an in-place reconnect (spec.md:63). Treating 4001/`reauth_required` identically to 4000/network-drop would not be extra caution — it would strand a participant retrying forever against a connection that can never succeed. See Decision D1a.

## Goals / Non-Goals

**Goals:**
- One client-side connection-health module, one state machine, **three** values (`connected` / `unknown-reconnecting` / `reauth-required`), consumed identically by the participant view and the facilitator grid. The disclosure-blind pair (`connected`/`unknown-reconnecting`) never branches by cause; `reauth-required` is a distinct, legitimately-disclosed state, not a fourth undifferentiated bucket (see Decision D1a).
- One rendered participant-facing treatment for `unknown-reconnecting`, applied identically regardless of cause, plus one minimal generic rendered treatment for `reauth-required`.
- One facilitator-only grid marker with a defined signal source, lifecycle, and visual bound, cause-blind by construction, scoped to `unknown-reconnecting` only.
- A uniform timing floor and retry policy that never branches on close-code value or connection-attempt outcome type — except the one narrow, named check for `REAUTH_GRACE_EXPIRED_CLOSE_CODE` that routes to `reauth-required` instead of the retry path (Decision D1a).
- A retry-symmetry test, a `reauth-required` no-retry test, and a cause-blind grid-marker test as CI-enforced, not just code-reviewed, acceptance conditions.

**Non-Goals:**
- Building the full live-session voting UI (topic display, vote casting, reveal countdown, results rendering). This design adds only the minimal host surface needed to mount and test the connection-health banner and grid marker against a real WebSocket connection (see Decision D9). The rest of the live-session frontend is tracked separately and is not blocked by this change, nor does this change block on it.
- Issue #33's reauthorization-specific grid distinction. This change leaves a generic, cause-blind seam; #33 consumes it, this change does not wire up the reauth case.
- Issue #32's fuller re-login UX for the `reauth-required` state. This change builds the state, its detection (message + 4001 fallback), the no-retry behavior, and a minimal generic rendered treatment ("please log in again," not styled or polished); #32 consumes this state for its richer UX, this change does not build it.
- Any new server-side signal, close code, or heartbeat. `STALE_SIGNAL_CLOSE_CODE` is consumed as-is; this change is purely client-side.
- Session-history / trend-continuity for stale-connection events (proposal.md Open Design Question 2). Explicitly declined — see Decision D12.
- Final visual styling of the grid marker. Blocked on a mock and Priya Nair's sign-off — see Decision D10 and the gate tasks in `tasks.md`.
- Configurability of the timing floor, retry backoff, or jitter via environment variable, feature flag, or admin surface. Permanently absent by design, matching the precedent set by `REAUTHORIZATION_INTERVAL_MS` and the grace-period constant in `websocket-connection-reauthorization`.
- **Aggregate, non-attributable operational telemetry for connection-health state distribution** (e.g., fleet-wide volume of clients hitting `reauth-required`, or retrying indefinitely against revoked connections). This is a distinct question from Decision D12's declined per-participant history — D12 is about attributable records; this is about whether any aggregate signal exists at all for incident response. Named here as a recorded gap (Security design review, Finding 4), not addressed by this change: this change is purely client-side and adds no new server-side signal, so it has no mechanism available to it to close this gap. Pursuing it would require its own server-side design.

## Decisions

### D1 — Module shape and location

`packages/frontend/src/realtime/connectionHealth.ts` (new directory, mirroring the backend's `packages/backend/src/realtime/` naming) exports:

- `type ConnectionHealthState = "connected" | "unknown-reconnecting" | "reauth-required"` — a three-value discriminated union. No fourth value exists anywhere in this module's public surface, enforced by TypeScript exhaustiveness checking plus the regression test in task 1.2. **Correction from the Engineer design review (Marcus Oyelaran), blocking:** an earlier draft of this decision described the guard backwards. A `switch` with no `default` case does not fail to compile when a case is missing — TypeScript permits a non-exhaustive switch with no default, and an added state simply falls through unmatched at runtime, silently. The actual, compile-enforced guard — and this codebase's established convention, per `packages/backend/src/realtime/ws-event-dispatcher.ts:81-88` — is the opposite shape: every `switch` on `ConnectionHealthState` (in the hook, in `ConnectionStatusBanner`, in the grid-marker component) includes a `default: { const _exhaustive: never = state; ... }` block. It is the `never` assignment inside `default` that fails to compile once the switch stops being exhaustive, not the absence of `default`. `reauth-required` is not a peer of `unknown-reconnecting` in the disclosure sense — see Decision D1a — but it is a peer in the type, since both are values a consumer must handle.
- `useConnectionHealth(connect: () => WebSocket): { state: ConnectionHealthState; socket: WebSocket | null }` — a React hook owning the WebSocket lifecycle: initial connect, classification of every close/error event, message inspection for the one recognized application-level signal (D1a), the timing floor (D3, `unknown-reconnecting` only), the retry loop (D2, `unknown-reconnecting` only), and silent recovery (D4).

**Alternative considered:** separate hooks for participant and facilitator use. Rejected — the shared-module requirement (proposal.md bullet 8, `exploration-notes.md` §6) is explicit that no second implementation may exist, including for #33's later work. One hook, two call sites.

### D1a — `reauth-required`: a third, legitimately-disclosed state

`websocket-connection-reauthorization`'s SEC-26 mechanism sends the client an in-band `{"eventType": "reauth_required"}` message before closing with `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (4001) — a signal pair the reauthorization spec deliberately keeps distinct from `STALE_SIGNAL_CLOSE_CODE` and states is legitimately disclosed to the affected client (spec.md:107-121), not a secret the wire protocol is withholding. `useConnectionHealth` recognizes both forms of this signal — the message (primary; arrives first and while the socket is still open) and the 4001 close code (fallback, for a client that misses or never receives the message) — and transitions `state` to `reauth-required` from either. The message is narrowed against the existing `WsClientMessage` type (`packages/shared/src/types/realtime.ts`), which already defines the `{ eventType: "reauth_required" }` shape — `connectionHealth.ts` imports and narrows against this shared type rather than hand-rolling an inline shape check (Engineer design review, section 9). See Decision D1b for where the two close-code constants themselves now live.

This is the **one, narrow, named exception** to "the handler does not read `event.code` for any purpose": the module checks for exactly `REAUTH_GRACE_EXPIRED_CLOSE_CODE` and no other value, and only to route to `reauth-required`, never to alter `unknown-reconnecting`'s classification, timing, or retry behavior. This does not reopen the disclosure question D2 closes, because the thing being checked for is not one of the causes `unknown-reconnecting` must stay blind to — it is a categorically different, spec-mandated, already-disclosed signal about the client's own token. Distinguishing "this client's own token needs renewal" from "we don't know what's wrong, keep trying" discloses nothing an onlooker (a facilitator, or the participant themselves) couldn't already legitimately know about their own connection.

`reauth-required` is cause-blind **within itself**: `useConnectionHealth` does not distinguish, and cannot distinguish from the signals available to it, whether the underlying SEC-26 failure was retry-budget exhaustion, a definitive identity-provider revocation, or a concurrent session destruction — matching SEC-26's own non-disclosure of that sub-cause (spec.md:154-159, "does not indicate whether the prior refresh failure was a definitive revocation or a transient/retry-exhausted failure").

**No retry is attempted from `reauth-required`.** `computeRetryDelay` (D2) is never called on this path — recovery is a full top-level page navigation to the identity provider (spec.md:63), which tears down this hook's JS execution context entirely; there is no in-place reconnect for the retry loop to attempt. Entering the retry loop here would not just be pointless, it would actively produce the exact stuck-forever outcome flagged at Propose review: a participant retrying indefinitely against a connection that can never succeed, with no signal telling them the actual fix is to log back in.

`reauth-required` is never reachable from a 4000 close or a raw network close/error, and `unknown-reconnecting` is never reachable from a `reauth_required` message or a 4001 close — the two paths do not merge or fall through into each other. Decision D1c makes this an enforced invariant against out-of-order events specifically, not only an outcome of the happy-path sequencing described above. Task 1.9's grep-based enforcement additionally covers debug-logging leaks of cause information — see task 1.9 (Security design review, Finding 5).

**Rendered treatment:** a minimal, generic string distinct from `unknown-reconnecting`'s banner — placeholder: "Your session needs to be renewed. Please log in again." — wired the same way as the `unknown-reconnecting` banner (Decision D8), non-final pending Priya Nair's copy sign-off (D11). This is the full extent of this change's UX for this state; issue #32 (spec.md:11/178) consumes this state for a richer treatment, per the Non-Goals above.

**Alternative considered:** fold 4001/`reauth_required` into `unknown-reconnecting`, per the proposal's original two-state framing. Rejected at Propose review (Marcus Delgado, BA) — the reauth spec's own "recovery is always a fresh connection, never an in-place resume" language (spec.md:63) means a retry-forever policy applied here cannot ever succeed, and the spec's own "legitimately disclosed" language (spec.md:121) means there is no disclosure benefit to hiding the distinction that would justify the resulting stuck state.

### D1b — Close-code constants relocate to `packages/shared`

**Blocking finding from the Engineer design review (Marcus Oyelaran).** Earlier drafting of this document (and the proposal's Impact framing) described `STALE_SIGNAL_CLOSE_CODE` and `REAUTH_GRACE_EXPIRED_CLOSE_CODE` as consumed directly from `packages/backend/src/realtime/staleness-signal.ts` and `connection-token-refresh.ts`. That is not buildable: `packages/frontend/package.json` depends only on `@dipstick/shared` and must not gain a dependency on `@dipstick/backend` — `connection-token-refresh.ts` imports `fastify`, `../redis.js`, `../db.js`, and `../auth/middleware.js`, none of which belong in a Vite-bundled browser client. There is no legal import path from `connectionHealth.ts` to either backend file, and neither `4000` nor `4001` exists anywhere in `packages/shared` today.

Both constants move to a new `packages/shared/src/types/ws-close-codes.ts`, exported as plain `export const` values — not `export type`, since these are runtime values `connectionHealth.ts` compares against, unlike every other export this package currently has, which are all types. `packages/shared/src/index.ts` re-exports them alongside its existing type exports. `staleness-signal.ts` and `connection-token-refresh.ts` are updated to import both constants from `@dipstick/shared` instead of declaring them locally — a small, mechanical change to two files this proposal otherwise does not touch. **Values and semantics do not change** (still `4000` and `4001`, still meaning exactly what SEC-25/SEC-26 defined them to mean); only their module of record moves. This document treats the proposal's "Consumed, not modified" framing (its Impact section) as still accurate at the semantic level — this change consumes the values and behavior, it does not alter what they mean — while clarifying here, without amending proposal.md itself, that the constants' physical location relocates to `@dipstick/shared` as a prerequisite.

This is a new prerequisite task, `tasks.md` Group 0 (task 0.1), ordered before Group 1 — specifically before task 1.10 (which references `REAUTH_GRACE_EXPIRED_CLOSE_CODE` by name) and task 1.9's grep (which needs a named exception to allow). Without this move, task 1.10 could only be implemented by re-declaring the literal `4001` (and `4000`) directly in the frontend module with a comment pointing at the backend source of truth — exactly the schema-drift risk this codebase's shared-types discipline exists to prevent: one side renumbers a close code during a future refactor, and the other silently stops matching, uncaught at build time.

**Alternative considered:** leave the constants in `packages/backend` and re-declare the literals in `connectionHealth.ts` with a comment. Rejected — this is precisely the "no shared symbol to catch drift" failure mode the Engineer review named, and the fix is cheap enough (two existing files, no behavior change) that there is no reason to accept the risk.

### D1c — `reauth-required` is a sticky, terminal state (race guards)

**Blocking finding from the Security design review (Tomás Ferreira).** D1a states that `unknown-reconnecting` and `reauth-required` "do not merge or fall through into each other" as an outcome. It did not state the mechanism enforcing this against events that arrive *after* the machine has already committed to one path — a real sequencing question for an event-driven WebSocket handler, not a hypothetical one. Two concrete races:

- **Race A:** a `reauth_required` message is processed (state → `reauth-required`), and a *subsequent* close event then fires — possibly carrying `STALE_SIGNAL_CLOSE_CODE` (4000), if a SEC-25 sweep tick and the SEC-26 grace expiry land on the same connection close together. Without an explicit guard, a naive handler could re-evaluate that later close and revert or re-derive `state`.
- **Race B:** a retry `setTimeout` scheduled during a prior `unknown-reconnecting` episode is still pending when a `reauth_required` signal arrives (on the same or a newly-reconnected socket). If entering `reauth-required` does not cancel that stray timer, it fires later, calls `connect()` again, and opens a new WebSocket after the user has already been told the fix is to log in — reopening exactly the "retry loop against a connection that can never succeed" outcome D1a exists to prevent.

**Decision:** `reauth-required` is a **sticky, terminal state for the lifetime of a given `useConnectionHealth` instance.** Once `state` is set to `reauth-required` (via either the message or the 4001 fallback):

1. Any pending retry `setTimeout` (from any prior `unknown-reconnecting` episode) is cleared synchronously, in the same tick that sets `state`, before that timer can fire — closing Race B.
2. No subsequent `close` or `error` event, of any code, is processed — the handler checks `state === "reauth-required"` first and returns immediately, before any other branching — closing Race A. This includes the socket's own eventual, expected 4001 close arriving after the message already moved the state (the normal SEC-26 sequence: message first, then grace-period close) — that close is a no-op, not a re-trigger, of a transition that already happened.
3. No further `connect()` call is ever made by this hook instance once `reauth-required` is entered. Recovery is exclusively the top-level page navigation described in D1a; nothing inside `useConnectionHealth` initiates or expects an in-place reconnect from this state.

`tasks.md` adds two tests to Group 1 (1.14, 1.15): (a) a `reauth_required` message followed by a close event carrying `STALE_SIGNAL_CLOSE_CODE` does not revert `state` away from `reauth-required`; (b) a pending retry timer from a prior `unknown-reconnecting` episode is cancelled the instant `reauth-required` is entered and never fires `connect()` afterward.

### D1d — `connect` is captured by reference, not re-invoked on identity change

**High-severity finding from the Engineer design review, incorporated directly.** `useConnectionHealth(connect: () => WebSocket)` will, at every realistic call site, receive an inline closure (`useConnectionHealth(() => new WebSocket(url))`). If the hook's setup effect lists `connect` in its dependency array — the naive, natural-looking implementation — every render of the host component produces a new `connect` reference, and since the hook's own state changes are themselves a re-render trigger for most consumers, the effect tears down and reconnects on close to every `connected` → `unknown-reconnecting` → `connected` cycle. This would pass a unit test that mocks `connect` as a stable `vi.fn()` and misbehave the moment it's wired to a real component (D9).

**Decision:** the hook stores the latest `connect` in a `useRef`, updated on every render via a ref-assignment effect with no cleanup, and the hook's *setup* effect (the one owning the socket lifecycle) has an empty dependency array (`[]`) — it reads `connect` through the ref at call time (initial connect and every retry), never re-running because `connect`'s identity changed. This is chosen over the alternative (require callers to pass a referentially-stable `connect` memoized with `useCallback`) because it is correct by construction for any caller, rather than depending on every future call site remembering to memoize correctly.

`tasks.md` adds a test (1.1b): mount the hook with a *fresh* `connect` closure supplied on every re-render (simulating a naive call site), and assert the hook does not tear down or reconnect the live socket as a result of `connect`'s changing identity alone.

### D1e — Message-stream ownership: `addEventListener`, never `.onmessage =`

**High-severity finding from the Engineer design review, incorporated directly.** `useConnectionHealth` returns `{ state, socket }`, and D1a requires the hook to inspect incoming messages for `{"eventType": "reauth_required"}`. D9's host components — and, out of scope here but inevitable once built, the real voting UI — need to read the socket's other message types (`vote_readiness_update`, `vote_revealed`, `session_state_change`, `topic_history_update`) off the same exposed socket. If the hook wires its own reauth-detection via `socket.onmessage = handler` (an assignment), any other code that also assigns `socket.onmessage` on the same socket silently replaces it, with no error and no warning.

**Decision:** the hook's internal message handling attaches via `socket.addEventListener("message", handler)`, never `.onmessage =`, specifically so it composes with any other `addEventListener("message", ...)` a consumer attaches to the same returned socket. The hook never calls `stopPropagation`/`stopImmediatePropagation` on a message it doesn't recognize — it reads what it needs and lets the event continue to any other listener.

`tasks.md` adds a test (1.1c): with the hook mounted and a second, independent `addEventListener("message", ...)` attached to the returned socket (simulating a future app-level consumer), assert both the hook's own reauth detection and the second listener each receive every message.

### D1f — WebSocket test double: hand-rolled `FakeWebSocket`, not jsdom's native implementation

**High-severity finding from the Engineer design review, incorporated directly.** Tasks 1.4, 1.6, 1.6a, 1.7, 1.8, 1.11–1.15, 3.2, 4.2a, 4.4–4.6, 4.10 all require forcing a `close`, `error`, or `message` event through the real hook and asserting on the resulting state. This is the first frontend WebSocket code in the repo — no `mock-socket` or `vitest-websocket-mock` is a devDependency today, and `vitest.config.ts`'s `jsdom` environment has no WebSocket-specific test setup.

A short spike (checked as part of this design pass) confirms `jsdom@29.1.1` does expose a global `WebSocket` constructor, but it is a real network client — it attempts an actual connection rather than behaving as a controllable double, which makes it unsuitable for deterministic, offline unit tests of retry timing and event sequencing.

**Decision:** build a small, hand-rolled `FakeWebSocket` test double, living in `packages/frontend/src/realtime/__tests__/fake-websocket.ts`, implementing exactly the surface `connectionHealth.ts` touches (`addEventListener`/`removeEventListener`, `close()`, `readyState`, the `CONNECTING`/`OPEN`/`CLOSING`/`CLOSED` constants) plus test-only methods to synthesize `open`/`close`/`error`/`message` events on demand. This keeps the retry-symmetry and cause-blindness tests deterministic with no real-network dependency in CI. New task, `tasks.md` 1.1a, ordered before task 1.4, since every test task in Group 1 depends on it existing.

### D1g — Unmount and teardown contract

**Medium-severity finding from the Engineer design review, incorporated directly.** Neither this document nor `tasks.md` previously specified what `useConnectionHealth`'s effect cleanup does. Two concrete failure modes follow from leaving this unspecified: (1) a participant navigates away mid-retry-loop, and the retry loop keeps running against an unmounted component, calling `setState` on nothing; (2) React 18 StrictMode's dev-mode double-invoke (mount → cleanup → mount) opens two real WebSocket connections against the backend's `ConnectionRegistry` if cleanup doesn't synchronously close the first socket before the second mount's effect runs.

**Decision:** the hook's cleanup function, unconditionally and regardless of current `state`: closes the live or in-flight socket; clears the pending retry `setTimeout` handle, if any; and clears the pending timing-floor `setTimeout` handle, if any (D3). This is the same synchronous-clear discipline D1c requires on entry to `reauth-required`, applied here to the more general case of the component going away entirely.

`tasks.md` adds a task (1.1d) with two tests: an unmount-mid-retry test (mount, force `unknown-reconnecting`, unmount before the retry fires, assert no further reconnect attempt or state update occurs); and a StrictMode double-invoke test (mount, unmount, remount in rapid succession, assert exactly one live socket exists at the end).

### D2 — Retry policy: one pure function, no cause input, `unknown-reconnecting` only

`computeRetryDelay(attempt: number): number` is a pure function taking only the retry attempt count — never the close code, never the outcome type of the failed attempt. Exponential backoff with full jitter: `min(30000, 1000 * 2^attempt)` as the upper bound, actual delay drawn uniformly from `[0, upperBound)`. No maximum attempt count — retries continue indefinitely at the 30-second-capped interval. This function, and the retry loop that calls it, apply only on the `unknown-reconnecting` path; `reauth-required` never calls it (Decision D1a).

This is the concrete mechanism behind proposal.md's retry-symmetry acceptance condition: `useConnectionHealth`'s `onclose`/`onerror` handler calls `computeRetryDelay(attempt)` and nothing else decides retry timing, for the 4000-close and raw-network-error/close cases. The handler does not read `event.code` for any purpose within this path — not to classify, not to log, not to branch — except the single D1a check that routes 4001 away from this path entirely before retry logic is reached. (See Risk 1 for the trade-off of retrying indefinitely against a connection that will always be rejected.)

**Jitter source (Engineer design review, incorporated directly):** the sole source of jitter is `Math.random()` — the function signature takes only `attempt` and excludes any RNG/seed parameter, so there is no argument surface through which a cause or a seed could leak or be injected. Tests control this ambient source via `vi.spyOn(Math, "random")` (a queued sequence of return values), not via a function-signature change. This is worth pinning down explicitly because the alternative someone might otherwise reach for — an optional second `rng` parameter "just for tests" — would quietly relax the "no cause input, attempt count only" contract this decision is built around, by giving the function a second parameter surface at all.

**Alternative considered:** a smarter strategy for ordinary flakiness (faster initial retry, since most network blips resolve in under a second). Rejected outright — `exploration-notes.md` §2 names this exact temptation as the most likely place this design gets quietly relaxed, and it is a disclosure regardless of how reasonable the UX motivation is.

**Second alternative considered (Engineer design review):** adopt an off-the-shelf reconnecting-websocket library instead of hand-rolling this. Rejected for the same reason — this design's disclosure-safety property depends on retry timing being byte-for-byte identical across causes, a guarantee a general-purpose library isn't built to provide and doesn't test for. Hand-rolling keeps full control over the one property that actually matters here.

### D3 — Timing floor: concrete value and enforcement

`STALENESS_TIMING_FLOOR_MS = 2000` (module-local constant in `connectionHealth.ts`, not exported for override). `useConnectionHealth` does not transition its reported `state` to `"unknown-reconnecting"` until at least this much time has elapsed since the triggering close/error event, even if the event itself fired instantly (the rejected-subscription case, which fails essentially instantly per `exploration-notes.md` §2).

2000ms is a development-time placeholder, following the same pattern as `CONTENT_TIMING_FLOOR_MS` in `timing-oracle.ts` (150ms, also a placeholder) — reused in *pattern*, not in module, per proposal.md bullet 18's explicit instruction, since that module solves a server-response-time problem for a different reason. Unlike `timing-oracle.ts`, this value is not gated by a production-deployment guard tied to a measured p95/p99, because the disclosure-safety property here does not depend on the specific value — only on its existence and uniform application (proposal.md bullet 18's two independent justifications: timing-leak prevention and visual-noise/facilitator-trust). The value is revisited as part of Priya Nair's usability-test commitment (Decision D11, `tasks.md` Group 6), not before a load test.

**Enforcement:** the constant is not read from `process.env`, a config file, or any feature-flag surface — matching the "not configurable" precedent `websocket-connection-reauthorization` set for `REAUTHORIZATION_INTERVAL_MS` (Decision D9a there). `tasks.md` task 7.3 confirms this by inspection, mirroring that change's own task 8.3.

### D3a — Early recovery before the timing floor elapses

**Clarification from the Engineer design review, incorporated directly.** Task 1.6, as originally scoped, covered "instant fail, floor holds" and "slow fail, same floor," but not the most common real-world case the floor exists to smooth over (proposal.md's own justification: "ordinary conference-room wifi flakes constantly") — a connection fails, the floor timer starts, and the connection successfully reconnects *before* the floor elapses.

**Decision:** a successful reconnect that completes before `STALENESS_TIMING_FLOOR_MS` has elapsed cancels the pending floor timer outright — `state` never flips to `"unknown-reconnecting"` for that episode at all, and no late, stale flash of the banner occurs after the user is already reconnected. This is D4's silent-recovery principle applied one step earlier: an interruption this fast is treated as invisible, not as a state transition that then immediately reverses.

`tasks.md` adds a test (1.6a): a connection fails, reconnects successfully before the floor elapses, and `state` is asserted to remain `"connected"` throughout — never observed as `"unknown-reconnecting"`.

### D4 — Silent recovery

When `state` transitions from `"unknown-reconnecting"` back to `"connected"`, `useConnectionHealth` emits nothing beyond the state value itself changing — no separate event, callback, or flag a consuming component could use to render a "reconnected" toast or transition treatment. A component that wanted to render one would have to synthesize it from the state change directly, and nothing in this design provides the hook to do so. This is the direct implementation of proposal.md's "recovery is silent" requirement: an explicit recovery signal that can only ever fire for the recoverable case would itself be a disclosure, since a revoked connection never produces one.

### D5 — Initial-connection failure folds into the same bucket

`useConnectionHealth`'s `connect()` call is made once at mount and again on every retry, with no distinction in the hook's internal state between "never had a good connection" and "had one, lost it." The very first failed connection attempt (a rejected subscription) drives `state` to `"unknown-reconnecting"` through the identical code path a mid-session drop would use — same timing floor, same retry function, same rendered treatment. There is no separate "couldn't connect" branch to accidentally invent, because the hook's internal transition logic has only one failure-handling path, entered from either the initial `connect()` or a reconnect attempt.

### D6 — Shared-module enforcement

`ConnectionStatusBanner.tsx` (participant, Decision D8) and the grid-marker treatment (Decision D7) both call `useConnectionHealth` directly — no wrapper, no per-surface re-implementation. `connectionHealth.ts` carries a header comment in the style of `staleness-signal.ts`'s, naming both issue #33 and issue #32 explicitly: *"This is the sole implementation of the connected/unknown-reconnecting/reauth-required state machine. Issue #33 must consume this module for its reauthorization-flow grid work, and issue #32 must consume its `reauth-required` state for the SEC-26 re-login UX — neither may fork it."* `tasks.md` task 2.2 makes the single-import requirement a checked code-review item, not just a comment, and files a PR-description note pointing both issues at this module.

### D7 — Grid marker signal source

The proposal (bullet 12, `exploration-notes.md` §5.3/§8.1) asks for a facilitator-only per-participant grid marker, bound to add at most one new visual state to the grid's baseline, introduce no new color/icon language beyond `disconnected`, and be cause-blind. It also states this change adds no new server-side signal and reuses the *same* shared module the participant view uses.

**Baseline correction (Propose review, Marcus Delgado, BA):** the grid's baseline is four states, not three — `connected+not-locked-in`, `connected+locked-in`, `disconnected_voted` (renders "ready" despite disconnection, preserving OR-1.3, per `redis-session-model.md:381,389`), and `disconnected_no_vote`. The proposal's earlier "existing three" count dropped `disconnected_voted`. The marker's "at most one new visual state" bound is measured against this corrected four-state baseline.

Those constraints together resolve the marker's signal source, even though the proposal does not spell out the mechanism: **the marker's underlying signal is the facilitator's own `useConnectionHealth` state — the health of the facilitator's own connection to the server — not an independently-tracked per-participant staleness flag.** When the facilitator's own connection enters `unknown-reconnecting`, the entire grid the facilitator is looking at may be behind (no new snapshot or `vote_readiness_update` can arrive over a dead connection), so the marker renders on every row simultaneously, clearing from every row simultaneously the instant the facilitator's own connection returns to `connected` (Decision D4's silent recovery, applied here too — no per-row "back to normal" flourish).

**Composition with `disconnected_voted`:** because the marker's signal is the facilitator's own connection health rather than any given row's state, it is driven independently of a row's readiness and overlays uniformly across all four baseline states, `disconnected_voted` included — it is not suppressed by a row already showing "ready." A row can legitimately show both "ready" (from `disconnected_voted`, per OR-1.3) and the marker (from the facilitator's own connection being stale) at once; these communicate different facts — the participant's last-known readiness, and the facilitator's confidence in currency of everything they're looking at, this row included — and neither overrides the other. OR-1.3's readiness indicator itself is unchanged by this design.

**Scoped to `unknown-reconnecting` only:** the marker's signal source is `useConnectionHealth`'s `unknown-reconnecting` value specifically, not `reauth-required` (Decision D1a). When the facilitator's own connection enters `reauth-required`, no grid-marker variant fires — the facilitator's client instead renders the same top-level `reauth-required` treatment (Decision D1a/D8) any client would, which supersedes the grid entirely (a facilitator who needs to log back in cannot usefully view a live grid regardless of markers). Introducing a second marker variant for this case would also breach the "at most one new visual state" bound above.

This reframes "per-participant" from the proposal's language as *per-row rendering of a single connection-level signal*, not *independently-computed per-participant staleness*. The reasoning:

- **No new server-side signal is available to compute genuine per-participant staleness beyond what already exists.** `connection_status` (`connected` / `disconnected_voted` / `disconnected_no_vote`, per `redis-session-model.md`) already reaches the facilitator for any cause of disconnection — including a raw network drop, a rejected subscription, or a force-expiry — and already renders as the existing `disconnected` grid state. A second, independently-computed "this specific participant might be stale" signal would require either a new server push (ruled out by proposal.md's Impact section) or a client-side heuristic (e.g., "no update seen for participant X in N seconds") that introduces exactly the kind of new per-participant timing surface §2's disclosure analysis warns against manufacturing.
- **Reusing the facilitator's own connection-health state is trivially cause-blind and requires zero new wire signal**, satisfying both binding constraints at once with no new attack surface.
- **It is literally the same module instance pattern already required by D6** — the facilitator's client runs one `useConnectionHealth` call for its own socket, exactly as the participant view does for its own socket. No divergence in shape between the two call sites.

**This is a Design-stage interpretation resolving an ambiguity the proposal left implicit, not a restatement of something the proposal already decided.** `tasks.md` task 4.1a asks Marcus Delgado and Priya Nair to confirm this reading before the grid-marker wiring task is considered done — a lightweight confirmation checkpoint, distinct in kind from the Decision D10 mock gate below (D10 is about visual register; this is about mechanism).

### D8 — Participant-facing rendered treatment

`ConnectionStatusBanner.tsx` renders one string per state — one for `unknown-reconnecting`, sourced from `useConnectionHealth`'s `state`, with no prop or code path that varies wording by *cause within* that state; and one for `reauth-required` (Decision D1a), likewise fixed regardless of the SEC-26 sub-cause. These are two different states rendering two different, fixed strings — not one state with cause-varied wording, which remains forbidden. Devon's and Priya's copy sketches from `exploration-notes.md` §5.2, plus the `reauth-required` placeholder from D1a, are wired in as placeholder text, explicitly marked non-final in a code comment referencing this document — see Decision D11 for the sign-off gate before any string is implementation-ready.

### D9 — Minimal host surface

No live-session page exists to mount these components against a real connection. This change adds the smallest surface that does: a participant-side host (wiring `useConnectionHealth` + `ConnectionStatusBanner` to a real session WebSocket) and a facilitator-side host (wiring the same hook + the grid-marker treatment to a stub row list sufficient for testing, not a feature-complete readiness grid). Building the full voting UI these will eventually live inside is explicitly out of scope (Non-Goals) — these hosts exist to make the acceptance conditions above testable end-to-end, including for issue #19, not to ship a usable live-session screen.

**Medium-severity finding from the Engineer design review, incorporated directly.** `packages/frontend/vite.config.ts`'s dev-server proxy currently has entries only for `/api` and `/auth`, both pointed at `http://localhost:3000`, with no `/ws` entry — and Vite's proxy requires an explicit `ws: true` flag per entry to upgrade and forward WebSocket connections at all. Without this, `npm run dev` cannot reach the backend's `/ws/sessions/:sessionId` route, which would block this decision's real-connection wiring from being verifiable in local dev (only against a built/served bundle talking to the backend directly). `tasks.md` adds task 5.1a to add a `/ws` proxy entry with `ws: true`.

### D10 — Grid marker visual register vs. color budget: deferred to a mock, not resolved here

Proposal.md's Open Design Question 1, restated because it is not resolved by anything above: Priya's instruction is a dimmed/hollow variant of the existing `connected+not-locked-in` state ("still connected, just uncertain"). The acceptance condition in proposal.md bounds new color/icon language to what the grid already uses for `disconnected`. These are two different existing states with two different implications for what a facilitator infers at a glance, and averaging them or picking one on this document's own authority would be exactly the silent-resolution the proposal explicitly warned against.

**This is not resolved in this design document.** It requires an actual mock — the marker rendered in the context of the grid's other four states, not prose — reviewed and signed off by Priya Nair. Until that sign-off exists, implementation may proceed on the *mechanism* (D7, D6, cause-blindness, at-most-one-new-state bound) using an intentionally neutral placeholder style, but the final visual treatment is gated. See `tasks.md` task 6.2 (Priya Nair's mock sign-off gate) and task 4.7 (implementation cannot ship final styling ahead of it).

### D11 — Copy sign-off gate

All three copy strings (`ConnectionStatusBanner`'s `unknown-reconnecting` string, its `reauth-required` string per Decision D1a, and the facilitator tooltip) are non-final pending Priya Nair's sign-off against actual layout — banner in context (both states), tooltip on the actual grid — per proposal.md bullet 25's filed-verbatim gate language. `tasks.md` Group 6 carries this forward as a named, checked gate, not a comment.

### D12 — Session-history / trend-continuity: declined, not deferred

Proposal.md's Open Design Question 2 (Priya's non-blocking flag that session history could someday note a stale-connection event) is not carried forward as scope here, including as a footnote to build later without scrutiny. A record tying connection-stability events to a named individual across sessions runs against the ritual's core constraint that session data must not be surfaceable in a way that allows comparison of individual engineers across teams or over time. This constraint does not soften because a single data point feels harmless. If this is ever pursued, it requires its own review against that constraint specifically, scoped at most to session-level unattributed aggregation ("a stale-connection event occurred during topic 3," no participant name) — never participant-level history. This design confirms the proposal's declination; `tasks.md` task 7.4 confirms by inspection that nothing in this change's implementation adds such a record.

## Risks / Trade-offs

- **[Risk] Indefinite retry against a connection that will always be rejected (a genuinely revoked participant's client retries forever at the 30-second-capped interval, never succeeding)** → **Mitigation:** this is required, not accidental — a retry cap or give-up state that differs by eventual outcome would itself leak cause once enough time passed (a "gave up" state that only a revoked connection ever reaches is the same disclosure as an explicit recovery event, mirrored). The participant-facing banner already tells the user to refresh; a user who does so re-authenticates through the normal flow rather than waiting on the retry loop. Documented here so it is not mistaken for a bug during implementation review.
- **[Risk] D7's grid-marker signal-source interpretation is a Design-stage inference, not something the proposal stated outright** → **Mitigation:** flagged explicitly as an interpretation (not silently treated as settled), with a lightweight confirmation checkpoint (`tasks.md` 4.1a) distinct from — and lower-weight than — the mock-gated D10 question.
- **[Risk] `STALENESS_TIMING_FLOOR_MS = 2000` is a placeholder, not measured data** → **Mitigation:** module-local, non-configurable (same discipline as the reauth change's interval constants), explicitly revisited as part of Priya Nair's usability-test commitment rather than shipped-and-forgotten.
- **[Risk] An engineer picking up issue #33 reasonably wants a second connection-health implementation tuned for the reauth grace-period case specifically** → **Mitigation:** `connectionHealth.ts`'s header comment names #33 directly, and `tasks.md` task 2.2 makes non-forking a checked review item, not a comment-only convention.
- **[Risk] The minimal host surface (D9) scope-creeps into a de facto live-session page during implementation** → **Mitigation:** Non-Goals states this explicitly; `tasks.md` Group 5 scopes the host components to exactly what the acceptance tests require.
- **[Risk] A 4001 close or `reauth_required` message, unhandled, would silently fall into `unknown-reconnecting` and retry forever against a connection that can never succeed** → **Mitigation:** this was the blocking finding at Propose review (Marcus Delgado, BA) against the proposal's original two-state framing. Resolved by Decision D1a: `reauth-required` is a third, legitimately-disclosed state with its own detection and no-retry behavior, not a fold-in. `tasks.md` task 1.10 tests that this signal never reaches the retry path.
- **[Risk] An engineer picking up issue #32 reasonably wants a second connection-health implementation tuned for the reauth-required UX specifically, mirroring the #33 risk above** → **Mitigation:** `connectionHealth.ts`'s header comment names #32 directly alongside #33 (Decision D6), and `tasks.md` task 2.2's non-forking review item covers both.
- **[Risk, recorded per Security design review Finding 2] The raw WebSocket close code remains visible to the affected client via browser DevTools' Network/WS inspector, independent of anything this state machine does.** `STALE_SIGNAL_CLOSE_CODE` (4000) is a real, distinct application-level code, not the browser's generic `1006` abnormal-closure code a genuine network death produces — anyone inspecting the wire, most relevantly the affected participant themselves, can read it directly, bypassing this design's carefully-symmetric JS-layer handling entirely. **Mitigation: none available at this layer** — this is a channel client-side application logic structurally cannot close, because it operates beneath the JS layer this design controls. Remediation, if pursued, belongs to the two backend changes that chose 4000/4001 (`websocket-delivery-time-authorization`, `websocket-connection-reauthorization`), not here. Recorded so it isn't silently assumed away, and as a forward pointer for whoever picks up issue #32 or #33, since both inherit the same limit.
- **[Risk, recorded per Security design review Finding 3] `websocket-connection-reauthorization`'s fixed, non-jittered `REAUTHORIZATION_INTERVAL_MS` (5 minutes, `connection-reauthorization.ts:25`, `setInterval`-based) is an observer-side correlation channel this client design cannot address.** This document's timing-floor and retry-symmetry work defeat *per-event* timing analysis, but a fixed five-minute sweep cadence is itself a signal external to this module: a disconnect that recurs at consistent five-minute-multiple offsets from connection start is statistically distinguishable from one that doesn't, by an observer doing arithmetic on wall-clock timestamps they already have (banner history, grid-marker on/off transitions) — no close-code inspection required. **Mitigation: none available here** — the interval lives in a different codebase, and jittering it is a backend decision with its own trade-offs (it would perturb the reveal-timing-independence guarantees `websocket-connection-reauthorization` established). Recorded as a forward-pointing note for a future reviewer of that change, or of issue #33, referencing the interval constant directly so the observation isn't rediscovered from scratch.

## Migration Plan

This is a purely additive frontend change — no backend change, no data migration, no existing client behavior to preserve (there is no existing WebSocket client). Sequencing, matching `tasks.md`'s group order:

1. `connectionHealth.ts` — module and its unit tests (state machine, timing floor, retry policy, silent recovery, initial-connection-failure bucketing, `reauth-required` detection and no-retry behavior per Decision D1a). No UI dependency; can be fully verified in isolation.
2. `ConnectionStatusBanner.tsx` plus the retry-symmetry, `reauth-required` no-retry, and banner-identity tests.
3. The facilitator grid-marker treatment, wired to D7's signal source, with placeholder styling (D10) and its cause-blind/lifecycle tests.
4. Minimal host surfaces (D9) sufficient to run these against a real session WebSocket, unblocking issue #19's E2E coverage.
5. Priya Nair's copy sign-off (D11) and visual-register mock sign-off (D10) — can proceed in parallel with steps 1–4, but must both complete, along with the usability test, before Group 6's pilot-readiness gate closes.

**Rollback:** revert the frontend deploy. Nothing server-side changes, so rollback carries no data or session-state risk. Per the gate carried forward from `websocket-delivery-time-authorization` task 9.3, this capability may go live in a non-pilot/staging environment before the Group 6 gate closes — it must not be used for a real pilot team's first live session until it does.
