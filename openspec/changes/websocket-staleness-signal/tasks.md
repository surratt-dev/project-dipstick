## 1. Shared Connection-Health Module (Core State Machine)

**No dependencies. Everything else in this change consumes this module (design.md Decision D1/D6).**

- [ ] 1.1 Create `packages/frontend/src/realtime/connectionHealth.ts`, exporting `type ConnectionHealthState = "connected" | "unknown-reconnecting" | "reauth-required"` and `useConnectionHealth(connect: () => WebSocket)`. Header comment names both issue #33 and issue #32 explicitly as required consumers, not forkers, of this module (design.md Decision D6, mirroring `staleness-signal.ts`'s header-comment convention).
- [ ] 1.2 Enforce no fourth state: TypeScript exhaustiveness (no `default` case anywhere `ConnectionHealthState` is switched on) plus a compile-time regression test that fails if a fourth value is added.
- [ ] 1.3 Implement `computeRetryDelay(attempt: number): number` as a pure function taking only the attempt count — full-jitter exponential backoff, `min(30000, 1000 * 2^attempt)` upper bound, uniform draw from `[0, upperBound)` (design.md Decision D2). No branch anywhere in this function or its caller reads `event.code` or any connection-attempt outcome type. This function is reachable only from the `unknown-reconnecting` path, never from `reauth-required` (task 1.10).
- [ ] 1.4 **Retry-symmetry test (proposal.md acceptance condition, spec.md scenario "A revoked connection and a flaky connection produce identical retry timing"):** force a `STALE_SIGNAL_CLOSE_CODE` close and, separately, a simulated raw network close/error, through the same `useConnectionHealth` handler; assert identical retry count, backoff schedule, and jitter draw sequence (seed the jitter source for determinism) for both.
- [ ] 1.5 Add `STALENESS_TIMING_FLOOR_MS = 2000` as a module-local constant (design.md Decision D3) — not read from `process.env`, a config file, or any feature-flag surface. Wire it into `useConnectionHealth` so the reported `state` does not flip to `"unknown-reconnecting"` until at least this long after the triggering close/error event. The floor does not apply to `reauth-required` (task 1.10) — that transition is not ambiguous the way a close/error event is, so there is no cause-leak reason to delay it.
- [ ] 1.6 **Timing-floor test:** an instantly-rejected subscription attempt does not surface `"unknown-reconnecting"` before the floor elapses; a slower-failing network drop is held to the identical floor via the identical code path (spec.md "An instantly-failing rejected subscription does not render before the floor elapses" / "The floor applies identically to a slower-failing network drop").
- [ ] 1.7 **Initial-connection-failure bucketing test (design.md Decision D5):** a rejected first-ever subscription attempt (no prior successful connection) drives `state` to `"unknown-reconnecting"` via the same code path, same timing floor, and same retry function as a mid-session drop — assert no separate internal branch or state exists for "never connected" vs. "lost connection."
- [ ] 1.8 **Silent-recovery test (design.md Decision D4):** transitioning from `"unknown-reconnecting"` back to `"connected"` produces no event, callback, or flag beyond the state value itself changing — assert no additional signal is observable to a consumer.
- [ ] 1.9 Code-review checklist item, backed by a grep-based regression test: no reference to `STALE_SIGNAL_CLOSE_CODE`, `.code ===`, or any close-code/outcome-type comparison exists anywhere in `connectionHealth.ts` or its retry/render call sites, **except** the single, named `REAUTH_GRACE_EXPIRED_CLOSE_CODE` check that routes to `reauth-required` (task 1.10, design.md Decision D1a) — the grep/review rule allows exactly this one exception and no other close-code or outcome-type comparison.
- [ ] 1.10 **`reauth-required` detection (design.md Decision D1a):** wire `useConnectionHealth` to recognize the in-band `{"eventType": "reauth_required"}` message and, as a fallback, a raw close with `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (4001), transitioning `state` to `"reauth-required"` from either. This path bypasses the timing floor (task 1.5) and never calls `computeRetryDelay` (task 1.3) or enters the retry loop.
- [ ] 1.11 **`reauth-required` no-retry test (proposal.md acceptance condition, spec.md scenario "A 4001 close or a `reauth_required` message never enters the retry path"):** force a `REAUTH_GRACE_EXPIRED_CLOSE_CODE` close and, separately, a `reauth_required` message, through the same `useConnectionHealth` handler; assert `state` becomes `"reauth-required"` in both cases and `computeRetryDelay` is called zero times.
- [ ] 1.12 **No-fallthrough test:** assert `"reauth-required"` is never reached via a `STALE_SIGNAL_CLOSE_CODE` close or a raw network close/error, and `"unknown-reconnecting"` is never reached via a `reauth_required` message or a `REAUTH_GRACE_EXPIRED_CLOSE_CODE` close — the two paths do not merge.
- [ ] 1.13 **`reauth-required` sub-cause-blindness test:** assert `useConnectionHealth` exposes no information distinguishing why the SEC-26 refresh failed (retry-budget exhaustion vs. definitive revocation vs. concurrent session destruction) beyond the single `"reauth-required"` state value, matching the reauth spec's own non-disclosure of that sub-cause.
