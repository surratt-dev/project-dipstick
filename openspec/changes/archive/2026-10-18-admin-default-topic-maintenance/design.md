# Design: admin-default-topic-maintenance (#216)

*Devon Calloway (Internal Champion); revised by Ingrid Sollenberger (Solution Architect) after the engineer and security design reviews (`design-review-engineer.md` R1 to R7 plus smaller findings; `design-review-security.md` S1 to S6 plus smaller items). "Review dispositions" at the end lists what was accepted, recorded or rejected. Mechanism below is engineering's; the decisions D1 to D14 are the exploration's (`exploration-notes.md` section 9) and are not reopened here. Vocabulary: MUST is a testable requirement; LEAN is a preference this design either adopts or overturns with a written reason.*

## Context

The twelve defaults are rows of the sentinel team `__default_topics__` (`team_id = 00000000-0000-0000-0000-000000000001`). `copyCanonicalDefaults` (`sessions/default-topics.ts`) copies the active `is_default` rows into each new team in a single `INSERT ... SELECT` statement, renumbering positions 1..n. Today nothing writes those rows except migrations. #188 made every team-scoped topic route answer `404 TEAM_NOT_FOUND` for the sentinel; #215 declined a write trigger on condition that #216 delivers one audited writer and reconsiders. This change adds that writer.

## Goals / Non-Goals

**Goals**
- Admins can add, edit, archive, restore and reorder template defaults and read the template with its archived rows and history, without a migration.
- Every successful write is audited atomically with full before and after values.
- The #188 guard and its structural test, the first-session lock and the live-session path are untouched.
- A template write can never leave the template in a state that breaks team creation.

**Non-Goals (each declined or deferred; see proposal)**
- No screen (D6). No propagation to existing teams. No reset-to-factory. No undo or revert operation. No draft/publish state. No notification of facilitators. No semantic filter on prompt text. No fix to restore-returns-old-wording or the `defaultTopicsNotActive` name join (D11, follow-up issues).
- No migration. No change to `checkWritableTeam`.

## Decisions

### E1. Routes (D10)

All under `/api/v1/admin/default-topics`. No path or body field accepts a team id; the template is implicit, and the sentinel id is never accepted as input. Topic ids in paths are template row ids only.

| Operation | Route |
|---|---|
| List (with archived) | `GET /api/v1/admin/default-topics` |
| Add | `POST /api/v1/admin/default-topics` |
| Edit | `PATCH /api/v1/admin/default-topics/:topicId` |
| Archive | `POST /api/v1/admin/default-topics/:topicId/archive` |
| Restore | `POST /api/v1/admin/default-topics/:topicId/restore` |
| Reorder (whole list) | `PUT /api/v1/admin/default-topics/order` |
| Audit history (D13) | `GET /api/v1/admin/default-topics/history` |

Seven routes (six operations plus the history read). **Success statuses:** add `201`; edit, archive, restore, reorder (including no-ops) `200`; both GETs `200`. The history route is kept as the sole recovery path (proposal, "Why the history endpoint stays").

`order` is registered as a static segment, so it never collides with `:topicId`. The mirror of TOPIC-003..006 shapes is deliberate so the follow-up screen can reuse patterns.

**Why this satisfies #188.** The structural test selects routes matching `^/api(/v\d+)?/teams/:[^/]+/topics` plus `EXTRA_IN_SCOPE_ROUTES` (today `GET /api/join/:token`, `GET /auth/callback`). `/api/v1/admin/default-topics*` matches neither, so the test is unchanged and `EXTRA_IN_SCOPE_ROUTES` is not edited. Task 4.6 adds a guard test that fails if any `admin/default-topics` route ever gains a `:teamId` segment; it enumerates routes with the same `onRoute` mechanism the #188 test uses. The plugin is registered in `register-routes.ts`, the single registration point; the session auth middleware applies by default (only `PUBLIC_ROUTES` bypass it), so no extra `onRequest` wiring exists.

**Request limits (security).** Each of the five body-carrying routes sets an explicit `bodyLimit` of 16 KiB (the largest legitimate body is a 800 + 400 + 60 code-point text set, which is under 5 KiB even fully `\uXXXX`-escaped, or 15 ids). Bodies must be `application/json`; Any other media type is refused with `415` (As built: Fastify 5 parses `text/plain` by default, so the route layer checks the media type itself; see "As built"). For `PUT .../order` the array length is checked (`> MAX_ACTIVE_DEFAULTS` is `422 INVALID_DEFAULT_ORDER`) before any per-element validation or query.

**Alternative rejected: single whole-set `PUT`.** Attractive for invariants, but a whole-set replace makes it easy to drop a topic by omission and makes the audit diff hard to read. Reorder alone is whole-list, as in TOPIC-006.

### E2. Authorization and check order (D2 of #200 model, own 403 code)

Model: `checkAssignDefaultsAuthorization` in `routes/topics.ts`, not the TOPIC-003..006 wrapper. Role is read live from `users.global_role`; `isApplicationAdmin(role)` is the only predicate. A `global_role` of `application_admin` is necessary and sufficient. Membership is irrelevant and is not consulted.

Order (stops at first failure):

1. Session authentication (`authMiddleware` `onRequest`): `401`.
2. Role: `403 DEFAULT_MAINTENANCE_ADMIN_ONLY`, `category: forbidden`, standard envelope. A code distinct from `NOT_AN_ADMIN` and `NOT_A_FACILITATOR`. Denial audit `topic.default_maintenance_denied` (`team_id` null, metadata method plus the route **template**, never the raw URL), fail-open, bounded per actor through `admitDenialAudit` (`DENIAL_AUDIT_LIMIT = { limit: 10, windowMs: 60000 }`: the 1st to 10th denial per actor per 60-second window write a row, the 11th does not; beyond the bound a log-only `topic.denial_audit_suppressed` event carrying the route family and the running suppressed count for that actor and window, so a burst is distinguishable from a trickle). Applies to all seven routes, reads included. The denial seam is **parameterized** (an `endpoint` / family label argument; the existing `auth/assign-defaults-audit.ts` hard-codes `ASSIGN_DEFAULTS_ENDPOINT` in its log events), a new thin module reusing `admitDenialAudit` and `fail-open-topic-audit`, not a copy of assign-defaults. Known blind spot, accepted: when the limiter store errors the shared seam writes no row and no per-denial event, so denial auditing for this family is blind during a Redis outage (the same outage fail-closes the write limiter with `503`). The seam emits one log event per actor per window in that state so the blindness is itself visible.
3. Non-canonical `:topicId` (anything other than 8-4-4-4-12 lowercase-or-uppercase hex): `404 DEFAULT_TOPIC_NOT_FOUND`, no query.
4. Shared topic-write rate limit for the five write routes (not for the two GETs): `429` or fail-closed `503`, exactly as TOPIC-003..008. `TopicWriteDenialContext` requires a `teamId` and an `attemptedOperation`: the sentinel id is passed as `teamId` (the limiter's breach audit row and log then carry the sentinel, and its `team_verified: false` metadata stays as is) and `attemptedOperation` is the maintenance operation name.
5. Body and field validation (`422`), before any database work.
6. One transaction: `lockTeamTopics(client, SENTINEL)`, target lookup (`404`), state checks (`409` / `422`), the write, the invariant check, the audit INSERT, COMMIT.

The timing floor is applied on every return, as for assign-defaults, through `applyTimingFloor(startTime)` from `content/timing-oracle.ts`. `TIMING_FLOOR_MS` is module-private there; the exported constant is `CONTENT_TIMING_FLOOR_MS` (currently 150 ms, a placeholder whose measurement issue #305 owns). This change adds no value; tests read `CONTENT_TIMING_FLOOR_MS` from the real module (several existing unit tests mock the module as `{ applyTimingFloor, CONTENT_TIMING_FLOOR_MS: 150 }`; tests of this family that assert the floor must not use that mock). The floor covers the whole 403 path including the denial write; it only reduces role-probing signal and #305 owns verification.

### E2a. Cross-origin, CSRF, trust assumptions (security S3, S4, and platform reliance, stated rather than discovered)

- **CSRF.** There is no CSRF token in the app and none is added. The inherited controls are: the session cookie is `sameSite: "strict"` (`app.ts`); CORS allows only the configured origin list (`getAllowedOrigins()`), with no wildcard and no permissive rule added for `/api/v1/admin`; and every body-carrying route requires `application/json` (a `text/plain` or form-encoded request gets Fastify's `415` and changes nothing). The bodyless `POST .../archive` and `.../restore` carry no body to type-check. **As built (security read S-A):** every mutating route in the family (add, edit, archive, restore, reorder) additionally requires the request header `X-Requested-With: dipstick`, checked in the same `preParsing` hook right after the role check (a non-admin still gets the role 403 first; a missing or wrong value is `403 MUTATION_CONTROL_HEADER_REQUIRED` in the envelope, with the timing floor and without echoing the received value). A cross-origin simple request cannot carry a custom header without a CORS preflight, and the preflight is granted only to the allow-listed origin (`app.ts` `allowedHeaders` now includes `X-Requested-With`). No such header convention existed in the app (the frontend client sets only `Content-Type`), so this is the first; the future template screen must send it. GET routes need no header. The server still does not check `Origin`, and SameSite=Strict remains a defence in depth, not the only control.
- **Client address.** `actor_ip` is `request.ip` under `trustProxy: 1`, correct only when exactly one trusted proxy fronts the app. If a client can reach the app directly or through two proxies the field is spoofable. This is the existing platform assumption; it is stated here because this is the first audit trail where admin forensics may depend on it.
- **Role TOCTOU.** The role is read at step 2 and the transaction starts at step 6. A demoted admin can complete one in-flight write and the audit row records the role read at step 2. A millisecond window; accepted in writing (re-reading with `FOR SHARE` was considered and declined as not worth the lock).
- **How `application_admin` is granted.** `users.global_role` is mapped from the IdP role claim on every sign-in (`auth/account-resolver.ts`); there is no admin-grant UI or DB flag workflow in this application. The claim is therefore trusted for a more powerful action than before (global content) and the IdP group-assignment process is now part of this control. Documented in `docs/deployment.md` and the threat model (tasks 8.6, 7.2, 10.1). Deactivated or deleted users are rejected by the existing session middleware, which this change relies on and does not alter.
- **Audit tamper resistance is an assumption.** `lastChangedAt/By` and the sole recovery path depend on `audit_log` being trustworthy, and the application's database role is not known to be denied UPDATE and DELETE on it. This design claims no tamper evidence it does not have: audit integrity relies on database access control (documented in the threat model and runbook). Revoking UPDATE/DELETE from the application role, with redaction done through a separate privileged role, is the right hardening but is a database-role change that belongs to its own change (declined here, see Review dispositions).
- **Single-admin control.** A template write needs one `application_admin` and no second approver; a compromised admin session can rewrite all fifteen prompts that every future team sees. Accepted for the first release (recorded in the proposal) and mitigated by detection, E5's structured log event, not by prevention. Reopen if the number of administrators grows beyond a handful, or after any incident.

### E3. One audited writer (the second-writer rule)

New module `packages/backend/src/sessions/default-topic-maintenance.ts` exports `writeTemplateTopics(op, actor, input)` and nothing else that writes. It is the only non-migration code that executes `INSERT`, `UPDATE` or `DELETE` against `topics` with the sentinel id. It runs the six-step transaction of E2 item 6 through `withAuditTransaction(domainWrite, auditInsert)`:

- `domainWrite`: first `SET LOCAL lock_timeout = '3s'` and `SET LOCAL statement_timeout = '10s'` (transaction scoped; `withAuditTransaction`'s own `SET LOCAL statement_timeout` covers only the audit INSERT, and `lockTeamTopics` otherwise waits indefinitely, so one stuck transaction would block all maintenance writes; team creation takes no such lock and is unaffected), then `lockTeamTopics` on the sentinel (and only the sentinel: it never locks a real team, E8), re-read the template inside the lock, apply the operation (setting `updated_at = now()` on every row it touches, including renumbered rows, as the TOPIC-003..006 handlers do), then run the post-write invariant backstop (E6). The backstop's scope and failure behavior are defined in E6; pre-existing template damage is not allowed to wedge maintenance.
- `auditInsert`: exactly one `audit_log` row (E5), unless the operation was a no-op, in which case none (the closure decides, as `withAuditTransaction` already supports).
- An audit failure rolls the domain write back (`AuditWriteError`) and no success row exists. This is the transactional discipline #215 required for "no silent drift".

**Error mapping (every outcome has a defined response; no raw driver or stack text ever reaches a body).**

| Outcome | Response | Log |
|---|---|---|
| typed domain / validation errors | the E4 table statuses and codes | none above `info` |
| `AuditWriteError` | `500`, existing generic envelope with `correlationId`; no success row; write rolled back | `error` |
| invariant backstop failure (E6) | `500`, generic envelope with `correlationId`; rolled back | `error` carrying the `InvariantId` |
| Postgres `23505` unique violation (positions index; should be unreachable under the lock) | `500`, generic envelope; rolled back | `error` carrying the constraint name |
| lock timeout (`55P03`) or statement timeout (`57014`) | `503 DEFAULT_MAINTENANCE_BUSY`, "Another change to the default topics is in progress. Try again in a moment." with `Retry-After: 3`; nothing changed | `warn` |
| any other unexpected error | `500`, generic envelope | `error` |

### E4. Validation and limits (D7, D2)

Fixed constants in `default-topic-maintenance.ts`, not configuration, not environment: `MAX_ACTIVE_DEFAULTS = 15`, `MIN_ACTIVE_DEFAULTS = 1`, `NAME_MAX = 60`, `PROMPT_MAX = 400`, `DESCRIPTION_MAX = 800`. Length is counted in Unicode code points after trim, with `[...s].length` (never `.length`, which counts UTF-16 units); tests include an astral-plane character at the boundary. The stored value is the trimmed string. All comparisons (name uniqueness, no-op detection) run **in JavaScript over rows read inside the lock**, never SQL `lower()`, so they cannot disagree with the application on non-ASCII names. Name uniqueness has no database backstop: it is enforced in code under the advisory lock, which serializes every sanctioned writer; a manual SQL edit or a second writer would defeat it, and E11's structural test is what covers the second writer. Add has no idempotency key by design: a double-submit is caught by `DEFAULT_NAME_DUPLICATE`, and that is the intended guard so nobody "fixes" it with a key. No Unicode normalization (consistent with the #218 name rule: `trim().toLowerCase()`, no locale; "E" and "e-acute" differ, NFC and NFD differ; recorded so nobody fixes it unilaterally).

**Seed verified against the limits** (task 3.2 repeats this as a test): the twelve rows of migration 11 have names 7..36, prompts 25..61, descriptions 181..262 characters, all plain text with no `<`, `>`, URLs or control characters. All pass. No limit was raised and no seed edited.

Plain text: `name`, `prompt` and `first_session_description` are rejected with `PROMPT_FORMAT_INVALID` (and `field`) if they contain: an HTML-tag-like sequence (`<` followed by a letter, `/` or `!`), an HTML entity (`&name;` or `&#...;`), a URL (`http://`, `https://`, `www.`), a Markdown link or image (`](`), or any character in Unicode category **Cc or Cf** (this includes `U+0000`, which would also break a `jsonb` audit insert, bidi overrides U+202A to U+202E and U+2066 to U+2069, zero-width U+200B to U+200D, and the BOM), or a lone surrogate (`name` and `prompt` also reject line breaks; the description allows `\n` and no other Cc/Cf character). The guard is deliberately narrow so it can be tested exhaustively; it is not a content filter (E9) and not the XSS control. **The XSS control is output encoding, a MUST (E4a).**

| Failure | Status | Code |
|---|---|---|
| required field missing or blank after trim | 422 | `DEFAULT_FIELD_REQUIRED` (+ `field`) |
| over length | 422 | `DEFAULT_FIELD_TOO_LONG` (+ `field`, `max`) |
| markup, URL, control character | 422 | `PROMPT_FORMAT_INVALID` (+ `field`) |
| `voteType` not one of `finger`, `roman`, `modified_roman` | 422 | `DEFAULT_VOTE_TYPE_INVALID` |
| `voteType` present on edit and different from stored | 422 | `DEFAULT_VOTE_TYPE_IMMUTABLE` (D2) |
| `voteType` present on edit and equal to stored | accepted, ignored | |
| name equals (trim, lowercase) the name of another active template row (the edited row itself is excluded) | 409 | `DEFAULT_NAME_DUPLICATE` (on restore, names the conflicting active default: `conflictingTopicId`, `conflictingName`) |
| `limit` on history is 0, negative, non-integer or non-numeric | 422 | `INVALID_HISTORY_LIMIT` |
| add or restore would exceed 15 active | 409 | `TEMPLATE_AT_CAPACITY` |
| archive would leave zero active | 409 | `LAST_ACTIVE_DEFAULT` |
| reorder list is not exactly the active ids | 409 | `REORDER_ID_MISMATCH` (+ `current`: the active list to reload) |
| reorder body malformed, longer than 15, or contains duplicates | 422 | `INVALID_DEFAULT_ORDER` |
| unknown or non-template topic id | 404 | `DEFAULT_TOPIC_NOT_FOUND` |
| lock or statement timeout (E3) | 503 | `DEFAULT_MAINTENANCE_BUSY` |
| edit of an archived default | 409 | `DEFAULT_ARCHIVED` ("restore it first") |
| archive of an archived / restore of an active default | 422 | `DEFAULT_ALREADY_ARCHIVED` / `DEFAULT_ALREADY_ACTIVE` |

Every rejection writes no success audit row and changes nothing. Error bodies carry the `field` name and, where relevant, `max`, **never the rejected value** (`PROMPT_FORMAT_INVALID` does not echo the offending substring), so admin-controlled text is not reflected into responses or logs; tested.

**Mass assignment.** Handlers pick `name`, `prompt`, `firstSessionDescription` and `voteType` from the body; they never spread it. A test sends `teamId`, `team_id`, `status`, `isDefault`, `displayOrder`, `archivedBy`, `archivedAt` and `id` on POST and PATCH and asserts no effect. The audit `metadata.topicId` and every id in a reorder list are taken from the **database row** (lowercase canonical), never from the request path or body, so a mixed-case id cannot make the `lastChangedAt` derivation (E5) miss its row; tested with an uppercase path id.

**Check order inside the transaction.** Validation (422) always precedes state checks (409), so an add that is both invalid and at capacity answers `422`. Restore: target lookup (404), already active (`422 DEFAULT_ALREADY_ACTIVE`), capacity (`409 TEMPLATE_AT_CAPACITY`), name collision (`409 DEFAULT_NAME_DUPLICATE`). Edit: lookup (404), archived (`409 DEFAULT_ARCHIVED`), field validation and vote type (422; validation runs before the transaction per E2 item 5), name duplicate (409). For the reorder body the array length (> 15) and element type checks run before any per-element or database work. Two simultaneous failures therefore always give one defined answer.

**Name duplicate excludes the row itself.** The comparison is against the other active rows only. PATCH "Pairing" to "pairing" or " Pairing " on the same row is not a duplicate: " Pairing " trims to the stored value (a no-op), "pairing" differs byte for byte (a real change, audited).

**Plain-text rule, exact.** `<` is rejected only when followed by a letter, `/` or `!`. Allowed: "rate < 5", "a <3 b", "x<5" (digit, space or end after `<`). `&` is rejected only as an entity (`&name;` or `&#digits;`/`&#xhex;`). Allowed: "Dev & Ops", "R&D" (no terminating `;` entity form). URLs are `http://`, `https://`, `www.` (case-insensitive). Unknown top-level body keys are ignored (as TOPIC-003). The name-uniqueness comparison and the capacity check run inside the lock, after a fresh read. *Edit of an archived default is refused* (my addition, not in the notes): allowing it would let an archived row's name collide with an active one and make a later restore fail on a surprising rule. Flagged for BA ratification; the cost of overturning is one branch.

A topic id that names a real team's topic is indistinguishable from a nonexistent id (`404`): the lookup is `WHERE id = $1 AND team_id = SENTINEL`, so the endpoint cannot be used to probe other teams.

### E4a. Template text is inert data (security S5)

**MUST.** Template text (`name`, `prompt`, `first_session_description`, and the audit `before`/`after` and history copies of it) is stored and transported as inert data, and **every consumer renders it as text**: no raw-HTML sink (`innerHTML`, `dangerouslySetInnerHTML`), no Markdown renderer, no auto-linker, no un-escaped interpolation in email or export. This is the real control; the E4 format guard is a denylist and does not claim otherwise (it misses `javascript:` strings without `://`, full-width `＜`, and the like, which is harmless only if this MUST holds). At the time of review the frontend has no raw-HTML sink in source and React escapes by default; no Markdown renderer exists (the `](` rule is a precaution against a future one). Consumers include WebSocket payloads, session snapshots (`session_topics.topic_name`), reports and the history response. Verification is a task checklist item (4.12): grep every consumer of those columns for such sinks and record the result; the follow-up screen issue must carry the same requirement.

### E5. Operations and audit content (D3)

All five writes return the full refreshed list (E7) plus the scope statement, so the admin never works from a stale view.

- **Add.** New row: `is_default = true`, `status = 'active'`, `display_order = MAX(active display_order) + 1` (equal to N+1 on a healthy template; using the active count instead would collide on the unique index, `23505`, against a gapped template). Every operation that changes active membership (add, archive, restore) ends by normalizing the active rows to dense 1..N in their current relative order (negate-then-set, only when they are not already dense), so a pre-existing gap is repaired by normal use rather than wedging maintenance (E6). Required: name, prompt, voteType, firstSessionDescription.
- **Edit (`PATCH`).** Editable: `name`, `prompt`, `firstSessionDescription`. **No-op, defined:** after trim, every supplied editable field equals the stored value byte for byte (case and internal whitespace count; no normalization). A no-op is `200`, `unchanged: true`, unchanged resource, no audit row. An empty body `{}` (or a body with only ignored keys, or only an equal `voteType`) supplies no editable field and is a no-op `200`; no new error code. **Atomicity:** a multi-field PATCH is all-or-nothing; if any supplied field is invalid, none is applied (validation precedes the write). A PATCH where some fields change and others equal stored changes only the differing ones and `changedFields` lists only those. A rename's response carries `notice`, exactly: "Renamed. Existing teams' topics are not renamed, and name-based matching for existing teams (restoring a default topic, and the defaultTopicsNotActive list) will no longer pair them with this default."
- **Archive.** Sets `status = 'archived'`, `archived_at`, `archived_by`; refused with `LAST_ACTIVE_DEFAULT` if it would leave zero active. Remaining active rows are renumbered dense 1..N with the negate-then-set two-step (TOPIC-006). The archived row keeps its old `display_order` (not meaningful, outside the partial unique index).
- **Restore.** Returns the original template row to active at `MAX+1` (N+1 when healthy; TOPIC-005 semantics), sets `restored_by`/`restored_at`, refused in the order `DEFAULT_ALREADY_ACTIVE` (422), `TEMPLATE_AT_CAPACITY` (409), `DEFAULT_NAME_DUPLICATE` (409, naming the conflicting active default). Because archived rows cannot be edited (E4), an admin resolves a collision by renaming or archiving the conflicting active default, then restoring. After restore the position is N+1, never the row's old number; an archived row's old `display_order` never blocks the partial unique index (outside it).
- **Reorder.** `PUT .../order` with `{ order: [id, ...] }`, whole list, exactly the active template ids. Negate-then-set. A list identical to the stored order is a no-op: 200, no audit row. Edge cases: a list of one when exactly one default is active is a no-op `200`; an empty list is `422 INVALID_DEFAULT_ORDER`; a list of the right length with a repeated id is `422 INVALID_DEFAULT_ORDER`; a list containing an archived id is `409 REORDER_ID_MISMATCH`; a stale list with the same id set is accepted (see E8).

**Audit row** (transactional, one per successful, non-no-op write):

| Column | Value |
|---|---|
| `operation` | `topic.default_added` / `_edited` / `_archived` / `_restored` / `_reordered` |
| `team_id` | the sentinel (precedent: migration 23's `team.template_cleanup`) |
| `actor_user_id`, `actor_global_role`, `actor_ip` | as for other audited topic writes (`actor_ip` = `request.ip`, subject to the `trustProxy: 1` assumption in E2a) |
| `actor_roles` | `NULL`: the documented meaning "not captured" (topic writes populate it nowhere today; migration 22 limits it to two operations). Not a failure. |
| `timestamp` | the column default (`now()`, i.e. transaction start). Writes are serialized by the advisory lock, so audit times are correctly ordered. |
| `metadata` | `{ topicId, operation, changedFields, before, after }` |

`before` and `after` hold the **full values of the changed fields**: `name`, `prompt`, `firstSessionDescription` as plain text; `status` and `displayOrder` as values. Add: `before = null`, `after` = the full new row. Archive and restore: the status transition and resulting position; archive also lists `renumbered: [{ topicId, from, to }]`. Reorder: no `topicId`; `before` and `after` are the full ordered id lists. A row is bounded (at most 400 + 60 + 800 code points of text per side, plus at most 15 ids), and the metadata object has a closed key set asserted by test.

**The text exception.** The repository convention is "no topic names or prompt text in audit rows". That convention protects team-authored content. Template text is global, non-personal, and exactly what an incident reviewer needs; there is no version table, so a hash could not reconstruct a change. The exception is scoped to these five operation names only; the `audit-logging-operations` delta states it and a test asserts that no other operation's metadata gains text fields. The five names are one exported constant, `MAINTENANCE_AUDIT_OPERATIONS`, from the writer module, and **every query and test that selects maintenance rows uses `operation = ANY($1)` with that constant** (history, `lastChangedAt`, the invariants gate (f), test cleanup, the closed-key-set test, the runbook query). `LIKE 'topic.default_%'` is forbidden: `_` is a single-character wildcard and would also match the existing `topic.defaults_assigned`, `topic.defaults_assign_denied` and `topic.defaults_assign_failed` rows, whose `team_id` can be the sentinel, corrupting the history shape and letting an unrelated denial disable gate (f). `topic.default_maintenance_denied` is deliberately not in the constant (`team_id` null, not a template change). A test asserts that the denial and rate-limit rows of these routes carry their documented `team_id` and do not match the constant.

**Log copy carries no text (security S2).** The `AuditEventName` additions are emitted through `emitAuditEvent` (which logs with `audit: true`) with **identifiers only**: `operation`, `topicId` (or none for reorder), `changedFields`, actor user id and role, `actorIp` (an identifier, needed by the suggested "new IP for that actor" alert), `correlationId`. Never `before`, `after`, or any name/prompt/description text; the log pipeline has different retention, access and redaction than the table, and the database exception does not authorize it. A test captures the emitted event for all five operations and asserts no text field and no value from the request body appears. This event is also the detective control (S4): one `info` structured event per effective template write, on which existing log-based alerting can page (suggested alert in `docs/deployment.md`: any `topic.default_*` event outside business hours, or from an IP not seen before for that actor). The audit row is the history: "undo" means editing the field back to the before-value from the row (D13).

**History read** (`GET .../history?limit=`): returns the newest-first audit rows for the sentinel with `operation = ANY(MAINTENANCE_AUDIT_OPERATIONS)`, as `{ id, operation, at, actor: { userId, displayName }, topicId, changedFields, before, after }`, where `at` is the `audit_log.timestamp` column (the table has no `created_at`). Order is `timestamp` descending, ties broken by `id` descending (a random UUID: deterministic but arbitrary, and said so). The history exposes actor ids and display names to every administrator; acceptable for an admin-only read. `limit`: absent is 50; an integer 1 to 200 is used as given; an integer above 200 is clamped to 200 (not an error); 0, negative, non-integer or non-numeric is `422 INVALID_HISTORY_LIMIT`. Boundary tests at 1, 200 and 201 (clamped to 200). Uses the existing `idx_audit_log_team` index. Reads are not audited (template content is non-personal; the TOPIC-002 admin-read audit exists because it exposes team-authored content).

**Per-row `lastChangedAt` / `lastChangedBy`** (D14), defined precisely: the `timestamp` (mapped to `lastChangedAt` in JSON) and actor of the latest `audit_log` row for the sentinel whose `operation` is one of the first four names in `MAINTENANCE_AUDIT_OPERATIONS` and whose `metadata.topicId` equals the row's id; null and null when no such row exists (a seeded row never touched). `topic.default_reordered` rows never count; the list carries a separate top-level `orderLastChangedAt`, the `timestamp` of the latest `topic.default_reordered` row (null if none). **One query, not N+1:** `SELECT DISTINCT ON (metadata->>'topicId') ... WHERE team_id = $1 AND operation = ANY($2) ORDER BY metadata->>'topicId', timestamp DESC, id DESC`, served by `idx_audit_log_team` (`team_id` only; `metadata->>'topicId'` is unindexed, fine at this scale because the sentinel's other audit rows are few: `topic.write_denied_template` is deduped and `team.template_cleanup` is one-off; a partial expression index would be a migration and its own change). The serializer nulls `displayOrder` from `status`, never from the stored column (an archived row keeps a stale number); the closed-shape test covers it. No schema change, no denormalized column that could drift from the audit trail.

**Audit-retention dependency.** Because these values are derived from audit rows, they are only as durable as audit retention. If audit rows are ever purged or archived, `lastChangedAt` silently reverts to null and the history read shrinks. Assumption recorded: audit rows for the sentinel template are **exempt from routine retention** (they are few and small); they are not "never deletable". The `docs/deployment.md` runbook states the exemption (any retention job must exempt rows with `operation = ANY` of the five names and the sentinel `team_id`) and also defines a **break-glass redaction procedure** (task 8.6), because these rows hold admin-authored text and an administrator can paste something that must not persist (a person's name, an internal hostname, a credential). Procedure: a named database operator replaces the text fields of the affected row's `metadata.before`/`after` with a tombstone string, adds a `redacted: { by, at, reason }` marker, leaves `timestamp`, `operation`, `actor_*` and `metadata.topicId` untouched (so `lastChangedAt` is unaffected), and records the action in the incident log; if the live template row still holds the text it is first corrected through the normal edit endpoint. This is stated to be the **only** sanctioned mutation of `audit_log`. Readers: the only code reading these rows is the new history and list queries and the existing `session.connection_recovered` query is unrelated; task 1.2 confirms no other reader, export or log shipper copies or unescapes `metadata` text.

### E6. Invariants after every write, and what "archived" now means (D1, D5)

Backstop checked inside the write transaction, after the write and the dense normalization (E5) and before the audit insert. It is scoped to what the operation produced, so **pre-existing damage can never wedge maintenance**, including the repair of that damage:
1. At least one active default (and at most 15).
2. Active positions are exactly 1..N, unique (guaranteed by the normalization; a failure here is a real bug).
3. The row(s) this operation inserted or edited have valid fields per E4.

Not blocking: a pre-existing `is_default = false` row on the template, a pre-existing gap or duplicate, or an old row (active or archived) that fails E4 validation. These are the damage #215's anomaly detector already logs at team creation (`template_anomaly`); the maintenance path neither aborts on them nor deletes them, and a gap is repaired by the normalization on the next add, archive, restore or reorder. The invariants integration test (below) is the CI-time detector for the other cases. A backstop failure (1 to 3) rolls the transaction back and maps to `500` with an `error` log naming the `InvariantId` (E3 table); it is a bug signal, not a user error. If an operator needs to repair a damaged template, the runbook gives the read-only inspection query already in `docs/deployment.md` (#215) and the repair is a data fix by a database operator.

Archived defaults are **valid state**. `canonicalDefaultsWhere` already requires `status = 'active'`, so archived rows are never copied: archive is "retire from new teams" with a recoverable history.

**`template-anomalies.ts`.** `non_active_default` is removed from the detector, its type union and its `topicIds` contribution. The other three anomalies (`duplicate_active_order`, `non_contiguous_order`, `non_default_row`) stay. ### E7. Response shapes

`GET` and every write return:

```
{
  defaults: [ { id, name, prompt, voteType, firstSessionDescription,
                status: 'active' | 'archived', displayOrder: number | null,
                lastChangedAt: string | null,
                lastChangedBy: { userId, displayName } | null } ],   // active by position, then archived
  limits: { minActive: 1, maxActive: 15, nameMax: 60, promptMax: 400, descriptionMax: 800 },
  orderLastChangedAt: string | null
}
```

Writes add `scope` (always, verbatim: "Applies to teams created from now on. Existing teams keep their current topics.") and, where relevant, `notice` (rename), `changedTopicId`, and `unchanged: true` on a no-op. `displayOrder` is `null` for archived rows. The `scope` text is the one copy; the follow-up screen shows it once per edit session near Save.

**Copy rules (D9).** No endpoint text, doc or runbook line calls a restored topic "canonical". The recovery docs state that Recover Zero-Topic Team hands out the template **as of now**.

**Transaction boundary for response and log (settled at task review).** Every write response carries the refreshed list, but a row's `lastChangedAt` is derived from the audit row the same call inserts, so the list cannot be read inside `domainWrite`. The writer reads it **after commit**, with the same list function the GET uses (a concurrent admin write between commit and read is acceptable: the response is a view, not authority). The `info` maintenance log event (E5) is likewise emitted **after commit**, so a write that rolls back (audit failure, backstop failure) never logs, which keeps the detective control honest. Tests: tasks 4.8 and 4.11.

### E8. Concurrency and live-session isolation

- Each admin write is one transaction under `lockTeamTopics(client, SENTINEL)` (a transaction-scoped advisory lock keyed on the sentinel id). Two admins editing at once serialize; neither can produce duplicate or non-dense positions. A lock timeout surfaces as `503 DEFAULT_MAINTENANCE_BUSY` (E3). A second reorder against a stale list gets `409 REORDER_ID_MISMATCH` with `current` and a plain-language message ("The default topics changed while you were editing. Reload the list and try again."), never a silently lost edit. A stale-but-same-id-set reorder is accepted (last write wins on order), as TOPIC-006 would for the same ids; the audit row records before and after so the overwritten order is recoverable. An admin may not expect this, so it is a spec scenario (two admins, same ids, second order wins, audit row holds the overwritten order), not only design text.
- **Team creation during an edit.** `copyCanonicalDefaults` is a single `INSERT ... SELECT` statement at READ COMMITTED; a statement sees one consistent committed snapshot, and a multi-statement admin transaction commits atomically, so a team created during an edit sees either the complete before-set or the complete after-set. Tasks 1.5 and 2.5 verify the copy is still one statement and adds a test that holds an admin transaction open (after the negate step) while a team is created, and asserts the copied set equals the before-set. If the copy ever becomes multi-statement, it must move to `REPEATABLE READ` or share the lock.
- **Live-session isolation (MUSTs).** (i) No maintenance operation reads or writes any real team's `topics`, `session_topics`, or an open session. (ii) The maintenance path takes `lockTeamTopics` on the sentinel only and shares no state with the live-session path. (iii) A negative test: snapshot every existing team's `topics` and every `session_topics` row, run all five operations, assert byte-identical afterwards.
- **Empty system.** The path works with no teams and no sessions; no special case.

### E9. Prompt content: documentation and structure, not a filter

The control for "prompts that name individuals" is verifiable documentation plus structure (BA option (a)). The REST API Contract entry (and later the screen copy) states that prompts address the team and the work, never individuals, with two or three good and bad examples, and notes that the first topics set the emotional tone of a session. ### E11. Outcome of the trigger reconsideration (D4)

#215 declined a `BEFORE INSERT/UPDATE/DELETE ON topics` trigger rejecting sentinel writes unless `current_setting('app.allow_template_topic_write', true) = 'on'`, on condition that this change (i) routes every template write through one audited function, (ii) writes one `audit_log` row per template write, (iii) reconsiders the trigger now that a sanctioned writer exists.

**Outcome (exactly one of the three): the trigger is declined again, replaced by an enumerating structural test.** Reasons:

- Benefit is real but narrow: a second writer could not appear silently. It is not a security boundary (anyone with SQL access can set the setting) and it guards against code paths and mistakes only.
- Cost is concrete: migrations 4 and 11 write the template, so the trigger must be numbered after them and every future default-topic migration must opt in; every existing test that mutates the template (snapshot and restore helpers, `withTemplateLock` users, the #188 and #215 suites) needs the opt-in or a shared helper, a wide, flaky-prone edit across suites that this change otherwise leaves untouched; and `topics` is a hot shared table that every team write would pay for. `withAuditTransaction` does open an explicit transaction, so `SET LOCAL` would not leak on a pooled connection, which removes #215's pooling worry, but not the migration-ordering and test cost.
- The structural test delivers the property that matters (a second writer cannot appear without a red build and a reviewer's eyes) at no schema cost.

**The test** (`routes/__tests__/template-writer-structural.test.ts`): reads every non-test `.ts` file under `packages/backend/src`, extracts SQL statements from string and template literals, and scans at **statement and enclosing-function granularity**, not file granularity, because the likeliest regression is a sentinel-targeted write added inside `routes/topics.ts`, which already holds many legitimate writes.

- *Patterns* (case-insensitive, whitespace- and newline-tolerant, with a word boundary after `topics` so `session_topics` and `topics_x` do not match): `INSERT INTO`, `UPDATE [ONLY]`, `DELETE FROM`, `TRUNCATE [TABLE]`, `MERGE INTO`, each followed by an optionally schema-qualified (`public.topics`) and optionally double-quoted (`"topics"`) `topics` with an optional alias (`UPDATE topics t`); `INSERT ... ON CONFLICT` is covered by the `INSERT INTO` match; writes inside CTEs (`WITH x AS (UPDATE topics ...)`) are found because the scan matches anywhere in the statement text. A write keyword followed by a `${...}` interpolation where the table name belongs, or a `topics` identifier built by concatenation next to a write keyword, **fails** (dynamic table names cannot be reasoned about).
- *Allowlist* (checked in, one-line justification per entry), keyed by file and enclosing function name: `sessions/default-topic-maintenance.ts` (the sanctioned template writer; the only place a sentinel write target is permitted); `sessions/default-topics.ts` `copyCanonicalDefaults` (writes new-team rows; the sentinel appears only as the SELECT source, which is why the sentinel rule exempts this one function by name); and each team-scoped writer function in `routes/topics.ts`, listed by name (task 6.4 generates the day-one list by running the scanner, so the allowlist is exact and the test is green on day one), each guarded by `checkWritableTeam` and covered by the #188 structural test. A new writer function in any file, including `routes/topics.ts`, is a red build until a reviewer adds a justified entry.
- *Sentinel rule* (scope settled in tasks 1.5): the rule is about **writes**. Any SQL statement that writes `topics` and targets the sentinel (it references `DEFAULT_TOPICS_TEAM_ID`, the sentinel UUID literal or `__default_topics__`), or the call expression that executes it, is allowed only inside the writer module (with the `copyCanonicalDefaults` exception above, where the sentinel is only the SELECT source). A bare reference that is not part of a write statement is not flagged: the existing `checkWritableTeam` guard, assign-defaults, `template-anomalies`, the denial seam, and the route passing the sentinel id as the rate limiter's `teamId` (E2 item 4) all legitimately reference it, and flagging them would make the test red on day one or silently over-exempted. Non-SQL uses import `DEFAULT_TOPICS_TEAM_ID` from `sessions/default-topics.ts` (its single definition); a second literal copy of the UUID outside that file and the migrations is a review finding. Limit, stated plainly: a sentinel id arriving through a runtime variable (a path parameter) cannot be detected statically; for the team-scoped handlers that runtime guard is `checkWritableTeam` and its #188 structural test, and the scanner's job is to make a new writer a conscious decision.
- *Fixtures*: a table of synthetic sources, each of which the pure scanner function must report: unlisted file, unlisted function in a listed file, `UPDATE ONLY topics`, `public.topics`, `"topics"`, aliased, CTE-wrapped, `TRUNCATE`, `MERGE`, `INSERT ... ON CONFLICT`, dynamic table name, and a sentinel reference outside the writer module; plus negative fixtures (`session_topics`, `topics_x`, comments) that must not match.
- Tests and migrations are out of scope for the scan: migrations are reviewed history, and tests are not production code. The test header says it guards against mistakes, not against an attacker with SQL access.

**Revisit triggers (recorded):** (1) a second sanctioned writer is proposed; (2) any production incident in which the template was changed outside the audit trail; (3) the migration-ordering and test cost falls (for example a single shared template-test helper replaces the scattered ones). Any of these reopens the trigger as its own change.

## Risks / Trade-offs

- **An edit that breaks team creation** (zero actives, duplicate positions, empty prompt): prevented by E4/E6 validation, the in-transaction backstop, and the tests. Residual: someone with SQL access.
- **Admin-authored text that targets individuals:** documentation, format guard, audit and review; no filter (E9). Residual accepted and recorded in the proposal as a known residual risk.
- **Audit text exception sets a precedent:** scoped to five names and tested so it cannot spread.
- **Two accepted consequences become visible for the first time** (restore returns superseded wording; `defaultTopicsNotActive` name mismatch after rename): documented, follow-up issues. Rename responses carry the notice.
- **Interim cost of API-only:** first users are developer-level. Mitigated by the pre-first-production-edit dry run checklist item (task 10.1), which is not a merge gate. FR-8.1 is reported "partially met, API only", never as self-service.
- **PO limits could move:** constants in one place, change by code with PO review.
- **Edit-of-archived refused (E4):** my addition; cheap to reverse.
- **Single-admin control and compromised session** (E2a): accepted for the first release, detected by the structured log event and the audit trail, not prevented. Reopen triggers recorded in the proposal.
- **Audit text outlives its welcome:** mitigated by the break-glass redaction procedure (E5); audit-table tamper resistance is an assumption, not a claim (E2a).
- **Retiring `non_active_default`** loses a signal for a state that is now legitimate. The remaining three anomalies still cover damage.

## As built (engineer pass and implementation reviews)

The code diverges from the text above in these places; this subsection is the authority where they disagree.

1. **Role check before the body is parsed.** The role is read once by a plugin-scoped `preParsing` hook (Fastify lifecycle: onRequest, preParsing, body parse, preValidation, handler), so a non-admin gets the envelope 403, the timing floor and the denial audit row whatever the body (oversize, malformed, wrong media type). `bodyLimit`, the parser and the media-type check therefore only ever apply to administrators. The role read is wrapped: a database failure is the generic envelope 500 with no error text.
2. **Media type and parser errors.** Fastify 5 parses `text/plain`, so the route layer checks the media type itself (`415 UNSUPPORTED_MEDIA_TYPE`, after the role check, before the rate limit). A plugin-scoped error handler maps parser failures for administrators to the envelope: `413 BODY_TOO_LARGE`, `415 UNSUPPORTED_MEDIA_TYPE`, `400 INVALID_JSON_BODY`. A plugin-scoped JSON parser tolerates an empty body (parsed as absent). **Archive and restore take no body**; an empty body with a JSON content type is accepted and a body they receive is ignored.
3. **Module split.** Constants, validators and `MAINTENANCE_AUDIT_OPERATIONS` live in `sessions/default-topic-validation.ts` (no database import) and are re-exported by `sessions/default-topic-maintenance.ts`.
4. **History shape.** `GET .../history` returns `{ history: [...] }`, not the list shape.
5. **Reorder no-op.** A reorder is a no-op only when the list equals the stored order **and** the active positions are already dense 1..N; the same order on a gapped template is an effective write that repairs the gap and writes an audit row.
6. **Test cleanup guard.** The audit-row cleanup helper refuses to run unless `VITEST` is set, the host is local and the database is `dipstick` or `dipstick_test` (the integration lane sets `NODE_ENV=development`, so `NODE_ENV` cannot be the guard). Template restore runs in its own transaction and writes only maintenance columns (not annotations), and the template lock is held per test.
7. **Sampled suppression log.** The log-only `topic.denial_audit_suppressed` event for this family is emitted at suppressed counts 1, 2, 4, 8, ...; the count is therefore sampled, not exact.
8. **`info` event content.** The log event carries `actorIp` in addition to the identifiers listed in E5.
9. **Post-commit list read failure.** If the list read after COMMIT fails, the write response is still `200`/`201` with `listUnavailable: true` and no list (the failure is logged), so a client does not retry a change that already happened.
10. **Plain-text guard.** U+2028/U+2029 are rejected in every field (only `\n` is allowed, in the description). Known gaps of the denylist, acceptable because every consumer renders as text (E4a): bare `javascript:`/`mailto:` schemes, `&#60` without a semicolon, non-Cc/Cf invisibles (U+3164, U+115F, U+2800, NBSP), private-use code points and homoglyphs. Name uniqueness is a JavaScript check under the advisory lock, not a database guarantee, and NFC/NFD and look-alike spellings count as different names (accepted).
11. **Limits in one place.** The reorder length check and the capacity message use `MAX_ACTIVE_DEFAULTS`.
12. **Other.** Maintenance operations act only on `is_default = true` rows. Rate-limit budget is shared with the other topic writes (an administrator who is also a facilitator shares one budget); the two GET routes are not limited.
