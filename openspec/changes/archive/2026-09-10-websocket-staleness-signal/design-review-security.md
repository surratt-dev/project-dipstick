# Design-Stage Security Review — websocket-staleness-signal

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope:** design.md and proposal.md, read against the wire contract established by the two archived changes this consumes (`websocket-delivery-time-authorization`, `websocket-connection-reauthorization`) and their own design-review-security.md files, which set the severity bar and precedent I'm calibrating against here. There is no implementation yet — this is genuinely greenfield frontend work, so unlike my two prior reviews on this feature line, I have no running code to verify claims against. My findings below are therefore about what this document commits to, tests for, and leaves silent, not about a discrepancy between prose and code.

**Bottom line:** The core non-disclosure architecture — one shared module, two disclosure-blind values with no cause branching, one narrowly-named exception for the legitimately-disclosed `reauth-required` state — is the right shape and I would not reopen D1, D1a, D2, D3, D4, or D6. I have one **finding I want resolved before implementation is considered done** (Finding 1: the state machine's transition guards are under-specified for two concrete race conditions that could silently reopen the retry-forever or reauth-disclosure problem D1a exists to close) and four **non-blocking findings worth recording**, several of which point at gaps this document cannot itself close (they live in the backend changes it consumes) but that I don't want lost the way I don't want anything deferred to become indistinguishable from forgotten.

---

## Finding 1 (Required before implementation is considered done): Two state-transition races are not named, guarded against, or tested

**What I looked for:** design.md is emphatic that `reauth-required` and `unknown-reconnecting` "do not merge or fall through into each other" (D1a) and that no retry is ever attempted from `reauth-required`. Tasks 1.12 and 1.11 test this for the two triggering signals arriving *first*. Neither the design nor the task list addresses what happens when a signal for one state arrives *after* the machine has already committed to the other, which is a real sequencing question in an event-driven WebSocket handler, not a hypothetical one.

**Race A — a close event arrives after a `reauth_required` message has already been processed.** D1a's own text says the message "arrives first and while the socket is still open," and the close code is a "fallback, for a client that misses or never receives the message." That framing already assumes an order. But nothing states what the handler does if, after transitioning to `reauth-required` on the message, the *subsequent* close event fires with some code other than `REAUTH_GRACE_EXPIRED_CLOSE_CODE` — including, concretely, `STALE_SIGNAL_CLOSE_CODE` (4000) if a SEC-25 sweep tick and a SEC-26 grace expiry land on the same connection close together (the reauth precedent review's own Q1 raised exactly this near-simultaneous-timer scenario and concluded "whichever `.close()` call lands first wins" at the *server*; this document needs the equivalent answer for what the *client* does when it already committed to one outcome and then receives a signal for the other). If the `onclose` handler isn't explicitly guarded to ignore further transitions once `reauth-required` is set, a design that reads "the two paths do not merge" as an outcome rather than as an enforced invariant will merge them the first time this ordering occurs — and it will do so silently, since nothing in Group 1's tests forces this specific sequence.

**Race B — a retry timer scheduled during a prior `unknown-reconnecting` phase is still pending when a `reauth_required` signal arrives.** A connection can legitimately be in `unknown-reconnecting` (ordinary flakiness, retrying on schedule), successfully reconnect, and shortly after receive `reauth_required` on the new connection. If the transition into `reauth-required` does not explicitly cancel any in-flight `setTimeout` left over from the *prior* `unknown-reconnecting` episode, that stray timer fires later, calls `connect()` again, and opens a new WebSocket after the design has already told the user (via the `reauth-required` banner) that the fix is to navigate away and log in — directly reopening the "retry loop against a connection that can never succeed" outcome D1a was written specifically to prevent. Task 1.11 only asserts `computeRetryDelay` is called zero times when the reauth signal is the *triggering* event; it does not exercise a timer scheduled before that signal arrives.

**Why this belongs in this review and not just as an implementation nitpick:** both races produce the exact failure mode this design's headline decision (D1a) exists to close — either a disclosure-relevant merge of the two state paths, or a stranded/looping retry against a connection that will never succeed. A design document that states an invariant ("the two paths do not merge or fall through into each other") without stating the mechanism that enforces it against out-of-order events is stating an outcome, not a control — the same distinction I drew in Finding 3 of the delivery-time-authorization review between "documented mitigation" and "code-level guard."

**Recommendation:** add an explicit decision (or amend D1a) stating that `reauth-required` is a **sticky/terminal** state for the lifetime of a given `useConnectionHealth` instance — once entered, no subsequent close/error event of any code is processed, and any pending retry timer is cleared synchronously on entry. Add two tests alongside 1.11/1.12: (a) a `reauth_required` message followed by a close event carrying `STALE_SIGNAL_CLOSE_CODE` does not revert `state` to `unknown-reconnecting`; (b) a pending retry timer from a prior `unknown-reconnecting` episode is cancelled the instant `reauth-required` is entered, and never fires `connect()` afterward.

## Finding 2 (Worth recording, not fixable in this change): the raw close code remains visible to the affected client via browser DevTools, independent of anything this state machine does

The entire design operates one layer above the browser's native `CloseEvent` — it's careful that no *rendered* string, *timing*, or *retry behavior* differs by cause. But `STALE_SIGNAL_CLOSE_CODE` (4000) is a real, distinct application-level WebSocket close code, not the browser's generic `1006` abnormal-closure code a genuine network death produces. Anyone with access to that browser's DevTools Network/WS inspector — most relevantly, the affected participant themselves, curious whether they were specifically revoked versus just unlucky with wifi — can read the close code directly off the wire, completely bypassing the JS state machine this design so carefully keeps symmetric. This is the one channel client-side application logic structurally cannot close, because it operates beneath the JS layer.

This isn't a defect in this design — Non-Goals correctly bars inventing a new close code or heartbeat here, and the fix (if one is wanted) lives in the two backend changes that chose 4000/4001 in the first place, not here. But I don't see this named anywhere in either archived backend design's own risk register, and it's directly on point for a document whose stated goal is "must NOT disclose... via timing, wording, or behavioral asymmetry" — DevTools visibility is a fourth channel, alongside those three, that nothing in this feature line has named. Recommend a one-line acknowledgment in this design's Risks section (even though the remediation is out of scope here), so it's recorded rather than silently assumed away, and a forward pointer for whoever eventually owns issue #32 or #33, since both will run into the same limit.

## Finding 3 (Worth recording, not fixable in this change): the SEC-25 sweep's fixed, non-jittered interval creates an observer-side correlation channel this client design cannot address

I checked `packages/backend/src/realtime/connection-reauthorization.ts:25`: `REAUTHORIZATION_INTERVAL_MS = 5 * 60 * 1000`, wired via a plain `setInterval` per connection (line 127) — a fixed five-minute cadence, not jittered, and explicitly "not configurable" by design (matching the same discipline this document itself follows for `STALENESS_TIMING_FLOOR_MS`).

This document's uniform-timing-floor and retry-symmetry work correctly defeats *per-event* timing analysis — no single `unknown-reconnecting` transition, examined in isolation, discloses its cause. But a facilitator (or a participant) watching a connection over the course of a long session sees a *sequence* of events, and a fixed five-minute sweep interval is itself a signal external to anything this client module controls: a disconnect that recurs at consistent five-minute-multiple offsets from connection start is statistically distinguishable from one that doesn't, purely by an observer doing arithmetic on wall-clock timestamps they already have (the grid marker's on/off transitions, or the participant's own banner history) — no close-code inspection required. This is a genuinely different channel from the three D1a/D2/D3 already defend against (wording, per-event timing, retry behavior), and nothing in this design, the delivery-time-authorization design, or the connection-reauthorization design discusses it.

I'm not asking this design to fix it — it can't; the interval lives in a different codebase and jittering it is a backend decision with its own trade-offs (it would also perturb the reveal-timing-independence guarantees the reauth change went to some trouble to establish). I am asking that it be named somewhere durable, ideally as a forward-pointing note in this design's Risks section referencing the interval constant directly, so a future reviewer of `websocket-connection-reauthorization` (or issue #33, which is explicitly about the reauth-flow grid distinction) inherits the observation rather than rediscovering it.

## Finding 4 (Worth recording): no signal — not even non-attributable/aggregate — exists anywhere for connection-health transitions, and the design doesn't say whether that's intentional at the aggregate level or just a side effect of being purely client-side

D12 is correct to decline a facilitator-visible, participant-attributable staleness history — that's squarely the surveillance concern the ritual's core constraint exists to prevent, and I have no objection to that reasoning. But D12's scope is specifically about *attributable, facilitator-visible* records. It doesn't address, and this document doesn't otherwise raise, a narrower question: whether security operations has *any* way to notice, fleet-wide, an anomalous volume of clients hitting `reauth-required` or retrying indefinitely against revoked connections — the kind of aggregate, unattributed signal that would matter during an actual incident (a bug that's wrongly revoking legitimate sessions, or a credential-compromise event producing a wave of forced re-authentications) and that carries none of the individual-comparison risk D12 is rightly worried about.

Since this change is purely client-side (Non-Goals bars any new server-side signal), there's no mechanism available to it to close this gap, and I'm not asking it to invent one under this change's scope. But the document should say, in one sentence, that this question exists and is out of scope rather than leaving it unaddressed by omission — the same discipline D12 itself models for the session-history question. Recommend a short addition to the Non-Goals or Risks section: aggregate, non-attributable operational telemetry for connection-health state distribution is a distinct question from D12's declined per-participant history, not addressed here, and would require its own server-side design if pursued.

## Finding 5 (Low, informational): the grep-based non-disclosure enforcement (task 1.9) should also cover debug logging, not just branching logic

Task 1.9 greps for close-code comparisons in the module and its call sites — a good, code-level (not just code-review) enforcement mechanism, and I have no objection to the pattern. It doesn't cover a different, equally common way this kind of invariant quietly erodes: a `console.log`/`console.error`/`console.debug` call added while debugging the state machine that prints `event.code`, `event.reason`, or the raw `reauth_required` payload. That wouldn't violate the letter of "no branching on close-code value," and it wouldn't fail any of the rendered-output-identity or retry-symmetry tests, but it would put cause information directly into the browser console for anyone who opens it — compounding Finding 2 rather than being independent of it. Recommend extending task 1.9's grep (or adding a sibling check) to also flag any `console.*` call within `connectionHealth.ts` that references `event.code`, `event.reason`, or the parsed message body, so a debugging leftover doesn't ship silently.

## What I checked and have no finding on

- **The non-disclosure invariant's scope (D1a's "one narrow, named exception"):** correctly bounded — the design is explicit that the `REAUTH_GRACE_EXPIRED_CLOSE_CODE` check exists only to route to a *different, already-disclosed* state, never to alter `unknown-reconnecting`'s classification, timing, or retry behavior, and task 1.9's grep is written to allow exactly this one exception and no other. I have no objection to treating this specific check as outside the disclosure boundary — the reasoning (spec.md's own "legitimately disclosed to this client" language) is sound and I'd have made the same call.
- **The timing floor's value-independence argument (D3):** I looked hard for a way 2000ms specifically (as opposed to the floor's mere existence and uniform application) mattered to the disclosure property, and I don't find one — the floor's job is to guarantee a *minimum* elapsed time before rendering, which is symmetric regardless of the constant chosen, as long as it's applied identically to both the instant-reject and eventual-fail paths. This is different in kind from `timing-oracle.ts`'s `CONTENT_TIMING_FLOOR_MS`, which has to exceed a measured response-time distribution to do its job — I agree with this document's own distinction on that point and don't think a production-deployment guard analogous to that module's is needed here. The *UX* half of the justification (avoiding facilitator alarm fatigue on routine wifi blips) does depend on real data, and I'm satisfied that's correctly routed to Priya Nair's usability-test gate rather than asserted as settled.
- **Retry-symmetry mechanism (D2) and its test (task 1.4):** a pure function keyed only on attempt count, with a determinism-seeded jitter test forcing both trigger types through the identical handler, is the right enforcement shape and matches the level of rigor I'd ask for.
- **Grid-marker cause-blindness as scoped (D7):** reusing the facilitator's own connection-health state rather than inventing a new per-participant signal is the correct call, and I traced no way the marker's composition with the pre-existing `disconnected_voted`/`disconnected_no_vote` states reintroduces a distinction between them — those states already exist and already carry whatever disclosure properties the earlier two changes assigned them; this design doesn't touch that boundary.
- **D12's declined session-history feature:** the reasoning is correct and consistent with the ritual's stated constraint; I'd have flagged it if this document had gone the other way.
- **Non-configurability (D3, task 7.3) and no-new-server-signal (Non-Goals):** both correctly mirror the precedent the reauth change set for its own interval constants, and both are backed by inspection-based tasks rather than left to convention.

## Summary disposition

| # | Finding | Severity | Blocking? |
|---|---|---|---|
| 1 | State-transition races (late close after `reauth-required`; stale pending retry timer) are unguarded and untested | Medium-High (directly reopens the exact stuck-retry / state-merge outcome D1a exists to prevent) | Yes — resolve before implementation is considered done; two concrete tests are enough to close it |
| 2 | Raw close code visible via DevTools to the affected client, bypassing this design's symmetric handling entirely | Medium (real channel, not fixable here; needs to be named, not fixed, by this document) | No — record it; remediation (if any) belongs to the backend changes that chose the close codes |
| 3 | Fixed, non-jittered `REAUTHORIZATION_INTERVAL_MS` (5 min) creates an observer-side correlation channel across multiple events | Low-Medium (requires sustained observation, not a single-event leak; not this document's mechanism to fix) | No — record it, forward-pointing to `websocket-connection-reauthorization` |
| 4 | No aggregate/non-attributable telemetry exists for connection-health transitions; the design is silent on whether that's a deliberate scope boundary | Low (D12's attributable-history decline is correct and distinct from this question) | No — recommend one sentence acknowledging the gap as out of scope, not addressed |
| 5 | Grep-based enforcement (task 1.9) doesn't cover debug-logging leaks of `event.code`/`event.reason` | Low | No — cheap to fold into the existing grep task |

Finding 1 is the only one I'd hold this document to before calling the design settled — it's a correctness gap in the exact mechanism (D1a) this change was built to get right, it's concretely testable with two additional cases alongside the tests already planned, and it costs nothing to specify now versus being discovered as a flaky-looking bug during implementation. Findings 2–4 point outside this document's own remediation boundary, and I'm comfortable carrying them forward as named, recorded risks rather than blockers — consistent with how I closed out both of the backend reviews in this feature line — provided they land somewhere durable rather than only in this file.
