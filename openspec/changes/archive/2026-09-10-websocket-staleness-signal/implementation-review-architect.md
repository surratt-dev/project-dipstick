# Architecture Review — `websocket-staleness-signal`

Reviewer: Ingrid Sollenberger, Principal Solution Architect
Scope: implementation on branch `agent-team/websocket-staleness-signal`, reviewed against `design.md` and `tasks.md` as finalized, and against `implementation-summary.md`'s own account.

## Summary

This is a well-executed implementation. I traced the state machine myself rather than taking the design doc's or the summary's word for it, ran both test suites, ran an independent `tsc --noEmit` pass, and grepped the frontend source myself for close-code branching rather than trusting task 1.9's self-contained test. Everything I checked confirms the claims made in `design.md` and `implementation-summary.md`. I have no blocking findings. I have two required-before-merge items (both narrow, non-architectural) and several suggested improvements, mostly aimed at closing gaps that this change correctly named but did not close.

This change does what my initial scoping review asked for on the real-time layer specifically: it makes an explicit, tested decision about what happens when a connection drops, how the facilitator is informed, and it does so without introducing any new authoritative client-side state or any new persistent/ephemeral data. That is the property I care most about here, and it holds.

## Required before this is considered production-ready (not blocking this PR's merge, but blocking the pilot gate)

1. **File a tracked follow-up to make the "Type Check" CI job actually type-check `packages/frontend`.** This is not new scope for this change — it's a pre-existing repo-wide gap — but this change is the first one whose safety property leans explicitly on TypeScript exhaustiveness checking (task 1.2, D1) as a named, load-bearing control, and that control currently has no CI enforcement, only a runtime proxy test. Per my own standard (retrofitting observability/verification is more expensive than building it in), I want this filed as an issue now, not discovered the next time someone adds a fourth `ConnectionHealthState` value and ships it because `vite build` stayed green. Concretely: add a `tsc --noEmit` step (or `--build`) for `packages/frontend` to CI, separate from `vite build`. The pre-existing test-file failures under strict mode will need to be triaged when that lands (exclude test files from the check, or fix them) — that's follow-up scope, not this change's.

2. **Add a facilitator-role gate to the `/session/:sessionId/facilitator` route, or explicitly document why it's deferred, before Group 5's host is ever wired to real per-participant data.** `ProtectedRoute` (`packages/frontend/src/auth/ProtectedRoute.tsx`) only checks `session` presence — it does no role check at all. Today this is harmless: `FacilitatorConnectionHost` renders only `STUB_ROWS`, a hardcoded fixture, so no real participant data is reachable by a non-facilitator who navigates to that URL. But the route is a real, deployed route (mounted in `App.tsx`, reachable via `npm run dev` and in production), and there is currently nothing — not even a code comment — flagging that the client-side gate is missing and deferred. This is exactly the implicit-decision pattern I push back on: the moment someone wires real facilitator-only data into this host (the natural next step once `disconnected_voted`/`disconnected_no_vote` per-participant rows become real), if they don't independently recall that `ProtectedRoute` has no role parameter, the frontend route becomes the only gate standing between a participant and the readiness grid the design says must be "facilitator-only" (OR-4.4). I confirmed the backend's `evaluateSessionSubscriberAccess` (`websocket-routes.ts:83`) still does real server-side authorization at the WS-subscription layer regardless of what this route renders, so there is no live vulnerability today — access control is enforced where it has to be, at the server. My ask is narrower: either add the role check now (cheap, and this route is currently a stub so there's no urgency pressure), or add a task to `tasks.md`'s Group 5/6 (or a code comment on the route) making the missing client-side gate an explicit, named gap tied to whoever picks up the real grid wiring — not a silent assumption.

## Suggested (non-blocking)

3. **`REAUTH_REQUIRED_TEXT` is duplicated verbatim as two independent module-local constants** — one in `ConnectionStatusBanner.tsx`, one in `FacilitatorReadinessGrid.tsx` — rather than defined once and consumed twice. D1a's own language is that the facilitator's client, on entering `reauth-required`, renders "the same top-level treatment any client would" — which reads more naturally as *the same component*, not *a second component with independently-typed matching copy*. As written, Priya Nair's copy sign-off (D11/task 6.1) has two places to update, and nothing enforces they stay identical beyond the fact that an engineer copy-pasted them correctly this time. Two options that would close this cheaply: (a) export the string from `ConnectionStatusBanner.tsx` and import it into `FacilitatorReadinessGrid.tsx`, or (b) have `FacilitatorReadinessGrid`'s `reauth-required` case literally render `<ConnectionStatusBanner connect={connect} />` instead of its own `<div role="status">`. (b) is closer to D1a's stated intent and also removes a few lines of duplicated JSX.

4. **The aggregate-telemetry gap (Security design review Finding 4, design.md Non-Goals) is recorded in prose but not tracked as an issue.** I agree with the design's reasoning that this change has no mechanism to close it (it's client-only, no new server signal). But "recorded in a design doc" and "on someone's backlog" are different things, and this is precisely the observability-retrofitting risk I flag on every project: if a production incident later produces a spike of `reauth-required`/`unknown-reconnecting` states, on-call currently has no aggregate signal and would learn about it from user reports, not a dashboard. Suggest filing the forward-pointer issue design.md already describes in words, so it survives past this document.

5. **Task 2.2 (PR-description note pointing #33/#32 at this module) is correctly left unchecked pending an actual PR**, per the summary. Flagging only so whoever opens the PR doesn't lose track of it — the module's header comment covers the substance, but the task itself isn't done until the note is filed.

## Things I confirmed are *not* problems (stated for the record, since I was asked to check specifically)

- No real-time state authority issue: this module holds no authoritative session/vote state; it is purely a client-visible reflection of connection health layered on top of signals the server already sends. Nothing here lets client and server state diverge undetected.
- No new ephemeral/persistent data: task 7.4's claim (no session-history/trend-continuity record added) checks out — this change touches no `db.query` or Redis call anywhere in its new files.
- D9's Vite `/ws` proxy fix is correctly scoped and doesn't touch the `/api`/`/auth` entries.
- Group 0's constants are plain `export const`, not `export type`, correctly — the frontend genuinely needs the runtime values, not just the type.

## Overall

No blocking defects. Item 1 (CI type-check gap) and item 2 (facilitator route role gate) are the two I'd want acknowledged with a tracked follow-up or a deliberate "not now, and here's why" before I'd sign off on this as pilot-ready — which tracks with Group 6's own gates already holding up pilot readiness for unrelated (copy/visual) reasons. The core disclosure-safety mechanism — the part of this change I was most concerned would be implemented as claimed rather than actually implemented — held up under my own tracing and my own greps, not just the design doc's assertions about itself.
