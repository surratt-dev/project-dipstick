## Why

`websocket-delivery-time-authorization` closed the wire-protocol leak: a rejected subscription and the 90-minute force-expiry both resolve to the same `STALE_SIGNAL_CLOSE_CODE` (4000), so a close code alone discloses nothing about why a connection ended. That change's own tasks.md left a gate open at 9.1/9.3, owned by Priya Nair (Facilitator SME) and never closed in that implementation session: what does a participant or facilitator actually *see* when this fires, and does the UI leak back in through a door the wire protocol closed? A close code is binary and checkable by a unit test. A UI is not — it can leak the same cause-of-revocation information through wording, through timing, or through behavioral asymmetry, none of which a close-code test will ever catch. This codebase has no frontend WebSocket client and no readiness-grid rendering surface today (`SessionLobbyPage.tsx` is pre-session only); this is greenfield frontend work, which means there is no existing pattern to accidentally deviate from and no existing pattern to lean on either. Until this gate closes, task 9.3's own language stands: this capability "MUST NOT be used for a real pilot team's first live session." Issue #19 (full-stack E2E) is also blocked behind it. This proposal turns the Explore-stage design (`exploration-notes.md`, revised after review from Marcus Delgado and Priya Nair) into a buildable, reviewable plan.

**This change also has to account for `websocket-connection-reauthorization` (SEC-25/SEC-26, archived issue #27), not just `websocket-delivery-time-authorization`.** That spec introduced a second wire signal pair, deliberately distinct from `STALE_SIGNAL_CLOSE_CODE`: `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (4001) and an explicit in-band `{"eventType": "reauth_required"}` message sent to the client before that close. Its own requirement ("Revocation closes and re-authentication signals are never conflated," spec.md:107-109) is explicit that this pair must never be reused across the SEC-25 sweep and the SEC-26 refresh path, and — critically — that the cause is *legitimately disclosed* to the affected client: "the cause is legitimately disclosed to this client (it is a statement about that client's own token, not a secret being withheld)" (spec.md:121). Recovery from it requires a full top-level page navigation to the identity provider; it is never an in-place reconnect (spec.md:63). A two-state, cause-blind retry-forever machine that swallows a 4001/`reauth_required` signal into the same bucket as an ordinary network drop would strand a participant behind a banner that retries indefinitely against a connection that can never succeed, with no signal telling them the actual fix is to log in again — a worse outcome than the disclosure risk this change exists to close. Because the reauth signal is not a secret from the client it happens to, folding it into the disclosure-blind bucket isn't required by (and actively works against) the non-disclosure goal. This proposal therefore treats it as a third, legitimately-disclosed state — see bullet 1a below — rather than silently folding it into `unknown-reconnecting` or leaving it unhandled.

## What Changes

- Add a single client-side connection-health state machine — `connected` / `unknown-reconnecting`, no *fourth* value, and no branching by cause within these two — that treats a raw network close/error and a 4000 (`STALE_SIGNAL_CLOSE_CODE`) close as one undifferentiated bucket at the state-machine level, not just at the render level. The client MUST NOT branch on close-code value or on connection-attempt outcome type anywhere within these two states.
- **1a. `reauth-required` is a third state, legitimately disclosed, not folded into the disclosure-blind bucket.** The state machine also recognizes exactly one additional signal pair as its own distinct state: the in-band `{"eventType": "reauth_required"}` message, and — as a fallback, since a client may miss or never receive the message — a raw close with `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (4001). Either signal transitions the state machine to `reauth-required`, a state that is never entered from a 4000 close or a raw network close/error, and from which no retry is ever attempted (recovery is a full top-level page navigation per `websocket-connection-reauthorization`, not an in-place reconnect — retrying would just loop forever against a connection that can never succeed). This is the one narrow, named exception to "MUST NOT branch on close-code value": the module is permitted to check for exactly this one code, because the reauthorization spec itself establishes that this signal is not a secret being withheld from the client it happens to. The `reauth-required` state remains cause-blind *within itself* — it MUST NOT distinguish a retry-budget-exhausted refresh failure from a definitive identity-provider revocation from a concurrent session destruction, matching SEC-26's own non-disclosure of that sub-cause. Issue #32 (the reauthorization spec's own tracked item for the client-visible UX of this signal, spec.md:11/178) is a second deferred consumer of this module, alongside issue #33: this change builds the state, its detection, its no-retry behavior, and a minimal generic rendered treatment; #32's later work owns the fuller, polished re-login UX layered on top of this state, consuming it rather than forking it — the same "deferred consumer" pattern already used for #33.
- **Requirement, not implementation detail:** exactly one client-side connection-health module is built, and it is the sole implementation of this state machine. It is consumed by both the participant view and the facilitator readiness grid. No second implementation may be built independently, including by issue #33's later work (the reauthorization-flow grid distinction) or issue #32's later work (the reauth-required re-login UX) — both #32 and #33 must consume this module, not fork it.
- Add one participant-facing rendered treatment for the `unknown-reconnecting` state — plain language, no blame, no urgency escalation, identical regardless of underlying cause. Applies uniformly whether the cause is a rejected subscription, a mid-session force-expiry, or an ordinary network drop.
- **Initial-connection failure folds into the same bucket as mid-session staleness.** A participant whose very first subscription attempt is rejected is not a distinct case from a connection that went stale mid-session — same state, same banner, same code path. This is stated explicitly because greenfield state-machine code has no existing pattern to prevent an engineer from reasonably inventing a separate "couldn't connect" path that reopens the disclosure risk this document exists to close.
- **Recovery is silent.** When a genuinely-flaky connection returns to `connected`, there is no distinct "reconnected" acknowledgment — no toast, no transition treatment. An explicit recovery signal that can only ever fire for the recoverable case would itself be a disclosure, since a revoked connection would never produce one.
- Add a facilitator-only per-participant grid marker for "last known state may be stale," gated to facilitator-only exactly as the rest of the readiness grid already is (OR-4.4), and bound by the following acceptance conditions:
  - Adds at most one new visual state to the grid's existing **four** (`connected+not-locked-in`, `connected+locked-in`, `disconnected_voted` — renders "ready" despite disconnection, per OR-1.3 — and `disconnected_no_vote`, per `redis-session-model.md`; corrected from an earlier three-state count that dropped `disconnected_voted`). The marker **composes with**, and is not suppressed by, the `disconnected_voted` "ready" treatment: since the marker's signal source is the facilitator's own connection health (not a per-participant flag — see Design), it is driven independently of any given row's readiness state and overlays uniformly across all four baseline states, `disconnected_voted` included. A row already showing "ready" via `disconnected_voted` can also show the marker; OR-1.3's readiness indicator itself is unchanged.
  - Introduces no new color/icon language beyond what the grid already uses for `disconnected`.
  - Is **cause-blind**: a facilitator cannot distinguish "stale because revoked," "stale because flaky," or "stale because not-yet-reauthorized" (issue #33's case) from the marker alone. The marker is scoped to the `unknown-reconnecting` state only (see bullet 1a) — it never activates because the facilitator's own connection is in `reauth-required`; that state instead surfaces the same top-level, generic reauth-required treatment described in bullet 1a for the facilitator's own client, not a new grid-marker variant (which would breach the "at most one new visual state" bound above).
  - Has a defined lifecycle: Design MUST state a TTL or fallback behavior (does the marker persist indefinitely, or collapse into the existing `disconnected_no_vote` state?), applied identically regardless of cause, for the same reason the timing floor below applies identically — a marker that resolves faster for revoked connections than for flaky ones is a timing leak in a new location.
  - Design MUST state which moments in the session lifecycle the marker can appear during (e.g., whether a row that goes stale mid-active-vote freezes at last-known-state or changes visually), not only what it looks like at rest.
- Add a minimum-display/minimum-delay timing floor before the `unknown-reconnecting` state renders, applied identically to both causes. Two independent justifications, both binding: (1) an instant-fail-vs-eventual-fail asymmetry leaks cause even with identical banner text; (2) ordinary conference-room wifi flakes constantly, and a marker that flickers on every two-second hiccup trains facilitators to ignore it by the third session, defeating the marker's purpose. The exact millisecond value is a Design-stage decision (it may need real latency data, following the `CONTENT_TIMING_FLOOR_MS` / `timing-oracle.ts` precedent in pattern, not in module reuse — that module is server-side for a different reason); the *existence and uniform application* of the floor is a requirement now, not deferred.
- **Retry-strategy symmetry as a testable acceptance condition:** retry count, backoff schedule, and jitter must be identical code paths for a 4000 close and a raw network error/close — verifiable by a test that forces both through the same handler and asserts identical retry timing. A "smarter" reconnect strategy for ordinary flakiness that isn't applied identically to the revocation case is a disclosure, regardless of how reasonable the UX motivation for it is. This symmetry requirement's scope is exactly these two triggers; it does not extend to `reauth-required` (bullet 1a), which is a categorically different, no-retry state by design, not a third input that must produce identical retry timing to the other two.
- **`reauth-required` no-retry as a testable acceptance condition:** a 4001 close and, separately, a `reauth_required` message, must each drive the state machine to `reauth-required` and MUST NOT invoke the retry/backoff path at all — verifiable by a test that forces both signals through the handler and asserts zero retry attempts and zero calls to the retry-delay function.
- **Facilitator-experience requirements** (Priya Nair's review, folded in as requirements, not preferences):
  - Visual register reads as "uncertain," not "broken" — closer to a dimmed/hollow variant than a new icon or alarm color. (See Open Design Questions below — this instruction and the color-budget acceptance condition above point at two different existing grid states and are not silently reconciled here.)
  - No outlier-flagging affordances: no click-to-ping, no auto-generated chat message, nothing that turns a quiet facilitator-only signal into a spoken room moment unless the facilitator chooses to make it one.
  - First-session support is a one-line hover tooltip, not a tutorial — self-explanatory without prior documentation. Placeholder text: "Last known state may not be current."
  - **Standing commitment, carried into the testing stage, not dropped once a mock technically satisfies OR-2.2/OR-4.4:** a live usability test with Priya Nair in the room (virtual acceptable), evaluated specifically against "does this read as an alarm," before this reaches a real pilot team.
- File the gate language from the originating task forward verbatim, not paraphrased: *"a filed draft that does not resolve all four bullets does not close this task"* and *"'filed' and 'signed off' are not the same completion condition."* Both copy sketches below are explicitly non-final and pending Priya Nair's sign-off against actual layout (banner in context, tooltip on the actual grid) — neither is implementation-ready:
  - Devon's sketch (participant-facing): "Your view may be stale. Refresh to continue."
  - Priya's sketch (participant-facing): "Your view may be out of date. Refresh to continue."
  - Priya's sketch (facilitator tooltip, deliberately duller register): "Last known state may not be current."
- **BREAKING:** None. This is the first frontend WebSocket client in this codebase — there is no prior client-facing contract to break.

## Open Design Questions (deliberately unresolved here — for Design stage, against an actual mock)

These are not gaps in this proposal's thinking; they are points where two constraints from this proposal genuinely point in different directions and resolving them in prose, rather than against a mock, would paper over a real design decision:

1. **Grid marker visual register vs. color budget.** Priya's instruction is a dimmed/hollow variant of the existing `connected+not-locked-in` state ("still connected, just uncertain"). The acceptance condition above bounds new color/icon language to what the grid already uses for `disconnected`. Those are two different existing states with two different implications for what a facilitator infers at a glance. Design must resolve this explicitly against a mock — not by averaging the two instructions, and not by this proposal guessing on Priya's behalf ahead of her sign-off.
2. **Session-history / trend-continuity for stale-connection events.** Priya raised, as an explicitly non-blocking flag, that session history could someday note a stale-connection event (e.g., "a connection was interrupted during topic 3"). This proposal does **not** carry that forward as scope, even as a footnote to add later without scrutiny. A record tying connection-stability events to a named individual across sessions runs directly against the ritual's core constraint — session data must not be surfaceable in a way that allows comparison of individual engineers across teams or over time — and that constraint does not get softened because a given data point feels harmless on its own. If this is ever pursued, it requires its own review against that constraint specifically, and any version of it should be scoped to session-level, unattributed aggregation at most (e.g., "a stale-connection event occurred during topic 3," no participant name), never participant-level history. Naming the question is not the same as pre-approving an answer to it.

## Capabilities

### New Capabilities

- `websocket-staleness-signal`: Client-facing connection-health state machine (`connected` / `unknown-reconnecting` / `reauth-required`) shared by the participant view and the facilitator readiness grid; the participant-facing rendered treatments for connection uncertainty and for the legitimately-disclosed reauth-required case; the facilitator-only, cause-blind grid marker with a defined TTL/lifecycle; the uniform timing floor and retry-symmetry constraints that prevent the UI from disclosing what the wire protocol already refuses to disclose.

### Modified Capabilities

(none — `websocket-session-authorization` and `websocket-connection-reauthorization` are unchanged by this proposal; this change consumes their existing close-code contract, it does not alter it)

## Impact

- **New frontend surface:** the first WebSocket client in `packages/frontend/src`. No prior pattern exists to extend; this proposal's constraints exist specifically because a state machine built from nothing has more places to accidentally reintroduce the disclosure the backend already eliminated.
- **New frontend module:** one connection-health module, shared by the participant view and the facilitator readiness grid (no readiness-grid rendering surface exists yet either — today "readiness grid" is a backend concept only, per `vote_readiness_update` and `evaluateSessionSubscriberAccess`).
- **Consumed, not modified:** `STALE_SIGNAL_CLOSE_CODE` and `REAUTH_GRACE_EXPIRED_CLOSE_CODE`/`reauth_required` (`packages/backend/src/realtime/staleness-signal.ts`, `connection-token-refresh.ts`) — this change is purely client-side and adds no new server-side signal or close code; it consumes both existing wire contracts (SEC-25's disclosure-blind 4000 and SEC-26's legitimately-disclosed 4001/`reauth_required`), not just the first.
- **Deferred consumer, not built here (issue #33):** facilitator grid distinguishing revocation from flakiness during the *reauthorization* flow specifically will consume this change's grid marker component rather than duplicate it. This change does not wire up the reauth case; it leaves the seam generic enough for #33 to use.
- **Deferred consumer, not built here (issue #32):** the fuller, polished client-visible UX for the SEC-26 re-authentication prompt (the reauthorization spec's own tracked item, spec.md:11/178) will consume this change's `reauth-required` state rather than duplicate the detection/no-retry mechanism. This change builds the state, its detection (message + 4001 fallback), and a minimal generic rendered treatment; it does not build #32's full UX.
- **Test surface:** a retry-symmetry test forcing both a 4000 close and a simulated network drop through the same handler, asserting identical retry timing; a `reauth-required` no-retry test forcing both a 4001 close and a `reauth_required` message through the same handler, asserting zero retry attempts; grid-marker lifecycle/TTL tests; a facilitator-in-the-room usability test (owned by Priya Nair) gating pilot readiness, not just requirement compliance.
- **Gate carried forward:** per the originating task's own language, this capability must not be used for a real pilot team's first live session until Priya Nair's sign-off on both copy sketches (in actual layout) is complete and the usability test has run.
