## 3. Write-side: authorization, existence, and lock gate (evaluated in this order — design.md Decision 9)

**Note on sequencing:** this section groups tasks by concern (authorization/existence/lock-check *logic*), not by build order. `topics.ts` and its registered route don't exist until Task 5.1, and the three checks below aren't wired into a concrete handler until Task 5.2. Task 3.5's tests are integration-level (they assert what a caller "receives" over HTTP) and are not runnable — and should not be attempted — until Task 5.1/5.2 land. This is a deliberate choice to keep concern-based grouping (so a reviewer can find "where's the auth logic" in one place) rather than reordering the document; see the equivalent note at the top of Section 4 for the same reasoning applied to audit logging.

- [x] 3.1 Implement a standing-facilitator authorization check for topic-write endpoints: `global_role = 'facilitator'` AND the caller is not an active member of the target team (design.md Decision 3). Reject with `403 Forbidden` and reason code `NOT_A_FACILITATOR` or `FACILITATOR_IS_TEAM_MEMBER` as appropriate, evaluated and returned before any team-existence check or lock check. This check SHALL NOT require the target team to exist (the role sub-check touches no team data; the membership sub-check against a nonexistent `teamId` is vacuously "not a member" and passes through to Task 3.2). **Per design.md Decision 9's engineer-review (M2) addendum: reuse `facilitator-sessions.ts`'s existing `POST /draft` authorization query verbatim** (`SELECT u.global_role, (tm.id IS NOT NULL) AS is_member FROM users u LEFT JOIN team_memberships tm ON tm.user_id = u.id AND tm.team_id = $2 AND tm.removed_at IS NULL WHERE u.id = $1`) rather than writing a third independent copy of it — either call it directly or extract it to a shared helper (e.g. `evaluateStandingFacilitatorAccess(userId, teamId)`) used by both `POST /draft` and this endpoint.
- [x] 3.2 Implement a team-existence check for `:teamId`, evaluated only after Task 3.1's authorization check passes: reject with `404 Not Found` if no team row exists for `teamId`. This SHALL run before the lock-gate check (Task 3.3) (design.md Decision 9). **Per design.md Decision 11: this query is `SELECT id FROM teams WHERE id = $1` — it SHALL NOT filter on `deactivated_at`.** A deactivated team is treated as existing, matching `POST /draft`'s identical check; this is a stated decision, not an oversight, so do not add a `deactivated_at IS NULL` clause here even though `GET /teams/facilitatable` uses one for a different (listing/discovery) purpose.
- [x] 3.3 Implement the lock-gate check using the shared helper (Task 1.1) as a precondition for any topic-write request, evaluated only after Task 3.2's team-existence check passes. Reject with `409 Conflict` and reason code `TOPIC_CUSTOMIZATION_LOCKED` when the team is locked.
- [x] 3.4 Implement the shared rejection response shape using this codebase's standard error envelope (design.md Decision 4, corrected per engineer review M1): `{ error: { category, code, message, correlationId } }`, with `category: "forbidden"` for `NOT_A_FACILITATOR`/`FACILITATOR_IS_TEAM_MEMBER` and `category: "precondition_failed"` for `TOPIC_CUSTOMIZATION_LOCKED`, and the fixed literal message `"Topics cannot be customized until this team's first session is completed."` for the `TOPIC_CUSTOMIZATION_LOCKED` case. Do **not** ship a bare top-level `{ code, message }` body — reuse `teams.ts`'s existing `error.code`-in-envelope shape (e.g. its `GLOBAL_ROLE_PRECONDITION_NOT_MET` response).
- [x] 3.5 Write tests confirming the full ordering (design.md Decision 9): a non-facilitator or same-team-member facilitator against a locked or nonexistent team receives `403` (not `404` or `409`), and the response does not reveal lock state or team existence; a standing, non-member facilitator against a nonexistent team receives `404` (not `409`); a standing, non-member facilitator against a locked, existing team receives `409` (not `404`); a standing, non-member facilitator against a *deactivated but existing* team is not rejected `404` for deactivation alone (design.md Decision 11).
- [x] 3.6 Implement Tasks 3.1/3.2/3.3's checks as functions parameterized on a shared `startTime` (not as inline handler code with its own entry point — no handler exists in this section) and call `applyTimingFloor(startTime)` at each one's early-return — the `403` (Task 3.1), the `404` (Task 3.2), and the `409` (Task 3.3) — per design.md Decision 9's security-review (Finding 1) amendment. The actual `startTime` recording happens at the concrete handler's entry, assembled in Task 5.2 — this section's checks receive it as a parameter from their caller, they do not record it themselves.

## 4. Audit logging for denied lock-bypass attempts

**Note on sequencing and scope:** this section covers only the denial-path audit write (4.1-4.4), which is genuinely independent of Section 5 — it hooks into Task 3.3's lock-gate check, a standalone function that exists once Section 3 is built, with no dependency on `topics.ts` existing at all. Task 4.3's test, however, is still integration-level in the sense that "a denied request" reads most naturally as a call against the registered route; it is not runnable end-to-end until Task 5.1/5.2 land, even though the audit-write logic it exercises (4.1) can be built and unit-tested against the standalone check function beforehand. The **successful**-write audit task has been moved to Section 5 (immediately after Task 5.4) because, unlike the denial path, it has no such independence — it writes inside a database transaction that doesn't exist until Task 5.4 creates it, so placing it here would be a forward reference to code two sections away. See Tasks 5.4.1/5.4.2.
