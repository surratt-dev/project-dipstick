## Context

Issue #48 (`default-topic-provisioning`) copies the canonical default topic set into every new team's own `topics` rows at team-creation time, and its spec closes with a deliberate statement that no "locked" column or record is written anywhere: whether a team's topic configuration is customizable is a *derived* fact, owned by whichever capability enforces it. This change is that capability. It has two parts that only make sense bundled together: a reusable, server-side lock check (#49), and the first topic-write endpoint that check ever needs to gate (#50, `TOPIC-003` — Add Custom Topic). A lock with nothing to protect is a promise, not a mechanism.

The relevant contract surface (`requirements/design/REST API Contract.md`, Group 3: Topic Management) was already drafted and reviewed against FR-8.1–FR-8.6 with a "Covered" disposition in the Validation Report. This design does not redraw that surface; it implements it, with three corrections stated explicitly below (Decision 2's `403`/`409` split, Decision 3's precondition-text correction, and the `name`-field gap carried in from exploration) rather than silently diverged from.

**Constraints carried in from exploration, not re-derived here** (see `exploration-notes.md` §§3–8 for full reasoning; this document states the resulting decisions):
- `name` is a required field on Add Custom Topic, distinct from `prompt` — a use-case documentation gap, not a design choice.
- Authorization is the standing, org-wide facilitator model (Philosophy 1): `global_role = 'facilitator'` AND the caller is not an active member of the team AND (for writes) the lock is not active.
- Lock rejection is `409 Conflict`; `403 Forbidden` is reserved for identity/role failures and is evaluated (and returned) first.
- `isCustomizationLocked` must be added to the already-shipped `GET /api/v1/teams/:teamId/topics` response.
- One reusable function computes the lock state for both the read-side flag and the write-side gate.
- Denied lock-bypass attempts are audited, synchronously, before the response is sent.

**Picking this up as Solution Architect (Ingrid Sollenberger), incorporating two independent design reviews.** `design-review-engineer.md` (Marcus Oyelaran) and `design-review-security.md` (Tomás Ferreira) both came back with findings that are compatible, not conflicting: a real concurrency bug in Decision 10's `displayOrder` race mitigation that would surface as a caller-visible `500` under load (fixed below, not merely amended); a response-shape decision (Decision 4) that reinvented a body shape this codebase already has; a check-ordering decision (Decision 9) that arrived at a correct answer without citing the one existing endpoint that already answered the same question; a missing timing-floor requirement that would reopen the exact enumeration risk Decision 9 exists to close; a missing audit trail on the successful-write path, when the denial path was already audited; a real, previously-unstated asymmetry between this change's read-side and write-side authorization on the same resource; and two previously-silent gaps (deactivated teams, rate-limiting/audit-failure handling on the denial path) that both reviews expect a stated decision on, not silence. Each is resolved as a stated decision below, not left as an open question — the same standard this document already holds itself to for the ten decisions Marcus's review confirmed as sound.

## Goals / Non-Goals

**Goals:**
- Make the topic-customization lock a real, server-enforced precondition that cannot be bypassed by any client behavior, including a direct API call.
- Expose the lock state on the read side (`TOPIC-001`) so a correctly built frontend can hide write controls without a wasted round trip, and give a stale/bypassing client a response it can render into a specific explanation, not a bare status code.
- Ship the first topic-write endpoint (`TOPIC-003`, Add Custom Topic) against that gate, establishing the pattern `TOPIC-004`–`TOPIC-007` (out of scope here) will reuse.
- Leave a paper trail for every decision that deviates from the contract's literal text or resolves a gap in it, so none of this gets rediscovered as an open question later.

**Non-Goals:**
- No remove, reorder, annotate, or re-add endpoints (`TOPIC-004`, `TOPIC-005`, `TOPIC-006`, `TOPIC-007`). Built later, against the same lock-check helper.
- No frontend UI (issues #51–#55).
- No schema migration. `topics` already has every column `TOPIC-003` needs (`name`, `prompt`, `vote_type`, `display_order`, `status`, `is_default`, `first_session_description`), confirmed against `packages/backend/migrations/2_create_tables.sql`.
- No real-time unlock push. The use case's own alternate flow marks this a nice-to-have, not a requirement; see Decision 7.
- No decision on `TEAM-002` lock exposure or topic attribution — both are named as open questions below, not resolved here.

## Decisions

### Decision 1 — Single reusable lock-check function, not two independent queries

**Decision:** One function, e.g. `hasCompletedFirstSession(teamId): Promise<boolean>` (naming/location an implementation detail — parallel in spirit to `packages/backend/src/auth/team-content-access-helper.ts`), performs a live, uncached `SELECT` for `COUNT(*) FROM sessions WHERE team_id = :teamId AND status = 'complete'` and returns whether that count is greater than zero (i.e., whether customization is unlocked). Both the `TOPIC-001` read-side `isCustomizationLocked` field and the `TOPIC-003` write-side precondition call this same function. No handler is permitted to inline its own `COUNT(*)`/`EXISTS` query against `sessions.status = 'complete'`.

**Why:** Two independently written queries computing the same derived fact is exactly how drift happens — one query quietly starts including `abandoned` sessions, or excludes a status the other includes, and a facilitator sees the read-side view say "unlocked" while the write-side gate still says "locked," or vice versa. A single function makes that class of bug structurally impossible rather than something a future code review has to keep catching.

**Alternatives considered:**
- *Two queries, kept in sync by convention/comments.* Rejected — this is the drift risk itself, not a mitigation of it.
- *Cache the result per team for the request lifetime or longer.* Rejected — matches this codebase's existing principle (`team-content-access` spec: "MUST execute a live database read on every call... MUST NOT be cached at any layer") for the structurally identical question of authorization state. The lock's very first moment of becoming `false` — the instant the first session's completion transaction commits — is exactly the moment correctness matters most, and a stale cache is the failure mode this rule exists to prevent.

### Decision 2 — Lock rejection is `409 Conflict`; `403 Forbidden` is reserved for identity/role failures, checked first

**Decision:** A write request against a locked team, from an otherwise-authorized standing facilitator, is rejected with `409 Conflict`. `403 Forbidden` is reserved for actor-identity/role failures (`global_role != 'facilitator'`, or the facilitator is an active member of the team) and is evaluated — and returned — *before* the lock check ever runs. This is a stated correction to the REST API Contract's literal `403`-for-everything text in `TOPIC-003`'s error table (and the analogous text in `TOPIC-004`/`TOPIC-006`, out of scope here but built against the same gate later).

**Why:** The lock is a derived fact about the team's session history — a state precondition — not a fact about who the caller is. This codebase already distinguishes these two failure categories with different status codes elsewhere (`action-item-owner-reassignment`'s resolved-item guard is `409`, not `403`; `session-topic-lifecycle`'s `already_revealed`/`advance_blocked` responses follow the same pattern). Checking identity/role first, and only checking the lock once identity/role has already passed, means lock state never leaks to a caller who was never going to be authorized on this team regardless — an unauthorized caller gets the same `403` whether the team happens to be locked or not.

**Alternatives considered:**
- *Ship the contract's literal `403` for the lock case, matching the written document exactly.* Rejected — this was never independently reviewed as its own line item in the Validation Report (unlike the authorization clause, which was reviewed and marked "Covered" with no caveat), so it's a genuine gap in the contract, not a stable, already-blessed answer. Silently diverging from it — implementing `409` in code while the contract still says `403` — would be worse than either shipping the contract's literal text or correcting it on the record. This decision corrects the contract.

### Decision 3 — Authorization model: standing, org-wide facilitator (Philosophy 1), traceability note carried verbatim

**Decision:** Both the lock check (#49) and the write endpoint (#50) use: `global_role = 'facilitator'` AND the authenticated user is NOT an active member of the target team AND (writes only) `isCustomizationLocked = false`. This is the REST API Contract's Group 3 clause exactly as drafted on 2026-03-08 and marked "Covered" against FR-8.2 with no caveat.

> Authorization for TOPIC-003 follows the pre-existing, unrevised REST API Contract clause for Group 3 endpoints. The narrower session-scoped model introduced by `action-item-owner-reassignment` was a locally-justified reuse decision for the action-item resource family and was never generalized in that change's spec or design.md; it does not apply here, and adopting it would conflict with the "usable between sessions" requirement in "View Active Topic Configuration."

**Why:** Topics are explicitly a between-sessions resource (see "View Active Topic Configuration"'s own notes: topic management must be usable outside a live session for the feature to be useful at all). `action-item-owner-reassignment`'s narrower, session-scoped authorization pattern was chosen for the action-item resource family specifically because it reuses `VOTE-002`'s existing pattern for that resource — its own spec frames the choice as a local reuse decision, not a general successor doctrine for all future facilitator-write endpoints. Generalizing it here would conflict with the requirement that topic management works between sessions, where there is no "current session" to scope authorization against. Philosophy 1 also matches this codebase's existing rationale for `TEAM-002`/session-creation's org-wide facilitator latitude: facilitators rotate across teams by design, specifically to satisfy the facilitator-from-another-team rule, so a standing, cross-team facilitator relationship to *unlocked* teams is the intended shape of the access, not an oversight.

**Scope note, stated on the record:** this authorization model means any facilitator, anywhere, can add a topic to any unlocked team's configuration — no requirement that they have ever run a session for that team. That breadth is real, but it is the stable, already-reviewed answer to a question about *which facilitator accounts can configure a team's topic list*, not a new erosion of anything ritual-integrity-related — it does not touch vote secrecy, the no-manager rule, or the no-individual-performance-comparison guardrail. It does, however, motivate Open Question 2 below (attribution).

**Correction, stated on the record (the third of the three named in Context):** the "Add Custom Topic" use case's own Preconditions section reads "The Facilitator is accessing the topic management area for the team **they are facilitating**" — plain language that implies an existing facilitation relationship with that specific team. That is narrower than Philosophy 1 as adopted above, and it is the one use case in `08 - Topic Management - Use Cases.md` whose precondition text reads this way: "Remove a Topic," "Reorder Topics," "Annotate Topic," and "Re-Add a Previously Removed Topic" all use the neutral "the Facilitator is authenticated" framing with no facilitation-relationship claim, and "View Active Topic Configuration" uses the broader, model-consistent "any team they are eligible to facilitate." This is corrected, not silently diverged from: the use case's precondition is updated to match the standing, org-wide model this decision already adopts (task 6.3). The correction does not change the decision itself — Philosophy 1 remains the answer, for the reasons above — it only brings the use case's own text into agreement with it.

**Related, lower-priority note (not counted as a fourth correction):** the sibling "Enforce Topic Customization Lock for First Session" use case describes the server-side lock rejection as "an authorization error" in its Alternate Flow. Decision 2 above treats that rejection as a state-precondition failure (`409`), explicitly not an authorization failure (`403`) — the same category of drift as the REST API Contract's blanket-`403` text that Decision 2 corrects, just documented in a different source file. Folded into the same documentation-correction pass (task 6.4) rather than raised as a separate open question.

**Alternatives considered:**
- *Philosophy 2 — session-scoped facilitator (must currently hold an active session for the team).* Rejected per the traceability note above: it was never a general doctrine, and it directly conflicts with topic management's own "usable between sessions" requirement.

### Decision 4 — Rejection response body: the codebase's standard error envelope, with a machine-readable reason code and a stable message string for the lock case

**Decision:** Every rejected write returns this codebase's standard error envelope — `{ error: { category, code, message, correlationId } }` — the same shape `teams.ts`'s `GLOBAL_ROLE_PRECONDITION_NOT_MET` `409` and its `TEAM006_BURST_LIMIT_EXCEEDED` `429` already use, not a new top-level shape. `error.code` distinguishes the specific rejection cause: `NOT_A_FACILITATOR` and `FACILITATOR_IS_TEAM_MEMBER` (`error.category: "forbidden"`) for the two `403`s, and `TOPIC_CUSTOMIZATION_LOCKED` (`error.category: "precondition_failed"`) for the `409` — matching `action-items.ts`'s own `precondition_failed` category for its resolved-item terminal-state `409` guard. `error.correlationId` is a fresh UUID per response, as it is everywhere else this envelope is used. For `TOPIC_CUSTOMIZATION_LOCKED` specifically, `error.message` is a stable, server-driven literal, not ad hoc per-request text:

> `"Topics cannot be customized until this team's first session is completed."`

This same message string, and the `isCustomizationLocked` field it is keyed off, are also what `TOPIC-001`'s read-side response makes available for the calm, non-error "not yet" view a facilitator sees on a locked team's topic screen — but the two are not the same field shape and are not designed as if they were: `isCustomizationLocked` is a plain top-level boolean on the `200` body; `TOPIC_CUSTOMIZATION_LOCKED`'s message lives nested at `error.message` on the `409` body, inside the envelope above.

**Why:** A bare `403`/`409` cannot drive three different plain-language explanations — a future frontend (issue #55) needs a field to switch on, not a number to guess a sentence from. Treating the lock message as a stable contract value (not placeholder prose a frontend writes on its own) means #55 can render it verbatim rather than inventing copy that could drift from the actual rule. The literal wording of anything beyond this fixed string — explaining *why* the rule exists, not just *that* it applies — is UI copy work for #55, once a frontend exists to render it in; this change's job is to make sure the field exists and is driven by server state.

**Corrected, on the record (engineer review M1):** the version of this decision the engineer review evaluated specified a bare, top-level `{ code, message }` body, with no `category` and no `correlationId`. That would have been a fourth, differently-shaped error body in this codebase, alongside the three that already exist — the plain `error.category/message/correlationId` envelope `action-items.ts`/`content.ts` use with no `code`; that same envelope extended with `error.code`, which `teams.ts` already uses for exactly this need (a `409`/`429` that needs a machine-readable reason code alongside its message); and the flat, `errorState`-discriminated bodies used for `SessionAlreadyExistsResponse`/`TeamAlreadyExistsResponse`/`RevealFailureResponse`. `teams.ts`'s envelope-plus-`code` shape already solves the identical problem this decision exists to solve, so this decision now reuses it rather than inventing a fourth. This is a correction, not a silent divergence: the original draft simply didn't know the precedent existed, and the review caught it before a frontend or a shared-types definition got written against the wrong shape.

**Alternatives considered:**
- *Bare top-level `{ code, message }`, no envelope.* Rejected on review — reinvents a shape (`teams.ts`'s `error.code` pattern) this codebase already has for exactly this need, with no stated reason to diverge from it.
- *Status code alone, no body-level reason code.* Rejected — it can't distinguish three causes that need three different sentences.

### Decision 5 — Route placement: new `topics.ts` route file

**Decision:** `POST /api/v1/teams/:teamId/topics` is implemented in a new `packages/backend/src/routes/topics.ts` file, registered in `app.ts` alongside the other route modules, rather than added to `content.ts`.

**Why:** `content.ts` today owns only read endpoints, and its own file-level comment describes it as team-content read routes with a specific authorization/timing-floor pattern (`evaluateTeamAccess`, `denyNullGrant`, `applyTimingFloor`) built for multi-role read access. `TOPIC-003`'s authorization model (Decision 3) and rejection shape (Decision 4) are different enough — standing facilitator only, no participant/EM/admin branches, `409` for a state precondition — that folding it into `content.ts` would mean a file named for read-only content delivery growing a write endpoint with a materially different auth pattern. `action-items.ts` is this codebase's existing precedent for "one file per resource family, reads and writes together" once a resource has both; `topics.ts` starts that pattern for topics. The existing `GET /api/v1/teams/:teamId/topics` handler in `content.ts` is *not* moved as part of this change — only its response body changes (Decision 1's `isCustomizationLocked` field) — to keep this change's diff focused; a future change may consolidate all topic routes into `topics.ts` if that becomes worth doing.

**Alternatives considered:**
- *Add the new endpoint directly to `content.ts`.* Rejected for the reason above — judgment call, not a ritual-integrity question, but the asymmetry (read auth pattern vs. write auth pattern) tips it.

**Casing of the existing `GET /topics` response, declined on the record (engineer review m1):** `content.ts`'s current `GET /api/v1/teams/:teamId/topics` handler returns `result.rows` untouched — `vote_type`, `display_order`, etc. remain snake_case, unlike every other mapped response in this codebase. Decision 1 adds `isCustomizationLocked` (camelCase, per both spec deltas' own scenarios) into that same body, making it the one camelCase key sitting next to a list of snake_case ones. This design declines to fix the existing response's casing while the handler is open for Decision 1's change. Reason: remapping `vote_type`/`display_order`/etc. to camelCase would change the *existing, shipped* field names in a response any current consumer of `TOPIC-001` already depends on — a breaking change to an established contract, not an additive one, contradicting this change's own Migration Plan claim that the new field is "additive, non-breaking for any existing consumer that ignores unknown fields." A full casing rewrite would also be an unrelated cleanup riding along on this change's diff rather than something either spec delta asks for. Left as a pre-existing inconsistency, not resolved here; a future change can remap the whole response's casing as a deliberate, reviewed, frontend-coordinated decision if that is judged worth doing on its own.

### Decision 6 — No row-level locking on the lock check

**Decision:** The lock check is a plain, uncached read (`SELECT COUNT(*) ... = 0`) with no `SELECT ... FOR UPDATE` or equivalent row lock.

**Why:** Unlike `session-topic-lifecycle`'s reveal race — a genuine concurrent-write correctness problem where two clients could both win a race to reveal — the thing being raced against here (a session's transition to `complete`) is itself a one-way, already-guarded transition enforced elsewhere (`SESSION-006`). The worst case of a race between "check the lock" and "a session completes" is that a write request evaluated microseconds before completion is rejected as locked, even though the team unlocks microseconds later — a false negative that costs the caller a retry, not a false positive that could ever let an edit through against a genuinely-still-locked team. That asymmetry means a plain read is sufficient.

**Alternatives considered:**
- *`SELECT ... FOR UPDATE` on the lock check.* Rejected — no correctness property depends on it; it would add contention for no protective benefit.

### Decision 7 — No real-time unlock push

**Decision:** No WebSocket event is added to notify an open topic-management screen that the lock has just lifted. A facilitator viewing the locked screen when the first session completes sees the unlock only on next navigation or reload.

**Why:** The use case's own Alternate Flows section states this explicitly: "real-time unlock is a nice-to-have, not a requirement." Confirmed here, on the record, as an intentional absence rather than a gap someone re-derives later — matching how `action-item-owner-reassignment` explicitly names "no broadcast is published" as a deliberate, confirmed choice rather than leaving it silently unaddressed.

### Decision 8 — Audit logging: denied lock-bypass attempts, written before the response

**Decision:** Every request rejected under the customization lock (`409`, `TOPIC_CUSTOMIZATION_LOCKED`) writes a synchronous `audit_log` row (`operation = 'topic.write_denied_locked'`) before the response is sent to the caller. The row carries `actor_user_id`, `actor_global_role`, `actor_ip`, `team_id`, and `metadata` including at minimum the endpoint and the attempted operation.

**Why:** This is the same shape of event this codebase already audits elsewhere — `TEAM-005`'s promotion-block writes `team.role_change_denied` before responding, for the same reason: a blocked attempt on a privileged boundary is itself a security-relevant fact, not just the resource state it failed to change. Beyond the integrity record, it's part of the same continuity value session history and trend data already provide: a facilitator returning to a team after months away, or taking over from a prior facilitator, can see that a bypass was attempted and correctly stopped before the lock lifted, without that visibility needing its own UI in this change.

**Alternatives considered:**
- *Audit only successful writes, not denials.* Rejected — the denial is the exact event this feature exists to make sure never fails silently; auditing only success would make a fully-blocked bypass campaign invisible in the trail.

**Amended following security review Finding 3: successful writes are audited too, not only denials.** As originally drafted, this decision audited the `409` denial path and left the success path with no `audit_log` row at all — `created_at` and nothing else. That is a real non-repudiation gap, not an equivalent-and-acceptable omission, and it is not the same cost trade-off Open Question 2 describes below: Open Question 2 is about whether `topics` gets a `created_by` schema column and a corresponding response field — a migration and an API-contract decision, genuinely deferrable. The `audit_log` table needs no migration; it already has every column this event needs (`actor_user_id`, `actor_global_role`, `actor_ip`, `team_id`, `metadata`), and this decision is already writing to it, in this same file, for the denial branch.

**Decision:** every successful Add Custom Topic write also writes an `audit_log` row — `operation = 'topic.custom_added'` — inside the same database transaction as the topic `INSERT` (i.e., the same transaction Decision 10's advisory-lock-guarded `MAX`-read-and-insert runs in). The row carries `actor_user_id`, `actor_global_role`, `actor_ip`, `team_id`, and `metadata: { topic_id }` at minimum.

**Why:** matches this codebase's established shape for "an access/existence-establishing event audited in the same transaction as the rows it authorizes" — `session.draft_created` and `team.created_with_session` are the direct precedent. Decision 3's standing, org-wide facilitator model means any facilitator, with no requirement of ever having run a session for the team, can trigger this success path; that breadth is exactly what makes a missing audit trail on the success path matter more here than on a narrower endpoint (a custom topic later found to be inappropriate or planted by a compromised credential otherwise has no way to answer "who, from every facilitator in the organization, wrote this"). Skipping the success-path write while shipping the denial-path write would leave that question unanswerable for the case that actually changes the team's configuration, while answering it fully for the case that didn't.

**Alternatives considered (added):**
- *Defer the success audit alongside Open Question 2's `created_by` column, since both are about "who did this."* Rejected — the audit row and the `topics.created_by` column solve different problems at different costs. The column needs a migration and a client-visible response-shape decision, which is genuinely deferrable scope; the audit row needs neither, and costs five lines in a file this change is already opening for the identical write on the denial branch.

### Decision 9 — Full check-ordering cascade for `TOPIC-003`: identity/role (`403`) → team existence (`404`) → lock (`409`) → body validation (`422`)

**Decision:** `TOPIC-003` evaluates checks in exactly this order, short-circuiting on the first failure and never evaluating (or reporting the result of) a later check once an earlier one has already failed:

1. Identity/role authorization — `global_role = 'facilitator'` AND not an active member of the target team (Decision 3). Failure → `403 Forbidden` (`NOT_A_FACILITATOR` or `FACILITATOR_IS_TEAM_MEMBER`).
2. Team existence — the `teamId` path parameter references an existing team. Failure → `404 Not Found`.
3. Customization lock — the shared lock-check function (Decision 1) returns unlocked. Failure → `409 Conflict` (`TOPIC_CUSTOMIZATION_LOCKED`, Decision 2).
4. Request body validation — `name`, `prompt`, `voteType`, and (if present) `firstSessionDescription` all satisfy their field rules. Failure → `422 Unprocessable Entity`.

**Why:** Two gaps neither the REST API Contract nor this design previously stated explicitly.

*Where `404` sits.* The contract's `TOPIC-003` error table lists `404 Not Found | Team does not exist`, but nothing in the contract, this design, the spec deltas, or `tasks.md` said where that check sits relative to `403`/`409`. Left unstated, a request against a nonexistent `teamId` would fall through both existing checks by default: the membership lookup in step 1 returns no rows for a nonexistent team (vacuously "not a member," so identity/role passes), and the lock-check's session count in step 3 is also vacuously zero (vacuously "locked"), so the request would be rejected `409` — or, absent even that, the insert itself would fail the `topics.team_id` foreign key as an unhandled `500`. Neither matches the contract's documented `404`.

This codebase's own precedent for this exact class of question is `action-item-owner-reassignment`'s explicit cascade, which returns `404` for any caller with "zero relationship" to a resource's team, specifically to close an enumeration oracle: it prevents a caller from distinguishing "this doesn't exist" from "it exists, but it isn't yours." That precedent's *literal* technique — folding "doesn't exist" and "not yours" into one `404` — does not transfer here, because Decision 3 deliberately rejected the relationship-scoped model it depends on: under Philosophy 1, no facilitator has a narrower or broader claim on one unlocked team than another, so there is no "not yours" population among facilitators for a `404` to hide anything from.

What *does* transfer is the precedent's underlying principle, and it's the same principle Decision 2 already applies once: a check that reveals nothing about a specific team should run before one that does. Identity/role authorization reveals nothing about any specific team — a non-facilitator's `403 NOT_A_FACILITATOR` fires identically whether the target team exists, is locked, or was never real, without the check ever touching the team table. Team existence is therefore evaluated immediately after identity/role, not before it: a caller who was never going to be authorized regardless of team never learns whether that team exists — the same leak-prevention logic Decision 2 already uses for lock state, extended one step earlier in the chain. A facilitator who clears identity/role but targets a team that turns out not to exist learns only that fact, which is not a leak: Philosophy 1 already grants every facilitator equal standing to know that much about every team.

*Where `422` sits.* `tasks.md`'s original task sequencing (validate the body, then check authorization/lock) implied validation ran first. That would tell a caller who was never going to be authorized, or who was targeting a locked team, exactly what was wrong with their `name` field before telling them they were never going to be allowed to write at all — the identical information-leak shape Decision 2 already solved for `403` vs. `409`, one link further down the chain. Body validation is therefore evaluated last, after identity/role, team existence, and the lock have all passed.

**Alternatives considered:**
- *Check team existence (`404`) before identity/role (`403`).* Considered, since it's the most literal reading of "does 404 come before or after 403" and matches the order in which a request handler might naturally load its path parameters. Rejected: it would tell a non-facilitator whether a specific team exists before telling them their role disqualifies them regardless — exactly the kind of team-specific fact Decision 2 already established shouldn't leak to a caller who was never going to be authorized. Role-first achieves the same outcome for every legitimately-interested caller while leaking strictly less to everyone else.
- *Leave `422` ordered before `403`/`409`, matching `tasks.md`'s incidental original sequencing.* Rejected as a real information leak (per Marcus's review), not merely a stylistic implementation-order choice.

**Precedent and extraction, stated on the record (engineer review M2).** This ordering is not a novel question this codebase is facing for the first time, and this decision should not read as though it were. `facilitator-sessions.ts`'s `POST /api/v1/teams/:teamId/sessions/draft` — the only other endpoint in this codebase using Decision 3's identical standing-facilitator-not-a-member model — already ships a check order for this exact combination: role (`403`) → team existence (`404`) → membership-conflict (`403`); i.e., team existence sits *between* the two `403` checks there, not after both of them, which is not literally the same ordering as this decision's role-`403`-then-membership-`403` both before existence-`404`. The two orderings are not a behavioral conflict, for a structural reason worth stating rather than leaving for the next reader to re-derive independently: `team_memberships.team_id` carries a `NOT NULL REFERENCES teams(id)` foreign key, so a membership row can only ever exist for a team that already exists. A nonexistent `teamId` therefore evaluates "not a member" vacuously true under both orderings — there is no real caller for whom the two orderings produce a different status code. Decision 9's ordering is correct as stated; it is a reordering of an existing, already-shipped precedent that happens to be behaviorally identical for every real caller because of that FK, not an independent answer arrived at from first principles alone, and it should have said so.

That precedent's authorization query — a single round trip joining `users` and `team_memberships` to resolve `global_role` and `is_member` together (`facilitator-sessions.ts` lines 261-271) — is also the concrete SQL Task 3.1's identity/role check reuses, rather than re-deriving a third independent copy of the same query (`teams.ts`'s EM-dual-check variant is the second). Either `topics.ts` calls the same query `POST /draft` already runs, or both are refactored to call a newly extracted helper (e.g. `evaluateStandingFacilitatorAccess(userId, teamId)`) — the exact location/naming is an implementation detail left to Task 3.1 — but the requirement stated here is: one query, not a third hand-written copy of it, for the identical drift-risk reason Decision 1 already states for the lock check (one query in `sessions_team_active_unique`-adjacent code drifting from another is exactly how a `deactivated_at` filter ends up on one copy and not the other — see Decision 11 below).

**Amended following security review Finding 1: every early-return in this cascade also applies the timing floor.** Decision 9's status-code logic is correct on its own terms — a caller who fails identity/role gets an identical `403` regardless of the target team's existence or lock state, so no *status code* leaks team-specific information to a caller who was never going to be authorized. But status code and response latency are two different channels, and this codebase already has a standing, written policy that closing one without the other does not close the oracle: `packages/backend/src/content/timing-oracle.ts`'s own header calls the timing floor "a BLOCKING design requirement," and `content.ts`/`action-items.ts`/`em-views.ts` all call `applyTimingFloor` at every early-return, `403` included. Decision 9's own four-step cascade does strictly more database work at each successive step — a role/membership lookup, then a team-existence lookup, then the lock-check's `COUNT(*)` aggregate over `sessions` — which is precisely the shape of side channel the floor exists to flatten. As specified, a non-facilitator's `403` should already be fast by construction (it never reaches steps 2-4), but "should be, if the short-circuiting is implemented exactly as written, with zero incidental work that scales with which branch is taken" is not this codebase's bar for this property anywhere else it applies this ordering technique — it wasn't sufficient for `action-item-owner-reassignment`'s identical enumeration-resistant ordering either (that change's own design.md records the same amendment, for the same reason, citing the same file).

**Decision:** every early-return path in the new `topics.ts` handler — the `403` at identity/role, the `404` at team existence, the `409` at the lock, and the `422` at body validation — records a `startTime` at handler entry and calls `applyTimingFloor(startTime)` immediately before every response, success (`201`) included, with no branch exempted. Task 5.6's tests are extended with a timing-side-channel assertion (mirroring `content/__tests__/timing-oracle.test.ts`'s existing pattern) that the `403` path is not detectably faster than the `404`/`409`/`422` paths.

**Alternatives considered (added):**
- *Rely on the short-circuiting being cheap enough that the difference is unlikely to be measurable.* Rejected — this is precisely the standard this codebase's own written policy already rejected for every other content/action-item endpoint; "unlikely to be measurable, if implemented exactly as specified" is not this codebase's bar, and a timing side-channel test is trivial to write once the requirement is written down, so there is no cost reason to accept the risk instead.

### Decision 10 — Concurrent `displayOrder` assignment is serialized within the insert transaction via a per-team advisory lock, not a row-level `FOR UPDATE`

**Corrected, on the record (engineer review B1 — blocking).** The previously-specified mitigation for this decision — `SELECT display_order FROM topics WHERE team_id = $1 AND status = 'active' ORDER BY display_order DESC LIMIT 1 FOR UPDATE` — does not close the race it was written to close, and this is a correctness bug in the design, not a style nit. `FOR UPDATE`'s wait-then-recheck behavior re-verifies only the specific row(s) already selected by the query's initial scan against the `WHERE` clause once the lock holder commits; it does not re-run the `ORDER BY ... LIMIT 1` ranking against the table's newly committed state. Concretely, for two concurrent requests against a team with active topics at `display_order` 1-12: transactions A and B both rank the same existing row (12) as "the max" and both attempt to lock it; A wins the lock, computes `next = 13`, inserts a **new** row 13, and commits — row 12 itself is never modified. B was blocked on row 12's lock, not on row 13 (which didn't exist yet when B's scan ran). B unblocks, re-checks row 12 — still unchanged — and independently computes `next = 13` too, colliding with A's already-committed row on the `topics_team_order` unique constraint: an unhandled `23505` surfacing as a `500`, exactly the failure this decision exists to prevent. The row lock correctly forces B to wait for A; it does not give B a fresh read of the value it needs after waiting, because that value lives in a row that didn't exist when B's snapshot was taken. A wider `FOR UPDATE` over the full candidate set (no `LIMIT`) has the identical flaw, for the identical MVCC reason — the candidate row set is still fixed at the original snapshot and never grows to include a row inserted afterward. This is fixed by locking the team itself, not a row whose relevant successor doesn't exist yet.

**Decision:** the `displayOrder = max(current active displayOrder) + 1` computation and the topic `INSERT` run inside the same database transaction, guarded by a Postgres advisory transaction lock taken on the target team before the `MAX` read:

```sql
BEGIN;
SELECT pg_advisory_xact_lock(hashtext($1::text));  -- $1 = teamId

SELECT COALESCE(MAX(display_order), -1) + 1 AS next_display_order
FROM topics
WHERE team_id = $1 AND status = 'active';

INSERT INTO topics
  (team_id, name, prompt, vote_type, display_order, status, is_default, first_session_description)
VALUES ($1, $2, $3, $4, /* next_display_order */, 'active', false, $5);

COMMIT;
```

`pg_advisory_xact_lock` is held for the duration of the transaction and released automatically on `COMMIT`/`ROLLBACK` — no separate unlock call, and no risk of leaking the lock past the request. A second concurrent Add Custom Topic request against the same team blocks on `pg_advisory_xact_lock` until the first transaction commits or rolls back. Critically, its own `MAX` read is not merely unblocked-and-rechecked against a stale scan — it is not *issued* at all until after the lock is granted, so it runs as a fresh statement against the now-committed state (including the sibling's newly inserted row) under READ COMMITTED's per-statement snapshot rules. Two concurrent requests against the same team can therefore never compute the same `displayOrder`. `hashtext()` maps the UUID `teamId` to a 32-bit integer lock key; a 32-bit hash collision between two different teams' keys would only ever force unnecessary serialization between those two teams' otherwise-unrelated requests, never a correctness failure — the lock is a pessimistic gate, not a data value.

The mitigation remains deliberately scoped to the team named in the request: two callers targeting different teams never contend on the same advisory-lock key (modulo the negligible hash-collision case above), so this adds contention only between two callers who would otherwise collide on the same team at the same instant, not as a standing cost on every request.

**Why the advisory lock over the alternative (catch-and-retry on `23505`):** both close the race correctly; this design adopts the advisory lock, but the alternative is not rejected on correctness grounds. Catch-and-retry on `err.code === "23505"` (matched against the `topics_team_order` constraint) is this codebase's own established idiom for the identical class of problem — `facilitator-sessions.ts`'s `POST /api/v1/teams` catches `23505` on `teams_name_unique`/`teams_name_unique_normalized` via a scoped `TeamNameCollisionSignal` marker, and its `POST /api/v1/teams/:teamId/sessions/draft` catches `23505` on `sessions_team_active_unique` by `err.code`/`err.constraint`, in both cases turning the collision into a clean, already-tested response. That precedent is genuine, and reusing it here would have been an equally correct fix — the retried `SELECT MAX(display_order)` would run after the collision, under READ COMMITTED's fresh-per-statement snapshot, and would correctly see the sibling's now-committed row. The advisory lock is preferred here for a narrower, endpoint-specific reason: it prevents the collision from ever occurring, rather than detecting and recovering from it after the fact, so the transaction never partially fails and restarts — no "roll back, re-run the read, re-run the insert, hope the second attempt doesn't collide too" control flow, and no need to distinguish this specific constraint violation from any other insert failure inside a `catch` block. It composes as a one-line addition (`pg_advisory_xact_lock(hashtext(teamId))`, first statement inside the existing `BEGIN`/`COMMIT` transaction shape already used throughout this codebase) rather than a new retry loop.

**Known residual gap, named rather than left silent (unchanged in substance from the prior version of this decision, now closed rather than merely acknowledged):** the previous `FOR UPDATE`-on-a-row mitigation locked an *existing* row, so it had nothing to lock — and serialized nothing — when a team had zero active topics. The advisory lock does not share that gap: it is keyed on the team itself, not on any topic row's existence, so it serializes correctly even against a team with zero active topics. That state remains unreachable today (every team is provisioned with the full default set per `default-topic-provisioning`, issue #48, and no endpoint shipped so far, or added by this change, can remove a topic) and becomes reachable once `TOPIC-004` (Archive Topic, out of scope here) ships against this same insertion path — worth stating explicitly so whoever builds `TOPIC-004` doesn't need to re-derive that this decision already covers the zero-active-topics case, unlike its predecessor.

**Alternatives considered:**
- *Catch-and-retry on the `23505` unique violation.* Not rejected on correctness — a fully valid fix, and this codebase's established idiom for the same problem shape (see "Why," above). Not adopted here specifically because the advisory lock prevents the collision outright rather than detecting and retrying after a partial transaction failure, with no error-code-sniffing required — a smaller, more contained change to Task 5.4's transaction body.
- *`SELECT ... FOR UPDATE` on the single highest-ordered row (`ORDER BY display_order DESC LIMIT 1 FOR UPDATE`).* This was the design's original mitigation. Rejected per the correction above — it does not serialize the actual race, because the row it locks is never the row the colliding `INSERT` needs a fresh read of.
- *`SELECT ... FOR UPDATE` on the full candidate row set (`WHERE team_id = $1 AND status = 'active'`, no `LIMIT`).* Rejected — the candidate row set is still fixed at the original snapshot and never grows to include a row inserted afterward, for the same MVCC reason the `LIMIT 1` version fails; this is a wider version of the same broken mechanism, not a fix.
- *Accept the race as an equivalent false-negative-only cost, per Decision 6's reasoning.* Rejected — the actual failure mode is a caller-visible, unhandled `500`, not a clean, retryable rejection; Decision 6's justification (a harmless retry) doesn't hold for this race.

### Decision 11 — Deactivated teams are not filtered by the write endpoint's existence check

**Decision:** the team-existence check (Task 3.2, Decision 9 step 2) is `SELECT id FROM teams WHERE id = $1` — it does not filter on `deactivated_at IS NOT NULL`. A deactivated team is treated as "exists" for `POST /api/v1/teams/:teamId/topics`, exactly as it already is for `POST /teams/:teamId/sessions/draft`'s identical existence check. A facilitator can therefore successfully add a custom topic to a deactivated team.

**Why:** this is a stated call, not an inherited default — raised by engineer review M3, which correctly points out that neither this design nor `tasks.md` said anything about it, so a copy-pasted existence check would have silently decided the question by omission. Every existing write-adjacent existence check in this codebase (`POST /draft`, `teams.ts`'s manager-association flow) treats deactivation as orthogonal to the specific precondition each endpoint enforces. The one exception, `GET /api/v1/teams/facilitatable` (`facilitator-sessions.ts:2238`), filters `deactivated_at IS NULL` because that endpoint's job is specifically to list teams a facilitator can currently choose to act on — a listing/discovery concern, not a resource-existence concern. `TOPIC-003` is the latter kind of check: nothing in FR-8.x, the REST API Contract, or either spec delta in this change ties topic customization's precondition to team activation status, and topic customization's own precondition (the lock, Decision 1) is already the deliberate, stated gate for this endpoint — deactivation is a separate lifecycle dimension this change does not touch. Matching the existing precedent (no filter) keeps this endpoint consistent with every other write-adjacent existence check in the codebase rather than introducing a fourth, ad hoc rule about what "exists" means for this one endpoint.

**Alternatives considered:**
- *Filter `deactivated_at IS NOT NULL` and return `404` for a deactivated team.* Rejected — no requirement asks for this, it would make `TOPIC-003`'s existence check the only write-path check in the codebase that treats deactivation as equivalent to nonexistence, and it would silently foreclose a legitimate case (a team is reactivated and its topic configuration should be ready before its next session) without ever having been asked to.

### Decision 12 — The write endpoint's authorization is broader than the read endpoint's on the same resource; the resulting asymmetry is accepted, not reconciled by widening the read side

**Decision:** `GET /api/v1/teams/:teamId/topics` (`content.ts`) keeps its existing authorization — `evaluateTeamAccess`'s three-path model, whose only facilitator-shaped grant (Path 3) requires an active/recent/draft session relationship with that specific team — unchanged by this design. `POST /api/v1/teams/:teamId/topics` (`topics.ts`) uses Decision 3's standing, org-wide model, which requires no session relationship at all. This design does not widen `GET`'s authorization to close the resulting gap.

The gap is real and is stated here rather than left as an emergent side effect of two decisions that don't look at each other (security review Finding 2): a facilitator with no membership and no session history for team X can add a topic to team X (`201`) but cannot view team X's current topic list, display order, or lock state through this endpoint first (`403`, via `denyNullGrant`/`denyCrossTeamFacilitator`) — the identical caller, the identical team, the identical resource, in this same change.

**Why:** the two endpoints are answering different questions on purpose, not by accident, and the asymmetry is a UX cost, not a security one. `GET /topics` (`TOPIC-001`) was scoped and shipped before this change against a general "who may read a team's content" question that `content.ts` answers uniformly across action items, sessions, and topics via one shared helper (`evaluateTeamAccess`); widening that helper's Path 3 — or adding a fourth path — to admit any org-wide facilitator would change read authorization for every other `content.ts` endpoint that reuses it, not just topics, which is a materially larger and differently-scoped change than #49/#50 were filed to make. Decision 3's org-wide write model, by contrast, is the write-side pattern this codebase has already established for the standing-facilitator relationship: `POST /teams/:teamId/sessions/draft` already grants this same org-wide, no-prior-session facilitator population the ability to create — and thereby begin acting on — a draft session for a team they have never read anything about, for the identical underlying reason (facilitators rotate across teams by design). A facilitator adding a topic to a team they have not first viewed through this specific `GET` endpoint is consistent with that existing shape, not a new erosion of it: this application already lets a standing facilitator write session-scoped state to a team before reading anything about it through a sanctioned read path. The cost this asymmetry imposes is real but bounded: the facilitator writing "blind" doesn't see the team's current topic list, order, or lock state before adding one, which may produce an accidental duplicate or an oddly-ordered topic — but it discloses nothing to anyone, and it creates no path for a caller who could never have written the topic in the first place to read one either.

Widening `GET`'s authorization instead was considered and rejected for this change specifically because it raises its own disclosure question — should `isCustomizationLocked` and a team's topic list be visible org-wide to any facilitator? — that has not been asked or answered anywhere in this design, and does not belong in a change whose Non-Goals already exclude `TEAM-002` lock exposure (Open Question 1). If the organization decides read access should be widened to match, that is a future change against `content.ts`'s shared helper, scoped and reviewed on its own terms, not an incidental side effect of shipping `TOPIC-003`.

**Alternatives considered:**
- *Widen `evaluateTeamAccess`'s Path 3 (or add a Path 4) to grant any standing facilitator read access to any unlocked team's topics, matching the write side.* Rejected for this change — correct in principle, larger in scope than #49/#50, and opens the org-wide-read-disclosure question this design isn't the place to resolve.
- *Narrow the write side to require the same session relationship the read side requires.* Rejected — this is Decision 3's Philosophy 2 alternative, already rejected there because it conflicts with topic management's "usable between sessions" requirement and was never a general doctrine in this codebase.

### Decision 13 — Rate limiting and audit-write-failure handling on the denial path: out of scope for this change, stated explicitly

**Decision:** no dedicated rate limit is added to `POST /api/v1/teams/:teamId/topics`'s `409` denial path in this change. Decision 8's (and Decision 8's amendment's) audit writes remain plain, unguarded `db.query`/in-transaction writes with no `withTimeout`/`AUDIT_WRITE_TIMEOUT_MS` bound — if such a write throws or hangs, the handler throws and the caller receives an unhandled `500` instead of the intended `409`/`201`, exactly as `TEAM-005`'s `role_change_denied` precedent already behaves today.

**Why:** security review Finding 4 correctly points out that `TEAM-006`'s `POST /teams/:teamId/managers` — a structurally similar synchronous-audit-before-response shape — received a dedicated, jointly-owned three-tier rate limiter (`q6-rate-limit-decision.md`), and that `TOPIC-003`'s denial path is reachable by a much wider population (any standing facilitator, org-wide, against any team that has never completed a session) than `TEAM-006`'s Application-Admin-only callers. That population difference is real and worth naming rather than assuming away. But the two endpoints' abuse ceilings are not equivalent, and that difference — not the caller-population difference alone — is what this decision turns on: a `TEAM-006` breach's worst case is unauthorized `engineering_manager` role elevation, a privilege-escalation outcome the organization explicitly decided merited a purpose-built limiter. A `TOPIC-003` denial-path breach's worst case is repeated `409`s against a team's own lock — no privilege is escalated, no data is disclosed beyond "this team is locked" (which the caller already knew, being the one testing it), and the lock itself cannot be bypassed by volume. The actual cost is `audit_log` row growth and DB load — the same category of cost `TEAM-005`'s unguarded precedent already accepts today for a narrower caller population. That places `TOPIC-003` closer to `TEAM-005`'s risk profile than to `TEAM-006`'s, and `TEAM-005` carries no rate limit.

This is accepted as a real, if modest, gap, not an oversight: if operational monitoring later shows this endpoint being hit at abusive volume, the fix is additive — an actor-scoped limiter in the same shape `TEAM-006`'s already establishes — and does not require reopening this design's authorization or audit decisions. The audit-write-failure behavior (an unhandled `500` on a DB hiccup during the audit insert) is accepted for the same reason `TEAM-005` accepts it: it fails closed. A failure here cannot pair a successful bypass with a missing audit row, because Decision 8's denial-path write and Decision 8's amendment's success-path write are each in the same transaction/before-response-send as the outcome they record — a failed audit write means no response has been sent yet, not that a response was sent unaudited. This is an availability gap, not an integrity or authorization one.

**Alternatives considered:**
- *Adopt `TEAM-006`'s three-tier actor-scoped limiter wholesale.* Rejected as disproportionate for this change — that limiter was purpose-built and jointly reasoned for a privilege-escalation-capable, admin-only endpoint; reusing it here for a lock-state-only denial path would be over-engineering relative to this endpoint's actual abuse ceiling.
- *Wrap the audit writes in `withTimeout`/`AUDIT_WRITE_TIMEOUT_MS`, matching the fail-open group's mechanism.* Rejected — that mechanism exists specifically for the fail-open group (`auth.success`, `auth.session_created`, `auth.idp_logout_failed`), where failing open is the deliberate choice. `TOPIC-003`'s denial and success paths are not in that group and should not silently start failing open on an audit-write hiccup without that being its own considered decision.

## Risks / Trade-offs

- **[Risk]** Standing, org-wide facilitator authorization (Decision 3) means any facilitator can add a topic to any unlocked team's configuration. → **Mitigation, largely closed:** Decision 8's amendment (security review Finding 3) now writes an `audit_log` row on every successful write, so "who did this and when" is answerable from the audit trail even though `topics` itself carries no `created_by` column. What remains open is narrower than originally stated: whether a `created_by` column and a corresponding *API-visible* attribution field should exist, so a facilitator can see attribution without a separate audit-log lookup — that residual question is Open Question 2 below, not a security gap.
- **[Risk]** A facilitator can write a topic to a team they cannot first view through `GET /api/v1/teams/:teamId/topics`'s own authorization (Decision 12's read/write asymmetry). → **Accepted, on the record:** the cost is a UX gap (writing "blind," with no visibility into current topics/order/lock state first), not a disclosure gap — see Decision 12 for the full reasoning and why widening the read side is out of scope for this change.
- **[Risk]** `POST /api/v1/teams/:teamId/topics`'s `409` denial path has no dedicated rate limit despite an org-wide caller population (Decision 13). → **Accepted, on the record:** the abuse ceiling is `audit_log` growth and DB load, not privilege escalation or disclosure, which is a materially smaller risk than `TEAM-006`'s admin-only endpoint that did receive a dedicated limiter — see Decision 13 for the comparison.
- **[Risk]** A stale client tab, cached frontend state, or a UI bug could still attempt a write against a team that just locked or is still locked, producing a user-visible error instead of a hidden control. → **Mitigation:** this is precisely what Decision 4's reason-code/message contract is for — the error is informative rather than a generic failure, and it's defense-in-depth on top of a frontend that should already be hiding write controls when `isCustomizationLocked` is `true`.
- **[Trade-off]** No real-time unlock notification (Decision 7) means a facilitator who happens to be staring at the locked screen at the exact moment the first session completes has to reload to see the change. → Accepted, per the use case's own explicit nice-to-have framing; revisit only if a future change finds this friction is worse in practice than the use case assumed.

## Migration Plan

No database migration. This is an insert-and-check change against existing schema. Deployment is a normal backend release: the new `topics.ts` route is registered, `content.ts`'s `GET /teams/:teamId/topics` response gains a field (additive, non-breaking for any existing consumer that ignores unknown fields), and the shared lock-check helper is introduced. No data backfill, no feature flag — the lock enforcement is unconditional from the moment this ships (consistent with Devon's standing concern that protective constraints must never be configurable). Rollback is a plain revert; no stateful cleanup is required since no rows are written by the lock mechanism itself (Decision 1 computes the lock, it doesn't store it).

## Open Questions

1. **Should `TEAM-002` (`GET /api/v1/teams/facilitatable`) also expose `isCustomizationLocked`?** Today it returns `lastSessionDate: string | null`, from which a caller can infer "definitely locked" when `null` — but that inference doesn't distinguish "locked" from "no session ever scheduled" as cleanly as an explicit flag would, and it's an inference the frontend has to make rather than a fact the API states. Not a ritual-integrity question — a completeness one. Left open for whoever builds the facilitator-team-list UI to decide against, rather than guessed at here.
2. **Should a custom topic carry a "who added this" attribution column?** `topics` has no `created_by`/`added_facilitator_id` today, and `TOPIC-003`'s response doesn't return one. Decision 8's amendment (security review Finding 3) now records every successful write's actor in `audit_log`, which closes the non-repudiation/security half of this gap — "who did this" is answerable today, just not without an audit-log lookup. What remains open is the narrower, UI-facing half: whether a `created_by` column and a corresponding API-visible field should exist so a facilitator can see attribution in the topic-management screen itself, without that separate lookup. It is cheaper to add this column now, at write-endpoint-creation time, than to retrofit it once historical rows already lack it — but that cost asymmetry is a scope-size judgment call for whoever picks this up, not a ritual-integrity or security call, and is explicitly not resolved in this change.
3. **(Traceability note only, not an open question for this change — security review Finding 5.)** BRD FR-8.2 is a `[HARD]` requirement naming *both* "the facilitator or Application Administrator" as eligible to add/remove/reorder topics after a team's first session (`requirements/BRD.md:323`). Neither the REST API Contract's `TOPIC-003` Authorization line nor Decision 3's Philosophy 1 grants `application_admin` any write path onto topics — the Validation Report's "Covered" disposition for FR-8.2 appears to cover only the facilitator half of a two-actor requirement. This is a pre-existing gap in the contract/validation-report pair this design inherits, not introduced by this change, and it is not fixed here. Noted for the BA/traceability owner: whoever eventually resolves the Application Administrator gap should know FR-8.2 was never fully validated against its own text, independent of anything this change does.
