## Security Review — `topic-customization-lock-and-add-custom-topic` (#49 / #50, `TOPIC-003`)

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope reviewed:** `design.md`, `proposal.md`, `specs/topic-customization-lock/spec.md`, `specs/add-custom-topic/spec.md`, `tasks.md`, cross-checked against `requirements/design/REST API Contract.md` (Group 3, §667–730), `requirements/design/REST API Contract - Validation Report.md`, `requirements/BRD.md` (FR-8.x), `requirements/use cases/08 - Topic Management - Use Cases.md`, and the shipped precedent this design cites or should cite: `packages/backend/src/auth/team-content-access-helper.ts` (`evaluateTeamAccess`), `packages/backend/src/content/timing-oracle.ts` (`applyTimingFloor`), `packages/backend/src/auth/audit-logger.ts`, `packages/backend/src/auth/audit-write-timeout.ts`, `packages/backend/src/routes/content.ts` (the existing `GET /topics` handler this change modifies), and the archived `2026-09-29-reassign-action-item-owner` and `2026-07-07-establish-manager-team-relationship` (Q6 rate-limit decision) changes.

**Overall assessment:** The check-ordering logic (Decision 9) is internally sound given its own premises, and Decision 2's `403`/`409` split is a correct, well-traced application of this codebase's existing house style. I have no objection to the *authorization decisions* themselves — Philosophy 1 is the contract's already-drafted answer, not an invention of this design. My findings are about four things this design is silent or thin on, in the same category as the findings I raised on the `reassign-action-item-owner` review: an enumeration-resistant ordering that never mentions the timing side-channel this codebase has an explicit, blocking policy about; a real read/write authorization asymmetry on the exact resource this change touches, introduced by not revisiting the read side's authorization when Decision 1 already opens that file; a successful, org-wide-facilitator-authored write with no audit trail at all, when this codebase already has a zero-cost precedent for exactly that; and an audited, synchronous-write denial path with no rate-limit discussion, on an endpoint whose caller population (Decision 3's own scope note) is the widest of any write endpoint reviewed to date. None of these invalidate Decision 3 as an authorization choice. They are, respectively, a missing control, a missing reconciliation, a missing five-line addition, and a missing decision paragraph.

---

### Finding 1 (Medium-High) — Decision 9's enumeration-resistant ordering never mentions the timing floor, and that omission repeats a gap I already flagged on this codebase once

Decision 9 explicitly frames its `403 → 404 → 409 → 422` ordering as designed to prevent a caller from learning "whether that team exists" or "whether it is locked" when they were never going to be authorized regardless. The status-code logic is correct: a caller who fails identity/role never reaches the team-existence query or the lock-check query, so no *status code* they receive can vary with the target team.

But status code and response latency are two different channels, and this codebase already has a standing, written policy that closing one without the other is not closing the oracle. `packages/backend/src/content/timing-oracle.ts`'s own header calls this "a BLOCKING design requirement," specifically because "the authorization check returns before the resource lookup for unauthorized callers, [so] denied responses may be detectably faster than authorized responses" — and every handler in `content.ts`, `action-items.ts`, and `em-views.ts` calls `applyTimingFloor` at every early-return point, including the ones that return `403`. Decision 9's own four-step cascade does *strictly more database work* at each successive step — a role/membership lookup, then a team-existence lookup, then the lock-check's `COUNT(*)` aggregate over `sessions` — which is precisely the shape of side channel `applyTimingFloor` exists to close. As specified, a non-facilitator's `403` should already be fast by construction (it never reaches steps 2–3), but "should be, if implemented exactly as specified" is not this codebase's standard for this exact property — I raised this same concern on `reassign-action-item-owner` (Finding 1 there: "'likely' is not what this codebase's own stated policy asks for") when the reused code lived in a file that already imported the floor. Here it's worse in one respect: `topics.ts` is a brand-new file (Decision 5), with no existing import of `applyTimingFloor` to lean on by proximity, and neither `design.md`, the two spec deltas, nor `tasks.md` mentions the floor once.

I checked whether this is actually low-risk because the only population that benefits from flat timing (non-facilitators, and facilitators who are active team members) already gets an unconditional `403` with no team-specific work performed — that reasoning holds *if and only if* the short-circuiting is implemented exactly as written, with zero incidental work (e.g., logging, header construction, or ORM overhead) that scales with which branch is taken. That "if and only if" is exactly the discipline `applyTimingFloor` exists to make unnecessary. This is also the one case in this design where getting it wrong is cheap to catch and expensive to discover later: a load test or a timing side-channel test is trivial to write, once the requirement is written down.

**Recommendation:** Add a decision (or amend Decision 9) stating that every early-return path in the new `topics.ts` handler — the `403` at step 1, the `404` at step 2, the `409` at step 3, and the `422` at step 4 — calls `applyTimingFloor(startTime)` before responding, consistent with `content.ts`/`action-items.ts`. Add a corresponding task (tasks.md 3.5/5.6 currently test only status codes and body content) and a timing-side-channel test asserting the `403` path is not detectably faster than the `404`/`409`/`422` paths, mirroring `content/__tests__/timing-oracle.test.ts`'s existing pattern.

### Finding 2 (Medium) — The write endpoint's authorization is broader than the read endpoint's, on the exact same resource, and neither decision reconciles it

Decision 1 modifies the *existing, shipped* `GET /api/v1/teams/:teamId/topics` handler (`content.ts:454-492`) to add `isCustomizationLocked`. That handler's authorization is unchanged by this design — it still calls `evaluateTeamAccess(userId, teamId, log)`, whose only path that can grant a `facilitator`-flavored access is **Path 3**: an *active session facilitator*, requiring a live/recent/draft session row for that specific team (`sessions.facilitator_id = userId AND sessions.team_id = teamId`, gated by status). A facilitator with no membership and no session history for team X gets `grant === null` from that call today, and `denyNullGrant` returns a `403` (`"You do not have access to this team's content."` or the cross-team variant) — confirmed by reading `content.ts:463-468` and its `denyAccess`/`denyCrossTeamFacilitator` helpers.

Decision 3 then defines `TOPIC-003`'s write-side authorization as the standing, org-wide model: `global_role = 'facilitator'` AND not a current member — *no session history with the team required at all*. Decision 3's own justification leans on "the sibling 'View Active Topic Configuration' use case already uses the correct, broader phrasing ('any team they are eligible to facilitate')" as evidence that the broader model is already the intended shape for topics generally. That's true of the *use case document*. It is not true of the *shipped code* the read side of this very resource runs on, which this same change touches (Decision 1) without revisiting.

The net effect: a facilitator who has never run a session for team X, and is not a member of team X, **can add a topic to team X's configuration** (`POST`, `201`) but **cannot view team X's current topic list first** (`GET` on the identical resource returns `403`) through this application's own read path. That is not a hypothetical inconsistency — it is the literal behavior of the two endpoints as designed, for the identical caller and the identical team, on the identical resource, in the same change. It also means a standing facilitator adding a topic has no way to see the team's existing topics, current display order, or lock state through the sanctioned read endpoint before writing — they are flying blind by construction unless they separately hold a broader grant.

This isn't primarily a "too permissive" finding (the write side isn't over-privileged relative to what FR-8.2/the contract already specifies) — it's an *unreconciled boundary* finding: this design silently assumes a read-side reality ("topics are usable between sessions, for any team a facilitator is eligible to facilitate") that the code it explicitly modifies does not implement. Either the read side should be widened to match (raising its own question of whether `isCustomizationLocked` and the topic list itself should be visible org-wide to any facilitator — a real disclosure decision that hasn't been made), or the write side's premise that this asymmetry is harmless needs to be stated and justified on the record, not left as an emergent property of two decisions that don't look at each other.

**Recommendation:** Add this asymmetry as a named, on-the-record decision (or extend Decision 3) — either accept it explicitly with a one-paragraph justification (e.g., "write access under Philosophy 1 does not require prior read access; a facilitator adding a topic blind is an accepted UX gap, not a security one, because X"), or open it as a formal Open Question alongside Open Question 1 (`TEAM-002` lock exposure) rather than an implicit side effect nobody stated.

### Finding 3 (Medium) — A successful Add Custom Topic write produces zero audit trail, when this codebase's own precedent already covers this exact case at no schema cost

Decision 8 audits *denied* lock-bypass attempts (`409`, `topic.write_denied_locked`). Neither `design.md`, `tasks.md`, nor `specs/add-custom-topic/spec.md` writes an `audit_log` row — or even a structured `emitAuditEvent` call — for a *successful* Add Custom Topic write. I checked `audit-logger.ts`'s `AuditEventName` union and the events it documents: `session.draft_created`, `team.created_with_session`, and `team.manager_established` are all described explicitly as "an access/existence-establishing event audited in the same transaction as the rows it authorizes" — the precedent this codebase already applies whenever a privileged actor's write creates a new row that grants or configures something for other people. `action_item.owner_reassigned` goes further and audits even the no-op path, specifically because — per that endpoint's own security review (mine) — a write with no audit trail is "invisible in the trail" regardless of whether anything material changed.

Open Question 2 in this design frames the gap as "should a custom topic carry a 'who added this' attribution column" and treats it as a scope/cost judgment call to defer — reasonable for the `topics.created_by` schema question specifically, since that is a migration and a response-shape decision. But the *audit_log* table needs no migration: it already has `actor_user_id`, `actor_global_role`, `actor_ip`, `team_id`, and `metadata`, and Decision 8 is already writing to it, in this same file, for the denial case. Skipping the identical write for the success case is not the same cost trade-off Open Question 2 describes — it's a five-line addition to code this change is already writing, following a pattern this change is already using one branch away.

This matters more here than it would on a narrower endpoint because of who Decision 3 says can trigger the success path: any facilitator, org-wide, with no requirement of ever having run a session for the team. That is a wide population relative to most of this codebase's other privileged-write callers (`TEAM-006`'s admin-only association, `VOTE-004`'s session-scoped facilitator), and it is exactly the combination this task asked me to scrutinize: standing-org-wide-write-access plus a deferred attribution column plus no audit fallback equals a genuine non-repudiation gap on the success path, not just the denial path. A custom topic later found to be inappropriate, mistaken, or planted by a compromised facilitator credential has, today, `created_at` and nothing else — no way to determine who, from a population of every facilitator in the organization, wrote it — even though the mechanism to answer that question already exists in this file and is already wired up for the sibling event.

**Recommendation:** Add a durable `audit_log` row (e.g. `operation = 'topic.custom_added'`), written in the same transaction as the topic `INSERT` — matching `session.draft_created`/`team.created_with_session`'s established shape — with `metadata: { topic_id, team_id }` at minimum. This closes most of the non-repudiation gap today, independent of whatever Open Question 2 eventually decides about a `created_by` response field; I'd treat this as something to land in this change, not deferred alongside the schema question, since it requires no schema change and no API contract change (it's not client-visible).

### Finding 4 (Low-Medium) — The lock-denial audit write has no rate-limit discussion, despite this codebase's own precedent for exactly this endpoint shape, and no stated failure-mode behavior

Decision 8's audit write is modeled explicitly on `TEAM-005`'s `role_change_denied` precedent: a plain, unguarded `db.query(INSERT INTO audit_log ...)`, awaited directly before the response, with no `withTimeout`/`AUDIT_WRITE_TIMEOUT_MS` bound (that bound exists only for the "fail-open group" — `auth.success`, `auth.session_created`, `auth.idp_logout_failed` — via `writeFailOpenAuditRow`). Two things follow from copying that precedent here without adaptation:

1. **Flood potential.** `TEAM-005`'s denial path is reachable only by an actor who already cleared `checkAssignRolesAuthorization` and is attempting one specific, low-frequency transition (`participant → engineering_manager`). `TOPIC-003`'s denial path is reachable by *any standing facilitator in the organization*, against *any team that has never completed a session* — a state every team passes through at creation and that, per the design's own Migration Plan, has no feature flag or rollout gating. This is a structurally larger and more automatable attack surface than `TEAM-005`'s, and it is the closest analog in this codebase to `TEAM-006`'s `POST /teams/:teamId/managers` — which received an explicit, jointly-owned (BA + Security) rate-limit decision (`q6-rate-limit-decision.md`) specifically because "every breach writes a durable `audit_log` row... synchronously... before the response is returned," and an attacker (or, just as plausibly here, a buggy retry loop in a stale client per the design's own Risk section) can turn that into unbounded audit-table growth and DB load with a valid-but-abusive credential. That decision's reasoning — actor-scoped limits, not IP-scoped, because "the threat model's attacker is a compromised credential" — applies at least as directly to a standing, non-team-scoped facilitator role as it did to `TEAM-006`'s admin-only endpoint.
2. **Undefined failure mode.** Decision 8 states the write happens "before the response is sent" but not what happens if it fails or hangs. Copying `TEAM-005`'s unguarded-`db.query` shape means a DB hiccup on the audit insert would throw inside the handler and surface as an unhandled `500` instead of the intended `409` — not an authorization bypass (the topic still isn't written, and nothing leaks), but an availability/robustness gap the design doesn't acknowledge either way.

I am not asking this change to build `TEAM-006`'s full three-tier limiter — that decision was scoped to a specific admin-only endpoint with a jointly-reasoned threshold. I am asking for an explicit decision, in writing, either way: accept the flood/growth risk as out of scope for this change (with a one-paragraph reason, the way Decision 7 accepts the no-realtime-unlock trade-off on the record), or add a lightweight per-actor rate limit on the `409` path before this ships. Silence on a question this codebase has already answered once, for a narrower endpoint, reads as an oversight rather than a considered choice.

**Recommendation:** Add a decision (or a Risk entry with a stated resolution, not just a mitigation pointer to "Open Question 2") addressing: (a) whether `POST /api/v1/teams/:teamId/topics` needs a per-actor rate limit given its org-wide caller population, referencing the `TEAM-006` Q6 precedent explicitly rather than silently declining to apply it; and (b) what happens to the `409` response if the audit write itself fails or times out.

### Finding 5 (Low, informational) — Decision 3's primary traceability anchor ("Covered against FR-8.2, no caveat") is itself incomplete, in a way worth naming even though it doesn't weaken the authorization decision

I traced Decision 3's central citation back to source. The REST API Contract's Group 3 text (`requirements/design/REST API Contract.md:679`) and the Validation Report's FR-8.2 row (`...Validation Report.md:65`) are exactly as Decision 3 describes — I confirmed both read. But `requirements/BRD.md:323` states FR-8.2 as a `[HARD]` requirement in its own right: *"After a team's first session, the facilitator **or Application Administrator** shall be able to add, remove, or reorder topics for that team."* `application_admin` is a real, distinct value in the `user_role` enum (`migrations/1_create_enums.sql`). Neither the contract's `TOPIC-003` Authorization line nor Decision 3's Philosophy 1 grants `application_admin` any write path onto topics — the Validation Report's "Covered" mark for FR-8.2 appears to cover only the facilitator half of a two-actor HARD requirement.

This is not a permissiveness problem — it's the opposite shape of gap from everything else in this review, and it predates this change (it's a pre-existing hole in the contract/validation-report pair this design inherits, not introduces). I raise it only because Decision 3 explicitly leans on "marked 'Covered' ... with no caveat" as evidence the authorization clause is a stable, already-litigated answer not requiring fresh scrutiny here. That framing is slightly stronger than the underlying citation supports — the disposition itself has an unaddressed half. This doesn't change my assessment of Philosophy 1 as the right model for the facilitator population; it just means "already reviewed and Covered" is doing a little more rhetorical work in Decision 3 than the record actually backs, and whoever eventually resolves the Application Admin gap should know it was never actually validated against FR-8.2's full text.

**Recommendation:** No change required to this design. Worth a one-line note to the BA/traceability owner that FR-8.2's Application Administrator clause has no implementing endpoint anywhere in Group 3, independent of this change.

### Non-findings — things I checked and are correctly handled

- **Decision 2's `403`/`409` split:** Confirmed against `requirements/design/REST API Contract.md:701` ("`403 Forbidden` | Not a facilitator; facilitator is a team member; customization lock is active") — the contract's literal blanket-`403` text is exactly as described, and correcting it to split identity/role from state-precondition is the right call and matches this codebase's established `409`-for-state-preconditions convention (`action-item-owner-reassignment`'s resolved-item guard).
- **Decision 3's traceability claim about `action-item-owner-reassignment`:** Confirmed against that change's own `design.md` D1 ("This endpoint's authorization inherits `VOTE-002`'s exact session-scoped trust boundary, on purpose... a locally-justified reuse decision for the action-item resource family"). The claim that the narrower model was never generalized into a successor doctrine is accurate, not a convenient paraphrase.
- **Decision 3's use-case-text corrections:** Confirmed against `requirements/use cases/08 - Topic Management - Use Cases.md` — the "Add Custom Topic" precondition (line 130: "the team they are facilitating") and the "Enforce Topic Customization Lock" alternate-flow wording (line 85: "an authorization error") both read exactly as Decision 3 states before correction, and the "any team they are eligible to facilitate" phrasing (line 467) is exactly what Decision 3 cites as the model-consistent sibling text.
- **Decision 9's core no-leak-to-unauthorized-caller logic:** Internally sound. A caller who fails identity/role gets an identical `403` regardless of target team's existence or lock state, *by the status-code logic alone* — contingent entirely on Finding 1's timing-floor gap being closed, since status-code equivalence without response-time equivalence is not the property this codebase has established as sufficient elsewhere.
- **Decision 6 (no row lock on the lock-check read) and Decision 10 (`FOR UPDATE` on the `displayOrder` read):** Both reasoned correctly — the asymmetry between a false-negative-only race (Decision 6) and a collision-producing race (Decision 10) is the right basis for treating them differently, and the named residual gap (zero-active-topics teams, unreachable until `TOPIC-004` ships) is exactly the kind of forward-reference I want to see written down rather than silently assumed away.
- **No caching of lock state (Decision 1):** Correctly matches `team-content-access-helper.ts`'s existing no-cache precedent for the structurally identical class of question (live authorization/precondition state).

---

### Summary for the record

Finding 1 (timing floor) and Finding 3 (no success-path audit trail) are the two I'd want addressed before this ships — the first because it's a previously-litigated, blocking codebase policy this design's own enumeration-resistance framing depends on and never mentions, and the second because it's a near-zero-cost fix to a real non-repudiation gap on a write endpoint whose caller population (org-wide, no team relationship required) makes that gap matter more than it would elsewhere. Finding 2 (read/write asymmetry) and Finding 4 (rate-limit/failure-mode silence) I'd like explicit decisions on, either way, rather than left as emergent side effects — consistent with how this design already handles Decisions 6, 7, and 10's residual risks. Finding 5 is informational, for the traceability record, not this change.

None of these findings ask Decision 3 to be replaced. Philosophy 1 is a real, disclosed, already-reviewed answer to "which facilitator accounts can write to a team's topic list," and the scope note in Decision 3 states its breadth plainly rather than hiding it. My concern is that the breadth of who can trigger the success path is precisely what makes the missing audit trail (Finding 3), the missing rate-limit decision (Finding 4), and the missing timing-floor discipline (Finding 1) matter more here than they would on a narrower endpoint — and none of those three gaps require reopening the authorization model itself to close.
