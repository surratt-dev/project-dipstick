## Why

A team's first session is supposed to run against the same twelve default topics every other team's first session runs against — that's what makes a team's baseline data comparable to anyone else's and comparable to itself over time. Issue #48 already gave every new team its own copy of the default set and marked that configuration as "locked" conceptually, but "locked" today is a description, not an enforcement mechanism: nothing in the running application stops a facilitator, an admin script, or a direct API call from editing a team's topics before that first session ever completes. The moment that happens, the team's baseline is contaminated at the exact point it's created, and there is no way to reconstruct what the untouched first session would have shown. That is the same category of failure as letting a manager join a session or letting a same-team facilitator run it: a structural guarantee that quietly becomes optional the first time someone routes around it — and the use case's own alternate flow ("Facilitator bypasses the UI and submits a topic modification request directly, e.g., via API") names the bypass explicitly, not hypothetically.

This change makes the lock real and server-side, and — because a lock protecting nothing is just a promise — bundles in the first (and only, for now) topic-write endpoint that ever needs to be gated by it: adding a custom topic. Landing the two together is deliberate: #49 has nothing to enforce against until a write path exists, and #50 has no gate to test against until the lock exists.

## What Changes

- **A single, reusable lock-check function** determines whether a team's topic configuration is customizable (`true` once the team has at least one session with `status = 'complete'`, `false` otherwise). This is the one place that truth is computed — no handler is permitted to run its own inline `COUNT(*)` query, so the read-side flag and the write-side gate can never quietly drift apart.
- **`GET /api/v1/teams/:teamId/topics` (`TOPIC-001`) starts returning `isCustomizationLocked`.** The shipped handler (`packages/backend/src/routes/content.ts`) currently omits this field entirely, even though the already-reviewed REST API Contract has always specified it. This is the field a facilitator's screen actually reads on almost every visit — a correctly built frontend hides the write controls when locked, so the calm "not yet" read-side view, not the write-rejection path, is where this feature is experienced nearly all of the time. Adding it is a required line item of this change, not a nice-to-have.
- **`POST /api/v1/teams/:teamId/topics` (`TOPIC-003`) — new endpoint.** Lets an authorized facilitator add a custom topic (`name`, `prompt`, `voteType`, optional `firstSessionDescription`) to an unlocked team, appended to the end of the display order.
- **Server-side rejection of writes against a locked team, with a body a future frontend can actually use.** A write against a locked team from an otherwise-authorized facilitator is rejected with `409 Conflict` (a state-precondition failure, distinct from an authorization failure) and a body carrying a machine-readable `code` (distinguishing "not a facilitator" / "facilitator is a team member" / "lock is active") plus a stable, server-driven message string for the lock case specifically — not a bare status code a frontend has to guess a sentence from.
- **Every denied lock-bypass attempt is audited before the response is sent** — the same shape of record this codebase already writes for other blocked privileged-boundary attempts (e.g., `TEAM-005`'s promotion block), and useful for the same reason: a facilitator returning to a team after a long absence, or taking over from someone else, can see that a bypass was tried and correctly stopped, the same continuity value session history already provides.
- **Three corrections to source documents, stated on the record rather than silently diverged from:**
  - The "Add Custom Topic" use case's form fields are corrected to include `name` as its own required field, distinct from `prompt` — the use case as written only lists prompt/vote type/description, but the schema, the already-reviewed `TOPIC-003` contract, and the sibling "Assign Default Topic Set" use case all treat a topic's short label as a field independent of its full prompt text. This is a documented gap in the use case, not a design choice being made here.
  - The REST API Contract's literal text folding "not a facilitator," "facilitator is a team member," and "lock is active" all into a single generic `403` is corrected: `403` is reserved for identity/role failures (evaluated, and returned, before the lock is ever checked, so lock state never leaks to a caller who was never going to be authorized regardless); the lock itself is `409`.
  - The "Add Custom Topic" use case's precondition — "The Facilitator is accessing the topic management area for the team **they are facilitating**" — is corrected to reflect the standing, org-wide facilitator model this change already builds against (design.md Decision 3): no prior facilitation relationship with the team is required, only that the caller holds `global_role = 'facilitator'` and is not an active member of the target team. As written, the precondition implies an existing facilitation relationship that Philosophy 1 explicitly does not require — the sibling "View Active Topic Configuration" use case already uses the correct, broader phrasing ("any team they are eligible to facilitate"); "Add Custom Topic" is the one use case in this document whose precondition text reads narrower than the model actually being built, and is corrected to match.
  - **Related, lower-priority terminology note (not a fourth formal correction, folded into the same documentation pass):** the "Enforce Topic Customization Lock for First Session" use case's Alternate Flow describes the server-side lock rejection as "an authorization error." Design.md Decision 2 is explicit that the lock rejection is a state-precondition failure (`409`), not an authorization failure (`403`) — the same distinction the second correction above already makes for the REST API Contract's text. This note closes the same gap in the sibling use-case document rather than treating it as a separate open question.

**Not changing:** no schema migration (the `topics` table already carries every column `TOPIC-003` needs), no remove/reorder/annotate/re-add endpoints, no frontend UI. Those are separate, already-filed issues (#51–#55) and are explicitly out of scope here.

## Capabilities

### New Capabilities
- `topic-customization-lock`: The reusable server-side determination of whether a team's topic configuration is customizable, the `isCustomizationLocked` field on `GET /api/v1/teams/:teamId/topics`, and the write-side precondition (with its `409` status, reason codes, and audit-on-denial behavior) that any topic-write endpoint — starting with `add-custom-topic` — must be gated by.
- `add-custom-topic`: The `POST /api/v1/teams/:teamId/topics` endpoint itself — request validation (`name`, `prompt`, `voteType`, optional `firstSessionDescription`), authorization (standing facilitator, non-member), display-order assignment, and the `201` response shape.

### Modified Capabilities
(none — no existing spec currently documents `GET /api/v1/teams/:teamId/topics`'s response shape or any topic-write endpoint; `default-topic-provisioning`'s spec already explicitly disclaims ownership of the lock state and hands it off to "topic-customization enforcement," which is what this change delivers. Nothing here needs a delta against an existing spec.)

## Impact

**Code:**
- `packages/backend/src/routes/content.ts` — `GET /api/v1/teams/:teamId/topics` handler gains `isCustomizationLocked` in its response, computed via the new shared helper.
- A new lock-check helper (naming/location is an implementation call for design.md — something like `hasCompletedFirstSession(teamId)`, parallel to the existing `team-content-access-helper.ts` pattern) backs both the read-side flag above and the write-side gate below. Live database read on every call, per this codebase's existing no-cache-on-authorization-state precedent; no row locking needed (this gates a read-then-decide against a one-way transition that's already guarded elsewhere, not a concurrent-write race).
- A new route for `POST /api/v1/teams/:teamId/topics` (file organization — new `topics.ts` vs. extending `content.ts` — is a design.md call, not a ritual-integrity question).
- Audit logging for denied lock-bypass attempts, synchronous, before the response is sent.

**Requirements documentation (blocking, non-code, same priority as the code):**
- `requirements/use cases/08 - Topic Management - Use Cases.md` — "Add Custom Topic" gains `name` as a required field in its form description and acceptance criteria; its precondition is corrected from "the team they are facilitating" to the standing, org-wide facilitator model; and "Enforce Topic Customization Lock for First Session"'s Alternate Flow wording is corrected from "an authorization error" to reflect the `409` state-precondition framing.
- `requirements/design/REST API Contract.md` — `TOPIC-003`'s error table is corrected from a blanket `403` to distinguish `403` (identity/role) from `409` (lock state).

**Not touched:** the no-manager-participation rule, the simultaneous reveal, the facilitator-from-another-team requirement, the no-individual-performance-comparison guardrail, any live-session code, and the remove/reorder/annotate/re-add topic endpoints (separate future issues, built against the same lock-check helper this change introduces).

**Explicitly out of scope, flagged for later rather than silently dropped:**
1. Whether `TEAM-002` (`GET /api/v1/teams/facilitatable`) should also expose `isCustomizationLocked` directly, versus continuing to let a facilitator's team-list view infer lock state from `lastSessionDate === null`. Real completeness gap, not a ritual-integrity question — worth deciding once a facilitator-team-list UI actually consumes it, not guessed at here.
2. Whether a custom topic should carry a "who added this and when" attribution column. `topics` has no `created_by` today, and under the standing-facilitator authorization model a facilitator who has never run a session for a team can still add one of its topics — a real continuity gap for a returning or handoff facilitator, and cheaper to add now than to retrofit once rows already lack it. Left as an open question for design.md to weigh against this change's size, not resolved here.
