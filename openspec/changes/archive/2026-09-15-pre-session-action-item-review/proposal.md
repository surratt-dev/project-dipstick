## Why

Every other ritual mechanic in this application — the simultaneous reveal, the no-manager rule, the facilitator-from-another-team requirement — is about getting an honest read on how the team feels right now. This screen is the one place the tool has to say something back about whether last session's commitments actually happened. Right now it can't: the facilitator's `POST /start` response carries the team's open action items in memory for an instant, but every other participant in the room has no REST endpoint they're allowed to call to see the same list, and nothing renders it for anyone. Without this screen, action items become things a team writes down once and never revisits, and the "trend dashboard shows sustained improvement over time" story has no visible mechanism underneath it for participants to trust.

This is a deliberate, named partial implementation of UC1 ("Surface Open Action Items at Session Start"): it ships the read-only surface (Main Flow steps 1–5, 7) now, and defers step 6 (owner-only inline status controls) and all of UC2/UC3 (owner- and facilitator-initiated status updates) — along with UC: Flag Stale Action Items' "cleared in real time" acceptance criterion (UC5), which depends on that same deferred write path — to a fast follow, not because the write path is unbuilt, but because it already is (`PATCH /api/v1/action-items/:actionItemId/status`, shipped in #64/#65/#95) and bolting inline controls onto this screen's first layout pass would mean designing it twice. A read-only screen displays the accountability loop's current state; it does not by itself close that loop. That is a stated limitation of this change, not an oversight — full accountability requires the deferred write path.

## What Changes

- New backend `GET` endpoint (session-scoped) that returns the team's open/in-progress action items for the pre-session review, for every session participant — not just the facilitator who happens to be looking at the `POST /start` response at the instant it returns. Reuses `evaluateSessionSubscriberAccess` for authorization (no new auth logic) and `fetchPreSessionActionItems` for the query (exported/shared, not rewritten).
  - Gated to sessions in `pre_session` status only. A participant joining after the session has moved to `active` does not receive the pre-session review via this endpoint (404/409) — the review is a one-way transition, per UC1's framing. This is stated as a default, not a permanent answer.
  - Returns `isFacilitator` (derived from the authorization grant's `path`) so the frontend has a trustworthy signal for whether to render the "Begin First Topic" control, without inventing a second facilitator check. **Added during design review (engineer finding #3):** `isFacilitator` is returned on every response path, including the `409` sent for a `lobby` or `active` session — not only on success — so the same signal also drives the new "Start Session" control below. The `409` body additionally carries `currentSessionStatus`, letting the frontend determine lobby/pre_session/active from this one endpoint without a second, team-scoped status call. See design.md Decision 1/3.
  - Applies the same timing floor (`applyTimingFloor()`) and `Cache-Control: no-store` header every other content-reading endpoint in this codebase applies at an authorization boundary (`content.ts`, `em-views.ts`) — added during design review (security findings F1/F2) as this is the first HTTP route built on `evaluateSessionSubscriberAccess`.
- **Added during design review (engineer finding #1), a real gap the original proposal didn't scope:** a "Start Session" control on `SessionLobbyPage`'s `lobby` branch, facilitator-only, wired to the already-existing `POST /api/v1/sessions/:sessionId/start`. Without it, nothing in the running application can move a session out of `lobby` at all — grepping the frontend for any existing trigger for `/start` turned up nothing. No backend change is required; `/start`'s behavior is unmodified.
- New frontend view rendering the pre-session action item review: description, owner display name, status label, originating session number, and staleness color for each open/in-progress item, read-only.
- Empty state ("no open action items") shown identically to engineers and the facilitator, minus the advance control for engineers, per UC: Skip Review When No Open Action Items.
- Facilitator-only "Begin First Topic" control wired to the existing `POST /begin-voting`, which already broadcasts the pre_session → active exit transition via the same `session_state_change` WebSocket mechanism used for the lobby → pre_session entry. No new event type is introduced.
- Always-visible legend explaining the staleness color scale (1/2/3+ sessions without an update → yellow/orange/red), so a participant's first red badge doesn't require live explanation from the facilitator.
  - **Resolved staleness-mapping blocker (propose-stage BA review):** the reused `computeStalenessLevel` (`facilitator-sessions.ts`) does not actually implement this 1/2/3 mapping — it steps levels at 1x/2x/3x of the configurable `application_settings.staleness_threshold_sessions` (default `2`), so at the shipped default, 3 sessions elapsed computes as `yellow`, not `red`. This change fixes `computeStalenessLevel` to implement the fixed 1/2/3-session mapping directly, matching UC: Flag Stale Action Items' explicit acceptance criteria. **This is a small change to already-shipped code (`SESSION-004`), and it means the Impact section's "no changes to existing contracts" framing no longer holds without qualification** — see Impact and design.md's Decision 7 for the full rationale and the alternatives (reinterpreting the use case, or making all three boundaries independently configurable) that were considered and rejected.
- A one-line, non-judgmental summary at the top of the list (e.g., "3 items need attention," a plain count of items at any non-`none` staleness level, not a severity-weighted phrasing) so the facilitator can absorb the state of the room without scanning line by line. When open/in-progress items exist but none are stale, the line shows neutral copy (e.g., "N open items — none need attention") rather than disappearing, so the summary's position on the screen stays predictable across sessions.
- Defined error/failure states for both new surfaces:
  - The participant-facing GET fails → explicit error state shown to that participant, not a blank screen or infinite spinner. This applies to the facilitator too — per design.md Decision 3/4, the facilitator's own review screen is fed by this same GET, not by `POST /start`'s response, so there is one error path here, not two. (**Corrected during design review, engineer finding #3:** an earlier draft of this bullet described a second, `POST /start`-payload-based gate for "Begin First Topic"; that data never reaches the rendered screen under this change's actual frontend architecture, so it was removed.)
  - "Begin First Topic" stays disabled until that same GET loads successfully; the session must not advance to voting on a failed query.
  - The new "Start Session" control fails → inline retry; the session remains in `lobby`.
  - A staleness-computation failure for a given item degrades to "no indicator shown" for that item, not a blocked screen.
- Draft copy for the empty state, each staleness tier (badge/label text, not just color), and the summary line (including its neutral no-stale-items variant) is a scope gate for this change — it must be drafted and stakeholder-approved before this change is considered implementation-ready, not treated as a nice-to-have polish pass. **Per executive review, Rachel Okonkwo (VP of Engineering) personally reviews the drafted staleness-tier and empty-state copy before it ships to a pilot team** — this is a named approval step, not satisfied by the gate's existence alone. A badge sitting next to an engineer's name is the closest this screen comes to her no-performance-tool constraint; the copy is what keeps it reading as "this has been sitting a while" instead of a compliance flag.
- A follow-up issue, filed before this change merges, scoped explicitly to: (a) rendering the owner/facilitator status controls this screen currently omits, (b) wiring them to the already-shipped `PATCH /api/v1/action-items/:actionItemId/status`, (c) no new backend work required. **Target: merged within 2 weeks of this change's own merge** — per executive review, this is a wiring task against endpoints that already exist, not new design work, so a short, concrete target is appropriate; a team's first sessions on this screen will otherwise show staleness creeping toward red with no in-app way to act on it, which is a worse experience than no screen at all if that gap sits open indefinitely.

**Explicitly deferred, not decided by this proposal (see design.md):**
- Item ordering: chronological oldest-first (as currently implemented) vs. stale-first. UC1's own Notes flag this as an unconfirmed assumption; it needs explicit stakeholder confirmation, not an inherited default.
- Whether the facilitator can flag an item for live discussion from this screen. Deliberately not folded into scope — every control this screen grows has to earn its place against the standing risk of the ritual feeling like software being run on engineers rather than a conversation they're having.
- Where this screen lives structurally (extend `SessionLobbyPage` to branch on session status, vs. a new route/page for `pre_session`). Not a requirements question — design.md owns it with a recommendation.
- The fetch-then-subscribe race for the **deferred item-status write path** only: what a client does with a status update landing between its initial GET and its WebSocket subscription going live, once the follow-up issue wires in the PATCH controls. **Narrowed during design review (engineer finding #4):** the same-shaped race for the *session-state transitions this change itself wires in* (`start`, `begin-voting`) is in scope and resolved by this change, not deferred — see design.md's Risks section and Decision 3's subscribe-before-fetch ordering.

**Explicitly out of scope:**
- Inline status-update controls (owner-on-own-item, facilitator-on-any-item) — covered by the follow-up issue above, not this change.
- Any change to how a team configures its `staleness_threshold_sessions` value, or to the `application_settings` schema/config surface generally. (Narrower than "no change to staleness computation" — the computation itself is corrected; see What Changes above and design.md Decision 7.)
- Any change to the pre-existing "no topic configured" error path on `POST /begin-voting` (bare `Error` surfacing as an unstructured 500) — a known SESSION-005 rough edge this change did not introduce and is not obligated to fix, but the "Begin First Topic" error handling should not assume a clean 4xx there.
- Reconciling `SessionConnectionHost`/`FacilitatorConnectionHost`'s stub/demo status into a full lobby→active routing story — this change only needs to solve the `pre_session` phase.

## Capabilities

### New Capabilities
- `pre-session-action-item-review`: the participant-facing GET endpoint (authorization, session-status gating, response shape) and the read-only review screen's required behavior — what's displayed, the empty state, the staleness legend, the summary line, the facilitator-only advance control, the facilitator-only "Start Session" control that makes the `lobby` → `pre_session` transition reachable at all (added during design review — see What Changes), and the defined error/failure states for the GET, the advance path, and the Start Session control. Does not cover status-update write behavior (see `action-item-status-management`, already shipped and unmodified by this change) or the WebSocket event fan-out mechanics for `session_state_change` or `action_item_status_updated` (see `websocket-specification`, also unmodified).

### Modified Capabilities
(none — no existing spec file documents a requirement this change contradicts. `computeStalenessLevel`'s corrected mapping (see Impact) touches code shipped under `session-topic-lifecycle`'s `SESSION-004`, but that spec's requirement text never specified a session-to-color mapping in the first place — there is nothing to write a delta against. The corrected mapping is specified for the first time as part of this change's own `pre-session-action-item-review` capability, below.)

## Impact

- **Backend:** New route `GET /api/v1/sessions/:sessionId/action-items-review` (`packages/backend/src/routes/facilitator-sessions.ts`, alongside `POST /start`/`POST /begin-voting`) exporting/reusing `fetchPreSessionActionItems` and `evaluateSessionSubscriberAccess` from `packages/backend/src/auth/session-subscriber-access-helper.ts`. No schema changes, no new tables, no changes to `POST /start` or `POST /begin-voting` write behavior. Applies `applyTimingFloor()` and `Cache-Control: no-store` (design review security findings F1/F2 — matches `content.ts`'s pattern for every HTTP endpoint built on a live-DB authorization helper). **One exception to "no changes to existing logic":** `computeStalenessLevel` (also in `facilitator-sessions.ts`, part of the already-shipped `SESSION-004`) is corrected to implement the fixed 1/2/3-session staleness mapping instead of its current 1x/2x/3x-of-configurable-threshold behavior — see design.md Decision 7. This changes the staleness color a facilitator sees on `POST /start`'s response too, not only on this change's new endpoint, since both call the same function. `application_settings.staleness_threshold_sessions` is left in place, unmodified as a config surface, but becomes unread by this function as a result.
- **Frontend:** New view logic in `packages/frontend/src/pages/SessionLobbyPage.tsx`, branching on the new endpoint's response rather than a separate status fetch (design.md Decision 3, revised during design review — engineer finding #2 found the originally-recommended `content.ts` status endpoint required a `teamId` route param `SessionLobbyPage` doesn't have). **New scope added during design review (engineer finding #1):** a facilitator-only "Start Session" control on the `lobby` branch, wired to the already-existing `POST /start` — without it, nothing in the codebase can move a session out of `lobby`. First place the frontend needs to know "am I this session's facilitator" for rendering purposes, for either control; the new endpoint's `isFacilitator` field (now present on every response path, not only success) is the sole source of truth for both.
- **No changes** to `action-item-status-management` (the PATCH endpoint and its authorization/transition rules ship unmodified) or to `websocket-specification`'s event shapes. The shared `SessionSubscriberGrant` type is also left unmodified — considered and rejected as a fix for a low-severity TOCTOU trade-off (design.md Risks, security finding F3) specifically because it would touch `actionitem-updated-live-broadcast`'s documented Decision D14, outside this change's stated boundary.
- **Follow-up work created, not performed here:** an issue for inline status-update controls, filed before this change merges.
