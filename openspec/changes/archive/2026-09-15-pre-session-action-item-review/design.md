## Context

`POST /api/v1/sessions/:sessionId/start` (SESSION-004, `packages/backend/src/routes/facilitator-sessions.ts`) already transitions a session from `lobby` to `pre_session` and returns the team's open/in-progress action items — but only to the facilitator, and only in that single response body. `POST /api/v1/sessions/:sessionId/begin-voting` (SESSION-005) already transitions `pre_session` to `active` and broadcasts a `session_state_change` WebSocket event to every subscriber, using the identical mechanism the `lobby → pre_session` entry transition uses. Both transitions are implemented and correct; nothing new is needed on either write path.

**Confirmed during design review (engineer review finding #1), and now in scope for this change:** nothing in the running application calls `POST /start` at all. `SessionLobbyPage.tsx`, `SessionConnectionHost.tsx`, and `FacilitatorConnectionHost.tsx` were each checked directly — none contain a call to `/start`, `/begin-voting`, or any "Start Session" affordance; the latter two are stub connection-health hosts against stub data. A session can be created and can sit in `lobby` indefinitely, but nothing in the codebase can move it forward. Without a trigger, this entire feature is unreachable in the running app — the design was silent on this because the write path itself needed no changes, but the UI control that invokes it was never scoped anywhere. This change now adds that control (Decision 3) as a small, frontend-only addition — not a change to `POST /start`'s behavior.

The other piece missing is the read side for everyone who isn't the facilitator at the instant `POST /start` returns. `SessionLobbyPage.tsx` (`packages/frontend/src`) today renders a static waiting message — no session-state fetch, no role check, no WebSocket connection. There is no REST endpoint a participant is authorized to call to fetch the pre-session action items list, and the one existing candidate (`GET /api/v1/teams/:teamId/action-items` in `content.ts`) is the wrong shape: it returns all items regardless of status, no staleness computation, ordered newest-first, built for a general team-content view rather than this screen.

Two authorization/query building blocks already exist and are reused, not reimplemented:
- `evaluateSessionSubscriberAccess(userId, sessionId)` (`packages/backend/src/auth/session-subscriber-access-helper.ts`) — returns a `SessionSubscriberGrant`, `{ path: 'facilitator', ..., sessionStatus }` or `{ path: 'participant', ..., }` (no `sessionStatus` on this variant), or `null`. No admin path; structurally excludes Engineering Managers on both grant variants.
- `fetchPreSessionActionItems(teamId)` (`facilitator-sessions.ts`, module-private today) — the query: `status IN ('open','in_progress')`, joined only against `sessions.status = 'complete'`, ordered oldest-first, staleness computed by `computeStalenessLevel`. **As shipped, this steps levels at 1x/2x/3x of the configurable `application_settings.staleness_threshold_sessions` (default `2`) rather than the fixed 1/2/3-session mapping UC: Flag Stale Action Items calls "a decided requirement" — the function's own comment names this as unreconciled. This change is the first to put a user-facing legend on top of that number, which is what turns the drift into a requirements problem worth fixing rather than a latent one. See Decision 7.**

This is a named partial implementation of UC1: Main Flow steps 1–5 and 7 ship here; step 6 (owner inline status controls) and UC2/UC3 are deferred to a follow-up issue filed before this change merges, because the write path they depend on (`PATCH /api/v1/action-items/:actionItemId/status`) already shipped (#64/#65/#95) — the follow-up is a wiring task against this screen's already-built layout, not new design work.

## Goals / Non-Goals

**Goals:**
- Every session participant (not just the facilitator) can see the pre-session action item review while the session is in `pre_session` status.
- The facilitator has a working "Start Session" control on the lobby branch that invokes the existing `POST /start` endpoint — without it, no session can ever reach `pre_session` in the running application (design-review engineer finding #1).
- The facilitator has a working "Begin First Topic" control, gated on successful data load, that advances the session via the existing `begin-voting` endpoint.
- Defined, testable error states for both the new GET and the advance action — no blank screens, no infinite spinners, no silent advance on failed data.
- Staleness and ownership display carry no cross-team or cross-owner comparison risk — reuse of `evaluateSessionSubscriberAccess` inherits the EM-exclusion and session-scoping this codebase already enforces correctly elsewhere.

**Non-Goals:**
- Any write path for action item status from this screen (deferred; see proposal.md's follow-up issue commitment).
- Any change to `POST /start`'s or `POST /begin-voting`'s transition behavior, to how a team configures its `staleness_threshold_sessions` value (the setting itself and its row in `application_settings` are untouched), or to the `action_item_status_updated` WebSocket event. (This is narrower than "no change to staleness computation at all" — see Decision 7, which does change the computation.)
- Fixing the pre-existing "no topic configured" bare-`Error` → unstructured 500 on `begin-voting` (SESSION-005 rough edge, out of scope here).
- Resolving what a late joiner sees when arriving after `pre_session` has ended (default: nothing from this endpoint — see Decision 2).

## Decisions

### Decision 1 — New endpoint: `GET /api/v1/sessions/:sessionId/action-items-review`

Session-scoped, no `teamId` in the path — consistent with the existing session-scoped pattern (`POST /api/v1/sessions/:sessionId/start`, `POST /api/v1/sessions/:sessionId/begin-voting`), as opposed to the team-scoped pattern (`/api/v1/teams/:teamId/sessions/:sessionId/...`) used by facilitator-only endpoints that need `teamId` for draft/advance/complete/reveal operations. This endpoint doesn't need a caller-supplied `teamId` — the session row already carries it, and deriving it server-side avoids a class of "does this teamId match this sessionId" checks the team-scoped routes have to do.

Handler flow:
1. Start a timing-floor clock at handler entry (`applyTimingFloor`, see Security below) — applied to every response path below (the `404` in step 2, the `409` in step 3, and the `200` in step 5), not only the success path.
2. `evaluateSessionSubscriberAccess(userId, sessionId)`. `null` → `404`, identical shape whether the session doesn't exist or the caller has no relationship to it (matches the established pattern in `action-item-status-management`'s Decision D12 — don't let a caller distinguish "no session" from "no access" without already having standing).
3. Session-status gate: the endpoint reads `sessions.status` and requires `pre_session`. **Implementation note:** the `participant` grant variant does not carry `sessionStatus` (only `facilitator` does), so this is a single explicit read applied uniformly to both grant paths, rather than branching on whether the grant happens to carry status — one code path, not two. Any status other than `pre_session` → `409 Conflict`, distinct from the `404` used for "no access at all." This distinguishes "you can't see this because you have no standing" from "you can't see this because the review has already ended," per the endpoint's own gating decision (see Decision 2). **The `409` body includes `currentSessionStatus: SessionStatus`**, reusing the exact field name `RevealFailureResponse`'s non-recoverable variant already established (`team-content-access.ts`) for "let the frontend display what happened" — see Decision 3 for why this field is what lets the frontend avoid a second, team-scoped status endpoint entirely. **The `409` body also includes `isFacilitator`**, computed identically to step 5 below — `grant.path` is already resolved by step 2, before this gate runs, so surfacing it here costs nothing and is not conditional on reaching `pre_session`. This is what lets the `lobby`-branch "Start Session" control (Decision 3) know who it's rendering for, using this endpoint's one grant as the single source for that signal at every session status, not just `pre_session`.
4. Call `fetchPreSessionActionItems(grant.teamId)` — exported from `facilitator-sessions.ts`, not rewritten.
5. Return `{ actionItems, isFacilitator: grant.path === 'facilitator' }`, with response headers `Cache-Control: no-store` (see Security below).

**Security additions (resolved from security review findings F1/F2, both treated as design requirements, not later hardening):**
- **F1 — Timing floor.** This is the first HTTP route to build an authorization boundary on `evaluateSessionSubscriberAccess`; every existing HTTP endpoint gating on a live-DB authorization helper (`content.ts`, `em-views.ts`, `action-items.ts`) applies `applyTimingFloor()` to every response path, success and denial alike, specifically because the three outcomes here (`404` one-query, `409` two-query, `200` four-query) have genuinely different cost and the endpoint's own `409`-vs-`404` split already accepts a small status-code-level information leak (see Risks) — a timing side channel would let an authenticated-but-unauthorized caller distinguish the same cases even if the codes were identical. Apply `applyTimingFloor()` the same way `content.ts` does: start the clock at handler entry, float every response path.
- **F2 — `Cache-Control: no-store`.** `content.ts` and `em-views.ts` apply this to every response as blanket policy, specifically because their payloads carry team/session content that shouldn't be cached by a browser, proxy, or shared-machine disk cache. This endpoint returns the same class of data (owner names, descriptions, statuses) to a broader audience than the facilitator-only `POST /start` response it parallels. Add the header to every response path (success, `404`, `409`), matching `content.ts`'s pattern exactly.

**Alternatives considered:** Extending `GET /api/v1/teams/:teamId/action-items` (content.ts) with query params to filter/reshape it for this use. Rejected — that endpoint is a general team-content view with different consumers and a different default ordering; overloading it with staleness computation and status filtering via query params would couple two independently-evolving read paths together for no reuse benefit, since the actual query logic (`fetchPreSessionActionItems`) already lives elsewhere and is what needs reuse, not the route.

### Decision 2 — Late joiner during `active`: gated out, by default

A participant who joins after the session has advanced to `active` gets `409` from this endpoint, not a reconstructed view of the (closed) review. Per the use case's own framing, the review is a one-way transition ("Out of Scope: Returning to the action item review after the first topic has begun"), so there is no product requirement this default violates. **This is stated as a default, not a permanent answer** — if real usage surfaces a need for late joiners to see a closed review's final state, that needs its own acceptance criteria, not a silent broadening of this endpoint's gate.

The same `409` — including its `currentSessionStatus` field (Decision 1) — also covers the symmetric case: a caller requesting the review while the session is still in `lobby`, before the facilitator has started it. Decision 3 relies on this: the frontend does not need a separate call to learn "we're still in the lobby" versus "we've moved past the review" — the one field on the one endpoint's `409` body answers both.

### Decision 3 — Frontend: extend `SessionLobbyPage`, don't add a new route

`SessionLobbyPage` is already the landing page participants reach for every pre-`active` session state; it just doesn't yet branch on status. It renders three branches: `lobby` (today's existing waiting message, plus the new "Start Session" control for the facilitator — see below), `pre_session` (the new review component, calling the Decision 1 endpoint), and a transition out of the page entirely once the session reaches `active`.

**Revised from the original recommendation, per design-review engineer finding #2.** The original recommendation was to fetch session status on mount via the existing `GET /api/v1/teams/:teamId/sessions/:sessionId` in `content.ts`. Checked directly against the code and rejected: `SessionLobbyPage`'s actual route is `/session/:sessionId` (`App.tsx`) — no `:teamId` in the URL — and `AuthSession.teamMemberships` is a list, not a single team, so there is no way to derive the `teamId` that endpoint's path requires without an extra lookup nothing in this design specified. Beyond the missing parameter, reusing `evaluateTeamAccess` (team-scoped, has an admin path) alongside the new endpoint's `evaluateSessionSubscriberAccess` (session-scoped, no admin path) would gate two halves of one screen with two mechanisms that aren't guaranteed to agree at the edges — e.g. an admin could fetch status via one endpoint and then 404 on the review GET, an intermediate state this design never defined.

**Resolution: one endpoint, not two.** `SessionLobbyPage` determines its branch entirely from the Decision 1 endpoint's own response, using the `currentSessionStatus` and `isFacilitator` fields Decision 1 now returns on every path, not only `200`:
- `200` → render the `pre_session` branch with the returned data; `isFacilitator` drives "Begin First Topic" per Decision 4.
- `409` with `currentSessionStatus: 'lobby'` → render the `lobby` branch (today's waiting message + the new Start Session control, rendered only when `isFacilitator` is `true`).
- `409` with `currentSessionStatus: 'active'` (or any other non-`pre_session` value) → leave the page.
- `404` → no standing on this session; existing no-access handling applies.

This is narrower than Marcus Oyelaran's design-review suggestion of adding a second, dedicated session-scoped status endpoint (`GET /api/v1/sessions/:sessionId/status`) alongside the review endpoint. **Architect's call, diverging from the literal suggestion while resolving the same root problem it identified:** a second endpoint would need to independently carry the same F1/F2 security hardening (timing floor, `Cache-Control: no-store`) the review endpoint already carries, doubling the surface that has to stay in sync for no functional gain — the review endpoint already resolves `sessions.status` on every call (Decision 1 step 3) and already has a `409` path that needs *some* body; attaching `currentSessionStatus` to that existing body is a smaller, better-contained fix than standing up a sibling route. `RevealFailureResponse`'s non-recoverable variant already establishes `currentSessionStatus` as this codebase's precedent for "an error body that tells the frontend what state things are actually in" — this reuses that precedent rather than inventing a new one.

One consequence worth naming: the `lobby` branch is now determined by a `409` response from an endpoint whose primary purpose is fetching review data, not a dedicated status check. This is judged acceptable because the endpoint already has to resolve status on every call regardless of outcome (Decision 1), so no extra query is introduced by using it this way — see the Risks section's F3 discussion for the one query cost this endpoint always pays.

**Facilitator's "Start Session" control (resolving design-review engineer finding #1):** the `lobby` branch renders a "Start Session" control, visible only when the `409` response's `isFacilitator` field (see Decision 1, step 3) is `true` — the same session grant the review endpoint always resolves, at every status, not only `pre_session`. This mirrors `App.tsx`'s own documented gap (the "KNOWN DEFERRED GAP" comment on the `/session/:sessionId/facilitator` route notes the frontend has never had a client-side concept of "am I this session's facilitator"): this change is what finally gives `SessionLobbyPage` that signal, sourced from the same backend grant throughout, rather than inventing a second one. As with Decision 4's reasoning for "Begin First Topic," a client-side bypass of this rendering signal is not a security hole — `POST /start`'s handler independently checks `facilitator_id` server-side (confirmed in `facilitator-sessions.ts`) regardless of what the client renders. On click, the control calls `POST /api/v1/sessions/:sessionId/start`; on success, the session transitions to `pre_session` server-side and every subscriber's WebSocket delivers `session_state_change`, moving all participants (including the clicking facilitator) to the `pre_session` branch, which then independently fetches the review data — the `POST /start` response's own `actionItems` payload is not consumed by the frontend at all (see Decision 4's reconciliation, below). On failure, the control shows an inline retry affordance and the session remains in `lobby`.

**Subscribe-before-fetch ordering (resolving design-review engineer finding #4 — see also Risks):** the WebSocket subscription to `session_state_change` is established *before or concurrently with* the initial Decision-1-endpoint fetch on mount, not after it. This closes the gap where a transition (`lobby → pre_session` via Start Session, or `pre_session → active` via Begin First Topic) commits between a page's initial fetch and its subscription going live, which would otherwise strand a participant on a stale branch until manual refresh. See Risks for the full mechanism.

**Alternatives considered:** A separate route/page for `pre_session`, entered via a redirect once the lobby detects the transition. Rejected as the primary recommendation — it would require inventing a redirect trigger that doesn't exist today (the lobby currently has no session-state awareness at all, so "redirect on transition" and "branch in place on transition" require building the same missing piece: a live status subscription), and it fragments one participant journey across two route components for no isolation benefit, since both states share the same WebSocket subscription and the same "am I the facilitator" signal. If a future change finds `SessionLobbyPage` becoming unwieldy as more states accrete, splitting is easy to do later; folding two routes back into one is not.

### Decision 4 — `isFacilitator` from the GET response is the frontend's facilitator signal

The frontend has no existing concept of "am I this session's facilitator" (per-session, not per-team) — `AuthSession` only carries global identity and team membership role; `App.tsx`'s own comments name this as a known gap. Rather than inventing a second facilitator check, the "Begin First Topic" control's visibility is driven by the same `isFacilitator` flag the review endpoint returns, itself derived from `evaluateSessionSubscriberAccess`'s grant path — the same authorization the backend already trusts for `begin-voting`'s own facilitator check. A client-side bypass of this rendering signal is not a security hole: `begin-voting` re-enforces `facilitator_id` server-side regardless of what the client renders.

**Reconciled with Decision 5 and spec.md, per design-review engineer finding #3.** Decision 3's architecture has the review screen independently call the Decision 1 endpoint for every participant, including the facilitator — the `POST /start` response's `actionItems` payload is consumed once, by the Start Session control, and never reaches the rendered review screen at all (see Decision 3). That means "Begin First Topic" has exactly **one** data source for both its visibility and its enabled/disabled state: the Decision 1 endpoint's own success/failure and its `isFacilitator` field. There is no second gate tied to `POST /start`'s payload having loaded — an earlier version of Decision 5 and spec.md described one, written before Decision 3's re-fetch architecture was fully settled; that scenario is corrected below and in spec.md to point at the same single source of truth this decision already established.

### Decision 5 — Error states

- **GET fails (network, 5xx, or session found but query error):** review component shows an explicit inline error with a retry affordance — not a blank screen, not an infinite spinner. Matches this endpoint's own postcondition contract (UC1: "the application displays an error and does not advance to topic voting"). This applies uniformly to every participant on the `pre_session` branch, **including the facilitator** — per Decision 3/4's reconciliation, the facilitator's review screen is fed by this same call, not by `POST /start`'s response.
- **"Begin First Topic" stays disabled until the review GET (the same call above) has succeeded** — one gate, not two (see Decision 4's reconciliation). The session must not be advanceable on a failed query; enforced client-side as a disabled-control state. `begin-voting` itself has no dependency on the review payload having loaded correctly, so this is purely a UX gate, not a new backend precondition. **Superseded:** an earlier version of this bullet tied the control's disablement to "the facilitator's action-items payload... on the `POST /start` response" — a different endpoint the rendered screen does not actually consume (see Decision 3/4). spec.md's corresponding scenario is corrected to match.
- **The new "Start Session" control (Decision 3) fails** (e.g. the facilitator double-clicks after another tab already started the session, or a network error): inline retry affordance on the `lobby` branch; the page remains on `lobby` and does not assume the transition happened.
- **Per-item staleness computation failure:** degrades to "no staleness indicator" for that one item, per UC: Flag Stale Action Items' own documented failure postcondition — never blocks the whole screen.
- **`begin-voting`'s pre-existing "no topics configured" bare-`Error`/500:** not fixed here (SESSION-005 issue), but the control's error handling must not assume it always receives a clean 4xx — a generic "couldn't advance, try again" fallback covers this case without depending on the underlying fix.

### Decision 6 — Ordering and the discussion-flag control

**Resolved during implementation (tasks.md 1.2), reasoned default — NOT a live stakeholder
confirmation.** No stakeholder session was available during this implementation pass, so
per the same "make and document a reasoned default, flag for real confirmation" approach
applied elsewhere in this change: item ordering is implemented **stale-first** (highest
staleness level first — red, then orange, then yellow, then none; ties broken by the
existing oldest-created-first order), matching the Facilitator persona's preference voiced
during the explore-stage review (`explore-review-facilitator.md`) — the room's most-in-need-
of-attention items surface first, rather than requiring a scan of the full list.

This is implemented in one isolated place — `packages/frontend/src/components/PreSessionActionItemReview.tsx`'s
`sortForReview` step (see tasks 5.2) — specifically so it is cheap to flip back to chronological
oldest-first (`fetchPreSessionActionItems`'s own query order, unchanged) if actual
stakeholder confirmation lands on the opposite answer. **This still needs real
stakeholder confirmation before being treated as settled** — UC1's own Notes section
never resolved this, and a persona-review preference from the explore stage is a
reasonable default, not a substitute for that confirmation.

Whether the facilitator can flag an item for live discussion from this screen is
**explicitly not in scope** for this change (see proposal.md) — it is not addressed
further here because it isn't being built.

### Decision 7 — Fix `computeStalenessLevel` to implement the decided 1/2/3-session mapping directly

**Blocking finding from propose-stage BA review:** `computeStalenessLevel(sessionsSinceUpdate, threshold)` steps `none`/`yellow`/`orange`/`red` at `< threshold` / `>= threshold` / `>= threshold*2` / `>= threshold*3`. At the shipped default (`threshold = 2`), an item with 3 sessions elapsed computes `yellow`, not the `red` the legend this change is required to build says it should be. UC: Flag Stale Action Items' Notes section calls the 1/2/3 mapping "a decided requirement," and its Acceptance Criteria state each boundary unconditionally (e.g., "An action item with 3 or more completed sessions elapsed... is displayed with a red indicator") — not "when the configured threshold is 1." No existing spec file documents the threshold-multiplier behavior as a contract either (checked: `session-topic-lifecycle`, the capability `SESSION-004` shipped under, has no staleness requirement text at all). The multiplier behavior was never reconciled against the requirement it was meant to satisfy — the function's own comment says as much.

**Decision: fix `computeStalenessLevel` to compare `sessionsSinceUpdate` against the fixed literals 1/2/3 directly, dropping its dependency on `application_settings.staleness_threshold_sessions` entirely.** This is the smallest change that makes the screen's legend and its data agree, and it makes the corrected function match a requirement that was already formally decided and never actually implemented — it is a bug fix against the use case, not a new product decision.

**Alternatives considered and rejected:**
- **(b) Treat the threshold-multiplier as the new decided requirement and update the use case doc instead.** Rejected: this would mean asking a facilitator/BA sign-off to overturn explicit, checkbox-form acceptance criteria ("1 completed session elapsed... displayed with a yellow indicator," unconditionally) in favor of behavior nobody asked for and that only exists because it was never checked against the requirement. Reinterpreting a decided requirement to match an implementation accident is the wrong direction for this fix to run.
- **(c) Make all three level boundaries independently configurable**, matching the letter of "three thresholds, not one" the use case's requirement implies. Rejected for this change specifically: it would mean designing and shipping new configuration surface (three settings instead of one, admin UI or seed-data changes, migration), which is materially more scope than a read-only review screen warrants, and it directly reopens this proposal's own explicit out-of-scope line ("any change to how staleness thresholds are configured"). If per-team-configurable staleness boundaries turn out to be wanted, that is its own change with its own proposal — not a rider on this one.

**Consequences named explicitly, not left implicit:**
- This edits already-shipped code (`SESSION-004`, `facilitator-sessions.ts`) — contradicts this proposal's general "no changes to existing contracts" framing in one specific place. Called out in proposal.md's Impact section, not left for a reviewer to discover independently.
- The fix changes what `POST /start` returns too, not only this change's new GET endpoint, since both call the same `fetchPreSessionActionItems` → `computeStalenessLevel` path. A team upgrading past this change will see some previously-yellow items become orange/red (and some previously-"none" items become yellow) the next time they open a session — this is the fix taking effect, not a regression, but it is a visible behavior change for any team that has already been looking at the pre-fix mapping via the facilitator-only path.
- `application_settings.staleness_threshold_sessions` becomes an orphaned setting — its row and seed migration are left untouched (no schema change, no config-surface change), but nothing reads it after this fix. Not cleaned up here; named so it isn't rediscovered as confusing dead configuration later. A future change can decide whether to repurpose or remove it.
- **New test requirement (tasks.md):** a route test asserting the legend's stated thresholds and `computeStalenessLevel`'s actual output agree — cheap insurance against the two drifting apart silently again, since this is exactly how the original drift went unnoticed.

## Risks / Trade-offs

- **[Risk] Fetch-then-subscribe race — deferred item-status write path (out of this change's scope).** A status update via the *deferred* PATCH path, once the follow-up issue wires it in, landing between a client's initial GET and its WebSocket subscription going live could show two participants transiently different lists. → **Mitigation, this change:** not applicable yet, since no write path exists in this change's scope for anything to race against. **Flagged for the follow-up issue:** the follow-up that wires in status-update controls must address this — likely by subscribing before issuing the initial GET, or by re-fetching once the subscription confirms live, rather than trusting a GET snapshot with no reconciliation. Noting it now so it isn't rediscovered as a surprise when the follow-up lands.
- **[Risk] Fetch-then-subscribe race — session-state transition (in this change's scope). Named separately per design-review engineer finding #4: this is not the same race as the item-status one above, and it is not deferred.** `begin-voting` is a write path this change wires in directly (the "Begin First Topic" control), and the same is now true of `POST /start` (the new "Start Session" control, Decision 3). Without a mitigation, this sequence is possible: (1) a participant's `SessionLobbyPage` completes its initial Decision-1-endpoint fetch and begins rendering a branch; (2) before that participant's WebSocket subscription to `session_state_change` goes live, the facilitator advances the session (`start` or `begin-voting` commits and publishes); (3) the participant's subscription starts after the publish, so they never receive the transition event and are stranded on a stale branch (`lobby` after the session moved to `pre_session`, or `pre_session` after it moved to `active`) until a manual refresh. → **Mitigation:** Decision 3 requires the WebSocket subscription to be established *before or concurrently with* the initial fetch, not after it — closing the window the sequence above depends on. Any transition published after the subscription is live is delivered normally; any residual gap between "subscription requested" and "subscription confirmed live" is reconciled by treating the initial fetch's own response as authoritative for the very first render, then trusting subsequently-delivered WS events from that point forward — the same reconcile-after-subscribe pattern the item-status risk above recommends for its own (deferred) case, applied here where it's actually in scope.
- **[Risk] `409` vs `404` distinction leaks a small amount of information** (a caller with a stale/guessed session ID can tell "exists but wrong status" from "doesn't exist or no access") — consistent with the precedent `session-topic-lifecycle` already sets for `already_revealed`/`advance_blocked` (authorization-before-precondition, precondition failures get their own status), and low-severity since the caller must already be authenticated. → **Mitigation:** none needed beyond following the existing precedent; not treated as a new exposure. **Security review F1:** a timing side channel could let an authenticated-but-unauthorized caller distinguish these cases even without relying on the status code or body at all — addressed by applying `applyTimingFloor()` to every response path (Decision 1), independent of this risk's own low-severity framing of the status-code leak itself.
- **[Risk] This change does not fully close the accountability loop.** A read-only screen displays the loop's current state; closing it requires the deferred owner/facilitator status-update path. → **Mitigation:** stated explicitly in proposal.md as a limitation, and the follow-up issue is a merge-blocking commitment (filed before this change merges), not an aspirational note.
- **[Trade-off] One additional DB read per GET call** (the explicit session-status check in Decision 1, step 3) beyond what the grant alone provides, because the participant grant variant doesn't carry `sessionStatus`. Accepted — this is a single indexed lookup on `sessions.id`, and keeping one uniform code path for both grant variants is worth more than saving one query on the facilitator path alone. **This is not only a performance trade-off — security review F3 correctly names it as reopening a documented property.** `session-subscriber-access-helper.ts`'s own header comment states its single-query design exists so "the authorization decision is made on a consistent snapshot (no TOCTOU gap between separate reads)"; Decision 1's second read evaluates the `pre_session` gate against a possibly-later snapshot than the one the grant itself was decided on. **Architect's decision: accept this explicitly (option (b) of F3's two proposed fixes), not F3's alternative (a) of adding `sessionStatus` to the `participant` grant variant.** Verified against the code before deciding: `ws-event-dispatcher.ts`'s `dispatchActionItemStatusUpdated` (Decision D14, `actionitem-updated-live-broadcast`) documents, as load-bearing rationale, that "`SessionSubscriberGrant`'s `participant` branch carries no `sessionStatus`" and works around that absence deliberately (an envelope-stamped status plus one dispatch-time reconciliation read, not a per-candidate grant read). Changing the shared `SessionSubscriberGrant` type to add `sessionStatus` to the `participant` branch is additive and would not break that code, but it would make D14's own comment inaccurate the moment it shipped, and it reaches into a sibling, already-shipped capability's documented design rationale that this proposal's own Impact section commits to leaving untouched ("no changes to... websocket-specification's event shapes"). The practical impact of the gap this leaves is low regardless, exactly as F3 itself concludes: read-only data, a millisecond-scale window, and the caller was already authorized at the moment the grant was evaluated — the worst case is a participant briefly seeing `pre_session` data for a session that transitioned moments earlier, not unauthorized exposure. Named here explicitly so a future reader of either module doesn't assume a guarantee this endpoint doesn't actually provide.
- **[Non-gap, named explicitly per security review F4] No audit logging for this endpoint's ordinary reads.** Consistent with `content.ts`'s precedent: ordinary authorized `member`/`facilitator` reads are never audit-logged there either — only `evaluateTeamAccess`'s `admin`-path denial is (`admin.session_content_denied`), because that helper has an admin path with no legitimate claim to session content, making its denial the security-relevant event worth recording. `evaluateSessionSubscriberAccess` has no admin path at all and structurally excludes Engineering Managers at the query level (a `null` grant, not a denial branch) — there is no analogous "elevated role got denied" event for this endpoint to log. This codebase does audit-log action-item *reads* specifically when the reader is an EM crossing the normal boundary (`em.action_items_accessed`/`em.action_item_accessed`, `audit-logger.ts`) — that precedent doesn't apply here because an EM gets `404` from this endpoint, never a read. This is a deliberate omission, not an oversight.
