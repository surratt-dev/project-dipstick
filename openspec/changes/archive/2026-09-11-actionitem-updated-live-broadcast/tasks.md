- [x] 1.3 Resolve Open Question 3 (design.md): HTTP response code for a rejected invalid-transition attempt. **Resolved:** `409 Conflict`, unhedged, ratified as drafted.
- [x] 1.4 (new) Resolve the anti-enumeration `403`/`404` ordering for this endpoint (design.md Decision D12, per Tomás Ferreira's F2 — not one of the original three questions, a gap the security review found in addition to them). **Resolved:** load-by-id-alone → `404` if missing; if found, `404` (not `403`) for a caller with zero relationship to the item's team; `403` only for a caller who has some relationship to the team (member, Application Admin, or a facilitator with any relationship to the team — including outside D10's narrower write-authorization window — per the broadened relationship test 3.1b defines), and is non-owner/non-authorized-facilitator. **Corrected by Ingrid Sollenberger's task-review Finding 1** (`tasks-review-architect.md`): the relationship test is self-contained (`evaluateTeamAccess` non-null, or any facilitator_id match for the team at any status), not a reuse of D10's narrower write-authorization query — see 3.1b.
- [x] 1.5 (new) Resolve the `audit_log` gap (design.md Decision D13, per Tomás Ferreira's F3 — not one of the original three questions). **Resolved:** add `AuditEventName` `action_item.status_changed`, written to `audit_log` in the same transaction as the status update and `action_item_history` insert, matching `recordRevealTriggeredAudit`'s pattern.
- [x] 1.6 (new) Resolve the dispatcher `sessionStatus` data-availability gap (design.md Decision D14, per Marcus Oyelaran's Blocker 1, closed alongside Tomás Ferreira's F5). **Resolved:** carry `sessionStatus` on the internal `ws:events` envelope (mirroring `VoteRevealedTriggerPayload`), plus one delivery-time freshness re-check per dispatch (not per-candidate).

## 3. Backend: action item status mutation (issues #64 + #65)

- [x] 3.1 Add `PATCH /api/v1/action-items/:actionItemId/status` (per `VOTE-002`'s documented path, ratified by 1.2) in a new or existing backend route file. The `200` response body matches VOTE-002's documented `UpdateActionItemStatusResponse` shape exactly: `actionItemId`, `status`, `resolutionNote`, `resolvedInSessionId`, `updatedAt` (per Marcus Delgado's minor task-review observation — `tasks-review-ba.md`).
- [x] 3.1a (new, Decision D12 — anti-enumeration ordering, per Tomás Ferreira's F2) Load the action item by ID alone first: `SELECT id, team_id, owner_id, status FROM action_items WHERE id = $1`. No row → `404`. This lookup happens before any ownership/facilitator check — the endpoint's URL carries no `teamId` to gate on the way `content.ts`'s team-scoped routes do, so the item must be loaded to learn its team before authorization can be evaluated at all.
- [x] 3.1b (new, Decision D12, corrected per Ingrid Sollenberger's Finding 1 — `tasks-review-architect.md`) With the item loaded, evaluate the caller's **relationship** to `team_id` — this is a disclosure-safety boundary, deliberately broader than 3.3/D10's write-authorization gate below, and does **not** reuse 3.3's narrow query as its facilitator signal:
  - owner (`owner_id = userId`); OR
  - `evaluateTeamAccess(userId, team_id)` returns a non-null grant (covers plain team membership, Application Admin, and a facilitator within `evaluateTeamAccess`'s own broader `draft`/`complete`-grace windows — all of these already have legitimate read-access standing on this team via other endpoints, so disclosing existence to them is not new information); OR
  - `EXISTS (SELECT 1 FROM sessions WHERE facilitator_id = userId AND team_id = team_id)` — **no status filter at all**, i.e. "has this user ever been the facilitator of any session for this team," broader even than `evaluateTeamAccess`'s grace windows (covers a facilitator whose only session for this team is now `complete` and past its grace window, or otherwise outside every window checked elsewhere).

  If **none** of the above hold, return `404` (not `403`) — indistinguishable from 3.1a's "doesn't exist," closing the enumeration oracle `content.ts:521-526` already closed once for the session case. If any hold, the caller has "some relationship" for 3.2's purposes, regardless of whether that relationship also satisfies 3.3/D10's narrower write-authorization scope. Apply the same timing floor (`applyTimingFloor`) across this and 3.2/3.3's denial branches.

  *Why not just reuse 3.3/D10's query, or reorder 3.1b after 3.3?* D10's check is deliberately narrow (`lobby`/`pre_session`/`active`/`wrap_up` only) because it's a write-authorization gate — a facilitator outside that window correctly gets denied the *write*. But that same narrow check, used as the *only* facilitator signal for the 404-vs-403 disclosure boundary, would wrongly return `404` for a facilitator who has real, disclosed standing on the team (e.g. via a `draft`/`complete`-grace-window session, or a long-past facilitation) — which is exactly what 6.1a-i/6.1a-ii's tests expect `403` for. These are two different boundaries; 3.1b now answers the disclosure question directly and self-contained, rather than forward-referencing 3.3's write-authorization query as if it answered both.
- [x] 3.1c (repositioned from 3.6a, per Ingrid Sollenberger's Finding 4 — `tasks-review-architect.md`; Decision D11) Validate an optional `sessionId`: `422` unless it references a session for the item's `team_id` with `status IN ('lobby','pre_session','active','wrap_up')` — same set as 3.3, distinct from Group 4's `pre_session`-only broadcast gate (D2, unchanged). Facilitator authorization (3.3) does not itself require `sessionId` to be supplied — it is evaluated independently against `team_id`; `sessionId`, when supplied, is used for 3.7/3.6's history and broadcast attribution. Grouped here with 3.1a/3.1b rather than nearer 3.7 (its only hard dependency, which it satisfies from either position): it validates an independent request-body field with no dependency on 3.2/3.3's authorization outcome, and reads more naturally alongside the other "figure out what we're dealing with before running business logic" checks.
- [x] 3.2 Implement owner enforcement: 403 if the authenticated user is not `action_items.owner_id` and not an authorized facilitator per 3.3 — reachable only after 3.1b confirms the caller has *some* relationship to the item's team (an ordinary team member, an Application Admin, or a facilitator whose relationship exists but falls outside 3.3/D10's narrower write-authorization window — see 3.1b; disclosing this to any of them via `403` is not new information, since each already has some legitimate standing that lets them see the item exists).
- [x] 3.3 Implement facilitator enforcement per the scope resolved in 1.1/Decision D10: a purpose-built check — `SELECT 1 FROM sessions WHERE facilitator_id = $1 AND team_id = $2 AND status IN ('lobby','pre_session','active','wrap_up')` — **not** a call to `evaluateTeamAccess` (its `draft`/`complete` grace windows are broader than "actively facilitating" and must not leak into this write path, per Tomás Ferreira's F1) and **not** 3.1b's broader "ever facilitated" existence check (that check answers "does this caller have any relationship worth disclosing," not "is this caller currently authorized to write"). 403 outside that scope, with a reason distinguishable from "not the owner" for frontend messaging and audit-log fidelity (SEC-13).
- [x] 3.4 Implement transition-validity checks: reject backward transitions and any PATCH targeting an item whose current status is already `Resolved`, using the response code resolved in 1.3.
- [x] 3.4a (new, per Ingrid Sollenberger's Finding 2 — `tasks-review-architect.md`) Open a database transaction and execute the `action_items.status` UPDATE, targeting the validated new status — only after 3.2/3.3's authorization checks and 3.4's transition-validity checks have passed. This transaction stays open through 3.6 (`resolutionNote`/`resolved_in_session_id`), 3.7 (`action_item_history` insert), and 3.9 (`audit_log` insert), all of which write inside it and commit or roll back together; 4.2's publish call fires only after this transaction commits. (3.5's same-status no-op is a separate, simpler branch — a single-row `updated_at` bump — and does not require this multi-table transaction.)
- [x] 3.5 Implement same-status no-op handling: bump `action_items.updated_at`, skip the `action_item_history` write and the broadcast, for `Open`/`In Progress` targets only (not `Resolved`, per 3.4).
- [x] 3.6 Implement `resolutionNote` handling (Decision D9, issue #65): accept an optional `resolutionNote` only meaningful when the transition targets `Resolved`; validate ≤500 characters, `422` otherwise (matching the existing `action_items_resolution_note_length` CHECK constraint); ignore (do not persist) a `resolutionNote` supplied on a non-resolving transition. **Within 3.4a's transaction, set `action_items.resolution_note` to the supplied note when the transition targets `Resolved`** (this is the column `content.ts`/`em-views.ts` read from directly, per Marcus Delgado's blocking Finding 2 — `tasks-review-ba.md`; see also design.md D5/D9's updated text) — `NULL` when the transition targets `Resolved` with no note supplied, unchanged (still `NULL`, per the CHECK constraint's own default) for a non-resolving transition. Also set `action_items.resolved_in_session_id` to the supplied `sessionId` when the transition targets `Resolved` and one was provided.
- [x] 3.7 Write the `action_item_history` row (per `action-item-status-management`'s history requirement) in the same transaction as the `action_items.status` update (3.4a): `changed_by_user_id` = acting user, `previous_status`/`new_status`, `resolution_note` per 3.6 (the same value written to `action_items.resolution_note`, duplicated onto this history row per D5's existing contract), `session_id` populated per 3.1c's resolution when applicable — distinct from and independent of `resolved_in_session_id` (3.6).
- [x] 3.9 (new, Decision D13, per Tomás Ferreira's F3) Add `action_item.status_changed` to `AuditEventName` (`packages/backend/src/auth/audit-logger.ts`). In the **same transaction** as 3.4a's `action_items.status` update and 3.7's `action_item_history` insert, `INSERT INTO audit_log` (`actor_user_id`, `actor_global_role`, `actor_ip`, `operation`, `team_id`, `metadata`), matching `recordRevealTriggeredAudit`'s shape. `metadata`: `action_item_id`, `previous_status`, `new_status`, `authorization_path` (`"owner"` | `"facilitator"`), `session_id` if supplied. Also call `emitAuditEvent(logger, "action_item.status_changed", ...)` for the operational structured-log counterpart. Skip for same-status no-ops (3.5), matching 3.7's history-write skip.
