## Context

Framed from my (Devon Calloway, Internal Champion) perspective, grounded in exploration (`exploration-notes.md`) and its two review passes (`explore-review-facilitator.md`, `explore-review-ba.md`).

There is no write path for `action_items.status` anywhere in the shipped codebase today — the only place FR-3.2/FR-7.3's status transition is specified is issue #64, itself open and unscheduled. FR-3.3's live broadcast (issue #95, `[PREF]`) has nothing to broadcast without it. Exploration concluded, and the team confirmed, that these ship together as one atomic change (exploration-notes.md §3/§9): the mutation should never exist without the correctly-cataloged event sitting next to it, closing the window where someone could bolt an ad hoc real-time mechanism onto #64 that doesn't follow this repo's `websocket-specification` catalog conventions.

This isn't a review of the ritual's five structural constraints (simultaneous reveal, no-manager participation, facilitator-from-another-team, topic-default restorability, cross-person comparison) — action item status is team backlog housekeeping, not psychological-safety content, and none of those five are touched here. It is a "don't let plumbing drift from the catalog's own conventions, and don't let a live broadcast start performing at people" review — a quieter kind of fidelity problem, but a real one.

**Correction, post-proposal-review:** an earlier draft of this design (and the proposal) stated that `requirements/design/REST API Contract.md` had no entry for this endpoint. That was wrong. `VOTE-002 — Update Action Item Status` (lines 1870–1935) is a complete, pre-existing contract for this exact endpoint — path, request/response shape, authorization rules, error table, and implementation notes — missed by exploration and both of its review passes as well as this design's first draft. This revision reconciles against it directly; see Decision D9 and the reframed Open Questions below. This is the same kind of cross-document drift risk this design has been naming throughout (D1's rationale, D8's forcing-function point) — it just turned out to apply to this change's own process, not only to what it was trying to prevent downstream.

## Goals / Non-Goals

**Goals:**
- Ship the `action_items.status` write path (owner + facilitator authorization, FR-7.3 transition validity, `action_item_history` audit trail) and the live WebSocket broadcast of pre-finalization changes (FR-3.3) as one atomic unit.
- Follow this repo's established WebSocket catalog conventions exactly: typed `WsEventType` member, `ws:events` Redis envelope, publish-after-commit-or-best-effort (see Decision D7), per-candidate delivery-time authorization inside `ws-event-dispatcher.ts`, and a flipped Event Registry row that the automated conformance test (`packages/shared/src/__tests__/websocket-spec-conformance.test.ts`) checks.
- Preserve the application's existing non-spotlight rendering principle for anything this change's payload/event design will eventually feed into a UI (issue #69), even though #69's frontend is not built here.

**Non-Goals:**
- The #69 pre-session review screen itself — this change ships the endpoint and event it will eventually consume, not the screen.
- Reconciling the BRD/use-case inconsistency on staleness-threshold semantics (FR-7.4's single threshold vs. the use cases' three-color graduated scale). This change's own reset write (`action_items.updated_at`, a plain timestamp) is neutral to either reading and does not attempt to settle which is correct — that's a separate BA documentation follow-up.
- Building any frontend rendering for this event. The non-spotlight constraints below (Decision D8) bind the payload/event contract so #69 doesn't have to rediscover them, but no UI ships in this change.

## Decisions

**D1 — Combine #64 and #95 into one change.**
Rationale: FR-3.2 (`[HARD]`) shipping without FR-3.3 (`[PREF]`) is a fine intermediate state — participants just refresh. FR-3.2 shipping with a *second, non-catalog* real-time mechanism bolted on, which #95 later has to adopt or rip out, is a worse outcome. Alternative considered: ship #64 alone first, #95 as a fast-follow. Rejected because #64's own acceptance criteria already claims "real-time propagation... when viewed in a shared context" — leaving that door open invites exactly the ad hoc implementation this decision exists to prevent.

**D2 — Delivery pattern: session-scoped, any valid grant, gated to `pre_session`.**
Matches `session_state_change`'s recipient breadth (any participant or facilitator with a valid session grant), not `participant_joined`/`participant_left`'s facilitator-only pattern. Rationale: FR-3.3's own text is "visible to all session participants," and the most recently-shipped precedent (#94, facilitator-only) is an easy but wrong pattern to copy from without reading the requirement text. Alternative considered: team-scoped, `topic_history_update`-style — rejected because it would deliver to any connected team member (e.g., an idle EM-dashboard connection), a real deviation from FR-3.3's stated scope, in exchange for slightly simpler trigger-side plumbing. Gated to `pre_session` because FR-3.1 places this review strictly "before the first voting topic is presented."

**D3 — New `WsEventType` member: `action_item_status_updated`.**
Distinct from `topic_history_update`'s `action_item_finalized` updateType (wrap-up-only, a different mechanism despite the superficially similar name) and distinct from the `actionitem.updated` dot-notation name in the corrected-names table (which is the prior/conceptual name, not a wire name — same convention already applied to `reveal.trigger`, `vote.locked`, etc.).

**D4 — Payload: `previousStatus` + `newStatus`, not `newStatus` alone. `resolvedInSessionId` deliberately not carried.**
Matches `SessionStateChangePayload`'s shape (the delivery-pattern precedent D2 already follows). Costs nothing — the mutation has both values in hand — and renders better client-side ("moved from In Progress to Resolved" vs. an undated "is now Resolved"). No `resolution_note` field, matching this catalog's existing payload-minimalism convention (`VoteReadinessUpdatePayload`, `ParticipantJoinedPayload`) — resolution notes are visible on re-fetch (the item's own detail view), not needed for the live "something changed" signal. Confirming a point the BA review raised: VOTE-002's REST response carries `resolvedInSessionId`, but the WS payload does not — this is a deliberate divergence, not an oversight. The REST response is the mutation's own durable record of what it did (useful to the actor and to anyone re-fetching); the WS payload is a live "something changed, here's what" signal to *other* connections, which don't need `resolvedInSessionId` to render a status update and would only be carrying it for parity's sake. The two contracts are allowed to differ in field set for this reason.

**D5 — `action_item_history` contract for this change, and its relationship to `action_items.resolved_in_session_id`.**
Cited directly against the existing schema (`packages/backend/migrations/2_create_tables.sql:152-161`, which already has every column needed — no migration required): `resolution_note` carries the supplied note when the transition targets `Resolved` and one was provided (validated ≤500 chars, `422` otherwise, matching the existing `action_items_resolution_note_length` CHECK constraint and VOTE-002's documented error table), `NULL` for any non-resolving transition or when omitted (see D9); `session_id` populated exactly when Open Question 2 (session-context plumbing) resolves to "a session was in play," `NULL` otherwise; `changed_by_user_id` is the acting user, not the item's `owner_id` — this closes the previously-open "actor visible in history" question from the action-item-history use case. History-row write and the `action_items.status` update happen in the same database transaction; either failing rolls back both.

**Correction (Marcus Delgado's blocking Finding 2, `tasks-review-ba.md`):** the resolution note write is **not** limited to `action_item_history.resolution_note`. The transition mutation also sets `action_items.resolution_note` itself — the action item's own current-state column — to the same supplied value, in the same transaction. This was never stated explicitly in any of proposal.md, this design, the delta spec, or tasks.md 3.6/3.7 prior to this correction, even though it's load-bearing: `content.ts:433-440` and `em-views.ts:800-907` both read resolution notes off `action_items.resolution_note` directly, never off `action_item_history`, and an existing passing test (`em-views.test.ts:681`) asserts that exact round-trip. Without this write, a resolution note would validate, audit-log, and persist to the history row correctly, and then never appear anywhere a user can actually see it — silently defeating D9's entire point (closing #65, making resolution notes visible). `action_item_history.resolution_note` and `action_items.resolution_note` are set to the same value in the same transaction, for the same reason `action_item_history.session_id` and `action_items.resolved_in_session_id` are two distinct-but-related writes below: one is the durable current-state column every read path already uses, the other is this specific transition's audit-trail entry.

This is a **distinct column from `action_items.resolved_in_session_id`**, which this change also wires up (per VOTE-002 and D9): `action_item_history.session_id` is written on *every* real transition and records the review context the change happened in; `action_items.resolved_in_session_id` is written only when the transition's target is `Resolved` and a `sessionId` was supplied, and records which session resolved the item — a property of the current `action_items` row, not of one history entry. Both get populated by this change; they answer different questions and are not redundant with each other.

**D9 — Resolution-note capture (`resolutionNote`, `resolved_in_session_id`) is in scope for this change, not deferred to issue #65.**
Reverses the original exploration/proposal framing, which deferred this as "issue #65, separate and unscheduled" — that framing was built on an incorrect premise (see Context's correction note above). VOTE-002, the pre-existing canonical contract for *this exact endpoint*, already specs `resolutionNote` and `resolved_in_session_id` as part of the same PATCH this change is building, not a second endpoint. The underlying schema (`resolution_note`, `resolved_in_session_id`, the length CHECK constraint), the shared TypeScript type, and the read path (`content.ts`, `em-views.ts`, with an existing round-trip test in `em-views.test.ts`) all already exist — only the write side was ever missing, and this change is building the write side regardless. Issue #65's own text confirms it isn't separable work: *"Direct extension of the status-update endpoint above — once it exists, add an optional resolution-note field..."* — it was only ever a follow-on because the endpoint didn't exist yet; now that this change builds the endpoint per VOTE-002's full contract, there's no remaining slice of #65 left to defer.

This is explicitly **not** the "while we're in there, let's also pull in adjacent scope" pattern the exec review specifically praised this change for avoiding with #65 and #69 in its first draft. The distinction: #69 is a different surface (a frontend screen, unscheduled, with its own scope) genuinely worth keeping separate. #65 was never a different *feature* — it was the unbuilt remainder of the same documented endpoint contract, artificially split into its own issue only because the endpoint itself didn't exist yet to extend. Implementing VOTE-002 as already documented, for the one endpoint this change was always building, is the option with *less* net drift from existing documentation, not more scope. Alternative considered: keep the original narrowing (ship without `resolutionNote`, formally revise VOTE-002 down, leave #65 open to revise it back up later). Rejected — it would mean deliberately shipping a different, narrower version of an endpoint than its own canonical contract describes, on the same path, then having to touch that contract a second time almost immediately to widen it back; strictly worse than building it once, correctly, against the contract that already exists.

**D6 — Same-status no-op semantics.**
A same-status request is accepted gracefully for `Open`/`In Progress` targets: `action_items.updated_at` is bumped (this is the field the read-time staleness computation reads, per the "Flag Stale Action Items" use case's own implementor note that staleness should be computed at read time, not stored), no `action_item_history` row is written, no broadcast is published. A same-status request against an already-`Resolved` item is **not** a no-op — it's rejected outright, because `Resolved` is a terminal state and not a valid PATCH target at all per the owner-update use case's precondition, a distinction the original exploration pass missed and the BA review caught. Authorization is enforced identically on a no-op as on a real transition.

**D7 — Mutation success is never coupled to broadcast success.**
The status mutation is authoritative and always succeeds or fails on its own merits; a missing or invalid session context, or a Redis publish failure, only ever affects whether the broadcast fires — never whether the PATCH succeeds. This mirrors two existing precedents at once: `ws-pubsub.ts`'s publish-after-commit discipline for durable-state events (publish only ever follows a successful commit, never blocks or rolls back the write it followed), and the participant-presence events' explicit carve-out from that same discipline (no backing transaction to commit before a live-connection signal). This event has a backing transaction (the status update) but the broadcast itself should be treated as best-effort on top of it, the same way a `vote_revealed` publish failure was never designed to undo a reveal.

**D8 — Non-spotlight rendering constraints (binding on the contract now, even though no UI ships in this change).**
Elevated from exploration's original "worth a sentence" framing after facilitator review (exploration-notes.md §7, §10): no toast, animation, sound, or color flash on receipt; no layout reflow that draws the eye (a status-grouped list must not visibly jump an item between sections mid-conversation); attribution (when a facilitator changes someone else's item) renders as informational/recorded, not performative — the specific rendering treatment is left to #69, but the payload's inclusion of both `previousStatus` and `newStatus` (D4) is what makes an "informative, not alarming" rendering possible without a re-fetch; failed-PATCH error states follow the same non-spotlight principle already stated for connection/error states elsewhere in this catalog; and the broadcast is informational only — nothing in this event's existence should couple to FR-3.4's review-advancement pacing, which stays exclusively facilitator-triggered.

**D10 — Facilitator authorization mechanism: a narrowed, purpose-built check, not `evaluateTeamAccess` reused verbatim.**
Resolves Open Question 1, incorporating Tomás Ferreira's F1 finding (`design-review-security.md`) and Marcus Oyelaran's reuse observation (`design-review-engineer.md`, "Open Question 1 — a reuse point the architect should have in hand").

Marcus is right that `evaluateTeamAccess`'s Path 3 (`team-content-access-helper.ts:38-46, 143-194`) is, almost verbatim, VOTE-002's documented middle formulation, and that reuse is this codebase's stated convention. Tomás is right that reusing it *unmodified* is unsafe: Path 3 also grants access when a team's session is `draft` (24h grace) or `complete` (`facilitator_access_expires_at` grace) — both windows exist for a defensible reason (read-content access to a session that just ended or hasn't started), but neither belongs on a *write* endpoint whose whole point is that facilitator authority is earned by actively running a session, not held standing. Calling `evaluateTeamAccess` as-is for this endpoint would quietly convert the ratified "active session exists" formulation into something closer to the standing-grant reading everyone — the BA, my own original lean, and both reviewers — agrees should be avoided.

**Resolution:** this endpoint's facilitator check is a new, explicit query, structurally similar to `evaluateTeamAccess`'s Path 3 and to `session-subscriber-access-helper.ts`'s own `LIVE_FACILITATOR_STATUSES` pattern, but scoped to the item's `team_id` (not a specific `sessionId`, since the endpoint's URL carries neither) and restricted to that narrower status set:

```sql
SELECT 1 FROM sessions
WHERE facilitator_id = $1 AND team_id = $2
  AND status IN ('lobby', 'pre_session', 'active', 'wrap_up')
```

No `draft`-grace branch, no `complete`-grace branch. This is deliberately **not** a modification of `evaluateTeamAccess` itself — that helper is shared by every other team-content-read endpoint, and narrowing its Path 3 to fix this one write path would silently change read-access behavior everywhere else it's called, which is a strictly worse outcome than a second, narrower, purpose-built check. Reuse the pattern (the SQL shape, the "priority-ordered grant" idea), not the function.

This same restricted status set is also what "active" means for Open Question 2's `sessionId` validation (see D11) — one definition of "active session for facilitator purposes," used consistently in both places, distinct from D2's `pre_session`-only broadcast gate.

**Stated for the record (Marcus Delgado's non-blocking Finding 3, `tasks-review-ba.md`):** this ratified set is broader than `03 - Pre-Session Action Item Review - Use Cases.md`'s own literal precondition for "Facilitator Updates Status of Any Action Item," which names only "the session is in the Pre-Session Action Item Review phase" (`pre_session` alone) and explicitly frames the permission as "session-scoped, not a general administrative one." Ratifying VOTE-002's broader formulation over the UC's narrower one (Open Question 1, above) was a deliberate choice, not an oversight — the comparison against `evaluateTeamAccess`'s still-broader grace windows (Tomás Ferreira's F1) and `session-subscriber-access-helper.ts`'s `LIVE_FACILITATOR_STATUSES` pattern is exactly this same tradeoff, just not previously checked directly against the UC text that originally motivated the question. Recording it here so the gap is a stated decision, not something visible only by reading the UC file directly.

**D11 — "Active session" definition for session-context plumbing, and the D7/Open-Question-2 boundary.**
Resolves Open Question 2, incorporating Tomás Ferreira's F4 finding.

`sessionId` is an optional request-body field (VOTE-002, ratified). When supplied, it is validated `422` unless it references a session for the item's team with `status IN ('lobby', 'pre_session', 'active', 'wrap_up')` — the same set D10 uses, chosen for consistency (one definition of "an active session exists for this team," not two). This is distinct from, and narrower in effect than, D2's broadcast-delivery gate, which stays `pre_session`-only and is otherwise unchanged: a facilitator can validly PATCH during `wrap_up` with a `sessionId` supplied (history/audit context recorded, `422` avoided) even though no live broadcast fires, because the session isn't in `pre_session`. That is not an inconsistency — D7 already establishes that broadcast eligibility and mutation success are different questions; this is the same principle applied one layer up, to broadcast eligibility versus session-context validity.

The facilitator-authorization check itself (D10) does not require the caller to supply `sessionId` — it independently asks "does an active session exist for this team where the caller is facilitator," using the item's `team_id`. `sessionId`, when supplied, is validated separately and used for `action_item_history.session_id` / broadcast targeting (Open Question 2's original session-context-plumbing problem — `action_items.session_id` is the item's *originating* session, not the one currently reviewing it, so the mutation has no other source for "which channel to publish to").

**The D7/Open-Question-2 tension, resolved explicitly (per Tomás's F4):** D7's "mutation success is never coupled to broadcast success" governs the failure domain *after* authorization has already passed — a missing `sessionId`, an inactive session referenced by one, or a Redis publish failure at that point only ever costs the broadcast, never the PATCH. It does **not** govern whether a facilitator is authorized in the first place. "No active session exists for this team where I'm facilitator" is an authorization-layer `403` (D10), evaluated before any transaction begins — not a broadcast-layer concern D7 makes lenient. These are different failure domains and D7 was never meant to reach into the first one; this sentence is what makes that explicit rather than inferred. The owner path needs no session context at all and is unaffected by any of this.

**D12 — Anti-enumeration ordering for this endpoint's `403`/`404` responses.**
New decision (not one of the original three Open Questions), resolving Tomás Ferreira's F2 finding.

VOTE-002's error table lists `403` ("not owner") and `404` ("does not exist") as independent rows. Implemented literally — look up the item by ID, `404` if missing, then check ownership/facilitator scope and `403` if found-but-unauthorized — this lets *any* authenticated user in the system, regardless of team, distinguish "this `actionItemId` exists" from "it doesn't" by observing `403` vs. `404`. That is a strictly worse version of the probe `content.ts:521-526` already closed for the equivalent session-lookup case (documented there as "Decision 7 / Blocking Issue 2").

This endpoint's URL (`PATCH /api/v1/action-items/:actionItemId/status`) carries no `teamId`, unlike `content.ts`'s team-scoped routes — so it cannot reuse `content.ts`'s exact mechanism (grant-evaluated-against-a-URL-supplied-`teamId`-first, then an `id AND team_id` filtered lookup). It must instead preserve the same invariant — a caller cannot learn "this ID exists" without already having some legitimate standing on its team — through a shape suited to an item-scoped URL:

1. Load the action item by ID alone: `SELECT id, team_id, owner_id, status FROM action_items WHERE id = $1`.
2. No row → `404`.
3. Row found: evaluate the caller's **relationship** to the item's `team_id` — a disclosure-safety boundary, deliberately broader than D10's write-authorization gate (step 4 below), and **not** implemented by reusing D10's narrow query as the facilitator signal here. Relationship holds if **any** of: owner (`owner_id = userId`); `evaluateTeamAccess(userId, team_id)` returns a non-null grant (plain team membership, Application Admin, or a facilitator within `evaluateTeamAccess`'s own broader `draft`/`complete`-grace windows — all already hold legitimate read-access standing on this team elsewhere, so disclosure is not new information); or a sessions row exists with `facilitator_id = userId AND team_id = team_id` for **any** status at all (broader even than `evaluateTeamAccess`'s grace windows — "has this user ever facilitated a session for this team"). If **none** of these hold (the caller has zero relationship to the item's team by any of these measures), return `404` — indistinguishable from step 2's "doesn't exist," which is the load-bearing move: an unrelated caller can never learn that a given `actionItemId` exists at all, anywhere in the system.
4. If the caller has *some* relationship per step 3 (an ordinary member, an Application Admin, or a facilitator whose relationship exists but falls outside D10's narrower write-authorization window — each of whom can already see this item exists via other read paths, so this discloses nothing new) but is not currently authorized to write per D10 (owner or the narrowly-scoped facilitator check), return `403`. This is the only branch where `403` is distinguishable from `404`, and it only fires for a caller who already has legitimate visibility into that team's action-item backlog.
5. Apply the same timing floor (`applyTimingFloor`, `content.ts`'s existing pattern) across steps 3–4's denial branches so timing doesn't reopen what the response code closes.

**Why step 3's relationship test doesn't just reuse D10's query (per Ingrid Sollenberger's Finding 1, `tasks-review-architect.md`):** D10's check is deliberately narrow — `lobby`/`pre_session`/`active`/`wrap_up` only — because it's a *write-authorization* gate, and this application's facilitator model is explicitly not team-membership-based (`evaluateTeamAccess`'s Path 3 keys purely off `sessions.facilitator_id`, and "facilitator-from-another-team" is one of this application's own load-bearing ritual constraints — a facilitator routinely has no `team_memberships` row at all for the team they facilitate). A facilitator whose only relationship to a team is a `draft`-grace or `complete`-grace session — exactly the case D10 deliberately excludes from write authorization — still has real, already-disclosed standing on that team via `evaluateTeamAccess`'s read paths. Using D10's narrow query as the *only* facilitator signal for this disclosure boundary would misclassify that caller as having zero relationship and return `404`, contradicting 6.1a-i/6.1a-ii's tests (which correctly expect `403`) and, worse, would be actively wrong: `404` implies no relationship exists, which is false for this caller. Step 3's relationship test is therefore a separate, broader check from D10's, evaluated independently — not a forward reference to D10's output.

Update VOTE-002's error table (task 5.3) to state this ordering, not two flat, independent rows.

**D13 — `audit_log` write, alongside `action_item_history`.**
New decision, resolving Tomás Ferreira's F3 finding.

`action_item_history` (D5) is a correctly-designed *business* record — read back by ordinary users through `content.ts`/`em-views.ts`, no `actor_global_role`, no `actor_ip`. It is not this codebase's security audit trail, and every other sensitive mutation writes to both: `teams.ts` (`team.role_changed`), `sessions.ts` (`session.vote_submitted`), `facilitator-sessions.ts` (`session.reveal_triggered`), `connection-reauthorization.ts` (`session.access_revoked_live`). This change follows the same pattern rather than treating the domain-history table as a substitute, which — per `audit-logger.ts`'s own established convention — this persona does not accept as equivalent.

Add a new `AuditEventName` member, `action_item.status_changed`, to `packages/backend/src/auth/audit-logger.ts`. Write an `INSERT INTO audit_log` (`actor_user_id`, `actor_global_role`, `actor_ip`, `operation`, `team_id`, `metadata`) in the **same transaction** as the `action_items.status` update and the `action_item_history` insert (D5) — matching `recordRevealTriggeredAudit`'s shape exactly. `metadata` carries at minimum: `action_item_id`, `previous_status`, `new_status`, `authorization_path` (`"owner"` or `"facilitator"` — making D10/D12's boundary auditable after the fact even if never exercised maliciously), and `session_id` when one was supplied. Also call `emitAuditEvent(logger, "action_item.status_changed", ...)` for the operational structured-log counterpart, matching every other audited mutation's dual-write.

**D14 — Dispatcher `sessionStatus` plumbing: carried on the internal envelope, with a delivery-time freshness check.**
Resolves Marcus Oyelaran's Blocker 1 and, as a consequence, Tomás Ferreira's F5.

`SessionSubscriberGrant`'s `participant` branch (`packages/shared/src/types/team-content-access.ts`) carries no `sessionStatus` — only the `facilitator` branch does. D2 requires delivering to *both* paths, gated on `sessionStatus === "pre_session"`. There is no existing precedent for that combination (`dispatchVoteReadinessUpdate` gates on status but only ever delivers to the facilitator path, which has the field; `dispatchSessionStateChange` delivers to both paths but gates on nothing), and `RegisteredConnection` has no fallback source either. Marcus's option 1 — carry `sessionStatus: SessionStatus` on the internal `ws:events` Redis envelope itself, mirroring `VoteRevealedTriggerPayload`'s existing precedent — is adopted over his option 2 (extending `SessionSubscriberGrant`'s `participant` branch), because the mutation handler already has the session's status in hand at publish time (it just validated it per D11), and extending a shared, heavily-documented helper's return type for one dispatcher's benefit is more invasive for no real gain.

The mutation handler stamps `sessionStatus` onto the envelope once, immediately after its own transaction commits, before publishing — the same discipline `VoteRevealedTriggerPayload` already establishes for `serverTimestamp`. This field lives on the envelope only; the client-facing `ActionItemStatusUpdatedPayload` (task 2.2) does **not** carry it, the same envelope-vs-wire-payload split D4 already draws for `resolutionNote`/`resolvedInSessionId`.

**Closing Tomás's F5 alongside this:** a publish-time-only envelope value would leave the narrow race F5 named — a session leaving `pre_session` in the instant between publish and delivery. Session status only ever moves forward (`pre_session` is never re-entered once left), so `dispatchActionItemStatusUpdated` uses the envelope value as a cheap fast-bail-out (if the envelope says not-`pre_session`, skip immediately — it can only be even-more-not-`pre_session` by delivery time), and when the envelope says `pre_session`, performs **one** additional live read of the session's current status (`SELECT status FROM sessions WHERE id = $1` — once per dispatch, not per-candidate, since status is uniform across every candidate of one session) immediately before fan-out. If that fresh read is no longer `pre_session`, no candidates receive the event. Per-candidate `evaluateSessionSubscriberAccess` authorization still runs for every candidate as D2 already specifies — the two status checks above govern *whether* anyone receives the event; per-candidate authorization governs *who*.

## Risks / Trade-offs

- **[Risk]** Combining #64 and #95 makes this a noticeably larger change than either ticket implied on its own → **Mitigation:** none of the added scope is net-new functionality. Ownership enforcement, transition validity, and the staleness reset were always implicit in FR-7.3 and #64's own stated scope; this design just stops leaving them implicit (exploration-notes.md §10). Proportionate-scope discipline — the same reasoning that deferred FR-3.3 once already — was applied to the review, not abandoned by it.
- **[Risk — RESOLVED]** Facilitator-authorization scope, if resolved too broadly, grants a facilitator standing write access to another team's action-item backlog independent of actively running a session for that team — a materially larger permission than anything else a facilitator holds in this system → **Mitigation:** resolved by Open Question 1 (ratified VOTE-002's middle formulation) and **D10** (a narrowed, purpose-built authorization check — `lobby`/`pre_session`/`active`/`wrap_up` only, no `draft`/`complete` grace windows — rather than reusing `evaluateTeamAccess` unmodified, per Tomás Ferreira's F1 finding, which is exactly this risk materializing through the obvious DRY implementation choice). Default posture in any ambiguous branch remains deny (`403`).
- **[Risk]** An implementation built without reading this design could still drift from catalog conventions (e.g., naming the event something ad hoc, or delivering it facilitator-only by copying the most recent precedent) → **Mitigation:** the automated conformance test fails CI the instant the new `WsEventType` member ships without the matching Event Registry flip — a forcing function, not just documentation. (Marcus Oyelaran's review caught that tasks.md 5.1, as originally worded, would have flipped the row's status without renaming it to real snake_case — leaving the row skipped by the conformance test's dot-notation filter and the new event type with no matching row at all, failing CI for a different, confusing reason. Fixed in tasks.md 5.1.)
- **[Risk]** A live status-change render, if built without D8's constraints in hand, could read as surveillance or performance rather than information (the same failure mode already named for outlier flagging) → **Mitigation:** D8 states the constraints now, ahead of #69's build, specifically so they don't have to be rediscovered or, worse, get shipped as a "nice touch" checkmark animation.

## Migration Plan

No database migration required — `action_items` and `action_item_history` already have every column this change needs, including `resolution_note` and `resolved_in_session_id`. Deploy is additive: a new REST endpoint, a new `WsEventType` union member, a new dispatch case, and delta-spec updates to `websocket-specification`'s catalog (Requirement content via this change's delta spec; the standalone Event Registry table and corrected-names table row updated directly in the living `openspec/specs/websocket-specification/spec.md`, since the delta-spec format is Requirement-scoped and doesn't model that table — tracked as an explicit tasks.md item). Nothing existing changes shape, so there's no rollback complexity beyond a normal revert.

`requirements/design/REST API Contract.md` already has an entry for this endpoint — `VOTE-002` — and this change **reconciles** it rather than adding a new one: align the documented path (already matches once this change adopts `:actionItemId/status`), update the facilitator-scope wording to state D10's narrowed mechanism (not a bare restatement of "actively facilitating," which is exactly the wording that invited the `evaluateTeamAccess`-reuse risk), correct the wire-event-name reference (`actionitem.updated` → `action_item_status_updated`, per this codebase's established naming-correction convention, not a contradiction of VOTE-002's intent), rewrite the error table so `403`/`404` are stated as the ordered, non-independent responses D12 describes rather than two flat rows, and remove or correct VOTE-002's stale claim that a database CHECK constraint (`action_items_resolved_has_session`) exists — it doesn't, per `packages/backend/migrations/2_create_tables.sql`; this is a pre-existing inaccuracy in VOTE-002, not introduced by this change, but this change is the one next touching that section and shouldn't leave it uncorrected a second time. No new migration is added to backfill that constraint — enforcement stays application-level, matching VOTE-002's own final line ("The application enforces this before writing"). VOTE-002's separate Notes-section *recommendation* for a transition-state-machine CHECK constraint (`(old_status, new_status) IN (...)`) is a distinct, still-open suggestion, not the stale claim above; this change leaves it as a deliberate no-op (app-level enforcement is this codebase's consistent pattern for transition/ownership checks elsewhere too) and states that explicitly in the reconciliation rather than leaving it looking like an oversight (Marcus Oyelaran's non-blocking observation).

## Open Questions — Resolved

Architect ratification pass (Ingrid Sollenberger), incorporating `design-review-engineer.md` (Marcus Oyelaran) and `design-review-security.md` (Tomás Ferreira). All three questions are resolved below; new Decisions D10–D14 record the mechanisms the reviews surfaced as needed to make those resolutions actually secure and implementable, not just textually decided.

1. **Facilitator Authorization Scope — RESOLVED, ratifying VOTE-002's textual formulation, overriding the implementation shortcut it invites.** Ratified: *"may update any action item belonging to a team they are actively facilitating (active session exists)"* — VOTE-002's middle formulation, not the UC's narrower session-scoped reading and not a standing grant. Rationale: this keeps the contract doc and shipped behavior in agreement without a documentation rewrite, and "team-wide while a session is active" is a defensible facilitator-authority boundary as long as "active" is defined narrowly — which is exactly where Tomás's F1 finding applies. See **Decision D10** for the resolved mechanism: this scope is **not** implemented by calling `evaluateTeamAccess` unmodified, because that helper's Path 3 also grants access during a `draft` session (24h grace) and a `complete` session (`facilitator_access_expires_at` grace) — both broader than "actively facilitating" and exactly the standing-grant-by-the-back-door risk this design's own Risks section already named as the thing to avoid. Marcus's reuse suggestion (Open Question 1 note in his review) is taken in spirit — reuse the *pattern*, not the *function* — per D10.

2. **Session-Context Plumbing — RESOLVED.** Ratified: `sessionId` as an optional request-body field, `422` if it doesn't reference a session in an active state. "Active state," for both this validation and the facilitator-authorization check in (1), means `sessions.status IN ('lobby', 'pre_session', 'active', 'wrap_up')` — the same restricted set D10 uses, not `evaluateTeamAccess`'s broader grace-window set. This is deliberately a *different, narrower* "active" than D2's broadcast gate, which stays `pre_session`-only and is unchanged. The `403` VOTE-002 documents for "facilitator attempting to update outside an active session context" is an authorization-layer rejection — no active session for that team means no facilitator grant exists at all, full stop, before any transaction begins. **Decision D11** states this explicitly and closes the tension this Open Question originally flagged against D7: D7's "broadcast never blocks the mutation" principle governs what happens *after* authorization has already succeeded (Redis publish failures, a session leaving `pre_session` mid-flight); it does not, and was never intended to, excuse the facilitator-authorization check itself. The owner path is unaffected either way — VOTE-002 never requires session context for an owner acting on their own item. This resolves Tomás's F4 finding directly.

3. **HTTP Response Code for Invalid Transitions — RESOLVED, ratified as originally drafted.** `409 Conflict`, unhedged, for both backward transitions and any transition targeting an already-`Resolved` item. No change from the prior draft; recorded here as a confirmed decision rather than an implicit one, per the original ask.

**Two additional gaps identified by security review, outside the original three questions, also resolved below (not reopening the three — these are new findings the design didn't previously surface at all):**

- **Anti-enumeration ordering for this endpoint's 403/404 responses** (Tomás's F2) — see **Decision D12**. VOTE-002's error table, read literally, lists `403` ("not owner") and `404` ("does not exist") as independent rows; implemented naively that reopens an `actionItemId` enumeration oracle for *any* authenticated user in the system, not just cross-team ones, because this endpoint's URL carries no `teamId` to gate on the way `content.ts`'s does. D12 states the resolved ordering explicitly, since the URL shape here doesn't let this endpoint reuse `content.ts`'s exact mechanics — only the same invariant.
- **Security audit trail** (Tomás's F3) — see **Decision D13**. `action_item_history` remains the correct business record; it is not a substitute for an `audit_log` row, and this change adds one, matching every other sensitive-mutation write path in this codebase.

**Also resolved: the dispatcher data-availability gap Marcus identified (his Blocker 1), which sits underneath D2's delivery pattern and Tomás's F5** — see **Decision D14**.

This change's own write (`action_items.updated_at`, D6) is neutral to both readings and does not try to settle which is correct.
