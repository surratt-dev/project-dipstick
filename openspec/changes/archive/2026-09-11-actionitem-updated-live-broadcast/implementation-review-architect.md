## (1) D12/Finding-1 anti-enumeration relationship check — implemented as the broadened test, correctly separate from D10

Confirmed correct. `action-items.ts`'s block labeled "3.1b" builds `hasRelationship` from three independent checks, in order: `isOwner` (item ownership), then — only if still false — `evaluateTeamAccess(userId, item.team_id) !== null` (catches plain team members, Application Admins, and facilitators inside `evaluateTeamAccess`'s own broader `draft`/`complete`-grace windows), then — only if still false — a standalone `EXISTS (SELECT 1 FROM sessions WHERE facilitator_id = $1 AND team_id = $2)` query with **no status filter at all** ("ever facilitated any session for this team, any status"). This is exactly D12 step 3 as corrected by my task-ordering review's Finding 1: a self-contained, broader-than-D10 relationship test, not a reuse of D10's narrow `ACTIVELY_FACILITATING_STATUSES` query.

The narrow D10 query is separately implemented in the block labeled "3.2/3.3," using its own independent `SELECT EXISTS (... AND status = ANY($3::text[]))` against `ACTIVELY_FACILITATING_STATUSES`. The two queries are genuinely distinct code paths — the implementer did not take the shortcut of computing the narrow check once and reusing it for both the disclosure boundary and the write-authorization gate, which is exactly the trap Finding 1 warned about.

Test coverage confirms this lands correctly: `6.1a-i`/`6.1a-ii` assert a `draft`-grace-only or `complete`-grace-only facilitator gets `403` (not `404`) — the exact scenario Finding 1 was about, and the exact assertion that would have failed against the pre-Finding-1 wording. `6.1b(b)` separately confirms a caller with genuinely zero relationship gets `404`, indistinguishable from `6.1b(a)`'s nonexistent-item case. `6.1c` confirms an Application Admin (who has `hasRelationship = true` via `evaluateTeamAccess`'s admin grant, but is not owner/facilitator) gets `403`, not a bypass — this is also a clean confirmation that D10's narrow facilitator query and D12's broad relationship query are doing separate jobs, since an admin has no `sessions.facilitator_id` row at all and still correctly lands in the `403` branch via the `evaluateTeamAccess` leg of the relationship test.

## (2) D14 dispatcher envelope-carried `sessionStatus` + delivery-time re-check — implemented as designed, not publish-time-only

Confirmed correct. The `WsEventEnvelope` variant for `action_item_status_updated` (`packages/shared/src/types/realtime.ts`) carries `sessionStatus: SessionStatus` as an internal-only field, explicitly documented as not part of the client-facing `ActionItemStatusUpdatedPayload` — matching the envelope/wire-payload split D4 already established for `resolutionNote`/`resolvedInSessionId`. `publishActionItemStatusUpdated` (`ws-pubsub.ts`) takes `sessionStatus` as an explicit third argument and stamps it onto the envelope at publish time.

`dispatchActionItemStatusUpdated` (`ws-event-dispatcher.ts`) implements both layers D14 specifies, in the right order: `if (envelope.sessionStatus !== "pre_session") return;` as the fast bail-out (no DB query at all when the envelope already says not-`pre_session` — confirmed by a test asserting `mockDbQuery` is never called in that case), then, only when the envelope says `pre_session`, **one** additional `SELECT status FROM sessions WHERE id = $1` — once per dispatch, before the candidate loop, not inside it — and if that fresh read isn't `pre_session`, the function returns before any per-candidate work runs. Per-candidate `evaluateSessionSubscriberAccess` authorization still runs inside `Promise.all(candidates.map(...))` regardless, for both participant- and facilitator-path grants (not restricted to one path, per D2).

The dispatcher test suite's "stale envelope" case is a precise regression test for exactly the race D14 describes: envelope says `pre_session`, the one fresh-read query returns `active`, and the test asserts **zero** delivery to either a participant-path or facilitator-path candidate, with the fresh-read query counted as the *only* DB call (`mockDbQuery` called exactly once) — confirming the implementation short-circuits before running per-candidate authorization, not after.

## (3) D13 `audit_log` write — genuinely transactional, not a best-effort side write

Confirmed correct. In `action-items.ts`, the `audit_log` `INSERT` sits inside the same `BEGIN`/`COMMIT` block, on the same `client` connection, as the `action_items.status` `UPDATE` and the `action_item_history` `INSERT` — three statements, one transaction, one `try`/`catch`/`finally` with `ROLLBACK` on any failure and `client.release()` guaranteed in `finally`. This is not routed through any best-effort or fire-and-forget path; a failure on the `audit_log` insert rolls back the status update and history row exactly as D13 requires. `metadata` carries `action_item_id`, `previous_status`, `new_status`, `authorization_path` (`"owner"` | `"facilitator"`, correctly threaded from the 3.2/3.3 authorization branch that was actually taken), and `session_id` (the validated one, or `null`) — matching D13's spec exactly. The separate `emitAuditEvent` call (the structured-log operational counterpart) correctly runs *after* the transaction commits, outside the `try` block — appropriate, since that's a log side-effect, not a durable record, and matches every other dual-write pattern in this codebase (`recordRevealTriggeredAudit` does the same split).

Test coverage: `6.2a` confirms the `audit_log` row is written with correct metadata in the same transaction, confirms rollback removes it too on a forced failure, and confirms **no** `audit_log` row is written for a same-status no-op — matching 3.9's "skip for same-status no-ops" requirement (the no-op branch in the route code is a separate, single-statement `UPDATE ... SET updated_at = NOW()` with no transaction wrapper at all, since D6 says no history/audit/broadcast for a no-op — correct, the no-op path never reaches the `BEGIN` block).

## (4) `resolution_note` dual-write (Marcus Delgado's blocking Finding 2) — present and correctly scoped

Confirmed correct. The single `UPDATE action_items SET status = $1, resolution_note = $2, resolved_in_session_id = $3, updated_at = NOW() ... RETURNING updated_at` statement writes `resolution_note` onto `action_items` itself, in the same statement as the status transition — not a separate write, not omitted. The `action_item_history` `INSERT` immediately after carries the same `noteToPersist` value into its own `resolution_note` column. Both use the identical `noteToPersist` variable, so there's no risk of the two columns drifting from different code paths.

The dual-write is correctly scoped to resolving transitions only: `noteToPersist = isResolving && resolutionNote !== undefined ? resolutionNote : null`, so a note supplied on a non-resolving transition is silently dropped from both columns (matching the spec's "ignored, not an error" scenario), and a resolving transition with no note supplied leaves both columns `NULL`.

Test `6.3`'s first case asserts both write sites explicitly and by name — it inspects the `UPDATE action_items` call's bound parameters for the `resolution_note` value and separately inspects the `action_item_history` insert's parameters, with an inline comment citing Marcus Delgado's Finding 2 and the exact `content.ts:433-440`/`em-views.ts:800-907` read paths D5's correction named as what would have silently broken without this write. This is the right test — it doesn't just check the REST response shape (which could pass even if only one column were written), it checks the actual bound query parameters at both write sites.

## Bare-`await` Redis-publish bug fix — confirmed present

The publish call is wrapped in `try { await publishActionItemStatusUpdated(...) } catch (err) { request.log.warn(...) }`, positioned after the transaction's `COMMIT` and after `emitAuditEvent`, with an inline comment explicitly citing D7 and stating the rationale ("a missing session context or a publish failure here must only ever cost the broadcast, never the PATCH's own 200 response"). This is not a bare `await` — a rejection is caught, logged at `warn` with `actionItemId`/`sessionId` context, and swallowed; execution falls through to the same `200` response that would have been returned on a successful publish. Test `6.2b` confirms this directly: it forces `publishActionItemStatusUpdated` to reject and asserts the response is still `200`, `COMMIT` appears in the transaction's query log, and the publish function was still called exactly once (so the failure is observed and handled, not silently skipped). This matches the team lead's description of the bug and its fix exactly.

## Other checks against the design (not specifically asked for, but worth recording)

- **D6 no-op semantics**: `currentStatus === "resolved"` is checked and returns `409` *before* the same-status/no-op computation runs, so a `resolved → resolved` request is correctly rejected rather than silently accepted as a no-op — matches the spec's explicit scenario distinguishing this from ordinary no-ops.
- **D9/VOTE-002 error validation ordering**: the over-length `resolutionNote` `422` check runs before the transaction opens, so an over-length note is rejected with nothing written — matches the spec.
- **D11 `sessionId` validation**: correctly filters `WHERE id = $1 AND team_id = $2`, so a `sessionId` belonging to a different team is rejected `422` rather than silently accepted (this also has a secondary anti-enumeration benefit consistent with D12's spirit, though D11 doesn't frame it that way explicitly).
- **3.8 (admin bypass absent)**: no code path in the route grants special treatment to `global_role = 'application_admin'` — an admin is authorized exactly like any other non-owner/non-facilitator, i.e., not at all. Confirmed by `6.1c`.
- **Transaction anchor (my task-review Finding 2)**: the implementation resolved this cleanly by combining the `action_items.status` update with the `resolution_note`/`resolved_in_session_id` writes into one `UPDATE` statement inside an explicit `BEGIN`/COMMIT` block (labeled "3.4a" in the route's own comments), which both `action_item_history` and `audit_log` write into. This is a better resolution than my review's suggested "add a separate anchor task" — combining the writes into one statement removes the ambiguity entirely rather than just documenting it.
- **VOTE-002 reconciliation (task 5.3)**: fully done and precise — the error table's `403`/`404` rows now state the ordered, non-independent relationship exactly as D12 (corrected) describes, including explicitly naming "Application Admin" and "facilitator outside the narrowed active-facilitating window" as `403`-eligible relationship holders (matching the broadened `evaluateTeamAccess`-based check in code, not the narrow D10 one) — this is a subtle detail that would have been easy to get wrong by copying D10's language instead of D12's, and it's correct. The facilitator-authorization wording, wire-event-name correction, stale CHECK-constraint claim, and the transition-state-machine CHECK constraint's deliberate-no-op note are all present as design.md specified.

## Finding — documentation-only, not a code defect: `openspec/specs/websocket-specification/spec.md` is internally inconsistent pending archive

The Event Registry table (top of file, line 28) and the corrected-names table (line 50) are both correctly updated: `action_item_status_updated` (real snake_case name, per Marcus Oyelaran's Blocker 2 fix) shows **Implemented**. But the Requirements section further down the same file (lines 268–275) still carries the *old* Requirement text verbatim: *"Live `actionitem.updated` is a documented future-state entry... SHALL be documented... as **NOT IMPLEMENTED**, tracked in issue #95, implementation unscheduled. This event SHALL NOT be built as part of this change."*

This is very likely expected, not a bug: design.md's own Migration Plan explains that the Event Registry table is hand-maintained directly (tasks 5.1/5.2, done now) because the delta-spec format doesn't model that table, while the Requirement-level `REMOVED`/`ADDED` content (which *is* delta-spec-scoped) normally reconciles into the living spec via this project's archive step — which hasn't run yet, consistent with "nothing committed yet." I confirmed this pattern already happened correctly for the prior `participant_joined`/`participant_left` change (#94/#98, merged and archived per git log), whose Requirement content **is** present in the living spec today.

Flagging it anyway because, read today, the file contradicts itself within a few dozen lines — the table says Implemented, the prose six lines away says "SHALL NOT be built as part of this change." Not blocking implementation review, but worth confirming explicitly that the archive step is still pending and on the plan before this change is considered fully landed, so the living spec doesn't sit in this contradictory state longer than necessary.

## Verdict

All four specifically-requested checks pass: the D12 relationship test is genuinely broadened and independent of D10's narrow query; the D14 dispatcher does real delivery-time re-validation, not publish-time-only gating; the `audit_log` write is genuinely transactional; and the `resolution_note` dual-write is present and correctly scoped. The reported Redis-publish bug fix is in the code as described and has a direct regression test. I found no code-level deviations from `design.md` worth blocking on. The one finding (pending spec archive) is a documentation-state note, not an implementation defect.
