## Why

The pre-session action item review exists so a team looks at its open commitments before it makes new ones — that's the whole point of FR-3.1's placement before the first voting topic. Right now that review has no write path at all: `action_items.status` cannot be changed anywhere in the shipped codebase (issue #64, FR-3.2/FR-7.3, [HARD]), and even once it can be, nobody but the person who clicked the button sees it happen without a page refresh (issue #95, FR-3.3, [PREF]). Building #95 alone would ship a broadcast with nothing to broadcast; building #64 alone risks a second, ad hoc real-time mechanism bolted onto the endpoint that doesn't follow this application's own WebSocket catalog conventions (`openspec/specs/websocket-specification/spec.md`), which exists precisely to stop that kind of drift. Exploration (`exploration-notes.md`, §2–§3, resolved in §9) concluded these ship together, as one atomic change, so the mutation and the correctly-cataloged event never exist one without the other.

**Reporting framing (per exec review):** the larger and more valuable half of what ships here is the mutation itself — the first write path for `action_items.status`, an authorization model with a facilitator-override boundary, FR-7.3 transition-validity enforcement, and the audit trail. The live broadcast is the UX layer on top of that, not the headline. When this is reported up past the team level, describe it as "shipped the action-item status mutation and its live broadcast," not "shipped a WebSocket event" — the change's own name (`actionitem-updated-live-broadcast`, inherited from issue #95's original framing) undersells the #64 half that actually moves the org's second success criterion (closing the loop on a prior commitment).

**Correction (post-proposal-review):** an earlier draft of this proposal and its design.md stated that `requirements/design/REST API Contract.md` had no entry for this endpoint. That was wrong — the BA review caught it. `VOTE-002 — Update Action Item Status` (lines 1870–1935 of that document) is a complete, previously-authored contract for this exact endpoint, missed by exploration and both exploration-stage reviews as well as the first proposal draft. This revision reconciles against it directly rather than treating it as a fresh design surface — see "Reconciliation with VOTE-002" below.

## What Changes

- Add `PATCH /api/v1/action-items/:actionItemId/status` (path aligned to VOTE-002 — see reconciliation below), the first write path for `action_items.status` in this codebase (issue #64, FR-3.2, FR-7.3):
  - An item's owner can transition its status (Open→In Progress, Open→Resolved, In Progress→Resolved); server-enforced, not UI-only.
  - A facilitator can transition status on any item belonging to the team they are facilitating — authorization scope is an open decision for the architect (design.md Open Question 1), now framed as ratify-or-override against VOTE-002's own existing formulation ("any action item belonging to a team they are actively facilitating (active session exists)"), not a blank-page decision.
  - Backward transitions and any transition targeting an already-`Resolved` item are rejected (FR-7.3). VOTE-002 already asserts `409 Conflict` for this, unhedged — design.md Open Question 3 is now "ratify or override," not "decide."
  - A same-status no-op is accepted gracefully: no `action_item_history` row, no broadcast, but the staleness clock still resets (`action_items.updated_at`), except that a same-status request against an already-`Resolved` item is not a no-op — it's rejected, since `Resolved` is terminal.
  - **Resolution note is in scope for this change**, not deferred to issue #65. VOTE-002 already specs an optional `resolutionNote` field (max 500 chars, matching the existing `action_items_resolution_note_length` CHECK constraint) as part of *this same endpoint's* contract, and `action_items.resolution_note`/`action_items.resolved_in_session_id` are already live schema columns, already read and displayed by `content.ts` and `em-views.ts` — there was never a second feature here to defer. Issue #65 itself is scoped as "a direct extension of the status-update endpoint... once it exists" — it isn't standalone work, it's the remaining slice of this exact endpoint, unblocked by this change existing at all. This change implements it and closes #65 alongside #64/#95 (see Impact and tasks.md 5.4).
  - `action_items.resolved_in_session_id` is set to the provided `sessionId` when the transition target is `Resolved` and a `sessionId` was supplied — distinct from, and in addition to, `action_item_history.session_id` (populated on every real transition, not only resolutions).
  - **The mutation writes the supplied resolution note to `action_items.resolution_note` itself, not only to the history row** (corrected per Marcus Delgado's blocking task-review Finding 2, `tasks-review-ba.md`) — this is the column `content.ts` and `em-views.ts` already read directly, so this write is what actually makes a submitted note visible anywhere; the `action_item_history` row below carries the same value as that transition's audit-trail entry, a second write, not the only one.
  - Every real transition writes an `action_item_history` row in the same transaction as the status update: `resolution_note` carries the supplied note (or `NULL` for non-resolving transitions or when omitted); `session_id` is populated when the update happens during a live pre-session review, `NULL` otherwise; `changed_by_user_id` is the acting user, which closes the previously-open "actor visible in history" question from the action-item-history use case.

### Reconciliation with VOTE-002

`requirements/design/REST API Contract.md`'s `VOTE-002 — Update Action Item Status` is the pre-existing, canonical contract for this endpoint. This change implements it, with the following notes rather than silent adoption or silent divergence:
- **Path, request/response shape, resolutionNote, resolvedInSessionId:** adopted as documented.
- **`sessionId` placement** (Open Question 2): VOTE-002 already specifies it as an optional request-body field, validated `422` if the referenced session isn't active — this change ratifies that unless the architect overrides it.
- **Facilitator authorization scope** (Open Question 1): VOTE-002's formulation is a third option alongside the two this proposal's own exploration stage considered (see design.md) — needs explicit architect reconciliation across all three, not just a pick between the original two.
- **Wire event name:** VOTE-002 refers to the broadcast informally as `actionitem.updated` — the pre-correction dot-notation name this codebase's `websocket-specification` catalog already established as historical, not a real wire name (same treatment as `reveal.trigger`, `vote.locked`, etc.). This change's real `WsEventType` member is `action_item_status_updated`, consistent with that existing convention — not a divergence from VOTE-002, just VOTE-002 predating the naming correction.
- **Stale claim corrected:** VOTE-002 asserts a database CHECK constraint (`action_items_resolved_has_session`) that does not exist in `packages/backend/migrations/2_create_tables.sql`. This is a pre-existing inaccuracy in VOTE-002, not introduced by this change — corrected as part of the reconciliation task (tasks.md 5.3) since this change is the next one touching that section. No new migration is added; enforcement stays application-level, as VOTE-002's own last line already says.
- Add a live, session-scoped WebSocket broadcast of pre-finalization action-item status changes (issue #95, FR-3.3), following this repo's existing event-catalog conventions (typed `WsEventType` member, `ws:events` Redis envelope, publish-after-commit, per-candidate delivery-time authorization in `ws-event-dispatcher.ts`):
  - Delivered to any valid session subscriber (participant or facilitator), matching `session_state_change`'s recipient breadth — not `participant_joined`/`participant_left`'s facilitator-only pattern.
  - Gated to sessions currently in `pre_session` status.
  - Payload carries `previousStatus` and `newStatus` (matching `SessionStateChangePayload`'s shape), identity, and timing — no resolution-note content, matching the catalog's existing payload-minimalism convention.
  - How the mutation determines which session's channel to publish to is an open design.md decision (`action_items.session_id` is the item's *originating* session, not the session currently reviewing it).
  - Rendering is low-drama and informational by design: no toast/animation/sound on receipt, no auto-advancement of the review, attribution and error-state rendering follow the spec's existing non-spotlight principle. (Frontend rendering itself is out of scope for this change — see Impact — but the WebSocket payload and this change's own design decisions must not foreclose a compliant implementation later.)
- Update `openspec/specs/websocket-specification/spec.md`: flip the `actionitem.updated` (live case) Event Registry row from NOT IMPLEMENTED to Implemented, update the corrected-names table row, and rewrite the "documented future-state entry" Requirement to describe the shipped behavior (mirroring how the `participant_joined`/`participant_left` Requirement reads today, closed by #94/#98).
- Reconcile the existing `VOTE-002` entry in `requirements/design/REST API Contract.md` with this change's decisions (see "Reconciliation with VOTE-002" above) — this is a correction/reconciliation task, not adding a missing entry.

**Out of scope for this change** (see exploration-notes.md §9, updated post-review): the pre-session review screen itself (issue #69, frontend, separate and unscheduled — this change ships the endpoint and event it will eventually consume; not scheduled as of this writing, but flagged here so it stays visible rather than falling off anyone's radar between this change and whenever #69 is picked up), and reconciling the BRD/use-case inconsistency on staleness-threshold semantics (FR-7.4's single threshold vs. the use cases' three-color graduated scale) — flagged as a separate BA documentation follow-up, not resolved here; this change's own data writes (a plain timestamp) stay neutral to either reading. Resolution-note capture (formerly listed here as issue #65) is now **in scope** — see "Reconciliation with VOTE-002" above.

## Capabilities

### New Capabilities
- `action-item-status-management`: server-side authorization and state-transition rules for changing an `action_items.status` value (owner-only for their own items, facilitator authority scope subject to architect ratification against VOTE-002's documented default, transition-validity enforcement per FR-7.3, same-status no-op handling, resolution-note capture on resolution, and the `action_item_history` audit trail this produces).

### Modified Capabilities
- `websocket-specification`: adds a new cataloged event (live, pre-finalization `actionitem.updated`, wired for real per FR-3.3) to the Event Registry and its corrected-names table, and rewrites the existing "documented future-state entry" Requirement to describe shipped, not future, behavior.

## Impact

- **Backend**: new route (likely `packages/backend/src/routes/action-items.ts` or an addition to an existing routes file — design.md's call), a new `WsEventType` member and payload type in `packages/shared/src/types/realtime.ts`, a new typed publish wrapper in `packages/backend/src/realtime/ws-pubsub.ts`, and a new dispatch case in `packages/backend/src/realtime/ws-event-dispatcher.ts`.
- **Shared types**: `WsEventType`, `WsEventEnvelope`, `WsClientMessage` unions in `packages/shared/src/types/realtime.ts` all grow by one variant; `packages/shared/src/__tests__/websocket-spec-conformance.test.ts` will fail CI until the Event Registry row flips to Implemented — expected, not a regression.
- **Database**: no schema change — `action_items` and `action_item_history` already have every column this change needs, including `resolution_note` and `resolved_in_session_id` (`packages/backend/migrations/2_create_tables.sql:134-161`).
- **Documentation**: `openspec/specs/websocket-specification/spec.md` (Registry + Requirement) needs updates as part of this change, not a follow-up. `requirements/design/REST API Contract.md`'s existing `VOTE-002` entry needs reconciliation (path already matches once this change aligns to it; facilitator-scope wording, stale CHECK-constraint claim, and wire-event-name correction all need updating in place).
- **Issue tracker**: issues #64, #65, and #95 all close together as part of this change (tasks.md 5.4) — #65 was never separable work; it was explicitly scoped as "a direct extension of the status-update endpoint," which this change builds.
- **Frontend**: none in this change. The pre-session review screen (#69) that will eventually call this endpoint and listen for this event is separate, unscheduled work; this change's contract needs to be stable enough for that screen to build against later without renegotiation.
- **Milestone reporting**: this change closes issues under two milestones ("Action Item Management" for #64/#65, "Pre-Session Action Item Review" for #95). Tasks.md 5.4 confirms both milestones' tracking reflects the shared delivery, not just the two issue bodies, so neither looks stalled or claims sole credit for shared work (per exec review).
