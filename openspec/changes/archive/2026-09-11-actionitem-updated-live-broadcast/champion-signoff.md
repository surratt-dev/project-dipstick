# Champion Sign-Off — `actionitem-updated-live-broadcast`

**Signed off by:** Devon Calloway, Internal Champion / founding SME
**Scope of this check:** ritual-fidelity only — do the five structural constraints I hold this application to (simultaneous reveal, no-manager participation, facilitator-from-another-team, topic-default restorability, cross-person comparison) still hold after everything that got added between my original exploration notes and the shipped code. I'm not re-reviewing correctness, security, or test coverage — Tomás, Ingrid, and Marcus O. already did that work thoroughly, and I've read their sign-offs rather than re-deriving what they already verified in the code.

## Verdict: sign off. No drift on any of the five constraints.

## Walking through all five

**Simultaneous reveal** — untouched. This change never reads or writes anything in the voting/reveal path. Not applicable to action item status.

**No-manager participation** — untouched, and I checked this specifically rather than assuming it from the name. VOTE-002 states plainly, "`engineering_manager`: no write access," and the shipped authorization model (D10, D12) never special-cases any `global_role` to grant one — the only two ways into a write are `owner_id` match or a narrow, session-table-derived facilitator check. Ingrid's implementation review confirms no admin bypass exists either (6.1c), and by the same logic, no manager bypass exists — there was never a role-based branch to add one to. The literal ritual constraint is about session *participation* (voting), which this endpoint doesn't touch at all; I'm noting this only because it's the adjacent case worth having checked.

**Facilitator-from-another-team** — this is the one I looked at hardest, per the specific ask, and it held up well through a lot of review churn. The load-bearing fact: D10's write-authorization check is `SELECT 1 FROM sessions WHERE facilitator_id = $1 AND team_id = $2 AND status IN (...)` — purely keyed off `sessions.facilitator_id`, never off `team_memberships`. Design.md says this explicitly, and says *why* it has to be this way: "this application's facilitator model is explicitly not team-membership-based... a facilitator routinely has no `team_memberships` row at all for the team they facilitate." That's my own constraint, stated back to me correctly, and used as the reason the team rejected the more convenient option (reusing `evaluateTeamAccess` unmodified) rather than the reason being incidental.

The part I wanted to check most carefully was D12's later broadening — the anti-enumeration relationship test that decides `403` vs `404`. It's genuinely broader than D10 (any team-membership grant, or *any* facilitator relationship at *any* session status, not just the narrow actively-facilitating set). I confirmed this broadening is scoped to *disclosure*, not *authority*: it only ever produces a `403` (you can see this item exists) instead of a `404` (it doesn't), never a write. Ingrid's implementation review confirms the two queries are genuinely separate code paths in the shipped route, not one computed-once-and-reused check — which is exactly the distinction that matters here. Nothing in D10 or D12 touches how someone *becomes* a session's facilitator in the first place; that assignment logic lives entirely outside this change, untouched. This change only ever reads an existing `sessions.facilitator_id` value and asks what it's allowed to authorize — it doesn't create any new path to becoming a facilitator of a team, same-team or otherwise.

One thing I'm recording rather than blocking on: D10's ratified scope ("actively facilitating," any status in `lobby`/`pre_session`/`active`/`wrap_up`) is broader than the specific UC text I'd have defaulted to ("session-scoped... not a general administrative one," `pre_session` only). Design.md is honest about this gap in its own text (D10's "stated for the record" paragraph) rather than burying it, which is exactly what I want to see when a ratified answer diverges from the narrowest reading — a facilitator running a team's session through `wrap_up` still being able to touch that team's action item backlog is a defensible reading of "actively facilitating," not a drift toward a standing grant. I'd rather this stayed written down than silently forgotten, which it now is.

**Topic-default restorability** — untouched. This change never touches the topic catalog.

**Cross-person comparison** — untouched, checked specifically because D13 adds a new `audit_log` write and D5 finally makes `changed_by_user_id` populate correctly. Two things kept this from becoming a new comparison surface: first, the `audit_log` row is an ops/security record (`actor_global_role`, `actor_ip`, no resolution-note text — Tomás's review confirms this matches this codebase's existing "no sensitive payload content in audit metadata" convention), not something rendered to any participant or EM. Second, `action_item_history.changed_by_user_id` now being populated correctly is data-layer plumbing for issue #67 (the still-unbuilt history/detail view) to eventually consume — no existing read path (`content.ts`, `em-views.ts`) surfaces per-actor history today, so this change doesn't add a new "who did what, how often" view anywhere a manager or teammate could see it. When #67 does get built, that's the point to re-ask this question, not now — it's out of scope for this change to answer on #67's behalf, and I don't want to hold this change hostage to a screen that doesn't exist yet.

## On the parts of the review trail furthest from my original exploration notes

D8's non-spotlight constraints — the part of this change closest to my own original "don't make the ritual feel like software" concern — got *stricter* through review, not softer: Priya's facilitator review elevated it to a stated hard constraint, and nothing in the later design/security/architect passes touched it at all. That's the direction I want to see review pressure move things, and it's worth noting explicitly since the resolution-note reversal (D9) moved in the opposite direction (more scope, not less) for reasons I already found sound when I wrote that decision.

The D10–D14 additions (the narrowed facilitator query, the anti-enumeration ordering, the audit_log write, the dispatcher freshness re-check) are all security- and architecture-driven corrections, not ritual-fidelity ones — none of them were things I flagged, and none of them needed to be, because none of them touch the five constraints. What they do share with my own concerns is the same underlying discipline: don't let a convenient shortcut (reusing `evaluateTeamAccess` verbatim, reusing D10's query for D12's purpose) quietly widen a boundary that was deliberately drawn narrow. I recognize that instinct in this review trail even where I wasn't the one applying it.

## Bottom line

This shipped correctly. The mechanics stayed exactly where my original exploration said they'd be — team backlog housekeeping, not psychological-safety content — and the one constraint most exposed to drift by how much the authorization logic changed (facilitator-from-another-team) held because the team kept re-deriving it from the same first principle (facilitator authority is earned by running a session, never by team membership) rather than from convenience. No concerns. No follow-ups needed from me.
