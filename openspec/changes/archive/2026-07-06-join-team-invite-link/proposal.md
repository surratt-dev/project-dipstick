## Why

The join link is the ritual's front door — the single mechanism by which a new engineer goes from knowing the Health Check exists to being able to participate in it. The core implementation is largely in place, but a review of the through-auth path has uncovered a class of correctness bugs where errors are swallowed silently, audit events carry placeholder values, and first-time users land in states with no explanation of what happened or what to do next. These gaps undermine the adoption story: if a new engineer clicks a link, authenticates, and arrives somewhere that looks broken or empty, the join link has failed at its primary job. Additionally, a vocabulary mismatch between the use case language ("Engineer") and the schema language ("participant") is a latent trap for any engineer who reads the use case and then looks at the insert site — close it now, before it causes a real defect.

## What Changes

- **Through-auth join failure is no longer silent.** When `executeJoinFlow` fails after OIDC callback (expired, revoked, or nonexistent `pendingJoinToken`), the callback handler redirects to the join error page with a `?joinError=` query parameter. The parameter-to-message mapping: `?joinError=expired` is appended when the token is expired or revoked; the join error page displays "This link has expired. Ask your facilitator for a new one." `?joinError=invalid` is appended when the token does not exist; the join error page displays "This link is not valid." Both error states also display a secondary line: "If this is your first time using this tool, sign out and ask the person who invited you for a new link." — this is in scope for this change, not deferred to a UX polish pass. The secondary line is harmless for returning users (it is a conditional instruction) and materially reduces abandonment risk for first-time users who authenticated successfully and then landed on an error with no context. The user is never routed to `/no-team` when a join token was present in the OIDC state.
- **First-time joiner receives a welcome confirmation.** When `executeJoinFlow` results in a new membership (not an already-a-member case), the redirect URL includes `?newMember=true`. `?newMember=true` is appended to whichever destination URL `executeJoinFlow` produces — both `/team/:teamId` and `/session/:sessionId` are possible, since landing destination is determined by whether an active session exists. The team page renders a transient notification banner — "You've joined the team. Your facilitator will share what comes next." — that auto-dismisses, and removes `?newMember=true` from the URL via `replace` navigation after rendering, consistent with the existing `?alreadyMember=true` handler. The session page explicitly ignores `?newMember=true` and does not render a welcome banner; a user landing directly in an active session already has the session context as confirmation that the join succeeded, and the banner content ("Your facilitator will share what comes next") is misleading when the session is already in progress. Detection of new membership versus existing membership uses `INSERT ... ON CONFLICT DO NOTHING RETURNING id`: a non-empty result set (one row returned) means a row was inserted and the membership is new; an empty result set means the insert was a no-op and the membership already existed. This mechanism is reliable under concurrent inserts because the RETURNING clause only emits rows for rows actually written.
- **`?alreadyMember=true` is appended on the through-auth path.** The direct join path already appends this parameter; the through-auth path now does the same when the membership already exists, so both paths behave identically for returning members.
- **`sourceIp: "callback"` placeholder is removed from audit events.** `executeJoinFlow` accepts a `sourceIp` parameter; callers pass `request.ip`. Audit events emitted by the through-auth path carry the real requester IP.
- **Role vocabulary is documented at the insert sites and in the spec.** Two inline comments are added — one in `join-links.ts`, one in `auth.ts` — explaining that `role: 'participant'` is what the use case calls "Engineer," and that these must not be conflated with the global `user_role` enum. The join-link spec gains a "Role vocabulary" section stating the same mapping.
- **Join link revocation endpoint is explicitly deferred.** The `revoked_at` column and validation logic exist; the write endpoint does not. This change documents the deferral with rationale and names the follow-on change that should close it.
- **EM protection and facilitator-on-own-team constraints are formally captured** in `openspec/specs/session-participation/spec.md` as hard requirements on the session participation feature, which does not yet exist. These constraints are not enforced at join time (by design); they must be enforced by the session participation layer when it is built.
- **Mid-session arrival UX is formally out of scope** with a documented requirement: the session participation spec must define how users arriving during an active vote interact with vote state and the facilitator's readiness grid before any session participation implementation begins.
- **"Team no longer exists" alternate flow is covered by existing validation.** The join link table enforces a foreign key on `team_id`; if a team is deleted and its associated rows cascade-delete, the join link token becomes nonexistent. The existing nonexistent-token validation path (`?joinError=invalid`) handles this case — the user sees "This link is not valid." This alternate flow does not require additional handling in this change and is not a gap.

## Capabilities

### New Capabilities
- `session-participation`: Constraint document establishing hard requirements that the session participation feature must satisfy — specifically, EM role enforcement at session join time, facilitator-from-another-team enforcement via `team_memberships`, and mid-session arrival handling relative to the reveal mechanic. No implementation in this change; the spec is created to ensure these requirements are visible when that feature is designed. This spec is intentionally a stub: it names the enforcement points and constraint categories, not the full behavioral specification. The session-participation change will complete the spec with testable acceptance conditions. What this change commits to in the stub: at minimum, one scenario skeleton for EM enforcement naming the enforcement point (the session participation endpoint, server-side), the trigger (a `global_role = 'engineering_manager'` check on the `users` table), and the constraint outcome (the user must not be recorded as a session participant). Specific HTTP status codes, redirect behavior, and user-facing error content are session-participation design decisions, not constraints this change can anticipate — locking them here would create rework for that feature.

### Modified Capabilities
- `join-link`: Requirements are changing in four areas: (1) through-auth error delivery — the spec now specifies the `?joinError=` mechanism, message mapping, and that the user must not land on `/no-team` when a join token was present; (2) already-a-member handling — the through-auth path must append `?alreadyMember=true` just as the direct path does; (3) new-member confirmation — the spec adds the `?newMember=true` requirement and the welcome banner content; (4) role vocabulary — a new "Role vocabulary" section maps "Engineer" (use case) to `participant` (schema).

## Impact

- `packages/backend/src/routes/auth.ts` — callback handler error routing; `executeJoinFlow` signature updated: add required `sourceIp` param, add `RETURNING id` to the membership INSERT (required for new-vs-existing membership detection), and update return type from `Promise<{ redirectUrl: string | null }>` to `Promise<{ redirectUrl: string }>` (error-as-redirect — failure cases return full redirect URL to `/join-error?joinError=...` rather than null); `?alreadyMember=true` and `?newMember=true` appended on relevant outcomes; `join.link_redeemed` audit event gated on actual INSERT result and gains `sourceIp` field; OIDC state retrieval in the callback handler updated from `redis.get` + `redis.del` to atomic `redis.getdel` — a concurrent second callback for the same state key can read the token before the first request deletes it; the atomic operation closes that window without behavioral change in the happy path
- `packages/backend/src/routes/join-links.ts` — inline role vocabulary comment at the `INSERT INTO team_memberships` call; error redirect targets updated from `/auth/error?category=invalid_request&message=...` to `/join-error?joinError=expired` and `/join-error?joinError=invalid` so both the direct path and the through-auth path converge on `JoinErrorPage`
- `packages/backend/src/app.ts` — add `trustProxy: 1` to Fastify configuration so `request.ip` resolves the real client IP from `X-Forwarded-For` in proxied deployments; without this every `sourceIp` field in every audit event carries the proxy IP in production
- `packages/frontend/src/pages/TeamPage.tsx` — handle `?newMember=true` with welcome banner (analogous to existing `?alreadyMember=true` handler)
- `packages/frontend/src/pages/JoinErrorPage.tsx` — new component; reads `?joinError=expired` or `?joinError=invalid` and renders the appropriate error message and secondary guidance line; accessible without authentication
- `packages/frontend/src/App.tsx` — new `/join-error` route pointing to `JoinErrorPage`; unauthenticated (analogous to `/auth/error`)
- `packages/backend/src/tests/auth.test.ts` — new test cases for expired, revoked, and nonexistent `pendingJoinToken` at callback time; test asserting the `team_memberships` row written by a successful join has `role = 'participant'` (not `'engineer'` or any other value), directly backstopping the vocabulary confusion this change is correcting
- `openspec/specs/join-link/spec.md` — role vocabulary section, through-auth error delivery requirement (including explicit message mapping), `?alreadyMember=true` through-auth parity requirement, `?newMember=true` requirement (with auto-dismiss and replace-navigation behavior, session page ignore behavior, and new-vs-existing detection mechanism)
- `openspec/specs/session-participation/spec.md` — new file; participation constraints section with EM enforcement scenario skeleton

## Resolved Design Questions

These questions were open in design.md and are closed here as part of this proposal.

**Secondary error line for first-time users** — In scope for this change. The join error page displays a secondary line on all error states: "If this is your first time using this tool, sign out and ask the person who invited you for a new link." The UX polish pass is not a reliable backstop — if real teams start using the tool before that pass, first-time users who follow expired links will have no path forward. The ritual's first impression is too important to leave that gap open.

**Session setup sequencing** — Confirmed. Session setup is the next change in the queue. This change plus session setup together reach the state where a facilitator can run a first session without database access: session setup bootstraps facilitator-level team membership, making the join link generation endpoint usable without manual database intervention. There are no other unbuilt dependencies between this change, session setup, and a first viable session for a real team.
