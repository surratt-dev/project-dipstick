# Architecture Review — join-link-redemption-wiring

Reviewer: Ingrid Sollenberger, Principal Solution Architect
Scope: implementation on `agent-team/166-join-link-redemption-wiring`, commits `10e7170` (Commit 1: behavior change + Migration A) and `3578ee0` (Commit 2: Migration B), against `design.md`.

## Verdict

**Approved.** The implementation matches the design's decisions faithfully, including the parts that were revised mid-review (extraction boundary, module location, `actor_global_role` sourcing). I did not find a decision that was documented one way and built another. This is not a rubber stamp — I checked the diff line-by-line against the specific claims below, ran the backend and frontend test suites, and confirmed the pre-existing `tsc` errors predate this branch.

## What I verified

**`packages/backend/src/auth/join-link-creation.ts` (Decision 2).** Exists, and its boundary matches the *revised* scope, not the original narrower one: `createJoinLink()` owns token/expiry generation, the `join_links` INSERT inside `withAuditTransaction`, the `audit_log` INSERT, and the post-commit `emitAuditEvent("join.link_created", ...)` call — the full `join-links.ts:65-122` sequence design.md called out as load-bearing. It also exports `JOIN_LINK_ACTIVE_SQL = "revoked_at IS NULL AND expires_at > NOW()"`, the one shared predicate. This is a genuinely new, non-route module (`auth/`, not exported from `join-links.ts`), consistent with this codebase's existing pattern of putting cross-cutting logic (`withAuditTransaction`, `evaluateSessionSubscriberAccess`, `applyTimingFloor`) outside `routes/` rather than having one route import another. `join-links.ts`'s `POST /api/teams/:teamId/join-links` now calls this function and no longer has its own copy of the sequence — verified via `git show 10e7170` that the old inline transaction block was deleted, not left as a second live path.

**Get-or-create wiring at both anchors (Decision 1).** `getOrCreateJoinLink()` in `facilitator-sessions.ts` does the SELECT against `JOIN_LINK_ACTIVE_SQL` (not a re-typed copy of the condition), most-recently-created wins, and falls through to `createJoinLink()` on a miss. It's called from both `POST /draft` (passing the already-in-scope `global_role`, no extra lookup — matches the design's claim that this is free here) and `GET .../facilitator-state`. The `facilitator-state` miss-path gap the design called "the one real gap" is closed exactly as specified: a `SELECT global_role FROM users WHERE id = $1` gated behind the `resolveActorGlobalRole` closure, which only executes on get-or-create's miss branch — I read the code, not just the comment, to confirm the closure is invoked only inside the `if (activeResult.rows.length > 0)` false-branch. `POST /api/v1/teams` (new-team creation) correctly gets no third anchor and no `joinToken` field at all, matching Decision 1's note; I confirmed `SessionCreationPage.tsx`'s new-team handler doesn't read that field, so this isn't a silent contract break.

**`GET /api/join/:token`'s active check (Decision 2's addendum).** Genuinely reconciled, not left duplicated. The SELECT now computes `(revoked_at IS NULL AND expires_at > NOW()) AS is_active` from the same `JOIN_LINK_ACTIVE_SQL` constant get-or-create's SELECT uses, and the handler gates on `!link.is_active`. The `revoked` vs. `expired` reason distinction for the audit log/redirect is preserved separately, as design.md specified — only the pass/fail gate itself was unified, which is the right amount of unification (collapsing the reason-reporting too would have been a needless change to user-facing/audit behavior).

**Two-migration split (Decision 6).** `13_sessions_join_token_nullable.sql` (Migration A, same commit as the behavior change) does exactly `ALTER TABLE sessions ALTER COLUMN join_token DROP NOT NULL` — nothing more. `14_sessions_drop_join_token.sql` (Migration B, second commit) does the `DROP COLUMN`. The five backend test files design.md enumerated as breaking on the column's actual removal (`ws-pubsub-integration.test.ts`, `facilitator-error-state-2-restricted-role.test.ts`, `facilitator-error-states-integration.test.ts`, `action-items-integration.test.ts`, `facilitator-sessions.test.ts`) were updated in the *same* commit as Migration B, not before — I diffed `3578ee0` directly and confirmed each `INSERT` lost its `join_token` column/value and the `facilitator-sessions.test.ts` constraint-name assertion was repointed from `sessions_join_token_unique` to `teams_name_unique`, which I confirmed is a real, still-existing constraint (`migrations/2_create_tables.sql`), not a fabricated one. This is the rolling-deploy safety property the design exists to protect, and it's built exactly as designed rather than collapsed into one migration for convenience.

**`buildJoinLinkPath` sharing (Decision 7 / the path half of the original bug).** `packages/shared/src/types/auth.ts` exports `buildJoinLinkPath(token) => "/api/join/" + token` with a comment explicitly naming why it must be the one place this path string is written. `DraftSessionHost.tsx` imports it from `@dipstick/shared` and uses it to build the rendered/copied URL. `e2e-join-link-redemption.test.ts` imports the *same* function from the *same* package — not a second implementation that happens to produce the same string today. I checked this isn't a case of two files independently agreeing on a literal; grep confirms exactly one definition site.

**The new e2e test (Decision 7 / Tasks 5.1–5.2).** This is a real test, not a tautological one. It stands up real Fastify apps against a real Postgres instance (self-skips if unreachable), calls the real `facilitator-state` endpoint to obtain the token through get-or-create's actual miss path (real INSERT, real audit row — verified by a follow-up query against `join_links` asserting `team_id` matches), builds the path with the shared function, and follows that exact path as a *different* real user against the real registered route, then asserts a real `team_memberships` row resulted. It also explicitly documents (and I have no reason to doubt, given the mechanism) that it was run against the pre-fix code and failed for the right reason — the response's `joinToken` came back null — rather than an unrelated assertion. The two supplementary tests are honestly labeled as structural guards rather than overclaimed as regression proof.

## Architectural fit

- **Boundaries.** The new module sits at the same layer as the other shared, non-route helpers this codebase already uses; no route imports another route. This is the right call and keeps the precedent clean for future extractions.
- **Server-authoritative access control.** Redemption's active/inactive gate is now a single server-side SQL predicate consumed by both write paths that need it, closing exactly the "two independently-maintained copies of an authorization-adjacent condition" pattern I'd otherwise flag on sight.
- **Ephemeral/persistent boundary.** Not touched by this change — `join_links` was already the correct persistent home for this data, and this change moves the draft-session join link onto that existing table rather than inventing a new one. No new Redis/Postgres boundary question introduced.
- **Named, bounded scope gap (Decision 5 / #164).** I have no objection to shipping this now rather than blocking on #164 — the reasoning (security-motivated fix vs. an unscoped, no-timeline backlog item) is sound, and the gap is honestly documented rather than silently absorbed. Task 6.2 (file/timeline #164) is correctly left unchecked in `tasks.md` as a follow-up commitment outside this implementation's scope, not swept under an "accepted" label. I'd want to see that filed promptly, as the design itself says, but that's a process follow-up, not an implementation defect.
- **Rolling-deploy discipline.** The two-commit migration split is the one place this change touches deployment-reproducibility concerns, and it was reasoned through against the actual documented deployment model (`requirements/High-Level Architecture.md` §9.2's Kubernetes rolling-update `Deployment`) rather than assumed safe. That's the standard I look for.
