## Context

`join_links` (team-scoped, cryptographically random, audited, spec'd in `openspec/specs/join-link/spec.md`) and `sessions.join_token` (session-scoped, a truncated `randomUUID`, validated nowhere) are two disconnected systems that happen to share a name in the UI. `DraftSessionHost.tsx` builds its displayed and copied URL from the latter, at a path (`/join/:token`) the backend never registers — only `/api/join/:token` is real. Both halves are broken independently; fixing only the token or only the path still 404s. This surfaced from a security review of the paused change `join-link-display-copy` (#45), which found the displayed link doesn't correspond to a working route.

This is the second time a change in this area has produced something that passes its own acceptance criteria while leaving the use case it serves non-functional (the first was #45 itself, on the copy-button UI). The verification approach below is written specifically to close that recurring gap, not just this instance of it.

Stakeholders: the Facilitator persona who copies and shares the link (silently broken today, with no error surfaced anywhere in the flow — the badge under it currently claims "not yet joinable," which reads as intentional, not broken), and the Engineer persona who clicks it (currently a dead end regardless of session state).

## Goals / Non-Goals

**Goals:**
- Make the join link a facilitator sees on a `draft` session's control view an actual, redeemable `join_links` token, at the actual registered redemption path.
- Reuse a team's existing active join link rather than minting a session-scoped one, matching the team-scoped shape `join_links` already has.
- Remove `sessions.join_token` entirely, including every code and schema reference to it, rather than leaving it as a documented-but-inert attractive nuisance.
- Verify this end-to-end against the real, frontend-constructed URL — not a direct backend call with a pre-known-good token and path.

**Non-Goals:**
- Fixing `SessionLobbyPage`'s unreachable lobby-landing branch (issue #164). This change makes redemption work; it does not make the post-redemption `lobby`-state landing experience complete. See Decision 5.
- Join-link revocation UI (already deferred by the `join-link` spec's own note).
- Any change to the copy-button/clipboard UI itself (issue #45, still paused pending this change).
- Any new server-side presence/readiness signal on `facilitator-state` (a reasonable idea, raised in exploration, but new plumbing and new UI that trades against the ritual's "disappear into the background" property — a decision for #164 or later, not this change).

## Decisions

### 1. Get-or-create, anchored at both `POST /draft` and `facilitator-state`

A get-or-create helper — reuse the team's active `join_links` row if one exists (`revoked_at IS NULL AND expires_at > NOW()`, most-recently-created wins on ties), else create one via the same audited path `POST /api/teams/:teamId/join-links` uses — is called from **both**:
- `POST /api/v1/teams/:teamId/sessions/draft`, so the endpoint's own `201` response body continues to include a working `joinToken` (existing tests already assert this field's presence; the response contract does not change shape).
- `GET .../facilitator-state`, the single place both the `draft`-view and `live-readiness-view` already read `joinToken` from, and which is polled repeatedly during the review window — so the link self-heals (a get-or-create miss just creates a new one) if it happens to expire while a facilitator is sitting on the page.

**Alternative considered:** anchor only at `advance` ("Open the room"). Rejected outright — it would mean no real link exists during `draft` at all, directly contradicting the `join-link-display-copy` design decision that the link must be visible and copyable before the room opens.

**Alternative considered:** anchor only at `facilitator-state`, treat `POST /draft`'s `joinToken` field as allowed to be briefly absent. Rejected — it silently changes the `201` response's shape from what existing tests and the current contract expect, to save one call to an already-cheap, already-indexed lookup (`idx_join_links_token`) that only writes on a rare miss. Calling the same helper from both places costs one extra function call, not meaningful complexity.

**Note on `POST /api/v1/teams` (new-team creation): not a third anchor point.** This endpoint (`facilitator-sessions.ts:435-612`) has its own, independent `sessions.join_token` generation (line 512), INSERT (558-564), and response field (610) — the same INSERT site Decision 6's footprint already catches for column-value removal. Verified against the frontend: `SessionCreationPage.tsx`'s new-team submission handler reads only `{ teamId, sessionId }` from this response (line 170) and navigates straight to `DraftSessionHost`, which independently re-fetches `facilitator-state` for its own `joinToken`; `SessionCreationPage.test.tsx`'s new-team mock response doesn't even include a `joinToken` field. Nothing consumes it today.

Engineer review (Marcus Oyelaran) correctly flagged that leaving this field in place after Migration A removes the underlying INSERT value would recreate the exact failure mode Decision 6 exists to close — a response field that looks wired up but is fabricated, with nothing about its name or shape signaling that. **Decision: drop `joinToken` from this endpoint's `201` response entirely**, rather than adding it as a third get-or-create anchor. Wiring get-or-create here too was considered and rejected: this endpoint creates a `lobby`-status session, not a `draft` one — there is no control view at this point in the flow that needs to display a join link, so a third anchor would add a real call site (and a second place `actor_global_role` must be sourced, trivial here since `globalRole` is already resolved at line 455, but still surface area) to serve a field nothing reads. Removing the field is the smaller, more honest change and it is a pure response-shape simplification: no frontend code or test depends on its presence (verified above). This is grouped into Migration A's commit (Decision 6, Migration Plan step 5) alongside the INSERT-site removal, since both touch the same handler; it also requires updating `facilitator-sessions.test.ts`'s existing `expect(typeof body.joinToken).toBe("string")` assertion for this endpoint (~line 566), which is the one test that would otherwise fail on this removal.

### 2. Shared audited creation helper, extracted from `join-links.ts`, into a new non-route module

The creation logic in `join-links.ts` is extracted into a function callable from both `POST /api/teams/:teamId/join-links` and the new get-or-create helper in `facilitator-sessions.ts`. This is a stated acceptance condition (see `specs/join-link/spec.md`'s new requirement), not a refactor-later nicety: a second, independently-written implementation of this logic is how the two copies drift on the audit guarantees the `join-link` spec's "Join link creation and redemption are durably recorded" requirement depends on.

**Extraction boundary (revised per engineer review — the original line-range framing was too narrow).** Design review verified `join-links.ts` directly: token generation and `expiresAt` computation (lines 65-68) sit before the transaction call, and the `emitAuditEvent(...)` call for `join.link_created` (lines 117-122) runs after it — both outside the originally-stated `76-104` boundary, and both load-bearing. Leaving `emitAuditEvent` outside the extracted function specifically risks the failure mode this decision exists to prevent: a second call site that either reimplements the structured-log emission independently (drift) or forgets it entirely (a `join_links` row created via get-or-create's miss branch with no matching structured log). **The extracted function owns everything from token generation through the post-commit `emitAuditEvent` call** — the full sequence at `join-links.ts:65-122` — not just the transactional half. Signature: `createJoinLink({ teamId, createdByUserId, actorGlobalRole, actorIp, logger }): Promise<JoinLink>`. Both `POST /api/teams/:teamId/join-links` and get-or-create's miss branch call this one function and use its returned `JoinLink`; neither reimplements, or separately invokes, any piece of it.

**Module location (revised per engineer review).** This function is extracted into a new module, `packages/backend/src/auth/join-link-creation.ts`, alongside `withAuditTransaction` which it wraps — not exported from `join-links.ts` for `facilitator-sessions.ts` to import. Verified against the codebase: no existing route file in `packages/backend/src/routes/` imports from a sibling route file today; every reusable cross-cutting piece (`withAuditTransaction`, `emitAuditEvent`, `evaluateSessionSubscriberAccess`, `applyTimingFloor`) lives in a dedicated non-route module and is imported into routes, never the reverse. Extracting into `auth/join-link-creation.ts` keeps `routes/` a leaf layer and avoids starting a route-imports-route precedent for what is, structurally, shared business logic rather than an HTTP concern. `join-links.ts`'s `POST /api/teams/:teamId/join-links` becomes a caller of this module, same as `facilitator-sessions.ts` will be.

**`actor_global_role` sourcing at the new call site (Blocking finding, both reviewers).** The extracted function requires `actorGlobalRole` as a parameter, matching the existing pattern (`join-link` spec's enumeration of per-call-site resolution). Verified directly against both handlers:
- `POST /api/teams/:teamId/join-links` (the existing call site) already resolves `userRole` at lines 44-53 before reaching the creation logic — no change needed.
- `POST /draft` (`facilitator-sessions.ts:214-241`) already resolves `global_role` and confirms `=== "facilitator"` before its own session INSERT — wiring get-or-create's miss branch here is free; the value is already in scope.
- `GET .../facilitator-state` (`facilitator-sessions.ts:1912-1999`) has **no** `global_role` lookup anywhere in the handler today — verified by reading the full handler; it authorizes purely on `sr.facilitator_id !== userSession.userId` and returns. This is the one real gap, and it is a blocking gap: without it, get-or-create's miss branch at this call site has no value to pass to a required parameter of a spec-governed audit write.

**Decision: add `const actorResult = await db.query<{ global_role: string }>("SELECT global_role FROM users WHERE id = $1", [userSession.userId])` to `facilitator-state`, paid only on get-or-create's miss path** (i.e., only when no active `join_links` row already exists for the team — the common case, an active row already existing, costs nothing extra). This matches the exact pattern already used elsewhere in this same file (e.g. `/advance`, `/start`, and the other `actorResult`/`global_role` lookups at lines 440-441, 687-688, 816-817, 1024-1025, 1212-1213, 1456-1457, 1626-1627, 2020-2021) — "re-read `global_role` live rather than trust cached session state" is this file's established convention, not a new pattern being introduced for this change. The rejected alternative — hard-coding `"facilitator"` on the reasoning that only a facilitator could have reached this session's draft state — was considered and rejected: it's an unstated assumption about role stability between draft-creation and now, and the cost difference (one indexed lookup, on a rare path) doesn't justify the assumption. Codified as a fourth bullet in `specs/join-link/spec.md`'s "Join link creation and redemption are durably recorded" requirement (see that file's delta).

**Addendum — one shared "active" definition, not two (per BA task review).** `specs/join-link/spec.md`'s "Get-or-create join link" requirement states that get-or-create and redemption must check "active" (`revoked_at IS NULL AND expires_at > NOW()`) "by construction from one shared definition, not two independently-maintained copies of it." Verified directly against the codebase: as of this revision, `GET /api/join/:token` (`join-links.ts:143-183`) encodes this rule as two separate JS conditionals (`if (link.revoked_at)`, `if (new Date(link.expires_at) < new Date())`) evaluated after an unconditional fetch-by-token, while get-or-create's design (Decision 1, Task 2.1) encodes the identical rule as a SQL `WHERE` predicate — two independent implementations of the same condition, in two different languages, that happen to agree today but are not reconciled by construction. This is the same "single source of truth" concern Decision 2 already exists to serve for the creation logic itself, extended to the predicate that decides when creation is skipped. **Resolution: export the predicate as a single SQL fragment constant, `JOIN_LINK_ACTIVE_SQL`, from the same `auth/join-link-creation.ts` module** (Task 1.3). Get-or-create's SELECT uses it directly in its `WHERE` clause; `GET /api/join/:token`'s SELECT adds it as a computed `(...)  AS is_active` column built from the same constant, and the handler gates rejection on `!link.is_active` rather than re-deriving the condition. The existing `revoked` vs. `expired` reason distinction in that handler's audit log and redirect is preserved (it still reads `link.revoked_at` and the expiry value to choose *which* reason to report) — only the pass/fail gate itself is unified to one definition (Task 2.6).

### 3. Race on concurrent get-or-create: accept and document, no DB constraint

Two near-simultaneous get-or-create calls for the same team (e.g., `POST /draft` and a `facilitator-state` poll landing together) can both observe "no active row" and both insert, producing two active rows for one team. This is **not** closed with a partial unique index, unlike the precedent at `packages/backend/migrations/10_sessions_team_active_unique.sql` (which closes an analogous race for session creation).

That precedent doesn't transfer: `sessions_team_active_unique` protects a real invariant (a team must not have two concurrently non-terminal sessions). A duplicate active `join_links` row protects nothing currently violated — the `join-link` spec already tolerates, by design, a team having multiple simultaneously-valid links (a facilitator can already produce this by clicking "generate new link" twice). A race producing a second valid row reaches the same spec-legal state a facilitator could reach on purpose. It's also not cleanly closeable the same way: `expires_at > NOW()` isn't an immutable expression, so a static partial index can't encode "active" the way `sessions_team_active_unique` encodes "non-terminal status" — closing it properly would require `SELECT ... FOR UPDATE` or an advisory lock, real complexity to spend on a race whose worst outcome is one redundant, harmless, spec-legal row, resolved by the most-recently-created tie-break the next time get-or-create runs.

### 4. Badge wording: reworded, not left as an accepted inaccuracy

Today's "(not yet joinable)" is literally true (nothing validates `sessions.join_token`). Once the link is a real, always-redeemable `join_links` token, that phrase becomes false — team join has never been gated on session status; that's what the join-link spec's "Session-aware join link landing" rule is for. Two options were on the table:
- Reword the badge around the operational question a facilitator actually has ("is it safe to share yet, and what happens if someone clicks it now").
- Leave the imprecision as a documented, accepted simplification.

**Decision: reword.** Final copy: **"This link works already — anyone who opens it before you open the room won't see a waiting screen yet."** This is one line of copy, not new UI chrome, and it directly serves the staging workflow `join-link-display-copy` was built for — a facilitator sharing the link ahead of "Open the room" specifically so people aren't creating accounts live in front of the group needs to know what an early clicker experiences, not which database row is technically gated. Codified in `specs/session-creation/spec.md`'s modified requirement.

### 5. Ship order relative to #164: ship now, relying on the `draft`-stage badge alone (no lobby-specific caution)

There is no existing stated sequencing between #166 (this change) and #164 (`SessionLobbyPage`'s lobby-landing branch is unreachable). Two options:
- Ship #166 only after #164 lands, so redemption and landing complete together and no gap window ever reaches a facilitator.
- Ship #166 now, as a deliberate choice, naming the gap.

**Decision: ship #166 now.** This change closes a currently-live gap (the entire join flow is dead) that originated from a security review; #164 is a separate, already-filed, unscoped routing problem with no committed timeline. Blocking a security-motivated fix on an unrelated backlog item indefinitely is a worse trade than shipping a bounded, explicitly-named gap. The gap itself is narrow: it only affects an Engineer who redeems the link while the session is specifically in `lobby` status (Decision 4's badge wording already tells the facilitator not to share it as "ready" before `draft`; the `active`-state late-join path is unaffected and works fully once this change ships).

To bound the risk Priya's review raised concretely — a facilitator staging a new team shares the link during `draft` ahead of "Open the room" specifically so people don't create accounts live, then advances to `lobby`, and an early clicker lands on a session-unaware `TeamPage` with no signal to anyone that anything happened — a lobby-specific caution "near the copy button" was the original plan here. Verified directly against `DraftSessionHost.tsx`: the branch rendered once `currentSessionState !== 'draft'` (`data-testid="live-readiness-view"`) currently renders no join-link element and no copy button at all — just a heading, an optional new-team acknowledgment, and "The room is open. Session status: {status}." There is no copy button, and no join link, for a lobby-specific caution to be placed near. Adding one would mean introducing a join-link/copy-button UI element to a view that today has none of that UI — a genuine, if small, new UI surface, not the "copy-only, no new UI surface" change this decision was originally framed as. It also edges directly into issue #45's territory (the copy-button UI itself), which `proposal.md`'s Impact section states explicitly is unaffected by this change.

**Decision: no lobby-specific caution. Rely on the `draft`-stage badge (Decision 4) alone, and state explicitly why that's sufficient.** By the time a session reaches `lobby`, the facilitator has already clicked "Open the room" — the sharing decision the `draft`-stage badge exists to inform has already been made. That badge already tells the facilitator, before they decide whether and when to share the link, what an early clicker experiences; restating the same information after the room is open gives that facilitator no new action to take. This is also the assumption the exec review (Rachel Okonkwo) reasons from directly: her sign-off treats the `draft`-stage badge as the sole informing mechanism ("the facilitator was already told (via the reworded badge)"), not a second, lobby-specific message. The task originally scoped as a `lobby`-state caution is dropped; the gap itself remains named in this document (below) and in the spec delta's dedicated scenario, but no additional frontend surface is built to further mitigate it. If a future change adds real `lobby`-state UI (as part of #164 or otherwise), a lobby-specific caution can be anchored to whatever UI that change introduces — it should not be invented ahead of it here, floating with nothing to attach to.

(A minimal join-count/presence signal on `facilitator-state` was also raised as an option; it's explicitly deferred — see Non-Goals — as new server-side tracking plus new UI that trades against the ritual's "stay in the background" property, better scoped on its own alongside #164 if pursued at all.)

**On #164 itself: this is a named stopgap, not a resolution.** Shipping #166 now with only the `draft`-stage badge as mitigation is an explicit, temporary trade — it closes the security-relevant redemption bug immediately while leaving the `lobby`-landing gap open, on the reasoning above that the gap is narrow and already-mitigated enough to not block a security fix. It is not a substitute for actually fixing #164. Per the exec review's condition, #164 should be converted from "unscoped, no timeline" into a scoped, scheduled change promptly after this one ships, not treated as indefinitely deferred cleanup — the longer the `draft`-badge-only mitigation stands in for a working `lobby` landing, the more it's being asked to do work a one-line caution was never designed to carry indefinitely.

### 6. `sessions.join_token`: removed via migration, full footprint enumerated, split across two deploys for rolling-deploy safety

Removal (not documentation-in-place) was chosen because a `NOT NULL` column named `join_token`, returned verbatim in an API response and formatted into a URL by frontend code, is exactly what invited this bug — nothing about its name or shape signals "inert." A better comment doesn't remove that gravitational pull for the next person skimming the code; removing the column does.

**Rolling-deploy check (per exec review, verified against the codebase's actual deployment model, not assumed).** `requirements/High-Level Architecture.md` §9.2 documents the production deployment target as Kubernetes, with `app` provisioned as a `Deployment` explicitly noted as supporting horizontal scaling — the standard rolling-update model, where old-code and new-code pods serve traffic concurrently for the duration of a rollout. No in-repo deployment runbook was found that pins down migration-vs-rollout sequencing precisely enough to rule out that overlap (§9.4 states a tested runbook is a production-readiness requirement; it does not evidence one existing yet in this repository). Given that, dropping a `NOT NULL` column in the same release as the code that stops referencing it is not safe as a single atomic step under a rolling deploy, in either sequencing order:
- If the migration is applied before the rollout completes, any still-running old-code pod's `INSERT` — which explicitly supplies `join_token`, because the column is `NOT NULL` today — fails with a schema error the moment the column is gone, for every pod still on old code.
- If the rollout completes before the migration is applied, that's fine for old code, but new code's `INSERT` (which omits `join_token` entirely) violates the still-live `NOT NULL` constraint from the moment the first new-code pod starts handling traffic — independent of rollout ordering, since the column hasn't been relaxed yet.

**Resolution: split the removal into two migrations, landed as two separate commits.**
- **Migration A** (same commit as Decisions 1–5 and 7's behavior changes): `ALTER TABLE sessions ALTER COLUMN join_token DROP NOT NULL` only — no column removal. A nullable column safely accepts a value from old code (still setting it) and safely accepts no value from new code (which omits it) — both pod flavors succeed concurrently against this schema, for the duration of the rollout.
- **Migration B** (a follow-up commit, applied only once Migration A's release is confirmed fully rolled out — zero pods still running pre-#166 code): `DROP COLUMN join_token` — this drops `sessions_join_token_unique` and `idx_sessions_join_token` automatically, no separate `DROP CONSTRAINT`/`DROP INDEX` step — bundled with the five backend test files below that reference it in raw SQL or by constraint name. This should land as the very next change after Migration A is confirmed deployed, not an indefinitely deferred cleanup — the goal is two sequenced, safe deploys, not a permanently half-migrated column.

This is the sequencing the exec review pre-authorized as the fallback if "a rolling-deploy window turns out to be more delicate than the doc assumes" — it does, for the reason above, so this document takes that fallback rather than asserting a single-commit atomic drop is safe.

**Full footprint** (verified directly against migration files and grep, not assumed):
1. **Migration A:** `ALTER TABLE sessions ALTER COLUMN join_token DROP NOT NULL` — lands in the same commit as the behavior changes (Decisions 1–5, 7).
2. **Two INSERT sites** in `facilitator-sessions.ts` (existing-team draft creation, and new-team draft creation) currently populate `join_token` because the column is `NOT NULL` today, plus the token-generation line and its stale comment ("`join_token` is required but not meaningful for draft sessions"). All lose their `join_token` reference in Migration A's commit — this is safe once the column is nullable, and doesn't need to wait for Migration B.
3. **The `facilitator-state` SELECT and response** currently selects `join_token` and maps it to `joinToken` in the response. This is the exact field Decision 1's get-or-create repoints to the real `join_links` value — same commit as Migration A, not a separate one.
4. **`DraftSessionHost.test.tsx`** (frontend) updates in Migration A's commit — it asserts against the frontend URL/badge-copy changes landing in that same commit (Decisions 1–5's frontend half), not against the database schema, so it has no dependency on the column actually being dropped. It is explicitly exempt from the "lands with the DROP COLUMN" grouping below for this reason, not by oversight.
4a. **Two `facilitator-state` unit tests break in Commit 1, not Migration B — a different mechanism than the schema drop, missed by the original footprint (both reviewers independently caught this).** These break the moment Task 2.3 repoints `facilitator-state`'s `joinToken` source from the `sessions.join_token` SELECT to get-or-create — independent of the column ever being dropped, because the handler's data source changes, not its SQL validity:
   - `facilitator-sessions.test.ts` (~lines 2206-2231, describe block `"GET .../facilitator-state"`) mocks the sessions SELECT to return `join_token: "join-token-abc"` and asserts `body.joinToken` equals that literal — stale the moment the source changes.
   - `http-session-expiry-no-partial-execution.test.ts` (~lines 150-163, the `#146` session-expiry-continuity regression test) mocks one `join_token: "tok"` row and stages exactly one `mockDbQuery` resolution; get-or-create's `join_links` SELECT (and, on the rare miss, its INSERT) needs a second staged resolution that isn't there today. Left unfixed, this either fails loudly (nothing queued) or — the worse case, since a security-relevant regression test is involved — passes without actually exercising get-or-create at all, silently losing coverage on the reauth path Decision 1 was built to keep working.
   Both are updated (new mock staging a `join_links` lookup, assertions against that value) in the same commit as Task 2.3, per `tasks.md` Task 2.5. Also fixed in this same commit: `facilitator-sessions.test.ts`'s `POST /api/v1/teams` assertion `expect(typeof body.joinToken).toBe("string")` (~line 566), removed per this decision's note above on dropping that endpoint's `joinToken` field.
4b. **Stale type and doc references, not schema-breaking but within the proposal's own stated bar ("every code and schema reference... removed"), folded in per engineer review:**
   - `packages/shared/src/types/session.ts:19` — `Session.joinToken: string` is dead (confirmed nothing imports this type; only `AuthSession` is used elsewhere) but still a reference. Removed in Migration A's commit.
   - `packages/shared/src/types/team-content-access.ts:219-224` — `FacilitatorSessionStateResponse.joinToken`'s JSDoc names `sessions.join_token` and "not-yet-joinable" directly; both become false the moment Task 2.3 and Decision 4 land.    - `facilitator-sessions.test.ts` — asserts on the literal constraint name `"sessions_join_token_unique"` (verifying an unrelated-constraint 23505 isn't misread as the concurrent-session 409); this assertion must be removed or rewritten against a different, still-existing constraint name, not merely updated in place

### 7. Verification: exercise the actual frontend-constructed URL

A test that calls `GET /api/join/:token` directly with a known-good token would pass today even with the frontend's path bug (`/join/:token` vs `/api/join/:token`) still present — it validates the token in isolation and misses the exact "technically complete, functionally invisible" failure this whole issue started from. Verification for this change SHALL instead exercise whatever URL the draft-session control view actually renders and puts on the clipboard (e.g., drive it through the rendered component / an integration test asserting on the constructed string, then follow that exact string against the backend), so a regression in either half (token or path) is caught by the same test.

## Risks / Trade-offs

- **[Risk] A join redeemed during `lobby` still doesn't land the Engineer on a working waiting screen (issue #164).** → Mitigation: named explicitly in Decision 5 and in `specs/session-creation/spec.md`'s modified requirement, scoped out rather than silently absorbed. No lobby-specific UI is added to mitigate it further (Decision 5) — the `draft`-stage badge, seen before the facilitator makes the sharing decision, is treated as sufficient. This is an explicit stopgap, not a resolution: #164 should be scoped and scheduled as a follow-up change promptly after this one ships, not left indefinitely on "unscoped, no timeline" status with this badge standing in for it.
- **[Risk] Concurrent get-or-create can produce two active links for one team.** → Mitigation: accepted by design (Decision 3) — spec-legal, harmless, self-resolving via the tie-break; not worth the complexity of a lock or an index that can't cleanly express "active" anyway.
- **[Risk] Dropping `sessions.join_token` breaks five backend test files' raw SQL immediately, not just assertions.** → Mitigation: full footprint enumerated in Decision 6 and itemized per-file in `tasks.md`. The drop itself is deferred to Migration B, landed in the same commit as those five test-file updates so CI never sees the column-dropped/tests-not-updated intermediate state; Migration A (constraint relax only) ships earlier, with the behavior changes, and doesn't touch these tests at all.
- **[Risk] A rolling Kubernetes deploy overlaps old-code and new-code pods against a `NOT NULL` column mid-rollout.** → Mitigation: verified against `requirements/High-Level Architecture.md` §9.2 (the `app` Deployment's horizontal-scaling/rolling-update model) — see Decision 6. Resolved by splitting the column removal into Migration A (drop `NOT NULL` only, safe for both old and new code concurrently) and Migration B (drop the column, gated on Migration A's release being fully rolled out). Noted per security review: during the rollout window itself, a request still landing on an old-code pod gets exactly today's status quo (the same non-functional link) — not a new regression, just the pre-existing bug persisting a little longer on a shrinking fraction of traffic until the rollout completes.
- **[Risk] `facilitator-state`'s get-or-create call site had no sourcing story for the `actor_global_role` its audit write requires.** → Mitigation: both the engineer and security reviews independently caught this as blocking. Resolved in Decision 2 — a miss-path-only `SELECT global_role FROM users WHERE id = $1`, matching the pattern already used at eight other call sites in the same file, and codified as a fourth bullet in `specs/join-link/spec.md`'s "Join link creation and redemption are durably recorded" requirement.
- **[Risk] A future change reintroduces a session-scoped join mechanism out of the same instinct that produced `sessions.join_token`.** → Mitigation: this design explicitly states why `join_links` is team-scoped by design (`specs/join-link/spec.md`'s existing "Facilitator generates additional join link" scenario), so the shape mismatch is documented, not just fixed once.
