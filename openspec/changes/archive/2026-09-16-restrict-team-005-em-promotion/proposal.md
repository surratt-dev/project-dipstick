## Why

TEAM-005 (`PATCH /api/v1/teams/:teamId/members/:userId/role`) can be used to establish a new Engineering Manager relationship on a team — the exact action Decision 1 reserves exclusively for TEAM-006 (`POST /api/v1/teams/:teamId/managers`) under Application-Admin control with a hard `global_role` precondition and a dedicated audit event. An EM already legitimate on Team A can use TEAM-005 to grant themselves, or any colleague, read access to a *different* team's session history and trends — no admin decision, no `team.manager_established` record, not even a rate-limit gate. `evaluateTeamAccess` (`packages/backend/src/auth/team-content-access-helper.ts`) grants `role: 'engineering_manager'` from `team_memberships.role` alone; `global_role` is read into the returned object but never compared, despite a comment directly above the code asserting the dual-check is exactly what happens. This is GitHub issue #109.

This is not a break in the Health Check ritual itself — simultaneous reveal, no-manager-participation, facilitator-from-another-team, and vote secrecy are all untouched. It is a break in Decision 1's promise that establishing EM read access is "a deliberate, audited action... not something a passing [non-admin] can perform without institutional accountability." A participant is told that boundary is structural. Right now it isn't, and the gap is silent — nothing about it depends on anyone noticing, which is exactly the property that makes it corrosive to the trust the ritual depends on.

The bug is two-layered, and fixing only one layer leaves the other exploitable:
- **Read-side:** `evaluateTeamAccess` grants EM access from `membership_role` alone, without confirming `global_role` independently. A target who has never been through TEAM-006 for *this* team — including an ordinary engineer with no EM status anywhere — can be granted EM read access to it.
- **Write-side:** even with the read-side fixed, someone already holding legitimate `global_role = 'engineering_manager'` from a *different* team can still be flipped into Team A's `engineering_manager` membership slot via TEAM-005. Both sides of a naive AND-check would then pass honestly, but no admin ever adjudicated that specific relationship, and no `team.manager_established` audit record exists for it. The administrative record — what the team-administration view and any facilitator inheriting the team would see — is still lying, independent of whether the access consequence is neutralized.

Both fixes are required; neither is a bonus once the other lands.

## What Changes

- **Read-side fix — `evaluateTeamAccess` requires the dual-check the code already claims to perform.** Path 1's `engineering_manager` sub-case (granting EM access from `membership_role` alone) is removed. EM read access to a team is granted only when `global_role = 'engineering_manager'` AND `team_memberships.role = 'engineering_manager'` for that team both hold — Path 2's existing dual-check pattern becomes the only path that can grant EM access, matching the pattern already correctly implemented in `checkAssignRolesAuthorization` (`packages/backend/src/routes/teams.ts:30-64`) for a structurally identical question.
- **Write-side fix — TEAM-005 unconditionally rejects the `participant → engineering_manager` transition.** `participant → engineering_manager` is TEAM-006's exclusive function per Decision 1; TEAM-005 can no longer originate it, regardless of actor (EM-on-this-team or Application Admin — see design.md for the admin-actor decision), regardless of whether actor and target are the same person, and regardless of the target's existing `global_role`. **BREAKING for any caller currently relying on TEAM-005 to promote a team member to Engineering Manager** — that caller must be redirected to TEAM-006. Demotion (`engineering_manager → participant`) via TEAM-005 is unaffected and continues to work exactly as it does today.
- **No admin-configurable exception, ever.** The write-side block is unconditional in code — no feature flag, environment variable, or admin override may relax it. This is a hard proposal-level requirement, not a default that happens to ship enabled (see design.md for the testable acceptance criterion and its verification method).
- **Audit-trail correctness restored.** Once the write-side fix lands, every new EM relationship traces back to a `team.manager_established` record written by TEAM-006. TEAM-005's mislabeled `team.role_changed` event stops being reachable for promotions (it remains correct and unchanged for demotions, which is its legitimate use).
- **Requirements-documentation correction (blocking, in scope) — two document sets, same failure mode.** `requirements/use cases/01 - Identity and Access - Use Cases.md` currently documents the pre-fix behavior as accepted, implemented design in three places: UC "Assign a Role to a Team Member" AC1 (checked off, authorizing the exact transition this change blocks), that UC's Out-of-Scope note ("TEAM-005 alone is sufficient for all `membership_role` writes"), and the sibling UC "Establish a Manager/Team Relationship"'s Dependencies/Notes ("TEAM-005... does not check `global_role`," stated as a factual boundary rather than the gap it is). A BA review of this proposal found the same problem in a second document: `requirements/design/REST API Contract.md`'s TEAM-005 section (line 421, 457) and its dated `REST API Contract - Validation Report.md` addendum (2026-03-15) restrict the promotion path for EM actors only and say nothing about Application Admins — which, read literally, currently documents admin-initiated promotion via TEAM-005 as permitted. That's not a neutral gap; it's an existing, dated decision record that bears directly on this proposal's own Open Question 1 (design.md) and needs to be surfaced to whoever resolves it, not silently left standing. Left uncorrected, either document is the same failure mode as the code comment that caused the original bug — a document asserting incorrect behavior as intentional, for the next engineer to trust in good faith, and the API contract is arguably the more load-bearing of the two during implementation. Correcting both document sets is a first-class task, at the same priority as the code fix, not an afterthought. Exact wording is the BA's call at implementation time; this proposal establishes that the task is mandatory and blocking.

## Capabilities

### New Capabilities
(none — this change closes a gap in existing capabilities; it does not introduce new user-facing functionality)

### Modified Capabilities
- `team-content-access`: `evaluateTeamAccess`'s Path 1 currently documents (and implements) granting `role: 'engineering_manager'` from `team_memberships.role` alone, with no `global_role` check — this is the read-side half of the bug, encoded directly in the spec's own requirement text, not just the code. The delta removes that sub-case and requires the existing Path 2 dual-check to be the sole path to an EM grant.
- `role-assignment`: TEAM-005's "Authorized actor can change a team member's membership role" requirement currently authorizes both directions of the `participant`/`engineering_manager` transition without restriction. The delta adds an unconditional restriction: TEAM-005 rejects `participant → engineering_manager`; only demotion remains available through this endpoint. The audit requirement gains a new event for blocked promotion attempts (pending the security analyst's decision recorded in design.md).

## Impact

**Not touched:** vote secrecy/attribution boundary, simultaneous reveal, no-manager-participation, facilitator-from-another-team, any live-session or facilitator-view code, TEAM-006 itself (its precondition and audit behavior are already correct and are the standard this change brings TEAM-005's read/write paths into line with), and issue #13's rate-limiting fix (a sibling Phase 2 blocker with an independent root cause and owner — not bundled into this change).
