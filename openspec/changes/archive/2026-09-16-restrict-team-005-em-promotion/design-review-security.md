# Security Design Review: restrict-team-005-em-promotion

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Reviewing:** `design.md`, `proposal.md`, `tasks.md` (this change), against `threat-model.md` (archived `establish-manager-team-relationship` change, Scenario 1 / finding 1.3, which I authored) and the current implementation of `evaluateTeamAccess` (`team-content-access-helper.ts`) and TEAM-005 (`teams.ts`).
**Purpose:** Resolve Open Questions 1–3 (mine to decide per design.md), weigh in on 5–7 where design.md invites security input, and flag anything left deferred or implicit that shouldn't be.

---

## Summary judgment

This design closes finding 1.3 correctly and completely. Decision A and Decision B together are exactly the "both fixes, neither optional" conclusion my threat model reached — I said at the time that a read-side-only fix leaves a cross-team-EM variant open (someone already legitimately EM elsewhere), and Decision B's unconditional block on the *transition* rather than on the *target's current global_role* closes that variant correctly. I have no objection to Decisions A, C, or D as written.

I'm resolving the three questions assigned to me below, with reasoning, and adding implementation-level flags that the design leaves implicit and that I want made explicit before this ships.

## Open Question 1 — Does the write-side block extend to Application-Admin actors, or only EM actors?

**Decision: Block all actors, including Application Admin, unconditionally. TEAM-005 must never originate `participant → engineering_manager`, regardless of who is calling.**

Reasoning:

1. **Decision 1's own language settles this.** Decision 1 (from the archived `establish-manager-team-relationship` change) names TEAM-006 as "the sole authorized actor" for establishing a new EM relationship — not "the sole authorized actor when a non-admin is involved." An Application Admin who reaches the same effect through TEAM-005 is not exercising a different, lesser authority than TEAM-006 requires; they're exercising the *same* authority through a door that was never built to carry the audit trail, the rate limiting, or the deliberate-single-action framing that makes TEAM-006's grant governable. "The admin has the authority anyway" is exactly the reasoning I'd reject if an engineering team offered it to justify skipping a control — the point of Decision 1 isn't that admins can't be trusted to promote someone, it's that promotion is supposed to be *a specific, auditable, rate-limited act*, and TEAM-005 can't provide any of those three properties no matter who calls it.

2. **This is what makes Decision C's "no admin-configurable exception" claim actually true.** Decision C says no admin override may exist to relax the write-side block. If Application Admins can still reach `participant → engineering_manager` through TEAM-005 unblocked, Decision C is true only in the narrow, technically-worded sense that there's no *config flag* — while the exact effect a config flag would have (admin bypasses the restriction) exists anyway via a different code path. I'd flag that as the same category of gap this whole change exists to close: a control that's true on paper and false in the reachable behavior.

3. **It's the only reading that makes the Goals section's audit claim true.** design.md's Goals state: "every EM relationship going forward traces to a `team.manager_established` record from TEAM-006." If admin-initiated promotion via TEAM-005 remains legal, that sentence is false for every admin-driven promotion — they'd trace to `team.role_changed` instead, which is precisely the mislabeling my threat model flagged as the reason an incident responder searching for `team.manager_established` wouldn't find this path. Blocking admins too is what makes the Goals section accurate rather than aspirational.

4. **On the "prior decision record" (REST API Contract.md:421, Validation Report 2026-03-15):** I read this before deciding, as design.md asked. I don't think it's the precedent design.md frames it as. The contract text is: *"An Engineering Manager may only assign the `participant` role via this endpoint. Assigning the `engineering_manager` role requires `application_admin` and is performed via TEAM-006, not this endpoint."* That second sentence is not scoped to "when an EM attempts it" — grammatically it's a general statement about how `engineering_manager` assignment happens at all: via TEAM-006, not via TEAM-005. The next sentence ("A request from an EM to set role='engineering_manager' must be rejected with 403") reads to me as the author calling out the one actor class who could plausibly reach TEAM-005 for this purpose at all under the *old* authorization model — not as a deliberate carve-out for admins. Silence on the admin case isn't evidence of an intentional "Option B" decision; it's evidence nobody asked the question, which is exactly design.md's own alternate theory. I'd treat this record as **needing correction, not as a vote for permitting admin promotion via TEAM-005** — and I'd ask the BA (tasks 5.5–5.6) to phrase the correction as removing an actor-scope ambiguity that was never actually resolved, not as reversing a considered decision.

5. **No operational cost.** Nothing in Non-Goals or the current admin workflow depends on TEAM-005 being an admin promotion path — admins already have TEAM-006, which is strictly more capable (it can onboard a user who isn't yet a team member at all, which TEAM-005 can't do regardless of this fix). Blocking admins doesn't remove any admin capability; it removes a second, worse-audited way to exercise a capability they still have in full via TEAM-006.

**Consequence for tasks.md:** Task 3.2 should apply the block unconditionally on the transition, with no actor-role branch at all — this actually *simplifies* the code versus a "block EM actors only" version, since there's no need to inspect `actorGlobalRole` in the new check. Task 4.4 should be the "Application Admin attempts the same transition via TEAM-005 — rejected" variant, not its alternative.

## Open Question 2 — Mismatched-state handling in `evaluateTeamAccess` (the AND-check's else branch)

**Decision: Graceful degradation to `role: 'participant'`, with a distinguishable audit/log signal. Not a hard 403.**

Reasoning:

- This is consistent with what I recommended in the threat model itself (finding 1.3's "Recommended mitigation" already offered both options and left the choice open — I'm closing that loop now, in favor of degradation).
- **Why not a 403:** the user in this state already holds an active `team_memberships` row for this team — they are a legitimate team member, just not correctly an EM. A hard 403 would lock a real team member out of a team's content entirely because of a data-integrity anomaly in a column they don't control (`global_role` is set from the IdP claim, not from anything the team-membership row reflects). That's an availability cost with no matching security benefit: degrading them to `participant` doesn't grant them anything beyond what their `team_memberships` row already entitles them to as a plain member. It denies exactly the delta this whole change exists to deny (the EM content profile), while not manufacturing a new failure mode a facilitator has to explain to a confused, blocked colleague.
- **Why this isn't "failing open":** the fail-safe direction here is *away from* the elevated grant, not toward denying baseline access the row already establishes. Degrading to `participant` is the security-conservative choice specifically because Decision B makes this state structurally unreachable via any live write path once both fixes ship — the only way to reach it going forward is stale pre-fix data or some future write path nobody has built yet (design.md's own framing in the Risks section). A state that can only arise from data staleness, not from anyone actively exploiting anything, should degrade gracefully with loud logging, not fail hard.
- **Precedent match:** this is the same shape as the OIDC claim-rejection pattern (`account-resolver.ts`) — an invalid/inconsistent input degrades to the safe default (there: `DEFAULT_GLOBAL_ROLE`; here: `participant`) with a logged signal, rather than blocking the request outright. I verified that pattern exists and is deliberate when I reviewed `account-resolver.ts` for the original threat model (Scenario 3, requirement 4) — reusing it here keeps the codebase's two "untrusted-input degrades safely" patterns consistent with each other instead of introducing a third, different shape.
- **The distinguishable signal is not optional.** A silent downgrade is exactly the "audit logs that don't get consulted are a comfort, not a control" problem I already raised in Scenario 2 of the threat model regarding EM account monitoring. This state should never occur post-fix; every occurrence is worth knowing about. I want a structured log event (new `AuditEventName`, e.g. `team.access_grant_mismatch`) emitted every time `evaluateTeamAccess` hits this branch, carrying `userId`, `teamId`, the mismatched `global_role` value, and `membership_role`. It does not need a synchronous `audit_log` DB row on every hit the way `admin.session_content_denied` gets one — `evaluateTeamAccess` is called on essentially every content request (Decision 6, no caching), so a user parked in this anomalous state would otherwise generate a DB write per page view. A structured log event alone is sufficient for detection/alerting; if this is ever seen in production even once, that's an incident to investigate by hand, not a volume of events to page on.

**Consequence for tasks.md:** Task 2.3 should implement the else-branch as `role: 'participant'` (not a new grant shape, not a 403) plus the new log event described above. Task 2.4's regression test should assert both halves: the returned grant is `role: 'participant'`, not `null` and not `'engineering_manager'`, *and* the log event fires.

## Open Question 3 — Does a blocked promotion attempt produce a distinguishable audit event?

**Decision: Yes. Required, not optional.**

Reasoning:

- This is close to a restatement of my own threat model's core complaint about the *original* bug: finding 1.3's severity rating rested partly on "no corresponding audit event... an incident responder searching `audit_log` for `operation = 'team.manager_established'` will not find this path." A fix that closes the access gap but leaves *attempts* against the closed door invisible repeats that exact blind spot one level up — instead of "EM got access with no record," it becomes "EM tried repeatedly to get access with no record until they gave up or found another way." A pattern of repeated blocked attempts against TEAM-005 for this specific transition is a legitimate detective signal (a credential probing for a gap that used to exist, or a still-unmigrated internal tool hammering the old endpoint), and it's exactly the kind of thing that shouldn't depend on someone thinking to add it later.
- **Precedent already exists in this codebase for this exact shape**, so this isn't a new pattern: `content.ts`'s `denyAdminContentAccess` (Task 5.11 from the earlier change) writes a synchronous `audit_log` row *and* emits a structured event for a denied-access case, before the 403 response is sent, with `http_status` in the metadata. I want the blocked-promotion case to follow that precedent exactly: a new `audit_log` operation (`team.role_change_denied` matches the naming tasks.md already floats) written synchronously before the error response, plus the corresponding `emitAuditEvent` call, carrying `actor_user_id`, `actor_global_role`, `actor_ip`, `target_user_id` (subject), `team_id`, and metadata for `{ from_role: 'participant', to_role: 'engineering_manager', http_status: <whatever 1.4 decides> }`.
- **Scope of when this fires:** only when an actor who *is* authorized to call TEAM-005 at all (passes `checkAssignRolesAuthorization`) hits the new transition block. An actor who isn't authorized to call TEAM-005 in the first place gets the existing, unrelated 403 — that's a different, already-handled case and doesn't need a new event. Don't conflate "not allowed to touch this endpoint" with "allowed to touch it, but not for this transition" in the audit trail; they're different signals with different response urgency.

**Consequence for tasks.md:** Task 3.4 should be unconditional (the "if task 1.3 resolves to yes" branch is now just "yes"). The audit write belongs in the TEAM-005 handler at the point Decision B's check fires, before the redirective error response is sent — same ordering guarantee `denyAdminContentAccess` already uses.

## Implementation-level flags (implicit in the design, need to be explicit before this ships)

These aren't open questions design.md routed to me, but reading the design against the actual `teams.ts` handler surfaced two ordering details I don't want left to implementer discretion:

1. **Where Decision B's check sits relative to the existing control flow.** The current TEAM-005 handler (`teams.ts`, PATCH handler) runs, in order: (a) `checkAssignRolesAuthorization` → 403 if the actor can't call this endpoint at all; (b) subject-membership lookup → 404 if the target isn't an active member, and this is also where `fromRole` (current `membership_role`) becomes known; (c) a no-op early return if `fromRole === newRole`; (d) the transaction that performs the write. Decision B's transition check needs `fromRole`, so it can only run at or after (b), and it must run *after* (c) — a no-op `engineering_manager → engineering_manager` request is not a promotion and must not be blocked by this check (it also never reaches TEAM-006 either way, so it creates no new grant). It must also run *before* (d) — no transaction should open for a request this check is going to reject. Just as importantly, it must run *after* (a), not before: an actor who isn't authorized to call TEAM-005 at all should get the existing generic 403, not a response that confirms "this specific transition is additionally blocked by policy" — that's a minor information-disclosure angle (confirming to an unauthorized caller that the promotion-block logic exists and what it targets) that costs nothing to avoid by keeping the existing check ordering. I'd like task 3.1's implementation to state this ordering explicitly rather than leave it to be inferred from where the diff happens to land.

2. **The mismatched-state log event's volume characteristics belong in the same comment block as Decision 6's no-cache note.** `evaluateTeamAccess` is called on effectively every content request per Decision 6 (no caching, by design). If Open Question 2's else-branch is ever hit by a real stale account, my chosen fix (log-only, no DB row) is deliberately lightweight so that an anomalous account casually browsing doesn't generate an `audit_log` INSERT per page view. Whoever implements task 2.3 should say so in the code comment, the way the existing rate-limiter code explains why `team.manager_association_rate_approaching` is log-only while `rate_limit_exceeded` gets a DB row — same reasoning, same place to look for it.

## Light-touch input on Questions 4–7 (not mine to decide, but asked-for or adjacent to my scope)

- **Q4 (error copy/status):** Not my call — Facilitator's, per design.md. No security objection to the redirective shape (Decision D); confirmed it doesn't disclose anything a caller doesn't already know (they're already authorized to call TEAM-005, and the message just names the correct endpoint).
- **Q5 (DB-layer defense-in-depth):** Architect's call, but I'll say plainly I'd support a check constraint or trigger here, for the same reason I noted in the threat model that `evaluateTeamAccess`'s AND-check is the correct backstop against "a future write path nobody has built yet" — a DB-layer constraint is one layer further out on the same principle, and the precedent (`migrations/7_team_memberships_partial_constraint.sql`) already exists for exactly this kind of guarantee on this table. Not blocking.
- **Q6 (phantom EM relationship backfill audit):** This is the direct, overdue follow-through on my own threat model's Scenario 1 finding — the gap has existed since finding 1.3 was live, so "no action needed" is not a safe default answer without someone actually running the query. I support the Executive Stakeholder's same-sprint timebox. I'd want the query to look for exactly the state my threat model traced: `team_memberships.role = 'engineering_manager'` rows with no corresponding `team.manager_established` audit_log entry for that `(user_id, team_id)` pair. Whoever owns this, I'm available to help define the query — it's a direct reuse of the attack path I already documented.
- **Q7 (historical mislabeled audit events):** Mild lean toward a corrective annotation rather than silent rewriting of history — if past `team.role_changed` rows are reclassified in place, that itself needs to be an audited action (you'd be rewriting the audit trail, which needs its own audit trail). A dated addendum/backfill marker that says "these N rows, identified by query X, are now known to represent EM-establishment events that should have been `team.manager_established`" preserves the original record's integrity while making the correction discoverable. Not blocking; flagging so whoever picks this up doesn't default to an in-place UPDATE on audit_log rows.
