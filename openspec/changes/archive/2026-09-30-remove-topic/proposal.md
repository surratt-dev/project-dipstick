## Why

`packages/shared/src/types/topic.ts` already models a topic's lifecycle as `status: "active" | "archived"` with `archivedAt: Date | null`, and `requirements/design/REST API Contract.md` already carries a fully drafted TOPIC-004 (`DELETE /api/v1/teams/:teamId/topics/:topicId`) sitting next to TOPIC-005 (Restore). None of that is a blank page — someone already thought hard about this endpoint's shape. What doesn't exist is the route handler itself, and there is no Topic Management screen anywhere in the frontend for a facilitator to reach it from. Issue #51 names both gaps directly: "soft-remove route and confirmation UI missing," even though the data model has supported archive/restore since #48.

This matters now for a reason bigger than "an endpoint is unbuilt." A team accumulates topics that stop being relevant — a technology stack question after a migration, a pairing prompt for a team that's gone remote-first — and today there is no way to retire one without either leaving it cluttering every future session or reaching into the database by hand. Every session after a team's first is supposed to feel like light bookkeeping the facilitator controls, not a fixed list nobody can touch. Leaving this unbuilt means the "topic flexibility within guardrails" property #49/#50 already delivered for adding topics stays half a feature: a team can grow its topic set but never prune it.

This is also the first issue in this feature area that requires a facilitator to look at a list of topics on a screen and act on one — #49/#50 shipped backend-only, with no round trip through a read endpoint before a write. That surfaces a real inconsistency sitting in the contract itself (detailed under Impact below): the read endpoint a management screen would call to render that list doesn't grant access to the same standing, org-wide facilitator population the write endpoints already do. That inconsistency was survivable when nothing read the list first. It isn't anymore.

## What Changes

- **`DELETE /api/v1/teams/:teamId/topics/:topicId` (TOPIC-004) — new endpoint.** Transitions a topic from `active` to `archived`, following the same check-ordering cascade, error envelope, and audit posture `topics.ts` already established for Add Custom Topic (#49/#50): `hasCompletedFirstSession`, `applyTimingFloor` on every branch, `{ error: { category, code, message, correlationId } }`. The identity/role check is the one piece *not* reused verbatim: FR-8.2 [HARD] requires that "the facilitator or Application Administrator" be able to add, remove, or reorder a team's topics, so TOPIC-004 authorizes `global_role = 'facilitator'` (not an active team member) OR `global_role = 'application_admin'` — the same model this change already applies to TOPIC-002 below, not TOPIC-003's facilitator-only check (a pre-existing, already-shipped gap against the same FR-8.2 that this change does not reopen — see Impact's "Not touched" list). This is a soft-delete only — `topics.status` transitions, no row is deleted, and `votes`/`session_topics` history is untouched by construction (`session_topics` is a per-session snapshot table with no re-derivation from `topics.status` after session start).
- **Hard block on removing a team's last active topic.** `409`, a new reason code, evaluated as part of the same cascade. Today no shipped endpoint can reach zero active topics — every team is seeded with defaults — so this has been a latent, untested gap. TOPIC-004 is the first endpoint that makes it reachable, and it does not ship without a gate.
- **Companion fix: `facilitator-sessions.ts`'s begin-voting handler no longer throws unhandled on zero active topics — but this is a symptom fix, not a fix of the underlying gap, and that gap is total, not rare.** The handler currently does `throw new Error(...)` when no topic exists at `display_order` 1 (`packages/backend/src/routes/facilitator-sessions.ts:1192`), which surfaces as an unhandled `500` in front of the team at the exact moment the facilitator clicks "Begin Voting." Stated plainly: **no shipped endpoint anywhere in this codebase currently populates `session_topics` at session creation** — not `POST .../sessions/draft`, not any other route. That means begin-voting cannot succeed for *any* session today, for any team, independent of anything in this change. This is pre-existing and was verified independently during this design (see design.md's Context) and by both the BA and executive reviews of this proposal. This change's fix does not close that gap; it replaces an unconditional crash with a clean, user-facing `409` at the one place the missing-topics state currently surfaces. Building the missing session-topics-snapshot-at-creation mechanism itself is out of this change's scope (design.md Non-Goals) — it is a materially larger, separately-scoped undertaking. Because of its severity, it is being filed as its own tracked GitHub issue, not left to be rediscovered (tasks.md 12.1).
- **Escalating confirmation flow**, matching FR-8.3 (always-true retention notice) and FR-8.5 (`[PREF]`, conditional open-action-item warning) as two steps of one dialog, not two independent always-shown dialogs: a generic, always-shown notice naming both the team and the topic ("Archive '{topic}' for {team}?" — the standing, org-wide facilitator model means a facilitator running several teams needs the confirmation itself to guard against archiving the right topic for the wrong team); escalating in place, when the server reports open action items on the first `DELETE`, to a specific warning with a server-derived count and an inline, view-only drill-down list of the open items (no navigation away from the dialog). The server re-derives the open-action-item check independently on the confirming `confirm=true` request — a client-held count from the first response is never trusted.
- **TOPIC-002's authorization corrected to the standing, org-wide facilitator model.** TOPIC-003 through TOPIC-007 all use `global_role = 'facilitator'` AND not a team member AND lock open — identical wording, five endpoints in a row. TOPIC-002 alone, sitting in the middle of that block, instead requires an active session for the team, the same model as TOPIC-001. This was never a considered decision (the sibling design's Decision 12 addresses TOPIC-001 specifically and does not mention TOPIC-002), it carries none of TOPIC-001's widening risk (TOPIC-002 is greenfield — no existing callers depend on its current shape, unlike TOPIC-001's `evaluateTeamAccess`, which is load-bearing across six other files), and it blocks this change concretely: a facilitator cannot browse a team's topics to pick one to archive if the read endpoint powering that screen only grants access to a facilitator currently running a session for that team. **BREAKING** for any caller currently relying on TOPIC-002's narrower, session-scoped authorization (none exist today — the endpoint and its backing route are unbuilt).
- **Facilitator-visible provenance on archived topics.** The removed-topics view shows, per topic, when it was archived and by whom — surfacing the same `topic.archived` audit event data in a facilitator-facing read path, not leaving it as an audit-only record. Under the standing, org-wide facilitator model, a facilitator inherits teams without a handoff conversation; "the topic is just gone" is a continuity regression from the spreadsheet-and-memory era this application replaces.
- **A new, minimal Topic Management frontend screen** — the first one to exist. Active topics in their current order (prompt, vote type, description per row, matching View Active Topic Configuration's existing acceptance criteria), a "Remove" affordance per row, and the confirmation flow above. Add/reorder/annotate controls stay out of this screen — those extend it when their own issues (#52–55) land. A decided nav entry point from `TeamPage.tsx` (currently renders only `MemberManagement`) is part of this change; a screen nobody can navigate to isn't a shipped feature.

## Capabilities

### New Capabilities
- `remove-topic`: The `DELETE /api/v1/teams/:teamId/topics/:topicId` endpoint (TOPIC-004) — authorization, the check-ordering cascade including the new last-active-topic `409` block, the open-action-item confirmation mechanism (`200`/`requiresConfirmation`/`confirm=true`), the archive transition itself, and audit posture.
- `topic-management-screen`: The frontend Topic Management screen — active topic list, remove action, the escalating confirmation dialog, the archived-topics view with facilitator-visible provenance (who/when), and the nav entry point into it from `TeamPage.tsx`.

### Modified Capabilities
- `topic-customization-lock`: TOPIC-002's authorization is corrected from "facilitator with an active session for the team, OR application_admin" to the standing, org-wide facilitator model (`global_role = 'facilitator'` AND not a team member, OR `global_role = 'application_admin'`; lock state is a separate cascade check) already used by TOPIC-003 through TOPIC-007 — TOPIC-004 included, per FR-8.2's admin requirement (see What Changes) — matching Appendix B's authorization matrix. The `403` error-table text at contract line 658 is corrected in the same change, since the authorization line and the error-table text cannot be fixed independently of each other.

## Impact

**Code:**
- `packages/backend/src/routes/topics.ts` — new `DELETE` handler, reusing the fact-only `evaluateStandingFacilitatorAccess` helper, `hasCompletedFirstSession`, `applyTimingFloor`, and the shared error envelope already established by the `POST` handler in this file, but with a new identity/role enforcement function (shared with TOPIC-002) that admits `application_admin` — the `POST` handler's own facilitator-only check is not reused verbatim (see What Changes, above). New: a reusable "does this topic have open action items" helper (`topics → session_topics → action_items WHERE status = 'open'`, across every session the topic has ever appeared in), co-located alongside `topic-lock-helper.js`'s pattern since TOPIC-005/006/007 will likely need something adjacent.
- `packages/backend/src/routes/facilitator-sessions.ts:1178-1196` — the unhandled `throw` in the begin-voting handler is replaced with a clean, user-facing validation error.
- `packages/backend/src/routes/content.ts` (or wherever TOPIC-002 ends up handled — a design.md call) — new `GET .../topics/all` handler, built against the corrected standing-facilitator authorization model from the start (this endpoint is unbuilt today).
- New frontend route (e.g., `/team/:teamId/topics`), `ProtectedRoute`-gated per the existing `App.tsx` pattern; a new screen component; no shared `Modal`/`ConfirmDialog` exists yet in `packages/frontend/src/components`, so the confirmation flow matches the existing inline-state pattern (`MemberManagement.tsx`, `PreSessionActionItemReview.tsx`) rather than introducing a generic modal abstraction for one consumer.
- `TeamPage.tsx` — a nav entry point into the new screen, next to (or alongside) `MemberManagement`.

**Schema:** one additive migration — `topics.archived_by uuid NULL REFERENCES users(id)`, populated in the same transaction as the archive transition, so the removed-topics view can show provenance via a plain join instead of an audit-log lookup. No backfill (no topic has ever been archived by any shipped endpoint).

**Requirements documentation (blocking, non-code, same priority as the code):**
- `requirements/design/REST API Contract.md` — TOPIC-002's `Authorization` line (line 609) and `403` error-table text (line 658) corrected together. TOPIC-004's `403` error-table row (line 786), which currently folds "customization lock active" into `403` the same way TOPIC-003's did before the sibling design's Decision 2 correction, is corrected to match: lock is `409`, `403` is reserved for identity/role failures.
- `requirements/use cases/08 - Topic Management - Use Cases.md` — the "Remove a Topic" use case's terminology (remove/re-add) is superseded by the shipped archive/restore data model and the already-drafted contract; its "Out of Scope" line stating "no archive state is defined" (line 232) is factually superseded by `topic.ts`'s shipped `status`/`archivedAt` fields. Design.md records both corrections on the record rather than silently diverging from the use case text; editing the use case document itself is out of scope for this change (separate governance workspace).

**Not touched:** the no-manager-participation rule, the simultaneous reveal, the facilitator-from-another-team requirement, the no-individual-performance-comparison guardrail, any live-session code, TOPIC-005/006/007 (Restore, Reorder, Annotate — separate future issues, #52–55), TOPIC-001 (its narrower, session-scoped authorization model is intentional per the sibling design's Decision 12 and is not touched by the TOPIC-002 correction above), and TOPIC-003's identity/role check (Add Custom Topic, #49/#50, shipped) — it shares TOPIC-004's pre-fix FR-8.2 gap (facilitator-only, no `application_admin` branch), but it is already-shipped, already-deployed code; widening it is a separate change with its own review and rollout considerations, deliberately deferred rather than silently bundled in here (design.md Non-Goals).
