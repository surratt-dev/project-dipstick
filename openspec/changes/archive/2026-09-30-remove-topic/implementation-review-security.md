## Implementation Security Review — `remove-topic` (#51, `TOPIC-004` + `TOPIC-002` correction)

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope reviewed:** the implemented diff against `design.md` and my own prior `design-review-security.md` findings — `packages/backend/src/auth/standing-facilitator-access-helper.ts`, `packages/backend/src/routes/topics.ts` (`DELETE /api/v1/teams/:teamId/topics/:topicId`), `packages/backend/src/routes/content.ts` (`GET /api/v1/teams/:teamId/topics/all`), `packages/backend/src/auth/audit-logger.ts`, `packages/backend/src/auth/open-action-items-helper.ts`, `packages/backend/migrations/16_topics_archived_by.sql`, `packages/backend/src/routes/facilitator-sessions.ts`'s begin-voting fix, `packages/shared/src/types/topic.ts`, and the corresponding test suites (`topics.test.ts`, `content.test.ts`, `remove-topic-integration.test.ts`).

**Overall assessment:** The implementation matches the design faithfully on every point I scrutinized. Both my design-review Finding 1 (timing floor) and Finding 3 (last-active-topic audit silence) were carried into `design.md` as explicit, on-the-record decisions rather than left implicit, and the code does exactly what those decisions say — including on the one point where the implementation took the alternative I recommended *against* (independent per-caller `applyTimingFloor` calls rather than folding it into the shared function) but did so correctly and with test coverage on both call sites. I have no blocking findings. One new, previously-unreviewed disclosure (`teamName`) is worth a short explicit note for the same reason `archivedBy` got one in the design review — not because it's risky, but because this project has been consistent about naming disclosure decisions rather than letting them be emergent.

### Verified: `checkStandingFacilitatorOrAdminAuthorization` is genuinely decision-only

`standing-facilitator-access-helper.ts:88-116` takes no `FastifyReply`, calls no `applyTimingFloor`, and returns a plain discriminated union (`{ authorized: true, actorGlobalRole }` / `{ authorized: false, reason }`). Confirmed against the two callers:

- `topics.ts`'s `checkArchiveTopicAuthorization` (topics.ts:332-352) calls `applyTimingFloor(startTime)` immediately before its own `reply.code(403).send(...)`, on its one rejection branch.
- `content.ts`'s TOPIC-002 handler (content.ts:536-551) independently calls `applyTimingFloor(startTime)` immediately before its own `reply.code(403).send(...)`, on the same rejection branch.

This is exactly Decision 1's and Decision 9's stated requirement, and it resolves my design-review Finding 1 — though not via the fix I recommended (folding the floor into the shared function "by construction"). `design.md`'s Decision 1 explicitly considered and declined that approach, stating the requirement as an obligation on each caller instead ("each caller remains responsible for calling `applyTimingFloor(startTime)`... on every early return"). I'd still note that this is a "by discipline" solution rather than a "by construction" one — a future third caller of this function could forget the call and nothing in the type system would catch it — but both existing callers implement it correctly, and both are covered by explicit tests (`content.test.ts:577-593`: "applies the timing floor on the 403 branch" / "applies the timing floor on the 200 success branch"). Not re-opening; noting for the record since it's the same residual risk shape as before.

### Verified: `topics.ts`'s DELETE cascade ordering, audit posture, and advisory lock

Read `topics.ts:555-730` end to end against Decision 2's eight-step cascade. The implementation matches step for step: identity/role (403) → team existence (404) → customization lock (409, audited via `writeLockDenialAudit`, unchanged from TOPIC-003) → topic existence (404 `TOPIC_NOT_FOUND`) → topic status (422 `TOPIC_ALREADY_ARCHIVED`) → last-active-topic guard (409 `TOPIC_LAST_ACTIVE`, inside the advisory-lock-held transaction) → open-action-item confirmation (200 `requiresConfirmation`) → success (200, archive `UPDATE` + `topic.archived` audit row). Every early-return I found — including both `ROLLBACK` branches inside the transaction — calls `applyTimingFloor(startTime)` before responding; no branch is exempt.

`TOPIC_LAST_ACTIVE`'s 409 (topics.ts:616-628) writes no audit row: it's a plain `ROLLBACK` + timing floor + response, no `INSERT INTO audit_log` anywhere in that branch. This matches `design.md` Decision 7's stated rationale exactly (my design-review Finding 3, accepted and answered on the record rather than fixed — scope discipline, not an oversight, with the explicit condition that this gets revisited if scripted last-topic-stripping attempts become an observed concern). `topics.test.ts` has no test asserting the *absence* of an audit row on this specific branch, but the code path itself is unambiguous, and I'm not asking for the behavior to change — this is a resolved decision, not an open one.

The success path (`topic.archived`, topics.ts:690-702) writes `metadata: { topic_id, openActionItemCount }` in the same transaction as the `UPDATE`, and `topics.test.ts:1210-1251` covers both the immediate-archive (`openActionItemCount: 0`) and `confirm=true` (freshly re-derived count) cases, including a test confirming the count in the audit row reflects the re-derivation, not a client-supplied value.

`pg_advisory_xact_lock(hashtext($1::text))` (topics.ts:604) is taken with `teamId` as the hash input, identical to `topics.ts`'s existing `POST /topics` handler (topics.ts:466) — same key, so the two endpoints correctly serialize against each other as well as against themselves. `remove-topic-integration.test.ts:304-359` ("two genuinely concurrent archive requests against a team's exactly two active topics never both succeed") exercises this against real Postgres, not a mock — good verification of the actual race-closing behavior, not just the query text.

### Verified: `content.ts`'s TOPIC-002 `archivedBy` disclosure matches Decision 6 exactly

`content.ts:581-598, 640-643` joins `topics.archived_by` to `users.display_name` and returns only `{ userId, displayName }` — no email, no other PII. `TopicManagementPage.tsx:415` renders only `displayName`. This matches what I reviewed and accepted in `design-review-security.md` Finding 2 (the disclosure boundary was named as a considered choice, not an emergent one, per Decision 6's added paragraph) — the implementation doesn't disclose anything beyond that boundary.

### New disclosure, not present in `design.md`: `teamName` on TOPIC-002 — low risk, but worth naming explicitly

The engineer's own code comment (`packages/shared/src/types/topic.ts`, on `GetAllTopicsResponse.teamName`) correctly flags this as an addition beyond the drafted contract, done to satisfy Decision 10's "the confirmation names both the topic and the team" requirement. I checked what population this newly exposes a team's display name to: `checkStandingFacilitatorOrAdminAuthorization`'s standing, org-wide caller population — any facilitator not an active member of the team, or any `application_admin`. I confirmed this is genuinely new exposure, not already available elsewhere to that population: both `GET /api/v1/teams/:teamId` and `GET /api/v1/teams/:teamId/members` (`teams.ts:370-432, 521-583`) gate on `isMember || application_admin`, not the standing-facilitator model, so a non-member standing facilitator had no prior path to a team's display name.

This is low risk and I don't think it needs to block anything: a team's display name is not personal data about an individual (the same "topic content isn't personal data" reasoning `design.md` Decision 6 already applied to prompts/vote types applies here, arguably even more so — it's a label for a group, not an individual), and the same standing facilitator population is already trusted to read that team's entire topic list, including who archived items from it. It's a strict subset of what the endpoint already discloses in aggregate. My only ask is procedural, in the same spirit as Finding 2 of my design review: this disclosure was never named as its own decision anywhere in `design.md`, only in an inline code comment. Given this project's own consistent practice of writing disclosure decisions down explicitly rather than letting them be emergent (Decision 6's own added paragraph is the direct precedent), I'd like a one-line addendum to `design.md` or the spec stating this is accepted, not just implemented. Not blocking.

### Verified: `active[].firstSessionDescription` is not a new disclosure category

This is topic content (matches "View Active Topic Configuration"'s existing acceptance criteria), already disclosed to the identical standing-facilitator population via the same endpoint's `prompt`/`voteType` fields. No new boundary crossed.

### Verified: no SQL injection surface, no enumeration/timing regression reintroduced

All new and modified queries (team existence, topic existence/status, last-active count, open-action-items join, archive `UPDATE`, `archived_by` join) are parameterized. No string-built SQL anywhere in the diff.

One inherited, pre-existing pattern I checked deliberately since the task asked about enumeration/timing: neither `teamId` nor `topicId` route params are validated as well-formed UUIDs before being passed into `db.query`. A malformed (non-UUID) `topicId` would cause Postgres to throw ("invalid input syntax for type uuid"), which propagates as an uncaught exception in `checkTeamExists`/`checkTopicExistsAndActive` (both run outside the try/catch that wraps the transaction) rather than a clean 404 — meaning that specific branch bypasses `applyTimingFloor` entirely. I checked whether this was something the sibling change's security review previously closed and needs to not be reintroduced here: it wasn't — the sibling review's timing/enumeration findings were about the `403`/`404`/`409` cascade ordering and the missing floor calls, not about input-format validation, and this exact unvalidated-param pattern already exists in `TOPIC-003`'s unmodified `checkTeamExists` (reused verbatim by `TOPIC-004`, per Decision 1). This is not a regression this change introduces, and it isn't exploitable for enumeration — a malformed ID reveals nothing about whether any *valid* ID exists or is accessible, only that the input itself is malformed, which the caller already knows. Not blocking, but flagging since it's adjacent to what I was asked to check: this is pre-existing codebase convention, not something `remove-topic` needs to fix, and not something it reintroduced.

### Verified: `facilitator-sessions.ts`'s begin-voting fix (Decision 8) has no security-relevant regression

The replaced `throw` (facilitator-sessions.ts:1194-1208) correctly issues `ROLLBACK` before returning the clean 409, and the surrounding `try/finally` (`finally { client.release(); }`, line 1265) still executes on this early return, so the Postgres client is released back to the pool correctly — no connection leak introduced by this fix. No new data is exposed by the 409 response.

### Summary for the record

Both findings I'd have wanted closed before shipping — the TOPIC-002 timing floor and the last-active-topic audit silence — were closed correctly: the first by explicit, tested code in both callers; the second by an explicit, on-the-record decision in `design.md` that I reviewed and accept. The `teamName` addition is the one loose end: low risk, correctly reasoned by the implementer's own comment, but not written down as a considered decision anywhere `design.md` or the spec deltas would show it — I'd like that closed with a one-line addendum before this ships, not because I think it's wrong, but because this project has held itself to naming disclosure decisions explicitly everywhere else and I don't see a reason to make this the exception. Nothing here reopens any authorization or architecture decision from the design review.
