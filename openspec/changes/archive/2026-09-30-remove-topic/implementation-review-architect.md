# Architecture Review — remove-topic (Issue #51)

**Reviewer:** Ingrid Sollenberger, Principal Solution Architect
**Scope:** Implementation against `design.md`'s decisions, boundary discipline, and the two deviations Marcus Oyelaran flagged for explicit ratification.
**Verdict:** Approved. Both flagged deviations are ratified as legitimate corrections. One implementation detail (the 0-row UPDATE fallback) is sound but its comment overstates what it explains — noted below, not blocking.

---

## 1. Deviation 1 — `GetAllTopicsResponse.teamName`

**Ratified.** This is not scope creep; it is a real contract gap that would have blocked the confirmation dialog design.md Decision 10 itself specifies (`"Archive '{topic.name}' for {team.name}?"`). I traced the caller population under Decision 9's standing, org-wide model: a facilitator hitting `TOPIC-002` may not be a member of the target team, and no other endpoint reachable by that caller (`evaluateStandingFacilitatorAccess`'s grant covers only `topics.ts`/`content.ts` reads, nothing team-identity-bearing) returns a team display name. Without this field, the frontend would have had to either issue a second round trip against an endpoint the design never specifies, or the dialog would have shipped without the team name the spec's own AC requires ("names both the topic and the team"). Adding it to `GetAllTopicsResponse` — sourced by a single `SELECT name FROM teams WHERE id = $1` alongside the existing query, `content.ts:557-558` — is the cheapest correct fix and was applied consistently: shared type (`topic.ts:37`), handler (`content.ts:619`), and `REST API Contract.md:625` all carry the same stated-correction comment with rationale. This is exactly the "corrected on the record, not silently edited" pattern the rest of this design already uses (Decisions 4, 6, 9). No objection.

## 2. Deviation 2 — `active[].firstSessionDescription`

**Ratified**, same reasoning. `specs/topic-management-screen` and design.md's Decision 10 both require the active list to show "prompt, vote type, and description per row, matching View Active Topic Configuration's existing acceptance criteria — not a stripped-down name list." The drafted `TOPIC-002` contract's `active[]` shape didn't carry `firstSessionDescription` at all — an omission, not a considered decision (parallel to Decision 9's own finding about `TOPIC-002`'s authorization being an unreviewed drafting gap, not a stable answer). Shipping the screen without it would fail the screen's own stated acceptance criteria. Extension is consistent everywhere: shared type, handler (`content.ts:628`, straight passthrough of the column already selected at `:567`), contract (`:634`), and the frontend renders it conditionally (`TopicManagementPage.tsx:314-321`) rather than assuming presence. No objection.

**General note on both:** I'd flag it if either extension had gone into the backend/shared type without a matching `REST API Contract.md` edit, or vice versa — that's exactly the "documented vs. implemented" drift Decision 4 already calls out as a recurring risk in this codebase. I checked all three surfaces (shared type, handler, contract) for both fields; they agree.

## 3. The 0-row UPDATE fallback (`topics.ts:673-685`)

**Sound, and correctly scoped — not papering over a bug.** The `UPDATE ... WHERE id = $2 AND team_id = $3 AND status = 'active'` at `topics.ts:667` can legitimately return 0 rows despite Task 3.3's pre-check (`checkTopicExistsAndActive`) having just confirmed `status = 'active'`, because that pre-check runs **before** the advisory lock is acquired (`topics.ts:604`), not inside the same lock-held section. Two concurrent `DELETE` requests against the *same* topic (not the last-two-active-topics race Decision 3's lock exists for) can both pass the pre-check, then serialize at the lock: the first commits the archive, the second's `UPDATE` matches zero rows because `status` no longer equals `'active'` by the time it runs. Returning `422 TOPIC_ALREADY_ARCHIVED` — the same response the pre-check itself would have given had it run a moment later — is the correct behavior, not a new code path papering over an unexplained state. It's a genuine, narrow TOCTOU window the design's own cascade ordering (pre-check outside the lock, mutation inside it) creates by construction, and the fallback closes it with the response Decision 2's cascade would have given anyway.

One documentation nit, not blocking: the inline comment at `topics.ts:673-677` attributes this to "a concurrent request between Task 3.3's pre-check and this UPDATE (both serialized per-team by the advisory lock, but the pre-check itself runs before the lock is taken)" — this is correct, but design.md's Decision 2/3 text doesn't independently state that the existence/status pre-check (step 4/5) runs outside the lock while the guard and mutation (steps 6-8) run inside it. That's a real architectural detail (why the lock's scope starts where it does) that's currently only discoverable by reading the code, not the design doc. Worth a one-line addition to Decision 3 or Decision 2 noting the pre-check/lock boundary explicitly — future readers debugging a "why did this 422 instead of behaving like the last-active guard" question shouldn't have to reconstruct this from code comments. Non-blocking; flagging for whoever does the next design.md pass on this area, per my own standing concern about implicit decisions.

## 4. Boundaries and patterns (my primary review lens)

- **File placement (Decision 1).** Verified no route file imports from another route file anywhere in `packages/backend/src/routes/` — `grep` for cross-route imports returned nothing. `checkStandingFacilitatorOrAdminAuthorization` lives in `auth/standing-facilitator-access-helper.ts`, has two callers (`topics.ts`, `content.ts`), touches no `FastifyReply`, and calls no `applyTimingFloor` — matching the decision-only contract Decision 1 specifies. Both callers (`topics.ts:332-352`, `content.ts:536-551`) write their own reply and their own `applyTimingFloor` call on every branch. This is the boundary I'd have pushed back on had it been drawn wrong, and it wasn't.
- **`open-action-items-helper.ts` placement and shape.** Co-located per `topic-lock-helper.ts`'s established one-function-per-file pattern, as Decision 5 specifies. The `Queryable` interface (executor defaults to the pool, accepts a transaction client) is a clean, minimal abstraction — it lets the same function serve both an ordinary standalone read and a call inside `topics.ts`'s advisory-lock-held transaction without duplicating the query or coupling the helper to `pg`'s concrete types. This is the right shape for a helper explicitly documented as intended for reuse by TOPIC-005/006/007.
- **`archived_by` as a first-class column, not an audit-log read path (Decision 6).** Correct call, and consistent with this codebase's existing precedent (`action_items.resolved_in_session_id`/`resolution_note` cited in design.md as the direct analogue — I checked, that precedent is real). The migration (`16_topics_archived_by.sql`) is additive, nullable, no backfill, matches its own stated rollback plan.
- **Timing floor discipline.** Every early return I traced in both the `TOPIC-004` cascade (`topics.ts`) and `TOPIC-002`'s handler (`content.ts:538`) calls `applyTimingFloor` before responding, including the two branches inside the transaction (`ROLLBACK` then floor then respond, consistently) and the 0-row fallback discussed above. No branch skips it.
- **Transaction/lock scope (Decision 3).** `pg_advisory_xact_lock(hashtext(teamId))` is acquired before the `active_count` read and held through the archive `UPDATE` and the success audit `INSERT`, released automatically on `COMMIT`/`ROLLBACK` — matches TOPIC-003's established pattern verbatim, reused rather than reinvented.
- **Audit posture (Decision 7).** `topic.archived` added to `AuditEventName`'s union with metadata `{ topic_id, openActionItemCount }`, written in the same transaction as the `UPDATE`, with a structured-log counterpart emitted after `COMMIT` — same two-part pattern (`db.query` INSERT + `emitAuditEvent`) as `topic.custom_added`. The re-derived open-action-item count is correctly observable (not discarded), addressing the engineer review's Finding 2 as claimed.
- **`facilitator-sessions.ts` begin-voting fix (Decision 8).** Scoped exactly as stated — replaces the unhandled `throw` with the file's existing local error shape (no `code` field, matching the adjacent status check), does not attempt the broader `session_topics` snapshot-at-creation fix. Correctly out of scope for this change; I'd have flagged it if it had crept wider.
- **Frontend (Decision 10).** No new shared `Modal`/`ConfirmDialog` component introduced — the one dialog's content is swapped in place via `RemoveTopicState`'s discriminated union, mirroring `MemberManagement.tsx`'s established inline-state pattern rather than extracting a generic component for a single consumer. Nav entry point added to `TeamPage.tsx` as a plain link; `ProtectedRoute` gating matches the existing pattern in `App.tsx` with no new client-side authorization primitive — access control is enforced server-side by `TOPIC-002`, exactly per this project's stated "authorization logic must not leak into the frontend as the only gate" concern.

## Summary

No architectural boundary violations found. Both flagged deviations are legitimate, minimal corrections to an underspecified contract, applied consistently across shared type / handler / contract documentation — exactly the "correct on the record, don't silently diverge" discipline this design has used throughout (Decisions 4, 6, 9). The 0-row UPDATE fallback is a real, narrow race the cascade's own pre-check/lock boundary creates, and the fix is the right one; I'd like a one-line addition to design.md's Decision 2 or 3 documenting that boundary explicitly, but that's a documentation follow-up, not a rework request.
