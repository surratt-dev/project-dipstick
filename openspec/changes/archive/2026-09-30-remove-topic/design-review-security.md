## Security Review — `remove-topic` (#51, `TOPIC-004` + `TOPIC-002` correction)

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope reviewed:** `design.md`, `proposal.md`, `tasks.md`, `specs/remove-topic/spec.md`, `specs/topic-customization-lock/spec.md`, `specs/topic-management-screen/spec.md`, cross-checked against the shipped precedent this design extends or must stay consistent with: `packages/backend/src/routes/topics.ts` (TOPIC-003, shipped), `packages/backend/src/routes/content.ts` (TOPIC-001, shipped, including `evaluateTeamAccess`/`denyNullGrant`/`denyAdminContentAccess`), `packages/backend/src/auth/standing-facilitator-access-helper.ts`, `packages/backend/src/auth/topic-lock-helper.ts`, `packages/backend/src/auth/audit-logger.ts`, `packages/frontend/src/components/MemberManagement.tsx`, and this feature area's own prior security review (`openspec/changes/archive/2026-09-29-topic-customization-lock-and-add-custom-topic/design-review-security.md`).

**Overall assessment:** This design carries forward the sibling review's Finding 1 (timing floor) and Finding 3 (success-path audit) lessons correctly *for TOPIC-004* — Decision 2's amendment and the archive-transaction audit write are both explicit, on the record, and match established convention. My findings here are that the same discipline is not carried as explicitly onto the *other* new surface this change introduces (TOPIC-002, sharing the same new authorization function but living in a different file); that a new category of disclosure — one named user's identity exposed to another, unrelated user — is introduced by the `archived_by` provenance feature without being named as its own decision; and that the last-active-topic guard, a state-integrity control reachable by the same wide caller population the sibling review already flagged as needing a rate-limit conversation, is audited nowhere, silently. None of these are authorization-model objections — Decision 1's admin-inclusion widening and Decision 9's TOPIC-002 correction are both well-reasoned and I have no objection to either as authorization decisions. My concern is, in the same shape as the sibling review's findings, about controls this design is thin or silent on around those decisions.

---

### Finding 1 (Medium) — The timing-floor requirement is stated explicitly for TOPIC-004 but never stated for TOPIC-002, which shares the same new authorization function

Decision 2's amendment is explicit and unambiguous: "every early-return in this cascade... calls `applyTimingFloor(startTime)` immediately before responding, with no branch exempted." `specs/remove-topic/spec.md`'s check-ordering requirement restates this as a `SHALL`. Good — this closes the sibling review's Finding 1 for the endpoint it was raised against.

But `checkStandingFacilitatorOrAdminAuthorization` is a *shared* function, reused by TOPIC-002 (`content.ts`) per Decision 1's and Decision 9's own text. I read every mention of "timing floor" in `design.md`, both spec deltas, and `tasks.md`. Decision 2's amendment is titled and scoped to "TOPIC-004's cascade." Decision 9 — the decision that actually defines TOPIC-002's authorization — does not mention timing at all. `specs/topic-customization-lock/spec.md`'s TOPIC-002 requirement and its four scenarios describe only status codes, never response latency. `tasks.md` Task 7.1 (the TOPIC-002 implementation task) does not mention `applyTimingFloor`. The only place in the entire artifact set that requires it for TOPIC-002 is Task 11.2's verification line, which happens to include "Section 7" in its parenthetical scope — a single incidental mention in a checklist item, not a stated requirement anywhere a reader would look first.

This matters because `content.ts` is not a blank file the way `topics.ts` was when the sibling review raised this — it is the file that already contains `denyNullGrant`, which embeds `applyTimingFloor` *inside itself* specifically "so every null-grant path has a single, consistent timing floor call site" (its own comment, `content.ts:193`), and `TOPIC-001`'s handler, which calls the floor on literally every branch including the admin-denial branch. TOPIC-002 will sit in the same file, next to a function that already demonstrates the discipline this design needs and doesn't state. Leaving it to Task 11.2 to catch at verification time, instead of specifying it at design time the way Decision 2 does for TOPIC-004, is exactly the gap the sibling review's Finding 1 already described once: relying on "should be fast by construction" instead of a written requirement.

**Recommendation:** State explicitly, either in Decision 9 or as its own line, that `checkStandingFacilitatorOrAdminAuthorization` embeds `applyTimingFloor` internally before sending either `403` response — matching `denyNullGrant`'s and TOPIC-003's existing `checkStandingFacilitatorAuthorization`'s self-contained pattern (function owns `reply` + `startTime`, callers don't have to remember to add the floor themselves). Making this true "by construction" in the shared function, rather than "by discipline" at two independent call sites in two different route files, is also the more reliable fix — it removes the choice entirely rather than asking both `topics.ts` and `content.ts` to each separately remember it. Add a scenario to `specs/topic-customization-lock/spec.md` asserting TOPIC-002's `403` is not detectably faster than its `200`, mirroring the existing timing-oracle test pattern.

### Finding 2 (Medium) — `archivedBy` is a new category of disclosure this feature area hasn't had before: one specific user's identity, exposed to a population with no prior relationship to that user or the team

Decision 6 and `specs/topic-customization-lock/spec.md`'s provenance requirement both frame `archivedBy` as answering a continuity question for the facilitator who inherits a team — a reasonable UX motivation, and I have no objection to the *column* (a first-class `archived_by` field is architecturally the right call over an audit-log read path, for exactly the reasons Decision 6 gives).

What isn't named as its own decision is who that provenance is disclosed *to*. Under Decision 9's standing, org-wide model, TOPIC-002's caller population is: any facilitator who is *not* an active member of the target team, or any `application_admin`. That is, by construction, every facilitator in the organization relative to any given team except that team's own members — a population with, per this design's own repeated framing elsewhere (Decision 6's "Why," citing Priya's review), *no prior relationship to the team at all*. `archivedBy` now surfaces a specific named colleague's identity (`userId` + `displayName`) — not a role, not an aggregate, a specific person — to every member of that population, for an action that colleague took on a team they may have no connection to either.

This is a materially different disclosure shape than anything else this feature area has shipped. TOPIC-001/002/003's existing surfaces disclose *topic content* (prompts, vote types) under the same broad population — a defensible call, since topic content isn't personal data about a specific individual. `MemberManagement.tsx` does disclose member names, but only to a team's own facilitator, about that team's own members — a bounded, relationship-gated disclosure, not an org-wide one. `archivedBy` is the first place in this design where a *specific person's identity* crosses the org-wide-facilitator boundary with zero relationship gating on either side (neither the viewer nor the archiving facilitator needs any connection to the team, or to each other). I'm not asserting this is wrong — display names are already visible facilitator-wide in other bounded contexts, and the actor here already had to be a standing facilitator to produce the data being viewed — but it's a new boundary crossing, and neither `design.md` nor either spec delta states it as a considered decision the way Decision 9 states the authorization widening itself. It reads as an emergent side effect of composing Decision 6 (provenance) with Decision 9 (org-wide read access) rather than a reasoned disclosure choice.

**Recommendation:** Add a short, explicit decision (or extend Decision 6's "Why") stating that `archivedBy`'s disclosure to the full org-wide-facilitator-or-admin population is an accepted, considered choice — not an emergent one — with the one-line reason (e.g., "facilitator display names are not treated as sensitive within the facilitator population; the standing model already treats every facilitator as trusted with any team's topic configuration, and a name is a strict subset of what TOPIC-002 already discloses"). If that reasoning doesn't hold once written down, this is the moment to catch it, not after the screen ships and a facilitator asks why they can see who on another team's roster archived something.

### Finding 3 (Low-Medium) — The last-active-topic guard's `409` denial is deliberately, silently never audited, on the same wide caller population the sibling review already flagged for a rate-limit conversation

`specs/remove-topic/spec.md`'s own scenario states it plainly: "A rejected request other than a lock denial writes no archive audit row" — explicitly covering the `TOPIC_LAST_ACTIVE` rejection. This is consistent with TOPIC-003's existing convention (identity/role `403`s aren't audited either), so it isn't a regression this design introduces on its own terms. But it's worth naming for the record, the same way this design already names other inherited gaps explicitly rather than leaving them implicit (Decision 8's scope note, Finding 5 below): the last-active-topic guard is a data-integrity control, reachable by exactly the caller population — any standing facilitator, org-wide, no team relationship required, now with `application_admin` added on top — that the sibling review's Finding 4 already flagged as the widest of any write endpoint reviewed to date and asked for an explicit rate-limit/audit decision on. This codebase's own established convention (`team.role_change_denied`'s precedent, cited in `audit-logger.ts`) is that "a blocked attempt on a privileged boundary is itself a security-relevant fact" worth a durable row. A repeated, scripted attempt to strip a team down to its last topic (whether from a compromised standing-facilitator credential or a buggy client retry loop) would today leave no trace beyond application logs — no `audit_log` row, and (per Finding 4, still apparently unresolved — see Finding 4 below) no rate limit either.

I'm not asking this change to add a new audited event for every state-precondition failure (that would be a much larger, unjustified expansion, e.g. `TOPIC_ALREADY_ARCHIVED` genuinely doesn't need one). I'm asking specifically about `TOPIC_LAST_ACTIVE`, because it's the one denial in this cascade that represents a blocked attempt to *change team state against a hard integrity rule*, not a caller mistake against already-settled state.

**Recommendation:** Either add an audited event for `TOPIC_LAST_ACTIVE` denials (no schema change needed — the same `audit_log` table Decision 7 already writes to), or add a one-paragraph stated decision explaining why this specific denial is excluded while `topic.write_denied_locked` is not. Silence-by-scenario-text ("this SHALL NOT write a row") is not the same as a reasoned decision on the record, and this design has otherwise been careful to draw that distinction everywhere else (Decision 8's scope note is the model to follow).

### Finding 4 (Low, carried forward) — This design explicitly inherits, rather than re-decides, the sibling review's open rate-limit question — confirm that question was actually closed somewhere, not just carried forward as settled

Task 11.3 states plainly that the denial-path and success-path audit writes "carry no rate limiter or `withTimeout`/`AUDIT_WRITE_TIMEOUT_MS` guard, matching the sibling change's Decision 13 precedent (fail closed, not fail open) — this is inherited, not re-decided, by this change." I have no objection to fail-closed-over-fail-open as the failure-mode choice (that part is a correct, deliberate application of this codebase's established position). What I can't confirm from this design's own artifacts is whether the sibling review's Finding 4 — which asked, in writing, for an explicit accept-or-mitigate decision on rate limiting the lock-denial write, given its org-wide caller population — was ever actually resolved on the record anywhere, as opposed to simply never revisited. TOPIC-004 doesn't just inherit that population; Decision 1 adds `application_admin` on top of it for the write path, and the last-active-topic guard (Finding 3, above) is a second synchronous, unguarded write reachable by the same population. If Finding 4 was never closed out, this design is quietly treating an open question as settled precedent rather than a gap still waiting on a decision.

**Recommendation:** Before this ships, confirm (and cite) where the sibling design's Finding 4 was actually resolved. If it wasn't, that's a pre-existing gap this change doesn't need to fix, but it does need to stop being silently inherited as though it were closed — the same "don't let it be silently rediscovered" standard this design already applies to the `session_topics` gap (Decision 8, Task 11.5) should apply here too.

### Finding 5 (Low, informational) — TOPIC-003's named FR-8.2 gap has no tracked follow-up issue, unlike this design's other deferred gap

Decision 1's Non-Goal and the proposal's "Not touched" list both name TOPIC-003's missing `application_admin` branch clearly and on the record — good, this is exactly the kind of explicit deferral I want to see rather than a silent one. But this design applies a stronger standard to itself for the `session_topics` gap it found while implementing: Task 11.5 explicitly files a tracked GitHub issue before the change is considered done, specifically so the gap isn't "left to be rediscovered." TOPIC-003's FR-8.2 gap gets the same clear naming but not the same tracked-issue discipline — there's no equivalent task committing to file an issue for widening TOPIC-003's authorization. Given this gap is a documented violation of a `[HARD]` BRD requirement (per the sibling review's own Finding 5, which found the Validation Report's "Covered" mark for FR-8.2 doesn't actually cover the admin half), it seems worth the same treatment.

**Recommendation:** Add a task alongside 11.5 filing a tracked issue for extending TOPIC-003 to admit `application_admin`, referencing this design and the sibling review's Finding 5 for context — consistent with the standard this design already holds itself to elsewhere.

### Non-findings — things I checked and are correctly handled

- **Decision 1's admin-inclusion widening does not create an exploitable inconsistency with TOPIC-003's unchanged, narrower model.** I scrutinized this directly, since it was named as a specific thing to check. TOPIC-004 is strictly *additive* relative to TOPIC-003's existing model — it doesn't weaken any check TOPIC-003 already enforces, and TOPIC-003's shipped code is untouched. There is no path by which a caller unauthorized under TOPIC-003's model gains anything from TOPIC-004's broader model; the two endpoints simply serve different, non-overlapping HTTP verbs on the same resource with different (and independently correct) authorization requirements. The result is a confusing *product* inconsistency (an admin sees "Remove" render and can use it, but the design doesn't also fix the parallel "Add" gap) — exactly what Decision 1 names it as — not a security weakness. Declining to bundle an authorization change to already-shipped, already-deployed code into a change scoped to a new endpoint is itself sound security change-management discipline: smaller, independently reviewable authorization changes are safer than bundled ones. My only addition is Finding 5's ask that the deferred half get a tracked issue, not that it be done here.
- **Decision 2's cascade ordering and its leak-prevention reasoning:** internally sound, and correctly extends the sibling design's `403→404→409→422` precedent with the same "reveal nothing about a specific team/topic to a caller not yet entitled to know it" logic, consistently applied to the two new topic-specific checks.
- **Decision 3's advisory-lock concurrency control:** correctly reuses the proven `pg_advisory_xact_lock(hashtext(teamId))` pattern for the identical race shape the sibling design already closed for `displayOrder`, taken before the count read, released automatically on commit/rollback. No new race is introduced.
- **Decision 5's server-side re-derivation on `confirm=true`:** correctly refuses to trust any client-supplied count or list — this is the right instinct and matches this codebase's established position (never let the client assert a fact the server can cheaply re-verify) exactly.
- **Decision 6's `archived_by` column over an audit-log read path:** architecturally correct for the reasons stated (unindexed JSONB, wrong dependency direction, matches `action_items.resolved_in_session_id`'s precedent of first-class columns for product-relevant state). My only addition is Finding 2's disclosure-boundary question, which is about *who sees it*, not *where it's stored*.
- **Decision 7's audit posture for the success path:** correctly matches `session.draft_created`/`team.created_with_session`'s established shape, same transaction as the state transition, no invented per-endpoint operation name for the shared lock-denial event.
- **`evaluateStandingFacilitatorAccess` reuse:** confirmed still fact-only (returns `{ globalRole, isMember }`, no policy decision baked in), unchanged by this design — the policy logic correctly lives only in the new enforcement wrapper, matching the separation TOPIC-003 already established.
- **No SQL injection surface:** all new queries described (topic existence, status, last-active-topic count, open-action-items join, archive `UPDATE`) are parameterized; no string-built SQL anywhere in this design.
- **Migration Plan's no-feature-flag stance:** correctly consistent with this codebase's standing position that data-integrity-adjacent constraints (the last-active-topic block, corrected authorization) are not configurable — matches the sibling design's identical stance.

---

### Summary for the record

Finding 1 (TOPIC-002's timing floor, stated nowhere but a verification checklist line) is the one I'd want closed before this ships — it's the same class of gap the sibling review already raised once for this exact feature area, on the exact same shared authorization function's other call site. Finding 2 (the `archivedBy` disclosure boundary) I'd like an explicit decision on, one way or the other, rather than left as an emergent property of composing two otherwise-sound decisions — consistent with how this design already handles its own residual risks elsewhere. Finding 3 and Finding 4 are worth resolving on the record but wouldn't block me on their own. Finding 5 is a process ask, mirroring the standard this design already applies to itself.

None of these findings reopen Decision 1, Decision 3, Decision 6, or Decision 9 as authorization or architecture choices — I checked the specific question I was asked to scrutinize (mixing two authorization models across sibling write endpoints) directly and found it sound, not exploitable, and reasonably deferred. My concern, in the same shape as my review of this feature area's first change, is that the caller population these decisions correctly grant standing, org-wide access to is exactly what makes the controls *around* those decisions — timing discipline, audit coverage, and now a new identity-disclosure boundary — matter more here than they would on a narrower endpoint.
