## Context

The TOPIC-002 handler's `!decision.authorized` branch (`routes/content.ts`) runs the #264 denial audit step, emits the event, applies the timing floor, then sends an inline 403 body: `category`, `message` (chosen by a ternary on `decision.reason`) and `correlationId`. `decision.reason` is already typed to exactly `NOT_A_FACILITATOR | FACILITATOR_IS_TEAM_MEMBER` and is already the audit `metadata.reason`. TOPIC-003..006 in `topics.ts` already send `buildErrorEnvelope("forbidden", message, decision.reason)`. This change gives TOPIC-002 the same shape.

## Goals / Non-Goals

Goals: machine-readable reason on TOPIC-002's two 403s; nothing else observable moves. Non-goals are in the proposal (TOPIC-001, correlation id, frontend, shared type, other 403 sites).

## Decisions

### D1. Reuse the existing two codes, sourced from `decision.reason`
Same reason, same code, as TOPIC-003..006. The body becomes `buildErrorEnvelope("forbidden", message, decision.reason)`. The message ternary stays as is, with byte-identical strings. There is no parallel mapping from reason to code, so code and audit `metadata.reason` share one source. The message ternary remains and is the only branch on reason; code is never derived from message. Alternative rejected: a compile-time exhaustiveness check on reason (restructures the branch, widens the diff). Security review (S4) mildly prefers a stronger guard than reviewer memory; the compromise inside this change's scope is a test, not a restructure: the exactly-two-codes test (D5) fails if a third code ever becomes observable, and its failure message says that a new reason is a disclosure decision that needs Security review. A third reason also breaks the local `Topic002DenialReason` type at compile time through `runDenialAuditStep`, an incidental guard, so the residual risk is small. Not adding a compile-time guard to the response path is deliberate: it would widen the diff to the branch structure and the shared helper, and can be revisited if a third reason is ever proposed. Alternative rejected: a new TOPIC-002-specific code or an EM-specific code; both fragment the vocabulary or disclose role more precisely. No code may distinguish an engineering-manager or application-admin denial without Security review; the global engineering manager keeps `NOT_A_FACILITATOR` on purpose so that role is not revealed (this rule is also written into the REST API Contract text, D6).

### D2. Envelope built at the send site; order untouched
The envelope (a `crypto.randomUUID()` and an object) is built where the body is built today, after the floor. The documented order insert, event, floor, send is unchanged, and the audit insert never sits between floor and send. `noStore(reply)` stays explicit. Alternative rejected: build the envelope first to share its correlation id with the audit (see D3).

### D3. Correlation id out of scope
Linking the response `correlationId` to the audit would require a key in the durable row `metadata` (reopens #264's pinned row shape) or in the event payload (changes event assertions). Both contradict "no audit-row behaviour changes". Recorded as a decision, with a follow-up for the event-only variant. Consequence, stated plainly (Security S2): the response `correlationId` on this 403 is generated per response and is not recorded in the audit row or the event, so it is not searchable in logs or audit. Support finds a denial by user, team, endpoint and time, not by quoting the id. This is not a regression (the inline body has the same property today). The contract text says so (D6), so nobody treats the id as a lookup key. Security has a standing request for the event-only variant if TOPIC-002 denials are ever alerted on.

### D4. Key order and the baseline fixture
`buildErrorEnvelope` emits `category, code, field, message, correlationId`; with no field, `code` lands between `category` and `message`. The #264 test compares the whole body string to a committed fixture, so the fixture must change. This deliberately breaks two #264 invariants: the `_comment` in the fixture and the comment block above the baseline `describe` both say it is never regenerated or edited. The change therefore:
- Hand-edits the two bodies, inserting `\"code\":\"<REASON>\",` after `category`. It is not regenerated by running the handler, which would make the test circular; a hand edit keeps the fixture an independent statement of the contract.
- Updates the fixture `_comment` and the describe-block comment to record that #263 deliberately added the `code` member and why, so the file does not contradict its own header.
- Accepts that the fixture is no longer a pre-change baseline. The `describe` title keeps the word "baseline" on purpose (renaming widens the test diff); the comments say what it now is. The real regression guard is `status`, `contentType`, message and every other byte, and the proof is a diff of exactly two insertions.
Key order is incidental to the JSON contract and only the fixture pins it.

### D5. Tests
In `content.test.ts`, additions only; no existing assertion is edited or removed. `expectBaseline403` is a shared helper used by the audit-row, audit-failure, timeout, event and `CASES`-table tests, so the fixture edit (D4) alone turns all of them green or red together. That covers AC 4 for free, and those blocks get no per-case `error.code` assertions added: duplicating them would drift. New code assertions live only in the one new parametrised block below. Updating the fixture is not a loosened test.
- Parametrised by reusing the existing `CASES` table (no fourth table). Its rows are global engineering manager with `isMember: true` (proves the EM keeps `NOT_A_FACILITATOR` even as a member), caller with no facilitator role, and facilitator who is an active member: `status` 403, `content-type`, `Cache-Control: no-store`, `error.category`, `error.code`, exact `error.message`.
- Test title `returning facilitator who is a member of the team gets FACILITATOR_IS_TEAM_MEMBER`.
- `error.code` equals the audit row `metadata.reason` for both reasons.
- Audit failure: with the denial insert rejected (and separately timed out), the 403 still carries the code and equals the snapshot. This is current fail-open behaviour (#264 D3, `runDenialAuditStep` wraps only the insert); the test pins it, the handler does not change it.
- Exactly-two-codes test: normalise `correlationId` by regex in each response body, then compare against the fixture strings (not against each other, so it cannot pass vacuously if both reasons collapse to one body). Assert the set of distinct bodies has size 2 and each equals one fixture body, and that the set of observable `error.code` values equals `{NOT_A_FACILITATOR, FACILITATOR_IS_TEAM_MEMBER}`. The failure message states: "A new or different TOPIC-002 denial code is a disclosure decision; get Security review before changing this test" (Security S4).
- Negative: a spurious header and query parameter leave status, code and message unchanged. Kept because it is cheap; it stays one test and does not grow into a probe-surface framework.
- Participant on an existing and a non-existent canonical UUID get the same `NOT_A_FACILITATOR` body (authorization precedes the team lookup; the 404 `TEAM_NOT_FOUND` of #265 is only for authorized callers). In the SQL-router mock the 403 branch runs before any `teams` read, so a mocked test is a near-tautology; this assertion belongs in the real-Postgres integration test that #264 mandates, and the mocked file keeps only the existing "no `teams` query" assertion. If no such integration case exists yet, add it there rather than in `content.test.ts`.
- Admin 200 body has no `code` member.
- Facilitator whose membership was removed is not blocked (200): already covered by the existing helper tests; point the spec scenario at them and add no duplicate.
- Timing (Security S5): the existing 403-versus-200 timing test and the floor assertions run through the same `CASES` rows, so they cover both reasons. Task 1.6 confirms this still holds after the change; no new timing test unless that confirmation fails. The envelope is built after the floor, costs the same for both reasons, and no differential between the reasons is introduced.
Template and archived teams: the 403 branch runs before any `teams` read, so they get the same two codes by the same decision; no separate case.

### D6. Documentation is part of the contract
The sentence "Reason names are internal labels" in `topic-customization-lock/spec.md` and in the REST API Contract becomes false and is replaced. The contract's TOPIC-002 error table lists both codes and states: clients MUST NOT use `error.code` to grant, unlock or hide an access decision; clients MAY use it to choose display text; an unknown code falls back to `error.message`; the server is the sole authority. The Code column on the TOPIC-002 403 rows gives code, message and trigger. The sentence that the two messages "differ only in `error.message`" is also removed. Edits are limited to these now-false sentences, plus two additions that Security asked to be in the contract text rather than only in the proposal: (a) "No code may distinguish an engineering-manager or application-admin denial without Security review", placed next to the MUST NOT sentence; (b) "`error.correlationId` on this 403 is generated per response and is not currently recorded in the audit row or the event, so it is not searchable" (D3).

## Risks / Trade-offs

- Denial audit is fail-open (#264 D3), and this change pins that in tests without changing it. Rationale (Security S1): a denial reveals only a self-referential bit about the caller; the structured event still records `rowWritten`, so a failed insert is visible in logs; and grants fail closed (the admin arm) while denials fail open. An attacker who can induce audit-table failures could probe unaudited, which is accepted for a read-only list. Compensating control, recorded as an optional operations follow-up: alert on the rate of `rowWritten: false`.
- Strings drift between backend, docs and a future frontend. Mitigated by D1 (one source) and the parametrised test.
- A client treats the code as an authorization input. Mitigated by the MUST NOT sentence in D6.
- A later sweep "fixes" TOPIC-001 or the other 403 sites. Mitigated by naming them as deliberate non-goals.
- The member message states the rule but not the next step. Accepted: changing it here would break the "message unchanged" guarantee; the follow-up carries it.
- Existing frontend behaviour on a 403 during refresh (does it clear the list?) is not changed here; checked during verification and filed as a bug if it does.

## Migration Plan

None. Additive response member; existing clients ignore it. Roll back by reverting the commit.
