## Context

A team can, in principle, have zero ACTIVE topics (legacy teams created before #175/#215 against an empty template, or data drift). Such a team is deadlocked: `getTopicLockState` stays `first_session` until a first session completes; room open (`POST .../sessions/:id/advance`) snapshots topics and refuses with `409 NO_ACTIVE_TOPICS` on zero; and add, restore, archive and reorder are all lock-gated (`409 TOPIC_CUSTOMIZATION_LOCKED`), administrators included. FR-8.6 [HARD] says the default set must be restorable for any team at any time, so an in-app recovery is required for this state. This change closes FR-8.6 for the zero-active-topics state only; partial restore and "visible" remain open (follow-up issue, proposal Why). Team creation no longer produces such teams (#175/#215: copy defaults, `snapshotSessionTopics` throws `NoActiveTopicsError` on zero, whole transaction rolls back), so the population is expected to be near zero and the design is deliberately small.

Most of what is needed exists: `lockTeamTopics` (the transaction-scoped advisory lock room open also takes), `rejectNonCanonicalTeamId`, `checkWritableTeam` (404 `TEAM_NOT_FOUND`, template 404 plus `topic.write_denied_template`), `enforceTopicWriteRateLimit`, `applyTimingFloor`, and the in-transaction audit insert pattern used by `topic.custom_added`. Three things the first draft called "existing" are not reusable as they stand (engineer design review B1-B3, verified in code), and are work items: `copyCanonicalDefaults` returns `void` (D2a), the TOPIC-002 denial-audit helper is private to `routes/content.ts` and hard-wired to TOPIC-002 (D9), and the `defaultTopicsNotActive` query mishandles an archived and an active row of the same name (D3a). The change is therefore small in surface but not "no refactor": see the time-box in Risks.

## Goals / Non-Goals

Goals: an application admin can, in one click on the existing Topic Management screen, give a zero-active-topic team the canonical default set; the facilitator is told the truth and who to ask; nothing about the customization lock or the ritual constraints moves.

Non-goals: see the proposal (partial top-up, bulk repair, template editing, EM/facilitator trigger, admin directory, notification, undo, any lock-gate change).

## Decisions

### D1. Option B: a dedicated admin-only endpoint, not an opened lock
`POST /api/v1/teams/:teamId/topics/assign-defaults`, 201 `{ topicCount }`. Rejected: opening the lock for admins when active topics are zero (Option C). It changes the semantics of `checkCustomizationLockGate` across four endpoints, and "add a custom topic" is the wrong fix, since the first session is supposed to run the canonical set. Rejected: documentation only (Option A), because FR-8.6 stays unmet and the recovery stays a hand-run DB fix, which is what the issue objects to. Rejected: a backfill job (Option D) unless the diagnostic query finds rows, and then it is a one-off script. Name `assign-defaults` over `restore-defaults`: it matches the button and the audit operation, and "restore" already means the per-topic `.../:topicId/restore`.

### D2. Check order, and where the lock exception sits
1. Non-canonical team id (404), lowercase the id. 2. Authorization: the caller's role is read **live from the `users` row at request time** (the same DB read the sibling topic-write authorization and `/advance` use; never a role cached in the session or a token claim, so a demoted or deprovisioned admin loses the carve-out on the next call; a missing user row is a non-admin), and must be `application_admin`, else 403 `NOT_AN_ADMIN` plus the bounded fail-open `topic.defaults_assign_denied` audit row (D9; same envelope and vocabulary shape as #263's `NOT_A_FACILITATOR` / `FACILITATOR_IS_TEAM_MEMBER`). The admin test is one exported predicate, `isApplicationAdmin(role)`, used by this endpoint and by the `canAssignDefaults` flag (D6). This does NOT use `checkStandingFacilitatorOrAdminAuthorization`: a facilitator must not do this. 3. Shared rate limit, after the 403 and before the team lookup, as in #184 (a 403-bound caller never consumes topic-write budget). Note, as the siblings do: a `404 TEAM_NOT_FOUND` for an admin on a bogus id has already consumed budget, and `checkWritableTeam` is not deactivated-aware (existing decision 11), so an admin can assign defaults to a deactivated team; both accepted, recorded so a reviewer does not rediscover them. 4. `checkWritableTeam`. 5. No lock gate. 6. In a transaction at the default READ COMMITTED isolation (the code sets none; D3 depends on it): `BEGIN`, `lockTeamTopics` (`pg_advisory_xact_lock`, released at COMMIT or ROLLBACK, so every path below releases it), then the zero-active precondition as a **fresh statement after the lock**. 7. `copyCanonicalDefaults` (D2a); zero inserted rows throws `DefaultTopicsUnavailableError`, rollback, 500 `DEFAULT_TOPICS_UNAVAILABLE`. 8. In-transaction `audit_log` insert (fail-closed: if it fails, rollback and the generic 500, as `topic.custom_added` does), COMMIT, then `emitAuditEvent` wrapped so it can never turn a committed success into a 5xx. 9. 201 with `Cache-Control: no-store`, matching the siblings. `applyTimingFloor` runs on every return (201, 403, 404, 409, 500), not only refusals; `ROLLBACK` and `client.release()` happen in `catch`/`finally` on every early return (the 409 precondition path included).

Any failure other than the empty template (23505 from constraint drift, connection loss, audit insert failure) is answered with a fixed generic 500 with its own code, `ASSIGN_DEFAULTS_FAILED`, and a generic message, the error logged with the correlation id and never formatted into the body, as the room-open and team-create handlers do. It is deliberately a different code from `DEFAULT_TOPICS_UNAVAILABLE` so the "template is empty" copy is never shown for an unrelated fault; the screen's 500 branch keys on the code, and an unknown 500 code gets the generic failure line.

**Request surface.** The route ignores any request body and rejects nothing on it; it reads no query parameter; it never accepts a source team id or template id (the template is always the sentinel constant). A future "copy from team X" is a new endpoint needing its own review.

**CSRF and CORS posture (security I1; checked in `app.ts`).** The session credential is a cookie (`@fastify/session`, `httpOnly`, `sameSite: "strict"`, `secure` in production), so this body-less POST is covered by the app's existing posture rather than a new control: `sameSite=strict` keeps the cookie off cross-site requests, and `@fastify/cors` is registered with an explicit single-origin allowlist (`getAllowedOrigins()`, `APP_ORIGIN` mandatory in production) with `credentials: true`, so no other origin can make a credentialed call and read the result. No route-specific CSRF token is added; this matches every other cookie-authenticated write in the app. The residual risk is the app-wide one (a same-site compromise, a wildcard `APP_ORIGIN` misconfiguration), not specific to this route. Task 1.1 re-confirms the registration and that the new route is not on any CORS exception.

**Principal-trust note.** `actor_ip` on the audit rows is only as trustworthy as the deployment's `trust proxy` configuration (pre-existing, app-wide); because the row now attributes a lock bypass, the pre-production checklist for this endpoint lists it.

The lock exception is justified by the precondition, not by the caller. A zero-active-topic team has no first-session-eligible configuration, so assigning the canonical set restores the invariant the lock exists to protect. The endpoint can only ever write the canonical set, so it cannot become a customization route. After the call the team is still `first_session`-locked. The lock use case's "no bypass or override mechanism" line is amended to name this carve-out so nobody reads a contradiction.

### D2a. `copyCanonicalDefaults` returns the inserted ids (engineer B1)
The function is `Promise<void>` (plain `INSERT ... SELECT`, no `RETURNING`) because team creation never needed a count; `snapshotSessionTopics` catches the empty case later. Recommended default (needs ratification, item 8): add `RETURNING id` and return the ids (`Promise<string[]>`), so `topicCount = ids.length` is exactly what was written and the audit `topic_count` cannot disagree with it, with no second query. The change is backward compatible: `POST /api/v1/teams` (facilitator-sessions.ts:705) ignores the return value and its behavior is unchanged (still relies on the snapshot to reject an empty copy), and its existing tests must stay green. `NoActiveTopicsError(sessionId)` formats a session message and takes a session id; it is not reused. A sibling `DefaultTopicsUnavailableError` (no argument, no session or team id in the message) is thrown by the new handler when `ids.length === 0`. The handler's transaction body may live in a small service module under `sessions/` so the route stays a thin cascade; the route handler itself stays in `routes/topics.ts` so the template-guard and lock-gate source tests (which scan that file) remain meaningful.

### D3. The precondition lives inside the transaction, under the topic lock
Checking zero-active outside the lock would race. The racers are other assign calls and room open, and the topic advisory lock serializes both. Add/restore cannot race with this at all, because the lock gate blocks them for a locked team (and for an unlocked zero-topic team, they are the normal path, so the endpoint's 409 is correct there). Two simultaneous assign calls: the second waits on the advisory lock, then sees active topics and returns 409 `TEAM_HAS_ACTIVE_TOPICS`. This holds only because the lock is `pg_advisory_xact_lock` (transaction-scoped, released on the 409 and 500 rollback paths, so it cannot leak on a pooled connection and block room open) and the zero-active count is a new statement after the lock under READ COMMITTED (it sees the other transaction's committed rows; under REPEATABLE READ it could be stale). Both facts are asserted by the real-Postgres two-connection test (task 3.4), which also proves the other racer that matters to the user: an `/advance` blocked behind the assign lock then snapshots the newly assigned rows. Advisory key collisions between two teams cost latency, not correctness; noted, not engineered for. "The template" is read by the single copy statement inside the transaction: a concurrent template edit yields the old or the new set, never a mix; the lock is the team's, not the template's. This is both the idempotency rule and the safety rule: a double click, a second admin and a stale button all land on 409 with no state change. Drop any add/restore race test; the observable requirement is one 201, one 409, exact template count, no duplicate `display_order`.

"Zero active", not "zero rows". The unique index on `(team_id, display_order)` (migration 18) constrains active rows only, so existing archived rows cannot collide with the renumbered copy. Archived rows are left alone; an active/archived pair with the same text is acceptable (archive is history, the active row is canonical), provided D3a holds. A team with some but not all defaults is not in scope (a policy question: deliberately archived or renamed topics).

### D3a. `defaultTopicsNotActive` must not list a default as restorable when an active copy exists (engineer B3)
Verified in `routes/content.ts`: the query is `FROM topics dt LEFT JOIN topics t ON t.team_id = $1 AND t.name = dt.name WHERE <canonical predicate> ORDER BY dt.display_order`, and the handler then filters `team_topic_status !== 'active'`. With an archived "X" and an active "X" the join yields two rows for default X; the active one is filtered out, the archived survives, and the screen lists X as a restorable archived default although an active X exists. This is reachable by exactly this feature's population (a zero-active team with archived rows, after assignment). It is also a pre-existing latent defect (any team that archived a default and re-added the same name), so the fix is not feature-specific. Further, restore (TOPIC-005, `routes/topics.ts`) updates by id with no name-collision check and `topics` has no unique constraint on name, so acting on the stale listing would create two active topics of the same name. Resolution, a small fix, not a redesign: change the query to one row per default, preferring an active match, e.g. `LEFT JOIN LATERAL (SELECT id, status FROM topics WHERE team_id = $1 AND name = dt.name ORDER BY (status = 'active') DESC, id LIMIT 1) t ON true`. Tasks: 2.6 (test first: zero-active team with an archived default, assign, GET all, assert `defaultTopicsNotActive` is empty and a partially-active team lists only genuinely absent defaults). Scope: one query and its test, about an hour. Out of scope and recorded as a follow-up observation: the plain archived list can still offer Restore on an archived "X" next to an active "X" (restore has no collision check); that is existing TOPIC-005 behavior, not widened by this change, and is filed with the FR-8.6 residual (task 8.4).

### D4. Machine-readable codes, and what stays out of the body
`NOT_AN_ADMIN` (403), `TEAM_HAS_ACTIVE_TOPICS` (409), `DEFAULT_TOPICS_UNAVAILABLE` (500, empty template), `ASSIGN_DEFAULTS_FAILED` (500, any other fault, generic message), `TEAM_NOT_FOUND` (404, existing). The template-team 404 and the missing-team 404 are the same response by design (existing template guard), so an admin cannot tell them apart. Empty template: the caller is an authenticated admin who can act on it, so the 500 gets its own code and a sentence (settled string in the specs, which names the runbook section "Zero-topic teams" rather than a vague operator) instead of the generic message team creation uses; no template id, which goes to `request.log.error` with the correlation id. The empty-template 500 gets a durable record (security S4): after `ROLLBACK`, the handler writes one **fail-open** `audit_log` row, `topic.defaults_assign_failed`, `metadata = { endpoint, http_status: 500, reason: "DEFAULT_TOPICS_UNAVAILABLE", correlation_id }` (no template id, no topic text), through the same parameterized fail-open helper that D9 extracts for the denial row, so this is not a new audit pattern, only a third caller of it (a try/swallow insert independent of the main outcome that emits the log-only `topic.audit_write_failed` on failure). The row is written after the rollback, on a separate statement on the pool, so it survives the rollback. Volume is not a concern (rare, admin-only; also bounded by the topic-write limiter). The error-level `request.log.error` line with the template id and correlation id stays as well, and the correlation id joins the log line to the audit row. This closes the gap that #175 accepted for team creation, for this endpoint only (team creation is unchanged); ratification item 4 is therefore reframed from "accept a gap" to "confirm the fail-open row is sufficient" and compliance still records a response. If the helper extraction (B2) is cut, fall back to the log-only record and the runbook search (the security-sanctioned alternative) and revert item 4 to the original wording.

### D5. Audit
New operation `topic.defaults_assigned`, metadata `{ topic_count, correlation_id }` only (counts and the request correlation id; never text, topic ids or template id), same transaction as the inserts, `emitAuditEvent` after COMMIT. `correlation_id` is the request id (`request.id`) on the success row, and the response envelope's `correlationId` on the failure and denial rows, so an audit row can be joined to the request log. The row carries `actor_user_id`, `actor_global_role` (`application_admin`), `actor_ip` and `team_id` (the "who did this" columns the runbook relies on). Second and third new operations: `topic.defaults_assign_denied` for the 403 (D9) and `topic.defaults_assign_failed` for the empty-template 500 (D4). All three are registered in `auth/audit-logger.ts`. **The `audit_log` row is the system of record; the `emitAuditEvent` structured event is a convenience notification** (a crash between COMMIT and emit loses the event, never the row). Retention for all three operations is the audit-log retention policy, stated in the runbook; a future bulk-repair script under `migrations-manual/` must apply the same zero-active precondition and write one row per team with the same operation name and an actor value that identifies the operator. Template refusal reuses `topic.write_denied_template` with `attempted_operation = 'topic.defaults_assigned'`; the template guard source test is extended to the new route. `audit_log.operation` is `TEXT NOT NULL` with no CHECK and `team_id` has no foreign key (migration 8), so no migration; task 1.1 re-confirms against the full migration set.

### D6. TOPIC-002 `canAssignDefaults`, fail-closed
Computed in the TOPIC-002 handler: `isApplicationAdmin(role)` (the same exported predicate as the endpoint's authorization, so no two expressions are kept in step by a parity test alone; the `topic-add-flag-parity.test.ts` pattern is applied to confirm it) AND zero active topics AND not the template team. The flag is UX only: no server code reads it back from a client, and a spoofed `canAssignDefaults: true` in a hand-built request changes nothing, because the endpoint authorizes independently (test: non-admin still gets 403). In the shared type the field is required (`canAssignDefaults: boolean`) so the backend cannot forget it; the frontend reads `=== true` as it does `canAddTopics`. Not dependent on the lock (the screen picks the control from the lock state). Treated by the frontend exactly like `canAddTopics`: missing or false renders no button. Truth table, (admin, zero active, template team) to flag: (yes, yes, no) is true; the other seven rows are false or absent. One table-driven test covers all eight rows, plus flag-absent on the frontend and parity with the endpoint's authorization. An unlocked zero-topic team still reports true for an admin; the screen shows the Add control there, not the Assign button. `activeResult` and `decision.actorGlobalRole` are already in the handler's scope and `isTemplateTeam` is already imported via `topic-lock-state`, so no extra query is needed (verified).

### D7. Copy, and why H1 is loosened here only
The existing screen rule forbade naming "an application role" because the vague "the people who run this application" had become an escalation magnet; the loosening to "an application administrator" for the locked zero-topic variants (the screen empty state and the room-open message) is deliberate: a named role is something an engineer can go and find. It is not loosened anywhere else. Not added: a "who are the admins" display (turns the application into a directory), a facilitator-facing line on the session draft page (persistent chrome for a rare state; the room-open message and the intact draft already cost one retry, not a lost session), polling or push (the server decides at open time, so staleness cannot cause a wrong action), a confirmation dialog on the button (additive, refuses on non-empty), a separate 409 notice (the refetched list is the message), any outcome copy beyond: success count line, template-empty line, and the existing generic failure line. Success count line is `{n} default topic(s) assigned.` built from the response `topicCount` (singular for 1), never a literal 12; #291 exists to stop template-size drift in copy. Accessibility: success in a status region, failures in an alert region, focus to the Active Topics heading after 201, in-flight state exposed on the button.

Frontend structure (engineer S5): `ActiveTopicsEmptyState` stays presentational. It gains **required** props `canAssign`, `assigning` and `onAssign` (required, like `addAllowed`, so a forgotten call site is a type error). The in-flight state, the status and alert regions, the outcome message and the focus move live in `TopicManagementPage` state, because the empty-state component unmounts on the refetch and would lose the success line. Assign is shown only when `isCustomizationLocked && canAssignDefaults === true`; `activeEmptyStateVariant(locked, archivedCount, ...)` in `pages/addCustomTopic.ts` is the single place that decides, and its full (locked, canAssign, canAdd, archivedCount) matrix is unit-tested there rather than in the component. Busy gating: Assign is blocked by the same states that block Add (`addSubmitBlockedReason`: an open annotation or archived-view dialog, any in-flight write); a dirty reorder is impossible with zero active topics.

### D8. Room-open message selection
The `409 NO_ACTIVE_TOPICS` branch keeps the code and the draft-stays-draft behaviour and picks one of two messages by lock state: locked-and-zero gets the "ask an application administrator" message, unlocked keeps the original. The lock read is `hasCompletedFirstSession`/`getTopicLockState`. Correction to the first draft (engineer S1): these query through the pool (`db.query`), not the transaction client, so they are not "in the same transaction"; calling them mid-transaction would take a second connection while one is checked out and the advisory lock is held. The read therefore happens **after `ROLLBACK`, inside the `NoActiveTopicsError` branch only**, and is advisory: session completion does not take the topic lock, and a stale message costs one extra retry at worst (the decision itself, the 409, is unaffected). `topic-lock-helper` is mocked as a whole module in the advance tests; the new tests plan for that. There is no caller-role branch and no admin variant: `/advance` requires the caller's live `users.global_role` to be `facilitator` (facilitator-sessions.ts), and the role map gives a user with both claims `application_admin` (precedence, #243; use case 01c), so an admin can never reach this branch. The earlier three-message design was dead copy and is dropped; do not widen roles to make it reachable.

### D9. Non-admin 403 and audit
Checked in code (not assumed). TOPIC-003..006 (the sibling writes) write no `audit_log` row for their 403s; they audit only the lock and template denials. TOPIC-002 (#264) does: one `topic.config_list_denied` row per 403, fail-open (the insert is wrapped so a failure never changes the response; a log-only `topic.audit_write_failed` is emitted instead). Decision: this endpoint follows TOPIC-002 (ratification item 5; security has confirmed it with the bound below). It bypasses the lock, so an attempt by a non-admin is the more interesting signal.

**Helper extraction (engineer B2, verified).** In `routes/content.ts` the helper is private and hard-wired: `insertTopic002DenialAuditRow`, `runDenialAuditStep`, `TOPIC_002_DENIAL_INSERT_SQL`, `TOPIC_002_DENIAL_OPERATION`, `TOPIC_002_ENDPOINT` and the `Topic002DenialReason` union are module-private, and the `topic.audit_write_failed` event carries TOPIC-002's endpoint and operation constants. It cannot be imported into `routes/topics.ts`, and a copy would be the fork of SQL cast rules the first draft forbade. Recommended default (needs ratification, item 5): extract a small parameterized helper into `auth/` beside `fail-open-audit-write.ts` (inputs: operation, endpoint, reason, optional extra metadata keys; it keeps the explicit `::uuid/::text/::inet/::jsonb` casts, the `LEFT JOIN users` read of `actor_roles` inside the insert, the `AUDIT_WRITE_TIMEOUT_MS` bound, and the `topic.audit_write_failed` emission parameterized by operation and endpoint). TOPIC-002 is refactored to call it with its own constants and its metadata byte-for-byte unchanged (`{ endpoint, http_status: 403, reason }`); the existing TOPIC-002 denial tests are the regression net and must stay green untouched, and the real-Postgres cast test covers both callers. This touches shipped, security-reviewed #264 code; it is budgeted in the time-box. The new row also takes `actor_roles` (the "who did this" runbook query may want it), at no extra cost because it is read inside the same insert. The same helper writes the D4 empty-template failure row. Fallback if cut: drop the 403 audit for this endpoint and follow TOPIC-003..006 (reverses item 5; a PO call) and use the log-only record for the 500.

**Bounding denial writes (security S3, condition).** The first draft wrote the denial row before the topic-write limiter so a 403-bound caller consumes no write budget, and accepted that any authenticated non-admin could then insert unlimited `audit_log` rows with an attacker-chosen `team_id` (no foreign key), flooding the table and burying a real probe. "Same as TOPIC-002" is not accepted as the answer on the more sensitive endpoint. Recommended default (needs ratification, item 5): a **separate per-actor limiter on the denial-audit write only**, using the existing sliding-window primitive (`auth/sliding-window-limiter.ts`, Redis, a distinct key namespace such as `dipstick:ratelimit:topic-denial-audit:{userId}`), with a generous bound of 10 denial rows per actor per minute (a probing actor beyond that still gets the 403, but no row; a log-only counter event `topic.denial_audit_suppressed`, with the actor, endpoint and count, is emitted, once per window to avoid recreating the flood in logs). This keeps the D9 intent (a 403 caller never touches the main topic-write budget) and bounds table growth to a known ceiling. If the limiter store errors, the denial row is skipped and a log-only event is emitted (best-effort audit, never a changed response). The limiter is a parameter of the extracted helper: enabled for the new endpoint now; TOPIC-002 adoption is a recorded follow-up (changing shipped behavior of #264 beyond the refactor is not done silently here) and is called out in the security threat-model update. The denial row can only be written after authentication (401 precedes it, as for TOPIC-002). The ceiling and the retention policy are stated in the runbook so on-call knows the table's worst case.

Operation `topic.defaults_assign_denied`, `metadata = { endpoint, http_status: 403, reason: "NOT_AN_ADMIN", correlation_id }`, actor and `team_id` as supplied (no foreign key, so a nonexistent team is recordable).

**Regression guard (security section 1).** Because the carve-out is permanent, the source test asserting "the four lock-gated endpoints (TOPIC-003, 004, 005, 006) call `checkCustomizationLockGate`, and `assign-defaults` does not" is a permanent test in the suite, not a change-time check. A second invariant test states the chain "from a team with one active topic, no API sequence available to an admin (archive, reassign, edit, delete, restore, reorder, template-team operations) results in zero active topics on a locked team" (`TOPIC_LAST_ACTIVE` plus the lock gate); the test names any path found.

### D10. Existing draft-page copy
The session draft host shows, when `activeTopicCount` is 0: "This team has no active topics. Add or restore a topic on Topic Management before opening the room." with a link to Topic Management. For a LOCKED zero-topic team, "Add or restore" cannot be done by that facilitator, so this text is also misleading. The exploration decided not to add persistent chrome to the prep page, and this change does not reword it (it would need the lock state and viewer role on the draft page). It is recorded as a known gap and a follow-up to file; revisit if the diagnostic query finds real teams. Task 1.5 verifies what the draft host shows and records the result. Accepted by me (Devon) in place of the PO; ratified at PR review. Reopen trigger: a usability-pass participant stumbles on the line, or the diagnostic query finds real teams. Consequence of leaving it: the facilitator learns the correct thing only after clicking Open room once.

## Risks / Trade-offs

- A new lock-bypassing path, however narrow. Mitigations: admin-only by role, structural precondition checked under the topic lock, canonical set only, no flag, audited in the same transaction, template refused, rate limited, and the lock gate code is unchanged.
- The empty-template 500 now writes a fail-open `topic.defaults_assign_failed` row (D4); compliance still records a response (ratification item 4, reframed). Denial-row growth is bounded by the D9 per-actor limiter.
- Template content propagates as-is to a team that did not review it (team creation does the same). The existing escape-at-render control is considered sufficient; security will test it in the pre-production review.
- Refactor risk: extracting the denial-audit helper touches shipped #264 code. Mitigation: TOPIC-002 tests unchanged and green, real-Postgres cast test for both callers.
- The rate limiter's 503 fail-closed means admin recovery is unavailable during a Redis outage (safe side). The runbook's manual DB path is a last resort, not a routine alternative.
- Scope creep. **Time-box, restated honestly: three to four working days** (engineer estimate), not the original two. Added by review: the `copyCanonicalDefaults` return change, the denial-helper extraction with the per-actor bound, the `defaultTopicsNotActive` fix, real-Postgres concurrency and cast tests, five delta specs, the use-case rewrite, the runbook and accessibility work. If it grows past four days, stop and re-scope with the PO. **Cut order if it grows** (the engineer's order, kept): 1) the usability pass (8.3); 2) runbook extras beyond the diagnostic query, audit lookup and empty-template section; 3) the D10 draft-copy check (1.5); 4) then B2 option 2 (drop the 403 audit, which also drops the D9 limiter and falls the 500 audit back to log-only) with PO agreement. Never cut: the endpoint, the flag, the button, the room-open message, the live role read, the lock-and-isolation tests, the B3 query fix. Must not displace onboarding work.
- The stale-button case: handled by 409 (not by polling). A stale facilitator view cannot cause a wrong action.
- Near-zero affected population means the feature may rarely run in production. Accepted: FR-8.6 [HARD] mandates it, and the build is small. The diagnostic query is run first (pre-build, task 1.3) and the count is recorded; it does not gate the endpoint, copy or runbook but decides the optional extras.
- `/start` soft spot: a pre-#175 legacy session sitting in `lobby` with no snapshot can reach `/start`. The one-query check (sessions in `lobby` with no `session_topics` rows) decides whether a guard is built: rows > 0 adds a task for `/start` returning `409 NO_ACTIVE_TOPICS`, 0 closes it (task 1.4). No code change by default.

## Migration Plan

No schema change (audit_log.operation is unconstrained TEXT). Deploy backend and shared types before the frontend: the frontend fails closed on a missing `canAssignDefaults`, so a frontend deployed ahead of its backend shows the non-admin locked message with no button. Rollback: remove the route and the flag; nothing is persisted that needs reverting except audit rows, which are history. Run the diagnostic and `/start` queries against each environment before build and after release and record the counts here.

## Appendix A. Draft use case: Recover Zero-Topic Team

*(For `requirements/use cases/08`; traceable to FR-8.6 [HARD] and FR-8.2, zero-active-topics state only.)*

**Summary.** An Application Administrator gives a team that has no active topics the canonical default topic set, so its facilitator can open a room and complete a first session. The team is otherwise left exactly as it was.

**Actor.** Application Administrator (any membership on the target team, or none, per FR-8.2 / #208).

**Trigger.** A facilitator reports being blocked at room open ("This team has no active topics..."), or the administrator opens Topic Management for a team and sees the locked, zero-topic empty state, or an operator's diagnostic query lists the team.

**Preconditions.** The team exists; it is not the template team; it has zero ACTIVE topics (any number may be archived); the actor's `global_role` is `application_admin`.

**Main flow.**
1. The administrator opens Topic Management for the team and sees "This team has no active topics, so its sessions can't run. Assign the default topics to restore the standard set." with "Assign default topics".
2. The administrator activates the button. No confirmation is asked.
3. The Application, in one transaction under the team's topic lock, re-checks that the team has zero active topics, copies the template's active topics (name, prompt, vote type, description; marked default; numbered 1..n in template order, no annotations), writes one `topic.defaults_assigned` audit row, and commits.
4. The screen refetches and shows the topics and "{n} default topic(s) assigned."
5. The facilitator, told by the administrator or on retry, opens the room from the same draft session; the session snapshots the assigned topics.

**Alternate flows.**
- A. Actor is not an application admin: 403 `NOT_AN_ADMIN`, a denial audit row, nothing changes.
- B. Target is the template team: 404, template-denial audit, never a target.
- C. Team does not exist: 404 `TEAM_NOT_FOUND` (non-admins get 403 first).
- D. Team already has active topics (double click, second admin, stale view): 409 `TEAM_HAS_ACTIVE_TOPICS`, no change; the screen refetches.
- E. The template has no active topics: 500 `DEFAULT_TOPICS_UNAVAILABLE`, rollback, a fail-open `topic.defaults_assign_failed` audit row and a log line; the administrator is pointed at the runbook "Zero-topic teams" section.
- F. Rate limited, or any other failure: the screen's generic failure message; the button stays.
- G. Unlocked zero-topic team: the normal Add / restore path applies; the Assign button is not shown (the endpoint would still accept).

**Postconditions.** Success: the team has the template's current active topics (not the template of its creation date), still `first_session`-locked, zero sessions, indistinguishable from a new team; archived rows unchanged; one audit row. Failure: nothing changed.

**Out of scope.** Any customization; partial top-up for teams with some defaults; notification; undo; a directory of administrators; editing the template.

**Related.** Assign Default Topic Set to New Team; Customization Lock (this is its single exception); FR-8.6, FR-8.2; Remove Topic (the last active topic cannot be archived, `TOPIC_LAST_ACTIVE`, so a zero-topic team arises only from legacy data or a data fault; the "do nothing more" count for the diagnostic query is 0).
