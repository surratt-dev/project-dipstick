# Proposal: zero-topic-team-recovery (#200)

*Framed by Devon Calloway (Internal Champion). Builds on `exploration-notes.md` (revision 2) with `explore-review-ba.md` and `explore-review-facilitator.md`, and revised (revision 2 of this proposal) after `propose-review-ba.md` (Marcus Delgado) and `propose-review-exec.md` (Rachel Okonkwo). Traceability: GitHub issue #200; BRD FR-8.6 [HARD] and FR-8.2; use cases `requirements/use cases/08 - Topic Management - Use Cases.md` (Assign Default Topic Set to New Team; Customization Lock); openspec specs `topic-customization-lock`, `audit-logging-operations`, `topic-management-screen`, `session-creation`, `default-topic-provisioning`. Items marked as my decision were made in place of the product owner, who could not be reached; the PO ratifies at PR review (see "Needs PO/compliance ratification before merge").*

## Why

The issue has two halves. **"Prevent a team being created with zero topics" was already delivered by #175 and #215**: team creation copies the template, and if the copy yields zero rows the whole transaction rolls back, no team or session is created, and the caller gets a fixed 500 with the template id in the log only. Nothing further is needed for that half and this change does not touch it.

The second half is "a documented in-app way to fix" a team that nonetheless has zero active topics, and that is still missing. Such a team is stuck in a deadlock: the customization lock stays on until the team completes a first session, a team with no topics can never open the room (`409 NO_ACTIVE_TOPICS`), so it never completes one, and every topic write is lock-gated for administrators too. Today the only exit is a hand-run database fix. The Topic Management empty state tells the facilitator to "ask the people who run this application for your organization", which is exactly the vague escalation phrase that ends up on my desk.

**What this does and does not close of FR-8.6.** FR-8.6 [HARD] says the canonical default set must be "visible and restorable for any team at any time, regardless of how much the team has customized their topic list." This change closes **only the zero-active-topics state** of that requirement. It does not close: (a) partial restore, meaning a team with some but not all defaults, or one whose defaults were archived and replaced by custom topics (a policy question: teams deliberately archive and rename topics); and (b) "visible", meaning whether the canonical set can be viewed from the Topic Management screen of a customized team. Once a team is unlocked, restoring individual archived defaults through the existing restore action (TOPIC-005) is the partial answer to (a). The residual is recorded as an open requirement gap with follow-up issue #293 (task 8.4; owner: PO; the restore name-collision check is #294) and FR-8.6 is not presented as satisfied by this change.

Why it is worth building even if few teams are affected: FR-8.6 is [HARD], and an unmet hard requirement in one state is a legitimate reason to build for a population that may be zero. The advance handler itself calls the state "unreachable through the API". The build is therefore deliberately small and **time-boxed**: one admin-only endpoint, one button, corrected copy, one half-page runbook section. It must not displace onboarding and first-session friction work, which is what drives adoption. The first estimate of about two working days was optimistic; after design review it is three to four working days (copy-function change, helper extraction, query fix, real-Postgres tests, five delta specs, use case, runbook, accessibility). If it grows beyond four days, stop and re-scope with the PO; the cut order is in design.md Risks (usability pass, runbook extras, draft-copy check, then dropping the 403 audit with PO agreement).

## What Changes

- **New endpoint** `POST /api/v1/teams/:teamId/topics/assign-defaults` (not configurable, no flag). Application admin only. Copies the canonical default set onto a team that has zero ACTIVE topics, in template order, using the existing default-copy routine (changed to return the inserted ids, so the count is exact; team-creation behavior unchanged), under the team topic lock, in one transaction. "The template" means its active topics as read inside that transaction, under the lock; later template edits do not affect an assignment already made.
- **Settled outcomes:**

| Outcome | Status / code | Audit | Notes |
|---|---|---|---|
| Success | 201 `{ topicCount }` | `audit_log` row `topic.defaults_assigned`, metadata `{ topic_count }`, same transaction, plus `emitAuditEvent` after COMMIT | Team stays in `first_session` lock |
| Non-admin | 403 `NOT_AN_ADMIN` | `topic.defaults_assign_denied` row, fail-open and bounded by a per-actor limiter (follows TOPIC-002 / #264; see "Non-admin 403 audit" below) | Role read live from the `users` row; checked before the team lookup, so also 403 for a missing team |
| Template team | 404 | `topic.write_denied_template` (existing) | Never a target, in UI or API |
| Missing team (well-formed id, admin caller) | 404 `TEAM_NOT_FOUND` | None, as siblings | |
| Team has active topics | 409 `TEAM_HAS_ACTIVE_TOPICS` | None (no state change) | |
| Empty template | 500 `DEFAULT_TOPICS_UNAVAILABLE` | Fail-open `topic.defaults_assign_failed` row written after the rollback, plus `request.log.error` (template id in the log, never in the body or the row) | Team creation (#175) keeps its log-only gap; compliance to confirm (ratification item 4) |
| Any other fault | 500 `ASSIGN_DEFAULTS_FAILED` | Log line with correlation id; the in-transaction audit insert is fail-closed, so nothing persists | Generic message; distinct code so the template-empty copy is never shown for an unrelated fault |
| Rate limited | Shared topic-write limit, inherited unchanged: the same 429 (or fail-closed 503 when the limiter store is unavailable) the sibling topic-write endpoints return | As siblings | No new limit values |

- **Non-admin 403 audit (decided).** I read the code. The sibling *write* endpoints (TOPIC-003..006) write no `audit_log` row for their 403s; TOPIC-002, the read endpoint, does (#264: `topic.config_list_denied`, one row per denial, fail-open so a failed insert never changes the 403, with a log-only `topic.audit_write_failed` when the insert fails). The TOPIC-002 pattern is the project's current rule for denial auditing and this endpoint is the one that bypasses the lock, so a denied attempt is more interesting than a denied add-topic. This endpoint therefore follows TOPIC-002: one `topic.defaults_assign_denied` row per `403 NOT_AN_ADMIN`, fail-open, `metadata = { endpoint, http_status: 403, reason: "NOT_AN_ADMIN" }`, actor and `team_id` as supplied (`audit_log.team_id` has no foreign key, so a non-existent team id is recordable). This replaces the earlier "same treatment as siblings" text and the contradiction BA B2 found. The delta spec carries a scenario for it. Security condition S3: because the row is written before the topic-write limiter, the write is bounded by a separate per-actor denial-audit limiter (recommended default 10 rows per actor per minute, then 403 with no row and a log-only suppression event), enabled for this endpoint now and recorded as a follow-up for TOPIC-002. The audit-write helper is extracted from `routes/content.ts` into `auth/` and parameterized so TOPIC-002, this endpoint's denial row and the failure row share one implementation (engineer B2).
- **Defect fixed on the way (engineer B3).** `GET .../topics/all` `defaultTopicsNotActive` lists a default as restorable when an archived and an active row share its name; assigning defaults to a zero-active team with archived rows makes that reachable. The query is fixed to return one row per default, preferring the active one (small, with a test).
- **Security posture stated:** role read live from `users` (revocation is immediate), cookie session with `sameSite=strict` and a single-origin credentialed CORS allowlist (no new CSRF control), request body and query ignored, no source or template override, audit_log is the system of record and the emitted event a convenience, correlation id in audit metadata.
- **Deliberate lock exception.** This endpoint does not run the customization-lock gate. The justification is its precondition (zero active topics), not the caller's role. The lock exists to guarantee "the first session runs the canonical set"; a zero-topic team has no such configuration, so assigning the canonical set restores the invariant. The endpoint can only ever write the canonical set, so it cannot be used to customize. After assignment the team stays locked until its first session completes and behaves exactly like a brand-new team with zero sessions. **The lock has exactly one carve-out.** Any future carve-out requires explicit PO sign-off, and the amended use case and spec Purpose say so.
- **TOPIC-002** (`GET /api/v1/teams/:teamId/topics/all`) gains `canAssignDefaults: boolean`: true only for an application admin, on a team with zero active topics, that is not the template team. Fail-closed: false or absent renders no button. Truth table (admin / zero active topics / template team): true only for (yes, yes, no); the other seven of the 2x2x2 rows are false or absent. The flag does not depend on the lock.
- **Topic Management empty state** (zero active topics) has these variants. Strings are verbatim:
  - Locked, `canAssignDefaults` not true (facilitator or any non-admin): "This team has no active topics, so its sessions can't run. Ask an application administrator to assign the default topics, then refresh this page." No button.
  - Locked, `canAssignDefaults` true (admin): "This team has no active topics, so its sessions can't run. Assign the default topics to restore the standard set." Primary button "Assign default topics". No sentence directing the viewer to ask an administrator.
  - Unlocked variants unchanged (an admin on an unlocked zero-topic team sees the existing "Add custom topic" and, if any, "Show archived topics (n)"; no "Assign default topics" button, because the normal add/restore path is open; the endpoint itself would still accept the call).
  - No confirmation dialog (additive; refuses on a non-empty team).
  - **Outcomes, minimum set.** 201: the screen refetches, the list replaces the empty state, and a status line reads "{n} default topic(s) assigned." with n the real `topicCount` from the response ("1 default topic assigned." / "5 default topics assigned."; never a hardcoded number). 409 `TEAM_HAS_ACTIVE_TOPICS`: refetch only; the list appearing is the message (no separate notice). 500 `DEFAULT_TOPICS_UNAVAILABLE`: "The default topic template is empty or unavailable, so nothing was assigned. An operator needs to fix the default topic template (see "Zero-topic teams" in the deployment runbook, docs/deployment.md), then try again." with the button kept for retry. Every other failure (403, 404, 429, 503, network, timeout): the screen's existing generic write-failure message, the empty state and enabled button retained, nothing lost. A link from the app into the runbook is not possible; naming the runbook section is the accepted limit.
  - **Accessibility.** The success line is in a status (polite live) region and failures in an alert region; after a 201 focus moves to the "Active Topics" heading (the button that had it is gone); while a request is in flight the button is disabled and its accessible name/state says it is assigning. The BRD states no formal accessibility standard; these are the screen's existing conventions.
- **Room-open `409 NO_ACTIVE_TOPICS`** (advance handler) keeps its code; the message is chosen by lock state only:
  - Locked team with zero active topics: "This team has no active topics, so the room can't open yet. Ask an application administrator to assign the default topics, then try again. Your session is saved."
  - Unlocked team: current message unchanged, "Add or restore a topic on Topic Management before opening the room."
  - The failed open leaves the session in `draft`, so the facilitator retries without recreating it: after an admin assigns the defaults, the facilitator's next `/advance` on the same session id returns 200 and the session is `lobby`; no new session row is created and the facilitator performs no step other than clicking Open room again.
  - **No admin variant.** An earlier draft had a third message for an admin caller. It is dead copy: `/advance` requires the caller's live `global_role` to be `facilitator` and the role map resolves a user holding both claims to `application_admin` (precedence, #243; use case 01c), so an admin cannot open a room. Dropped, with its spec scenario and the D8 "wrinkle". (Review disposition BA B3 / Exec 1.)
- **H1 is loosened for the zero-topic locked variants only**: this copy may name "an application administrator". A named role is something an engineer can go and find; the vague phrase has been an escalation magnet. Who knows who the administrators are: administrators are whoever the deployment's OIDC role map (#243) maps to `application_admin`; the application does not list them (no directory, a non-goal), and the usability pass tests exactly this step.
- **Use-case amendments** (`requirements/use cases/08`): new use case **Recover Zero-Topic Team** (drafted in full in design.md Appendix A; traceable to FR-8.6 for the zero-active case only); the Customization Lock out-of-scope "no bypass or override mechanism" line is replaced with: "The lock can be released for a team only by completing a first session, except that an application administrator may assign the canonical default set to a team with zero active topics (see Recover Zero-Topic Team). This does not permit customization. Any further exception requires explicit product owner sign-off."; the Customization Lock "Failure (lock not enforced)" postcondition and the Notes line "The lock is based on session completion" each get a one-line cross-reference to that exception; the Assign Default Topic Set Failure postcondition (stale since #175) is replaced with: "No team or session is created; a team that nonetheless has zero active topics is recovered through Recover Zero-Topic Team." The use case "existing teams retain their assigned configuration" line gets the clarification that a recovered zero-topic team receives the *current* template, not the template of its creation date; that is intended.
- **Spec Purpose wording** (`topic-customization-lock`, applied at sync, task 9.2). Replacement sentence, appended to the Purpose paragraph: "The one exception to the lock is `POST /api/v1/teams/:teamId/topics/assign-defaults`, which lets an application administrator assign the canonical default set to a team with zero active topics; it does not permit customization, and any further exception requires explicit product owner sign-off."
- **Short runbook** (half a page, `docs/deployment.md`, section "Zero-topic teams"): (a) the diagnostic query; (b) how to find `topic.defaults_assigned` (and `topic.defaults_assign_denied`) rows; (c) what to do when the template itself is empty (restore its active default topics in team configuration; the in-app button cannot help).
- **Known gap, not fixed here**: the session draft page's own disabled-state line ("Add or restore a topic on Topic Management...") is misleading for a locked zero-topic team and its facilitator cannot act on it; the correct locked copy is shown only after clicking Open room. Accepted by me (Devon) in place of the PO; ratified at PR review. Reopen trigger: any usability-pass participant stumbles on that line, or the diagnostic query finds real teams. Recorded in design D10 and checked in task 5.4.
- **Pre-build verification (task group 1, before any code)**: run the **diagnostic query** (teams other than the template with no ACTIVE topic) and the **legacy-lobby query for `/start`** and record both counts in this change. Definitions: a *legacy lobby* is a session with status `lobby` and no `session_topics` rows, which can only exist from before the open-room snapshot (#175) was enforced. The conditional guard is: `/start` returns `409 NO_ACTIVE_TOPICS` for a lobby session with an empty snapshot. Decision rule: rows > 0 means the guard is added as a task with a test; 0 rows means record the count and close. The diagnostic count does not change what is built (FR-8.6 [HARD] mandates the endpoint, copy and runbook regardless) but it sets the optional extras: with a count of 0 the usability pass (AC 9) is skipped or deferred and the draft-page copy fix is still made (PO decision at PR review); with rows > 0 a bulk-repair script under `migrations-manual/` is proposed to the PO (not built here) and the draft-page follow-up is raised in priority.

## Ritual constraints preserved

- **No-manager rule.** Untouched. The endpoint writes topics only, never membership or participation. Admin write access regardless of membership is the existing #208 decision (an admin who is on the team, on another team, or on no team is treated identically); this change does not widen it to engineering managers by global role.
- **Facilitator from another team.** Untouched. A facilitator is not an actor here at all: the endpoint is application_admin only, so there is no new path that lets a facilitator, or a same-team facilitator, change topic state.
- **Constraints structural, not configurable.** No flag, no env toggle. The zero-active-topics precondition is structural and checked inside the transaction under the lock; it is the thing that makes the lock exception safe.
- **Template guard (#214).** The template team is refused with 404 and the existing audit, and is never a target in UI or API.
- **The lock itself is unchanged.** `checkCustomizationLockGate` and the four lock-gated endpoints are not modified (a source test asserts the new route does not call it and the four still do). Recovery does not unlock; it does not offer customization.
- **Not a performance tool / probe surface.** Responses never include the template team id or topic text; audit metadata is ids and counts only. Timing floor and fixed-shape errors are copied from siblings.
- **Application disappears into the background.** No notification to the team's facilitator, no polling, no push, no persistent chrome on the session prep page. The facilitator's copy says "refresh this page"; the server decides at open time, so a stale view cannot cause a wrong action.

## Non-goals (so a later sweep does not "fix" them blindly)

Partial-set top-up for teams with some but not all defaults (a policy question; the FR-8.6 residual, tracked by the follow-up issue); a "visible canonical set" view (same follow-up); a bulk repair job (a one-off script under `migrations-manual/` only if the diagnostic query finds rows, and only with PO agreement); a UI for editing the template; an engineering-manager or facilitator trigger; a "who are the admins" directory; a notification to the facilitator; undo of an assignment; any change to reorder or annotation behaviour; any change to the lock gate; any new support-channel concept; any participant-facing copy (a draft session is not joinable, so participants never see this state); an admin-specific room-open message (dead copy, see above).

## Acceptance criteria

The list is the complete contract; each maps to delta-spec scenarios.

1. **Result.** Given an application admin and a non-template team with zero active topics (any number archived), POST returns 201 `{ topicCount: n }` where n is the template's active topic count as read in the transaction. The team then has n active topics, each marked default, `display_order` 1..n in template order, whose name, prompt, vote type and description equal the template's, with null annotation fields; archived rows are unchanged; the lock state is unchanged.
2. **Refusals.** Non-admins (a facilitator who is or is not a member, any engineering manager, an engineer, a caller with no user row) get 403 `NOT_AN_ADMIN`, including on a nonexistent team (403, not 404); an admin gets 404 for the template team and 404 `TEAM_NOT_FOUND` for a nonexistent one; a team with active topics gets 409 `TEAM_HAS_ACTIVE_TOPICS` and no change. Check order: canonical id, authorization, rate limit, team lookup and template guard, precondition.
3. **Concurrency.** Two simultaneous calls on a zero-active team (real Postgres, two connections) yield exactly one 201 and one 409, and the team has exactly the template's topic count with no duplicate `display_order`; the lock is released on every path; an `/advance` blocked behind the assign lock snapshots the assigned rows.
4. **Empty template.** Yields 500 `DEFAULT_TOPICS_UNAVAILABLE`, rolls back, writes no topics and no success row (one fail-open `topic.defaults_assign_failed` row is written after the rollback), and exposes no template id or topic text; an error-level log line names the template id and correlation id.
5. **Audit (success).** A success writes exactly one `topic.defaults_assigned` row in the same transaction, carrying the acting admin's user id (`actor_user_id`), `actor_global_role = 'application_admin'`, `actor_ip` and the target `team_id`, with `metadata = { topic_count, correlation_id }` only; `emitAuditEvent` is called only after COMMIT; nothing is written on any refusal or rollback.
6. **Audit (denial).** A `403 NOT_AN_ADMIN` writes exactly one `topic.defaults_assign_denied` row (actor, `team_id` as supplied, metadata `{ endpoint, http_status: 403, reason, correlation_id }`) and emits an event, subject to the per-actor bound (beyond it: 403, no row, a log-only suppression event); a failed insert leaves the response a 403 and emits only the log-only `topic.audit_write_failed`.
7. **`canAssignDefaults`.** Matches the truth table above (true only for admin, zero active, not template), is fail-closed, and agrees with whether the endpoint answers 403 for each caller class. A refetch of TOPIC-002 after a successful assignment returns the topics and `canAssignDefaults: false`.
8. **Tenancy.** Assigning on team A changes no other team and not the template.
9. **Lock untouched.** After recovery the team is still `first_session`-locked; add, archive, restore and reorder return 409 `TOPIC_CUSTOMIZATION_LOCKED`; annotate as admin returns 403; the new route does not call `checkCustomizationLockGate` and the other four still do. No notification is sent and no undo exists. Behaviour of an *unlocked* zero-topic team: an admin sees the unlocked variant (Add custom topic, archive action), no Assign button; a post to the endpoint still succeeds with 201.
10. **Room open.** A facilitator blocked at room open gets the locked-team message, the session stays `draft` (no snapshot, audit row or event), and after an admin assigns the defaults the facilitator's next `/advance` on the same session id returns 200 with the session in `lobby`, snapshotting the assigned topics, with no new session row and no step other than clicking Open room again. Authorization is checked before status, status before topic count.
11. **Screen.** The empty-state variants, the 201 / 409 / 500 / other-failure outcomes and the in-flight disabled state behave as specified above, with the success count taken from `topicCount` (singular when 1).
12. **Accessibility.** Outcome messages are announced (status/alert regions), focus lands on the Active Topics heading after a 201, and the in-flight state is exposed to assistive technology.
13. **Runbook.** `docs/deployment.md` states the diagnostic query, the audit lookup, and what to do when the template is empty; an operator can detect and recover a zero-topic team from it alone.
14. **Usability pass (non-gating, cheap).** A facilitator who has not seen the copy, with a real admin on staging, completes blocked-open, ask-admin, return-and-open with no verbal help. Pass: they name "ask an application administrator" as the next step unprompted, and open the room on the second attempt. Owner: Priya (facilitator reviewer; has offered), result recorded in tasks.md 8.3. It does not gate the merge; it is skipped if the diagnostic count is 0 (see pre-build verification).
15. **Authorization source and request surface.** The caller's role is read from the `users` row at request time: an admin demoted between login and call gets 403 `NOT_AN_ADMIN`; a spoofed client `canAssignDefaults` flag changes nothing for a non-admin; a request body or query containing `templateTeamId`, `teamId` or `topics` behaves identically to one without. From a team with one active topic, no admin API sequence reaches zero active topics on a locked team.
16. **Restorable-defaults listing.** `GET .../topics/all` never lists a default in `defaultTopicsNotActive` when the team has an active topic of the same name; a zero-active team with an archived default, once assigned, returns an empty `defaultTopicsNotActive`.
17. **Existing behavior intact.** Team creation behaves as before with the changed `copyCanonicalDefaults`; the TOPIC-002 denial tests pass unchanged on the extracted helper.

## Capabilities

### New Capabilities

None. The behaviour belongs in existing capabilities; a separate capability for one endpoint would split the lock contract across two specs.

### Modified Capabilities

- `topic-customization-lock`: new requirements for the assign-defaults endpoint (authorization, check order, the lock exception and its zero-active precondition, outcomes, atomicity and idempotency, copy fidelity, tenancy, no-leak responses, template guard) and for `canAssignDefaults` on TOPIC-002 (with its truth table); the lock-ordering requirement names the one exception; the spec's Purpose paragraph is touched up at sync time (a Purpose edit is not expressible in a delta; replacement sentence given above; see tasks 6.3).
- `audit-logging-operations`: new requirements for the `topic.defaults_assigned` operation (same-transaction row, actor and team, metadata limits, post-COMMIT event), the `topic.defaults_assign_denied` fail-open denial row, and the empty-template failure being log-only with the accepted gap named.
- `topic-management-screen`: the empty-state requirement gains the viewer-specific locked variants, the "Assign default topics" action and its minimal outcome set; the existing scenario that defers administrator copy to #200 is replaced.
- `session-creation`: the `409 NO_ACTIVE_TOPICS` requirement gains the lock-state-specific message and the draft-stays-intact guarantee.
- `default-topic-provisioning`: the template-team and empty-template requirements gain the assign-defaults endpoint as a consumer (template never a target; empty template is a refusal, never a partial copy).
