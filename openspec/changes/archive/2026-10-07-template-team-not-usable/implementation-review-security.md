# Implementation review (Security): template-team-not-usable (#214)

*Reviewer: Tomás Ferreira (Senior Application Security Analyst), 2026-10-07. Scope: the uncommitted
working tree on `agent-team/214-template-team-not-usable` (`git diff` plus the untracked files), checked
against `design.md`, my `design-review-security.md` and the "Implementation notes" in `tasks.md`. I read
the guard module, the constraint-violation module, every guarded handler (`facilitator-sessions.ts`,
`teams.ts`, `join-links.ts`, `auth.ts` `executeJoinFlow` and the callback `catch`), migration 23, the
auth middleware, `action-items.ts`, and the structural, guard, handler, migration, redemption and
real-team-spelling tests. I did not run the suites.*

## Verdict

**Approve. No blocking findings.** Every item from my design review (B1, S1–S6, A1–A6) is implemented
as the design dispositions say. The three recorded deviations are acceptable. The action-item finding
is a legitimate follow-up, not a blocker for this change. The implementer's description of it also
overstates the exposure (see §3). There are four small should-fix items and some advisories below.
None of them lets a template row persist or leaks data.

---

## 1. Verified as implemented

**Guard normalisation (my B1).** `isTemplateTeam` (`teams/template-team-guard.ts`) strips one enclosing
`{…}` pair, removes every `-`, lowercases, and compares the result with the constant's 32 hex digits.
Postgres's `string_to_uuid` accepts an optional brace pair, a hyphen after any 4-digit group, and hex
of either case, with no whitespace. The guard therefore matches a superset of the spellings Postgres
reads as the template. Postgres rejects the extra spellings it accepts (for example `0000-…` groupings
that are invalid there). Those are still only spellings of the template, so the error is on the safe
side. Unbalanced braces and double braces return `false`, and Postgres rejects them too (22P02, not a
template write). Non-strings return `false`. Unit tests cover all of these cases.

**Every create/redeem path is guarded at the designed point.** I checked all six `INSERT` sites
(`grep` of `INSERT INTO sessions|team_memberships|join_links`, `getOrCreateJoinLink(`,
`createJoinLink(`):

| Path | Guard placement observed | OK |
|---|---|---|
| `POST …/sessions/draft` | after the 401 (global `onRequest`) and the facilitator 403, before the team lookup and both `INSERT`s / `getOrCreateJoinLink` | yes |
| `advance` / `complete` / `topics/advance` / `facilitator-state` | first statement after auth (after `advance`'s canonical-`sessionId` check), before the session lookup and before `getOrCreateJoinLink` (l.2514) | yes |
| `reveal` | first statement, before the session lookup | yes |
| `GET …/members`, `PATCH …/role`, `POST …/managers` | after their authorization (and the TEAM-006 limiter), before the existence/member lookup and the `INSERT` (l.1266) | yes |
| `POST /api/teams/:teamId/join-links` | after the 401, before the membership check and `createJoinLink` | yes |
| `GET /api/join/:token` | right after the token row is found, before `is_active` and the login redirect; it compares on the DB-returned canonical `team_id` | yes |
| `/auth/callback` → `executeJoinFlow` | right after the row is found, before the revoked/expired branch; login has already completed | yes |

`POST /api/v1/teams` inserts a session only for a team id generated by the database, so it cannot
target the template. Its `catch` now logs the marker anyway.

**Guard ordering vs. authz and session lookup.** None of the guards is a `preHandler`. Authentication
is the global `onRequest` in `auth/middleware.ts`, so the structural test's unauthenticated pass
correctly expects that middleware's own 401 and no row. On the session sub-routes the guard runs
before the only authorization there is (`facilitator_id = caller` from the row), which is the design's
intent. It does mean that any authenticated user reaches the writer; D2a bounds that.

**Migration 23 (S1, S5, A1, A4, A6).**
- It takes `ACCESS EXCLUSIVE` on all three tables up front under `SET LOCAL lock_timeout = '200ms'`.
  Nothing can commit between the cleanup and `ADD CONSTRAINT`, and the lock is never upgraded.
- The non-terminal statuses are enumerated (`draft, lobby, pre_session, active, wrap_up`). The clamp
  touches only `complete` rows whose expiry is still in the future. The two `UPDATE`s in step 2c work
  on disjoint row sets, so the same row is never modified twice in one statement.
- Prior values are read in a data-modifying CTE, which sees the pre-statement snapshot. One
  `team.template_cleanup` row is written per changed table, with ids and prior values. `HAVING count(*) > 0`
  keeps the no-op case silent. `actor_global_role` is `TEXT`, so `'system'` is valid.
- The CHECKs are `NOT VALID`, and `VALIDATE` runs only on tables with no template rows. The header
  documents frozen rows, realtime and rollback. The down section matches the repository convention.

**Error handler (S2).** `registerTemplateConstraintErrorHandler` runs first in `registerRoutes`, so
every route plugin inherits it, and nothing else in `src/` calls `setErrorHandler`. The predicate
checks fields only (`DatabaseError`, `23514`, `constraint` ending `_not_template_team`). The template
body is a fixed envelope. Every other error is rethrown to Fastify 5's default handler, and a unit test
compares status, body and content type with and without the handler. The structural probe proves that
the full app returns a sanitized 500 and that no response body contains the constraint name. The
callback `catch` logs the marker before `mapAuthError`, and a test checks the order. The local catches
on `advance` and `POST /api/v1/teams` log the marker without changing the response.

**Audit writer and dedupe (S3, S4).**
- The role comes from the caller or from one `SELECT global_role`, never a placeholder. A missing
  `users` row means no row is written and `audit_write_failed` is logged.
- The role lookup, the Redis claim and the insert share a single `withTimeout(…, 500 ms)`.
- Errors are logged as code and message only. Metadata is `{ endpoint, surface }`, with no token and
  no body. Tests check that the join token never appears in the insert parameters.
- The dedupe key is `template-denial:<actorUserId>:<endpoint>`. `endpoint` is a constant route pattern
  in each handler, not the raw URL. An attacker who varies `sessionId` or the template spelling
  therefore cannot get past the bound: there are at most about 13 rows per actor per minute across all
  endpoints. Keys expire after 60 s, so the keyspace is bounded too. If Redis fails, the row is written
  (fail-safe toward evidence). A null actor writes no row and touches neither the database nor Redis.

**Structural test fail-closed property.** `selectRoutes` enumerates every route registered through
`registerRoutes`, and the test asserts that the selected set **equals** the table keys. A new route
under the prefix without an entry therefore fails by name. `REFUSED_BEFORE_GUARD` is asserted equal to
the closed four-element constant. Every `audit` entry is sent in three spellings and must show:

- the expected status, and parity with the response for a missing team;
- never a 500, and no constraint name in the body;
- exactly one denial row for the route's own `endpoint` string, which also catches a typo in a handler's
  endpoint label;
- no new template row.

Probe (b) shows that an unguarded route with a table entry still fails (500, no row). The file throws
under `REQUIRE_DB`, and `integration.yml` runs on `pull_request` to `main`. The property is fail-closed
**for the prefix and the two extra routes only**. A3 records that limit. See advisory V3.

**Real teams unchanged.** `team-template-guard-real-team-spelling.test.ts` compares the guarded app
with a baseline whose guard is stubbed out, for the braced and no-hyphen spellings of a real team id,
and requires no denial row. That is the evidence I wanted for the "no new boundary rejection" decision.

## 2. Recorded deviations — all accepted

1. **`draft` rejects non-canonical ids before the guard, with no audit row.** The rejection happens at
   the route boundary, before any SQL, and returns the same `404 TEAM_NOT_FOUND` (the parity check in
   the structural test confirms it). No write is possible, and the canonical spelling is audited. This
   matches #188's topic routes. The forensic gap is only that a probe using a non-canonical spelling on
   this one route leaves no row. **Accepted.**
2. **`reveal` returns `409 reveal_failure` for the template.** That is the route's own answer when a
   session is not found for the team, and the governing rule in D3 is parity with the missing case.
   The body echoes `teamId`/`sessionId` as `application/json`, which is pre-existing behaviour on the
   not-found path. **Accepted.**
3. **Admin gets 403 on `draft`.** An admin fails draft's facilitator-role check for every team, and the
   guard is deliberately placed after authorization. A 403 there gives nothing away and shows no
   override exists. **Accepted.**

## 3. The action-item finding (tasks 8.2): legitimate follow-up, not in-scope blocking

I traced `routes/action-items.ts`. The implementer's note is **partly inaccurate**:

- The "ever facilitated" check and the owner check are only the **disclosure** gate: they decide 404
  versus continue. Write authorization is narrower. A non-owner must be *actively* facilitating
  (`ACTIVELY_FACILITATING_STATUSES` = `lobby, pre_session, active, wrap_up`) on both `status` and
  `owner`. Migration 23 leaves no template session in those statuses, and the constraint stops new
  ones. A **past template facilitator therefore gets 403 and cannot update anything.** The only
  residual for them is a 403-versus-404 existence oracle on template action item ids, which requires
  already knowing a random UUID.
- The **owner** of an existing template action item *can* still change that item's status
  (`PATCH …/status`, owner path; `owner` reassignment has no owner path). This is a user updating their
  own pre-existing item on a frozen team. It creates no session, membership or join link. It re-opens
  no grant. It touches no real team's data. It exists only if H1 finds historical template sessions
  that produced action items.

Why not blocking: this change's invariant is "the template is never the subject of a session,
membership or join link", and its security goal is closing Chains A and B and the facilitator grant.
Both hold. Mutating historical template action items is a frozen-history (H2) question, not an
authorization bypass. **Required before archive:** file the separate issue linked to #214 as task 8.2
says, with the corrected description above. It should cover making template action items read-only
(for example a 404 on the owner path when `isTemplateTeam(item.team_id)`) and closing the existence
oracle. Mention it in the PR description. If H1 finds zero template action items in production, the
issue can be prioritised low.

## 4. Should fix (non-blocking, small)

- **F1. Dedupe slot is claimed before the insert.** If the insert fails or times out after a successful
  `SET NX`, the slot stays taken, and that actor's refusals on that endpoint leave no durable row for up
  to 60 s. Only the log event remains. An attacker cannot cause the failure, so the impact is low. Fix:
  `DEL` the key in the `catch` when the claim succeeded, or claim after the insert. Either is a
  two-line change.
- **F2. `reveal`'s template branch has no `correlationId` in the writer call.** Its body has no
  `correlationId` field, so there is nothing to correlate. Everywhere else the event and the response
  share one. Optional: generate one and log it, for consistency in incident reconstruction.
- **F3. Redis key namespace.** Other keys use `dipstick:` (for example
  `dipstick:ratelimit:team-manager:…`). `template-denial:` does not. Prefix it so key-pattern tooling
  and ACLs treat it like the rest.
- **F4. PR description.** Record the 8.4 note on `GET /api/v1/teams/:teamId`: an admin still gets the
  template's team record (stored name, empty member list). This is admin-only and not a write, but it
  is the one admin surface where the template is not answered as missing. That is acceptable, but it
  should be stated, not discovered later.

## 5. Advisories (no change requested in this PR)

- **V1. Rolling deploy window.** Between the migration and the last old-build pod draining, an old pod
  that writes a template row gets the constraint error through Fastify's default handler. That handler
  echoes `violates check constraint "<table>_not_template_team"`. It leaks the constraint name only,
  for a short time. The maintenance window (mandatory when H1 finds live sessions) also covers this.
- **V2. Lock scope during `VALIDATE`.** `VALIDATE` scans the full table while the up-front
  `ACCESS EXCLUSIVE` lock is held, and reads are blocked for the scan. At current table sizes this is
  negligible. `lock_timeout` bounds only the acquisition, not the scan. Recheck if the tables grow
  large before this deploys.
- **V3. Structural test scope.** The test is fail-closed for `registerRoutes` routes under the prefix,
  plus the two redemption routes. A future membership-writing route outside the prefix (for example a
  user-addressed "add me to team" route) or a WebSocket route in `app.ts` is protected only by the
  constraint, which gives a sanitized 500 with the marker. That is acceptable, and it is recorded in
  A3. Keep `integration.yml` a required check, because the property depends on it running.
- **V4. Stale-cookie attribution on `GET /api/join/:token`.** That route is public, so it is not
  re-validated by the middleware. A template refusal attributes the row to `session.userId` even when
  that session is past its absolute lifetime. This matches the route's existing behaviour for real
  joins. Note it in any future review of public-route session handling.
- **V5. Deploy gate.** The H1 counts and the H2 confirmation remain human gates (tasks.md workflow
  follow-up). The migration is safe in every data state, but if H1 finds a live template session, the
  realtime residual (≤ 5 min) makes the window mandatory.
