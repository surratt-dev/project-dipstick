# Security Review: re-add-removed-topic (TOPIC-005)

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope reviewed:** `design.md`, `proposal.md`, cross-checked against shipped code (`packages/backend/src/routes/topics.ts`, `packages/backend/src/auth/standing-facilitator-access-helper.ts`, `packages/backend/migrations/16_topics_archived_by.sql`, `packages/backend/migrations/8_audit_log.sql`, `packages/backend/src/auth/audit-logger.ts`, `packages/shared/src/types/topic.ts`), and against the drafted contract (`requirements/design/REST API Contract.md:806-846`).
**Verdict:** No blocking findings. The design closes the gap it claims to close, and does so correctly — verified against running code, not just the design's own narrative. Two non-blocking notes below for the record.

---

## 1. Authorization fix — verified, not just claimed

I checked this independently rather than taking the design's word for it.

**The contract gap is real.** `REST API Contract.md:818` drafts TOPIC-005's authorization as `global_role = 'facilitator'` AND not a team member AND `isCustomizationLocked = false` — no `application_admin` branch — and `:845-846` folds the lock into the `403` row rather than a separate `409`. Confirmed by reading the contract directly; the design's citation is accurate.

**The fix is the same fix already shipped and working for TOPIC-004.** `checkStandingFacilitatorOrAdminAuthorization` (`standing-facilitator-access-helper.ts:88-116`) is a decision-only function: it admits `application_admin` unconditionally (lines 103-105), otherwise requires `global_role = 'facilitator'` AND not an active team member, and returns a typed rejection reason rather than writing a response itself. TOPIC-004's handler (`topics.ts:338-358`, `checkArchiveTopicAuthorization`) wraps it, applies its own message per rejection reason, and calls `applyTimingFloor` on every branch. This is exactly the shape design.md Decision 1 says TOPIC-005 will reuse as a third caller. I have no reason to doubt it will work identically for TOPIC-005 — it's the same function, same call signature, same wrapper pattern — but I could not verify the TOPIC-005 handler itself, since it does not exist yet (design phase, no code). **Flag for implementation review, not design review:** confirm the shipped TOPIC-005 handler actually calls `checkStandingFacilitatorOrAdminAuthorization` and not a re-derived inline check, and confirm the lock check is wired to `409` (via the existing shared `checkCustomizationLockGate`, which already returns `409 TOPIC_CUSTOMIZATION_LOCKED` — `topics.ts:209-240`) rather than a fresh `403` branch that reintroduces the contract's original mistake.

**Cascade ordering (Decision 2) is sound and matches the enumeration-resistance pattern already proven for TOPIC-003/004:** identity/role before team-existence before lock before topic-existence before topic-status, with `applyTimingFloor` on every branch including the `200`. No step leaks more specific information than the step before it needed to. I have no changes to recommend here.

**This closes an FR-8.2 `[HARD]` gap before ship, which is the correct time to close it** — Decision 1's own risk note (an unshipped endpoint has no caller to break) is accurate and I don't need to add caveats to it.

## 2. Provenance / audit — no forgery or leakage surface found

- **`restored_by` cannot be client-forged.** Per the established pattern (`topics.ts:683`, `session.userId` sourced from server-side session state, never request body), Decision 3's transaction sets `restored_by = $userId` from the same trusted source. There is no client-suppliable actor field anywhere in this design. Same for `restored_at` (`now()`, server clock). I have no reason to expect this to diverge from the `archived_by`/`archived_at` precedent, which is already correct in shipped code.
- **`archived_at`/`archived_by` preserved through restore, not cleared — no tampering surface.** Decision 4 leaves these columns untouched on restore. Since neither field is ever client-writable (both are server-set on the archive path, same as restore), preserving them creates no new avenue for a non-privileged actor to alter or erase prior provenance. If anything, clearing them would have been the riskier choice from an audit-integrity standpoint — it would let a restore silently overwrite the record of who archived the topic and when, with no equivalent "who cleared this" audit row. Correct call.
- **`topic.restored` audit event (Decision 6) mirrors `topic.archived` correctly.** `audit_log.operation` is a plain `TEXT` column with no `CHECK` constraint (`migrations/8_audit_log.sql:31`) and `AuditEventName` is a TypeScript-only union (`audit-logger.ts:3`) — adding `"topic.restored"` is additive and requires no migration, consistent with how `topic.archived`/`topic.custom_added` were added. The event carries `actor_user_id`, `actor_global_role`, `actor_ip`, `team_id`, `metadata: { topic_id }` inside the same transaction as the state flip — same shape as `topic.archived`, written before commit rather than best-effort after. Good; this is the pattern I'd have asked for if it weren't already there.
- **No new data-classification exposure.** `restoredBy`/`restoredAt` on `GetAllTopicsResponse.archived[]` extend an authorization boundary that already exists and was already reviewed for `archivedBy`/`archivedAt` (TOPIC-002, shipped). This design doesn't widen who can see that boundary — it adds two more fields behind the same gate. I'm not reopening that boundary here since it's out of this change's scope, but noting it for completeness: TOPIC-002's "standing facilitator" model means any org-wide facilitator not on the team, plus any `application_admin`, can already see who archived a topic; restore extends that to who restored it. Same actor population, same data class (an internal user's id/display name), nothing new.

## 3. Cross-team / cross-tenant boundary — closed correctly

The concrete question: can a facilitator restore a topic belonging to a team other than the one named in the URL? **No, by construction.** The existing topic-lookup pattern TOPIC-005 reuses (`checkTopicExistsAndActive`, `topics.ts:366-395`) scopes on `WHERE id = $1 AND team_id = $2` — both the path's `teamId` and `topicId` must match the same row, or it's a `404`. A caller cannot supply `teamId` for a team they're scoped into and `topicId` for a different team's topic and have it resolve. Decision 3's `UPDATE ... WHERE id = $topicId AND team_id = $teamId AND status = 'archived'` repeats the same double-scoping inside the transaction, belt-and-suspenders against a TOCTOU gap between the pre-check and the write. This is the correct IDOR defense and the design inherits it verbatim rather than re-deriving it.

**Separately, and not a finding against this design specifically:** the "standing facilitator" authorization model itself (`evaluateStandingFacilitatorAccess`) grants any `global_role = 'facilitator'` user write access to *any* team's topics, as long as they are not a member of that specific team — this is Philosophy 1, an intentional org-wide model that predates this change and was presumably accepted in TOPIC-002/003/004's own security reviews. Restore becomes its fourth caller. I'm naming it here only so it's on the record for whoever eventually revisits that model's blast radius — a compromised facilitator credential can archive or restore topics for every team in the org, not just teams that facilitator actually runs. That's a pre-existing architectural risk, not something introduced or worsened by this design, and not something I'm asking this change to fix.

## Multi-provider IdP note

Per team memory, I checked this design for Entra-specific assumptions given it's an auth-adjacent change. It isn't one — this design performs no authentication, issues no tokens, and touches no IdP integration surface. Authorization is entirely session/role-based (`global_role`, `team_memberships`), evaluated against already-established session state; nothing here assumes a specific identity provider. No concern.

## Non-blocking notes

- **[Note, not a finding]** Decision 2/3 do not audit `TOPIC_NOT_FOUND` or `TOPIC_ALREADY_ACTIVE` denials, matching TOPIC-004's existing convention of only auditing the lock-denial branch. I won't ask this design to reopen that scope — it's consistent with the established convention — but flagging it so it's a deliberate, named choice rather than a silent gap if anyone later asks "why don't we have a row for every rejected restore attempt." The design.md text already states this explicitly (Decision 6, "Why other denial branches remain unaudited"), which is the right way to handle it.
- **[Note, not a finding]** I have not reviewed implementation — this is a design review. My verification above is against the existing TOPIC-003/004 code this design proposes to reuse, not against a TOPIC-005 handler that doesn't exist yet. I'll want a short pass at implementation/PR time to confirm the actual handler wires the pieces the way this design says it will (see §1's flag above) — that's a five-minute check given how much is reused verbatim, not a new review.

## Summary for the team

The design does what it claims: it reuses `checkStandingFacilitatorOrAdminAuthorization` as a third caller, closing the exact `application_admin`-branch gap and `403`/`409` miscategorization that the contract draft still has and that `remove-topic` already found and fixed once for TOPIC-004. I verified this against the contract text and the shipped helper/handler code rather than accepting the design's citation at face value, and it holds up. Provenance columns are server-set only, non-forgeable, and preserve rather than destroy prior audit trail. The restore endpoint's team/topic scoping closes cross-tenant access the same way TOPIC-004's already does. No OIDC/Entra assumptions are introduced. No blocking findings; one implementation-time check flagged above (confirm the shipped handler actually wires to the corrected auth function and 409, not a re-derived check).
