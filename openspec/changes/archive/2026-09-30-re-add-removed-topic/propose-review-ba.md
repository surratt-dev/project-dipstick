# BA Review — Re-Add a Previously Removed Topic (#54)

**Reviewer:** Marcus Delgado, Senior Business Analyst
**Reviewed:** proposal.md, design.md, tasks.md, specs/ (restore-topic, topic-management-screen, topic-customization-lock, manager-team-association), against `requirements/use cases/08 - Topic Management - Use Cases.md` and `requirements/BRD.md`.

## Summary

This is buildable. The authorization correction, cascade, advisory-lock reuse, and provenance decisions are all stated as concrete, testable conditions and verified against the actual codebase (function names, file paths, column names all check out — this isn't aspirational reuse, it's real reuse). The capability/spec-impact classification in the proposal (`restore-topic` New; `topic-management-screen`, `topic-customization-lock`, `manager-team-association` Modified) is internally consistent with what's in `specs/` and with what already exists in `openspec/specs/`. One finding is blocking-adjacent (a wrong requirement citation baked into a design decision's stated rationale), and two are gaps in acceptance-criteria coverage worth a decision on the record rather than silent omission.

## Finding 1 — FR-8.6 is cited for a claim it doesn't support (correct the citation)

Proposal.md's "What Changes" section states: *"appended at the end of the current display order (not its prior position — FR-8.6)."* Design.md Decision 3 and exploration-notes.md §2 build on the same citation.

I checked the actual text. **FR-8.6** (`requirements/BRD.md:331`) reads: *"The canonical default topic set must remain visible and restorable for any team at any time, regardless of how much the team has customized their topic list."* That's a requirement about default-topic restorability — it says nothing about append-vs-prior-position ordering semantics. The append-at-end decision is independently well-justified in design.md Decision 3 (the `topics_team_order UNIQUE (team_id, display_order, status)` constraint and the position-collision problem restoring-to-prior-slot would create) — the *decision* is sound, but the FR-8.6 citation supporting it in the proposal's own "Why" framing is wrong.

This citation error originates in the contract itself (`REST API Contract.md:851`, pre-existing, not introduced by this change), but this proposal repeats it in a customer-facing artifact (the proposal document) without catching it, and tasks.md Task 8.4 will propagate it into the use case document's resolved Note unless corrected. Given how much weight this team puts on requirement-to-feature traceability, a stated decision resting on a mis-cited FR undermines exactly the thing citation is supposed to buy.

**Recommendation:** Before Task 8.4 is executed, change the justification for "append not prior slot" to cite design.md Decision 3's own reasoning (the uniqueness-constraint / collision-avoidance argument) rather than FR-8.6. Separately worth a one-line flag (not this change's job to fix): FR-8.6 talks about default topics being restorable "at any time," and `defaultTopicsNotActive` — the field that would actually serve *that* requirement, including default topics that were never seeded (not just archived ones) — still isn't consumed anywhere in the frontend, per exploration-notes.md §0. TOPIC-005 satisfies FR-8.6 for the archived-default-topic subcase; it does not close FR-8.6 for a never-seeded default topic. That's a pre-existing gap, not one this change needs to own, but the proposal's citation implies FR-8.6 is being satisfied here, which overstates it.

## Finding 2 — AC "included in the next session" has no spec coverage (acknowledge explicitly, don't let it sit unstated)

Use case Acceptance Criteria: *"After reinstatement, the topic appears in the active topic list and is included in the next session."*

The "appears in active topic list" half is covered (restore-topic spec, Scenario: "A valid request restores an archived topic"; topic-management-screen spec, Scenario: "Confirming the restore updates both lists"). The "included in the next session" half has no scenario anywhere in `specs/` — not in restore-topic, not in topic-management-screen. Design.md and exploration-notes.md both know this and say why: no shipped endpoint populates `session_topics` at session creation (#175, still open), so "included in the next session" can't be demonstrated for *any* active topic today, restored or not.

This is the same caveat `remove-topic` already recorded for its own acceptance criteria, and I'm not asking this change to fix #175. But there's a difference between "known limitation stated in design.md's prose" and "an acceptance criterion with zero spec-level scenario coverage." Right now a reader of `specs/restore-topic/spec.md` alone — without also reading design.md's Risks section — would not know this AC is only half-satisfiable. Recommend one of: (a) an explicit scenario in restore-topic spec stating the topic's active status makes it eligible for the next session snapshot subject to #175, marked as blocked/deferred, or (b) a one-line note directly in the spec's Purpose section pointing to #175, so the gap is visible from the spec itself, not only from design.md. Either is fine; leaving it entirely unstated in `specs/` is not.

## Finding 3 — AC "can be reordered within the active list after reinstatement" has no coverage anywhere, including outside this change

Use case AC: *"The re-added topic can be reordered within the active list after reinstatement."* TOPIC-006 (Reorder) is explicitly a Non-Goal of this change, and — more importantly — I confirmed by grep that no reorder endpoint or capability exists anywhere in the codebase yet, for any topic, restored or otherwise. This isn't a gap this change introduces; it's a gap in the whole feature area that predates it. A restored topic becomes an ordinary active topic and would be reorderable the moment TOPIC-006 ships, same as any other active topic — there's no restore-specific blocker.

I'm not asking this change to build TOPIC-006. I am flagging that this AC is currently unsatisfiable for *any* topic in the shipped product, and neither this proposal nor (as far as I can tell) `remove-topic`'s or `add-custom-topic`'s proposals called that out explicitly against this specific use case's AC list. Recommend a one-line acknowledgment in this change's proposal (Impact → Not touched section already lists TOPIC-006 as deferred; add that this specific AC is covered by that deferral) so it doesn't read as a silent gap on re-review.

## Verified clean — no further action needed

- **Capability/spec-impact classification.** `restore-topic` is genuinely new (no prior spec); `topic-management-screen`, `topic-customization-lock`, and `manager-team-association` all have pre-existing entries under `openspec/specs/`, confirmed by directory listing, so "Modified" is the correct classification for all three, not "New." The delta files' own headers (`## ADDED Requirements` for restore-topic/topic-management-screen/manager-team-association's new requirements; `## MODIFIED Requirements` for topic-customization-lock's extended response shape) match the proposal's stated classification. No inconsistency found.
- **FR-8.2 citation** (the authorization-gap finding, proposal.md line 9). Verified against `BRD.md:323` — "the facilitator or Application Administrator shall be able to add, remove, or reorder topics" — this citation is accurate, and the `[HARD]` gap it's fixing (no `application_admin` branch in the drafted TOPIC-005 authorization) is real, confirmed by reading `REST API Contract.md:818`.
- **Reuse claims are real, not aspirational.** Grepped `packages/backend/src/routes/topics.ts` and `audit-logger.ts` directly: `checkStandingFacilitatorOrAdminAuthorization`, `checkTeamExists`, `checkCustomizationLockGate`, `applyTimingFloor`, `writeLockDenialAudit`, and the `TOPIC_ALREADY_ARCHIVED` reason code all exist exactly as cited. `TOPIC_ALREADY_ACTIVE` and `topic.restored` are new additions, correctly scoped as such.
- **AC coverage — the rest.** "Provides access to the list of previously removed topics" is satisfied by the already-shipped, already-archived `topic-management-screen` main spec (not restated here, correctly — it's untouched). "Each removed topic can be individually reinstated," "confirmation step... describing history preservation," and "trend view reflects the gap... rather than interpolating" are all covered by explicit scenarios in this change's `specs/` (restore-topic; topic-management-screen delta; manager-team-association delta). "Historical vote data... preserved and accessible" is covered by restore-topic's "historical vote data remains accessible" scenario for the preservation half; the "accessible in trend views" half rests on the pre-existing trend view already rendering from unmodified `session_topics`/`votes` — reasonable to treat as inherited rather than requiring a new scenario, since nothing in this change touches how the trend view reads that data.
- **Capabilities are specific enough to implement.** The check-ordering cascade, lock SQL sequence, provenance column decisions, and gap-derivation logic are all stated as explicit, numbered steps with concrete reason codes, not left as "applies by analogy" — this is exactly the "buildable, not just correct" standard I look for, and design.md says so itself, correctly.

## Bottom line

Two acceptance-criteria gaps (Findings 2, 3) are pre-existing scope boundaries, correctly identified in design.md's prose but not reflected at the spec-scenario level — worth a one-line fix each before this moves further, not a re-scope. Finding 1 (FR-8.6 mis-citation) should be corrected before Task 8.4 writes it into the use case document as settled, since that would compound a citation error that's already loose in the contract into a second requirements artifact.
