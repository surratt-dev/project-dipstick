# Engineering Design Review — `http-session-expiry-reauth-parity`

**Reviewer:** Marcus Oyelaran, Full Stack Engineer
**Reviewed:** `design.md`, `proposal.md`, `tasks.md`
**Verified against:** `packages/frontend/src/realtime/connectionHealth.ts`, `packages/frontend/src/auth/AuthContext.tsx`, `packages/backend/src/auth/middleware.ts`, `packages/backend/src/routes/auth.ts`, `packages/frontend/src/components/ReauthRequiredTreatment.tsx`, `packages/frontend/src/pages/SessionLobbyPage.tsx`, `packages/frontend/src/pages/DraftSessionHost.tsx`, `packages/frontend/src/pages/SessionCreationPage.tsx`, `packages/frontend/src/components/MemberManagement.tsx`, `packages/frontend/src/App.tsx`. Also read the two precedent archives (`session-timeout-continuity`, `reauth-required-client-prompt`) named in the brief.

## Verdict

The scope calls (Decision 1a's per-call-site role determination, Decision 7's `MemberManagement.tsx` split, the two allow-list additions) are all sound and match the real code. But the design has two concrete implementability problems, not style opinions: the shared helper's stated `Promise<boolean>` contract cannot support the "reuse whatever the helper returns... rather than reading twice" promise it also makes, for a 401 case that genuinely exists in `authMiddleware` today; and `SessionLobbyPage.tsx`'s "single boolean gate" idempotency rule has no stated implementation shape against a page that currently renders its detection signals from four independent, non-mutually-exclusive locations — a literal reading of tasks 3.1–3.4 produces two banners on screen at once under a real, described race, not a hypothetical one. Both need a design answer before implementation starts.

## Blocking findings

### 1. `detectSessionExpiry`'s `Promise<boolean>` return type can't deliver the "read once, reuse what it returns" promise — verified against a real 401 case, not a hypothetical

Decision 1 states two things that don't fit together:

- The signature is "roughly `async function detectSessionExpiry(res: Response): Promise<boolean>`."
- "Every call site... restructures to read the body exactly once, through the helper, and reuses whatever the helper returns (**or re-derives the generic-error message from the same parsed body**) rather than reading twice."

A bare `boolean` gives the caller nothing to re-derive a message from. `Response.json()` can only be called once — if the helper consumes the body internally to check `category`, the parsed object is gone; the caller's own `body?.error?.message ?? "..."` fallback either has to skip re-parsing (losing the real message) or call `res.json()` again and throw.

This isn't only a problem for the "helper is careless" case the design already flags for `DraftSessionHost.tsx`'s existing double-`.json()` risk. It's a real, currently-reachable 401 that isn't `session_expired`: `authMiddleware`'s `transient_failure` branch (`middleware.ts:217-232`) returns `reply.code(401).send({ error: { category: "provider_unavailable", ... } })` — a 401 status with a *different* category, on the exact same `onRequest` hook every in-scope call site sits behind. To evaluate `status === 401 AND category === "session_expired"`, the helper *must* parse the body whenever `status === 401`, including this case. When it does and the result is `false` (not session-expired), the boolean-only return leaves the caller with no way to get at `error.message` — and two real call sites hit exactly this gap:

- `DraftSessionHost.tsx`'s `loadFacilitatorState` (`facilitator-state` GET) and `openTheRoom` (`advance` POST), both: `if (!res.ok) { const body = (await res.json().catch(() => null)) as ...; setLoadState({ status: "error", message: body?.error?.message ?? "..." }); }` (lines 58-64, 85-91). A `provider_unavailable` 401 here — a facilitator's session mid-token-refresh-failure while loading or clicking "Yes, open the room" — hits `res.json()` a second time and throws inside the `!res.ok` branch, unless that branch is rewritten around whatever the helper hands back.
- `MemberManagement.tsx`'s `submitRoleChange`: `if (!res.ok) { const body = (await res.json()) as { error?: { message?: string } }; setRoleChangeState({ status: "error", message: body.error?.message ?? "Role change failed." }); }` (`MemberManagement.tsx:154-161`) — same shape, same real 401 case, no `.catch` guard even.

`SessionLobbyPage.tsx`'s `start`/`begin-voting` and `SessionCreationPage.tsx`'s two call sites are not affected — their generic-error branches don't read the body at all today (hardcoded strings), so a boolean-only helper costs them nothing. This is specifically a `DraftSessionHost.tsx` + `MemberManagement.tsx` problem, both explicitly in scope.

**Fix:** the helper's return type needs to carry the parsed body (or at minimum the derived message) alongside the boolean, e.g. `Promise<{ isSessionExpired: boolean; body: unknown }>` or `Promise<{ isSessionExpired: boolean; message?: string }>`, so a caller that gets `isSessionExpired: false` on a 401 can still recover `error.message` without a second read. State this in Decision 1's contract section, not left to "implementation's to pick" — the *shape*, not just the name, is exactly what's underspecified here.

### 2. `SessionLobbyPage.tsx`'s "single boolean gate" has no stated structural home, and a literal implementation of tasks 3.1–3.4 renders the treatment twice under a real ordering, not a manufactured one

The tech lead's question was whether the idempotency rule holds up against React's render/effect timing. The timing itself is fine — JS is single-threaded, so a fetch `.then` callback and a WS `state`-driven effect can never literally execute concurrently; whichever "arrives" first (in event-loop terms) really does run to completion before the other can. That's not where the risk is.

The risk is structural. `SessionLobbyPage.tsx` today renders its branches as **four independent, non-mutually-exclusive JSX conditions**, not a single discriminated switch:

1. `branch.kind === "error" | "no-access" | "left" | "lobby" | "pre_session"` — a discriminated union, mutually exclusive *within itself* (`SessionLobbyPage.tsx:204-262`).
2. `startError`, rendered nested *inside* the `branch.kind === "lobby"` block (line 244-248) — independent state, not part of the `branch` union.
3. `beginVotingError`, passed as a prop into `PreSessionActionItemReview`, rendered *inside* the `branch.kind === "pre_session"` block — also independent state.
4. (New, per task 3.4) `state === "reauth-required"` from `useConnectionHealth` — nowhere in the existing structure; the task description implies a new, presumably top-level, condition.

Tasks 3.1–3.3 describe wiring the helper into each of the three fetch call sites individually, each "rendering the treatment in place of the existing branch logic" *for that call site*. Taken literally, that's three more independent local conditions, on top of the WS one. Concretely: a facilitator's session expires. The WS close (`CLOSE_FORCE_EXPIRED`) flips `state` to `"reauth-required"` at roughly the same moment a POST already in flight (`start` or `begin-voting`) gets its own `session_expired` 401 back — this is exactly the race Decision 2 itself names as the reason both signals must stay live ("no ordering guarantee between them... a real window where the fetch response arrives before the socket's scheduled close does"). If the WS-driven condition is a top-level, unconditional check (`{state === "reauth-required" && <Treatment/>}`, checked every render regardless of `branch.kind`) and the POST-driven condition renders *inside* the `lobby`/`pre_session` block that `branch.kind` hasn't moved off of (because the POST failing doesn't change `branch`, only `startError`/`beginVotingError`) — **both conditions are true in the same render pass, in two different DOM locations, and React renders both.** That's two visible banners, not "second signal is a no-op." The `action-items-review` GET's own session-expiry (task 3.1) is likely modeled as a new `branch.kind` variant, which *is* mutually exclusive with `lobby`/`pre_session`/etc. within the union — so that one specific pairing is safe by construction. The WS-vs-POST-error-slot pairing above is not, and neither design.md nor tasks.md says how the four signals feed one shared gate.

Design Decision 2's own framing — "fetch-response AND `useConnectionHealth` state," as if there are two signals — undercounts what's actually on this page: there are three independent fetch call sites plus the WS state, four sources, three of which currently render into three different DOM locations. "A single boolean gate (has the treatment already been shown for this page instance)" is the right target, but it needs a design answer for *where* that gate lives and *what it hijacks* — the natural fix is that all four signals write into one shared piece of state (e.g., collapse `startError`/`beginVotingError`'s session-expiry case into the same `branch.kind` union the GET already uses, and check that same union — plus the WS state — from one top-level early return that supersedes the entire existing branch/error render tree, not from four scattered local conditionals). That's a real, if small, restructuring of the page's state shape beyond "wire the helper into each call site," and it isn't in tasks.md as its own step.

**Fix:** Add a decision (or expand Decision 2) stating explicitly: all four detection signals on this page write into one shared state value (not `branch.kind` for the GET and separate local state for the two POSTs); the page's top-level render does one check against that shared value, before any of the existing branch/error JSX, and returns the treatment there — not as an additional condition layered alongside the existing blocks. Give tasks.md its own task for this restructuring (distinct from 3.1–3.3, which currently read as three independent, per-call-site wirings) so it isn't discovered mid-implementation when two banners show up in a test.

## Medium-severity findings

### 3. The WS-driven render path (task 3.4) has no stated `role` value

`ReauthRequiredTreatmentProps.role` is a required prop (`"participant" | "facilitator"`, `ReauthRequiredTreatment.tsx:132`) — TypeScript will force an implementer to supply something, but the design never says what. Decision 1a carefully works out `role` for the three fetch call sites (including the non-obvious `action-items-review` proxy), but Decision 2's WS-driven branch is silent on it. The obvious answer is the same `session?.canFacilitateSessions ? "facilitator" : "participant"` proxy already established for `action-items-review` — since it's the same page, same available signal — but "obvious" isn't "stated," and this is exactly the kind of gap BA review's Finding 2 already caught once on this same page for a different call site. Say it explicitly in Decision 1a or Decision 2 rather than leaving it as an implementer's guess.

### 4. `category: "session_expired"` is not unique to the absolute-lifetime-expiry case the treatment is meant for — worth naming as an accepted trade-off, not left implicit

Design's own Context section notes `sessions.ts`/`facilitator-sessions.ts` also emit `category: "session_expired"` for a "no row in `users` for `session.userId`" data-integrity edge case, distinct from `authMiddleware`'s absolute-lifetime branch. The detection helper (Decision 1) can't and doesn't try to distinguish these — both will route to `ReauthRequiredTreatment`, which will tell a user with a **missing `users` row** to "log in again," which won't fix their actual problem (their session isn't expired; their account row is gone or was never created). This is a reasonable call to leave alone — the copy is not actively wrong-sounding, and disambiguating would require a new category the design correctly scopes out — but it should be one sentence in the Risks section (it currently isn't), since it's a second, already-known source of false-positive routing beyond the "generic try again forever" problem this change fixes.

## Low-severity / implementation-detail findings

- **`DraftSessionHost.tsx`'s `.catch(() => null)` guard on the existing `res.json()` calls is not mirrored in `MemberManagement.tsx`'s `submitRoleChange`** (`MemberManagement.tsx:155`: bare `await res.json()`, no catch). Once the helper's contract is fixed per Finding 1, whichever call site ends up doing a second read (or the helper's own internal read) should use the same non-throwing guard consistently across both restructured call sites — worth a one-line note in tasks.md 6.1 so the `MemberManagement.tsx` version doesn't quietly stay less defensive than its `DraftSessionHost.tsx` sibling.
- **`AuthContext.tsx`'s own `/auth/session` 401 handling is a pre-existing, unconditional `window.location.href` navigation** (`AuthContext.tsx:73-84`) — no `returnTo`, no inline treatment, the exact pattern Decision 6 calls out as the thing this change and its precedents deliberately avoid everywhere else. Not a bug in this change (the file isn't touched, and it's plausibly out of scope — a fresh page load has no in-place UI to render into), but it means a user who refreshes an already-expired page gets a silent bounce with no explanation, while a user who's mid-click gets the disclosed banner this change adds — a real behavioral seam immediately adjacent to this change's problem space. Worth a one-line forward note next to the existing `MemberManagement.tsx loadMembers`/EM-pages deferral note in proposal.md, so it isn't rediscovered later as a surprise inconsistency.
- **`teams.ts`'s "user row missing" 401 for `PATCH .../role` itself** — design.md's Context section is explicit that this route gets the real `authMiddleware`-produced `session_expired` category, not the mislabeled one, and I confirmed the route sits behind the same global `onRequest` hook with no route-level override before it. Confirmed correct as stated.

## Confirmed-correct claims (spot-checked against code, not assumed)

- `useConnectionHealth`'s return shape really is `{ state, socket }`, `state: "connected" | "unknown-reconnecting" | "reauth-required"`, and `SessionLobbyPage.tsx` really does destructure only `{ socket }` today (`connectionHealth.ts:86-89`, `SessionLobbyPage.tsx:111`) — Decision 2's premise is accurate.
- `RETURN_TO_ALLOW_LIST` really is exactly the two UUID-pinned entries described, with `validateReturnTo` running the character-rejection checks before the allow-list match, unmodified logic (`auth.ts:73-118`) — Decision 3's "no new validation logic, only new accepted shapes" claim holds.
- The two new route shapes match the real routes: `App.tsx` really mounts `SessionCreationPage` at `/sessions/new` (line 104) and `DraftSessionHost` at `/team/:teamId/session/:sessionId` (line 124) — both exactly as Decision 3 states, and `SessionLobbyPage` at `/session/:sessionId` (line 138) is already covered by the existing `/session/:id` entry, needing no addition — consistent with the design not proposing one.
- `session?.canFacilitateSessions` exists on `AuthSession` and is computed live from `users.global_role` on every `/auth/session` call, never cached in the Redis session blob (`auth.ts:711-735`) — Decision 1a's proxy is reading a real, live-computed field, not something derived from a snapshot that could go stale mid-session.
- `authMiddleware`'s three 401-producing branches (`middleware.ts:163-165`, `168-181`, `201-216`) all run in `onRequest`, before any route handler body executes — Decision 4's no-partial-execution guarantee for `advance` (and Decision 7's identical claim for `submitRoleChange`) is accurate as stated.
- `DraftSessionHost.tsx`'s two call sites really do each call `.json()` once already inside their own `if (!res.ok)` branch (lines 59, 86) — the double-read hazard the design names for this component is real, confirmed by reading the code, not just plausible.

## Recommendation

Not a rewrite — the scope decisions and the allow-list/role-proxy work are correct and match the real code closely. Fix Findings 1 and 2 before implementation starts: both are "as literally written, this doesn't do what it claims" problems verified against actual call sites (`provider_unavailable`'s real 401, and the WS/POST-error-slot double-render), not judgment calls. Findings 3 and 4 should each get a sentence in design.md so they're not rediscovered mid-implementation. The low-severity items are fine left as implementer judgment but cheap to state now.
