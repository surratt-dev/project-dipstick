## Context

This change closes issue #146, `session-timeout-continuity`'s own Open Questions section (and tasks.md task 5.5) naming the HTTP-side gap it deliberately deferred: the WebSocket-side absolute-lifetime expiry (`ABSOLUTE_LIFETIME_MS`, 90 minutes, NFR-AUTH-005/SEC-26) already routes to the disclosed `reauth-required` treatment via `CLOSE_FORCE_EXPIRED` aliasing `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (`session-timeout-continuity` Decision 1). The same 90-minute ceiling, hit by an in-flight HTTP request instead of a live socket, still produces a generic "try again" message today — none of the affected call sites read the response body on a non-2xx status, let alone branch on it.

**Where the signal actually comes from.** Every session-scoped HTTP request already passes through one centralized choke point: `authMiddleware`'s `onRequest` hook (`packages/backend/src/auth/middleware.ts:156-242`). Three branches there produce `category: "session_expired"` on a 401 — no session/`userId` (line 164), `Date.now() - sessionCreated > ABSOLUTE_LIFETIME_MS` (line 180), and a `revoked` token-refresh result (line 215). This hook needs no new work; the entire gap is client-side, because nothing today reads the `category` field it already sends. A separate, narrower set of route-level 401s (`sessions.ts`, `facilitator-sessions.ts` at `category: "session_expired"`; `teams.ts`'s `GET /api/v1/teams/:teamId` at `category: "invalid_request"` for the identical "no row in `users` for `session.userId`" condition) is a pre-existing data-integrity edge case, not the scenario this issue is about — see the `MemberManagement.tsx`/`teams.ts` scope note below. This mislabeling is specific to that one `teams.ts` route; `teams.ts`'s `PATCH /api/v1/teams/:teamId/members/:userId/role` route sits behind the same global `authMiddleware` `onRequest` hook as every other in-scope call site and gets the real `category: "session_expired"` on absolute-lifetime expiry, which is why it's in scope below despite being defined in the same file as the mislabeled GET.

**A fourth 401 shares the same hook, same status code, a different category.** `authMiddleware`'s `transient_failure` branch (`middleware.ts:217-232`, reached when a token refresh fails without an explicit revocation) also returns `reply.code(401).send({ error: { category: "provider_unavailable", ... } })` — same `onRequest` hook, same 401 status, every in-scope call site sits behind it. This is not a session-expiry, but the detection helper (Decision 1) cannot tell that without parsing the body, and once it has, the caller still needs that body's `message` for its own generic-error fallback. This is the reason Decision 1's contract below carries the parsed body through, not just a boolean.

**What this reuses, unmodified.** `ReauthRequiredTreatment.tsx` already accepts `returnTo?: string` and `role: "participant" | "facilitator"` (`session-timeout-continuity` Decisions 3–4) and both existing call sites (`ConnectionStatusBanner.tsx`, `FacilitatorReadinessGrid.tsx`) already compute `returnTo` as `window.location.pathname + window.location.search`. The `returnTo` OIDC round-trip (`/auth/login`, `/auth/callback`, the Redis `state` payload, the allow-list check) is fully shipped and unmodified except for the allow-list constant itself (Decision 3 below). No new backend route, no new authorization decision anywhere in this design — `returnTo` is a destination, re-authorized on landing by the destination route's own checks, exactly as `reauth-return-to`'s "does not grant, infer, or bypass any authorization" requirement already states.

**Constraint carried forward, restated because it's easy to violate by accident:** re-authentication must never grant a role, team membership, or facilitator status the user didn't already hold. Nothing in this design introduces a new authorization decision.

Consistent with [[project_oidc_multi_provider]]: `/auth/login?returnTo=...` is already provider-agnostic (confirmed directly in `auth.ts`), and this change adds no IdP-aware code anywhere.

## Goals / Non-Goals

**Goals:**
- Recognize a disclosed `session_expired` 401 at each in-scope fetch call site and render `ReauthRequiredTreatment` in place — never an automatic navigation — matching the WS-side precedent exactly.
- On `SessionLobbyPage.tsx`, also consume the WS-side signal (`useConnectionHealth`'s `state`) that's already available there and currently discarded, so an in-progress fetch and a scheduled WS close are both covered regardless of which one observes the expiry first.
- Extend the `returnTo` allow-list to cover the two additional route shapes this change's in-scope pages need.
- Ship a single shared detection helper so six call sites don't each reimplement the same "is this a disclosed session-expiry" check independently.

**Non-Goals:**
- OR-1.7 (rejoin with topic/vote state restored) — the live-voting UI this would rejoin a user into doesn't exist yet.
- A pre-expiry warning affordance — a separate, later UX decision.
- Any change to the 90-minute policy number, `authMiddleware`'s detection logic, or the WS-side mechanics `session-timeout-continuity` already shipped.
- A general-purpose HTTP interceptor for every error class — this is specifically the disclosed `session_expired` 401 case, nothing else.
- `MemberManagement.tsx`'s `loadMembers` GET, the three EM pages, and the `teams.ts` category-label fix — deferred per proposal.md's scope decision; not designed here.
- Any participant-facing "waiting for the facilitator" UI — named as a forward note in proposal.md, not built here; no such surface exists to design against yet.

## Decisions

### Decision 1: Shared detection helper — contract, not just "a helper"

A single function, roughly `async function detectSessionExpiry(res: Response): Promise<{ isSessionExpired: boolean; body: unknown }>` (exact name/signature is implementation's to pick, the shape of the return value is not):

- **Owns the body read.** It calls `res.json()` (guarded against a non-JSON or already-consumed body — a failed parse resolves `body` to `null`, not a throw) itself. Callers do not pre-parse the body and hand in an object. This matters concretely: `DraftSessionHost.tsx`'s two existing branches already call `.json()` once for their generic-error fallback (`body?.error?.message ?? "..."`) — a second `.json()` read on the same `Response` throws. Every call site this change touches restructures to read the body exactly once, through the helper.
- **Returns the parsed body alongside the boolean, not a bare boolean.** This isn't optional plumbing: `authMiddleware`'s `transient_failure` branch (see Context above) produces a real, reachable 401 with `category: "provider_unavailable"` on the exact same hook every in-scope call site sits behind — `isSessionExpired: false` on a 401 is a normal, expected outcome, not just a theoretical one. `DraftSessionHost.tsx`'s two call sites and `MemberManagement.tsx`'s `submitRoleChange` all read `res.json()` today to build their own generic-error message (`body?.error?.message ?? "<call-site-specific default>"`) inside their `!res.ok` branch. With only a boolean, a caller that gets `isSessionExpired: false` back on a 401 has no way to recover that message without reading the body a second time — which throws, since the helper already consumed it. Returning `body: unknown` (the same parsed object the helper checked `category` against, or `null` if parsing failed) lets every caller derive its own message the same way it does today — `(body as { error?: { message?: string } })?.error?.message ?? "<default>"` — from the single read the helper already performed. The helper does not attempt to type or validate `body` beyond parsing it as JSON; each caller narrows it the same way it narrows a directly-read body today.
- **Checks `status === 401 AND` parsed `category === "session_expired"`**, not bare `status === 401` alone. A route-specific authorization 401 that isn't a session-timeout (`provider_unavailable` above, or, per the deferred `teams.ts` case, a data-integrity 401 mislabeled `invalid_request`) must not be mis-routed into a "your session expired" message that isn't true.
- **`role` is caller-supplied, never derived.** Nothing in the 401 body says whether the caller is a facilitator or a participant — that's page-level context (which button rendered, which route it is). Each call site passes its own `role` through to `ReauthRequiredTreatment`, the same way `ConnectionStatusBanner.tsx`/`FacilitatorReadinessGrid.tsx` already do.
- **`returnTo` is computed by the caller, not the helper**, as `window.location.pathname + window.location.search` — identical to every existing call site, not something the helper should own since it has no reason to know the current URL beyond what `window.location` already exposes uniformly.

**Alternative considered:** hand-edit each call site's existing `if (!res.ok)` branch to add a `res.status === 401` check inline, no shared function. Rejected — the whole point of this change is that these call sites currently duplicate the same "generic non-ok handling" shape independently; letting six call sites each reimplement the 401 special-case too just relocates the duplication problem instead of closing it, and risks the `status === 401` vs. `status === 401 AND category === "session_expired"` distinction getting implemented inconsistently across call sites.

### Decision 1a: `role` determination per call site, stated explicitly for the two cases that aren't "obviously the current page's actor"

Decision 1 states `role` is caller-supplied, never derived by the helper. That's necessary but not sufficient — per BA review Finding 2, "pass the caller's role" was implicit enough at two call sites that it wasn't actually computable as originally stated. Stated explicitly, per call site:

- **`SessionLobbyPage.tsx`'s `start` and `begin-voting` POSTs — `role` is `"facilitator"`.** Both are only reachable from UI already gated on `branch.isFacilitator === true` (the facilitator-only controls block, `SessionLobbyPage.tsx:234`) — by the time either POST fires, the page already knows the caller is the facilitator. No ambiguity.
- **`SessionLobbyPage.tsx`'s `action-items-review` GET (`fetchReview`) — `role` is `session?.canFacilitateSessions ? "facilitator" : "participant"`, an explicit proxy, not the page's own `isFacilitator` distinction.** This is the call that *establishes* `branch.isFacilitator` in the first place (`setBranch({ kind: "lobby", isFacilitator: body.isFacilitator })`, reached only on a 200 or a 409). If this exact call 401s instead, `isFacilitator` was never set for this page instance — there is no existing facilitator/participant distinction to match yet, which is what an earlier draft of this design and spec.md's requirement text assumed was available. `useAuth()`'s `session.canFacilitateSessions` (`packages/shared/src/types/auth.ts`, already in scope at `SessionLobbyPage.tsx:63` via `const { session } = useAuth()`, not otherwise used on this page) is the one signal actually available before this fetch resolves. It's an imperfect proxy — it answers "can this user facilitate sessions at all," not "is this user the facilitator of *this specific* session" — but it's an acceptable one here because `role`'s only effect is which sentence `ReauthRequiredTreatment` renders (Decision D4 of `session-timeout-continuity`, restated at the top of that component's file), not any authorization decision, and in practice this application has exactly one facilitator per team, so the proxy is correct except in the narrow window where a `canFacilitateSessions` user is viewing a session someone else on their team facilitates.
- **`DraftSessionHost.tsx`'s two call sites, `SessionCreationPage.tsx`'s two call sites — always `role="facilitator"`.** Both pages are gated on `canFacilitateSessions` before rendering at all; unconditional, no derivation needed.
- **`MemberManagement.tsx`'s `submitRoleChange` PATCH — `role="facilitator"`, used only to suppress the vote-loss sentence, not as a facilitator claim.** This call site isn't in a session context at all — it's a team-role-management action by an EM or Application Admin. Neither `ReauthRequiredTreatment`'s prop values describe that actor literally; `role="participant"` would append "Any vote you haven't submitted yet will be lost," which is false here (there is no vote to lose — this isn't a voting session), while `role="facilitator"` unconditionally omits that sentence (`ReauthRequiredTreatment.tsx`'s own comment: "facilitators never vote... factually inapplicable to that role, unconditionally"). `role="facilitator"` is the correct choice for what it does — suppress an inapplicable sentence — not for what it claims about the caller. Stated here so it isn't read as a mistake or a copy-paste from the other facilitator-gated call sites.

### Decision 2: Dual-signal detection on `SessionLobbyPage.tsx` — fetch-response AND `useConnectionHealth` state, first-wins/second-is-no-op

`SessionLobbyPage.tsx` is the one call site in this inventory that already has a second, independent signal in hand: it calls `useConnectionHealth(connect)` for its own WS subscription but destructures only `{ socket }`, discarding the `state` value — the same `"connected" | "unknown-reconnecting" | "reauth-required"` machine the WS-side fix already wired to `ABSOLUTE_LIFETIME_MS`. The moment the same 90-minute ceiling this issue cares about elapses, `state` on this page already flips to `"reauth-required"` — the page just never looks at it.

**Decision:** consume both signals, not one instead of the other.
1. Every fetch call site on this page (including this page's own three) runs its response through Decision 1's helper, exactly as every other in-scope page does.
2. Additionally, this page renders `ReauthRequiredTreatment` when `state === "reauth-required"`, mirroring `SessionConnectionHost.tsx`'s existing consumption of the same signal.
3. **Idempotency rule:** whichever signal arrives first renders the treatment; the other, whenever it arrives, is a no-op — it does not re-render, re-trigger navigation, or cause a flicker. This is a single shared gate (has the treatment already been shown for this page instance), not a priority order between the two channels. Its structural home is specified below, not left to implementation.

**Structural home for the gate — required, not left to implementation.** `SessionLobbyPage.tsx` today renders its detection signals from four independent, non-mutually-exclusive JSX locations: the `branch.kind` union itself (`"loading" | "error" | "no-access" | "left" | "lobby" | "pre_session"`), `startError` (local state, rendered nested inside the `branch.kind === "lobby"` block), `beginVotingError` (local state, passed into `PreSessionActionItemReview` inside the `branch.kind === "pre_session"` block), and the new `state === "reauth-required"` check (point 2 above, with no existing home). Because there is no ordering guarantee between a POST's own 401 and the WS close (this decision's own point above), a `start`/`begin-voting` session-expiry and the WS-driven check can both be true in the same render pass — and because `startError`/`beginVotingError` render into different DOM locations than a hypothetical top-level WS check, a literal per-call-site wiring of point 1 and an unconditional top-level check for point 2 would render the treatment twice, not once, under that race. "A single boolean gate" therefore needs one shared piece of state, not four independent local ones:

- Add one piece of page-level state, e.g. `const [reauthRequired, setReauthRequired] = useState<{ role: "facilitator" | "participant"; returnTo: string } | null>(null)`.
- All four signal sources write into it the same way: `setReauthRequired((prev) => prev ?? { role, returnTo })`. The `prev ?? ...` guard is the entire idempotency rule — whichever signal calls this first wins and is kept; every later call (the other channel, or the same channel firing again) is a no-op against an already-non-null value, by construction, not by convention.
- The `action-items-review` GET's own session-expiry (task 3.1) still routes through this same shared state, not a new `branch.kind` variant — collapsing it into `branch.kind` would leave it out of step with `startError`/`beginVotingError`/the WS signal, which don't live in `branch` at all; one shared `reauthRequired` value, not `branch.kind` for one signal and something else for the other three, is what keeps all four uniform.
- The component's top-level render gets one early return, before the existing `branch`/`startError`/`beginVotingError` JSX tree: `if (reauthRequired) return <ReauthRequiredTreatment role={reauthRequired.role} returnTo={reauthRequired.returnTo} />;`. This supersedes the entire existing render tree rather than being layered alongside it — the existing four render locations are otherwise untouched (they still exist for the non-expiry case), but none of them independently renders `ReauthRequiredTreatment` anymore; only this one top-level check does.

**`role` for the WS-driven signal (point 2), stated explicitly, not left as an implementer's guess.** `ReauthRequiredTreatmentProps.role` is required. The WS-driven check uses the same proxy Decision 1a already establishes for this page's `action-items-review` call site: `session?.canFacilitateSessions ? "facilitator" : "participant"`. It's the same page, the same available signal, and the same reasoning (an imperfect but acceptable proxy, since `role` only selects which sentence renders) — restated here so it isn't a second, silent instance of the gap BA review's Finding 2 already caught once on this page.

**Why this differs from the WS-side single-detector precedent.** `session-timeout-continuity`'s WS-side fix has exactly one detector because it only ever had one signal to reconcile. This page has two, and they are not redundant: the WS close timer and an in-flight HTTP request's own 401 are two *independently authoritative* evaluations of "now minus sessionCreatedAt" against two different clocks (a server-side scheduled timer vs. a request arriving at `onRequest`), with no ordering guarantee between them. A POST already in flight when the boundary is crossed gets its own authoritative 401 regardless of what the socket is doing; relying on `state` alone would leave a real window where the fetch response arrives before the socket's scheduled close does. The fetch-response check is load-bearing on its own, independent of `useConnectionHealth` — it is not superseded by adding the WS signal, and the WS signal is not superseded by the fetch check either. Both stay live; the idempotency rule is what keeps that safe.

This is also, deliberately, not the same shape of problem as `session-timeout-continuity`'s Decision 5 (facilitator-reconnect broadcast vs. a local per-pod registry): that was two *unreliable* paths independently *guessing* at the same fact, where only one guess could be right. Here, both channels are correct whenever they fire — there's no "wrong" one to distrust, so the fix is first-wins/second-is-no-op, not suppressing either channel.

**Alternatives considered:**
- *Fetch-response only (ignore `state`).* Rejected — leaves the discarded signal on the table for no reason on the one page where it's already free, and the WS close could in principle fire while no fetch happens to be in flight (e.g., the user is idle, not clicking anything) — a case the fetch-response check alone can't catch.
- *`useConnectionHealth` state only (ignore fetch responses).* Rejected — doesn't exist at all on pages with no socket (`DraftSessionHost.tsx`, `SessionCreationPage.tsx` — neither opens a WS), and even on this page, leaves the in-flight-request race window open (above).

### Decision 3: `returnTo` allow-list gains two new shapes, both UUID/literal-pinned, not widened generally

`RETURN_TO_ALLOW_LIST` (`packages/backend/src/routes/auth.ts`) currently accepts `/session/:id` and `/team/:id`, `:id` pinned to this application's UUID format. Two additions, each justified by an in-scope page's actual route:

1. **`/team/:teamId/session/:sessionId`**, both segments UUID-pinned, optional trailing query string tolerated — same style as the two existing entries: `new RegExp(`^/team/${UUID_PATTERN}/session/${UUID_PATTERN}(?:\\?.*)?$`)`. Needed for `DraftSessionHost.tsx`, whose route (`App.tsx`) is exactly this combined shape — neither existing entry matches it today.
2. **`/sessions/new`**, a literal static path with no dynamic segment: `new RegExp(`^/sessions/new(?:\\?.*)?$`)`. Needed for `SessionCreationPage.tsx`. This is a new shape *class* for this allow-list (every prior entry is UUID-anchored; this one is a fixed string) — worth naming explicitly rather than silently extending the pattern style. It's exactly as safe: a literal string match is at least as restrictive as a UUID-anchored one, just without a variable segment to anchor.

Both additions run through the existing `rejectReturnToCharacters` check unmodified — no new validation logic, only new accepted shapes in the existing list.

**Alternative considered:** a single, broader `/team/:id(/session/:id)?` pattern to cover both the bare team route and the combined route in one regex. Rejected — the existing style is one explicit pattern per accepted shape, not parameterized optionality within a pattern; matching that style keeps every accepted shape indepedently readable and auditable, consistent with `session-timeout-continuity` Decision 3's "no broader wildcard" precedent.

### Decision 4: No-partial-execution is a stated requirement `DraftSessionHost.tsx`'s fix depends on, not incidental color

Because `authMiddleware`'s `session_expired` check runs in `onRequest`, before any route handler executes, a `session_expired` 401 on a POST is guaranteed to mean the action never ran server-side. This is load-bearing specifically for `DraftSessionHost.tsx`'s `advance` call: the confirm dialog's own copy states "cannot be undone." That promise survives a reauth interruption only because a 401 on that POST is guaranteed to mean the room did not open. If implementation ever changes how `advance`'s 401 is produced (e.g., moves any part of the session-expiry check into the route handler itself, after some side effect), this guarantee would need to be re-verified before this design's confidence about `DraftSessionHost.tsx` still holds. Stated here so it isn't silently assumed.

**The guarantee also depends on `app.ts`'s wiring order, not only on `middleware.ts`'s own logic.** `authMiddleware`'s `onRequest` hook is registered directly on the root `app` instance (`app.ts`), and every route plugin this change touches (`teamRoutes`, `sessionRoutes`, `facilitatorSessionRoutes`) is registered after that call — Fastify's hook encapsulation means a hook added to a parent context is inherited by every child context registered afterward, which is why this guarantee holds uniformly across every in-scope mutating call site without needing separate verification per route file. A future refactor that moved a route plugin's registration ahead of `authMiddleware`, or wrapped `authMiddleware` in its own scoped `register()` block, would silently reintroduce a partial-execution race without touching `middleware.ts` at all. Naming this so the guarantee's full dependency surface — hook logic and registration order both — is written down, not only inferable from reading `app.ts` cold.

This also grounds the two acceptance conditions for `DraftSessionHost.tsx`'s two call sites, treated as separate, not one implying the other (the GET rehydration on mount, and the POST from the confirm step) — both need the same routing, and Priya Nair's exploration review caught that a mount-time GET fix is easy to skip if only the button click is pictured.

**Named limitation, not fixed here:** `advanceState.phase === "confirming"` is plain React state, not persisted. If a facilitator's session expires while they're sitting on the confirm step (after "Open the Room," before "Yes, open the room"), `returnTo` lands them back on the bare draft view, not back on the confirm step. This is correct, expected behavior consistent with the general `returnTo`-gets-you-to-the-page-not-the-in-flight-action nuance below, not a gap — restated here because this is the one call site in this inventory with a two-step confirm in front of its POST.

### Decision 5: `returnTo` lands on the page, not mid-action — stated, not silently assumed

For a GET call (`action-items-review`, `facilitator-state`, `eligible-for-session`), landing back on the page after reauth is sufficient — the page re-fetches on mount. For a POST call that 401'd (`start`, `begin-voting`, `advance`, `sessions/draft`), landing back on the page does not resume or retry that POST — the user re-triggers the action manually. This is correct behavior, not a gap, and is worth stating explicitly so no implementer assumes "returnTo" means "and also finish what I was doing."

### Decision 6: Inline rendering, never auto-navigate — including on `DraftSessionHost.tsx` under time pressure

Every call site swaps its content for `<ReauthRequiredTreatment role={...} returnTo={...} />` in place, on recognizing the 401 or the WS state — never an automatic `window.location.href` navigation. This matches `reauth-required-client-prompt`'s D1/D2 precedent (assertive/persistent, user-initiated CTA, no auto-navigate) and the WS-side implementation exactly: every existing `reauth-required` surface requires a click, and this isn't the exception.

This applies to `DraftSessionHost.tsx` too, even though it's the one surface in this inventory where "just get the facilitator back in fast, skip the click" is a real-sounding argument (people are already waiting to join). It loses: a facilitator under time pressure is the person least likely to be reading the screen carefully, and getting yanked to a login redirect with no explanation while they still think they're mid-click is more disorienting, not less.

**Layout requirement this does change (not the rendering choice):** `DraftSessionHost.tsx` already has a two-button confirm step ("Yes, open the room" / "Cancel") occupying exactly the layout position this banner would render into. The banner's CTA needs to be visually unmistakable from the confirm dialog's own buttons on this specific page — a rushed facilitator misreading a reauth prompt as another confirm-dialog button is a bad moment to get wrong. **A mock of the reauth banner rendered over the confirm-dialog layout should be reviewed before this is considered visually settled** — tasks.md carries this as its own task, not assumed away as "just reuse the existing component."

### Decision 7: `MemberManagement.tsx`'s `submitRoleChange` — same no-partial-execution guarantee, own named limitation, no new allow-list entry

`submitRoleChange` (`MemberManagement.tsx:127`) is a `PATCH` behind `checkAssignRolesAuthorization` and a two-step confirm flow (422 `requiresConfirmation` → re-submit with `confirmedZeroParticipant: true`, `teams.ts:702-706`). It's wired into the shared helper the same way as every other in-scope call site, with three things worth stating explicitly because this call site's shape doesn't exactly match any other single one:

- **No-partial-execution applies here too, for the same reason as `advance`.** `authMiddleware`'s session-expiry check runs in `onRequest`, before `teams.ts`'s route handler executes — a `session_expired` 401 on either PATCH submission (the first, un-confirmed one, or the second, `confirmedZeroParticipant: true` one) guarantees the role change did not apply server-side. This matters concretely: an EM or Admin retrying after reauth should not need to wonder whether the role already changed. This is the same guarantee spec.md's "disclosed-session-expiry 401 on a POST guarantees the action did not execute server-side" requirement already states generically (not DraftSessionHost-specific in its requirement text, only in its example scenario) — this call site is a second scenario under that same requirement, not a new one.
- **Named limitation, same shape as Decision 4's for `DraftSessionHost.tsx`:** `roleChangeState.status === "awaiting_confirmation"` is plain React state, not persisted. If the session expires while an EM or Admin is sitting on the confirmation step (after the first PATCH returned 422, before they click to confirm), `returnTo` lands them back on the bare member list, not back on the pending confirmation — they re-initiate the role change from scratch. Correct and expected, consistent with Decision 5 below, restated here because this is the second (and only other) call site in this inventory with a two-step confirm in front of its mutation.
- **No new `returnTo` allow-list entry needed.** `MemberManagement.tsx` mounts at `/team/:teamId` (`App.tsx`), which the allow-list already accepts (`RETURN_TO_ALLOW_LIST`'s existing `/team/:id` entry, `auth.ts:75`) — unlike `DraftSessionHost.tsx`'s combined route or `SessionCreationPage.tsx`'s new static path, this call site introduces no new allow-list surface.
- **No Decision-6-style visual-collision mock review needed here, unlike `DraftSessionHost.tsx`.** `submitRoleChange` moves `roleChangeState` off `"awaiting_confirmation"` before the PATCH fires, the same way `openTheRoom` moves `advanceState.phase` off `"confirming"` before its fetch fires — so the per-row "Confirm change" / "Cancel" dialog (gated on `isAwaitingConfirm`) is already gone from the render tree by the time any response, a 401 included, could render the treatment. There's no overlapping layout slot for the banner to collide with: `roleChangeState`'s error/treatment renders at a fixed top-level location, not inside the per-row dialog's slot, and proposal.md names no "someone is waiting on the other end of this click" time pressure for a role change the way it does for `DraftSessionHost.tsx`. tasks.md section 6 carries no mock-review task for this reason.

## Risks / Trade-offs

- **[Risk] Six call sites restructuring their existing `.json()`-consuming error branches to route through one shared helper is a small refactor per site, not a pure addition — a mismatched restructure could silently regress the existing generic-error message for non-401 failures.** → Mitigation: tasks.md requires each call site's existing non-session-expiry error path (500, network failure, other 4xx, the 422 `requiresConfirmation` branch) to keep its current message and behavior, verified by a test per call site, not just the new session-expiry branch.
- **[Risk] The `returnTo` allow-list's new `/sessions/new` entry is the first literal, non-UUID-anchored shape in that list — a future contributor could read it as license to add other loose literal paths without the same scrutiny.** → Mitigation: the design and delta spec both name this as a deliberate, narrow exception (a fixed string, not a wildcard), consistent with how `session-timeout-continuity`'s Decision 3 named its own UUID-pinning as deliberate.
- **[Risk] Deferring `MemberManagement.tsx`'s `loadMembers` GET, the EM pages, and the `teams.ts` category fix means those surfaces keep showing a generic, unexplained "try again" message on session expiry indefinitely, with no tracking issue filed as part of this change.** → Mitigation: proposal.md states this deferral and its reasoning explicitly (not a silent gap); filing the follow-up issue is a task in tasks.md so it doesn't become an implicit TODO that never gets written down.
- **[Risk] `session?.canFacilitateSessions` as the `role` proxy for `SessionLobbyPage.tsx`'s `action-items-review` call site (Decision 1a) is not a literal "is this user this session's facilitator" check.** → Mitigation: the only consequence of a wrong guess is which sentence renders in `ReauthRequiredTreatment`, not an authorization outcome; named explicitly in Decision 1a and spec.md rather than left implicit, so a future reader doesn't mistake the proxy for a precise check if this page's role model ever changes (e.g., co-facilitators).
- **[Trade-off] No live-app verification of the "generic try again forever" failure mode has been performed for any of the six call sites** — like `session-timeout-continuity`'s own design.md, this proceeds on a direct code read (each call site's `if (!res.ok)` branch, traced by hand), not an observed reproduction. Implementation should include a manual or integration-test confirmation that each fix actually resolves the described behavior.
- **[Informational] This change adds no new audit-logging requirement — the two `session_expired` branches its detection actually reaches are already durably audited.** `authMiddleware`'s absolute-lifetime cutoff and `revoked` refresh-result branches both already call `writeSessionInvalidatedAuditRow` and `emitAuditEvent("auth.session_invalidated", ...)` at the moment the 401 is produced, independent of whether or how any client reacts to it (shipped in prior, archived work). The third `session_expired`-producing branch — no session/`userId` at all — is not audited, but that's pre-existing, out of scope (this design changes no part of `authMiddleware`), and not reachable from any of this change's six call sites in a way that matters: a genuinely session-less request never gets far enough to hit any of them.
- **[Forward note, non-blocking, out of scope] `AuthContext.tsx`'s own `/auth/session` 401 handling is a pre-existing, unconditional `window.location.href` navigation, no `returnTo`** — the exact auto-navigate pattern Decision 6 deliberately avoids everywhere else in this design. Not a bug here (the file isn't touched, and a fresh page load has no in-place UI to render into), but it means a user who refreshes an already-expired page gets a silent bounce while a user who's mid-click gets this change's disclosed banner — a real behavioral seam immediately adjacent to this change's problem space, worth knowing about if `AuthContext.tsx` is ever revisited.

## Migration Plan

No data migration. Deploy order:
1. Backend: the two `RETURN_TO_ALLOW_LIST` additions (Decision 3) — backward compatible; an old frontend simply never sends a `returnTo` matching the new shapes yet.
2. Frontend: the shared detection helper, and all six call sites' restructuring to use it (Decisions 1, 1a, 2, 4, 5, 6, 7) — ship together, since `SessionLobbyPage.tsx`'s dual-signal wiring and the other five call sites' single-signal wiring share the same underlying helper and there's no reason to split a change this small across multiple deploys.

Rollback is a straightforward revert at each layer — the allow-list additions are additive-only (no existing accepted shape changes), and an unpatched frontend ignores the new allow-list entries entirely.
