## Why

Issue #146 is the HTTP-side half of a gap `session-timeout-continuity` deliberately split in two and deferred: when a session-scoped fetch call gets back a `session_expired` 401 mid-ritual, the user should land on the same disclosed `reauth-required` treatment — with the same click-through CTA and the same `returnTo` mechanism — that the WebSocket-side absolute-lifetime expiry already routes to. Today it doesn't. `SessionLobbyPage.tsx`'s three in-session actions and `DraftSessionHost.tsx`'s two facilitator-control calls all treat a `session_expired` 401 the same as a 500 or a dropped network connection: a generic "try again" message that doesn't tell the user retrying won't work, because their session is gone. I signed off on deferring this half of the split myself when `session-timeout-continuity` shipped (`champion-signoff.md`, "Not our call, correctly deferred") — the two gaps are qualitatively different in severity, and this is the smaller, second one, now due.

## What Changes

- Add a shared client-side helper that inspects a fetch `Response` and recognizes a disclosed session-expiry (`status === 401 AND` parsed body `category === "session_expired"`), so call sites stop independently reimplementing this check.
- Wire that helper into `SessionLobbyPage.tsx`'s three call sites (`action-items-review` GET, `start` POST, `begin-voting` POST) and `DraftSessionHost.tsx`'s two call sites (`facilitator-state` GET, `advance` POST — a correction to issue #146's own inventory, which didn't name this component). On a recognized session-expiry, the call site renders `<ReauthRequiredTreatment role={...} returnTo={...} />` in place, inline — never an automatic navigation.
- `SessionLobbyPage.tsx` additionally consumes `useConnectionHealth`'s already-available `state` value (today destructured and discarded) and renders the same treatment on `state === "reauth-required"`. This is a second, independent detector of the same 90-minute absolute-lifetime cutoff, not a replacement for the fetch-response check — first signal to arrive renders the treatment, the second is a no-op.
- Add a third `returnTo` allow-list entry for `DraftSessionHost.tsx`'s combined `/team/:teamId/session/:sessionId` route shape, and a fourth, non-UUID literal-path entry for `/sessions/new` (see scope decision below).
- Wire the same shared helper into `SessionCreationPage.tsx`'s two call sites (`eligible-for-session` GET, `sessions/draft` POST) — see scope decision below.
- Wire the same shared helper into `MemberManagement.tsx`'s `submitRoleChange` call site (`PATCH /api/v1/teams/:teamId/members/:userId/role`) — see scope decision below. `MemberManagement.tsx`'s other call site (`loadMembers`, `GET /api/v1/teams/:teamId`) remains out of scope.
- **BREAKING (spec-narrowing, not runtime-breaking):** narrows `reauth-return-to`'s allow-list requirement text to name two additional accepted shapes; no existing accepted shape is removed or behaves differently.

## Scope decision: `MemberManagement.tsx` and `SessionCreationPage.tsx`

Exploration left this open (exploration-notes.md, Open Question 6) rather than defaulting it. I resolved it in the first draft of this proposal by splitting `SessionCreationPage.tsx` (in) from `MemberManagement.tsx` (out, as a whole component). BA review (`propose-review-ba.md`, Finding 1) caught that `MemberManagement.tsx` isn't one call site — it's two — and the deferral reasoning I gave only actually covers one of them. Revising that here: the split is now per call site, not per component.

- **`SessionCreationPage.tsx` — IN SCOPE.** This is the facilitator's session-creation flow (`eligible-for-session` picker, `sessions/draft` confirm-and-create), gated on `canFacilitateSessions` — the same facilitator audience as `DraftSessionHost.tsx`, and its `sessions/draft` POST is the immediate predecessor step to `DraftSessionHost.tsx`'s `advance` POST in one continuous facilitator journey (pick a team → create the draft → open the room). If a facilitator's absolute lifetime expires mid-click on "Create session," they hit the identical "try again forever" failure mode this issue exists to fix — one screen earlier than the call site we're already committed to fixing. Shipping the fix on the second screen of a two-screen flow and not the first would be an inconsistent, confusing half-measure, not a defensible scope line. It needs its own `returnTo` allow-list entry: `/sessions/new` is a static path with no UUID segment, unlike every shape the allow-list has accepted so far.
- **`MemberManagement.tsx`'s `loadMembers` GET — DEFERRED, filed separately.** `GET /api/v1/teams/:teamId` is a team-membership roster read, mounted inside `TeamPage.tsx`, with no ritual action and no mutation that could 401 mid-something-irreversible. It's read-only, lower-stakes, and — per exploration's Correction 1 — this specific call site currently reads `teams.ts`'s `category: "invalid_request"` label for a narrow "user row missing" edge case, not the `session_expired` category this change's detection keys on. Because it's deferred, the `teams.ts` category-label fix (`invalid_request` → `session_expired`, matching `sessions.ts`/`facilitator-sessions.ts`) buys this change nothing for this call site — nothing it builds ever reads that field for a GET that never gets `session_expired` in the first place — so it's correctly left as a separate, non-blocking cleanup issue, not folded in here.
- **`MemberManagement.tsx`'s `submitRoleChange` PATCH — IN SCOPE, reversing my original all-of-`MemberManagement.tsx`-deferred call.** `PATCH /api/v1/teams/:teamId/members/:userId/role` is gated on `checkAssignRolesAuthorization` (Engineering Manager on this team, or Application Admin) — an elevated-capability check, the same shape of gate as `canFacilitateSessions` on `SessionCreationPage.tsx`, just for a different capability. It mutates state, sits behind a two-step confirm flow (422 `requiresConfirmation` → re-submit with `confirmedZeroParticipant: true`) with its own "cannot be undone in one step" shape, and — per Marcus's read of `authMiddleware`'s globally-registered `onRequest` hook — gets the real `category: "session_expired"` 401 on absolute-lifetime expiry, not the mislabeled `invalid_request` category I'd cited when I deferred the whole component. That mislabeling is real, but it's specific to the sibling GET; it never applied to this PATCH, and I was wrong to let one call site's justification stand in for the component's second, different call site.

  Applying my own `SessionCreationPage.tsx` test to it directly: is this the same actor-class hitting the same "try again forever" dead end on an elevated-capability action? Yes. An EM or Admin whose session expires mid-role-change today gets `body.error?.message ?? "Role change failed."` — a message that tells them to retry an action that cannot succeed, with no indication their session is gone. That's the exact failure mode this change exists to fix, on a mutating, confirm-gated, capability-gated call site I'd missed. Leaving it out after fixing `advance` and `sessions/draft` — the same shape of call site — would be the same kind of half-measure I already rejected for `SessionCreationPage.tsx`, just smaller. No new `returnTo` allow-list entry is needed: `MemberManagement.tsx` mounts at `/team/:teamId`, already allow-listed. `role="facilitator"` is passed to `ReauthRequiredTreatment` for this call site — not because the actor is a session facilitator, but because that value is what suppresses the vote-loss sentence, which is unconditionally inapplicable outside a session context; see design.md Decision 1a.
- **The three EM pages (`EmSessionHistoryPage.tsx`, `EmTrendDataPage.tsx`, `EmActionItemsPage.tsx`) — DEFERRED, same reasoning as `MemberManagement.tsx`'s GET.** Read-only EM dashboards, no ritual action, no mutating call site of any kind. Exploration's Open Question 6 bundled these with `MemberManagement.tsx`; that bundle still holds for these three, which is why they're deferred together with `MemberManagement.tsx`'s GET as one later, low-urgency application of the same shared helper — the mechanism this change builds is generic, so extending it later is cheap, and there's no reason to hold the ritual-critical fix on this change for pages that were never mid-ritual to begin with.

## Capabilities

### New Capabilities

- `http-session-expiry-signal`: recognizing a disclosed `session_expired` 401 on a session-scoped HTTP fetch call and rendering the existing `ReauthRequiredTreatment` in place, provider-agnostically, at `SessionLobbyPage.tsx` (three call sites, plus consuming the already-available `useConnectionHealth` WS signal as a second, independent detector), `DraftSessionHost.tsx` (two call sites), `SessionCreationPage.tsx` (two call sites), and `MemberManagement.tsx` (one call site — `submitRoleChange`). Parallel, HTTP-side counterpart to `websocket-staleness-signal`'s existing WS-side detection — reuses that capability's `ReauthRequiredTreatment` component as-is, does not modify it.

### Modified Capabilities

- `reauth-return-to`: the allow-list requirement ("Return-to value is allow-listed by known internal path shape") gains two additional accepted shapes — `/team/:teamId/session/:sessionId` (both segments UUID-pinned) and the literal path `/sessions/new` — alongside the two it already accepts. No existing accepted shape changes.

## Impact

- **Frontend only.** No new backend route. The backend's `session_expired` 401 shape (`authMiddleware`'s `onRequest` hook) and the `returnTo` OIDC round-trip (`/auth/login`, `/auth/callback`) are both already shipped and unmodified by this change, except the allow-list constant itself (`packages/backend/src/routes/auth.ts`'s `RETURN_TO_ALLOW_LIST`).
- Affected files: `packages/frontend/src/pages/SessionLobbyPage.tsx`, `packages/frontend/src/pages/DraftSessionHost.tsx`, `packages/frontend/src/pages/SessionCreationPage.tsx`, `packages/frontend/src/components/MemberManagement.tsx` (`submitRoleChange` call site only), a new shared detection helper module, `packages/backend/src/routes/auth.ts` (`RETURN_TO_ALLOW_LIST`).
- Not touched: `ReauthRequiredTreatment.tsx` (consumed as-is), `websocket-routes.ts`, `connectionHealth.ts`'s state machine, any backend authorization logic, `MemberManagement.tsx`'s `loadMembers` call site, the three EM pages, `teams.ts`'s category labels.
- Forward note, not built here: with `DraftSessionHost.tsx`'s `advance` in scope, a facilitator who hits reauth mid-"Open the Room" produces a narrow stall window on the participant side — there is no "waiting for the facilitator" screen today for a participant to see during that window. Named so whoever eventually builds the participant-facing join/waiting experience knows this failure mode exists; not this change's job to build that screen.
