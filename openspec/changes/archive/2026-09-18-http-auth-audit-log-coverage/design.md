## Context

`websocket-connection-reauthorization` (archived 2026-09-09) added real `audit_log` rows for three *new* WS-triggered events — `session.access_revoked_live` (D2), `session.token_refresh_failed_live` (D3b), `session.connection_recovered` (D9) — while stating plainly, in its own Non-Goals, that the *pre-existing* HTTP-side siblings (`auth.session_invalidated`, `auth.token_refresh_success`, `auth.token_refresh_failure`) were out of scope for that change. This design closes that named gap.

Grounded directly against the current code (`middleware.ts`, `auth.ts`, `audit-logger.ts`, `connection-reauthorization.ts`, `session-store.ts`, migration `8_audit_log.sql`) rather than assuming the WS-side pattern transfers unmodified — it doesn't, in three respects this design addresses head-on:

1. These events fire from a Redis-backed session operation (`session.destroy()`, a Redis session-store write), not a Postgres state transition. There is no domain transaction to join the way `session.reveal_triggered` et al. do — the WS-side events are the correct precedent for the INSERT's *shape* (a bare `db.query()` call) precisely because they have the same property, not because they're an approximation of the transactional pattern used elsewhere in this codebase.
2. The WS-side precedent covers shape only, not failure handling. `runSweepCheck`'s own `INSERT` has no try/catch and runs as an unhandled-rejection-risking `void` call inside a `setInterval` — a non-issue there (no in-flight HTTP request depends on it), but it means this design writes the HTTP-side fail-open behavior from scratch. Nobody should go looking in the WS files for a try/catch to copy.
3. Unlike the WS timers (`actor_ip: NULL`, no live request to source one from), all four call sites here run inside a real HTTP request with `request.ip` available — the first HTTP-triggered write in this codebase's audit trail with that specific shape (fail-open, no transaction, but with a real client IP), which is worth naming rather than silently copying the WS `NULL` convention where it doesn't apply.

The existing HTTP-side audit-write precedent that *does* exist — `content.ts`'s `denyAdminContentAccess`, an awaited `INSERT` before a 403 — has no fail-open handling at all; a DB failure there would propagate as a 500. This design deliberately departs from that precedent for the events in scope here (see Decision D5) and says so explicitly, rather than let a reviewer assume it copied a pattern that doesn't include the behavior this design actually wants.

**Constraint carried forward from standing project guidance:** this auth layer must remain provider-agnostic (Entra is the primary configured IdP today, not the only one this code is allowed to assume). Checked directly against this design's field mapping: `actor_global_role` comes from this application's own `users` table, and `reason`/`failureType` are this codebase's own vocabulary derived from `refreshOidcToken`'s `invalid_grant` classification, not an Entra-specific claim or shape. No part of this design branches on IdP identity.

## Goals / Non-Goals

**Goals:**
- Give `auth.session_invalidated` a durable `audit_log` row at all four of its existing call sites (three in `middleware.ts`, one in `auth.ts`), closing the "three of four `reason` values audited" gap that a `middleware.ts`-only fix would otherwise leave visible.
- State explicitly, as a decision rather than an implicit default, which of the three named events get a row and which don't — the issue left this open by design.
- Reuse the WS-side field-resolution helpers (`resolveActorGlobalRole`, `resolveTeamIdForAudit`) rather than writing a third copy of either lookup.
- Define fail-open behavior for the new write precisely enough to be a testable acceptance condition: both DB round trips it depends on, a bounded timeout distinct from an explicit error, and a paired detectability signal so a sustained failure doesn't silently and permanently thin the audit trail.
- Preserve the existing latency profile of `auth.token_refresh_success`'s hot, ordinary-traffic path untouched.

**Non-Goals:**
- Fixing the structurally identical `audit_log` gap in `auth.ts`'s other six events or any of `join-links.ts`'s three — materially larger surface than this issue was filed to close; named in proposal.md as a recommended follow-on issue, not addressed here.
- NFR-AUTH-005's 90-minute absolute session lifetime's session-continuity/UX behavior during a live Health Check session. A real concern, not this design's to solve — it's about what happens to a ritual mid-flight, not about whether an already-firing event gets a Postgres row.
- Retrofitting `runSweepCheck`'s pre-existing unhandled-rejection gap in `connection-reauthorization.ts`. Unrelated subsystem, unrelated failure mode, not touched here.
- Re-litigating Decision D3c's refresh-token-rotation/reuse-detection residual risk (tracked as issue #34).
- Any admin-facing configuration surface. There is no interval, threshold, or on/off switch in this change to expose, and none is added.
- Cancelling a hung Postgres query on the underlying connection when `withTimeout` times out. `withTimeout` stops the *caller* from waiting; it does not, and this design does not attempt to make it, cancel the in-flight `pg` query or return its connection to the pool early. Named explicitly in Decision D5 and the Risks section as an accepted limitation, not silently assumed away.
- Building or wiring any monitoring/alerting consumer for `auth.audit_write_failed` or any other `AuditEventName`. This design produces a detectable signal; it does not make that signal watched. See Decision D5 and the Risks section.

## Decisions

### Decision D1: Scope — `session_invalidated` gets a row; `token_refresh_failure` does not; `token_refresh_success` does not

**Choice:** Only `auth.session_invalidated` gets a new `audit_log` row, at all four of its call sites. `auth.token_refresh_failure` and `auth.token_refresh_success` remain exactly as they are today — `emitAuditEvent`-only, no DB row, no change to either's emit site beyond `token_refresh_failure`'s two failure branches also feeding `session_invalidated`'s metadata (Decision D2).

**Rationale:**
- `session_invalidated` is the unambiguous match for SEC-13's "logout" and "expiry" categories, across every one of its four `reason` values. It is also already a low-frequency, request-terminating path in every branch — the latency argument that matters for `token_refresh_success` barely applies here.
- `token_refresh_failure` fires from inside `refreshSessionTokens` and, in every branch that reaches it (`"revoked"` and exhausted-retry `"transient_failure"`), is followed within the same request by `middleware.ts` calling `request.session.destroy()` and emitting `session_invalidated` moments later for the identical failure. A second row would mostly restate the first. The one thing it would add — `retryCount` and `failureType` — is preserved instead by relocating it into `session_invalidated`'s own row (Decision D2), so nothing is silently dropped, only moved.
- `token_refresh_success` is the one event of the three that sits in front of ordinary, successful, high-volume traffic — it can land on any authenticated request, including a vote submission or reveal trigger mid-session. It is not one of SEC-13's named categories ("login, logout, failure, expiry" — a successful mid-session token renewal is none of these). There is no current instrumentation in this codebase to pull a real production events-per-minute number for it, and no existing precedent for a bounded query/statement timeout to lean on (`db.ts`'s `pg.Pool` sets none). Absent a real number, the design's answer is the more conservative one available: add zero synchronous DB round trips to this path. This is a stated latency budget, not a felt sense of "a lot of traffic" — the budget is "no additional round trips on the success path of ordinary traffic," full stop, which is achieved by not writing a row here at all rather than by tuning a timeout tight enough to hope it doesn't matter.

**Alternative considered:** All three get a row, matching the WS side's "give every new/adjacent event a row" instinct. Rejected — SEC-13 doesn't require `token_refresh_success` specifically, and the "just be consistent" argument doesn't outweigh a *known* cost (two DB round trips in front of arbitrary authenticated requests, including live-session actions) against an *unquantified* benefit (a row that, for `token_refresh_failure`, would mostly duplicate the `session_invalidated` row that follows it milliseconds later anyway).

### Decision D2: `retryCount`/`failureType` live in `session_invalidated`'s metadata, not a separate row; `authSessionId` and `reason` are unconditional members of that same metadata

**Choice:** Every `session_invalidated` `audit_log` row's `metadata` JSONB unconditionally includes `reason` (the branch that produced the row) and `authSessionId` (the Fastify/HTTP session being invalidated — see naming note below). When `reason` is `"token_revoked"` or `reason: "refresh_failure"`, `metadata` additionally includes `failureType` (`"revoked"` | `"transient"`) and `retryCount` (see below for how this crosses the function boundary). For `reason: "absolute_timeout"` and `reason: "explicit_logout"`, `metadata` contains only `reason` and `authSessionId` — neither `failureType` nor `retryCount` applies, and neither is included.

**Naming — `authSessionId`, not `sessionId` (security review Finding 3, accepted as written):** `audit_log.metadata` is a single JSONB column shared across every `operation` in this table, and `session_id` (snake_case) is already an established convention in that same column for a completely different entity — the Health Check ritual's domain session (`em-views.ts:380`, `facilitator-sessions.ts:57`, both `JSON.stringify({ session_id: ... })`). A bare `sessionId` here would collide with that convention by casing alone, which is exactly the ambiguity `connection-registry.ts`'s `RegisteredConnection.fastifySessionId` field was deliberately named to avoid one layer down, for the identical reason ("`conn.sessionId` next to that was a standing misread risk"). This design reuses that codebase's own precedent rather than reintroducing the collision it already fixed once: the field is `authSessionId` everywhere it appears — in the write helper's parameter, in `metadata`, and in `auth.audit_write_failed`'s payload (Decision D5). An incident responder running `metadata->>'authSessionId'` vs. `metadata->>'session_id'` across this table can no longer confuse the two entities by casing alone.

**Rationale:**
- `failureType`/`retryCount`: this is the one piece of detail `token_refresh_failure`'s own event carries that `session_invalidated` doesn't already have a home for. SEC-12's "reconstruct a sequence of events" framing is exactly the kind of retry/sequence detail this preserves — moving it costs nothing an implementer or reviewer can observe as a gap, since the two `reason` values this applies to map 1:1 onto `token_refresh_failure`'s two `failureType` values.
- `authSessionId`: SEC-13 requires a "target resource identifier" in every audit entry, and for a `session_invalidated` event the resource being acted on is the session, not just the user. The structured log this DB row is meant to outrank in authority already carries this same identifier (as `sessionId`, its pre-existing, unchanged field name in the structured log) at all four call sites today; the new row needs to carry it too, or it would be a step backward in identifiability relative to the log line it supersedes. This matters most exactly where Decision D4 already establishes the underlying fact pattern: a user can hold more than one active session at once, so `session_invalidated` alone — without a session identifier — can't tell an incident responder *which* session this row is about, or let them correlate it back to whichever WS connections were live under that session.
- **`retryCount` actually crossing the function boundary (engineer review Finding 1, corrected here):** as originally written, this design assumed `retryCount` was already available to `middleware.ts`'s `onRequest` hook at the `"revoked"`/`"transient_failure"` branches. It is not — `RefreshResult`'s `revoked` and `transient_failure` variants (`middleware.ts:46-50`) carry no payload today; `retries` is a local variable inside `refreshSessionTokens` that is consumed only by that function's own `emitAuditEvent(..., "auth.token_refresh_failure", ...)` calls before it returns. Verified against the code, not assumed. **Decision, made explicitly here rather than left as a contradiction for an implementer to discover:** scope in the small change needed to actually surface it, rather than drop `retryCount` from `session_invalidated`'s metadata. Concretely: `RefreshResult`'s `revoked` and `transient_failure` variants each gain a `retryCount: number` field, and `refreshSessionTokens`'s two corresponding return statements (currently `return { status: "revoked" }` and `return { status: "transient_failure" }`) populate it from the already-computed `retries` local. This is worth the small addition to a shared return type — it's the only way SEC-12's retry/sequence detail actually reaches the audit row, and the alternative (dropping `retryCount` from metadata entirely) would silently discard information this design's own Goals section commits to preserving. The added field is purely additive (a new required field on two variants of a discriminated union) and structurally invisible to `connection-token-refresh.ts`, the WS-side caller of the same function noted in `middleware.ts`'s own header comment (`middleware.ts:54-58`) — that caller switches on `result.status` today and does not destructure `retryCount`, so it compiles and behaves identically whether or not it reads the new field. Migration Plan step 1 below states this as its own task rather than bundling it into the write-helper work.

### Decision D3: The fourth call site (`auth.ts`'s `explicit_logout`) is in scope

**Choice:** `auth.ts`'s `/auth/logout` handler's `session_invalidated` emission gets the identical `audit_log` row treatment as the three `middleware.ts` sites.

**Rationale:** Leaving this site out produces a visibly incomplete result — three of four `reason` values audited, the fourth silently not, with no stated reason why. The issue's silence on this site reads as scoped-to-`middleware.ts`-by-construction (that's where the archived design's Non-Goal pointed), not as a deliberate exclusion, and shipping this change without it would create exactly the kind of unexplained, discoverable-later gap this codebase has already had to correct once (the archived `websocket-delivery-time-authorization` design's own Decision D7 mistake). Same event name, same shape, same underlying gap — closing three quarters of it and calling the change done is worse than not stating a boundary at all.

### Decision D4: `team_id` is `NULL` on all four rows, uniformly and deliberately

**Choice:** None of the four `session_invalidated` `audit_log` rows attempts to resolve a non-NULL `team_id`, including at the `auth.ts` logout call site, even though that handler runs an active-sessions query (`SELECT s.id FROM sessions s JOIN session_participants sp ...`) one hop away from a real `team_id` via the already-exported `resolveTeamIdForAudit("session", id)`.

**Rationale:** Three separate reasons converge on the same answer:
1. **The three `middleware.ts` sites have no candidate at all.** `onRequest` runs on every authenticated route with no reliable, uniform way to resolve a `team_id` for an arbitrary in-flight request. This part of the reasoning was never in question.
2. **The `auth.ts` logout site's candidate is not well-defined even though data exists.** The active-sessions query only runs when the client has *not* already confirmed logout (`!confirmed`); if it finds active sessions, the handler returns `confirmRequired: true` and does not destroy the session or emit the event at all in that request. By the time `session_invalidated` actually fires — either because the query found zero active sessions, or because the client already passed `confirmed=true` on a follow-up request where the check is skipped entirely — there is either nothing to resolve, or no re-query to resolve it from without adding a DB call whose only purpose is populating one optional audit column. And a user can in principle have more than one active session, possibly across different teams, at the moment of logout: "resolve `team_id` from the active session" has no single well-defined answer in that case, not just an inconvenient one.
3. **Uniformity is itself worth something here.** Three sites legitimately have no answer; making the fourth sometimes carry a real value and sometimes `NULL`, depending on which logout branch happened to fire, would be the same shape of silently-confusing inconsistency Decision D3 exists to avoid for `reason` coverage — just moved to a different column. `NULL` is already a legal, indexed-for state (`idx_audit_log_team ... WHERE team_id IS NOT NULL`); leaving it uniformly `NULL` here is a stated choice, not an oversight, and doesn't foreclose adding real resolution later if a genuine need for it surfaces.

**Investigative path for NULL `team_id` (security review, non-blocking, added so it isn't rediscovered mid-incident):** an incident responder who needs to recover team context for an `explicit_logout` row with `team_id: NULL` should join on `actor_user_id` against `session_participants` (`user_id` column) filtered to rows whose session was active around the row's `created_at` timestamp, then resolve `team_id` from that session's parent `sessions` row. This is a manual reconstruction step, not something the row itself points to — worth stating once here so it's the documented recommended path rather than something an investigator has to re-derive under time pressure during a real incident.

**Not resolved here, named as cheap-to-defer:** whether an explicit logout initiated by a facilitator mid-session (if that's ever a supported in-app action) should be distinguishable, in the audit trail, from an involuntary one. `session_invalidated` already distinguishes voluntary (`explicit_logout`) from involuntary (`absolute_timeout`/`token_revoked`/`refresh_failure`) via `reason` — whether `explicit_logout` needs its own additional actor-context field is a question for whenever (if ever) that product surface exists, not for this change to answer speculatively.

### Decision D5: Fail-open covers both round trips under one true 500ms bound, distinguishes timeout from error explicitly, and pairs with a signal whose detectability claim is stated honestly

**Correction from the reviewed draft (engineer review Finding 2, security review Finding 5):** the original write-up wrapped the `SELECT` (via `resolveActorGlobalRole`) and the `INSERT` in two *independent* `withTimeout(..., 500)` calls and then stated the resulting bound as "≤500ms" in three places (this decision, D6, and the Risks section). Two independently-timed-out sequential awaits worst-cases at ~1000ms, not 500ms — the stated number didn't match the mechanism. **Decision:** rather than restate "~1000ms" everywhere the old number appeared, redesign the mechanism so 500ms is actually the true end-to-end bound — a single `withTimeout` around the whole two-step sequence, not one per step. This is a better fix than just correcting the prose (engineer review's own preferred option): it keeps the latency argument in D6 intact at the number D6 actually needs, and it collapses timeout-vs-error disambiguation to one call site instead of two.

**Choice:** The write path for each `session_invalidated` event is:

```
// metadata's full shape, stated once here so it never needs reconstructing from D2 + the spec's scenarios:
//   { reason: "absolute_timeout" | "token_revoked" | "refresh_failure" | "explicit_logout",  // always present
//     authSessionId: string,                                                                 // always present (SEC-13's target resource identifier)
//     failureType?: "revoked" | "transient",                                                  // only for "token_revoked" | "refresh_failure"
//     retryCount?: number }                                                                   // only for "token_revoked" | "refresh_failure" (see D2)

class AuditWriteTimeoutError extends Error {}

async function writeAuditRow(): Promise<void> {
  const actor_global_role = await resolveActorGlobalRole(userId);
  await db.query(
    `INSERT INTO audit_log (actor_user_id, actor_global_role, actor_ip, operation, team_id, metadata)
     VALUES ($1, $2, $3, 'auth.session_invalidated', NULL, $4)`,
    [userId, actor_global_role, request.ip, JSON.stringify(metadata)],
  );
}

try {
  await withTimeout(writeAuditRow(), AUDIT_WRITE_TIMEOUT_MS); // one 500ms budget for SELECT+INSERT together
} catch (err) {
  const failureMode = err instanceof AuditWriteTimeoutError ? "timeout" : "error";
  emitAuditEvent(request.log, "auth.audit_write_failed", {
    userId, authSessionId, reason, failureMode, sourceIp: request.ip,
  });
  // no rethrow — the 401/logout response proceeds exactly as it would have before this change
}
```

`AUDIT_WRITE_TIMEOUT_MS` is a new module-local constant (`500`), not read from environment or any admin-facing setting (consistent with this codebase's existing "no new configurable surface" discipline for auth timers). `withTimeout` is a small `Promise.race` helper against a `setTimeout` that throws `AuditWriteTimeoutError` — a dedicated sentinel type, not a message-string comparison, so the `catch` block can distinguish "the timer won" from "the DB call itself rejected" with a plain `instanceof` check (this is what makes `failureMode: "error" | "timeout"` actually derivable, not just asserted). `withTimeout` `clearTimeout`s its own timer on the non-timeout path (no dangling timer per call) and attaches a no-op `.catch` to the losing promise when the timer wins, so a query that eventually rejects *after* the race is already decided doesn't surface as an unhandled-rejection warning. There is no existing per-query timeout mechanism in this codebase to reuse (`db.ts`'s `pg.Pool` sets no `statement_timeout`/`query_timeout`), so this is new, narrowly-scoped machinery, not a wrapper around something already there.

**What `withTimeout` does not do, stated explicitly (engineer review Finding 4):** racing a hung query with `Promise.race` stops the *caller* from waiting; it does not cancel the underlying `pg` query or return its connection to the pool. If `resolveActorGlobalRole`'s SELECT or the INSERT is slow because the connection pool is genuinely under pressure — plausibly correlated with a burst of `absolute_timeout` invalidations, i.e. exactly the scenario this design is bounding for — `withTimeout` gives up waiting after 500ms, but the abandoned query keeps holding its checked-out connection until Postgres actually responds, compounding the same pool pressure that caused the timeout. This does not break the fail-open guarantee for the response (that part is unaffected), but it's a real second-order cost, not a solved problem, and full query cancellation is out of scope for this change (see Non-Goals). Named as an accepted trade-off in Risks below.

Additionally, at all four call sites, the existing (otherwise unchanged) `emitAuditEvent(request.log, "auth.session_invalidated", { userId, sessionId, reason })` structured-log call gains a `sourceIp: request.ip` field. This is a small, adjacent fix (security review Finding 1, "related, not blocking"), scoped in here because it is genuinely cheap — `request.ip` is already in scope at every one of these sites for the new DB write — and because leaving it out would mean this design touches all four call sites without closing the exact `sourceIp`/`correlationId` completeness gap the immediately preceding commit (`7e89bb7`) fixed for `auth.success`/`auth.session_created`. `correlationId` is deliberately *not* added to this same log line: unlike `/auth/callback`'s events, which share one `correlationId` minted once at handler entry, none of these four call sites (three in `middleware.ts`'s `onRequest` hook, one in `auth.ts`'s `/auth/logout`) mints or has access to a correlation ID today — verified against the code, not assumed. Inventing one here would be new correlation-ID infrastructure, out of scope for an audit-coverage change; if `/auth/logout` or `onRequest` ever gain one for other reasons, it should be threaded through both the log and `auth.audit_write_failed` at that point, not before.

On any rejection — a thrown DB error, or the timeout firing first — the `catch` block does not rethrow (the already-prepared 401/logout response proceeds exactly as it would have before this change) and emits a new `AuditEventName`, `auth.audit_write_failed`, via `emitAuditEvent`, carrying `{ userId, authSessionId, reason, failureMode: "error" | "timeout", sourceIp }` — deliberately *not* an `audit_log` row itself (if the DB is the thing that's unreachable, writing a DB row about that is not a real fallback).

**Detectability claim, stated honestly (security review Finding 2 — the original wording overstated this):** `auth.audit_write_failed` is a plain, greppable structured log entry — a sustained rate of it is *distinguishable in the log stream* from unrelated request failures, by anyone or anything reading that stream. It is not, today, *monitored*: no alert rule, anomaly-detection job, or dashboard in this codebase reads `audit_log` or any `AuditEventName` stream, including its cited precedent `team.manager_association_rate_limit_check_failed` — confirmed absent by this codebase's own prior security work (`establish-manager-team-relationship/threat-model.md`'s Finding on EM monitoring; `task-3.10-implementation-review-security.md`'s review of that exact precedent event). The original draft's "an operator or alert rule can watch for" phrasing read as if a consumer existed or was assumed; none does. This design's honest claim is narrower: it produces a signal that plays the same *role* `team.manager_association_rate_limit_check_failed` plays — log-only parity with an already-unmonitored precedent, not a new detection capability. Whether anything consumes it is a pre-existing, codebase-wide gap (see Risks), not something this change closes or claims to close.

This answers all four parts of the acceptance condition explicitly:
1. **Scope of round trips covered:** both the `SELECT global_role` (via `resolveActorGlobalRole`) and the `INSERT` run inside `writeAuditRow`, which is itself wrapped in the single `withTimeout` — a connectivity failure on the `SELECT` is treated identically to one on the `INSERT`, and both share one 500ms budget rather than one each. (`resolveActorGlobalRole`'s existing no-row-found fallback to `"unknown"` is unaffected — that's not a failure case, it's the function's documented behavior for a resolvable-but-absent user.)
2. **Detectability, precisely scoped:** `auth.audit_write_failed` is the paired signal, greppable and structurally ready for a future monitoring consumer — see the honest claim above; this design does not itself provide monitoring.
3. **Non-blocking as a stated behavior:** the request proceeds regardless of outcome — this was true before this change (there was no write to fail) and remains true after.
4. **Timeout distinct from an explicit error:** the `AuditWriteTimeoutError` sentinel makes this an `instanceof` check, not string-matching, and `failureMode` carries the distinction into the log signal.

**Why this deliberately departs from `content.ts`'s `denyAdminContentAccess` precedent (awaited, no try/catch, implicitly fail-closed):** that endpoint's 403 audit write failing today would propagate as a 500 to an admin's blocked request — acceptable there because it's a rare, already-denied admin action. `session_invalidated` fires on every session termination in the system, including the routine, high-volume `absolute_timeout` and ordinary logout paths; a Postgres blip should not additionally lock a user out of retrying sign-in on top of whatever already ended their session. Fail-open is the deliberate choice for this event's write, not an oversight relative to the codebase's other pattern.

**Why "non-blocking" here doesn't mean "fire-and-forget, unawaited":** unlike `token_refresh_success` (excluded entirely by Decision D1 for exactly this reason), all four `session_invalidated` call sites are already request-terminating paths where a bounded, single 500ms of added latency before a 401 or logout response is a non-issue — matching this codebase's existing tolerance for `content.ts`'s own awaited pre-403 audit write. Awaiting (with the timeout bound) is simpler than a detached background write with its own separate error-observability path, and there is no in-session, latency-sensitive request depending on this specific response's speed the way there could be for `token_refresh_success`.

### Decision D6: No new race introduced by the three unawaited `destroy()` calls in `middleware.ts`

**Choice:** No change to `middleware.ts`'s existing `request.session.destroy()` calls, which remain fire-and-forget (no callback, not awaited) exactly as today. The new audit write is sequenced after `destroy()` is called and before the 401 reply is sent, identical in position to where `emitAuditEvent` already sits today.

**Checked, not assumed:** this does not introduce a new session-visible symptom. The Redis `destroy()` may still be in flight when the 401 is returned — true today, unchanged by this design. Adding a single, bounded (≤500ms total, per Decision D5's corrected mechanism), awaited audit write between the `destroy()` call and the reply only delays how soon the 401 is sent; it does not change whether `destroy()` has completed by then, and the client already treats a 401 from this hook as terminal regardless of the exact moment the Redis key clears. `auth.ts`'s logout call site is unaffected by this note — its `destroy()` is already properly awaited today, unchanged by this design.

### Decision D7: Reuse `resolveActorGlobalRole` verbatim; `resolveTeamIdForAudit` is not imported at all

**Correction from the reviewed draft (engineer review Finding 5, security review Finding 7):** the original wording said both new call sites "import `resolveTeamIdForAudit`... but... never call it." Taken literally that's an unused import, which fails this repo's `@typescript-eslint/no-unused-vars: "error"` lint rule (`eslint.config.mjs`, no `varsIgnorePattern` exemption) and therefore CI. The intent was always "not needed here" (Decision D4); the prose just said it backwards.

**Choice:** Both new call sites (`middleware.ts`, `auth.ts`) import and call `resolveActorGlobalRole` from `packages/backend/src/realtime/connection-reauthorization.ts` — already exported for exactly this kind of reuse by the WS-side design. Neither site inlines its own `SELECT global_role FROM users WHERE id = $1`. Neither file imports `resolveTeamIdForAudit` at all: Decision D4 already establishes the outcome is `NULL` at every one of these four call sites, and D5's `INSERT` hardcodes `team_id` as a literal `NULL`, not a bound parameter fed by any lookup — there is no code path here that would ever call it. This matches tasks.md 2.4 as already written, which only calls for importing `resolveActorGlobalRole`.

**Rationale:** Several existing HTTP route files (`facilitator-sessions.ts`, `action-items.ts`, `sessions.ts`, `em-views.ts`, `teams.ts`) already each inline their own copy of this one-line query — pre-existing duplication this change does not attempt to clean up. But adding a *fourth* inline copy in `middleware.ts`, when an exported function already exists for precisely this purpose, would compound a problem this design is in a position to simply not add to.

## Risks / Trade-offs

- **[Risk] `AUDIT_WRITE_TIMEOUT_MS` (500ms, now a true single end-to-end bound per Decision D5's corrected mechanism) is a stated engineering judgment, not a number backed by production latency data — this codebase has no existing per-query timeout to calibrate against.** → **Mitigation:** Scoped deliberately to already-terminating paths (a 401 or a logout response) where up to 500ms of added latency has no plausible session-visible cost, unlike `token_refresh_success`, which this design excludes from a row entirely for exactly this reason. If this value proves wrong in either direction (too tight, causing spurious `failureMode: "timeout"` signals under normal DB load; too loose, delaying a 401 further than necessary under real degradation) it's a one-line constant to adjust, not a design change.
- **[Risk] `withTimeout` abandons a hung query without cancelling it — under sustained pool pressure, the abandoned query keeps holding a connection, compounding the pressure that caused the timeout (engineer review Finding 4).** → **Accepted, not mitigated.** This is a real second-order cost of the `Promise.race` approach, most likely to bite during exactly the scenario this design targets (a burst of `absolute_timeout` invalidations under load). Full query cancellation (e.g. tying the query to an `AbortSignal` or a `pg` statement-level cancel) is out of scope for this change (see Non-Goals) — it would meaningfully expand this change's surface for a codebase that has no existing precedent for query cancellation to build on. The fail-open guarantee for the *response* is unaffected either way; only pool health under sustained degradation is the residual concern. Worth reconsidering if a future change gives `db.ts`'s `pg.Pool` a configured max size and connection-pressure becomes observable enough to know whether this actually matters in practice.
- **[Risk] `auth.audit_write_failed` is not actually monitored by anything in this codebase today — nor is any other `AuditEventName`, including its cited precedent (security review Finding 2).** → **Stated honestly, not mitigated by this change.** Decision D5 above states this precisely: the signal is greppable and structurally ready for a consumer, but no alert rule, anomaly-detection job, or dashboard reads `audit_log` or any log-based `AuditEventName` stream anywhere in this codebase — confirmed against this codebase's own prior security findings (`establish-manager-team-relationship/threat-model.md`, `task-3.10-implementation-review-security.md`). This is a pre-existing, codebase-wide gap this design does not create and is not positioned to close on its own; building monitoring is a separate, larger effort. Compounding case worth naming rather than leaving implicit: if the *logging pipeline itself* (not the DB) is what's degraded — the transport-filtering caveat `docs/deployment.md`'s `### Logging` subsection already documents for `emitAuditEvent` generally — then `auth.audit_write_failed` itself can be silently dropped for the identical reason it exists to catch. In that compound scenario, an attacker (or just bad luck) who induces DB/pool pressure at the moment their own session is invalidated degrades this event's coverage from "durable row + log line" back to "log line only" — today's pre-change baseline, not zero evidence — and if the log line is also being filtered, that baseline itself goes dark with no indication anything was lost. Neither half of this compound risk is new: the DB-write failure mode is this design's own fail-open behavior working as intended, and the transport-filtering risk is `docs/deployment.md`'s existing, already-documented caveat. The combination is worth naming so it isn't rediscovered as a surprise during a real incident. `docs/deployment.md`'s at-risk-event enumeration should list `auth.audit_write_failed` as a 19th log-only, no-DB-backing event for exactly this reason (tasks.md 6.2).
- **[Risk] Someone later "completes" this issue's job by adding rows for `token_refresh_success`/`token_refresh_failure` too, not realizing Decision D1 excluded them deliberately.** → **Mitigation:** Decision D1's reasoning is stated here in full, and specs.md states the exclusion as an explicit, testable scenario (not merely a design-doc aside) — a future change that wants to revisit this has something concrete to argue against rather than rediscovering the tradeoff from scratch.
- **[Risk] `team_id: NULL` at the logout call site reads, to a future reader, like an oversight rather than a decision, precisely because the data is "right there."** → **Mitigation:** Decision D4 states the reasoning in full, including the multi-active-session ambiguity and the recommended `session_participants`-based investigative join for when that context is genuinely needed, specifically so this doesn't get "fixed" into an ambiguous resolution later without re-deriving why it was left `NULL`.

## Migration Plan

1. Extend `RefreshResult`'s `revoked` and `transient_failure` variants (`middleware.ts:46-50`) with a `retryCount: number` field, and update `refreshSessionTokens`'s two corresponding return statements to populate it from the already-computed `retries` local (Decision D2 correction). Confirm `connection-token-refresh.ts` (the WS-side caller of `refreshSessionTokens`) compiles and behaves unchanged — it switches on `result.status` only and does not destructure the new field.
2. Add `AUDIT_WRITE_TIMEOUT_MS` constant, the `AuditWriteTimeoutError` sentinel class, and a small `withTimeout` helper (co-located with the new write logic; no existing timeout utility in this codebase to extend) — one `withTimeout` call wraps the full SELECT+INSERT sequence per Decision D5's corrected mechanism, not one per call.
3. Add `auth.audit_write_failed` to `AuditEventName` (`audit-logger.ts`), with the file's existing documentation convention for new event names, payload `{ userId, authSessionId, reason, failureMode, sourceIp }`.
4. `middleware.ts`: at each of the three `session_invalidated` emission sites, call the new write helper (Decision D5) after `request.session.destroy()` and before the corresponding `emitAuditEvent`/reply, passing the branch-specific `reason` and, for `"token_revoked"`/`"refresh_failure"`, the `failureType`/`retryCount` now actually available on `RefreshResult` per step 1. Add `sourceIp: request.ip` to the existing, otherwise-unchanged `emitAuditEvent(..., "auth.session_invalidated", ...)` call at each site.
5. `auth.ts`: at the `/auth/logout` handler's `session_invalidated` emission (after the already-awaited `destroy()`), call the same write helper with `reason: "explicit_logout"`, no `failureType`/`retryCount`; add `sourceIp: request.ip` to that site's existing `emitAuditEvent` call too.
6. Both call sites import `resolveActorGlobalRole` from `connection-reauthorization.ts` rather than inlining a lookup; neither imports `resolveTeamIdForAudit` (Decision D7).
7. Update `middleware.test.ts` (add `db.js` and `resolveActorGlobalRole`-module mocks it does not have today) and confirm `auth.test.ts`'s existing `db.js` mock is extended to satisfy the new SELECT/INSERT calls without disturbing its existing query-mock assertions — necessary scaffolding, not incidental to task 5.3 (engineer review Finding 3; see tasks.md Section 5, tasks 5.1-5.2).

   **As shipped, this step's mocking approach differs from the line above, deliberately (implementation-review-security.md, non-blocking observation):** `middleware.test.ts` mocks `session-invalidation-audit.js` directly at the module boundary, rather than mocking `db.js` and `resolveActorGlobalRole` — `middleware.ts` only ever reaches those transitively, through `session-invalidation-audit.ts`, so mocking that one module is sufficient and avoids duplicating the timeout/fail-open coverage that module's own dedicated test file already provides. `auth.test.ts` does mock `db.js` directly (as originally instructed here) and lets the real `writeSessionInvalidatedAuditRow` → `resolveActorGlobalRole` → `db.query` path execute against that mock. Both are functionally sound; this is noted so the literal instruction above isn't mistaken for an unaddressed task when read against the diff.
8. No migration file — `audit_log.operation` is unconstrained `TEXT`; no schema change needed to add rows under the existing `auth.session_invalidated` value.
9. Update `openspec/specs/auth-error-handling/spec.md` per this change's delta spec (existing "Authentication event logging" requirement's `Session invalidation logged` scenario updated; new requirements added for the DB-row scope/fields, the deliberate `token_refresh_success`/`token_refresh_failure` exclusion, and fail-open/detectability behavior).
10. Update `docs/deployment.md`'s `### Logging` at-risk-event enumeration to list `auth.audit_write_failed` as a 19th log-only, no-DB-backing event (security review Finding 6).

**Rollback:** Standard code-level rollback (revert the deploy). No feature flag exists or is needed — this is a straightforward additive instrumentation change with no runtime toggle to disable.
