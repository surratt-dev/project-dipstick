# Exploration Notes: http-auth-audit-log-coverage

**Author:** Devon Calloway (Internal Champion / SME), explore stage, GitHub issue #30.

## What this is, and what it isn't

Issue #30 is the footnote `websocket-connection-reauthorization` (issue #27, archived 2026-09-09) deliberately declined to absorb. That design's Non-Goals section names it in so many words: *"Retroactively adding `audit_log` rows to the pre-existing HTTP-side `auth.session_invalidated`/`auth.token_refresh_success`/`auth.token_refresh_failure` events... worth its own tracking issue, not fixed here."* Decisions D2 and D3b of that design gave the three **new** WS-triggered events (`session.access_revoked_live`, `session.token_refresh_failed_live`, `session.connection_recovered`) real `INSERT INTO audit_log` coverage, correcting the archived `websocket-delivery-time-authorization` design's own Decision D7, which had made the identical mistake once already (shipping `emitAuditEvent`-only and needing a security-review finding to catch it). #30 is that same correction, applied to the three older HTTP-side siblings that were never touched.

I want to hold this to the same scope discipline the #27 design.md modeled, and be explicit about what I'm not deciding here, per the issue's own "What this issue is NOT" section:

- Not choosing which of the three events get a DB row, or whether it's all three. I'll lay out the considerations below — volume, severity, what "authoritative" even means for an event with no Postgres state-transition to piggyback on — but that's a Design-stage call, and the issue is explicit that this isn't pre-selected.
- Not designing the exact field mapping. Same reasoning.
- Not fixing the wider gap I found while grounding this (see below) — but I'm naming it clearly rather than letting it hide, because it changes how I'd frame "done" for this change.

## Grounded in what's actually built today

I read `middleware.ts`, `audit-logger.ts`, and both realtime files the issue points to, plus `auth.ts`, `session-store.ts`, and the `audit_log` migration itself, rather than taking the issue's characterization on faith. A few things are worth stating precisely because they change what "follow the WS-side pattern" actually means here:

- **The three named events, traced to their exact call sites in `middleware.ts`:**
  - `auth.session_invalidated` fires from three branches of the `onRequest` hook: absolute-timeout (`reason: "absolute_timeout"`, line 172), revoked-refresh-token (`reason: "token_revoked"`, line 202), and exhausted-retry transient failure (`reason: "refresh_failure"`, line 213). All three call `request.session.destroy()` **without awaiting it** — no callback, no `await new Promise(...)` wrapper — immediately before `emitAuditEvent` and the 401 reply.
  - `auth.token_refresh_success` / `auth.token_refresh_failure` both live inside the extracted `refreshSessionTokens` (also in `middleware.ts`, shared with the WS-side timer via a `source: "http" | "websocket"` parameter — Decision D3 of the #27 design). `token_refresh_failure` carries `failureType: "revoked" | "transient"` and `retryCount`.
- **`auth.session_invalidated` has a fourth call site the issue doesn't mention: `auth.ts`'s `/auth/logout` handler (line 424), `reason: "explicit_logout"`.** Same event name, same shape, same gap — no DB row anywhere. Unlike the middleware.ts destroy() calls, this one *is* properly awaited (`await new Promise<void>((resolve) => { request.session.destroy(() => resolve()); })`, line 420-422). I don't think the issue's silence on this site is a decision to exclude it — it reads more like the issue was scoped to `middleware.ts` specifically because that's where the #27 design's Non-Goal pointed, and nobody grepped for the event *name* across the whole codebase. Worth flagging plainly: if the fix covers only `middleware.ts`'s three call sites, `auth.session_invalidated` will have DB rows for three of its four `reason` values and not the fourth, which is a strange, hard-to-explain gap to leave in a completed change. I'd want whoever designs this to at least make that a stated, deliberate exclusion rather than an accident of where the issue happened to point.
- **This is actually a bigger, older gap than the issue names, and I want that on the record even though it's explicitly not this issue's job to fix.** I grepped every `INSERT INTO audit_log` call site in the codebase. Every one of them lives in `teams.ts`, `sessions.ts`, `facilitator-sessions.ts`, `action-items.ts`, `em-views.ts`, `content.ts`, or the three `realtime/` files #27 added. **Zero live in `auth.ts` or `join-links.ts`.** That means `auth.authorization_initiated`, `auth.callback_received`, `auth.success`, `auth.failure`, `auth.first_access_created`, `auth.role_claim_mapped`, `auth.idp_logout_failed`, `join.link_created`, `join.link_redeemed`, and `join.link_rejected` are *all* `emitAuditEvent`-only today, with the identical structural gap this issue is about. BRD SEC-13 is unambiguous that "login... failure, expiry" belong in "the audit log" — not just expiry. Recent commits (`7e89bb7`, closes #4) added `sourceIp`/`correlationId` fields to `auth.success` and `auth.session_created`'s structured-log calls, which tells me this file has had recent, careful attention — and the DB-row gap still wasn't the thing that attention closed. My read of the timeline: DB-row discipline for `audit_log` seems to have started around the TEAM-005/006 work (migration 8, `establish-manager-team-relationship`) and was applied consistently to everything built after that point; `auth.ts`, `join-links.ts`, and `middleware.ts` predate it and were never retrofitted. Issue #30 closes part of that retrofit debt, not all of it. **I'm not asking this change to absorb the rest** — that's exactly the kind of scope creep I'd flag in review if someone else proposed it — but whoever archives this change should open the follow-on tracking issue for `auth.ts`/`join-links.ts`'s login/logout/join events the same deliberate way #27's design.md spun this one off, rather than let it quietly stay a known-but-untracked gap.
- **`audit_log`'s schema (migration `8_audit_log.sql`) constrains the field mapping regardless of which events get rows:** `actor_user_id` and `actor_global_role` are `NOT NULL`; `actor_ip`, `target_user_id`, `team_id` are all nullable; `metadata` is `JSONB`, nullable. `SessionData` (`session-store.ts`) does **not** carry `global_role` — so, exactly like the WS-side code, a DB lookup (`SELECT global_role FROM users WHERE id = $1`) is unavoidable before any of these three events can get a row. `connection-reauthorization.ts` already exports `resolveActorGlobalRole` for exactly this; the HTTP-side fix should call that, not write a third copy of the same query. (`facilitator-sessions.ts`, `action-items.ts`, `sessions.ts`, `em-views.ts`, `teams.ts` each currently inline their own copy of this same one-line query rather than sharing it — that's pre-existing duplication, not something I'd ask this change to clean up, but it's the reason I'd push back hard on a fourth inline copy landing in `middleware.ts` when an exported function already exists for this.)
- **Every existing HTTP-triggered `audit_log` INSERT in this codebase supplies a real, non-NULL `team_id`.** The only `NULL team_id` writes today are the three WS-side background-timer events, and those are `NULL` because they're driven by a connection's `scope`/`id`, not a live request. `middleware.ts`'s `onRequest` hook runs on *every* authenticated route — `/api/teams/...`, `/api/sessions/...`, `/api/action-items/...`, whatever — with no reliable, uniform way to resolve a `team_id` for an arbitrary in-flight request at the point a token needs refreshing or a session needs destroying. I don't think there's a real team_id to source here, and NULL is already a legal, indexed-for state (`idx_audit_log_team ... WHERE team_id IS NOT NULL`) — but this is a genuinely new situation for an HTTP-request-triggered audit write in this codebase, not a copy-paste of an existing pattern. It should be stated as a deliberate choice in design.md, not left for an implementer to notice mid-implementation. (This reasoning covers the three `middleware.ts` sites specifically — it does **not** automatically extend to the fourth `auth.ts` logout call site if that's brought into scope; see the correction under Open Question 2 below.)
- **The "follow the WS-side field-mapping pattern" instruction in the issue is right about the *shape* of the INSERT, but the WS-side code is not, in one respect, the closer precedent — the domain-write-transaction pattern is the wrong one to reach for, and I want to say why explicitly so nobody reaches for it by habit.** Most of this codebase's audit_log writes (`session.reveal_triggered`, `session.state_changed`, `action_item.status_changed`, the `team.*` ones) are deliberately inserted **in the same Postgres transaction** as the domain state-transition they're auditing — that's the whole "authoritative record" doctrine `audit-logger.ts`'s own comments repeat event after event. These three HTTP auth events have no such counterpart: the state transition being audited is a **Redis** operation (`session.destroy()`, or a Redis session-store write via the refresh), not a Postgres write, so there is no transaction to join. This makes the WS-side events (`session.access_revoked_live` et al.) — which are *also* bare, un-transactioned `db.query()` calls, for the identical reason — the correct precedent for the INSERT's *shape*, not an approximation of one. Worth stating outright in design.md so "same transaction" language doesn't get cargo-culted in here from the other call sites.

  **Correction from review (BA):** that precedent covers shape only, not failure handling — I'd stated it in a way that implied both. I read `connection-reauthorization.ts`'s `runSweepCheck` directly to check: its `db.query(INSERT INTO audit_log ...)` has no try/catch, and it's invoked as `void runSweepCheck(...)` from inside a `setInterval` callback in `scheduleReauthorizationSweep` — so a rejected INSERT today is an unhandled promise rejection, invisible to any caller, not a handled fail-open path. That's a non-issue for the WS timer (no in-flight HTTP request depends on it), but it means **Design is writing the HTTP-side fail-open error handling from scratch, not porting an existing pattern.** Nobody should go looking in the WS file for a try/catch to copy. Whether `runSweepCheck`'s own unhandled-rejection gap should be fixed at the same time: no — explicitly deferred, not an open question. It's a pre-existing, unrelated gap in a different subsystem's timer; fixing it isn't this issue's job, and if it's worth fixing it should be its own small issue on its own merits.

## Considerations specific to the request-response path (not present on the WS side)

This is the part that makes "just port the WS-side pattern over" not quite sufficient as a design, and where I think the real thinking for this change needs to happen:

- **These three events fire from inside `authMiddleware`'s `onRequest` hook — a hook that runs before *every* authenticated request's actual handler.** `token_refresh_success` in particular is not a rare, human-scale event the way `team.manager_established` or `admin.team_detail_accessed` are. It fires transparently, mid-request, on ordinary API traffic every time a session's token nears expiry (once per token lifetime per active session — not once per request, since a successful refresh updates `tokenExpiresAt` and the next several requests skip the branch — but at real aggregate volume across every concurrently active session in production). Adding a synchronous `SELECT global_role` + `INSERT INTO audit_log` (two DB round trips) directly in front of the user's actual request, on the *success* path of ordinary traffic, is a different latency/reliability profile than any existing HTTP-side audit write in this codebase — every one of those lives inside a dedicated endpoint handler that's already making several DB calls for its own purpose. I don't think this rules out a DB row for `token_refresh_success`, but it's a real cost that the "should all three get a row" question the issue leaves open needs to actually weigh, not wave through as "it's the same pattern as the others."

  **Sharpened from review (Facilitator + BA):** "a real cost to weigh" isn't yet something Design can act on — it needs a number on at least one side of the scale before this becomes a decision instead of a feeling. Two concrete asks for whoever picks up Design, before this gets decided:
  - **Pull an order-of-magnitude estimate before deciding:** how many `auth.token_refresh_success` structured-log events fire per minute in production today (this already exists as a structured log — the count should be queryable), and what added p99 latency two extra DB round trips represent against this route's existing baseline. Absent real numbers, state an explicit latency budget (e.g., "acceptable if it adds no more than Xms at p99") so the decision has a stated threshold rather than a felt sense of "a lot of traffic."
  - **Frame the answer in terms of who feels it, not just what it costs the backend.** A token refresh can land on *any* authenticated request — including a vote submission, a reveal trigger, or a facilitator action mid-Health-Check-session. Two synchronous DB round trips in front of that response is, in the worst case, latency a facilitator or participant could feel at exactly the moment I'd care most about responsiveness. "Negligible p99 addition" and "negligible p99 addition on the specific requests that happen to coincide with a live session's reveal-adjacent actions" aren't guaranteed to be the same claim, and Design should be able to say which one it's making.
- **Fail-open vs. fail-closed on the audit write itself needs an explicit answer, and I don't think it's the same answer for all three events.** If the `audit_log` INSERT fails (a Postgres blip) on the `token_refresh_success` path, should the otherwise-healthy request proceed anyway (fail-open — matching how this codebase already treats `team.access_grant_mismatch`'s log-only path, and matching plain good sense: an audit-log outage shouldn't lock out the whole user base), or should it be allowed to bubble up and fail the request? I'd argue fail-open for all three — this is different in kind from `team.manager_association_rate_limit_check_failed`'s deliberate fail-closed design, because that's a rate-limit *control* whose entire job is to deny traffic when it can't verify a limit; an audit record failing to write is not itself a reason to deny an authenticated user their session. But "I'd argue" isn't the same as design.md stating it and why — this needs to be a written decision, not an assumption baked into whichever try/catch shape an implementer happens to reach for.

  **Turned into an acceptance condition (from review — BA + Facilitator):** "fail-open" as stated above is a principle, not yet something an implementer or a reviewer could check a PR against. Design needs to state, explicitly:
  1. **Scope of the round trips covered.** Fail-open has to cover *both* DB calls this requires, not just the INSERT — `resolveActorGlobalRole`'s `SELECT global_role` has to fail open too. That SELECT's no-row-found case is already handled gracefully by existing code (falls back to `"unknown"` rather than throwing), so the new failure mode to design for is a genuine DB *connectivity* failure on that SELECT, which is a distinct case from the INSERT failing and needs the same explicit answer.
  2. **Detectability.** Does a failure get a paired observability signal (an error log line, a metric, an alert) so a sustained audit-write outage is itself detectable — the way `team.manager_association_rate_limit_check_failed` exists specifically so an operator can tell "the control is down" from "an unrelated 500"? SEC-12 frames the audit log as the mechanism for post-hoc incident reconstruction; a failure mode that silently and permanently drops rows with no accompanying signal quietly defeats that purpose. Design should say whether an equivalent signal is expected here or explain why it isn't needed at this volume/severity.
  3. **Non-blocking, not just non-fatal.** Fail-open as a *behavior* (the request proceeds after a failure) is different from fail-open as an *implementation* (the request isn't held up waiting to find out whether it needs to fail open). Priya's phrasing from review is the right bar: "not a `try/catch` that still adds the round-trip's latency before deciding to ignore the error." Design should confirm which one is being built.
  4. **Timeout/hang behavior, distinct from an explicit error.** None of the above says what happens if the audit write *hangs* — a connection-pool exhaustion or a slow query — rather than erroring cleanly. Fail-open as described handles a thrown error; it doesn't yet say whether there's a timeout bounding how long the response can be blocked waiting for the audit write to resolve one way or the other. This matters most for `token_refresh_success`, which sits in front of ordinary successful traffic, not only the error/termination paths where a few hundred extra milliseconds is a non-issue. Design should state whether the audit write is subject to a timeout, or whether fail-open is scoped to explicit errors only and a hang is accepted as low-risk given these are short-lived, request-scoped calls.
- **The three `middleware.ts` `request.session.destroy()` calls are fire-and-forget today — no callback, not awaited — while `auth.ts`'s logout handler awaits its own `destroy()` explicitly.** This predates #30 and isn't this issue's bug to fix, but it's directly relevant to sequencing: if the new DB insert is awaited before the 401 reply is sent (my instinct, since these are already error/termination paths where a little added latency is a non-issue), the response will now depend on the audit write completing while the session-destroy it's describing may still be in flight in Redis, unchanged from today. That's an existing inconsistency, not a new one this change introduces, but I'd want it named in design.md rather than silently inherited so nobody attributes a new bug to "the audit change" that was actually already there.

  **Added from review (Facilitator):** I'm not asking #30 to fix this — it's pre-existing and out of scope, same as stated above. But if Design ends up touching this code path at all (for example, to add the awaited audit INSERT next to the unawaited `destroy()`), I want it stated as a checked fact, not an inherited assumption, that this race can't produce a session-visible symptom — a participant or facilitator seeing a confusing "you're logged out, no wait you're not" flicker mid-session. That's a one-line confirmation to write down, not new scope to take on.
- **None of the three events' metadata needs a change to stay provider-agnostic, and I checked this deliberately rather than assuming it.** `actor_global_role` comes from this app's own `users` table, not an IdP claim. `reason` (`absolute_timeout` / `token_revoked` / `refresh_failure` / `explicit_logout`) and `failureType` (`revoked` / `transient`) are this codebase's own vocabulary, derived from `refreshOidcToken`'s `invalid_grant` classification (`middleware.ts`'s `ResponseBodyError` check) — not an Entra-specific field or claim shape. The one place provider behavior *does* matter for this whole area — whether `invalid_grant` reliably means "genuinely revoked" versus "the deployed IdP rotates refresh tokens and this was a legitimate concurrent redemption" — is Decision D3c's residual risk from the #27 design (tracked separately as issue #34), not something #30's field-mapping needs to re-litigate. I looked for a reason this change would need to branch per-provider and didn't find one; flagging that I checked, per the standing instruction that this auth layer must stay provider-agnostic and not get designed Entra-first by default.

## Where this touches the BRD directly

- **SEC-12/SEC-13 are the actual mandate here, not just "the WS-side did it so this should too."** SEC-13 names "user authentication (login, logout, failure, expiry)" as a required audit-log category, in that order, with "logout" and "expiry" both explicit. `session_invalidated` (all four reasons, including the `explicit_logout` one the issue doesn't name) is squarely "logout" and "expiry." SEC-12 frames the audit log as the mechanism for post-hoc incident reconstruction — which is precisely the thing an `emitAuditEvent`-only structured log line doesn't durably guarantee the way a `NOT NULL`-actor, indexed Postgres row does.
- **SEC-14 is worth reading against what actually happened here, because it cuts the opposite direction from how it reads on paper.** SEC-14 requires "WebSocket events must be logged with the same fidelity as HTTP requests" — written, I'd guess, on the assumption that HTTP was the fidelity baseline WS needed to catch up to. What actually happened is the reverse: #27 gave the *new* WS-triggered events real DB rows, while the *pre-existing* HTTP-side equivalents were never retrofitted — so today the WS side has strictly more audit fidelity than HTTP for structurally identical events (a connection/session losing its authentication). #30 is, in effect, catching HTTP up to a bar the WS side already cleared. Worth a line in design.md if only so nobody reads SEC-14 backwards later and assumes HTTP was already the reference implementation.
- **This doesn't create a new admin-configurable surface, and I checked for that specifically because it's the thing I always check for.** There's no interval, no threshold, no on/off switch implied by "add a DB row to an existing emit site" — this is a straightforward instrumentation fix, not a new mechanism with knobs. I don't have a standing concern to raise here the way I did for #27's timers; I'm noting the check, not a finding.

## Open questions for whoever picks up Design

1. **Which of the three events get a DB row — the issue explicitly leaves this open, and I think the honest answer requires weighing the request-path latency point above against SEC-13's plain requirement.** My own instinct, not a decision: `session_invalidated` is unambiguous (it's the actual "logout"/"expiry" security event SEC-13 names, it's already a low-frequency error/termination path, the latency argument barely applies). `token_refresh_failure` is one step removed but still error-path and still low-frequency, and it's already followed by `session_invalidated` in every branch that destroys the session — meaning giving `token_refresh_failure` a row largely duplicates what `session_invalidated`'s own row would already capture moments later, except for the case where a caller wants the retry count / failure-type detail specifically. `token_refresh_success` is the one I'd genuinely want Design to weigh carefully rather than default to "yes, for consistency" — it's the only one of the three on a hot, successful, ordinary-traffic path.

   **Added from review (BA):** the "except for" clause above is doing real work I hadn't resolved. `session_invalidated`'s `reason` field (`token_revoked` / `refresh_failure`) only coarsely maps to `token_refresh_failure`'s `failureType` (`revoked` / `transient`), and `retryCount` has no counterpart on `session_invalidated` at all. If Design decides `token_refresh_failure` doesn't get its own row, `retryCount` and `failureType` need an explicit stated home — `session_invalidated`'s own row (for the `token_revoked`/`refresh_failure` reasons) should carry them in its metadata instead. That should be a stated tradeoff (the detail is moved, not dropped), not a side effect of choosing not to duplicate the row. This is exactly the kind of retry/sequence detail SEC-12's "reconstruct a sequence of events" language cares about.
2. **Should this change also close the fourth call site (`auth.ts`'s `explicit_logout`) even though the issue only names `middleware.ts`?** I've laid out why I think leaving it out produces a visibly incomplete result (three of four `reason` values audited, one not, no stated reason why). This is a scope decision the proposal stage should make explicitly, not something Design should assume either way.

   **Correction from review (BA):** if the answer is yes, its `team_id` treatment should **not** be assumed identical to the three `middleware.ts` sites by default — I'd built the NULL-`team_id` reasoning above entirely around `middleware.ts`'s constraint (an arbitrary route with no reliable way to resolve a team) and hadn't checked whether it actually carries over to `auth.ts`'s logout handler. I read the handler directly: before destroying the session, it already runs `SELECT s.id FROM sessions s JOIN session_participants sp ON s.id = sp.session_id WHERE sp.user_id = $1 AND s.status = 'active'` to populate `activeSessions` for its confirm-required flow. `resolveTeamIdForAudit("session", id)` — already exported from `connection-reauthorization.ts` — is a one-hop lookup away from that same session id, meaning a logout with an active session at destroy time *can* plausibly resolve a real `team_id`, unlike the three arbitrary-route middleware sites. That said, this isn't a decision I should make in an exploration doc either: a user could in principle have more than one active session, possibly across different teams, at logout time — so "resolve team_id from the active session" isn't obviously well-defined when there's more than one candidate. Design should answer explicitly whether to attempt the resolution and what to do in the multi-team-session case, rather than inheriting the `middleware.ts` NULL precedent by default just because it's the pattern already in view.

   **Added from review (Facilitator):** if the fourth call site is included, Design should also confirm whether an explicit logout initiated by a facilitator mid-session (if that's ever a supported in-app action) is distinguishable, in review, from an involuntary one — `session_invalidated` already covers both voluntary and involuntary endings under different `reason` values, so this is really just asking whether `explicit_logout` needs its own actor-context detail the other three reasons don't. Not urgent, and not something this exploration needs to resolve, but cheap to name now.
3. **Fail-open confirmed as the right default for all three, or does Design want a different answer for one of them?** I've stated my instinct above; I don't have the standing to make this a decision in an exploration doc.
4. **Does closing this issue's three (or four) events change how "done" should be described relative to the wider `auth.ts`/`join-links.ts` gap I found?** I'd want the proposal to say, in so many words, "this closes the `middleware.ts` gap named in #30 and does not address the pre-existing, structurally identical gap in `auth.ts`'s other events or `join-links.ts`" — the same explicit disclaimer #27's design.md used for this exact issue — rather than let a reader assume "HTTP auth audit coverage" is now complete once this ships.

## Recommendation on the wider gap

I'm not asking this change to fix `auth.authorization_initiated` / `auth.callback_received` / `auth.success` / `auth.first_access_created` / `auth.role_claim_mapped` / `auth.idp_logout_failed` / `join.link_created` / `join.link_redeemed` / `join.link_rejected` — that's a materially larger surface (nine more event names across two files) than what #30 was filed to fix, and bolting it on here would repeat the exact scope-bleed #27's design.md was careful to avoid. What I'd ask for instead is a short, explicit line in this change's proposal.md naming that gap and recommending it become its own tracked issue once #30 closes — the same move that produced #30 itself. I'd rather see this pattern repeat deliberately, issue by issue, than have someone eventually discover the whole thing at once and wonder why nobody said anything sooner.

**A second, unrelated pointer worth naming the same way (from review — Facilitator):** the `absolute_timeout` reason on `session_invalidated` exists because of NFR-AUTH-005's 90-minute absolute session lifetime. A Health Check session with a slow start and a full topic list can run close to that window, and a participant or facilitator hitting a hard, timer-driven logout mid-session is a real session-continuity concern — nobody should discover that by having it happen to them mid-ritual. I agree this is worth a line in whatever follow-on issue gets filed for the wider auth gap, or its own issue: "the 90-minute absolute timeout's *behavior* during a live session — not just its audit coverage — deserves a look from a session-continuity/UX angle." That's the full extent of what belongs in this document. The timeout policy itself — whether it should be facilitator-controlled, extendable mid-session, or paired with a graceful re-auth that preserves session state — is not this issue's problem to solve, and I'd push back on treating it as one. #30 is about whether an already-existing event gets a Postgres row; it is not the place to reopen NFR-AUTH-005.
