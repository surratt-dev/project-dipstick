# Facilitator Review: http-auth-audit-log-coverage Exploration Notes

**Reviewer:** Priya Nair (Facilitator / SME persona)
**Reviewed:** `exploration-notes.md`, explore stage, issue #30

## Framing — reading this honestly, from where I sit

I want to be straightforward about something before the specific notes: I'm the person you consult when a change might alter the *feel* of a live Engineering Health Check session — the reveal, the readiness grid, outlier flagging, session pacing. This exploration is about adding Postgres rows for three (or four) auth-middleware events that already exist as structured log lines. There is no facilitator view, no participant-facing surface, no session flow, and no UI in scope here. So the direct answer to "does this capture real user pain points and workflow friction" is: **it captures a real pain point, but not a user's** — it's an incident-responder's pain point (SEC-12's "post-hoc incident reconstruction"), not a facilitator's or a team's. That's fine and worth saying plainly rather than stretching my usual lens to fit where it doesn't.

That said, I don't think this document is *free* of session-experience consequences. A few places touch things I do care about, and I don't see them named as such in the notes — not because Devon missed them technically, but because they weren't looked at through a "does someone feel this during a live session" lens. That's the gap I can usefully fill here.

## Observations

1. **The `token_refresh_success` hot-path latency point is the one piece of this document that is actually a facilitator/participant-facing concern, and it isn't framed as one.** The notes correctly identify that this event fires "transparently, mid-request, on ordinary API traffic" and that adding a synchronous `SELECT` + `INSERT` in front of the response is "a different latency/reliability profile than any existing HTTP-side audit write." What isn't said: a token refresh can land on *any* authenticated request, including a vote submission, a reveal trigger, or a facilitator action mid-session. If that request now carries two extra DB round trips synchronously, the person on the other end feels that as lag on the exact actions where I care most about responsiveness — casting a vote right before reveal, or the facilitator hitting "reveal" itself. The notes treat this purely as a backend cost/volume question. I'd want it treated as a "could this ever add visible latency to a reveal-adjacent action" question too.

2. **The fail-open recommendation is right, and it's the one place this document already protects the thing I'd protect.** I want to affirm rather than just critique: Devon's instinct that an audit-write failure shouldn't block the underlying request is exactly the property that keeps this invisible to a session in progress. If this had leaned fail-closed on `token_refresh_success`, a Postgres blip mid-session could turn into a facilitator or participant getting logged out or stalled *because the audit log had a hiccup* — that would be a session interruption caused by the observability layer, which is the worst kind of interruption because nobody in the room would understand why it happened. Whoever picks up Design should keep this decision and state it as loudly as the notes suggest.

3. **The absolute-timeout / `session_invalidated` event surfaced here is a bigger deal to me than its treatment in this document suggests, even though it's genuinely out of scope for #30.** The notes mention NFR-AUTH-005's 90-minute absolute session lifetime only in passing, as background for why `reason: "absolute_timeout"` exists. But from where I sit: a Health Check session with a slow start, a long discussion on one topic, and several more topics queued up can run close to or past 90 minutes. If a participant's or — worse — the facilitator's session hits that absolute timeout *during* a live session, they get force-logged-out mid-ritual. That's not a logging problem, it's a "the facilitator calls it, not a timer" problem, and it's the exact category of thing I listed as a standing concern (no automatic interruptions, the facilitator controls pacing). I understand this issue is only about *auditing* that event, not changing the timeout policy — but I'd ask that whoever writes the follow-on tracking issue Devon recommends (see below) also flag this as a UX question worth its own look, not just a security-log gap. Nobody should discover this by having it happen to them mid-session.

4. **"Fire-and-forget `destroy()`" being pointed out but explicitly deferred is the right scope call, but I want it on record that I'd treat it differently if it ever surfaces as a session-visible bug.** If a participant's session is destroyed in Redis but the audit write (or the 401 response) races ahead of it, and that ever produces a confusing "you're logged out, no wait you're not" flicker mid-session, that stops being a backend correctness footnote and becomes exactly the kind of thing that makes a tool feel unreliable in the room. I'm not asking #30 to fix it — I'm asking that if Design touches this code path at all, someone actually confirms this can't produce a session-visible symptom, rather than inheriting the ambiguity silently a second time.

## Questions

1. For `token_refresh_success` specifically: has anyone measured (or will Design measure) the added per-request latency of the `SELECT global_role` + `INSERT` pair under realistic concurrent-session load, and is there a latency budget this needs to stay under? "It's a cost that needs to be weighed" is correct but not yet an answer I could act on if I were asked "will facilitators notice this."
2. If the audit-log INSERT fails on a request that's mid-reveal or mid-vote-submission (fail-open, so the request proceeds) — does the failure get surfaced anywhere a facilitator or on-call engineer would see it in time to matter, or does it just silently disappear into an error log nobody's watching until an incident review? Fail-open protects the user experience; it shouldn't come at the cost of the audit gap becoming invisible too.
3. Is there any scenario where the new DB round-trips on the refresh path could push a request past a client-side timeout that the frontend enforces during an active session (e.g., waiting on a reveal or vote confirmation)? The notes don't mention frontend timeout budgets at all, and I don't know this codebase's frontend well enough to know if one exists — but if it does, this is worth checking against it explicitly.
4. On the absolute-timeout point above: is there already a UX treatment for "your session expired mid-Health-Check-session" (a graceful re-auth that preserves session state, versus a hard kick to a login screen that loses context)? If there isn't, that's a separate, real facilitator-facing gap I'd want tracked — this exploration is the wrong place to fix it, but it's the place where I noticed it, so I'd rather say so now than let it go unrecorded.

## Would this lead to a tool that disappears into the background?

Mostly yes, if built the way the notes lean — fail-open, no new admin surface, no behavior change to the actual auth flow, just a DB row alongside an existing log line. That's exactly the kind of change that should be invisible to a session in progress, and I don't have a reason to think it won't be, provided:

- the `token_refresh_success` latency question above gets an actual answer instead of being waved through for "consistency" (the notes' own words — I'd treat that as a flag, not a resolution), and
- fail-open is implemented as genuinely non-blocking (not a `try/catch` that still adds the round-trip's latency before deciding to ignore the error).

The one way this stops disappearing into the background is if the added synchronous work on the refresh path ever becomes perceptible during exactly the moments I care most about — the seconds around a reveal, or a facilitator action mid-session. Nothing in the notes suggests that's likely, but nothing in the notes rules it out with a number either.

## Suggested additions to carry into Design

1. A stated latency budget (or explicit "we measured and it's negligible") for the `token_refresh_success` path, framed in terms of "could a person in a live session ever notice this" — not just "this is a different cost profile than other audit writes."
2. An explicit confirmation that fail-open is implemented as non-blocking, not just non-fatal.
3. A one-line acknowledgment, in whatever follow-on tracking issue gets filed for the wider `auth.ts`/`join-links.ts` gap, that the 90-minute absolute-session-timeout behavior itself (not just its audit coverage) deserves a look from a session-continuity angle — separate issue, separate owner, but worth naming now so it doesn't get rediscovered the hard way during a real session.
4. If Design decides `session_invalidated`'s `explicit_logout` reason (the fourth call site) gets included: confirm that an explicit logout initiated by a facilitator mid-session (if that's ever a supported action) is distinguishable in review from an involuntary one. Not urgent, just flagging it since the notes already surface that this event covers both voluntary and involuntary session endings.
