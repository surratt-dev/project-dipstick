## Why

`websocket-connection-reauthorization` (archived 2026-09-09) gave its own newly-added WS-triggered auth events real `audit_log` rows and, in its own words, left the pre-existing HTTP-side siblings — `auth.session_invalidated`, `auth.token_refresh_success`, `auth.token_refresh_failure` in `packages/backend/src/auth/middleware.ts` — as "worth its own tracking issue, not fixed here." That issue is this one (#30). Today those three events, plus a fourth call site the issue doesn't name (`auth.ts`'s `/auth/logout` handler, `reason: "explicit_logout"`), are `emitAuditEvent`-only: a structured pino log line, which `audit-logger.ts` itself documents as "the operational alert path," not the durable record. BRD SEC-13 requires "user authentication (login, logout, failure, expiry)" in the audit log without qualification, and SEC-12 frames that log as the mechanism for post-hoc incident reconstruction — a guarantee a log line alone doesn't durably provide the way an indexed, non-modifiable-by-the-application Postgres row does (SEC-15). The WS side already clears this bar for the identical event shape (a connection/session losing its authentication); this closes the same gap on the HTTP side, and does so before it accretes further as more auth call sites get added or touched.

**Why now, specifically:** there is no scheduled security review or named customer gate this closes. This is opportunistic hygiene, not urgent compliance work — it's being picked up now because it was discovered as a fully-scoped, cheap-to-close gap while implementing `websocket-connection-reauthorization`, and a ticket this well-defined is worth clearing before it goes stale rather than because a deadline is forcing it. The honest ordering, if it matters: SEC-12/13 are BRD requirements regardless of timing, and this is infrastructure that protects the option to pass a future security review, not something advancing this quarter's adoption metrics. If a real gate does surface later — a team's security function asking to see the audit trail before letting their engineers put real morale data into this tool — this work will already be done instead of being discovered as a blocker at that point.

## What Changes

- `auth.session_invalidated` gains a real `INSERT INTO audit_log` row at all four of its existing call sites — the three in `middleware.ts`'s `onRequest` hook (`absolute_timeout`, `token_revoked`, `refresh_failure`) and the previously-unaudited fourth site in `auth.ts`'s `/auth/logout` handler (`explicit_logout`). This is the one that closes the visibly incomplete "three of four `reason` values have a DB row" state a `middleware.ts`-only fix would otherwise leave behind.
- `auth.token_refresh_failure` does **not** get its own row. Every branch that emits it is followed, moments later in the same request, by a `session_invalidated` emission for the same failure — a second row would mostly duplicate the first. Instead, `retryCount` and `failureType` move into `session_invalidated`'s own row as `metadata` fields when the reason is `token_revoked` or `refresh_failure`. The detail is relocated, not dropped.
- `auth.token_refresh_success` does **not** get a row, and stays exactly as it is today (structured log only). It is the only one of these events on a hot, successful-traffic path — it can fire in front of any authenticated request, including a vote submission or a reveal trigger mid-session — and it is not one of the "login, logout, failure, expiry" categories SEC-13 actually names. Adding synchronous DB round trips to that path buys no BRD-mandated coverage and risks becoming latency a participant or facilitator could feel at exactly the wrong moment.
- The new `audit_log` write fails open, deliberately and explicitly, covering **both** database round trips it depends on (the `resolveActorGlobalRole` lookup and the `INSERT` itself), bounded by an explicit timeout rather than left able to hang, with its own failure signal so a sustained outage of this write path is operationally visible rather than a silent, permanent gap in the audit trail.
- `team_id` is `NULL` on all four `session_invalidated` rows, uniformly, as a stated decision — not an accident of which call site happened to be easiest. See design.md for why this is deliberate even at the logout call site, which has an active-sessions query sitting right next to it.
- No new admin-facing configuration surface, no new interval, no new on/off switch. This is instrumentation of an existing emit site, not a new mechanism.

## Capabilities

### New Capabilities

None. This instruments an existing authentication-event-logging capability; it does not introduce a new domain of behavior.

### Modified Capabilities

- `auth-error-handling`: the "Authentication event logging" requirement's `session_invalidated` scenario is updated to state the new DB-row guarantee and its metadata shape. New requirements are added covering the `audit_log` row's scope and fields, the deliberate exclusion of `token_refresh_success`/`token_refresh_failure` from getting their own rows, and the fail-open/detectability behavior of the write itself.

## Impact

- **Code:** `packages/backend/src/auth/middleware.ts` (`refreshSessionTokens`'s three call sites' worth of `session_invalidated` emissions, and the shape of the data available to them), `packages/backend/src/routes/auth.ts` (`/auth/logout` handler's `session_invalidated` emission), `packages/backend/src/auth/audit-logger.ts` (one new `AuditEventName` for the fail-open detectability signal). No new module — this reuses `resolveActorGlobalRole` already exported from `packages/backend/src/realtime/connection-reauthorization.ts` rather than writing a third copy of that lookup.
- **Data:** No schema migration. `audit_log` (migration `8_audit_log.sql`) already has the columns this needs; `operation` is unconstrained `TEXT`, so no `CHECK` constraint or enum needs updating to add rows under the existing `auth.session_invalidated` operation name.
- **Latency:** A bounded, fail-open DB round trip is added to four already-terminating error/logout paths (each already ending in a 401 or a logout response). No change to the successful-request hot path — that is the entire point of excluding `token_refresh_success`.
- **Explicitly out of scope, named here so "done" isn't overread once this ships:**
  - The much larger, structurally identical gap in `auth.ts`'s other events (`auth.authorization_initiated`, `auth.callback_received`, `auth.success`, `auth.first_access_created`, `auth.role_claim_mapped`, `auth.idp_logout_failed`) and all of `join-links.ts`'s events — none of these have `audit_log` rows today either, and none are touched by this change. This is recommended, explicitly, as its own follow-on tracking issue once this one closes — the same move that produced this issue from `websocket-connection-reauthorization`'s own Non-Goals.
  - NFR-AUTH-005's 90-minute absolute session lifetime's *behavior* during a live Health Check session (whether a hard, timer-driven logout mid-ritual needs a session-continuity fix) is a product/UX question, not an audit-logging one, and is not addressed here. Worth its own future issue; not this one's problem to solve.
  - The WS-side `runSweepCheck`'s own unhandled-promise-rejection gap (`connection-reauthorization.ts`) is a pre-existing, unrelated gap in a different subsystem's timer. Not fixed here; if it's worth fixing, it's its own small issue on its own merits.
  - Decision D3c's residual refresh-token-rotation/reuse-detection risk from the archived `websocket-connection-reauthorization` design is tracked separately as issue #34 and is not re-litigated by this change.
