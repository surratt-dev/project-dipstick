# Design-Stage Security Review — http-auth-audit-log-coverage

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope:** design.md, proposal.md, tasks.md, `specs/auth-error-handling/spec.md`. Verified against actual code, not assumed from prose: `packages/backend/src/auth/middleware.ts`, `packages/backend/src/routes/auth.ts`, `packages/backend/src/auth/audit-logger.ts`, `packages/backend/src/realtime/connection-reauthorization.ts`, `packages/backend/src/realtime/connection-registry.ts`, `packages/backend/src/routes/em-views.ts`, `packages/backend/src/routes/facilitator-sessions.ts`, `packages/backend/migrations/8_audit_log.sql`, `docs/deployment.md`, and the immediately preceding commit (`7e89bb7`, "add sourceIp and correlationId to auth.success and auth.session_created events (closes #4)").

**Bottom line:** The core shape is sound and I would not reopen D1 (scope), D3 (the fourth call site), D6 (no new race), or D7's underlying intent (reuse `resolveActorGlobalRole`, don't write a third lookup). D4's `team_id: NULL` reasoning holds up under scrutiny — I checked whether the logout site's "candidate right there" data actually resolves the ambiguity it claims to, and it doesn't; NULL is the correct call, not just the convenient one. I have three **findings required before implementation** (the new failure signal regresses a completeness bar this codebase fixed one commit ago; the "detectability" claim for that signal has no monitoring behind it anywhere in this codebase, and the design doesn't say so; a metadata field name collision that this exact codebase already hit once and fixed elsewhere) and three **worth-naming, non-blocking** items. None of these require reopening the architecture — all are corrections or additions within it.

## Finding 1 (Required before implementation): `auth.audit_write_failed`'s schema omits `sourceIp` and `correlationId` — regressing the exact bar the immediately preceding commit established for this file

Decision D5 specifies `auth.audit_write_failed`'s payload as `{ userId, sessionId, reason, failureMode }`. I checked this against the commit directly before this design was written: `7e89bb7`, "add sourceIp and correlationId to auth.success and auth.session_created events," whose own commit message states the problem it closed: those two events "did not carry sourceIp/correlationId like every other security-relevant event in the auth callback... made it impossible to trace a complete authentication event through the audit log during an incident investigation." That fix shipped to `main` immediately before this change was proposed.

`auth.audit_write_failed` is, by this design's own framing, a signal meant to be watched for a *sustained rate* during an incident — exactly the kind of event the prior fix was written to make traceable. It omits `sourceIp` even though all four call sites run inside a live HTTP request with `request.ip` already in scope (design.md says so explicitly, Context section, point 3) and even though the new `audit_log` INSERT sitting two lines above it in the same write path already captures `actor_ip` from that same value. It also omits `correlationId` — not applicable at the two `middleware.ts` `onRequest` branches (no per-request correlation ID exists there today), but `auth.ts`'s `/auth/logout` call site has no correlation ID either, unlike `/auth/callback`'s events which all share one minted at handler entry.

This isn't a hypothetical gap — it's the same gap, in the same file, one commit later, on a signal whose entire job is incident traceability. Add `sourceIp: request.ip` to `auth.audit_write_failed`'s payload at minimum (cheap, data already in scope at every call site); if a correlation ID is introduced for `/auth/logout` as part of this work, thread it through here too.

**Related, not blocking:** the *existing*, unchanged `auth.session_invalidated` structured-log emission at all four call sites (`middleware.ts` x3, `auth.ts` x1) also has no `sourceIp` today — `emitAuditEvent(request.log, "auth.session_invalidated", { userId, sessionId, reason })`, verified. This predates this design and isn't its job to fix, but since this design is already touching every one of these four call sites, and `request.ip` is already sitting in the surrounding code (about to be passed to the new `audit_log` INSERT), leaving the *log* emission still missing it is a cheap, adjacent opportunity this design doesn't take. Worth a line in tasks.md rather than leaving it for a third pass at this file.

## Finding 2 (Required before implementation): The "detectability" claim for `auth.audit_write_failed` is not backed by any monitoring in this codebase, and the design states it as if it is

Decision D5 says the paired signal plays "the same 'control is down, not an unrelated 500' role `team.manager_association_rate_limit_check_failed` already plays for a different subsystem," and the Risks section calls a sustained rate of it "distinguishable, in logs or an alert rule, from unrelated request failures" — phrasing that reads as if an alert rule is a live, if unspecified, possibility already accounted for.

I checked whether that's true anywhere in this codebase. It isn't. `docs/deployment.md`'s own Logging section states plainly that every `auth.*` event is "log-only with no database backing anywhere in this codebase" and is at risk of silent loss under a filtering transport, with **no reachability check built** (explicitly deferred, GitHub issue #3). More directly: this codebase's own prior security work already flagged this exact gap for the event D5 cites as precedent. `establish-manager-team-relationship/threat-model.md` (archived): *"I found no alerting rule, no anomaly-detection job, and no dashboard definition anywhere in this repository that reads `audit_log` or the `em.*` log stream... The audit substrate is real and well-built; the monitoring the design doc credits as a compensating control does not exist in this codebase."* And `task-3.10-implementation-review-security.md`, reviewing the precedent event D5 names directly: *"If Redis becomes unreachable, every call to this endpoint will 500, indistinguishable in the logs from any other unrelated 500 on this route, unless someone is specifically watching for a spike."* `team.manager_association_rate_limit_check_failed` is not a proven detection mechanism — it's a well-formed signal sitting in a log stream nobody has wired an alert to, by this codebase's own prior admission.

Citing it as precedent for "operationally detectable" therefore overstates what exists. `auth.audit_write_failed` will be exactly as detectable as that event is today — which is to say, detectable in principle, by someone who greps for it, and invisible in practice until a monitoring/alerting pipeline exists to consume it. This design's own Risks section discusses only the *transport-filtering* caveat (correctly inherited from `docs/deployment.md`) but doesn't name the more basic point: there is no consumer for this signal, or any `AuditEventName`, today. State that plainly rather than implying "an alert rule" is a live backstop, and either (a) file this as part of the same follow-on monitoring gap this codebase has already twice deferred (threat-model.md's Finding 2.3, still open), explicitly naming `auth.audit_write_failed` as another item for it, or (b) don't claim detectability as a mitigation this design provides — only as a signal a *future* mechanism could consume.

## Finding 3 (Required before implementation): `metadata.sessionId` collides with this exact table's existing `session_id` convention — the same naming hazard this codebase already hit and fixed one layer down

Decision D2/D5 puts a bare `sessionId` key in `audit_log.metadata` for the Fastify/HTTP auth session identifier (`request.session.sessionId` — a Redis-backed session-store key, unrelated to any domain row). I checked how this exact column is used elsewhere in this codebase for the *other* thing this application calls a "session" — the Health Check ritual session (the `sessions` table, `team_id`-scoped, votes/topics/participants). `em-views.ts` (line 380): `JSON.stringify({ session_id: sessionId })`. `facilitator-sessions.ts` (line 57): `JSON.stringify({ session_id: params.sessionId })`. Both snake_case, both referring to the domain ritual session's UUID — a completely different entity from what this design's `sessionId` means.

This codebase has already been burned by this exact ambiguity once, one layer down, and fixed it explicitly. `connection-registry.ts`'s `RegisteredConnection.fastifySessionId` field comment: *"Named `fastifySessionId`, not a plain `sessionId`, to avoid collision with this object's domain-level session concept... `conn.sessionId` next to that was a standing misread risk."* That fix was made specifically so a future reader of that object wouldn't conflate the two. This design reintroduces the identical collision one layer up, in `audit_log.metadata` — the table SEC-12 exists specifically so an incident responder can query across operations to reconstruct a sequence of events. An analyst running `metadata->>'session_id'` across this table (matching the existing, more common convention) will silently miss every `auth.session_invalidated` row; one running `metadata->>'sessionId'` expecting a Health Check session id will get an HTTP session identifier instead and misinterpret it. Casing is a thin distinction to rely on for correctness in ad hoc incident-response SQL.

Recommend renaming this field to `authSessionId` (mirroring the codebase's own `fastifySessionId` precedent) before this ships, or at minimum stating explicitly in design.md and the delta spec that `metadata.sessionId` on this operation is the HTTP/auth session identifier, distinct from every other operation's domain `session_id`/`scopeId` in this same column.

## Findings worth naming, not blocking

**4. Fail-open's threat model considers accidental DB failure, not adversarial triggering — and the design doesn't say so either way.** The question I was asked to scrutinize: can an attacker deliberately trigger the 500ms timeout to suppress evidence of their own session invalidation? Directly: no cheap, targeted lever exists — `withTimeout` races a `Promise` against a `setTimeout`; there's no per-request knob a client can pull to selectively slow down *their own* `SELECT`/`INSERT`. But the indirect path is real and undiscussed: an attacker who can drive general connection-pool pressure (concurrent requests against slow endpoints, or simply enough parallel traffic) pushes *every* in-flight query's effective latency up, including this one's, at the moment their own revoked/expired session's request lands. `db.ts`'s `pg.Pool` has no `statement_timeout`/`query_timeout` (design.md notes this itself) and no dedicated reservation for audit writes — a saturated pool degrades this write exactly like every other query. The realistic worst case is bounded, though, and worth stating precisely rather than leaving to inference: the existing `emitAuditEvent(request.log, "auth.session_invalidated", ...)` call is unconditional and unaffected by the new write's outcome (verified — it's untouched by this design at all four call sites), so the worst an attacker achieves is degrading coverage from "durable Postgres row + log line" back to just "log line" — today's status quo, not zero evidence. That compounds badly only in combination with Finding 2's transport-filtering caveat (a log line that's also silently dropped downstream), which the design doesn't connect. Also unspecified: whether `withTimeout` cancels the underlying query on timeout or merely stops awaiting it — if the latter, the abandoned query still holds a pool connection until Postgres actually responds, which under sustained load is exactly the kind of thing that makes the pool pressure causing the timeout worse, not better. Worth a line in the Risks section naming this compounding case explicitly, even if the conclusion is "accepted risk" — an internal app's threat model includes compromised-credential and insider actors deliberately probing failure modes, not just random DB blips.

**5. The stated latency budget undercounts the actual worst case by roughly 2x.** Decision D5's Risks section characterizes `AUDIT_WRITE_TIMEOUT_MS` as adding "a few hundred milliseconds" before the 401/logout response. As written, the `SELECT` (via `resolveActorGlobalRole`) and the `INSERT` are two *sequential*, independently `withTimeout`-wrapped awaits — a worst case where both genuinely hang bounds at up to ~1000ms added latency, not ~500ms. Given these are already-terminating paths this is almost certainly still fine, but "a few hundred milliseconds" undersells it by 2x, which matters if someone later has to explain why a logout felt slow during a real degradation. State the true worst-case bound (or wrap both calls under one shared 500ms budget instead of two independent ones, if a tighter total bound is actually wanted).

**6. `auth.audit_write_failed` isn't added to `docs/deployment.md`'s enumerated at-risk-event list, and it's a self-referential blind spot if it's missed.** Migration Plan step 7 updates the delta spec but neither it nor tasks.md's Section 5 touches `docs/deployment.md`'s Logging section, which currently enumerates "18 events... at risk if a filtering transport is introduced." `auth.audit_write_failed` is deliberately log-only with no DB row (D5's own stated rationale — a DB row about the DB being unreachable isn't a real fallback), which is exactly the shape of event that list exists to track. Add it as the 19th, and note explicitly: if the same filtering transport that could drop it is ever introduced, the fail-open path's *own detectability mechanism* goes dark for the identical reason it exists to catch — the one signal meant to reveal "the audit trail is thinning" can itself be thinned by the exact failure mode it's watching for. Cheap to document, easy to miss if it isn't named.

**7. Minor/cosmetic — Decision D7's text directs an import with no reason to exist.** D7 as written says both `resolveActorGlobalRole` and `resolveTeamIdForAudit` are "imported" at the new call sites, with the latter "never called with a non-NULL-producing intent." Since D5's INSERT hardcodes `team_id` as a literal `NULL` (not a bound parameter fed by any lookup), there's no code reason to import `resolveTeamIdForAudit` at all — an unused import would fail this codebase's lint config. tasks.md's task 1.4, correctly, only calls for importing `resolveActorGlobalRole`. Fix D7's prose to match tasks.md rather than the reverse — not worth a design revision, just a wording correction before an implementer reads D7 literally.

## Answers to the specific questions raised

**Does fail-open create a way for an attacker to suppress evidence of their own session invalidation?** Not a targeted, cheap one. See Finding 4: the realistic degrade is back to today's log-only baseline, not to silence, and reaching even that requires the attacker to also induce general DB/pool pressure, not just wait for a coin flip. The compounding case (pool pressure *and* a filtering transport dropping the fallback log line) isn't discussed in the design and should be named as an accepted residual risk rather than left implicit.

**Is `auth.audit_write_failed` itself monitored, or just another log line nobody reads?** As specified, the latter — verified against this codebase's own prior findings on the exact precedent event D5 cites (Finding 2). The design states detectability as though a consumer exists or is assumed; none does anywhere in this repository today.

**Does NULL `team_id` create a reporting/investigation blind spot inconsistent with SEC-12?** Partially, but it's the correct call, not an oversight — I checked whether the logout site's active-sessions query actually resolves the ambiguity D4 claims, and it doesn't: a user can hold session participation across more than one team at logout time, and there is no well-defined single answer to resolve to without an arbitrary tie-break. NULL is honest about that ambiguity rather than papering over it with a first-match query. The actual blind spot is smaller and different: an investigator will need to know to join `actor_user_id` + timestamp proximity against `session_participants` to recover team context for an `explicit_logout` row, since nothing in the row itself points there. That's a fine trade — but it's a query an incident responder needs to know to run, and neither design.md nor the delta spec states it as the recommended reconstruction path. Worth one sentence in design.md's D4 rationale so it doesn't have to be rediscovered during an actual incident.

## Confirmed sound, not reopened

**D1 (scope: `session_invalidated` only, not `token_refresh_success`/`token_refresh_failure`).** The latency argument for excluding `token_refresh_success` is correctly conservative given no production numbers exist, and I agree a second row for `token_refresh_failure` would be near-duplicate given `session_invalidated` fires moments later in the same request — verified this is true in every branch (`middleware.ts`'s `"revoked"`/`"transient_failure"` cases both call `request.session.destroy()` and emit `session_invalidated` immediately). **D3 (fourth call site in scope).** Correct instinct — leaving `auth.ts`'s logout site out would have been a visibly incomplete fix for no stated reason. **D6 (no new race from unawaited `destroy()`).** Verified: the three `middleware.ts` branches' `destroy()` calls are unchanged, fire-and-forget both before and after this design; inserting an awaited, bounded write between the call and the reply doesn't change whether `destroy()` has completed by the time the 401 is sent, which was already true. **D7's underlying intent.** Reusing `resolveActorGlobalRole` verbatim rather than a third inline `SELECT global_role FROM users` is correct and verified against the actual export in `connection-reauthorization.ts` — my only note on D7 is the cosmetic one in Finding 7 above.
