## 2. Shared write-path plumbing

- [x] 2.1 Add `AUDIT_WRITE_TIMEOUT_MS = 500` constant, an `AuditWriteTimeoutError extends Error` sentinel class, and a small `withTimeout(promise, ms)` helper (Decision D5) in a new module, `packages/backend/src/auth/session-invalidation-audit.ts` (see task 2.3 for why this is a new module rather than co-located in `middleware.ts`). `withTimeout` throws `AuditWriteTimeoutError` on the timer branch, `clearTimeout`s its own timer on the non-timeout path, and attaches a no-op `.catch` to the losing promise so a query that rejects after the race is decided doesn't produce an unhandled-rejection warning. New, narrowly-scoped code; no existing timeout utility in this codebase to extend.
- [x] 2.2 Add `auth.audit_write_failed` to `AuditEventName` in `packages/backend/src/auth/audit-logger.ts`, documented with the file's existing inline convention for new event names (what fires it, why it's log-only with no DB row, and its `{ userId, authSessionId, reason, failureMode, sourceIp }` shape — no `correlationId`: none of the four call sites has one today, see design.md Decision D5).
- [x] 2.3 Add a `writeSessionInvalidatedAuditRow(userId, authSessionId, reason, request, metadata?)`-shaped helper, **exported** from the same new module as task 2.1, `packages/backend/src/auth/session-invalidation-audit.ts`. This is the single, non-duplicated instance of this helper — `middleware.ts` and `auth.ts` (Sections 3 and 4) each import `writeSessionInvalidatedAuditRow` from this module. Neither `middleware.ts` nor `auth.ts` imports `resolveActorGlobalRole` directly; only `session-invalidation-audit.ts` does (from `connection-reauthorization.ts`), so there is exactly one place in this change that imports it and exactly one inline `SELECT global_role FROM users WHERE id = $1` call site (inside `resolveActorGlobalRole` itself, unchanged). Do **not** import `resolveTeamIdForAudit` anywhere in this change — `team_id` is a literal `NULL` in the INSERT, not a bound parameter fed by any lookup (Decision D4/D7).

  **Module choice, stated rather than left as a coin flip (architect review, non-blocking preference, accepted):** a new module — rather than co-locating the helper in `middleware.ts`, as originally left open — avoids introducing a one-directional `routes/auth.ts` → `auth/middleware.ts` import edge that doesn't exist today, which would blur the boundary between "the onRequest hook" and "a route handler." `session-invalidation-audit.ts` sits alongside `audit-logger.ts` in the same `auth/` directory both call sites already import from, so this adds no new cross-directory dependency shape to the codebase. It also sidesteps a smaller, related question the co-located option would otherwise leave implicit — whether the helper needs to be `export`ed off `middleware.ts` for `auth.ts` to reach it — by making export-from-a-shared-module the obvious, only design.

  The helper itself: derives `log = request.log` internally rather than taking it as a separate parameter (every call site already has `request` in scope and there is no call site that would ever pass a different logger); wraps the actor-global-role lookup (via `resolveActorGlobalRole`) *and* the `INSERT` together in a single call to `writeAuditRow()`, itself wrapped in **one** `withTimeout(..., AUDIT_WRITE_TIMEOUT_MS)` call covering both — not one `withTimeout` per DB call (Decision D5's corrected mechanism: a true 500ms end-to-end bound, not ~1000ms from two independent timeouts); builds the row's `metadata` as `{ reason, authSessionId, ...metadata }` (the helper's own `authSessionId` and `reason` parameters always folded in unconditionally, with whatever the caller passed via the optional `metadata?` bag merged on top per Decision D2); performs the `INSERT INTO audit_log` with `actor_ip` from `request.ip` and `team_id: NULL`; and on any rejection (caught via a single `try/catch` around the one `withTimeout` call, `failureMode` set via `err instanceof AuditWriteTimeoutError ? "timeout" : "error"`) emits `auth.audit_write_failed` with `sourceIp: request.ip` included, without rethrowing.
  - Note: `tsconfig.base.json` sets `exactOptionalPropertyTypes: true`. Build `metadata` via conditional spread (`{ reason, authSessionId, ...(hasFailureDetail ? { failureType, retryCount } : {}) }`), not by assigning `failureType: condition ? "revoked" : undefined` directly — the latter does not compile under this repo's strict settings.
- [x] 2.4 Add a mock for the new `session-invalidation-audit.js` module to `middleware.test.ts` (it has none of the mocks this change needs today — it mocks `oidc-client.js`, `token-encryption.js`, `session-store.js`, `audit-logger.js`, `config.js` only), matching that file's existing per-import mocking style (e.g. a `mockWriteSessionInvalidatedAuditRow` spy backing `vi.mock("../session-invalidation-audit.js", ...)`). Because `middleware.ts` only ever reaches `db.js`/`connection-reauthorization.ts` transitively through `session-invalidation-audit.ts` (task 2.3's module choice), mocking this one boundary is sufficient — `middleware.test.ts` does not need its own `db.js` mock or a `resolveActorGlobalRole` mock, since neither is ever imported directly by `middleware.ts`. Separately, confirm `auth.test.ts`'s existing `db.js` mock (it already has one, for its existing `db.query` calls) is extended to also satisfy the new SELECT/INSERT that `session-invalidation-audit.ts` issues (vitest mocks are resolved-path-keyed, so this one mock also intercepts `db.js` when it's imported transitively via `session-invalidation-audit.ts` from `auth.ts`) — without disturbing any existing query-mock call-count assertions.

  **Landed here, alongside Section 2, rather than deferred to Section 5 (architect review, non-blocking, accepted):** without this, `middleware.test.ts`'s existing `absolute_timeout`/`token_revoked`/`transient_failure` branch tests would hit a real, unconfigured `pg.Pool` as soon as Section 3 wires `middleware.ts` up to call the new helper — two sections before this fix would land under its original placement (a deferred "5.1") — and would either fail non-deterministically or "pass" only by coincidentally hitting the new fail-open path (engineer review Finding 3). This is a prerequisite for Section 3 landing without breaking today's suite, not merely for the new tests in Section 5 that come after it.
