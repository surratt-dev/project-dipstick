## 7. Backend registration payload (`session_registration_snapshot`, design.md Decision D3)

This group is now real, in-scope backend implementation work for this change — not a deferred placeholder. It must land before task 8.1 (frontend wiring) can be attempted against a real payload, so complete 7.1–7.5 before starting 8.1.

- [x] 7.1 Add `SessionRegistrationSnapshotPayload` and the `session_registration_snapshot` variant of `WsClientMessage` to `packages/shared/src/types/realtime.ts`, per design.md D3a: `{ sessionId, sessionStatus, currentTopic: { sessionTopicId, status } | null, hasLockedInVote: boolean }`.
- [x] 7.2 Implement `buildSessionRegistrationSnapshot(userId, sessionId)` in new module `packages/backend/src/realtime/session-registration-snapshot.ts`, running the single live query from design.md D3c (`sessions` LEFT JOIN `session_topics` LEFT JOIN `votes`, scoped to `voter_id = userId`). No caching of the result. Return `null` for the zero-row case (session deleted between the access grant and this read). Add a code comment directly on the function declaration stating that `userId` MUST be `request.session.userId` (server-derived, never client-supplied) — per design.md's "Call-site discipline" note.
- [x] 7.3 Unit test `buildSessionRegistrationSnapshot`: (i) session in `lobby`/`pre_session` with no current topic returns `currentTopic: null`; (ii) session `active` with current topic `voting` and no vote row for this user returns `hasLockedInVote: false`; (iii) same, with a vote row for this user present, returns `hasLockedInVote: true`; (iv) another user's vote row for the same topic does NOT affect this user's `hasLockedInVote` (self-disclosure only, per design.md D3d); (v) session in `wrap_up` returns `currentTopic: null`; (vi) no matching session row returns `null`.
- [x] 7.4 Wire `websocket-routes.ts`'s `GET /ws/sessions/:sessionId` handler to call `buildSessionRegistrationSnapshot`, per design.md D3c's "Ordering and failure containment" note: placed strictly *after* `scheduleReauthorizationSweep`, `scheduleTokenRefreshMonitor`, and `checkAndRecordGraceRecovery` have already run — never before or interleaved between them — and wrapped in its own `try/catch`. On any failure (thrown error or a `null` return), log at `warn` and send no `session_registration_snapshot` message; never throw past this point, never surface as an unhandled promise rejection, never close or otherwise degrade the connection. On success, send via the existing `safeSend(registry, "session", sessionId, conn, JSON.stringify({ eventType: "session_registration_snapshot", payload }))` path (same send mechanism `reauth_required` already uses in `connection-token-refresh.ts`). Sent on every registration, per design.md D3b — no "is this a reconnect" branching added to the handler.
- [x] 7.5 Integration test: a session-scoped WS connection that successfully registers receives exactly one `session_registration_snapshot` message before any other session-scoped event, with a payload matching the session/topic/lock-in state seeded in the test fixture. Also test the negative case: a connection rejected by `evaluateSessionSubscriberAccess` (e.g. closed session) receives no `session_registration_snapshot` — confirming D3d's "piggybacks on an already-made grant, does not leak past it" property. Also test the failure-containment case: force `buildSessionRegistrationSnapshot` to throw (or return `null`) and assert `scheduleReauthorizationSweep`/`scheduleTokenRefreshMonitor` still ran, no `session_registration_snapshot` was sent, the connection stayed open, and nothing propagated as an unhandled rejection. Also test D3b's "every registration, not just the first" claim directly: register a second connection (or a reconnect) on the same session after seeding a state change (e.g. a lock-in recorded between the two registrations) and assert the second registration also receives its own, freshly-computed `session_registration_snapshot` reflecting the new state — not a cached or suppressed send.
