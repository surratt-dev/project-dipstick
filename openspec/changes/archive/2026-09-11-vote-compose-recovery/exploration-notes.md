## Exploring: issue #31 — composed-but-unsubmitted vote state and SEC-26 grace-period recovery

**Persona note:** written by Devon Calloway (Internal Champion / founding advisor), as exploration input to a future proposal. Not a design, not a commitment — the usual caveats.

**Revision note (this pass):** updated after review by Marcus Delgado (BA) and Priya Nair (Facilitator SME) — see Section 7 for what changed, what I pushed back on, and why. Sections 3, 4a–4d, and 5 are revised in place rather than left as a separate errata list, since the revised versions are what should actually carry into Propose. Original section numbering is preserved; new subsections are appended where the review surfaced gaps rather than corrections.

### 1. Where this actually comes from

This isn't a new idea someone had — it's a gap the reauthorization design admitted to itself. `websocket-connection-reauthorization`'s Decision D7 (archived `openspec/changes/archive/2026-09-09-websocket-connection-reauthorization/design.md`) states the backend-side guarantee correctly and narrowly: the backend never receives a composed-but-unsubmitted vote value at all (SEC-16/SEC-22 — nothing is transmitted before lock-in), so there's structurally nothing for a SEC-25 sweep or a successful SEC-26 refresh to lose, because neither ever closes the socket.

Decision D4 is the one that punches the hole. It establishes — for good, load-bearing reasons I'm not second-guessing here — that grace-period recovery can never be an in-place resume. Every OIDC re-login in this app is `window.location.href = "/auth/login"` (`AuthContext.tsx`, `AuthErrorPage.tsx`): a real top-level navigation, not a fetch, not a popup. That tears down the JS heap the same as closing the tab. D4's own text names the consequence directly and hands it off: "composed-but-unsubmitted vote state cannot be assumed to survive a SEC-26-triggered re-login without an explicit frontend persistence mechanism... frontend-stage work outside this design's Migration Plan." Task 5.5 turned that sentence into this issue rather than letting it evaporate when the PR merged. Good instinct — that's exactly the kind of thing that becomes "huh, I guess nobody thought about that" eighteen months from now if it isn't tracked.

So: this is real, it's narrow, and it's already correctly scoped as frontend-only by people who understood the backend side cold. I don't need to relitigate D1–D9a. I need to make sure the frontend fix doesn't casually violate anything the backend design was careful about.

### 2. What "composed but unsubmitted" actually is, concretely

Worth being precise here because "vote state" sounds bigger than it is. Per `requirements/voting mechanics - enhanced.md`, a vote is one of: a finger count 1–4, a thumb up/down, or (trend topics) up/down/flat. It's a single small enum value a participant has tapped/selected in the UI but not yet locked in — the digital equivalent of holding up a closed fist before the "3, 2, 1, vote" reveal. It is genuinely ephemeral by ritual design: the closed-fist moment exists specifically so nobody commits before everyone commits together (simultaneous reveal, so nobody anchors on anyone else).

Two things follow from that:
- The content itself is not sensitive in the way, say, a token or an actual submitted-but-not-yet-revealed vote would be. It's one bit of "what were you about to say," known only to the one browser tab it's in.
- But the *moment* it represents is exactly the moment the whole ritual is built to protect. A mechanism that touches this state carelessly is touching the one piece of the flow the "simultaneous reveal" guarantee exists for. That's why I want this treated carefully even though the payload is small. **Marcus's review sharpened this further and I'm adopting his framing outright: a stale restore — the wrong topic's answer silently reappearing as if it belonged to the current one — is not an occasional-bug-we-tolerate case. It's the one failure mode of this whole mechanism that is categorically worse than the mechanism not existing at all, because it does to the participant, via the tool, exactly what the no-early-disclosure rule forbids peers from doing to each other. If the restore logic is ever in doubt about whether a draft belongs to the current topic, the answer is discard, not restore. That's not a tiebreaker rule — it's the governing one.**

### 3. Sequencing and the persistence trigger — settled, not left as a judgment call

My original framing here treated this as an open sequencing question for whoever picks up Propose to weigh. Marcus's review resolved it, and I agree with his resolution — this section is rewritten to reflect that, not just annotated.

**Correction to my own grounding first.** I wrote that "nothing calls `window.location.href = '/auth/login'` in response to [`reauth-required`] today" and treated that as meaning no hook point exists. Marcus is right that this overstated the gap: `useConnectionHealth`'s `state` value, including `reauth-required`, is already a public, consumed return value (`ConnectionStatusBanner.tsx`, `FacilitatorReadinessGrid.tsx` both react to it today). Any future component — including #32's eventual redirect trigger — can already subscribe to `state === "reauth-required"` via its own effect. What's actually missing is narrower than "a hook point": (a) the effect that calls `window.location.href`, which is #32's deliverable, and (b) the compose UI's own React state to persist, which doesn't exist because the compose UI doesn't exist. Worth stating precisely, since "no hook point exists" and "the consuming component hasn't been written yet" are different claims, and the proposal should make the narrower, correct one.

**The mechanism itself: persist on every compose-value change, not as a one-shot write triggered by navigation.** I originally suggested "persist... before the re-authentication navigation begins" as the hook point. Marcus's objection is correct and I'm adopting it as the design: a write keyed to the moment right before an unload/navigate is a well-known flaky pattern even where it *can* be made to work (`beforeunload`/`pagehide` handlers racing bfcache, mobile OS process termination, `window.location.href` not guaranteeing synchronous code after it runs to completion) — and this is a mechanism protecting ritual-integrity state, not a nice-to-have where "usually works" is good enough. The compose UI's own `onChange`/`onSelect` handler writing to `sessionStorage` on every value change (debounced or not — an implementation choice, not a requirements one) is strictly better on both counts that matter:

- **It removes the dependency on issue #32 entirely**, not just decouples from it. There's no call site to hook into for "navigation is about to happen," because the write no longer needs one — the only integration point this change needs is the compose UI's own change handler, owned by whoever builds that UI.
- **It also covers, for free, a case my original framing didn't name**: an ordinary tab close or browser crash during the closed-fist moment, with no SEC-26 event involved at all. `sessionStorage` survives a same-tab reload regardless of why the reload happened. A write-before-navigate design would only ever have helped the SEC-26 path I was scoping for; write-on-change helps that path and this one at no additional design cost.

I want to be precise about what this does and doesn't change in scope, because I flagged scope discipline as a risk in my own Section 4c and I'm holding myself to it here too: **the change is still named and justified by the SEC-26 grace-period recovery story** — that's the issue it traces to, and that's the "why this matters" framing for the proposal. But the write itself is not conditional on detecting a SEC-26 event specifically, and the proposal should say so explicitly, so nobody reads "scoped to SEC-26 recovery" as "the persistence write only fires when SEC-26 recovery is happening." It doesn't need to know why a reload occurred. See Section 4c below and Section 7 for where I drew a line on how far to let this broader-than-strictly-necessary coverage get framed.

**What this means for scoping the proposal:** build and merge the persistence/restore module now, as a standalone, unit-testable contract — see the acceptance-tier split in the new Section 4f. Do not gate this change on #32 landing. Do gate the *integration* — the compose UI actually calling `persistDraft`/`restoreDraft` — on the compose UI existing, but that's a wiring task tracked wherever the compose UI change ends up living, not a blocker on this proposal being written, reviewed, or implemented.

### 4. What could go wrong if this drifts — the part I actually care about

**4a. Restoring into the wrong topic (or the wrong session).** The grace period is ~30 seconds server-side, but the actual wall-clock gap the participant experiences is that *plus* a full OIDC round trip through the identity provider and back through `/auth/callback` — could be anywhere from a few seconds to "I got distracted by an MFA prompt and came back a minute later." During that gap, the session doesn't pause. A facilitator can reveal the current topic, or — per `session-topic-lifecycle` spec (`SESSION-012`) — advance to the next one entirely, or advance all the way past the final topic into `wrap_up`, which clears `sessions.current_topic_id` outright rather than pointing at a different topic. If the persisted draft gets blindly reapplied into whatever topic UI happens to be showing after reconnect, the participant could end up staring at "3" pre-filled for a topic they never saw the prompt for. That's not a security bug, it's a ritual-integrity bug — per Section 2 above, the worst-case failure mode this mechanism can produce, not an incidental one.

Mitigation direction, now stated as acceptance scenarios rather than prose (contract-level — see 4f for what "acceptance scenario" can mean before a compose UI exists):

- *GIVEN a persisted draft for `(sessionId, sessionTopicId)`, WHEN the fresh connection registers and the server-authoritative current topic for that session matches both fields AND that topic's status is `voting`, THEN the draft is restored into compose state.*
- *GIVEN a persisted draft for `(sessionId, sessionTopicId)`, WHEN any of the following hold — (i) the server-authoritative current topic differs from the persisted `sessionTopicId` (topic advanced), (ii) the topic matches but its status is no longer `voting` (revealed or complete), (iii) the session has moved to `wrap_up` and has no current topic at all, or (iv) the `sessionId` itself no longer matches an active session for this participant — THEN the draft is discarded silently and cleared from storage. No banner, no toast, no visible difference from "nothing was composed."*

Four distinct discard conditions, not one — my original single sentence ("anything else gets silently discarded") was right about the behavior but didn't enumerate the branches, and the `wrap_up`/no-current-topic case in particular is easy to miss if you're only thinking about "wrong topic."

**4b. Restoring after the participant's vote already exists another way — stated as an ordering constraint, not just a precedence rule.** "Locked-in wins, always" is still the rule and I have no notes on the rule itself. What was missing is *when* the restore logic is allowed to run relative to receiving server-authoritative state — that ordering is obvious in my head and invisible to whoever implements it. Stating it plainly: restoration is a two-step sequence, not a race.

1. The fresh connection registers and receives server-authoritative state, including this participant's own lock-in status for the current topic, from the registration payload.
2. Only after that payload is in hand does the restore logic read `sessionStorage` and decide whether to apply, discard, or ignore it.

There is no code path where the `sessionStorage` read happens, or where its result gets applied to UI state, before step 1 completes.

*GIVEN a persisted draft exists for the current `(sessionId, sessionTopicId)` tuple, WHEN the fresh connection's registration payload indicates this participant has already locked in a vote for that topic (via whatever mechanism — a stale second tab, a retry that actually succeeded), THEN the draft is discarded and the UI reflects the server-reported locked-in state, never the draft value, regardless of which the local code would have computed first.*

**4c. Persisting vote content at all is a first for this codebase, and it should stay narrow.** `grep` across `packages/frontend/src` for `sessionStorage`/`localStorage` today returns nothing — this would be the first client-side persistence of anything vote-adjacent in the application. SEC-16 and SEC-22 exist because vote/trend data isn't supposed to show up in places it doesn't need to. `sessionStorage` never leaves the browser and this mechanism doesn't change what's transmitted to the backend — D7's invariant (backend never sees an unsubmitted value) stays true, full stop, this is client-local only. But "never transmitted" isn't the same as "no constraints." Hard properties, tightened from the review:

- **Write trigger:** on every compose-value change (Section 3). **Read/clear trigger, pinned down precisely:** the restore attempt happens exactly once per page load — on the first WebSocket registration this tab performs after that load. That covers the SEC-26-recovery reload (the only reload this app's re-auth flow currently produces) without needing to detect "was this specifically a SEC-26 recovery" at all, which the write-on-change design makes unnecessary. An ordinary in-tab reconnect (a network blip recovered without a page reload) never re-attempts a restore, because it never re-runs the mount-time "first registration after load" code path in the first place — that code runs once, at mount, full stop. Whether the draft was restored or discarded, the stored entry is cleared at the end of that one attempt — it does not sit in `sessionStorage` for the rest of the tab's life.

  This precision matters because my original phrasing — "read once on the registration that follows a recovery" — doesn't say what "a recovery" means operationally, and combined with write-on-change, an indiscriminate reading ("every registration this tab ever does") would quietly turn this into the "ordinary refresh recovers your draft too" feature I explicitly ruled out below as a different, bigger feature. Pinning the read to "first registration after page load, once" closes that gap without needing any SEC-26-specific detection logic.

  **Named side effect, addressed rather than left implicit:** because the read trigger is "first registration after any page load," an ordinary manual refresh (F5, not a SEC-26 event) in the same tab will also restore a still-valid draft, going through the identical `(sessionId, sessionTopicId)` + server-authoritative + locked-in-precedence checks as the SEC-26 case. I considered whether this crosses the line I drew in my own bullet below against a "resume my draft" feature, and I don't think it does: it's the same single tuple, the same discard rules, still entirely client-local, no new feature surface, nothing cross-device, nothing server-backed. It's an accepted incidental consequence of building the write-on-change mechanism correctly, not a feature to design toward or document as a benefit. The proposal should state it as exactly that — an accepted consequence, named once, not advertised — so it's a decision on record rather than a thing someone notices during implementation and has to guess whether it was intended. See Section 7 for where I'm holding a firmer line on this.

- **Persisted record shape**, stated as a real structure rather than "a tuple," per the review's ask — illustrative, not binding on the eventual implementer: `{ sessionId: string, sessionTopicId: string, value: VoteValue, composedAt: string }`, stored under a single `sessionStorage` key scoped to this mechanism (e.g. `dipstick:vote-draft`) — one entry, since a participant has at most one active session and current topic per tab at a time, so the key itself doesn't need session/topic scoping; the scoping check happens on read, against the stored record's fields.

- **No broadening later into some cross-device or server-backed "resume my draft" feature.** That's a different, much bigger feature with real privacy tradeoffs, and it's not what D4/D7/issue #31 are asking for. If this shows up in the proposal as a stated goal, that's scope creep, not scope discovery — see Section 7 for why I'm not letting the same-tab-refresh side effect above soften this line.

- **Never becomes a second place vote state can live in the DB or in Redis** — the backend's `dipstick:reauth-grace:{userId}` marker (Decision D4) is a recovery-detection flag with no vote content in it, and it should stay that way. Nothing about this frontend change should motivate adding a server-side counterpart.

**4d. Don't let the fix grow new UI chrome — and hold this as a closed list, not a starting point.** The direction here is exactly right in shape and the review didn't move me off it, only sharpened where the edges are. What I don't want to see: a "we restored your answer!" toast, a visible diff/confirmation step, or anything that turns a thirty-second hiccup into a moment the tool draws attention to itself for. Restore-or-discard is a rendering requirement, not just a copy guideline: **the decision must resolve before the compose control's first paint.** No spinner state, no flash of the stale value before it's cleared, no visible transition from "old answer" to "blank." If the topic advanced while the participant was away, they land on the fresh topic with an empty compose control, indistinguishable from a participant who was simply slow to start — that's the actual bar, not "eventually looks right." A discarded draft must also be indistinguishable at the code level, not just visually: no console-visible warning a curious participant could find via devtools that contradicts "nothing happened."

Closed list of things this change does not add, stated so it reads as closed during implementation review rather than an invitation to add "just one small thing":
- No toast, banner, or confirmation of any kind, restore or discard.
- No new sound.
- No new animation (a highlight pulse on the restored value, etc. — easy to reach for as a "nice touch," and it isn't one).
- **No facilitator-visible signal of any kind — grid marker, tooltip, color, or otherwise — that distinguishes "disconnected, mid-recovery, with a draft queued" from any other disconnected state.** This is new to this revision, from Priya's review, and I'm treating it as load-bearing rather than a nice-to-have: the facilitator's readiness grid shows lock-in status, not intent, and a "they have a draft queued" signal is intent — it's the readiness-without-spoilers guarantee, applied to a case I hadn't considered. Today a participant mid-recovery reads on the grid as `disconnected_voted` or `disconnected_no_vote` (per `FacilitatorReadinessGrid.tsx` and the `websocket-staleness-signal` spec's four baseline states), same as any other disconnect, and that's correct. This change must not add a fifth state or a variant of an existing one for this case. State it as an explicit non-goal in the proposal, not left silent — Priya's point, and a fair one: this is exactly the kind of thing that accretes a status indicator during implementation if it isn't ruled out in writing up front.

**4e. Facilitator-experience non-goals — new subsection, from Priya's review.** These are boundary statements, not design work; the mechanism doesn't change, but the proposal should say all of this explicitly rather than leave it inferred, since each is adjacent to a guarantee people care about:

- **Facilitator pacing is unaffected and this change doesn't try to improve it.** A facilitator today can't distinguish "stepped away," "flaky wifi," and "got bounced to re-login" from the grid alone, and that's fine and pre-existing. This change doesn't reduce that ambiguity and isn't trying to — session pacing stays entirely the facilitator's call, on the same information they have today. Worth a line saying so, so "recovery mechanism" doesn't get misread as also delivering facilitator-side diagnosis.
- **Reveal eligibility is unaffected for a participant still in `reauth-required` or reconnecting at reveal time.** A participant who hasn't locked in a vote by the time the facilitator triggers reveal simply has no vote counted — identical treatment to any other participant who didn't finish in time, connection state irrelevant. Nothing about this mechanism changes reveal timing, eligibility, or the simultaneity guarantee; it only affects what's sitting in the participant's own compose control when they reconnect, which is upstream of submission entirely.
- **Outlier flagging is unaffected by recovery timing.** Per `requirements/High-Level Architecture.md`'s outlier definition, flagging is keyed to vote *value* (absolute deviation from the group average), not to when or how the vote was cast. A participant who discards a stale draft and casts a fresh vote seconds later is flagged (or not) exactly as any other vote at that value would be. No timing-based signal exists anywhere in the outlier path for this to interact with.
- **No age-based staleness cutoff beyond the topic/session match itself.** Priya raised this as a real question rather than an assumption: could a draft persist "too long" (a participant gone 20 minutes because the facilitator was mid-discussion, topic never advanced) such that it should be discarded on age alone even though the topic/session check would still pass it? I don't think an age cutoff is justified. The `(sessionId, sessionTopicId, status === voting)` check is already correctness-complete: if the topic hasn't advanced and is still open for voting, the draft is exactly as valid as it was when composed, regardless of elapsed time — the ritual-integrity risk isn't age, it's mismatch. An artificial age cutoff would add a second failure mode (a still-valid draft discarded for no reason tied to the actual risk) without closing any gap the tuple check doesn't already close. No age limit; topic/session match plus status is the whole test.
- **Facilitators do not vote, so their own drafts are not in scope for this mechanism.** Confirmed rather than assumed: `requirements/BRD.md` and `requirements/Engineering Health Check Explained.md` describe the facilitator role as running the room — stating prompts, counting down, capturing/observing results, prompting discussion on outliers — not as a participant who casts a vote; the application's own serializer boundaries (`team-content-access` spec) treat `serializeForFacilitator` as structurally distinct from the participant vote path, and the facilitator's readiness grid shows *other people's* lock-in status, not a lock-in state of their own. There is no facilitator-compose-a-vote surface anywhere in the requirements or the existing specs for this mechanism to apply to. Stated here so it's on record rather than an open question someone has to re-derive later.
- **The participant-side felt experience of the redirect itself stays out of scope here, on purpose — cross-reference only.** Issue #32 owns the actual navigation trigger and, per Priya's review, the copy on the resulting login screen is where the "did I just get kicked out of the session" feeling for those 10–60 seconds actually gets addressed, not here. This document isn't adding scope to #32, just leaving a pointer for whoever picks it up: the felt experience of that gap is the single most visible moment in this whole flow from the participant's side, even though the mechanism in *this* change is deliberately silent. A restore mechanism that works perfectly doesn't by itself make that gap feel fine; that's #32's copy to write, not a persistence-module concern. Worth naming once, here, so it doesn't get treated as "just an auth screen" later.
- **First-session cost, acknowledged, not designed for.** A team's first session is already the highest-anxiety moment a facilitator manages, and a silent forced re-login mid-vote costs more in trust there than it does for a team on its twentieth session. This isn't a case for new chrome — "narrow, silent, low-drama" is still the right call generically, and Section 4d's closed list stands regardless of session count. It's worth one line in the proposal acknowledging that the cost isn't evenly distributed across a team's lifecycle, so the design isn't read as having assumed all sessions are equally seasoned. That's acknowledgment, not a design fork.

**4f. Acceptance scenario tiers — new subsection, from Marcus's review, and the point I most want on record before this goes to Propose.** Several of my own examples above (4a) are written as user-observable scenarios — "staring at '3' pre-filled for a topic they never saw the prompt for." That's the right way to *explain* the risk. It cannot be the shape of an acceptance scenario for this change as scoped, because there is no compose UI to stare at anything in yet, and per Section 3 this change is meant to ship without waiting for one. The proposal should state two tiers explicitly and say which tier each scenario belongs to:

- **Contract-level (verifiable now, in this change):** scenarios written against the `persistDraft`/`restoreDraft` (or equivalent) functions directly, with fixture data standing in for what a real compose component would supply — e.g., "given `restoreDraft` is called with a stored record for topic A and a current-topic argument of topic B, it returns `null` and clears storage." All of 4a–4c's scenarios above are this tier, and they're fully testable today with no UI at all.
- **Integration-level (deferred, tracked, not blocking this change):** scenarios that require the actual compose UI and #32's redirect trigger to exist — "a participant who reloads via SEC-26 recovery sees their in-progress selection restored." These should be named in the proposal as follow-up verification owed once the compose UI lands, not written as if testable now, and not used to block this change's own completion.

Without this split, the likely failure mode is the one I'd expect from my own Success Criteria concerns generally: someone tries to write "participant sees their vote restored" against components that don't exist, either fakes a component just to make the test pass (verifies nothing real) or quietly drops the scenario and nobody notices it was never actually checked.

### 5. What I'd want a proposal to state explicitly, up front

- Persist-then-restore is scoped to exactly one `(sessionId, sessionTopicId, value)` tuple, keyed so a stale entry can never apply to a different topic or a different session.
- The write happens on every compose-value change, not on a one-shot navigation hook; the read/clear happens exactly once, on the first WebSocket registration after page load. Neither trigger is conditional on detecting a SEC-26 event specifically.
- Restoration is subordinate to server-authoritative state on reconnect (current topic, lock-in status), and that subordination is an ordering constraint (server payload arrives, then and only then is storage read/applied), not a race resolved by precedence rules alone.
- Never transmitted to the backend; `sessionStorage` only; single-use, cleared after the one restore attempt (successful or discarded), whether that attempt followed a SEC-26 reload or an ordinary manual refresh.
- No new admin-facing toggle for any of this — same standing rule as everything else touching the reauth/staleness mechanisms (SEC-26's Decision D9a). This is small enough that nobody's proposed making it configurable, but I've been surprised before.
- No facilitator-visible signal of any kind for "recovering with a draft," stated as an explicit non-goal, not left silent.
- Restore-or-discard resolves before the compose control's first paint — a rendering requirement, not a copy guideline.
- Contract-level and integration-level acceptance scenarios are named separately, with integration-level scenarios explicitly deferred rather than attempted against nonexistent UI.
- No dependency on issue #32 for this change to be specified, implemented, reviewed, or merged. A pointer (not a dependency) to #32 owning the felt experience of the redirect screen itself.

### 6. What this is *not*

Not a backend change (confirmed independently — D7's structural argument holds regardless of what the frontend does; nothing here reopens D1–D9a). Not a chance to revisit the 30-second grace period, the two-close-code split, or anything else settled in the reauthorization design — that's relitigating decisions I already signed off on once. Not an opportunity to build a general "resume where you left off" feature for the whole session — it's specifically the closed-fist moment, and specifically the one recovery path (SEC-26 grace-period-then-reconnect, plus the same-tab ordinary-refresh case named in 4c as an accepted incidental consequence of the same mechanism) that a page reload actually touches. An ordinary network blip that never reloads the page already survives via in-memory state per D7 and needs nothing new. Not a change to facilitator-side visibility, reveal eligibility, or outlier flagging (4e). Not the place where the redirect screen's copy gets written (4e, #32).

### 7. Response to review — what changed, and what I pushed back on

Both reviews were thorough and I don't have a fight to pick with most of it — the disposition below is mostly "adopted," and I want to be honest about that rather than manufacture disagreement for its own sake.

**Adopted in full:**
- Marcus's sequencing resolution (persist-on-change, no dependency on #32) — Section 3. This is a genuine improvement on my original framing, not just a preference: it's more robust (covers tab-close/crash for free) and removes a real integration risk (flaky unload-timing patterns) that my "persist before navigation" framing would have carried even once #32 existed.
- Marcus's four-branch discard enumeration, including the `wrap_up`/no-current-topic case I missed — Section 4a.
- Marcus's ordering constraint for locked-in precedence — Section 4b.
- Marcus's pinned-down clear trigger and persisted record shape — Section 4c.
- Marcus's contract/integration acceptance-scenario split — Section 4f.
- Marcus's factual correction about the "hook point" existing already (Section 3) — my original phrasing was imprecise and his is right.
- All of Priya's non-goals and confirmations — no facilitator-visible signal, no sound/animation, restore-before-first-paint, facilitator pacing/reveal-eligibility/outlier-flagging unaffected, no age-based staleness cutoff, facilitators don't vote, #32 as a cross-reference not a dependency, first-session cost acknowledged without new chrome — Sections 4d–4e.

**One place I held a firmer line than the review's framing, on record rather than silently:** Marcus's write-on-change recommendation is correct and adopted, but his framing emphasizes that it "costs nothing extra" to also cover ordinary tab-close/crash and same-tab refresh, as a point in the design's favor. I agree it's true and it's a fine reason to prefer this mechanism over write-before-navigate. What I'm not adopting is treating that broader coverage as something to lean into, document as a feature, or let soften my own 4c guardrail against a "resume my draft" feature. The mechanism being incidentally more robust than the SEC-26 case strictly requires is a reason to build it this way; it is not license to describe it, in the proposal or later, as "your draft is always saved" — that's a different feature with different privacy tradeoffs than the one D4/D7/issue #31 actually asked for, and the fact that it would arrive for free doesn't change whether we mean to be building it. Section 4c names the same-tab-refresh side effect once, as an accepted consequence, and stops there. If a future change wants to build actual cross-session or cross-device draft resume, that's its own proposal, its own privacy review, and not something this change should be read as having already delivered a foundation for.
