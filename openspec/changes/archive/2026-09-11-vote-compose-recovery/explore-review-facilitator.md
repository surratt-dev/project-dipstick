# Facilitator review — vote-compose-recovery exploration notes

Reviewer: Priya Nair (Facilitator SME), reviewing Devon Calloway's exploration notes for issue #31.

Scope of this review: usability and ritual-feel, not implementation architecture. I'm reading this the way I'd read any change that touches the reveal, the readiness grid, or what a participant experiences mid-session — because a "small frontend fix" can still change how the ceremony feels even when it doesn't touch the reveal mechanic itself.

## Overall take

The notes get the thing I care about most right on instinct: restore quietly, discard quietly, never narrate. Section 4d says it almost exactly the way I would. I don't have pushback on the technical shape (sessionId/sessionTopicId scoping, server-authoritative-wins, single-use sessionStorage) — that all reads as sound and consistent with how the rest of this state machine already behaves. My review below is about what's *missing* from a lived-experience standpoint: the notes reason carefully about the data, less so about the person holding the phone.

## Observations

1. **The notes correctly identify the ritual-integrity risk (4a) but frame it entirely as a data-correctness problem.** Restoring "3" into the wrong topic isn't just wrong data — it's the tool doing to a participant exactly what we forbid peers from doing to each other (pre-committing them before they've seen the current prompt). That's worth stating as a first-class requirement, not just a consequence of the sessionId/topicId key check. I'd want the proposal to say explicitly: *a stale restore is not a bug we tolerate occasionally, it is the one failure mode that is categorically worse than doing nothing.* If in doubt, discard.

2. **"Silent" is right, but silent has to mean silent to the room too, not just silent-in-UI-copy.** Nothing in the notes addresses what happens on the *facilitator's* screen while a participant is off doing the OIDC round trip. Today that participant just reads as `disconnected-no-vote` or `disconnected-voted` on my readiness grid (per `FacilitatorReadinessGrid.tsx`) — same as any other disconnect. Good: I don't think this change should introduce a new grid state for "recovering with a pending draft." I want to see that stated as an explicit non-goal, because it would be an easy scope-creep target ("let's show the facilitator this person is mid-recovery so they know to wait") — and that's exactly the kind of thing that turns into surveillance-flavored UI. My readiness grid shows lock-in status, not intent. A "they have a draft queued" signal is intent. Don't build it.

3. **What does *my* pacing decision look like during that gap?** I already can't tell the difference today between "stepped away," "flaky wifi," and "got bounced to re-login." That's fine and pre-existing — I don't need a diagnosis, I need to know whether to wait. This change doesn't need to solve that, but the exploration notes should say clearly that it isn't trying to, so nobody reads "recovery mechanism" and assumes it also improves my visibility into *why* someone's grayed out. Session pacing stays entirely mine either way — I just want the doc to say so instead of leaving it implied.

4. **The participant-side experience during the redirect itself is out of scope but worth flagging as a seam.** The notes correctly scope this to persistence, and issue #32 owns the actual navigation trigger and its copy. But from where I sit: a participant mid-tap suddenly lands on a bare login screen with zero session context. Even if their draft comes back perfectly, the *feeling* in that gap is "did I just get kicked out of the session." That's psychologically the opposite of a ritual tool disappearing into the background — for those 10-60 seconds it's the most visible thing in their day. I know that's #32's copy to write, not this change's — but I want it on record here so whoever picks up #32 doesn't treat it as "just an auth screen." A single line of reassurance on that screen (not here, not in this change) would do more for trust than anything the restore mechanism itself does.

5. **Discard-and-say-nothing needs to feel like "nothing happened," not like "something happened and got hidden."** 4a's mitigation direction (silently drop a stale draft, no banner) is right, but I want to check the actual felt experience: if the topic already advanced while they were away, they land back on a fresh topic with an empty compose control — indistinguishable from a participant who was simply slow to start voting. Confirm that's really the rendered outcome. If instead there's any flicker, any "restoring..." spinner state, any visible moment where the old value briefly appears before being cleared, that reintroduces exactly the pre-commitment/anchoring risk the mechanism exists to prevent, just on the person's own screen instead of the room's. I'd want a stated requirement: the restore-or-discard decision happens before first paint of the compose control, not as a visible transition after it.

6. **Does the facilitator role itself vote, and if so, is Priya's own draft in scope?** The notes don't say either way. If facilitators cast votes on topics (as opposed to purely running the room), then my own composed-but-unsubmitted state is subject to the same recovery/discard logic, and I'd want that stated rather than assumed obvious. If facilitators don't vote, say that too, so it's not an open question later.

7. **First-session consideration.** A brand-new team's first session is already the highest-anxiety moment I manage — people are still learning the format. A forced re-login mid-vote in someone's very first session, with no in-app acknowledgment anywhere in the flow, is a rougher first impression than the same event happening to a team on their twentieth session who already trusts the tool. I'm not asking for new chrome to solve this (see point 4/8) — just flagging that "narrow, silent, low-drama" is the right call generically, but its cost is highest exactly when trust is lowest. Worth a line in the proposal acknowledging this rather than treating all sessions as equally seasoned.

8. **Agree strongly with 4c/4d's "don't grow new UI chrome" and "don't grow a bigger feature."** This matches the core ritual constraint precisely: this tool has to get out of the way once a session is running. No toast, no confirmation, no "we noticed you were gone" — all correct. I'd add one more boundary to that list explicitly: no new *sound* or *animation* either (a highlight pulse on the restored value, etc.) — same principle, easy to reach for during implementation as a "nice touch," and it isn't one.

## Questions I'd want answered before this becomes a proposal

- Is there any facilitator-visible signal at all planned for this — even indirectly (e.g., a change to grid marker semantics)? I want to see it stated as "no" rather than left silent, given how easily this kind of thing accretes a status indicator during implementation.
- If a participant's draft is discarded because the topic moved on, and they then vote fresh on the new topic in the next few seconds, is there any risk that a *fast* re-vote reads to the system (or to me) as anomalous / outlier-flagged for reasons unrelated to their actual position? (Probably not, since outlier flagging is presumably keyed to vote value not timing, but worth a sentence ruling it out.)
- Confirm: does reveal timing/eligibility change at all for a participant who is still in `reauth-required` or `unknown-reconnecting` state at reveal time? I'd assume no — they just don't have a vote in, same as anyone who didn't finish in time — but I want it stated, not inferred, since it's adjacent to the reveal-simultaneity guarantee I care about most.
- The 30-second server grace period plus real-world OIDC/MFA time could put someone away for a while. Is there an upper bound past which the persisted draft is considered stale *by age* even if the topic technically hasn't advanced yet (e.g., they were gone 20 minutes, topic never changed because the facilitator was mid-discussion)? I'd lean toward "no age limit needed, topic/session match is the only test that matters" — but I want that reasoned through explicitly rather than assumed, since a 20-minute-old silently-restored value feels different than a 15-second-old one even though the mechanism is identical.

## Suggested additions to the eventual proposal

- Add an explicit non-goal: "No facilitator-visible signal (grid state, marker, tooltip) distinguishes a recovering participant from any other disconnected participant." Ties directly to readiness-without-spoilers and to not turning disconnection into a performance for the room.
- Add an explicit requirement that the restore/discard decision resolves before the compose control's first paint — no visible transition, no flash of stale content.
- Add a cross-reference note (not a dependency, just a pointer) flagging that issue #32's login-redirect screen is the felt experience for this whole flow, and that its copy should carry the reassurance this change deliberately doesn't put anywhere else.
- State plainly whether facilitators vote and are therefore in-scope for their own draft recovery.
- Carry forward 4c/4d's "no new chrome" list with sound/animation added explicitly, so it reads as a closed list during implementation review rather than an invitation to add "just one small thing."

## Bottom line

This direction, if built as scoped, disappears into the background the way it needs to — I don't see anything here that adds visible interruption to the session itself. My concerns are entirely about the edges the notes didn't reach: what I see on my grid during the gap (nothing new — confirm it stays that way), what the participant feels during the gap (out of scope here, but flag it for #32), and making sure "silent" is enforced as a rendering requirement (before first paint) and not just a copy guideline (no toast).
