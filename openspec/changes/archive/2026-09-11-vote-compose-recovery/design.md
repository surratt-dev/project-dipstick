## Context

Issue #31 traces to `websocket-connection-reauthorization` Decision D4/D7: SEC-26 grace-period recovery is always a full top-level page navigation (`window.location.href = "/auth/login"` in `AuthContext.tsx`/`AuthErrorPage.tsx`), which tears down the JS heap exactly as a tab close would. The backend structurally never receives a composed-but-unsubmitted vote value (D7), so there is nothing server-side to lose — but the frontend has, until now, had nothing that survives the reload either, because there is no client-side persistence of vote-adjacent state anywhere in the codebase today (`grep` for `sessionStorage`/`localStorage` across `packages/frontend/src` returns nothing).

The compose UI itself does not exist yet. This design specifies a persistence/restore contract that can be built, unit-tested, and merged against fixture data now, with the compose UI wiring itself deferred as an integration task owned by whoever builds that UI. `useConnectionHealth`'s `state` (`"connected" | "unknown-reconnecting" | "reauth-required"`) is already a public, consumed value (`connectionHealth.ts`; consumed today by `ConnectionStatusBanner.tsx` and `FacilitatorReadinessGrid.tsx`), so no new hook point is needed for a future consumer to react to `reauth-required` — this design does not add one.

Governing principle, carried forward from exploration without softening: **a stale restore — the wrong topic's answer silently reappearing as if it belonged to the current one — is categorically worse than the mechanism not existing at all.** It does to the participant, via the tool, what the no-early-disclosure rule forbids peers from doing to each other. Wherever the restore logic is in doubt, the answer is discard, not restore.

**Scope decision (superseding the earlier placeholder framing):** this change was originally scoped frontend-only, with the WS registration payload treated as an external, unscoped dependency (task 7.0). That framing is retired. The registration payload is now designed and built as part of this change — see Decision D3 below, which replaces the placeholder-interface language with a concrete payload, its assembly, and its send point. Confirmed by direct inspection at the time this decision was made: `GET /ws/sessions/:sessionId` in `packages/backend/src/realtime/websocket-routes.ts` previously sent no message back to the client on successful connect — no ack, no initial-state push. The only session-scoped WS events a client received (`packages/shared/src/types/realtime.ts`) were `vote_readiness_update` (fires only when someone *else* locks in), `session_state_change`, `vote_revealed`, and `reauth_required` — none an initial-state snapshot. D3 adds exactly one more: `session_registration_snapshot`, sent directly to the connection, once per registration, the same way `reauth_required` is already sent directly to a single connection (`connection-token-refresh.ts`'s `safeSend(registry, scope, id, conn, JSON.stringify({ eventType: "reauth_required" }))` pattern).

## Goals / Non-Goals

**Goals:**
- Persist a composed-but-unsubmitted vote value client-locally, keyed to `(sessionId, sessionTopicId)`, written on every compose-value change.
- Restore it exactly once per page load, on the tab's first WebSocket registration, only after server-authoritative state confirms the topic still matches, is still `voting`, and the participant has no existing lock-in for it.
- Discard it silently and unconditionally in every other case, with the decision resolved before the compose control's first paint.
- Ship independent of issue #32 (redirect trigger) and independent of the compose UI's existence, as a contract verified with fixture data.
- Design and build the WS registration payload (`session_registration_snapshot`, D3) as a first-class backend capability of this change — not deferred, not a placeholder — so `restoreDraft`'s ordering guarantee (D3) has a real interface to be verified against once the compose UI lands, not only fixture data standing in for one.

**Non-Goals:**
- Not a cross-device or server-backed "resume my draft" feature. This stays single-tab, `sessionStorage`-only, never transmitted to the backend.
- Not a second place vote state lives — the backend's `dipstick:reauth-grace:{userId}` marker (D4) stays a content-free recovery-detection flag; nothing here motivates a server-side counterpart.
- Not a facilitator-visible signal of any kind for "recovering with a draft queued." The readiness grid's four baseline states (`connected+not-locked-in`, `connected+locked-in`, `disconnected_voted`, `disconnected_no_vote`) gain no fifth state or variant.
- Not new UI chrome: no toast, banner, sound, animation, or devtools-visible console warning for either a restore or a discard.
- Not an age-based staleness cutoff. Topic/session match plus `voting` status is the whole test; elapsed time is not a signal.
- Not a change to facilitator pacing, reveal eligibility, or outlier flagging — all are keyed to server-authoritative state or vote value, untouched by this mechanism.
- Not the redirect screen's copy or felt experience (#32's scope) — cross-referenced, not depended on.
- Not a relitigation of the 30-second grace period, the two-close-code split, or any other `websocket-connection-reauthorization` decision (D1–D9a).

## Decisions

**D1 — Write on every compose-value change, not on a navigation/unload hook.** A write keyed to "just before the re-auth navigation begins" is a well-known flaky pattern even where it can be made to work at all (`beforeunload`/`pagehide` racing bfcache, mobile OS process termination, no guarantee of synchronous continuation after `window.location.href` is set) — unacceptable for a mechanism protecting ritual-integrity state. Writing on the compose UI's own `onChange`/`onSelect` handler removes the dependency on issue #32 entirely (no navigation call site to hook into is needed) and, as a side effect of doing this correctly, also covers an ordinary tab close/crash with no SEC-26 event involved at all. *Alternative considered:* write-before-navigate, tied to #32's eventual redirect effect — rejected for the flakiness above and for creating an avoidable sequencing dependency on #32.

**D2 — Read/clear exactly once, on the first WebSocket registration after page load; not on every reconnect.** Pinning the read to "first registration this tab performs after a page load, once" covers the SEC-26-recovery reload without needing to detect that a reload was specifically a SEC-26 event. An ordinary in-tab reconnect (a network blip recovered without a page reload) never re-attempts a restore, because the mount-time code path that performs the one attempt never re-runs. The stored entry is cleared at the end of that one attempt regardless of outcome (restored or discarded) — it does not persist for the rest of the tab's life. *Named accepted side effect:* because the trigger is "first registration after any page load," an ordinary manual refresh (F5) also restores a still-valid draft, through the identical checks as the SEC-26 case. This is accepted as an incidental consequence of building the write-on-change/read-once mechanism correctly — not a feature to document or advertise as "your draft is always saved." *Alternative considered:* detect SEC-26 specifically (e.g., via a query param or a marker read) and gate the restore attempt on that detection — rejected as unnecessary complexity once write-on-change removed the reason to distinguish causes at all.

**D3 — Restoration is an ordering constraint, not a race; the registration payload is a real, first-class capability of this change.** The fresh connection's registration payload (server-authoritative current topic, this participant's own lock-in status) must be in hand before the `sessionStorage` read happens or its result is applied to UI state. There is no code path where the storage read, or the application of its result, precedes receipt of that payload. Locked-in server state always wins: if the registration payload indicates this participant already has a lock-in for the current topic — via any mechanism, including a stale second tab or a retry that actually succeeded — the draft is discarded and the UI reflects the server-reported locked-in state, never the draft, regardless of which the local code would have computed first.

**D3a — Payload shape.** A new `WsClientMessage` variant, `session_registration_snapshot`, added to `packages/shared/src/types/realtime.ts` alongside the existing `reauth_required`/`vote_readiness_update`/etc. variants:

```ts
export interface SessionRegistrationSnapshotPayload {
  sessionId: string;
  sessionStatus: SessionStatus;
  currentTopic: { sessionTopicId: string; status: SessionTopicStatus } | null;
  /** This connection's own lock-in status only — never another participant's. */
  hasLockedInVote: boolean;
}
```

`currentTopic` is `null` whenever `sessions.current_topic_id` is `null` — `lobby`/`pre_session` (voting hasn't started) and `wrap_up` (cleared per `SESSION-012`) are both represented this same way; the frontend does not need to special-case `wrap_up`, it only needs to check `currentTopic === null`. `hasLockedInVote` is meaningful only when `currentTopic` is non-null and its `status` is `voting`; it is computed and sent regardless (always this connection's own true status), and `restoreDraft` is responsible for only consulting it under those conditions (task 4.3).

**D3b — When sent.** On *every* successful session-scoped WS registration (`GET /ws/sessions/:sessionId`), not conditionally on "is this a reconnect vs. a first load." The backend has no reliable, cheap way to distinguish a SEC-26 recovery reload, an ordinary F5, or an in-tab reconnect from each other — and does not need to: D2's "restore exactly once per page load" gate is already a frontend-only concept, enforced by the module-local flag in `voteDraft.ts` (tasks.md 3.1). The backend's job is simpler and uniform — always send a fresh snapshot on registration — and the frontend decides, using its own gate, whether this particular registration is the one attempt it will act on. This also means the snapshot is naturally available to a *first* registration (the case `restoreDraft` actually needs), with no special-casing required in `websocket-routes.ts` for "is this the tab's first connection."

**D3c — Assembly and backend module.** A new function, `buildSessionRegistrationSnapshot(userId, sessionId)`, in a new module `packages/backend/src/realtime/session-registration-snapshot.ts`, performing one live DB read (no cache, matching the no-cache principle `evaluateSessionSubscriberAccess` and the delivery-time dispatcher already apply to session-scoped reads):

```sql
SELECT s.status AS session_status,
       s.current_topic_id,
       st.status AS topic_status,
       (v.id IS NOT NULL) AS has_locked_in
FROM sessions s
LEFT JOIN session_topics st ON st.id = s.current_topic_id
LEFT JOIN votes v ON v.session_topic_id = s.current_topic_id AND v.voter_id = $2
WHERE s.id = $1
```

`websocket-routes.ts`'s `GET /ws/sessions/:sessionId` handler calls this after `evaluateSessionSubscriberAccess` grants access and the connection is added to `connectionRegistry`, then sends the result via the existing `safeSend(registry, "session", sessionId, conn, JSON.stringify({ eventType: "session_registration_snapshot", payload }))` helper — the same connection-registry send path `reauth_required` already uses, not a new delivery mechanism.

**Ordering and failure containment, stated explicitly (not left to call-site placement).** The existing registration sequence in `websocket-routes.ts` — `connectionRegistry.register`, `scheduleForceClose`, `scheduleReauthorizationSweep`, `scheduleTokenRefreshMonitor`, `checkAndRecordGraceRecovery` — runs today inside a single unprotected `void (async () => { ... })()` IIFE with no `try/catch` anywhere in it and no backend-wide `unhandledRejection` handler. That is a pre-existing property of this file, not introduced by this change, and fixing it generally is out of scope here. But this change adds a fourth fallible DB round-trip into that exact sequence, and its placement relative to the existing calls is a security-relevant ordering decision, not a style choice:

- `buildSessionRegistrationSnapshot` MUST be called strictly *after* `scheduleReauthorizationSweep`, `scheduleTokenRefreshMonitor`, and `checkAndRecordGraceRecovery` have already run — never before or interleaved between them. Those three calls schedule and record the SEC-26 timers and grace-recovery flag a connection depends on for the rest of its lifetime; this change's own new fallible read must never be positioned where a failure in it could prevent them from running.
- The call MUST be wrapped in its own `try/catch`. On any failure — a DB error, or the zero-row race case below — the handler logs at `warn` and sends no `session_registration_snapshot` message at all. It never throws past this point, never surfaces as an unhandled promise rejection, and never closes or otherwise degrades the connection.
- This is a deliberate silent-discard-shaped failure mode, not an oversight, and it is consistent with this design's own governing principle (Context, above): `restoreDraft` (D3, D4.4) is already required to never apply a value before a registration payload arrives, so "no snapshot arrives this registration" degrades to "this tab's draft, if any, is not restored this load" — the same discard-by-default posture this design already applies everywhere else.
- If the query returns zero rows (e.g., the session was deleted in the narrow window between the access grant and this read), `buildSessionRegistrationSnapshot` returns `null`; the handler treats that identically to a query failure — skip the send, do not throw.

**D3d — Composition with `evaluateSessionSubscriberAccess` (no data leak).** The snapshot is only ever assembled and sent *after* `evaluateSessionSubscriberAccess` has already granted this connection access to this session — it piggybacks on an access decision that has already been made, it does not make a new one. It discloses exactly one thing beyond what the grant itself already implies (that this user may subscribe to this session's events): this user's own `hasLockedInVote` for the current topic, via `voter_id = $2` bound to the authenticated `userId` from `request.session` — never another participant's. This is self-disclosure of the requester's own state, the same category of information the participant already receives implicitly by being allowed to submit or be blocked from submitting a lock-in (`sessions.ts`'s `ON CONFLICT` upsert). No aggregate or other-participant vote data is added to any payload by this design — `FacilitatorReadinessGrid.tsx` and the reveal-gated serializers remain the only places vote content or cross-participant readiness is exposed, and both are untouched by D3.

Both grant paths (`facilitator` and `participant`) receive a snapshot on registration; a facilitator's `hasLockedInVote` will simply read `false` in the ordinary case (facilitators do not submit lock-ins), which is harmless and requires no path-specific branching in `buildSessionRegistrationSnapshot`.

**Call-site discipline, stated explicitly.** `buildSessionRegistrationSnapshot(userId, sessionId)` — like `evaluateSessionSubscriberAccess` before it — performs no internal provenance check on `userId`; it trusts whatever its caller passes. The non-spoofability of `hasLockedInVote` is therefore a property of the one call site in `websocket-routes.ts`, not a guarantee the function itself enforces. That call site MUST pass `request.session.userId` — server-derived from the signed, `httpOnly`, `sameSite: strict` session cookie, set only at OIDC callback — never a client-supplied value from a query param, header, or message field. This constraint is recorded here as a standing design decision, and MUST also appear as a code comment directly on `buildSessionRegistrationSnapshot`'s declaration, so a future second call site inherits the constraint instead of rediscovering it.

**D3e — Audit logging: a stated decision not to log, not silence.** `session_registration_snapshot` sends are not written to `audit_log`. This is deliberate, matching existing precedent: ordinary WS registration/subscription itself is not audited today — only the reauth/refresh/grace-recovery lifecycle layered on top of an established connection is (SEC-25's revocation close, SEC-26's refresh-failure and grace-recovery signals). `session_registration_snapshot` is a passive read of state the participant already has standing to see — their own lock-in status, the current topic — the same category of information the unaudited registration itself already discloses implicitly. It is not an action like vote submission, reveal, or topic advance, all of which remain audited. It does not receive its own `audit_log` row, and this is recorded here so the absence reads as a decision, not an oversight, to anyone reviewing this later.

**D4 — Four explicit discard conditions, enumerated rather than left as "anything else."** A persisted draft for `(sessionId, sessionTopicId)` is discarded, silently and unconditionally, when any of: (i) the server-authoritative current topic differs from the persisted `sessionTopicId` (topic advanced); (ii) the topic matches but its `session_topics.status` is no longer `voting` (revealed or complete); (iii) the session has moved to `wrap_up` and has no current topic at all (`sessions.current_topic_id` cleared per `SESSION-012`); (iv) the `sessionId` itself no longer matches an active session for this participant. Restoration requires the positive case: topic matches, status is `voting`, no existing lock-in (D3).

Condition (iv) is a defensive/race condition, not a normal-path branch, given the current WS access gate. `evaluateSessionSubscriberAccess` (`packages/backend/src/auth/session-subscriber-access-helper.ts`) authorizes a session-scoped WS connection only while `sessions.status IN ('lobby', 'pre_session', 'active', 'wrap_up')`, evaluated at connect time — a session that has already moved past those statuses (closed/complete) fails the connection outright, so the tab never reaches a successful registration to attempt a restore against in the first place. Condition (iv) is therefore reachable only in a genuine race — the session closes in the gap between a successful connect and the restore attempt reading the registration payload — not through ordinary use the way (i)–(iii) are (each reachable via ordinary topic advance). It is kept as an enumerated condition rather than dropped, because the behavior it specifies (discard) is unambiguously correct regardless of how rarely it fires, and because leaving it out would make the four conditions read as exhaustive when they are not. Whoever implements task 4.5's unit test for it should build a fixture for this race window deliberately, not search for a "normal" code path that produces it.

**D5 — Persisted record shape (illustrative, not binding on implementation):** `{ sessionId: string, sessionTopicId: string, value: VoteValue, composedAt: string }`, stored under a single `sessionStorage` key scoped to this mechanism (e.g. `dipstick:vote-draft`). One entry is sufficient — a participant has at most one active session and current topic per tab at a time — so the key itself carries no session/topic scoping; the scoping check happens on read, against the stored record's fields.

**D6 — Restore-or-discard resolves before first paint; this is a rendering requirement, not a copy guideline.** No spinner state, no flash of a stale value before it clears, no visible transition from "old answer" to "blank." A participant whose topic advanced while they were away lands on the fresh topic with an empty compose control, indistinguishable from a participant who was simply slow to start.

**D7 — Contract-level vs. integration-level acceptance scenarios, named as separate tiers.** Contract-level scenarios (verifiable now, against `persistDraft`/`restoreDraft` or equivalent, using fixture data standing in for a real compose component) cover D1–D5 fully and are this change's actual test surface. Integration-level scenarios (require the real compose UI and #32's redirect trigger to exist — e.g. "a participant who reloads via SEC-26 recovery sees their in-progress selection restored") are named as deferred follow-up verification, owed once the compose UI lands, and are not written as if testable now, and not used to block this change's completion.

## Risks / Trade-offs

- **[Risk] A future compose UI implementer treats the same-tab-refresh side effect (D2) as license to build toward a broader "always save my draft" feature.** → Mitigation: state the side effect once, explicitly, as an accepted consequence in the spec and this design — not a documented benefit — so the boundary is a decision on record, not something discovered and reinterpreted during implementation.
- **[Risk] Restore logic drifts toward "restore unless clearly wrong" instead of "discard unless clearly right."** → Mitigation: D4's four discard conditions plus D3's ordering constraint are written as the full positive test for restoration; anything not affirmatively matching all of them discards. Contract-level tests (D7) enforce this directly.
- **[Risk] A visible flash of stale content before discard, if the wiring implementation reads storage after first paint.** → Mitigation: D6 states this as a rendering requirement in the spec, with a contract-level scenario asserting the discard/restore decision is available synchronously before the compose control mounts with any value.
- **[Risk] The mechanism becomes a second de facto vote-state store if a future change reads `sessionStorage` from somewhere other than the one restore call site.** → Mitigation: single key, single read/clear call site (D2), stated as a hard property in the spec; no age-based cutoff or additional read paths are introduced by this design.
- **[Risk] This is the first time vote content — not just draft-presence — persists outside active memory anywhere in this codebase, and that crossing needs to be legible as a security decision, not just an architectural one.** Until now, the project's standing guarantee has been structural: the backend never receives a composed-but-unsubmitted vote value, and the frontend held it in JS memory only — nowhere durable enough to extract except by compromising the live page. D5 changes that: the actual vote value now sits in `sessionStorage`. → Mitigation: the existing minimal-exposure scoping is correct and already answers this — single tab, single key, single call site, no age-based retention, cleared on the first successful restore attempt (D2), never transmitted (Non-Goals) — this risk entry does not change any of it, it only names the boundary explicitly. Two residual properties are worth recording alongside it, for whoever reviews this again later: (1) `sessionStorage` is same-origin, JS-readable by anything with same-origin storage access, not only full-page XSS — a browser extension with broad storage permissions or local devtools access could read it, though this adds no exposure beyond what full XSS already has; (2) `sessionStorage` is not reliably cleared "on tab close" in every real browser — session-restore/crash-recovery features in several browsers persist it across what a user would call a close, so the actual at-rest exposure window can exceed "until the tab closes" in practice, even though D2's read-once-then-clear logic still runs and still clears the entry on the next successful registration regardless of how the tab came back. Neither changes the design; both should be known residuals rather than a silent assumption. Forward-looking note for whoever eventually adds error-reporting/RUM tooling (none exists in this codebase today): the `dipstick:vote-draft`-shaped key carries session content and must be excluded from whatever such a tool captures by default.

## Migration Plan

No database schema changes (D3c's query reads existing `sessions`/`session_topics`/`votes` columns; no new table or column). This ships as: (1) a new, additive frontend persistence/restore module with no existing call sites to migrate; (2) a new, additive backend snapshot module (`session-registration-snapshot.ts`) plus one new `WsClientMessage` variant and one new `safeSend` call site in `websocket-routes.ts`'s existing registration handler — additive to that handler, no change to its existing authorization, timer-scheduling, or grace-recovery logic. Rollout is: (1) merge the persistence/restore contract with its unit tests and the backend snapshot capability together, since this change now owns both sides of the interface D3 defines; (2) wire the compose UI's own `onChange`/mount-time calls into both once that UI is built (tracked wherever that work lives, not gated on this change — see tasks.md 7.1); (3) integration-level scenarios (D7) are exercised once that wiring lands, now against the real `session_registration_snapshot` payload rather than only fixture data. No feature flag or admin toggle — consistent with the standing rule that none of the reauth/staleness mechanisms are made configurable (SEC-26 Decision D9a). Rollback, if ever needed, is deleting the frontend module and its one call site, plus reverting the one added `safeSend` call and payload type in `websocket-routes.ts`/`realtime.ts`; there is no persisted server-side state (D3's payload is computed fresh on every send, never stored) to clean up.

## Open Questions

- **Known limitation for the future compose UI (task 8.1): no live "topic changed" push exists today for a connected, idle participant.** Confirmed by direct inspection of `facilitator-sessions.ts`'s topic-advance handling: the ordinary topic-to-topic branch calls `publishTopicHistoryUpdate` only — a **team-scoped** event delivered over `/ws/teams/:teamId/events`. `publishSessionStateChange`, the session-scoped event, is published only in the wrap-up-entry branch (session status actually transitioning to `wrap_up`), not on ordinary topic-to-topic advance. The doc comment on `SessionStateChangePayload` in `realtime.ts`, which describes it as pushed "when session status transitions (lobby advance, session close, and — once GitHub issue #26 lands — topic advance)," is stale relative to the code as it stands and should be corrected when that file is next touched (not by this change). This is not a defect this change introduces or needs to fix: D2's restore-once gate only needs a payload at the moment of registration, and D3b's registration-only send timing is unaffected. It is named here because it is an open dependency for whoever builds the compose UI (task 8.1) — that UI's steady-state "is my currently-composing topic still current" question, for a participant who stays connected across a topic advance, has no live server push to key off today, and `session_registration_snapshot` alone goes stale the instant the facilitator advances. Closing that gap — a new session-scoped broadcast on topic advance, the compose UI forcing a fresh registration, or another mechanism — is explicitly out of scope for this change and should not be assumed already solved when task 8.1 begins.
- Debounce behavior for the `onChange`/`onSelect` write (none vs. a short debounce) is left as an implementation choice for whoever builds the compose UI — not a requirements-level decision, since either way satisfies "written on every compose-value change" from the participant's perspective.
- Exact `sessionStorage` key name (`dipstick:vote-draft` used above) is illustrative; final naming is an implementation detail for tasks/implementation, not fixed by this design.
- Whether `session_registration_snapshot` should also be sent on the team-scoped route (`GET /ws/teams/:teamId/events`) is left open — D3 scopes it to the session-scoped route only, since the compose UI's restore need is inherently session-scoped and the team-scoped route has no equivalent "current topic for me" concept.
