# BA Review: Proposal — vote-compose-recovery (issue #31)

**Reviewer:** Marcus Delgado, Business Analyst
**Reviewing:** `proposal.md`, `design.md`, `specs/vote-compose-recovery/spec.md`, `tasks.md`
**Lens:** Is each capability specific enough to build without a round-trip back to me? Are acceptance criteria explicit or implicit? Does the artifact set faithfully carry forward what I asked for at exploration review, and does it hold up against BRD SEC-25/26, the voting mechanics doc, and the actual state of the codebase these artifacts describe?

**Bottom line:** This is the tightest artifact set I've reviewed on this project. Every one of my five exploration-stage asks made it in faithfully, not just in spirit — I checked wording, not just intent. I have one finding I consider load-bearing enough to resolve before implementation starts (Section 1: the "registration payload" this whole mechanism is keyed to does not exist as described anywhere in the current codebase), and a handful of smaller precision gaps below it. Nothing here should require new design work; all of it is a paragraph of tightening, same as my exploration review.

## 1. Load-bearing: "the fresh connection's registration payload" is not a real interface in this codebase today — the spec and design assert it as settled when it is not

Design.md's Decision D3 and spec.md's Requirement 3 both hinge on a single object: "the fresh connection's registration payload — including the server-authoritative current topic and this participant's own lock-in status for it." D3 states plainly: "There is no code path where the storage read... precedes receipt of that payload." Task 4.1 has `restoreDraft(registrationPayload)` accept this as an input. The design's Context section leans on this being settled: "`useConnectionHealth`'s `state`... is already a public, consumed value... so no new hook point is needed for a future consumer to react to `reauth-required` — this design does not add one."

That last sentence is true for `connectionHealth.ts`'s three-value state (`connected`/`unknown-reconnecting`/`reauth-required`) — I confirmed that against `packages/frontend/src/realtime/connectionHealth.ts` directly. It is **not** true for "current topic + this participant's own lock-in status delivered atomically at WS registration," which is a different claim quietly riding on the first one's credibility. I checked the actual WS registration handler:

- `packages/backend/src/realtime/websocket-routes.ts`'s `GET /ws/sessions/:sessionId` handler, on a successful connection, does exactly this and nothing else: authorizes access, registers the connection in `connectionRegistry`, schedules the SEC-25/SEC-26 timers, and checks/records grace recovery. **It sends no payload back to the client at all.** There is no ack message, no initial-state push, nothing carrying `currentTopic` or a lock-in flag.
- The only WS events a session-scoped client ever receives (`packages/shared/src/types/realtime.ts`) are `vote_readiness_update` (fires only when *someone else* locks in — carries `voterId`, not "am I locked in"), `session_state_change`, `vote_revealed`, and `reauth_required`. None of these is an initial-state snapshot delivered on connect.
- There is no participant-facing REST endpoint today that returns current topic + this participant's own lock-in status either — I checked `sessions.ts` (only a vote-submission `POST`) and `content.ts` (no matching read). `currentTopic` as a served field exists only on the **facilitator** side (`facilitator-sessions.ts`), which is a different grant path and not what a participant's compose UI would call.

So "the registration payload" as named in D3/D4/D5's illustrative shape and spec Requirement 3 is not a thing that exists anywhere in this codebase right now — under any name, on the WS side or the REST side. This is a real gap, not a pedantic one, for three reasons:

1. **D3's ordering guarantee is unverifiable as written.** "No code path precedes receipt of that payload" is a strong claim about a payload whose actual source (WS push? REST fetch chained after registration? something new?) is undefined. Contract-level tests can and should still pass fixture data into `restoreDraft` regardless (that part is fine, per D7's own tiering) — but the *design-level* claim that this ordering is already structurally enforceable, because the hook point already exists, is not supported by what I found. It's an assumption dressed as a settled fact.
2. **Task 7.1 inherits the gap silently.** "Once the compose UI exists, wire its mount-time effect (after `useConnectionHealth` registration) to call `restoreDraft`" reads as routine wiring. It isn't — whoever picks this up first has to *invent* the mechanism that assembles "current topic + my lock-in status" in the first place (a new WS push on registration? a REST call raced against the WS connect? something else?), and that's real design work with its own ordering and race questions, not a wiring task. As written, task 7.1 will be picked up by someone who reasonably assumes the payload already exists, discovers it doesn't, and is back asking a clarifying question — precisely the round-trip this review stage exists to prevent, just deferred to the follow-up change instead of caught here.
3. **It affects how "server-authoritative" should be read in the spec.** Every discard/restore scenario in spec.md is written as `GIVEN a persisted draft... WHEN the registration payload reports X`. That's the right shape for a contract-level scenario using fixture data (D7), and I have no notes on the scenarios themselves. But the spec should say, once, explicitly, that "the registration payload" is this change's own placeholder name for an interface that does not yet exist and is out of this change's scope to build — not imply, by omission, that it's an established wire format this design is merely consuming.

**Suggested fix, concrete:** Add a line to design.md's Context or Open Questions — "The `registrationPayload` shape referenced throughout this design (current topic + this participant's lock-in status) is this change's own interface contract for what a future caller must supply to `restoreDraft`; it is not an existing WS or REST payload in the codebase today (confirmed: WS registration in `websocket-routes.ts` sends no initial-state payload; no participant-facing REST endpoint returns this either). Assembling it is scoped to the compose-UI integration task (tasks.md 7.1), not to this change." That one paragraph converts an implicit, false-by-omission claim into an explicit, honest scope boundary — and it's the kind of thing that, left unstated, becomes a surprised implementer's Slack message to me in three months, which is exactly what I'm here to prevent.

This does **not** change my assessment that the change is well-scoped to ship now as a standalone contract — D7's tiering already protects the current change from needing this interface to exist. It changes what "no dependency on #32" should also say alongside it: there's a second, unnamed dependency here (the registration-payload assembly), and it should be named as clearly as the #32 dependency already is.

## 2. Minor: discard condition (iv) — "sessionId no longer matches an active session" — may be unreachable given the actual access gate, and the spec should say so or drop the ambiguity

Spec Requirement 4, condition (d), and design D4(iv): the draft is discarded when "the `sessionId` itself no longer matches an active session for this participant." I checked `evaluateSessionSubscriberAccess` (`packages/backend/src/auth/session-subscriber-access-helper.ts`): a WS connection to `/ws/sessions/:sessionId` is authorized only while `sessions.status IN ('lobby', 'pre_session', 'active', 'wrap_up')`, evaluated at connect time. A session that has moved past those statuses (closed/complete) would fail the connection outright — the tab would never reach a successful registration to attempt a restore against in the first place.

This means condition (iv) may be **unreachable in the current access model** except in a genuine race (session closes in the gap between a successful connect and the restore attempt reading it) — worth stating as a defensive condition rather than a normal-path branch, so whoever writes task 4.5's unit test for it (currently listed flatly alongside the other three, which *are* reachable via ordinary topic advance) knows they're constructing a fixture for a race window, not a common case, and doesn't spend time looking for a "normal" code path that produces it. Not a blocker — the behavior (discard) is unambiguously correct regardless of reachability — just a precision gap worth one sentence in design.md.

## 3. Verification against BRD and voting mechanics — all confirmed accurate

- **SEC-25/SEC-26 grounding (BRD lines 596, 598):** the proposal's framing — SEC-26 requires a defined grace period, re-authentication notice, and "session state must not be corrupted by the disconnection" — is represented accurately. The proposal correctly does not relitigate the grace period length, close-code split, or D9a's no-feature-flag rule (BRD doesn't specify these; they're `websocket-connection-reauthorization`'s decisions, correctly cross-referenced rather than restated).
- **SEC-16/SEC-22 (BRD lines 572, 588 — vote/trend data not logged or replicated):** the proposal's repeated claim that this mechanism "SHALL NOT introduce any new server-side or database-side store of vote content" is consistent with these and with D7's structural argument in the archived `websocket-connection-reauthorization/design.md` (confirmed by direct read: "the backend already never receives a composed-but-unsubmitted vote value... SEC-16/SEC-22: vote values are never transmitted before lock-in"). Accurate quote, accurate use.
- **Voting mechanics doc (`voting mechanics - enhanced.md`):** the vote value enum referenced in D5's illustrative record shape (`VoteValue`) is consistent with the three documented vote types — finger count 1–4, thumbs up/down, and (trend topics) up/down/flat. The proposal doesn't redefine or narrow this enum, which is correct; it treats `VoteValue` as an opaque type owned elsewhere.
- **`session-topic-lifecycle` (`SESSION-012`):** I read the current spec directly. The proposal's claim that advancing past the final topic "clears `sessions.current_topic_id` outright rather than pointing at a different topic" is exact — `SESSION-012`'s own scenario text: "`sessions.status` transitions to `wrap_up`... and `sessions.current_topic_id` is cleared." Discard condition (c) is grounded correctly, not an invented edge case.
- **`websocket-staleness-signal` (four baseline grid states):** the proposal's claim that the grid has exactly four baseline states (`connected+not-locked-in`, `connected+locked-in`, `disconnected_voted`, `disconnected_no_vote`) and that this change adds no fifth is an exact match to the current spec's own "Facilitator-only, cause-blind grid marker" requirement. Good — this is a claim that would have been easy to get subtly wrong (e.g., miscounting a state that spec already treats as a marker/overlay rather than a fifth state), and it's stated correctly.

No requirement in BRD or the voting mechanics doc is contradicted, narrowed without acknowledgment, or silently reinterpreted anywhere in these four artifacts.

## 4. Verification of my own exploration-stage recommendations — all five carried forward faithfully

I compared each of my asks from `explore-review-ba.md` against the current artifacts, not just for intent but for whether the specific resolution I proposed is what actually shipped in the wording:

1. **Persist-on-change over persist-before-navigation.** My ask: resolve Section 3 as a settled decision, not a judgment call, and adopt write-on-change specifically because write-before-navigate is a known-flaky pattern. Design.md D1 states this exactly, including my own reasoning (`beforeunload`/`pagehide` racing bfcache, no guaranteed synchronous continuation after `window.location.href`) and my "removes the dependency on #32 entirely, not just decouples" framing, verbatim in substance. **Faithful.**
2. **The `wrap_up`/no-topic discard branch.** My ask: add this as an explicit fourth discard condition, distinct from "wrong topic," grounded in `SESSION-012` clearing `current_topic_id` outright. Design D4(iii) and spec Requirement 4(c) both state it as its own enumerated condition, with its own scenario (`Requirement: Discard conditions...` → "A draft is discarded when the session has moved to wrap_up"). **Faithful**, and correctly distinguished from condition (a) (topic differs) rather than collapsed into it.
3. **Locked-in precedence as an ordering constraint, not just a rule.** My ask: state explicitly that server-authoritative state must be *received* before storage is read or applied — a two-step sequence, not a race, with the ordering itself as a testable property. Design D3 and spec Requirement 3 both state this as an ordering constraint with the exact two-step structure I proposed, plus the GIVEN/WHEN/THEN I drafted almost verbatim (down to "a stale second tab, a retry that actually succeeded"). **Faithful.** (This is also exactly where Section 1 above lives — the ordering constraint is stated correctly relative to *a* payload; my finding is that the payload itself isn't grounded, not that the ordering logic built on top of it is wrong.)
4. **Precise clear trigger and persisted-record shape.** My ask: pin the read/clear trigger to "first WebSocket registration after page load, once" rather than "the registration that follows a recovery," and state the record as a real structure. Design D2 and D5 do exactly this, including the "named accepted side effect" framing for the ordinary-refresh case that I flagged as needing to be stated once and not leaned into as a feature — D2 states it, and the design's Section 7 response explicitly holds the line I asked for on not treating that side effect as license to build toward "always save my draft." **Faithful**, and the response-to-review section shows the line was actually understood, not just copied.
5. **Contract-level vs. integration-level test split.** My ask: state two explicit tiers, name which scenarios belong to which, and don't let anyone write an E2E scenario against components that don't exist yet. Design D7 states the split with the same two tiers and the same reasoning ("Integration-level scenarios... are named as deferred follow-up verification, owed once the compose UI lands... not used to block this change's completion"), and tasks.md Section 5 and Section 7 operationalize it correctly — Section 5 is the contract-level suite, Section 7 is explicitly "Deferred integration follow-up (tracked, not part of this change's completion)." **Faithful**, and correctly carried into tasks.md, not just design.md.

None of my five asks were watered down, reinterpreted, or dropped. This is exactly the "paragraph of tightening, not new design work" outcome I was hoping for at exploration review.

## 5. Smaller notes — none blocking, worth a line each

- **Spec Requirement 5's non-goal framing is unusually strong and I want it on record as correct, not just adequate.** "The application SHALL NOT surface any toast, banner, sound, animation, or devtools-visible console message that distinguishes a restore from a discard from an ordinary empty compose control" is stated as a hard SHALL NOT, not a stylistic preference — this is exactly the rigor I asked Devon for at exploration ("a discarded draft must also be indistinguishable at the code level, not just visually"). Good.
- **Task 6.4's guardrail ("grep the diff for any `fetch`/API client usage — expect none")** is a genuinely good, concrete, checkable acceptance condition for a non-goal that's otherwise easy to hand-wave past in code review. I'd like to see this pattern — a stated verification command, not just a checkbox — used more often across the project's non-goal guardrails generally; flagging it here as a positive example, not a gap in this change.
- **Proposal's Impact section says "no backend, API, or database changes."** That's accurate for *this* change's own diff. Given Section 1 above, I'd tighten it to acknowledge that a future change (whoever owns task 7.1, or possibly its own follow-up) will need to introduce *some* interface — new or reused — to supply the registration payload this module consumes. Not a correction to this proposal's scope, just a place where "no backend changes" could be misread as "no backend changes will ever be needed for this mechanism to actually work end-to-end," which isn't true.

## Summary of asks before this moves to Tasks/implementation

2. State in design.md that discard condition (iv) (session no longer active) is a defensive/race condition given the current WS access-gate behavior, not a normal-path branch, so its unit test isn't built looking for a "normal" trigger that doesn't exist (Section 2).
3. Optionally tighten the proposal's Impact section so "no backend, API, or database changes" reads as scoped to this change's own diff, not as a claim that no backend work will ever be needed to wire this end-to-end (Section 5).

Nothing above requires new design work — the same standard I held Devon's exploration notes to. Item 1 is the one I'd actually block on if I had blocking authority at this stage; it's a factual claim in the design ("no new hook point is needed") that I can show, by direct inspection of the code it's making a claim about, does not hold for the specific interface this design depends on.
