# Security Review: vote-compose-recovery

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope:** design.md, proposal.md, specs/vote-compose-recovery/spec.md (GitHub issue #31)
**Method:** Design read against current implementation of `websocket-routes.ts`, `session-subscriber-access-helper.ts`, `connection-token-refresh.ts`, `audit-logger.ts`, and the `votes`/`sessions`/`session_topics` schema, to verify the design's claims are accurate to the code they build on top of, not just internally consistent.

## Summary

The backend half of this change (D3) is well-scoped and I can verify its central safety claim directly: `userId` is server-derived from the signed, `httpOnly` session cookie (`request.session.userId`, set only at OIDC callback), never client-suppliable, so `hasLockedInVote`'s `voter_id = $2` binding cannot be spoofed by a connecting client. The snapshot's placement after `evaluateSessionSubscriberAccess` grants access is correctly reasoned and matches the only viable insertion point in the existing handler — I traced the handler and confirmed no code path sends anything to the client before that grant resolves. My findings are one real (if narrow) gap in the authorization model's self-enforcement, one process gap around audit logging that the design should resolve explicitly rather than leave silent, and a threat-model note on `sessionStorage` that the design's Non-Goals correctly bound but does not name as a security decision in its own right.

Nothing here blocks the design as scoped. Findings 2 and 3 are things I want on record before implementation, not blockers to writing tasks.

---

## Finding 1 — Authorization scoping is correct; call-site discipline is the actual control, not a structural guarantee

**Verified accurate.** I read `session-subscriber-access-helper.ts` and `websocket-routes.ts` directly. `evaluateSessionSubscriberAccess(session.userId, sessionId)` is called with `session.userId` sourced from `request.session` — populated by `@fastify/session`, Redis-backed, `httpOnly`/`secure`/`sameSite: strict` cookie, written only at OIDC login (`routes/auth.ts`). There is no query param, header, or message field on `GET /ws/sessions/:sessionId` through which a client supplies its own userId. D3d's claim — "self-disclosure ... via `voter_id = $2` bound to the authenticated `userId` from `request.session`" — is accurate to the code as it stands today.

**Caveat worth naming in the design, not just in this review:** `evaluateSessionSubscriberAccess` itself is a generic `(userId, sessionId) -> grant` function with no internal provenance check on `userId` — it trusts whatever the caller passes. The same will be true of `buildSessionRegistrationSnapshot(userId, sessionId)` as specified in D3c. The non-spoofability property I just verified is a fact about the *one current call site* in `websocket-routes.ts`, not a structural guarantee the function itself enforces. This is exactly the pattern I flag on every review (see my persona's "Secure Defaults That Don't Require Discipline to Maintain"): a control that depends on every future call site remembering to pass `request.session.userId` and never a client-influenced value is a control that will eventually be defeated by someone adding a second call site under time pressure. I'm not asking for a redesign — a single-call-site function reading a session-derived parameter is a normal and reasonable pattern here — but I want this named as a standing constraint (e.g., a code comment on `buildSessionRegistrationSnapshot` stating "userId MUST be `request.session.userId`, never a client-supplied value" — mirroring the comment pattern already used elsewhere in this codebase) so the next person who touches this function inherits the constraint instead of having to rediscover it.

## Finding 2 — Audit logging for the new WS message is an implicit decision, not a stated one

Per BRD SEC-13/SEC-14 (restated in `websocket-session-authorization`'s "WebSocket-triggered actions are audit-logged with delivery context" requirement) and the established pattern I traced through `audit-logger.ts` and its `AuditEventName` catalog, this codebase treats WS-channel security-relevant events as requiring an `audit_log` row with the same fidelity as HTTP events: vote submission, reveal, state changes, topic advance, the SEC-25 revocation close, the SEC-26 refresh-failure, and the SEC-26 grace-recovery signal are all audited. I confirmed by direct inspection that **ordinary successful WS registration/subscription itself is not currently audited** — only the reauth/refresh/recovery lifecycle layered on top of an established connection is. That's the right precedent to reason from, and by that precedent `session_registration_snapshot` — a passive, per-registration read of state the participant already has standing to see — does not obviously need its own `audit_log` row the way an *action* (submit, reveal, advance) does.

My finding is not "add an audit row." It's that **design.md and spec.md never mention audit logging for this message at all** — not to require it, not to explicitly exempt it. Every other WS-adjacent decision in this codebase's design docs (see D3d itself, and the `websocket-connection-reauthorization` design this change builds on) states its audit posture as a reasoned decision on the record, even when the answer is "no new row needed." This design should do the same: add one sentence to D3 (or a new D3e) stating explicitly that `session_registration_snapshot` sends are not separately audit-logged, and why — consistent with registration itself being unaudited today, and because the payload discloses only state the participant already holds standing to know via other means (their own lock-in status, current topic). Silence here reads, to a security reviewer coming to this later without the context you and I have now, as an oversight rather than a decision. Given how deliberately every other disclosure boundary in this design is justified (D3d's whole paragraph exists for exactly this reason), leaving this one boundary unstated is inconsistent with the design's own standard for itself.

## Finding 3 — sessionStorage persistence of vote *content* is a real, if narrow, first-time shift in the threat model — name it as one

I confirmed by inspection (design.md's own context section, and a grep of `packages/frontend/src`) that this is the first client-side persistence of vote-adjacent state anywhere in the codebase. Until this change, the project's standing guarantee has been structural: the backend never receives a composed-but-unsubmitted vote value, and — as a corollary that was true only incidentally, not by design — the frontend held it in JS memory only, meaning it existed nowhere durable enough to be extracted except by compromising the live page. D5 changes that: the vote's actual value (not just "a draft exists") now sits in `sessionStorage`, which is:

- Same-origin, JS-readable by any code running on the page — so it adds no exposure to an attacker who already has XSS (they can already read live component state), but it does add exposure to anything with same-origin storage access that *isn't* full XSS: a browser extension with broad storage permissions, a devtools-open local user, or future instrumentation that snapshots storage without itself needing script-execution-level access to the page.
- Not reliably cleared "on tab close" in every real browser configuration. The spec-nominal behavior (cleared when the tab closes) is what D2/the Non-Goals section implicitly assumes, but several browsers' "reopen closed tab" / crash-recovery / session-restore features persist `sessionStorage` across what a user would call a "close," not just a reload. This doesn't break any requirement here — the mechanism's own read-once-then-clear logic (D2) still runs and still clears the entry on the *next* successful registration regardless of how the tab came back — but it does mean the actual at-rest exposure window can be longer than "until the tab closes" in practice, and I'd rather that be a known, named residual than an assumption baked silently into the design's risk reasoning.
- Not addressed by any telemetry/error-reporting concern today — I checked, and this codebase has no Sentry/Bugsnag/RUM-style tool wired into the frontend currently, so there's no live vector where a crash-reporting SDK's default storage-snapshotting behavior would exfiltrate draft vote content to a third party. This is a forward-looking note, not a current finding: if such tooling is ever added, whoever adds it needs to know a `dipstick:vote-draft`-shaped key exists and carries session content, so it gets excluded from whatever the tool captures by default.

None of this is a reason to change the design — D5's "single tab, `sessionStorage`-only, never transmitted" scoping is the correct minimal-exposure choice, and is explicitly the right call against the alternatives (`localStorage` would be strictly worse: cross-tab, no natural clear point). My finding is narrower: the Risks/Trade-offs section lists four risks, all framed as *ritual-integrity* or *architectural-drift* risks (stale restore, ambiguous logic, visible flash, second store). None is framed as a *security/data-classification* risk, even though this design is the first place in the codebase that moves vote content — which the project's own data classification already treats as sensitive per BRD SEC-16/SEC-22 (the same standard that keeps vote values out of audit log metadata) — into a persistence layer outside active memory. I'd like one Risk entry added, in the same enumerated form as the other four, naming this explicitly: *persisting vote content to `sessionStorage`, even single-tab and unsent, is a boundary this project has not crossed before; mitigation is the existing minimal-exposure scoping (single key, single call site, no age-based retention, cleared on first successful restore attempt) — already true of the design as written, just not named as answering a security question.* This is the kind of decision that should be legible as deliberate to someone doing exactly the review I'm doing now, six months from now, without having to reconstruct that it was considered.

## What I verified and did not find problems with

- **Data access boundary (D3d):** Correctly rides the existing `evaluateSessionSubscriberAccess` gate. I traced the actual handler in `websocket-routes.ts` line-by-line: the only client-facing action before the grant resolves is `socket.close()` on denial (a close frame, no payload); `connectionRegistry.register` — the point after which the connection becomes reachable for any send — only executes after the grant check passes. There is no code path today, and the design proposes none, where the snapshot could reach a connection before authorization is decided.
- **Cross-participant disclosure:** The D3c query's `voter_id = $2` binding correctly scopes `hasLockedInVote` to the connecting user only; I confirmed the `votes` table schema (`voter_id uuid NOT NULL REFERENCES users(id)`, unique on `(session_topic_id, voter_id)`) supports exactly this read with no risk of the query returning another participant's row. The facilitator-gets-`false`-harmlessly reasoning in D3a/D3d is sound and requires no path-specific branching, consistent with how `evaluateSessionSubscriberAccess` already treats facilitator and participant grants uniformly downstream.
- **No new cache/staleness risk:** D3c's "no cache, live read on every send" matches the established `evaluateSessionSubscriberAccess`/delivery-time-dispatcher convention (Decision 6 in the sibling helper) — this design doesn't introduce a second caching discipline to keep in sync with the first.
- **No second vote-state store:** D3's server-side payload is computed fresh and never persisted; the client-side draft is `sessionStorage`-only. Neither introduces a durable server-side or cross-device store of vote content, consistent with the Non-Goals and with SEC-16/SEC-22's standing constraint that audit metadata (and, by the same logic, any new persistence) must not carry vote values into a place they don't already reach.

## Recommendation

Proceed with implementation. Before tasks.md is finalized, I'd like:
1. A one-line addition to D3c/D3d (or a comment on `buildSessionRegistrationSnapshot`) stating the `userId`-must-be-server-derived constraint explicitly (Finding 1).
2. A sentence in D3 stating the audit-logging posture for `session_registration_snapshot` explicitly, even though I believe "no new row" is the right answer (Finding 2).
3. A fifth Risk entry naming the `sessionStorage`-vote-content boundary as a security decision, not only an architectural one (Finding 3).

None of these change the design's shape. They convert three implicit calls into three recorded ones, which is the whole of what I'm asking for here.
