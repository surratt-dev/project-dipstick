## 2. Return-to mechanism (reauth-return-to)

- [x] 2.1 Confirm the complete set of allow-listed internal path shapes for `returnTo` (design.md Open Questions names `/session/:id` and `/team/:id` as a starting point) against `executeJoinFlow`'s existing redirect-target construction in `packages/backend/src/routes/auth.ts`. Match `:id` against this application's UUID id format specifically — not a loose "up to the next `/`, `?`, or end-of-string" class (design.md Decision 3, per Tomás Ferreira's design review) — and accept an optional `?`-prefixed query string suffix on an otherwise-matching path rather than dropping the whole value when one is present (design.md Decision 3, per Marcus Oyelaran's design review).
- [x] 2.2 Reject/strip any `returnTo` value containing `://`, a leading `//`, an explicit scheme/authority component, a raw CR or LF character, or a backslash (`\`), before the allow-list match in task 2.3 — this ordering (character-rejection checks before the allow-list pattern match) matches design.md Decision 3's intended runtime order. Each rejection also goes through task 2.3's debug/warn log path (design.md Decision 3; CRLF/backslash checks per Tomás Ferreira's design review).
- [x] 2.3 In `GET /auth/login`'s handler, accept an optional `returnTo` query parameter; after task 2.2's character-rejection checks pass, validate it against the allow-list; on match, add `stateData["returnTo"] = returnTo` alongside the existing `pendingJoinToken` handling; on no match (including a rejection from task 2.2), drop it silently (no error surfaced to the caller) but emit a `request.log.debug`- or `.warn`-level structured log noting the rejected value and rejection reason, so repeated allow-list probing is visible to anyone who goes looking, even though it is not an audit-tier event (design.md Decision 3; per Tomás Ferreira's design review — blocking).
- [x] 2.4 Confirm the `returnTo` handling added in tasks 2.2/2.3 (`/auth/login`) and 2.5 (`/auth/callback`) does not branch on which OIDC provider is configured — the allow-list check, character rejection, and redirect logic all run against the shared, provider-agnostic auth flow, with no Entra-specific (or any other IdP-specific) code path. This is a standing project requirement: multi-provider OIDC support is not Entra-only, and this mechanism must not become the exception (per [[project_oidc_multi_provider]]).
- [x] 2.5 In `GET /auth/callback`'s handler, read `stateData.returnTo` from the same `redis.getdel` payload already read for `pendingJoinToken`. When `pendingJoinToken`'s redirect is used, ignore `returnTo`. Otherwise, when a valid `returnTo` was stored, redirect there instead of the `/team/:teamId`/`/no-team` default.
- [x] 2.6 Add tests for both allow-listed shapes named in task 2.1: (a) login with a valid allow-listed `/session/:id` `returnTo`, complete callback with no join token, assert redirect to the stored path; (b) the same for a valid allow-listed `/team/:id` `returnTo`. Parametrize or duplicate so both shapes are exercised explicitly, not just one representative case.
- [x] 2.7 Add a test: login with both a `pendingJoinToken` and a `returnTo`, assert the join flow's redirect wins and `returnTo` is unused.
- [x] 2.8 Add a test: login with a non-allow-listed or scheme-bearing `returnTo`, assert it is dropped and login/callback behave exactly as with no `returnTo`.
- [x] 2.9 Add a test confirming the destination route's own authorization still runs on redirect (e.g., a `returnTo` pointing at a session the user lost access to during re-auth is denied by that route's normal check, not bypassed).
- [x] 2.10 Confirm join-token log redaction (`join-link` spec) is unaffected — `returnTo` values are internal paths, not secrets, so no redaction is required for them, but verify no existing redaction rule accidentally matches or mis-handles the new query parameter.
- [x] 2.11 Add a test asserting a rejected `returnTo` value (non-allow-listed shape, scheme/authority-bearing, or containing a CRLF or backslash) emits a debug/warn log entry via task 2.3's log path, and does NOT write an `audit_log` row (this is a discard-trace log, not an audit event) (per Tomás Ferreira's design review).
- [x] 2.12 Add a test asserting the stored `returnTo` value is single-use: after a callback redeems it (task 2.5), a second callback attempt against the same OIDC `state` cannot read or redeem the same `returnTo` value again.
