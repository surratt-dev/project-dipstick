## Why

A live Health Check session runs almost entirely over its WebSocket connection, and today the 90-minute absolute session lifetime (NFR-AUTH-005/SEC-26) ends that connection by sending the same disclosure-blind close code used for a revoked or never-granted connection — the one code `websocket-staleness-signal`'s client deliberately cannot distinguish from an ordinary network blip. A facilitator or participant whose session ages out mid-ritual is left retrying forever in `unknown-reconnecting`, never routed to the `reauth-required` prompt SEC-26 already built for exactly this kind of recoverable expiry. Fixing the routing surfaces a second gap immediately behind it: the CTA that prompt offers ("Log in again") drops the user on a generic team page, not back in the room they left, because no return-to path exists in the OIDC login/callback flow. Neither gap is a new product concept — OR-1.7 and the Live Voting use cases already commit to "reconnect, re-authenticate, rejoin" as the contract for a mid-session token expiry. What's missing is that the absolute-lifetime timer doesn't invoke that contract, and the contract's own exit door doesn't lead back to where the user was.

This is the session-continuity gap BRD §16 OQ-2(b) already named as open ("what timeout or staleness policy applies to a session stuck in an active or wrap-up state") and that `http-auth-audit-log-coverage` (issue #30) explicitly deferred, twice, to its own follow-up issue. This is that issue.

## What Changes

- Fix the WebSocket absolute-timeout force-close to send the disclosed `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (the same code SEC-26's refresh-failure path already uses) instead of the disclosure-blind `STALE_SIGNAL_CLOSE_CODE` it sends today. The client's existing `reauth-required` state machine and CTA — built and shipped by `reauth-required-client-prompt` — already do the right thing once they receive the correct signal; no new client-side state is introduced. **BREAKING** (spec-level): this reverses part of `websocket-session-authorization`'s existing "same close code for revocation and absolute-timeout" requirement, deliberately, for the absolute-timeout case only.
- Add a return-to mechanism to the OIDC login/callback flow: the current session/page URL is carried through the OIDC `state` round-trip (the same pattern `join-link`'s `joinToken` already establishes) so that following the `reauth-required` CTA lands the user back in the session they were in, not `/team/:teamId` or `/no-team`. This flow is the same `/auth/login` → IdP redirect → `/auth/callback` sequence every login already uses, for whichever IdP is configured — no provider-specific behavior is introduced.
- Fix `ReauthRequiredTreatment.tsx`'s copy so the vote-loss sentence ("Any vote you haven't submitted yet will be lost") does not render for the facilitator call site, since facilitators never vote (per the ritual narrative, BRD.md §3 — "each participant votes" — and `entities-and-relationships.md`'s Facilitator relationship list, which has no "casts vote" entry; no single requirement ID states this directly). This is a narrow, named exception to the copy string only — the shared component, its single state machine, and its role-blind CTA/navigation mechanism (Decision D9) are unchanged.
- Add a quiet, participant-facing "Facilitator reconnecting…" indicator for the window during which the facilitator is re-authenticating, so participants can tell "she's thinking" from "the room is stuck" without inferring it from stalled progress alone.

**Explicitly out of scope:** verifying or building "rejoin with state restored" (topic position, vote state, readiness grid) — the live-session voting UI that OR-1.7's fuller contract would rejoin a user *into* does not exist yet (`SessionConnectionHost.tsx`/`FacilitatorConnectionHost.tsx` are explicitly stubbed). That is a separate follow-up issue once that UI exists, not this change. Also out of scope: reopening `websocket-staleness-signal`'s role-blind reauth *mechanism* (one component, one state machine, one close-code path) beyond the single copy-string carve-out above; a pre-expiry warning affordance (treated as a distinct, later UX decision); admin reassignment of facilitator control and partial-session retention policy (BRD OQ-2(a)/(c)); HTTP-side 401 parity for in-session action calls (`SessionLobbyPage.tsx`'s `start`/`begin-voting`/`action-items-review`, none of which route to a reauth flow today) — a real, bounded-risk gap, scoped as its own named follow-up issue rather than left implicit (see design.md Open Questions for the disposition and rationale).

## Capabilities

### New Capabilities

- `reauth-return-to`: carrying the originating session/page URL through the OIDC `state` round-trip so the `reauth-required` CTA's login flow returns the user to it, generalizing the destination-preservation pattern `join-link` established for join tokens to the re-authentication case, provider-agnostically.
- `facilitator-reconnect-indicator`: a new, cause-blind, participant-facing signal that the facilitator's own connection is currently `unknown-reconnecting`, and the delivery mechanism that gets that signal to participants (today, participants receive no visibility into the facilitator's connection health at all).

### Modified Capabilities

- `websocket-session-authorization`: the "Server-initiated close codes do not disclose the cause of connection termination" requirement currently mandates the same disclosure-blind close code for both a rejected subscription and the absolute-lifetime force-close. This changes the absolute-lifetime case specifically to use the disclosed `REAUTH_GRACE_EXPIRED_CLOSE_CODE` instead, since an expected 90-minute ceiling is not a fact requiring non-disclosure the way a revocation is. The rejected-subscription case is unchanged.
- `websocket-staleness-signal`: the "Copy and CTA are identical regardless of participant or facilitator role" requirement currently mandates byte-identical rendered output for both roles. This adds a narrow, named exception for the vote-loss sentence only (facilitators never vote), leaving the shared component, state machine, ARIA role, and CTA/navigation mechanism otherwise role-blind and unchanged.

## Impact

- **Backend:** `packages/backend/src/realtime/websocket-routes.ts` (`CLOSE_FORCE_EXPIRED` constant assignment), `packages/backend/src/realtime/connection-registry.ts` (`scheduleForceClose`), `packages/backend/src/routes/auth.ts` (`/auth/login`, `/auth/callback` — return-to parameter, Redis state payload), and the connection-registry/websocket-routes layer that would need a mechanism to signal a facilitator's connection health to session participants (does not exist today).
- **Frontend:** `packages/frontend/src/components/ReauthRequiredTreatment.tsx` (role-aware copy), a new participant-facing indicator component consuming `connectionHealth.ts`'s existing state machine (no fork), and whatever surface currently initiates `/auth/login` navigation (adding the return-to parameter).
- **Specs:** delta specs for `websocket-session-authorization` and `websocket-staleness-signal`; new specs for `reauth-return-to` and `facilitator-reconnect-indicator`.
- **No database schema changes** anticipated; the return-to value travels through the existing Redis-backed OIDC `state` payload, the same store `joinToken` already uses.
- **No change** to NFR-AUTH-005's 90-minute policy number, to SEC-26's refresh/retry mechanics, or to the no-manager/facilitator-from-another-team protective constraints — re-authentication runs through the same OIDC flow every login uses and cannot grant a role or team membership the user didn't already hold.
