## Context

This change closes the gap `http-auth-audit-log-coverage` (issue #30) twice deferred and BRD §16 OQ-2(b) already named open: what happens, from inside the room, when `ABSOLUTE_LIFETIME_MS` (90 minutes, NFR-AUTH-005/SEC-26) fires on a live WebSocket connection. Today `websocket-routes.ts`'s `scheduleForceClose` closes the socket with `CLOSE_FORCE_EXPIRED`, an alias of `STALE_SIGNAL_CLOSE_CODE` (`packages/shared/src/types/ws-close-codes.ts`, value 4000) — the code `websocket-staleness-signal`'s client-side state machine (`connectionHealth.ts`) is deliberately built to treat identically to a raw network drop. The client enters `unknown-reconnecting` and retries forever with exponential backoff; the one code that machine *does* route differently, `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (value 4001), is never sent for this cause.

Three already-shipped capabilities bound this design tightly:
- `websocket-connection-reauthorization`'s SEC-26 path (silent refresh, grace period, `REAUTH_GRACE_EXPIRED_CLOSE_CODE`) is the disclosed-close mechanism this change reuses. Reuse means: send the same close code, land in the same client state, use the same CTA. It does not mean copying the grace-period/notify-then-close choreography — the absolute-lifetime cap is a scheduled, known deadline (not a failed-refresh discovery), so there is nothing to notify in advance of; the fix is which code the already-scheduled close sends, not a new pre-close signal.
- `websocket-staleness-signal`'s `connectionHealth.ts`, `ReauthRequiredTreatment.tsx`, and their pilot-readiness gate (issue #136) are the client-side surface this change touches. `ReauthRequiredTreatment.tsx` currently takes no props at all — by design (Decision D9 of `reauth-required-client-prompt`, "no props derived from cause, role, or session-moment state") — and its CTA is a bare `window.location.href = "/auth/login"` with no parameters, a behavior its own spec currently makes mandatory ("SHALL NOT be parameterized with a query string, fragment, or any other value"). Both of those existing constraints are the two spec-level collisions this design has to resolve deliberately, not route around silently.
- `join-link` already solved "carry a value through the OIDC round-trip and act on it after callback" for join tokens: `/auth/login?joinToken=<token>` → `stateData.pendingJoinToken` in the Redis-stored OIDC `state` payload → read via atomic `redis.getdel` in `/auth/callback` → used to compute the post-login redirect. This is the template for the return-to mechanism, generalized from a join-flow-specific token to an arbitrary internal return path, and made IdP-agnostic in the same way join-link already is (the mechanism lives entirely in this app's own login/callback routes, never touching provider-specific claims).

**Constraint carried forward from every prior change in this area, restated because it is easy to violate by accident:** re-authentication must never be able to grant a role, team membership, or facilitator status the user did not already hold. Nothing in this design introduces a new authorization decision — the return-to value is a *destination*, not a grant, and is validated as such (see Decision 3).

## Goals / Non-Goals

**Goals:**
- Route the absolute-lifetime force-close through the same disclosed signal SEC-26 already uses, so the client reaches `reauth-required` instead of retrying forever.
- Give the `reauth-required` CTA a way to return the user to the page they were on, provider-agnostically, without turning the navigation into a place that leaks connection state, cause, or another user's data.
- Make the facilitator call site's copy factually correct (facilitators don't vote) without reopening the role-blind rendering *mechanism* that copy shares with the participant call site.
- Give participants a quiet, cause-blind signal that the facilitator is currently reconnecting, using the existing connection-health vocabulary rather than inventing a new one.

**Non-Goals:**
- Rejoining with topic position, vote state, or readiness-grid data restored (OR-1.7's fuller contract). The live-session voting UI this would rejoin a user *into* does not exist yet (`SessionConnectionHost.tsx`/`FacilitatorConnectionHost.tsx` are explicitly stubbed hosts). Follow-up issue once that UI exists.
- A pre-expiry warning affordance. Treated as a separate, later, genuinely-new UX decision — this change fixes the post-expiry signal only.
- Any change to the 90-minute policy number, the SEC-26 refresh/retry/grace-period mechanics, or the composed-but-unsubmitted vote persistence gap (issue #31).
- A general-purpose "deep link" or arbitrary-redirect mechanism. The return-to value is constrained to this application's own known route shapes (see Decision 3) — it is not a place to route to an arbitrary caller-supplied URL.
- Reopening `websocket-staleness-signal`'s single-component/single-state-machine/one-close-code-path guarantee (D9). The copy fix is a role-conditioned string inside that same shared component, not a fork of it.

## Decisions

### Decision 1: Fix `CLOSE_FORCE_EXPIRED` to alias `REAUTH_GRACE_EXPIRED_CLOSE_CODE`, and modify `websocket-session-authorization`'s disclosure requirement accordingly

`websocket-routes.ts`'s `const CLOSE_FORCE_EXPIRED = STALE_SIGNAL_CLOSE_CODE;` becomes `const CLOSE_FORCE_EXPIRED = REAUTH_GRACE_EXPIRED_CLOSE_CODE;`. `CLOSE_UNAUTHORIZED` (the subscription-rejection code) is untouched — it keeps using `STALE_SIGNAL_CLOSE_CODE`, since an unauthorized-subscription rejection is exactly the kind of cause that still must not be disclosed. No change to `scheduleForceClose`'s timing, `isPastAbsoluteLifetime`, or the SEC-25/27 sweep — only which code the already-scheduled close emits.

This requires an explicit `MODIFIED` delta against `websocket-session-authorization`'s "Server-initiated close codes do not disclose the cause of connection termination" requirement, which today states both the rejected-subscription case and the absolute-lifetime force-close "SHALL use the same close code for every such case." That sentence was correct when written and is being deliberately narrowed here, not silently violated: an unauthorized subscription is a fact about *this user's authorization* that must not leak; the 90-minute ceiling is a fact about *elapsed time*, identical and predictable for every session regardless of who is in it, disclosing it to the client it happens to reveals nothing about anyone's access. The two causes were conflated originally because the constant already existed and reuse was the path of least resistance (exploration notes), not because a symmetric disclosure argument applies to both.

**Alternatives considered:**
- *Leave the close code alone; fix only the client.* Rejected — the client's non-branching rule (`websocket-staleness-signal`'s own "SHALL NOT branch on the WebSocket close-code value... except for the single, named check for `REAUTH_GRACE_EXPIRED_CLOSE_CODE`") is exactly the mechanism this change needs to reuse, not work around. Introducing a second branch would violate that requirement's "single shared implementation" guarantee.
- *Introduce a third, new close code specific to absolute-lifetime expiry.* Rejected — SEC-26's `reauth-required` state, CTA, and pilot-readiness-gated copy already exist and are exactly the right destination; a new code would mean either a new client state (duplicating `reauth-required`) or teaching `connectionHealth.ts` a second alias for the same state, adding a branch for no behavioral gain.

### Decision 2: No pre-close notification or grace period for the absolute-lifetime case

SEC-26's refresh-failure path sends an in-band `reauth_required` message, then waits ~30s, then closes — because refresh failure is discovered asynchronously and the client benefits from a moment to react before the socket dies. The absolute-lifetime cap is different: it is scheduled from the moment the connection registers (`scheduleForceClose(conn, sessionCreatedAt, ...)`), so the exact close time is known in advance. `connectionHealth.ts` already accepts `REAUTH_GRACE_EXPIRED_CLOSE_CODE` as a fallback trigger for `reauth-required` with no in-band message required. This design sends no in-band message before this particular close — the close code alone is sufficient to route correctly — keeping the change to the one-line constant fix Decision 1 describes.

**Alternative considered:** send an in-band `reauth_required` message some seconds before the scheduled close, mirroring SEC-26 exactly. Rejected for this change — it would blur into the pre-expiry-warning UX decision this proposal explicitly defers, and the fallback path already exists and is already tested; adding a redundant notify step buys no client-visible improvement over the fallback alone.

### Decision 3: Return-to value is an internal path, allow-listed by shape, carried through the OIDC `state` round-trip — not a raw redirect URL

Following `join-link`'s pattern: the CTA's navigation becomes `window.location.href = \`/auth/login?returnTo=${encodeURIComponent(currentPath)}\``, where `currentPath` is `window.location.pathname + window.location.search` captured at render time (never a full origin — this stays same-origin by construction, the same way `joinToken` never carries a URL). `/auth/login`'s handler adds `stateData["returnTo"] = request.query.returnTo` alongside the existing `pendingJoinToken` handling, gated by an allow-list of known internal path shapes (`/session/:id`, `/team/:id`) — the same shapes `executeJoinFlow` already produces as redirect targets — so a malformed or unexpected value is dropped rather than trusted. `/auth/callback` reads `stateData.returnTo` via the same `redis.getdel` atomic read already in place, and — only when no `pendingJoinToken` redirect took precedence — redirects there instead of `/team/:teamId`/`/no-team`.

**The `:id` segment is pinned to this application's UUID format, not left as an unspecified placeholder (per Tomás Ferreira's design review).** Every id this allow-list needs to match — `sessions.id`, `teams.id` — is a Postgres `uuid` column, generated via `gen_random_uuid()` (`packages/backend/migrations/2_create_tables.sql`). The allow-list SHALL match `:id` against that format specifically (the standard 8-4-4-4-12 hex-and-hyphen UUID shape), not a loose "anything up to the next `/`, `?`, or end-of-string" class — so `/session/<uuid>` and `/team/<uuid>` are accepted and `/session/../../etc` or `/session/<anything-non-uuid>` is not, independent of the scheme/authority checks below.

**Query strings are tolerated, deliberately, because the capture already includes them.** `currentPath` is captured as `window.location.pathname + window.location.search`, not the bare pathname — so the allow-list SHALL treat an optional `?`-prefixed query string as part of a valid match (`/session/<uuid>` or `/session/<uuid>?<query>`), rather than silently dropping any `returnTo` value that happens to include one. The query string itself is not further parsed or validated beyond the same scheme/authority/CRLF/backslash checks applied to the whole value — it is carried through opaquely, the same way the path segment is, since it is still same-origin by construction and still resolved through the destination route's own authorization on landing (this decision's closing paragraph). Without this, any `returnTo` captured while the current URL has a query string (e.g., a join-outcome suffix, or any future tab/filter state) would be silently and needlessly dropped to the generic default instead of the page the user was actually on.

**The rejection-path character checks are stated explicitly, not left implied (per Tomás Ferreira's design review).** In addition to rejecting any value containing `://`, a leading `//`, or an explicit scheme/authority component, the allow-list check SHALL also reject any value containing a raw CR or LF character (header-injection into the eventual `Location` response header) or a backslash (`\`, which some URL-parsing contexts normalize to `/`, and which a strict allow-list match should exclude rather than rely on implicitly). Both checks run before the allow-list pattern match, on the raw decoded value.

Precedence order when both a join flow and a return-to value could apply: `pendingJoinToken`'s redirect wins, unchanged from today. A return-to value is only meaningful for an already-team-scoped user reauthenticating out of a session they were already in; a join-link flow is definitionally a different, higher-priority path (a user who wasn't a team member yet). These cases don't overlap in practice, but the precedence is stated explicitly so no future change has to guess.

This requires a `MODIFIED` delta against `websocket-staleness-signal`'s "Reauth-required call-to-action" requirement, whose current text ("SHALL NOT be parameterized with a query string, fragment, or any other value derived from connection state, cause, or session identifiers") would otherwise flatly forbid this. The modification narrows the ban to what it was actually protecting against — leaking *cause* or *connection state* (which SEC-26 sub-case fired, whether a vote was in flight, etc.) — while permitting exactly one new parameter, `returnTo`, whose value is the current page path and nothing else. `ReauthRequiredTreatment.tsx` gains its first prop (`returnTo?: string`) to carry this; the component still reads no cause, role note excepted (Decision 4), or session-moment state.

**Alternatives considered:**
- *Store return-to server-side keyed by session id, pass only an opaque reference.* Rejected as unnecessary complexity — the value is already going through the same Redis-backed `state` store as `joinToken`, single-use and short-lived by the existing OIDC flow's own TTL; there is no additional secret to protect here that a second layer of indirection would help with.
- *Let the frontend read `document.referrer` or `sessionStorage` after landing on the team page instead of a server-side round-trip.* Rejected — fragile across the full-page navigation this flow requires (`websocket-connection-reauthorization`'s own note that recovery is "always a fresh connection, never an in-place resume," including a fresh JS execution context), and it would mean the redirect decision is made client-side after an unconditional server redirect already happened, requiring a second navigation.
- *Accept an arbitrary path with no allow-list.* Rejected — an unvalidated caller-influenced redirect target is an open-redirect-shaped risk even same-origin (e.g., interaction with any future route that itself redirects elsewhere); allow-listing by known shape costs little and closes it outright.

### Decision 4: Role-aware copy is a single conditional inside the existing shared component, not a fork

`ReauthRequiredTreatment.tsx` gains a second prop, `role: "participant" | "facilitator"`, supplied by each call site (`ConnectionStatusBanner.tsx` already knows it's rendering for a participant; `FacilitatorReadinessGrid.tsx` already knows it's rendering for the facilitator — neither call site needs new information to supply this). The vote-loss sentence is the only text that varies:

- `participant`: unchanged wording, including the vote-loss sentence (still gated by the existing `voteDraft.ts`-import grep check per that requirement's existing conditional-disclosure logic).
- `facilitator`: the vote-loss sentence is omitted; the rest of the copy (session-renewal explanation, leave-and-return statement, CTA) is identical.

This requires a `MODIFIED` delta against `websocket-staleness-signal`'s "Copy and CTA are identical regardless of participant or facilitator role" requirement and the adjacent "Uniform participant-facing rendered treatment" requirement's "Neither treatment's content... SHALL vary based on... role" sentence. Both are narrowed to name this one exception explicitly, rather than reopened generally: the CTA, ARIA role (`role="alert"`), persistence behavior, visual register, and every other content requirement (no countdown, no sub-cause disclosure, leave-and-return statement) remain byte-identical across roles. Only the single vote-loss sentence is conditioned, and only because it is factually false for one of the two roles (facilitators never vote — BRD.md §3's ritual narrative and `entities-and-relationships.md`'s Facilitator relationship list, which has no "casts vote" entry; there is no single requirement ID that states vote-ineligibility directly, so this cites the narrative/entities sources rather than a requirement number) — this is a correctness fix to a copy string, not a role-based behavioral branch in the state machine, the CTA, or the navigation mechanism D9 protects.

**Alternative considered:** two separate components/copy constants, selected by call site. Rejected — this is exactly the drift D9 was written to prevent (the pre-D9 history was two independently-maintained copies of this same treatment silently diverging); a single component with one narrow, named conditional keeps the "one place to change this" property D9 established.

### Decision 5: Facilitator-reconnect indicator is a new, minimal WS broadcast, delivered through the existing Redis-backed fan-out — not a local-registry iteration

Today, participants receive no signal about the facilitator's connection health at all — `websocket-session-authorization`'s four content-access events don't cover it, and `websocket-staleness-signal`'s grid marker is facilitator-only, reporting on *participants'* staleness to the facilitator, the opposite direction. This is new wire surface, not a client-side reuse of an existing signal.

**Mechanism (revised per Marcus Oyelaran's design review — blocking finding):** the first draft of this decision described the broadcast as a direct iteration of the local, per-pod `ConnectionRegistry` (`byScope.session.get(sessionId)`, `.send()` to whatever's registered there). That is wrong, for the same reason every other session-scoped event in this codebase — `vote_readiness_update`, `session_state_change`, `vote_revealed`, `topic_history_update`, `participant_joined`, `participant_left`, `action_item_status_updated` — does not do that: `connection-registry.ts` states outright that its registry "lives entirely in-process, per pod... NOT shared across pods." A facilitator's connection and a participant's connection are two independent WebSocket upgrades with nothing pinning them to the same pod; in any multi-pod deployment, a facilitator disconnecting on pod A while a participant is connected to pod B means pod A's local iteration never sees pod B's connection, and the event silently fails to deliver. This is exactly the failure mode `ws-pubsub.ts`/`ws-event-dispatcher.ts` exist to prevent, and this design must use that path, not a shortcut around it.

This capability is implemented with the same three-part shape as `participant_joined`/`participant_left`, its closest existing analogues:
- **Publish (`ws-pubsub.ts`):** a new `publishFacilitatorConnectionStatus(sessionId, { connected })` wrapper, calling `publishWsEvent({ eventType: "facilitator_connection_status", sessionId, payload: { connected } })` on the shared `ws:events` Redis channel — the same channel every other session-scoped event already fans out on.
- **Dispatch (`ws-event-dispatcher.ts`):** a new `dispatchFacilitatorConnectionStatus` case, added to the existing `eventType` switch, delivered to each pod's local candidates for that session via `evaluateSessionSubscriberAccess` (the same per-candidate, per-message authorization check every other case already runs), filtering out the facilitator's own connection by `subscriberPath` so a facilitator never receives their own status back.
- **Publish call sites (`websocket-routes.ts`):** wired into the *same* two call sites that already call `recordFacilitatorConnectionAudit("connected" | "disconnected", ...)` (lines ~137 and ~158 today) — not a second, independently-derived detection of "the facilitator disconnected." One fact, one call site per transition, two consumers (the existing audit write, this new broadcast), so the client-facing signal and the audit-log signal (issue #94's `session.facilitator_connected`/`disconnected` rows) can never drift out of sync with each other. This also directly answers Tomás Ferreira's audit-logging question: facilitator connection health is already captured in `audit_log` today, cause-blind, at full fidelity; this broadcast is a second reader of that same fact, not a new detection mechanism.

**"Prior disconnect" requires a small piece of shared state, not local memory.** "Reconnect fires for a session with a prior disconnect" (tasks.md task 4.6) names a fact about the *session*, not about any one connection or any one pod's memory: if the facilitator drops from pod A and reconnects to pod B, pod B has no local record that a disconnect occurred, and can't tell whether `{connected: true}` is a reconnection-worthy transition or a no-op. This design adds one small Redis key per session, `facilitator_connected:<sessionId>` (a boolean flag, set on facilitator connect, cleared on facilitator disconnect), read-before-write at each of the two call sites above so any pod can determine whether the transition it just observed is actually a change from the session's point of view before publishing. The key is cleared when the session leaves `pre_session`/`active` status (same lifecycle boundary that gates the broadcast itself), so it does not outlive the session it describes. This is bounded, single-purpose state — not a new registry, not a new authorization surface — colocated with the existing `publishParticipantJoined`/`publishParticipantLeft`-style call sites so it is visible next to the pattern it mirrors.

**Client-side:** a new, small consumer subscribes to this event and renders a quiet, dismissible-only-in-the-sense-that-it-clears-itself, `role="status"` (not `role="alert"` — this is informational, not actionable by the participant) one-line indicator, styled in the same restrained register as `unknown-reconnecting`'s existing banner (explicitly not `reauth-required`'s register — the participant cannot do anything about the facilitator's connection, so this must never look actionable). It does not touch `connectionHealth.ts`'s own state machine, since it is not reporting on *this client's* connection — it is a sibling, single-purpose piece of client state fed by the new event, following the same "one shared module, no forking" discipline `websocket-staleness-signal` established, scoped to its own new, narrow concern. See Decision 6 for how this consumer gets a socket to listen on.

**Alternatives considered:**
- *Derive this client-side from existing signals (e.g., participants infer staleness from a stalled `vote_readiness_update`/`session_state_change` stream).* Rejected — silence is not a signal a client can act on with confidence (a quiet lobby looks identical to a stuck one), which is exactly the ambiguity Priya's review identified as the problem.
- *Reuse `websocket-staleness-signal`'s existing grid-marker component/module for this, inverted.* Rejected — that module's signal source is explicitly "the facilitator's own `unknown-reconnecting` state" as observed *by the facilitator's own client*; there is no existing path for that fact to reach a different user's client at all. This is new information flow, not a new renderer for old information, so extending that module would misrepresent what's actually new here.
- *Push the full `reauth-required`/`unknown-reconnecting` distinction to participants.* Rejected — deliberately narrower. Participants get exactly one bit (connected/not), never the cause, keeping the same non-disclosure posture the rest of this system holds toward the reasons behind another user's connection state.
- *Iterate the local `ConnectionRegistry` directly (the original draft of this decision).* Rejected per Marcus Oyelaran's design review — silently no-ops across pods in any multi-instance deployment, which is precisely the bug class the existing `ws-pubsub`/`ws-event-dispatcher` split was built to eliminate for every other session-scoped event. See "Mechanism" above.

**Known limitation, named rather than left implicit (per Tomás Ferreira's design review):** the payload (`{ connected: boolean }`) is cause-blind by design, but the *emergent* signal is not fully blind to one thing the payload doesn't carry: duration. A facilitator gone for 30 seconds and a facilitator gone permanently (role removed, access revoked, employment ended) produce the identical payload shape, but participants can still distinguish "blip" from "permanent" purely by how long the indicator persists — there is no requirement anywhere in this change for the indicator to stop showing "reconnecting" if the underlying disconnect turns out to be permanent. This is a real product gap (participants could sit looking at a "reconnecting" indicator indefinitely), but it is out of scope here: resolving it requires a decision this change's Non-Goals already defer (e.g., some notion of a duration cutoff or a facilitator-reassignment flow) that doesn't exist yet. Named here, and in tasks.md, as a known limitation to track as a follow-up, not something to silently discover in production.

### Decision 6: The new indicator consumer shares the session's live socket by lifting `useConnectionHealth` up, not by opening a second connection

Marcus Oyelaran's design review (should-fix finding) identified that no current wiring path gives Decision 5's client-side indicator a reference to the session's live WebSocket: `ConnectionStatusBanner.tsx` calls `useConnectionHealth(connect)` itself and never exposes the resulting socket to its parent, and `SessionConnectionHost.tsx` — the only real mount point today — never sees a `WebSocket` instance at all. Two options exist to give the new indicator something to listen on; this decision picks one before tasks.md's Group 4 depends on an answer.

**Decision:** lift the `useConnectionHealth` call up one level, from `ConnectionStatusBanner` to `SessionConnectionHost`. `SessionConnectionHost` calls `useConnectionHealth(connect)` itself, and passes the resulting `{ state, socket }` down: `state` (and `socket`, if needed for future work) to `ConnectionStatusBanner`, now accepting both as props instead of calling the hook internally, and `socket` to the new facilitator-reconnect indicator module, which attaches its own `message` listener to that same socket for the `facilitator_connection_status` event. `useConnectionHealth`'s existing `addEventListener`-based design already anticipated exactly this (its own comment: "composes with any other listener a consumer attaches to the same returned socket") — this decision is what actually calls that intent into being at a real call site.

**Alternative considered:** open a second WebSocket to `/ws/sessions/:sessionId` solely for the new indicator to listen on. Rejected — it duplicates the full per-connection server-side cost (subscription-time authorization check, `scheduleForceClose` timer, SEC-25/26 sweep and refresh timer, registration snapshot send) for every participant, for no reason other than client-side message routing; that is a meaningful amount of duplicated backend machinery to spin up per participant per session, for a problem the existing hook design already solves for free once the socket is shared.

**Scope note:** this is a small, mechanical refactor of `ConnectionStatusBanner`'s prop surface (it gains `state`/`socket` props, loses its internal `useConnectionHealth` call) and of `SessionConnectionHost` (it gains the hook call it currently delegates entirely to its child). It does not change `useConnectionHealth`'s own implementation, `connectionHealth.ts`'s state machine, or any requirement `websocket-staleness-signal` states about `ConnectionStatusBanner`'s rendered output — those requirements are about what is rendered per state, not about which component calls the hook.

## Risks / Trade-offs

- **[Risk] The `websocket-session-authorization` and `websocket-staleness-signal` requirement modifications are the riskiest part of this change** — they are deliberate reversals of requirements that existed for real security reasons (non-disclosure, role-blind rendering, unparameterized navigation). A future reader of the archived requirement history could mistake this change's narrowing as evidence those protections are generally negotiable. → Mitigation: each MODIFIED delta spec states explicitly and narrowly what changed and why (elapsed-time disclosure vs. identity/access disclosure; one copy string vs. the whole rendering mechanism; one allow-listed same-origin path parameter vs. arbitrary parameterization), so the scope of the exception is legible from the spec text alone, not just this design doc.
- **[Risk] The `returnTo` allow-list drifts out of sync with real route shapes as the app grows new routes.** → Mitigation: the allow-list is defined once, colocated with `executeJoinFlow`'s own redirect-target construction (which already enumerates the same shapes), so a new route added to one is visible next to the other; not a strong guarantee, named here so a future reviewer knows to check both together.
- **[Risk] The facilitator-reconnect indicator's broadcast could be mistaken for a precedent that any connection-health fact can be freely fanned out to other session participants.** → Mitigation: the design deliberately sends the narrowest possible signal (a boolean, no cause) and the delta spec states the cause-blindness bound as a hard requirement, not an implementation detail.
- **[Trade-off] No live-app verification of the "retries forever" failure mode has been performed** — exploration notes flagged this as read-from-code, not observed. This design proceeds on that read because the code path is unambiguous (one constant, one branch in `connectionHealth.ts`), but implementation should include a manual or integration-test confirmation that the fix actually resolves observed behavior, not just satisfies the unit-level close-code assertion.

## Migration Plan

No data migration. Deploy order, to avoid a window where the frontend expects a `returnTo`-aware backend that isn't live yet or vice versa:
1. Backend: `CLOSE_FORCE_EXPIRED` constant fix (Decision 1) and `/auth/login`/`/auth/callback` `returnTo` handling (Decision 3) can ship together or backend-first — both are backward compatible with the current frontend (an old client ignores the new close-code routing benefit until it's updated; `/auth/login` without a `returnTo` query param behaves exactly as today).
2. Frontend: `ReauthRequiredTreatment.tsx`'s new `role` and `returnTo` props (Decisions 3, 4), the `useConnectionHealth`-lifting refactor of `SessionConnectionHost`/`ConnectionStatusBanner` (Decision 6), and the new facilitator-reconnect indicator consumer (Decision 5), ship together — Decision 5's consumer has nothing to attach to until Decision 6's refactor lands, and both call sites need updating in the same change to avoid one surface gaining role-aware copy while the other doesn't.
3. Backend: the new `facilitator_connection_status` broadcast — publish wrapper, dispatcher case, and the two `websocket-routes.ts` call sites (Decision 5) — should ship no earlier than the frontend consumer that renders it, to avoid an unconsumed event; ordering it last is simplest.

Rollback is a straightforward revert at each layer — none of these changes are additive-only in a way that creates a one-way migration; the `returnTo` Redis payload field is ignored by an unpatched callback handler exactly like any other unrecognized JSON field.

## Open Questions

- **HTTP-side 401 parity — disposed as a named follow-up, not left to "a future reviewer":** confirmed against current code, not assumed. `AuthContext.tsx`'s one-time `fetchSession` (run once on initial SPA load) already navigates unparameterized to `/auth/login` on a 401 — a pre-existing gap this change does not touch or worsen. More relevant to a live session: `SessionLobbyPage.tsx`'s in-session action calls (`start`, `begin-voting`, `action-items-review`) each handle a 401 ad hoc today, and none of them route to any reauth flow — `handleStartSession`, for example, treats a 401 the same as any other non-2xx response and surfaces a generic "Couldn't start the session. Try again." message. There is no shared HTTP interceptor for session-expiry 401s anywhere in the frontend today, session-scoped pages or otherwise.

  Building one is a cross-cutting change in its own right — auditing and updating every HTTP call site that can 401 mid-session (at minimum the three in `SessionLobbyPage.tsx`, plus the other `session_expired`-emitting routes in `teams.ts`, `facilitator-sessions.ts`, and `sessions.ts`), not a one-line fix like Decision 1's close-code alias. That is disproportionate to this change's bounded scope, for the same reason OR-1.7 restoration and the pre-expiry warning were deferred rather than folded in.

  The interim risk is real but bounded, and qualitatively different from the WebSocket gap this change fixes: the WS gap stranded a connection silently, with no user action, for the rest of the session; the HTTP-side gap only surfaces if a user's absolute lifetime happens to expire in the narrow window between clicking an in-session action and its response, and today's failure mode is a visible, retryable error message — not a silent infinite-retry loop — so nothing look broken in a way that reads as "stuck." No data is lost and no security boundary is crossed by leaving this as-is.

  **Follow-up:** file a dedicated HTTP-side session-expiry parity issue, scoped to a shared 401-handling mechanism across session-scoped fetch calls that routes to the same `reauth-required` treatment this change ships (with `returnTo`, reusing Decision 3's mechanism). Track it separately from OR-1.7's restoration follow-up — the two are unrelated gaps that happen to share a "deferred" label, and conflating them risks either being used to justify delaying the other.
