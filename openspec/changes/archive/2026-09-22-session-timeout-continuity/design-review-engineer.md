# Engineer Design Review — session-timeout-continuity

Reviewer: Marcus Oyelaran (Full Stack Engineer)
Scope: design.md, proposal.md, and the four delta/new specs, checked against the actual current code in `packages/backend/src/realtime/`, `packages/backend/src/routes/auth.ts`, and `packages/frontend/src/{realtime,components,pages}/`.

## Summary

Decisions 1–4 (close-code fix, no pre-close notification, `returnTo` mechanism, role-aware copy) are implementable as written, compose cleanly with the existing code, and are the right size for the problem. Decision 5 (facilitator-reconnect indicator) is not implementable as specified without either violating this application's own established cross-pod delivery pattern or introducing new server-side state the design never names. That's the one finding I'd block on. Everything else below is a should-fix or a note.

## Finding 1 (Blocking): The facilitator-reconnect broadcast bypasses this app's own multi-pod fan-out pattern

Decision 5's "Mechanism" section, and `tasks.md` task 4.1 verbatim, describe the broadcast as: given a session id, iterate `byScope.session.get(sessionId)` — the **local, per-pod** `ConnectionRegistry` — and `.send()` directly to whatever's registered there.

That is not how any other session-scoped event in this codebase reaches participants, and the reason is documented at length in the code the design claims to be reusing. `connection-registry.ts:4-24` states outright: "This registry lives entirely in-process, per pod. It is NOT shared across pods." Every one of the seven existing event types (`vote_readiness_update`, `session_state_change`, `vote_revealed`, `topic_history_update`, `participant_joined`, `participant_left`, `action_item_status_updated`) — including the two closest analogues, `participant_joined`/`participant_left`, which the design's own alternatives section cites as precedent — goes `publish*() → ws-pubsub.ts's WS_EVENTS_CHANNEL (Redis) → every pod's subscriber → ws-event-dispatcher.ts's per-candidate authorization check against that pod's local registry`. That round-trip through Redis is exactly what makes an event fan out to a participant connected to a *different* pod than the one that produced the event.

A facilitator's connection and a participant's connection are two independent WebSocket upgrades — nothing pins them to the same pod. In any deployment with more than one backend instance (which the entire ws-pubsub/registry split exists to support — see connection-registry.ts's and ws-pubsub.ts's own doc comments), a facilitator disconnecting on pod A while a participant is connected to pod B means pod A's local `byScope.session.get(sessionId)` iteration never sees pod B's connection at all. The event silently fails to deliver to exactly the participants it's for, with no error anywhere. This is precisely the shape of bug the codebase's own architecture was built to prevent, and precisely the shape I've been burned by before: something that works in a single-instance dev/docker-compose environment and fails silently the first time the app is scaled to two pods.

It also doesn't just need the existing fan-out — it needs new state the design doesn't name. Task 4.2 says the reconnect broadcast fires "for a session with a prior disconnect." "Prior disconnect" is a fact about the session, not about any one connection or any one pod's memory. If the facilitator drops from pod A and reconnects to pod B, pod B has no local record that a disconnect ever happened, so it can't know whether to fire `{connected: true}` — there's no reconnection-worthy transition to detect from pod B's point of view. This needs a small piece of shared state (a Redis key per session, `facilitator_connected:<sessionId>`, set/cleared alongside the existing `publishParticipantJoined`/`publishParticipantLeft`-style calls) that any pod can read before deciding whether a transition actually occurred — not something derivable from a local `Set`.

**Fix:** implement this the same way `participant_joined`/`participant_left` already are — a `publishFacilitatorConnectionStatus(sessionId, { connected })` wrapper in `ws-pubsub.ts`, a `dispatchFacilitatorConnectionStatus` case in `ws-event-dispatcher.ts` (delivered via `evaluateSessionSubscriberAccess`, filtering out the facilitator's own connection by `subscriberPath`, exactly per the spec's authorization requirement), called from the same `websocket-routes.ts` connect/cleanup call sites that already call `recordFacilitatorConnectionAudit`. The "was previously connected" transition needs a small piece of durable-enough shared state (a Redis flag scoped to the session, cleared on session close/completion so it doesn't leak past a session's lifetime) rather than anything read off the local registry. This is a real but bounded addition — it doesn't change the shape of Decision 5, just its plumbing — and it's the same pattern already proven out three times in this file for the closest-analogous events.

## Finding 2 (Should-fix before implementation): No wiring path exists from the new indicator to the session socket

`tasks.md` 4.4 says to add "a new, single-purpose frontend module... that subscribes to `facilitator_connection_status`" — but doesn't say what it subscribes *to*, and none of the current code provides an answer.

`ConnectionStatusBanner.tsx` calls `useConnectionHealth(connect)` itself and never exposes the resulting `socket` to its parent. `SessionConnectionHost.tsx` — the only real integration point that exists today — mounts `ConnectionStatusBanner` and nothing else; it never sees a `WebSocket` instance itself. So a second consumer (the new indicator) has no way to attach a `message` listener to the *same* connection without one of:

- **Opening a second WebSocket** to `/ws/sessions/:sessionId` just for this signal — which duplicates the per-connection server-side cost (subscription-time authz check, `scheduleForceClose` timer, SEC-25/26 sweep + refresh timer, registration snapshot send) for every participant, for no reason other than message routing on the client. That's a meaningful amount of duplicated backend machinery to spin up per participant per session, and it's the kind of incidental complexity I'd push back on if a PR introduced it without calling it out.
- **Restructuring `SessionConnectionHost`/`ConnectionStatusBanner`** so the socket is lifted up and shared — which is a real (if small) refactor of a component the `websocket-staleness-signal` spec currently treats as closed and stable, and isn't mentioned anywhere in this design or its tasks.

`useConnectionHealth`'s `addEventListener`-based design (Decision D1e's own comment: "composes with any other listener a consumer attaches to the same returned socket") clearly anticipated a second consumer sharing the socket — the intent is there — but the actual call-site wiring to make that happen isn't specified. This should be resolved as an explicit decision (most likely: `SessionConnectionHost` calls `useConnectionHealth` itself, passes `socket` to a `ConnectionStatusBanner` that accepts it as a prop instead of calling the hook internally, and passes the same `socket` to the new indicator module) before implementation starts, not discovered mid-task-4.

## Finding 3 (Note, not blocking): `returnTo` allow-list shape vs. captured value

Decision 3 and tasks 3.4/3.5 capture `returnTo` as `window.location.pathname + window.location.search` at render time, but the allow-list spec's examples (`/session/abc123`, `/team/xyz789`) and scenarios never show a query string. If the allow-list regex ends up as a strict `^/session/[^/]+$` / `^/team/[^/]+$` full match (the natural first implementation), any `returnTo` captured while the current URL has a query string (e.g., `?newMember=true` from the join-outcome suffix, or any future tab/filter state) gets silently dropped in its entirety — falling back to the generic `/team/:teamId` default, not a stripped-but-still-useful path. That's a safe failure mode (nothing breaks), but it means the `+ window.location.search` half of the capture is currently dead weight unless task 2.1 explicitly decides the allow-list should tolerate an optional query string. Worth a one-line decision in task 2.1 rather than leaving it to whoever writes the regex.

## What holds up well

- **Decision 1/2 (close-code fix):** the one-line constant change is exactly the right scope for what's being fixed. `scheduleForceClose`'s timing and the SEC-25/27 sweep are correctly left untouched. Task 1.2 already accounts for the now-stale "same close code for both cases" comment block above `CLOSE_UNAUTHORIZED`/`CLOSE_FORCE_EXPIRED` (websocket-routes.ts:50-60) and the equivalent module doc in `staleness-signal.ts` — both need updating and both are tracked.
- **Decision 3 (`returnTo` precedence in `auth.ts`):** composes cleanly with the actual code. The existing structure — `if (stateData.pendingJoinToken) { redirectUrl = ... }` followed by `if (!redirectUrl) { ... }` — already has exactly the right seam for a `returnTo` check to slot into the second block, no restructuring needed. Staying same-origin/relative-path-only, appended the same way `redirectUrl` already is (`${appOrigin}${redirectUrl}`), correctly avoids turning this into an open-redirect vector.
- **Decision 4 (role-aware copy):** a single new `role` prop and one conditional string is the correct, minimal shape — doesn't reopen D9's single-component guarantee, and `ConnectionStatusBanner`/`FacilitatorReadinessGrid` already have everything they need to supply it without new plumbing.
- **`connectionHealth.ts` isolation:** correctly left alone by everything except Finding 1/2's wiring question. The spec's "exactly one indicator-consuming module, connectionHealth.ts unmodified" requirement is checkable and the right bar.

## Recommendation

Don't block on Findings 2/3 — they're implementation-detail gaps a competent implementer resolves in an hour of reading. Finding 1 is different: as written, Decision 5 would ship a feature that appears to work in every test and in local docker-compose, and silently no-ops for a meaningful fraction of participants the moment this runs on more than one backend instance. That's worth a design-doc correction before tasks.md's Group 4 is implemented, not a fix-it-in-review catch.
