# Exploration Notes: session-timeout-continuity

**Author:** Devon Calloway (Internal Champion / SME), explore stage, GitHub issue #133.

**Revision note (2026-09-22):** Updated after review from Marcus Delgado (BA, `explore-review-ba.md`) and Priya Nair (Facilitator, `explore-review-facilitator.md`). Marcus independently re-verified the close-code finding against the code and resolved my central open question — see the OR-1.7 section and Recommendation below, both rewritten to reflect that. Priya raised three gaps from the room's-eye view; I checked her third claim (the reauth CTA's return-to behavior) against the code myself rather than taking it on faith, and it holds up — see the new "Return-to path" open question. Where the two reviewers pulled in different directions on scope, I've said so explicitly rather than silently picking a side.

## What this is, and what it isn't

Issue #133 is the session-continuity/UX question that `http-auth-audit-log-coverage` (issue #30, archived 2026-09-18) deliberately declined to absorb, twice over — named in its proposal.md's "Explicitly out of scope" and its design.md's Non-Goals, both pointing here. It's also the thing Priya Nair (Facilitator) flagged in that change's explore-stage review and Rachel Okonkwo (VP Eng) flagged again in that change's propose-stage review as more adoption-relevant than the audit-logging work that actually shipped. Two people, two different lenses, same finding, both times waved through as "worth its own issue." This is that issue, and I want to hold it to the same scope discipline I asked of #30: this is about what a user *experiences* when `ABSOLUTE_LIFETIME_MS` fires mid-ritual, not about whether the firing gets logged (that's closed, separately, by #30) and not about whether NFR-AUTH-005's 90-minute number itself is right (nobody has argued it isn't).

## Grounded in what's actually built today — and it's worse than the issue body states

The issue frames the gap as "no in-app warning, no grace period, and no continuity path today" on the HTTP side. That's true, but I read the WebSocket side too, since a live Health Check session runs almost entirely over the WS connection, not repeated HTTP calls — and what I found there is a sharper problem than silence. It isn't just that the WS side lacks a warning; it's that the WS side's existing signaling for this exact event actively misleads the client.

**The HTTP side (as the issue states):** `middleware.ts`'s `onRequest` hook, unconditionally: `Date.now() - sessionCreated > ABSOLUTE_LIFETIME_MS` → `request.session.destroy()` → 401 `session_expired`. No prior signal. I checked whether any frontend infrastructure translates that 401 into a graceful redirect today — I grepped for `session_expired` across `packages/frontend/src` and found zero references. There is no shared API-client interceptor that catches this category and routes the user somewhere coherent. Whether a given page handles its own 401 gracefully is presumably ad hoc, page by page; I did not audit every call site, and I don't think this exploration needs to.

**The WebSocket side (the issue doesn't mention this, and it's the one that actually touches the ritual):** `connection-registry.ts`'s `scheduleForceClose` (added by the archived `websocket-connection-reauthorization` design, Decision D8) independently tracks the same 90-minute bound and force-closes the socket when it elapses — `websocket-routes.ts:60`, `const CLOSE_FORCE_EXPIRED = STALE_SIGNAL_CLOSE_CODE`. That constant assignment is the finding. `STALE_SIGNAL_CLOSE_CODE` is the codebase's deliberately **disclosure-blind** close code — the one `websocket-staleness-signal`'s own design.md built specifically so a revoked connection can't be distinguished, from the wire, from ordinary network flakiness (a defensible security property for *that* event: don't tell an attacker whose access was pulled that it was pulled). The frontend's `connectionHealth.ts` — the sole state-machine implementation, explicitly not forkable per that module's own header comment — treats every close carrying this code identically to a raw network drop: it enters `unknown-reconnecting` and retries forever with exponential backoff (capped at 30s), on the explicit design principle (Decision D2/D3) that this pair "never branches on close-code value." The ONE code this module is wired to treat differently is `REAUTH_GRACE_EXPIRED_CLOSE_CODE`, which routes to the `reauth-required` state SEC-26 built a real CTA for (`reauth-required-client-prompt`, archived 2026-09-18). The absolute-timeout force-close does not send that code. It sends the same code as "the wifi blipped."

The consequence, traced all the way through: when `ABSOLUTE_LIFETIME_MS` fires on a live WS connection, the client doesn't see a warning, and it doesn't even see a clean, terminal failure — it sees what looks like a recoverable hiccup and starts silently retrying. Each retry attempt is a fresh WS upgrade request, which passes through `authMiddleware`'s `onRequest` hook (confirmed in `websocket-routes.ts`'s own comments: "validated by authMiddleware's existing onRequest hook (app.ts)... on the same onRequest chain") — and the underlying Fastify session is *still there* (only the WS socket was closed; nothing called `request.session.destroy()` on the HTTP session at force-close time), so whether the retry succeeds depends on exactly how close to the 90-minute mark the original connection was when the timer fired, and how fast the client's backoff schedule runs. If the HTTP session's own clock has also crossed the line by the time a retry lands, that upgrade attempt 401s — and a failed WS upgrade doesn't hand the browser a status code to inspect, just another close/error event, which `connectionHealth.ts` — again, correctly, by its own design — treats exactly the same as the first one. **The facilitator or participant is left in an indefinitely-retrying `unknown-reconnecting` state that will never resolve, with a banner that (pre- or post-SEC-26) has never claimed to be actionable for this state, because this state was built for "sit tight, it's probably transient," which is precisely the wrong message once the absolute lifetime has actually elapsed.**

I want to be precise about what I'm claiming here and what I'm not:
- I'm not saying `connectionHealth.ts`'s disclosure-blind design is wrong. It's right, for the threat model it was built for (`websocket-staleness-signal`'s design.md is explicit about why revocation shouldn't be distinguishable from flakiness on the wire). I checked whether that reasoning was meant to cover the absolute-timeout case too, and I don't think it was — `scheduleForceClose`'s own comment cites Decision D8 as "a compensating control... a connection that never receives another event is still eventually closed," framed as a backstop against an unbounded connection, not as a case requiring non-disclosure. Reusing the disclosure-blind code here reads like it was the path of least resistance (the constant already existed, `CLOSE_FORCE_EXPIRED` is literally aliased to the same value as `CLOSE_UNAUTHORIZED`) rather than a deliberate security decision for *this* event.
- I'm not asserting the retry-forever failure mode as observed behavior — I read the code and traced the logic; I did not run the app and watch it happen. Whoever picks up Design should treat "does a WS reconnect attempt after absolute-timeout actually loop indefinitely in practice, or does something else intervene (a page-level fetch, a heartbeat, a full reload) that I haven't traced" as a thing to verify against the running app, not assume from my read alone.

**Status after review: settled, not a hypothesis.** Marcus independently re-verified the close-code assignment and its consequences line-by-line (`websocket-routes.ts:60` and `:334`, the distinct `REAUTH_GRACE_EXPIRED_CLOSE_CODE` in `connection-token-refresh.ts:166`, `connectionHealth.ts`'s single branch at line 220, and a fresh `session_expired` grep against the frontend). Proposal should treat "the absolute-timeout force-close sends the disclosure-blind code instead of the disclosed reauth code" as an established fact of the current codebase, not an open question to re-check. The retry-forever *consequence* is still worth a live-app confirmation, per the caveat above, but the *cause* no longer is.

## Ritual mechanics this bears on directly

- **FR-4.1 / OR-1.4 ("No automatic advancement under any condition; the facilitator controls all topic progression"):** an involuntary timer-driven logout is not the application advancing session state, technically — but from inside the room, a facilitator who is suddenly unable to trigger a reveal or advance a topic because their session died silently is functionally indistinguishable from the ritual stalling on its own. The BRD's own protective-constraint language is about the application never taking control away from the facilitator's explicit action; an uncommunicated forced logout is the same loss of control by a different mechanism. I don't think this makes #133 a violation of FR-4.1 in the letter, but it's the same spirit, and it's worth Design naming that connection rather than treating this purely as an auth/session ticket unconnected to the FR that already protects facilitator control.
- **FR-4.6.1 (15-second reveal delivery bound, with latency "surfaced in system monitoring"):** if the facilitator's connection is mid-`unknown-reconnecting` at the exact moment they'd otherwise click "reveal," the reveal doesn't fire late — it doesn't fire at all, because the button lives on a connection that no longer exists in any form the server will honor. This isn't a delivery-latency problem FR-4.6.1's monitoring would catch; it's a different failure class entirely, upstream of delivery. Worth naming so nobody conflates the two when scoping a fix.
- **OR-1.7 and the Live Voting use cases already commit to the shape of the right answer — this is the part I think is most load-bearing for whoever designs this.** I went looking for whether "disconnect, reconnect, re-authenticate, rejoin with state restored" is a novel concept this issue would be introducing, and it isn't:
  - OR-1.7, verbatim: *"Upon reconnection and successful re-authentication, the facilitator may rejoin the session they created and resume full facilitation control. The session remains in its last known state during the facilitator's absence."*
  - `04 - Live Voting - Use Cases.md` line 495, verbatim, for participants specifically: *"Participant's session token expires during disconnection: On reconnection attempt, the application requires re-authentication. After authentication, they rejoin the session if it is still active."*
  - Same file, line 371, for a facilitator whose connection drops immediately before triggering a reveal: reconnect-and-reauthenticate-to-resume is the stated contract, with the reveal simply waiting until they're back.

  **This means #133 is not asking anyone to invent session continuity as a new product concept.** The product already has an explicit, spec'd contract for "your token expired mid-session, here's the reconnect path." What's missing is that the absolute-lifetime force-close doesn't *invoke* that contract — it sends the wrong signal (disclosure-blind, not the reauth signal), so the client never enters the state that would tell it to go re-authenticate and rejoin. The gap here reads to me less like "design a new continuity mechanism" and more like "wire the existing 90-minute timer into the re-authentication path the product already promises, on both the WS side (send `REAUTH_GRACE_EXPIRED_CLOSE_CODE` or an equivalent, not the disclosure-blind code) and the HTTP side (give the 401 a client-side handler that lands on the same re-auth surface SEC-26 already built, instead of an unhandled failed fetch)." That's a materially smaller design question than the issue's "Named next step" section implies when it lists "a server-side grace/extension path" and "an explicit recovery flow" as candidate directions to invent from scratch — one of the three candidates it names may already be half-built.
  - **Resolved on review — and the answer is the larger-scope one, not the one I leaned toward.** I'd flagged the rejoin-with-full-state half of OR-1.7 as the thing I couldn't confirm by reading alone. Marcus went and found the answer: there is no consumer of `session_registration_snapshot` anywhere in the frontend (`grep -rn "session_registration_snapshot" packages/frontend/src` returns nothing outside a test-file comment in `voteDraft.test.ts`, and that comment points at `vote-compose-recovery`'s own `tasks.md`, archived 2026-09-11, which leaves tasks 8.1–8.3 unchecked pending a compose UI that doesn't exist yet). More directly: the live-session voting screen OR-1.7 describes rejoining *into* — topic display, vote casting, a real readiness grid, the reveal control — does not exist in this codebase today. `SessionConnectionHost.tsx` and `FacilitatorConnectionHost.tsx` both carry header comments stating the full live-session UI is explicitly out of scope of the change that built them, and `FacilitatorConnectionHost.tsx` renders `FacilitatorReadinessGrid` against hardcoded `STUB_ROWS`, not real participant data. There is no "ordinary reconnect and rejoin" experience today for this question to be asked about — the honest framing isn't "is it implemented," it's "the thing it would be implemented *in* doesn't exist yet." I'm correcting my own recommendation below to reflect this rather than let the smaller-scope framing carry into proposal.

## The no-manager rule, the facilitator-from-another-team rule, and why this doesn't touch them

I checked, because it's the thing I always check for: does anything about a session-continuity fix create a path where either protective constraint becomes optional, skippable, or silently bypassed? I don't see one. Re-authentication runs through the same OIDC flow every login does — it can't hand someone a role or team membership they didn't already have; `resolveActorGlobalRole` and the app's own `users`/team-membership tables are the source of truth regardless of which door someone walked through to get re-authenticated. A facilitator who reconnects mid-session and "resumes full facilitation control" per OR-1.7 is resuming a role they already held for that specific session, not acquiring one. I don't think this issue has a load-bearing-constraint angle the way, say, a "let an admin extend someone's session" feature might — but I'm naming that I checked, the same way I did for #30, rather than silently assuming it's clean.

One thing worth a sentence, not a concern: if "Design" ends up building a client-side warning-before-expiry affordance (one of the issue's three named candidate directions), that's new UI surface appearing during a live session — exactly the category of thing I watch for "does this make the ritual feel like software instead of a conversation." A single, quiet, dismissible-but-not-actually-dismissing warning in the last few minutes is a very different product decision than a modal, a countdown timer, or anything gamified. I don't have a strong view yet on which of the three candidate directions is right — that's explicitly this issue's own "Named next step," not mine to pre-empt — but if a warning-toast direction is chosen, I'd want it to read as closer to `reauth-required`'s existing restrained treatment (a persistent, non-alarming, one-line prompt) than to a new interruption pattern.

## Provider-agnosticism check

I looked for a reason this touches OIDC-provider-specific behavior and didn't find one, consistent with the standing project constraint that this auth layer must support multiple IdPs, not just Entra. `ABSOLUTE_LIFETIME_MS` is this application's own policy constant (NFR-AUTH-005), entirely independent of which IdP issued the original token — it's measured from `sessionCreatedAt`, a value this app sets at its own session-creation time, not from any IdP-supplied claim. Whatever re-authentication path this issue ends up wiring the timeout into is the same `/auth/login` → IdP redirect → callback flow every login already uses (the same reuse `reauth-required-client-prompt`'s proposal explicitly noted: "the CTA does not need to know or care which IdP is configured"). No part of a session-continuity fix here has a reason to branch on provider identity, and I'd flag it in review if one did.

## Where this touches the BRD directly

- **BRD §16, OQ-2(b) ("Session State Recovery After Interruption — Partially Resolved") is directly on point, and I missed it in my first pass.** Marcus caught this. OQ-2 confirms OR-1.7's resolved half verbatim, then lists as still-open: *"(b) what timeout or staleness policy applies to a session stuck in an active or wrap-up state."* That's this issue, by the BRD's own accounting — not a new discovery, a previously-flagged gap #133 is positioned to close. Worth citing directly in proposal as prior evidence the gap was anticipated. OQ-2's other two open items — (a) admin reassignment of facilitator control, (c) partial-session retention policy — are not this issue's scope and shouldn't drift in.
- **NFR-AUTH-005** is the requirement whose *policy number* (90 minutes, sliding/silent refresh) is not in question here — nobody in this thread (Priya, Rachel, the issue itself) has argued 90 minutes is wrong or that the refresh mechanism is broken. What's in question is purely the *user-facing consequence* when the absolute ceiling is reached mid-ritual, which NFR-AUTH-005 doesn't speak to one way or the other.
- **SEC-26** (token-expiry-during-WS handling) already required, and already got, real work: "notify the client that re-authentication is required if the refresh cannot be completed silently... terminate the connection if the client does not complete re-authentication within a defined grace period." That's `websocket-connection-reauthorization` + `reauth-required-client-prompt`, both archived and both about the *refresh-failure* path (a token that can't be silently renewed). SEC-26's own last sentence is the part that's under-realized: **"The absolute maximum session lifetime of 90 minutes must be enforced even if a valid token is present"** — that enforcement exists (`scheduleForceClose`), but it was built to the letter of "must be enforced," not to the spirit of the same requirement's earlier sentence about notifying the client and giving it a grace period. The requirement asks for graceful notification-then-terminate behavior for refresh failures and silently reuses the ungraceful, disclosure-blind mechanism for the absolute-lifetime case sitting right next to it in the same sentence. That reads, to me, like an oversight in how broadly SEC-26's "notify... grace period" language was applied, not a deliberate distinction someone decided the absolute-timeout case didn't need. Worth Design confirming whether that's a correct read or whether there was a reason (that I'm not seeing) the absolute-timeout path was deliberately left out of SEC-26's notify-and-grace-period treatment.
- **OR-1.7 and the Live Voting use cases' disconnect/reconnect scenarios** are, as laid out above, the existing product commitment this issue should be resolved *against*, not around. I'd treat "does the fix make the absolute-timeout case behave the way OR-1.7 already says session interruptions should behave" as close to the actual acceptance bar, more than inventing new UX from the issue's three candidate directions in a vacuum.

## Open questions for whoever picks up Design

1. ~~Is OR-1.7's "reconnect, re-authenticate, rejoin with full state restored" contract actually implemented today for the ordinary case, or only spec'd?~~ **RESOLVED (Marcus, on review): it is not implemented, because the UI it would be implemented in doesn't exist yet.** See the OR-1.7 section above and the Recommendation below for the scope split this produces.
2. **Should the absolute-timeout WS force-close send the same `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (or an equivalent, deliberately-disclosed code) that SEC-26's refresh-failure path already uses, rather than the disclosure-blind `STALE_SIGNAL_CLOSE_CODE` it sends today?** Yes — treat this as decided, not open. This is the close-code fix; see Recommendation.
3. **Does the HTTP side need equivalent handling — a shared response interceptor that recognizes `category: "session_expired"` and routes to the same re-auth surface — or is per-page 401 handling judged sufficient once the WS side (which is where a live session actually lives) is fixed?** Still open. Marcus's read (his review, §"Is anything here too vague") is that Design should pick one framing explicitly — "fix the signal wherever it's broken" (in scope) vs. "fix the live-session experience specifically" (arguably out) — rather than let it default by omission. I agree that's the right shape for the question; I don't have a strong lean either way.
4. **Is a pre-expiry warning (the issue's first candidate direction) worth building in addition to fixing the post-expiry signal, or does fixing the signal satisfy the real concern on its own?** Unchanged from my first pass: I lean toward fixing the signal first, since it's the smaller change and reads as a bug rather than a missing feature, and treating a pre-expiry warning as a separate, later, genuinely-new-UX decision. Marcus's independent lean (his review, same section) agrees. Not our call to close off in an exploration doc, but the proposal should attribute this as a scoping decision, not let it pass silently.
5. **Does the facilitator's absence during re-auth need its own participant-facing indicator?** I'd originally leaned toward "might be unnecessary." Priya pushed back, and I'm persuaded on the merits, with a caveat. Her point: the room stalls the moment the facilitator's timer fires regardless of how gracefully the facilitator's own client handles it — participants keep voting into a room nothing is advancing, with no way to tell "she's thinking" from "her connection died." A quiet, one-line, non-alarming "Facilitator reconnecting…" indicator is cheap and answers exactly that. It's also consistent with the register I'd want for this kind of signal anyway — restrained, `reauth-required`-adjacent, not a countdown or anything gamified — so it doesn't trip my own "does this make the ritual feel like software" concern. **I'm changing my lean to: fold it in.** But Marcus is right that it shouldn't be silently absorbed into #133's acceptance criteria alongside the close-code fix — it's a distinct, separable, small piece of new UI, not implied by the routing fix. Proposal should name it as its own explicit line item with an explicit yes/no recorded, the way #31 was carved out as its own scope rather than folded into whatever touched it.
6. **(New, mine) Does "Log in again" on the reauth CTA actually return the user to the session they were in?** No — I checked. `ReauthRequiredTreatment.tsx`'s control does a hard `window.location.href = "/auth/login"` with no query parameter carrying the current location. `/auth/login` (`packages/backend/src/routes/auth.ts`) accepts and Redis-persists a `joinToken` for the join-link flow, but nothing equivalent for "return here after re-auth" — `/auth/callback` redirects to `/team/:teamId` or `/no-team` off live membership data when no join token is pending, never back to the originating URL. Priya raised this as a suspicion from reading the client code; I traced it through the backend login/callback routes to confirm it's real, not a client-side gap that a server-side mechanism might paper over. **This means the close-code fix alone is necessary but not sufficient**: even after a facilitator or participant correctly lands in `reauth-required` and clicks through, they surface on a generic team/session-list page, not back in the room. Design needs an explicit return-to mechanism — the `pendingJoinToken` pattern in `stateData` is a reasonable template (carry the current session URL through the OIDC state round-trip the same way) — and it belongs in scope alongside the close-code fix, not as a follow-up, because without it the visible symptom ("I clicked reauth and I'm not back in my session") is barely improved over today's infinite spinner.

## Recommendation

**Scope splits into two pieces with two different timelines — this replaces my first-pass framing, which assumed the smaller outcome before Question 1 was actually checked.**

**(a) Ship now, independent of any UI:** the close-code routing fix — `CLOSE_FORCE_EXPIRED` should send `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (or an equivalent, deliberately-disclosed code), not the disclosure-blind `STALE_SIGNAL_CLOSE_CODE` it sends today — plus the return-to mechanism from Open Question 6 above, plus Priya's facilitator-copy fix (below). None of these three depend on the live-voting UI existing; all are backend/connection-health/shared-component level changes, testable today. This is the actual, real bug in #133, and it's small.

**(b) Explicitly out of scope for #133, worth its own follow-up issue:** verifying that a facilitator or participant who reconnects lands back at the correct topic with the readiness grid intact — the "rejoin with state restored" half of OR-1.7. This cannot be built, tested, or accepted against real UI until the live-session voting screen (topic display, vote casting, real readiness grid, reveal control) exists as a change of its own; today only stubbed connection-health hosts exist. (a) does not block on (b), and (b) is not blocked by (a) — the close-code fix gets someone out of the infinite-retry trap regardless of what they land back into. Proposal must say this plainly rather than write acceptance criteria implying full state-restoration verification, which nobody could execute today.

**Also folding in from Priya's review, both in scope for (a):**
- The `ReauthRequiredTreatment.tsx` copy ("Any vote you haven't submitted yet will be lost") is factually wrong for the facilitator call site — facilitators never vote (FR-4.5). This doesn't touch D9's role-blind *mechanism* (one component, one state machine, one close-code path); it's a copy-accuracy fix, not a reopening of that decision. At minimum the vote-loss sentence shouldn't render for the facilitator call site.
- The participant-facing "Facilitator reconnecting…" indicator (Open Question 5) — named explicitly as its own small scope item, not implied by the close-code fix.

**Deliberately not folding in, with rationale:** whether an Application Administrator can reassign facilitator control mid-session (BRD OQ-2(a)) and partial-session retention policy (OQ-2(c)) — both explicitly out of scope per the BRD's own accounting, and neither reviewer asked for them. Also not reopening D9's role-blindness *mechanism* itself, even though Priya raised it as a live question — a copy-level fix resolves her factual concern without touching the one-component/one-state-machine guarantee that mechanism protects, and I don't see a reason to trade that guarantee for anything raised here.

I checked, again, whether any of this creates a path around the no-manager or facilitator-from-another-team rules: it doesn't. Re-authentication runs through the same OIDC flow every login does and can't grant a role or team membership someone didn't already have; a facilitator who reconnects is resuming a role they already held for that session, not acquiring one.

## Acceptance conditions by scenario (from Marcus's review — Design should use these directly)

These make the recommendation above testable. Organized by the scenarios the issue body itself invites: mid-vote, mid-reveal, participant vs. facilitator drop, HTTP vs. WS.

1. **Facilitator's absolute timeout fires mid-vote, pre-reveal:** WS force-close must send the disclosed reauth code. Client must land in `reauth-required`, not `unknown-reconnecting`. Per the existing use-case contract (`04 - Live Voting - Use Cases.md` line 371), the topic must remain in the voting phase — no reveal, no auto-advance — until the facilitator completes re-auth and rejoins. Testable today, independent of the live-voting-UI gap, because it's a backend/connection-health-level behavior.
2. **Facilitator's absolute timeout fires mid-reveal (after clicking, before all clients confirm receipt):** Out of scope for #133 to newly define — FR-4.6.1's reveal is a one-way, server-committed transition ("no un-reveal"); a facilitator logout after the transition has committed server-side doesn't need to block or roll back anything. Acceptance condition: confirm (don't newly build) that the reveal, once server-committed, completes for all other clients regardless of the facilitator's own connection state.
3. **Participant's absolute timeout fires mid-vote (composed, not yet locked in):** Out of scope per the issue body's own reference to #31 — don't re-litigate composed-vote-state persistence here. Acceptance condition for #133 specifically: the participant reaches `reauth-required`, not an infinite retry loop; what happens to their compose state on the other side of re-auth is #31's territory.
4. **Participants when the facilitator is the one who dropped:** No spec'd "facilitator is away" indicator exists for participants today. Per the Recommendation above, this is folded in as its own explicit scope item (the quiet indicator), not silently inherited by the close-code fix and not silently dropped either.
5. **HTTP-side 401 on `session_expired` (any page, not mid-WS-session):** No shared interceptor exists today (confirmed by grep). In scope for #133 only if the proposal's stated goal is "fix the signal wherever it's broken," not if it's "fix the live-session experience specifically." Design should pick one framing explicitly (Open Question 3) rather than let it default by omission.
