## 2. What the threat precisely is

Terminology for the new text: use the use-case/BRD wording ("topic customization lock", "locked team", "zero active topics"). Mention `first_session` once, as the design-state name for a team with no completed session. Define "carve-out" on first use; the reader is a pre-production reviewer (8.4) who has not read #200 and should not need to open the archived changes.

Before #200, an application_admin had no way to put topics on a team whose customization lock was engaged: the lock gate returns `409 TOPIC_CUSTOMIZATION_LOCKED` for add, restore, archive and reorder, admins included (lock state is derived live from whether a completed session exists). The lock is a protective constraint: it stops anyone, including admins, from shaping a team's topics during its first-session window. `POST /api/v1/teams/:teamId/topics/assign-defaults` (file `packages/backend/src/routes/topics.ts`; cite path and file only, no line numbers) is the single deliberate carve-out. It does not call `checkCustomizationLockGate`.

Preconditions the endpoint accepts (to be stated as a plain precondition line, not left implicit): the team has zero ACTIVE topics, and the team is either locked or unlocked. On a locked zero-topic team it is a true carve-out. On an unlocked zero-topic team it is not a bypass (the normal add/restore path also works there), but it would still accept. Archived topic rows are not counted and the handler only inserts, so existing archived history is left in place and not resurrected (implementer to confirm against the handler before the sentence is written; drop it if not confirmed).

The trust relationship that is new: one credential, the `application_admin` role (granted by IdP group claim mapped on every sign-in; no in-app grant UI), can write to any such team's topics, and the team did not ask for it and cannot refuse it. With #208's decision (PR #268, `requirements/use cases/08b - Member Admin Topic Writes - Decision.md`: admins are a trusted role, only barred from facilitating their own team), this applies even to an admin who is a member of the team.

Attack framings, with what the attacker actually gets:

1. Compromised or malicious admin session calls assign-defaults for every team that has zero active topics. Gain: the attacker writes the template's current active rows (name, prompt, vote type, description, default flag, numbered 1..n) into those teams. Nothing else: no free text, no chosen source team or template id (the handler reads no body and no query), no annotations, no unlocking.
2. Chain with #216 (the real new exposure). #216 lets one admin rewrite the template prompts every future team sees. assign-defaults copies the template's current active topics, so an admin who can edit the template can make assign-defaults deliver attacker-chosen text into zero-topic teams. This is the same single role and both steps are audited (template writes under the `topic.default_*` operations, assign under `topic.defaults_assigned`; the implementer confirms the exact operation names and what metadata each carries, and the text says only "audited" with the operation name unless metadata is verified). The model should say the real bound is "whatever the template holds", so template integrity is part of this control. #200 predates #216, so its "canonical set only" argument was written against a template nobody could edit through the API.
3. Compromised admin as a nuisance actor: assign to a team that is empty by fault, or race a legitimate repair. The repair baseline is `docs/deployment.md` "Zero-topic teams": a non-zero count needs a product owner decision about a one-off repair, and the repair then uses the same endpoint (or the documented manual path with the same precondition and audit operation). The difference between legitimate and malicious use is therefore the PO decision, not the mechanism. Impact of the nuisance case: the team gets the standard set, which a first session runs anyway.
4. Availability angle (not integrity): the endpoint holds the per-team advisory lock (transaction-scoped) for one INSERT...SELECT. Bounded. The per-actor topic-write limiter applies after authorization.

What the threat is NOT, and the model should say so to avoid over-claiming:
- It does not let an admin change the content of an existing active topic set on a locked team. add/restore/archive/reorder remain gated. The regression tests listed in section 3 are what hold that line (worded to what they assert, not more).
- It does not touch in-progress `session_topics`, which is a snapshot taken at room open under the same advisory lock. For the lobby / room-open state (Priya's question 5): the concurrency test asserts that a room open (`/advance`) queued behind an assignment snapshots the assigned rows, and that a room open that wins the lock first is refused `NO_ACTIVE_TOPICS`. So a room never opens on a half-assigned set, and the assignment cannot change an already-snapshotted session. The text states exactly this, and makes no broader promise than the tests give.
- The ritual's load-bearing constraints (no-manager rule, simultaneous reveal, facilitator from another team) are not touched; the endpoint has no participation or facilitator path. The change also alters no session pacing, reveal, readiness or outlier behavior, so reviewers need not re-test those. It is not a vote, trend or individual-performance data path; the 201 body is `{ topicCount }`.

Devon's lens on the ritual: "topic flexibility within guardrails", with protective constraints structural, not toggles. This carve-out is acceptable because it is justified by a precondition (zero active topics: nothing for the lock to protect) rather than by who the caller is, and it is a dedicated endpoint, not a flag or an opened lock. The failure mode I would object to is anyone later "generalizing" it (top-up, copy-from-team-X, EM/facilitator trigger, partial restore). The model names that as a reopen trigger.

Regression tests: I read the bodies of all three. The text may claim exactly the following and no more.

- `assign-defaults-lock-gate-source.test.ts` (source inspection, no database). Asserts: (a) the set of routes registered in `routes/topics.ts` equals a pinned list of seven, so adding or removing a topic route fails the test; (b) each of five routes (add, archive, restore, reorder, restore-defaults) still contains a call to `checkCustomizationLockGate`; (c) the assign-defaults route contains no call to it and no call to the lock-state readers (comments stripped); (d) a self-test of the route splitter. Note: five gated routes, not four (restore-defaults is gated too, per #218). It does NOT assert "the carve-out set changes" in any general sense: it pins the route list, which makes a new, differently-gated route show up, and it checks the presence of the gate in the named routes. Claimable wording for 8.2: "a source test pins the list of topic routes, requires the five lock-gated writes to call the lock gate, and requires assign-defaults not to".
- `assign-defaults-concurrency-integration.test.ts` (real Postgres, skipped when infrastructure is down unless REQUIRE_DB is set). Asserts: two simultaneous calls on a zero-active team (two admins, and the same admin twice) yield exactly one 201 and one 409 `TEAM_HAS_ACTIVE_TOPICS`, the template's topic count, contiguous display order, a free lock, and exactly one `topic.defaults_assigned` row; the precondition runs at READ COMMITTED; a room open (`/advance`) queued behind the assignment snapshots the assigned rows; a room open that wins the lock first is refused `NO_ACTIVE_TOPICS` and the assignment then succeeds; recovered topics equal a freshly created team's field for field. It does NOT assert anything about archived topics or about the template-edit chain.
- `zero-topic-invariant-integration.test.ts` (real Postgres). The earlier claim "no admin API sequence takes a locked team to zero active topics" overstates it. What it asserts: on a locked team with one active topic and one archived topic, an admin's archive, reorder, restore, add and annotate attempts are each refused (409 or 403, never 2xx) and the active set stays exactly the one topic; on an unlocked team with two topics, archiving the first succeeds and archiving the last is `409 TOPIC_LAST_ACTIVE` with the set unchanged. It is one scripted attempt per endpoint, not a sequence search. Claimable wording: "refuses add, restore, archive, reorder and annotate on a locked one-topic team, and refuses archiving the last active topic on an unlocked team". The word "sequence" and any "permanent invariant" language are dropped. Its own header comment also says it was written to support the premise that zero-topic teams are legacy or drifted data; that is a statement of the premise, not a proof, and the text does not upgrade it. It is cited only with the narrowed wording above.

## 4. Residual risk and assumptions (what the threat model must state honestly)

1. Single privileged role, no approval step, no step-up authentication. The control is the IdP group that maps to `application_admin`, not an identity. Compensating process: review of that group, plus the audit trail.
2. Blast radius of one compromised admin is every zero-active-topic team, same as any other admin write (#208, accepted under the trusted-role decision). The text says "expected: none" and cites `docs/deployment.md` "Zero-topic teams"; it states no number (no recorded diagnostic count was located). This is a stated requirement, not an open question.
3. Detective, not preventive. Nothing blocks a malicious call; the success audit row is the record. The application's DB role can still modify `audit_log` and no tamper evidence is claimed. No monitoring consumer reads these signals (#131, open at time of writing; re-check on the day of landing). Operationally this means nobody is alerted that a team is empty either: today the facilitator who cannot open a room is the de facto detector of a zero-topic team (Priya's observation 4). The text says so.
4. Template integrity is a dependency of this control (chain with #216).
5. Denial rows are best-effort: sampled after a per-actor threshold and absent during a Redis outage (log-only `topic.denial_audit_suppressed` is the signal). The 403 path is not request-rate limited. Only the success row is guaranteed durable. This S-B limitation is stated for the assign-defaults path only.
6. `actor_ip` is only as trustworthy as `trustProxy` for each deployment (app-wide, pre-existing).
7. The generic `ASSIGN_DEFAULTS_FAILED` 500 has no durable row, only a log line with the correlation id; it left no state behind.

Residual risk rating and basis (one sentence, stated in the text): Residual risk is rated low. That rating rests on the expected affected population being none and on `application_admin` already being an accepted trusted role (#208), not on the controls being preventive: the controls are detective, and the audit trail is the only record.

Acceptance wording for the chained path (template rewrite then assign): "accepted under #208's trusted-role decision; the chained path is recorded as a reopen trigger". The text does not say "accepted by the product owner" for the chained path, because that acceptance was not given specifically.

## 7. Facilitator and operator experience (added from Priya's review)

Accepted and added:
- The Operator and facilitator experience paragraph in 8.1.1 (2 to 3 lines). It says: the carve-out exists so a team stuck at zero topics can be unblocked quickly; the first person to notice is a facilitator who cannot open a room (room open answers `NO_ACTIVE_TOPICS`); the recovery path is an `application_admin` calling assign-defaults; and facilitators are deliberately NOT given self-service recovery. It records the cost of that choice (a wait on an administrator before a scheduled session) so a future reader weighs both sides rather than treating "no facilitator trigger" as free. It also states that the lock, which protects the first-session window, is the reason the facilitator cannot fix this alone.
- Recovery-speed note in the reopen triggers (section 6 item 2): added approval or step-up would delay facilitator recovery before a scheduled session, and must be weighed against the near-zero affected population.
- Onboarding impact of the #216 chain: an emptied or badly edited template makes team creation roll back (a new team cannot be created) and degrades the first sessions of any new team. This is another reason template integrity is part of the control, stated in 8.1.1 item d.
- Statement that nothing here alters session pacing, reveal, readiness or outlier behavior (section 2).
- Operational finding that the facilitator is the de facto detector of an empty team because there is no monitoring (section 4 item 3).
- No participant-visible trace of admin activity: stated via the #271 reader-inventory control (section 3).

Declined, with rationale:
- "Recovery should not require a second approver given the low risk" written as a requirement in the doc. I agree with the intent (recovery speed must not gain approval delays) and the text records it as a weighing factor in any reopen decision, but a threat model document should not pre-commit the project against a future security or compliance requirement; that would conflict with the reopen trigger that exists for exactly that case. So the doc states the cost and the weighing, and the reopen trigger stays.
- Making the doc promise anything about the UI a facilitator sees, or about an open page refreshing after assignment (Priya's questions 1 and 3). I have not verified either, a threat model is the wrong place to promise UI behavior, and this change is documentation only. They go in as one follow-up item below, not as claims.

Open questions for the team, none blocking, to be listed in the proposal as follow-ups rather than scope:
1. Verify what a facilitator of a zero-topic team sees today when trying to open a room, and, if there is no clear actionable message (for example "This team has no topics. Ask an administrator to restore the default set."), file a follow-up issue. Same follow-up: whether an already-open page updates after assignment or needs a refresh, and a way for a facilitator to tell an admin which team without a screenshot (one line, out of scope to build).
2. Priya's question 4 (does a team that previously ran sessions get the generic defaults back): by the precondition, assign-defaults needs zero ACTIVE topics, so a team with prior sessions can only be affected if its topics were all archived or lost, and the lock would be released for such a team anyway (a completed session unlocks customization). The text states the precondition and does not claim anything about teams with history beyond "archived rows are left in place" if confirmed. If the facilitator concern is real it belongs in the same follow-up.
