# Security Review — `facilitator-error-states-e2e` design

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope reviewed:** `design.md`, `proposal.md`, `tasks.md`, cross-checked against `packages/backend/src/routes/content.ts`, `facilitator-sessions.ts`, `packages/backend/src/routes/__tests__/facilitator-error-states.test.ts`, `packages/backend/src/realtime/__tests__/ws-pubsub-integration.test.ts`, and the archived `enforce-access-control-on-team-content` tasks.md (Group 10 / task 11.10).

## Summary

This is a test-only change and I confirmed that claim holds — no route handler, authorization helper, or audit-logging code path is touched. My review is therefore about whether the *test* is trustworthy as evidence, not whether it introduces a vulnerability. On that standard: the core non-disclosure assertion for Error State 4 is preserved at the level the design explicitly commits to, but I found one place the design's own stated rigor bar is narrower than the mocked test it claims to match, one operational risk in how the real-infra fixture forces Error State 2, one implicit (unstated) scope decision about authentication that should be named explicitly, and one gap — audit logging — that isn't addressed at all despite this being the first time these six states will run against a real, queryable `audit_log` table. None of these are blockers. Two are should-fix.

## 1. Authentication flow in the test harness

**Finding: the test harness does not exercise real authentication, and the design should say so explicitly.**

I traced how a "facilitator" identity gets attached to a request in the existing mocked suite (`facilitator-error-states.test.ts`, `buildContentApp`/`buildFacilitatorApp`, lines 89–107): it's `app.decorateRequest("session", null)` plus an `onRequest` hook that does `request.session = { userId }` directly — no cookie, no signature, no OIDC token, nothing that resembles the real `@fastify/session`-backed flow. Every route handler in `content.ts`/`facilitator-sessions.ts` then trusts `request.session.userId` verbatim (`const session = request.session as unknown as SessionData`). This is correct isolation for what these routes are actually supposed to be tested for: `evaluateTeamAccess` is a live DB-backed *authorization* check, independent of how the identity got there, which is exactly the server-side-authorization pattern I want to see (identity assertion and authorization decision are separable, and the authorization decision is the one under test here).

Design.md D1/D4 describe the new real-infra file as following the same fixture conventions (`ws-pubsub-integration.test.ts`'s raw-SQL, `crypto.randomUUID()`-per-test pattern), and `ws-pubsub-integration.test.ts` itself never touches HTTP auth at all — it registers a fake socket directly into `ConnectionRegistry`. I read this as strong evidence the new suite will continue injecting `session.userId` synthetically rather than performing a real OIDC login or session-cookie round trip for "facilitator authenticated for Team B" vs. Team A. That's a reasonable scope boundary — OIDC token validation has its own dedicated coverage (`oidc-client.test.ts`, `middleware.test.ts`) — but **the design does not say this anywhere**. Given this proposal repeatedly uses "full-stack" and "through the full stack" language (echoing archived task 11.10's own wording), a future reader could reasonably assume "full-stack" includes the authentication hop. It doesn't, and it shouldn't have to for this change's stated goals, but the Non-Goals section should say so in one line, the same way it already explicitly disclaims the timeout-trigger variant. **Should-fix:** add a Non-Goal stating this suite continues to synthesize `session.userId` rather than performing a real OIDC/session-cookie flow, and that authentication itself is out of scope (covered elsewhere).

No risk of leaking real-looking credentials — the fixtures never construct anything that resembles a real token, cookie, or client secret; `SESSION_SECRET`/`OIDC_CLIENT_SECRET` env fallbacks are hardcoded placeholder strings identical to `ws-pubsub-integration.test.ts`'s, not secrets pulled from any real config. Fine as-is.

## 2. Data access boundaries / fixture isolation

D4 and tasks 2.1/4.1 commit to `crypto.randomUUID()`-generated IDs per test and `finally`-block cleanup, matching the one proven precedent in this codebase. I have no objection to the pattern itself — it's the same isolation `ws-pubsub-integration.test.ts` already relies on for a same-class test that has apparently run cleanly in CI.

**One operational risk not addressed in Risks/Trade-offs: task 3.1's DB-role privilege mutation.** To force Error State 2 for real (a genuine query exception after authorization succeeds, not an authorization denial — correctly distinguished from Marcus's original suggestion per the proposal's disposition section), task 3.1 proposes *revoking the test DB role's `SELECT` privilege on `session_topics`* for the duration of one test, restored in `finally`. This is different in kind from the other fixtures: every other fixture inserts/deletes rows scoped by random UUIDs and cannot collide with anything else running concurrently. A `REVOKE`/`GRANT` on a table is **not row-scoped — it's connection/role-scoped**, and if this suite's tests (or any other suite sharing the same CI Postgres instance and role) execute concurrently against the same database, a mid-test revoke can cause unrelated tests to fail with spurious permission-denied errors, or — worse — if the `finally` doesn't run (process crash, unhandled rejection, CI timeout kill) the privilege is never restored and every subsequent test in that CI run session that touches `session_topics` starts failing for a reason that has nothing to do with what it's testing. This is a blast-radius question, not a data-confidentiality one, but it's exactly the kind of "hard to reverse, affects shared state" mutation I'd want named as a risk with a stated mitigation (e.g., confirm the CI Postgres instance is single-database-per-run and this test suite doesn't run with `--pool=threads`/parallel workers against the same connection, or scope the revoke to a role only this test uses). **Should-fix:** add this to design.md's Risks/Trade-offs with an explicit mitigation, not leave it to be discovered during implementation.

## 3. Audit logging — not addressed anywhere in this change

I checked whether any of Groups 1–7 in `tasks.md`, or any Decision in `design.md`, assert against `audit_log` writes. They don't — I grepped both files for `emitAuditEvent`/`audit_log` and got zero hits. I also confirmed the *existing* mocked suite doesn't assert on it either: `mockEmitAuditEvent` is defined and wired to intercept `emitAuditEvent` calls, but nothing in `facilitator-error-states.test.ts`'s 22 tests ever asserts it was called with anything. So this isn't a regression this change introduces — it's a pre-existing gap this change had a natural opportunity to close and didn't take.

That opportunity is real: this is the first time these six states will run against a real, queryable `audit_log` table, and I traced two places where the audit story is worth stating explicitly rather than leaving implicit:
- `facilitator-sessions.ts`'s reveal path (`recordRevealTriggeredAudit`) writes a real `audit_log` row **inside the same transaction** as the reveal — Error State 1's recoverable/non-recoverable *failure* paths never reach that code (they return before the transaction begins), so correctly, no audit row should be written for those two states. Worth a one-line assertion (`SELECT count(*) FROM audit_log WHERE session_id = ...` returns 0) precisely because it's cheap now that Postgres is real, and it's the kind of "prove the absence, not just the presence" check I'd otherwise have to ask for separately.
- `content.ts`'s `denyNullGrant` → `denyCrossTeamFacilitator` (Error State 4's actual code path) **does not call `emitAuditEvent` at all** — I read the function; it applies the timing floor and returns the denial, nothing else. Compare this to the sibling admin-denial path this same file implements for Task 5.11 ("Application Admin session-content denial audit... entry written BEFORE the response is sent"), which *does* audit-log its denial. A cross-team facilitator probing for another team's session data is at least as audit-worthy as an admin hitting a session-content endpoint — arguably more so, since it's the scenario closest to the "compromised credentials, lateral movement" threat model I care about for internal apps. This is a production-code gap, not a test gap, and this change's own Non-Goals correctly rule out route-handler changes — so I am **not** asking this change to add the audit call. I *am* asking that this finding be written down somewhere it won't get lost, since right now nothing in this codebase's tests or specs documents that cross-team denial attempts are silently unaudited. **Should-fix (scope-appropriate form):** add a line to design.md's Risks/Trade-offs or Open Questions naming this as a known gap for a follow-up change, so it doesn't stay invisible. Not a blocker for this test-only change.

## 4. Error State 4 non-disclosure rigor — the specific question I was asked to verify

Design.md's Goals state: *"Preserve the non-disclosure rigor `facilitator-error-states.test.ts` already applies to Error State 4 — assert Team A's ID, name, and existence are absent from the response body, not just that the expected message string is present."* Tasks 3.2/3.3 restate this as asserting "by absence... that the response body contains no Team A identifier, name, or any other existence signal."

I compared this against what the mocked suite's Task 10.5 test (`facilitator-error-states.test.ts:707-734`) actually does, since that's the rigor bar being claimed:

```js
const rawBody = res.body;                          // raw string, not parsed JSON
expect(rawBody).not.toContain(teamAId);
expect(rawBody).not.toContain("team-A");
const body = res.json() as { error: { message: string } };
expect(body.error.message).not.toContain(teamAId);
expect(body.error.message).not.toContain("Team A");
expect(body.error.message).not.toContain("session history");
```

Note the first two assertions run against `res.body` — the **raw, unparsed HTTP response string** — not just the parsed JSON's message field. That matters: it's the check that would catch a leak anywhere in the response (a stray debug field, an unexpected header echoed into the body, a serialization bug that dumps more of the object than intended), not only a leak in the one field the test author thought to check.

Design.md and tasks.md both say "the response body" without specifying raw string vs. parsed-field assertion. Given this design's own Context section states the correct precedent is to reuse existing patterns "rather than inventing a new one" (D2), and given task 3.3 explicitly says "matching `facilitator-error-states.test.ts`'s existing rigor," my read is that the intent is to carry the raw-body check forward too — but the design doesn't say so in enough detail that an implementer under time pressure couldn't reasonably settle for checking only the parsed `body.error.message` field and call it done, which would be a real reduction in rigor versus the file being explicitly used as the bar. **Should-fix, low severity given the stated intent is clearly the right one:** tasks.md 3.3 should spell out the raw-`res.body`-string assertion explicitly (not just the parsed-JSON field checks), the same way 3.2/3.3 already spell out the exact message string, so this isn't left to implementer discretion.

Beyond that phrasing gap, moving to real infra does **not** introduce a new leak vector I can see for this specific assertion: the fixture team's real UUID and real name only ever exist in the test's Postgres INSERT, the request, and (if the test fails) the test framework's own failure diff — none of which is the *production* response body this assertion is checking. I looked for a scenario where a real-Postgres error (versus a mocked, hand-authored rejection) could leak Team A's identifier through an unhandled-exception path instead of the controlled 403 path, and didn't find one: `content.ts`'s authorization gate (`evaluateTeamAccess` → `denyNullGrant`) runs and returns before any resource query touches Team A's row, so a real DB round trip for the denial path has no opportunity to throw a Postgres error containing Team A's data in the first place. This is a case where "authorization before lookup" (the file's own documented Decision 7 pattern) is exactly the property that keeps a real-infra test from being able to accidentally expose more than the mocked version did.

## 5. Other observations (no action needed)

- **Secrets:** No new secrets, hardcoded credentials, or config are introduced. Env-var fallbacks match the existing `.env.example`-derived pattern verbatim (D2), which I've already reviewed favorably for the file it's copied from.
- **CI blast radius:** Confirmed via the design's own claim and a read of the Impact section — no `.github/workflows/integration.yml` changes, so this doesn't touch pipeline security posture.
- **`describe.skipIf` self-skip behavior:** Same as the existing precedent; not a concern. Worth noting only that a suite which silently skips outside Docker environments means a developer who never runs `docker compose up` locally gets zero local signal that Error State 4's non-disclosure check ran at all — CI is the only enforcement point. That's an accepted, pre-existing trade-off (Risks/Trade-offs already names it), not new to this change.

## Verdict

No blockers. Two should-fix items before this moves to implementation:
1. Add a Non-Goal stating authentication (OIDC/session-cookie flow) is not exercised by this suite — the harness continues to synthesize `session.userId`, same as the mocked file.
2. Add the DB-role-privilege-mutation risk (task 3.1) to Risks/Trade-offs with a stated mitigation for CI concurrency/cleanup-failure blast radius.

One optional strengthening, not required for this change to proceed:
3. Tighten tasks.md 3.3's wording to explicitly require the raw-`res.body` substring check, not just the parsed-JSON field check, so the stated rigor bar is unambiguous to whoever implements it.

One finding for the record, out of this change's scope to fix:
4. Error State 4's actual denial code path (`denyCrossTeamFacilitator` in `content.ts`) writes no audit_log entry — cross-team probing attempts are currently unaudited in production, unlike the sibling admin-denial path. Recommend a follow-up change; flagging here so it isn't lost.
