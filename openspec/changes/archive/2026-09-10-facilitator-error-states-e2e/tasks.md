## 3. Error State 2 / 4 — content endpoints, real Postgres

- [x] 3.1 In the dedicated file created in task 1.5, test: `GET /api/v1/teams/:teamId/sessions`, called by a facilitator whose `evaluateTeamAccess` grant already resolves to `path: "facilitator"` with an active-set `sessionStatus` (authorization succeeds — this state is not an authorization denial, see note below) — assert real `200`, the empty-state body, the exact "still active" string, and explicitly assert the status is not `403`. Steps, per design.md D7:
  1. Using the normal `dipstick` superuser connection, `DROP ROLE IF EXISTS dipstick_restricted_probe;` (defensive, self-heals a prior crashed run) then `CREATE ROLE dipstick_restricted_probe LOGIN PASSWORD '<fixed test-only password>' NOSUPERUSER;`, then `GRANT CONNECT ON DATABASE dipstick TO dipstick_restricted_probe; GRANT USAGE ON SCHEMA public TO dipstick_restricted_probe; GRANT SELECT ON users, team_memberships, sessions TO dipstick_restricted_probe;` — deliberately omitting `session_topics` and every other table.
  2. Insert fixture rows (user, team, membership, session, session_topics) via the same `dipstick` superuser connection.
  3. Save the current `process.env["DATABASE_URL"]`, then set it to `dipstick_restricted_probe`'s connection string, and (in this file only) dynamically import `db.js`/`config.js`/`app.ts`'s `buildApp` fresh so the app-under-test's `db` singleton connects as the restricted role.
  4. Make the real `GET .../sessions` call against that app instance as the fixture's facilitator. `evaluateTeamAccess` (reads `users`/`team_memberships`/`sessions`) succeeds for real; `buildSessionHistoryQuery`'s facilitator branch (joins `session_topics`) fails for real with Postgres's own `permission denied for table session_topics`, landing in `content.ts`'s existing `catch` block.
  5. In `finally`: restore the saved `DATABASE_URL`; using the `dipstick` superuser connection, delete the fixture rows (this test only calls `GET`, which writes no `audit_log` row, so no `audit_log` cleanup is needed here — unlike the reveal/advance/complete-triggering tests in Groups 2 and 4, see 2.1 and 4.3) and `DROP ROLE dipstick_restricted_probe;`.
  - Note: `content.ts`'s `try/catch` around the session-history query only reaches the Error State 2 branch on a genuine query/serialization exception *after* authorization has already succeeded (`grant.path === "facilitator"` and `isFacilitatorInActiveSession(grant)`); a fixture engineered to fail authorization (a non-matching membership/session row) instead produces a 403 via `denyNullGrant`, which is a different error state (4) with a different mechanism. Do not conflate the two.
  - Note: do **not** implement this by revoking a privilege from `dipstick` itself — `dipstick` is a Postgres superuser (verified: no other role exists in migrations 1-9, `docker-compose.yml`/CI both provision only `POSTGRES_USER: dipstick`, and the official `postgres` image grants that user superuser by default), and superusers bypass all privilege checks, so a `REVOKE` against `dipstick` would silently no-op and this test would falsely pass against a broken assertion.

## 5. Handling real-infra discoveries

- [x] 5.1 If any test in Groups 2-4 fails against real infra in a way the mocked suite's assumptions didn't predict (a genuine behavioral bug, not a fixture mistake), stop and flag it explicitly rather than adjusting the test to match the unexpected behavior silently (design.md Risks). Document the finding in the PR description and decide with the team whether it's in-scope to fix here or needs its own follow-up change.

  **Finding (implementation, 2026-09-10):** `npm run db:migrate` never leaves `audit_log` in place on a fresh database, in any environment — including CI. `node-pg-migrate` treats every `.sql` file in `packages/backend/migrations/` as its own runnable migration, so `8_rollback.sql` (written as a manual, opt-in rollback script — see its own header comment, and migration `8_audit_log.sql`'s "Do NOT add a DROP TABLE audit_log here" comment, which assumed rollback was not automatic) runs automatically as the very next migration after `8_audit_log.sql` and does exactly what it says: recreates `role_change_audit` and `DROP TABLE audit_log`. Confirmed against a completely fresh Postgres container (no stale volume): `pgmigrations` records `8_audit_log` then `8_rollback` then `9_draft_session_and_facilitator_expiry`, in that order, on every run. This has been silently invisible until now because no existing real-infra test (`ws-pubsub-integration.test.ts`) writes to `audit_log`; this change's tests are the first real-infra tests to exercise `reveal`/`topics/advance`/`complete`, all of which write real `audit_log` rows. It is a genuine, pre-existing migration-tooling bug — not a route-handler bug, not a fixture mistake — and out of scope to fix in this test-only change (design.md's Impact section scopes this change to the two new test files plus two documentation annotations). Verified locally, without editing any repository file, by applying migration 8's `CREATE TABLE audit_log` statement directly against the local database so this change's own tests could be run for real against the intended schema; that workaround is not part of this change's diff. **Follow-up needed:** rename or relocate `8_rollback.sql` so `node-pg-migrate` does not auto-discover it as a runnable migration (e.g. move it outside `migrations/`, or give it a non-migration-glob name), and re-verify CI's `integration` workflow actually has `audit_log` present today. Flagging for the team to decide whether that follow-up is its own change or an urgent hotfix, given every fresh deploy currently loses the audit table.

  **Escalated:** filed as [issue #39](https://github.com/surratt-dev/project-dipstick/issues/39) per this project's established pattern of naming deferred/discovered work explicitly (issues #26, #38) rather than leaving a severe finding inside an already-archived change's task file. Confirmed with the project owner that this system has never been deployed to production or staging, so this is a tooling-correctness fix, not an incident.
