## Context

`facilitator-error-states.test.ts` (833 lines, 22 tests) already asserts the response shapes for all six in-scope states against a Fastify instance with `db.query` fully mocked (`vi.mock("../../db.js", ...)`). That file is not being thrown away — its assertions on exact strings, status codes, and the `errorState`/`recoverable`/`requiresReveal` fields are correct and stay as fast unit coverage. This change adds a second layer underneath it: the same six states, proven against a real Postgres and real Redis, so "the route handler returns the right JSON" and "a real database round-trip and a real Redis-published event actually produce that JSON" stop being the same untested assumption.

There is also a trap already sitting in the codebase worth naming up front: `session-lifecycle-e2e.test.ts` is named "e2e" but is fully mocked (`vi.mock("../../db.js")`, `vi.mock("../../realtime/ws-pubsub.js")`) — it's a good sequential-narrative unit test, but it is not what this change means by full-stack. This change's tests must not be confused with, or modeled on, that file's mocking pattern. The correct precedent already exists: `ws-pubsub-integration.test.ts` (`packages/backend/src/realtime/__tests__/`) is the one file in this codebase that talks to real Postgres and real Redis — real `db.query` (unmocked), a real `ioredis` `PUBLISH`/`SUBSCRIBE` round trip, `describe.skipIf(!infraAvailable)` gating, and raw-SQL fixture setup/teardown in a `finally` block. This design reuses that pattern rather than inventing a new one.

Relevant endpoints (all in `packages/backend/src/routes/facilitator-sessions.ts` unless noted):
- `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal` — Error States 1 (recoverable/non-recoverable) and 1a (`already_revealed`)
- `POST /api/v1/teams/:teamId/sessions/:sessionId/topics/advance` — Error State 1b (`advance_blocked`, `requiresReveal: true`) and, on the wrap-up-entry branch, the real `publishSessionStateChange` trigger for Error State 3
- `POST /api/v1/teams/:teamId/sessions/:sessionId/complete` — an alternate real `publishSessionStateChange` trigger for Error State 3
- `GET /api/v1/teams/:teamId/sessions` and `GET /api/v1/teams/:teamId/sessions/:sessionId` (`packages/backend/src/routes/content.ts`) — Error State 2 ("Historical data is temporarily unavailable. Your session is still active.") and Error State 4 ("This data is not available in your current session.")

CI already runs both real services: `.github/workflows/integration.yml` provisions Postgres on port 5433 and Redis on port 6380 for every push/PR to `main`, then runs `npm run test` — the exact ports `ws-pubsub-integration.test.ts` probes for. No CI changes are needed for this change to run for real in the pipeline that gates merges.

## Goals / Non-Goals

**Goals:**
- Prove all six in-scope states (1 recoverable, 1 non-recoverable, 1a, 1b, 2, 4) against a real Postgres round-trip through the actual route handlers, with no `db.query` mock anywhere in these tests.
- Prove Error State 3 against its real production trigger: a real committed state transition (via `topics/advance` wrap-up entry or `complete`) that calls the real `publishSessionStateChange`, delivered to a real subscriber over the actual Redis `PUBLISH`/`SUBSCRIBE` channel — not a directly-invoked function call and not a manually-published stand-in event.
- Follow the `ws-pubsub-integration.test.ts` precedent exactly: env-var fallbacks matching `.env.example`, a reachability probe for both services, `describe.skipIf(!infraAvailable)` so the suite self-skips with a clear message in any environment without `docker compose up`, and raw-SQL fixture insert/cleanup so the test owns its own data lifecycle.
- Preserve the non-disclosure rigor `facilitator-error-states.test.ts` already applies to Error State 4 — assert Team A's ID, name, and existence are absent from the **raw response body string** (`res.body`, matching `facilitator-error-states.test.ts:707-734`'s existing `rawBody`/`res.body` check), not just that the expected message string is present in the parsed JSON.

**Non-Goals:**
- No exercise of real authentication. The harness establishes `request.session = {userId}` directly (matching `facilitator-error-states.test.ts` and `ws-pubsub-integration.test.ts`'s existing convention), not a real OIDC login/cookie round-trip. "Full-stack" in this change's scope means the HTTP → route handler → Postgres/Redis path; OIDC and cookie-session establishment have their own dedicated test coverage and are out of scope here.
- No new frontend code, component, or rendering of any of these six states. That is issue #38.
- No test for Error State 3's "system timeout" trigger variant. No timeout-driven auto-transition mechanism exists in this codebase; there is nothing to trigger. **This is a separate, unbuilt mechanism, not a consequence of issue #26 or anything this change resolves** — issue #26 is fully resolved (all four production-trigger events fire from real, committed code paths); the timeout variant was simply never built, on any timeline.
- No changes to `facilitator-error-states.test.ts`'s existing mocked assertions for behavior outside these six states, and no removal of its existing coverage for these six states either — the mocked layer and the real-infra layer are complementary, not a replacement of one by the other in the sense of deleting the fast unit tests.
- No changes to route handler behavior, response shapes, or error strings. This change is test-only; if a real-infra assertion fails, the fix is in the test's fixture or the test's understanding of the endpoint, not a spec or handler change (barring an actual bug discovery, which would be handled as its own follow-up, not folded silently into this change).

## Decisions

**D1 — New test file, not a rewrite of `facilitator-error-states.test.ts`.** The mocked file's fast unit coverage stays exactly as-is. A new file (working name: `facilitator-error-states-integration.test.ts`, placed alongside `ws-pubsub-integration.test.ts` in `packages/backend/src/realtime/__tests__/` if the test needs the same WS-subscriber harness for Error State 3, or alongside `facilitator-error-states.test.ts` in `packages/backend/src/routes/__tests__/` if it doesn't — decided during implementation based on which directory's existing helpers are reused more) carries the real-infra assertions. Editing the existing file in place to swap its mocks for real connections was considered and rejected: it would force every one of the file's 22 fast tests to pay real-DB/Redis latency and the `describe.skipIf` self-skip behavior, turning a currently-always-green fast suite into one that silently skips in any environment without Docker running — the opposite of what a mocked regression suite is for.

**D2 — Reuse the `ws-pubsub-integration.test.ts` infra-probe pattern verbatim, not a new abstraction.** `isRedisReachable`/`isPostgresReachable`, the `PROBE_TIMEOUT_MS` constant, the env-var fallback block, and the `describe.skipIf(!infraAvailable)` gate are copied (not imported as a shared helper) into the new file, matching how the existing file is itself self-contained. A shared test-infra helper module was considered; rejected as unnecessary abstraction for two call sites, consistent with this codebase's general bias against premature shared helpers for N=2.

**D3 — Error State 3 is asserted through its real trigger endpoint, not by calling `publishSessionStateChange` directly, AND through the endpoint that actually computes the spec's required banner text/shape.** Two separate real-Postgres assertions, both required, because they prove different things:
  - The WS pub/sub delivery assertion: the test performs the real HTTP `POST .../topics/advance` (or `.../complete`) call against fixture data engineered so the wrap-up-entry branch fires, with a real WS subscriber registered beforehand (same `ConnectionRegistry` / `createWsSubscriber` / `attachWsEventDispatcher` wiring `ws-pubsub-integration.test.ts` already uses), then asserts the subscriber receives `session_state_change` with the correct current-state field within a bounded wait window. This proves the real Redis `PUBLISH`/`SUBSCRIBE` hop fires on a real committed transition.
  - The `GET /api/v1/teams/:teamId/sessions/:sessionId/facilitator-state` assertion: a real HTTP call against real fixture data (session status set directly to `wrap_up`/`complete`/`abandoned`), asserting the response's `bannerState.type`, `displayType: "banner"`, `currentSessionState`, the exact "Session state has changed. [state]. Resume or review." message, and `action`. This is the endpoint the facilitator client actually polls, and the only place the spec's required banner text/shape is computed — the WS delivery assertion never calls it, so without this second assertion the real-infra layer would still be trusting the mocked suite's word for the one thing (banner text/shape) that endpoint alone produces.

  The `POST .../complete` trigger variant has a real authorization asymmetry worth naming here (not just in tasks.md): `evaluateSessionSubscriberAccess`'s facilitator path (`session-subscriber-access-helper.ts`) only grants when `sessions.status IN ('lobby', 'pre_session', 'active', 'wrap_up')` — `complete` is deliberately excluded, so a facilitator-registered WS subscriber does not receive delivery for the `/complete` trigger. This is delivery-time authorization working as designed (a completed session's facilitator grant window is governed separately, via `facilitator_access_expires_at`, not via this subscriber path), not a bug — but it means the `/complete` variant of the WS delivery assertion must use a participant subscriber, not a facilitator subscriber, or it will fail for reasons unrelated to what it's testing. The `/topics/advance` (wrap-up-entry) variant is unaffected since `wrap_up` is in the granted set.

  This is the assertion pair in this change that exercises the full HTTP-through-WebSocket path and the HTTP-through-Postgres path for Error State 3, which is the literal scope of archived task 11.10's "through the full stack" language for the part of it this change covers.

**D4 — Fixtures are raw SQL against the real schema, following the existing convention exactly, and cleanup explicitly includes `audit_log`.** Same shape as `ws-pubsub-integration.test.ts`: `INSERT` a user, a team, a membership/facilitator row, and a session per test (or per describe block, cleaned up in `finally`), rather than a shared fixture-builder utility. Matches this codebase's established per-file fixture convention rather than introducing a new one for this change alone.

  Unlike `ws-pubsub-integration.test.ts` (whose fixtures never write `audit_log`), this change's tests trigger `reveal`, `topics/advance`, and `complete` — all three write real `audit_log` rows via `emitAuditEvent`/direct `INSERT INTO audit_log` (`facilitator-sessions.ts`). `audit_log.actor_user_id` and `audit_log.team_id` are deliberately not foreign keys (migration `8_audit_log.sql`'s comment: "not FKs, so records remain stable even if the referenced user is later deactivated or deleted") — so deleting the fixture's `sessions`/`team_memberships`/`teams`/`users` rows does **not** cascade-delete the `audit_log` rows those actions wrote. Every `finally` block that triggers reveal/advance/complete must explicitly `DELETE FROM audit_log WHERE actor_user_id = $1` (or `team_id = $1`) for its fixture's IDs, or CI accumulates permanently orphaned rows across every run, forever (no TTL, no periodic cleanup job exists for this table).

**D7 — Error State 2's forced-query-failure mechanism is a dedicated, permission-restricted Postgres role, created and dropped inside its own isolated test file — not a privilege revocation against the app's connection role.** The app connects to Postgres as `dipstick` (`DATABASE_URL` in `.env.example`/`docker-compose.yml`/`.github/workflows/integration.yml` all set `POSTGRES_USER: dipstick`, and no migration or init script creates any other role). The official `postgres` Docker image grants the user named by `POSTGRES_USER` full superuser privileges by default, and Postgres superusers bypass every privilege check unconditionally — there is no configuration that makes `REVOKE` meaningful against a superuser. This was verified directly (migrations 1-9 contain no `CREATE ROLE`/`GRANT` statement scoping any non-superuser role; `docker-compose.yml` and `.github/workflows/integration.yml` both provision only the single `dipstick` superuser). A test that `REVOKE`s a privilege from `dipstick` and expects a query to fail would silently no-op and the test would falsely pass against a broken assertion — worse than not testing it, since it would look like coverage that doesn't exist.

  Instead: a dedicated Postgres role (working name `dipstick_restricted_probe`) is created by the test itself, using the existing superuser connection, scoped to exactly the tables `evaluateTeamAccess` reads for its facilitator path — `SELECT` on `users`, `team_memberships`, `sessions` only, confirmed by reading `team-content-access-helper.ts` directly. It is deliberately never granted `SELECT` on `session_topics` (or any other table `buildSessionHistoryQuery`'s facilitator branch joins). The test then makes the real `GET /api/v1/teams/:teamId/sessions` HTTP call using an app instance whose `db.js` singleton is connected as this restricted role instead of `dipstick`, so `evaluateTeamAccess` (facilitator authorization) succeeds for real, and the subsequent session-history query then fails for real with a genuine Postgres `permission denied for table session_topics` error — landing in `content.ts`'s existing `catch` block exactly as Error State 2 requires, with no route handler change and no mocking.

  Because `db.js` reads `DATABASE_URL` from `config.js` once at module import time, and every other test in this change's suite needs the ordinary `dipstick` superuser connection (for fixture inserts and every other assertion), this one test lives in its **own small dedicated file**, separate from the rest of the new suite, so setting `process.env["DATABASE_URL"]` to the restricted role's connection string before that file's dynamic imports cannot affect any other test file's connection. The file explicitly captures and restores the original `DATABASE_URL` value in a `finally`/`afterAll` (not relying on assumed test-runner process isolation between files) as a second, independent safeguard. Fixture rows for this one test (user/team/session/session_topics) are still inserted/cleaned up via a separate `dipstick`-superuser connection, since the restricted role has no write privileges at all — it exists solely to make the one query under test fail.

  This mechanism requires **no changes to `docker-compose.yml` or `.github/workflows/integration.yml`**: `dipstick`, already a superuser, can `CREATE ROLE`/`DROP ROLE` at runtime with a plain SQL statement, so the role is provisioned and torn down entirely within the test file's own fixture lifecycle — consistent with D4's "the test owns its own data lifecycle" convention, just extended to role lifecycle for this one test.

**D5 — Error States 1a and 1b are asserted as backend-contract-only, per `team-content-access/spec.md`'s own framing.** The spec's implementation note already states their backend contract is implemented and covered by backend tests, with only the frontend rendering left open. This change's 1a/1b assertions check the real HTTP response shape (`errorState`, `revealedAt` for 1a; `errorState`, `requiresReveal: true` for 1b) and the ordering rule (authorization runs before either precondition check) — they do not and cannot assert any rendering, since none exists.

**D6 — The archive annotation and the spec implementation note are hand-written prose edits, not generated from test output.** Both follow the exact style of the existing annotations they extend (task 11.10's current "PARTIALLY UNBLOCKED by" note; `team-content-access/spec.md` line 13's Error States 1a/1b note) so the document's voice stays consistent rather than introducing a new annotation format for this one change.

## Risks / Trade-offs

- **Real-infra tests are slower and can flake on timing.** The Error State 3 assertion waits on an async Redis round trip (`ws-pubsub-integration.test.ts` uses fixed `setTimeout` waits of 200-300ms after each publish). → Mitigation: reuse the same waits that are already proven stable in `ws-pubsub-integration.test.ts` rather than inventing a tighter timeout; keep the bounded-wait assertion generous rather than racing it.
- **Test-only fixture data must not collide with the schema's real constraints (facilitator-from-another-team, active-session uniqueness, etc.).** → Mitigation: follow `ws-pubsub-integration.test.ts`'s pattern of `crypto.randomUUID()`-generated IDs per test and full cleanup in `finally`, so fixtures never persist across runs or collide with each other.
- **A test asserting real behavior might surface a latent bug the mocked suite couldn't catch (e.g., the actual SQL for `already_revealed` behaving differently under a real constraint than the mock assumed).** → This is a feature of this change, not a risk to suppress, but it does mean the change's scope could, in a small way, expand to "fix a bug the real-infra test found." If that happens, it should be called out explicitly in the implementation, not silently absorbed. → Mitigation: tasks.md will flag this as an explicit decision point rather than leaving it implicit.
- **This change runs only in CI and any local environment with `docker compose up` — it self-skips silently elsewhere, same as `ws-pubsub-integration.test.ts` today.** → Mitigation: this is the existing, accepted trade-off for this class of test in this codebase; no new mitigation needed beyond the clear skip-reason console message the existing pattern already prints.
- **The Error State 2 restricted-role mechanism (D7) is connection/role-scoped state, not row-scoped like every other fixture in this suite — a category of risk the rest of this change's fixtures don't have.** A row-scoped fixture that fails to clean up leaves orphaned rows that, at worst, affect re-runs of that same test. A privilege-scoped mechanism that fails to clean up (test crash before `finally`, CI timeout, a killed process) could in principle leave shared state that affects *other* tests, if that state were shared. → Mitigation, and why this is deliberately designed down to near-zero rather than merely accepted: the restricted role is uniquely named, created and dropped entirely within one dedicated test file, and referenced by no other test, fixture, or production code path — nothing else in the suite ever connects as it or depends on its existence. If teardown doesn't run, the only consequence is an orphaned, unused role sitting in the Postgres catalog; it grants no one anything, so it cannot cause a false pass or false fail in an unrelated test. The dedicated file also defensively `DROP ROLE IF EXISTS`s before creating, so a crashed prior run self-heals on the next run without manual cleanup. This is materially safer than the rejected REVOKE-on-`dipstick` mechanism would have been even if that mechanism had worked against a non-superuser role — that alternative would have toggled privileges on the connection role every other test in the file also uses, making cross-test cascade a live risk this design avoids by construction rather than by discipline.

**Noted for the record, not addressed by this change (out of scope):**
- `denyCrossTeamFacilitator` (`content.ts`) writes no `audit_log` entry in production, unlike the sibling Application Admin denial path. A real gap, flagged by security review, but this is a test-only change — fixing it means touching route handler behavior, which is explicitly out of scope here. Worth a follow-up issue.
- No `audit_log` assertions exist for any of the six states in either direction (write or non-write). Now that this change makes `audit_log` writes real instead of mocked, adding those assertions would be cheap — but it's net-new coverage, not part of proving the six response-shape states this change targets, so it's left for a future change rather than expanding this one's scope.
