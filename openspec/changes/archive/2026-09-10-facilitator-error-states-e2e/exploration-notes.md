## 1. What's actually being asked of me here

The issue text reads like the last domino in a chain that's been falling for two months: backend behavior done (Group 10, 22 tests), WebSocket layer done (`websocket-delivery-time-authorization`), so "write the E2E test" sounds like typing. I don't think it is, and I want to show my work on why before I say what I'd do instead.

## 2. The four states, and what's already true about them

From Group 10 of the archived change, precisely:

1. **Reveal failure** — recoverable (session still active, 503, "Try again") vs. non-recoverable (session no longer active, 409, "review the session status")
2. **Historical data unavailable during an active session** — 200 with an empty-state body and "still active" language, deliberately *not* a 403, because a facilitator mid-session must never read a data hiccup as an access problem
3. **Session status transition during live facilitation** — a non-blocking `displayType: "banner"` push, current state included, action string "Resume or review"
4. **Cross-team denial** — "This data is not available in your current session," and Task 10.5 is explicit that the response must not leak Team A's ID, name, or existence

`facilitator-error-states.test.ts` covers all four thoroughly — 22 tests, and they're good tests. Structured error shapes instead of generic 403 bodies, the exact spec strings asserted verbatim, the non-disclosure property asserted both by absence-of-substring and by explicit "does not say X" checks, `sessionActive: true` checked, `displayType` checked against `'modal'` as well as for `'banner'`. This is backend behavior I'd sign off on without hesitation. But every single one of these 22 tests calls `app.inject(...)` against a Fastify instance with a fully mocked `db.query`. There is no real database, no real WebSocket, and — this is the part that matters for issue #19 — no client anywhere in the test file. It answers "does the route handler produce the right JSON," which is a different and narrower question than "does a facilitator sitting in a browser ever see the right thing."

This is where the issue's framing and the codebase's reality diverge, and I want to be precise rather than hand-wavy about it.

There is no reveal button anywhere in this codebase. There is no facilitator-facing page that calls `GET /api/v1/teams/:id/sessions` or `/trends` — the only consumers of those endpoints are the EM pages (`EmSessionHistoryPage`, `EmTrendDataPage`), which are a completely different role and completely different UI. There is no component that calls `GET /api/v1/teams/:id/sessions/:id/facilitator-state` — the banner endpoint Error State 3 depends on isn't fetched from anywhere on the client. And there is obviously no rendering of "This data is not available in your current session," because there's no code path that could produce that request in the first place.

So the honest inventory is: **zero of the four error states have any client-side rendering today.** Not "rough" or "unstyled" — absent. The only live-session frontend that exists renders connection-health strings, which is a different feature entirely.

## 4. The trap I want to name explicitly: these are not the same gate

The issue text bundles two blockers together — "(1) WebSocket infrastructure (see #18) and (2) Priya Nair approval of facilitator error message text" — and says both have cleared. I want to pull those apart because I think conflating them is exactly how this issue could quietly turn into either less than it should be or more than anyone signed up for.

**Gate 1 (WebSocket infra) is genuinely clear, and more thoroughly than I first gave it credit for.** `evaluateSessionSubscriberAccess`, the per-candidate delivery-time checks, the four events — all built, all tested (`websocket-delivery-time-authorization` Group 9, `websocket-staleness-signal` Group 1). I originally wrote that `vote_revealed`'s and `topic_history_update`'s real production triggers remained blocked on GitHub issue #26, citing the archived `websocket-delivery-time-authorization` tasks.md. That was stale the moment I wrote it: `session-lifecycle-transitions` (archived 2026-09-08) resolved issue #26 directly. All four events — `vote_readiness_update`, `session_state_change`, `vote_revealed`, and `topic_history_update` — now fire from real, committed production writes: reveal (`POST .../reveal`, `voting → revealed`), topic-advance and wrap-up entry (`POST .../topics/advance`, `SESSION-012`), lobby-advance, and session-close. I verified this by reading the actual handler code, not by trusting a spec's Purpose-section note — the reveal handler's inline comment reads "issue #26 is resolved by this change," and the pattern repeats at the topic-advance call site.

This means none of the four error states is blocked on a missing production trigger. Error States 2 and 4 were always pure HTTP content-endpoint behavior. Error State 4's cross-team denial has nothing to do with this gap either way. Error State 1 (reveal) and Error State 3 (session status transition) — the two I originally flagged as sitting on top of the gap — can now be tested against their real triggers, full stack, no directly-invoked or manually-published stand-in required, and no "re-run once #26 lands" caveat needed. The one exception, which is a different and narrower gap: Error State 3's *specific* trigger variant of "system timeout" has no timeout-driven auto-transition mechanism in the codebase at all — that's not an issue-#26 consequence, it's a mechanism that was never built. Section 6 restates piece 1 accordingly.

**Gate 2 (Priya's sign-off) is a case of mistaken identity.** I went looking for where Priya signed off on "facilitator error message text" and I don't think it exists as this issue describes it. What exists is Group 6 of `websocket-staleness-signal` — Priya's copy sign-off on exactly three strings: the `unknown-reconnecting` banner, the `reauth-required` banner, and the grid-marker tooltip. Those are connection-health strings. They are not the reveal-failure message, not the historical-data-unavailable message, not the session-transition banner text, and not the cross-team-denial message — those four strings live in Group 10 of the *access-control* change and, as far as I can find, were never routed to Priya for a UX pass the way the staleness-signal strings explicitly were. If someone reads "Priya approval of facilitator error message text" and checks it off because Group 6 of the staleness-signal change closed, they've signed off on the wrong four sentences. I don't think this was done maliciously or even carelessly — the two efforts landed close together and use similar language ("facilitator," "error state," "banner") — but it's exactly the kind of drift I'd rather catch here than after a test gets written against strings nobody with UX authority has actually reviewed.

And this connects to something I take seriously for its own sake, not just as a process nitpick. My persona note above says it plainly: a manager exception "has a way of becoming norms." The same logic applies to sign-off gates. This project has now built the *habit*, three times running (Group 9 of the delivery-time-authorization change, Group 6 of the staleness-signal change, and the archived Group 9 gate before that), of not letting a user-facing string ship without a named human actually looking at it in context. If this issue lets that habit lapse — by treating an unrelated sign-off as satisfying this one, just to clear a checkbox — that's a worse outcome for the project than the test taking another sprint. I'd rather the gate go unresolved and clearly marked than get quietly waved through.

## 5. Direct answer to `websocket-staleness-signal` task 5.3

That task asks me to confirm whether `SessionConnectionHost` and `FacilitatorConnectionHost` are sufficient to unblock this issue's test, or to name what else is needed. Having read both components fully: **they are not sufficient, and it isn't close.** Not because they're poorly built — they're exactly right for what they were scoped to do — but because they solve a different problem. They exist to prove a real WebSocket connection can drive a real React render for connection-health states. They render none of the four error states this issue needs, they don't call the reveal endpoint, they don't call the historical-data endpoints, and `FacilitatorConnectionHost`'s participant rows are a hardcoded fixture, not session-derived data. Reusing their *plumbing* (the real WS connection, the route pattern, the `ProtectedRoute` wrapping) is sensible and saves real work. Treating their *existence* as satisfying this issue would be a category error — it would be answering "is there a WebSocket client" when the question is "does a facilitator see the four specific messages Group 10 defines."

I'd also flag, while I'm in this file: the known deferred gap already written into `App.tsx`'s comment on the `/session/:sessionId/facilitator` route — no client-side facilitator-role check exists yet, harmless today only because `FacilitatorConnectionHost` renders `STUB_ROWS`, a hardcoded fixture — becomes exactly the kind of thing that stops being harmless the moment this issue wires in real facilitator-only content (historical data, reveal controls). This is piece 2's job, not "whoever picks this up": piece 1 introduces no new frontend surface, so it cannot be the change that closes this gap, and piece 2 is precisely the change that stops the component from rendering stub data. Section 6 names this as a hard-gate acceptance condition on piece 2.

## 6. Where I land

Reading the four options honestly:

- **(a) Write E2E tests against existing backend behavior plus whatever minimal frontend surface already exists, deferring styled UI.** This doesn't work as stated, because "whatever minimal frontend surface already exists" is none, for these four states specifically. There's nothing to point a test at.
- **(b) Build new minimal frontend components for these four states first.** Closer to true, but stated this baldly it invites exactly the scope-creep failure mode I care most about: quietly turning "close out task 11.10" into "design and ship facilitator live-session UI," without anyone deciding that on purpose. New user-facing surface means new copy, and new copy on a live-session screen — the room I have the strongest opinion about protecting, because it's where the ritual either stays a conversation or starts feeling like software being run on people — needs the same sign-off discipline every other user-facing string in this system has gotten. That's not a testing task. That's a Design-stage decision with its own proposal, its own review, and its own gate, the same shape as `websocket-staleness-signal`'s Group 6.
- **(c) Something else — split it, and say so out loud.** This is where I land. Two honest, separately-scoped pieces:

### Piece 1: full-stack backend/WebSocket E2E, real infra, no new UI

Runs against a real Postgres and real Redis via the `integration` npm workflow (see Section 7 — this is a decision, not an open question, as of this revision), replacing `facilitator-error-states.test.ts`'s mocked `db.query` for these specific assertions. Now that issue #26 is resolved (Section 4), every state below tests its *real* production trigger — no directly-invoked or manually-published stand-in needed anywhere in piece 1, which is a stronger position than my original draft described.

Per-state acceptance conditions, held to the specificity bar I'd already reached for State 4 in my first draft:

1. **Error State 1 (reveal failure), recoverable path** — endpoint: `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal`. Trigger: call the real endpoint against a session/topic fixture engineered to fail the authorization check (e.g., a facilitator row that doesn't match) while the session itself remains active. Infra: real Postgres. Assert: `503`-class recoverable body, `errorState: "reveal_failure"`, `recoverable: true`, exact message string, `sessionActive`/session-status field confirms active. Also assert the already-revealed and advance-blocked precondition paths (`already_revealed` / `advance_blocked` error states) against the real endpoint, since `session-lifecycle-transitions` already implemented and unit-tested these — see item on 1a/1b below for why these ride with State 1 rather than getting their own numbered piece-1 item.
2. **Error State 1, non-recoverable path** — same endpoint. Trigger: call reveal against a session fixture whose `sessions.status` is not in the active set. Infra: real Postgres. Assert: `409`, `errorState: "reveal_failure"`, `recoverable: false`, exact "review the session status" string.
3. **Error State 2 (historical data unavailable mid-session)** — endpoint: the facilitator historical-data content endpoint. Trigger: real HTTP call during a fixture session with `status = 'active'`, against a condition that would otherwise deny access. Infra: real Postgres. Assert: `200`, empty-state body, exact "still active" string, explicitly *not* `403`.
4. **Error State 3 (session status transition), real-trigger case — the corrected primary case, per Marcus's finding.** Endpoint: `POST /api/v1/sessions/:sessionId/topics/advance` (`SESSION-012`, wrap-up-entry branch) or the lobby-advance/session-close endpoints — any of these commits a real `session_state_change` publish today. Trigger: call the real endpoint with a subscriber connected, real Redis pub/sub hop, no manual publish. Infra: real Postgres + real Redis. Assert: the subscriber receives `session_state_change` with the correct current-state field, over the actual `ws:events` channel, within a bounded time window.
5. **Error State 3, timeout-variant — named and explicitly deferred, not silently dropped.** No scheduled/timeout-driven auto-transition mechanism exists anywhere in this codebase. This is not an issue-#26 consequence (per Marcus's correction, confirmed against `websocket-delivery-time-authorization` Group 0 task 0.3) — it's a separate, unbuilt mechanism. Piece 1 does not test this variant. Naming it here so whoever eventually builds a timeout mechanism finds this note rather than searching issue #26 for something that isn't there.
6. **Error State 4 (cross-team denial)** — endpoint: the team-content-access-guarded facilitator content endpoint, called by a facilitator authenticated for Team B against Team A's data. Infra: real Postgres. Assert: the denial message string exactly, and — mirroring Group 10's Task 10.5 non-disclosure property and the rigor `facilitator-error-states.test.ts` already applies — assert by absence that the response body contains no Team A identifier, name, or existence signal.

**Error States 1a/1b — in scope for piece 1, riding with State 1 above, not a separate line item.** `team-content-access/spec.md`'s own implementation note for `session-lifecycle-transitions` says the backend contract for both (`already_revealed`, `advance_blocked`) is "implemented and covered by backend tests" already, and explicitly names the *frontend* rendering as the open follow-up work — not the backend/HTTP layer piece 1 tests. Since piece 1 is exactly "real HTTP against real infra, no new UI," 1a and 1b's backend contracts belong in piece 1 for the same reason 1's do; their frontend rendering (the "looks like success," "offers reveal directly" behavior) belongs in piece 2 for the same reason 1's does. I'm folding them into State 1's acceptance conditions above rather than a fifth/sixth state, since spec.md itself frames them as sub-cases of the same reveal/advance surface, not independent error states.

### Piece 2: UI rendering of all four (six, counting 1a/1b) states — new scope, its own proposal

**Filed as GitHub issue [#38](https://github.com/surratt-dev/project-dipstick/issues/38).** Per the discussion that followed this exploration, piece 2 is deferred to its own tracked issue rather than bundled into this change — matching this project's established pattern (issues #26, #32, #33, #36) of naming deferred/gated work explicitly instead of letting a change's scope quietly expand. Issue #19 (and this change) is scoped to piece 1 only; task 11.10 stays unchecked until #38 lands.

The actual UI rendering of these states — a facilitator historical-data view, a reveal trigger and its error/success rendering (including the 1a "renders as success" and 1b "offers reveal directly" behaviors), a session-transition banner consumer, a cross-team-denial-producing request path — needs its own proposal. It does not inherit sign-off from Group 6 of the staleness-signal change; it needs its own, on its own four (six) strings, in situ. Priya's review adds real, specific requirements that piece 2's scope description must carry, not defer to "whoever writes piece 2's tasks.md":

This is a UX-architecture decision, not a per-component styling choice, and Priya has asked to see it before piece 2's implementation, not after.
- **A spec for what *other participants* (not just the facilitator) see when a reveal fails.** This is the simultaneity guarantee extended to the failure path and it is not named as in-scope anywhere in the archived Group 10 work or in my original draft. **Named hard-gate acceptance condition — the `App.tsx` facilitator-role check.** Per Priya's and Marcus's independent flags: piece 2 must add a client-side facilitator-role check on `/session/:sessionId/facilitator` (either a role-aware `ProtectedRoute` variant or a check inside `FacilitatorConnectionHost`) as a named, numbered acceptance condition — not an aside for "whoever picks this up." This is the change that stops the component from rendering `STUB_ROWS` and starts it rendering real facilitator-only content (historical data, reveal state), which is the exact moment the existing `App.tsx` comment says the gap stops being harmless. Piece 2 cannot be considered complete without this check landing alongside the new UI it protects.

**Named gate structure, inherited explicitly, not just in spirit.** Per Marcus's recommendation: piece 2's proposal should name the same four-gate shape `websocket-staleness-signal` Group 6 used, by name, up front — not a single "gets sign-off" checkbox that's easier to wave through than the precedent it's supposed to match:
- Copy sign-off (Priya, on the four/six strings, in situ)
