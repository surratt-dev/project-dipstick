# Security Review — `facilitator-error-states-e2e` implementation

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope reviewed:** `packages/backend/src/routes/__tests__/facilitator-error-states-integration.test.ts`, `packages/backend/src/routes/__tests__/facilitator-error-state-2-restricted-role.test.ts`, cross-checked against `packages/backend/src/auth/audit-logger.ts`, `packages/backend/src/routes/facilitator-sessions.ts`, `packages/backend/src/routes/content.ts`, `packages/backend/migrations/8_audit_log.sql`, `packages/backend/migrations/8_rollback.sql`, `.github/workflows/integration.yml`, `packages/backend/vitest.config.ts`, and `tasks.md` task 5.1's finding. This is a follow-up to my design review (`design-review-security.md`), verifying the two should-fix items landed and independently assessing the implementer's task-5.1 discovery.

## Verdict up front

Both of my design-stage should-fix items are resolved correctly in the implementation. The Error State 4 raw-body check is present and correct. The restricted-role mechanism is a genuine, well-executed mitigation with one residual low-severity gap I'm noting for the record, not blocking. Item 4 — the audit_log finding — is the substantive result of this review: it is **more severe than an audit-trail gap**, and I am escalating it beyond how task 5.1 currently frames it.

## 1. Restricted-role mechanism (Error State 2)

This is a correct implementation of what I asked for at design stage, with good engineering discipline:

- **Not a REVOKE against `dipstick`.** The file's own header comment (lines 21-36) documents exactly the reasoning I raised in review — `dipstick` is a superuser and a REVOKE against it would silently no-op. It creates a dedicated `dipstick_restricted_probe` role instead, scoped to `SELECT` on exactly `users`/`team_memberships`/`sessions`, deliberately excluding `session_topics`. This is the right mechanism.
- **Teardown reliability.** The privileged setup/insert/override/call sequence runs inside `try`, and `finally` (lines 241-255) restores `DATABASE_URL` first, then deletes fixture rows, then drops the role — in that order, which is correct (restore the connection string before doing more privileged work, in case anything downstream depends on it). A crash *inside* the `try` block before `finally` executes (process kill, unhandled rejection escaping the test runner) would still leave the role behind — no `try`/`finally` construct can fully close that gap — but the code defends against exactly that with `dropRestrictedRoleIfExists`'s existence-check-then-`DROP OWNED BY`+`DROP ROLE` pattern, called both at the start of the test (self-heals a prior crashed run) and in `finally`. This is the right shape: self-healing on the next run rather than assuming the `finally` is infallible. Task 7.1's separate verification test (lines 258-268) independently confirms the role is gone after a full run, which is good practice — it converts "we believe teardown works" into an assertion.
- **`DROP ROLE` mechanics.** The comment at lines 113-122 correctly identifies that `DROP ROLE` alone fails once `GRANT` has created `pg_shdepend` entries, and uses `DROP OWNED BY` first. This is correct Postgres behavior and I verified it's necessary — a plain `DROP ROLE IF EXISTS` after a `GRANT SELECT` does fail with "cannot be dropped because some objects depend on it."
- **Fixed role name collision safety — residual gap, not a blocker.** `RESTRICTED_ROLE = "dipstick_restricted_probe"` is a fixed name, not per-test-run unique (unlike every other fixture in this change, which uses `crypto.randomUUID()`). This file is deliberately isolated as its own single-test file (task 1.5), and CI (`.github/workflows/integration.yml`) provisions a fresh, ephemeral `postgres:16-alpine` service container per job — so two *CI* runs never share a database and can't collide on the role name. The residual case is local development: `docker compose up` gives every developer machine one long-lived Postgres instance, and if this file's test is run twice concurrently against that same instance (e.g., two terminals, or a watch-mode rerun overlapping a manual run), the second `CREATE ROLE` can race the first. The self-healing `DROP ROLE IF EXISTS`-equivalent at the top of the test reduces the blast radius to a loud failure (role-already-exists error) rather than silent data corruption — this fails safe, not open. I'm noting it for the record; I don't consider it a blocker given the isolation already in place and vitest's file-level process isolation (see §3) meaning this is not a within-CI-run risk.

**Conclusion:** this fully addresses my design-stage should-fix item 2. Well done.

## 2. Error State 4 non-disclosure — raw body check

Confirmed present and correctly matches the rigor bar I required. `facilitator-error-states-integration.test.ts` lines 512-520:

```js
const rawBody = res.body;
expect(rawBody).not.toContain(teamAId);
expect(rawBody).not.toContain(teamAName);
expect(body.error.message).not.toContain(teamAId);
expect(body.error.message).not.toContain(teamAName);
```

This checks `res.body` — the raw, unparsed HTTP response string — not only the parsed `body.error.message` field, exactly matching `facilitator-error-states.test.ts:707-734`'s existing pattern I cited at design stage. It goes one step further than the mocked suite by asserting against `teamAName` (a real, randomized fixture value) in addition to `teamAId`, which is a meaningful strengthening given this is now a real Postgres round trip rather than a hand-authored mock response. This fully addresses my design-stage should-fix item 3 (the optional strengthening) as well as confirms the raw-body check itself.

## 3. DATABASE_URL override/restore — leak risk assessment

I checked three distinct leak vectors:

- **Leaking the restricted connection into other test files.** `packages/backend/vitest.config.ts` has no `pool`/`poolOptions` override, so vitest runs on its default (`forks` — one OS process per test file in recent vitest versions), which gives full `process.env` isolation between files. The restricted-role file's own header comment (lines 12-19) correctly identifies this as the primary safety mechanism and treats its own `finally`-block restore as "a second, independent safeguard" rather than the sole protection — that's the right posture; don't rely on a single control for an env-var mutation like this. I have no findings here.
- **Leaking the privileged `dipstick` connection string in test output/logs.** Both files' unreachable-infra warning (`console.warn`) redacts the password with `DATABASE_URL.replace(/:[^:@]+@/, ":****@")` before logging. I checked whether anything else in either file or in `db.ts`/`content.ts` logs the connection string un-redacted — it doesn't; `db.ts` passes `connectionString` straight into `pg.Pool` with no logging. No finding.
- **Reflecting the restricted role's permission-denied error back to the client.** I checked `content.ts`'s catch block (lines 325, 394) directly — the caught error is bound as `_err` and discarded; the response body is the fixed `historical_data_unavailable` shape, never the underlying Postgres error text. This matters because a restricted-role permission error's message text (`permission denied for table session_topics`) would, if ever reflected, disclose internal schema details to a client. It isn't. No finding — this is the same "authorization/error handling doesn't leak internals" property I'd want regardless of this test's existence.

**Conclusion:** no leak risk found in any of the three vectors I checked for this pattern.

## 4. Audit log gap (tasks.md 5.1) — security/compliance severity assessment

I traced this beyond what task 5.1 documents, because the finding as written ("audit_log doesn't exist after any fresh migration run") undersells what I found once I checked *how* `audit_log` is written to in production code.

**The finding is not "the audit trail is silently thin." It's "the audited actions themselves fail."**

`emitAuditEvent` (`audit-logger.ts`) is the *structured-log* audit path — a pino `logger.info()` call, independent of the database. It is not what's affected by the missing table. The affected writes are the `INSERT INTO audit_log` statements in `facilitator-sessions.ts`, and I confirmed by reading the handlers directly that every one of them runs **inside the same explicit `BEGIN`/`COMMIT` transaction as the state-changing action it's auditing** — reveal (~line 1042), topics/advance (~line 613, and the wrap-up-entry branch ~line 1351), complete (~line 1212/1300), and the draft→lobby transition (~line 337). The code comment at line 544 states the design intent explicitly: *"Both writes commit together in the same transaction or neither does."* Every one of these blocks has a `catch` that issues `ROLLBACK`.

Given that: if `audit_log` does not exist, the `INSERT INTO audit_log` statement throws a real Postgres error (`relation "audit_log" does not exist`) inside the transaction, the `catch` rolls the whole transaction back, and **the reveal, the topic advance, or the session completion itself fails** — not just its audit record. This is not an audit-visibility gap. It is a functional-availability bug wearing an audit-log costume, and I traced *why* it's existed undetected:

- **This is not a new bug introduced by this change.** `migrations/8_rollback.sql` was added in commit `9536d32` (PR #14, "Establish a Manager/Team Relationship (TEAM-006)", 2026-07-07) — over two months before today (2026-09-10) — in the *same PR* that added `8_audit_log.sql`. `node-pg-migrate` treats every `.sql` file in the migrations directory as an independently runnable migration and applies all pending ones in file order on every `db:migrate` invocation; it has no concept of "this one is opt-in." So from the moment PR #14 merged, `8_rollback.sql` has run automatically immediately after `8_audit_log.sql` on **every single migration run**, fresh or incremental — there is no path through this migration history that leaves `audit_log` in place.
- **Why CI never caught it:** I read `.github/workflows/integration.yml` — it provisions a fresh, ephemeral `postgres:16-alpine` service container per job and runs `npm run db:migrate` against it every time, so CI's database has never had `audit_log` survive a migration run since PR #14 merged. But no *existing* real-infra test exercised a code path that writes to it: `ws-pubsub-integration.test.ts` never calls reveal/advance/complete, and the existing mocked `facilitator-error-states.test.ts` uses `vi.mock` for `db.query`, so no real `INSERT INTO audit_log` was ever attempted in CI until this change's new tests ran. That is a plausible, coherent explanation for why a two-month-old bug of this severity has never shown up red in a pipeline.
- **What I can't confirm from this codebase alone, and consider the urgent open question:** whether this has also been silently breaking reveal/advance/complete for any team actually using a deployed environment. If any environment (staging or production) has had `npm run db:migrate` executed against it since 2026-07-07 — whether that was a fresh provision or an incremental run against a database that already had migrations 1-7 applied — `8_rollback.sql` would have run as part of that same migration invocation (it doesn't wait for a separate deploy), meaning: (a) if the environment already had `audit_log` with real records in it (e2. TEAM-006 manager-association audit rows), **those records were permanently destroyed** — `8_rollback.sql` line 74 is an unconditional `DROP TABLE audit_log`, and its own header (lines 21-23) says so explicitly: *"This rollback destroys all TEAM-006 audit records and all non-role-change audit records written to audit_log since migration 8 ran"*; and (b) every reveal/topics-advance/complete call in that environment since that migration ran would have been failing outright with a 500-class error, not silently degrading.

**Severity, from a security/compliance standpoint, distinct from the architect's engineering-process framing:**

1. **Audit trail (compliance) impact — Severe.** This affects every audit_log-backed control this codebase has built and asserted was in place: TEAM-006 manager-establishment audits, EM read-access audits (`em.*`), Application Admin audits (`admin.*`, including the session-content-denial audit from the archived `enforce-access-control-on-team-content` change's task 3.4/5.11 that this review's requester asked me to assess directly), and every `session.*` WebSocket-triggered audit row from the `websocket-delivery-time-authorization` change. All of these were represented in their respective design docs and specs as delivered, real controls. If any environment has been running against a post-PR#14 migration state, **none of them have actually been recording anything** — the table they write to hasn't existed. This is precisely the auditability failure mode I flagged as a foundational concern in my persona: *"An application without meaningful audit logging is an application where incidents are harder to detect, harder to scope, and harder to explain to anyone who asks afterward."* Here it's worse than absent — it was represented as present and verified, repeatedly, across multiple prior changes, none of which had a real-infra test to catch it.
2. **Data integrity impact — Severe, and irreversible if it already occurred.** Any environment where `8_rollback.sql` executed against a database that already held real audit_log rows has permanently lost those rows. This can't be fixed going forward; it can only be prevented from recurring and assessed for what's already gone.
3. **Availability impact — Severe, if any live environment has hit this.** Reveal, topic-advance, and session-complete are core facilitation actions. If they've been failing in any environment reachable by real facilitators since July, that's a production-availability incident that has apparently gone unreported — which itself is worth asking about directly, since a 500 on "reveal" during a live session is the kind of thing a facilitator would have complained about loudly.

**What I recommend, distinct from and in addition to the engineering fix (renaming/relocating `8_rollback.sql` so it isn't auto-discovered):**

- Treat this as urgent, not as a routine follow-up ticket. Before anything else, someone needs to check `pgmigrations` in every real (non-CI) environment — staging and production, if either exists — to determine (a) whether `audit_log` currently exists, and (b) whether `8_rollback.sql` has already run there. If it has, this is an incident: assess what was destroyed (query `pgmigrations` timestamps to bound the window), and separately determine whether reveal/advance/complete have actually been failing for real users during that window, or whether some other factor (e.g., these environments were never migrated past migration 7, or the app has not yet had live facilitator traffic) has coincidentally masked it.
- This is exactly the "internal tool with no security review catches the real-world consequence" pattern I've seen before — the fix belongs to engineering, but the *investigation* of what already happened belongs with security/compliance, not just a tasks.md follow-up note.

I want to be precise about scope: I am not asking this test-only change to fix the migration bug — task 5.1 correctly identifies that as out of scope for a test-only PR, and I agree with that scoping decision. What I'm flagging is that the *severity assessment* attached to this finding needs to be corrected before the team decides how urgently to act on it — "the audit table doesn't exist after a fresh migration" undersells a bug that also silently deletes existing audit data and breaks core session actions in any environment where it runs against a non-empty database.
