# Engineering Review — Participant Readiness View
**Reviewer:** Marcus Oyelaran, Senior Full Stack Engineer
**Focus:** Implementability, boundary cleanliness, technology fit, hidden coupling, missing error paths

## Verdict: Not yet implementable as written. Two findings are blocking — both are boundary bugs, not scope disagreements — plus one open decision (D2) I want to weigh in on before it's made.

I read this against `packages/frontend/src/realtime/connectionHealth.ts`, `packages/frontend/src/pages/DraftSessionHost.tsx`, `packages/frontend/src/pages/SessionLobbyPage.tsx`, `packages/backend/src/realtime/websocket-routes.ts`, `packages/backend/src/realtime/ws-event-dispatcher.ts`, `packages/backend/src/auth/session-subscriber-access-helper.ts`, `packages/backend/src/routes/sessions.ts`, and `packages/shared/src/types/realtime.ts`. Most of this design is exactly the kind of thing I want to see — it reuses existing primitives instead of inventing new ones. The two findings below are the places where "reuse the existing primitive" was stated as the plan but the primitive's actual behavior, read closely, doesn't do what the plan needs it to do.

## Finding 1 (Blocking) — `participant_joined` carries no name, but the row it's supposed to update usually doesn't exist yet

`ParticipantJoinedPayload` is `{ sessionId, userId, joinedAt }` (`packages/shared/src/types/realtime.ts:141-145`). No display name.

Design.md D3 and tasks.md 3.2 describe the live-update behavior as "add-or-clear, never delete-and-reinsert" — `participant_left` marks a row disconnected, `participant_joined` "clears the marker on the existing row." That phrasing assumes a row is already there to be found. But the entire reason this change exists (proposal.md's Why section, verbatim: "an empty roster that fills in live as Engineers join") is the case where a `participant_joined` event is the *first* thing the Facilitator's client ever hears about that `userId`. There is no existing row to clear the marker on. The hook has to insert a new row — and the only data it has to insert is a UUID. It cannot render a name, because the event that's supposed to drive "updates in real time as participants join" (spec.md, `participant-readiness-roster`) doesn't carry one.

This isn't a hypothetical edge case sitting off to the side of the happy path — it *is* the happy path this feature was scoped around. A first implementation that follows D3/task 3.2 literally will either render a blank/UUID row for every first-time joiner, or the engineer building it will discover this gap mid-implementation and have to make an unreviewed call about how to fill it.

Two real fixes, and design.md should pick one rather than leaving it for tasks.md to discover:
1. **Extend `ParticipantJoinedPayload` with `displayName`.** Touches a shared, already-shipped event contract (FR-2.5, issue #94) — worth checking whether anything else consumes that payload shape before widening it, but it's a small, additive change and keeps the roster fully event-driven with no extra round trip.
2. **On `participant_joined` for an unrecognized `userId`, the hook re-fetches the D5 REST endpoint instead of trying to construct a row from the event alone.** No shared-type change, reuses the endpoint that already has to exist, and "updates without requiring a page refresh" (the spec's actual wording) still holds — a background re-fetch triggered by a WS event isn't a page refresh. Slightly more chatter on a burst of joins (each first-time join fetches the full roster), which is fine at this feature's scale.

I'd take option 2 — it's the smaller diff and doesn't touch a contract another consumer might depend on — but either is fine as long as it's a stated decision, not an implementation-time discovery. Recommend adding this as D3a (or folding it into D3) before this goes to tasks.

## Finding 2 (Blocking) — `DraftSessionHost` gaining "its own WebSocket subscription" as literally described will produce a reconnection storm during `draft` status

This is the one I'd have flagged hardest in the original architecture review, because it's precisely the failure mode I built `connectionHealth.ts` to guard against, and this design point-blank walks into it.

Here's the chain:
- `DraftSessionHost` renders two branches from one component function: `draft-control-view` when `currentSessionState === 'draft'`, `live-readiness-view` otherwise (`DraftSessionHost.tsx:225-297,297-357`).
- Per the AC Reconciliation section of proposal.md, the `draft`-status landing state is not a rare transient — for the existing-team flow it's the *normal* landing state, deliberately, until the Facilitator clicks "Open the room."
- `evaluateSessionSubscriberAccess`'s Path 3 (facilitator grant) explicitly excludes `draft` from `LIVE_FACILITATOR_STATUSES` (`session-subscriber-access-helper.ts:55`, `["lobby", "pre_session", "active", "wrap_up"]`). A facilitator has no participant row either, so Path 1 doesn't apply. **A facilitator has zero valid grant paths while the session is `draft`.**
- `websocket-routes.ts:101-104` runs that check at subscription time and closes with `CLOSE_UNAUTHORIZED` (`STALE_SIGNAL_CLOSE_CODE`) immediately if there's no grant.
- `connectionHealth.ts` treats `STALE_SIGNAL_CLOSE_CODE` exactly like a raw network failure — it is deliberately disclosure-blind and only special-cases `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (`connectionHealth.ts:20-23,220-223`). Every other close/error, including this one, drives `beginOrContinueUnknownEpisode()` → the exponential-backoff retry loop.
- `useConnectionHealth`'s setup effect runs once, with `[]` dependencies, and never re-evaluates whether the session status has changed (`connectionHealth.ts:301`). If the hook is invoked unconditionally near the top of `DraftSessionHost`, mirroring how `SessionLobbyPage` calls it today (`SessionLobbyPage.tsx:148-151`), it opens a socket on mount — including during the `loading` state and during `draft` status — and once that socket starts getting rejected, it retries forever, because nothing in the hook's lifecycle is watching `currentSessionState`.

Net effect: every Facilitator sitting on the (normal, common) draft-control-view gets a client silently hammering `/ws/sessions/:sessionId` on exponential backoff, indefinitely, getting rejected every time, until they click "Open the room." That's a self-inflicted reconnection storm against our own authorization boundary — not a third-party failure mode, one we'd be building deliberately if design.md's current wording ("`DraftSessionHost` reuses the same `useConnectionHealth` pattern... open the session-scoped socket, attach a `message` listener") is followed as a flat addition to the existing component body.

The fix is a real one, not a tweak: the WS subscription can't be called unconditionally in `DraftSessionHost`'s top-level function scope the way `SessionLobbyPage` does it, because `SessionLobbyPage` doesn't have a pre-lobby branch with no legitimate grant. `DraftSessionHost` does. React's rules of hooks mean you can't conditionally *call* `useConnectionHealth` — so the connection has to be conditionally *mounted*: extract the live-readiness branch into its own child component that owns the `useConnectionHealth` call, and only render that child once `data.currentSessionState !== 'draft'`. Mount/unmount becomes the gate, not a status check inside the hook. This is a normal React pattern, but it's a structural change to how `DraftSessionHost` is organized today (one function, two early-return branches, not two components), and design.md should say so explicitly rather than leaving "gains its own WebSocket subscription" to be read as a one-line addition. I'd rather this be named now than have someone build the naive version, pass all the roster tests (which won't catch this — they don't sit and watch retry behavior for a `draft`-status session), and have it show up as log noise and needless connection churn in production.

## Note on D2 (not blocking — design.md already defers this correctly, but here's a fact worth weighing before the choice is made)

Reading the two candidate mechanisms against the actual code:

**Option 1 (auto-upsert at WS-connect time)** composes cleanly with what's already there. `evaluateSessionSubscriberAccess`'s Path 1 doesn't gate on session status at all — it only checks for an existing `session_participants` row plus active team membership plus non-EM (`session-subscriber-access-helper.ts:155-168`). If the upsert (with the EM dual-check replicated inline, matching `sessions.ts`'s existing `ON CONFLICT (session_id, user_id) DO NOTHING` pattern) runs immediately before the `evaluateSessionSubscriberAccess` call at `websocket-routes.ts:101`, Path 1 picks up the freshly-inserted row on the very same request with **zero changes to `evaluateSessionSubscriberAccess` itself**. That's a clean boundary — the authorization helper stays a pure read, the write happens once, right before the read that depends on it, in the one place that already owns this connection's lifecycle.

**Option 2 (relax the REST gate + add a frontend caller)** has a race option 1 doesn't: `useConnectionHealth`'s `connect()` opens the socket unconditionally on mount, in the same render pass as everything else — there's no existing "wait for this POST to resolve, then open the socket" sequencing anywhere in this codebase's WS-page pattern (`SessionLobbyPage.tsx:148-151`, `SessionConnectionHost.js`). A frontend caller that fires `POST /participants` on mount without the WS connection waiting on it will, on a slow or contended request, hit the exact same "no grant yet" `CLOSE_UNAUTHORIZED` → retry-storm path as Finding 2, for every first-time joiner, every time. It's avoidable (await the POST before calling `useConnectionHealth`'s `connect`), but that's new sequencing discipline this codebase doesn't currently have an established pattern for, and it's asymmetric with the facilitator side, which has no REST call to wait on at all.

I'm not asking design.md to pick a mechanism here — D2 is right that this belongs behind its own security review, not a default. I'm flagging that Option 1 is the lower-risk implementation from a "boundaries fail predictably" standpoint, and whoever runs the security review in tasks.md 1.1-1.4 should have this tradeoff in front of them, not just the authorization-surface question D2 already names.

## What's solid

- **D5's REST endpoint** is a clean, minimal addition. `users.display_name` joined against `session_participants`, filtered by the same EM dual-check already established in `sessions.ts` and `session-subscriber-access-helper.ts` — no new pattern, no new join shape, directly implementable from existing SQL in this file.
- **Shared roster component/hook, one implementation** — this is exactly the discipline `connectionHealth.ts` already enforces on itself (`// THE CENTRAL RULE... never fork it`), and D1 is explicit that the roster hook is host-agnostic (takes a socket + fetch function, doesn't know which page it's in). Good precedent, low risk.
- **`userId`-keyed rows, never deleted** — matches the schema exactly (`session_participants` has no `DELETE` anywhere in the backend, confirmed), and the disconnected-marker behavior correctly reuses `connectionHealth.ts`'s disclosure-blind posture rather than inventing a second one.
- **Non-goals are genuinely held out of the code paths that would tempt scope creep** — no quorum counter, no removal control — and the spec.md scenarios for each are concrete and testable as written.

## Bottom line

Two blocking findings, both about the gap between "reuse the existing thing" as a design statement and what the existing thing actually does when you look at its code: the WS event this design depends on for live updates doesn't carry the data the roster needs, and the WebSocket-subscription reuse pattern being proposed for `DraftSessionHost` will self-DoS against our own auth check during a status this codebase already treats as a normal, common landing state. Both are fixable without changing the shape of the feature — Finding 1 needs a stated decision (extend the payload, or re-fetch on unknown `userId`), Finding 2 needs `DraftSessionHost`'s live-readiness branch restructured into its own mounted/unmounted child component rather than a flat addition to the existing function body. I'd want both resolved in design.md, not discovered during tasks 4.1-4.3, before this moves to implementation.
