## Context

`02 - Session Setup - Use Cases.md`'s "View Participant Readiness Before Session Begins" exists so the Facilitator can judge when to start a session — a waiting-room roster, not the live-voting grid (`FacilitatorReadinessGrid.tsx`, issue #33's territory, confirmed by reading it: its state names — `connected-locked-in`, `disconnected-voted`, etc. — are all voting concepts that don't exist pre-session, and its marker reflects the *facilitator's own* connection health, not a per-participant signal).

Two facilitator-facing pages currently render a `lobby`-status waiting screen with no roster, and they are not symmetric:
- **`DraftSessionHost.tsx`** (`live-readiness-view`, `session-creation` capability) — the Facilitator's durable landing page after creating a session (`session-lobby-routing-gap` D1). Pure REST fetch-on-mount today; no WebSocket connection of any kind (`session-lobby-routing-gap` D3 named building one "real work this change does not take on").
- **`SessionLobbyPage.tsx`** (`lobby` branch, `pre-session-action-item-review` capability) — has a working `useConnectionHealth` WebSocket subscription and already listens for `session_state_change`, but a Facilitator only lands here via a navigate-link from `DraftSessionHost`, not as their normal landing page.

The use case's own Main Flow Addendum ("Create Session for Existing Team," step 10) describes the transition into this view as happening in place, without navigation, on the page the Facilitator is already on — that page is `DraftSessionHost`. Building the roster only where the WebSocket plumbing happens to already exist (`SessionLobbyPage`) would satisfy the acceptance criteria's literal wording while leaving the page the Facilitator actually watches roster-less.

Separately, and more materially: no first-time-joining Engineer can appear in any roster today. `POST /api/v1/sessions/:sessionId/participants` (`packages/backend/src/routes/sessions.ts:42-145`) is the only code that inserts a `session_participants` row, and it 422s unless `status === 'active'`; it has zero frontend call sites. `evaluateSessionSubscriberAccess`'s Path 1 (the sole grant path for a non-facilitator session-scoped WebSocket connection) requires a pre-existing `session_participants` row — no row, no grant, `CLOSE_UNAUTHORIZED`, and `GET .../action-items-review` returns `404`. This is `session-lobby-routing-gap` Decision D7, confirmed still open. It is not a nice-to-have: the use case's core scenario (an empty roster that fills in live as Engineers join) cannot occur for any first-time joiner without it.

## Goals / Non-Goals

**Goals:**
- A Facilitator-only, live-updating roster of who has joined, visible on both `DraftSessionHost` and `SessionLobbyPage` during `lobby` status, built as one shared component/hook — not two independently-drifting implementations (the same "sole implementation, no forking" discipline `connectionHealth.ts` already holds itself to).
- Close the `session_participants` registration gap (D7) so a first-time-joining Engineer can actually appear in the roster, with the Engineering Manager exclusion check preserved exactly wherever the new registration point lands.
- A stable list: a participant's row identity and position do not change on disconnect/reconnect (including a simple page refresh).

**Non-Goals:**
- Vote status, readiness-to-vote signals, or quorum enforcement — that's `FacilitatorReadinessGrid`'s (#33) territory, and a distinct component's job. No "N of M expected" counter — the application has no roster of expected attendees, and a counter invites quorum-pressure this view isn't meant to create. The resulting "who's missing" cognitive-load gap is accepted, not solved.
- Participant-visible roster. Engineers see an unchanged waiting screen — no names, no count.
- Facilitator-initiated removal of a participant from the roster (source Out of Scope; disconnected-and-held rows make this a plausible-sounding ask mid-implementation — it stays out).
- Visual continuity of the roster across the `lobby → active` transition. The roster unmounts (or is superseded by `FacilitatorReadinessGrid`) when the session advances past `lobby`; issue #33 owns what the Facilitator sees next.
- Surfacing a blocked/failed join attempt to the Facilitator. Named, explicit deferral (see Risks) — not solved by this change.

## Decisions

**D1 — Roster renders on both `DraftSessionHost` and `SessionLobbyPage`, via one shared component/hook; `DraftSessionHost` gains its own WebSocket subscription as in-scope work, mounted only once session state leaves `draft`.**
Resolves proposal.md's open questions 1 and 4 (`exploration-notes.md` §9). `DraftSessionHost` reuses the same `useConnectionHealth` pattern `SessionLobbyPage` already demonstrates: open the session-scoped socket, attach a `message` listener alongside whatever `session_state_change` handling it already needs. The roster component/hook itself is host-agnostic — it takes a socket and an initial-fetch function, and doesn't know which page it's mounted in. This is real, non-trivial work (`session-lobby-routing-gap` D3 named it exactly that when deferring it), but shipping the roster only on `SessionLobbyPage` would answer the acceptance criteria's letter while leaving the page the Facilitator is actually looking at during the wait roster-less — not an acceptable reading of "done" for this change, per both the Internal Champion's and the Facilitator persona's review of exploration.
*Alternative considered:* `SessionLobbyPage`-only, with `DraftSessionHost` as a fast-follow. Rejected as the default outcome — not because the cost (new WebSocket-subscription work) isn't real, but because leaving it as a "someday" fast-follow after the cheaper path ships is exactly the kind of scope erosion this design stage exists to prevent. If implementation discovers the `DraftSessionHost` subscription is materially riskier than expected, that is a mid-implementation escalation, not a reason to have defaulted to the cheap path here.

*Correction (engineering review, Finding 2) — the subscription cannot be called unconditionally, or it self-DoS's against our own auth boundary:* `DraftSessionHost` renders two branches from one component function today — `draft-control-view` when `currentSessionState === 'draft'`, `live-readiness-view` otherwise (`DraftSessionHost.tsx:225-297,297-357`). Per the AC Reconciliation section, `draft` status is not a rare transient for the existing-team flow — it is the normal landing state until the Facilitator clicks "Open the room." But `evaluateSessionSubscriberAccess`'s Path 3 (facilitator grant) excludes `draft` from `LIVE_FACILITATOR_STATUSES` (`session-subscriber-access-helper.ts:55`), and a facilitator has no `session_participants` row either, so Path 1 doesn't apply — **a facilitator has zero valid grant paths while the session is `draft`.** `websocket-routes.ts:101-104` closes with `CLOSE_UNAUTHORIZED` (`STALE_SIGNAL_CLOSE_CODE`) at subscription time with no grant, and `connectionHealth.ts` is deliberately disclosure-blind about close codes other than `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (`connectionHealth.ts:20-23,220-223`) — it treats this rejection like a raw network failure and drives `beginOrContinueUnknownEpisode()`'s exponential-backoff retry loop, indefinitely, because the hook's setup effect runs once on mount (`connectionHealth.ts:301`) and never re-evaluates session status. Calling `useConnectionHealth` unconditionally near the top of `DraftSessionHost` — mirroring how `SessionLobbyPage` calls it today (`SessionLobbyPage.tsx:148-151`) — would mean every Facilitator sitting on the (normal, common) draft-control-view gets a client silently hammering `/ws/sessions/:sessionId` on exponential backoff until they open the room: a self-inflicted reconnection storm against our own authorization boundary.

React's rules of hooks mean the call can't be conditional; the *mount* has to be. **Fix, stated explicitly so it is not read as a flat addition to the existing component body: extract the live-readiness branch (currently `live-readiness-view`, `DraftSessionHost.tsx:225-297`) into its own child component that owns the `useConnectionHealth` call and the roster hook, and render that child only when `data.currentSessionState !== 'draft'`.** Mount/unmount is the gate, not a status check inside the hook or a branch inside a single always-rendered component. This is a structural change to how `DraftSessionHost` is organized today (currently one function with two early-return branches, not two components) — tasks.md 4.1 states this restructuring explicitly rather than leaving "gains its own WebSocket subscription" to be implemented as a one-line addition.

**D2 — The registration gap (D7) closes via [mechanism TBD by implementation, gated on its own security review] — auto-upsert at WS-connect/join-redemption time, or relax the REST gate plus a frontend caller.**
Both options were named in exploration (§9.2) as real, competing authorization-boundary designs:
1. Auto-create/upsert a `session_participants` row when a session-scoped WebSocket connection is established (or at join-link redemption), regardless of session status.
2. Relax `POST .../participants`'s `status === 'active'` gate to also accept `lobby`/`pre_session`, and add a frontend caller (at join-link redemption, or on `SessionLobbyPage`/`DraftSessionHost` mount for a participant).
This design intentionally does not pick between them here. Per D7's own recommendation, whichever option is chosen SHALL receive a dedicated security review before merge — the same rigor `evaluateSessionSubscriberAccess` originally received — not an expedited pass riding along on this change's roster work. **This review is a blocking task in tasks.md, not an optional follow-up.**
*Consequence stated plainly:* this is the one place in this design where "how" is deliberately left open past design.md. That is a scope decision, not an oversight — closing an authorization boundary correctly is worth the extra review cycle even though it costs this change a fully-nailed-down implementation plan on the first pass.

*Correction (security review, Finding 1):* the design's original wording instructed implementers to "replicate `session-participation`'s dual-check EM-exclusion pattern... exactly," pointing at `sessions.ts:86-129`'s existing query. That query is itself incomplete: it `LEFT JOIN`s `team_memberships` and rejects only on `global_role === 'engineering_manager' || membership_role === 'engineering_manager'`, so a user with **no** `team_memberships` row for the session's team at all gets `membership_role = null` and passes — a non-member can register as a participant. `evaluateSessionSubscriberAccess` Path 1 (`session-subscriber-access-helper.ts:155-161`) gets this right: it additionally requires `membership_exists && membership_removed_at === null`. "Replicate exactly" is corrected to mean **replicate `evaluateSessionSubscriberAccess` Path 1's full condition set** — `membership_exists`, `membership_removed_at IS NULL`, `global_role !== 'engineering_manager'`, `membership_role !== 'engineering_manager'` — not `sessions.ts`'s current query. `sessions.ts:86-129` (`POST .../participants`) and `sessions.ts:233-279` (`POST .../lock-in`'s identical role check) carry the same gap and SHALL be fixed in the same pass as D2's implementation, since D2 already requires touching this exact area. This is a correctness fix to a pre-existing gap, not a change to D2's own scope — see tasks.md 1.3/1.4.

*Audit logging (security review, Finding 3, Medium):* `POST .../participants` currently writes no `audit_log` row on success or EM-rejection, unlike its neighbors (`lock-in`'s `session.vote_submitted`, join-link redemption's `join.link_redeemed`/`join.link_rejected` in `join-links.ts`). Whichever mechanism D2 chooses SHALL emit an audit event at the registration point, at minimum `session.participant_registration_rejected` on EM-rejection, following `join-links.ts`'s existing transactional pattern (INSERT + audit row in one transaction, `emitAuditEvent` fired only after commit). Auditing successful registration too is worth doing in the same pass rather than as a follow-up.

**D3 — Roster rows are keyed by `userId`; `participant_left` marks disconnected, `participant_joined` clears the marker on the existing row.**
`participant_joined`/`participant_left` (already shipped, FR-2.5/issue #94) are connection-lifecycle events, not durable-state events — a participant refreshing their own tab emits `left` immediately followed by `joined` on reconnect. A naive delete-on-left/insert-on-joined implementation would flicker a still-present Engineer out of the list and back in. Keying by `userId` and treating `left` as "mark disconnected" rather than "remove" avoids this, and is consistent with `session_participants` rows never being deleted (confirmed: no `DELETE FROM session_participants` anywhere in the backend) — "restored from the session record" on refresh (the AC's own requirement) falls out naturally as long as the initial roster fetch reads that table, not connection-registry state.
*Known edge case, accepted:* per `websocket-specification`'s own documented behavior, `participant_joined`/`participant_left` are **not deduplicated by `userId`** — a participant with two simultaneous connections (two browser tabs) produces one event pair per connection. Closing one of two tabs will mark that participant's row disconnected even though their other tab is still live, until that tab's own `joined`/reconnect event (if any) clears it, or until the row is corrected by the next full roster refresh. This is accepted as a known limitation for v1, not silently ignored: multi-tab presence accuracy is not a requirement this view makes, and the alternative (per-user connection counting) is meaningfully more backend state to introduce for a case the source use case doesn't ask about.

**D3a — `participant_joined` carries no display name; on an unrecognized `userId` the hook re-fetches D5's roster endpoint, rather than extending the shared WS payload contract.**
`ParticipantJoinedPayload` is `{ sessionId, userId, joinedAt }` (`realtime.ts:141-145`) — no display name. D3's "clears the marker on the existing row" phrasing assumes a row is already there, but the use case this change is scoped around (proposal.md's Why: "an empty roster that fills in live as Engineers join") is exactly the case where `participant_joined` is the *first* the Facilitator's client hears of that `userId` — there is no existing row, and the event alone gives the hook nothing renderable but a UUID. Two fixes were weighed: extending `ParticipantJoinedPayload` with `displayName` (touches a shared, already-shipped event contract, FR-2.5/issue #94), versus having the roster hook re-fetch D5's REST endpoint when `participant_joined` names a `userId` not already present in its local state. **Decision: the hook re-fetches on unrecognized `userId`.** It's the smaller diff, it doesn't widen a shared contract another consumer might depend on, and "updates without requiring a page refresh" (the spec's actual wording) still holds — a background re-fetch triggered by a WS event is not a page refresh. This means the roster hook needs the D5 fetch function available on every `participant_joined`, not only on mount; task 3.1 states this explicitly. Slightly more request volume on a burst of simultaneous first-time joins (each triggers a full roster re-fetch) is accepted at this feature's scale.

**D4 — Sort order: alphabetical by participant name.**
Resolves proposal.md's open question 5 (`exploration-notes.md` §9). Two defaults were proposed in review: join-order/earliest-first (pairs naturally with `userId`-keyed, never-reordered rows) and alphabetical (a name is always in the same visual position, like a seating chart). This is a facilitator-experience call, not a ritual-fidelity one — decided in favor of Priya Nair's (Facilitator persona) stated rationale: a Facilitator scanning the room for a specific name benefits more from a stable, predictable position than from an ordering that reflects join timing, which they have no independent way to verify anyway. The one hard invariant carries forward regardless of which default was chosen: a participant's position SHALL NOT change on disconnect or reconnect.

**D5 — New REST endpoint for the initial/refresh roster fetch; no existing response is extended.**
`FacilitatorSessionStateResponse` and `action-items-review`'s response both lack a participant field, and `action-items-review` itself is gated to `pre_session` only (409s during `lobby`, which is exactly when this view needs data). `session_registration_snapshot` is a per-connection recovery payload about one user's own state, not a roster. A new, purpose-built endpoint avoids overloading an endpoint whose gating and audience don't match this view's needs. It applies the same EM-exclusion filter `evaluateSessionSubscriberAccess` Path 1 applies, for consistency with D2/D7's registration-side enforcement — the read side and the write side of "who's a valid participant" must agree.

*Correction (security review, Finding 2) — who may call the endpoint, stated explicitly:* "the same grant `evaluateSessionSubscriberAccess` applies" described row-level content filtering (excluding an EM who somehow has a row) but left caller-side authorization ambiguous, and this codebase has two contradictory existing precedents for what "same grant" means on a facilitator-only view:
- **Wrong for this feature:** `GET .../action-items-review` (`facilitator-sessions.ts:969-1018`) accepts *both* `facilitator` and `participant` grants and differentiates only via an `isFacilitator` flag in the response body, filtered client-side. Correct for that endpoint (action items are legitimately shared content) — wrong here, because it would serve the full participant roster, including names, to any Engineer sitting in the session who calls the endpoint directly with their own valid cookie.
- **Right for this feature:** `dispatchParticipantJoined`/`dispatchParticipantLeft` (`ws-event-dispatcher.ts:310-354`) — the existing, shipped delivery logic for this exact data — explicitly checks `grant?.path === "facilitator"` and delivers to no one else.

The roster endpoint SHALL follow the `dispatchParticipantJoined`/`dispatchParticipantLeft` precedent, not the `action-items-review` precedent: call `evaluateSessionSubscriberAccess`, and reject (404, disclosure-blind, matching `facilitator-sessions.ts:978-988`'s and `sessions.ts:439-448`'s existing null-grant convention) any request where `grant?.path !== "facilitator"`. A `participant`-grant caller gets the same 404 as a caller with no grant at all — the roster must be unreachable by a participant grant at the server layer, not merely hidden in the UI. tasks.md 2.3 splits the "excludes a user who would fail session-subscriber authorization" test into two distinct cases: an EM who somehow has a row (row-level content filtering) and a legitimately-registered Engineer participant calling the endpoint directly (caller-level authorization) — these are different failure modes and a suite covering only the first could pass while the second gap ships.

*Disclosure-blind conventions (security review, Finding 4, Low):* `action-items-review` applies `applyTimingFloor()` and `Cache-Control: no-store` on every response path as a stated requirement from its own security review. The roster endpoint is materially the same shape — a facilitator-sensitive, session-scoped GET — and SHALL apply both conventions on every response path (200 and 404) for the same reason.

**D6 — Per-row status is list membership alone; the only per-row indicator is the disconnected marker.**
The source AC ("a status indicating they are present but the session has not yet begun") is satisfied by appearing in the list, undecorated — there is exactly one non-disconnected state pre-session, so an explicit "Present" badge would be redundant, not informative, and edges toward the attendance-taking posture this ritual deliberately avoids. The disconnected marker itself borrows `connectionHealth.ts`'s existing disclosure-blind principle (never distinguish cause — network drop, reauth, anything else — just show the fact). Final visual weight (color, size, placement) is explicitly not finalized here; it routes through Priya's usability review before implementation locks it in, per her standing offer.

## Risks / Trade-offs

- **[Risk] D2's registration-gap fix is an authorization-boundary change shipped without a fully specified mechanism in this document.** → Mitigation: intentional (see D2's consequence note); a dedicated security review is a blocking task before merge, not a follow-up, and the mechanism is now specified to replicate `evaluateSessionSubscriberAccess` Path 1's full condition set (membership-exists check included, per D2's correction), not `sessions.ts`'s incomplete query, plus an audit event at the registration point.
- **[Risk] Multi-tab presence inaccuracy (D3's accepted edge case)** could show a participant as disconnected while they're still present in another tab. → Mitigation: accepted for v1, bounded (self-corrects on next full refresh or on that tab's own reconnect), and not a requirement the source use case asks about.
- **[Risk] A blocked/failed join attempt is invisible to the Facilitator** — the roster can look complete-and-current while an Engineer is stuck on the `no-access` screen, which is arguably worse than an obviously-incomplete roster because it doesn't invite anyone to check. → Mitigation: named, explicit deferral for v1 (not a silent gap); worth a follow-up issue once D2's mechanism is chosen and real failure rates are observable.
- **[Risk] `DraftSessionHost` gaining a WebSocket subscription (D1) is genuinely new surface area**, not a copy of existing behavior — a bug here affects the Facilitator's primary landing page. → Mitigation: reuses `useConnectionHealth`'s existing, already-tested subscribe-before-fetch ordering pattern rather than inventing a new one; the roster hook itself is shared with `SessionLobbyPage`, so it is exercised on a page with existing test coverage too. The `draft`-status self-DoS failure mode (facilitator has no valid grant path while `draft`) is closed by D1's mount/unmount gate — the subscription lives in a child component rendered only once `currentSessionState !== 'draft'`, not by a status check inside the hook.
- **[Trade-off] The "who's missing" cognitive-load gap remains unsolved** (see Non-Goals) — the Facilitator still holds "who's expected" in their head. → Accepted; stated explicitly rather than implied-fixed by rejecting the quorum-counter alternative.
