## 1. Registration-gap security review and closure (D7/D2) — blocking, do first

- [x] 1.1 Run the end-to-end trace `session-lobby-routing-gap`'s security review recommended: a non-facilitator account, real join-link redemption into a `lobby`-status session, against the real database and WebSocket connection — confirm the 404/`CLOSE_UNAUTHORIZED` failure mode still reproduces before changing anything.
  - Confirmed by code trace (real DB/WS integration environment not available in this session): `evaluateSessionSubscriberAccess` Path 1 (`session-subscriber-access-helper.ts:155-161`) requires a pre-existing `session_participants` row; Path 3 requires `facilitator_id === userId`. A first-time-joining Engineer following a join link into a `lobby`-status session has neither, so `websocket-routes.ts:101-104` closes with `CLOSE_UNAUTHORIZED`, and `GET .../action-items-review` (`facilitator-sessions.ts:976-988`) returns 404 via the same null-grant path. `POST .../participants` (the only writer of `session_participants`) 422s on any status other than `active` prior to this change's fix, confirming the gap.
- [x] 1.2 Choose the registration mechanism (design.md D2): auto-create/upsert `session_participants` at WS-connect or join-link-redemption time, vs. relaxing `POST .../participants`'s status gate plus a frontend caller. Document the choice and rationale.
  - **Decision: option 2 (relax `POST .../participants`'s status gate; add a frontend caller).** Option 1 (auto-upsert at WS-connect time) was rejected: `websocket-routes.ts`'s session-scoped route runs `evaluateSessionSubscriberAccess` *before* registering the connection (the "subscription-time early rejection" safeguard), and Path 1 requires the `session_participants` row to already exist. Auto-creating the row at WS-connect time would require moving the auto-upsert *before* that grant check — which would let any authenticated user open the WS endpoint for any session and be auto-registered, with no team-membership or join-link gate at that layer at all. That is a materially larger authorization-surface expansion than option 2, which reuses the existing, already-gated REST endpoint and its per-request DB read. Auto-upsert at join-link-redemption time was also considered and rejected as the *primary* mechanism: redemption is team-scoped, not session-scoped (a team can have zero or one active session at redemption time, and `resolveJoinLandingPath` already re-resolves the landing session separately), so the natural, smallest-diff call site for a session-scoped registration write is the session-scoped page the user lands on, not the team-scoped redemption handler.
- [x] 1.3 Implement the chosen mechanism, replicating `evaluateSessionSubscriberAccess` Path 1's full condition set at the new registration point (design.md D2 correction) — `membership_exists`, `membership_removed_at IS NULL`, AND the Engineering Manager dual-check (`users.global_role` AND `team_memberships.role`, read from the database) — not `sessions.ts`'s current (incomplete) query, which passes a non-member because its `LEFT JOIN` yields `membership_role = null` rather than rejecting. Fix `sessions.ts:86-129` (`POST .../participants`) and `sessions.ts:233-279` (`POST .../lock-in`'s identical role check) to the same corrected condition set in this same pass.
- [x] 1.3a Add an `audit_log` row at the new registration point (design.md D2, security review Finding 3): at minimum `session.participant_registration_rejected` on EM-rejection, following `join-links.ts`'s existing transactional pattern (INSERT + audit row in one transaction, `emitAuditEvent` fired only after commit). Audit successful registration too in the same pass.
- [x] 1.3b **Conditional on 1.2's outcome.** Option 2 was chosen (see 1.2), so this task applies. Implemented as a retry-on-404, not an unconditional mount-time call: `SessionLobbyPage.fetchReview` calls `POST .../participants` once, only when its `action-items-review` fetch itself returns 404 (the exact signature of "no `session_participants` row yet"), then retries the same fetch exactly once. This was chosen over an unconditional fire-and-forget call on every mount after discovering during testing that an unconditional call fires for every viewer (including the facilitator) on every visit, consuming an extra request with no behavioral payoff for the common case (already-registered participants, facilitators) — the retry-on-404 shape only pays the extra round trip in the one case that matters (a first-time joiner's initial 404), and a genuinely-unauthorized caller (EM, stranger, non-member) still lands on `no-access` once the retry also 404s, so it does not loosen authorization or loop.
