# Exploration Notes — Issue #47: View Participant Readiness Before Session Begins

**Explored by:** Devon Calloway (Internal Champion), from a ritual-fidelity and institutional-durability lens, backed by a direct trace of the current codebase.

**Revised:** 2026-09-29, incorporating feedback from Priya Nair's facilitator review and Marcus Delgado's BA review (`explore-review-facilitator.md`, `explore-review-ba.md`). What changed and what I declined to change is noted inline and summarized in §10.

## 0. Correction to the issue framing — read this first

The GitHub issue describes `SessionLobbyPage.tsx` as "a static 65-line stub — no participant list, no real-time updates." That was true before `pre-session-action-item-review` and `session-lobby-routing-gap` shipped. It is not true today. `SessionLobbyPage.tsx` is now 377 lines: it already fetches session state, already opens a session-scoped WebSocket via `useConnectionHealth`, already re-fetches on `session_state_change`, already renders a distinct `lobby` branch for facilitator vs. Engineer, and already has a `handleStartSession` control. The real-time plumbing this issue asks for is *closer than the issue text suggests* — but the specific thing that's missing (a roster of who has joined, updating live, with a disconnect indicator) is genuinely absent from both `SessionLobbyPage`'s `lobby` branch and `DraftSessionHost`'s `live-readiness-lobby` branch (see §2). The gap is real; the starting point described in the issue is stale. Whoever picks up design work should read the actual files, not the issue body, before scoping.

## 1. What this use case protects

`02 - Session Setup - Use Cases.md`, "View Participant Readiness Before Session Begins," exists so the Facilitator can judge when to start — that's the whole function. It is deliberately **not** the live-voting grid (issue #33's territory): no vote status, no readiness-to-vote signal, no quorum enforcement. It's a waiting-room roster: who's here, who dropped. That's a narrow, low-drama surface, and it should stay that way. The AC (line 414) marks this as something that "should be confirmed," and the source Notes (line 426) says it "warrants a decision" — so this is not settled by the source document itself, whatever confidence I stated in an earlier pass of these notes. It's a strong recommendation on my part, and Marcus is right to call out that I'd written it as already-decided. Recording it properly:

> **Decision:** The participant roster is Facilitator-only. Engineers see a waiting screen during `lobby` status with no participant names or count. **Rationale:** consistent with `SessionLobbyPage`'s existing `lobby` branch, which already withholds the Start Session control and any participant-identifying information from non-facilitators; a visible roster of peers turns a waiting-room utility into a social check-in surface, which is out of character for this ritual.

That decision needs a participant-side AC to go with it, since the source AC only describes what the Facilitator sees, not what the Engineer sees instead:

> - [ ] A participant (Engineer) viewing the session room during `lobby` status sees a waiting message only — no participant names, no participant count, no indication of how many others have joined.

I still think this is the right call — a leaked roster turns a "who's in the room" utility into something closer to a check-in log people perform for each other. I just want it carried into the proposal as a recorded decision with a rationale, not as an assumption that happens to match what these notes want.

## 2. Where the "static waiting room" problem actually lives

Two pages currently show a `lobby`-state waiting screen with no roster, and they are not symmetric:

- **`DraftSessionHost.tsx`** (`live-readiness-lobby` branch, lines ~247-269) — "Waiting for participants to join. Start the session when you're ready." Per `session-lobby-routing-gap`'s design.md (D1-D3), this is the facilitator's *normal, durable landing page* after creating a session — the page they're actually looking at 90% of the time during the wait. **It has no WebSocket connection of any kind.** It's pure REST fetch-on-mount. This was a deliberate, named deferral in that change (D3: "reproducing `SessionLobbyPage`'s subscribe-before-fetch WebSocket ordering... inside `DraftSessionHost` is real work this change does not take on").
- **`SessionLobbyPage.tsx`** (`lobby` branch, lines ~300-333) — "Session {sessionId} — waiting for the facilitator to start," with the `Start Session` button. This page *does* have a working WebSocket subscription (`useConnectionHealth`), already listens for `session_state_change`, and is where a facilitator lands if they follow a navigate-link from `DraftSessionHost` after `pre_session`, or (per D3's still-open follow-up) if a facilitator happens to be routed here directly. But in normal use, per D1-D3's own stated intent, the facilitator is *not* usually looking at this page during the lobby wait — they're on `DraftSessionHost`.

**This is the central design question for issue #47, and it's not answerable from the acceptance criteria alone:** if the roster is built only on `SessionLobbyPage` (cheapest path — the WS plumbing already exists there), it technically satisfies a literal reading of the AC but does not serve the facilitator in the moment they actually experience 90% of the time, because that moment happens on `DraftSessionHost`, which has no live channel at all. Building it only on `DraftSessionHost` means taking on new WebSocket-subscription work that a prior change explicitly, deliberately deferred as "real work." I don't think this change can honestly call itself done by picking the cheap option and calling the AC satisfied — that's exactly the kind of "technically shipped, actually didn't help anyone" gap that erodes trust in the tool once a facilitator opens it expecting a roster and finds one only on the page they never look at. This needs an explicit decision in the design doc, not a default.

My lean: build the roster as one shared piece (component + hook), consumed by both surfaces, and treat giving `DraftSessionHost` its own WebSocket subscription as in-scope — not a follow-up. The alternative (roster on `SessionLobbyPage` only) ships something that answers the letter of the issue while missing its point.

One framing constraint worth locking in regardless of which surface(s) the design stage ultimately picks: tie it back to the source Main Flow's step 1 ("Facilitator views the session room after creating the session"). A single-surface implementation shouldn't get to claim AC compliance while leaving the page the Facilitator actually lands on after creating a session roster-less. Whichever surface(s) get chosen, that's the test to apply.

To be clear about how far I'll push this: I agree with Priya that a `SessionLobbyPage`-only roster, with `DraftSessionHost` as a "fast-follow," ships something that answers the letter of the AC without serving the moment it exists for, and I'd say so directly if asked. But the cost side of that tradeoff — new WebSocket-subscription work that `session-lobby-routing-gap`'s D3 explicitly deferred as "real work" — is a genuine resourcing call, and exploration notes aren't the place to make it unilaterally on the design stage's behalf. What I won't accept is that call getting made silently, by default, because the cheap path was easiest to ship first. It needs to be a named decision in the design doc, with the consequence Priya describes stated plainly next to it, not softened into "and `DraftSessionHost` gets it eventually."

## 3. `FacilitatorReadinessGrid.tsx` is correctly out of scope — confirmed by reading it, not just its header comment

Its own header comment says this explicitly (`websocket-staleness-signal` design.md D9): it's a "minimal readiness grid," scoped to proving out a stale-connection marker mechanism for the **live-voting** surface, not a feature-complete roster. Confirmed by reading the code: `ParticipantRowState` is `"connected-not-locked-in" | "connected-locked-in" | "disconnected-voted" | "disconnected-no-vote"` — every state name references voting/lock-in, which doesn't exist yet in the pre-session lobby. Its `state` marker also means something different from what issue #47 needs: `FacilitatorReadinessGrid`'s marker reflects the **facilitator's own connection health** (when the facilitator's own socket is `unknown-reconnecting`, every row shows the marker simultaneously — it's not a per-participant signal at all). Issue #47 needs the opposite: a **per-participant** presence/disconnect signal, driven by that specific participant's own connection, not the facilitator's. Don't let a future implementer reach for `FacilitatorReadinessGrid`'s marker mechanism by analogy — it answers a different question. Build a distinct component.

## 4. The hard blocker: nothing registers a participant during `lobby` today

This is the finding that most needs to surface before design work starts, because it isn't a nice-to-have — without it, this feature cannot show a single participant during the state it exists to cover.

Traced end to end:
- `POST /api/v1/sessions/:sessionId/participants` (`packages/backend/src/routes/sessions.ts:42-145`) is the *only* code that inserts a `session_participants` row, and it 422s unless `status === 'active'` (line 72-80). It also has **zero frontend call sites** — grep confirms nothing in `packages/frontend/src` calls it.
- `evaluateSessionSubscriberAccess` (`packages/backend/src/auth/session-subscriber-access-helper.ts`), the sole authorization gate for a session-scoped WebSocket connection, has a Participant path (Path 1) that *requires* a pre-existing `session_participants` row. No row, no grant.
- Join-link redemption (`join-links.ts`, `auth.ts`) inserts into `team_memberships` only — never `session_participants`.

Net effect, confirmed by tracing the actual code paths rather than assuming: an Engineer who has never previously participated in this exact session, following a join link into a `lobby`-status session, gets `evaluateSessionSubscriberAccess` → `null` → their session WebSocket connection closes immediately with `CLOSE_UNAUTHORIZED`, and `GET .../action-items-review` (which `SessionLobbyPage` calls to determine its branch) returns `404`. They land on `SessionLobbyPage`'s `no-access` branch — "You don't have access to this session" — not the waiting screen. `participant_joined` (see §5) never fires for them, because the publish only happens *after* a successful WS registration.

This is not a new finding — it's `session-lobby-routing-gap`'s design.md Decision D7, confirmed still open by checking `sessions.ts` directly: the status gate is unchanged, and there's still no frontend caller. D7 explicitly scoped this out and named it a follow-up requiring its own design-stage security review, specifically because closing it means choosing between real authorization-boundary designs (auto-creating a `session_participants` row at join time regardless of status, vs. relaxing the endpoint's `active`-only gate and wiring a frontend caller) — and *either* choice must independently re-implement the EM-exclusion check (`global_role` or `membership_role === 'engineering_manager'` → reject) that Path 1 depends on.

**I don't see how issue #47 can be considered done without resolving this.** The use case's whole premise — an empty state that fills in live as Engineers join during the wait — cannot occur today for any first-time joiner. This isn't "reuse existing infrastructure," it's "the existing infrastructure has a known, previously-deferred hole exactly where this feature needs to stand." The design stage should treat this as in-scope work, done with the rigor D7 itself asked for (an explicit security review of whichever registration approach is chosen), not as a silent prerequisite bundled in without the same scrutiny. This is precisely the kind of authorization-boundary decision I'd want flagged to me directly if I were still doing day-to-day review — whatever gets chosen must preserve the EM-exclusion check exactly. If a manager can end up in this roster because a new registration path skipped that check, that's a direct violation of the no-manager rule, and it would be visible to the facilitator in exactly the surface built to show "who's here" — which makes the failure mode worse than most, not better, because it's a rule violation made visible rather than quietly absorbed.

One more thing worth naming while this gap is open, raised in review: right now a blocked join — an Engineer hitting the `no-access` branch because of this exact gap, or for any other reason once it's closed — is invisible to the Facilitator. The roster can look complete and current while someone on the team is stuck on an error screen with no way for the Facilitator to know it's happening, which is arguably a worse failure mode than an obviously-incomplete roster, since it doesn't invite anyone to check. I'm not proposing a fix here. The design stage should decide on purpose whether that's acceptable for v1 or whether the Facilitator needs some passive signal that a join attempt failed, rather than let the answer fall out implicitly from whichever registration fix gets chosen for §4 itself.

## 5. What's already usable once §4 is resolved

- `participant_joined` / `participant_left` (`packages/shared/src/types/realtime.ts:141-151`, wired in `packages/backend/src/realtime/websocket-routes.ts:139-197` and `ws-pubsub.ts`) already exist, shipped by issue #94/FR-2.5. They fire on session-scoped WS connect/disconnect for any connection whose grant path is `"participant"` — i.e., exactly the moment an Engineer's browser opens or drops the session socket. Nothing in the frontend consumes them yet (grep confirms zero non-test references in `packages/frontend/src`).
- Payload is minimal: `{ sessionId, userId, joinedAt | leftAt }` — no display name. The roster will need to resolve `userId → users.display_name` itself, either via a REST roster fetch (needed anyway, see below) or a lookup the frontend already has cached from elsewhere. Don't assume the WS payload alone is enough to render a name.
- These events are connection-lifecycle events, not durable-state events — a participant who simply refreshes their own tab will emit `participant_left` immediately followed by `participant_joined` on reconnect. If the roster is implemented naively (delete-on-left, insert-on-joined, keyed by connection), a refresh will make a still-present Engineer flicker out of the list and back in. **Key rows by `userId`, not by connection/event ordering** — `participant_left` should mark a row disconnected, not remove it; `participant_joined` should add-or-clear-disconnected. This also answers the use case's own open question ("is a disconnected participant's slot held or released?") in a way that's consistent with the AC's refresh-restore requirement: hold the slot. `session_participants` rows are never deleted (confirmed — no `DELETE FROM session_participants` anywhere in the backend), so "restored from the session record" on refresh is achievable as long as the roster's initial fetch reads that table, not connection-registry state.

That's a recommendation grounded in what the schema currently permits, which isn't the same thing as a stated product decision — "the database happens to make this easy" is a rationale that doesn't survive a future schema refactor. Recording it on its own terms:

> **Decision:** A disconnected participant's slot is held for the duration of the `lobby` state, not released. Reconnecting (including a page refresh) restores the participant to their existing row rather than creating a new one. **Rationale:** matches the AC's refresh-restore requirement (line 413) and avoids a participant flickering out of the list on a simple tab refresh.
- There is currently **no REST endpoint that returns the current roster** — not on `FacilitatorSessionStateResponse` (checked its full shape, `packages/shared/src/types/team-content-access.ts:208-228` — no participant field), not on `action-items-review`'s response, nowhere. `session_registration_snapshot` (the closest-sounding existing thing) is a *per-connection* recovery payload about that one user's own vote/topic state — it carries no participant list at all. A new read path is needed for: (a) initial roster on page load/mount, and (b) the "Facilitator refreshes the page — list restored, no participants lost" AC. This read should apply the same EM-exclusion filter `evaluateSessionSubscriberAccess` Path 1 applies, for the same reason D7 keeps coming back to: consistency of the no-manager rule across every surface that can reveal who's "in" a session.

## 6. Wiring shape, once the above is resolved

- Reuse `useConnectionHealth`'s existing `socket` return value for whichever host page(s) render the roster — don't open a second WebSocket to the same session route. `SessionLobbyPage` already demonstrates the pattern its own `session_state_change` listener uses (`socket.addEventListener("message", ...)` on the socket `useConnectionHealth` returns); the roster's `participant_joined`/`participant_left` listener should attach the same way, on the same socket, not a parallel one.
- If `DraftSessionHost` gains a `useConnectionHealth` subscription (see §2), the roster hook should be shape-compatible so both host pages can mount it without duplicating the disconnect/reconnect bookkeeping — this is the same "sole implementation, no forking" discipline `connectionHealth.ts`'s own header comment insists on, and I'd hold the roster component to the same bar rather than let two slightly-different implementations drift the way `SessionLobbyPage`/`DraftSessionHost` copy already has (flagged as an accepted, named risk in `session-lobby-routing-gap`'s design.md — don't repeat that pattern here without at least naming it the same way).

## 7. Ritual-fidelity notes, stated plainly

- **No-manager rule.** The roster is the first place "who's in the room" becomes visible to a human, before any vote happens. Whatever registration path closes the §4 gap must replicate the EM-exclusion check exactly — not "close enough." This is not a preference; treat it as a correctness requirement with a test, the same way `evaluateSessionSubscriberAccess`'s own EM checks are tested.
- **Feels like software, not a tool run on engineers.** Resist the urge to add a progress indicator, a "3 of 8 expected" counter, or any framing that implies quorum — the use case explicitly puts quorum enforcement out of scope, and the application doesn't know how many people are "expected" anyway (there's no roster of expected attendees, only a team roster, and even that's not fetched here). A plain list of names with a disconnected marker is the right amount of UI. Anything more starts to look like attendance-taking.
- **Facilitator-only, confirmed, not reopened.** Don't let "should participants see each other" resurface as a design question — the AC already answers it, and reopening it invites exactly the kind of scope creep that turns a waiting-room utility into a social feature.
- **Disconnect styling should borrow the existing disclosure-blind posture**, not invent new visual language. `connectionHealth.ts`'s own design principle — never distinguish cause (network drop vs. reauth vs. anything else) in the UI, just "disconnected" — is the right model here too. A participant's connection dropping is not information the facilitator needs to diagnose; it's a fact to note and move on from. That's the posture; the actual visual weight (color, size, placement) is not specified here on purpose, and shouldn't be finalized without a usability pass. Priya's already offered to do that pass — the design stage should route the marker's visual treatment through her before it's built, not after. A marker that's too quiet gets missed; one that's too loud reads as an alert and pulls focus the same way an aggressive outlier callout would in the live-voting view.
- **Per-row status: list membership is the status; it doesn't need its own label.** The source AC (line 394) asks for "a status indicating they are present but the session has not yet begun." There's exactly one non-disconnected state in this view, so appearing in the list, undecorated, satisfies that requirement on its own — an explicit "Present" badge on every row would be redundant, not informative, and it's the same kind of decoration the quorum-counter rejection below is arguing against. The disconnected marker is the only per-row indicator this view needs. I want this decided now, not left for whoever picks up the ticket to guess.
- **Roster sort order needs to be stable — which order it is isn't decided here.** Two reasonable defaults came up in review: alphabetical (so a name is always in the same place to glance at, like a seating chart) and join-order/earliest-first (which pairs naturally with keying rows by `userId` and never reordering on reconnect, above). Both satisfy the one hard requirement: a participant's position must not change on disconnect/reconnect — that's the same jitter problem the identity-keying fix above solves, just reintroduced at the layout layer if it's not also handled here. Which default wins is a facilitator-experience call, not a ritual-fidelity one, so I'm not making it in these notes. It needs Priya's input at the design stage, not a default that falls out of whichever query happens to be easiest to write.
- **The "who's missing" gap is accepted, not solved.** I stand by rejecting a quorum counter, above — the app doesn't know who's expected, and a counter invites quorum-pressure that isn't the roster's job to create. But rejecting the counter doesn't make the underlying problem disappear: today the Facilitator holds "who's missing" in their head during the wait, and this view will still only ever say who's *here*. The proposal should name that gap explicitly as accepted-but-unsolved, rather than let the quorum-counter rejection read as "the waiting-room cognitive-load problem is solved." It isn't — it's partially solved.
- **Restating the source's Out of Scope, since it's easy to reintroduce by accident:** removing a participant from the roster is explicitly out of scope (source line 418). Holding a disconnected participant's slot rather than releasing it (above) makes "shouldn't the Facilitator be able to clear a stuck row" a plausible-sounding ask mid-implementation. It isn't in scope. Worth a one-line restatement in the proposal so it doesn't get reintroduced as a "nice to have" partway through the build.

## 8. Explicit non-overlap with issue #33

Confirmed by reading `FacilitatorReadinessGrid.tsx` directly: its scope is live-voting connection-health markers on a grid that already assumes voting rows (`connected-locked-in`, `disconnected-voted`, etc.). Issue #47's surface has no voting concept at all — it's pre-session. The two should not share a component, though they may reasonably share the *underlying* per-connection presence primitives if `participant_joined`/`participant_left` end up feeding both (worth flagging to whoever owns #33, not deciding unilaterally here).

One thing the non-overlap doesn't address: what happens to this view the moment the Facilitator clicks Start Session. Does the roster just unmount in favor of `FacilitatorReadinessGrid`, with no carried-over sense of "who was here during the wait"? I'm not asking to design that continuity here — that's #33's territory — but the proposal should say explicitly whether the transition itself is in scope for #47, rather than let the answer fall out of whichever component happens to render first:

> The roster's visual continuity across the transition from `lobby` to an active-voting state is not guaranteed by this change; issue #33 owns the post-start experience.

## 9. Open questions for the design stage (not resolved here)

1. **Where does the roster render** — `DraftSessionHost` only, `SessionLobbyPage` only, or both via a shared component? (§2 — my lean is both, shared.)
2. **How does §4's registration gap get closed** — auto-create/upsert `session_participants` at WS-connect time, or relax the `POST .../participants` status gate and add a frontend caller during join-link redemption? Either needs its own security review per D7's own recommendation.
3. **New REST endpoint shape** for the initial/refresh roster fetch — new route, or an addition to `facilitator-state`/`action-items-review`'s existing response? Whichever surface(s) get the roster component from Q1 determines which existing response(s) it should extend.
4. **Does `DraftSessionHost` get a WebSocket subscription** as part of this change, or does the roster ship `SessionLobbyPage`-only pending that as a fast-follow? I've stated a preference (§2) but this is a real scope/cost call the design stage should make explicitly, not by default.
5. **Roster sort order** — alphabetical or join-order/earliest-first? (§7 — both are reasonable, needs Priya's input; the only non-negotiable is that position doesn't change on disconnect/reconnect.)
6. **Is a blocked or failed join attempt surfaced to the Facilitator in any way**, even passively, or is that an explicit, named deferral for v1? (§4)

## 10. Response to review — what changed and what didn't

This pass incorporated nearly all of Priya's and Marcus's feedback — most of it sharpened things these notes were already gesturing at rather than introducing new territory. Two places where I only partially took the suggestion, on purpose:

- **Priya asked that a `SessionLobbyPage`-only ship not be accepted as done.** I agree with her diagnosis and said so more directly in §2. I did not convert it into a hard rule inside these notes, because the cost side of that tradeoff — new WebSocket work D3 named as deliberately deferred — is a real design-stage resourcing call, not something exploration should pre-empt on the design stage's behalf. What I did do is make sure that call can't get made silently by default.
- **Marcus proposed a specific sort-order AC (earliest-first).** I didn't adopt it as-is, because Priya independently proposed a different default (alphabetical) for a different, equally legitimate reason. Picking between them is a facilitator-experience call these notes shouldn't settle unilaterally — I've recorded both defaults, named the one hard requirement (stability across reconnect), and left the choice to the design stage with Priya's input (§7, §9.5).

Everything else — the facilitator-only decision record, the hold-the-slot decision record, the per-row status resolution, the residual "who's missing" gap, the blocked-join visibility question, the disconnect marker's usability-review gate, the transition-to-live-session note, and the Out of Scope restatement on participant removal — is incorporated inline above, not held back.
