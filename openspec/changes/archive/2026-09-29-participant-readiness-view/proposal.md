## Why

GitHub issue #47 asks for the participant readiness view described in `02 - Session Setup - Use Cases.md`. The Facilitator's whole job during the wait is deciding when to start — and today they cannot see who has joined. `DraftSessionHost` (their actual landing page after creating a session) shows a static "waiting for participants" message with no roster and no live channel at all; `SessionLobbyPage`'s equivalent `lobby` branch has a working WebSocket subscription but also renders no roster. Worse: even where a roster could be wired up, no first-time-joining Engineer can appear in one today, because nothing registers a `session_participants` row for a session still in `lobby` status (`POST .../participants` 422s unless `status === 'active'`, and has zero frontend callers) — a gap `session-lobby-routing-gap`'s design.md named and deliberately deferred (Decision D7). This use case's core scenario — an empty roster that fills in live as Engineers join during the wait — cannot occur until that gap closes. This change delivers the roster and closes the gap it depends on in one piece of work, rather than shipping a roster that stays empty for every real, first-time-joining team.

## What Changes

- Add a Facilitator-only, live-updating participant roster covering the `lobby` status wait, rendered on **both** `DraftSessionHost` and `SessionLobbyPage` via a shared component/hook — not one surface with the other as a "fast-follow." `DraftSessionHost` gains its own `useConnectionHealth` WebSocket subscription as in-scope work for this change (previously named as deliberately deferred, real work by `session-lobby-routing-gap` D3). **Decision, resolving open questions 1 and 4** (`exploration-notes.md` §9 — where the roster renders, and whether `DraftSessionHost` gets its own WebSocket subscription; these two questions are resolved together because the answer to one determines the other): the source use case's own Main Flow Addendum ("Create Session for Existing Team," step 10) describes the Facilitator's view updating "in place — without navigating away — to the participant readiness view" the moment the room opens — that view is `DraftSessionHost`, the page the Facilitator is actually on. A roster that ships only where the WebSocket plumbing happens to already exist (`SessionLobbyPage`) satisfies the acceptance criteria's letter while leaving the page the Facilitator looks at 90% of the time roster-less. That is not an acceptable reading of "done" for this change.
- Close the `session_participants` registration gap (`session-lobby-routing-gap` Decision D7) as in-scope work, with the same design-stage security review D7 itself called for. The exact mechanism — auto-creating/upserting a `session_participants` row at WS-connect or join-link-redemption time regardless of status, vs. relaxing the REST endpoint's `active`-only gate and wiring a frontend caller — is a design-stage decision, but closing the gap itself is not optional: the use case's core scenario cannot occur without it, and this change does not get to claim AC compliance while a first-time joiner still gets `404`/`CLOSE_UNAUTHORIZED`. Whichever mechanism is chosen MUST replicate the Engineering Manager exclusion check (`session-participation`'s dual-check pattern: `users.global_role` AND `team_memberships.role`) exactly — a manager appearing in this roster would be a no-manager-rule violation made visible in the one surface built to show "who's here," not quietly absorbed.
- Add a new REST endpoint for the initial/refresh roster fetch (no existing response carries participant identity — `action-items-review` is gated to `pre_session` only and 409s during `lobby`). Exact route shape is a design-stage decision.
- Roster updates consume the existing `participant_joined`/`participant_left` WebSocket events (shipped, FR-2.5/issue #94, facilitator-connection-only delivery — already the right audience for this Facilitator-only view). Rows are keyed by `userId`, not by connection: `participant_left` marks a row disconnected rather than removing it, and `participant_joined` clears the marker on the existing row rather than inserting a new one. **Decision:** a disconnected participant's slot is held for the duration of `lobby`, not released — matching the AC's refresh-restore requirement and preventing a simple tab refresh from flickering a still-present Engineer out of the list.
- **Decision, resolving open question 5** (`exploration-notes.md` §9 — sort order): the roster is sorted alphabetically by participant name. Priya Nair's facilitator-persona review argued for this directly — a stable position lets the Facilitator's eye find a name in the same place on every glance, the way a seating chart works, rather than a list that reshuffles as people connect. The one hard invariant, regardless of sort order, carries forward unchanged: a participant's position MUST NOT change on disconnect or reconnect.
- Each participant entry shows name only; list membership itself is the "present, not yet begun" status the source AC calls for — no separate "Present" badge. The only per-row indicator is the disconnected marker, styled per the existing disclosure-blind posture (`connectionHealth.ts`: never distinguish cause, just show the fact), with final visual weight subject to Priya's usability pass before ship, not after.
- Engineers see an unchanged waiting screen during `lobby` — no participant names, no count, no indication of how many others have joined. This view is Facilitator-only, confirmed as a recorded decision (the source AC marks this "should be confirmed," not settled): a visible peer roster turns a waiting-room utility into a social check-in surface, out of character for this ritual.
- Named, explicit non-goals carried forward rather than left to be inferred: no quorum counter or "N of M expected" framing (the app has no roster of expected attendees, and a counter invites quorum-pressure that isn't this view's job to create — the resulting "who's missing" gap is accepted, not solved, and stated as such rather than implied-fixed); no facilitator-initiated participant removal (source Out of Scope, easy to reintroduce as a "nice to have" once disconnected rows are visibly held); no visual continuity guarantee across the `lobby → active` transition (issue #33 owns the post-start experience); a blocked/failed join attempt is not surfaced to the Facilitator in this change (named deferral, not a silent gap — see Impact).

## Acceptance Criteria Reconciliation

The source AC ("View Participant Readiness Before Session Begins," line 410) states the roster "is displayed immediately after session creation, before any participants join." This holds as written for the new-team flow, which lands the Facilitator directly in `lobby`. For the existing-team flow, it does not hold literally: per "Create Session for Existing Team"'s own draft-landing decision (already implemented), the Facilitator lands on the draft control view first, and the roster begins only after they explicitly activate "Open the room." That later, more specific decision supersedes this AC's general wording for the existing-team path — the roster still renders correctly once `lobby` is reached, it is just not "immediately after session creation" in that flow. This is not a gap this change introduces or needs to resolve; it is a pre-existing sequencing fact worth stating so a future audit against the source AC checklist doesn't misread the existing-team path as unmet.

## Scope Notes

Two things worth stating explicitly rather than leaving implicit in the sequencing above:

- **This change absorbs two previously-deferred IOUs from `session-lobby-routing-gap` as in-scope, blocking work**, not as incidental reuse: the `session_participants` registration gap (D7) and `DraftSessionHost`'s WebSocket subscription (D3) were both named and deliberately deferred by that change. Closing them here is a deliberate sequencing decision — a roster that can never show a real first-time joiner isn't a feature, it's a demo — and it is called out here so that velocity tracked against this change's estimate is read correctly: part of the work is closing debt from a prior change, not net-new roster scope.
- **Building the roster on both surfaces, rather than shipping `SessionLobbyPage` first and fast-following on `DraftSessionHost`, was a deliberate call, not the default path.** The cheaper single-surface option was on the table and named explicitly in `design.md` D1. It was rejected because `DraftSessionHost` is the page the Facilitator is actually on per the source use case's own flow — trusting the use case over whichever surface happened to be cheaper to build on.

## Capabilities

### New Capabilities
- `participant-readiness-roster`: the Facilitator-only live roster itself — initial REST fetch, `participant_joined`/`participant_left`-driven live updates, disconnect-hold/reconnect-restore behavior, alphabetical stable sort, and the participant-side waiting-screen requirement (no names/count visible to non-facilitators).

### Modified Capabilities
- `session-participation`: gains the requirement that a `session_participants` row can be created for a session in `lobby` status (not only `active`), closing the D7 gap, with the existing Engineering Manager dual-check enforcement preserved exactly at whatever new registration point is chosen.
- `session-creation`: `DraftSessionHost`'s `live-readiness-view` gains a WebSocket subscription (via `useConnectionHealth`) and renders the participant roster while `currentSessionState === 'lobby'`.
- `pre-session-action-item-review`: `SessionLobbyPage`'s `lobby` branch renders the same shared roster component, and its non-facilitator waiting copy is confirmed to withhold participant identity/count.

## Impact

- **Frontend:** `packages/frontend/src/pages/DraftSessionHost.tsx` (new WebSocket subscription + roster render in `live-readiness-view`), `packages/frontend/src/pages/SessionLobbyPage.tsx` (roster render in its `lobby` branch), a new shared roster component/hook (distinct from `FacilitatorReadinessGrid.tsx`, which is issue #33's live-voting component and answers a different question — the facilitator's own connection health, not a per-participant presence signal).
- **Backend:** new REST endpoint for roster fetch; whichever registration-gap fix is chosen at design stage touches either `packages/backend/src/routes/sessions.ts` (`POST .../participants`'s status gate) with a new frontend caller, or the WS-connect/join-link-redemption path with a new upsert — this decision requires its own security review per D7, and must be made explicitly, not by default.
- **Specs:** new spec for `participant-readiness-roster`; delta specs against `session-participation`, `session-creation`, `pre-session-action-item-review`.
- **Named deferral, not silently dropped:** a blocked or failed join attempt (an Engineer landing on the `no-access` screen) is invisible to the Facilitator in this change — the roster can look complete while someone is stuck on an error screen. Design stage decides explicitly whether this is acceptable for v1 or whether the Facilitator needs a passive signal; either answer must be a stated decision in design.md, not an implicit default.
