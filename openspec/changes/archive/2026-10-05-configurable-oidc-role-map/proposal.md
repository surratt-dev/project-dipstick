# Proposal: Configurable OIDC role map (#243)

**Proposer:** Devon Calloway, Internal Champion
**Source:** GitHub issue #243; exploration notes and reviews in this change directory (`exploration-notes.md`, `explore-review-ba.md`, `explore-review-facilitator.md`, `propose-review-ba.md`, `propose-review-exec.md`)

> **Archive status (2026-10-05):** archived with three human-pending tasks (see `tasks.md` §7): **7.1** Security Analyst sign-off on `security-review.md` (blocks merge), **7.2** release owner's per-deployment IdP check recorded in `release-check.md` (blocks release), **7.4** follow-up issues in `follow-ups.md` still to be filed and linked below.

## Why

The 01b decision (commit 2083753) made the IdP the only source of the `facilitator` role, but today a facilitator cannot actually arrive that way. The backend accepts only our internal enum strings on the role claim, `facilitator` and `senior_engineer` are not on the allowlist, and array claims (`groups: [...]`) are flattened to `"a,b"` and silently dropped to `engineer`. Real IdPs send their own group and role names. So every new team has two options: ask its IdP admin to emit our strings, or ask us to change code. That is exactly the friction that stops a team I have never spoken to from adopting the ritual on its own, and right now it means nobody can be designated a facilitator through a supported path, so FR-2.1 sessions cannot be run for real.

The same translation layer decides who the application recognises as a manager. A gap in the map means a manager is treated as an engineer, TEAM-006 refuses to record them, and nothing stops them from joining by link. The no-manager rule then fails open without anyone noticing. This change has to make role *recognition* configurable without making the *constraints* configurable, and it has to fail loudly when the config would weaken them.

## What Changes

- **New `OIDC_ROLE_MAP` setting.** A per-deployment JSON object that maps IdP claim values to the fixed internal roles. Internal role values (Postgres `user_role` enum, TypeScript types, API contract, audit rows) do not change.
- **Strict startup validation.** The process exits at startup on invalid JSON, a non-object, a non-string or empty key or target, a key with leading or trailing whitespace, a duplicate key, or an unknown target. `engineer` is not a valid target, and the error says why: it is the fixed default every unmapped user already gets. Errors name the broken rule and the offending key, never the full map value. An empty or whitespace-only `OIDC_ROLE_MAP` counts as unset.
- **BREAKING: production must configure the map.** With `NODE_ENV=production`, startup fails if `OIDC_ROLE_MAP` is unset or if no key targets `engineering_manager`. A deployment with genuinely no managers in its IdP maps a placeholder group nobody belongs to; `docs/deployment.md` documents that as a deliberate choice. A production deployment upgraded without the map will not boot. That is intentional.
- **Startup warnings and summary.** Whenever a map is configured, in any `NODE_ENV`, startup warns once for each of `engineering_manager` (outside production; production fails instead), `facilitator` (plain wording: no one will be able to run a session) and `application_admin` that no key targets. The built-in default never warns. One info line, logged once after validation succeeds, reports the map source (`configured` or `default`) and key counts for all four targets including zeros, with no key names.
- **Identity default only for a local IdP outside production.** If the map is unset, `NODE_ENV` is not exactly `production`, **and** `OIDC_ISSUER` is a local/private address (the same gate persona-login uses), `application_admin`, `engineering_manager`, `facilitator` and `senior_engineer` map to themselves. `engineer` is reached through the fixed fallback, not a mapping. Dev, CI and the local OIDC stub keep working without configuration. **Also breaking:** any deployment on a non-local issuer (`staging`, `uat`, a mislabelled `prod`) with no map now fails to boot, so a real IdP can never receive the identity default.
- **Claim resolution at sign-in.** A non-empty string claim is one value. An array keeps only its non-empty string elements; if none survive, the claim counts as missing. Anything else and `""` count as missing. Lookup is exact, case-sensitive, and checks only keys the operator wrote (so `constructor` and `__proto__` do not resolve). With one or more mapped values, the highest wins by the fixed precedence `application_admin > engineering_manager > facilitator > senior_engineer > engineer`. With none, the role is `engineer`, and that default is fixed. `users.global_role` stays single-valued.
- **Logging that is quiet in the normal case and loud when it matters.** A missing claim logs nothing, unless the token says the claim was omitted for size (Entra group overage), which logs one value-free `claim_overage` warning. A present claim with zero mapped values logs one warning per sign-in attempt that carries the claim name and the sign-in's `correlationId`, and no values. Partial matches are normal for `groups` and are not warned. No log line or audit row ever contains a claim value or map key.
- **Precedence-discard log line.** When the resolved role outranks `facilitator` or `engineering_manager` but a mapping to that role was also present, the backend emits a warn-level log line carrying the claim name, the resolved internal role, the discarded internal roles and the `correlationId`, and no values. It fires on every such sign-in, for new and returning users alike. An operator can then answer "why can't this person facilitate?" and "why wasn't this manager excluded?" without group names being logged. The manager case (manager + admin resolves to `application_admin`) is reported even though D11 now blocks it, so operators can fix the IdP groups.
- **Application admins do not take part in live sessions (binding user decision on S1).** `application_admin` gets the same treatment as `engineering_manager` under the no-manager rule. Admins are refused at participant registration and vote lock-in, and the session subscriber authorization gives them no participant grant, so they cannot connect to or receive live session events. They also do not appear on the roster. The responses reuse the manager denial: 403 `invalid_request`, and the same `session.participant_registration_rejected` audit row. Precedence is unchanged. This closes the path where a manager who is also in the admin group resolves to `application_admin` and slips past the manager checks. Team membership, join links and every admin function outside sessions are unaffected. No discard flag is added to audit metadata; a durable, user-visible record of this conflict belongs to #241.
- **Role changes are always audited.** `auth.role_claim_mapped` now also fires when a returning user's resolved role differs from their stored role, including demotion to `engineer`. This makes the 01b claim "removing the claim demotes the user and the audit records it" true. Today a reversion to `engineer` is explicitly not recorded.
- **Local stub.** `facilitator-001` carries `role: "facilitator"`, so under the default map it signs in as a real facilitator who can create a draft session.
- **Docs and release notes.** `docs/deployment.md` gets an `OIDC_ROLE_MAP` reference with a `groups` example, a manager warning, the no-managers placeholder workaround, the ~90-minute revocation bound (roles are re-resolved at interactive sign-in, not token refresh), and a group-hygiene checklist ("people who facilitate must not also be in the admin or manager groups"; "people in the manager group must not also be in the admin group"). Upgrade notes lead with the production boot failure and include a post-deploy check that a facilitator can create a draft session.

## Capabilities

### New Capabilities
- `oidc-role-mapping`: How a deployment translates IdP role-claim values into the fixed internal global roles. Covers `OIDC_ROLE_MAP` configuration and startup validation, the production requirements and warnings, the non-production identity default, claim normalization, own-key exact lookup, fixed precedence, the fixed `engineer` fallback, the logging rules, and the precedence-discard signal.

### Modified Capabilities
- `first-access`: In "Application provides a mechanism for assigning `global_role`", the hard-coded allowlist (validation requirement 4) is replaced by the claim → normalize → map → precedence → default pipeline defined in `oidc-role-mapping`. Requirement 5 is corrected: roles are re-evaluated at each interactive sign-in, not at token refresh (the code never re-resolved on refresh). The scenarios are rewritten to match, including the rule that the unmapped-claim warning carries the claim **name** only. This fixes a drift where the spec said the warning "identifies the unrecognized claim value". `facilitator` and `senior_engineer` become reachable roles.
- `auth-error-handling`: In "First Access and role-claim-mapping events are durably recorded", `auth.role_claim_mapped` also fires when a returning user's resolved role differs from their stored role, including reversion to `engineer`. The "reversion is not represented" scenario's body is replaced. Audit metadata gains no discard flag.
- `session-participation`: adds "Application Admin non-participation enforcement" and its companion requirements. Admins are refused at participant registration and lock-in, with the manager rejection's response and audit row, and are left off the roster. Team join is unaffected.
- `websocket-session-authorization`: adds "Application Admins do not receive live session events". The session subscriber authorization gives admins no participant grant at subscription, delivery or re-authorization, and endpoints that reuse it deny them the same way.
- `local-dev-environment`: The simulated OIDC provider gives `facilitator-001` a `role: "facilitator"` claim, which resolves to `global_role = 'facilitator'` under the default map. The production-mode guards add the `OIDC_ROLE_MAP` requirements, a non-local issuer requires the map in every environment, and `OIDC_ROLE_MAP` is listed as an optional variable.

## Constraints that must be preserved

- **No-manager participation stays structural.** The dual check (`users.global_role` or `team_memberships.role` = `engineering_manager`) is unchanged. The map only decides recognition, and production refuses to boot without a manager mapping. A manager who is also in the admin group resolves to `application_admin` under the decided precedence. The admin exclusion (design D11) keeps them out of live sessions, so the rule still holds for them.
- **Fixed internal roles and a fixed default.** No deployment can rename a role, map anything to `engineer`, or raise the default role for everyone.
- **Signed ID token only, one writer.** The role still comes only from `tokens.claims()` and is re-evaluated at every sign-in. Team membership roles stay app-assigned.
- **No claim values in logs or audit.** Claim values are attacker-influenced. Only claim names and internal role names are ever recorded.
- **Facilitator-from-another-team and FR-2.1 gates are unchanged.** All checks keep comparing against the exact string `facilitator`.

## Deviations from the literal text of #243

The user decision is to implement #243 as written. These points differ from the issue's wording. Each gives the same or safer observable behaviour and none reopens precedence or storage. Task 7.3 updates the issue's acceptance criteria to match.

| #243 says | This change says | Why |
|---|---|---|
| Unset map: each value maps to itself for all five values | Four self-mappings; `engineer` comes from the fixed fallback | Same observable result, and keeps `engineer` out of the target list (explore C4/C8) |
| Every target must be a valid `user_role` value | `engineer` is rejected as a target | Mapping a group to `engineer` could hide a manager (C4) |
| An unmapped **or missing** claim logs a warning | A missing claim logs nothing | The issue contradicts itself; existing first-access item 3 says MUST NOT warn (C1) |
| Production requires the map to be set | Also requires at least one `engineering_manager` target | Stops the no-manager rule failing open silently (C5) |
| Unset map outside production uses the identity default | Only with a local/private `OIDC_ISSUER`; a real IdP without a map fails boot in every `NODE_ENV` | A real IdP must never grant roles from raw internal strings (security S2) |
| (silent on what an admin can do in a session) | `application_admin` cannot register, vote, or receive live session events | Under #243's precedence, manager + admin resolves to admin and would otherwise escape the no-manager rule (security S1; binding user decision) |

## Known divergence from #235 / #238 / #241 (risk, not a design input)

By user decision, #243 ships as written: its own precedence and a single-value `users.global_role`. Open issue #235 (rescoped to a `users.roles user_role[]` column) and #238/#241 (EM + facilitator resolves to EM, audited and **shown to the user**) cover overlapping ground and differ in several ways. #235 uses a different precedence (`application_admin > facilitator > engineering_manager > …` with a discard rule) and role-set storage. #241 adds a user-facing notice. Here, EM + facilitator resolves to `engineering_manager` with no user-facing notice. That is pinned as known behaviour, not a bug. **Risk:** whichever of #243 and #235 lands second has to reconcile its resolver with the other, and must re-run security checks S1 (manager + admin collapse) and S4 (own-key target validation) from `design-review-security.md` against the merged resolver. #235/#241 own that reconciliation. If #235 merges first, this change's `first-access` delta is rebased onto its version.

## Impact

- **Code (admin exclusion, D11):** `packages/backend/src/routes/sessions.ts` (participant registration and lock-in conditions), `packages/backend/src/auth/session-subscriber-access-helper.ts` (participant path, which covers WebSocket connect, delivery and re-authorization, plus the HTTP endpoints that reuse it), `packages/backend/src/routes/facilitator-sessions.ts` (roster query).
- **Behaviour change for admins:** application admins who are also team members can no longer vote in their team's sessions. The release note says so.
- **Code:** `packages/backend/src/config.ts` (`loadConfig(env)` exported; parse, validate, production and issuer guards, startup summary line); `packages/backend/src/auth/role-map.ts` (new leaf module, including the `GlobalRole` type); `packages/backend/src/auth/account-resolver.ts` (`resolveGlobalRole` replaces `PERMITTED_GLOBAL_ROLES`; the map and a `correlationId`-bound child logger are injected; pino argument order fixed); `packages/backend/src/routes/auth.ts` (one firing-condition helper for `auth.role_claim_mapped`, `previousRole` on the structured event, `DEV_LOGIN_OPTIONS`); `docker/oidc/accounts.js`. Tests: `__tests__/config.test.ts` must set a map because it uses a public issuer.
- **Config / ops:** New `OIDC_ROLE_MAP` env var, added (commented out) to `.env.example`. **Breaking for production and for any deployment on a non-local `OIDC_ISSUER`**: they must set it before upgrading.
- **Release-blocking IdP check.** Any IdP that already sends `facilitator` or `senior_engineer` on the configured claim grants those roles at the next sign-in. Owner: the engineer who ships the change (release owner). Artifact: `release-check.md` in this change directory, one line per known deployment with its owner, configured claim and status (`confirmed`, mapping reviewed, or `not affected`). Exit condition: no line blank or `unknown`. The release does not ship until then.
- **Docs:** `docs/deployment.md`, `docs/local-development.md`, upgrade/release notes.
- **Security sign-off before merge.** Changes how privileged roles are granted at sign-in. Reviewer: the Security Analyst (Tomás Ferreira). Artifact: `security-review.md` in this change directory covering six points: the target allowlist, the production guards, own-key lookup, precedence, the discard log line, and the existing admin bypass of the facilitator `isMember` guard (`standing-facilitator-access-helper.ts`), which is unchanged here but more reachable once groups map to admin. Exit condition: each point marked `accepted` or `accepted with follow-up <link>`, plus a dated sign-off line. Merge is blocked until then.
- **No change** to the database schema, the `user_role` enum, audit metadata shape (apart from the wider firing condition), or team membership roles. The API contract changes only in two contract-visible ways: application admins become a denied class of caller at participant registration and lock-in, and the lock-in 403 message text changes. `requirements/design/REST API Contract.md` is updated accordingly.

## Review disposition

Reviews: `propose-review-ba.md` (Marcus Delgado, BA) and `propose-review-exec.md` (Rachel Okonkwo, VP Engineering). Fixed precedence and single-value `global_role` were out of scope for both by user decision.

**Accepted**
- **B1** (missing-target warnings): took the BA's recommended option. Warnings fire for any configured map in any `NODE_ENV`. The default map never warns. Production fails instead of warning on a missing manager target. Scenarios added.
- **B2** (empty value): empty or whitespace-only counts as unset. This matches how `loadConfig` already skips falsy optional variables. Scenarios added for both `NODE_ENV` branches.
- **B3** (normalization): the spec now uses the design's rule (non-empty strings only). Added a `["", 42, null]` scenario.
- **B4** (first-sign-in discard): took **option (b)**, which also reconciles B4 with the Executive's request to defer the audit flag. The discard is recorded by the value-free log line only, for new and returning users alike. Neither audit event carries a flag. Option (a) would have widened a durable audit contract that #241 must then inherit or migrate. Picking (b) gives one coherent rule and still answers "why can't this person facilitate?" in the first week, because the log line fires on first sign-in too.
- **S1–S5**: non-production default covers `staging` and is documented; summary-line rules and default-map scenario; positive content and every-sign-in rule for the discard line; manager + facilitator discard scenario; "per sign-in attempt" wording plus `correlationId` on both warnings.
- **S6**: "Deviations from the literal text of #243" table added.
- **S7** and Exec 5: the release IdP check and the security sign-off now each have an owner, an artifact and an exit condition.
- **S8** and Exec 6: interim behaviour stated, priority set (before a second team), listed under Follow-ups. Per instruction, no issue is filed from this proposal; task 6.5 files it.
- **N1**: removed the non-testable rename notes from THEN clauses. The renames stay in task 6.4. **N2**: keys with leading or trailing whitespace are rejected. **N3**: added the no-restart scenario. **N4**: widened the first-access audit constraint.
- **Exec 1** (defer the audit flag): accepted, as above. **Exec 2** (bound the duplicate scanner): one function, two tests, with an explicit cut-to-follow-up rule. **Exec 3**: the `engineer`-target error explains it is the fixed default. **Exec 4**: the no-managers placeholder workaround and the "facilitators not in admin/manager groups" rule are in the docs tasks and the facilitator checklist.

**Rejected or narrowed**
- **B4 option (a)** (flag on `auth.first_access_created`): rejected for the reason above.
- **S8 "open a GitHub issue now"**: narrowed. Per instruction, follow-ups are listed here and filed under task 6.5, with a hard deadline of before a second team goes live.
- **S5 user id on the warning**: not adopted. On first access the user row is created in the same transaction, so `correlationId` is the identifier that is always available. It joins the warning to the audit row and structured events for that sign-in.

### Design-stage reviews

`design-review-engineer.md` (R1–R6, C1–C8) and `design-review-security.md` (S1–S9) were all accepted or deferred to named follow-ups. Nothing was rejected. The full disposition is in `design.md`, "Review disposition". The changes that reach this proposal: the identity default now also requires a local issuer (S2, a second breaking condition); the discard signal covers manager + admin; the first-access refresh claim is corrected (S5); an overage warning is added (S8); and follow-ups 7–10 are added.

**S1 is resolved by enforcement, not just a log line and docs.** The binding user decision is that application admins are denied live-session participation (design D11): no registration, no vote lock-in, and no live events, with the same treatment and error shape as managers. That closes the manager + admin path without changing precedence. The discard log line and the docs rule stay, so operators can fix the IdP groups. Revision 2 of the design had left this as a signalled-but-unprevented residual risk. That position is withdrawn.
