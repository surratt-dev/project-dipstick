## Context

Single restore (`POST /api/v1/teams/:teamId/topics/:topicId/restore`, TOPIC-005, `packages/backend/src/routes/topics.ts`) reactivates one archived topic. Restoring a team's whole default set means up to twelve dialogs. This change adds one endpoint that does the same operation for every restorable archived default, in one transaction. Decisions D1-D14 are settled in `exploration-notes.md` Section 8; this document records the code-verified facts the exploration flagged (Section 10), the few places design had to decide, and the implementation shape. Where it differs from exploration, proposal.md "Changed from exploration" says so.

## Goals / Non-Goals

**Goals:** one confirmation and one request for any number of archived defaults; identical guards, ordering, provenance and lock semantics to single restore; no duplicate active names produced; no effect on an opened session; preview that cannot drift from server behavior.

**Non-Goals:** reset-to-canonical-order, restoring custom topics, per-topic selection, bulk undo, trend treatment, changing limiter numbers, any configuration toggle, enforcing the duplicate rule on single restore or Add, fixing the thrown-path timing gap on the other topic writes (bulk itself closes it, D22), adding a global CSRF/Origin control or lock timeout (pre-existing, recorded in D21).

## Verification of flagged facts (all by reading code)

### V1. Topics are snapshotted at room open (D8) - confirmed; fallback not needed
`packages/backend/src/sessions/session-topic-snapshot.ts` is "the single place `session_topics` rows are written". `snapshotSessionTopics` runs one `INSERT ... SELECT` from the team's `status = 'active'` topics, copying `topic_name`, `topic_prompt`, `vote_type`, `topic_annotation` and renumbering `1..N`. Its callers are `facilitator-sessions.ts` (POST /advance from draft, and direct-to-lobby creation), under `lockTeamTopics`. After room open, a session reads its own `session_topics` rows, not `topics`. Consequences:
- A restore committed before room open is in the snapshot (matches the existing restore-topic scenario for draft sessions). A restore committed after room open cannot change that session's order or content.
- A restore racing room open is serialized by the same advisory lock (`TEAM_TOPICS_LOCK_KEY_SQL`): the session gets either the pre-restore or post-restore set, never a mixture, because the snapshot is one statement.
- The D8 fallback (block bulk restore for a team with an open room) is **not** adopted. Required test: restore during a session in `lobby` and in progress, then assert that session's `session_topics` rows (ids, names, order) are unchanged.

### V2. Name uniqueness (D1) - no server-side check exists anywhere
- `topics` has no unique constraint on `name` (`migrations/2_create_tables.sql`; migration 18 made only `(team_id, display_order)` unique among active rows). `teams.name` has a normalized unique index (migration 12), which is unrelated.
- Add (`topics.ts`, TOPIC-003) validates name as non-empty after trim, at most 100 characters, then inserts with no duplicate check. Single restore updates the row with no name check.
- The only duplicate detection is a client-side hint, `findDuplicate` in `packages/frontend/src/pages/addCustomTopic.ts`, matching `trim().toLowerCase()` on name OR prompt against the loaded lists, documented as "a hint, not an authoritative check".
- Decision: the bulk rule compares **name only**, `trim().toLowerCase()` (JavaScript, no locale argument), the same normalizer the client hint uses. It is implemented once as `normalizeTopicNameForMatch` in `@dipstick/shared`. The comparison runs in application code on rows read inside the transaction, not in SQL, because Postgres `btrim` (spaces only) and JavaScript `trim` (all whitespace) differ and the two sides must agree. **`addCustomTopic.ts` is left alone** (Engineer review: a duplicated one-line normalizer is cheaper than coupling an unrelated screen's tests to this change; the former optional task is removed; task 7.1 checks it is absent from the diff). Doc comment on the shared function (Security M6): it is a UX and duplicate-hint rule, not an identity check, and must never be used for uniqueness or any access decision. NFC/NFD is intentionally not normalized.
- **Single authoritative rule for bulk (Engineer S2).** Three notions of "same name" now exist in the tree: `defaultTopicsNotActive` in `GET /topics/all` (exact, case-sensitive `name = dt.name` against the *template*, not read by the screen, #197), the client hint `findDuplicate` (name OR prompt), and single restore (none). For bulk, `planDefaultRestore` is the only rule: the server uses it to decide, the dialog uses it to preview, and `defaultTopicsNotActive` and `findDuplicate` MUST NOT be reused for bulk availability. The module comment on `planDefaultRestore` states this. The server compares against names of *active* rows only, and the frontend feeds it `data.active` from `GET /topics/all`, which is returned in full, so no new data is needed.
- Prompt is deliberately not compared: a default and an active custom topic with the same prompt but different names are not "the same topic" to the facilitator.

### V3. Topic caps - none beyond the reorder request cap
The only numeric bound on topics in `topics.ts` is `MAX_REORDER_TOPICS = 200` (reorder body length). Add has no cap; neither does restore. Bulk adds at most the number of archived defaults with distinct normalized names, which in practice is at most the template's size (12 today). Nothing to enforce; bulk obeys no limit single restore does not. The distinct-name rule also bounds a team that accumulated several archived copies of the same default (for example after #200 re-assignment): at most one per name is restored.

### V4. Route collision with `:topicId` routes (D14) - no collision
Registered under `/api/v1/teams/:teamId/topics`: `POST /topics`, `POST /topics/assign-defaults`, `DELETE /topics/:topicId`, `POST /topics/:topicId/restore`, `PUT /topics/order`, `PUT /topics/:topicId/annotation`, `GET /topics/all` (content.ts). `POST /topics/restore-defaults` has a different segment count from `POST /topics/:topicId/restore`, and the only single-segment parametric route, `DELETE /topics/:topicId`, is a different method. A static literal also outranks a parametric segment in Fastify's router, and `restore-defaults` is not a canonical UUID so it could never validly be a `topicId`. `POST /topics/assign-defaults` (#200) is the precedent for a literal sibling. A routing test still covers `/topics/restore-defaults`, `/topics/order` and `/topics/:topicId/restore` resolving to their own handlers.

### V5. Restore history reads the columns (D2) - confirmed
`content.ts` (`GET /topics/all`) selects `t.restored_at, t.restored_by` and joins `users` on `restored_by` for the archived/active mapping (`restoredAt`, `restoredBy`). It does not read `topic.restored` audit rows. So bulk restore, which writes the columns and one `topic.defaults_restored` row, is visible exactly as single restore is. No per-topic audit rows are needed.

### V6. Per-role outcomes (Section 4) - confirmed
`checkRestoreTopicAuthorization` delegates to `checkStandingFacilitatorOrAdminAuthorization(userId, teamId)`: app admin admitted whatever the membership (#208); facilitator admitted only if not an active member (`FACILITATOR_IS_TEAM_MEMBER` otherwise); anyone else `NOT_A_FACILITATOR`. The bulk handler adds a thin wrapper with its own message strings and reuses the helper unchanged. The cascade is the live order in the single-restore handler body, which is also issue #218's order: `authMiddleware` (`onRequest`, 401) before the handler, then `rejectNonCanonicalTeamId` (404), then the role check (403), `enforceTopicWriteRateLimit`, `checkWritableTeam`, `checkCustomizationLockGate`; not the older order in its header comment. Re-verified at revision 2 of this change. Consequence for a non-canonical id: unauthenticated 401, every authenticated caller class the same 404, no handler query. `evaluateStandingFacilitatorAccess` is therefore never reached with a malformed id, which resolves the BA's concern that the role helper would need the id.

### V7. Locked team with archived defaults (item 6) - effectively unreachable, 409 still correct
The lock is derived live from "a completed session exists" (`hasCompletedFirstSession`) and never relapses. Archive (TOPIC-004) is lock-gated, so a team can only hold archived defaults after unlocking. A locked team with archived defaults can arise only from legacy or directly edited data. If reached, `409 TOPIC_CUSTOMIZATION_LOCKED` (with the shared `topic.write_denied_locked` audit row via `writeLockDenialAudit`) is correct and is tested with a fixture that inserts such a row.

## Decisions (design-level; D1-D14 from exploration stand)

### D15. Shared pure planner
`planDefaultRestore(archivedDefaults, activeNames)` in `@dipstick/shared` (kept deliberately small: one pure function plus the normalizer, no options, no classes; stays server-side only if the dialog preview slips): input archived default rows `{id, name, displayOrder}` and a list of active topic names; output `{ restore: [{id, name}] in restore order, skipped: [{id, name, reason: "NAME_ACTIVE"}] }`. Sort by `displayOrder` ascending then `id` ascending; walk sequentially, adding each restored name to the seen set so a later same-named row skips (D1). The handler assigns positions `base + 1 ... base + k`. The dialog preview calls the same function on the loaded lists. One implementation of the rule. Build note (Engineer): `@dipstick/shared` is consumed from `dist`, so CI and the root test script must build shared before running backend and frontend tests; task 2.1 verifies the root script does this and fixes it if not, so the suite is not order-fragile. If the preview slips, the planner stays server-side with no other change.

### D16. Handler shape
Placed in `topics.ts` next to the other topic routes (the limiter module must not be imported by session, voting or WebSocket code; the structural test stays green). The restore pattern is copied, not factored into a shared cascade helper (the file is already large; unifying is a later refactor). `reply.header("Cache-Control", "no-store")` is set once, first, as the reorder and annotation handlers do, so every exit including the 500 written by the global error handler carries it. No topic row is read before `lockTeamTopics` (the lock-gate check reads only session and lock state). Sequence after the cascade:
1. `BEGIN`; `lockTeamTopics(client, teamId)` (`pg_advisory_xact_lock`, transaction-scoped: an error or dropped connection releases it).
2. Two statements, never one aggregate with names: (a) `SELECT id, name, display_order FROM topics WHERE team_id = $1 AND status = 'archived' AND is_default = true`; (b) `SELECT name, display_order FROM topics WHERE team_id = $1 AND status = 'active'`. The active names are the planner input and `B = max(display_order)` (0 when none) is computed in JavaScript from (b), so the planner and handler read the same rows.
3. Run the planner. **If nothing to restore: `ROLLBACK`** (nothing was written; this releases the lock immediately), then `applyTimingFloor` and `200 {restored: [], skipped}` with no audit row. Skips with nothing restored still return the skipped list.
4. One `UPDATE topics SET status='active', display_order = v.pos, restored_at = now(), restored_by = $actor FROM unnest($ids::uuid[], $positions::int[]) AS v(id, pos) WHERE topics.id = v.id AND topics.team_id = $team AND topics.status = 'archived' RETURNING id`. Both arrays are built from the same ordered `restore` list (ids[i] receives B+1+i; an invariant test asserts it). `archived_at`/`archived_by` are preserved, as in single restore. Statement count is independent of N.
5. One `INSERT INTO audit_log` (`topic.defaults_restored`) in the same transaction; `COMMIT`; then `emitAuditEvent` inside its **own** `try/catch` that wraps only that call: a failure is logged by `request.log.error` (ids and error message only) and never changes the 200. It must not be a broad catch that could also swallow `applyTimingFloor` or `reply.send` errors (the lesson recorded for the TOPIC-002 denial audit). In single restore the emit sits inside the outer try, so an emit throw there would reach `ROLLBACK` after `COMMIT`; bulk deliberately does not copy that.
6. `applyTimingFloor` on every exit, including the thrown path (D22).
The request body is never read by the handler (framework-level parsing is described in D21).

### D17. Concurrency
Everything between steps 1 and 5 happens under the per-team advisory lock, which Add, single restore, archive, reorder and room open all take. Two concurrent bulk requests: the second blocks on the lock, then reads post-commit state, finds nothing archived-and-restorable, returns `200` empty. Positions are above the active max, so the partial unique index `topics_team_active_order` cannot collide. The `WHERE status = 'archived'` guard on the UPDATE is belt-and-braces; if row count differs from the plan, the transaction rolls back and the request fails as a thrown error, answered by the global error handler as `500` with the standard error envelope (`correlationId`, no database detail), never a partial result. The audit-insert failure takes the same path (rollback, `500`). The row-count guard is unreachable under the lock except through an ordering bug or a hand-edited database, so it is otherwise dead code: **forced-failure unit tests** (mock client) cover (a) row-count mismatch, (b) audit-insert failure with a real-DB or mock assertion that every topic is still archived, and (c) `emitAuditEvent` throwing after COMMIT, which must still return 200 and still apply the floor. Requirement (Security M1): a restore never commits without its audit row. Two concurrent bulk requests: exactly one returns the full set and the other an empty `restored`; tests assert union equals the set, intersection empty, one audit row, not which request wins. Further real-DB concurrency tests: bulk racing room open (the session snapshot is the pre- or post-restore set, never a mixture); bulk racing an Add of a same-named custom topic (the rule is evaluated under the lock, so either the Add wins and the default is skipped, or the default is restored and the later Add succeeds as today since Add has no name check; both outcomes deterministic and collision-free); archived rows with identical and negative `display_order` (the legacy migration-18 down shape) produce a collision-free result.

Lock facts (Security L1, verified): `lockTeamTopics` is `pg_advisory_xact_lock`, transaction-scoped. No `lock_timeout`, `statement_timeout` or pool `connectionTimeout` is set for topic writes (`new Pool({connectionString})`; only migrations set lock timeouts), so a stuck holder could block every topic write and room open for that team, and waiters each hold a pooled connection. This is pre-existing for Add, restore, archive, reorder and room open; bulk is no worse (fixed small statement count) and the limiter (120 per 10 minutes per actor) bounds waiters per actor. Noted, not fixed here (follow-up 8.6).

### D18. Limiter and logging hygiene
`attemptedOperation: "topic.defaults_restored"` and `endpoint: "POST /api/v1/teams/:teamId/topics/restore-defaults"` in the `TopicWriteDenialContext`. Every admitted request, including the empty `200` and later 404/409, spends one unit of the actor's existing budget; 429s are not counted. `TOPIC_WRITE_LIMITS` untouched. Logs and event fields carry ids, never topic names. Extending the `topic-write-identifier-hygiene` test to the new route is **mandatory** (it is the control for the denial-context fields), not optional. The new route goes through `enforceTopicWriteRateLimit` itself, not a copy.

### D19. Archived `displayOrder` in `GET /topics/all`
Additive integer on each archived item, read from the existing column (kept and justified in proposal "Review disposition": the dialog promises an order and the duplicate winner depends on it; droppable with the ordering sentence if the PO disagrees). Archive never renumbers, so it holds the prior position; migration 18 notes archived positions are "not maintained", which is why D3 uses it only as a relative sort key with an `id` tie-break, never as a slot to return to). No other contract change.

**Order is best-effort (Engineer S1).** Archive never touches an archived row's `display_order` and reorder renumbers only active rows, so after several archive, reorder and restore cycles archived positions are stale snapshots from different historical orderings and can tie or invert. The `id` tie-break is deterministic but arbitrary (random UUID). Therefore the design promises only what is true: the server places the topics in the order the dialog lists them, and that order is derived from where each topic used to sit, where known. The dialog sentence no longer says anything about prior order (spec: "They will be added to the end of your list, in the order shown."); spec and proposal describe the sort as best-effort. A test with stale, tied and negative archived positions asserts determinism only (same input, same output; bulk equals sequential restores in the same order), not that the order matches what the facilitator last saw. Task 8.2 watches whether facilitators object to the order.

### D20. Frontend
- `canBulkRestore` derives from the loaded data: the exact predicate that shows single Restore (reused, not restated; matrix: admin shown, non-member facilitator shown, member facilitator hidden, participant hidden), the team not locked (same indicator that hides single Restore; a stale view that still posts gets 409, shows the locked notice and refetches), and `planDefaultRestore(archived.filter(isDefault), activeNames).restore.length > 0`. Hidden otherwise (no disabled lecture). Disabled with "Save or discard your edit first." only for a dirty definition draft or an unsaved reorder; "another dialog open" is dropped as unreachable behind a modal. `restoreDialogState` and the new dialog state remain mutually exclusive.
- Dialog per D10 with the literal copy fixed in the spec (singular and plural count, `NAME_ACTIVE` line, single-restore sentence, no forbidden words); skipped ordered by restore order; scrollable list with max height, focusable, names wrapped. Focus trapped, returned to the control on close; result in a polite live region.
- Submit: the confirm button is disabled and shows a busy state while the request is in flight, guarded by a ref plus state as `assigning` is for assign-defaults (a double click would otherwise spend two limiter units and show "Nothing to restore." over the success line). One `fetch`, then the existing `finishAfterTopicWrite` quiet refetch. Result line from the response (D9; delta line "Restored A of P topics. The list changed after you opened this dialog." whenever the actual count differs from the preview). A `200` with empty `restored` renders "Nothing to restore." and no success banner. The transient highlight is deferred.
- Zero-active-topics empty state (#200 overlap): when a restorable set exists, "Restore default topics" is primary and "Assign default topics" secondary with copy that it creates fresh copies; otherwise only Assign remains. `activeEmptyStateVariant` gains the input; its tests grow.
- Error mapping: 403/404/409/429/503 handled as for single restore (429/503 reuse the existing rate-limit notices). On every non-200 response the dialog closes (it must not strand the user on a stale preview) and shows the notice on the screen. 403 (for example a facilitator who joined the team after the page loaded, `FACILITATOR_IS_TEAM_MEMBER`), 404 and 409 (locked) also refetch so the screen reflects the new truth and the control re-evaluates; 429, 503 and a generic 500 leave the list unchanged (transaction atomic) and the user may retry. Focus returns to the control on close.

### D21. Security decisions register (from the security review; each is a decision, not an oversight)
1. **Timing floor measurement (H1).** `TIMING_FLOOR_MS` is a development placeholder (150 ms) with `[PENDING]` measurement fields. Bulk is plausibly the slowest topic write after reorder: two reads, a planner pass, an unnest UPDATE and an audit INSERT whose metadata grows with N. Bulk's authorized latency at N=12 and at the 50-row fixture is therefore added to the floor measurement (alongside reorder at its 200 cap, per the existing TODO-GROUP6 note), and the floor must be at or above the larger p95/p99. Denied exits are cheap and equal because the expensive work occurs only after the role, team and lock gates; the risk is the 200 exits being slower than the denied exits, which only the floor hides. Tasks 4.12 and 4.14 test and measure this. **Requirement:** the empty 200 and the non-empty 200 are deliberately timing-indistinguishable under the floor (they differ in work done). The impact is low (an authorized caller can read `GET /topics/all` anyway) but it is written as a property so a floor regression is caught.
2. **Thrown-path floor (H2): decided, apply it in bulk.** See D22.
3. **No restore commits without its audit row (M1).** Requirement and forced-failure test. An empty 200 writes no audit row and spends one limiter unit; the limiter's own breach logging is the only trace of such requests. Accepted: no state changed.
4. **Audit row content (M2).** The row carries `actor_user_id`, `actor_global_role` (from the authorization result), `actor_ip = request.ip`, `team_id`, `operation`, `metadata`. `request.ip` is the trusted-proxy-resolved address (verified: `trustProxy: 1` in `app.ts`), the same as the other topic writes. Nothing from the request body or headers is logged or stored. Metadata is bounded: `restored` lists every restored id with position (bounded by archived defaults with distinct names, about 70 bytes each); `skipped` is capped at 100 entries with a `skipped_count` carrying the true total; `restored_count` is always present. Provenance: single restore writes one `topic.restored` row per topic and bulk writes one `topic.defaults_restored`, so incident queries for "who restored topic X" must union both operations; the per-row `restored_by`/`restored_at` columns are the authoritative per-topic provenance in both paths (noted in the audit delta and in `docs/deployment.md` audit lookups). Those columns are overwritten on each restore, so the audit log is the only history of earlier restores and its retention matters.
5. **Limiter accounting (M3).** Bulk is deliberately one unit regardless of N; the effect bound is the set of archived defaults (a second bulk call restores nothing), not the limiter. The limiter therefore no longer bounds topics mutated per window the way single restore does; accepted. Role refusal precedes the limiter so a 403-bound caller spends no budget; 429s are not counted; the 503 fail-closed is inherited through `enforceTopicWriteRateLimit`.
6. **Existence oracles (M4).** No new oracle. A byte-identical-404 scenario is added for a nonexistent team (compared with single restore for the same inputs, and with assign-defaults for an admin), in addition to the template team. 200-empty versus 409 reveals lock state to an authorized facilitator, already visible elsewhere. There is no per-topic-id surface.
7. **Retention (M5).** `topic.defaults_restored` rows follow the existing `audit_log` retention policy (`docs/deployment.md`; there is no table-specific purge), the same as every other `audit_log` operation. Stated in the audit delta and in the deployment audit-lookups paragraph.
8. **Global facilitator authority (L2, inherited).** `checkStandingFacilitatorOrAdminAuthorization` admits any non-member facilitator for any team. A compromised facilitator credential can bulk restore defaults on any team; the effect is limited to reactivating archived defaults, reversible by archive, audited and rate-limited, and blocked after the first session by the lock. Recorded for the threat model; no change.
9. **Response headers (L3, verified).** The handler sets `Cache-Control: no-store` first so every handler exit and the global-error-handler 500 carry it; the limiter's 429 and 503 set it themselves (`topic-write-rate-limit.ts`). The `authMiddleware` 401 does **not** set it (verified in `auth/middleware.ts`); that is pre-existing, carries no data, and is out of scope. Tests assert `no-store` for 403, 404, 409, 200, 429, 503 and the 500; no assertion on the 401.
10. **CSRF, Origin and body handling (L4, verified).** There is no CSRF token and no HTTP Origin check (the Origin check in `realtime/origin-check.ts` is WebSocket-only). The control for cross-site POST is the session cookie `SameSite=strict` plus `httpOnly` (`app.ts`), together with a CORS allowlist (`getAllowedOrigins`), which is not itself a block on simple requests. A cross-site form POST therefore arrives without the session cookie and receives 401. This applies to every state-changing route and bulk adds no exemption and no new control. Body handling: the handler never reads `request.body`, but Fastify parses by content type before the handler runs, and no `bodyLimit` is configured, so the framework default of 1 MiB applies. Consequences, which correct the proposal's earlier "not parsed, not rejected" wording: `application/json` is parsed (malformed or empty JSON yields a framework 400), `text/plain` is buffered up to the limit, an unknown content type yields 415, and a body over the limit yields 413. All are pre-handler, issue no topic query and change no state. The client sends no body and no Content-Type (as `assignDefaults.ts` does). A test sends a small `text/plain` body, a form-urlencoded body, a junk JSON body and a body over 1 MiB and asserts: no state change, no 5xx, no body content in logs.
11. **Name comparator (M6).** See V2: the shared normalizer is a UX hint, not an identity check; a doc comment says so.

### D22. Thrown path applies the timing floor in bulk (Security H2, decided)
Bulk diverges from single restore here. Single restore's catch is `ROLLBACK; throw err` and skips `applyTimingFloor`. Bulk adds two deliberate throw sites (row-count mismatch, audit-insert failure), reachable only by a caller who has passed every gate, so the gap is not an existence oracle for unauthorized callers; but "consistent with a known defect" is not a security argument and the fix is three lines: `catch (err) { try { await client.query("ROLLBACK"); } catch (rollbackErr) { request.log.error(...) } await applyTimingFloor(startTime); throw err; }` (the original error is rethrown even if ROLLBACK fails, and `client.release()` stays in `finally`). The 500 is then produced by the global error handler as before, with the floor already served. The thrown-path exemption is removed from the bulk spec; a unit test asserts the floor on both forced throw paths. Follow-up 8.2 is narrowed to the *other* topic writes (TOPIC-003..007) and names an owner at filing; it does not carry bulk, so no security exception with an expiry is needed. The extra delay on a 500 is acceptable (error rate is near zero).

### Recorded deviation (7.1): `addCustomTopic.ts` appears in the diff
D1/V2 said to leave `addCustomTopic.ts` alone (no shared normalizer coupling), while D20 and task 5.7 require `activeEmptyStateVariant` to take the bulk-restorable input, and that function lives in `addCustomTopic.ts`. The two instructions conflict; the diff resolves it by touching only `activeEmptyStateVariant` and its union type (a fourth optional boolean, a new `unlocked_restorable` variant). `findDuplicate` and the duplicate-hint logic are unchanged and not used for bulk, so the coupling D1 feared did not occur. The 7.1 diff check therefore reads "absent except `activeEmptyStateVariant`". If the function grows another input it should take an options object (not in this change).

## Risks / Trade-offs

- **Customs first, defaults last.** A tailored team that restores defaults gets them after its customs. Accepted and stated in the dialog; worst-case reordering cost is the existing reorder UI. Mitigation is honest copy, not a hidden reorder (FR-2.7).
- **Bulk stricter than single restore for skipped topics.** Deliberate: skipped topics stay archived and single restore remains available. Follow-up recommended, not bundled.
- **Archived defaults after #200 recovery stay archived indefinitely** because fresh active copies share their names. Acceptable; the control is hidden when nothing is restorable.
- **Preview/actual drift under concurrency.** The server recomputes under the lock and ignores client input; the result view reports the delta (D5).
- **Audit without names** reduces forensic readability; ids join to `topics` for anyone with database access, and the row is for operators, not teams.
- **Amplification.** Bounded by archived defaults with distinct names; statement count independent of N. See D21 item 5 for the limiter consequence.

## Migration Plan

No migration. `audit_log.operation` is unconstrained text and `team_id` has no foreign key. Deploy order is irrelevant (additive endpoint; additive response field). Rollback: remove the route and control; no data to undo (restored rows are ordinary active topics).
