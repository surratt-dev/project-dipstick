# Facilitator Review — "Facilitator Team Membership Constraint Violation" (Issue #46)

**Reviewed by:** Priya Nair (Facilitator persona, subject matter expert)
**Reviewing:** Devon's exploration notes (`exploration-notes.md`), recommending #46 be closed as a duplicate of #43/PR #153, with no new proposal/design/implementation.

I read this the way I'd read any change that touches the boundary of the facilitation role: not "does the code do what it says," but "would I, running my Tuesday session for a team I don't belong to, ever notice this was built carelessly." Devon's technical read is thorough. I checked it against the use case's own language, line by line, and independently re-verified the one claim Devon flagged as wanting a second pair of eyes.

## Observations

**1. Acceptance criteria, checked one at a time against `requirements/use cases/02 - Session Setup - Use Cases.md`, "Facilitator Team Membership Constraint Violation":**

- "The team selection list shown during session creation excludes all teams the authenticated user belongs to." — `GET /api/v1/teams/eligible-for-session` (`facilitator-sessions.ts:1819-1837`) does this with a `LEFT JOIN team_memberships ... WHERE tm.id IS NULL AND removed_at IS NULL`, live on every call, no caching. Met.
- "If the user belongs to all teams in the application, the session creation screen shows no available teams and explains why." — `SessionCreationPage.tsx:210-216` renders a specific empty-state message keyed off `callerHasTeamMemberships`, distinct from the zero-home-team case. Met, and it's the *right kind* of met — two different reasons get two different sentences, not one generic "nothing here."
- "A server-side check prevents session creation for the user's own team regardless of how the request is submitted." — the `is_member` check in `POST /draft` (`facilitator-sessions.ts:261-289`) runs on every request to that endpoint, UI or not. Met.
- "The error message, if shown after a rejected submission, is clear and does not suggest a workaround." — "A facilitator cannot create a session for a team they are a member of." States the rule, stops there. I specifically looked for the failure mode I'd flag hardest — the message implying there's a way around it, or making the rejection feel personal — and it isn't there. Met.

**2. Main Flow and Alternate Flows, walked step by step:** picker excludes owned teams before the facilitator ever sees a list (steps 1–4); empty-eligible-list state offers no session-creation path (step 5, confirmed — the picker only renders `picker-team-list` when `eligibleTeams.length > 0`, otherwise only the empty-state paragraph); direct-API bypass is rejected server-side with an authorization error and no session created; the race-condition alternate flow ("membership changes between page load and submission") is re-validated at submission — I confirmed this isn't just asserted in the spec but has a real code path and a matching test (`facilitator-sessions.test.ts:208-237`, test id 2.3/2.6/2.7) and a dedicated spec scenario ("Membership acquired after the eligible-teams list was fetched is caught at submission"). All present.

**3. The multiple-team-memberships claim — independently re-checked, not taken on Devon's word.** Devon's notes flag this as the one thing worth a second reviewer confirming rather than trusting self-review. I went to the schema directly rather than re-reading the same query Devon already read: `migrations/2_create_tables.sql:34` has `CONSTRAINT team_memberships_unique UNIQUE (team_id, user_id)` — the uniqueness is per (team, user) pair, not per user. Nothing in the schema limits a user to one team. That structurally confirms a facilitator can hold N active memberships, and the `POST /draft` check (`tm.team_id = $2` scoped to the one `:teamId` in the URL) blocks each one independently on its own request — there's no "home team" concept anywhere in this path to break on a multi-membership user. I'm satisfied this isn't a latent assumption; it's actually impossible for the current query shape to special-case a single team even if someone wanted it to.

**4. Rejection messaging, from the experience a facilitator actually has — not just the message text.** Because the picker excludes owned teams up front, a facilitator using the app the normal way will essentially never see the 403 at all. It only surfaces in the race-condition case (joined a team via link between list-fetch and submit) or a direct API call. When it does fire, the confirm screen doesn't strand the facilitator — the "Back" button stays available alongside the error (`SessionCreationPage.tsx:157-161, 183-190`), and the stale list is marked for re-fetch on return to the picker rather than silently reused (`listStale` / `task 6.5`, matching the spec's explicit scenario for this). This is the detail I'd have pushed back on if it were missing — an error that leaves the facilitator with no way forward feels like a wall, not a guardrail.

**5. One nitpick, not a gap.** The "You're already a member of every team in the organization" empty-state copy fires whenever `callerHasTeamMemberships` is true and `eligibleTeams` is empty. That's also the state produced if the facilitator belongs to only some teams and every *other* team happens to be deactivated — the copy would then overstate things slightly (they don't literally belong to every team). This matches the spec's own scenario definition verbatim ("member of every other non-deactivated team"), so it's not a deviation from what was speced — just a spot where the speced behavior is a little more generous with the word "every" than a pedantic reading would want. Not something I'd hold up a close for.

**6. Confirm screen context matches what I actually need as a rotating facilitator.** The confirm screen shows team name plus `lastSessionAt` (`SessionCreationPage.tsx:148-155`), not just a bare name — which is the detail that matters when I'm choosing among three teams on a rotation and need to recognize which one I'm about to commit to before I click. This is called out explicitly as a requirement in `session-creation/spec.md` ("Confirm screen shows more than the bare team name"), and it's implemented, not just speced.

## Verdict

I agree with Devon's recommendation. I checked the use case's acceptance criteria, main flow, and alternate flows against the shipped code and tests directly — not against the exploration notes' description of them — and found nothing missing. The one claim Devon flagged as wanting independent confirmation (multiple team memberships handled without a "home team" special case) checks out at the schema level, independent of the query-reading Devon already did. The rejection experience doesn't create the kind of awkward, judgment-feeling dead end I'd have flagged as a trust problem, and the picker's exclusion means most facilitators will never see that rejection at all.

**The use case is fully satisfied by what's already shipped. Nothing further is needed under #46.** I'd close it as a duplicate of #43 / PR #153, same as Devon recommends.
