## On the specific question: is the "no team_memberships call occurred" proof shape sound, or could it false-positive?

I traced through the failure mode carefully because this is exactly the kind of test that can look like it's testing something when it's actually testing nothing (Marcus's words, not just mine — I don't ship tests that don't explain what they protect).

The mechanism: `mockDbQuery` is a bare `vi.fn()` with no default `mockResolvedValue` set anywhere in the file (confirmed — grepped for `mockResolvedValue(` at the top level, found none; every describe block only does `beforeEach(() => vi.clearAllMocks())`, which clears call history but not queued implementations). The new test queues exactly one `mockResolvedValueOnce` for the `sessions` read.

Suppose, hypothetically, a future change adds a `team_memberships` query to this handler as a regression. Two sub-cases:

1. **The code awaits the result and uses it** (e.g., a new membership-based gate). The second `db.query` call has no queued mock value, so it falls through to the bare `vi.fn()` default, which resolves to `undefined`. `undefined.rows` throws a `TypeError` inside the async handler. `buildApp()` registers no custom error handler, so Fastify's default handler catches it and returns 500. The test's `expect(res.statusCode).toBe(200)` fails — caught, independent of the `team_memberships` string-search assertion.
2. **The code fires the query but doesn't meaningfully use the result** (dead code, logging-only, a swallowed `.catch()`, fire-and-forget without `await`). Case 1's crash doesn't happen, and a naive "assert response shape only" test would pass right through this regression — which is exactly the false-positive shape the team lead is asking about. But this test doesn't only assert response shape: it separately asserts `mockDbQuery.mock.calls` contains no call whose query text includes `team_memberships`. That assertion fires the instant `db.query(anything-containing-that-string)` is *invoked*, regardless of whether the call is awaited, whether its result is used, or whether it succeeds or throws. So case 2 is caught too.

The one real gap — and it's the same gap the design doc already names and accepts for test 3.7's precedent — is a query that references the `team_memberships` table without the literal substring `"team_memberships"` appearing in the string passed to `db.query` (a differently-aliased CTE, a query built via string concatenation from a variable, a raw client bypassing `db.query` entirely via `db.connect()` a la the transaction-based routes elsewhere in this file). That's a known, inherent limit of string-matching on mocked SQL, not a defect introduced by this specific test, and the design's Risks/Trade-offs section already accepts the equivalent risk for the existing pattern. I don't think it's worth trying to engineer around here — a parser-based assertion would be new infrastructure for a coverage-only, zero-production-risk change, which cuts against the stated Non-Goals.

Net: the proof shape is sound for the claim it's actually making ("no query naming `team_memberships` is issued by this handler"), and it fails loudly on the regression shapes that matter. It is not — and doesn't claim to be — a proof that no *future* mechanism could ever reach `sessions` from a membership change through some entirely different code path (a new endpoint, a new job). That's a scope limit correctly acknowledged by the "Non-Goals" section, not a hole in this test.

## Gaps worth flagging before implementation

1. **New `describe` block needs its own `beforeEach(() => vi.clearAllMocks())`.** Every other describe block in the file has one (confirmed by grep — 11 instances, one per block). Task 3.1 doesn't spell this out. If omitted, `mockDbQuery.mock.calls` could carry over calls from whatever test runs immediately before it in file order, which would corrupt the "no team_memberships call" assertion (false negative on a passing case, or worse, masking behavior depending on ordering). Trivial to get right by following the file's own convention, but worth calling out since tasks.md is otherwise this precise about everything else.
2. **Task 2.2's isolation requirement is real and needs a second look at implementation time.** The draft-session endpoint issues at least three queries per request in some paths (actor query, team-exists check, audit-log insert per test setup at lines 210-211). The `.find()` predicate for task 2.1 needs to key on something that uniquely identifies the actor query — `"FROM users u"` looks right based on the query literal at line 207, but whoever implements this should confirm no other query call in that same describe block's mock sequences also contains that substring before trusting `.find()` to return the right call.
3. Minor: design.md's line citations for the eligible-teams query (1827-1834) and draft-session query (204-217) are a few lines looser than the actual boundaries I found. Doesn't affect implementability since tasks.md doesn't rely on those exact numbers, but if design.md is meant to stay a durable reference, it'd be worth tightening to 1819-1836 and 204-213 respectively. Not blocking.

## Coupling risks

None beyond the above. This is genuinely test-only: no production file changes, no new shared types, no new endpoints. I don't see any risk of this test suite change destabilizing CI timing (three new tests, all synchronous mock-based, no new async fixtures) or interacting badly with the existing 1974-line file's structure — it slots in as a new trailing `describe` block plus two inline test additions to existing blocks, consistent with how every other addition to this file has been made.
