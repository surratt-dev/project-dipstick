## Why

GitHub issue #117 is Decisions H and I (`openspec/changes/archive/2026-09-16-restrict-team-005-em-promotion/design.md`) finally getting the artifact they were always going to need. Those decisions named the on-call Production Data Engineer as owner and set a deadline of 2026-09-23 — one week from the 2026-09-16 fix — for running a detection query against production `team_memberships`/`audit_log` data, and a companion query to annotate historically mislabeled audit rows. Nothing was built. Today is 2026-09-29: the deadline is six days past due, not "at risk." tasks.md task 6.4 in the archived change flagged exactly this failure mode ("if archiving happens before 2026-09-23, the pending query execution should be tracked as an explicit follow-up item rather than silently dropped") — that is precisely what happened, and #117 is the follow-up surfacing late rather than never. This proposal exists to give the named owner a correct, safe, handoff-ready artifact to run, honestly dated against the missed timeline rather than written as if still inside the original window.

## What Changes

- Add `packages/backend/migrations-manual/8_phantom_em_detect.sql` — a reusable, re-runnable, **read-only** query implementing Decision H/G's detection control: any active `team_memberships` row with `role = 'engineering_manager'` and no corresponding `team.manager_established` `audit_log` entry for that `(user_id, team_id)` pair. Safe to run any number of times by anyone with read access; this is the ongoing detection control (Decision G), not a one-shot.
- Add `packages/backend/migrations-manual/8_phantom_em_annotate.sql` — a separate, idempotency-guarded script implementing Decision I's companion query: identifies historical `audit_log` rows where a `participant → engineering_manager` transition was recorded as `team.role_changed` (mislabeled, because it predates the TEAM-005 fix) and inserts one additive `team.manager_established_retroactive_annotation` row per match, referencing the original row's id. Re-running it after a successful pass inserts zero rows.
- These are **two separate files run as two separate, deliberately-invoked commands** — never one script that runs both in a single pass. The annotation step (a write against an append-only audit table) must never be an accidental consequence of running the detection step. This split is a structural requirement carried forward from exploration, not a style preference, and design.md must not collapse it.
- Add a named place to record what the scripts actually found when someone runs them: `openspec/changes/phantom-em-relationship-detection/query-result.md`, templated with fields for run date, environment confirmed, operator, Query 1 row count (and rows if non-zero), Query 2 row count, and notification recipient/channel if Query 1 found anything.
- Carry forward two decisions, unresolved by this proposal, for the Solution Architect to settle in this pipeline's Stage 3 design review:
  - **Decision J (new):** what value populates `audit_log.actor_user_id` and `actor_global_role` for a script-generated row, given there is no logged-in application actor for a `psql` session. Exploration names a candidate shape (the operator's own `users.id` as a mandatory parameter with no default; a fixed literal like `'system:production_data_engineer'` for `actor_global_role`) but does not decide it.
  - **The notification recipient/channel:** Decision H's deliverable shape ("checked, N found, here's who was notified") names no recipient, channel, or owner for notification, and doesn't say whether notifying is itself in scope versus something the operator improvises. Design.md must name a recipient and state explicitly that notification is escalation, not remediation — it does not authorize the operator to revoke or modify a flagged row.

**BREAKING:** none. No application code changes; no schema changes beyond nothing (no migration is added — these are explicitly *not* `node-pg-migrate`-discovered migrations).

## Impact

- **New files only:** `packages/backend/migrations-manual/8_phantom_em_detect.sql`, `packages/backend/migrations-manual/8_phantom_em_annotate.sql`, `openspec/changes/phantom-em-relationship-detection/query-result.md`. No existing file is modified.
- **No application code changes.** `packages/backend/src/routes/teams.ts` (TEAM-005's `team.role_change_denied` write at lines 821–847, `team.role_changed` write at lines 969–985; TEAM-006's `team.manager_established` write at lines 1291–1307) and `packages/backend/src/auth/audit-logger.ts` were read to confirm the join keys, metadata shapes, and the append-only invariant these scripts depend on — none of them are touched.
- **Preserved invariant:** `audit_log` is append-only in this codebase (confirmed by inspection — no UPDATE or DELETE against it anywhere in `packages/backend/src/`). Decision I's annotate-don't-rewrite approach depends on this holding; these scripts must never introduce the first write path that violates it.
- **Preserved correctness fix:** the annotation query's `operation = 'team.role_changed'` predicate must stay explicit and must not be dropped or "simplified" — without it, the query also matches TEAM-005's post-fix `team.role_change_denied` rows (same `from_role`/`to_role` metadata shape, different operation), which would manufacture phantom annotations for promotions that never completed.
- **Owner and execution:** the on-call Production Data Engineer, against production, outside this pipeline's access. This change delivers the artifact; it does not deliver an executed result or a remediation program (out of scope per Decision H, unchanged here).
- **This change's completion is "artifact ready," not "checked."** Merging this proposal does not close Decision H or Decision I. Those decisions close only when the named operator has actually run both scripts against production and `query-result.md` records a real run date, operator, and row count (and notification recipient/channel, if Query 1 found anything). Until that entry exists, Decision H and Decision I remain open — no downstream review, PR description, or archive note should characterize them as resolved on the strength of this change alone.
- **Timeline:** this proposal is written 2026-09-29, six days after the original 2026-09-23 target. **New execution deadline: 2026-10-08** — ten calendar days from today, allowing roughly a week for this pipeline's remaining stages (Stage 3 design review resolving Decision J and the notification recipient, tasks review, implementation) plus a few business days of buffer for the on-call Production Data Engineer to run both scripts after handoff. This is a committed date, not a placeholder for a later stage to fill in. **Escalation path if 2026-10-08 passes without a `query-result.md` entry:** whoever performs the handoff (tasks.md 5.3) must, at handoff time, also put in place a tracking mechanism that does not depend on this pipeline noticing a second miss on its own — silent pipeline self-tracking is exactly what let the original deadline lapse for six days. If the date slips anyway, escalate directly to Rachel Okonkwo, VP of Engineering, who set the original 2026-09-23 deadline and remains the Executive Stakeholder for this change.
