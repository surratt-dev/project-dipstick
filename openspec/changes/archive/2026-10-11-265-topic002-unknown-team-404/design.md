## Context

TOPIC-002 (`GET /api/v1/teams/:teamId/topics/all`) reads the team name with `SELECT name FROM teams WHERE id = $1` after the admin arm, and treats a missing row as an empty name (`teamName: ""`), which yields an empty `200` and, for an admin, an audited access row with `team_found = false`. The write routes already answer a missing team with `404` through `checkWritableTeam` and `teamNotFoundEnvelope()`. This design closes the read-side gap without disturbing the audit stream or the facilitator's query profile.

## Goals / Non-Goals

Goals: 404 for a team id that names no team, after authorization; no audit row on that 404; no new query for a facilitator; no ghost-team admin audit rows; a clear screen state.

Non-goals are listed in the proposal. Notably: no change to TOPIC-001, the template team, deactivated teams, or live session routes.

## Decisions

### D1. Order: boundary 404, authz 403, role assertion, name read 404, admin arm
The existence check sits after the shared authorization check and the role assertion, before the admin arm. Why after authorization: an unauthorized caller (a participant) must see a response identical for an existing and a non-existent team. Checking existence first would let any authenticated user enumerate team ids by 404 vs 403. This holds only while the authorization helper and role assertion never touch `teams` for the unauthorized case (the helper reads membership and role data; `audit_log.team_id` has no FK, so the #264 denial row inserts for a non-existent team too). A test pins it: an unauthorized caller (participant, member-facilitator) hitting a non-existent team triggers zero `teams` queries, so a later refactor that adds a `teams` join to the helper fails loudly. The existence check stays in the TOPIC-002 handler and is not pushed into the shared helper (also used by TOPIC-004 and the write routes). A standing facilitator with no membership on a missing team is authorized (no `team_memberships` row can exist), so the real path is facilitator + unknown team = 404, tested explicitly. Why before the admin arm: the arm computes `membership_role` and `actor_idp_roles_include_em` and writes the audit row. Placing the check after it, "to keep the arm's prefix reads identical", would keep emitting ghost-team rows and spend membership and role-set reads and audit-write failure paths on non-events. Tests pin both orders.

### D2. The 404 is deliberately not audited (policy question open: see proposal)
- Signal quality: an audit row for a non-existent team records access to nothing and dilutes the `admin.topic_config_*` stream, which exists to show every time an admin reached into team topic configuration.
- Consistency: write routes already do not audit missing-team 404s; this keeps the read consistent.
- Flooding is NOT a justification. The #264 denial path already lets any authenticated caller (every participant) write one `topic.config_list_denied` row per request with a random UUID, including for non-existent teams, because the denial is audited before existence is known and `audit_log.team_id` has no FK. That `audit_log` growth exposure exists today and this change neither creates nor fixes it. It is a **named residual**: unbounded 403 denial rows with attacker-chosen `team_id` values (UUID-typed, so no injection; they pollute per-team audit queries via `idx_audit_log_team`, low severity). Follow-up options, out of scope here: a per-actor rate limit, or collapsing repeat denials per (actor, reason, window). Owner: Brian to file the follow-up issue when he answers the merge gate.
- The asymmetry (403 audited, 404 not) is intentional and must not be "fixed" by a later tidy-up. It is a policy question for Brian / the VP of Engineering; implementation follows the issue meanwhile. If the answer changes, only the 404 branch changes.
- Accepted risk, stated plainly: after this change an admin (or a hijacked admin session) can probe whether team ids exist with unlimited attempts and leave no durable trace and no log event of any kind. Team ids are random v4 UUIDs so blind enumeration is infeasible and the data revealed is one bit, but an incident responder loses the failed attempts of a reconnaissance pattern. We deliberately add no structured log line for it (scope cap per the Executive review). This residual is part of the merge-gate question to Brian.

### D3. Mechanism: move the existing name SELECT earlier; add no query
Issue #265 mentions both "reuse `SELECT id`" and "fold into the name query". We take the second: move the existing `SELECT name FROM teams WHERE id = $1` ahead of the admin arm. A found team has its name in hand, a missing team becomes the 404. A standing facilitator therefore executes exactly the pre-change multiset of SQL texts (a test asserts equality, not a bound), so the #259 SQL-text-count test needs no change and no facilitator gains a query. A new `SELECT id` would add one and break that test. On the admin path only the absence of membership-role and role-set reads on 404 is required. The admin mock fixtures in `content.test.ts` are query-order-sensitive (the helper that returns "no row" for the team-name SELECT); task 0.4 settles whether they dispatch by SQL text or by position and sizes the churn before the handler is touched. Two code comments become false and are fixed as tasks: the handler comment above the admin arm ("Both reads run before any team-name/topic/lock read ..." and "Every admin request runs the same prefix (helper row -> membership row -> role-set row)", now name row first) and the `audit-logger.ts` comment.

### D4. Lookup semantics
No `deactivated_at` filter and no template-team exclusion (matches `checkWritableTeam` and Decision 11; do not share a helper that rejects the template). The 'no mid-request deletion' assumption rests on no application route deleting a `teams` row (only test cleanup and a seed rollback do); it is an observed property, not a schema guarantee, and the race is accepted. `__default_topics__` is a real row, so it stays `200` with the admin row. "Names no team" is keyed on the absent row, never on empty lists; a team with zero topics is `200`.

### D5. Response
`await applyTimingFloor(startTime)` then `noStore(reply).code(404).send(teamNotFoundEnvelope())`, mirroring the 403 path. Never the literal string (structural test; run `team-not-found-envelope-structural.test.ts` early, since it may count call sites). Unlike `checkWritableTeam`, the read route sends `no-store`; the divergence is intentional. The test mechanism is a spy on `applyTimingFloor` asserting one call, ordered before the reply send. If the team-name read itself throws, the existing 500 path applies and no audit row is written, for a facilitator and an admin alike; for an admin the failure now precedes the membership and role-set reads (still fail-closed: no data, no audit row), and a test covers the admin case. The 404 emits no audit event of any kind (no `admin.*`, no `topic.*` denial event; `topic.config_read_denied_role` belongs to TOPIC-001, not this route). The floor is a call-site requirement only. The spy test proves placement, not equivalence, and must not be cited as evidence that timing is flat. An authorized unknown-team 404 does less work than a 200, so its raw latency is shorter; the floor flattens it, its adequacy is out of scope, and callers reaching it are already authorized. Indistinguishability of 404 from 200 for authorized callers holds only up to the measured floor; the floor is the existing unmeasured 150 ms placeholder that already blocks production startup (`timing-oracle.ts`), and this change does not alter that blocker. The admin-404 path also skips the membership and role-set reads, which is the origin of its extra gap; same reasoning.

### D6. `team_found` removed, not kept constant
After D1 the admin arm only runs for existing teams, so the key is always `true`. A constant key reads as a live check later. Removed from the row metadata (exact key set) and `teamFound` from the event; the `audit-logger.ts` comment is fixed. Historic rows may carry the key with either value and are not rewritten. The repo grep found only tests, docs and comments. A task for the human (whoever owns log queries, SIEM saved searches and dashboards) records whether any external consumer reads it; the outcome is an acceptance condition (AC 12). Historic rows carrying `team_found: false` are the only evidence of past ghost-team admin reads: no retention job may purge them as noise. Because `metadata->>'team_found' = 'false'` now matches only pre-change rows, the cutover (PR number and date) is recorded in the docs so an analyst does not read the absence as no incidents.

### D7. TOPIC-001 vs TOPIC-002
TOPIC-001 is session-scoped and decides authorization before lookup, so an unknown team yields `403`; TOPIC-002 is role-scoped and, once the caller's role is authorized, an unknown team yields `404`. This sentence goes into the REST API Contract so the two answers do not look like a bug.

### D8. Frontend
In `loadTopics` only: a `404` whose JSON body has `error.code === "TEAM_NOT_FOUND"` sets the error to exactly "Team not found." (full stop included), rendered from a literal constant in the page, never from `body.error.message`, so a server wording change cannot silently alter the copy and nothing from the response is reflected. The code check is a sibling helper (or inline condition) such as `hasEnvelopeCode(body, "TEAM_NOT_FOUND")`; `hasEnvelopeMessage` and the 403 branch are not widened. The body is parsed defensively as the 403 branch does, including a JSON body whose `error` is not an object (generic message). A non-canonical team id in the URL gets the same envelope from the boundary check and shows the same state. The page does not echo the team id and sends neither the URL nor the id to any client-side error reporter. Any other non-ok response, including a proxy 404, an empty or non-JSON 404 and a JSON 404 with another code, keeps "Failed to load topics.". The state is the existing error state (`role="alert"` paragraph, "Back to team" link), so there is no list, definition block or write control, no empty-shell flash (the page already shows "Loading topics..." until `loading` clears), and no new component or navigation. A `TEAM_NOT_FOUND` from a write action keeps its existing handling.

Quiet refetch: `fetchAllTopics` already never calls `setError`, so a refetch that fails (404/403/500) after a successful load cannot blank the screen, and each caller already surfaces its own inline failure. We add a test pinning that and no code. Rejected: a new shared inline notice (new UI, out of the capped scope). If the test shows a path that does blank the screen, that path is deferred to a follow-up issue.

## Risks / Trade-offs

- Authorized callers learn whether a team exists (accepted by the issue).
- No durable trace of an admin's failed existence probes (see D2); accepted, part of the merge gate.
- The existing 403 denial-row flood (D2) remains.
- Timing residual in D5.
- Keyed on row absence: a future shared helper that filters the template team or deactivated rows would silently change behaviour; regression tests pin both.
- Removing `team_found` changes a pinned key set; downstream consumers, if any, read undefined. Mitigated by the verification task.
- Stale-link confusion is not fully solved (deactivated teams and remembered ids are follow-ups).

## Migration Plan

No migration. Ship backend and frontend together; the frontend degrades to "Failed to load topics." against an old backend and the backend change is independent of it. Rollback is a plain revert. Docs record the cutover (PR and date) for `team_found` readers.
