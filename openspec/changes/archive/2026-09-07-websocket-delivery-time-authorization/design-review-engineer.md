# Design-Stage Review: websocket-delivery-time-authorization

**Reviewer:** Marcus Oyelaran, Full Stack Engineer (lead implementer)
**Stage:** Design (design.md, proposal.md, tasks.md — all reviewed against actual code in `packages/backend/src`, not taken on the document's word)
**Date:** 2026-09-07

---

## 0. Bottom line

This is buildable, and the transport/fan-out decisions (D1, D2) are the right calls for what this codebase actually is — I'd have made the same ones. The grant-shape claims check out verbatim against the code, the audit-logging correction (D7) matches the real schema and the `em-views.ts` precedent exactly, and the Blocking Dependency boundary is drawn in the right place: I went looking for the "implementer discovers mid-sprint" failure mode and didn't find it in the reveal/topic-advance/membership seam — that one's actually clean.

I found four things this document doesn't have that it needs before Tasks starts, none of which require reopening the transport decision:

1. **The design never says the Redis pub/sub subscriber needs its own connection, separate from the shared `redis` singleton.** This isn't a style nit — if an implementer wires `.subscribe('ws:events', ...)` onto the same `Redis` instance imported from `redis.ts`, every other consumer of that instance (health checks, OIDC login, the session store) breaks the moment the first subscription happens, because an ioredis connection in subscriber mode can't run ordinary commands. Section 1.
2. **No Origin validation on the WebSocket upgrade.** The design leans on `request.session` for connection-time auth (SEC-28) and that part is sound, but a WS upgrade handshake is exempt from CORS preflight — a malicious page can open a WS connection to this server and the browser will still attach the session cookie. Nothing in three review rounds (Facilitator SME, BA, Executive) touches this. Section 2.
3. **`topic_history_update`'s authorization is narrower than the HTTP endpoints serving the same content**, and the design doesn't explain why. `GET /api/v1/teams/:teamId/topics` and `/action-items` allow `member` *and* `facilitator` grants; the WS event's per-event mapping table allows only `member` (Path 1/2) and is silent on Path 3. Section 3.
4. **Two concrete error paths the design's error-path list is missing:** what happens to in-flight events during an ioredis reconnect window (pub/sub has no replay — a dropped subscriber connection silently loses whatever was published while it was down), and what `ws`'s `.send()` actually does across `CLOSING` vs. `CLOSED` readyState, which the D2 "implicit deregistration on throw" mechanism depends on being reliable. Section 4.

None of these are "start over" findings. All four are additions to Migration Plan / tasks.md, not architecture changes.

## 1. Redis: the shared client cannot also be the pub/sub subscriber — verified against `redis.ts` and every consumer of it

`packages/backend/src/redis.ts` is the entire file:

```ts
import { Redis } from "ioredis";
import { config } from "./config.js";

export const redis = new Redis(config.REDIS_URL);
```

One singleton instance, imported directly (not via a factory) by:

- `packages/backend/src/app.ts` — passed into `createRedisStore(redis)` for `@fastify/session`'s Redis-backed store (`.setex`, `.get`, `.del` on every session read/write)
- `packages/backend/src/routes/health.ts:20` — `await redis.ping()`
- `packages/backend/src/routes/auth.ts:44,87` — `.setex` / `.getdel` for OIDC state

This is a plain ioredis client used for ordinary commands. The moment any code calls `.subscribe()` on this same instance, ioredis puts that connection into subscriber mode, and per ioredis's own contract, a connection in subscriber mode can only run `subscribe`/`unsubscribe`/`psubscribe`/`punsubscribe`/`ping`/`quit` — every other command (`get`, `setex`, `getdel`, the session store's reads) starts throwing. Wire this up naively — which is the obvious first thing to write, since `redis.ts` is the only Redis handle in the codebase and nothing in design.md or tasks.md says "don't reuse it" — and you take down health checks, login, and session resolution on every pod the instant its subscriber connects. This isn't a hypothetical; it's the default outcome of following Decision D2 as written ("`ioredis` is already a dependency... reuse it") without an implementer independently knowing the ioredis subscriber-mode gotcha.

**What's missing, concretely:** Migration Plan step 4 and tasks.md 1.3/1.4 need one explicit line: the subscriber uses a *second* connection, created via `redis.duplicate()` (ioredis's standard pattern for exactly this case — a duplicated client shares connection options but is a separate TCP connection, free to enter subscriber mode without affecting the original). The publisher can keep using the existing shared `redis` client (`PUBLISH` is a normal command, no mode change). This is a small addition — one `redis.duplicate()` call and a one-sentence comment explaining why — but it's load-bearing enough that I'd want it in the document, not left for whoever writes task 1.3 to discover by reading ioredis's error message in CI.

## 2. Missing error/security path: Origin validation on the WS upgrade (CSWSH)

Design D1 says connection-time authentication is "the existing session validation applied to the upgrade request, not a new mechanism," and that's correct as far as it goes — `@fastify/session` resolves `request.session` via an `onRequest`-stage hook, and `@fastify/websocket`'s upgrade handling runs through Fastify's normal request lifecycle (hooks included) before the handler takes over the socket, so `request.session` genuinely is populated and valid by the time a WS route handler runs. I verified this holds structurally; it's not a false claim.

What's not addressed anywhere in design.md, the spec, or three rounds of review (Facilitator SME, BA, Executive — I grep'd all of them for "origin" and "CSWSH" and came up empty): **a WebSocket upgrade handshake is not subject to the Same-Origin Policy's CORS preflight.** `packages/backend/src/app.ts` registers `@fastify/cors` with an origin allowlist for ordinary HTTP requests, but that plugin's enforcement doesn't extend to the WS upgrade path the way it does to `fetch`/XHR. A page on any origin can open `new WebSocket("wss://this-host/ws")` from a victim's browser, and the browser will still attach the `dipstick:session:*` cookie on the handshake request — because cookie attachment follows the cookie's own domain/SameSite rules, not CORS. If `SameSite` on the session cookie is `Lax` (the common default, and worth confirming against `session-store.ts`'s cookie config, which this file doesn't set directly — that's set wherever `@fastify/session` is registered in `app.ts`), a cross-site page can silently open an authenticated WS connection as the victim. This is the standard "cross-site WebSocket hijacking" (CSWSH) class of bug, and it's exactly the kind of boundary-between-frontend-assumption-and-backend-contract failure that doesn't show up until someone builds it against a hostile page.

**What I'd add:** a `preHandler` or `onRequest` check inside the WS route registration that inspects `request.headers.origin` against the same allowlist `@fastify/cors` already uses in `app.ts`, and rejects the upgrade (before `request.session` is even consulted) if it doesn't match. This is a small, mechanical addition — the allowlist already exists — but it needs to be a named task, not an assumption that "session auth" covers it, because session auth and origin validation are answering different questions (who is this cookie's owner vs. is this request coming from a page we trust to hold that cookie).

## 3. `topic_history_update`'s authorization is narrower than its own HTTP analog, unexplained

Design D3's per-event mapping table:

| Event | Check to reuse |
|---|---|
| `topic_history_update` | Path 1 or Path 2 of `evaluateTeamAccess`, **with the `admin` grant path explicitly rejected** |

Task 4.5 repeats this: "deliver only if the returned grant path is `member`... explicitly reject an `admin`-path grant." Facilitator (`path: 'facilitator'`, Path 3) is never mentioned as a valid recipient for this event.

I read the HTTP endpoints that serve the content `topic_history_update` is modeled on — `GET /api/v1/teams/:teamId/action-items` and `GET /api/v1/teams/:teamId/topics` in `packages/backend/src/routes/content.ts` (lines 400–484). Both call `evaluateTeamAccess`, deny only `grant.path === "admin"`, and proceed identically for `member` **and** `facilitator` grants — there's no facilitator-specific query variant for either endpoint; a facilitator hits the same code path as a team member. The HTTP-layer authorization matrix for this exact content type is "member or facilitator, not admin." The WS event's matrix, as written, is "member only, not admin" — facilitator is silently excluded.

This might be intentional (maybe a facilitator running a live session is expected to get topic/action-item state through `session_state_change` instead, and doesn't need the team-wide stream), but the document doesn't say that, and it's a real behavioral difference from the endpoint it claims to be the WebSocket equivalent of: a facilitator who could `GET /api/v1/teams/:teamId/action-items` and see finalized action items in real time via polling would get nothing if they subscribed to `topic_history_update` instead. If it's deliberate, D3 should say so and why; if it's an oversight (the archived HTTP design's "Path 1 or Path 2" language, carried forward from `propose-review-ba.md`'s own note that this terminology doesn't exist in the code, may have caused the "or Path 3" case to just get dropped in translation), it needs fixing before task 4.5 is implemented as literally written. I'd flag this as a one-sentence clarification the document owner should resolve, not block Tasks over — but it should be resolved explicitly, because right now an implementer following D3 exactly will build something that doesn't match its own stated HTTP precedent, and nobody will notice until a facilitator asks why their action-item view isn't live-updating.

## 4. Two missing error paths in the pub/sub lifecycle

The task specifically asked me to check register/deregister on disconnect, Redis connection loss, and mid-delivery-check socket closure. D2's "implicit deregistration on send failure" and the registry lifecycle in tasks.md 3.2/3.3 cover the common case reasonably — a socket that's already closed when `.send()` is attempted is logged and deregistered, not treated as an auth failure. Two things aren't covered:

**4a. Redis pub/sub has no replay, and ioredis reconnection is silent about the gap.** `ioredis` will automatically reconnect a dropped connection and automatically re-issue `SUBSCRIBE` for previously-subscribed channels on reconnect (this is built-in behavior, not something to build) — so the *subscription* recovers on its own. But Redis pub/sub itself is fire-and-forget: any message `PUBLISH`ed while a given pod's subscriber connection is down is gone, permanently, for that pod. Nothing re-delivers it. For the three events that matter for the simultaneous-reveal guarantee, this means: if Pod B's Redis connection blips for even a few hundred milliseconds at the exact moment a `vote_revealed` is published, every locally-held socket on Pod B silently never receives that event — not delayed, not retried, just gone — while Pod A's sockets get it fine. The facilitator and the three participants pinned to Pod A see the reveal; the two pinned to Pod B don't, with no error, no reconnect prompt, nothing distinguishing this from "the browser tab is just quiet." This is a materially different failure mode from "average latency is fine" (which Decision D6's measurement plan does check) — it's a total-loss event for a subset of recipients, correlated with pod-level network blips, not measured by a p95/p99 latency number at all. I'm not asking for a queued/durable pub/sub here (that would undercut D2's own rationale for not adding a second broker) — I'm asking that this be named as a known, accepted gap with a mitigation direction (e.g., emit a pino warning on ioredis `reconnecting`/`ready` transitions so it's at least visible in logs when it happens, since the client-side staleness signal in Group 9 is the only thing that would ever surface this to a real user, and only if the participant refreshes). Right now it isn't named anywhere in the Risks section.

**4b. The "`.send()` that throws" mechanism D2 relies on needs a verified premise.** D2 says: "a `.send()` that throws because the socket already closed is treated as an implicit deregistration." The underlying `ws` library's actual behavior here is readyState-dependent and, in some versions/paths, callback-dependent rather than throw-dependent — `ws`'s `send()` does not uniformly throw synchronously for every non-OPEN state; behavior differs between `CONNECTING` (throws), `CLOSING`/`CLOSED` (historically inconsistent across `ws` major versions, and callback-vs-no-callback call sites behave differently). Since `@fastify/websocket` pins a specific `ws` version as a dependency (currently `^8.16.0` per the package I checked against the registry), this is easy to verify empirically — write the registry deregistration test (tasks.md 3.4 already asks for "the case where `.send()` throws") against the actual pinned `ws` version's actual behavior in each readyState, not assumed from the design doc's prose. If it turns out `ws` silently no-ops instead of throwing in some state, the registry needs an explicit `readyState` check before every `.send()` call as a second deregistration trigger, not just a try/catch. Small fix, but worth calling out as "verify, don't assume" given task 3.4 as written could pass against a mocked socket that always throws on command, without ever exercising the real library's actual behavior.

## 5. Things I checked and found accurate (worth stating, since I was asked to verify rather than trust)

- **Grant shape** (`packages/shared/src/types/team-content-access.ts`): `TeamAccessGrant` is exactly `{path:'member', role:'participant'|'engineering_manager', teamId, actorGlobalRole}` | `{path:'facilitator', sessionId, teamId, sessionStatus, actorGlobalRole}` | `{path:'admin', actorGlobalRole:'application_admin'}`. Matches the design's description precisely — no boolean coercion, no hidden Fastify-request coupling in `evaluateTeamAccess` itself (it takes `(userId, teamId)` as plain strings and returns a plain object; it composes cleanly into a non-HTTP call site like a WS message handler with zero adaptation).
- **`@fastify/websocket` + Fastify 5:** confirmed against the npm registry — the package's 11.x line (currently 11.3.0) was released specifically for Fastify 5 compatibility (its prerelease tags are literally `11.0.0-pre.fv5.1`/`.fv5.2`), and its own dependency on `ws@^8.16.0` is unproblematic alongside the rest of this stack. No version conflict with `fastify@^5.0.0` or `ioredis@^5.0.0` in `packages/backend/package.json`. This is a practical, low-risk dependency addition.
- **D4 (`vote_revealed` reuses `serializeForFacilitator`/`serializeForMemberParticipant`):** read both functions in full. They take a grant + a query-result object and return a plain content view — no `FastifyRequest`/`FastifyReply` coupling anywhere in `team-content-serializers.ts`. This is a genuinely clean reuse, not a forced fit: the WS handler needs to run its own query (shaped like `buildFacilitatorQueryResult`/`buildParticipantQueryResult`'s input) and call the same function HTTP does. No adaptation shim needed.
- **D7's audit-logging correction:** matches the real `audit_log` schema (`migrations/8_audit_log.sql`: `actor_user_id, actor_global_role, actor_ip, operation, target_user_id, team_id, timestamp, metadata`) and the real `emitAuditEvent` (`audit-logger.ts`, a pino structured-log emitter, not a DB writer) exactly. The `em-views.ts` precedent (lines 372–386) is a verbatim match for the INSERT-then-emitAuditEvent pattern D7 prescribes.
- **The Blocking Dependency boundary is clean at the code level.** I looked specifically for the failure mode the task asked about — dead code paths or TODO-riddled handlers from treating #26 as external. It isn't there, structurally: the publisher wrapper (task 1.4) and the `vote_revealed`/`topic_history_update` handlers (4.4/4.5) can be fully written and unit-tested by calling them directly or hand-`PUBLISH`ing a synthetic envelope — no stub branches, no feature flags, no dead `if (false)` guards inside the reveal endpoint. The only thing that doesn't exist yet is a single call site (`publishEvent(...)` invoked from inside the reveal handler), and that call site simply isn't written yet — there's nothing broken-looking in its absence. **One nuance worth naming, though, not blocking:** this does mean `packages/backend/src` will carry a handful of exported functions (the publisher wrapper for the three blocked triggers, and per task 7.2 a `session.reveal_triggered` audit-write function) that are invoked only from tests, not from any production request path, for as long as issue #26 stays open. That's a normal and defensible way to stage this kind of work, but it's the kind of thing a reviewer doing a "grep for callers" pass will flag as looking like dead code if it isn't visibly commented as intentionally-not-yet-wired (a `// TODO(#26): wire into reveal handler once the reveal-status write exists` at each such site would be enough). I'd add that as a one-line convention to Migration Plan step 4 rather than leave it to each implementer's judgment.
- **D7's "same transaction" instruction is achievable, but is a bigger change to `facilitator-sessions.ts` than "add a call after" implies.** `packages/backend/src/routes/teams.ts` (lines 494–577, 767–812) has the only existing explicit-transaction pattern in the codebase (`db.connect()` → `BEGIN` → queries → `COMMIT`/`ROLLBACK` in `catch` → `client.release()` in `finally`). The lobby-advance and session-close handlers in `facilitator-sessions.ts` currently do a single bare `db.query(UPDATE ...)` against the pool — no transaction. Task 7.3 ("in the same statement/transaction as the action's own state-transition write") means these two handlers need to be refactored from a bare pool query to the `teams.ts` transaction pattern, not just have an INSERT appended after them. It's a known, copyable pattern — not a design risk — but tasks.md 7.3 doesn't say "refactor the existing UPDATE call site to use a transaction," and an implementer who reads it as purely additive will either skip the transaction wrapping (weakening the atomicity guarantee D7 asks for) or discover the refactor mid-task. Worth a one-line addition to 7.3.

## 6. Tasks.md sanity-check against the design

Walked tasks.md group by group against design.md's decisions. Groups 0–3 map cleanly to D1–D3 and the Migration Plan; Group 4's per-event tasks match the per-event mapping table field-for-field; Group 5's integration tests correctly target the pub/sub hop itself (5.2) rather than an in-process shortcut, which is the one test in this whole plan that actually has to exist for the drift risk D3 names to be catchable — good that it's called out as its own numbered task rather than folded into the general matrix. Group 6 is appropriately scoped down per the Executive review (I agree with Rachel's read: a one-time sanity check against a labeled placeholder is the right amount of rigor for a system with zero production traffic — chasing a load profile that doesn't exist would be its own kind of incidental complexity). Group 7's audit tasks are consistent with the corrected D7 except for the transaction-refactor gap noted above. Groups 8–11 are process/tracking tasks, not implementation tasks, and are fine as written.

The one structural gap in tasks.md relative to what I found above: **nothing in Group 1 (Dependencies and Infrastructure Setup) names the `redis.duplicate()` requirement or the Origin-validation check.** I'd add both as explicit subtasks under Group 1 (alongside 1.1–1.5) before implementation starts, since both are Group-1-shaped ("infrastructure setup," not per-event logic) and both are the kind of thing that's cheap to name now and expensive to discover after the shared Redis client has already taken down health checks in a dev environment once.

## 7. Recommendation

Approve for Tasks with two additions to Migration Plan / tasks.md Group 1 (Redis subscriber connection isolation; WS upgrade Origin validation), one clarification needed from the document owner (facilitator's exclusion from `topic_history_update` — intentional or not), and one line each added to tasks 3.4 and 7.3 (verify `ws`'s actual close-state `.send()` behavior against the pinned version; note that 7.3 requires refactoring the existing bare-query lobby-advance/session-close handlers into the `teams.ts` transaction pattern, not just appending a call). None of these require reopening D1/D2/D3/D4 — the transport and fan-out architecture is sound and I'd build it as designed.
