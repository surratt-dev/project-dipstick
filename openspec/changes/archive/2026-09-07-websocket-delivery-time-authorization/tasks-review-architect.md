# Tasks-Stage Review: websocket-delivery-time-authorization

**Reviewer:** Ingrid Sollenberger, Principal Solution Architect
**Stage:** Tasks (tasks.md, cross-checked against design.md and proposal.md — including my own Design-Stage Review Disposition section, which I authored in the prior stage and am now holding tasks.md to)
**Date:** 2026-09-07
**Scope of this review:** task ordering against architectural dependencies only. I am not re-litigating the transport/fan-out/authorization decisions (D1–D10) — those are settled and I signed off on them at Design stage. This review asks one question: does the sequence in which tasks.md asks the team to build things match the sequence in which the design actually requires things to exist.

---

## 0. Bottom line

The task list is implementable and the big-rock sequencing is sound: Group 0 correctly scopes the blocking dependency without letting it leak into places that don't need it, the `redis.duplicate()` task lands before the pub/sub delivery-wiring task, and D9/D10 are attached to the right neighboring tasks. I did not find a case where a later group silently assumes a write that Group 0 says doesn't exist.

I found three real ordering problems, none of which requires reopening a Design-stage decision — all three are tasks.md structural fixes:

1. **Group ordering contradicts Migration Plan step 2's explicit instruction.** The Migration Plan says build and test `evaluateSessionSubscriberAccess` "before any WebSocket route wiring." tasks.md's Group 1 contains the actual route/plugin registration (1.2, 1.2a) and the full Redis pub/sub implementation (1.4) — and Group 1 comes *before* Group 2, which is where the auth helper gets built and tested. Nothing in Group 1 calls the helper, so there's no broken compile-time dependency, but the document's own stated sequencing discipline (mirroring how the archived change built `evaluateTeamAccess` in isolation first) is not what the group numbers actually enforce. Section 1.
2. **Two task groups edit the same three handlers without coordinating which one runs first.** Task 1.4 wires a `redis.publish(...)` call into the vote lock-in, lobby-advance, and session-close handlers as they exist today — bare `db.query()` calls, no transaction. Tasks 7.3 and 7.6 later refactor those same three handlers into the `teams.ts` `BEGIN`/`COMMIT` pattern. Nothing in either task says where the publish call ends up relative to the new transaction boundary. Section 2.
3. **Minor completeness/labeling gaps** in Group 0's own self-referencing task list, and in the correspondence between tasks.md's Group 1 and Migration Plan step 11's placement of the Redis-hardening confirmation. Section 3.

Everything else I checked — the specific items I was asked to verify — came back clean. Details below.

## 1. Group ordering contradicts Migration Plan step 2

**What Migration Plan step 2 says, verbatim:** *"Build `evaluateSessionSubscriberAccess` (Decision D3) alongside `evaluateTeamAccess`, tested in isolation **before any WebSocket route wiring**, the same way the archived change built and tested `evaluateTeamAccess` independently of endpoint changes."*

That's not a throwaway line — it's citing a specific precedent (the archived change built and proved the authorization predicate before any HTTP endpoint touched it) and asking this change to repeat the discipline for the WebSocket transport. The reasoning behind it is sound: prove the thing that decides who gets data before building the pipe that delivers data, so the transport is never built against an authorization contract that doesn't exist yet or hasn't been exercised in isolation.

**What tasks.md actually does:**

- Group 1 ("Dependencies and Infrastructure Setup") contains 1.1 (dependency add), **1.2 (register the `@fastify/websocket` plugin — this is the route wiring the Migration Plan is talking about)**, 1.2a (Origin check on that same route), 1.3 (channel topology), **1.4 (the full publisher/subscriber implementation, including wiring the publisher into three live handlers)**, 1.5 (payload shapes), 1.6 (Redis hardening confirmation).
- Group 2 ("Authorization Helper") — where `evaluateSessionSubscriberAccess` is built and unit-tested in isolation — comes **after** Group 1.

Read as a build sequence (which is how Group 4's explicit "Depends on: Groups 1–3" line tells us to read these groups — sequential, not parallel-optional), a team following tasks.md in order registers the WebSocket route and builds the entire Redis publish/subscribe pipeline *before* the authorization predicate that pipeline exists to gate has been written or tested. Task 1.2 doesn't call `evaluateSessionSubscriberAccess`, so nothing breaks mechanically — but that's exactly the gap: the ordering constraint Migration Plan step 2 is asking for isn't a compile dependency, it's a discipline (prove the gate before you build the door), and tasks.md's group numbers actively invite skipping it.

**Recommendation:** Either (a) renumber so the auth-helper group precedes the route-registration and pub/sub tasks — i.e., swap the position of Group 2 to sit between "1.1 dependency add" and "1.2 route registration" — or (b) if there's a reason to keep dependency-installation and route-registration adjacent in the document, add an explicit sequencing note to Group 1's header stating that 1.2/1.2a/1.4 should not begin implementation until Group 2 is complete, mirroring the "Depends on" convention Group 4 already uses. I'd prefer (a): it's a pure reordering, touches no task content, and makes the document's own stated discipline visible in the numbering instead of contradicted by it.

## 2. Task 1.4 and tasks 7.3/7.6 edit the same handlers with no stated relative order

This is the more consequential of the two findings, because it's not just a documentation-clarity issue — it's a real place where doing the tasks in numeric order produces code that has to be revisited, and where the revisit isn't just "add a line," it's "relocate a side effect across a transaction boundary that didn't exist when it was written."

**The handlers in question:** vote lock-in (`sessions.ts`), lobby advance (`facilitator-sessions.ts`), session close (`facilitator-sessions.ts`). Design.md's Blocking Dependency section and D7 both establish that all three commit a real state transition today via a single bare `db.query(...)` call — no transaction wrapper.

**What task 1.4 does to them:** "Wire the publisher into the triggering action handlers that commit a real state transition today: vote lock-in, lobby advance, session close." Read plainly, this means each of those three handlers gains a `redis.publish(...)` call, presumably immediately after (or near) the existing bare `db.query(...)` call, since that's the only commit point that exists in the handler at the time task 1.4 is done — Group 7 hasn't run yet.

**What tasks 7.3 and 7.6 later do to the same handlers:** "Requires refactoring both handlers from a bare `db.query` call to the `teams.ts` transaction pattern" (7.3, lobby advance/session close) and "Requires refactoring this handler from a bare `db.query` call to the `teams.ts` transaction pattern" (7.6, vote lock-in) — introducing `db.connect()` → `BEGIN` → queries → `COMMIT`/`ROLLBACK` → `client.release()` around the state-transition write and the new `audit_log` INSERT.

**The gap:** design.md's D7 correction is explicit that the point of the transaction refactor is to avoid "a window where one write commits without the other." That's a sound rule for the two writes *inside* the transaction (state-transition + audit INSERT). But neither 7.3 nor 7.6 says anything about the `redis.publish(...)` call that 1.4 already put in that handler. Three things could happen depending on implementation order and who's doing the work:

- The publish call ends up **before** `BEGIN` — harmless but pointless (nothing has committed yet, but nothing has failed yet either, so this specific ordering doesn't create a correctness bug for these three handlers specifically, since none of them currently has a plausible rollback path that isn't already publish-safe — but it's accidental correctness, not designed correctness).
- The publish call ends up **inside** the transaction, between the state-transition write and `COMMIT` — this is the one that matters. If the audit INSERT (or anything else in that transaction) fails and the transaction rolls back, a Redis subscriber has already been told the event happened. For `session.state_changed` / `vote_readiness_update`, that means a client could be notified of a lobby-advance or vote-lock-in that Postgres subsequently rolled back — a real, if narrow, correctness gap of exactly the kind this design has otherwise been careful to close (D3's entire concurrency-model discussion exists to prevent exactly this class of "told the client something not yet true" defect).
- The publish call ends up correctly **after `COMMIT`**, but only if whoever does 7.3/7.6 independently reasons their way there — nothing in either task's text says to.

**Recommendation:** Add one sentence to 7.3, 7.6 (and, for symmetry, 7.2 once it unblocks): *"Task 1.4 already added a `redis.publish(...)` call to this handler; when introducing the transaction wrapper, the publish call MUST execute after `COMMIT` succeeds, never before or inside the transaction — publishing before commit risks notifying a subscriber of a state transition that a subsequent statement in the same transaction rolls back."* This is a one-line fix to the task text, not a redesign, and it converts an implicit assumption an implementer would otherwise have to independently arrive at into an explicit, checkable instruction — precisely the standard this document holds everything else to (see D3's own "the tell in code review" framing for the analogous subscription-time-caching risk).

## 3. Minor completeness and placement gaps

**3a. Group 0's own task 0.3 under-lists which tasks carry the BLOCKED annotation.** Task 0.3 names "the corresponding tasks (1.4, 4.4, 4.5, 7.2, 7.3)" as the ones annotated with what's buildable now versus blocked. That list omits 5.6, 11.1, and 11.2, which also carry explicit BLOCKED-on-#26 language later in the document (5.6's topic_history_update E2E caveat, 11.1's reveal-E2E gate, 11.2's topic_history_update-E2E-portion gate). Task 0.4 — the actual gate task — does correctly name 5.6/11.1/11.2, so the gate itself is not broken. But 0.3 is the task most likely to be read first as "here is the complete map of what's affected," and it isn't complete. Low-cost fix: add 5.6, 11.1, 11.2 to 0.3's enumeration so Group 0 is internally consistent with itself.

**3b. Task 1.6 (Redis hardening confirmation, D10) sits in Group 1, but Migration Plan step 11 places the equivalent confirmation second-to-last, immediately before the spec front-matter step.** This isn't a functional dependency problem — 1.6 is a deployment-environment confirmation with no code dependency on anything else in Group 1, and it carries its own "before this capability reaches production" gating language inline. Grouping it with the other Redis-infrastructure tasks (channel topology, publisher/subscriber) is a defensible organizational choice by topic rather than by chronology. But it does mean tasks.md and the Migration Plan tell two different stories about *when* this confirmation is expected to happen: Group 1 reads as "day one," Migration Plan step 11 reads as "final pre-production checklist item." I'd resolve this by either (a) leaving 1.6 where it is but adding the same explicit `**Gate — before production**` bold-label convention Groups 8 and 9 already use, so it's unambiguous that "task appears early in the list" doesn't mean "task must be *done* early," or (b) duplicating a one-line pre-production checklist pointer back to 1.6 near Group 11 (End-to-End Verification), where the other final-readiness gates live. Either is a small edit; I don't think this one is worth reordering the group over.

**3c. Task 1.4 and task 4.1 both use the word "subscriber" for what reads as two different pieces of work, with the boundary between them left implicit.** Task 1.4 says "Implement the subscriber as a separate connection created via `redis.duplicate()`... Log a structured warning on the subscriber connection's `reconnecting` and `ready` events." Task 4.1 says "Implement the per-pod Redis subscriber for `ws:events`: on each message, look up local registry candidates..." Taken together, these two tasks clearly divide into "create and instrument the connection" (1.4) versus "attach the message handler that does registry lookup, per-candidate authorization, and `.send()`" (4.1) — and that division is exactly what I'd want, and matches Decision D2's architecture. But nothing in either task's text says so explicitly; both use the bare word "subscriber" for their piece. I don't think this rises to the level of a real ordering defect — Group 1 correctly precedes Group 4 either way — but it's worth a one-clause clarification in 1.4 or 4.1 (e.g., "the message-handling logic itself — registry lookup, per-candidate authorization, delivery — is implemented in task 4.1") so two people picking up these tasks independently don't duplicate the `.subscribe()` call or leave a gap where neither of them wires it.

## 4. Specific items verified — all clean

**Group 0 positioning and blast radius.** Group 0 is first in the document, correctly frames itself as naming-not-resolving the dependency, and its own tasks (0.1–0.6) require nothing that depends on issue #26 landing. I checked every task carrying a "BLOCKED on Group 0 / #26" annotation (1.4's wiring-in clause, 4.4, 4.5, 7.2, 7.3's topic-advance exclusion, 5.6, 11.1, 11.2) and checked every other task in the same groups (1.1–1.3, 1.5, 1.6; 4.1–4.3, 4.6; 7.1, 7.4–7.7; 5.1–5.5, 5.7–5.10; 11.3) for a silent assumption that the reveal-status flip, `removed_at` write, or topic-advance write already exists. None of them do — the revocation tests (5.2–5.5, 11.1's revocation portion) correctly operate on `team_memberships.removed_at` as a column tests can set directly via fixture SQL, not as a value a production endpoint needs to produce, exactly per design.md's own reasoning for why those tests are unblocked. This boundary is drawn correctly and consistently everywhere I checked it.

**`redis.duplicate()` ordering.** Task 1.4 (Group 1) creates the subscriber connection; task 4.1 (Group 4, "Depends on: Groups 1–3") is the first task that wires up actual pub/sub message delivery. The connection-creation task is ordered strictly before the delivery-wiring task, satisfying the specific check requested. (See 3c above for a related but non-blocking clarity note on the boundary between the two tasks.)

**D9 (Origin/CSWSH) and D10 (Redis hardening) positioning.** 1.2a sits immediately adjacent to 1.2, the route-registration/session-validation task it modifies, and both are ahead of any pub/sub or registry work — correct placement relative to the connection-handling tasks it changes, matching Migration Plan step 3's instruction to add it "as part of this same route-registration step." (One numbering nit, not a sequencing bug: 1.2a is listed after 1.2, while its own text says it must run *before* `request.session` is consulted — i.e., before what 1.2 does at runtime. Since both are still built together in Group 1, this doesn't create an implementation-order problem, but a reader skimming the numbers alone could get the runtime order backwards. Worth a one-clause note in 1.2a reiterating "this runs first in the request pipeline, despite the numbering.") D10 (task 1.6) is discussed in 3b above — placement is defensible but drifts from the Migration Plan's narrative position.

**Vote-submission audit logging (7.6) and SEC-25 compensating control (3.2/3.6/4.1/5.10) relative to their dependencies.** SEC-25's control is correctly sequenced: `sessionCreatedAt` capture (3.2) and scheduled force-close (3.6) in Group 3, before the delivery-time rejection that reads it (4.1) in Group 4, before the tests that verify both (5.10) in Group 5 — no issues. Vote-submission audit logging (7.6) is correctly ordered *within* Group 7 relative to the transaction pattern it needs (the pattern is stated as a precondition in the group header and restated in 7.6 itself) — the issue here is the cross-group one already covered in Section 2, not an internal Group 7 ordering problem.

**Transaction-refactor implication — explicit, but only within Group 7.** The refactor is not left implicit: the Group 7 header states it as a correction with rationale, and 7.2, 7.3, and 7.6 each restate it locally as part of their own scope, bundled with the audit-log addition rather than split into a separate checkbox — which I think is the *right* call structurally, since splitting "refactor to transaction" and "add audit write inside it" into two separate tasks would recreate exactly the atomicity window D7 is trying to close (a state where the refactor has landed but the audit write hasn't, or vice versa, reviewed and merged as two separate changes). So: explicit and correctly ordered *within* Group 7. The gap is the cross-group one in Section 2 — the refactor's interaction with task 1.4's already-present publish call is the piece that's still implicit.

**Migration Plan cross-check, general.** Steps 1, 5, 6, 9, 10, 12 map cleanly onto tasks.md (1.1; 4.4; 4.5; Groups 5–6; Group 8; 10.2) with no drift. Step 8 (SEC-25/26 compensating control) is, by the Migration Plan's own text, meant to be built concurrently with steps 3 and D3 rather than as a discrete later step, and tasks.md reflects that by embedding it directly into Groups 3–4 rather than giving it a separate group — consistent, not drift. Steps 2, 3, 4, and 11 are the ones with the ordering/placement notes above (Sections 1 and 3b).

## 5. What I did not check

Per this review's scope, I did not re-verify the correctness of the authorization rules themselves (D2–D4's grant-path logic), the audit-log schema fields (D7), the security posture of D9/D10, or the measurement plan's numbers (D5/D6) — those were reviewed and accepted at Design stage by the engineer and security reviewers, and by me, and none of my ordering findings above require reopening them. This review is strictly: given the decisions as made, does tasks.md sequence the work the way the decisions require it to be sequenced. Sections 1 and 2 are the two places where the answer is "not quite, but the fix is a tasks.md edit, not a design change."
