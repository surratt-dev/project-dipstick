# Facilitator Review: WebSocket Delivery-Time Authorization Exploration

**Reviewer:** Priya Nair, Facilitator SME
**Reviewing:** `exploration-notes.md` (Devon Calloway, 2026-09-07), cross-referenced against `websocket-session-authorization/spec.md` and archived `design.md` Decision 5/6.
**Lens:** Does this hold up in a live session with real people watching a screen, not just in a threat model?

I want to say up front: the security reasoning here is careful, and I don't have a technical objection to delivery-time checks over a timer. My objections are about what happens on the other end of the wire, which this document never looks at. It resolves the transport and the fan-out mechanism in ten pages and does not spend one sentence on what a participant or facilitator *sees* when a check fails. For a document whose entire justification is protecting the felt experience of the ritual (the no-surveillance guarantee, the reveal), that is a real gap, not a nitpick.

---

## Observations

1. **This is a pure backend-and-security document; the live-session experience is entirely absent.** Every section is about where the check runs, which library, which query gets reused. Nothing addresses what the client renders differently before and after a delivery-time check starts failing. That absence is itself notable given how much weight this document (correctly) puts on "the ritual constraint this protects." Protecting the guarantee and protecting the *experience of trusting* the guarantee are related but not the same problem, and only the first one got explored.

2. **"The event is not delivered" is a description of server behavior, not of user experience.** Section 5 and the spec both describe revocation as: nothing gets pushed, no error, no signal. From a participant's chair, that is indistinguishable from a network hiccup, a slow connection, or the application being broken. If I'm mid-session and my `session_state_change` events just stop, I don't know I've been removed — I know the app looks frozen. That's the exact "silently stop updating" scenario I was asked to watch for, and it is the specified behavior here, not an oversight in a client someone hasn't built yet. The spec bakes silence into the contract (Requirement: Membership revocation takes effect without reconnection — "the server stops delivering... the connection may remain open").

3. **The design.md Non-Goals already punted on this once** ("Notification of membership revocation to the affected user — out of scope"), and this exploration inherits that non-goal without re-examining whether it still holds for a *live, synchronous* voting session specifically. A membership removal that silently stops your access to a historical report page is a UX shrug. A membership removal that silently stops your access mid-vote, in a room where everyone else's screen keeps moving and yours doesn't, is a materially different failure mode — the person doesn't know if the app broke, if they should refresh, or if they should say something out loud in a room that is actively trying to be psychologically safe. I'd want this re-opened, not carried forward as settled.

4. **The readiness grid is the one piece of UI I depend on to stay present in the room, and this document is silent on what happens to it under a delivery-time failure.** My whole "control surface" ask is that the grid is trustworthy without me cross-checking it. If a `vote_readiness_update` for one participant silently fails to deliver (say, their session_state changed underneath them, or a role changed mid-session per the EM-transition scenario in the spec), does my grid show that participant as "not locked in" forever, with no indication that the state is stale versus accurate? A grid that goes quietly wrong is worse than a grid that shows an explicit "connection issue" indicator, because I will trust a wrong-looking-normal grid completely. Nothing in Section 6's per-event mapping or Section 9's test plan touches this.

5. **Section 3's two-pods-two-independent-evaluations design is described as a correctness win, but from where I sit it reads as a simultaneity risk, and that risk is not measured anywhere in this document.** The diagram is explicit: "Two pods, two independent authorization evaluations for the same event, **at two different physical moments** (whenever each pod happens to service its local recipients)." That sentence is exactly the failure mode I care most about. If the facilitator's connection lives on Pod A and a participant's on Pod B, and Pod A happens to be busy servicing three other local sockets before it gets to mine, the reveal is not simultaneous anymore — it's staggered by however long Pod A's loop takes plus whatever Redis pub/sub propagation delay exists between the publish and each pod's subscriber callback firing. The document treats "different physical moments" as an acceptable, even necessary, consequence of doing the security check correctly. I need it treated as a budget to be measured and bounded, not a shrug.

6. **Section 9's latency target measures the wrong thing for my top priority.** It says: "measure per-event, per-candidate-connection authorization-check-plus-send latency... comfortably under ~100ms." That's a per-connection absolute latency bound. My requirement is about *relative* skew between connections receiving the *same* event — i.e., does participant A's vote_revealed arrive within (say) low tens of milliseconds of participant B's and the facilitator's, not "does each one individually feel fast." A system where every single check-plus-send completes in 20ms but where cross-pod propagation and per-pod queueing add 300ms of variance between recipients would pass Section 9's stated test and fail the actual reveal-simultaneity requirement. I'd ask for a distinct measurement: max observed delta between first-recipient and last-recipient delivery timestamp for the same reveal event, under realistic concurrent session load — not just single-connection latency.

7. **Serial vs. parallel per-recipient checks within one pod is an open implementation question that directly affects skew, and it isn't asked.** Section 3's diagram shows "for EACH local candidate socket: evaluateTeamAccess... RIGHT NOW." If a pod is holding multiple sockets for the same session (unlikely at single-digit session size, but the facilitator plus several participants could plausibly land on the same pod), and the checks run in a naive `for` loop with awaited DB round-trips, the last socket in that loop gets its event measurably later than the first — on the same pod, before Redis or cross-pod effects even enter the picture. I want this named as a question for Design/Tasks: are per-recipient checks issued concurrently (e.g., `Promise.all`) or serially, and if serially, what is the worst-case fan-out width per pod that keeps that serial chain under the skew budget from observation 6?

8. **The subscription-time "cheap, good UX" framing in Section 7 is the one place this document touches UX at all, and it's a real point in the document's favor** — rejecting an unauthorized subscription attempt early rather than making a client wait for the first event to learn it can't see anything is exactly the kind of thing I'd ask for. But it stops one step short: what does the client actually receive on that rejection (a close code, an error frame, silence), and does the UI have a defined state to render for it? If subscription-time rejection is well-designed but delivery-time cessation is silent, participants get two different experiences for what looks to them like the same category of thing ("I can't see this"), and only one of the two tells them anything.

9. **SEC-26 (token expiry, 90-minute session cap, silent refresh) is correctly flagged as out-of-scope-but-adjacent in Section 7, and I want to underline why that adjacency matters to me specifically.** "Session pacing under facilitator control: no automatic topic advancement, no timeouts, no nudges to participants. The facilitator calls it" is a property I insisted on for the ritual itself. A 90-minute hard connection cap that silently stops a participant's live updates mid-vote because a token expired is functionally an automatic timeout I did not call and cannot see happening. I'm not asking this document to solve it — it correctly scopes it out — but I want it tracked with an owner before this ships, not left as a footnote, because it's the same "silent stop" failure class as observation 2, just triggered by a clock instead of a membership change.

10. **The one thing I don't have a concern about: reusing `evaluateTeamAccess` and `serializeForFacilitator` instead of building parallel logic.** That's the right call for keeping the pre-reveal enforcement I care about most (no premature vote visibility) consistent between HTTP and WebSocket. I'd rather see effort spent proving the reveal is simultaneous under real network conditions than spent re-deriving the reveal-gating logic a second way.

## Questions

- When a participant's delivery-time check starts failing mid-session, what does their client actually do — does the last-received state simply stop updating with no visual change, does a "connection issue" indicator appear, or does something else happen? If the answer is "not decided yet," who owns deciding it, and is it decided before or after this WebSocket layer ships?
- Does the facilitator get any signal — even a subtle one, like a "last updated" timestamp on the readiness grid — that would let me tell the difference between "nobody has locked in recently" and "an update failed to deliver"? Or is the grid designed to look identical in both cases?
- What is the measured (or estimated) worst-case delta between when the first subscriber and the last subscriber receive the same `vote_revealed` event, across pods, under a realistic number of concurrent sessions? Section 9 asks for single-connection latency; I don't see this asked anywhere.
- Are per-recipient delivery-time checks within a single pod's local registry issued concurrently or in sequence? If sequential, what's the largest local fan-out this design expects per pod, and has anyone estimated the worst-case serial chain length against the skew budget?
- Is there a defined client-visible behavior for subscription-time rejection (Section 7), and does it differ from delivery-time cessation in a way a participant would actually notice, or in a way only a developer reading logs would notice?
- Is the "notification of membership revocation is out of scope" non-goal from the archived design being re-affirmed for this specific real-time context, or was it just inherited without a fresh look? I'd like an explicit yes/no, not a silent carry-forward.
- Has anyone thought about whether a participant who is silently cut off mid-vote might, reasonably, think the *application* is broken and say so out loud in the session — which is itself a small disruption to the room, even if the underlying security behavior is correct?
- Who is accountable for tracking SEC-26 (token expiry/90-minute cap) as a related-but-separate gap, and on what timeline relative to this change shipping?

---

## Suggested Additions

1. **Add a client-experience section to Design (not this exploration necessarily, but before Tasks locks in), covering, at minimum:** what a participant sees when delivery-time revocation occurs mid-session, what a participant sees on a rejected subscription attempt, and whether these two are visually distinguishable from ordinary network flakiness. Even a one-paragraph "explicitly punted, here is the interim behavior, here is who owns closing the gap" is better than silence carried forward from the archived design's non-goals list.

2. **Add a cross-connection skew measurement to the Section 9 test plan**, distinct from the existing single-connection latency measurement: capture the delta between first-delivered and last-delivered timestamps for the same fan-out event across all locally- and remotely-held recipient connections, under a realistic concurrent-session load. This is the number that actually answers "does the reveal still feel simultaneous," which is the property I was told this whole change exists to protect.

3. **Name the concurrency model for per-recipient checks within a pod explicitly** (parallel vs. serial) as a Design-stage decision, with the worst-case fan-out width and its effect on skew stated the same way the transport and fan-out mechanism were stated here — as a decision, not a detail to be discovered during implementation.

4. **Re-open, rather than silently inherit, the "no revocation notification" non-goal specifically for the live-session case.** At minimum, get an explicit decision — even if the decision is "still out of scope, here's why" — rather than letting a non-goal written for a different (HTTP, asynchronous) context quietly cover a synchronous live-voting context it wasn't evaluated against.

5. **Track SEC-26 with a named owner and a target change/issue**, even though it's correctly out of scope for Group 9 — it's the same silent-stop failure mode on a different trigger, and I don't want it discovered as a surprise during a real session that happens to run long.

6. **Before this ships to a live team, I want a usability pass on the reveal specifically** — not just a latency number under a threshold, but people in a room (or a realistic multi-device simulation) confirming the reveal still feels instantaneous under the pod/pub-sub architecture described in Section 3, given that "different physical moments" is explicitly part of the design as written. I've already offered to test the facilitator view; I'd extend that offer specifically to a reveal-timing check once there's something real to click.
