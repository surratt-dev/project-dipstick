## Verification of the two reported bug fixes

**1. Close-code disclosure (staleness-signal.ts / websocket-routes.ts) — genuinely fixed.**
`packages/backend/src/realtime/websocket-routes.ts` lines 41–51 define `CLOSE_UNAUTHORIZED` and `CLOSE_FORCE_EXPIRED` as two *names*, but both are assigned the same value: `STALE_SIGNAL_CLOSE_CODE` (4000) from `staleness-signal.ts`. Both call sites (`socket.close(CLOSE_UNAUTHORIZED)` at rejection, `socket.close(CLOSE_FORCE_EXPIRED)` at the scheduled 90-minute force-close) therefore emit an identical wire-level close code. `websocket-routes.test.ts` asserts `STALE_SIGNAL_CLOSE_CODE` at both call sites (lines 106, 169, 266). This is the correct fix and it is tested at the point that matters (the actual `.close()` call), not merely at the constant definition.

**2. EM-promotion gap (session-subscriber-access-helper.ts) — genuinely fixed.**
The query in `evaluateSessionSubscriberAccess` (`packages/backend/src/auth/session-subscriber-access-helper.ts` lines 81–96) selects `tm.role AS membership_role`, and Path 1 (lines 155–168) rejects if either `global_role` or `membership_role` is `engineering_manager`. This mirrors the identical dual-check already used in `sessions.ts` (verified directly: lines 117–118 and 267–268 of `packages/backend/src/routes/sessions.ts` use the same `global_role === "engineering_manager" || membership_role === "engineering_manager"` condition). Tested at both the helper level (`session-subscriber-access-helper.test.ts` lines 142, 155) and the dispatcher level, including a facilitator-path promotion case that a naive fix might have missed (`ws-event-dispatcher.test.ts` line 262, "stops delivering vote_readiness_update... (facilitator path)"). I don't consider this a superficial patch — the facilitator-path test in particular shows the fix was reasoned through, not just pattern-matched to the participant case.

## Decision-by-decision verification

- **D1 (transport):** `@fastify/websocket` added at `^11.2.0`, `ws` resolves to `8.21.x` (satisfies `@fastify/websocket`'s `^8.16.0` pin, verified in package-lock.json). No Socket.IO present. Confirmed.
- **D2 (fan-out, subscriber isolation):** `ws-pubsub.ts` uses `redis.duplicate()` for the subscriber (line 134) and the shared `redis` singleton for `PUBLISH` (line 43) — exactly the split D2 requires. `reconnecting`/`ready`/`error` handlers all log structured warnings (lines 136–152). Envelope shape matches D2's stated JSON shape exactly (`packages/shared/src/types/realtime.ts`). Confirmed, no drift.
- **D3 (delivery-time check placement, concurrency model):** `ws-event-dispatcher.ts`'s four `dispatch*` functions each call the relevant authorization helper **inside** `Promise.all(candidates.map(...))`, per candidate, on every message — not once per subscription. I checked this is not a shape that only *looks* like per-message dispatch: `handleIncomingMessage` is invoked from the `subscriber.on("message", ...)` handler (line 53–56 of `ws-event-dispatcher.ts`), and every dispatch function re-derives its candidate list from the registry and re-runs the query per call — there is no cached grant anywhere on `RegisteredConnection`. The drift risk D3 names explicitly (subscribe-time caching disguised as delivery-time checking) does not appear in this code. Task 4.6's code-review checklist item and the dedicated regression test ("re-runs the authorization check on every message," `ws-event-dispatcher.test.ts` line 186) both target this specific risk directly.
- **D4 (serializer reuse for `vote_revealed`):** `vote-revealed-payload.ts` calls `serializeForFacilitator`/`serializeForMemberParticipant` and `buildFacilitatorQueryResult`/`buildParticipantQueryResult` verbatim from `team-content-serializers.ts` — I confirmed these are the actual exported functions (not shadowed or reimplemented) and that the pre-reveal gating (`revealStatus === 'revealed'`) lives entirely inside the serializer, untouched. The adapter code in `buildVoteRevealedPayload` (lines 101–129) constructs `TeamAccessGrant`-shaped objects purely to satisfy the serializers' type signature — no field on those adapted objects is computed independently of the `SessionSubscriberGrant` that produced it. This is clean reuse, not a forced fit: the only "force" is a type adapter, and it carries no logic.
- **D5/D6 (skew measurement, acceptance test plan):** Correctly and honestly deferred. Group 6 is explicitly marked `[ ]` throughout tasks.md with a clear "DEFERRED — not performed in this implementation session" note, consistent with Rachel Okonkwo's Executive-review framing that this is a one-time sanity check against a real deployment, not something a sandboxed session can produce. I have no complaint about the deferral itself — it's honestly labeled, not silently skipped — but see Finding 1 below.
- **D7 (audit logging):** All three triggering actions verified directly in code, not from tasks.md's claims:
  - `sessions.ts`'s vote lock-in handler (lines 306–348): `db.connect()` → `BEGIN` → `INSERT INTO votes` → `INSERT INTO audit_log` (`operation = 'session.vote_submitted'`, metadata excludes `vote_value`/`vote_type`) → `COMMIT`, with `ROLLBACK` in `catch` and `client.release()` in `finally`. `emitAuditEvent` and `publishVoteReadinessUpdate` both happen *after* this block, at function-body scope, not inside the `try`.
  - `facilitator-sessions.ts`'s lobby-advance (lines 258–307) and session-close (lines 393–446) handlers: identical transaction pattern, `operation = 'session.state_changed'`, metadata carries prior/new status. Both publish calls sit after the transaction block.
  - The reveal action's audit write (`recordRevealTriggeredAudit`, lines 31–63 of `facilitator-sessions.ts`) is correctly *not* called from the production reveal handler — see the Group 0/#26 section below.
  - `AuditEventName` union in `audit-logger.ts` carries all three new values with the file's existing per-entry commenting convention.
- **D8 (SEC-25/26 compensating control):** `connectionRegistry.ts` captures `sessionCreatedAt` at registration (`websocket-routes.ts` lines 83–84, 114–115) and `isConnectionExpired` (`ws-event-dispatcher.ts` lines 93–102) rejects before the event-specific check runs, exactly as D8 specifies ("before running the event-specific authorization check ... reject if past absolute lifetime"). `scheduleForceClose` (`websocket-routes.ts` lines 138–152) independently force-closes at the 90-minute mark even with zero events pushed — this is the part of D8 that the delivery-time check alone cannot reach, and it is implemented as a real `setTimeout`, not a TODO.
- **D9 (Origin/CSWSH check):** `origin-check.ts`'s `registerOriginCheck` is called first inside `registerWebSocketRoutes` (websocket-routes.ts line 57), and `registerWebSocketRoutes(app)` is called before `authMiddleware(app)` in `app.ts` (lines 97, 100). Fastify's `onRequest` hooks execute in registration order across the whole app instance regardless of which routes they're later matched against, so the Origin check genuinely runs before `request.session` is consulted, as D9 requires. `getAllowedOrigins()` is the same function `@fastify/cors` uses for its origin allowlist (`app.ts` line 54) — no separate configuration surface was introduced, matching D9's "reuses an existing allowlist" claim. The hook only inspects requests carrying the `Upgrade: websocket` header (`isWebSocketUpgradeRequest`), so ordinary HTTP requests are unaffected, also as claimed.
- **D10 (Redis hardening assumptions):** This is a deployment-environment decision, not a code decision, and design.md says so itself ("not built by this change's code"). Task 1.6 is honestly marked deferred with a note explaining why (target deployment environment not in scope for this session). Nothing to verify in code; nothing contradicts D10.

## The Group 0 / GitHub issue #26 boundary

This is the finding I looked hardest for a violation of, since it's the easiest place for an implementer under schedule pressure to quietly "fix" the blocking dependency instead of respecting it. I did not find one.

- `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal` (`facilitator-sessions.ts` lines 484–599) still does exactly what design.md's Blocking Dependency section says it does today: validates facilitator identity and session status, returns `200 { revealed: true, ... }`, and does **not** write to `session_topics.status`, does **not** call `recordRevealTriggeredAudit`, and does **not** call `publishVoteRevealed`. No invented state-transition write exists anywhere in this handler or elsewhere in `packages/backend/src` (I grepped for `UPDATE session_topics` and `removed_at =` writes and found none outside test fixtures).
- `publishVoteRevealed` and `publishTopicHistoryUpdate` (`ws-pubsub.ts` lines 85–104) and `recordRevealTriggeredAudit` (`facilitator-sessions.ts` lines 31–63) are exported, unit-tested, and each carries a `TODO(#26)` comment naming the specific handler and the specific missing write — matching task 0.5's convention exactly (not a generic "TODO: wire this up"). None of the three is called from any production request path. I confirmed this by grepping for each function's usage across `packages/backend/src` outside `__tests__` directories — zero production call sites for all three.
- Conversely, the parts that **are** buildable today are actually wired into production, not left stubbed out of excess caution: `publishVoteReadinessUpdate` fires from the real vote lock-in handler, and `publishSessionStateChange` fires from both the real lobby-advance and session-close handlers. This is the correct reading of the Blocking Dependency section — it does not ask the implementer to stub everything defensively, only the three genuinely-blocked triggers.

## Publish-after-commit ordering (D2's bug, caught during Tasks-stage review)

I read the actual transaction blocks in both files rather than trusting the inline comments claiming correctness, since a comment asserting "runs after commit" next to code that doesn't is worse than no comment. In all three handlers I checked (`sessions.ts` vote lock-in; `facilitator-sessions.ts` lobby-advance and session-close), the `redis.publish*` call is textually and structurally outside the `try { BEGIN ... COMMIT } catch { ROLLBACK } finally { client.release() }` block — it executes after `client.release()` has already run, never between a query and `COMMIT`, never inside the `catch`. This is correct in all three places. I did not find the ordering bug tasks.md's own review history says was caught and fixed; it stayed fixed through to the current working tree.

I'm not asking for anything to change now — the recommendation Tomás Ferreira already made (route issue #26's implementation through this change's authorization-helper-plus-serializer contract, with a startup guard) covers this. I'm naming it here only so whoever picks up #26 knows this adapter exists and is the seam to check.
