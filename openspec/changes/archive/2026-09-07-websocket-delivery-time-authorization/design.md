## Goals / Non-Goals

**Goals:**
- Implement true delivery-time (per-connection, wire-level push) authorization checks for all four content-access WebSocket events, reusing `evaluateTeamAccess` and the existing grant types — no parallel authorization logic.
- Stand up the WebSocket transport (`@fastify/websocket`) and cross-pod fan-out (Redis pub/sub via `ioredis`) this application does not yet have.
- Reject `admin`-path grants for `topic_history_update` at the WebSocket layer, closing the surveillance path an Application Admin subscribed to a team's event stream would otherwise have.
- Reuse `serializeForFacilitator` / `serializeForMemberParticipant` for `vote_revealed` payload construction — no independently-maintained reveal-gating logic for the WebSocket path.
- Name and measure the acceptance criteria the exploration notes require: per-event/per-recipient latency (p95/p99), an explicit per-pod concurrency model with a stated worst-case fan-out width, and a cross-recipient delivery-skew measurement tied to the simultaneous-reveal guarantee.
- Add WebSocket-triggered audit logging for the reveal, session-state-change, **and vote-submission** actions (SEC-13/SEC-14), verified against actual code rather than assumed.
- File a companion tracking issue for the SEC-25 idle-connection heartbeat and SEC-26 token-expiry mechanism, with a named owner, before this change is considered complete.

**Non-Goals:**
- **Implementing the missing state-transition writes this change's event triggers depend on** — the topic reveal-status flip, the `team_memberships.removed_at` write, or the topic-advance/action-item-finalization write. See "Blocking Dependency" above and GitHub issue #26. This change wires publish calls and delivery-time authorization to the *point* a state transition commits; it does not build the business logic that produces that commit where it doesn't exist yet.
- **Designing or implementing the SEC-25 idle-connection re-authorization heartbeat or the SEC-26 token-expiry/silent-refresh mechanism.** These are real, named requirements (see the new spec requirement "Idle-connection re-authorization (SEC-25) is tracked, not satisfied, by delivery-time checks alone") but their mechanism, interval, and owner are explicitly out of scope for this change. Delivery-time checks close the SEC-27 window on connections receiving events; they cannot reach connections receiving nothing, and this document does not pretend otherwise by inventing a heartbeat design under time pressure.
- **Designing the client-visible UX for delivery-time cessation or rejected subscriptions.** Named as a Design-stage deliverable owned by Priya Nair's review (exploration notes Section 10). This document does not specify client rendering states, error banners, or staleness indicators.
- **Re-deriving the 60-second timer-based fallback bound.** The fallback is a contingency, not the chosen path (exploration notes Section 4, Section 8). This document does not name a scheduling mechanism, measure its p99, or validate the 60-second figure. If the load measurement in this document's acceptance test plan ever shows true delivery-time checking is infeasible, that re-derivation happens then, against the measurement that triggered it — not speculatively now.
- **Disclosing the cause of revocation to the affected connection.** Reaffirmed as a non-goal for the same no-surveillance reasoning as the archived change: silence is correct, and telling a removed connection why its events stopped would itself be a surveillance-adjacent behavior.
- **Socket.IO, or any transport whose idiomatic fan-out abstraction hides the moment of per-recipient write.** Ruled out in Explore (Section 2), not reopened here.

## Decisions

### Decision D1: Transport — `@fastify/websocket`, not Socket.IO

**Choice:** Use `@fastify/websocket` (the official Fastify plugin, built on `ws`). Add it to `packages/backend/package.json`.

**Rationale (from exploration notes Section 2, adopted verbatim):** The wire-level push requirement — the delivery-time check must be evaluated immediately before a specific connection's `.send()` call — is the deciding factor, not house style. With `@fastify/websocket`, a connection is a plain object with a `.send()` method called once per recipient in application code; the authorization check and the `.send()` call are adjacent lines in the same function, with no framework abstraction between them that could pull the check earlier. `@fastify/websocket` also integrates with Fastify's request lifecycle, so the WebSocket upgrade handshake runs through the same `request.session` resolution every HTTP route already gets — connection-time authentication (SEC-28) is the existing session validation applied to the upgrade request, not a new mechanism.

Socket.IO's idiomatic `io.to(room).emit(...)` pattern abstracts away exactly the moment this design needs to control. Its Redis adapter dequeues and re-emits to a room; nothing in that flow invites a per-recipient authorization check at the point of write without fighting the library's own idiom — which is the exact anti-pattern the spec names ("evaluates authorization when events are dequeued from the channel and caches the result until wire delivery").

**Alternative considered:** Socket.IO with manual per-socket iteration bypassing the room/adapter abstraction. Rejected — if the room abstraction has to be bypassed to get the required property, Socket.IO contributes a heavier dependency and a non-standard wire protocol for no benefit over raw `ws`.

### Decision D2: Fan-out — Redis pub/sub via `ioredis`, required

**Choice:** Redis pub/sub sits in the delivery path for all four events. Every backend pod publishes to a shared channel; every pod's subscriber inspects its own local connection registry and acts only on locally-held candidates.

**Rationale (from exploration notes Section 3):** The `app` deployment is stateless and horizontally scalable by explicit architectural commitment (`requirements/High-Level Architecture.md` lines 626, 765). A WebSocket connection is pinned to whichever pod accepted it; an event triggered on pod A (an HTTP request, or a WebSocket message handled on pod A) has no way to reach a socket living in pod B's process memory without a cross-pod signaling mechanism. `ioredis` is already a dependency, already used for the session store and live session state. Introducing a second broker for this one purpose would add infrastructure the codebase doesn't need and would contradict the stateless-app premise already decided elsewhere.

**Architecture:**

**Note on the top box below:** as of this revision, "Postgres commit" is real for vote lock-in, lobby advance, and session completion. It is **not yet real** for reveal, topic advance, or membership change — see "Blocking Dependency" above. The diagram states the general shape of the pipeline for all four events; the reveal/topic-advance/membership-change legs of it have no commit to trigger from today.

```
Postgres commit (vote lock-in / reveal / topic advance / membership change)
        │
        ▼ triggers event
  Redis PUBLISH (ioredis) — channel: ws:events
        │
        ├──────────────► Pod A: local registry lookup → for EACH local candidate
        │                  socket: evaluateTeamAccess (or session-scoped check)
        │                  RIGHT NOW → ws.send() if authorized, nothing if not
        │
        └──────────────► Pod B: local registry lookup → for EACH local candidate
                           socket: evaluateTeamAccess (or session-scoped check)
                           RIGHT NOW → ws.send() if authorized, nothing if not
```

The check is never done once "for the event" — it is done once per candidate connection, on whichever pod happens to hold that connection, at the instant that pod is about to write to it. This is the only way to satisfy "the server MUST NOT rely on the subscriber's authorization status as evaluated at connection time or subscription time" once a pub/sub hop sits between the trigger and the socket.

**Sub-decisions named by the exploration notes as Design-stage work (Section 11), resolved here:**

- **Message envelope / channel topology:** A single Redis channel (`ws:events`) carries all four event types for every team and session. Each published message is a JSON envelope: `{ eventType: 'vote_readiness_update' | 'session_state_change' | 'vote_revealed' | 'topic_history_update', sessionId?: string, teamId?: string, payload: unknown }`. Session-scoped events (`vote_readiness_update`, `session_state_change`, `vote_revealed`) carry `sessionId`; the team-scoped event (`topic_history_update`) carries `teamId`. A single channel is chosen over per-team/per-session channels because the local registry lookup (keyed by `sessionId` or `teamId`) already narrows the fan-out to relevant local sockets cheaply — splitting channels would add Redis-side subscription management complexity without reducing the per-message authorization work, which is the actual cost center per Section 4's analysis.
- **Subscriber connection isolation (named during Design-stage review, Marcus Oyelaran, Full Stack Engineer — verified against `packages/backend/src/redis.ts`):** The per-pod pub/sub subscriber MUST use a connection created via `redis.duplicate()`, not the shared `redis` singleton `redis.ts` exports. That singleton is a plain `ioredis` client already used for ordinary commands by three other call sites — `@fastify/session`'s Redis-backed store (`app.ts`), the health check (`health.ts`), and OIDC state (`auth.ts`). The moment `.subscribe()` is called on an `ioredis` connection, that connection enters subscriber mode, and a connection in subscriber mode can run only `subscribe`/`unsubscribe`/`psubscribe`/`punsubscribe`/`ping`/`quit` — every other command on that same connection starts throwing. `redis.duplicate()` creates a second TCP connection sharing the original's connection options, free to enter subscriber mode without affecting the shared client. The publisher keeps using the existing shared `redis` client (`PUBLISH` is an ordinary command; it does not change connection mode). Called out explicitly here — and in Migration Plan step 4 and tasks.md Group 1 — because `redis.ts` is the only Redis handle in this codebase, nothing prior to this revision said "don't reuse it," and the failure mode (session store, health check, and OIDC login all breaking simultaneously the instant the first subscription connects) is severe enough that it should not be left to be discovered in CI.
- **Local registry lifecycle:** A socket is added to its pod's local registry at successful subscription (post-connection, once the client identifies which session or team channel it wants), keyed by `sessionId` (three session-scoped events) or `teamId` (`topic_history_update`). A socket is removed from the registry on WebSocket `close` or `error`, and on the server's own send failure (a `.send()` that throws because the socket already closed is treated as an implicit deregistration, logged but not raised as an authorization failure). Deregistration MUST happen before the next pub/sub message is processed for that socket to avoid a `.send()` call against a closed connection. **Verification required, not assumed (named during Design-stage review, Marcus Oyelaran):** `ws`'s actual `.send()` behavior across `CLOSING`/`CLOSED` readyState is version- and call-site-dependent — `ws` does not uniformly throw synchronously for every non-`OPEN` state, and `@fastify/websocket` pins `ws@^8.16.0`. Task 3.5 requires verifying this empirically against the pinned version's actual behavior in each readyState before treating "a `.send()` that throws" as the sole deregistration trigger. If the pinned version no-ops instead of throwing in some readyState, the registry needs an explicit `readyState` check before every `.send()` call as a second deregistration trigger, not just a `try`/`catch`. This is a verification task, not a design blocker — it does not change the deregistration mechanism described above, only confirms (or corrects) the assumption it rests on.
- **Redis pub/sub has no replay (named during Design-stage review, Marcus Oyelaran):** `ioredis` automatically reconnects a dropped connection and automatically re-issues `SUBSCRIBE` for previously-subscribed channels on reconnect — the *subscription* recovers on its own, no code required. Redis pub/sub itself is fire-and-forget, however: any message `PUBLISH`ed while a given pod's subscriber connection is down is gone, permanently, for that pod — not delayed, not retried. For `vote_revealed` specifically, this means recipients pinned to a pod whose subscriber connection blips for even a few hundred milliseconds at the exact moment of publish silently never receive that event, while recipients on unaffected pods do — a correlated, per-pod total-loss failure for a subset of recipients, not a latency tail the p95/p99 measurement in Decision D6 would ever surface. This is accepted as a known, named gap for this change — a queued or durable pub/sub mechanism would require a second broker, contradicting this decision's own rationale for reusing `ioredis` — with one required mitigation, not zero: the subscriber connection MUST log a structured warning on `ioredis`'s `reconnecting` and `ready` events, so an operator can correlate a "my view went quiet" report with a real reconnect event in the logs. The client-side staleness signal (tasks.md Group 9) is the only thing that would ever surface this to a participant directly, and only if they notice and refresh.
- **Dual-role admin+member trade-off, confirmed intentional (named during Design-stage review, Tomás Ferreira, Security Analyst):** `evaluateTeamAccess`'s precedence order (`packages/backend/src/auth/team-content-access-helper.ts`) checks and returns `{ path: 'admin' }` for `application_admin` callers before `team_memberships.role` is ever inspected, even though both are fetched in the same query row. A user who is globally `application_admin` **and** holds a genuine `team_memberships` row for a team therefore receives only the `admin` grant — never the `member` grant their own membership would otherwise produce. Combined with `topic_history_update`'s `admin`-path rejection (below), such a person receives zero WebSocket team-content events for their own team, not a reduced admin view. This is not a new decision introduced by this change — it is inherited verbatim from the archived `enforce-access-control-on-team-content` change's Decision 2/Decision 8 (Option B), and it is applied identically at the HTTP layer today (the same person gets 403 on session-content HTTP endpoints too). This document records it here as a known, accepted trade-off of Option B, not an oversight: disambiguating "is this admin session legitimately also a member session" at delivery time would require carrying additional context through the grant that Decision 8 deliberately kept out of the helper's contract, and blocking the union is the safer failure mode from a surveillance-prevention standpoint. Onboarding guidance (outside this change) should flag that assigning `application_admin` to someone who also needs ordinary session access on a team they belong to will silently cost them that access — that guidance is not this change's deliverable, but the trade-off itself should be documented here rather than discoverable only by reading the spec's scenario text closely.

### Decision D3: Delivery-time check placement and the concurrency model

**Choice:** The authorization check for each locally-held candidate connection runs inside the pod's Redis subscription message handler, individually per candidate socket, immediately before that socket's `.send()` call. Never before, never cached, never batched across recipients without a per-recipient check — this rule is inherited from Decision 6 of the archived design (authorization cache prohibition) and is not re-derived here; it applies structurally to this transport the same way it applies to the HTTP layer.

**Per-pod concurrency model (named as a required Design decision in exploration notes Section 9, item 5):** Recipient authorization checks for local candidates of the same event run **concurrently** (`Promise.all` over the local candidate set for that event), not serially. Given this application's session sizes (a facilitator plus a handful of participants — single digits, per the ritual's own small-team design), the worst-case local fan-out width for a single pod holding multiple candidates for the same event is bounded in the single digits. Concurrent evaluation avoids the tail-latency problem a serial loop would introduce (the last socket checked on a pod holding several candidates would otherwise see its event measurably later than the first, before any cross-pod effect even enters the picture) and is the direct input the cross-recipient skew measurement (Decision D5) depends on.

**Per-event mapping (exploration notes Section 6, unchanged from Explore):**

| Event | Scope | Check to reuse |
|---|---|---|
| `vote_readiness_update` | Session | `sessions.facilitator_id = $subscriber AND sessions.status IN ('pre_session', 'active')` — Path 3 predicate, narrowed to live statuses |
| `session_state_change` | Session | Active participant OR active facilitator — combination of Path 1/3 |
| `vote_revealed` | Session | Same participant-or-facilitator check, plus `serializeForFacilitator` / `serializeForMemberParticipant` reveal-status gating |
| `topic_history_update` | Team | `evaluateTeamAccess` verbatim; deliver to `member` **or** `facilitator` grant paths; **the `admin` grant path is explicitly rejected** |

`topic_history_update` calls `evaluateTeamAccess` verbatim and delivers to any non-`admin` grant path — `member` and `facilitator` alike — inspecting `grant.path !== 'admin'` before delivering. **Corrected during Design-stage review (Marcus Oyelaran, Full Stack Engineer):** an earlier revision of this table read "Path 1 or Path 2," loosely inherited from the archived HTTP design's numbered-path terminology (where "Path 3" denotes the facilitator grant), and — combined with tasks.md 4.5's earlier wording, "deliver only if the returned grant path is `member`" — implied facilitator subscribers should be rejected alongside admin. That was never the intent, and it was never consistent with this change's own delta spec: `specs/websocket-session-authorization/spec.md`'s requirement text already correctly states delivery to `grant.path === 'member'` **or** `grant.path === 'facilitator'`, admin rejected. It also matches the HTTP endpoints serving the same content class — `GET /api/v1/teams/:teamId/topics` and `/action-items` in `content.ts` (lines 400–484) deny only `grant.path === 'admin'` and proceed identically for `member` and `facilitator` grants; there is no facilitator-specific query variant for either endpoint. Only this table's shorthand, and tasks.md 4.5's wording, had drifted from both the spec and the HTTP precedent — this document's own `grant.path !== 'admin'` framing was already correct. Fixed here (and in tasks.md 4.5) to drop the numbered-path terminology entirely and state the rule the way the spec and the HTTP endpoints both already do: reject only `admin`; deliver to `member` and `facilitator` alike.

The three session-scoped events need a lighter, session-specific check that doesn't exist as a standalone function yet: a new narrow helper, `evaluateSessionSubscriberAccess(userId, sessionId)`, built in `packages/backend/src/auth/` alongside `team-content-access-helper.ts`, implementing the same Path 1/3 query shape scoped to a session rather than a team. This is a thin sibling, not a third independent implementation of the same predicate — it queries the same tables with the same indexes (`sessions(facilitator_id, team_id, status)`, `team_memberships(user_id, team_id)` from Groups 1–2) and returns a grant-shaped result the WebSocket handlers can branch on the same way HTTP handlers branch on `evaluateTeamAccess`'s return value.

**The drift risk this decision exists to prevent (exploration notes Section 5, restated for implementers):** The natural way to write a Redis pub/sub consumer is to subscribe once and, in the message handler, iterate local sockets and forward the payload — code that *looks* like a per-event check because it runs once per incoming pub/sub message. If the authorization check that gates each socket's `.send()` was actually done at subscription time (when the socket first joined the channel) and the result stored on the connection object for reuse, the implementation has silently regressed to subscription-time checking while appearing, structurally, to be an event-driven delivery loop. The tell in code review: is the authorization check called inside the per-message handler, once per candidate socket, every single time a message arrives — or is it called once at subscribe time with the result cached? The second shape compiles and passes a naive test. It is wrong. The integration test named in Decision D6 exists specifically to catch this.

### Decision D4: `vote_revealed` reuses the existing serializer — no parallel reveal logic

**Choice:** The WebSocket handler for `vote_revealed` calls `serializeForFacilitator` / `serializeForMemberParticipant` (`packages/backend/src/content/team-content-serializers.ts`) to construct the event payload. It does not build independent payload-construction logic, even logic that appears "obviously" equivalent.

**Rationale:** Decision 9 of the archived design requires two independent enforcement layers for the pre-reveal/post-reveal boundary: the authorization check and the serializer. If the WebSocket handler reimplements payload construction instead of calling the existing serializer functions, the two-layer enforcement becomes two *different* implementations of the same layer, and the named regression tests (`layer-removal-serializer-check`, `layer-removal-auth-check`) protect only the HTTP path. `vote_revealed` is a new content endpoint in every sense that matters here, and it inherits the "call the shared function, do not build a parallel one" rule without exception — the same rule Decision 8's grant-type contract and this document's own D3 apply to the authorization side.

### Decision D5: Cross-recipient delivery-skew measurement

**Choice:** In addition to per-connection authorization-check-plus-send latency (measured at p95/p99 under a stated concurrent-session/event-rate load, per exploration notes Section 9 items 1–2), measure the delta between the first-delivered and last-delivered timestamps for the same fan-out event, across all locally- and remotely-held recipient connections, under realistic concurrent-session load.

**Rationale:** Single-connection latency numbers verify that one check-plus-send is fast. They do not verify that all recipients of the same `vote_revealed` event see it within a tight window of each other — which is the property the simultaneous-reveal guarantee actually depends on, and one of the ritual's load-bearing constraints (alongside the no-manager rule and the facilitator-from-another-team requirement). A system where every individual check-plus-send completes in 20ms but cross-pod pub/sub propagation and per-pod queuing add 300ms of variance between recipients would pass the per-connection latency test and still fail the actual reveal-simultaneity requirement.

**Pass/fail threshold:** Not set in this document. Per the spec's new requirement ("Cross-recipient delivery skew is bounded for simultaneous fan-out events"), the measurement MUST be taken and checked against a documented budget before production; the numeric budget itself requires a UX-sourced input this document doesn't have. Whoever sets it should pair the measured number with the Facilitator SME's offered live or simulated multi-device usability pass on the reveal specifically — a measured skew number and a human confirming the reveal still feels simultaneous is the right combination of rigor and felt-experience validation for a requirement this central to the ritual.

**Right-sized per Executive review (Rachel Okonkwo):** this measurement is a **one-time sanity check against a documented placeholder budget**, not a fully-derived, UX-sourced acceptance gate re-run to exhaustion. There is no production traffic and no real concurrent-session load profile yet — only "single digits per session, per the ritual's own design." Take the measurement once under a plausible pilot load, confirm it doesn't blow up against a generously-set, explicitly-labeled placeholder budget, document it, and move on. If real pilot usage later shows the number needs tightening, that is a follow-up informed by actual data, not a reason to hold this change's correctness work (the authorization checks themselves, admin-grant rejection, reveal-serializer reuse) for a number nobody can source today. This does not relax the *labeling* discipline Marcus's review asked for immediately below — a placeholder that is a sanity check must still be visibly a placeholder, not a number that quietly becomes treated as validated because nobody revisited it.

### Decision D6: Acceptance test plan (analog to Group 6's timing-oracle precedent, right-sized to a system with no live traffic)

The following measurements and tests are required before this capability ships to production. Items 1–3 (performance/skew) mirror the *rigor* `timing-oracle.ts` established for the HTTP timing-oracle mitigation but not its *weight*: per Rachel Okonkwo's Executive review, this is a one-time sanity check against a documented placeholder, not a fully-derived acceptance gate chasing a load profile that doesn't exist yet. Item 5 onward (correctness) is not right-sized down — those tests are cheap, non-negotiable, and required at full rigor regardless of traffic volume.

1. Measure per-event, per-candidate-connection authorization-check-plus-send latency under a realistic concurrent session/connection count, at p95 and p99 (not mean). One-time measurement, not a recurring load-test regime.
2. Confirm p99 does not exceed a stated threshold. The exploration notes' ~100ms figure is an engineering placeholder pending a sourced UX number — Design (this document) does not invent a replacement number; whoever runs this measurement should **explicitly label the figure a placeholder** if no UX-sourced number exists by the time the measurement is taken (the same discipline already applied to the 60-second fallback figure in exploration notes Section 8), rather than letting an unlabeled number quietly be treated as validated.
3. Measure cross-recipient delivery skew per Decision D5, at a documented, explicitly-labeled placeholder budget if no UX-sourced figure exists yet — same labeling discipline as item 2.
4. Document all of the above measurements before production deployment, the same way Group 6 requires for the timing floor.
5. Write an integration test that exercises the actual Redis pub/sub hop (not just an in-process call): subscribe a connection, revoke `team_memberships.removed_at` mid-connection, publish an event on the channel via Redis `PUBLISH` (not a direct in-process function call), and assert nothing is delivered. This is the test that catches the subscription-time-caching drift named in Decision D3 — an in-process-only test would not exercise the actual dequeue/re-check path and would not catch that regression.
6. Write an integration test asserting an Application Admin subscriber does not receive `topic_history_update` events (Decision D2's grant-path rejection).
7. Write integration tests for all four events per archived task 9.10: authorized subscriber receives the event; unauthorized subscriber does not; a subscriber removed mid-connection stops receiving events on the next push without reconnecting.

### Decision D7: Audit logging for WebSocket-triggered actions (SEC-13/SEC-14)

**Choice:** Verified against actual code (not assumed, per the exploration notes' own instruction to Propose): `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal` in `packages/backend/src/routes/facilitator-sessions.ts` currently authorizes and validates session state but does not write an `audit_log` row. Session-state-transition actions in the same file are similarly not currently audit-logged. This means the exploration notes' expected default ("the triggering action is already logged; the fix is additive — a session identifier only") does **not** hold. Per the exploration notes' own contingency for this outcome, this change adds audit logging for the reveal action and session-state-change actions as an in-scope acceptance criterion, not a follow-up.

**Corrected during Propose-stage review (Marcus Delgado):** the field list and mechanism originally written here did not match the actual `audit_log` schema or the actual behavior of `emitAuditEvent`. Both are fixed below. This was a factual bug in this document, not a judgment call — an implementer following the prior text would have written a query against columns that don't exist.

**What was wrong:**
- `emitAuditEvent` (`packages/backend/src/auth/audit-logger.ts`) does **not** write to the `audit_log` table. It is a structured-log (pino) emitter — the code's own comments call it "the operational alert path," explicitly distinct from the authoritative DB record. Every real `audit_log` row is written by a hand-written `INSERT INTO audit_log (...)` (via `db.query` or `client.query` inside a transaction), executed *alongside* — never instead of — a separate `emitAuditEvent` call.
- The field list named (`action`, `resource_type`, `resource_id`) does not exist on the table. The real schema (migration `8_audit_log.sql`) is: `id, actor_user_id, actor_global_role, actor_ip, operation, target_user_id, team_id, timestamp, metadata (JSONB)`. Every existing call site uses `operation` — a dot-namespaced string from the `AuditEventName` union — and puts endpoint-specific detail, including a session identifier, into `metadata` as JSON. `em-views.ts` line 380 is the direct precedent: `JSON.stringify({ session_id: sessionId })` alongside `operation: "em.session_detail_accessed"`.
- `AuditEventName` (`audit-logger.ts`) is a closed union type, not a free-form string. This change needs two new values added to it, following the file's existing naming and commenting convention (each entry names which DB write it's the structured-log counterpart to).

**Implementation (corrected):** For each triggering action, in the same statement/transaction as the action's own state-transition write:

1. Execute `INSERT INTO audit_log (actor_user_id, actor_global_role, actor_ip, operation, team_id, metadata) VALUES ($1, $2, $3, $4, $5, $6)`, matching the exact pattern in `em-views.ts` (e.g. lines 372–381) and `content.ts`.
2. Use a new `operation` value for each of the two action types, added to the `AuditEventName` union in `audit-logger.ts` with a comment identifying it as the structured-log counterpart to this DB row, matching the file's existing convention:
   - `session.reveal_triggered` for the reveal action.
   - `session.state_changed` for session-state-transition actions (lobby advance, session close — see the Blocking Dependency section above for why topic advance is not included yet).
3. Put the session identifier, and any other endpoint-specific detail (e.g. prior/new status for state-transition actions), in `metadata` as JSON: `{ session_id: sessionId, ... }`, following the `em.session_detail_accessed` precedent.
4. Call `emitAuditEvent(request.log, operation, fields)` immediately after the INSERT, with the same operation name and fields, as the structured-log counterpart — not a substitute for the INSERT.

This is once per triggering action, not once per WebSocket recipient. The audit entry is traceable to the live session in which the resulting WebSocket delivery occurred via the `session_id` in `metadata`.

**Extended during Design-stage review (Tomás Ferreira, Security Analyst): vote-submission audit logging was missing entirely, and is not blocked on issue #26.** BRD SEC-13 names vote *submission* alongside *reveal* as a required audit category ("vote events (submission, reveal)"); SEC-14 restates this for the WebSocket path specifically ("Vote submissions, reveals, and session state changes over WebSocket must appear in the audit log"). The version of this decision reviewed at Design stage added audit logging only for the reveal action and session-state-change actions — verified against `packages/backend/src/routes/sessions.ts`'s vote lock-in handler (`POST /api/v1/sessions/:sessionId/topics/:sessionTopicId/lock-in`), there is no `audit_log` write and no `emitAuditEvent` call anywhere in that file. Vote submission was not audit-logged at all, at either the HTTP or the WebSocket layer, and — unlike the reveal and topic-advance gaps — this one is **not** blocked by GitHub issue #26: the lock-in handler's `INSERT INTO votes` (line ~296) already commits today, the same way lobby-advance and session-close already commit. There was no reason for this gap to wait.

This decision now adds a fourth triggering action to its scope:

- New `AuditEventName` value: `session.vote_submitted`, added to `audit-logger.ts` alongside `session.reveal_triggered` and `session.state_changed`, following the file's existing naming/commenting convention.
- `INSERT INTO audit_log (actor_user_id, actor_global_role, actor_ip, operation, team_id, metadata)` with `operation = 'session.vote_submitted'`. `metadata` carries `{ session_id: sessionId, session_topic_id: sessionTopicId }` **and explicitly excludes `vote_value` and `vote_type`** — the same SEC-16/SEC-22 exclusion this decision already applies to reveal and state-change metadata, restated here because vote submission is the one triggering action in this document where the sensitive value being excluded and the value the handler is actually processing are the same field, so the exclusion is easiest to get wrong here.
- Followed immediately by `emitAuditEvent(request.log, 'session.vote_submitted', fields)`, the same structured-log counterpart pattern as the other two operations.

This is once per lock-in attempt, including re-submission — the handler's own `ON CONFLICT (session_topic_id, voter_id) DO UPDATE` treats a resubmission as an update to the same row, not a new one, so the audit trail records once per lock-in call, matching the row it updates — not once per WebSocket recipient of the resulting `vote_readiness_update` event, the same "once per triggering action" principle this decision already establishes for reveal and state-change.

**Transaction-pattern correction (Marcus Oyelaran, Full Stack Engineer, Design-stage review):** "in the same statement/transaction as the action's own state-transition write" (point 1 of the corrected mechanism, above) assumes a transaction wrapper that does not exist yet at any of the three call sites this decision now touches. `packages/backend/src/routes/teams.ts` (lines 494–577, 767–812) is the only place in this codebase with an explicit `db.connect()` → `BEGIN` → queries → `COMMIT`/`ROLLBACK` (in `catch`) → `client.release()` (in `finally`) pattern. The lobby-advance and session-close handlers in `facilitator-sessions.ts`, and the vote lock-in handler in `sessions.ts`, all currently execute a single bare `db.query(...)` against the shared pool — no transaction. Adding an `audit_log` INSERT to each of these three handlers means refactoring each from a bare pool query to the `teams.ts` transaction pattern, not simply appending a second `db.query` call after the first — appending would leave a window where the state-transition write commits but the audit write fails (or vice versa), silently weakening the atomicity this decision asks for. This is a known, copyable pattern, not a design risk, but it is a real scope addition to each of the three handlers, and tasks.md 7.2, 7.3, and the new vote-submission task now state it explicitly rather than leave it implicit.

**Dependency note (see Blocking Dependency, above):** for the reveal action specifically, there is currently no point at which the reveal "is authorized and executed" — only a point at which its preconditions are validated (see the Blocking Dependency section). The `session.reveal_triggered` audit write cannot be placed "in the same statement/transaction as the reveal's state-transition write" until that write exists. This task is buildable and unit-testable against a stubbed commit point today; it is blocked from real end-to-end completion on GitHub issue #26, same as the `vote_revealed` publish call itself. The `session.state_changed` write for lobby-advance and session-close has no such blocker — both already commit a real state transition today.

**Alternative considered:** Logging at the WebSocket fan-out layer instead of the triggering-action layer (one row per event published, or one row per delivered push). Rejected: this would produce one row per recipient for a single facilitator action, misrepresenting the actual action count in the audit trail, and would duplicate work already naturally located at the point where the action is authorized.

### Decision D8: SEC-25/SEC-26 tracked to a companion effort, not designed here

**Choice:** File a companion issue (or change, at the discretion of whoever triages it) covering both SEC-25's idle-connection re-authorization gap and SEC-26's token-expiry/silent-refresh requirement, before this change (websocket-delivery-time-authorization) is marked complete. This document does not name the mechanism (single combined heartbeat vs. two separate mechanisms), the interval, or the owner — per the exploration notes (Section 7), that is explicitly Design-stage work for the companion effort, not for this document.

**Rationale:** Delivery-time checks (this change's actual scope) close the SEC-27 revocation-latency window on connections actively receiving events. They structurally cannot reach a connection that receives no events for an entire token-expiry window — there is nothing to check against. That is a different requirement (SEC-25) than the one this change resolves (SEC-27), and conflating them was an error caught during Explore-stage review that this document does not want to repeat by inventing a heartbeat mechanism under this change's own time pressure. The one commitment this document makes is that the gap gets a named tracking destination and does not ship as a footnote nobody reads again.

**Compensating control added during Design-stage review (Tomás Ferreira, Security Analyst): reuse the existing absolute-lifetime cap rather than leave the idle-connection window fully unbounded.** `packages/backend/src/auth/middleware.ts` already implements `ABSOLUTE_LIFETIME_MS = 90 * 60 * 1000` (90 minutes), enforced in an `onRequest` hook: if `Date.now() - sessionCreated > ABSOLUTE_LIFETIME_MS`, the session is destroyed and `auth.session_invalidated` (`reason: "absolute_timeout"`) is emitted — exactly BRD SEC-26's absolute-session-lifetime requirement. Per Decision D1, the WebSocket upgrade handshake runs through this same hook, so the check fires once, at connect time. It does not run again for the life of an already-established socket, because there is no subsequent HTTP request for the hook to attach to — an idle or long-lived connection's authorization window would otherwise stay unbounded until the SEC-25/26 companion effort ships its own heartbeat, with nothing this change does closing it in the meantime.

This document does not design the SEC-25 heartbeat (periodic re-authorization against current team membership) here — that stays deferred to the companion effort, unchanged. But bounding the connection's *absolute* lifetime is a different, much cheaper problem: the value already exists, is already resolved onto `request.session` at upgrade time (`session.sessionCreatedAt`), and needs no new query or mechanism to reuse. This change adds:

1. Capture `sessionCreatedAt` from `request.session` into the per-pod connection registry entry at the time a socket is registered (Decision D2's local registry, Group 3).
2. The delivery-time check (Decision D3) rejects — treated the same as an ordinary authorization failure, not surfaced as a distinguishable error — if `Date.now() - sessionCreatedAt > ABSOLUTE_LIFETIME_MS`, before running the event-specific `evaluateTeamAccess`/`evaluateSessionSubscriberAccess` check. This is a cheap, no-new-query addition to a check that already runs on every push.
3. A server-side scheduled force-close of the socket at the 90-minute mark, mirroring what `authMiddleware` already does for HTTP, so a connection that never receives another event is still eventually closed rather than left open indefinitely — closing the specific "quiet lobby" scenario the spec's own SEC-25 scenario names, which (2) alone cannot reach (it only runs when an event is pushed).

This converts the residual risk from "unbounded until SEC-25/26 ships" to "bounded to the same 90-minute absolute cap already enforced everywhere else in the application" — a materially different posture, for the cost of reusing one existing constant and one existing timestamp. It is explicitly **not** a substitute for the SEC-25 heartbeat: a membership change that happens well inside the 90-minute window is still not caught by this control, only total connection age is. The companion effort remains the acceptance criterion for SEC-25/26's own resolution, per the spec's existing "Companion tracking effort exists" scenario — this is a bound on the window's outer edge, not a fix for its middle.

### Decision D9: Explicit Origin validation on the WebSocket upgrade handshake (CSWSH)

**Named during Design-stage review (Marcus Oyelaran, Full Stack Engineer) — absent from three prior review rounds (Facilitator SME, BA, Executive) at Explore and Propose stage.**

Decision D1's connection-time authentication claim is correct as far as it goes: `@fastify/websocket`'s upgrade handling runs through Fastify's normal request lifecycle, so `request.session` is genuinely resolved and validated by the time a WS route handler runs — verified structurally during this review, not assumed. What that claim does not cover: a WebSocket upgrade handshake is not subject to the Same-Origin Policy's CORS preflight the way a `fetch`/XHR request is. `@fastify/cors`'s origin allowlist (`app.ts`) does not extend to the WS upgrade path. A page on any origin can open `new WebSocket(...)` against this server from a victim's browser, and the browser will still attach the session cookie on the handshake request, because cookie attachment follows the cookie's own attributes, not CORS.

**Verified, not assumed, during this review:** the session cookie is already configured `sameSite: "strict"` (`app.ts`, the `@fastify/session` registration). A `SameSite=Strict` cookie is not attached on a genuinely cross-site request, which substantially mitigates this class of attack already — this is a real, existing control, not a gap this document invents a fix for from nothing. It is not, however, a complete substitute for an explicit Origin check on the WS path specifically: `SameSite` enforcement for WebSocket upgrade requests has historically been less consistently implemented across browser versions than for `fetch`/XHR, and relying on a cookie attribute alone — set for an unrelated reason (general CSRF hardening), never evaluated by anyone as this application's CSWSH control — is exactly the kind of implicit security decision this review process exists to surface and make deliberate instead of accidental.

**Choice:** The WebSocket route registration adds an `onRequest` (or equivalent `preHandler`, run before `request.session` is consulted) check that inspects `request.headers.origin` against the same allowlist `@fastify/cors` already uses in `app.ts`, and rejects the upgrade if it does not match. This reuses an existing allowlist — no new configuration surface — and answers a question `request.session` resolution does not answer: not "who does this cookie belong to," but "is this request coming from a page we trust to hold that cookie."

**Alternative considered:** Relying solely on `SameSite=Strict`. Rejected as the *sole* control — it's a real mitigation worth keeping, but it protects against this attack class as an accident of an unrelated CSRF-hardening choice, not a decision anyone made about WebSocket security specifically; treating it as sufficient here would be exactly the un-reviewed, framework-default security posture this design process exists to prevent.

### Decision D10: Redis hardening assumptions for vote-value payloads now transiting the shared Redis instance

**Named during Design-stage review (Tomás Ferreira, Security Analyst) — not previously stated anywhere in this document's threat model.**

Decision D2's fan-out model publishes the full event envelope — for `vote_revealed`, including the revealed vote distribution — to a single shared Redis channel that every pod subscribes to, unconditionally, before any per-recipient authorization decision is made. This is the correct architecture for the cross-pod delivery problem (Decision D2 is not reopened here), but it changes what this Redis instance carries: today it holds session-store data (`dipstick:session:` keys) — opaque server-side identifiers. This change adds a new, higher-sensitivity payload class — actual revealed vote content and team/session identifiers — to the same instance, delivered as a broadcast primitive by design.

This is acceptable only if Redis itself is treated as inside the trust boundary and hardened accordingly. This document states that assumption explicitly rather than leaving it implicit:

1. **Authentication and network isolation are required, not optional.** The Redis instance MUST require authentication (`requirepass` or ACL) and MUST be network-isolated to the backend pods — not reachable from outside the cluster/VPC. This is a deployment-configuration requirement this design depends on; it is not built by this change's code, but this change's security properties do not hold without it.
2. **Redis command logging must not become an unaudited copy of the audit trail's own exclusion list.** SEC-16/SEC-22 already require that vote data never be written to application logs. That requirement extends to Redis's own operational logging: `MONITOR` and argument-capturing slow-log, if enabled in production, would write full `PUBLISH` payloads — including revealed vote values — to a destination this document's audit-logging decision (D7) neither covers nor knows about. Production MUST confirm `MONITOR`/argument-capturing slow-log is disabled, or, if there is a genuine operational need for it, that its output is treated as an `audit_log`-adjacent sensitive destination with equivalent access controls.
3. **TLS in transit is required if Redis ever crosses a network boundary that isn't already fully trusted** — e.g., a managed Redis service reached over a shared network rather than a same-VPC path. Not required for a same-cluster deployment where the network path is already the trust boundary; required the moment that assumption changes.

None of this changes Decision D2's fan-out architecture. It is a statement of what has to be true about the deployment environment for that architecture's security properties to hold — the same kind of explicit boundary-and-dependency documentation this document already provides for the OIDC identity provider and the Kubernetes stateless-app commitment, extended to cover a dependency (Redis) whose sensitivity classification just changed as a side effect of this change's own design.

## Risks / Trade-offs

**[Risk: An implementer treats the reveal, topic-advance, or membership-removal publish/audit wiring as a simple "add a call after the existing commit" task, discovers mid-sprint that no such commit exists, and either invents one under time pressure or stalls] → Mitigation:** Named explicitly and in advance in the Blocking Dependency section above, in proposal.md's Out of Scope section, and in tasks.md's Group 0. The gap is filed as GitHub issue #26 rather than left implicit. Tasks 1.4, 4.4, 4.5, and 7.2 are annotated with exactly which parts are buildable now (against a stubbed trigger) and which parts are blocked on issue #26 for true end-to-end completion.

**[Risk: Delivery-time checks add latency to every pushed event] → Mitigation:** The authorization queries are already fast and indexed (Groups 1–2's `sessions(facilitator_id, team_id, status)` and `team_memberships(user_id, team_id)` indexes). Fan-out volume is small — this is an internal tool with single-digit session sizes and human-paced event triggers, not a high-frequency stream. Decision D6's measurement plan verifies this holds under realistic load before production; if it does not, the timer-based fallback is the named (but not pre-approved) contingency in the exploration notes, Section 8.

**[Risk: Cross-pod pub/sub propagation introduces cross-recipient skew that breaks the felt simultaneity of a reveal] → Mitigation:** Decision D5's dedicated skew measurement, informed by Decision D3's concurrent (not serial) per-pod concurrency model, catches this before production. Priya Nair's offered live/simulated multi-device usability pass on the reveal specifically is the felt-experience complement to the numeric measurement.

**[Risk: A well-intentioned implementation regresses to subscription-time caching while structurally appearing to be a delivery-time check] → Mitigation:** Decision D3 names the exact code-review tell; Decision D6 item 5 requires an integration test that exercises the actual Redis pub/sub hop, not just an in-process handler, specifically because this drift is invisible to a test that bypasses the hop.

**[Risk: `topic_history_update`'s admin-grant rejection is missed because "reuse the existing helper" reads as sufficient] → Mitigation:** The modified spec requirement and Decision D2 both state the rejection explicitly and normatively. Decision D6 item 6 requires a dedicated integration test for this specific case, independent of the general four-event authorized/unauthorized test matrix.

**[Risk: SEC-25/SEC-26 tracking is filed and then forgotten, becoming exactly the kind of footnote this document argues against] → Mitigation:** Named as a completion criterion for this change (Decision D8; also reflected in tasks.md), not merely a suggestion. The new spec requirement makes the tracking destination's existence — not the mechanism — the testable acceptance criterion, so its absence is a spec violation, not an omission that only shows up in a retrospective conversation.

**[Risk: The reveal/session-state audit logging added here (Decision D7) is scoped too narrowly and misses other privileged facilitator actions] → Mitigation:** This change's scope now covers the three actions SEC-13/14 name explicitly (vote submission, reveal, session state change) and that fire three of the four in-scope WebSocket events. Other privileged actions (topic advance, session close) are session-state-change triggers and are covered by the same audit-logging addition at the point they transition `sessions.status`. If additional privileged actions are discovered during implementation that trigger these events without going through the audited code path, they must be added to the same audit point, not given a separate one.

**[Risk: Redis pub/sub has no replay; a subscriber-side reconnect silently drops whatever was published during the gap, correlated per-pod rather than showing up as latency] → Mitigation:** Named explicitly in Decision D2 (added during Design-stage review, Marcus Oyelaran) as a known, accepted gap rather than left undiscussed — queuing or durable delivery would require a second broker, contradicting D2's own rationale for reusing `ioredis`. The named mitigation is operational visibility, not elimination of the gap: the subscriber connection logs a structured warning on `ioredis`'s `reconnecting`/`ready` transitions. The client-side staleness signal (tasks.md Group 9) is the only path by which this would ever surface to an affected participant, and only if they notice and refresh.

**[Risk: A WebSocket upgrade handshake bypasses CORS preflight, letting a cross-site page ride the session cookie onto a live socket (CSWSH)] → Mitigation:** Decision D9 (named during Design-stage review, Marcus Oyelaran). The existing `sameSite: "strict"` session cookie already mitigates this substantially, but is not treated as sufficient on its own — an explicit `Origin` check against the existing `@fastify/cors` allowlist is added to the WS upgrade path as defense-in-depth, per OWASP's WebSocket security guidance.

**[Risk: Vote-value payloads now transit the same Redis instance used for session storage, as an unfiltered broadcast to every pod, with no stated hardening assumptions] → Mitigation:** Decision D10 (named during Design-stage review, Tomás Ferreira) states the required Redis AUTH/ACL, network isolation, command-logging, and TLS-in-transit assumptions explicitly, so this change's security properties are not resting on an unstated deployment assumption.

**[Risk: Vote submission — a BRD-named audit category alongside reveal — was not audit-logged anywhere in the codebase, at either the HTTP or WebSocket layer] → Mitigation:** Named during Design-stage review (Tomás Ferreira) and closed in this revision, not deferred: Decision D7 now adds a `session.vote_submitted` audit-log write for the vote lock-in handler, which is not blocked by GitHub issue #26 (it already commits today). See Decision D7's extension, above.

## Migration Plan

1. **Dependency addition:** Add `@fastify/websocket` to `packages/backend/package.json`. No new Redis dependency — `ioredis` is already present.
2. **Authorization helper sibling:** Build `evaluateSessionSubscriberAccess` (Decision D3) alongside `evaluateTeamAccess`, tested in isolation before any WebSocket route wiring, the same way the archived change built and tested `evaluateTeamAccess` independently of endpoint changes.
3. **WebSocket route registration and connection registry:** Register the `@fastify/websocket` plugin and the per-pod local connection registry (keyed by `sessionId` / `teamId`, per Decision D2), capturing `sessionCreatedAt` into each registry entry at registration time (Decision D8's compensating control). Connection-time authentication runs through the existing `request.session` resolution — no new authentication mechanism. **Add the explicit `Origin` header check (Decision D9) as part of this same route-registration step, before `request.session` is consulted** — it is infrastructure setup, not per-event logic, and belongs alongside the plugin registration, not deferred to a later group.
4. **Redis pub/sub wiring:** Implement the `ws:events` channel publisher and the per-pod subscriber that performs the local-registry lookup and per-recipient delivery-time check (Decision D3). **The subscriber MUST use a connection created via `redis.duplicate()` (Decision D2), never the shared `redis` singleton from `redis.ts`** — reusing the shared client breaks the session store, health check, and OIDC login the instant the first subscription connects. Log a structured warning on the subscriber connection's `reconnecting`/`ready` transitions (Decision D2's named reconnect-gap mitigation). Follow the `TODO(#26)` comment convention (Blocking Dependency section) at every export invoked only from tests pending issue #26. The publisher is invoked from the HTTP action handlers whose state transition actually commits today — vote lock-in, lobby advance, session close. **It cannot yet be invoked from the reveal, topic-advance, or membership-change handlers, because none of those currently commits a state transition** (see Blocking Dependency, above; GitHub issue #26). Build and unit-test the publisher wrapper itself against a stubbed/direct call for those three; wire it into the real handler once the corresponding write exists.
5. **Serializer reuse for `vote_revealed`:** Wire the WebSocket handler to call `serializeForFacilitator` / `serializeForMemberParticipant` (Decision D4) — no new serializer logic.
6. **Admin-grant rejection for `topic_history_update`:** Implement the explicit `grant.path !== 'admin'` check (Decision D2/D3) as part of the same commit that wires `topic_history_update`, not a follow-up patch. Delivery proceeds for both `member` and `facilitator` grant paths — see D3's corrected per-event mapping table.
7. **Audit logging addition:** Add the `audit_log` writes for the vote-submission, reveal, and session-state-change actions (Decision D7, extended). This requires refactoring the vote lock-in handler (`sessions.ts`) and the lobby-advance/session-close handlers (`facilitator-sessions.ts`) from a bare pool query to the `teams.ts` explicit-transaction pattern (Decision D7's transaction-pattern correction) — not merely appending a second query.
8. **SEC-25/26 compensating control:** Wire the existing `ABSOLUTE_LIFETIME_MS` value into the connection registry entry and the delivery-time check, and add the scheduled 90-minute force-close (Decision D8's compensating control), as part of the same work that builds the registry (step 3) and the delivery-time check (Decision D3).
9. **Acceptance test plan:** Implement the measurements and integration tests named in Decision D6, including the pub/sub-hop revocation test and the admin-grant-rejection test, before this capability is considered ready for production.
10. **Companion tracking issue:** File the SEC-25/SEC-26 companion issue (Decision D8) with a named owner before this change is archived. This tracks the periodic re-authorization heartbeat and token-expiry mechanism — it is not superseded by step 8's compensating control, which only bounds absolute connection age.
11. **Redis hardening confirmation:** Confirm the Redis AUTH/ACL, network-isolation, command-logging, and TLS-in-transit assumptions named in Decision D10 hold for the target deployment environment, before this capability reaches production.
12. **Spec front matter:** When this change is archived and synced into `openspec/specs/websocket-session-authorization/spec.md`, remove the "Implementation status: gate-blocked" note from the spec's Purpose section — the gate this note refers to is closed by this change. This is a front-matter edit outside the delta-spec Requirements format and should be done by whoever runs the archive step.

**Rollback:** The `@fastify/websocket` addition and the new WebSocket route are additive — no existing HTTP endpoint behavior changes. If the delivery-time mechanism needs to be rolled back post-deployment, disabling the WebSocket route registration (feature-flag or route removal) reverts clients to no live-event delivery without affecting HTTP content access, which remains governed entirely by the existing `enforce-access-control-on-team-content` enforcement layer.

**Ingrid's real bug risk — accepted in full, fixed at both ends, not merely commented.** She's right that tasks.md, read in numeric order, wires a bare `redis.publish(...)` into the vote lock-in, lobby-advance, and session-close handlers (task 1.4) before tasks 7.2/7.3/7.6 refactor those same handlers into a `BEGIN`/`COMMIT` transaction for the audit-log write — and that neither task said where the publish call should land relative to the new transaction boundary.
