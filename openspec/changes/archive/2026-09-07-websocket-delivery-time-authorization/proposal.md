## Why

`enforce-access-control-on-team-content` (archived 2026-07-07) closed every access-control gap it could close except one: Group 9, WebSocket delivery-time authorization, was gate-blocked because no WebSocket infrastructure existed yet and the "engineering lead" decision the gate required — a concrete, testable transport and enforcement approach — was never made. That gate traces directly back to BRD SEC-25, which the Business Analyst flagged during that change's own exploration as unverifiable as written ("meaningful intervals" is not a number). Until this gap closes, the no-surveillance guarantee this project exists to protect — the same guarantee that motivated the EM query changes, the pre-reveal serializer enforcement, and the Application Admin Option B boundary — has a hole in it at exactly the layer where a removed team member or an over-scoped admin would be hardest to notice: a live socket nobody is watching. The Explore stage for GitHub issue #18 (`openspec/changes/websocket-delivery-time-authorization/exploration-notes.md`) made the concrete decision the gate demanded. This proposal turns that decision into a buildable plan.

## What Changes

- Add true delivery-time (per-connection, wire-level push) authorization checks to all four content-access WebSocket events — `vote_readiness_update`, `session_state_change`, `vote_revealed`, `topic_history_update` — reusing `evaluateTeamAccess` and the existing grant types from `packages/backend/src/auth/team-content-access-helper.ts`. No parallel authorization logic.
- Introduce WebSocket infrastructure that does not exist in this codebase today: `@fastify/websocket` for the transport, and Redis pub/sub (via the existing `ioredis` dependency) as the required cross-pod fan-out mechanism, consistent with the `app` deployment's stateless/horizontally-scalable architecture.
- Reject `admin`-path grants from `evaluateTeamAccess` for `topic_history_update`. **BREAKING for any code that assumed an admin grant is sufficient to push team-scoped WebSocket content** — none exists today since Group 9 was never implemented, but this closes the surveillance path an Application Admin subscribed to a team's event stream would otherwise have, one layer above where Decision 2 already closed it for HTTP.
- Reuse `serializeForFacilitator` / `serializeForMemberParticipant` for `vote_revealed` payload construction — no independent reveal-gating logic for the WebSocket path.
- Add connection-time authentication (WebSocket upgrade validated inside Fastify's request lifecycle against `request.session`) and subscription-time early-rejection checks as additive safeguards, per the spec's three-check-point model. Neither substitutes for delivery-time checks.
- Add the acceptance test plan Group 9 has always required, expanded per Explore-stage review: per-event/per-recipient latency measurement (p95/p99 under stated load), an explicit per-pod concurrency-model decision (parallel vs. serial recipient checks) with a stated worst-case fan-out width, and — new this round — a distinct **cross-recipient delivery-skew measurement** for the same fan-out event, because the simultaneous-reveal guarantee is a felt, room-wide property that single-connection latency numbers cannot verify on their own.
- Add WebSocket-triggered audit logging for the vote-submission, reveal, and session-state-change actions (SEC-13/SEC-14). Verified during this proposal (not assumed): `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal` in `packages/backend/src/routes/facilitator-sessions.ts` does not currently write an `audit_log` row. Per the exploration notes' own instruction, this means the underlying triggering action is not already logged independently of its WebSocket delivery, so this change adds that logging as an in-scope acceptance criterion rather than deferring it. **Corrected on Propose-stage review:** the mechanism is a direct `INSERT INTO audit_log` (columns `operation`/`team_id`/`metadata`, not `action`/`resource_type`/`resource_id`), executed alongside — not via — the `emitAuditEvent` structured-log helper; see design.md Decision D7. **Extended on Design-stage review (Tomás Ferreira):** vote submission (BRD SEC-13's other named audit category, alongside reveal) was not audit-logged anywhere in the codebase and is not blocked by GitHub issue #26 — the vote lock-in handler already commits today; see design.md Decision D7's extension.
- **Document, as a verified blocking dependency this change does not implement:** the reveal-status flip, the `team_memberships.removed_at` write, and the topic-advance/action-item-finalization write that this change's `vote_revealed` and `topic_history_update` publish calls (and their audit-logging counterparts) are meant to trigger from do not exist anywhere in the codebase today — verified against `packages/backend/src`, not assumed. Only vote lock-in, lobby advance, and session completion currently commit a real state transition. See design.md's "Blocking Dependency" section for the full accounting and GitHub issue #26, filed to track the gap without scoping its fix. This change's own unit/integration tests mock or stub the affected trigger points; true end-to-end tests for the reveal and topic-advance/action-item-finalization paths cannot pass until issue #26 resolves.
- File a companion tracking issue for the SEC-25 idle-connection re-authorization heartbeat and the SEC-26 token-expiry/silent-refresh mechanism, with a named owner, before this change is considered complete. **The heartbeat/token-refresh mechanism itself is explicitly NOT designed or implemented in this change** — see Out of Scope below and Section 7/13 of the exploration notes for why delivery-time checks and a periodic idle-connection heartbeat are different mechanisms closing different windows. **Filed as GitHub issue [#27](https://github.com/surratt-dev/project-dipstick/issues/27)**, with a proposed owner (Marcus Oyelaran) and target quarter (Q4 2026) pending repository-owner confirmation (tasks.md Group 8).
- Name, but do not resolve, a Design-stage client-experience deliverable (owned by the Facilitator SME) covering what a participant/facilitator sees when delivery-time cessation or a rejected subscription occurs. This proposal and its design intentionally do not specify client-visible UX. **Per Executive review (Rachel Okonkwo), this deliverable is a hard gate, not a soft hand-off:** tasks.md names an explicit gate — the generic client-facing staleness signal must ship before any real pilot team's first live session, with the same enforcement teeth as the SEC-25/26 tracking gate already in Group 8.

## Out of Scope (explicitly deferred, per Section 13 of the exploration notes)

- **Implementing the state-transition writes this change's WebSocket event triggers depend on** — the topic reveal-status flip, the `team_memberships.removed_at` write, and the topic-advance/action-item-finalization write. Verified during Propose-stage review (not assumed) to not exist anywhere in `packages/backend/src` outside test fixtures — see design.md's "Blocking Dependency" section and GitHub issue #26. This is a **blocking dependency** for this change to be fully testable end-to-end, not scope this change absorbs: this change's own unit/integration tests can mock or stub the affected trigger points, but the true end-to-end reveal flow and the true end-to-end topic-advance/action-item-finalization flow cannot pass until the underlying writes exist. The repository owner's explicit decision is that building those writes is separate, unscoped work — this change's scope stays the WebSocket delivery-time authorization layer itself.
- **The SEC-25 idle-connection heartbeat and SEC-26 token-expiry/silent-refresh mechanism's actual design** (single combined mechanism vs. two, exact interval, named owner). This change commits only to filing the tracking issue with a named destination — not to a mechanism, an interval, or an implementation.
- **The generic client-facing staleness signal** (what a participant sees when events stop arriving, or when a subscription is rejected). This is a named Design-stage deliverable for the Facilitator SME (Priya Nair's review), not resolved in this proposal or its design.
- **Re-deriving or invoking the 60-second timer-based fallback bound.** True delivery-time checking is the chosen approach (Section 4 of the exploration notes found no evidence that either condition justifying the fallback — unacceptable latency or unacceptable complexity — holds in this codebase). The 60-second figure remains documented as a contingency reference point only, gated behind a load measurement this change does not expect to trigger, and is not re-validated or built here.
- **Cause-disclosure of revocation** (telling a removed connection why its events stopped) remains a non-goal, reaffirmed for the same no-surveillance reasoning as the archived change.

## Impact

- **New dependency:** `@fastify/websocket` added to `packages/backend/package.json`. No new message broker — reuses the existing `ioredis` dependency.
- **New backend modules:** a WebSocket route/plugin registration; a per-pod local connection registry (keyed by `sessionId` for the three session-scoped events, `teamId` for `topic_history_update`); a Redis pub/sub publisher/subscriber pair on a defined channel topology (Design-stage decision, named but not resolved in exploration).
- **Reused, not duplicated:** `evaluateTeamAccess` (`packages/backend/src/auth/team-content-access-helper.ts`), `serializeForFacilitator` / `serializeForMemberParticipant` (`packages/backend/src/content/team-content-serializers.ts`), the `audit_log` table and `emitAuditEvent` helper (`packages/backend/src/auth/audit-logger.ts`).
- **New indexed queries:** none expected beyond what Groups 1–2 already added (`sessions(facilitator_id, team_id, status)`, `team_memberships(user_id, team_id)`) — a lighter session-scoped check may be added as a narrow sibling function, not a new query pattern.
- **Test surface:** new integration tests exercising the actual Redis pub/sub hop (not just an in-process handler) for the revocation scenario, the admin-grant-rejection scenario, and the cross-recipient skew measurement; unblocks the previously-blocked E2E tasks 11.3 and 11.10 from the archived change. **Testability limit, named explicitly:** the true end-to-end versions of the reveal flow (`vote_revealed`) and the topic-advance/action-item-finalization flow (`topic_history_update`'s real-world trigger) cannot pass until GitHub issue #26's writes exist — this change's own tests for those paths run against a directly-invoked handler or a stubbed trigger, per design.md's "Blocking Dependency" section.
- **Follow-on work created, not performed here:** a companion issue/change for the SEC-25/SEC-26 connection-lifecycle mechanism; a Design-stage client-experience deliverable for staleness/rejection UX (now a hard pre-pilot gate, not a soft hand-off — see tasks.md Group 9); GitHub issue #26, tracking the missing reveal-status/membership-removal/topic-advance-and-action-item-finalization state-transition writes as a blocking dependency for full end-to-end testability of this change.
