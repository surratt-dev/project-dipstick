Where a claim in design.md's Design-Stage Review Disposition could be independently verified against code rather than taken on trust, I verified it rather than citing the disposition section as its own evidence.

Every specific claim I was asked to verify — the Origin check's actual enforcement, the admin-grant rejection, the EM-promotion fix, the serializer reuse, the single close code, the audit logging shape, the Redis subscriber isolation, the honest task 1.6 disposition, and the fail-closed property of the blocking-dependency boundary — checks out against the code as written, not merely as documented. ## 1. Origin/CSWSH validation (D9) — enforced, no bypass path found

**Files:** `packages/backend/src/realtime/origin-check.ts`, `packages/backend/src/realtime/websocket-routes.ts`, `packages/backend/src/app.ts`.

`registerOriginCheck` adds an `onRequest` hook directly on the root `app` instance (not inside a `.register()`-scoped child), and it is called as the *first* statement inside `registerWebSocketRoutes`, before `@fastify/websocket` is registered and before the two `app.get(..., { websocket: true }, ...)` route definitions. `app.ts` calls `registerWebSocketRoutes(app)` before `authMiddleware(app)`, with an explicit comment recording that ordering intent. Because both the hook and the WS route definitions are registered on the same `app` reference (no encapsulation boundary introduced by `app.register(websocketPlugin)` separates them — the hook was already attached to the parent context before that registration ran), the hook is genuinely positioned ahead of `request.session` resolution on the actual runtime request path, not merely in source order.

The hook correctly scopes itself: it inspects `request.headers.upgrade` and returns immediately (no-op) for anything that isn't a WebSocket upgrade, so it does not become an ambient Origin check for the whole application — only the WS upgrade path pays this cost. It reuses `getAllowedOrigins()` (`config.ts`) — the exact same allowlist source `@fastify/cors` is configured with in `app.ts` (`origin: getAllowedOrigins()`) — so there is no second, driftable configuration surface for this control. Rejection is a clean `403` with a generic message; it does not leak which origins are allowed.

I looked specifically for a bypass path — a route registered before the hook, a second WS route registration path that skips `registerOriginCheck`, or a code path where `@fastify/websocket`'s upgrade handling could dispatch to a route handler without running the standard `onRequest` chain. I did not find one. Both WS routes (`/ws/sessions/:sessionId`, `/ws/teams/:teamId/events`) are registered inside the same function, after the hook, on the same instance.

**Verified against test, not just code reading:** `origin-check.test.ts` and `websocket-routes.test.ts` both boot a real Fastify instance (the latter with a real `ws` client connecting over an actual loopback TCP socket, not `app.inject()`) and assert the 403 fires on a disallowed-origin upgrade attempt, that a missing `Origin` header is rejected (fails closed on absence, correct), that the check is case-insensitive on the `Upgrade` header, and that ordinary non-upgrade HTTP requests are unaffected. This is exactly the kind of test that would have caught an encapsulation-ordering bug if one existed — it exercises the real hook chain, not a mocked stand-in for it. I have reasonable confidence this control holds at runtime, not only on paper.

**Residual observation (Informational, not a finding):** the `SameSite=Strict` cookie remains the deeper control per design.md's own analysis; the Origin check is defense-in-depth, correctly labeled as such in code comments. I have no disagreement with that framing and no new information that changes it.

## 2. Admin-grant rejection for `topic_history_update`, and the EM-promotion fix

**File:** `packages/backend/src/auth/session-subscriber-access-helper.ts`, `packages/backend/src/realtime/ws-event-dispatcher.ts` (`dispatchTopicHistoryUpdate`).

**Admin rejection — correct.** `dispatchTopicHistoryUpdate` calls `evaluateTeamAccess(conn.userId, envelope.teamId)` verbatim, then explicitly checks `if (grant.path === "admin") { ...; return; }` before ever calling `sendClientMessage`. I traced `evaluateTeamAccess`'s three return paths in `team-content-access-helper.ts`: `path: "admin"` (Application Admin, returned first, before membership is even checked), `path: "member"` (any active `team_memberships` row, participant or EM), and `path: "facilitator"` (the facilitator-eligibility query). The dispatcher's `grant.path === "admin"` check is therefore logically equivalent to "deliver to `member` and `facilitator`, reject only `admin`" — matching the delta spec's requirement text exactly (`grant.path === 'member' or grant.path === 'facilitator'`, admin rejected) and the `content.ts` HTTP precedent for the same content class. No third grant path exists that could slip through un-handled. The subscription-time early-rejection in `websocket-routes.ts`'s team route (`grant === null || grant.path === "admin"`) mirrors the same rule, so a would-be admin subscriber is rejected at both subscription time and delivery time — belt and suspenders, correctly implemented at both points, with delivery time (not subscription time) doing the actual enforcement work per the spec's own three-check-point model.

**EM-promotion fix — correct, and the dual-check is real, not cosmetic.** `evaluateSessionSubscriberAccess`'s Path 1 (Active Session Participant) guard is:

```
row.participant_row_id !== null &&
row.membership_exists &&
row.membership_removed_at === null &&
row.global_role !== "engineering_manager" &&
row.membership_role !== "engineering_manager"
```

Both `global_role` (from `users`) and `membership_role` (from `team_memberships`, scoped to this session's team) are pulled in the same single query and both are checked. This matters because the codebase's own EM semantics (confirmed by the identical dual-check pattern in `sessions.ts`'s vote lock-in handler, referenced in this file's own comment) allow a user to be an EM by either signal independently — a global `engineering_manager` role, or a team-scoped membership role of `engineering_manager` while their global role is still `engineer`. Checking only one of the two fields would have left exactly the gap the spec's "Role change from participant to engineering_manager revokes live session event access" scenario exists to close. Since this is a single live database read per call with no caching (verified: no memoization, no result storage, a fresh `db.query` on every invocation), a mid-connection promotion is caught on the very next event push — this is delivery-time revocation working as designed, not just as claimed.

I also checked the facilitator path (Path 3) does not have an equivalent EM-exclusion need — it doesn't, because facilitator eligibility is a distinct global-role gate elsewhere in the system and is out of this helper's scope — and confirmed the query's `LEFT JOIN team_memberships` means a participant with no membership row at all (e.g., removed and the row hard-deleted rather than soft-deleted) correctly falls through to `membership_exists = false` and is rejected, not accidentally admitted via a null-safe comparison.

## 3. `vote-revealed-payload.ts` — genuinely reuses the HTTP serializer, no drift risk

**File:** `packages/backend/src/realtime/vote-revealed-payload.ts`, compared against `packages/backend/src/content/team-content-serializers.ts`.

`buildVoteRevealedPayload` imports and calls `serializeForFacilitator` and `serializeForMemberParticipant` directly from `team-content-serializers.ts` — the same functions the HTTP content endpoints use. It does not reimplement pre-reveal/post-reveal gating logic anywhere in this file. The only work this module does independently is: (1) two SQL queries scoped to a single live session (structurally identical in shape to the team-history queries the HTTP path already runs, just narrowed by `session_id` instead of aggregated across a team's completed sessions), and (2) adapting a `SessionSubscriberGrant` into the `TeamAccessGrant` shape the serializer functions expect as their type-level parameter. I checked whether that adaptation step smuggles in any independent decision — it does not: every field on the adapted `facilitatorGrant`/`memberGrant` object is copied verbatim from the `SessionSubscriberGrant` that produced it (`sessionId`, `teamId`, `actorGlobalRole`), with no field computed by new logic in this file. The reveal-status check (`reveal_status === 'revealed'`) that actually enforces the pre-reveal boundary lives entirely inside the imported serializer functions, untouched by this module.

This satisfies the two-independent-layers requirement (authorization check + serializer) the archived change's Decision 9 established and this design's Decision D4 extends to the WebSocket path: because both HTTP and WebSocket call the *same* serializer function object, a future regression to the serializer's reveal-gating logic breaks both paths identically and is caught by the serializer's own existing regression tests — there is no second implementation to drift out of sync.

**Note, not a finding:** this handler is one of the two events (`vote_revealed`) still blocked on GitHub issue #26 for real end-to-end firing (see Section 7 below). The code here is correct and fully unit-testable today against a stubbed/direct call; it simply has no production trigger yet, which is accurately reflected in the code's own comments and is not misrepresented as complete end-to-end functionality.

## 4. Close-code disclosure fix — verified, single code, no distinguishing signal

**Files:** `packages/backend/src/realtime/staleness-signal.ts`, `packages/backend/src/realtime/websocket-routes.ts`.

`staleness-signal.ts` exports exactly one constant, `STALE_SIGNAL_CLOSE_CODE = 4000`. `websocket-routes.ts` defines `CLOSE_UNAUTHORIZED` and `CLOSE_FORCE_EXPIRED` as two named aliases, both bound to the same `STALE_SIGNAL_CLOSE_CODE` value — this is a readability device (so call sites read intent-revealing names), not two distinct codes. I confirmed both use sites: the subscription-time rejection path (`socket.close(CLOSE_UNAUTHORIZED)`, both routes) and the scheduled 90-minute force-close (`scheduleForceClose`'s `conn.socket.close(CLOSE_FORCE_EXPIRED)`) resolve to the identical numeric value at runtime. A client inspecting the WebSocket close event's code has no way to distinguish "you were never authorized" from "your connection aged out at 90 minutes" — both surface as `4000`, and an ordinary network failure surfaces as a close with no application-level code distinguishable from this one either. This correctly implements the non-goal ("Disclosing the cause of revocation to the affected connection") and closes the exact risk named in design.md's Risks section. `websocket-routes.test.ts` exercises this path with real WS clients and asserts the observed close code, so this isn't only true by code inspection — it's asserted by a test that would fail if the two paths ever diverged.

One clarification worth naming for completeness, not a gap: the *delivery-time* revocation path (a subscriber who loses their grant mid-connection and simply stops receiving events, per the "zero-latency revocation" model) does not close the socket at all — it silently withholds the event, which is a different and correctly-designed non-disclosure behavior (the connection just goes quiet for that content stream) from the close-code question this task asked about. I did not find a case where these two mechanisms are conflated or where a delivery-time rejection incorrectly triggers a close.

## 5. Audit logging — schema-consistent, atomic with the state-transition write, and vote values excluded

**Files:** `packages/backend/src/routes/sessions.ts` (vote lock-in), `packages/backend/src/routes/facilitator-sessions.ts` (lobby-advance, session-close, reveal), `packages/backend/src/auth/audit-logger.ts`.

All three real (non-blocked) audit-log call sites — `session.vote_submitted` (`sessions.ts`), `session.state_changed` for lobby-advance and for session-complete (`facilitator-sessions.ts`, two separate call sites) — use the identical, correct schema: `INSERT INTO audit_log (actor_user_id, actor_global_role, actor_ip, operation, team_id, metadata) VALUES (...)`, matching the actual `audit_log` table shape (not the incorrect `action`/`resource_type`/`resource_id` shape design.md records as an earlier drafting error that was caught and fixed before implementation). Each is immediately followed by the corresponding `emitAuditEvent(...)` structured-log call using the same `operation` name and equivalent fields — the DB row is the authoritative record, the log emission is the correlatable operational-alert counterpart, exactly the pattern the rest of the codebase (`em-views.ts`) already establishes. `AuditEventName` in `audit-logger.ts` was extended with three new values (`session.reveal_triggered`, `session.state_changed`, `session.vote_submitted`), each carrying a comment identifying which DB write it's the counterpart to and which are blocked on issue #26 — this is accurate to what I found in the route files (see Section 7).

**Transaction atomicity — correctly implemented, not merely appended.** All three real call sites were refactored from a bare pool query to an explicit `db.connect()` → `BEGIN` → queries → `COMMIT` (or `ROLLBACK` in `catch`, `client.release()` in `finally`) pattern, matching the existing `teams.ts` precedent. I read all three in full: the state-transition write (`INSERT INTO votes ... ON CONFLICT ... DO UPDATE`, or `UPDATE sessions SET status = ...`) and the `audit_log` INSERT are both inside the same `BEGIN`/`COMMIT` block in every case, so a failure in either statement rolls back both — there is no window where the vote or state transition commits while the audit row is lost, or vice versa. This is exactly the atomicity property design.md's transaction-pattern correction called for, and it is implemented identically at all three sites rather than only at the one Marcus Oyelaran originally flagged.

**Publish-after-commit ordering — verified correct.** In both `sessions.ts` (vote lock-in) and `facilitator-sessions.ts` (lobby-advance), the `publishVoteReadinessUpdate` / `publishSessionStateChange` call is placed textually after the `try`/`catch`/`finally` block that performs `COMMIT`, not inside the transaction and not before `BEGIN`. This is the ordering Ingrid Sollenberger's tasks-stage review specifically flagged as a real bug risk (notifying a subscriber of a transition Postgres might still roll back), and I confirm the implementation places the publish call strictly after a successful commit in every call site I checked.

**SEC-16/SEC-22 vote-value exclusion — verified by reading the actual `metadata` payload, not by trusting the comment.** The vote-submission audit row's `metadata` is `JSON.stringify({ session_id: sessionId, session_topic_id: sessionTopicId })` — no `voteValue`, no `voteType`, even though both are local variables in scope at that exact point in the handler (this is the "same field being processed and excluded" case design.md flags as the easiest place to get this wrong, and I checked it precisely because of that framing). The `emitAuditEvent` structured-log call for the same action likewise carries only `actorUserId`, `actorGlobalRole`, `actorIp`, `sessionId`, `sessionTopicId` — no vote data reaches either the DB row or the log stream for this action. I did not find a second, less-scrutinized code path (e.g., an error-handling branch, a debug log statement) that logs the vote value in this handler.

**Once-per-triggering-action cardinality — correct.** Each of the three handlers writes exactly one audit row per HTTP call, not one per WebSocket recipient — the INSERT happens once, inside the same handler invocation that eventually calls the publish wrapper once; delivery fan-out happens entirely downstream in `ws-event-dispatcher.ts`, which never touches `audit_log`. This matches the spec's explicit "does not mandate one audit row per delivered WebSocket push per recipient" requirement.

## 6. `ws-pubsub.ts` — subscriber isolation confirmed, D10 hardening honestly deferred (not silently dropped)

**File:** `packages/backend/src/realtime/ws-pubsub.ts`.

`createWsSubscriber` calls `redis.duplicate()` — I confirmed this is the actual call, not a re-export or a differently-configured `new Redis(...)` that happens to look similar — and returns that duplicated connection for the caller to `.subscribe()` on. The publisher-side functions (`publishWsEvent` and its four typed wrappers) use the shared `redis` singleton directly, consistent with the design's statement that `PUBLISH` is an ordinary command that doesn't change connection mode. I checked the three other call sites design.md names as at-risk (`app.ts`'s session store, `health.ts`, `auth.ts`'s OIDC state) — none of them import or reference `ws-pubsub.ts` or the subscriber connection; they continue to use the shared `redis` client exclusively. There is no code path by which the subscriber's `.subscribe()` call could be invoked on the shared singleton instead of the duplicated connection — the subscriber connection object never escapes `ws-pubsub.ts` except as the `Redis` instance handed to `attachWsEventDispatcher`.

The reconnect-gap mitigation is implemented as specified: `reconnecting` and `ready` event handlers both call `logger.warn(...)` with a structured message naming the channel and explaining the permanent-loss property in the log line itself (a nice touch for anyone triaging a "my view went quiet" report without having read this design document). An `error` handler is also present (not explicitly required by D2, but a sensible addition — silent Redis connection errors on a subscriber would otherwise be invisible).

**D10 (Redis hardening) and task 1.6 — honestly represented as deferred, not silently dropped.** I read tasks.md's task 1.6 directly: it is the only unchecked (`- [ ]`) box I found among the tasks this review's scope covers, and its own text states plainly: "DEFERRED — not performed in this implementation session: requires confirming the actual target deployment environment's Redis configuration, which is outside this session's scope." It carries the same "Gate — before production" label as the Group 8/9 gates, with a placement note explaining why it appears early in the task list despite not being chronologically early. This is exactly the honest representation the review request asked me to confirm: the AUTH/ACL, network-isolation, `MONITOR`/slow-log, and TLS-in-transit confirmations named in Decision D10 are **deployment-environment verification steps this implementation pass could not perform** (no target deployment environment exists to inspect), and the task tracking says so in plain language rather than being checked off, deleted, or reworded into something that looks satisfied. I consider this correctly and transparently handled — it is a real gap, but it is a documented one with a named remaining owner action, not a regression from what was promised.

## 7. The Blocking Dependency (#26) boundary — fail-closed property holds; no stub masquerades as real enforcement

This was the finding I weighted most heavily, because a design can be entirely correct on paper and still fail here if an implementer — under the exact time pressure design.md's own risk register anticipates — wires a stub into a real path "to make the demo work." I checked this directly rather than trusting the code comments' own claims.

**`publishVoteRevealed` and `publishTopicHistoryUpdate`** (`ws-pubsub.ts`): I grepped every `.ts` file under `packages/backend/src` (excluding `__tests__`) for references to these two function names. The only occurrences outside `ws-pubsub.ts` itself are inside test files. Neither function is imported or called from `facilitator-sessions.ts`, `sessions.ts`, `content.ts`, or any other route file. Both carry the required `TODO(#26)` comment naming the specific handler and specific missing write, per the convention design.md establishes.

**`recordRevealTriggeredAudit`** (`facilitator-sessions.ts`): same check — this function is exported from the route file but is not called anywhere within that file's actual `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal` handler. I read the reveal handler in full (lines 484–599): it performs its authorization and session-state validation, and on success returns `reply.code(200).send({ revealed: true, sessionId, teamId, sessionStatus: sr.status })` — no `UPDATE` to any reveal-status column, no call to `publishVoteRevealed`, no call to `recordRevealTriggeredAudit`. This matches design.md's Blocking Dependency table exactly: the reveal endpoint validates preconditions only, and this implementation has not silently filled that gap with an invented commit to make the audit/publish wiring "work."

**Why this matters as a security property, not just a completeness one:** if either of these had been wired into the real handler against a stub state-transition (e.g., a developer adding a fake `UPDATE session_topics SET status = 'revealed'` without the accompanying business logic, just so the publish call had something to hang off), the system would *look* like it enforces delivery-time authorization on a real reveal event while actually gating access to a state transition nobody else in the system treats as authoritative — a classic "looks enforced, isn't" pattern. I found no evidence of this. The gap is exactly as wide as documented, in exactly the two places documented (reveal, topic-advance/action-item-finalization), and nowhere else. The vote-submission and lobby-advance/session-close paths, which design.md states are *not* blocked because they already commit real transitions today, are in fact wired into real, callable production code paths (Section 5, above) — so the boundary between "real" and "stubbed" tracks the actual commit-existence facts, not a blanket "everything in this change is stubbed" or "everything is wired" simplification in either direction.

I also confirm the recommended (not required) code-level guard named in design.md's Blocking Dependency section — a startup assertion or unit test verifying any future production `vote_revealed`/`topic_history_update` publish call site has an inline authorization check — was correctly *not* built in this pass, since design.md itself scopes that guard to issue #26's own future implementation, on the reasoning that there is nothing yet for such a guard to check. I agree with that reasoning; building a guard against call sites that don't exist yet would be speculative and untestable.
