## 1. The Decision

| Question | Answer |
|---|---|
| Delivery-time approach | **True delivery-time (per-connection, wire-level push) authorization checks.** Not a timer-based fallback. |
| WebSocket library/transport | **`@fastify/websocket`** (the official Fastify plugin, built on `ws`) |
| Does Redis pub/sub sit in the fan-out path? | **Yes — it is required, not optional.** |
| Where is the authorization check evaluated? | Inside each backend instance's local pub/sub message handler, individually per local socket, immediately before that socket's `.send()` call — never before, never cached, never batched across recipients without a per-recipient check. This includes explicitly rejecting an `admin`-path grant for team-scoped events (see Section 6 — resolved in this revision, was implicit before review). |
| Timer-based fallback bound (contingency only — not the chosen path) | **60 seconds from the `team_memberships.removed_at` (or equivalent) database commit**, and only permitted if a measurement artifact (mirroring Group 6's timing-oracle precedent) demonstrates true delivery-time is infeasible under real load. This number is a continuity reference point, not a pre-validated bound — see Section 8, revised in this round after review. |

I want to be blunt about why I am not hedging on this: the issue asks the "engineering lead" to make a call, and a call that says "we'll decide the transport later" or "somewhere between ws and Socket.IO, TBD" is not a call. It is the same failure mode as "meaningful intervals" — a phrase standing in for a decision nobody actually made. I am naming the library, naming the fan-out mechanism, and naming the contingency number, in the same document, at the same time.

## 2. Why `@fastify/websocket`, not Socket.IO

This is not a preference call — it follows from what Decision 5's "wire-level push requirement" actually demands and from what already exists in this codebase.

**What already exists (`packages/backend/package.json`):** Fastify 5, `ioredis` 5, `@fastify/cookie`, `@fastify/session`, `@fastify/cors`, `@fastify/helmet`, `@fastify/sensible`. No `ws`, no `socket.io`. Every other real-time-adjacent piece of this application is a `@fastify/*` plugin that hooks into Fastify's own request lifecycle — `@fastify/session` in particular is what resolves `request.session` (backed by the Redis-backed `SessionStore` in `packages/backend/src/auth/session-store.ts`, keys prefixed `dipstick:session:`). `@fastify/websocket` is the same family: it upgrades a Fastify route to a WebSocket and hands the handler the raw `ws` socket plus the full `request` object — including `request.session` — for connection-time authentication. Socket.IO does not plug into Fastify's request lifecycle the same way; it runs its own HTTP server binding and its own client protocol (not a plain WebSocket on the wire), which would sit awkwardly next to a codebase where every other cross-cutting concern (cookies, CORS, helmet, sessions) is expressed as a Fastify plugin.

**The wire-level push requirement is the deciding factor, not house style.** Decision 5 says: *"the delivery-time check must be evaluated at the moment of per-connection wire-level push — the instant immediately before bytes leave the server for a specific WebSocket connection."* With raw `ws` (via `@fastify/websocket`), a connection is a plain object with a `.send()` method that I call myself, once per recipient, in application code I write. The authorization check and the `.send()` call are adjacent lines in the same function — there is nowhere else for the check to "helpfully" get pulled earlier by a framework abstraction between them.

Socket.IO's whole value proposition works against this. Its idiomatic pattern is `io.to(room).emit(event, payload)` — a single call that fans out to every socket in a room via Socket.IO's Redis adapter. That adapter is specifically built to abstract away *when* each individual client is written to; the abstraction *is* the product. To do a delivery-time check per recipient with Socket.IO, I would have to bypass the emit-to-room abstraction and manually iterate connected sockets anyway — at which point I am not getting anything from Socket.IO except a heavier dependency and a non-standard wire protocol. Worse: the natural, unmodified way to use Socket.IO's Redis adapter is exactly the anti-pattern the spec names — "an implementation that evaluates authorization when events are dequeued from the channel and caches the result until wire delivery." Socket.IO's adapter dequeues from Redis and re-emits to a room; nothing in that flow invites a per-recipient authorization check at the point of write unless the developer already knows to fight the library. Given that this is the single most important property this change must get right, I do not want the chosen library's idiomatic path to be the wrong path.

`ws` gives explicit, unabstracted control over every individual write. That is exactly the property this decision needs.

## 3. Why Redis pub/sub is in the fan-out path — this is not optional

I want to be precise about why I am not treating this as a free architectural choice.

`requirements/High-Level Architecture.md` states, for the `app` Kubernetes workload: *"Stateless; horizontal scaling is possible without architectural changes"* (line 626), and gives the explicit rationale for choosing Redis over application memory for live session state: *"Application memory does not survive a process restart and does not support multi-instance deployments. Redis provides the right combination of low latency, data structure flexibility, and horizontal scalability"* (line 765).

That architectural commitment was made before any WebSocket infrastructure existed, and it has a direct consequence for this decision: **a WebSocket connection is pinned to whichever backend pod accepted it.** If a participant votes (an HTTP request, or a WebSocket message handled on pod A) and the facilitator's `vote_readiness_update` connection happens to be held open on pod B, there is no way for pod A to write to a socket object that lives in pod B's process memory — unless there is a cross-pod signaling mechanism. `ioredis` is already a dependency, already used for the session store and for the live session state model (`requirements/design/redis-session-model.md`), and `ioredis` supports pub/sub natively. Introducing a second message broker for this one purpose, when a `Deployment` with `horizontal scaling ... without architectural changes` and an existing Redis client are both already given facts, would be adding infrastructure the codebase doesn't need and contradicting the "stateless app" premise that was already decided elsewhere. Redis pub/sub is the only fan-out mechanism consistent with everything already committed to.

This is precisely the scenario Decision 5's wire-level push requirement is written for: *"If a pub/sub intermediary such as Redis pub/sub is in the delivery path, events generated before a membership removal and still buffered in the intermediary queue must be checked at the push layer, not at the dequeue layer."* This is not a hypothetical the design anticipated defensively — it is the actual shape of this system once the "stateless, horizontally scalable app" commitment is taken seriously.

**Consequence for the architecture:** each backend pod keeps a local, in-process registry of which sockets it is currently holding (keyed by `sessionId` for the three session-scoped events, and by `teamId` for `topic_history_update`). When any pod needs to emit one of the four events, it publishes a single message to a Redis channel. Every pod's subscriber receives that message and looks only at its *own local* registry — pods with no matching local connections do nothing. For each locally-held candidate connection, the authorization check runs **at that moment**, individually, immediately before that specific connection's `.send()` call. Two pods, two independent authorization evaluations for the same event, at two different physical moments (whenever each pod happens to service its local recipients) — which is exactly what "the authorization state at the moment of wire-level push is what governs, not the authorization state at the moment the event was fetched from the queue" requires.

```
                          ┌─────────────────────────────────────────┐
                          │        Postgres commit: e.g.             │
                          │  team_memberships.removed_at = NOW()     │
                          └───────────────────┬───────────────────┘
                                              │
              vote lock-in / reveal /         │ triggers event
              action item finalize /          ▼
              membership change      ┌──────────────────┐
                     ────────────────▶  Redis PUBLISH    │  (ioredis)
                                      │  channel: ws:events│
                                      └─────────┬─────────┘
                                    fan-out to every pod's SUBSCRIBE
                        ┌───────────────────────┼───────────────────────┐
                        ▼                                                ▼
              ┌───────────────────┐                              ┌───────────────────┐
              │   Pod A            │                              │   Pod B            │
              │  local registry:   │                              │  local registry:   │
              │  session S →       │                              │  session S →       │
              │   {facilitator ws} │                              │   {participant ws} │
              │                    │                              │                    │
              │  for EACH local    │                              │  for EACH local    │
              │  candidate socket: │                              │  candidate socket: │
              │   evaluateTeamAccess│                             │   evaluateTeamAccess│
              │   (or session check)│                             │   (or session check)│
              │   RIGHT NOW ───────┼──► ws.send()  if authorized  │   RIGHT NOW ───────┼──► ws.send() if authorized
              │                    │    (nothing sent if not)     │                    │    (nothing sent if not)
              └───────────────────┘                              └───────────────────┘
```

The check is never done once "for the event." It is done once **per candidate connection**, on whichever pod happens to hold that connection, at the instant that pod is about to write to it. That is the only way to satisfy "the server MUST NOT rely on the subscriber's authorization status as evaluated at connection time or subscription time" once a pub/sub hop is between the trigger and the socket.

**A note added on review (Priya Nair):** Priya reads "two pods, two independent evaluations... at two different physical moments" as a simultaneity risk, not just a correctness win — if the reveal is supposed to feel instantaneous to everyone in the room at once, "different physical moments" is exactly the phrase that should worry a facilitator SME. I agree with her that this needs to be measured and bounded rather than accepted as an unavoidable shrug. I haven't changed the architecture in this diagram — the two-pod, two-evaluation design is still correct and still required by Section 3's own argument — but I have added a distinct cross-recipient skew measurement and a concurrency-model decision to Section 9, and I discuss why in more detail there and in Section 11.

## 4. Why true delivery-time, not the timer fallback

Decision 5 offers the timer fallback as an escape valve, and Decision 6's risk mitigation frames it as acceptable "if delivery-time checking introduces unacceptable latency or implementation complexity." I looked for evidence that either condition holds in this codebase and did not find it:

- **The authorization queries are already fast and already indexed.** Tasks 1.3 and 1.4 (both `[x]` complete) added `sessions(facilitator_id, team_id, status)` and `team_memberships(user_id, team_id)` indexes specifically to support these lookups. `evaluateTeamAccess` in `packages/backend/src/auth/team-content-access-helper.ts` is a single indexed round-trip (two, in the facilitator-path miss case) already proven fast enough to run on every HTTP content request without a caching layer — Decision 6 forbids caching it, and the HTTP layer ships that way today.
- **Fan-out volume is small.** This is an internal tool. A session has one facilitator and a handful of participants (single digits, per the ritual's own design — Engineering Health Check sessions are small-team retrospectives, not broadcast events). `vote_readiness_update` and `session_state_change` fire on human-paced actions (a person locks in a vote, a person advances a topic), not a high-frequency stream. There is no plausible load profile in this application where "one indexed DB read per local recipient per event" becomes a bottleneck.
- **Complexity is comparable either way.** A timer-based re-check still needs a live subscriber registry, still needs to run the same authorization query on a schedule, and additionally needs a scheduler/interval per connection and a clock-skew-tolerant story for "when did the last check run relative to when the membership was revoked." True delivery-time needs the registry and the query and nothing else — it is not the more complex design, it is the simpler one that happens to also be more correct.

Given that neither condition Decision 6 names as the reason to reach for the timer actually holds, reaching for it anyway would be choosing a documented surveillance window (however small) over a documented zero-latency guarantee, for no performance benefit. That is the wrong trade to make on the layer that exists specifically to make SEC-25/SEC-27 testable.

**What would change my mind:** a measured result, not a guess. If the Design or Tasks stage runs the equivalent of Group 6's load test — authorization-check-plus-send latency under a realistic number of concurrent connections and events per second — and that measurement shows unacceptable added latency to the live session experience, then and only then does the contingency in Section 8 apply, and it applies by producing a documented measurement artifact, the same way Decision 7 required for the timing floor. Nobody gets to invoke the fallback by assertion.

**A scope note added on review (Marcus Delgado):** this section's argument is about *revocation* latency on connections that are actively receiving events — it is not, and was never meant to be, an argument that delivery-time checking alone satisfies every periodic-re-authorization requirement in the BRD. Marcus's review caught that I'd implicitly treated SEC-25 (periodic re-authorization) as fully answered by this section's reasoning about SEC-27 (revocation latency), and those are different requirements once a connection sits idle with no events to check against. I address that gap on its own terms in Section 7, and I reconcile it explicitly with this section's argument there so the two don't read as contradictory.

## 5. What's actually at stake — Devon's read

I signed off on the original change with a conditional: *"When the real-time layer is eventually built, Decision 5's requirements apply in full... The person who builds the WebSocket layer must read Decision 5 before writing a line of code."* This exploration is that reading, and I want to restate why I hold this line as hard as I do.

**The ritual constraint this protects is the no-surveillance guarantee, extended to the wire.** Everything the archived change built — the EM query that forces `NULL::uuid AS voter_id`, the serializer that structurally excludes vote attribution from the EM view, the two-layer pre-reveal enforcement — exists so an engineer can trust that voting honestly does not carry a cost. That trust is binary, per the BRD's own framing (Objective 4: *"Zero engineers will raise a concern... This outcome is binary"*). A WebSocket layer that gets this wrong doesn't produce a partial version of that guarantee. It produces the exact bypass path the original change's design doc named as the threat model: *"a WebSocket subscription that does not revoke when membership is removed"* (design.md Context section, and my own exploration notes from the archived change, Section 6.3).

**Why zero-latency revocation specifically, and not "fast enough":** SEC-27 says access revocation must take effect "within a defined interval" — but the spec I'm reading (`websocket-session-authorization/spec.md`) goes further and calls delivery-time evaluation "the zero-latency revocation model: no timer, no polling, no reconnect required." The reason a bounded interval is not good enough here is the same reason Decision 6 rejected a 5-minute HTTP cache TTL: *"a 5-minute window is a 5-minute surveillance gap. If a facilitator discovers a bypass and exploits it during a session, the data exposure has already occurred before the cache expires."* A removed team member who keeps receiving `vote_revealed` events with individual attribution for even sixty more seconds has, functionally, already seen data they should never have seen. There's no partial-credit version of "the removed member didn't see it." Either delivery-time evaluation stopped the next push, or it didn't, and the member either saw the vote or they didn't.

**What could go wrong if the design drifts from "wire-level push, not queue-dequeue-time":** this is the one I want the implementation team to internalize before writing code, because it is the failure mode that looks correct in a code review. The natural way to write a Redis pub/sub consumer is: subscribe to a channel once, and in the message handler, iterate local sockets and forward the payload. That code *looks* like it's checking per-event, because it runs once per incoming pub/sub message. But if the authorization check that gates each socket's `.send()` was done at subscription time — when the socket first joined the channel — rather than inside that message handler on every message, the implementation has silently regressed to subscription-time checking while appearing, structurally, to be an event-driven delivery loop. The spec names this exact shape: *"An implementation that evaluates authorization when events are dequeued from the channel and caches the result until wire delivery does not satisfy this requirement."* The tell in code review is: **is `evaluateTeamAccess` (or the session-scoped equivalent) called inside the per-message handler, once per candidate socket, every single time a message arrives — or is it called once when the socket subscribes, with the result stored on the connection object and reused?** The second shape compiles, passes a naive "does authorized-subscriber-get-the-event" test, and is wrong. I want an integration test analogous to Decision 9's `layer-removal-*` tests for exactly this: revoke membership mid-connection, publish an event on the channel the connection is already subscribed to, assert nothing is delivered. Task 9.8 already names this; I am flagging that its test must exercise the pub/sub hop, not just a single in-process handler, or it will not catch this drift.

**A second, quieter drift risk:** reusing a single grant lookup across multiple recipients in the same fan-out batch as a "performance optimization." If ten sockets are all candidates for the same `session_state_change` event, it is tempting to fetch "the" authorization state once and apply it to all ten. That's wrong on its face for this design because the four events have *different* subscriber requirements (facilitator-only, participant-or-facilitator, team-membership) — there is no single grant that answers all four — but even within one event type, each recipient is a different `userId` and needs their own row-level check. A shared/cached check here would be the pub/sub version of the ORM-cache and session-cache violations Decision 6 already named and forbade at the HTTP layer. The prohibition carries over structurally; it isn't restated per-transport in the spec, and it should be treated as inherited, not re-derived.

**A third drift risk, specific to this change because of Decision 9:** the `vote_revealed` event must not become a second, independently-maintained serializer. Task 9.3 already says to "apply the same grant-path serializer that enforces pre-reveal/post-reveal content restriction" — I want to underline *same*, not *equivalent*. `serializeForFacilitator` in `packages/backend/src/content/team-content-serializers.ts` is the function that checks `revealStatus === 'revealed'` before including vote values. If the WebSocket handler for `vote_revealed` builds its own payload construction logic instead of calling that function (even if the new logic is "obviously" correct), the two-layer enforcement Decision 9 required becomes two *different* implementations of the same layer, and the named regression tests (`layer-removal-serializer-check`, `layer-removal-auth-check`) protect only the HTTP path. This is the same pattern I flagged in my sign-off about `em-views.ts`: *"The shared authorization helper exists precisely so future content endpoints don't need their own authorization logic. Anyone adding a new content endpoint must call `evaluateTeamAccess` and must not build a parallel authorization function, regardless of how narrow the case seems."* WebSocket delivery is a new content endpoint in every sense that matters here. It inherits that rule without exception.

**This is also exactly why the gap Marcus found in Section 6 below matters as much as it does.** A "new content endpoint that must inherit the shared authorization rule without exception" is precisely what `topic_history_update` is, and "maps directly onto the existing helper" is not the same claim as "correctly excludes the grant path that helper returns for admins." I got the reuse right and the gate wrong. See Section 6.

## 6. Per-event mapping — reusing existing infrastructure, not building parallel checks

| Event | Scope | Check to reuse | Source |
|---|---|---|---|
| `vote_readiness_update` | Session | `sessions.facilitator_id = $subscriber AND sessions.status IN ('pre_session', 'active')` — same predicate as Path 3 in `evaluateTeamAccess`, narrowed to the two live statuses relevant to an in-progress vote | `team-content-access-helper.ts` Path 3 query shape |
| `session_state_change` | Session | Active participant (`session_participants` / `team_memberships`) OR active facilitator (Path 3) | Combination of Path 1/3 |
| `vote_revealed` | Session | Same participant-or-facilitator check as above, **plus** the existing `serializeForFacilitator` / `serializeForMemberParticipant` reveal-status gating — do not reimplement the reveal check | `team-content-serializers.ts` |
| `topic_history_update` | Team | Path 1 or Path 2 exactly as `evaluateTeamAccess` already implements it, **with the `admin` grant path explicitly rejected** (see addendum below — resolved on review, was left implicit before) | `team-content-access-helper.ts` Path 1/2 |

No new authorization primitive is needed for any of the four events. `topic_history_update` can call `evaluateTeamAccess` verbatim, subject to the addendum immediately below. The three session-scoped events need a lighter, session-specific check (participant/facilitator-of-this-session) that doesn't exist as a standalone function yet — Design/Tasks should specify whether that's a new narrow helper (e.g., `evaluateSessionSubscriberAccess`) that itself calls into the same Path 1/3 query logic, or an extension of `evaluateTeamAccess`'s exported internals. Either is fine; a *third* independent query implementing the same predicate a third way is not.

**Addendum — admin-grant rejection for `topic_history_update` (resolved per review, Marcus Delgado's review, Clarification 4):** Marcus's review caught something the original version of this table left dangerously implicit. `evaluateTeamAccess` returns `{ path: 'admin' }` uniformly for Application Admin callers (design.md Decision 8), and that grant path is exactly the one Decision 2 requires *session-content* endpoints to reject with 403, while *administrative-data* endpoints accept it — the helper itself has no notion of which kind of endpoint is asking; the caller has to enforce that boundary. Saying `topic_history_update` "maps directly onto the existing helper with no new query needed" was true about the query and silent about the gate. Action items — the thing this event fires for ("historical session data is updated, e.g., action items finalized") — are named in BRD Constraint 1 as session content restricted to team members, the EM, and the facilitator, not admins. If the WebSocket handler calls `evaluateTeamAccess`, gets back an `admin` grant, and treats "the helper returned a grant" as sufficient to push the event, an Application Admin who subscribes to a team's event stream receives live action-item updates with no gate stopping them — which is the exact HTTP-layer surveillance path Decision 2 closed, reopened one layer up, over a transport that pushes to the client without the admin even issuing a request.

This is not a hypothetical I'm willing to shrug off. My own stated bar for this whole project is that session data must not be surfaceable in a way that turns the Health Check into a tool for watching individuals or teams — I'd rather the feature not exist than exist with insufficient access controls. "An administrator can watch a team's action items update live because a WebSocket handler forgot the boundary the HTTP handler remembers" is precisely that failure, and it's a worse version of it than the HTTP case, because nothing about it requires the admin to take any action beyond having subscribed once.

**Resolved, not deferred:** the WebSocket handler for `topic_history_update` MUST reject an `admin`-path grant from `evaluateTeamAccess`, mirroring the HTTP session-content endpoint's rejection of admin grants under Decision 2. An Application Admin subscribed to a team's event stream MUST NOT receive `topic_history_update` pushes. This is now a normative requirement of this document (reflected in Section 1's table), not an implementation detail left to Design's discretion. I'm adopting Marcus's suggested language for this because it says exactly the right thing and I don't have a better way to phrase it.

## 7. Connection-time and subscription-time — additive, not substitutive

Per the spec, these two checks may exist but cannot replace delivery-time. My recommendation for what they should do here, so Design isn't starting from nothing:

- **Connection time:** the WebSocket upgrade handshake must run inside Fastify's request lifecycle so `request.session` (the existing `@fastify/session` cookie, Redis-backed) is available and validated before the upgrade completes. This satisfies SEC-28 ("the server must not accept a WebSocket upgrade request from an unauthenticated client") and costs nothing new — it's the same session validation every HTTP route already gets, just applied to the upgrade request. `@fastify/websocket`'s integration with Fastify routing makes this the default behavior, not an add-on.
- **Subscription time:** when a client asks to subscribe to a specific session or team channel (post-connection), run the relevant check once to reject obviously-unauthorized subscription attempts early (cheap, good UX — no reason to make a client wait for the first event to learn they can't see anything). This is a convenience and an early-rejection optimization. It is explicitly not the security boundary; Section 5's drift risk above is what happens when someone mistakes this check for sufficient. What the client actually receives on a rejected subscription attempt, and whether that's visually distinguishable to a participant from a network problem, is a client-experience question I'm routing to Section 10 rather than answering here — see that section for why, and for what I am and am not deciding about client-visible behavior in this document.

Two adjacent SEC requirements I want named so they aren't quietly dropped, even though they sit outside Group 9's four content-access events. Both got sharper on review, in different ways.

- **SEC-26 (token expiry mid-connection, 90-minute session cap, silent refresh):** This is a connection-lifecycle concern, not a content-access-event concern, and the spec explicitly scopes itself to the four content-access events. But a connection whose token silently expires and is never re-validated is a second path to the same problem this whole change is about — stale authorization state on an open socket. I'm flagging this as adjacent and out of scope for Group 9, not resolved. **Resolved further on review — tracking, not full resolution:** both Priya and Marcus independently pushed on this, from different angles (Marcus: no owner or destination named; Priya: "who is accountable... on what timeline" — see Section 11 for the convergence). A rationale for exclusion is not a disposition, and both reviewers are right that I hadn't given this one. I don't have the standing to assign an engineering owner myself — I'm an IC advisor, not someone with headcount to assign — but I do have the standing to insist this doesn't ship without a destination. See the combined tracking decision immediately below, which folds SEC-26 together with a related gap Marcus separately surfaced (SEC-25 for idle connections), because both are instances of the same underlying problem: a connection nobody has recently revalidated.

- **SEC-25 (periodic re-authorization) for idle connections — a new gap, correctly distinguished from SEC-27 (Marcus Delgado's review, Clarification 3):** BRD SEC-25 requires re-authorization "at meaningful intervals — no less frequent than once per token expiry window" — independent of whether any content event fires. Delivery-time checks, as designed in Sections 3 and 6, only run when there is an event to check against. A facilitator sitting in a quiet pre-session lobby, or a participant on a slow stretch of a session where nobody locks in a vote or advances a topic, can go an entire token-expiry window without a single `evaluateTeamAccess` call running against their connection — not because the design is wrong about SEC-27, but because SEC-25 and SEC-27 are answering different questions, and I conflated them in Section 4's original framing. I want to be direct about this: Section 4 argues that true delivery-time checking is superior to a timer for revocation latency on the active-event path, and that argument still holds — it says nothing about connections that never receive an event to check. That's a real, distinct gap, not a restatement of the SEC-26 gap I'd already flagged, and Marcus is right to insist I not fold it into SEC-26 by treating "connection lifecycle stuff" as one undifferentiated bucket.

  **Decision:** this needs an explicit periodic per-connection re-authorization heartbeat, running independent of event traffic, at an interval no less frequent than the token-expiry window SEC-25 names — in addition to, not instead of, delivery-time checks. This does not contradict Section 4's rejection of the timer *fallback*: Section 4 rejected using a timer as a *substitute* for delivery-time revocation on the active event path, because a timer reintroduces a surveillance window on data actively flowing to a connection. A periodic heartbeat for a connection that is otherwise idle has no such window to reintroduce — there is no content flowing for an idle connection to leak in the interval between heartbeats, because nothing is being delivered at all. The two mechanisms answer different threats: delivery-time checks close the SEC-27 window on the connections that matter most (the ones receiving live content); the heartbeat closes the SEC-25 window on the connections delivery-time checks structurally cannot reach (the ones receiving nothing). I'd be repeating Section 4's exact mistake — asserting a design property instead of examining where it stops applying — if I let "delivery-time is strictly superior to a timer" stand as a blanket claim after it's been shown not to cover this case.

  **Scope decision — this is where I'm doing more than "track and defer":** because this heartbeat mechanism and the SEC-26 token-refresh mechanism are both, at bottom, "periodically revalidate an open connection that delivery-time checks alone don't reach," I think Design should evaluate them as one combined connection-lifecycle mechanism rather than two separately-owned gaps — a single periodic task per connection that re-validates session/token state (closing SEC-26) and re-runs the relevant authorization check (closing SEC-25 for idle connections) in the same pass. I'm not mandating that specific outcome — that's a Design-stage call, and it's possible the token-refresh mechanics and the authorization re-check want different intervals or different owners once someone looks closely — but I am mandating that both gaps get a single named tracking destination and are not shipped as two footnotes in two different documents that nobody reads together again. **Tracked as:** a companion issue to be filed against this change (or its Design artifact) before Group 9 is marked complete, covering both SEC-25-for-idle-connections and SEC-26, with an owner named at Design/Propose time. I don't have the standing to assign that owner from this seat, but I do have the standing to insist it isn't shipped without one.

- **SEC-13/SEC-14 (audit logging fidelity for WebSocket events):** SEC-14 requires "vote submissions, reveals, and session state changes over WebSocket" to be logged with the same fidelity as HTTP. Two of our four events (`vote_revealed`, `session_state_change`) are literally named there. Neither the spec (`websocket-session-authorization/spec.md`) nor tasks.md Group 9 mention audit logging at all. **Resolved direction on review (Marcus Delgado, Clarification 6 and Suggested Rewrites):** the original version of this bullet said Propose "should either close or explicitly defer" this gap — which is exactly the unmade call Section 0 says this document refuses to hand forward. Marcus is right that I didn't hold this bullet to my own document's stated standard, and I'm adopting his framing rather than inventing my own, because it asks the one question that actually determines scope and my draft didn't: **does "same fidelity as HTTP" mean one audit-log row per triggering action, or one row per delivered WebSocket push per recipient?** Before Propose: confirm whether the underlying triggering action (e.g., the reveal action itself, which already happens via an HTTP/action-authorization path) is already audit-logged independent of its WebSocket delivery. If so, this change's scope is limited to adding the WebSocket session identifier (per SEC-13's added clause) to that existing entry — not creating new per-recipient log rows. If the triggering action is not already logged independently of its WebSocket delivery, this change must add that logging as an in-scope acceptance criterion, not a follow-up. I'm naming a recommended default rather than leaving Propose an open fork: my expectation, based on how the rest of this system is built (actions are HTTP-authorized and then fanned out over WebSocket, not initiated over WebSocket), is that the triggering action is already logged and the fix is additive (session identifier only) — but that's an expectation, not a verified fact. I haven't gone and read the actual audit-log call sites in `packages/backend` to confirm it, and asserting an unverified guess as settled would be exactly the failure mode I'm calling out elsewhere in this document. Propose should verify before treating this as closed.

## 8. The contingency — stated in full, and gated

I am not choosing the timer fallback. I am naming its terms anyway, because Decision 5 requires a specific number if it is ever invoked, and I don't want a future implementer under deadline pressure to reach for "meaningful intervals" as a shortcut.

**If, and only if,** a load measurement (structured the same way as Group 6's timing-oracle measurement: representative concurrent connection count, representative event rate, measured under realistic database load) shows that per-connection delivery-time checks introduce latency that degrades the live session experience, the fallback is:

> **Maximum 60 seconds from the `team_memberships.removed_at` (or session-status-change) database commit to cessation of event delivery to the affected connection.**

**Revised framing per review (Marcus Delgado's review, Section 5 scrutiny):** I need to walk back one sentence in the original version of this section. It said: *"Sixty seconds is not an arbitrary 'reasonable-sounding' number — it's the figure I already proposed for this exact gap,"* as though continuity with a prior document were the same thing as the number being correct. Marcus caught the conflation cleanly, and I don't have a defense. The number's actual provenance is that design.md offered it as an illustrative example ("e.g., 'no more than 60 seconds'"), and the only thing carrying it forward accomplishes is that the team has seen it before and won't be confused by a new number appearing from nowhere. That's a real reason to prefer it over inventing an unrelated number out of thin air if a fallback number is ever needed — but it is not evidence the number is right, and I shouldn't have implied otherwise.

Worse, Marcus points out that Section 4's own argument undercuts the number outright: I wrote there that a removed member who keeps receiving `vote_revealed` events "for even sixty more seconds has, functionally, already seen data they should never have seen" — which is an argument that sixty seconds is an *unacceptable* exposure window, sitting a few paragraphs above a proposal to accept sixty seconds as the exposure window if the fallback is ever used. I did not reconcile that when I wrote it, and I should have caught it myself before a reviewer had to.

**What I'm accepting and what I'm deferring, and why:** Marcus's suggested rewrite — requiring a named scheduling mechanism, a p99 measurement against that mechanism's actual worst case under load, and treating 60 seconds as a starting reference point rather than a pre-validated bound — is the right standard for the moment the fallback is actually invoked. What I am *not* going to do right now is spend more effort deriving that mechanism, running that measurement, or picking a percentile for a path that Section 4's entire argument says should never be taken. Section 4 is unambiguous that delivery-time is the chosen approach and the fallback is a contingency gated behind a load measurement I don't expect to ever come back positive. Spending Design-stage rigor now on the exact worst-case percentile of a mechanism nobody has named, for a fallback I've argued shouldn't be needed, is exactly the kind of effort spent on the wrong thing that I'd push back on if someone brought it to me as a request on any other part of this system.

**Decision:** the correction to the overclaiming language ("not arbitrary") is made now, in this document, because it costs nothing and the original claim was simply wrong. The full re-derivation Marcus asks for — naming the mechanism, measuring its p99, confirming 60 seconds against that measurement, choosing a percentile discipline for the bound itself — is explicitly deferred to the point, if it ever arrives, where the Section 4 load measurement actually triggers use of the fallback. If that day comes, whoever implements it must treat 60 seconds as a reference point to re-validate, not a number to inherit unexamined. I am not pre-approving it here; I am naming it as the number to test against, which is a materially weaker and more honest claim than what the original draft made.

I'd still go further than Decision 6's phrasing on one point, if the fallback is ever built: a startup guard analogous to `timing-oracle.ts`'s production guard, gating production deployment on a recorded measurement value the same way `TIMING_FLOOR_MS === 150` throws in production today. That pattern worked once; I'd reuse it rather than trust a code comment. But that guard is itself part of the deferred re-derivation work above, not something to build against an unvalidated number now.

1. Measure per-event, per-candidate-connection authorization-check-plus-send latency under a realistic concurrent session/connection count.

## 10. Client-Experience and Silent Revocation — A Scope Decision (Priya Nair's Review)

Priya's core finding is that this document resolves the transport, the fan-out mechanism, and the security guarantee in careful detail, and says nothing about what a participant or facilitator actually sees when a delivery-time check starts failing mid-session. She's right that the absence is real, and right that it matters more here than it would in an ordinary backend document, because the entire justification for this change is protecting the *felt experience* of the ritual — the no-surveillance guarantee, the simultaneous reveal — and "the event silently stops arriving" is a description of server behavior that says nothing about what happens to that felt experience on the other end of the wire.

**Where I agree without reservation:** the silence itself — no error frame, no close code tied to the reason, nothing that tells a revoked connection *why* its events stopped — is correct and should stay exactly as specified. This isn't a gap I'm going to soften. Revealing "you have been removed from this team's session" to the removed connection in real time is arguably worse than saying nothing: it announces a membership change mid-session, in a room whose whole design depends on people trusting that leaving the room (or being asked to) doesn't come with public commentary or a real-time notification of the reason. A generic client-side signal that something is stale is a UX question (see below); a signal that specifically discloses *why* is a different thing, and I'd resist that even if it were requested directly, because it reopens exactly the kind of "the app tells everyone what happened to you" surveillance-adjacent behavior the no-surveillance guarantee exists to prevent. I don't think Priya is asking for cause-disclosure specifically, but I want the line drawn explicitly here since the two are easy to conflate once someone starts designing an indicator, and this is precisely the kind of place where a protective constraint quietly erodes if nobody names the boundary.

**Where I agree there's a real gap, but disagree it's this document's gap to close:** what a participant's client renders when updates stop — silence with no visual change, a generic "connection issue" indicator, a "last updated" timestamp on the facilitator's readiness grid, whether a rejected subscription attempt looks different from a network hiccup — all of that is client/UX design, not authorization design. This document (per Section 0) exists to close one specific gate: the transport, fan-out, and delivery-time mechanism for Group 9. It does not exist to design the client. I don't think expanding this document's scope to cover client rendering states is the right fix, for the same reason I wouldn't want a security exploration to start prescribing button copy — it's not the lens this document is written from, and stretching it risks doing that job worse than a document actually written from the participant-experience lens would do it.

**Decision: named as an explicit follow-on for Design, not a silently-inherited non-goal.** Priya is specifically right that design.md's original non-goal ("notification of membership revocation — out of scope") was written for a different context — an async, HTTP-served report page — and has been carried into this live-session context without anyone re-examining whether it still holds. It shouldn't be carried forward silently again. My answer, explicitly: the *non-goal on notifying the cause of revocation* is re-affirmed, for the reason given two paragraphs up. The *absence of any client-visible signal distinguishing "stale due to an authorization change" from "stale due to network flakiness"* is **not** re-affirmed as a non-goal — it's an open UX question that this document is not equipped to close and should not pretend to close by silence.

I'm asking that a client-experience section be added at the Design stage — before Tasks locks in, per Priya's Suggested Addition 1 — covering at minimum: what a participant sees on delivery-time cessation, what a participant sees on a rejected subscription attempt (Section 7's subscription-time check), whether the two are visually distinguishable from ordinary network flakiness, and what (if anything) the facilitator's readiness grid shows to distinguish "stale" from "accurate." Priya should be the reviewer for that section — this is her lens, not mine — and I'd ask that whoever runs Design treat her review of it with the same weight this document asks Design to treat mine on the security side.

Priya's observation that a silently frozen client might lead a participant to say "is this broken?" out loud mid-session — itself a small disruption to a room designed to feel psychologically safe — is a good illustration of why this follow-on matters. It doesn't need separate tracking; it's the same gap, described from the room instead of from the wire.

I'm being explicit that this is a real decision — out of *this* document's scope, into Design's, with a named owner-by-role — rather than a shrug, because a shrug is exactly what Priya's review is calling out, and I don't want to repeat the mistake one layer down.

## 11. Where the Two Reviews Agree, and the One Place They Pull in Different Directions

I looked for an actual disagreement between Priya's review and Marcus's review — not just two reviewers raising different topics, but two reviewers wanting incompatible things — because I was asked to flag one if it exists rather than pick a side quietly. Here's what I found.

**Convergence, not conflict, in most places.** Priya and Marcus independently arrived at the same two findings from completely different lenses:

- **Concurrency model for per-recipient checks.** Marcus flags it as an acceptance-testability gap — Section 9's latency number "means something different depending on which model is chosen" (his Clarification 5). Priya flags the identical gap as a simultaneity risk (her Observation 7 and Question 4). Neither is wrong, and neither needs to be preferred over the other — they're describing the same unresolved design decision from two different consequences of leaving it unresolved. - **SEC-26 tracking.** Marcus wants a named owner and destination (his Clarification 7). Priya independently asks "who is accountable for tracking SEC-26... on what timeline" (her Question 8, Suggested Addition 5). Same ask, same answer (Section 7's combined tracking decision).

This convergence is itself informative: when two reviewers reading from unrelated lenses land on the same gap independently, that's a stronger signal than either alone would be, and I gave both of those decisions more weight in this revision than I might have from a single reviewer's ask.

**The one place I'd call a genuine tension, not a factual disagreement:** Priya's ask is for this document (or, generously read, "before Tasks locks in") to grow a client-experience section examining participant- and facilitator-visible behavior. Marcus's review explicitly scopes what he thinks still needs answering to four concrete sub-decisions — message schema, registry lifecycle, admin-grant handling, concurrency model — all backend/security mechanics, and never mentions client UX at all. That's not because he disagrees with Priya's concern; it's because it sits entirely outside the lens he's reviewing from ("is each idea specific enough to become a requirement... without a round trip to ask what did you mean"). So this isn't Priya-says-X, Marcus-says-not-X. It's that Priya's concern and Marcus's concerns live at different altitudes of the same document, and a reader who only skimmed Marcus's review could come away thinking his silence on UX means it doesn't matter, when it just means it wasn't the question he was asked to answer.

I resolved this by *not* picking between them: both sets of concerns are legitimate, and I've addressed both, but I've routed them to different destinations rather than treating "client experience" as a fifth item on Marcus's list of backend sub-decisions, or shrinking Marcus's four sub-decisions to make room for UX in the same section. Marcus's four sub-decisions stay Design's remaining backend work (Section 9's item 5, plus the two items named directly below). Priya's client-experience concern becomes a named Design-stage deliverable with Priya as reviewer (Section 10). Neither reviewer's concern got diluted to make room for the other, and neither got to override this document's own stated scope (Section 0) by being folded into it — each got its own explicit, named landing spot instead.

**Two remaining Design-stage sub-decisions from Marcus's review that I'm accepting without much discussion, because there isn't a disagreement to weigh here, just work to name:**

- **Message envelope / channel topology (Clarification 1):** whether `ws:events` is a single channel carrying all four event types for every team and session, or split per-team/per-session, and the field list every published message carries (event type, `sessionId` vs. `teamId`, payload). Two implementers building against this document as written could produce incompatible registries without this named.
- **Local registry register/deregister lifecycle (Clarification 2):** what adds a socket to a pod's local registry (connection? subscription?) and what removes it (disconnect, explicit unsubscribe, both) — without deregistration, a delivery-time check could pass for a socket that has already closed, and `.send()` would throw.

Both are real gaps in what Design needs to build this without re-deriving decisions this document didn't make, and both are appropriately Design-stage detail rather than Explore-stage decisions — naming them here, rather than letting Design discover them independently, is the right level of resolution for a document at this stage.

## 12. Summary for whoever picks this up next

- **Transport:** `@fastify/websocket` (`ws` under the hood). Not Socket.IO — its idiomatic room/adapter abstraction fights the per-connection, per-event check this design requires.
- **Fan-out:** Redis pub/sub via the existing `ioredis` dependency. Required, not optional, because the `app` deployment is explicitly stateless and horizontally scalable (`requirements/High-Level Architecture.md` line 626/765) — a socket lives on one pod, and events can originate on any pod.
- **Delivery-time model:** true per-connection, wire-level checks, evaluated inside each pod's local pub/sub message handler, immediately before each socket's `.send()`, reusing `evaluateTeamAccess` (or a narrow session-scoped sibling built the same way) — never cached, never batched across recipients, never done at subscribe time only, and never accepting an `admin`-path grant for `topic_history_update` (resolved this round — was implicit, now explicit and normative).
- **Fallback bound (contingency, not chosen):** 60 seconds from DB commit, invoked only behind a documented load measurement, gated the way the timing floor was gated. As of this revision, that number is explicitly a continuity reference point pending re-validation if the fallback is ever invoked — not a pre-approved bound.
- **SEC-25/SEC-26:** a periodic per-connection re-authorization heartbeat, independent of event delivery, is required to close SEC-25's idle-connection gap, tracked to one combined destination together with SEC-26's token-expiry gap. Neither is resolved in mechanism here; both are resolved as named, tracked requirements rather than footnotes.
- **SEC-14:** disambiguated into one concrete question (per-action vs. per-delivery audit logging) with a recommended default, to be confirmed against actual audit-log call sites before Propose treats it as closed.
- **Cross-recipient skew and per-pod concurrency model:** both added to the Section 9 acceptance test plan this round, because single-connection latency doesn't verify the simultaneous-reveal guarantee, and the concurrency model is a direct input to that skew.
- **Client-experience follow-on:** named explicitly for Design, owned by Priya's review — not resolved here, and not silently dropped either.
- **What must not happen:** a parallel authorization function for WebSocket events; a reveal-gating reimplementation instead of reusing `serializeForFacilitator`/`serializeForMemberParticipant`; an authorization check performed once at pub/sub subscription and silently treated as delivery-time; an `admin` grant silently passing through to a team-scoped push.

The gate above Group 9 is closed. Group 9's tasks (9.1–9.10) and the blocked E2E tests (11.3, 11.10) can proceed against this decision. I'd ask that whoever writes the Design artifact for this change link back to Section 5 of this document specifically — that section is the part most likely to be skimmed and most likely to be where a well-intentioned implementation quietly fails the requirement — and to Section 10 for the client-experience follow-on, so it doesn't get rediscovered as a surprise the way the archived design's non-goal almost did here.
