## Why

`GET /api/v1/teams/:teamId/topics` (TOPIC-001) returns `200` to a team's engineering managers. The contract's TOPIC-001 prose, its Authorization Matrix, the `team-content-access` content matrix (EM column "None"), the use case "View Active Topic Configuration" (Out of Scope), and BRD FR-9.5 / Constraint 2 all say EMs get no topic configuration. The code is the outlier. This is a defect fix, not a new policy, so it needs no VP sign-off (GitHub #187).

Nothing leaks today, because TOPIC-001 does not return the team's own free text. But the next item on its roadmap is `teamAnnotation` ("Our team's definition", FR-8.7), and the `topic-annotation` spec already says that change must "first deny engineering managers." The no-manager rule is not just about voting. Engineers have to know that the place where they describe their team's health in their own words belongs to them. If a manager can read it, people will write it for the manager. TOPIC-001 has no production consumer today, so this is the cheapest moment we will ever get to close the gap.

**No user-visible change.** No frontend code calls TOPIC-001. The Topic Management screen reads TOPIC-002, and the live session reads the `session_topics` snapshot. No facilitator, participant, or EM workflow changes when this ships. EM-facing views get topic names through TREND-001 and SESSION-007/008, as intended.

## What Changes

- **TOPIC-001 becomes an explicit allow-list.** It returns `200` only to (a) an active `participant` member of the team (judged by membership role, not by grant role, so the path 2' degraded grant does not qualify), or (b) an eligible session facilitator (as `evaluateTeamAccess` / `team-content-access` define it), and in both cases only when the actor is not an engineering manager. Every other grant, including any grant variant added later, gets `403`.
- **"Engineering manager" uses OR semantics for this rule.** A caller is an EM when their active membership role on the team is `engineering_manager` **or** their `users.global_role` is `engineering_manager`. This covers all three EM states: EM by both signals (grant path 2), an EM membership with a non-EM global role (path 2', which the helper currently degrades to `participant`), and a global EM with a `participant` membership (demoted through TEAM-005 or joined by link). This matches the vote lock-in in `sessions.ts`.
- **Facilitator grants are not denied because of team membership.** A **facilitator grant** (path 3) whose live `actorGlobalRole` is `facilitator` is never denied by this rule. The helper issues a facilitator grant only when the caller has no active membership on the team. A user whose global role is `facilitator` but who holds an `engineering_manager` membership on the team gets the member grant, not the facilitator grant, and the membership signal denies them. IdP drift can produce this state, and FR-1.4 calls this user the team's manager. A facilitator grant whose live `actorGlobalRole` has drifted to `engineering_manager` fails closed. The app cannot create that state, because session creation requires `global_role = facilitator`.
- **The rule is unconditional.** There is no feature flag, configuration setting, or administrative override, matching TEAM-005's wording. To make that checkable, the admission decision is a pure function of the access grant (which carries the stored global role) and the caller's active membership role. It reads no environment variable, config object, feature-flag service, or database setting. The security reviewer confirms this by inspection (tasks.md 6.4).
- **The denial reveals nothing.** The response is the standard `denyAccess` 403 envelope with `Cache-Control: no-store` and the same timing floor. Neither the topics query nor the lock check runs. A denied caller never receives `isCustomizationLocked`. Each denial emits one log-only `topic.config_read_denied_role` event (no topic data), so a manager probing the team's topic space is visible after the fact (design.md Decision 6).
- **Application Admin denial is confirmed on purpose.** TOPIC-001 keeps its `403` and the `admin.session_content_denied` audit row. Topic configuration remains available to admins through TOPIC-002, whose own admin-read auditing is a pre-existing gap this change records but does not fix (Follow-ups, item 7). The denial began as a side effect of task 5.10's blanket rule. We now keep it deliberately and fix the docs that say "Yes".
- **REST API Contract reconciled.** TOPIC-001 gets a "Corrected (#187)" authorization note, an "EM flows do not call TOPIC-001" scope line, reworded 403/404 rows (exact text in tasks.md 5.3), a TOPIC-001 entry in the "Path id shape" note, and corrected Authorization Matrix cells (EM: "No (403, #187; membership or global role)"; Admin: "No (403 + audit; reads via TOPIC-002)").
- **The camelCase remap is deferred, with a contract note.** An "As built (#187)" note records that topic rows are raw snake_case DB rows today, that the camelCase shape is the target, and that the first change adding a TOPIC-001 consumer SHALL do the remap.
- **Stale rationale removed.** Every place that says TOPIC-001 "admits engineering managers" (contract comment, `topic-annotation` spec, `content.ts` SQL comment, `shared/src/types/topic.ts`, the S1 integration-test comment) is updated. This is verified by `grep -rn "admits engineering" requirements packages/*/src` returning no hits (the pattern also matches `content.ts`'s "currently admits engineering managers").
- **Tests:** the two EM-gets-200 tests flip to `403`, and the S1 no-leak body assertion is **kept**. New tests cover path 2', a global EM with a participant membership, a global facilitator with an EM membership, a facilitator drifted to EM, an admin who also holds an EM membership (the admin path wins and writes exactly one audit row), the 404-before-gate ordering for a non-canonical `teamId`, and the template team's EM. Regression tests pin `200` for participants, for facilitators, and for a global facilitator with a `participant` membership.

**Considered, not chosen:** retiring TOPIC-001 entirely. For: it has no consumer and is one more surface the no-manager rule has to defend. Against: it is the only topic-configuration read a participant has, and so the natural endpoint for first-session onboarding. The use case says engineers see topics only in the room. That gap is for the BA to resolve with facilitator stakeholders (Follow-ups, item 1).

**Out of scope:** adding `teamAnnotation` to TOPIC-001; the camelCase remap; admitting admins; retiring TOPIC-001; renaming audit operations; changing the admin denial message; changing Decision E's degrade-to-participant on any other endpoint; realigning the contract's facilitator-window prose.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `team-content-access`: adds the requirement "The active-topics endpoint admits only non-manager participant members and eligible session facilitators" (OR-semantics EM definition, allow-list, no override, non-revealing denial, admin denial confirmed). Modifies "Application Admin access is limited to administrative data" to say admins' topic-configuration read is served by TOPIC-002, and TOPIC-001 denies them with an audit row.
- `topic-annotation`: modifies "The active-topics endpoint does not return the team annotation". The "admits engineering managers" rationale is replaced: EMs are now denied (#187), and the annotation still stays off TOPIC-001 until a consumer exists. That first consumer change also owns the camelCase remap.
- `topic-customization-lock`: modifies "The active-topics response exposes the team's customization lock state". The flag is present on every `200` for every caller the endpoint admits, and a denied caller receives no lock state.

3. **Realign the contract's "facilitator with an active session" prose** with the grant's real window: active statuses, a draft under 24 hours old, and the post-session grace window. (BA N6.)
4. **TOPIC-001-specific admin denial message.** The "session content" wording is wrong for topic configuration. Changing it needs a message parameter on the shared `denyAdminContentAccess`. Keep the audit operation name. (BA N6.)
5. **`teamAnnotation` release-note messaging.** When `teamAnnotation` ships to any participant-facing read, its release notes must say plainly that engineering managers cannot read the team's definitions, and cite #187 / this change. Team champions are the ones who will repeat that to skeptical engineers. It is also recorded as a contract note on the TOPIC-001 `teamAnnotation` comment (tasks.md 5.2). (Exec Condition 3.)
6. **A1 deferred (Decision 1 = B).** Owner: Solution Architect. Move `membershipRole` onto `TeamAccessGrant` (Option A1) once a second consumer needs to detect path 2', and decide then how constructors without a membership read (the synthetic grant in `realtime/vote-revealed-payload.ts`) should represent it. Until then `readActiveMembershipRole` stays. (Exec Condition 1; engineer design review.)
7. **TOPIC-002 admin access controls.** Owners: Security (Tomás Ferreira) and Solution Architect. (a) TOPIC-002 admits `application_admin`, returns `team_annotation`, and writes no admin read-audit row or event, which the `team-content-access` "Application Admin access is limited to administrative data" requirement calls for. (b) `checkStandingFacilitatorOrAdminAuthorization` admits an admin before looking at membership, so an admin who also holds an active `engineering_manager` membership on the team can read that team's annotations through TOPIC-002 while TOPIC-001 denies them. Decide whether the OR rule applies there now that TOPIC-002 serves annotations. Pre-existing; not created or widened by this change. Should be resolved before `teamAnnotation` reaches any wider audience. (Security design review B2.)
8. **How `global_role = 'facilitator'` persists across sign-in.** Owner: Solution Architect, with Security. `PERMITTED_GLOBAL_ROLES` in `account-resolver.ts` does not include `facilitator`, and the sign-in upsert sets `global_role = EXCLUDED.global_role` unconditionally, so as the code reads a facilitator who signs in is reset to the IdP-mapped value. Confirm whether that is intended; if not, it is a separate defect. This change's facilitator arm does not depend on the answer. (Security design review N1.)
9. **App-wide error handler for 500s.** Owners: Security (Tomás Ferreira) and Solution Architect. The backend has no `setErrorHandler`, so Fastify's default handler echoes `error.message` (for example a pg driver message) to the client, without `Cache-Control: no-store` or the timing floor. Add an app-level handler that returns a generic envelope with a `correlationId` and `no-store`, and logs the detail server-side. Pre-existing and app-wide; this change's new membership read fails the same way the helper's query already does. (Implementation security review N1.)
