## Context

`DraftSessionHost` (`packages/frontend/src/pages/DraftSessionHost.tsx`) is the real, refresh-safe route (`/team/:teamId/session/:sessionId`) a Facilitator lands on after creating a session and stays on through `draft` → `lobby` → later states. It already fetches `GET .../facilitator-state` on mount, which returns `joinToken` unconditionally regardless of session status (`FacilitatorSessionStateResponse`, `packages/shared/src/types/team-content-access.ts:227`). Today:
- `data.currentSessionState === "draft"` renders `draft-control-view`, which shows the join link as muted text (`data-testid="draft-join-link"`, `DraftSessionHost.tsx:183`) next to a badge (`data-testid="draft-join-link-badge"`, `DraftSessionHost.tsx:185-187`) reading "This link works already — anyone who opens it before you open the room won't see a waiting screen yet." — no copy button.
- Any other status renders `live-readiness-view`, which shows only `"The room is open. Session status: {status}."` — no join link at all.

**Token/URL reality, resolved.** This design was originally written against `sessions.join_token`, a value a security review (`design-review-security.md`, Finding 1) found corresponded to no working route. That's since been fixed and merged to `main` by `join-link-redemption-wiring` (#166, archived at `openspec/changes/archive/2026-09-24-join-link-redemption-wiring/`): `data.joinToken` is now sourced from a real, always-redeemable `join_links` row via get-or-create (that change's design.md Decision 1), `sessions.join_token` has been removed entirely, and the JSDoc on `FacilitatorSessionStateResponse.joinToken` (`packages/shared/src/types/team-content-access.ts:218-227`) documents this directly. The URL itself is built via `buildJoinLinkPath(token)` (`packages/shared/src/types/auth.ts:63-65`), a shared helper that returns `/api/join/${token}` — not a manually-constructed `${origin}/join/${token}` template literal, which was the other half of the original bug (a path the backend never registered). `DraftSessionHost.tsx:184` already calls it: `` `${window.location.origin}${buildJoinLinkPath(data.joinToken)}` ``. Finding 1 is resolved; nothing in this design should treat the token as unverified or the link as non-functional going forward.

Exploration for this change (`exploration-notes.md`) traced the real navigation graph and confirmed that `SessionLobbyPage`, the only other component in the codebase with a built `lobby`-status join-link-adjacent view, is unreachable by any current navigation path during the `lobby` window — nothing routes to `/session/:sessionId` until a session reaches `active` status (per `join-link`'s "Session-aware join link landing" requirement). `live-readiness-view` is therefore the only real surface to build on; this design targets it exclusively.

No clipboard-handling code exists anywhere in the frontend today (`grep -rl clipboard packages/frontend/src` returns nothing). This change establishes that pattern for the first time, so its shape is likely to be reused (e.g., the deferred join-link revocation UI named in `join-link`'s spec will likely want the same copy affordance).

## Goals / Non-Goals

**Goals:**
- Render the join link with a working copy-to-clipboard control in `live-readiness-view` (currently entirely absent there).
- Extend the same copy control to `draft-control-view` so a Facilitator can stage a share message before opening the room.
- Establish a clipboard-copy pattern (success confirmation, unavailable/rejected fallback, no false positives) reusable by future features.
- Fix the visual weight of the joinable-state link so it reads as the primary actionable element, not an inherited footnote style.

**Non-Goals:**
- Modifying `SessionLobbyPage` or fixing its routing gap — tracked separately as [GitHub issue #164](https://github.com/surratt-dev/project-dipstick/issues/164).
- Any change to join-link token generation, validation, or the session-aware-landing redirect rule (`join-link` capability) — this change is purely additive display/copy UI on the Facilitator-facing surface.
- QR codes, in-app link sharing/notifications, or any other alternate distribution mechanism (already excluded by the source use case's Out of Scope section).
- A general-purpose toast/notification system — the confirmation reuses the existing inline auto-clearing banner convention.

## Decisions

### D1: Build a shared `useCopyToClipboard` hook, not a component-local `onClick` handler

Both `draft-control-view` and `live-readiness-view` need identical copy behavior (feature-detect → write → success/failure branching → confirmation state), so the logic lives in one hook (`packages/frontend/src/hooks/useCopyToClipboard.ts`) rather than being duplicated per view. It returns `{ copy(text): Promise<void>, status: "idle" | "copied" | "unavailable" }`. Both `DraftSessionHost` branches call the same hook. This is the first clipboard-handling code in the app; keeping it in one place is what makes it reusable for the deferred link-revocation UI later, per the exploration notes' framing.

The join URL itself (`` `${window.location.origin}${buildJoinLinkPath(data.joinToken)}` ``) is computed exactly once, near where `teamLabel` is already computed above both branches (`DraftSessionHost.tsx:145`), and the same string is passed into whichever branch renders (per design-review-engineer.md Finding 5) — not rebuilt separately inside each branch's JSX.

**Alternative considered:** inline the logic directly in `DraftSessionHost` since it's currently the only consumer. Rejected — the two branches (`draft-control-view`, `live-readiness-view`) already need the identical behavior today, not hypothetically later, so the duplication cost is immediate, not speculative.

**Testids for the new elements** (verified non-colliding with the existing `draft-join-link` and `draft-join-link-badge`): `draft-join-link-copy-button` and `draft-join-link-copied-banner` in `draft-control-view`; `live-join-link`, `live-join-link-copy-button`, and `live-join-link-copied-banner` in `live-readiness-view`. `tasks.md` §2–3 use these names; design and tasks are kept in agreement here per design-review-engineer.md Finding 3.

### D2: Feature-detect via `typeof navigator.clipboard?.writeText === "function"`, never `document.execCommand('copy')`

`execCommand('copy')` can report success without the application being able to verify the copy actually happened, which would violate the "no confirmation on fallback" requirement. The hook feature-detects `navigator.clipboard.writeText` at call time; if absent, it never attempts a copy and never shows a success confirmation. If present but the call rejects (permission denied, insecure context, etc.), the hook treats that identically to "unavailable" — same fallback state, same suppressed confirmation. This is one status value (`"unavailable"`), not two, by design: the UI must not be able to accidentally special-case a rejection into a false-positive path.

**Alternative considered:** a three-state model (`idle`/`copied`/`api-missing`/`write-failed`) with the same suppressed-confirmation behavior for both failure cases. Rejected as unnecessary complexity — both reviewers (BA and Facilitator personas) confirmed the same UI treatment applies to both, so a single `"unavailable"` state is sufficient and less error-prone to implement correctly.

### D3: Copy button and badge remain independent — the badge now signals an early-click caveat, not non-joinability

The link is a real, always-redeemable `join_links` token as of #166, so it works from `draft` onward — the badge no longer claims otherwise. `join-link-redemption-wiring`'s design.md Decision 4 reworded it accordingly, from "(not yet joinable)" to: "This link works already — anyone who opens it before you open the room won't see a waiting screen yet." The badge (`data-testid="draft-join-link-badge"`) stays exactly as that change left it; it now warns about the *experience* of clicking early (no waiting/lobby screen yet, per #164's still-open routing gap), not about whether the link is functional. The copy button is unaffected by this distinction — it's added alongside the badge in both `draft` and `lobby`+ states, and its presence/behavior is identical either way — same hook, same confirmation, same fallback. Nothing about the copy control itself changes based on session status or badge wording; only the badge's presence (and, since #166, its meaning) differs.

**Alternative considered:** withholding the copy button entirely during `draft` (the exploration's original default). Superseded during review — see `exploration-notes.md` §3 for the facilitator-workflow rationale (staging a Slack message before opening the room).

### D4: Confirmation banner reuses `MemberManagement.tsx`'s inline auto-clearing pattern, with an 8s clear instead of 5s, plus timer cleanup and a stacking guard

`MemberManagement.tsx`'s role-change confirmation (`role="status"`, `aria-live="polite"`, `setTimeout`-based auto-clear, `packages/frontend/src/components/MemberManagement.tsx:186-189` — a component, not a page; fixing the path design-review-engineer.md Finding 1 flagged) is the established convention for "acknowledge a successful action without a toast library." This change reuses that shape — `role="status"`, `aria-live="polite"`, literal text `"Link copied"` — but extends the auto-clear window to 8 seconds. `MemberManagement`'s 5s assumes the user is watching the screen after the action; this control's actual usage pattern is copy → alt-tab to Slack/email → paste → return, which can exceed 5 seconds before the user looks back. 8s is a directional fix for that gap, not a re-litigation of `MemberManagement`'s own timing.

Unlike `MemberManagement.tsx`'s literal implementation, which holds no reference to its timer and has no unmount cleanup, `useCopyToClipboard` does not reuse it *verbatim* — it fixes two latent bugs in the source pattern that would not be harmless here (design-review-engineer.md Finding 2), because `DraftSessionHost` sits on a real route a Facilitator can navigate away from mid-timer, and because D1 explicitly frames this hook as reusable infrastructure, not a one-off:
- **Stacking guard:** the pending timeout id is held in a `useRef`, and any existing timer is cleared before a new one is started on each `copy()` call. A second copy within the 8s window resets the clock rather than letting a stale first timer fire early and clear the banner while the second copy's confirmation should still be showing.
- **Unmount cleanup:** the pending timer is cleared in a `useEffect` cleanup on unmount, so no `setState` runs after `DraftSessionHost` unmounts.

Because `useCopyToClipboard` is invoked once at the `DraftSessionHost` level and both branches read the same `status` (D1), the confirmation banner and its timer survive the `draft` → `lobby` transition performed in place by `openTheRoom()` (`DraftSessionHost.tsx:112-118` — updates `loadState` directly, no remount, no navigation). This is a deliberate decision, not an accident of shared state: the copied URL is identical in both states (spec's "Copied URL is identical across draft and lobby status" scenario), so a "Link copied" banner that keeps showing across the transition is still describing a true fact about the clipboard's contents. No reset-to-idle-on-transition behavior is added.

**Alternative considered:** no auto-clear, dismiss-on-next-copy only. Rejected — leaves a stale confirmation on screen indefinitely if the Facilitator never triggers another copy, which drifts toward the "software feels like it's running a process" concern this project's SME (Devon) explicitly watches for.

### D5: Joinable-state link styling breaks from `draft`'s muted treatment; badge keeps its own style

`draft-control-view`'s existing `<p data-testid="draft-join-link" style={{ color: "#9e9e9e" }}>` treatment is deliberately de-emphasized and stays exactly as-is while the badge is present. Once the session reaches `lobby`+ (badge absent), the link renders in the page's default body text color — full emphasis, matching its status as the primary actionable element on the page. This is a one-line style change (drop the muted color when not in `draft`), not a new visual system.

**Alternative considered:** keep the muted style everywhere for visual consistency between `draft` and `lobby`+. Rejected per facilitator-persona review — the muted treatment reads as "don't bother with this yet," which is actively wrong messaging once the link is the thing the Facilitator most needs to act on.

### D6: `SessionLobbyPage` is untouched; the routing gap is out-of-scope by design, not oversight

Confirmed via `join-link`'s "Session-aware join link landing" requirement (redirect to `/session/:sessionId` fires only on `active` status) and exhaustive grep of frontend navigation call sites: nothing routes any user to `SessionLobbyPage` during `lobby` status today. Implementing this change there would satisfy the acceptance criteria against a component nothing reaches — passing tests while remaining invisible to a real Facilitator. `live-readiness-view` is the only surface a Facilitator actually reaches during the window this use case is about. The routing gap is filed as [#164](https://github.com/surratt-dev/project-dipstick/issues/164) rather than fixed here, since resolving it is a larger, separately-risked change (touching `TeamPage`, `DraftSessionHost`'s post-advance behavior, and possibly the join-link landing rule itself).

## Risks / Trade-offs

- **[Risk] A Facilitator copies the link during `draft` and shares it before opening the room; an early clicker doesn't get a waiting-screen experience.** → Mitigation: the link is a real, always-redeemable `join_links` token as of `join-link-redemption-wiring` (#166) — an early click reaches the actual redemption route rather than 404ing, but the `lobby`-landing experience it lands on remains incomplete pending #164, which that change's design.md Decision 5 accepts as a named, temporary gap rather than something this change needs to re-solve. The badge (`data-testid="draft-join-link-badge"`, reworded by #166 to "This link works already — anyone who opens it before you open the room won't see a waiting screen yet.") is read by the Facilitator before any sharing decision, in the same view as the copy button — no separate caution is needed here because that one already exists and is seen first.
  **On the clipboard-write delta specifically:** the token's DOM exposure in `draft-control-view` is unchanged from today — it was already server-rendered and manually copyable. What's new is a one-click `navigator.clipboard.writeText()` call, which measurably lowers the friction of getting the token onto the OS clipboard (a system-wide resource other local processes, extensions, or clipboard-sync tools can read) versus a deliberate select-and-copy gesture. That's a real, if small, reduction in copy friction — not "not a new risk," and it's worth naming precisely rather than waving off. It does not change the credential's blast radius: per `join-link`'s spec, the token is team-scoped, single-role (participant-join only), and time-bounded (7-day expiry, revocation deferred by that spec's own accepted decision), so the worst case a lower-friction copy enables is the same bounded outcome — an unintended team join — reachable today by manual copy, just easier to trigger, including incidentally by the Facilitator themselves per D3.
- **[Risk] 8-second auto-clear is a judgment call, not user-tested.** → Mitigation: it's a small, easily-tunable constant in one hook; not a structural commitment. Flagged in design rather than silently defaulted so it can be revisited if real usage shows it's still too short (or too long).
- **[Risk] `useCopyToClipboard` becomes a de facto shared primitive before its second real consumer exists.** → Mitigation: kept intentionally minimal (feature-detect, write, one status enum) — no speculative configuration options added for hypothetical future consumers (e.g., the deferred link-revocation UI), consistent with the project's guidance against premature abstraction.
- **[Risk] `SessionLobbyPage`'s `lobby` branch remains dead code indefinitely if #164 isn't prioritized.** → Mitigation: this change does not make that worse — the branch is already unreachable today. Filing #164 makes the gap visible and trackable instead of silently absorbed, which was the explicit ask from both reviewers.
