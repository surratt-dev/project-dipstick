# Architecture Review: TEAM-006 Threat Model

**Reviewer:** Ingrid Sollenberger, Principal Solution Architect
**Reviewing:** `threat-model.md` (Tomás Ferreira), against `design.md` and the implementation as of this branch.
**Scope of this review:** architectural soundness of the threat model's central claim and its recommended fix, plus a check of the remaining findings for accuracy and boundary discipline. I am not re-running the security analysis; I am judging whether the document's architectural reasoning holds up against what Decision 14 actually requires and what the code actually does.

---

## Verdict on Finding 1.3: CONFIRMED GAP

Tomás is correct. This is a real architectural violation of Decision 14, not a misreading of an acceptable alternate interpretation.

**What Decision 14 requires.** Read in isolation, Decision 14's text ("MUST be implemented as independent controls and must remain independent... they serve different purposes even when they produce the same result in the common case") could be read narrowly as only requiring two separate code paths that happen to agree in the common case — which is the reading the code comment at `team-content-access-helper.ts:124-132` relies on ("the dual-check is enforced by the serializer, not by the access grant").

That narrow reading does not survive contact with the rest of Decision 14 and the Risks section. Decision 14's own rationale states the purpose explicitly: *"If a user's global_role is updated out-of-band while their team_memberships row is not, or if a future change allows global_role = 'engineering_manager' to be set without going through TEAM-006, consolidating these checks creates a single point of failure with no backstop."* A backstop, by definition, has to be consulted at the moment the grant decision is made. The corresponding Risk entry removes any ambiguity: *"Both the global_role check and the team_memberships.role check remain in place and independent (Decision 14). The dual check must not be weakened regardless of how the relationship was established."* "Regardless of how the relationship was established" is the tell — it means the check has to hold even when `team_memberships.role` was set through a path other than TEAM-006. That is precisely the scenario `evaluateTeamAccess` fails to defend against.

**What the code actually does.** `evaluateTeamAccess`'s Path 1/2 (`team-content-access-helper.ts:134-141`) grants the EM content profile from `membership_role` alone. `global_role` is read into the grant object (`actorGlobalRole`) but never compared against `membership_role` before the grant is returned. The header comment block above the function (lines 24-36) describes a "dual-check" as though it gates the grant — it does not; it's describing the common case where both happen to be true, not a check the code performs. The comment at 130-132 says the quiet part directly: "the membership role governs, not the global role." That is one check, not two independent ones. Decision 14 is not "documented but implemented as one check" — it's not implemented at all in this function. The two checks are not independent controls; one of them (`global_role`) is dead weight in the grant path — read, logged, but never adjudicated.

Contrast this with `checkAssignRolesAuthorization` in `teams.ts:30-64`, which correctly implements the AND-logic Decision 14 calls for: `global_role === 'application_admin' || (global_role === 'engineering_manager' && membership_role === 'engineering_manager')`. This is the same codebase, the same design decision, implemented correctly twenty lines up in a sibling function used by the identical class of authorization question (can this actor act as an EM on this team). The inconsistency itself is evidence that the omission in `evaluateTeamAccess` is a defect, not an alternate but valid interpretation — if the AND-check were architecturally unnecessary, `checkAssignRolesAuthorization` wouldn't need it either.

**My judgment:** this is not a case of two reasonable people reading an ambiguous decision differently. Decision 14's rationale and its Risk-section restatement both point at a single, unambiguous requirement — the grant must fail if either check fails — and the code implements a weaker property (the two values usually agree) while a same-file comment mislabels that weaker property as the thing Decision 14 asked for. That mislabeling is the actual defect worth naming precisely: it's not that the code is undocumented or ambiguous, it's that the documentation confidently describes behavior the code doesn't have.

## Assessment of the Recommended Fix

Tomás's recommendation has two parts. I'll take them separately.

**1. `evaluateTeamAccess` requires `membership_role === 'engineering_manager' AND global_role === 'engineering_manager'` before granting the EM profile.** This is the correct fix and it is architecturally necessary regardless of what else changes. It makes `evaluateTeamAccess` match `checkAssignRolesAuthorization`'s existing pattern in the same file family, so it also improves internal consistency rather than introducing a new one. I checked for legitimate reliance on the current "membership role governs" behavior:

- The design.md line Tomás's own analysis quotes — "the membership role governs, not the global role" — traces to the *session-participation* spec's dual-check note in the code comment, not to a Decision 14 requirement. I found no acceptance criterion, spec, or test anywhere that depends on an EM profile being granted to a user whose `global_role` is `'engineer'`. The one place this state is supposed to be reachable (per the comment) is precisely the gap being fixed.
- `em-views.ts`'s tests (referenced by the threat model at `em-views.test.ts:289-290` for the no-date-boundary assertion) test the attribution boundary and access scoping, not this specific bypass path — nothing in the described test suite fixtures an EM with mismatched `global_role`/`membership_role` as a *positive* case. Adding the AND-check would not contradict any currently-asserted behavior I can find in the files reviewed; it removes a state space (`membership_role = 'engineering_manager'`, `global_role != 'engineering_manager'`) that no test currently exercises as "should succeed."

Fixing this alone closes the *read*-side gap: even if TEAM-005 (or any future code path) writes `membership_role = 'engineering_manager'` for a user without the matching `global_role`, that write no longer buys the actor an EM data grant.

**2. TEAM-005 should not be permitted to set `team_memberships.role = 'engineering_manager'` for a target whose `global_role` is not already `'engineering_manager'`.** I agree this is also warranted, but for a different reason than closing 1.3 specifically. Once fix (1) is in place, TEAM-005 setting a mismatched membership role no longer grants anything — the read-side AND-check neutralizes it. So fix (2) is not strictly required to close finding 1.3's stated harm (unauthorized EM data access). It is still worth doing, for a reason the threat model under-states: without it, TEAM-005 is left able to write a `team_memberships` row that *asserts* an EM relationship (visible in `TeamMembersResponse`'s `engineeringManagers` array per Decision 12, rendered in the team admin view's labeled EM section per Decision 7) for a user who isn't actually one by the global-role definition — a data-integrity and UX-correctness problem (a phantom EM shown to facilitators and participants) even after the security hole is closed. I'd frame fix (2) as a data-integrity constraint that happens to also remove a redundant path to the same stale state, not as a second security control layered on top of fix (1).

**Is fix (1) alone sufficient, or are both needed?** Fix (1) alone is sufficient to close finding 1.3 as a security gap — it makes the access grant correct regardless of how `team_memberships.role` came to be set, which is exactly the backstop property Decision 14 asks for. Fix (2) is good hygiene and prevents a confusing, incorrect membership state from being writable in the first place, but it is not load-bearing for security once (1) is in place. I'd land both, but I would not accept fix (2) alone as a substitute for fix (1) — that would leave the actual access-grant function relying on an invariant enforced only at a different call site (TEAM-005), which is exactly the "single point of failure" pattern Decision 14 exists to prevent. If a third write path is ever added that sets `team_memberships.role = 'engineering_manager'` (a migration, an admin bulk-edit tool, a future endpoint), fix (2)'s protection doesn't travel with it; fix (1)'s does, because it's enforced at the read/grant boundary every caller goes through.

## Other Findings — Architectural Accuracy Check

- **1.1 (TEAM-006 direct bypass) / 1.4 (race condition):** Both read as accurate against the code I reviewed (`teams.ts:654+`, the `xmax` upsert pattern). No issues.
- **1.2 (TEAM-005 as onboarding substitute):** Accurate, and correctly scoped — it stops short of claiming TEAM-005 can onboard a stranger, which the "existing member only" check (`teams.ts:447-457`) correctly forecloses. Good boundary discipline in this sub-finding; it hands off cleanly to 1.3 rather than overstating itself.
- **Rate limiting gap (3.10 / Q6):** Accurate. I confirmed no `@fastify/rate-limit` dependency and no rate-limiting code exist anywhere in `packages/backend/src`. This is correctly represented as "not yet built," not "poorly built."
- **EM monitoring gap (2.3):** Architecturally fair. The audit substrate (`audit_log` writes, `em.*` structured log events) is real and matches Decision 9/11's requirements; the document correctly distinguishes "audit trail exists" from "something consumes it as a detective control" and correctly declines to guess whether monitoring exists outside the repo rather than asserting a negative it can't verify. No overstatement.
- **Race condition analysis (1.4) and Decision 3 idempotency:** The `xmax`-based upsert claim matches design.md Decision 3's specified idiom and the described `ON CONFLICT ... RETURNING (xmax = 0)` pattern. I did not re-derive the SQL from scratch but the description is internally consistent with Decision 3 as written.
- **OIDC claim handling (Scenario 3):** The five-requirement table is the most rigorous section of the document — each row cites a specific line range and describes what it verifies rather than what it assumes. The one nuance flagged (allowlist rejection logs a warning and defaults, rather than aborting authentication) is correctly identified as a wording distinction, not a defect, and the document is careful not to inflate it into a finding. This is the right call — Decision 2 requirement 4 says "not silently mapped or silently ignored," and a logged default satisfies that; requiring hard authentication failure on a bad role claim isn't what Decision 2 asked for and would be a scope-creeping recommendation if it had been made. Correctly not made.
- **One accuracy note on severity framing, not a correction:** Finding 1.3's write-up in Scenario 1 asserts the exploiting actor needs no more than "any EM in good standing on a single team." I verified this against `checkAssignRolesAuthorization` (`teams.ts:58-61`): the actor must have both `global_role = 'engineering_manager'` AND `membership_role = 'engineering_manager'` on the target team to call TEAM-005 with EM authorization at all — i.e., the exploiting actor is already a legitimately-established EM on that team (via a prior correct TEAM-006 call), not an arbitrary participant. The threat model does say this ("An EM who is legitimately associated with Team A... via a prior, properly-gated TEAM-006 call") but it's stated once, briefly, in the middle of the attack-path narrative rather than in the severity framing. Given that qualifier, "High" severity is still the right call — the harm (bypassing the Application Admin gate, the audit event, and the not-yet-built rate limiting for a *second* team-scoped grant) doesn't depend on the actor being anonymous, only on them being an EM rather than an Admin — but I'd have surfaced the precondition more prominently next to the severity rating rather than only inside the narrative.

## Boundary Discipline

The document holds its stated boundary well. It explicitly declines to relitigate Decision 5 (attribution boundary), Decision 6 (undated historical access), and Decision 13 (action item visibility/inference risk), and in each case it does so correctly:

- **Decision 5** is invoked only to confirm the boundary holds technically (no `voter_id` selected, CI-asserted) and to note the coupling between Decision 5 and Decision 6's risk acceptance — that's an observation about risk *composition*, not a challenge to Decision 5 itself.
- **Decision 6** is explicitly named as accepted org-level risk not up for debate ("I am not relitigating that decision"), with the document narrowing its own actionable scope to the *compensating control* (3.10 rate limiting) that design.md itself named as required — that's holding the design doc to its own stated mitigation, not second-guessing the underlying tradeoff.
- **Decision 13** gets the most careful treatment: the document goes out of its way to state up front that the inference risk is "not a bug... not recommending it be closed" before describing the mechanics, and closes by explicitly declining to assign it a residual-risk rating "as if it were a gap." This is the correct posture for an accepted, named risk and avoids the common failure mode of a security document quietly re-opening a decision under the cover of "just documenting" it.

I found no place where the document drifts into recommending changes to these three decisions' actual tradeoffs. Finding 1.3 is not a Decision 14 relitigation — it's a claim that the code doesn't implement Decision 14 as written, which is in scope and, per my review above, correct.

---

## Recommendation

**The document is ready to guide a fix as written.** Finding 1.3's technical claim is accurate, its severity rating is justified even with the actor-precondition more clearly stated, and its recommended remediation (both parts) is architecturally sound and consistent with the existing correct pattern in `checkAssignRolesAuthorization`. I would not send this back for revision. Two small, non-blocking suggestions for whoever picks up the fix:

1. Implement fix (1) — the AND-check in `evaluateTeamAccess` — as the primary and load-bearing change; treat fix (2) — restricting TEAM-005's write — as a data-integrity companion fix, not a substitute.
2. When the fix ships, update or add a test that pins the specific state finding 1.3 describes (`membership_role = 'engineering_manager'`, `global_role != 'engineering_manager'` → grant must NOT carry `role: 'engineering_manager'`) so this exact regression can't reappear silently the next time someone edits this function's comment block instead of its logic.

I concur with blocking Phase 2 production deployment on finding 1.3 and would not clear it without also seeing 3.10 (rate limiting) landed and the EM-monitoring disposition (2.3) answered, consistent with the threat model's own recommendation.
