# Exploration Notes — Session Creation for Existing Teams (Issue #43)

**Explored by:** Devon Calloway (Internal Champion / SME), in `opsx:explore` mode.
**Use case:** `requirements/use cases/02 - Session Setup - Use Cases.md` — "Create Session for Existing Team"
**Related use case:** "Facilitator Team Membership Constraint Violation" (same file) — this is not a separate feature, it's the same feature's failure mode, and I'm treating it that way throughout.

---

## 1. What this feature actually is, underneath the CRUD

On paper this is "add a GET endpoint and a picker screen." I want to name what it's really doing before anyone starts writing routes: **this is the entry point that either preserves or quietly breaks the facilitator-from-another-team rule.** Every other constraint in this application (simultaneous reveal, no-manager-participation) is enforced once a session exists. This one is enforced *at the moment the session is created* — get this wrong and there's no downstream check that catches it. A session created with a same-team facilitator isn't a session that "later becomes invalid," it's a session that was never legitimate, and everyone in it will have an honest conversation under a broken pretense without knowing it.

So the eligible-teams list isn't a UI convenience. It's the load-bearing control. The confirm screen is a courtesy. The server-side check on the POST is the actual constraint. If any implementation treats the GET list as sufficient enforcement, that's the "silent bypass" scenario I most want to avoid (see §3).

**Pushback accepted, with a boundary (per Priya's review, observation 3):** "courtesy" was the wrong word, and I'll drop it — Priya's point that the confirm screen is where *she* catches her own mistake before real participants are affected is real, and worth designing for deliberately rather than treating as enforcement theater. Concretely: the confirm screen should show more than the bare team name the use case literally specifies — at minimum enough for a facilitator picking from a rotating set of teams to recognize which team they're about to commit to (e.g., last session date). I'd stop short of turning it into a dashboard, though — team history and trend data belong on the draft control view the facilitator lands on after confirming (see §7's revised decision), not duplicated onto the confirm step itself. Loading it twice, once thin on confirm and once fully on the landing screen, adds UI weight without adding a decision the facilitator couldn't make with a lighter cue — and "the app disappears into the background" cuts against stacking context screens in front of a one-click confirm. Exact content is a design.md call, but "just the team name" per the use case's literal wording is not enough, and "a full history dashboard" is more than this step needs.

## 2. Ritual constraints in play

- **Facilitator-from-another-team.** Confirmed hard requirement, not a warning, per the use case's own "Facilitator Team Membership Constraint Violation" companion doc: *"A server-side check prevents session creation for the user's own team regardless of how the request is submitted."* This document doesn't hedge — it says no exceptions are defined and lists "allowing any exception to the cross-team rule" as explicitly out of scope. Good. That's the correct posture.
- **No silent failure.** The alternate flow requires an explicit, clear rejection ("the Facilitator must be from a different team") — not a filtered list that just quietly excludes the option with no explanation of why. A picker that simply never shows the user's own team, with nothing else, technically satisfies the acceptance criteria but fails the spirit if a facilitator later tries the same thing via a stale link, replay, or direct API call and gets a vague 403.
- **Facilitator eligibility is a global property, scoped per-request.** `global_role = 'facilitator'` is what makes someone eligible to run sessions at all; team exclusion is what makes a *specific* team off-limits to *this* facilitator. Both checks are independent and both must be server-side. Confirmed both exist independently elsewhere in this codebase's patterns (`checkAssignRolesAuthorization`, `evaluateTeamAccess` — see §5) — this feature should follow the same shape, not invent a new one.

## 3. Finding: the existing draft-session endpoint does not enforce the exclusion rule at all

This is the important one. I read `packages/backend/src/routes/facilitator-sessions.ts:180-255` (`POST /api/v1/teams/:teamId/sessions/draft`) end to end. Its authorization check is:

```
1. Look up users.global_role for the caller.
2. Reject if global_role !== 'facilitator'.
3. Verify the team exists.
4. Create the draft session. No further checks.
```

There is no query anywhere in this handler against `team_memberships` for the requesting user. A user with `global_role = 'facilitator'` can call this endpoint today with their **own** team's ID and it will happily create a draft session — no rejection, no audit flag, nothing. I confirmed this isn't just an oversight in reading: the test file (`facilitator-sessions.test.ts`) has no test case for "facilitator attempts to create a session for their own team" anywhere in its ~1400 lines — I grepped for `eligib`, `own team`, and `team_memberships` in that file and found nothing tied to this endpoint. The constraint that the requirements call out as a *hard, no-exceptions block* is not implemented at the one endpoint that creates sessions.

I want to be precise about why this matters more than a typical missing-validation bug: this isn't a gap that degrades gracefully. A frontend picker that correctly excludes the facilitator's own team from the list will make this invisible in the demo. Nobody clicking through the UI will ever see it. It only shows up if someone calls the API directly, or if a future change reuses this endpoint from a different entry point that doesn't happen to filter first. That is exactly the "constraints become configurable/bypassable by accident, not by decision" failure mode I care most about. This needs a hard fix as part of this change, not a follow-up ticket — the use case whose acceptance criteria this endpoint is supposed to satisfy explicitly requires it, and the companion use case exists *specifically* to describe this exact bypass path.

**Recommendation:** the fix belongs in the same transaction/check as the existing `global_role` check, using the same query shape the codebase already uses elsewhere (`evaluateTeamAccess`'s pattern of reading `team_memberships` with `removed_at IS NULL` for the given team). A facilitator with an active membership row for `:teamId` gets a 403 with a message that names the rule ("You cannot create a session for a team you belong to"), not a generic forbidden message. This should ship as a correctness fix to the existing endpoint, with its own test, regardless of what the new picker UI does.

**Test scenarios (per Marcus's review, §2a — "add a test" was too soft):** Marcus is right that a hard, no-exceptions constraint needs enumerated acceptance conditions, not one bullet. These are the scenarios the proposal's task list should name explicitly, each as its own AC against `POST /api/v1/teams/:teamId/sessions/draft`:

1. Caller has `global_role = 'facilitator'` and an active (`removed_at IS NULL`) `team_memberships` row for `:teamId` → 403, with an error identifying the cross-team constraint by name. No session record is created.
2. Caller was previously a member of `:teamId` but was removed (`removed_at` set) → allowed. Historical membership is not a permanent bar (consistent with the exclusion definition in §4).
3. Caller's `global_role !== 'facilitator'` → 403, and the message is distinguishable from scenario 1's message — these are different failure reasons and the copy shouldn't collapse them.
4. The request is submitted directly (bypassing the picker/confirm UI entirely) → same 403 as scenario 1. This is the literal scenario the companion use case exists to name, so it should be a named test, not something covered only implicitly by scenario 1.

Tracing directly to the use case's own AC ("A server-side check prevents session creation for the user's own team regardless of how the request is submitted"):

> Given a caller with `global_role = 'facilitator'` and an active `team_memberships` row for `:teamId`, `POST /api/v1/teams/:teamId/sessions/draft` returns 403 with an error identifying the cross-team constraint by name, and creates no session record. This holds regardless of whether the request originated from the picker UI or was submitted directly.

## 4. The new GET endpoint

Needs: `GET` returning teams where the caller (`global_role = 'facilitator'`) has **no active `team_memberships` row**. Shape questions worth deciding explicitly rather than by accident:

- **Exclusion definition.** "Not a member" should mean no row with `removed_at IS NULL` — consistent with how membership is checked everywhere else in this codebase (`teams.ts`, `evaluateTeamAccess`). A facilitator who was previously removed from a team should be eligible to facilitate it again; nothing in the requirements suggests otherwise, and treating historical membership as a permanent exclusion isn't a rule anyone asked for.
- **Deactivated teams.** `teams.deactivated_at` exists in the schema. The use case doesn't mention deactivated teams at all. **Decision (per Marcus's review, §3 — this needs to be a stated AC, not a design.md footnote that might not survive):** teams with `deactivated_at` set are excluded from the eligible-teams list. Stating it once here.
- **Who can call this endpoint, and the exact response shapes (per Marcus's review, §3):** the principle — don't collapse "not a facilitator" and "zero eligible teams" into identical UI — was right but under-specified. Concrete shapes for the proposal:
  - Caller's `global_role !== 'facilitator'` → `403`, body identifies the reason (e.g., "Only facilitators can view eligible teams").
  - Caller is a facilitator with zero eligible teams → `200` with an empty array, plus a response-level flag or field the frontend can use to render the "nothing eligible" copy from §6.2's zero-eligible-teams state (rather than the frontend inferring "empty" means "nothing to show"). Exact field name is an implementation detail; the requirement is that `200` + `[]` is not visually or semantically identical to the 403 case on the frontend.
  - Caller is a facilitator with eligible teams → `200` with the array, each entry carrying at least team name and enough context to support whatever the confirm-screen decision in §1 settles on (e.g., last session date).
- **This is a new, narrow query — not `evaluateTeamAccess`.** `evaluateTeamAccess` (in `team-content-access-helper.ts`) answers "does this user have access to *this specific* team's content" and is deliberately per-team, no caching, live read. This feature needs the inverse shape — "give me every team this user is *not* already tied to" — which is a different query (`teams` LEFT JOIN `team_memberships` ... `WHERE membership IS NULL`) with different performance characteristics as the team count grows. Don't try to force-fit the existing helper; write the new query, but keep it in the same "always a live DB read, never cached" posture (ADR / Decision 6 precedent from `team-content-access-helper.ts`) since a stale eligible-teams list is exactly the kind of thing that would let someone facilitate a team they joined five minutes ago.

## 5. The confirm step and the server-side re-check

The use case is explicit that step 4 (confirm screen) and step 5 (submit) are separate steps, and the companion use case calls out the race condition directly: *"User's team membership changes between page load and submission... The application re-validates at submission time."* This means:

- The picker's GET response is **not** a valid authorization decision by the time the POST happens. Whatever time elapses between listing and confirming — however short — the POST handler (§3's fix) must re-check membership from the database at submission time, not trust that the frontend only offered eligible options. This is the same principle as `checkAssignRolesAuthorization` and `evaluateTeamAccess` already follow in this codebase (live read, no session-cached role), so there's a consistent existing pattern to point to — this isn't a new idea for this codebase, just a new place it needs to be applied.
- This is also why fixing §3 is not optional scope creep on top of "just add a GET and a page" — the picker literally cannot be a correct implementation of this use case without the POST-side check also being correct. They're one control, split across two requests.

**Frontend behavior for the race rejection (per Marcus's review, §3 — I'd only specified the backend side):** when the POST-side re-check rejects a confirm submission because membership changed since the GET, the confirm screen shows an inline error naming the reason (the same 403 message from §3's fix) and does not silently bounce the facilitator back to the picker — that would look like the click did nothing. The picker's eligible-teams list should be treated as stale at that point and re-fetched the next time the facilitator opens it, but the immediate feedback is on the confirm screen where the rejection happened.

## 6. Frontend gap: there's no entry point today, and the landing logic actively works against one

I read `App.tsx` and `NoTeamPage.tsx`. Two things worth flagging:

1. **`AuthSession` (the shared type returned to the frontend after login) does not carry `globalRole` at all** — only `user.id`, `displayName`, `email`, and `teamMemberships`. There's actually a comment already in `App.tsx` (around the `FacilitatorConnectionHost` route) acknowledging this exact gap for a different feature: *"AuthSession carries only global identity and per-team MembershipRole... the facilitator determination is per-session backend state the frontend never fetches."* This change will hit the same wall from a different angle: the frontend cannot decide whether to show a "Create a session" entry point at all without knowing the caller's global role. That needs to be added to `AuthSession` (or the picker page needs to attempt the GET and branch on 403 vs 200 — which works but is a slightly backwards way to drive navigation, and means an Engineer with no team memberships would hit a 403 network call it can't distinguish visually from "no eligible teams" (see §4) unless the frontend is careful).
2. **`AuthenticatedLanding`'s routing decision is currently binary on `teamMemberships.length`, not aware of `global_role` at all.** A facilitator who is not a member of any team would land on `/no-team` today. `NoTeamPage` tells them to "ask your facilitator for a join link" and offers nothing else. That's actively wrong copy for a user whose job *is* being the facilitator.

**Correction (per Marcus's review, §1 — this was wrong as originally written):** I originally wrote that "the requirements don't rule out" a facilitator with zero team memberships, leaning on the entities doc rather than the use case. Marcus is right that this contradicts the use case's own stated precondition ("The Facilitator is recognized by the application as a member of at least one team") and that I hadn't actually checked whether that precondition is *enforced* anywhere or just asserted. I went and checked. Findings:

- `account-resolver.ts` maps the OIDC role claim to `global_role` via `PERMITTED_GLOBAL_ROLES` — and that allowlist contains only `engineer`, `engineering_manager`, `application_admin`. **`facilitator` is not on it.** There is no authentication-time path that ever produces `global_role = 'facilitator'`.
- I grepped the entire backend for any endpoint that writes `global_role = 'facilitator'`. There isn't one. `checkAssignRolesAuthorization` (`teams.ts`) only assigns `team_memberships.role = 'engineering_manager'`; it explicitly does not touch `users.global_role`.
- The archived `assign-role-to-team-member` change confirms this in its own scope notes: *"Facilitator designation (`users.global_role = 'facilitator'`) — requires a new privileged endpoint; deferred to a separate use case"* and *"Bootstrapping the first admin or facilitator account — must be addressed as a named follow-on with a designated owner... Target: Q3 2026."*
- The only places `global_role = 'facilitator'` appears anywhere in the codebase are test fixtures — raw SQL inserts in `ws-pubsub-integration.test.ts` and mocked rows elsewhere.

**Conclusion:** the use case's precondition ("recognized as a member of at least one team") describes an *intended* invariant, not an *enforced* one. Every facilitator account that exists today was created by someone manually seeding `users.global_role = 'facilitator'` outside the application — there is no application code path that assigns that role and a team membership together, or that assigns it at all. Nothing prevents that manual process from producing a facilitator with zero `team_memberships` rows, because the two facts (global role, team membership) are set independently with no linkage or validation anywhere in the system. This is exactly the scenario Marcus asked me to rule in or out — I'm ruling it **in**: it's a real, currently-reachable state, not a hypothetical.

Per Marcus's own suggested resolution path: since the state is reachable, the fix belongs on the use case document (the precondition should be reworded to reflect that this is assumed but not currently enforced — that's a one-line correction for Marcus to make, not a reason to change this change's scope), and **my §6.2 recommendation stays in scope**: `AuthSession` needs `globalRole`, and `AuthenticatedLanding` needs to branch a facilitator with zero home-team memberships away from `/no-team`'s participant-facing copy. This is also, incidentally, a stronger argument for the fix than my original one: this isn't a defensive-code-for-a-state-that-might-happen-someday change, it's a fix for a gap that the *current* bootstrapping process (informal as it is until Q3 2026) will hit on day one for the very first facilitator accounts anyone creates.

Concretely, this change needs to touch:
- `AuthSession` type + the session-serialization code that builds it, to add `globalRole`.
- `AuthenticatedLanding` (or wherever routing decisions happen), to branch a facilitator with zero eligible actions differently from a facilitator with a home team.
- A new route (I'd guess `/sessions/new` or similar — no strong opinion, whoever owns routing conventions should pick) for the picker → confirm → create flow, gated on `globalRole === 'facilitator'`.

None of this is exotic, but it's more than "add a page" — it's a small, necessary change to the auth/session surface that this feature's frontend can't work without.

**Cutting the GET-fallback alternative (per Marcus's review, §3):** I originally floated "or the picker page could attempt the GET and branch on 403 vs 200" as a fallback if `AuthSession` isn't extended. Marcus is right to cut this — it would need the frontend to infer three-way meaning (not-a-facilitator / zero-eligible-teams / has-eligible-teams) out of a two-way HTTP response, and §4 already requires distinguishing the first two for the same endpoint. It's not a viable alternative; I'm removing it as an option. The `AuthSession` change is required, not optional.

**Zero-eligible-teams landing state (per Priya's review, observation 4):** now that §1 is resolved as in-scope, this needs actual copy, not a blank state. Two distinct empty states need to be written out (not improvised at implementation time):
- **Facilitator with a home team but zero eligible targets** (every other team already has a live session, or no other teams exist yet): "There are no teams available for you to facilitate right now" + whatever context is available (e.g., "Team Falcon's session is already in progress" if the cause is §8's concurrent-session block, once that data is easy to surface).
- **Facilitator with zero home-team memberships** (the case just resolved above): this is not "no teams available," it's "you don't have a home team, but you can still facilitate any team." The landing copy must not reuse `NoTeamPage`'s "ask your facilitator for a join link" text — that's participant-facing copy aimed at exactly the wrong audience here.

Exact copy is a design.md decision, but the distinction between these two states must survive into the proposal as a named requirement, not "the frontend should be careful" (Marcus's phrase for my own hand-waving here, fairly applied).

## 7. Landing in the session room afterward

The use case's step 8 and the issue description both call for landing the facilitator in the session room with the join link after creation. Looking at `facilitator-sessions.ts`, session creation via `POST /api/v1/teams/:teamId/sessions/draft` produces a **draft** session (`status: 'draft'`), not a `lobby` session — draft sessions exist specifically so a facilitator can review team history before opening the room (see the Decision 3/4 comments at the top of that file, and ADR-007 in the architecture doc on context-scoped facilitator access). Opening the room to participants is a **separate** call: `POST /api/v1/teams/:teamId/sessions/:sessionId/advance` (draft → lobby).

This matters for scoping the frontend flow: "creates a session and lands the facilitator in the session room with a join link" is actually two backend calls in sequence (draft, then advance), not one. The use case's plain description elides this because it predates the draft/lobby split (that split came from a later change, `enforce-access-control-on-team-content`). Whoever designs this needs to decide: does the picker → confirm flow call `/draft` and then immediately auto-call `/advance` so the facilitator always lands in an open lobby, or does it land the facilitator in the draft state with an explicit "open the room" action?

**Revised decision (reversing my original lean, per Priya's review, observation 1):** I originally leaned toward auto-advancing immediately, reading the use case's "waiting for participants" postcondition as `lobby`. Priya pushed back, and I think she's right, for a reason that matters more than my literal-wording argument: **draft mode exists, by this document's own §7 finding, specifically so a facilitator can review team history before the room opens (ADR-007).** If session creation for an *existing* team auto-advances straight to lobby, that review window never exists for the one flow where there's history to review — the team already has sessions, trend data, prior action items. A brand-new team (the companion "Create Session for a New Team" use case) has no history yet, so auto-advance costs nothing there; landing an existing-team facilitator in an already-open room removes the exact protection ADR-007 was built for. I was defaulting to the literal use-case wording without checking whether it was still describing the right thing post-ADR-007. It wasn't.

**Decision for this proposal: land the facilitator in `draft` status, not auto-advanced to `lobby`.** Concretely:
- Submitting the confirm screen calls `POST /draft` and navigates the facilitator to their own control view (not a participant-facing room) showing: the team's history/trend data (the thing draft mode exists to let them see — this also answers Priya's observation 2, "which room do I land in"), the generated join link (visible, but the session is not yet joinable — see below), and an explicit **"Open the room"** action.
- Activating "Open the room" calls the existing `POST /advance` endpoint. On success, the session transitions to `lobby`, becomes joinable, and the same screen updates in place to the live participant-readiness view — no navigation, no second confirm step.
- **Failure mode (per Marcus's review, §2c — this was missing entirely):** if `/advance` fails, the facilitator is not left staring at an ambiguous state, because they never left their own control view — the draft session still exists, visibly, on the screen they're already looking at. They see an inline error and can retry "Open the room" with no side effects (the draft row is untouched by a failed advance attempt). This is a direct benefit of not auto-advancing: it converts "draft succeeded, advance failed, user is stranded" from a two-call race the frontend has to paper over into a normal, visible, retryable user action.
- **Use case document conflict (per Marcus's review, §2c):** this makes the source use case's main flow (steps 5–8, written as one continuous sequence ending in an already-open participant readiness view) inaccurate for this feature as scoped. That's a real conflict, not a nuance — the use case needs an addendum describing the draft-landing step and the explicit "Open the room" action as part of this change, not a silent divergence between what's documented and what ships.
- **Still open, and deliberately not resolved here:** what happens if an Engineer clicks the join link while the session is still in `draft` (before the facilitator opens the room)? That's a real state now that draft-landing is the default, and it needs its own decision (a distinct "session hasn't opened yet" message, not conflated with the "invalid link" error page) — but it's a design.md-level decision for whoever builds the join-link landing page, not something I'm resolving in these notes.

**This is a firm recommendation for the proposal, not a final decision.** Priya asked to walk through the picker → confirm → land-in-room flow with whoever builds design.md before it's locked — I'm honoring that here: this is the direction I'd bring into that review, not a decision made without her. The concrete behavior above exists so the proposal has something testable to build against in the meantime, not to preempt her sign-off.

The join link itself: `join_token` is generated and stored at draft-creation time already (`facilitator-sessions.ts:233`), so there's no new join-link generation logic needed here — this change just needs to surface the existing token as a URL in the response the frontend receives, consistent with whatever the `join-link` spec (`openspec/specs/join-link/spec.md`) already defines for link format. I didn't re-derive that spec here; it should just be reused, not reinvented.

## 8. Concurrent sessions for the same team — the use case flags this as open, I'd resolve it now

The use case's Notes section explicitly leaves open whether two sessions can be active for the same team simultaneously. I'd push back on leaving that open through this change. Two facilitators independently creating sessions for the same understaffed or popular team isn't a paranoid edge case — it's the kind of thing that happens the first time two senior engineers both decide to be helpful in the same week. If it's not prevented, you get two competing join links, participants randomly split across two rooms, and two sets of vote data that look like duplicate/conflicting Health Check results for the same period — which pollutes the exact trend data this project exists to produce.

**"Block," not "warn" (per Marcus's review, §2d):** I originally wrote "block or warn" as if they were interchangeable options. Marcus is right that they aren't, and that only one of them actually solves the problem I opened this section with. "Warn and proceed anyway" still lets a second session get created after an acknowledgment click — it doesn't prevent the two-competing-join-links, split-participants, polluted-trend-data outcome, it just adds a click in front of it. If preventing that outcome is the goal — and it is, that's the entire reason this section exists — the policy has to be **block, full stop**: a facilitator cannot create a session for a team that already has a non-terminal session (`draft`, `lobby`, `pre_session`, `active`, `wrap_up`). No exception path, consistent with how this document treats the cross-team constraint elsewhere.

**Blocked-state UX (per Priya's review, observation 5):** a flat rejection here just reads as a glitch and invites an immediate retry. The rejection needs to name the existing session as the reason (matching the "no silent failure" principle from §2, applied consistently) — at minimum, that a session already exists for this team; ideally enough for the facilitator to decide whether to go join it instead of trying again later. Exact copy/whether there's a "go to that session" action is a design.md call, but the response needs to carry enough data (at minimum the existing session's status) to support that decision, not just a boolean rejection.

**Fixing the race-condition inconsistency (per Marcus's review, §2d):** Marcus caught something I should have caught myself — I insist elsewhere in this document (§3, §5) that authorization checks must be re-validated server-side at submission time because a `SELECT`-then-decide pattern is a race condition someone will eventually hit, and then here I proposed a bare `SELECT` before `INSERT` with no transaction or lock and called it "sufficient," for a check whose entire stated purpose is to catch two facilitators acting *concurrently*. That's the same class of race I'm not willing to accept in §3. Applying the same standard here: the right fix is a **partial unique index** — `UNIQUE (team_id) WHERE status IN ('draft', 'lobby', 'pre_session', 'active', 'wrap_up')` — so the database itself makes a second non-terminal session for the same team impossible to insert, rather than relying on an app-level check-then-act window. The `INSERT` either succeeds or fails a uniqueness constraint; a failed insert is caught and translated into the blocked-state response above (with a follow-up `SELECT` to fetch the existing session's details for that response — that read doesn't need to be race-safe itself, since the insert already is). This closes the exact race I was previously waving away, using a mechanism that's simpler than the `SELECT`-then-`INSERT` pattern it replaces, not more complex.

**Concrete acceptance condition:**

> If a non-terminal session (`draft`, `lobby`, `pre_session`, `active`, `wrap_up`) already exists for the target team at the time a session-creation request is submitted, the request is rejected, naming the existing session as the reason. This is enforced by a database-level constraint (a partial unique index on `sessions.team_id` scoped to non-terminal statuses), not an app-level `SELECT`-then-`INSERT` check, so that two concurrent requests cannot both succeed.

**Repeat-use friction — logged, not in scope (per Priya's review, observation 6):** Priya's point that a facilitator running this flow for a rotating set of teams shouldn't re-scan a flat, unordered list every time is fair, and consistent with "the tool should disappear into the background." But it's a personalization feature (remembering recent teams, or surfacing most-recently-facilitated first) layered on top of a picker that doesn't exist yet — building it now would be designing convenience features for a flow nobody has used. I'd log it as a named follow-on for whoever owns the picker UI post-launch, not carry it into this change's scope. Flagging it here so it isn't lost, not committing to it.

## 9. Summary of what I'd want in the proposal

1. **Fix, don't just wrap:** add the missing team-membership exclusion check to the existing `POST /api/v1/teams/:teamId/sessions/draft` handler, server-side, with its own test (see §3's four enumerated scenarios). This is the actual enforcement point; treat it as a required part of this change, not a pre-existing bug to file separately.
2. **New endpoint:** `GET` for eligible teams (facilitator's non-memberships), live DB read, 403 for non-facilitators, explicit empty-vs-unauthorized response shapes (§4), deactivated teams excluded.
3. **`AuthSession` gains `globalRole`**, and `AuthenticatedLanding` (or equivalent) is updated to give facilitators a path into this flow, including the case where they have zero home-team memberships — confirmed in scope, not a hypothetical (§6.2).
4. **New frontend flow:** picker → confirm (team name + facilitator's own name + enough team context to be a real check, per §1) → submit → land on the facilitator's own draft-status control view with team history/trend data, join link, and an explicit "Open the room" action (§7) — not auto-advanced to lobby. This direction goes to Priya for sign-off in the design.md walkthrough before it's final.
5. **Decided:** same-team concurrent session handling is a **block**, enforced by a database-level partial unique index, not an app-level check-then-act (§8). Deactivated-team exclusion is a stated AC (§4).
6. **Use case document needs two corrections**, owned by Marcus: the "at least one team membership" precondition should be reworded as assumed-but-unenforced rather than guaranteed (§6.2); the main flow's steps 5–8 need an addendum reflecting the draft-landing step and explicit "Open the room" action (§7).

I'd rather see this scoped correctly up front than see a "picker only" version ship that looks complete in a demo but leaves the actual constraint unenforced at the API layer. That's the version of this feature I'd be most unhappy to find out about after the fact.
