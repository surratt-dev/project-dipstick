## Why

Every protective constraint this application exists to enforce — simultaneous reveal, no-manager participation, the facilitator-from-another-team rule — depends on a session having been created legitimately in the first place. Today there is no entry point for creating a session for an existing team at all, and the one endpoint that would need to enforce the facilitator-from-another-team rule (`POST /api/v1/teams/:teamId/sessions/draft`) does not check team membership: a facilitator can currently call it with their own team's ID and it succeeds silently. A frontend picker that correctly filters the facilitator's own team out of the list would make this invisible in a demo — the gap only surfaces when someone bypasses the picker, and the companion use case ("Facilitator Team Membership Constraint Violation") exists specifically to describe that bypass path. This change builds the missing entry point and closes the enforcement gap in the same pass, because the picker cannot be a correct implementation of the use case while the endpoint underneath it stays unenforced.

## What Changes

- **Fix (not follow-up):** `POST /api/v1/teams/:teamId/sessions/draft` gains a server-side check that rejects session creation when the caller has an active `team_memberships` row for the target team, with an error that names the constraint. This closes the gap regardless of whether the request comes from the new picker UI or is submitted directly. Both the rejection and a successful draft creation now write a synchronous audit record, following this codebase's existing precedent for auditing blocked privileged-boundary attempts and newly-established access grants (`team.role_change_denied`, `team.manager_established`) — a fix for a named, previously-invisible enforcement gap that itself left no audit trail would repeat the exact blind spot it exists to close.
- **New:** `GET /api/v1/teams/eligible-for-session` returns the teams a facilitator may create a session for (teams with no active membership row for the caller, deactivated teams excluded), with response shapes that distinguish "not a facilitator" (403) from "facilitator with zero eligible teams" (200, empty, flagged) from "facilitator with eligible teams" (200, populated).
- **New:** Concurrent-session protection — a facilitator cannot create a session for a team that already has a non-terminal session (`draft`, `lobby`, `pre_session`, `active`, `wrap_up`), enforced with a database-level partial unique index on `sessions.team_id`, not an app-level check-then-act.
- **New:** Frontend picker → confirm → create flow at a new route, gated on facilitator eligibility. The confirm screen shows team context beyond the bare name (e.g., last session date) so a facilitator picking from a rotating set of teams can recognize what they're about to commit to.
- **New:** Session creation navigates the facilitator to a real, bookmarkable route (`/team/:teamId/session/:sessionId`) showing the session's own `draft`-status control view (join link visible, session not yet joinable) with an explicit **"Open the room"** action that calls the existing `POST /advance` endpoint. This is a deliberate reversal of the use case's literal wording (which describes landing directly in an open participant-readiness view) — draft mode exists so a facilitator can review team context before the room opens (ADR-007), and auto-advancing an *existing* team's session past that window removes the one protection ADR-007 was built for. The route survives a page refresh or bookmark (rehydrating via the existing facilitator-state endpoint), and, since opening the room is a one-way transition, the action is preceded by a lightweight inline confirmation. A failed "Open the room" attempt leaves the facilitator on the same screen with an inline error and a retryable action, not stranded between two states.
- **New (corrected from exploration):** `AuthSession` gains a server-computed `canFacilitateSessions: boolean` field, evaluated fresh on every `/auth/session` call from `users.global_role`. **This is not the raw `globalRole` field the exploration notes proposed** — the `role-assignment` capability already establishes, for exactly this class of decision, that `globalRole` MUST NOT be added to `AuthSession.user` and that the frontend MUST react to a server-computed capability flag rather than compute authorization from a role value itself (the `canAssignRoles` precedent). This change follows that existing pattern instead of introducing a second, inconsistent one.
- **New:** The `/no-team` landing path gets an explicit carve-out: a user with `canFacilitateSessions = true` and zero team memberships is routed to the session-creation entry point instead, not to the participant-facing "ask your facilitator for a join link" page. Today's `first-access` spec has no such carve-out and would conflict with this if left unchanged.
- **Not in this change, logged as follow-ons:** picker personalization/ordering for facilitators who rotate across many teams; the "session hasn't opened yet" join-link landing message for an Engineer who clicks the link before the facilitator opens the room; a full team trend/history dashboard (the draft control view shows lightweight team context, not a trend dashboard that does not yet exist as a capability).

## Capabilities

### New Capabilities
- `session-creation`: Facilitator-initiated session creation for an existing team — the eligible-teams listing, the concurrent-active-session block, the draft-status landing control view, and the "Open the room" advance action. (The new-team variant of session creation, and any picker personalization, are explicitly out of scope for this change and left for this capability to grow into later.)

### Modified Capabilities
- `session-participation`: The existing "Facilitator-from-another-team enforcement at session setup" requirement is a first-entry stub with no concrete enforcement point or test coverage. It is removed from this capability and superseded by a fully specified version in the new `session-creation` capability, which is where the enforcement point (`POST /api/v1/teams/:teamId/sessions/draft`) actually lives.
- `project-structure`: `AuthSession` gains the `canFacilitateSessions` capability flag described above.
- `first-access`: The "No-team landing page" requirement gains an explicit exception for users eligible to facilitate sessions, so it no longer unconditionally routes every zero-team-membership user to participant-facing copy.

## Impact

- **Backend:** `packages/backend/src/routes/facilitator-sessions.ts` (the `POST /draft` handler gains the combined membership check, transactional audit writes, and the concurrent-session 409 handling; a new `GET` eligible-teams route is added nearby), `packages/backend/src/auth/audit-logger.ts` (two new `AuditEventName` values: `session.draft_denied_membership_conflict`, `session.draft_created`), a new migration for the partial unique index on `sessions.team_id` (with a self-enforcing pre-check guard), `packages/backend/src/routes/auth.ts` or the session-serialization code that builds `/auth/session` responses.
- **Frontend:** `packages/frontend/src/App.tsx` (`AuthenticatedLanding` routing, a new route for the picker → confirm flow, and a new real route `/team/:teamId/session/:sessionId` for the draft control view / live-readiness view), `packages/shared/src/types/auth.ts` (`AuthSession` field addition), `packages/shared/src/types/team-content-access.ts` or similar (new named response types: `EligibleTeamsResponse`, `EligibleTeam`, `SessionAlreadyExistsResponse`).
- **Database:** new partial unique index; no new tables. `deactivated_at` on `teams` is read, not written, by this change.
- **Requirements documents:** `requirements/use cases/02 - Session Setup - Use Cases.md` needs three corrections (owned by the BA, tracked as a dependency of this change, not implemented by it): the "at least one team membership" precondition should read as assumed-but-currently-unenforced; the main flow's steps 5–8 need an addendum describing the draft-landing step and the "Open the room" action; and the Acceptance Criteria checklist's "creates a session record with status 'waiting for participants'" and "the Facilitator sees the session room (participant readiness view) after creation" bullets both need to be corrected to describe the draft-landing behavior — as written today, no shipped build will ever satisfy them.
- **No breaking API changes** for existing callers; the `POST /draft` fix tightens previously-unenforced (and untested) behavior rather than changing a documented contract. **Verified for this change:** a repo-wide search (frontend source, backend source, and any scripts) found no existing caller of `POST /api/v1/teams/:teamId/sessions/draft` anywhere outside the route's own handler and its test file — there is no production UI or tool that calls this endpoint today. The membership-check fix in this change therefore has no existing caller whose behavior it changes; it closes a gap that has never been exercised by any real client, not a silently-exploited one.
