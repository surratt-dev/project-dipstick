## Context

`POST /api/v1/teams/:teamId/sessions/draft` already exists and creates a `draft`-status session (see `packages/backend/src/routes/facilitator-sessions.ts:180-255`). Today its authorization check is `global_role === 'facilitator'` and nothing else — no query against `team_memberships` at all. There is no frontend entry point that calls it for an existing team, and no test exercises the self-team case. The use case this change implements (`requirements/use cases/02 - Session Setup - Use Cases.md`, "Create Session for Existing Team") and its companion ("Facilitator Team Membership Constraint Violation") both treat the facilitator-from-another-team rule as a hard, no-exceptions block that must hold "regardless of how the request is submitted" — i.e., the picker UI is not the control, the endpoint is.

Three existing constraints shape this design and are treated as fixed:
- `role-assignment`'s `canAssignRoles` requirement: `globalRole` MUST NOT be added to `AuthSession.user`; the frontend reacts to a server-computed capability flag, it does not compute authorization from a role value.
- `first-access`'s no-team landing page: currently unconditional for any user with zero team memberships.
- `session-participation`'s dual-check pattern: any authorization decision that depends on a user's relationship to a team reads `team_memberships` live from the database, never from cache or client-supplied state.

## Goals / Non-Goals

**Goals:**
- Close the enforcement gap at `POST /draft` so the facilitator-from-another-team rule is a real, tested, server-side block, independent of any frontend picker.
- Ship a working picker → confirm → draft-landing flow for an existing team, gated on a capability flag that follows the existing `canAssignRoles` precedent rather than inventing a new pattern.
- Prevent two non-terminal sessions from existing for the same team at once, at the database level.
- Land the facilitator in `draft` status with an explicit, retryable "Open the room" action rather than auto-advancing to `lobby`.

**Non-Goals:**
- The "Create Session for a New Team" use case (team creation as part of session setup) — separate change.
- A trend/history dashboard on the draft control view. No such capability exists yet; the control view shows only lightweight team context (name, last session date if one exists).
- Picker personalization or most-recently-facilitated ordering — logged as a follow-on.
- The join-link landing experience for an Engineer who arrives while the session is still in `draft` (before "Open the room" is activated) — a distinct decision for whoever builds that page next.
- Revisiting `role-assignment`'s `canAssignRoles` mechanism itself — this change follows that precedent, it does not change it.

## Decisions

**D1 — `POST /draft` enforcement is a dedicated, inline check, one combined query, not a call into `evaluateTeamAccess`.**
`evaluateTeamAccess` (team-content-access) answers "what role-qualified grant does this user have on this team's content," a different and more expensive question than "does any `team_memberships` row exist for this user and this team at all." The `/draft` handler adds its own targeted check, following the same live-read, no-cache posture `evaluateTeamAccess` and the session-participation dual-check already use, without forcing the two into one helper.

**Query shape (revised per engineering review — Marcus Oyelaran):** the global-role and membership conditions are resolved in a single query, mirroring the LEFT JOIN pattern `checkAssignRolesAuthorization` and `evaluateTeamAccess` already use for this exact shape of question — a global-role condition and a team-scoped condition evaluated together:

```sql
SELECT u.global_role,
       (tm.id IS NOT NULL) AS is_member
FROM users u
LEFT JOIN team_memberships tm
      ON tm.user_id = u.id
     AND tm.team_id = $2
     AND tm.removed_at IS NULL
WHERE u.id = $1
```

**Check order, made explicit (closing engineering review's ordering gap):**
1. User not found → `401` (unchanged from today's handler).
2. `global_role !== 'facilitator'` → `403`, "not a facilitator" message. This runs first because it depends only on the actor's identity, not on `:teamId` — it is not an existence-or-relationship question, so it carries none of the ordering hazard step 4 has.
3. Team existence (`SELECT id FROM teams WHERE id = $1`) → `404` if missing. Runs before the membership rejection so that rejection's code path — and its audit write, below — is never reached for a `:teamId` that doesn't exist, mirroring the order every other handler in this file uses (existence checks before relationship-adjacent checks; see `/advance`, `/complete`).
4. `is_member` (already fetched in step 1's query — no additional round trip) → `403`, cross-team-constraint message, distinct wording from step 2's message (required so the acceptance-criteria scenarios stay distinguishable). This is the check that closes the enforcement gap.
5. Insert (see D3 for the concurrency handling and the transactional audit write on success).

Net effect: two queries before the insert (the combined users/membership query, then team existence) — one fewer round trip than a naive "add a third query for membership" approach, while still checking existence before the relationship check.

**Audit logging (required — Security review and engineering review converged on this independently).** Every other state-changing endpoint in `facilitator-sessions.ts` audits both its denial and success paths for security-relevant actions; `POST /draft` today audits neither, and this change's entire purpose is closing a named, previously-invisible enforcement gap. Shipping that fix with no record of anyone hitting the boundary it enforces repeats "the exact blind spot that made the original bug severe" — the reasoning `team.role_change_denied` (`packages/backend/src/auth/audit-logger.ts`, `packages/backend/src/routes/teams.ts:821-877`) exists to prevent. Two new `AuditEventName` values:

- **`session.draft_denied_membership_conflict`** — written synchronously (a plain `INSERT INTO audit_log`; no transaction needed, since there is no paired state change) immediately before the step-4 `403` response, carrying `actor_user_id`, `actor_global_role`, `actor_ip`, `team_id`. Followed by `emitAuditEvent` as the structured-log operational-alert counterpart — the same DB-row-is-authoritative / log-is-alerting-path split `team.role_change_denied` uses.
- **`session.draft_created`** — written in the same transaction as `INSERT INTO sessions` (see D3), carrying `actor_user_id`, `actor_global_role`, `actor_ip`, `team_id`, and `session_id` in `metadata`. A successful draft creation is the root of a content-access grant (Path 3 in `evaluateTeamAccess`) that persists for up to 24 hours, and every other event in this codebase that establishes an access grant is audited — `team.manager_established` is the direct precedent, including the "written in the same transaction as the row it authorizes" property. Followed by `emitAuditEvent` after commit.

**Declined: an audit event for the step-2 (`global_role !== 'facilitator'`) rejection.** Security review flagged this as [RECOMMENDED]; I'm not adding it. This codebase's existing convention does not audit a plain "you have no standing to do this at all" rejection — only a rejection of one specific privileged action by an actor who otherwise *does* have standing gets an audit event. `checkAssignRolesAuthorization`'s baseline "not authorized for this team" `403` is not audited anywhere; only the narrower `team.role_change_denied` case (an authorized actor attempting one specific blocked transition) is. Step 2 here is the direct analogue of that unaudited baseline case — "you are not a facilitator, full stop" — while step 4 is the analogue of the audited case — "you are a facilitator, but this specific team is off-limits to you." Auditing step 2 would establish a new convention (audit every generic authorization-boundary `403`) rather than apply the existing one, and a design review for one feature isn't the place to make that call for the whole codebase. If that broader convention is wanted, it should be its own reviewed change.

*Alternative considered:* Reuse `evaluateTeamAccess` and reject on any grant. Rejected — that helper is shaped to return "what can this user do," and a facilitator with an active session on the team would already get a `path: 'facilitator'` grant back, which is a different (and irrelevant) case for this check; force-fitting it adds complexity without reuse benefit.

**D2 — Eligible-teams response distinguishes *why* the list is empty, not just *whether* it is.**
`GET /api/v1/teams/eligible-for-session` returns `403` for non-facilitators. For facilitators, it returns `200` with `{ eligibleTeams: [...], callerHasTeamMemberships: boolean }`. The `callerHasTeamMemberships` field is what lets the frontend choose between the two empty-state copies specified in the proposal (zero-home-team facilitator vs. facilitator who is already a member of every other team) — the HTTP status code alone (`403` vs `200`) already separates "not a facilitator" from "is a facilitator," so no additional field is needed for that distinction; the additional field is only for telling apart the two reasons a `200` response can still be an empty array. Each team entry includes at least `teamId`, `teamName`, and `lastSessionAt` (nullable) for confirm-screen context. Deactivated teams (`teams.deactivated_at IS NOT NULL`) are excluded via the query's `WHERE` clause, not filtered client-side. This is a new, purpose-built query (`teams` LEFT JOIN `team_memberships` ... `WHERE membership IS NULL AND deactivated_at IS NULL`) — the inverse shape of `evaluateTeamAccess`, and, like it, always a live read.

**`lastSessionAt` is `MAX(completed_at)` over `status = 'complete'` sessions only** (closing an engineering-review ambiguity), mirroring `fetchPreSessionActionItems`'s existing convention of sourcing only from completed sessions. A live or draft session for a team never masquerades as "last session" context on the confirm screen — this matters specifically because the Resolved decision below deliberately leaves teams with a live session in `eligibleTeams`, so a "Last session: today" reading on a team that is actually mid-session right now would otherwise be a confusing, avoidable confirm-screen moment.

**This endpoint's own `403`-vs-`200` authorization gate is a live database read of `users.global_role`, not a cached or session-carried value** (required per security review). This is the same query used for D1's step-2 check, run fresh on every request; the handler does not trust `canFacilitateSessions` or any other value attached to `request.session`. This matches the live-read discipline every other authorization decision in this codebase already follows (`session-participation`'s dual-check, `evaluateTeamAccess`, D1's own check above): a facilitator whose role is downgraded mid-session loses the ability to enumerate teams on their very next call to this endpoint, not whenever their session object happens to refresh.

**Org-wide team enumeration by any facilitator is a deliberate, accepted disclosure scope, not a leak** (stated explicitly per security review, so a future reviewer doesn't have to reconstruct it from the use case document). The use case this endpoint implements is unambiguous that a facilitator may see and act on any team in the organization they don't belong to — there is no narrower "authorized-adjacent" set to leak beyond. `teamName` and `lastSessionAt` for every non-deactivated team, visible to every `global_role = 'facilitator'` account, is accepted as within this endpoint's intended scope.

**Response type.** `{ eligibleTeams: EligibleTeam[], callerHasTeamMemberships: boolean }` is a named interface, `EligibleTeamsResponse`, in `@dipstick/shared`, alongside `EligibleTeam { teamId, teamName, lastSessionAt }` — matching this file's existing convention of typed response shapes (`FacilitatorSessionStateResponse`) rather than an ad hoc inline body.

**Resolved:** the eligibility query is exactly the two conditions above — membership and deactivation — and deliberately does not join against `sessions` to exclude teams with an existing non-terminal session. A team with a live session can still appear in `eligibleTeams`; selecting it is caught by D3's `409` at submission time. *Alternative considered:* add a third condition excluding teams with a non-terminal session, so the list only ever shows truly creatable teams. Rejected — it would duplicate the "does this team have a live session" check in two places (the listing query and the insert-time constraint) for a case the submission path already handles correctly and unconditionally (the list is never trusted at submission regardless). This was raised during propose-stage review as a contradiction between this decision and an earlier draft of the "zero eligible targets" scenario, which named a live session as a possible cause of an empty list; the scenario has been corrected to match this decision rather than the other way around.

**D3 — Concurrent-session protection is a partial unique index, not a check-then-insert.**
```sql
CREATE UNIQUE INDEX sessions_team_active_unique
  ON sessions (team_id)
  WHERE status IN ('draft', 'lobby', 'pre_session', 'active', 'wrap_up');
```
**Why these five statuses and not all seven** (stated explicitly per security review [RECOMMENDED]): `session_status` has seven values. `complete` and `abandoned` are its only two terminal outcomes; the other five are all blocking. No code path anywhere in this codebase transitions a session to `abandoned` today — it exists in the enum as a defined terminal state but is not yet reachable (confirmed by inspection) — so excluding it from the index is currently correct. This is recorded here so a future change that starts writing `abandoned` mid-session (an idle-timeout auto-abandon feature, for instance) has to reconsider this index's status list deliberately, rather than silently reopening the exact race this decision closes.

The `INSERT` for a new draft session, together with the `session.draft_created` audit_log row (D1), is attempted inside a single transaction: `BEGIN` → `INSERT INTO sessions ... RETURNING id` → `INSERT INTO audit_log ...` → `COMMIT`. A unique-violation error — Postgres code `23505`, matched on the concrete node-postgres field `err.constraint === 'sessions_team_active_unique'`, not a message-substring match — on the `sessions` insert triggers a `ROLLBACK` and is translated into a `409` response; any other error propagates unchanged. On the `409` path, a follow-up `SELECT` (run as its own statement, after the rollback) fetches the existing non-terminal session's `id` and `status` to populate the rejection body, so the facilitator can be told what already exists and navigate to it (see D6). This follow-up read does not need to be race-safe itself — the index already made the write race-safe.

**Response type.** The `409` body is a named interface, `SessionAlreadyExistsResponse { errorState: 'session_already_exists', existingSessionId, existingSessionStatus, teamId }`, in `@dipstick/shared` — matching this file's convention for structured, frontend-actionable failure states (`RevealFailureResponse`, `TopicAdvanceBlockedResponse`) rather than the generic `{ error: { category, message, correlationId } }` body. D6 uses `existingSessionId` directly to route the facilitator to their existing session.

**Migration guard is self-enforcing, not a runbook step** (closing an item both engineering and security review raised independently). Rather than a manual pre-check query an operator is expected to run before the migration, the migration file itself contains a `DO $$ ... IF EXISTS (SELECT team_id FROM sessions WHERE status IN ('draft','lobby','pre_session','active','wrap_up') GROUP BY team_id HAVING COUNT(*) > 1) THEN RAISE EXCEPTION ...; END IF; END $$;` block immediately before `CREATE UNIQUE INDEX`. `node-pg-migrate` runs each `.sql` migration inside its own transaction by default (this migration needs no `CONCURRENTLY`, so that default holds), so a violation aborts the whole migration transaction and fails the deploy loudly — no dependency on an operator remembering a separate, out-of-band step.

*Alternative considered:* `SELECT` for an existing non-terminal session, then `INSERT` if none found. Rejected for the same reason the codebase already rejects this pattern elsewhere (`session-participation`'s dual-check precedent): the window between `SELECT` and `INSERT` is exactly where two concurrent facilitators would both pass the check.

**D4 — `AuthSession` gains `canFacilitateSessions`, not `globalRole`.**
The exploration notes recommended adding `globalRole` directly to `AuthSession`. That conflicts with `role-assignment`'s existing requirement, which was written to prevent exactly this shape of change: exposing a raw role and letting the frontend derive authorization from it. Instead, `/auth/session` computes `canFacilitateSessions: boolean` from `users.global_role === 'facilitator'` on every call — evaluated live, alongside the existing team-membership resolution that endpoint already does, never cached in the Redis session blob. This is additive to `AuthSession`, not nested under `user`, keeping the same shape distinction `role-assignment`'s requirement text draws between identity data and a computed authorization signal: *"`globalRole` MUST NOT be added to `AuthSession.user`... The `canAssignRoles` flag is more defensive: the client reacts to a server authorization result; it does not compute one."* (`spec.md:242`). Correction from engineering review: `canAssignRoles` itself is not a field on `AuthSession` anywhere in the current codebase — it lives on the per-team `GET /members` and `GET /:teamId` responses, always evaluated per-team via `checkAssignRolesAuthorization`. This design follows the *principle* that requirement text states, not a literal reuse of an existing `AuthSession` field; `canFacilitateSessions` is the first field of this shape to actually live on `AuthSession`.

**D5 — Routing carve-out order in `AuthenticatedLanding`.**
1. `teamMemberships.length > 0` → existing team-view routing (unchanged).
2. Else, `canFacilitateSessions === true` → route to the session-creation entry point.
3. Else → `/no-team` (unchanged participant-facing copy).
This requires a corresponding change to `first-access`'s "No-team landing page" requirement, which today applies unconditionally; see the `first-access` spec delta.

**D6 — Draft landing is a control view, not a navigation to a participant-facing room, at a real, refresh-safe route.**
Submitting the confirm screen calls `POST /draft` and navigates the facilitator to a new, dedicated route, `/team/:teamId/session/:sessionId`, rendering their own control view: team context, the join link (visibly marked not-yet-joinable), and "Open the room."

**Why a real route (revised per engineering review — this was the one item Marcus Oyelaran said he'd block on).** The original version of this decision rendered the control view "in place," with no URL behind it beyond the initial navigation to the picker. A page refresh, dropped tab, or bookmark attempt at that point would strand the facilitator back at the picker with no way to return — and D3's new partial unique index means they can't even recreate the session to get back to it, since one already exists for that team.

**The route is real and rehydratable.** On mount — whether arriving via the create flow's navigation, a refresh, a bookmark, or the `409`-resume affordance below — the component calls the existing `GET /api/v1/teams/:teamId/sessions/:sessionId/facilitator-state` endpoint (shipped by `enforce-access-control-on-team-content` / `session-lifecycle-transitions`), which already enforces `facilitator_id === caller` server-side on every call and already returns `currentSessionState`. The component renders the draft control view when that status is `draft`, and the live participant-readiness view otherwise — one shared component invoked two ways (initial render from the `POST /draft` response, or rehydration from this endpoint), not two components that can drift, per engineering review's note. No new backend endpoint is needed for this: the authorization and the data this route needs already exist.

This also resolves "resume a draft the facilitator navigated away from" without a second mechanism: D3's `409` response already carries `existingSessionId`, `existingSessionStatus`, and `teamId` for a caller who has already passed the membership check for that exact team; the confirm screen's `409` handling (task 7.4) offers "go to your existing session," navigating to this same route. One route serves both of engineering review's proposed options — a real URL, and a resume path surfaced from the `409` — rather than building two separate mechanisms for what is really one gap.

**Deliberately not built on the existing `/session/:sessionId/facilitator` route.** That route is reserved for the future OR-4.4 live participant-connection grid (`FacilitatorConnectionHost`, currently a hardcoded stub) and carries its own documented, deliberately-deferred gap: no client-side facilitator-only check yet, safe today only because it renders no real data. Wiring this change's control view into that route would both drag a live, previously out-of-scope authorization gap into this change, and conflate two distinct pieces of functionality — a facilitator's pre-room review-and-open control, versus a not-yet-built live connection-status grid — under one URL. A dedicated route keeps that boundary clean; the two can converge later, deliberately, once OR-4.4 exists and that's the right call to make.

**Opening the room is a one-way transition — Priya's open question, resolved.** Activating "Open the room" calls the existing `POST /advance`. No session-lifecycle transition anywhere in this codebase moves backward (`draft → lobby → pre_session → active → wrap_up → complete`/`abandoned` is strictly forward), so this is not reversible once it succeeds. Given that, and given how much "opening a room to a full team" commits to, the button is preceded by a lightweight inline confirmation — not a new flow, not a modal round-trip to the server — before the request fires. On success, the same view re-renders in place as the live participant-readiness view — no second navigation. On failure, the view stays exactly as it was (the draft session is untouched by a failed advance), with an inline error and the same retryable button.

**Deferred, with rationale: abandoning a wrongly-picked draft — Priya's second open question.** Not addressed by this change. `session_status` already defines `abandoned` as a terminal state (see D3), and no code path anywhere transitions a session to it today. A "discard this draft" action means a new state-mutating endpoint (`draft → abandoned`) with its own authorization check, its own audit event, and its own interaction with D3's unique index (an abandoned draft must free the team up for a new one) — that's new scope, not a documentation gap, and doesn't belong in a change whose stated non-goals already exclude picker personalization and trend/history. Logged as a follow-on. In the meantime, Priya's own observation holds: a facilitator who picked the wrong team simply doesn't open the room and doesn't return to that draft — sufficient for the window this change ships in.

**Forward-compatible with the trend/history capability.** Priya's sign-off condition is that when a trend/history capability is eventually built, it attaches to this same control view rather than one she has to navigate to separately. The dedicated route introduced here is the right home for that: it's already the facilitator's own view of one specific session, scoped by `teamId` and `sessionId`, with room to grow.

## Risks / Trade-offs

- **[Risk]** The partial unique index migration will fail outright if any team in production already has two non-terminal sessions (a state today's missing enforcement could theoretically have allowed). → **Mitigation:** the migration file itself contains a self-enforcing `DO $$ ... RAISE EXCEPTION` guard (see D3) that fails the migration transaction closed if it finds a violation — not a manual runbook step an operator has to remember to run first. If it fires, violations are resolved (oldest session moved to a terminal status by an operator) and the migration is re-run.
- **[Risk]** Catching unique-violation errors too broadly could misreport an unrelated constraint failure as "a session already exists for this team." → **Mitigation:** match on `err.code === '23505' && err.constraint === 'sessions_team_active_unique'` (the concrete node-postgres `DatabaseError` fields, not a message-substring match) before translating to the `409` response; re-throw anything else. A dedicated test forces a `23505` on a different constraint, and a non-`23505` error, through this path and asserts both propagate as a 500, not a false-positive `409`.
- **[Risk]** Adding a second field (`callerHasTeamMemberships`) to a new endpoint's response is easy to under-specify at implementation time and drift from the two documented empty-state copies. → **Mitigation:** named explicitly as a requirement with scenarios in the `session-creation` spec, not left as a design note.
- **[Trade-off]** Landing in `draft` rather than auto-advancing to `lobby` means an extra click for every session creation, including the common case where the facilitator has nothing to review. → Accepted: this was Priya's explicit trade-off, made deliberately to preserve the ADR-007 review window. **Resolved:** Priya signed off on this decision during her D6 walkthrough (APPROVE WITH SUGGESTIONS, non-blocking); her two follow-up questions are addressed directly in D6 (opening the room's irreversibility, resolved; abandoning a wrongly-picked draft, deferred with rationale).
- **[Trade-off]** Neither `POST /draft` nor `GET /eligible-for-session` has a stated rate limit, despite security review noting that `TEAM-006` — a comparably-scoped cross-team-privilege action (establishing a manager/team relationship) — shipped with one. → Accepted as a follow-on, not designed here: `TEAM-006`'s rate limiting was itself a separate, explicitly signed-off decision (the Q6 decision, `openspec/changes/archive/2026-07-07-establish-manager-team-relationship/q6-rate-limit-decision.md`) with its own sliding-window burst/daily/global design and its own audit events, shipped after the base feature rather than speculatively alongside it. The actor population and risk profile here (any `global_role = 'facilitator'` account, an internal, low-volume set) is comparable enough that the same path — a deliberate, separately-scoped follow-on, informed by this feature's real traffic pattern once it's live — is the right one, not a rate limit designed against a population that doesn't exist yet.

## Migration Plan

1. Ship the `sessions_team_active_unique` migration. The pre-check described above runs as part of the migration file itself (the `DO $$ ... RAISE EXCEPTION` guard) — not as a separate manual step — so the migration fails closed on its own if it finds a violation.
2. Ship the `POST /draft` membership check, its audit logging (both the denial and success paths — see D1), and its tests. This is independently deployable and independently valuable — it closes the enforcement gap, with an audit trail, even before the picker UI exists.
3. Ship the `GET /eligible-for-session` endpoint and its tests.
4. Ship the `/auth/session` `canFacilitateSessions` field and the `AuthenticatedLanding` carve-out.
5. Ship the frontend picker → confirm → draft-control-view flow (including the `/team/:teamId/session/:sessionId` route from D6), wired to 1–4.
6. No rollback complexity beyond standard migration/deploy reversal: the unique index can be dropped independently of the application-code changes if it needs to be backed out, since the app-level `409` handling degrades to "insert fails uncaught" (a 500) rather than silently permitting duplicates — acceptable as a temporary rollback state, not as a shipped one.

## Open Questions

- Exact route path for the picker (`/sessions/new` or similar) — no strong opinion; whoever owns routing conventions should pick at implementation time. (This is distinct from the draft-control-view route, which D6 now fixes explicitly at `/team/:teamId/session/:sessionId`.)
- Whether the confirm screen's "enough team context to be a real check" (D2) needs more than `lastSessionAt` is a UI-detail decision for implementation, not resolved here.
