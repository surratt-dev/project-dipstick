## Why

Issue #24 was written as a gate: "Real-time layer implementation cannot begin until this document is approved" (`todo.md` lines 23–43; restated in `requirements/design/REST API Contract.md` Appendix D, lines 2958–2968, and closed as Discrepancy 7 in `requirements/design/REST API Contract - Validation Report.md`, line 141, on the promise that a dedicated WebSocket Specification document would exist first). The gate didn't hold. Five other changes — `websocket-session-authorization` (archived as `2026-09-07-websocket-delivery-time-authorization`), `websocket-connection-reauthorization`, `websocket-staleness-signal`, `vote-compose-recovery`, and `session-lifecycle-transitions` (which also produced the `session-topic-lifecycle` capability spec) — each built one slice of the real-time layer against scattered proposal/design docs, and it shipped, tested, into production. No one document ever held the full picture up against the BRD at once.

That reconciliation, done now, surfaces a live compliance gap: FR-4.6.1 (`[HARD]`) requires the reveal event to carry a server-generated timestamp so clients can measure and log delivery latency against the 15-second simultaneity SLA. It does not exist anywhere in the shipped payload (`packages/shared/src/types/realtime.ts`, `packages/backend/src/realtime/vote-revealed-payload.ts`) — traced by file and function, not asserted. The reveal is the one mechanic the whole Health Check ritual depends on being simultaneous and honest, and right now nobody is measuring whether it actually is in production. I'm not willing to write a spec that describes that payload as compliant when it isn't, and I'm not willing to let it sit open indefinitely once named — this change closes it rather than filing it away.

This is also the moment to fix the vocabulary. The issue text, `todo.md`, and Appendix D all still use dot-notation event names (`reveal.trigger`, `vote.submit`, `vote.locked`, `session.revealed`, `topic.advance`/`topic.advanced`) that do not match what shipped. A spec written by copying that table would be wrong about roughly half its own content on day one, and wrong in a way that contradicts already-tested production code. That correction has to happen once, consolidated, and it has to happen here.

## What Changes

- Add a new capability spec, `websocket-specification`, that is the connective document issue #24 was always supposed to produce: one place with the full event catalog (corrected names, matching shipped code), the connection lifecycle end to end, envelope/wire-frame shapes, and error/close-code handling — assembled from and pointing into the five existing specs rather than re-deriving their mechanics.
- **Close the FR-4.6.1 gap now, in this change** (not deferred): add a `serverTimestamp` field (ISO 8601, UTC) to the `vote_revealed` wire frame, captured once per reveal at publish time (before the event is published to Redis, so every pod's dispatch reads and forwards the same value — corrected on Design-stage review, since dispatch-time capture would produce a different value per backend pod), and specify the client-side computation the BRD requires (`observed_latency = received_at − serverTimestamp`, logged and surfaced to monitoring). This is a small, scoped type/endpoint/dispatcher change (`packages/shared/src/types/realtime.ts`, `packages/backend/src/routes/facilitator-sessions.ts`, `packages/backend/src/realtime/ws-event-dispatcher.ts`), not a redesign — implementing it here is the difference between this spec documenting a HARD requirement as true versus documenting it as aspirational.
- State five named, traceable ritual-integrity invariants directly in the new spec body (no pre-reveal vote-value leak; simultaneity is measured, not assumed, with the computation and destination defined; reconnection creates no side door; the facilitator's elevated visibility cannot see vote values pre-reveal; nothing in this catalog is configurable), each citing the FR or existing mechanism it rests on, so any reader — not just the person who wrote this — can verify them against the catalog.
- Document `participant.joined`/`participant.left` (FR-2.5, `[PREF]`) and live `actionitem.updated` for pre-finalization status changes (FR-3.3, `[PREF]`) as normative future-state catalog entries, each marked **NOT IMPLEMENTED** and tracked in issue #91. **Spec-and-defer, not build**: pulling either in now would mean designing authorization, delivery, and reconnection-safety behavior for two net-new events inside what is otherwise a documentation-and-reconciliation change, re-creating the exact "spec catches up to code built under pressure" failure this change exists to fix.
- Add the facilitator/participant-experience requirements the wire-protocol view alone was missing: connection-health state must reach the facilitator's readiness grid as a signal distinct from vote-readiness (not collapsible into "still voting"); each of the three recovery mechanisms (staleness signal, idle re-auth/token refresh, vote-compose-recovery) gets a stated visible-behavior answer, citing the existing treatment where one already exists rather than re-deriving it; and connection/error handling carries the same non-spotlight principle OR-2.4 already establishes for outlier flagging.
- Append one consolidated, dated correction note to `requirements/design/REST API Contract.md` Appendix D (matching the format of the existing `session-lifecycle-transitions` correction at line 2947) covering all of `reveal.trigger`, `vote.submit`, `vote.locked`, `session.revealed`, `topic.advance`/`topic.advanced`, `participant.joined`/`left`, and `actionitem.created`/`updated` in one place, and check off `todo.md`'s "WebSocket Specification" item with a pointer to the new spec.
- Cross-check the new catalog's "does not cover" boundary against the stated non-goals of all five source specs for contradiction, as an owned task with a named outcome — not a caveat carried forward unresolved.

## Capabilities

### New Capabilities
- `websocket-specification`: the full WebSocket message catalog (corrected event names matching shipped code), connection lifecycle (auth handshake → registration → delivery → close), envelope and wire-frame shapes, error/close-code handling, the FR-4.6.1 `serverTimestamp` requirement and its client-side latency computation, the five ritual-integrity invariants, the two deferred future-state events, and the facilitator/participant visible-behavior requirements for connection health and recovery. Delegates authorization mechanics, idle re-auth/token refresh, client connection-health rendering, and vote draft persistence to the four specialist specs that already own them; delegates session/topic phase transitions to `session-topic-lifecycle`.

### Modified Capabilities
- None. `websocket-session-authorization`, `websocket-connection-reauthorization`, `websocket-staleness-signal`, `vote-compose-recovery`, and `session-topic-lifecycle` are all cited and delegated to, not altered — this change adds one field to a wire frame those specs don't define (`vote_revealed`'s payload shape is explicitly out of scope for `websocket-session-authorization`, which covers its authorization gating only) and does not change any existing requirement's behavior.

## Impact

- **Code**: `packages/shared/src/types/realtime.ts` (`serverTimestamp` on `VoteRevealedTriggerPayload` and on the `vote_revealed` `WsClientMessage` variant), `packages/backend/src/routes/facilitator-sessions.ts` (the reveal endpoint stamps `serverTimestamp` once, at publish time, after commit), `packages/backend/src/realtime/ws-event-dispatcher.ts` (`dispatchVoteRevealed` reads and forwards that value from the envelope — it does not generate its own), corresponding backend/frontend tests for the new field (including a cross-pod case) and the client-side latency computation.
- **Documentation**: new `openspec/specs/websocket-specification/spec.md`; one consolidated correction note appended to `requirements/design/REST API Contract.md` Appendix D; `todo.md`'s "WebSocket Specification" item checked off with a pointer to the new spec.
- **No API break**: `serverTimestamp` is an additive field on an existing event payload; no existing consumer reads or depends on its absence.
- **Scope boundary carried forward from exploration**: this change does not touch authorization mechanics, idle re-auth/token refresh, client connection-health rendering, vote draft persistence, or session/topic phase-transition logic — all five are cited by reference, not re-opened. It does not build `participant.joined`/`left` or live `actionitem.updated` — both are spec-and-defer. It does not decide whether an SLA violation ever becomes facilitator- or session-history-visible (carried forward as an explicit open question for design.md, addressed to the BA and facilitator SME jointly — a new product decision, not a reading of FR-4.6.1's existing text).
