- Deciding whether an FR-4.6.1 SLA violation ever becomes visible to the facilitator or the session record. FR-4.6.1's text commits only to a monitoring obligation ("surfaced in system monitoring"); a facilitator- or session-history-visible consequence is a new product decision, not a reading of the existing requirement. Carried forward as an open question below.
- Changing the no-manager-participation rule, the facilitator-from-another-team requirement, or any other ritual constraint that lives outside the WebSocket layer entirely. Nothing in this change touches them, and nothing here should be read as reopening them.

### D2 — `serverTimestamp` is captured once per reveal, at publish time, and forwarded unchanged by every pod

FR-4.6.1 requires the reveal payload to carry "a server-side timestamp" clients use to compute `observed_latency = received_at − serverTimestamp`. This value must be identical for every recipient of one reveal — including recipients connected to different backend pods, since `connection-registry.ts` is explicit that its registry is per-pod, not shared, and `websocket-session-authorization`'s own spec names multi-pod fan-out as a normative, in-scope scenario for exactly this event ("the facilitator triggers the reveal for topic T in session S with multiple connected participants distributed across more than one backend pod").

**Corrected per Design-stage review (Marcus Oyelaran):** an earlier draft of this decision captured the timestamp inside `dispatchVoteRevealed` (`packages/backend/src/realtime/ws-event-dispatcher.ts`), once per invocation of that function, before its `Promise.all` fan-out. That is wrong in this codebase's actual topology: `dispatchVoteRevealed` runs once **per pod**, independently, each time that pod's own Redis subscriber receives the `vote_revealed` envelope. Capturing `new Date().toISOString()` there gives every *local* recipient on one pod an identical value, but each pod computes its *own* value, independently, at whatever moment its own subscriber's message handler happens to fire — which differs across pods by Redis pub/sub fan-out and event-loop scheduling variance. In today's single-pod dev deployment that difference is invisible; in the multi-pod topology this architecture is built for, it directly violates this same requirement's "every recipient receives an identical serverTimestamp" guarantee, and no test in the existing suite (`ws-event-dispatcher.test.ts`, `reveal-timing-independence.test.ts`) can catch it, because every existing `vote_revealed` test constructs exactly one `ConnectionRegistry` and calls `handleIncomingMessage` once — i.e., it can only ever model a single pod.

**Corrected design:** the timestamp is captured exactly once, at publish time — before the envelope is published to Redis at all — not at dispatch time. Concretely:
- `VoteRevealedTriggerPayload` (`packages/shared/src/types/realtime.ts`, the internal Redis envelope payload) gains a `serverTimestamp: string` field.
- The reveal endpoint (`packages/backend/src/routes/facilitator-sessions.ts`, `POST .../reveal`) stamps `serverTimestamp` once, after its transaction commits, when it calls `publishVoteRevealed` — the same publish-after-commit call site this change already touches.
- Every pod's `dispatchVoteRevealed` reads `envelope.payload.serverTimestamp` off the single published envelope and forwards that one value, unmodified, into every local recipient's `vote_revealed` `WsClientMessage`. It no longer generates a fresh timestamp itself.

Because the envelope is published exactly once to a single Redis channel and every pod's subscriber receives that same serialized message, every pod reads the identical `serverTimestamp` string regardless of which pod a given recipient is connected to or when that pod's subscriber happens to fire. This is the property the earlier draft assumed dispatch-time capture would have and that only publish-time capture actually guarantees.

**This is still the load-bearing choice the original decision was reaching for**: if each recipient's timestamp were captured independently per-connection (the alternative Decision D2 has always rejected), two recipients' `serverTimestamp` values would differ by however long authorization evaluation and serialization take for the connections ahead of them — which would make the client-computed `observed_latency` partly measure the server's own fan-out order rather than purely network delivery time. Moving capture to publish time doesn't change that reasoning; it fixes the one place the original wording under-delivered on it.

Field placement on the wire frame is unchanged from the original decision: `serverTimestamp` lives on the `WsClientMessage` variant for `eventType: "vote_revealed"`, not on `ParticipantContentView`/`FacilitatorContentView` (`packages/shared/src/types/team-content-views.ts`). Those types are shared with the HTTP session-history endpoints, which have no delivery-latency concept — adding `serverTimestamp` there would leak a WebSocket-specific field into an HTTP response shape for no reason. The wire frame, not the content view, is where a delivery timestamp belongs; it is simply sourced from the envelope now, rather than generated fresh at the point that constructs the wire frame.

```ts
// packages/shared/src/types/realtime.ts — VoteRevealedTriggerPayload (Redis envelope, publish-time source of truth)
export interface VoteRevealedTriggerPayload {
  sessionId: string;
  sessionStatus: SessionStatus;
  serverTimestamp: string; // ISO 8601 UTC, stamped once by the reveal endpoint before publish
}

// packages/shared/src/types/realtime.ts — WsClientMessage, vote_revealed variant (per-client wire frame)
| { eventType: "vote_revealed"; payload: VoteRevealedPayload; serverTimestamp: string } // forwarded from envelope.payload.serverTimestamp, never regenerated
```

Client obligation (frontend, cited as a requirement, implemented as part of this change's task list): on receipt, compute `observed_latency_ms = Date.now() - Date.parse(serverTimestamp)`, log it, and surface it to whatever the project's existing monitoring/logging pipeline is (no new monitoring infrastructure is introduced by this change — it uses what already exists for other client-side logging). **Per Security review (Tomás Ferreira):** because this metric is necessarily tagged with `sessionId` to be useful at all, it is session-timing metadata, not vote content — but a metrics pipeline can have broader read-access than application logs, so this SHALL route to a monitoring destination access-controlled at least as tightly as the application's other session-tagged operational logs (e.g., the `session.access_revoked_live`-class audit surface below), confirmed at implementation review rather than assumed.

**Alternatives considered:**
- *Use the existing `revealedAt` field from `team-content-access.ts`.* Rejected — that field lives exclusively in the `already_revealed` error-state response, is not part of the `vote_revealed` event payload, and was never documented anywhere as satisfying FR-4.6.1. Reusing it would mean quietly redefining an existing field's contract rather than adding the one FR-4.6.1 actually asks for.
- *Capture the timestamp at dispatch time, inside `dispatchVoteRevealed`, before its `Promise.all`.* This was the original text of this decision. Rejected on Design-stage review (Marcus Oyelaran) — it rests on the premise that "publish and dispatch happen in the same process today, no cross-pod fan-out delay between them," which is false against this codebase's own per-pod connection registry and against `websocket-session-authorization`'s explicit multi-pod scope for this exact event. Dispatch-time capture only produces an identical value within one pod's local candidates, not across pods.
- *Defer implementation, spec the requirement only (Open Question 1, Option B from `explore-review-ba.md`).* Rejected per Devon's and Marcus's shared position: this is a small, low-risk addition to an already-identified call site, and documenting a HARD requirement as "not yet true, tracked elsewhere" is the paper-compliance failure mode this change exists to prevent.

### D3 — Connection lifecycle is narrated once, assembled from three already-shipped mechanisms

The new spec's lifecycle section is: **connection-time check** (HTTP-layer auth/origin validation before the WebSocket upgrade completes — `websocket-session-authorization`) → **registration** (`evaluateSessionSubscriberAccess`/`evaluateTeamAccess` grant evaluation; on success, a session-scoped connection receives `session_registration_snapshot` — `vote-compose-recovery` Decision D3a) → **delivery-time authorization** (the mandatory, non-substitutable check `websocket-session-authorization` requires on every content-access event) → **periodic re-authorization** (the ≤5-minute sweep, `websocket-connection-reauthorization`) → **silent token refresh** (SEC-26, transparent up to the 90-minute absolute connection lifetime) → **close** (either the disclosure-blind `STALE_SIGNAL_CLOSE_CODE` = 4000, or the disclosed `REAUTH_GRACE_EXPIRED_CLOSE_CODE` = 4001 following an in-band `reauth_required` message).

This is prose plus one sequence diagram-equivalent table, not new mechanics. Every step cites the spec that owns it; this document adds no new authorization logic and changes no existing check's behavior or ordering.

**Alternative considered:** omit the lifecycle section entirely, since all five steps are individually documented elsewhere. Rejected — this is exactly the "connective document" job Finding 3 identifies: a reader today has to open five spec files to reconstruct the sequence, and nothing states that connection-time and delivery-time checks are both mandatory rather than either/or (a distinction `websocket-session-authorization` states as its own second requirement, worth restating at the catalog level where a new reader is more likely to look first).

**Audit-log surface, alongside the close-code table (per Security review, Tomás Ferreira):** three events in this lifecycle are recorded as `audit_log` rows, not merely structured logs, because each is security-relevant in its own right (all owned and defined by `websocket-connection-reauthorization`, not redefined here):

| Lifecycle event | `audit_log` row | Why it's audited, not just logged |
|---|---|---|
| Periodic re-authorization sweep finds a revoked grant | `session.access_revoked_live` | A live connection's access being cut mid-session is security-relevant in its own right |
| Silent token refresh exhausts its retry budget or receives a definitive revocation response | `session.token_refresh_failed_live` | Records the failure type (no token values) that triggers the `reauth_required` grace period |
| A connection reconnects and recovers session state | `session.connection_recovered` | Generic, facilitator-visible reconnect signal in session history |

A reader relying solely on this connective document, without opening `websocket-connection-reauthorization` directly, should still know these three audit rows exist; the table above is that pointer, not a redefinition of any of the three.

### D4 — Ritual-integrity invariants are catalog-level statements, each traced to an FR or existing mechanism

Per Marcus's review, the exploration's five-item personal checklist becomes five statements in the spec body itself:

1. **No pre-reveal vote-value leak, anywhere in the catalog** (FR-4.6, FR-4.7) — checkable against every event in the D1 table in one pass, citing `vote_readiness_update`'s structural exclusion and `vote_revealed`'s per-topic `reveal_status` gate (both already required by `websocket-session-authorization`).
2. **Simultaneity is measured, not assumed** (FR-4.6.1) — defined per Decision D2 above: computation is `received_at − serverTimestamp`, destination is client-side log plus system monitoring, and facilitator/session-record visibility of a violation is explicitly out of scope pending the open question below. **Named gap, with an owner and an archiving gate (per Security review, Tomás Ferreira):** `websocket-session-authorization` states a second, complementary, server-side measurement requirement — "Cross-recipient delivery skew is bounded for simultaneous fan-out events" — covering the delta between first- and last-delivered timestamps for the same `vote_revealed` fan-out, checked against a documented budget. That measurement (Group 6, tasks 6.1–6.7, of the archived `2026-09-07-websocket-delivery-time-authorization` change) was never performed and is marked DEFERRED; no budget has ever been set. This is the client-side/server-side counterpart to the `observed_latency` computation this change adds, not a duplicate of it, and *performing* the measurement itself is out of this change's scope — it requires a live deployment with realistic concurrent-session load, which is real engineering work, not a documentation correction. What this change does own, per Security review: this gap gets the same accountability structure tasks.md 5.3/6.4 already give the two `[PREF]` events, not a naming paragraph alone — a `SHALL`-level requirement on a shipped capability, tied to this application's core ritual-integrity guarantee, should not carry a *weaker* accountability structure than a documentation gap on two non-binding `[PREF]` events. **Owner: Marcus Oyelaran (FSE).** Tracked in issue #92, citing the archived change by name rather than a generic "measure performance" issue (tasks.md 5.4/6.5). **Mitigating factor, not a substitute control:** this change's own FR-4.6.1 fix gives the system a partial, indirect detection capability it didn't have before. Client-side `observed_latency` is logged per-recipient against the 15-second SLA; it doesn't measure cross-recipient skew directly, but if skew were large in practice it would very likely show up as increased *variance* in `observed_latency` across recipients of the same reveal, in the monitoring data this change already produces. That is not a substitute for the formal measurement-against-a-budget the sibling spec requires — no budget exists to check variance against — but the gap does not run completely blind between now and whenever the owned follow-up lands.
3. **Reconnection creates no side door** (FR-4.6, FR-4.7) — "no reconnection payload includes another participant's vote or lock-in status before reveal," citing `session_registration_snapshot`'s self-disclosure-only design (`vote-compose-recovery` spec.md: the snapshot's `hasLockedInVote` reflects only the connecting participant's own status).
4. **The facilitator's elevated visibility cannot see vote values pre-reveal** (FR-4.6, FR-4.7) — citing `VoteReadinessUpdatePayload`'s structural exclusion of vote value (`websocket-session-authorization` spec.md, "WebSocket content-access events do not include vote values before reveal").
5. **Nothing in this catalog is configurable** — carried as review guidance for whoever reviews this spec at design/implementation time, not as an acceptance condition, since nothing currently proposed introduces an SLA toggle or similar.

### D5 — Facilitator/participant experience requirements (Priya's review, four of five taken on fully)

- **Connection health reaches the facilitator's readiness grid as a distinct signal.** `websocket-staleness-signal` already builds a cause-blind client-side state machine and a facilitator-only grid marker (`connectionHealth.ts`, consumed identically by `ConnectionStatusBanner.tsx` and `FacilitatorReadinessGrid.tsx`). This document states, as a cross-cutting requirement, that the facilitator's readiness grid must render that state machine's output as a third signal distinct from "voted"/"not yet voted" — not left as a private rendering decision for whichever component happens to read it. No new mechanism; a stated consumption requirement on top of the existing one.
- **Each recovery mechanism gets a stated visible-behavior answer:**
  - Staleness signal: cites `websocket-staleness-signal`'s existing rendered treatment (participant banner + facilitator grid marker); states it reads as informational, not alarming.
  - Idle re-auth/token refresh: states plainly that successful silent refresh produces no visible state change (by design), and that the forced-reauth path is visible by necessity, using the existing `reauth-required` state and its generic rendered treatment (`websocket-connection-reauthorization`/`websocket-staleness-signal`) rather than implying either path is invisible.
  - Vote-compose-recovery: states that a restored draft reappears without requiring the participant to notice or re-enter it, citing `vote-compose-recovery`'s Requirement "Restore-or-discard resolves before the compose control's first paint, with no visible or facilitator-visible trace."
- **Non-spotlight principle for connection/error states.** Extends OR-2.4's existing outlier-flagging principle ("communicate the observation without visual treatment that prescribes a specific facilitation response or amplifies discomfort for the flagged participant") to connection and error UX generally: recoverable and low-drama by default, informative rather than performative. Stated as a principle at the catalog level; does not change any of the three specialist specs' actual close-code or rendering behavior, all of which already reads as appropriately quiet.
- **First-session UX acknowledgment.** One-line note: connection/error UX during a team's first session is not being re-litigated by this change; if it needs dedicated attention, that's a future onboarding-experience change.
- **Not resolved here (Priya's fifth ask):** whether an SLA violation ever reaches the facilitator or session record. Carried forward as an explicit open question, addressed jointly to the BA and facilitator SME — see Open Questions below.

`session-lifecycle-transitions` already established the pattern: a dated, attributed correction note appended inline to Appendix D (line 2947) and to SESSION-005 (line 1270), reviewed by Marcus for accuracy, with no new BA Validation Report cycle. ## Risks / Trade-offs

- **[Risk]** Adding `serverTimestamp` to a production wire frame, even additively, touches a code path five other changes depend on being stable. → **Mitigation**: the field is additive only (no existing field removed or renamed), captured at a single well-understood call site (the reveal endpoint's publish-after-commit call to `publishVoteRevealed`, per the corrected Decision D2) and forwarded, never regenerated, by `dispatchVoteRevealed`. Covered by the existing `reveal-timing-independence.test.ts` and `ws-event-dispatcher.test.ts` suites plus new tests asserting all recipients of one reveal receive an identical `serverTimestamp` value — including a test that models cross-pod fan-out by constructing two independent `ConnectionRegistry` instances against the same published envelope, per Marcus Oyelaran's finding that the existing single-registry test shape cannot detect a dispatch-time regression. **Process note (per Executive review, Rachel Okonkwo):** this code change goes through the same design-review (Full Stack Engineer + Security Analyst) and implementation-review gates as any standalone code change in this pipeline — it is not exempted or lightened because it is riding inside a change whose title and primary deliverable are documentation.
- **[Risk]** Marking `participant.joined`/`left` and live `actionitem.updated` as spec-and-defer risks the gap being forgotten. → **Mitigation**: both are stated explicitly as NOT IMPLEMENTED and tracked in issue #91 rather than silence — the same visibility Devon insisted on for the `serverTimestamp` finding, applied here in the opposite direction (naming an unowned gap rather than closing it, because these are `[PREF]` and out of this change's scope).
- **[Risk]** The cross-check of non-goal boundaries against all five prior specs (owned task, see tasks.md) could surface a real contradiction late, after this design is written. → **Mitigation**: the task is scheduled before the spec is finalized, not after; if a contradiction surfaces, it is resolved in the spec draft, not patched in as a follow-up correction to a second document.
- **[Trade-off]** This document deliberately does not decide the facilitator/session-history visibility of an SLA violation (Priya's fifth ask), even though answering it now would make the spec more complete. → Accepted per Devon's position: deciding it here would be scope creep past FR-4.6.1's actual text, performed unilaterally by the person who would otherwise object to exactly that pattern in someone else's constraint.

## Migration Plan

No data migration. Deployment sequencing:
1. Ship the `serverTimestamp` field first (backend-only; additive field on `VoteRevealedTriggerPayload` and `WsClientMessage`, no consumer depends on its absence): the reveal endpoint stamps it once at publish time, and every pod's `dispatchVoteRevealed` reads-and-forwards it from the envelope rather than generating a fresh value.
2. Ship the frontend client-side latency computation and logging.
3. Publish the spec document and the Appendix D / todo.md corrections (no code dependency; can land independently, but should land in the same change so the spec doesn't describe a `serverTimestamp` that doesn't exist yet).

No rollback concerns beyond a normal revert — the field is additive and no existing behavior changes.
