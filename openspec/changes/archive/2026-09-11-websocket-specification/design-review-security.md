# Security Review — `websocket-specification` design.md

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope reviewed:** `openspec/changes/websocket-specification/design.md`, `proposal.md`, `specs/websocket-specification/spec.md`, cross-checked against the five source specs (`websocket-session-authorization`, `websocket-connection-reauthorization`, `websocket-staleness-signal` — purpose/scope only, not re-read line by line since it carries no authz content — `vote-compose-recovery`, `session-topic-lifecycle`) and the shipped code (`ws-event-dispatcher.ts`, `ws-close-codes.ts`, `connection-token-refresh.ts`, `connection-reauthorization.ts`).

**Verdict: Approve, with one required change before archiving and one finding that needs a stronger commitment than currently written.**

---

## 1. Does `serverTimestamp` create a new information-disclosure surface?

**No new surface. This is the correct design, and I want to say explicitly why, because the alternative the design rejected (per-recipient capture) would have been a real, if minor, finding.**

- **Audience is unchanged.** `serverTimestamp` rides on `vote_revealed`, delivered only to subscribers who already pass `evaluateSessionSubscriberAccess` and already receive the full revealed vote distribution. Nothing about this field expands who receives data — it adds one field to a payload that only ever reaches the already-authorized recipient set. There is no scenario where a party who couldn't see vote values now can see something new.
- **Content is low-value even to an authorized recipient.** It is a single UTC dispatch-decision timestamp, identical across the whole fan-out. It tells an authorized participant "the server decided to reveal at time T" — information that participant could already infer approximately from their own message-arrival clock. It adds precision, not a new category of fact.
- **The shared-value design is a genuine defense-in-depth win, not just a measurement-accuracy one.** Decision D2's rejected alternative — capturing the timestamp per-recipient, inside the per-connection callback — would have leaked a timing side channel: two recipients' timestamps would differ by however long *their own* authorization evaluation and payload serialization took relative to others in the same `Promise.all`. That's a subtle thing to hand an authorized-but-adversarial client: a way to infer something about the server's internal per-connection processing order and relative latency, which in a system with role-dependent serialization cost (`serializeForFacilitator` vs. `serializeForMemberParticipant`) could in principle be probed. Capturing once, before fan-out, closes that off entirely — verified against `ws-event-dispatcher.ts:194-216`, where the current (pre-fix) code already computes `buildVoteRevealedPayload` per-recipient inside the `Promise.all`; the fix must land the timestamp capture *outside* that block, exactly as D2 specifies. I flag this only so the implementation review holds the line on placement — get this wrong and the shared-timestamp property becomes a per-recipient one silently, in a two-line refactor mistake.
- **One item worth a one-line confirmation, not a blocker:** the design states the client "logs it, and surfaces it to whatever the project's existing monitoring/logging pipeline is." A per-reveal latency metric tagged with `sessionId` (needed to make the metric useful at all) is session-timing metadata — it tells anyone with access to that monitoring surface that Team X's session was active at time T, at a granularity independent of session-content access. If the monitoring pipeline's access is broader than the set of people authorized to know a given team is in session (e.g., SRE/on-call with dashboard access but no team membership), that's a mild data-classification question, not a vulnerability — this is schedule metadata, not vote content, and every other WebSocket mechanism in this catalog already logs structured events with `sessionId`/`teamId` to the same operational log surface (`session.access_revoked_live`, `session.token_refresh_failed_live`, audit rows generally). I'm noting it for completeness because it's a new *metric*, not a new *log line*, and metrics pipelines sometimes have broader read-access than application logs. Not a finding; confirm during implementation that the latency metric goes to the same access-controlled destination as everything else, and move on.

**Conclusion on this question: closed correctly.** The design's own alternatives-considered section did the security reasoning I would otherwise have had to demand — that is exactly what I want to see happening at design time rather than caught in implementation review.

## 2. Is documenting-but-not-fixing the DEFERRED cross-recipient skew requirement acceptable, or does it need stronger escalation?

**It needs a firmer commitment than the current text gives it. This is the review's one required change.**

First, the security characterization: the undelivered requirement — "cross-recipient delivery skew is bounded for simultaneous fan-out events," `websocket-session-authorization`, spec.md lines 165-184 — is **not an authorization or confidentiality control**. No one sees data they're not entitled to if skew is large; every recipient of a `vote_revealed` fan-out is already independently authorization-checked per D1's catalog and per the code I read. What's at risk if skew is large is the **ritual-integrity property** this whole application is built to protect: simultaneous reveal exists specifically so no participant's stated estimate is anchored by seeing another's first. A facilitator or fast-connection participant who reliably received the reveal meaningfully earlier than a slow one is a real degradation of that guarantee, even though it never touches an authorization boundary. This document's own Decision D4 (ritual-integrity invariant #2) correctly identifies it as the "server-side counterpart" to the client-side latency computation this change *does* implement — which is exactly why I don't think the current treatment is calibrated correctly.

Here is the asymmetry I want fixed: this change closes FR-4.6.1 (the client-side half of the simultaneity guarantee) with actual code, in this change, now — correctly, per Devon's and Marcus's stated position that "documenting a HARD requirement as not-yet-true is the paper-compliance failure mode this change exists to prevent." I agree with that position completely; it's the right call. But the **server-side half of the same guarantee** — a `SHALL`-level requirement in an already-shipped, already-archived spec, whose own measurement task (Group 6, tasks 6.1-6.7) was marked DEFERRED with no budget ever set — gets only a paragraph of naming in this document. Compare the actual gates:

- The two `[PREF]` events (`participant.joined`/`left`, live `actionitem.updated`) — genuinely lower-stakes, since neither is even a currently-binding requirement — get: a named owner (Marcus Delgado, tasks.md 5.3), a required GitHub issue number, and an explicit **hard archiving gate** (tasks.md 6.4: "a filed intent to file the issue is not the same completion condition as the issue existing").
- The skew-measurement gap — a `SHALL` requirement on a shipped capability, tied directly to the same ritual-integrity property this change is otherwise treating as important enough to fix in code — gets: a naming paragraph, no owner, no issue number, no archiving gate.

That's backwards from a risk-proportionate standpoint. I'm not asking this change to *perform* the measurement — the design's own reasoning for not doing so is sound (it requires live concurrent-session load that a documentation-and-reconciliation change correctly shouldn't be scope-creeping into). But "documented, unowned, no target" is the same failure mode this change was chartered to stop, applied to a requirement one level up the stack from the one it's fixing. **Required change:** give this the same treatment tasks.md already gives the two PREF events — a named owner, a filed GitHub issue tracking the Group 6 measurement work specifically (not a re-reference to the already-closed `websocket-session-authorization` change), and ideally a stated interim compensating signal (see below) — before this change is archived.

**One mitigating factor worth stating on the record, because it affects how urgently this needs to move, not whether it needs an owner:** this change's own FR-4.6.1 fix gives the system a partial, indirect detection capability it didn't have before. Client-side `observed_latency` is logged per-recipient against the 15-second SLA. It doesn't measure cross-recipient skew directly, but if skew were large in practice, it would very likely show up as increased *variance* in `observed_latency` across recipients of the same reveal in the monitoring data this change already produces. That's not a substitute for the formal measurement-against-a-budget the sibling spec requires — no budget exists to check variance against — but it means the gap isn't running completely blind between now and whenever the owned follow-up lands. I'd like that observation added to the spec's callout of this gap, so a future reader doesn't have to rediscover it: the existing telemetry is a weak, unbudgeted signal, not a replacement control.

## 3. Are the five specs' authorization/authentication boundaries correctly and completely represented, or does summarizing risk dropping a nuance?

I read all five source specs in full (not just the connective document's citations) and cross-checked every authorization-relevant claim in `design.md` and `spec.md` against them, plus the actual dispatcher code. Findings:

**Accurate, and I want to name what's *right* about this, since Section 4's persona guidance says to record validated judgment calls too:**

- The D1 event catalog table matches `ws-event-dispatcher.ts` exactly — all four dispatch functions, the facilitator-only gating on `vote_readiness_update`, the explicit `admin`-path rejection on `topic_history_update` (code comment at line 261 confirms this is a deliberately corrected, reviewed trade-off, not an oversight), and the "payload constructed per-recipient, not taken from envelope" property for `vote_revealed`. No stale claims.
- D3's connection lifecycle sequence (connection-time → registration → delivery-time → periodic sweep → silent refresh → close) is a correct assembly of the three specs' actual requirements. Critically, it preserves the one nuance I would have flagged as *missing* if it weren't there: `websocket-session-authorization`'s explicit statement that connection-time and subscription-time checks are "necessary but not sufficient" and delivery-time is the only check that satisfies the revocation requirement. The connective document restates this rather than flattening it into "auth happens at connect time." That distinction is the one most likely to get silently lost in a summarization pass, and it didn't.
- The two close codes (`STALE_SIGNAL_CLOSE_CODE` = 4000, disclosure-blind; `REAUTH_GRACE_EXPIRED_CLOSE_CODE` = 4001, disclosed) are cited correctly by name and by disclosure property, verified against `ws-close-codes.ts` and their actual call sites in `connection-reauthorization.ts` and `connection-token-refresh.ts`. The design doesn't blur the distinction between "this close discloses nothing" and "this close is intentionally disclosed because it's a statement about the client's own token" — that distinction is the entire point of `websocket-connection-reauthorization`'s "never conflated" requirement, and it survives the summary intact.
- The `session_registration_snapshot` self-disclosure-only property (invariant #3, reconnection creates no side door) is correctly traced to `vote-compose-recovery`'s actual requirement text and scenario, including the correct nuance that it composes with the existing `evaluateSessionSubscriberAccess` gate rather than performing an independent check.
- The facilitator vote-value exclusion (invariant #4) correctly cites `VoteReadinessUpdatePayload`'s *structural* exclusion — i.e., the field doesn't exist in the type, not merely "isn't populated" — which is the stronger and correct framing per the source spec's own language ("the vote value is never included in this event regardless of the recipient's access level").

**One completeness gap, minor, worth a fix before finalizing (not a blocker on its own, but bundle it with the required change above since both touch the same paragraph):**

- `websocket-connection-reauthorization`'s audit-relevant detail — that a SEC-25 revocation close is separately logged as an `audit_log` row (`session.access_revoked_live`), *in addition to* the existing structured-log emission, specifically because "a live connection's access being cut off mid-session is a security-relevant event in its own right" — is not mentioned anywhere in `design.md` or the current `spec.md` draft. Neither is `session.token_refresh_failed_live` or `session.connection_recovered`. Given that Tomás's own persona concern (and this project's own SEC-13/SEC-14/SEC-25 lineage) treats audit logging as a security control, not an operational nicety, and given that this connective document explicitly aims to be the one place a reader checks the whole picture, I'd expect the audit-log surface for the WebSocket layer to appear somewhere in this catalog — even as a one-line pointer table (event → audit row → source spec), the same treatment the close codes already get. As written, a reader relying solely on this document would not know these three audit rows exist at all. This doesn't change any actual behavior (the audit rows are already implemented and correct per my read of the source spec), so it's a documentation-completeness gap, not a security gap in the running system — but for a document whose entire purpose is "don't make a reader open five files to reconstruct the picture," this is exactly the kind of nuance that's supposed to survive the summary and currently doesn't.

**On the open, unresolved cross-check task itself (tasks.md 1.1-1.3, currently unchecked):** I did the substance of this cross-check myself as part of this review, reading all five specs' non-goals sections against this document's boundary claims, and found no contradiction beyond the audit-logging omission above. I'd still treat tasks.md 1.1-1.3 as a real, not-yet-satisfied gate rather than something my review substitutes for — the task's outcome should be recorded by whoever owns that task, against all five specs by name, per its own stated completion criterion, before this design is treated as finalized.

## Summary of required actions

1. **Required before archiving:** give the `websocket-session-authorization` cross-recipient delivery-skew gap the same accountability structure already applied to the two `[PREF]` events — a named owner, a filed GitHub issue for the deferred Group 6 measurement work, and (recommend) an archiving-gate note comparable to tasks.md 6.4. A "named but unowned" gap on a `SHALL` requirement tied to this application's core ritual-integrity guarantee should not have a weaker accountability structure than a documentation gap on two `[PREF]` events that aren't even binding requirements yet.
2. **Recommended, low-cost, bundle with #1:** add the three WebSocket-layer audit-log events (`session.access_revoked_live`, `session.token_refresh_failed_live`, `session.connection_recovered`) to the spec's catalog, even as a one-line pointer table, so this document's stated job — one place, whole picture — actually covers the audit surface and not just the event/authorization surface.
3. **No action required, confirm only:** verify at implementation review that the `serverTimestamp` capture lands textually outside the `Promise.all` in `dispatchVoteRevealed` (per D2), not merely "before the loop starts" in a way a future edit could accidentally move inward — this is the one place a correct design could regress into the per-recipient timing leak D2 explicitly rejected.
4. **No action required, note for the record:** confirm the client-side latency metric added by this change routes to a monitoring surface with access controls at least as tight as the application's other session-tagged operational logs. Not blocking; a data-classification hygiene check, not a vulnerability.

Everything else in this design — the `serverTimestamp` field itself, the five ritual-integrity invariants, the connection-lifecycle narrative, the close-code disclosure rules, and the decision not to build the two `[PREF]` events inside a docs-scoped change — reflects the shipped system's actual authorization/authentication posture accurately and I have no objection to it.
