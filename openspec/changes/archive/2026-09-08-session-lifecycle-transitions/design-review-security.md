# Security Review: session-lifecycle-transitions

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope:** design.md, proposal.md, tasks.md, and the delta specs for `session-topic-lifecycle` and `team-content-access`. Cross-checked against the already-merged `websocket-delivery-time-authorization` code (`ws-event-dispatcher.ts`, `vote-revealed-payload.ts`, `ws-pubsub.ts`, `session-subscriber-access-helper.ts`) and the current implementation this design modifies (`facilitator-sessions.ts`, `sessions.ts`, `audit-logger.ts`, `2_create_tables.sql`, `8_audit_log.sql`).
**Verdict:** No blocking security defect in the design's authorization or concurrency reasoning. One correctness bug (not itself a security bypass, but worth understanding precisely) and several specification gaps that should be closed before implementation, named below in priority order.

---

## 1. Reveal concurrency (Decision D2) — the conditional `UPDATE` closes the race with the same rigor as a lock, given the isolation level actually in use

I verified the mechanism, not just read the rationale. `db.ts` constructs a plain `pg.Pool` with no `SET default_transaction_isolation` anywhere in the codebase, and `client.query("BEGIN")` is issued bare (no `ISOLATION LEVEL` clause) at every transaction call site I found (`teams.ts:496`, `teams.ts:772`, and every handler in `facilitator-sessions.ts`/`sessions.ts`). That means every one of these transactions runs at Postgres's default, **READ COMMITTED**.

Under READ COMMITTED, `UPDATE ... WHERE status = 'voting'` behaves exactly as Decision D2 claims: Postgres locks each candidate row as it evaluates the `WHERE` clause, and if a second transaction is already holding that row's lock, the second `UPDATE` blocks until the first commits or rolls back, then **re-evaluates its own `WHERE` clause against the just-committed row** (EvalPlanQual) before deciding whether it matches. A second concurrent reveal for the same topic therefore deterministically affects zero rows — there is no TOCTOU window narrower than what a `SELECT ... FOR UPDATE` + separate `UPDATE` would give you. This claim would **not** hold under REPEATABLE READ or SERIALIZABLE (the loser would raise a serialization-failure error instead of cleanly returning `rowCount === 0`, requiring retry-loop handling this design doesn't have) — but since nothing in this codebase sets a stricter isolation level, that's not a gap today. **Flag for the implementer, not a design defect:** if any future change adds a per-transaction isolation override near this code, Decision D2's zero-row-on-loss guarantee needs to be re-verified against it.

Decision D5's `SELECT ... FOR UPDATE` in the lock-in transaction takes a row lock on the same `session_topics` row that the reveal's conditional `UPDATE` takes. `UPDATE` and `SELECT ... FOR UPDATE` lock modes conflict with each other in Postgres (both are exclusive-class row locks), so the two decisions correctly compose: whichever transaction (reveal or lock-in) reaches the row first forces the other to wait and re-evaluate post-commit state. I don't see a narrower window here either.

**One placement detail worth naming to the implementer:** `sessions.ts`'s lock-in handler already runs a non-transactional, non-locking pre-check (`topic_status !== 'voting'` → `422`, lines ~213–221 of the current file) *before* `db.connect()`/`BEGIN`. This is fine as a fast-path optimization, but design.md/tasks.md should say explicitly that this pre-check is **not** the security boundary — the `SELECT ... FOR UPDATE` inside the transaction (task 2.1) is the only check that may be trusted for correctness. As currently worded, tasks.md 2.1/2.2 gets this right, but a future reader skimming only the pre-check code could mistake it for sufficient. Worth a one-line comment at the pre-check site when this is implemented.

## 2. `sessions.current_topic_id`'s foreign key targets `topics(id)`, not `session_topics(id)` — Decision D1 and D4's SQL will not commit as written

This is the most concrete defect I found, and it sits directly under the audit/publish machinery this review was asked to verify, so I'm flagging it here rather than leaving it for the BA/engineer pass alone.

`migrations/2_create_tables.sql`:
```sql
ALTER TABLE sessions ADD CONSTRAINT sessions_current_topic_fk
    FOREIGN KEY (current_topic_id) REFERENCES topics(id);
```
`sessions.current_topic_id` is a foreign key into `topics`, the team's reusable topic catalog — **not** into `session_topics`, the per-session snapshot rows that `session_topics.id` identifies and that Decision D2/D4's `UPDATE session_topics SET status = ... WHERE id = $1` operates on.

Decision D1 (SESSION-005) writes `sessions.current_topic_id = <first topic's id>` in the same sentence it writes `session_topics.status = 'voting' for that first topic`, without distinguishing which "id" — `topics.id` or `session_topics.id` — it means. Decision D4 (SESSION-012) is unambiguous and, as written, wrong:

```sql
UPDATE session_topics SET status = 'voting' WHERE id = $nextTopicId;
UPDATE sessions SET current_topic_id = $nextTopicId WHERE id = $sessionId;
```

Both statements use the same `$nextTopicId` value. The first requires a `session_topics.id`. The second requires a `topics.id` (the FK target). These are two different UUID spaces populated by two different `gen_random_uuid()` defaults in two different tables — a `session_topics.id` will essentially never equal the `topics.id` it was snapshotted from. As written, the second `UPDATE` will raise a foreign-key-violation error on every real invocation (once a session actually has more than one topic to advance through), which the `teams.ts` transaction pattern's `catch` block will correctly `ROLLBACK` and rethrow as a 500.

**Why this belongs in a security review and not just a bug report:** the failure mode is a hard rollback, not a partial commit — so it does not itself produce an authorization bypass, an audit gap, or a premature publish (the whole point of the transaction pattern is that this class of error is safe). But it means, as specified, **SESSION-012 cannot ever successfully commit past the first topic**, which means `recordRevealTriggeredAudit`, `publishTopicHistoryUpdate`, and the `session.topic_advanced` audit write this review was asked to verify would never fire in production for any session with more than one topic — the exact "TODO(#26) is now a real call site" claim tasks.md 3.4/3.5/4.8/4.9 makes would be false for multi-topic sessions until this is fixed. The correct fix is for the design to state explicitly which column supplies which UPDATE — the natural fix is `UPDATE sessions SET current_topic_id = (SELECT topic_id FROM session_topics WHERE id = $nextTopicId) WHERE id = $sessionId`, or to carry both `nextSessionTopicId` and `nextTopicId` (`session_topics.topic_id`) as distinct variables from the task 4.4 lookup query, which already has to join to fetch `topicName`/`topicPrompt`/`voteType` per Decision D4a's "Query cost" note — that same query can trivially also select `topic_id`. This needs a decision update before task 4.5/1.4 are implemented, or an integration test (4.10, 1.6) will catch it immediately, but I'd rather this not be discovered at test time given how directly it blocks the audit/publish wiring this whole change exists to complete.

## 3. Audit logging — correctly wired everywhere I checked, with one completeness gap

`recordRevealTriggeredAudit` (facilitator-sessions.ts:31–63) writes `actor_user_id`, `actor_global_role`, `actor_ip`, `operation = 'session.reveal_triggered'`, `team_id`, and `metadata = { session_id }` — matches the `audit_log` schema (`8_audit_log.sql`), and `target_user_id` is correctly left null (there is no target user for a reveal action; the column is nullable for exactly this case). The design correctly reuses this function verbatim rather than reinventing it (Decision D2/tasks 3.4).

Every new/modified state-changing endpoint in this design writes an audit row in the same transaction as its state-transition write, per Decision D1/D2/D4 and tasks 1.1/1.4/3.4/4.5/4.6 — consistent with the existing `draft→lobby` and `wrap_up→complete` pattern in the same file, and with the "commit the state row and the audit row together or neither" discipline `teams.ts` established. I did not find a new-endpoint code path in this design that skips the audit write.

**Gap:** Decision D4's wrap-up-entry branch (task 4.6) writes `operation = 'session.state_changed'` with `metadata = { session_id, prior_status: 'active', new_status: 'wrap_up' }` — but that branch *also* completes the current topic (`session_topics.status = 'complete'`) in the same transaction, and that fact is not recorded anywhere in the audit metadata. Contrast with the topic-to-topic branch (task 4.5), whose `session.topic_advanced` metadata explicitly names `completed_session_topic_id`. An incident reviewer reconstructing "which topic was the team discussing when this session moved to wrap-up" from the audit log alone can do it for every topic-to-topic transition but not for the final one — they'd have to cross-reference `session_topics.completed_at` timestamps against the `session.state_changed` row's `timestamp` and hope nothing else touched that table in the same window. Recommend adding `completed_session_topic_id` to the wrap-up branch's `metadata` alongside `prior_status`/`new_status` — it's already sitting in the same transaction from task 4.2's row-count check, so this is metadata, not a new query.

Also worth confirming explicitly at implementation time (not visible from design.md alone): `audit-logger.ts`'s `AuditEventName` union comment block currently says `session.reveal_triggered` is "BLOCKED on GitHub issue #26" and `session.state_changed` "excludes topic advance until issue #26 lands" — tasks.md 6.4 correctly schedules removing this stale language, but it's specifically the kind of comment that rots into a misleading audit-code paper trail if the doc-correction task slips relative to the code task. I'd sequence 6.4 immediately after Group 4 lands, not deferred to the end of the tasks list where it currently sits.

## 4. Publish-after-commit ordering — every new call site in tasks.md is correctly sequenced

I checked all five new/modified publish call sites against the "no commit, no publish" property `ws-pubsub.ts`'s own comments state as the load-bearing security/correctness invariant (a subscriber notified of a reveal that then rolls back would be shown vote data that was never actually committed as revealed — the exact failure mode the reveal guarantee exists to prevent):

- Task 1.3 (`SESSION-004` → `publishSessionStateChange`): "After the transaction commits" — correct.
- Task 1.5 (`SESSION-005` → `publishSessionStateChange`): "After the transaction commits" — correct.
- Task 3.5 (reveal → `publishVoteRevealed`): "After the transaction commits (never before, never inside it)" — correct, and explicitly restates the invariant.
- Task 4.8 (topic-to-topic → `publishTopicHistoryUpdate`): "After commit" — correct.
- Task 4.9 (wrap-up entry → both `publishSessionStateChange` and `publishTopicHistoryUpdate`): "After commit" — correct.

All five match the existing, already-audited pattern in `facilitator-sessions.ts`'s `advance`/`complete` handlers (publish call sits structurally after the `try/catch/finally` block that owns `BEGIN`/`COMMIT`/`ROLLBACK`/`client.release()`). I found no new call site that publishes from inside the transaction or before it.

**Adjacent reliability note, not a security defect:** none of these publish calls (existing or new) are wrapped in their own try/catch — if `publishVoteRevealed`/`publishSessionStateChange`/`publishTopicHistoryUpdate` throws (e.g., transient Redis error) *after* a successful commit, the exception propagates to Fastify's default error handler and the client sees a 500 for an action that actually succeeded server-side. For the reveal endpoint specifically this is self-healing by design — a client retry lands on the `already_revealed` 409, which Decision D3 requires to render indistinguishably from success. For `SESSION-004`/`005`/`012` there's no equivalent soft-landing; a retry of `SESSION-005` after a publish-only failure would 409 on `sessions.status` already being `active`, and the client would need its own "treat 409 on this endpoint as maybe-already-succeeded, re-fetch state" handling. Not blocking, but worth a one-line note in tasks.md's frontend-integration section (Group 5) so it isn't discovered as a confusing bug report later — the same pattern of "name it now" this design already applies well to the `topic_history_update` team-scoped delivery gap.

## 5. Authorization boundaries for the new/modified endpoints

`SESSION-004`, `SESSION-005`, and reveal all correctly gate on `sessions.facilitator_id = userSession.userId`, matching the existing `advance`/`complete` handlers' pattern. Good.

**Gap in the design's specification, not necessarily the eventual code:** design.md Decision D4 and tasks.md 4.1 specify `SESSION-012`'s authorization only as "Authorize (facilitator only)" — a single clause. Every *existing* handler in `facilitator-sessions.ts` that takes both `:teamId` and `:sessionId` as path params (`advance`, `complete`) performs **two** checks, not one: `sessionRow.team_id !== teamId → 403` ("Session does not belong to this team") *and* `sessionRow.facilitator_id !== session.userId → 403`. `SESSION-012`'s URL is `/api/v1/teams/:teamId/sessions/:sessionId/topics/advance` — same two-param shape. Because `facilitator_id` is scoped to a specific session already, a facilitator who is not this session's facilitator would still be rejected even without the team-id cross-check, so I don't think this is an exploitable authorization bypass as things stand — but it is a departure from this file's own established defense-in-depth pattern, and the existing tests for `advance`/`complete` explicitly assert the team-mismatch 403 case as its own scenario. I'd ask that tasks.md 4.1 be reworded to name both checks explicitly (mirroring `advance`'s two `if` blocks), and that a task-4.10/4.11-adjacent test assert the team-mismatch 403, the same way `advance`'s own test suite does — otherwise this is the kind of check that's easy to silently drop during implementation because the design prose doesn't ask for it by name.

I did not find anything in this design that widens who can trigger `SESSION-004`/`005`/`012` beyond "the session's own facilitator" — no participant, EM, or admin path is introduced or accidentally left reachable.

## 6. 409 response bodies (`already_revealed`, `advance_blocked`) — no information disclosure to an unauthorized caller, contingent on ordering

Both new error states are safe **provided** the authorization check runs strictly before the precondition check, so that a non-facilitator never reaches the branch that returns `sessionTopicId`/`revealedAt`/`requiresReveal`. I confirmed this ordering holds in the *existing* reveal handler (facilitator check at line 543, precondition check at line 577 — auth first) and tasks.md 4.1→4.2 for `SESSION-012` states the same order ("Authorize... [then] Add the conditional-UPDATE precondition write"). This is correct as specified; I'm naming it explicitly because it's exactly the kind of ordering that's easy to invert by accident during implementation (e.g., an implementer who runs the cheap `rowCount` check first as a "fast path" before the more expensive facilitator lookup) — if that ordering were ever inverted, a non-facilitator could learn a topic's `revealedAt` timestamp or a session's advance-blocked state via a 409 shape without being authorized to see it. Worth a named test case (not currently in tasks.md 3.8/4.12): a non-facilitator's reveal/advance attempt against an already-revealed or not-yet-revealed topic still returns the existing generic 403, never `already_revealed`/`advance_blocked`.

Beyond ordering, the fields themselves (`sessionId`, `teamId`, `sessionTopicId`) are already known to any caller who could construct the request (they're path parameters), so there's no new disclosure in the response bodies themselves once the ordering point above holds.

## 7. Interaction with the open SEC-25/SEC-26 gap (GitHub issue #27)

I read issue #27 directly to check this. It tracks two *known, already-scoped-out* gaps in the delivery-time authorization layer: idle-connection re-authorization (SEC-25) and mid-connection token-expiry handling (SEC-26), compensated for today only by the 90-minute absolute connection lifetime (`isPastAbsoluteLifetime`, checked in `ws-event-dispatcher.ts`'s `isConnectionExpired` before every dispatch).

This design does not touch, widen, or weaken that compensating control, and it does not introduce a new authorization gap: `dispatchVoteRevealed` and `dispatchTopicHistoryUpdate` both call `evaluateSessionSubscriberAccess`/`evaluateTeamAccess` **fresh, per-candidate, per-message** — exactly the pattern the WebSocket change's own code comments insist on ("the authorization check... runs INSIDE this message handler... EVERY SINGLE TIME a message arrives"). So when a reveal or topic-advance event actually fires under this design, an idle connection's grant is still correctly re-evaluated against live DB state at the moment of delivery — a participant whose membership was revoked while idle will not receive the payload; a session's own facilitator-status is checked live too.

What *does* change, and is worth naming plainly since the review asked for it: **before this design ships, `vote_revealed` and `topic_history_update` never fired in production, so issue #27's gap was real but operationally inert for these two event types** — there was no actual vote or topic content that a stale-but-not-yet-expired idle connection could receive, because reveal never happened. Once this design ships, that stops being true. A connection sitting idle for, say, 85 minutes (inside the 90-minute absolute cutoff, so `isConnectionExpired` doesn't reject it) held by a user whose access *should* have been reconsidered sooner than the absolute-lifetime bound — the exact scenario issue #27 describes — will now actually receive real vote values and topic-advance content the moment a reveal or advance fires, where before there was nothing real to receive. The per-event grant check still correctly blocks a user whose membership was *revoked*; the residual exposure issue #27 tracks is narrower — a user whose authorization *should* be periodically re-challenged (token freshness, SEC-26) but whose grant still technically evaluates true at delivery time, since delivery-time authorization checks current DB role state, not token freshness. This design doesn't create that gap, but it's the change that first gives it something real to expose. I'd recommend flagging issue #27 for re-prioritization alongside this change's rollout rather than leaving it at its currently-proposed Q4 2026 placeholder target, since its blast radius just went from theoretical to concrete.
