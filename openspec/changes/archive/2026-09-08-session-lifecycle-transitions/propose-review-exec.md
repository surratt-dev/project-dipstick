# Executive Review — `session-lifecycle-transitions`

**Reviewer:** Rachel Okonkwo, VP of Engineering (Executive Stakeholder)
**Scope of this review:** strategic alignment and scope proportionality, not implementation detail. I have not reviewed the SQL, the transaction pattern, or the concurrency proof — that's the engineering team's job, and I trust the design doc shows its work.

## Verdict

**Approve to proceed.** This is the rare internal-tooling proposal that undersells itself by reading as "wiring," when it's actually closing the gap between "we built the delivery pipe" and "the pipe carries anything." I'd be more worried if this proposal *weren't* on the table right now.

## Why this is the right increment, not scope creep

I asked for three things from every team building toward my adoption goal: ship something usable quickly, don't balloon scope, and don't let the ritual quietly stall. This proposal reads like it was written by someone who'd already internalized all three, which is worth naming rather than assuming.

**The 8 task groups are not 8 units of new design.** I went looking for where this could be split or trimmed and didn't find much. Groups 1, 3, and 4 wire three endpoints to patterns and hooks that already exist — Decision D1 says outright it's copying the `draft → lobby` and `wrap_up → complete` handlers "verbatim." Group 6 is documentation correcting a contract that's currently self-contradictory. Group 7 is spec sync. The only genuinely new *design* surface here is the reveal write's concurrency handling and the topic-advance/wrap-up branch — everything else is disciplined reuse. I don't want this consolidated further; consolidating "session-phase entry" and "the reveal write" into one task group would just hide the sequencing dependency the team correctly called out (you can't test a reveal without a session that can reach `active`). I also don't want it split further — splitting the race fix out as its own change would break the one property I actually care about here (see below).

**Deferring team membership removal is the correct call, and it doesn't ship "half a state machine."** I checked this the way I'd check any adoption-risk claim: can a pilot team run a full session — open the room, vote, reveal, move through every topic, wrap up, close — without membership removal existing? Yes. `SESSION-006` (session close) is already in production; this proposal adds every transition between "session created" and that existing close. Membership removal is a roster-management concern (who's on the team), not a session-runtime concern (what happens during a session) — those are genuinely different pieces of surface with different owners, and the proposal is explicit that the deferred piece has its own blocking dependency (issue #23) that isn't this team's to resolve. Bundling it in wouldn't get a pilot team running any sooner; it would just make this change wait on a BA decision it doesn't need. That's the opposite of the stall I worry about.

**The vote lock-in race fix belongs in this change, and I don't read it as a smuggled hotfix.** The distinction that matters to me: is this a live bug in production today, quietly bundled into a feature branch to dodge a release-process conversation? No — the proposal's own framing (and I'd have pushed back if it weren't stated this plainly) is that this race is *inert today* because nothing has ever moved a topic to `revealed`. It only becomes exploitable the moment this change ships the reveal write. Shipping the reveal write without the fix would mean *this proposal* introduces a way for a vote to sneak into a revealed topic — a direct hit against the one guarantee (simultaneous, un-gameable reveal) this whole application exists to protect. Sequencing it as a gated prerequisite (tasks.md Group 2 before Group 3) rather than a follow-up ticket is the right risk call. If anything, I'd be more nervous about a version of this proposal that shipped the reveal write and left this as "future hardening."

**Appendix D and SESSION-012 are corrections, not additions to issue #26's ask.** I don't love scope growing beyond a ticket's literal text, so I looked at this one skeptically. Appendix D currently tells engineers something false — that reveal and topic-advance "must NOT be implemented as REST endpoints," while the same document specifies `SESSION-004`/`SESSION-005` as REST endpoints two sections over. Leaving that standing while shipping code that contradicts it isn't a neutral choice; it's choosing to leave a landmine for the next engineer who reads the contract before the code. Same logic for `SESSION-012`: wrap-up entry has no endpoint ID anywhere today, which the proposal is careful to call "undesigned," not "unbuilt." You can't wire a transition that was never designed — writing it down and implementing it in the same change is the only order that makes sense.

## What I'd want tracked, not what I'd block on

**Task group 5 (frontend integration notes) needs an owner and a date, not just a footnote.** The named integration gap — a client only subscribed to its session channel won't see `topic_history_update` events unless it also subscribes to the team channel — is exactly the kind of thing that becomes a confusing, quiet failure for a pilot team rather than a loud one. It's correctly scoped out of this backend change, but "named, not implemented" is only safe if someone owns closing it before a pilot team hits a live session. I'd like to see this handed off with the same explicitness the BA follow-on (task 7.4, membership removal) got.

**I didn't see an effort estimate, and I'd like one before this is greenlit for a sprint.** Everything in the scope argument above holds up, but "proportional to value" is a statement about size too, and I can't independently judge that from task counts alone. Given how much of this is pattern reuse, my expectation is this should be small — if the estimate comes back large, that's worth a second look at whether something drifted from "wire existing hooks" into "redesign."

## Bottom line

This closes the gap between an event-delivery layer that's fully built and unit-tested, and an event-delivery layer that has ever fired outside a test suite. Every one of my teams' pilot sessions is currently blocked on this, whether anyone's said so in those words or not — a session cannot leave the lobby today. Ship it.
