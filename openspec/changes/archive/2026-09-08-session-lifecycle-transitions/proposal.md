## Why

The simultaneous-reveal guarantee — the single property this application exists to protect above all others — has no code behind it today. `POST .../reveal` checks "are you the facilitator" and "is the session active," then returns `200 { revealed: true }` and writes nothing. The pre-reveal read path correctly withholds vote values only because `session_topics.status` never moves off `voting` — forever, because nothing moves it. That is not the guarantee holding; it is the guarantee never being exercised. FR-4.6.1's 15-second delivery SLA, the outlier detection that runs "for each topic's reveal," and the discussion-note window that opens "from the moment a topic is revealed" are all unreachable code paths, not tested-and-passing ones. The `websocket-delivery-time-authorization` change (archived 2026-09-07) built and unit-tested the delivery-time authorization layer and the audit-log hooks this reveal depends on — `recordRevealTriggeredAudit`, `publishVoteRevealed`, `publishTopicHistoryUpdate` — and left them deliberately uncalled from production code, tracked as GitHub issue #26, waiting for exactly this change.

The gap is bigger than a single missing `UPDATE`. Re-verified against `packages/backend/src` for this proposal: there is no code path that ever moves a session out of `lobby` (`SESSION-004`/`SESSION-005` are documented in the REST API Contract but no route exists), no code that advances a session from one topic to the next, and no code that enters `wrap_up` at all — the last of these has no endpoint ID anywhere in the contract, meaning it was never designed, not merely never built. Wiring only the reveal write, without these session-phase entry points, would ship a topic that can be revealed but that a session can never legally reach.

## What Changes

- Implement `POST /api/v1/sessions/:sessionId/start` (`SESSION-004`, lobby → pre_session) and `POST /api/v1/sessions/:sessionId/begin-voting` (`SESSION-005`, pre_session → active, sets the first topic to `voting`, sets `sessions.current_topic_id`). These are two distinct, meaningfully-labeled facilitator actions per FR-3 — "open the room" and "old business is handled, begin new business" — not one collapsed generic transition. FR-3.5's no-open-items case is a genuine one-click pass-through.
- Implement the reveal write itself: `session_topics.status` `voting` → `revealed`, `revealed_at = NOW()`, inside the existing `POST .../reveal` endpoint (which today validates preconditions only). Guarded by a hard precondition — the topic must currently be `voting` — enforced via a conditional `UPDATE ... WHERE status = 'voting'` with a row-count check, not a separate lock statement. A second reveal call on an already-`revealed` topic returns `409`, and the WebSocket publish only fires once, on the call that actually flipped the row.
- Implement a new endpoint, `POST /api/v1/teams/:teamId/sessions/:sessionId/topics/advance` (assigned `SESSION-012` — no endpoint ID exists for this today), covering topic-to-topic advance and entry into `wrap_up`. Guarded by a hard precondition — the current topic must be `revealed` — enforced the same conditional-`UPDATE` way. When a next topic exists in `display_order`, the current topic is marked `complete`, the next is set to `voting`, and `sessions.current_topic_id` updates; the session stays `active`. When no next topic exists, the current topic is marked `complete` and the session transitions to `wrap_up` (`sessions.wrap_up_started_at = NOW()`) — this is genuinely undesigned work, not wiring: no endpoint ID for this transition exists anywhere in the REST API Contract today, confirmed by direct review of all 34 documented endpoints.
- **Required correctness fix, not previously identifiable as a gap because nothing ever set `session_topics.status = 'revealed'` before now:** the vote lock-in handler (`packages/backend/src/routes/sessions.ts`) does not currently check `session_topics.status` before inserting a vote. Once the reveal write is real, a vote submitted after a reveal has committed could still be silently inserted and would appear in the revealed set — a direct violation of FR-4.7 and the simultaneous-reveal guarantee. This change adds a `session_topics` row-lock-and-status-check to the lock-in transaction so a lock-in racing a reveal for the same topic loses cleanly (`409`) rather than sneaking a vote into an already-revealed topic.
- Rule out mid-session topic-skipping for this change (see "Topic-Skip Decision" below) rather than design a new skip path.
- Wire into the exact stubbed, unit-tested hooks the WebSocket change built and left uncalled: `recordRevealTriggeredAudit` (`facilitator-sessions.ts` lines 31–63), `publishVoteRevealed` and `publishTopicHistoryUpdate` (`ws-pubsub.ts`), consumed by the already-built `dispatchVoteRevealed`/`dispatchTopicHistoryUpdate` (`ws-event-dispatcher.ts`) and `buildVoteRevealedPayload` (`vote-revealed-payload.ts`). No new dispatch, authorization, or payload-construction logic — this change makes the triggers real; the delivery layer already exists.
- Add one new `AuditEventName` value, `session.topic_advanced`, for the topic-to-topic case where `sessions.status` does not itself change (the wrap-up-entry case reuses the existing `session.state_changed` operation, consistent with every other `sessions.status` transition already audited).
- Correct Appendix D of the REST API Contract: `reveal.trigger` and `topic.advance` are currently marked "must NOT be implemented as REST endpoints," citing BRD 6.1 — a rationale that supports excluding vote *submission* from REST (timing exposure) but not the facilitator's own privileged *trigger* action, and which already self-contradicts `SESSION-004`/`SESSION-005` being specified as REST endpoints in the same document. Rewrite both Appendix D rows and `VOTE-003`'s note to describe the actual architecture: authenticated REST trigger, single simultaneous WebSocket broadcast for fan-out, publish-after-commit. `vote.submit`'s REST exclusion is untouched — its rationale doesn't share this flaw.
- Add `SESSION-012` to the REST API Contract as a new, fully-specified endpoint entry (request/response shape, authorization, error responses) — the contract currently has no entry for this transition at all.
- **409s from both new preconditions are UX-specified, not left as "the backend returns 409, the frontend figures it out":** a second reveal on an already-revealed topic must render on the facilitator's screen indistinguishably from a successful reveal (the screen already shows the revealed state — no error chrome). An advance-before-reveal `409` must land the facilitator somewhere actionable — the blocked-advance state should offer the reveal action directly. Both reuse the existing `errorState`-keyed response shape (`packages/shared/src/types/team-content-access.ts`), not an ad hoc `409` body.

## Topic-Skip Decision

Ruled out for this change: mid-session topic-skipping is not supported. A topic that no longer applies to a team must be removed from the topic list before the session is **created**, not before it "starts" — per FR-8.2, and per `SESSION-001`'s own contract notes (REST API Contract, line ~1019), the topic list is snapshotted into `session_topics` at session creation, not at `SESSION-004` (lobby → pre_session, what a facilitator actually thinks of as "starting" the session). A topic-list edit made after a session already exists in `lobby` has no effect on that session, however long it sits in `lobby` before the facilitator clicks "start." Facilitators are directed to prepare the topic list accordingly, before creating the session.

**Caveat — this is a narrower escape hatch than "before it starts" implied, and it's worth naming plainly rather than smoothing over.** A facilitator who creates a session ahead of the actual meeting — for instance, to generate and distribute the join link early — gets no signal, at creation time or afterward, that the topic list is about to be locked in for that session. If they notice a topic is stale after creation but before the session starts, the "edit the topic list" workaround silently does nothing, and nothing in this change surfaces that failure to them; the facilitator would reasonably believe the edit worked until they see the stale topic appear live. This isn't severe enough to reopen the topic-skip decision itself — Marcus confirmed ruling out mid-session skip is still the right scope call, and I agree a real skip path is authorization surface this change shouldn't take on — but it is sharper than the original "before it starts" framing suggested, and it deserves a named follow-on rather than getting fixed by a word change alone. Candidate for that follow-on, not designed here: a creation-time signal (e.g., surfacing the about-to-be-snapshotted topic list back to the facilitator for a last look before `SESSION-001` confirms) would close this gap without reopening the authorization-surface problem a real mid-session skip path would create. This stems from the same underlying tension as the topic-skip scenario below — topic-list edits and session timing don't currently give facilitators a clean signal of when "too late" actually is — so track both under the same future follow-on rather than as two unrelated asks.

Priya Nair's review named a real scenario (a team's context changes between topic-list setup and the session reaching that topic — an on-call topic for a team that just deprecated on-call). That scenario doesn't conflict with the hard reveal-before-advance precondition above — skipping a topic *before any vote exists for it* strands nothing — but building a facilitator-initiated skip path is new authorization surface (who can trigger it, what gets audited, how it interacts with `display_order`) that this change does not have review bandwidth to design correctly under the scope already committed to above (two session-phase endpoints, one new topic-advance endpoint, a reveal write, and a lock-in race fix). Ruling it out keeps this change's scope to the transitions already named as broken, rather than growing it by one more undesigned endpoint. This is named as a candidate for a future, narrowly-scoped follow-on change, not silently dropped.

## Capabilities

### New Capabilities

- `session-topic-lifecycle`: The session-and-topic phase state machine — `lobby → pre_session` (`SESSION-004`), `pre_session → active` (`SESSION-005`), topic-to-topic advance and `active → wrap_up` entry (`SESSION-012`), and the reveal write (`voting → revealed`) with its hard preconditions (no re-reveal, no advance before reveal) and their calm, non-error-chrome UX treatment. Includes the vote lock-in / reveal race-condition fix as a correctness requirement of the reveal guarantee this capability establishes.

### Modified Capabilities

- `team-content-access`: The "Live session error states for facilitators" requirement (Error State 1) is extended to cover two new precondition failures — an already-revealed topic and an advance attempted before reveal — both specified as calm, non-alarming states rather than generic error presentation, consistent with the existing Error State 1 pattern.

**Not a requirement change, but named here for completeness:** `websocket-session-authorization`'s Purpose section carries a "Production trigger status" note stating that `vote_revealed` and `topic_history_update` are implemented but not wired to any production trigger. No requirement in that spec changes — this change corrects the note directly (a Purpose-section edit, the same category of out-of-band correction the WebSocket change itself made to the archived `team-content-access` spec's "gate-blocked" note) as a documentation task, not a delta spec.

## Out of Scope

- **Team membership removal.** A separate, orthogonal change with a different authorization owner (admin/EM roster management, not facilitator session control) and its own dependency on GitHub issue #23 (open action item reassignment authorization). To be filed as its own future OpenSpec change, referencing this decision. Nothing in this change depends on membership removal existing, and nothing this change builds needs to anticipate its design.
- **GitHub issue #23 (action item reassignment authorization).** Stays a BA-owned open question (`OQ-5` in the REST API Contract, `VOTE-004`'s reassignment authorization). This change does not touch `VOTE-004` or its "new owner must be an active participant" constraint.
- **"Action item finalization" as a separate deliverable.** Confirmed during Explore-stage BA review, verified directly against the schema and the REST API Contract: `action_items` has no `finalized`/`finalized_at` column, and finalization is a read-time join on `sessions.status = 'complete'` — already satisfied by the existing session-complete write (`SESSION-006`, already committed in production). `topic_history_update`'s real trigger set narrows to topic-to-topic advance only; no new write is needed for finalization. This proposal corrects the stale "action item finalization" framing carried in GitHub issue #26 and in the WebSocket change's dispatcher comments (`ws-pubsub.ts`, `ws-event-dispatcher.ts`) as part of its documentation tasks, without building anything new for it.
- **Mid-session membership removal** (what happens to a participant's connection, in-flight vote, and the facilitator's readiness grid if a team membership removal lands while that person is in a running session). Named in the exploration notes as a real open question at the boundary of this change and the deferred membership-removal change; it stays with the deferred change, since its trigger (a roster event) and its owner (admin/EM authorization) both live there. This change's own session-runtime code is unaffected either way — `evaluateSessionSubscriberAccess` and the lock-in handler already read `team_memberships.removed_at`/`role` live on every check, whether or not anything sets them yet.
- **Mid-session topic-skipping.** See "Topic-Skip Decision" above.

## Impact

- **New REST endpoints:** `SESSION-004` (`POST /api/v1/sessions/:sessionId/start`), `SESSION-005` (`POST /api/v1/sessions/:sessionId/begin-voting`), `SESSION-012` (`POST /api/v1/teams/:teamId/sessions/:sessionId/topics/advance`) — all currently documented (004/005) or undocumented (012) but unimplemented in `packages/backend/src/routes/`.
- **Modified endpoint:** `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal` (`facilitator-sessions.ts`) gains the actual state-transition write; refactored to the `teams.ts` transaction pattern (`BEGIN`/`COMMIT`/`ROLLBACK`) so the reveal write, the `recordRevealTriggeredAudit` insert, and the precondition check commit atomically.
- **Modified endpoint:** `POST /api/v1/sessions/:sessionId/topics/:sessionTopicId/lock-in` (`sessions.ts`) gains a `session_topics` row-lock-and-status precondition check to close the reveal/lock-in race named above.
- **Database:** No schema changes. `session_topics.status` (`waiting`/`voting`/`revealed`/`complete`), `sessions.wrap_up_started_at`, and `sessions.current_topic_id` already exist and already support every transition this change implements.
- **Reused, not duplicated:** `evaluateSessionSubscriberAccess`, `evaluateTeamAccess`, `serializeForFacilitator`/`serializeForMemberParticipant` (via the already-built `buildVoteRevealedPayload`), the `teams.ts` transaction pattern, `emitAuditEvent`, and the delivery-time WebSocket dispatch layer built by `websocket-delivery-time-authorization`. This change adds zero new authorization logic and zero new WebSocket infrastructure.
- **New `AuditEventName` value:** `session.topic_advanced`, added to `audit-logger.ts` alongside the three added by the WebSocket change.
- **Documentation:** REST API Contract Appendix D (`reveal.trigger`/`topic.advance` rows) and `VOTE-003`'s note corrected; new `SESSION-012` entry added; GitHub issue #26's and the WebSocket change's stale "action item finalization" language corrected.
- **Unblocks:** the WebSocket change's own blocked end-to-end tasks (11.1's reveal-triggered portion, 5.6/11.2's `topic_history_update` real-trigger portion) become runnable against real production triggers for the first time.
- **Follow-on work named, not performed here:** a future OpenSpec change for team membership removal (with its own dependency on issue #23); a future, narrowly-scoped change for facilitator-initiated topic-skipping, if demand is confirmed beyond the single scenario named in this proposal's review, bundled with the creation-time topic-list-signal gap named in the "Topic-Skip Decision" caveat above (both stem from facilitators lacking a clear signal of when a topic-list edit stops taking effect).
