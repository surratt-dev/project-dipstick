## 0. What I verified before writing anything down

I did not take issue #26's accounting on faith, even though it's careful work. I re-read `packages/backend/src/routes/facilitator-sessions.ts` in full, checked the actual `session_status` and `session_topic_status` enums and the `sessions`/`session_topics`/`action_items` table definitions in the migrations, and read the REST API Contract's session-lifecycle endpoints end to end. Two things came out of that re-check that change the shape of this document from a straight restatement of the issue:

1. **The gap is bigger than issue #26 names.** The issue's own evidence table lists five transitions and says only two are real (lobby-advance, session-complete). But the `session_status` enum (`packages/backend/migrations/1_create_enums.sql`) has six values: `lobby`, `pre_session`, `active`, `wrap_up`, `complete`, `abandoned` (plus `draft`, added later in migration 9). The REST API Contract documents two more transitions that don't exist in code at all and aren't mentioned in issue #26: `POST /api/v1/sessions/:sessionId/start` (lobby → pre_session, SESSION-004) and `POST /api/v1/sessions/:sessionId/begin-voting` (pre_session → active, SESSION-005). Neither route exists anywhere in `packages/backend/src/routes/`. There is also no route that transitions a session into `wrap_up` at all. So the honest inventory of missing session-level state machine code is: lobby→pre_session, pre_session→active, active→wrap_up (topic-advance-adjacent), topic voting→revealed, and wrap_up→complete's sibling for `session_topics`/`action_items`. Issue #26 named the ones its author hit while tracing the WebSocket change's specific triggers. I'm naming the rest here because a design that only wires up "topic advance" and "reveal" without also producing the pre_session and active entry points will not actually let a facilitator run a session end to end. See Section 4.

2. **"Action item finalization" is not obviously its own database write.** `action_items` (migration `2_create_tables.sql`) has no `finalized` or `finalized_at` column, and the REST API Contract's own account of action item visibility (ACTION-004: "Only items from sessions with `status = 'complete'` are included... this is the mechanism that prevents draft items from appearing in the public backlog before session close") ties finalization entirely to the *session's* status, not to any per-item write. `ACTION-001`'s own note says action items are "written to PostgreSQL immediately at creation — not buffered until session close." If that's accurate, "action item finalization" may already be fully satisfied by the session-complete write that exists today (`facilitator-sessions.ts` line ~397), and the WebSocket dispatcher naming in issue #26 and the archived change ("topic_history_update... e.g., action items finalized") may be describing an *event* — something changed and clients should refresh — rather than a *missing write*. I'm flagging this because if it's right, it shrinks the scope of this change materially, and if it's wrong, Propose needs to say specifically what "finalization" writes beyond session completion. I did not find a missing write for this in the schema; I could be missing something in application logic I haven't traced (e.g., a stale-flag recompute). This needs a direct answer before Propose, not an inherited assumption — see Section 4.3.

## 1. What this use case is trying to accomplish

This is not a new feature. It is finishing a state machine whose skeleton — enum values, foreign keys, timestamp columns, REST contract prose — was designed and partially scaffolded a long time ago, and whose muscle was never attached. Two consequences follow from that framing, and I want them stated up front because they should shape how Propose scopes this:

- This is **not** "design the reveal mechanic." The reveal mechanic is designed, in detail, in the BRD (FR-4.6, FR-4.6.1, FR-4.7) and in the REST API Contract. What's missing is the line of SQL that flips `session_topics.status` from `voting` to `revealed`.
- It **is**, partially, "design the membership-removal endpoint," because unlike reveal/advance, no removal endpoint appears anywhere in the REST API Contract. That's a real design gap, not a wiring gap, and I don't want Propose to treat all four transitions as the same kind of work.

## 2. What's actually at stake — Devon's read

I signed off on the archived access-control change and the WebSocket delivery-time change on the premise that the authorization layer around session content was airtight. That premise has a hole in it that has nothing to do with authorization and everything to do with the fact that the thing being authorized doesn't happen. A few consequences of that, stated plainly:

**The simultaneous reveal — the load-bearing constraint I care about most in this application — has no code.** `POST .../reveal` today checks "are you the facilitator" and "is the session active," then returns `200 { revealed: true }` and touches nothing. Nothing stops votes from being visible before this endpoint is even called correctly, because nothing about calling it correctly changes any row. The reveal *works* today only in the sense that the pre-reveal read-path correctly withholds vote values as long as `session_topics.status` stays `voting` — forever, because nothing ever moves it. That's not the reveal guarantee holding. That's the reveal guarantee never being exercised. FR-4.6.1's 15-second delivery SLA, the outlier detection in FR-5.1 that runs "for each topic's reveal," the discussion-note write window that opens "from the moment a topic is revealed" (SESSION-009) — every one of these is unreachable code today, not tested-and-passing code.

**The no-manager-participation rule and the facilitator-from-another-team rule are both intact and unaffected by this gap** — worth saying because it's not everything that's broken. Those are enforced at join-time and session-creation-time (`session-participation` spec, `TEAM-002`'s facilitator eligibility filter), and neither depends on any of the four missing transitions. I don't want this document to read as "the whole ritual is unbuilt." It isn't. The parts that keep the wrong people out of the room are solid. The parts that make the room itself do what it's supposed to do once people are in it are not.

**Membership removal touches a different nerve.** There is no removal endpoint anywhere — not partially built, not stubbed, not in the REST API Contract at all. `team_memberships.removed_at` is read defensively everywhere (`WHERE removed_at IS NULL`) as though someone expected this column to be populated by something. Nothing populates it. Today, a person cannot be removed from a team through this application, full stop. Whether that's a gap this change should close, or a decision that removal is out of scope for now and the column exists only for future-proofing, is a real open question — see Section 5.

## 3. Decision (a): One change, or several?

**My recommendation: two changes, not one, and not four.**

**Change 1 — the session topic lifecycle (reveal, topic advance, and whatever "action item finalization" turns out to require).** These three are causally chained inside a single session's runtime: you cannot advance past a topic that hasn't been revealed (FR-4.1 says the facilitator controls progression, but nothing in the BRD suggests a facilitator can skip the reveal — see Section 4.1 for why I think this needs to be a hard precondition, not just a facilitator convention), and the wrap-up phase that action items belong to only begins after the last topic's reveal. These three transitions share one authorization pattern (facilitator-of-this-session), one transaction pattern (the `teams.ts` `BEGIN`/`COMMIT` style already established), and one set of downstream consumers (the `vote_revealed` and `topic_history_update` WebSocket dispatchers, both already built and waiting). Splitting reveal from topic-advance into separate changes would mean shipping half a state machine twice.

**Change 2 — team membership removal.** This is a roster-management operation, not a session-runtime operation. It's triggered by an HR/org event (someone leaves the team), not by anything happening inside a live session. Its authorization model is a different question entirely (facilitator? EM? admin? — see Section 5), and it has a real, unresolved dependency on issue #23 (open action item reassignment) that the BA owns, not this change. Bundling it with the topic-lifecycle work would either stall the topic-lifecycle work on a BA decision that has nothing to do with reveals, or force a design that guesses at #23's answer. Keep it separate. It can also ship on its own schedule — nothing about `vote_revealed` or `topic_history_update` depends on membership removal existing.

**Why not one change for all four, matching issue #26's framing exactly:** issue #26 groups all four together because they share one symptom — "no code commits this" — not because they share a design. I don't think the symptom is a good organizing principle for the fix. The WebSocket change's own tasks.md (Group 0, task 0.3) already tracks the two session-runtime events (`vote_revealed`, `topic_history_update`) as a pair, distinct from membership removal's role in the third event's authorization checks (`evaluateTeamAccess`, which reads `removed_at` but isn't blocked by this gap — the read-side already handles `removed_at IS NULL` correctly whether or not anything ever sets it). That's already implicitly two problems in the code that consumes this gap. I'd make that explicit rather than merge it back together for this change.

**Why not four separate changes:** reveal and topic-advance in isolation from each other would each need to re-derive the same session-state-transition authorization and transaction pattern, and a reveal-only change would ship a topic that can be revealed but never advanced past — not a usable increment. There's no clean seam between reveal and advance the way there is between the topic lifecycle and membership removal.

**One more traceability note, from Marcus's review:** action item continuity — one of the product properties I care about most — has requirement surface in both changes' orbit without being owned by either. The topic-lifecycle change's action-item-finalization language (Section 4.3) touches how items become visible in the backlog; the membership-removal change's open-item-count surfacing (Section 5.2) touches the same table from the ownership angle. Neither change modifies `VOTE-004` (reassignment) or its "new owner must be an active participant" constraint, which is correct — but both change documents should say so explicitly, rather than leaving a reviewer to infer it from silence in two separate documents. `VOTE-004` and reassignment policy stay untouched and reserved for issue #23; both proposals should cross-reference that fact rather than each assuming the other states it.

## 4. Decision (b): The topic lifecycle — reveal, advance, and finalization

### 4.1 Reveal: what actually needs to happen, and the precondition question

The write itself is small and already fully specified by the schema: `UPDATE session_topics SET status = 'revealed', revealed_at = NOW() WHERE id = $1`, in the same transaction as the `session.reveal_triggered` audit write the WebSocket change already built and is waiting to attach (`recordRevealTriggeredAudit`, `facilitator-sessions.ts` lines 31–63 — exported, unit-tested, deliberately not called from production code, with a `TODO(#26)` naming exactly this handler). The `redis.publish(...)` call for `vote_revealed` must fire only after that transaction's `COMMIT` succeeds — the WebSocket change's design.md is explicit and non-negotiable about publish-after-commit ordering (Decision D7's note, tasks.md 7.2), and I'm restating it here because it's the single easiest thing for an implementer to get backwards under time pressure: publish, then realize a later statement in the same transaction needs to roll back, and a subscriber has now been told about a reveal that never committed.

**What Devon actually cares about here, though, is smaller and sharper than the write itself.** The BRD's vote-immutability language (FR-4.7: "Votes that have been revealed shall be immutable") and OR-1.5 ("session state must be server-authoritative") both assume the reveal is a single atomic gate: before it, no vote is readable by anyone, through any path; after it, votes are frozen and readable by everyone in the session simultaneously. Two questions Propose needs to answer explicitly, because the schema doesn't answer them for you:

- **Re-reveal handling.** Can the facilitator call `/reveal` again on a topic that's already `revealed`? The current endpoint's `validRevealStates = ["active"]` check is on *session* status, not topic status — nothing today stops a second reveal call on an already-revealed topic once the write exists, unless the new code adds a topic-status precondition (`session_topics.status = 'voting'` required, `409` otherwise). I think this must be a hard precondition, not a convenience no-op: a "successful" second reveal that just returns `200` again is harmless by itself, but if it also re-publishes `vote_revealed`, it re-broadcasts an event for something that already happened, and downstream clients (and the audit log, if it's not similarly guarded) have no way to distinguish "the reveal actually happened again" from "the facilitator double-clicked." I'd rather this be a `409` — matching the existing failure-state pattern the endpoint already uses for other invalid-state cases — than a silent success.
- **Concurrent facilitator actions.** Nothing in the current endpoint locks the topic row. If the same facilitator (or, in a bug, a stale second tab) fires two reveal requests for the same topic near-simultaneously, both could pass the `status = 'voting'` precondition read before either write commits, unless the write itself is guarded. This is the exact race the `assign-role-to-team-member` change already solved once, for a different table, with `SELECT ... FOR UPDATE` before the read that gates the write (`teams.ts` lines ~494–510, the team-membership-lock pattern cited in Section 5 below). The reveal write should use the same discipline: lock the `session_topics` row (or check-and-update with `WHERE status = 'voting'` in the `UPDATE`'s own predicate and inspect the row count, which is cheaper and avoids a separate lock statement) so a second concurrent reveal attempt gets a clean `0 rows updated` rather than racing past a stale read.

**Client-facing behavior of these preconditions — this is a UX requirement, not just an API contract detail.** Priya (Facilitator reviewer) pushed on this and she's right: a 409 that reaches the facilitator's screen as a generic error state — a red banner, a toast, anything reading as "something went wrong" — recreates exactly the kind of doubt-inducing moment the paper-and-spreadsheet version of this ritual never had. The facilitator did nothing wrong in either case: double-clicking Reveal because the screen didn't update fast enough for their taste, or fat-fingering "next topic" out of habit before revealing. But now they're looking at their laptop wondering if they broke something, at the exact moment they're supposed to be watching the room. That's a cost this application would be introducing that didn't exist before. Propose must specify this explicitly, as a UX requirement, not leave it as "the backend returns 409 and the frontend will figure it out":

- A second reveal call on an already-revealed topic must resolve, on the facilitator's screen, indistinguishably from a successful reveal — the screen shows the revealed state (because it already is revealed), with nothing implying an error occurred.
- An advance-before-reveal 409 must land the facilitator somewhere they can act, not at a dead end they have to puzzle out — ideally the blocked-advance state offers the reveal action directly, rather than requiring them to back out and find the right button. That's a UI decision more than a state-machine one, but Propose needs to say so explicitly so it doesn't get lost between this document and implementation.
- The response body for both 409s should reuse the endpoint's existing error-state shape — the `errorState`-keyed pattern already used elsewhere in `facilitator-sessions.ts` (lines 509, 554, 564, 579) — rather than a bare `409` with an ad hoc body invented for this case. Small thing, but it's exactly the kind of "what did you mean by 409" question I'd rather Propose answer than have asked mid-implementation.

**Tie-breaking:** I checked. There isn't one, and there shouldn't be. `requirements/voting mechanics.md` and its enhanced version describe three vote types — Finger (1–4, even scale, no midpoint by design, "prevents the team from clustering in the center"), Roman (thumbs up/down, binary), and Modified Roman (up/steady/down, trend-only). None of these produce a single "winning" value that a "tie" could apply to — a reveal shows the *distribution* of individual votes (`RevealedVoteEntry[]`, per the REST API Contract), not a computed aggregate the group has to agree on. There's no consensus step, no runoff, nothing to break a tie between. I'm noting this explicitly so Propose doesn't invent tie-breaking logic nobody asked for; the aggregate shown post-reveal (FR-4.8, "average, distribution") is informational, not decisional.

**Vote lock-in timing:** already fully governed by existing, working code — the vote lock-in endpoint (`packages/backend/src/routes/sessions.ts`, referenced in the WebSocket change's Decision D7 as already committing today via `INSERT INTO votes ... ON CONFLICT DO UPDATE`) is not part of this gap. The reveal's only relationship to lock-in timing is that it must not be callable in a way that lets a vote submitted *after* the facilitator has triggered reveal be silently included — i.e., the reveal write and any in-flight lock-in write need to not race in a way that admits a late vote into a "simultaneous" reveal. I'd want this named as an explicit test case (lock-in request and reveal request racing for the same topic) rather than assumed safe because the general shape resembles the topic-status race above — it's a different table and a different failure mode (a vote appearing in the revealed set that arrived after the reveal moment, not a duplicate reveal), and deserves its own test.

### 4.2 Topic advance: what "advance" means, and the gap issue #26 didn't name

This is where Section 0's finding matters most. "Topic advance" in issue #26's language conflates at least two distinct transitions that the REST API Contract keeps separate:

- **Session-level phase entry** — `lobby → pre_session` (SESSION-004, `/start`) and `pre_session → active` (SESSION-005, `/begin-voting`, which also sets the *first* topic to `voting` and `sessions.current_topic_id`). Neither route exists in `packages/backend/src/routes/` at all. Without these, a session can never leave `lobby` in any code path other than the one that already exists (`draft → lobby`), which means it can never reach a state where a reveal would even be legal (`reveal`'s own precondition requires `status = 'active'`).

  **Correction from my first pass, prompted by Priya's review:** I undersold this by calling these "two undocumented session-phase entry points" — language that reads like bureaucratic overhead, two extra clicks between the facilitator and voting. It isn't. `pre_session` is the pre-session action item review (FR-3.1–3.5): the screen where open action items from the last session get looked at before voting starts on anything new. `start` (lobby→pre_session) and `begin-voting` (pre_session→active) are two distinct facilitator moments with two distinct jobs — one opens the room, the other is a deliberate "we've dealt with old business, now new business." They must ship as two separate, meaningfully-labeled actions, not get collapsed into one generic "next phase" button because they're adjacent in the state machine. Losing that distinction would take away something FR-3 clearly intends the facilitator to have, and it's exactly the "continuity across facilitators" value this application exists to provide.

  **Confirmed:** per FR-3.5, when there are no open action items (or this is a team's first session), this screen should let the facilitator "proceed immediately" with a clear indicator — this must be a genuine one-click pass-through, not a screen the facilitator has to consciously dismiss every time even when it's empty.
- **In-session topic-to-topic advance** — moving from one revealed topic to the next topic in `display_order`, setting the new topic to `voting`, updating `sessions.current_topic_id`. This is the transition issue #26 is most directly pointing at (`session_topics.status` never gets written anywhere), and it's the one the archived WebSocket change's `topic_history_update` dispatcher is waiting on.
- **Entry into wrap-up** — `active → wrap_up`, presumably triggered when the facilitator advances past the *last* topic. No route commits this, and FR-6.1 ("After the final topic is voted on and revealed, the facilitator shall advance to the session wrap-up screen") describes exactly this transition without naming an endpoint for it. **Confirmed, not just suspected** — Marcus checked the full 34-endpoint REST API Contract directly (all of `TEAM-001` through `HEALTH-002`) and there is no `SESSION-0XX` entry anywhere for `active → wrap_up`. Unlike topic-to-topic advance, where the design exists and only the code is missing, this transition is undesigned — the same category of work as membership removal (Section 5), not a peer of the topic-advance wiring. Propose needs to design this transition, including assigning it a real endpoint ID, as explicit scope, not fold it silently into "topic advance."

**My recommendation:** Propose should treat all of these as one unit of work — "the session-and-topic phase state machine" — rather than build topic-to-topic advance in isolation and leave the session-level entry points (start, begin-voting, wrap-up entry) as a second undiscovered gap. A design that wires up `topic_history_update` to fire on topic-to-topic advance, but ships with no way to ever reach the `active` phase where topics get voted on in the first place, doesn't produce a working session — it produces a better-tested version of the same non-functional state machine. I'd rather Propose scope this explicitly and say so, than have someone discover mid-implementation that "advance" needed three routes, not one.

**The precondition question for topic advance, mirroring 4.1's reveal question:** should advancing to the next topic require the current topic to be `revealed` first? I believe yes, and I don't think this is a close call — FR-4.1 says progression is facilitator-controlled, but nothing suggests the facilitator can skip a reveal, and the entire ritual point of "one topic at a time, reveal before moving on" collapses if a facilitator can advance a topic that's still `voting`, stranding uncounted votes in Redis with no way to ever reveal them (Redis vote hashes have an 8-hour TTL per other design docs I've seen referenced in this codebase — an un-revealed, advanced-past topic's votes would simply expire, unrecoverably). This should be a hard `409`, the same class of failure as the reveal preconditions.

**An open question this hard-precondition framing obscured: is there ever a legitimate reason to move past a topic without voting on it at all?** Priya raised this from direct facilitation experience, and it's real: a team's context changes between when the topic list was set and when a session reaches a given topic — an on-call-rotation topic for a team that just deprecated on-call, a topic referencing a practice the team stopped doing three sprints ago. Today, facilitators handle this by just saying "let's skip this one" and moving on: nobody votes, nothing is revealed.

I want to be precise about why this doesn't conflict with the hard-precondition stance above. The reveal-before-advance gate exists to protect votes that have already been cast or are in flight — that's the FR-4.7 immutability guarantee, and it stays a hard, non-negotiable `409`. Skipping a topic *before any vote exists for it* doesn't touch that guarantee at all; there's nothing to strand. These are two different scenarios my first pass both filed under "advance without revealing," and conflating them is what let this gap hide.

I'm not resolving this — it's a real design decision, not something exploration should decide by default. Propose has two honest paths, and either is acceptable from where I sit:
1. **Rule it out explicitly:** skipping is not supported mid-session; a topic that no longer applies must be removed from the topic list before the session starts (FR-8.2). If this is the answer, it needs to be said plainly to facilitators, because it changes how they run pre-session prep.
2. **Design a real skip path:** a facilitator-explicit "skip this topic" action, distinct from and not reachable through the reveal→advance chain, that moves `session_topics.status` straight past `voting` without ever entering `revealed`.

What must not happen is this falling out of scope by default because the hard-`409` framing on the *other* scenario made this whole area sound settled. It didn't cover this case, and I should have said so the first time.

### 4.3 Action item finalization: confirmed — no new write needed

**Marcus (BA reviewer) checked this directly against the schema and the contract, independent of my read, and confirmed it: no new write is needed.** This is no longer an open question for Propose — it's a fact this document should have stated plainly the first time instead of hedging it.

Evidence Marcus verified: `action_items` (`migrations/2_create_tables.sql:134-150`) has no `finalized` or `finalized_at` column — there's nothing in the schema for a finalization write to target. `ACTION-004`'s own text defines "finalized" as belonging to a session whose `status = 'complete'` — a read-time join condition, not a stored flag. `stalenessLevel` (FR-7.4) is likewise computed at query time against `application_settings.staleness_threshold_sessions`, not committed by any write. Marcus also checked for a hidden write disguised as something else: a `stale`-related grep across the application turns up only `realtime/staleness-signal.ts`, a WebSocket *connection*-staleness close code that shares a word with FR-7.4 and nothing else — worth flagging so nobody chasing "stale" in the code mistakes that file for this.

**Action for Propose:** correct the "action item finalization" language in issue #26 and in the WebSocket change's dispatcher comments (`ws-pubsub.ts:92-94`, `ws-event-dispatcher.ts:230`) to say what's actually true — `topic_history_update`'s trigger for the wrap-up-adjacent case is the *session-complete* write (already built, already firing `session_state_change`), not a separate finalization event. This narrows `topic_history_update`'s real trigger set to one thing: topic-to-topic advance. State this explicitly in Propose's scope statement, traceably — don't just quietly drop the fourth deliverable my first pass implied might exist.

## 5. Decision (c): Membership removal

### 5.1 Authorization model

The REST API Contract has no endpoint for this at all — not a stub, not a documented-but-unimplemented route. That's different from reveal and topic-advance, where the *design* exists and only the *code* is missing. Here, Propose is doing real design work, not just wiring.

I'd anchor the authorization model to the closest existing precedent rather than invent a new one: **TEAM-005 (Update Team Member Role)**, whose authorization is `application_admin` (any team) OR `engineering_manager` with an active membership for that team (own team only). Membership removal is a strictly more consequential version of the same "who manages this team's roster" question TEAM-005 already answers, and the BRD's own authority for TEAM-005 (FR-1.6, "admin manages membership," extended 2026-03-15 to let EMs manage their own team) reads naturally as covering removal too — TEAM-005 changes a role; a removal is the limit case of changing someone's role to "not on this team anymore." I don't see a reason the facilitator should be able to remove a member — the facilitator's role in this system is consistently scoped to *session* actions, never team-roster actions (TEAM-001 through TEAM-006 are all admin/EM territory), and giving a facilitator-from-another-team the power to alter a team's permanent roster would cut against the entire arm's-length-facilitator design this application is built around. I'd treat "facilitator can remove a member" as something Propose should explicitly rule out, not leave ambiguous.

**Correction Marcus surfaced:** he verified TEAM-005's authorization text directly (REST API Contract.md:407-465) and confirmed the precedent is real, not reconstructed from memory — `application_admin` (any team) OR `engineering_manager` with active membership for that team (own team only), exactly as I described. But he also found that Appendix C's open-questions table has a stale entry that could mislead a future reader into doubting it: OQ-6 (line 2856) describes an authorization question about a "facilitator-only, non-member requirement" that has nothing to do with TEAM-005 as currently written — it reads like a leftover from an earlier draft that never got updated when the 2026-03-15 EM-extension decision landed. Propose should flag OQ-6 for correction or removal as a small housekeeping item alongside this change, so a future reader hitting it doesn't wrongly conclude TEAM-005's own authorization model is unsettled and therefore unsafe to anchor on. It isn't unsettled; the open question is just mislabeled.

**Concurrency guard, borrowed directly from precedent.** `TEAM-005`'s implementation (`teams.ts` lines ~494–510) already solved the "don't leave a team in an invalid state under concurrent modification" problem for role changes: lock every active membership row for the team with `SELECT ... FOR UPDATE` before evaluating a post-write guard, specifically to close a race where two concurrent admins could each pass a stale precondition check. Removal needs the identical guard for the identical reason: two concurrent removals targeting the last two participants of a two-person team could each read "count will still be ≥1 after my removal" against pre-transaction state and both proceed, leaving zero participants with no confirmation step ever triggered. This isn't a new risk this change invents — it's the same risk TEAM-005 already named and fixed, applied to a sibling operation on the same table.

**Zero-participant guard.** Following directly from the above: does removing the last active `participant` on a team require confirmation, the same way TEAM-005's role change does (`422` with `requiresConfirmation: true` when a role change would leave zero participants)? I'd say yes, for the same reason TEAM-005 has it — a team with zero participants can't run a session, and that state shouldn't be reachable silently.

### 5.2 Side effects — and the seam for issue #23

`requirements/BRD.md`'s own open-questions list already names this precisely, at OQ-5: *"When a member is removed from a team, are their open action items orphaned, reassigned, or flagged? Should the application block removal of a team member who has open action items?"* — and issue #23 is the tracked, BA-owned resolution of exactly that question, explicitly assigned to Marcus Delgado, explicitly not yet answered. I am not going to guess at an answer here. What I will say, because it's within my lane and issue #23's isn't:

- **This change must not silently orphan action items as an implementation default.** `action_items.owner_id` is `NOT NULL REFERENCES users(id)` — there's no schema-level "unowned" state, so a removal that doesn't address open-item ownership at all will leave `owner_id` pointing at a user who no longer has an active `team_memberships` row for that team. That's not a crash, but it is a silent gap: `VOTE-004` (reassign action item owner) already requires the *new* owner to be "an active `participant` member of the action item's team" — so a removed member's open items become permanently unreassignable through that endpoint's own validation (`422`, "New owner is not an active participant member") the moment they're removed, unless something reassigns or flags them at removal time.
- **The seam this design must leave, without resolving what goes in it:** the removal endpoint should be built so that "what happens to this member's open action items" is a clearly named extension point — a hook, a follow-up call, a documented TODO citing issue #23 by number, the same convention the WebSocket change used for issue #26 itself (`// TODO(#23): <specific behavior> once BA resolves reassignment authorization`). What I don't want is a removal endpoint that ships with *no* awareness that open items exist, forcing issue #23's eventual resolution to also mean re-opening this change's removal endpoint to retrofit the check. At minimum, the removal endpoint should query for open action items owned by the departing member as part of its own transaction (cheap — it's already touching `team_memberships` for this user) and surface the count, even if the *decision* of what to do with that count is deferred. That's a smaller commitment than "block or don't block," and it's one I think this change can and should make without stepping on the BA's decision.

**Specifics Marcus pushed me to pin down, and I agree these don't need to wait on issue #23:**
- **Response field name and shape:** `openActionItemCount: number` in the removal response, matching the `actionItemsFinalized: number` pattern SESSION-006 already established.
- **Whether a nonzero count blocks.** I'd recommend yes, via the same `422 { requiresConfirmation: true }` pattern TEAM-005 already uses for its zero-participant guard, rather than surfacing the count as purely informational. Silently letting someone remove a member who has open commitments, with no signal to the person clicking the button, is exactly the kind of silent gap that turns into a support ticket — and it's the kind of thing that erodes trust that the tool is keeping track of people's outstanding work. This is a UX/acceptance-condition decision Propose can make now; it's orthogonal to what issue #23 eventually decides should *happen* to those items.

### 5.3 What is out of scope, stated plainly

Whether removal blocks on open action items, whether reassignment is automatic or manual, and who besides the facilitator can trigger reassignment (VOTE-004 currently restricts this to `facilitator`, which OQ-5/issue #23 hasn't confirmed either) are issue #23's questions. This change should not answer them by default just because it happens to be the change touching the removal path first.

### 5.4 A gap this document didn't have, named by Priya: membership removal during a live session

Section 5's framing above treats removal as purely a roster-management event, decoupled from anything happening in a live session — true of the *trigger* (an EM handling an unrelated personnel matter has no reason to know a session is live), but not necessarily true of the *effect*, if the event happens to land while a session is running.

Priya (Facilitator reviewer) put the concrete scenario in front of me: a session is in progress, and an EM removes someone from the team mid-topic. What happens to that person's WebSocket connection? Does the facilitator's readiness grid just show a vote count that no longer adds up — "waiting on 1 of 8" when it's actually 1 of 7 — with no signal about why? If the removed member had already locked in a vote for the current topic, does it survive to reveal, or does it silently vanish? If a reveal is in flight when this happens, does it change what gets published?

I'm not resolving this — it sits at the boundary of both changes (session runtime state, which this document owns, and membership removal, which the sibling document owns), and it's genuinely a design question, not a documentation gap I can close from this seat. But it deserves the same explicit, named, has-an-owner treatment the issue #23 seam got in Section 5.2, rather than staying invisible until the first live team hits it.

**Naming it here as an open question for Propose:** what should happen, on both the connection-handling side and the facilitator-visible readiness-grid side, when a team membership removal lands for a user who is an active participant in a running session. Both change documents (topic-lifecycle and membership-removal) should cross-reference this open question rather than let either one silently assume the other handles it.

## 6. The integration contract this change owes the WebSocket change

This isn't optional context — it's a set of constraints the archived `websocket-delivery-time-authorization` change already committed to in writing, on the assumption that this change would eventually exist and honor them:

- **Publish-after-commit ordering, no exceptions.** For every one of these new writes, the corresponding `redis.publish(...)` call must execute only after the enclosing transaction's `COMMIT` succeeds — never before `BEGIN`, never between a query and `COMMIT`. This is stated repeatedly and forcefully in the WebSocket change's design.md (Decision D7) and tasks.md (1.4, 7.2, 7.3, 7.6) because the alternative — a subscriber notified of a state change that a later statement in the same transaction rolls back — corrupts the one guarantee that whole change exists to provide: a delivered event always corresponds to a committed state.
- **Route through the existing helper-plus-serializer contract, not a parallel implementation.** The reveal write's downstream payload must go through `serializeForFacilitator`/`serializeForMemberParticipant` (`team-content-serializers.ts`) — already built, already the thing that enforces the pre-reveal/post-reveal boundary — not a new independently-written payload construction. This is Decision D4 of the WebSocket design, and it exists specifically so the two-layer enforcement (authorization check + serializer) doesn't become two different implementations of the same layer.
- **Use the `teams.ts` transaction pattern, not a bare `db.query` call.** All three of the currently-bare-query handlers this change touches (`facilitator-sessions.ts`'s reveal and topic-advance-family endpoints, and whatever new membership-removal endpoint) need the explicit `db.connect()` → `BEGIN` → queries → `COMMIT`/`ROLLBACK`/`release` pattern already established at `teams.ts` lines ~494–577 and ~767–812, both for the audit-log atomicity this requires and for the row-locking pattern Section 5.1 needs for membership removal.
- **Wire into the exact stubbed hooks that are already unit-tested and waiting.** `recordRevealTriggeredAudit` (`facilitator-sessions.ts` lines 31–63) and the `TODO(#26)`-annotated exports in `ws-pubsub.ts`, `ws-event-dispatcher.ts`, and `vote-revealed-payload.ts` are not placeholders to be rewritten — they're finished, tested code waiting for exactly the commit points this change produces. Wiring them in should be closer to "add one function call at the right point in a new transaction" than "build new integration code."
- **Recommended (not required) guard, named by the WebSocket change's own Security Analyst review, for this change to consider adopting:** a startup or unit-test-level assertion that any code path publishing `vote_revealed` or `topic_history_update` in production has a corresponding delivery-time authorization check inline before `.send()` — mirroring the existing `timing-oracle.ts` production-boot guard. This isn't required for this change to be complete, but the WebSocket change's own design.md explicitly recommended it be considered here, and I think it's cheap insurance against exactly the kind of "someone adds a fifth publish call two years from now and forgets the check" drift this whole review chain exists to prevent.

## 7. REST-triggered vs. WebSocket-triggered reveal — and the wider Appendix D problem Marcus found

My first pass treated this as one stray line: the REST API Contract's own text for `VOTE-003` says, plainly, *"The reveal itself is triggered via WebSocket (`reveal.trigger`), not this endpoint."* That's a different transport than what's actually implemented: `POST /api/v1/teams/:teamId/sessions/:sessionId/reveal` is a REST endpoint, already built, already handling authorization and state-precondition validation, and it's the endpoint the WebSocket change's own design explicitly plans to attach the missing write to (design.md's Blocking Dependency section, tasks 7.2/7.4).

**Marcus checked further and found the actual scope is bigger: this isn't a stray note, it's a dedicated section of the contract that formally excludes something already built.** Appendix D ("Endpoints Explicitly Excluded from HTTP REST," lines 2862–2873) states that the following behaviors "must NOT be implemented as REST endpoints... Implementing them as REST would violate the simultaneous reveal integrity requirement (BRD Section 6.1)" — and the table lists **both** `reveal.trigger` and `topic.advance`. That second one matters directly to this change: Section 4.2 above plans to build session-phase entry (`SESSION-004`/`SESSION-005`) and topic-to-topic advance as REST endpoints, and `SESSION-004`/`SESSION-005` are **already formally specified as REST endpoints in this same contract**, performing advance-shaped transitions and firing WS broadcasts for fan-out. The contract contradicts itself internally, independent of what code exists.

Marcus went back to BRD 6.1's actual text to settle which side is authoritative, since Appendix D cites it as its reason. BRD 6.1 requires that votes not yet revealed stay unreadable and that the reveal be "a single, server-triggered event that makes all votes visible simultaneously" — a requirement on *delivery*, not on the transport of the facilitator's own trigger action. A REST call from the facilitator's authenticated client, followed by a transaction commit and a single Redis-publish-triggered WebSocket broadcast to everyone connected, satisfies that requirement exactly as well as a WebSocket-native trigger would. The simultaneity guarantee lives in the fan-out step — WebSocket either way — not in whether the facilitator's button-click is an HTTP POST or a WS frame.

**Marcus's conclusion, which I'm adopting as this document's recommendation rather than leaving open: Appendix D over-applies BRD 6.1.** It's correct to exclude vote *submission* from REST (`vote.submit` — HTTP polling would expose vote timing to observers, a real and different concern) — that exclusion stays untouched, its rationale doesn't share this flaw. But extending the same exclusion to the *trigger* actions for reveal and topic-advance isn't supported by BRD 6.1's actual text, and it directly conflicts with `SESSION-004`/`SESSION-005` already being specified as REST in the same document.

**This is now an explicit task for Propose, not a silent side-fix bundled into "implement the reveal endpoint":**
1. Rewrite Appendix D's `reveal.trigger` and `topic.advance` rows to describe the actual architecture — privileged trigger via authenticated REST call, single simultaneous WebSocket broadcast for fan-out, publish-after-commit — and narrow the rationale column so it no longer implies the trigger transport itself is the integrity mechanism.
2. Correct `VOTE-003`'s note (line 1924) to match.
3. Leave `vote.submit`'s REST exclusion untouched.

This doesn't need its own tracked change — it's a same-document correction directly caused by and scoped to the transitions this change wires up, and no other in-flight change depends on Appendix D's current text. But it needs to be a visible task with a trail back to the reasoning above, not just an updated line with no explanation, so a reviewer checking the contract against BRD 6.1 during this change's review can see why.

## 8. Summary for whoever picks this up next

- **Split into two changes:** session topic lifecycle (reveal, topic advance including the session-phase entry points, and action-item finalization) as one change; team membership removal as a separate change. Don't bundle, don't split further. Both documents should explicitly note that `VOTE-004`/reassignment stays untouched and reserved for issue #23, so action-item-continuity requirements don't end up implicitly split across two documents with no cross-reference.
- **The topic-lifecycle change's real scope is bigger than issue #26's literal list:** it needs `lobby→pre_session` and `pre_session→active` — two distinct, meaningfully-labeled facilitator actions per FR-3, not a collapsed generic transition, with FR-3.5's no-open-items case as a genuine one-click pass-through — topic-to-topic advance, entry into `wrap_up` (confirmed undesigned, no endpoint ID anywhere in the contract — real design work, not just wiring), and the reveal write.
- **Action item finalization is confirmed to need no new write.** Verified directly against schema and contract: no `finalized`/`finalized_at` column exists, and finalization is a read-time join on session status. `topic_history_update`'s real trigger narrows to topic-to-topic advance only; the session-complete write already fires `session_state_change`.
- **Reveal and topic-advance both need explicit precondition guards** (no re-reveal of an already-revealed topic, no advance past an unrevealed topic) and row-level concurrency protection, following the exact pattern `teams.ts` already established for role changes. These aren't optional hardening — FR-4.7 (vote immutability) and the entire simultaneous-reveal guarantee depend on the reveal being a genuine one-way gate, not a convention nobody enforced. **These 409s must also be specified as non-alarming, non-error states on the facilitator's screen** — a UX requirement, not just an API contract detail (Section 4.1).
- **Open decision, not settled by the hard-precondition framing above:** whether a facilitator can skip a topic entirely, without voting, mid-session. Either rule it out explicitly (manage via topic-list edits before the session, per FR-8.2) or design a real facilitator-initiated skip path. Don't let this fall out of scope by default (Section 4.2).
- **No tie-breaking mechanism is needed or should be built** — none of the three vote types produce a value a tie applies to.
- **Membership removal's authorization model should mirror TEAM-005** (admin any team, EM own team, facilitator excluded), with the same zero-participant confirmation guard and row-locking discipline TEAM-005 already uses. Flag Appendix C's OQ-6 as a stale/mismatched entry that could otherwise cast false doubt on this precedent.
- **Membership removal must leave an explicit, named seam for issue #23** (open action item reassignment) — surface the open-item count (`openActionItemCount: number`, matching the `actionItemsFinalized` pattern) as part of removal, and require confirmation (`422 requiresConfirmation: true`, TEAM-005-style) on a nonzero count. Don't decide reassignment policy; don't ship blind to the question either.
- **Open question, unresolved here, needs an owner:** what happens when a membership removal lands while that person is an active participant in a running session — connection handling, in-flight vote handling, facilitator-visible readiness-grid consistency. Named the same way the issue #23 seam is named, not left invisible until a live team hits it (Section 5.4).
- **Every new write in the topic-lifecycle change must honor the WebSocket change's existing integration contract**: publish-after-commit ordering, the `teams.ts` transaction pattern, reuse of `serializeForFacilitator`/`serializeForMemberParticipant`, and wiring into the specific `TODO(#26)`-annotated hooks that are already built and unit-tested and waiting — `recordRevealTriggeredAudit` chief among them.
- **Appendix D of the REST API Contract formally, and incorrectly, excludes both `reveal.trigger` and `topic.advance` from REST**, on a rationale (BRD 6.1) that only supports excluding delivery, not trigger transport — and it already self-contradicts `SESSION-004`/`SESSION-005` in the same document. Correct Appendix D's rows for both, and `VOTE-003`'s note, as an explicit Propose task; leave `vote.submit`'s REST exclusion untouched.
- **What must not happen:** treating this as "add four `UPDATE` statements." Each of the topic-lifecycle transitions needs an explicit precondition and concurrency answer this document has tried to force into the open rather than leave implicit; membership removal needs real (if narrow) design work the REST API Contract never did; and both need to land inside the transaction and publish-ordering discipline the WebSocket change is already depending on.
