## Context

`reauth-required-client-prompt` (archived 2026-09-18) shipped the `reauth-required` mechanism — CTA, `role="alert"`, persistence, D9's shared `ReauthRequiredTreatment.tsx` — but deliberately deferred its visual register and sign-off to "Group 6" of that change's own tasks.md, mirroring the pattern `websocket-staleness-signal` had already set for `unknown-reconnecting`'s grid marker (issue #36). That gate exists specifically to prevent a placeholder from being treated as a decision. A prior simulated sign-off attempt against #36's placeholder was correctly withheld — the placeholder committed to nothing, so no register judgment was possible from it. `ReauthRequiredTreatment.tsx`'s current styling (`border: "2px solid currentColor"`) is the identical shape of artifact: distinct-from-neutral in a token sense, but not a candidate register anyone — real or simulated — can form a felt judgment about.

This change's stage-1 exploration (`exploration-notes.md`, incorporating two rounds of review from Priya Nair and Marcus Delgado) confirmed this directly by reading the component and its own header comment, which states plainly that final styling "is not implemented here." That exploration is the input to this design; nothing here relitigates its conclusions.

## Goals / Non-Goals

**Goals:**
- Replace the placeholder border with a real, committed visual register (color, weight, icon-or-no-icon decision) implemented in `ReauthRequiredTreatment.tsx`.
- Render that register through both real host surfaces — `SessionConnectionHost.tsx` and `FacilitatorConnectionHost.tsx` — not a bare/isolated instance of the subcomponent, matching the review discipline `reauthRequiredHostParity.test.tsx` already established for the mechanism.
- Produce two sign-off artifacts (mock, copy-in-layout) that are honest, checkable, and bounded to what a persona-simulated review can actually judge — explicit about which host(s) each verdict covers, explicit about mechanical-vs-felt judgments, and explicit that a positive outcome here is not evidence toward #142.
- Land the copy sign-off and stale-comment cleanup for #137/#138, which per exploration is substantively close to done — mostly a sign-off-against-the-real-mock-plus-comment-cleanup exercise, not a copywriting exercise.

**Non-Goals:**
- #142 (live usability test — "reads as an alarm without failing to be noticed," evaluated by a real facilitator in a real session) and #143 (blocked on #142). Neither is attempted, simulated, or partially satisfied here. Per Priya's review, #142's eventual test plan must separately cover near-reveal timing (the highest-friction moment, since D6 keeps this mechanism deliberately blind to reveal state) and screen-reader/modality (where "reads as an alarm" is an ARIA-announcement question, not a color question) — neither of which this change's visual-register work can stand in for.
- Building a richer session-screen mock than the two existing hosts provide. `SessionConnectionHost.tsx` and `FacilitatorConnectionHost.tsx` are both deliberately minimal (no topic display, no vote UI, no reveal state) per their own comments and `websocket-staleness-signal`'s design.md Non-Goals — building that out is other, deferred work. "Actual layout" for this change's sign-off purposes means the real hosts, driven by a real (faked-socket) state transition, not an idealized future session screen.
- Resolving issue #33 (facilitator-disconnect blast radius). Out of scope for this gate; named as a risk below so it isn't an implicit casualty of #137–#141 closing.
- Re-opening any settled mechanism decision from `reauth-required-client-prompt` (state machine, ARIA role, CTA, persistence, D6's reveal-blindness). This change touches visual presentation and sign-off status only.

## Decisions

### D1. The register is real implementation work, not a design mock

#139 cannot be satisfied by pointing at the existing placeholder or by producing a static image mock disconnected from the codebase. It must be an actual code change to `ReauthRequiredTreatment.tsx` — a committed color, weight, and icon-or-no-icon decision — because #140/#141's sign-off needs something to review that behaves like the shipped artifact will behave (same DOM, same cascade context, same host chrome), not a proxy for it. This mirrors why `reauthRequiredHostParity.test.tsx` mounts the real hosts rather than the bare subcomponent.

**Alternative considered:** produce a static visual mock (e.g., an image or isolated Storybook-style rendering) for Priya's review, then implement afterward if signed off. Rejected: this reintroduces the exact gap Marcus Oyelaran's engineer design-review caught once already (Finding 1, `reauth-required-client-prompt`) — reviewing something structurally different from what ships risks a sign-off that doesn't transfer to the real DOM/cascade context. The real hosts are cheap enough to render against directly; there's no reason to review a proxy.

### D2. Register direction: amber/warning-toned, not red/error-toned; icon from a starting allow-list, not a closed one

Per exploration §6, the color direction is amber/warning register rather than red/error register — a saturated red-plus-exclamation-triangle risks reading as an *error*, which D4's checklist item 4 already rules out for the copy (no "error" string, no "!"); the visual register must not contradict that by putting error-register color language next to non-error-register text. Icon choice is checked against a starting, non-exhaustive allow-list — a closed-lock glyph, a sign-in-arrow glyph, or no icon at all — none of which reads as a duration or countdown under any reasonable interpretation. This list is a starting point the implementer may extend; the bar for anything outside it is "does a careful reviewer, real or simulated, agree it doesn't echo a countdown," not membership in this specific list.

**Alternative considered:** a closed, exhaustive icon list. Rejected per exploration's own reasoning — declaring a final icon is a decision for whoever implements #139 against the real hosts, informed by how it actually looks, not something to fix in a planning document before any candidate has been rendered.

**Implementation constraints on the icon (per engineer and security design review):**
- The digit-pattern test (`ReauthRequiredTreatment.test.tsx`) scans `container.innerHTML`, not just visible text — it therefore also sees attribute values. Any accessible name given to the icon (an SVG `<title>`, an `aria-label`, a `title` attribute) must avoid the same digit+time-unit patterns the copy text already avoids (e.g. a careless icon-library title like "reauth in 5 min" would trip the existing test; "closed lock icon" would not).
- Prefer an inline SVG with `fill="currentColor"` over a Unicode glyph. A glyph like a lock emoji can render with forced color-emoji presentation in some fonts/browsers, which would visually fight a color applied via CSS `color` since glyph color wouldn't inherit; inline SVG avoids this failure mode and costs little given the component has no build-time SVG tooling to wire up.
- Reuse the existing amber/warning color precedent — `MemberManagement.tsx`'s `#fff3e0` background / `#ffb74d` border — rather than inventing an unrelated warning-color pair, keeping the app's color vocabulary from growing for no reason.
- Forward-looking, non-blocking: if implementation pulls in a new third-party icon library rather than an inline SVG or an existing in-tree pattern, that is a new dependency and should go through the same dependency-hygiene expectation as any other addition (known-vulnerability tracking, not a one-time add-and-forget). Not a requirement of this design — noted so it isn't an unexamined side effect of Group 1's implementation.

### D3. No-animation constraint is checked mechanically, not judged — and enforced by a standing test, not a one-time grep

The negative constraint that the mock must contain no animated element whose duration/timing approximates the grace period (D3 of the prior change, restated at #140's checklist item 2) is a yes/no mechanical check — `animation`, `transition`, `@keyframes`, any duration value tied to elapsed time — not a felt judgment. This is deliberately kept separate from the assertive-vs-alarming felt judgment in the sign-off template (D5 below), so the artifact doesn't read as uniformly confident when parts of it are mechanically certain and parts aren't.

Per Tomás Ferreira's security design review: a one-time manual grep at implementation/sign-off time is not sufficient enforcement, because nothing would stop a later, unrelated change (a hover effect, a subtle attention pulse) from reintroducing a countdown-surrogate animation without anyone re-running the check. This constraint is therefore implemented as a standing, CI-enforced automated test — co-located with the existing digit-pattern test in `ReauthRequiredTreatment.test.tsx` — asserting the rendered output contains no `animation`, `transition`, `@keyframes`, or elapsed-time-tied duration property. Group 1's self-check (task 1.3) and Group 2's sign-off (task 2.2) both cite this test's passing result as their evidence, rather than an ad hoc grep performed only at sign-off time.

**Known limitation (per Tomás Ferreira's implementation-stage security review):** this test inspects a single static render's serialized markup, so it has no visibility into a future JS-driven style mutation (e.g. a `setInterval` or `requestAnimationFrame` loop that adjusts a style property without ever writing the literal words `animation`, `transition`, or `duration`). The component has no hooks or effects today, so this is not a live risk, but it is an accepted blind spot rather than a closed one — a future change that adds imperative, time-driven styling to this component must be reviewed against this constraint by other means, since this test alone would not catch it.

**File scope:** the test (and the self-check that precedes it) must inspect wherever the visual register's styling actually lives, not only `ReauthRequiredTreatment.tsx` read as source. Today that's the component's inline `style={{...}}` object, which the digit-pattern test's `innerHTML` check already has full visibility into, since React serializes inline styles into the DOM's `style` attribute. If Group 1 (or any later change) moves styling to an external stylesheet or CSS Module, an `innerHTML` check has no visibility into rules defined there — a class name in `innerHTML` carries no textual trace of what that class does — and both the digit-pattern check and the no-animation check must be extended to inspect that file directly. This applies to both checks equally; neither is exempt just because it currently passes under the inline-style pattern.

### D4. Sign-off artifacts follow the fixed template from exploration §3a

Both #140 and #141's sign-off artifacts use the same fixed shape, in this order: (1) per-bound verdict against the relevant checklist, one line each with cited evidence (a screenshot description, a CSS property, a DOM check — not an assertion); (2) the no-animation negative constraint, cited not asserted (mock sign-off only); (3) a clearly separated "felt judgment — persona-simulated, not equivalent to a real facilitator's read" section covering the assertive-vs-alarming call; (4) one closing line using exactly one of `Signed off`, `Withheld — <reason>`, `Signed off with conditions — <conditions>`; (5) the standing disclaimer paragraph, unparaphrased across runs. This is adopted as-is from exploration rather than re-derived, so the artifacts are executable rather than merely directionally correct.

**Why a fixed template over "produce an honest verdict, whatever it is":** the latter is a correct mindset but not an acceptance condition — it doesn't specify what shape the note takes, which risks each run inventing its own format and losing comparability across #140, #141, and any future gate that reuses this pattern (e.g., #36's eventual re-attempt).

### D5. D4 (copy tone) is split into a mechanical check and a felt check, and stays split at sign-off

`reauth-required-client-prompt`'s D4 checklist item 4 ("tone register appropriate to an expected token-lifetime event, not an error condition") bundles a mechanical negative check (no "error" string, no "!" — already CI-enforced and passing) with a felt judgment (does it read as *assertive*, not merely absent-of-alarm-words — calm-to-the-point-of-passive is a different failure mode than alarming, and the shipped sentence clears the mechanical bar without the felt bar necessarily being cleared). #141's sign-off evaluates the felt half explicitly, in the felt-judgment section per D4 above, rather than letting a checklist row imply a felt call was already made.

Per Tomás Ferreira's security design review: D2's icon allow-list is deliberately open-ended, with the bar for anything outside the starting three options being a felt judgment ("does a careful reviewer agree it doesn't echo a countdown") rather than a mechanical one — there is no test equivalent to the digit-pattern check for "does this glyph look like a countdown." The mock sign-off's felt-judgment section (#140, task 2.3) therefore explicitly includes screening the chosen icon's shape for countdown-adjacent forms — clock, hourglass, gauge, dial, or anything else that visually implies elapsed or remaining time — in addition to, not instead of, the assertive-vs-alarming tone call this section already covers. A felt-judgment section silent on icon shape is treated as incomplete for #140, the same way D6 treats a verdict silent on host coverage as incomplete rather than conservative.

### D6. Host-pairing: a verdict covers only the host(s) it was actually reviewed against

`SessionConnectionHost.tsx`'s participant banner and `FacilitatorConnectionHost.tsx`'s facilitator grid-replacement are different visual contexts — different surrounding chrome, different sibling elements, a lone banner vs. one cell in a stub grid — and a register that reads correctly in one does not automatically carry to the other, the same reasoning `reauthRequiredHostParity.test.tsx` already applies to the mechanism. #139's mock is rendered through both real hosts; #140/#141's sign-off artifacts name explicitly which host(s) each verdict covers. A sign-off silent on host coverage is treated as incomplete, not as implicitly covering both.

### D7. Comment cleanup is conditioned on the sign-off outcome, not scheduled unconditionally

`ReauthRequiredTreatment.tsx`'s "STYLING IS A PLACEHOLDER" / "COPY IS NOT FINAL" header comments, and `ConnectionStatusBanner.tsx`'s stale "both strings below are placeholders" framing, are only updated if #140/#141 land as `Signed off` or `Signed off with conditions` (conditions addressed). If either sign-off is `Withheld`, the comments stay as-is — they are currently accurate, and updating them to claim finality against a withheld verdict would be the exact false-positive failure mode this whole gate exists to prevent.

### D8. spec.md's status notes are updated to reflect the actual, possibly-partial outcome

`specs/websocket-staleness-signal/spec.md`'s "Pilot-readiness gate" requirement's descriptive "Current status" text is updated once #140/#141's actual verdicts are known — not written in advance to presuppose a clean pass. If either sign-off is withheld, the status text says so plainly, names the reason, and continues to state that #142/#143 (and now, conditionally, #140/#141) remain open. The gate's normative SHALL text is unchanged; only the descriptive status narration is delta'd.

## Non-blocking observation (not a task in this change)

The #136–#143 dependency order — copy/comment cleanup before mock, mock before mock sign-off, mock sign-off and copy sign-off before live usability test — is currently enforced only in prose, in `exploration-notes.md` §3 and in issue #136's own body text. None of #137–#143's GitHub issues have their structured `blocked-by`/`blocking` fields populated, so GitHub's own "show unblocked work" filtering would currently present #137, #139, #140, and #141 as simultaneously startable, which contradicts the order this design (and the exploration it builds on) assumes. This change does not wire those links — that's project-tooling work, not planning or implementation work for this gate — but flags it so it isn't silently assumed fixed. Whoever has write access to issue metadata should either wire the links or consciously accept prose-only enforcement going forward.

## Risks / Trade-offs

- **Closing four issue numbers reads as more progress than it is if the register isn't genuinely committed.** → D1: no sign-off is attempted against anything short of a real, host-rendered register; if the implementer can't produce that, #139/#140 stay open rather than being closed against a border-only placeholder.
- **A simulated sign-off, once written down, gets cited later as equivalent to Priya's real review.** → D4's template includes the standing disclaimer in every artifact, unparaphrased; this design and the proposal both state explicitly that a clean #140/#141 pass is not evidence toward #142.
- **The register drifts toward error-register color/icon to maximize noticeability, undermining D4's tone bound and the "doesn't feel like alarm software" concern.** → D2: amber/warning direction, icon checked against the starting allow-list rather than an open-ended judgment call.
- **"Actual layout" gets satisfied by rendering the subcomponent in a test file's isolated `render()` call and calling that sufficient.** → D1/D6: review is against the real `SessionConnectionHost`/`FacilitatorConnectionHost`, driven through a real state transition, matching `reauthRequiredHostParity.test.tsx`'s existing pattern.
- **Issue #33 (facilitator-disconnect blast radius) quietly falls off the backlog because closing #136's visible sub-issues reads as "the reconnection-signal problem is handled."** → Named explicitly in this document and in proposal.md's Impact section; this change does not resolve or claim to resolve it.
- **A withheld or conditional #140/#141 verdict gets treated as this change's failure rather than its intended honest outcome.** → Both proposal.md and this design state up front that withheld is an acceptable, expected-possible outcome; tasks.md's Group 3/4 completion criteria are written to accommodate it (see tasks.md).

## Migration Plan

Not applicable in the deploy/rollback sense — this change alters presentation and sign-off documentation within an already-shipped, flag-free component. If a positive sign-off lands, the visual register ships as part of the normal build; if withheld, the placeholder styling remains shipped exactly as it is today (no regression, no rollback needed) and the gate stays open.

None outstanding that this change can resolve — the substantive open question ("what does the final register look like, and does it clear sign-off") is the work of Groups 2–4 in tasks.md, not a question to pre-answer here.
