# Engineer Design Review — reauth-required-copy-and-visual-signoff

**Reviewer:** Marcus Oyelaran (Full Stack Engineer persona)
**Scope:** design.md, proposal.md, tasks.md against the real code at `ReauthRequiredTreatment.tsx`, `ConnectionStatusBanner.tsx`, `FacilitatorReadinessGrid.tsx`, `SessionConnectionHost.tsx`, `FacilitatorConnectionHost.tsx`, and the existing test suite (`ReauthRequiredTreatment.test.tsx`, `reauthRequiredHostParity.test.tsx`, `ConnectionStatusBanner.test.tsx`, `FacilitatorReadinessGrid.test.tsx`).

## Verdict

Implementable as designed. No structural change to the component's prop surface or the host wiring is required. I have one finding worth fixing before implementation starts (icon accessible-name interaction with the digit-pattern test) and a few observations that don't block but should inform how #139 gets built.

## 1. D9 compliance — is the register implementable without new props?

Yes, cleanly. `ReauthRequiredTreatment.tsx:94-110` has exactly two props today — `returnTo` and `role` — and D9's rule is "no props derived from cause/role/session-moment state beyond the already-existing exceptions." A visual register (color, weight, icon) is a **constant** the component renders unconditionally, not a value derived from any of those three things. It doesn't need a third prop; it replaces the fixed `REAUTH_REQUIRED_STYLE` object at line 89-92 with a richer fixed style object (or a style object plus a fixed icon element), the same shape the placeholder already has. `role` still only gates the vote-loss sentence (line 113-114); nothing about the register logic needs to branch on it. So D9 is not at risk from this work as scoped — the risk would only appear if an implementer got clever and, say, varied icon or color by role "for extra polish," which the design correctly doesn't ask for and I'd flag in code review if I saw it.

One structural note for whoever implements #139: since the register is a fixed constant, it costs nothing to keep it exported as a named constant (mirroring `REAUTH_REQUIRED_STYLE`'s current pattern) rather than inlining it in the JSX — keeps the "what is the committed register" question answerable by reading one binding, which matters for #140's sign-off (reviewers should be able to cite "the value of X" as evidence, per D4's evidence-citation discipline).

## 2. Test breakage risk

**Host-parity test (`reauthRequiredHostParity.test.tsx`) — safe.** It does a byte-for-byte `outerHTML` diff between the participant and facilitator renders, with the vote-loss sentence explicitly stripped out before comparing (lines 80-85). Since both hosts render the same `ReauthRequiredTreatment` component with the same fixed style/icon, any register change is present identically on both sides of the diff — it doesn't touch the one dimension (`role`) this test discriminates on. This test only breaks if the register is made to vary by role, which nothing in the design calls for.

**Digit-pattern test (`ReauthRequiredTreatment.test.tsx:10-19`) — real risk, needs a specific caution.** This test checks `container.innerHTML` (not just visible text) against `/\d+\s*(s|sec|second|m|min|minute)s?\b/i`, explicitly covering attribute values per Tomás's security-review widening. This is the constraint that actually threatens icon work, not the ARIA/role tests. Concretely: an inline SVG `<title>`, an `aria-label`, or a `title` attribute on the icon that happens to read like "closed lock icon" is fine, but something like "sign in" is fine too — the risk case is a careless accessible name like "reauth in 5 min" or a copy-pasted icon-library title containing a version string or size token (e.g. some icon sets embed `24x24` — that wouldn't match the pattern since `x` isn't a time unit, but it's the class of mistake to watch for). This is a narrow, mechanical thing to check, not a design flaw — I'm flagging it as a task-1.2-adjacent self-check the implementer should run explicitly, not just infer from the design doc, since design.md doesn't call it out by name and it's not obviously implied by D3's animation-only framing.

**ARIA role test (`ConnectionStatusBanner.test.tsx:206-227`, `FacilitatorReadinessGrid.test.tsx:245-265`) — safe if the icon is decorative.** Both assert `getByRole("alert")` and `getByRole("button", { name: /log in again/i })` continue to resolve. An icon rendered as `aria-hidden="true"` (the standard pattern for a purely decorative glyph next to text that already conveys the same meaning) doesn't interact with either query. The one thing to avoid: don't give the icon its own `role` or make it focusable — nothing in the design suggests that, but it's worth stating as a constraint since it's not yet written down anywhere. I'd also flag `ConnectionStatusBanner.test.tsx:242`'s `expect(container.querySelector("[aria-modal]")).toBeNull()` — a completely inert check today, but worth the implementer's awareness that D1's non-modal constraint is partially test-enforced, so nothing in the register work should add `aria-modal` or wrap the treatment in anything dialog-shaped.

## 3. Icon allow-list — concrete enough to implement without further design decisions?

Mostly yes, with one gap worth naming rather than silently working around. D2/exploration §6 gives three named options (closed-lock glyph, sign-in-arrow glyph, no icon) plus an open-ended "or a justified alternative if a careful reviewer agrees it doesn't echo a countdown." That's enough to start — it isn't enough to fully determine the *mechanism* by which an icon gets rendered, because the codebase has no icon library dependency today (checked `packages/frontend/package.json`: no lucide/heroicons/etc., no SVG loader configured) and no existing icon usage to follow as precedent — the closest analog is `FacilitatorReadinessGrid.tsx:104`'s plain Unicode `"○"` character for the stale marker. So the implementer has two realistic paths — a Unicode glyph (🔒, →, or similar) styled via the existing inline-style-object convention, or a small hand-written inline `<svg>` — and the design doesn't pick between them. I don't think it needs to; this is exactly the kind of "informed by how it actually looks" call D2 explicitly reserves for implementation, and both paths are cheap and reversible. I'm noting it so it's a conscious choice at implementation time rather than something that reads as pre-decided and then gets second-guessed at sign-off.

If a Unicode glyph is chosen, double-check it renders consistently in whatever the sign-off screenshots are taken in — some emoji-presentation glyphs (e.g. a lock emoji) render with forced color emoji presentation in some fonts/browsers, which could visually fight an amber/warning color applied via CSS `color` (glyph color wouldn't inherit). An inline SVG with `fill="currentColor"` avoids that failure mode entirely and is a two-minute addition given the component already has no build-time SVG tooling to wire up. I'd lean the implementer toward inline SVG for this specific reason, though I wouldn't block on it — it's a quality note, not a correctness one.

## 4. Hidden coupling risk between the styling work and the sign-off artifacts

The design's own D1/D6 answer this directly and I agree with the mechanism: because #140/#141 review the real hosts (not an isolated render), and because `reauthRequiredHostParity.test.tsx` already enforces that both hosts render identically apart from the vote-loss sentence, there's no plausible path for the mock and the shipped implementation to drift *after* sign-off — they're the same code path, not a copy. The drift risk that does exist is narrower than "mock vs. shipped": it's *between the sign-off artifact's prose and the code at the moment of signing*, if the implementation changes after #140/#141 are written but before #139/tasks Group 4 land. Tasks.md's task 4.0 (cite the specific diff/property/screenshot for any stated conditions) is the right mitigation for this and I don't have anything to add beyond making sure whoever executes Group 4 actually re-reads the current component rather than trusting the sign-off artifact's description of it — the artifact is evidence about a point in time, not a live spec.

One boundary-clarity note, not a coupling risk: proposal.md's Impact section says `SessionConnectionHost.tsx`/`FacilitatorConnectionHost.tsx` have "no changes expected." I confirmed this by reading both files (`SessionConnectionHost.tsx:39-44`, `FacilitatorConnectionHost.tsx:40-47`) — they pass `state`/`role` through and render the child unconditionally; nothing about a register change touches them. Correct as stated.

## 5. Error paths / missing cases

Nothing missing at the mechanism level — D6's reveal-blindness, D3's no-animation constraint, and the CTA/persistence behavior are all untouched by a styling-only change, and the design correctly scopes itself away from all of them. Two small implementation-time notes, neither of which needs a design change:

- The codebase already has an amber/warning color precedent worth reusing rather than inventing new values: `MemberManagement.tsx:353-354` (`backgroundColor: "#fff3e0"`, `border: "1px solid #ffb74d"`, its own `zero-participant-warning` test id) and `PreSessionActionItemReview.tsx:36-38`'s `STALENESS_COLORS` (`yellow: "#f9a825"`, `orange: "#ef6c00"`). Reusing one of these (or a value drawn from the same family) rather than picking an unrelated amber keeps the app's color vocabulary from growing an unrelated warning-color pair for no reason — a minor "code the next engineer can extend" concern, not a blocker.
- `REAUTH_REQUIRED_STYLE` is a module-level plain object today, recreated once, not per render — the current placeholder already gets this right (no inline object literal in JSX, so no unnecessary re-render churn). Whatever replaces it should keep that shape rather than moving to an inline literal in the `style={{...}}` position, for the same reason.

## Summary

- D9: not at risk. No new props needed; the register is a fixed constant like the placeholder it replaces.
- Host-parity test: safe by construction (role-blind register, role-only diff).
- ARIA-role test: safe if the icon is `aria-hidden` and non-interactive, which nothing in the design contradicts.
- Digit-pattern test: the one real risk, and it's about the icon's *accessible name* (title/aria-label), not its visual form — flagging as an explicit self-check for whoever implements #139, since design.md doesn't name this test by name and it's easy to only think about the animation-duration angle when reading D3.
- Icon mechanism: two viable paths (Unicode glyph vs. inline SVG), correctly left open by the design; I'd lean toward inline SVG with `fill="currentColor"` to avoid emoji-presentation color-fighting, but this is a recommendation, not a finding.
- Mock/shipped drift: not a real risk given D1/D6's real-host review discipline; the actual risk is artifact-vs.-code drift across time, already mitigated by tasks.md 4.0.
