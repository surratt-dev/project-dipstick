# Security Review — Design Stage (reauth-required-copy-and-visual-signoff)

**Reviewer:** Tomás Ferreira (Security Analyst persona), Stage 3 review
**Verified against:** design.md, proposal.md, tasks.md, `ReauthRequiredTreatment.tsx`, `ConnectionStatusBanner.tsx`, `ReauthRequiredTreatment.test.tsx`, `reauthRequiredHostParity.test.tsx`, `SessionConnectionHost.tsx`, `FacilitatorConnectionHost.tsx`, and the archived `reauth-required-client-prompt` design.md (Decisions D2–D9, particularly D3 and D9, which this change's constraints build on).

**Bottom line:** this design does not reopen the disclosure boundary I flagged in the prior review, and its structural choices (no cause/session-moment props on the shared subcomponent, fixed `/auth/login` literal, no new WebSocket or auth surface) keep the security-relevant properties I care about intact. I have one real gap to flag (D3's no-animation check is not CI-enforced the way the digit-pattern check is, and its file scope is unstated) and two smaller notes (icon-provenance guardrail, and a scope reminder on what "closes the gap" actually means here). Nothing here blocks the design from moving to implementation, but I want the CI gap addressed before Group 1 implementation is considered done, not left to the sign-off artifacts' prose.

---

## 1. Does D3's no-animation check actually close the gap I flagged in the archived review, or does it leave room for a disguised countdown surrogate?

**Mostly closes it, for a reason stronger than the check itself — but the check itself has a real gap.**

My original concern (`reauth-required-client-prompt` design.md D3, restated in this change's design.md line 66) was that a countdown doesn't have to be numeric to disclose the grace-period interval — a progress bar draining, a spinner whose rotation period matches the ~30s window, or a color transition timed to elapsed time would leak the same information a digit string would, without tripping a digit-pattern regex.

Two things work in this design's favor, and I want to credit them before naming the gap:

- **Structural mitigation, not just a review step.** The archived design's D9 (unchanged, restated at this change's design.md non-goals) holds that `ReauthRequiredTreatment.tsx` takes no props derived from cause, role, or session-moment state — confirmed by reading `ReauthRequiredTreatmentProps` directly (`returnTo` and `role` only, `ReauthRequiredTreatment.tsx:94-110`). There is no time-remaining value, tick count, or elapsed-time signal available inside the component to drive an animation's duration even if an implementer wanted to build a disguised countdown. A real countdown surrogate would require *first* plumbing a session-moment value into the component — which is a visible, reviewable violation of D9 on its own, independent of whatever CSS ends up attached to it. This is the kind of secure default I look for: the leak is foreclosed by the data model, not merely by an inspector's judgment.
- **The digit-pattern test's scope is wider than a naive text check.** `ReauthRequiredTreatment.test.tsx:11-19` asserts against `container.innerHTML`, not `textContent` — so a numeric duration expressed as an inline `style` attribute (e.g., an implementer writing `style={{ animationDuration: "30s" }}`) would actually be caught, since React serializes inline styles into the `style="..."` DOM attribute, which `innerHTML` includes. That's good coverage for the most likely accidental case.

**The gap:** D3's no-animation constraint itself — as opposed to the digit-pattern check — is explicitly *not* elevated to the same CI-enforced status. Design.md says plainly it's "a yes/no grep-and-inspect check... not a felt judgment," and tasks.md operationalizes it as a one-time manual step: task 1.2 (implementer self-check) and task 2.2 (sign-off author cites grep/inspection evidence). Neither produces a persisted, re-runnable test. Compare this to the digit-pattern check, which is a standing `it()` block that runs on every future change to this file. Once Group 1 ships and Group 4's cleanup lands, nothing stops a *later*, unrelated change from adding a CSS `transition` or `@keyframes` to this component — a hover effect, a subtle pulse for attention, anything — without anyone re-running D3's grep. The mock sign-off's citation is a snapshot of the state at sign-off time, not an ongoing guarantee.

This is exactly the pattern I look for and flag on every review: a control that depends on someone remembering to check it, next to a sibling control (the digit-pattern test) that was correctly built not to depend on that. The fix is cheap and mirrors what already exists — a `expect(container.innerHTML).not.toMatch(/animation|transition|@keyframes/)` (or an inspection of the actual stylesheet/style object, depending on how the register is implemented) added to `ReauthRequiredTreatment.test.tsx` alongside the existing digit-pattern test, so a future regression fails the build instead of going unnoticed until someone happens to re-grep.

**Recommendation (non-blocking for design, should land in Group 1/2, not deferred past this change):** add a CI-enforced negative-constraint test for animation/transition/duration properties, co-located with the digit-pattern test. If tasks.md's authors want to keep the manual grep as the *sign-off's* evidence-gathering step, that's fine — but it shouldn't be the only enforcement mechanism going forward.

## 2. Does real visual styling introduce new leak risk via CSS custom properties, `animation-duration`, or similar that a digit-pattern text regex wouldn't catch?

**Yes, one real path — file scope.** The digit-pattern test's `innerHTML` check only sees what ends up in the rendered DOM. It has full visibility into inline styles (`style={{...}}}` on the element) because those serialize into the DOM's `style` attribute. It has **no visibility** into rules defined in an external stylesheet, a CSS Module, or a `:root`-scoped custom property declared elsewhere (`:root { --dipstick-grace-period: 30s; }` consumed via `var(--dipstick-grace-period)` in a class the component merely references) — a class name in `innerHTML` gives no textual trace of what that class does.

Design.md D1 and D2 don't specify whether the register is implemented via inline styles (as the current placeholder is: `REAUTH_REQUIRED_STYLE` as a plain object, `ReauthRequiredTreatment.tsx:89-92`) or a stylesheet/class-based approach. If Group 1 keeps the existing inline-style pattern, the digit-pattern test's coverage carries forward unchanged and this concern is moot in practice. If it moves to an external CSS file for the color/icon work, the existing test stops being able to see anything defined there — which is exactly the same blind spot named in point 1, just via a different implementation path (a duration hidden in a stylesheet rather than a duration hidden by simply not writing a test for it).

This isn't a reason to block the design — the design doesn't mandate either approach, and inline styles remain the lower-risk default given the existing test's reach. But I want this named explicitly rather than assumed: **whichever approach Group 1 takes, the no-animation check (point 1's recommendation) needs to inspect the actual location the styling lives in, not just the component's own `.tsx` file.** Design.md's D3 language ("grep... `animation`, `transition`, `@keyframes`") doesn't state a file scope; tasks.md task 1.2 and 2.2 don't either. If a new CSS file is introduced, both the self-check and the sign-off evidence need to grep that file too, not just `ReauthRequiredTreatment.tsx`. Worth a one-line clarification in tasks.md so a future implementer doesn't grep the wrong file and call it done.

## 3. Is the SEC-26 sub-cause non-disclosure boundary intact given the new styling work?

**Yes, structurally — same reasoning as point 1.** The concern here would be a register that indirectly encodes *why* reauthorization is required (revoked vs. expired vs. transient failure) through, say, a different icon or color for different causes. This is foreclosed the same way the countdown-surrogate risk is: `ReauthRequiredTreatmentProps` has exactly two fields (`returnTo`, `role`), and `role` conditions only the vote-loss sentence per the archived design's Decision 4 — it does not, and per D9 must not, touch icon, color, or weight. There is no `cause` value anywhere in this component's call chain for a color/icon decision to branch on, and `connectionHealth.ts` — the one place that would know the sub-cause, if it were tracked at all — is explicitly untouched by this change (proposal.md's Impact section, design.md's Non-Goals).

One thing worth stating plainly since it wasn't spelled out in design.md: this holds **as a single, uniform register** — one color, one icon, applied identically regardless of which host renders it or which underlying WebSocket close code triggered the state transition. `reauthRequiredHostParity.test.tsx` already asserts DOM-level parity between the two hosts (modulo the vote-loss sentence), which is the right test for role-parity but does not, and doesn't need to, assert anything about cause-parity, because there is structurally no cause data available to have diverged on in the first place. I don't have a specific ask here — I'm confirming the boundary holds, and naming *why* it holds (data model, not discipline) so it's clear this isn't merely "nobody proposed a cause-aware icon yet."

The one soft spot: this guarantee currently rests on `ReauthRequiredTreatmentProps`'s shape staying exactly what it is today, enforced by nothing more than code review (there's no test asserting "this component has no cause/session-moment prop"). That's a lower-severity version of the same "discipline-dependent" pattern in point 1, but I'm not asking for a test here — a prop-shape invariant is awkward to test meaningfully and the existing header comment (`ReauthRequiredTreatment.tsx:14-19`) already states the constraint clearly for the next reviewer. Comment-level documentation is an adequate control for this one, given TypeScript's own interface would need to change (a reviewable diff) before any violation could occur.

## 4. Is anything security-relevant here being deferred without being flagged?

**One thing, adjacent to point 1, that I want named even though it doesn't block this change:** the icon allow-list (D2) is deliberately non-exhaustive, with the bar for anything outside the starting three options being a *felt* judgment ("does a careful reviewer agree it doesn't echo a countdown") rather than a mechanical one. I don't disagree with keeping that felt — a closed-lock glyph versus some hypothetical fourth icon is a design judgment, not a security-checkable fact, and design.md is explicit that closing the list early would be overreach (exploration-notes.md §6, carried into design.md D2's alternative-considered). But I want it on record that **the only backstop against a poorly-chosen icon that reads as a clock, hourglass, gauge, or dial is the sign-off's felt-judgment section** — there is no mechanical check equivalent to the digit-pattern test for "does this glyph look like a countdown." That's an acceptable trade-off given the nature of the judgment, not a gap I'm asking to be closed, but it does mean the mock sign-off's felt-judgment section (design.md D5, tasks.md task 2.3) is carrying real security weight here, not just a tone-and-feel call. Whoever performs that sign-off should treat the icon choice as in-scope for the felt check, not only the assertive-vs-alarming tone question D5 names explicitly.

Everything else that's deferred in this design is flagged as deferred, and correctly so:
- #142/#143 (live usability test) — named explicitly as out of scope in every artifact, consistent with my own standing position that a simulated review is not a substitute for a real facilitator in a real session.
- D7's comment cleanup being conditional on sign-off outcome, and D8's spec-status text reflecting the actual (possibly withheld) verdict rather than presupposing a clean pass — both are exactly the "don't let a placeholder get treated as a decision" discipline I want to see, and both are stated plainly rather than implied.
- Issue #33 (facilitator-disconnect blast radius) is named as explicitly not resolved by this change, in both design.md and proposal.md.

No new WebSocket surface, no new endpoint, no change to `connectionHealth.ts`'s state machine or the `/auth/login` literal-string boundary (still the exact-match, no-query-parameter constraint from my prior review, unchanged and untouched by this change per proposal.md's Impact section) — so none of my other standing concerns (token validation, server-side authorization, secrets management, dependency hygiene) are implicated by a pure-presentation change, with the one caveat below.

**Minor note on dependency hygiene, forward-looking only:** tasks.md task 1.1 leaves "icon chosen from the starting allow-list... or a justified alternative" open on *how* the icon is rendered — inline SVG, a project-local icon component, or a new third-party icon package dependency. If Group 1 pulls in a new icon library to satisfy this, that's a new dependency and should go through the same dependency-hygiene expectation I hold for any other addition (known-vulnerability tracking, not a one-time add-and-forget). If it's an inline SVG or reuse of something already in the tree, this is moot. Not a design-blocking concern — I'm flagging it so it isn't an unexamined side effect of Group 1's implementation.

## Summary for implementation

Nothing here blocks the design from proceeding. Two concrete items I'd like to see land no later than Group 1/2 (not deferred to some future change):

1. **Add a CI-enforced test for the no-animation/no-duration constraint**, co-located with `ReauthRequiredTreatment.test.tsx`'s existing digit-pattern test, so this negative constraint doesn't rely solely on a one-time manual grep that a later, unrelated change could silently regress past.
2. **Clarify the grep/inspection scope in tasks.md tasks 1.2 and 2.2** to explicitly cover wherever the visual register's styling actually lives (inline styles vs. an external stylesheet/CSS Module), not implicitly assume `ReauthRequiredTreatment.tsx` is the only file that matters.

One thing to carry into the sign-off artifacts themselves (not a design change): treat the icon-shape judgment ("does this glyph echo a countdown/duration") as part of the felt-judgment section's scope, not only the assertive-vs-alarming tone call — the allow-list's open-endedness means this is the only backstop against a countdown-adjacent icon choice.

The structural guarantees I care about most — no cause/session-moment data reaching this component, no change to the `/auth/login` literal or `connectionHealth.ts`, the SEC-26 sub-cause boundary holding by construction rather than by discipline — are all intact in this design.
