# Security Review: auth-events-audit-log-coverage — design.md

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope of review:** `design.md` and `proposal.md`, verified directly against the current implementation (`packages/backend/src/routes/auth.ts`, `join-links.ts`, `teams.ts`, `auth/account-resolver.ts`, `auth/session-invalidation-audit.ts`, `auth/audit-logger.ts`, `routes/health.ts`, `docs/deployment.md`), and against the delta specs (`specs/auth-error-handling/spec.md`, `specs/join-link/spec.md`).

**Verdict: Approve.** This is the kind of change I want to see more of, not less — it closes a real gap (thirteen call sites logged but not durably recorded) with reasoning that engages honestly with the trade-off it's making rather than asserting it away. I verified the design's factual claims against the actual code and found no discrepancies: the call sites, the two mechanism groups, the `teams.ts` precedent shape, the `/health/ready` behavior, and the `docs/deployment.md` "19 at-risk events" enumeration all match what's on disk today. I have a small number of findings below, none of which I consider blocking, and one item I want tracked rather than left as a Risk bullet.

## Findings

### F1 (Informational — endorse) The multi-provider constraint is honored, correctly and non-trivially

I checked this specifically given the standing project guidance that OIDC must not be designed Entra-only. `account-resolver.ts`'s `mapRoleClaimToGlobalRole` confirms `previousRole`/`globalRole` are drawn from this codebase's own three-value allowlist (`engineer`/`engineering_manager`/`application_admin`), never the raw claim string — a rejected claim value is logged with only the claim *name*, never the value, specifically because "the value is attacker-controlled input... could be exploited to inject misleading content into compliance-relevant records" (existing comment, `account-resolver.ts:75-77`). This design's new fields (`previousRole`) go through the same mapping function, on the same code path, so they inherit that protection without needing to reason about it fresh. No part of this design branches on issuer identity or introduces an Entra-shaped assumption. Good.

### F2 (Low, accepted) Decision D3's coupled-fate trade-off is reasoned honestly, and I accept it — with one addition

I want to be explicit that I reviewed this looking for the "it's fine, trust me" pattern I usually have to push back on, and didn't find it. Section D3 states plainly that there is no uptime SLA for `audit_log` or Postgres generally, names exactly what `/health/ready` does and doesn't cover (a full outage vs. a table-isolated failure — a lock, a constraint violation, a disk-quota problem scoped to `audit_log` specifically), and doesn't invent a number to make the decision look more grounded than it is. That is exactly the standard I hold designs to. I accept the coupling for the four events in the transactional group, for the same reason `team.manager_established` already established it: these are one-time-per-account or bounded, gate-kept actions, not high-volume traffic, and letting a first login or a join-link creation fail loudly is more defensible than a silently thinning audit trail for events this significant.

The one addition I want: the design's own language ("worth monitoring in practice") is the right instinct but isn't a commitment. I'd like the narrower gap — an `audit_log`-table-isolated failure that `/health/ready` doesn't catch — named as a concrete, tracked follow-up (a dashboard query or alert on `auth.audit_write_failed` volume and on `AuditWriteError` occurrence in `auth.callback_error` logs), not left as a "worth watching" sentence with no owner. This doesn't need to block this change; it's the kind of thing that belongs in the same tracked-issue discipline the design already applies to #156.

### F3 (Low) `role_claim_mapped`'s reversion blind spot bears directly on my own Success Criterion 4 — I want it tracked, not just named

Decision D4's Risk is candid: a role dropping back to the default (`engineer`) still produces zero rows, so "no reversion row" is structurally indistinguishable from "the account simply never authenticated again." I agree this is out of scope for an audit-*coverage* change (it changes when an event fires, not whether an existing emission gets a row) — that line is correctly drawn. But this is the exact event my own Success Criterion 4 depends on ("did an EM's role ever get misapplied, and when"), and an investigator who queries this trail two years from now, sees a `role_claim_mapped` row showing `engineering_manager` and no subsequent row, cannot distinguish "still an EM, hasn't logged in recently" from "was demoted, no trace of when." I'd like this filed as a tracked follow-up alongside #156 rather than resting solely on a Risks-section sentence — the same discipline this design already correctly applies to the four deferred events.

### F4 (Informational — verified, no new exposure) `join.link_redeemed`'s `role='participant'` mismatch for EM joiners is contained by an existing compensating control

I checked whether making this scenario durably visible (Non-Goals) could be mistaken for this design fixing or normalizing it, per its own stated risk. It doesn't fix it, correctly. More importantly, I checked whether the underlying mismatch itself (an EM landing in `team_memberships` with a participant-shaped row while `users.global_role` still says `engineering_manager`) is a live authorization gap today — it isn't a new one: `team.access_grant_mismatch` (documented in `audit-logger.ts`, from `restrict-team-005-em-promotion`) already exists specifically to detect and degrade this exact mismatched state to `participant` rather than granting elevated access on a stale membership row. This design doesn't touch that control and doesn't need to. No new privilege-escalation surface here — only a durability improvement to an already-handled degrade path.

### F5 (Informational — verified) `AuditWriteError` does not leak anything sensitive

I traced where `sanitizeOidcError`'s output for `AuditWriteError` actually goes: `request.log.error({ err: sanitizeOidcError(err, ...), ... })` at `auth.ts:423-428` — server-side structured logging only, never returned to the client. The client-facing response is built from `mapAuthError`'s category/message, which is a fixed, static string ("We couldn't finish signing you in due to a temporary internal problem...") with no dynamic content. `AuditWriteError.message` is a static string by construction (never built from the underlying Postgres error, per the class definition in Decision D7), and `causeClass` is a constructor name (e.g., `"DatabaseError"`), not the error's own message — no risk of an underlying Postgres error echoing query content into a log an attacker could ever see. This meets my bar for the "distinct error messages must not include technical identifiers" requirement already in the `auth-error-handling` spec.

### F6 (Low, worth a test) `previousRole`'s CTE has a narrow concurrent-login accuracy edge case

Decision D4's CTE (`WITH prior AS (SELECT global_role ... ) INSERT ... RETURNING ..., (SELECT global_role FROM prior) AS previous_global_role`) reads the pre-update value as a subquery alongside — not locked against — the `INSERT ... ON CONFLICT DO UPDATE`. For two concurrent authentications by the *same* user (double-tab login, or a retried callback), it's plausible depending on exact statement/lock timing for the second transaction's `prior` CTE to observe a value that a concurrently-committing first transaction is in the process of superseding, producing a `previousRole` value that doesn't reflect the true prior state as of that row's commit order. This doesn't grant any incorrect access — it's a forensic-accuracy question, not an authorization one — but it directly affects the reliability of the record Success Criterion 4 depends on. I'd like a concurrency test added (two near-simultaneous `resolveOrCreateAccount` calls for the same `oidc_subject`/`oidc_issuer` with different role claims) to confirm actual behavior under Postgres's read-committed semantics, rather than relying on the CTE's correctness being obvious. If the test shows an issue, the fix is likely cheap (e.g., `SELECT ... FOR UPDATE` in the CTE); if it shows no issue, that's worth stating in the design record so the next person doesn't have to re-derive it.

### F7 (Informational — endorse) The four-event deferral is real risk-based reasoning, not the "it's just internal" pattern I usually have to correct

I want to say this explicitly because it's the thing I watch for hardest. `authorization_initiated`, `callback_received`, and two of `auth.failure`'s three branches are deferred because they're reachable by *unauthenticated* traffic — a synchronous DB write on that path is a write an attacker gets to trigger for free, and that's a legitimate availability/DoS concern for a write-amplification vector, not a severity judgment about the data. `join.link_rejected`'s deferral rests on a genuinely unanswerable volume question (`docs/deployment.md` confirms no log transport exists to get a real number from) rather than a guess dressed up as an answer. Both are exactly the standard I hold "internal app" projects to. I have no objection to proceeding on this reasoning, and I'll register the same caution the design already registers: if issue #156 never gets prioritized, this reasoning needs to be revisited on its own terms eventually, not left permanently deferred on the strength of a decision made in 2026.

### F8 (Process) Threat model revisit before production — I'm treating this as my checkpoint, not a gap in the design

My Success Criterion 1 requires the design-stage threat model to be revisited against the implemented application before production, not treated as a one-time artifact. This document doesn't need to satisfy that criterion itself — it's a design record, not a pre-production sign-off — but I want it on record here that I expect to review the merged diff before this ships, specifically: (a) that `tasks.md` 3.4/5.3's rollback-on-audit-failure tests actually demonstrate the coupling Decision D3 claims (they're specified correctly in tasks.md; I have not yet seen them pass), (b) that `tasks.md` 3.5/5.4's classification/asymmetry tests hold, and (c) a quick confirmation that no `metadata` payload added by this change (userId, oidcSubject, globalRole, sourceIp, correlationId, teamId, linkId, previousRole) ever picks up a raw claim value — I checked the design's field list and it doesn't, but I check this again at implementation time as a matter of habit, since this is exactly the kind of thing that regresses silently when a field gets added later by someone who didn't read this document.

### F9 (Out of scope, flagged as an aside) A dead authorization branch in `join-links.ts`, unrelated to this change

While reading `POST /api/teams/:teamId/join-links` to verify Decision D5/D2's claims, I noticed `canCreate`'s check includes `userRole === "facilitator"` (`join-links.ts:47`), but `account-resolver.ts`'s `PERMITTED_GLOBAL_ROLES` allowlist only ever produces `engineer`, `engineering_manager`, or `application_admin` — `global_role` can never actually be `"facilitator"` today. This branch is dead code, not a vulnerability (it doesn't grant anything; it's just unreachable), and this design doesn't touch this line. I'm noting it only so it isn't mistaken for something this review should have caught as new — it predates this change. Worth a cleanup ticket, not a blocker here.

## Items from my persona's standing concerns that this design does *not* need to address, stated so their absence isn't misread as an oversight

- **WebSocket re-authorization / WS event logging fidelity:** out of scope for this design, and correctly so — this change is HTTP-only (`auth.ts`, `join-links.ts`). I confirmed separately that `session.reveal_triggered`, `session.vote_submitted`, `session.state_changed`, and the `session.access_revoked_live`/`token_refresh_failed_live` WS-side events already have DB-backed audit rows from prior changes (`audit-logger.ts`'s own inline documentation, and `connection-reauthorization.ts`'s `evaluateSessionSubscriberAccess`/audit-write code I read while verifying `resolveActorGlobalRole`). No gap here for this design to close.
- **Secrets management, dependency hygiene:** not implicated — no new secrets, no new third-party dependency introduced by this change.
- **Token validation (signature/expiry/audience/issuer):** unchanged by this design; out of scope, and I have no new concern to raise against my existing review of that path.
