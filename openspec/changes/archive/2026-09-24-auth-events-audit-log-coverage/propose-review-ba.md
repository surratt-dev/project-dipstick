# BA Review: Proposal — auth-events-audit-log-coverage (SEC-12/SEC-13/SEC-15)

**Reviewer:** Marcus Delgado, Business Analyst
**Reviewing:** `proposal.md`, cross-checked against `design.md`, `specs/auth-error-handling/spec.md`, `specs/join-link/spec.md`, and `tasks.md`
**Lens:** Are the capabilities specific enough for the implementation team to build without a round-trip back to me or Devon? Are the acceptance criteria in the delta specs explicit, or do they leave a load-bearing detail implicit? Does everything downstream of the proposal actually agree with it?

I read the code this change touches directly rather than taking the documents' characterization at face value — `routes/auth.ts` (the full `/auth/callback` try/catch, `executeJoinFlow`), `routes/join-links.ts` (both handlers, in full), `auth/error-handler.ts`, `auth/oidc-error-sanitizer.ts`, and `auth/session-invalidation-audit.ts` — the same discipline I applied to the exploration draft. Two findings below come directly out of that check, not out of the documents' own text.

Overall assessment first: this is the most internally consistent set of documents in this three-part chain. The proposal's event list, design.md's decisions, the delta specs' requirements, and tasks.md's checklist items name the same seven events, the same two mechanisms, and the same field shapes, in the same words, every time I cross-referenced them. `AuditEventName` really does already contain all seven operation names (verified against `audit-logger.ts`), `AUDIT_WRITE_TIMEOUT_MS` really is 500 (verified against `session-invalidation-audit.ts`), and the `globalRole !== "engineer"` firing condition for `role_claim_mapped` really does fire on every applicable login, not only on change (verified against `auth.ts:311`) — matching what design.md says about it. That's a high bar for a document chain this size to clear, and it clears it. My findings below are the places where that discipline has a gap, not a wholesale critique of the approach.

## 1. Major: the transactional group's failure path is real, traceable, and actively works against SEC-12 — this needs to be named as a decision, not left implicit

Design.md's Decision D3 states the transactional group's coupled-fate cost honestly: an `audit_log` failure during `auth.first_access_created`/`auth.role_claim_mapped` rolls back the account-creating UPSERT, and "the login fails, rather than succeeding with a silently-missing audit row." The delta spec's scenario says the same thing: "the authentication attempt fails rather than succeeding with a silently missing audit row." Both stop at "the request fails" — neither says what that failure actually looks like once it happens, and I traced it, because SEC-12's entire premise is that this trail is what someone reconstructs an incident from.

Here's what actually happens, verified line-by-line:

- `auth.first_access_created`/`auth.role_claim_mapped` fire inside `GET /auth/callback`'s single `try` block (`auth.ts:201`–`420`). `join.link_redeemed`'s through-auth call site is inside the same block too — `executeJoinFlow` is invoked at `auth.ts:385`, before the block ends.
- Task 3.1's transaction wrapper matches `teams.ts`'s shape: `ROLLBACK` then `throw err` — the raw Postgres error, unwrapped, unmarked as anything other than "an error that happened during this request."
- That rethrow lands in the existing `catch (err: unknown)` at `auth.ts:420`, the same catch block every `auth.failure` branch already shares. Two things happen to `err` there, both of which I read in full:
  - `mapAuthError(err)` (`error-handler.ts:9`–`109`) checks `err` against `MissingClaimError`, then a series of `message.toLowerCase().includes(...)` checks for OIDC-specific substrings (`access_denied`, `invalid_grant`, `econnrefused`, `state`/`nonce`, etc.). A Postgres error's message matches none of these. It falls through to the default at line 105: category `authentication_failed`, message *"An unexpected error occurred during sign-in. Please try again..."*
  - `sanitizeOidcError(err, request.log)` (`oidc-error-sanitizer.ts:44`–`106`) checks `err` against six recognized OIDC error classes. A Postgres error matches none of them either, and falls to the "unrecognized class" branch at line 89: `message` and `stack` are **redacted**, replaced with only `errorClass` and `unrecognized: true`, plus a second, separate `oidc_error_sanitizer.unrecognized_class` log line carrying just the class name.

Net effect: the specific failure mode Decision D3 spends a full section justifying as an accepted cost — an `audit_log` outage during a new user's first login, or during a facilitator/EM/admin's login, or during a through-auth join redemption — surfaces to whoever is debugging it as a generic, redacted "sign-in failed" error. The actual Postgres error message and stack trace (connection refused, constraint violation, whatever it actually was) are scrubbed by a mechanism that exists for a completely different reason: keeping IdP-supplied secrets out of logs. The end user sees a message that says "sign-in" when the root cause has nothing to do with sign-in at all. This is not a hypothetical edge case — it is the literal failure mode this change's own coupled-fate decision creates, hitting an existing sanitizer that was never designed with a Postgres error in mind because, before this change, nothing in this call path could throw one.

I don't think this is a reason to revisit Decision D3's coupling choice — the reasoning there is sound and I'm not reopening it. But an initiative whose entire justification is SEC-12's incident-reconstruction guarantee should not ship a failure mode that redacts the one piece of information an incident responder would need to tell "the IdP had a problem" apart from "our own database had a problem." This is a gap in the design, not just in the wording — no document in this chain names that the transactional group's error rethrow passes through `sanitizeOidcError`/`mapAuthError` at all.

**Suggested concrete fix, scoped to what's already open in this change:** wrap the audit `INSERT`'s thrown error in a small, distinguishable error class (e.g. `AuditWriteError`) before the `ROLLBACK`/rethrow in task 3.1 (and the equivalent in `executeJoinFlow`'s treatment, task 6.2) — the same pattern `MissingClaimError` already uses to get special-cased in both `mapAuthError` and `sanitizeOidcError`. Then:
- `sanitizeOidcError` gets one more recognized branch: preserve a generic, non-sensitive message ("audit log write failed") and `stack`, since neither ever contains IdP-supplied content for this error class.
- `mapAuthError` gets one more recognized branch: a category and message that doesn't say "sign-in" (existing categories don't quite fit — this may be the one place this change needs to ask whether a fifth `AuthErrorCategory` value, or a reuse of `provider_unavailable`'s "try again in a few moments" framing, is more honest than `authentication_failed`'s current default text).

This is two files already open for this change, touching call sites already being edited — the same "small, adjacent, cheap fix while this file is already open" reasoning Decision D6 already uses elsewhere in this exact design. I'd want it added as a decision (D7, or folded into D3) before this moves to implementation, not discovered when someone's first production audit-log hiccup produces a support ticket that says "I can't sign in" with a redacted stack trace behind it.

## 2. Moderate: `join.link_redeemed`'s `actor_global_role` source is stated as settled in the spec, but tasks.md correctly flags it as unresolved — and I can resolve half of it right now

`specs/join-link/spec.md` line 7 states: *"`actor_global_role` SHALL be the actor's `global_role` as already resolved earlier in the same handler (no additional lookup where it's already in scope)."* Read at face value, this sounds like a settled fact. `tasks.md` task 6.3 says otherwise: *"Confirm both call sites resolve `actor_global_role`... via a `SELECT global_role FROM users WHERE id = $1` if not already in scope at that point in either function — check before assuming; `executeJoinFlow` and the `GET` handler may need one small additional lookup here."* That's not a settled fact, that's an open implementation question — and the spec's parenthetical hedge is doing a lot of work to paper over the gap.

I checked both call sites directly, and the answer isn't uniform, which is exactly the kind of thing that should be stated in the requirement rather than left for whoever picks up task 6.3 to discover:

- **`join-links.ts`'s `GET /api/join/:token`** (lines 96–195): I read the full handler. It never queries `global_role` for the joining user anywhere — only `session.userId` is in scope. This call site genuinely needs a new `SELECT global_role FROM users WHERE id = $1` before its `join.link_redeemed` audit row can be written. Task 6.3's hedge is correct here.
- **`auth.ts`'s `executeJoinFlow`** (lines 637–722): this one does *not* need a new query. The caller — `GET /auth/callback`, right at the call site (`auth.ts:385`) — already has the full resolved `user` object in scope, including `user.globalRole`, used two statements earlier for the `auth.success` emission (`auth.ts:361`). `executeJoinFlow` today receives only `userId: string` as its first parameter, not the full user or its role. The fix here isn't a lookup at all — it's threading `user.globalRole` through as a new parameter to `executeJoinFlow`, which costs nothing (the value already exists in the caller's scope).

These are two different fixes (a new query at one call site, a free parameter pass at the other), and the spec's current wording — "no additional lookup where it's already in scope" — doesn't tell an implementer which call site is which, or that one of them requires touching `executeJoinFlow`'s function signature. Given how precisely this design otherwise distinguishes call-site shapes (D5 does exactly this for `team_id`), I'd expect the same precision here.

**Suggested rewrite for spec.md line 7:** *"`actor_global_role` SHALL be the actor's `global_role`. At `join.link_created` and at `executeJoinFlow`'s `join.link_redeemed` call site, this value is already resolved in the calling scope (`user.globalRole` in `GET /auth/callback`) and SHALL be passed through rather than re-queried — `executeJoinFlow`'s signature gains a parameter for it. At `join-links.ts`'s `GET /api/join/:token`, no such value exists in scope; this call site SHALL issue a `SELECT global_role FROM users WHERE id = $1` before writing the audit row."* This also gives task 6.3 a concrete answer instead of a "check before assuming" instruction to carry into implementation.

## 3. Minor: SEC-15 traceability is inherited, not addressed — worth one sentence confirming that's deliberate

SEC-15 requires the audit log be written to "a destination that is not modifiable by the application process." Nothing in this proposal, design, or the delta specs addresses database-level write/delete permissions for the `audit_log` table — which is correct, since that's an infrastructure property of the table itself, not something seven new call sites change. I checked that neither this change's Impact section nor its Migration Plan claims to touch this, and it doesn't. I'm not asking for scope to expand — I'm flagging it so a future reader doesn't mistake proposal.md's silence on SEC-15 for an oversight. One sentence in the Impact section ("SEC-15's write-only guarantee is a property of the `audit_log` table's existing permissions, unchanged by this change") would make that explicit rather than implicit, matching this document chain's own stated discipline of naming boundaries rather than leaving them true only by omission.

## 4. Minor: `join-links.ts`'s direct-path failure mode is a plain 500, not the redirect-with-message path — asymmetric with the through-auth path, worth naming once

I checked `join-links.ts` for an equivalent try/catch to the one `auth.ts` has around its OIDC flow — there isn't one. A rethrown error from the new transactional wrapping in tasks 5.1 or 6.1 (a failed `join.link_created` or direct-path `join.link_redeemed` audit `INSERT`) would fall through to Fastify's default error handler: a generic 500, no `mapAuthError`/`sanitizeOidcError` involved at all. This is a materially different, and honestly less concerning, failure mode than Finding 1's — a facilitator creating a join link, or a user hitting `/api/join/:token` directly, gets an ordinary API failure rather than a misleadingly-worded redirect. I don't think this needs a design change. I'd still want one sentence somewhere (design.md's Decision D3 or Migration Plan) noting that the two `join.link_redeemed` call sites fail differently from each other post-rollback — a plain 500 at the direct path, the OIDC-flavored redirect-with-redacted-message at the through-auth path — so nobody assumes "identical treatment at both call sites" (which D5 correctly claims for the audit-write mechanics) also means "identical failure UX," which it doesn't.

## What's already solid (no rewrite needed)

- **The seven-event scope list and its rationale.** Every claim I checked against the code (which events already exist in `AuditEventName`, which have a Postgres write nearby, which don't) held up exactly as stated.
- **Decision D1's treatment of `auth.failure` as a single deferred unit rather than split by call site**, and the explicit rejection of the "audit the catch-all branch only" alternative — this is precisely the "don't reproduce the three-of-four-`reason`-values mistake" discipline this whole chain exists to enforce, and it's applied correctly here.
- **Decision D4's `previousRole` field and its CTE.** I checked the SQL — capturing the prior value via a CTE inside the same UPSERT statement is correct and adds no extra round trip. The "brand-new user has no previous role" and "reversion to default is unrepresentable" scenarios are both named explicitly in the spec rather than left as things a future reader has to infer.
- **Decision D5's `join.link_redeemed` both-call-sites coverage**, matching the exact shape of gap the `session_invalidated` precedent's fourth call site created. Verified `executeJoinFlow` really is invoked from `/auth/callback` and really does duplicate the event.
- **Issue #156's role as the deferral mechanism**, consistently referenced across proposal.md, design.md, both delta specs, and tasks.md — the chain's own "a Non-Goals bullet alone is how the next exploration re-discovers a solved gap" lesson from the exploration stage was actually applied here, not just stated.
- **The test task list (tasks.md Section 9).** Concrete, one assertion per event, includes rollback-on-failure and timeout-triggers-failure-signal tests per mechanism group. This is exactly the level of specificity I want to see — nothing in that section requires a round-trip back to me to interpret.

## Summary of asks before this moves to Design sign-off / implementation

1. **Name the transactional group's actual failure UX as a decision**, including that today's implementation would redact the diagnostic detail and misattribute the cause to sign-in — and either accept that explicitly (with a stated reason) or fix it with the small `AuditWriteError`-class addition suggested in Finding 1.
2. **Resolve `actor_global_role`'s source at both `join.link_redeemed` call sites explicitly in the spec** — a parameter pass at `executeJoinFlow`, a new query at `join-links.ts`'s `GET` handler — rather than leaving it as a "check before assuming" item in tasks.md that the spec's wording implies is already settled.
3. **Add one sentence on SEC-15** confirming its guarantee is an inherited, unchanged property of the `audit_log` table, not something this change addresses.
4. **Name the asymmetry between the two `join.link_redeemed` call sites' failure UX** (plain 500 vs. redirect-with-message) so "identical treatment" isn't read more broadly than D5 actually claims.

None of these require reopening the scope calls this proposal already made well — which seven events get a row, which four are deferred, which mechanism each group uses. They're about making sure the acceptance criteria this change ships with actually describe what happens when the design's own accepted failure mode (Decision D3) occurs, and about closing two spots where a downstream document states as settled something that's still genuinely open.
