I grepped every `emitAuditEvent(` call in both files directly rather than trusting that list, and found two more DB-row-less events living in the exact same file, in the exact same "no `audit_log` row anywhere" state, that neither list names:

- **`auth.failure`** — three call sites in `auth.ts`'s `/auth/callback` handler (line 209: missing `state` param; line 228: expired/invalid state; line 442: the catch-all handler for any thrown error, including `MissingClaimError`). SEC-13 literally names "failure" as one of four required authentication categories ("login, logout, failure, expiry") — this is arguably the *most* on-the-nose match of any event in scope here, and it's missing from both the precedent's Non-Goals and this issue's list.
- **`auth.session_created`** — one call site (line 355), fired in the same breath as `auth.success` right after `request.session.regenerate()`. SEC-13 separately names "session lifecycle (creation, join, close, facilitator changes)" as its own required category, distinct from "user authentication" — `session_created` is arguably the cleanest match for that half of SEC-13 of anything in this file.

I don't think either omission was a decision — I looked for a stated reason in `http-auth-audit-log-coverage`'s design.md and proposal.md and found none; the Non-Goals bullet just doesn't mention them. This is the second time in a row a call-site inventory for this file has needed correcting after the fact (the first time, #30's own issue text didn't name `auth.ts`'s fourth `session_invalidated` call site — Decision D3 of the precedent design had to add it explicitly). I'd rather this issue's proposal stage state, in writing, whether `auth.failure`/`auth.session_created` are in scope here or are being deliberately deferred *again* — either answer is fine, but a third silent miss on the same file would stop looking like an oversight and start looking like a pattern nobody's checking for.

**`join-links.ts` doesn't hold the whole join-event surface — `auth.ts` duplicates two-thirds of it.** The issue's file list points at `join-links.ts` only. But `auth.ts` has its own, separate implementation of join-link redemption — `executeJoinFlow` (lines 637-722), invoked from `/auth/callback` when a `pendingJoinToken` rode through the OIDC state round-trip (the case where an unauthenticated user clicks a join link and gets bounced through login first). This is a second, parallel code path emitting the same event names as `join-links.ts`'s `GET /api/join/:token` handler, which handles the case where the user was already authenticated:

| Event | `join-links.ts` call sites | `auth.ts` (`executeJoinFlow`) call sites |
|---|---|---|
| `join.link_created` | 1 (`POST /api/teams/:teamId/join-links`) | — |
| `join.link_redeemed` | 1 | 1 |
| `join.link_rejected` | 3 (`not_found`, `revoked`, `expired`) | 2 (`not_found`, `revoked`-or-`expired` combined) |

That's five real call sites behind three event names, across two files, not three call sites in one file. This matters for the same reason the fourth `session_invalidated` call site mattered in #30: whoever writes design.md for this needs to grep the event *names*, not the file the issue happens to point at, or this ships with `join.link_redeemed` durable from one login path and silently not from the other — a gap indistinguishable, from the outside, from the "three of four `reason` values audited" mistake Decision D3 existed specifically to avoid repeating.

**A small field inconsistency between the two `join.link_rejected` implementations, worth a look, not a fix, right now:** `auth.ts`'s `executeJoinFlow` runs *after* the user is already authenticated (it's called with `userId` already resolved), so `userId` is in scope at its two `link_rejected` branches — but neither branch includes it in the event's fields, unlike its sibling `join.link_redeemed` emission a few lines later in the same function, which does. `join-links.ts`'s `GET` handler's three `link_rejected` branches genuinely have no `userId` available (they fire before the session check), so their omission is structural, not an oversight. `auth.ts`'s is the one worth Design deciding about explicitly rather than copying forward silently.

**Transaction availability is not uniform across these events, and I don't think the session_invalidated precedent's mechanism transfers to all of them by default.** This is the thing I most want on the record before Design reaches for `session-invalidation-audit.ts` as *the* template. That module's whole shape — a bare `db.query()` wrapped in a single `withTimeout`, fail-open, paired with `auth.audit_write_failed` — exists because `session_invalidated` fires from a **Redis** operation (`session.destroy()`) with no Postgres transaction anywhere nearby to join (design.md's Context, point 1, states this explicitly). That's not true of all nine-or-eleven events here:

- **No Postgres write anywhere in the call path — `session_invalidated`'s situation exactly:** `auth.authorization_initiated` (Redis `setex` only), `auth.callback_received` (fires before `handleCallback`'s token exchange, no DB write), `auth.idp_logout_failed` (fires after the session is already destroyed and only on IdP-side failure). `auth.success` also has no write of its own — `resolveOrCreateAccount`'s upsert already ran earlier in the same handler. `auth.failure` (all three branches) — no DB write on any of them. For this group, `withTimeout`/`AuditWriteTimeoutError`/the fail-open pattern is the directly applicable precedent to evaluate.
- **A Postgres write already in flight, in the same function, moments before the emit — a live option `session_invalidated` never had:** `auth.first_access_created` and `auth.role_claim_mapped` both fire immediately after `resolveOrCreateAccount`'s single-statement `UPSERT ... RETURNING` (verified — `account-resolver.ts:121-131` — it's one `db.query` call, not wrapped in an explicit `BEGIN`/`COMMIT` today, but nothing structural prevents wrapping upsert+audit-row in one transaction if Design wants synchronous coupling). `join.link_created` fires right after `INSERT INTO join_links ... RETURNING`. Both `join.link_redeemed` call sites fire right after `INSERT INTO team_memberships ... RETURNING id`. For this group, the closer precedent in this codebase is the in-transaction pattern (`team.manager_established`, `session.draft_created`, `action_item.status_changed` — audit row committed alongside the state change it's about), not the bare-INSERT fail-open pattern built for a Redis-only event. Whichever way Design goes, I'd want it stated as a choice, the way D5 stated departing from `content.ts`'s awaited-no-fail-open precedent — not assumed by habit because `session-invalidation-audit.ts` is the freshest example in the file.
- **`team_id` is not the ambiguous, NULL-by-necessity value it was for `session_invalidated`.** Decision D4 went NULL uniformly because `middleware.ts`'s call sites have no candidate at all and `auth.ts`'s logout site's candidate was ambiguous (a user can hold multiple active sessions). None of that applies here: every `join.*` call site already has `link.team_id` (or the route's own `:teamId` param) sitting in scope, unambiguous, no query needed. Design shouldn't inherit the NULL convention here without checking that it doesn't apply — it doesn't.

## Per-event severity/frequency lens (Decision D1's discipline, reapplied — not gestured at)

The issue is right that this needs a per-event judgment call, not a blanket row. Here's my own pass, stated as instinct for Design to weigh, not a decision:

- **`auth.success`** — unambiguous. SEC-13's "login" category, fires once per completed sign-in, request-terminating-adjacent (redirect follows immediately). Strongest, cleanest candidate in the set — same shape of argument that made `session_invalidated` unambiguous in D1.
- **`auth.first_access_created`** — the single rarest event of this entire set (once per account, ever, for the lifetime of the system). High-significance, effectively zero volume concern. Strong candidate.
- **`auth.role_claim_mapped`** — fires on every login for a user whose IdP-asserted role is non-default (facilitator/EM/admin), so bounded by the population of privileged accounts, not by ordinary traffic. This is the one I'd personally push hardest for — see the ritual-fidelity note below.
- **`auth.idp_logout_failed`** — rare (only fires when the IdP's own end-session call throws), operationally meaningful (a dangling IdP-side SSO session an incident responder would want to find). Similar shape to `session_invalidated`'s own failure branches.
- **`join.link_created`** — low-frequency, gate-keeper action (only facilitators/EMs/admins can call it). Same "access-granting administrative action" shape as `team.manager_established`, which already has a row. Strong candidate.
- **`join.link_redeemed`** — grants team membership, the access-granting event of the three `join.*` names. Same lens as `join.link_created` and `session.draft_created` (both already-audited, access-establishing writes). Strong candidate.
- **`auth.authorization_initiated` / `auth.callback_received`** — these are the two the issue itself flags as needing extra care ("fire on every sign-in attempt, including unauthenticated ones"), and I agree they need real scrutiny — but I'd push back gently on treating that phrase as automatically meaning "exclude, like `token_refresh_success`." `token_refresh_success`'s exclusion in D1 was about volume *class*: it fires on ordinary, successful, mid-session authenticated traffic — any vote, any reveal, at real per-request volume across every live session. These two fire once per login *attempt* — bounded by the login funnel, not by in-session request volume, and definitely not reachable from inside a live Health Check session the way a token refresh is. That's a materially different traffic shape even though both phrases contain the word "every." Where they *do* deserve real caution, and it's two costs, not one, worth naming separately rather than folding into a single "write-amplification" line the way I did the first time: first, `callback_received`/`authorization_initiated` are reachable by unauthenticated, potentially hostile traffic (anyone can hit `/auth/login`), so a synchronous DB write here is a write an attacker gets to trigger for free, which `auth.success`/`first_access_created` are not (those only fire after a successful IdP round-trip). Second — and this is the angle I missed and Priya caught — if a synchronous write adds perceptible latency to this step, that's not only a security cost, it's a first-session-onboarding cost: a brand-new team's first Health Check session is already the highest-friction one anyone runs (learning vote types and the format while also logging in through OIDC for the first time), and any added lag at that exact step compounds friction I'm otherwise managing carefully by design. Both costs point toward the same ask — an explicit number, the same way D1 asked for one on `token_refresh_success` — but they're different costs (write-amplification-by-unauthenticated-request vs. added first-login latency) and Design should weigh both, not assume checking one covers the other. See the open questions below on where that number would actually come from.
- **`auth.failure`** and **`auth.session_created`** — not in the issue's list at all (see above); if Design brings them into scope, `auth.failure`'s two pre-authentication branches (209, 228) share `authorization_initiated`/`callback_received`'s unauthenticated-reachability profile above; its third branch (442, the catch-all) fires only after real IdP round-trip work already happened, which is a different profile again. `session_created` shares `auth.success`'s profile exactly (same call site, same moment).
- **`join.link_rejected`** — the one I'd genuinely want a real number on before anyone decides. Token-guessing against `/api/join/:token` is plausible hostile traffic (a bare random-string GET, no auth required), which could put this in `team.access_grant_mismatch`'s "too volume-prone for a synchronous row" bucket — or it could be human-scale (expired/already-used links from real users, not scanning), which would put it closer to `team.role_change_denied`'s "a blocked attempt against a security boundary should be visible to audit" bucket. I don't have a number and wouldn't guess one; Design should pull whatever's queryable from the existing structured log the way D1's review asked for a `token_refresh_success` volume estimate — but see the open question below before treating "pull a number" as a guaranteed path to an answer.

## Where this touches the ritual, specifically — not generically

I want to be honest that this issue's substance is backend security hygiene, not session mechanics — none of my three core constraints (no-manager-participation, facilitator-from-another-team, simultaneous reveal) are directly implicated the way, say, a session-creation change would be. But two things here are closer to my actual concerns than "audit logging is generally good," and I want to name them specifically rather than pad this section with a generic pass:

- **`auth.role_claim_mapped` is the event that would show its work if someone's `global_role` ever moved into or out of `engineering_manager` via an IdP claim.** My Success Criterion 4 is "no manager has participated in a session, and no exception to that rule has been made" — and the only way anyone would ever *know* that held, two years from now, across every team, is durable records of who held which global role and when it changed. Today that fact lives only in a structured log line, which — by this codebase's own documented admission (`docs/deployment.md`'s Logging section) — a future pino transport with a level filter can silently drop with zero indication anything was lost. I'm not saying this event is a backdoor into the no-manager rule; the rule itself is enforced elsewhere and isn't touched by this issue. I'm saying: if I ever had to answer "did an EM's role ever get misapplied, and when," I'd want that answer to survive a logging-infra decision made for unrelated operational reasons, not depend on nobody having configured a transport filter in the meantime yet. **One thing I stated too loosely the first time, worth being precise about here:** today's emit (`auth.ts:318-324`) carries only the *current* `globalRole` — no `previousRole` field — and fires on every login where the role is non-default, not only on a change. Persisting it as-is still supports the claim above, but only by reconstruction: diffing consecutive rows for a `userId` to infer a transition, with the caveat that a reversion to the default role (`engineer`) emits nothing at all, so it's visible only as an absence of rows, never as a row of its own. That indirection may be perfectly fine for what Success Criterion 4 needs — but whether it is, or whether the claim actually needs an explicit `previousRole`/prior-value field, is a fact about the requirement that Design should decide explicitly, not something I should let this document imply was already settled.
- **`join.link_redeemed` always inserts `team_memberships` with `role = 'participant'`, regardless of the joining user's `global_role`.** That means an account with `global_role = 'engineering_manager'` can redeem a join link and land in `team_memberships` with a participant-shaped row. **Correcting something I got wrong in an earlier draft of this document:** I'd originally described this as "the identical mismatch shape `team.access_grant_mismatch` already exists elsewhere in this codebase to detect." I checked `openspec/specs/team-content-access/spec.md` directly and that's not right — `access_grant_mismatch` fires on exactly one direction (`team_memberships.role = 'engineering_manager'` while `users.global_role != 'engineering_manager'`); what I'm describing here is the mirror-image pairing (`users.global_role = 'engineering_manager'` while `team_memberships.role = 'participant'`), and nothing currently existing in this codebase flags that direction as anomalous at all. The spec also confirms `access_grant_mismatch` itself is deliberately log-only, not a synchronous `audit_log` row, because that helper runs on essentially every content request — so even the direction it does cover was never intended to produce a durable database record. I'm not asking this issue to fix the mismatch itself — it's not this issue's job, and evaluating it is arguably its own question for the join-link feature, not the audit-coverage one. But `join.link_redeemed`'s own durability, if this issue gives it a row, would be the *only* record anywhere of this scenario occurring — not a second copy of a signal that already exists elsewhere. That's a materially different level of urgency than what I originally wrote, and it's exactly what would let an incident responder (or just an EM asking "wait, how did I end up on this team's roster") reconstruct how and when it happened. That's SEC-12's "reconstruct a sequence of events" framing, applied to a scenario that's adjacent to my own rule even though it isn't the rule itself.
- **I checked whether any of this creates a new individual-comparison surface, because that's the thing I always check for, and it doesn't.** I grepped every `FROM audit_log` reference in the backend — every hit is a write site (`session-invalidation-audit.ts`, `connection-reauthorization.ts`, `connection-token-refresh.ts`, the various route files' `INSERT`s) or an unrelated helper (`team-content-access-helper.ts`, which reads `team_memberships`, not `audit_log`). Nothing in this application reads `audit_log` back out for display to any role — no admin dashboard, no facilitator view, nothing. Adding rows here doesn't create a new place an engineer's login pattern becomes visible or comparable to anyone inside the product; it's still purely an incident-response artifact reachable only by direct database access. I'd want design.md to state this plainly (no new read endpoint, full stop) so it stays true rather than becoming a footnote nobody checks when the ninth or tenth event gets added here. **Worth stating as its own boundary, not just as a fact about this issue:** `audit_log` and the session-history/trend-dashboard data are unrelated stores serving unrelated purposes — the trend dashboard is what serves continuity between facilitators (Success Criterion 3), never this audit trail, and this audit trail is what serves incident reconstruction, never the dashboard. Nothing here proposes blurring that, and I'd want Design to write the boundary down explicitly rather than leave it true only by omission — if a future change ever proposes surfacing audit events anywhere facilitator-adjacent "since we're already tracking it," that's a different review with different stakes, and this line is what it should get measured against.
- **This is invisible infrastructure the same way the last one was, and I don't have a session-visible-friction concern the way I'd have for anything client-facing.** None of these nine-to-eleven events sit in front of an ordinary in-session action the way `token_refresh_success` did — they fire pre-authentication, at account-creation/role-mapping time (once per login), at logout, or at team-join time (a one-time action). None of them sit between a live Health Check session and a vote, a reveal, or a topic advance. That's a real structural difference from the one event D1 excluded specifically because it *did* sit there, and I don't think Design should feel obligated to manufacture a latency exclusion here just because D1 had one — the traffic shape that justified D1's exclusion mostly isn't present in this set (the possible exception is the unauthenticated-reachability cost I raised for `authorization_initiated`/`callback_received`/`join.link_rejected` above, which is a different kind of cost than mid-session latency).

4. **What does Design want on `join.link_rejected`'s volume profile before deciding whether it gets a row — and is a number even obtainable?** I don't have a number; I don't think anyone should guess one. But before handing this to Design as an open-ended "pull whatever's queryable from the existing structured log," it's worth confirming that a queryable log destination exists at all: `docs/deployment.md`'s Logging section states plainly that no transport is configured anywhere in this codebase today, and issue #3's reachability-check request was deferred for the identical reason. If production logs today are stdout on ephemeral pods with no aggregation behind them, there may be no number to pull short of someone having ad hoc pod-log access from a long enough window. If that's the case, Design's fallback should be to proceed on the qualitative reasoning above with a stated assumption, or to treat "no volume data obtainable" itself as the reason to default to the more conservative choice (exclude, or no synchronous row) until observability exists to revisit it — not to leave "get a number" sitting as an action item with no path to completion. The same caveat applies to the unauthenticated-reachability cost for `authorization_initiated`/`callback_received` above.
5. **Is there a latency number for any write added to `/auth/login` or `/auth/callback` before it's authenticated?** This is the same "is a number obtainable" question as #4, but the cost it informs is different: first-session onboarding friction, not just write-amplification risk. If the answer is "negligible, single-digit ms," this closes as a non-issue — but I'd want it closed with a number, not assumed, and I'd want Design to weigh it explicitly against the fail-open/timeout mechanism chosen for these two events, not just against the security cost.
6. **What satisfies SEC-13's "authenticated user identity" mandatory field for `authorization_initiated` and `callback_received`, given that neither carries a `userId` today and both fire before authentication exists?** Candidates I can see without deciding among them: `NULL` (matching Decision D4's precedent of a deliberate, uniform gap rather than an inconsistent partial fill), or the truncated `stateNonce` as a correlation key back to the eventual `auth.success`/`auth.failure` row. Design should say which, not leave it implicit.
7. **Does `auth.ts`'s `executeJoinFlow` get `userId` added to its two `join.link_rejected` emissions while this file is already open for this change?** Small, cheap, matches the "small adjacent fix" precedent D5 used for adding `sourceIp` to `session_invalidated`'s log line while that call site was already being touched — not a blocking question, just one I'd want stated as decided rather than silently inherited or silently fixed without comment.
8. **Does `auth.idp_logout_failed`'s structured log gain `sourceIp`, matching the sibling fix `session_invalidated` already got in the same handler?** I checked: today `auth.idp_logout_failed`'s `emitAuditEvent` call (line 534-537) carries only `userId`/`sessionId` — no `sourceIp`, even though `request.ip` is already in scope two lines away and `session_invalidated`'s own emission in the same handler already has it. Same shape of small, cheap, adjacent gap as the last question.
9. **Who signs off on field shape — the `userId`/`sourceIp` gaps named throughout this document — from the perspective of the person who'll actually query this trail under incident pressure?** Everyone else touched by this issue has a voice somewhere in this process: the facilitator/participant experience gets Priya's review, ritual fidelity gets mine. Nobody in this chain represents the security/ops engineer who'll be the one reconstructing an incident from these rows. I'm not assigning that role myself — that's not exploration's call — but I don't think this should ship without someone naming who it is, the same seriousness a facilitator-facing view would get before shipping.

## Recommendation

I don't think this issue should try to close everything in one pass — nine-to-eleven events across two files, three of which turn out to have two implementations apiece, is a lot of individual judgment calls to make well in one change. What I'd ask Proposal to do explicitly: state which of the events named here (plus the two I found that weren't named) are actually going into this change's scope. And if anything gets deferred again — `auth.failure`/`session_created` a third time, `join.link_rejected` pending a volume answer that may not be obtainable, or anything else — I want that held to the full pattern this document opened by describing, not half of it: state the deferral in proposal.md's Non-Goals the way the last two changes did, *and* open a tracked GitHub issue for it before this change is considered done, matching #27→#30 and #30→#132 exactly. A Non-Goals bullet on its own is exactly how a future exploration ends up re-discovering a gap from scratch instead of picking up a filed issue — which is the failure mode this whole document exists to avoid. Three deferrals in a row is a healthy pattern as long as each one is a decision on the record, filed somewhere findable — it stops being healthy the moment one becomes a sentence instead of a ticket.
