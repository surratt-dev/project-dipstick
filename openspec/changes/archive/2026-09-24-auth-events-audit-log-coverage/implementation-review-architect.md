# Implementation Review — Solution Architect

**Reviewer:** Ingrid Sollenberger, Principal Solution Architect
**Change:** `auth-events-audit-log-coverage`
**Scope of this review:** does the shipped code match design.md's architectural decisions; are system boundaries respected; are patterns consistent with existing code in `packages/`. I did not review domain correctness of the join/session logic, UX copy, or test-suite completeness beyond what bears on the architectural questions above — that is Engineer/QA territory.

## Verdict

**Matches design. No architectural findings that block.** This is a well-executed implementation of a design I'd characterize as unusually disciplined about naming its own trade-offs. I verified the two mechanisms, the shared helpers, the transactional coupling, the error-classification boundary, and the provider-agnosticism constraint directly against the diff — all hold. Two minor observations below, neither blocking.

## What I checked and confirmed

**1. Two-mechanism split (Decision D2) is implemented exactly as designed, not defaulted to one shape.**
- `writeFailOpenAuditRow` (`packages/backend/src/auth/fail-open-audit-write.ts`) is used for `auth.success`, `auth.session_created`, `auth.idp_logout_failed` — verified at all three call sites in `packages/backend/src/routes/auth.ts`. No transaction is opened for these; the fail-open/timeout shape is preserved.
- `withAuditTransaction` (`packages/backend/src/auth/audit-write-transaction.ts`) is used for the four transactional-group events at all four call sites: `auth.ts`'s `/auth/callback` (`first_access_created`/`role_claim_mapped`), `auth.ts`'s `executeJoinFlow`, and `join-links.ts`'s two handlers (`join.link_created`, `join.link_redeemed`). This is the correct assignment per D2's stated test (whether a Postgres write is already in flight nearby).
- Both mechanisms are single shared implementations, not reproduced per call site. This is the right call — the design explicitly rejected "a third hand-copied timeout mechanism" and "four hand-copied transaction blocks," and the code honors that.

**2. `session-invalidation-audit.ts` extraction is a pure refactor, verified by diff.** `withTimeout`/`AuditWriteTimeoutError`/`AUDIT_WRITE_TIMEOUT_MS` moved to `audit-write-timeout.ts` unchanged; `session-invalidation-audit.ts` re-exports them for backward compatibility with existing importers. No behavior change — confirmed by reading both the extracted module and the diff (deletion + import + re-export, nothing else touched).

**3. `withAuditTransaction` matches the established precedent (`teams.ts`'s `establishManagerAssociation`), and the one place it improves on it is deliberate, not drift.** I read `teams.ts:1258-1304` directly. Shape matches: `connect()` → `BEGIN` → domain write → audit `INSERT` → `COMMIT`, `ROLLBACK`+rethrow on failure, `release()` in `finally`. The one difference — `withAuditTransaction`'s `ROLLBACK` is wrapped in `.catch(() => {})` where `teams.ts`'s bare `await client.query("ROLLBACK")` is not — is explicitly commented as intentional ("connection is already lost; nothing more to do") and is a genuine hardening, not an inconsistency introduced by accident. Worth a follow-up note (not this change's job) that `teams.ts`'s own inline block could pick up the same guard next time it's touched, so the two "same pattern, two implementations" sites don't quietly diverge further over time. Since `withAuditTransaction` didn't touch `teams.ts` itself and this isn't in scope, I'm not asking for it here — flagging it so it doesn't get lost.

**4. `SET LOCAL statement_timeout` fix (Decision D3) is real, not just documented.** The code issues `SET LOCAL statement_timeout = ${TRANSACTIONAL_AUDIT_STATEMENT_TIMEOUT_MS}` immediately before the audit `INSERT`, inside the transaction, using a fixed internal constant (400, not request-derived) — matches the design's own justification for why string interpolation here is safe despite `SET` not accepting bind parameters. This is the part of the design I'd have pushed back hardest on if it had shipped as originally drafted (a client-side timer racing a query on a single-command-slot connection does not bound anything) — the corrected mechanism is the right fix and it's actually in the code, not just in the document's prose.

**5. `AuditWriteError` boundary (Decision D7) is scoped correctly.** It wraps exactly two things — the audit `INSERT`'s failure and `db.connect()`'s failure — and nothing else. `resolveOrCreateAccount`'s own UPSERT failure is confirmed to propagate unwrapped (the `domainWrite` closure's errors are not caught by `withAuditTransaction`, only `auditInsert`'s are), consistent with the design's statement that this is a separate, pre-existing failure mode not being newly scoped in. The classification only reaches `mapAuthError`/`sanitizeOidcError` at the two `auth.ts` call sites that flow through `GET /auth/callback`'s catch block; `join-links.ts`'s two call sites correctly get a plain, unclassified 500 (Fastify's default handler) — the asymmetry the design names explicitly is the asymmetry that shipped, not something quietly equalized or quietly left unequal without acknowledgment.

**6. Provider-agnosticism constraint (the standing project guidance from `project_oidc_multi_provider.md`, and design.md's own explicit check) holds in the diff.** I checked every new field this change adds: `actor_global_role`/`previousRole`/`globalRole` all come from this application's own mapped vocabulary (`account-resolver.ts`'s `resolveOrCreateAccount`/`mapRoleClaimToGlobalRole`), never a raw IdP claim. Nothing in `audit-write-timeout.ts`, `fail-open-audit-write.ts`, or `audit-write-transaction.ts` branches on IdP identity or references Entra-specific shapes — these three new modules are pure Postgres/timing mechanics, correctly IdP-agnostic. This change doesn't touch the OIDC client abstraction itself, so it neither strengthens nor erodes that layer, but it also introduces no new coupling to Entra-specific behavior, which is what I'd have flagged had it existed.

**7. `resolveOrCreateAccount`'s new `client?: PoolClient` parameter is a clean, additive extension** — defaults to the existing `db` pool when omitted (`const queryExecutor = client ?? db`), so the function's contract for any caller outside this change's scope is unchanged. This is the right shape for threading a transaction client through an existing function without forking it.

**8. `join-links.ts`'s new `SELECT global_role FROM users WHERE id = $1` is correctly placed outside the transaction** (Decision D5, and specifically the connection-scoping point I raised in design review, Finding 5) — verified it runs on the plain pool (`db.query`) before `withAuditTransaction`'s `db.connect()` is called, not on the checked-out client. This is the right boundary: a read with no correctness dependency on the pending write shouldn't occupy a connection a rollback would tear down.

**9. Structured-log-after-commit reordering (Engineer Finding 3) actually happened at all four transactional call sites** — verified in the diff that `emitAuditEvent` for `first_access_created`, `role_claim_mapped`, `join.link_created`, and both `join.link_redeemed` call sites now fires after `withAuditTransaction` returns, not at the old pre-transaction source position. This was the easy-to-miss step the design called out by name, and it's the kind of thing that's simple to verify and easy to get wrong silently, so I checked it directly rather than trusting the task checklist.

**10. `packages/shared`/`packages/frontend` boundary is respected.** `AuthErrorCategory`'s new `internal_error` value is added once, in `packages/shared/src/types/auth.ts`, and consumed from there by both the backend (`mapAuthError`) and frontend (`AuthErrorPage.tsx`'s `isRetryable`) — no duplicated union, no frontend-side reimplementation of the category logic. This is the correct shared-types pattern already established elsewhere in the codebase.

**11. Verified independently, not just by reading the design's claims:** I ran the new and touched test suites (`audit-write-transaction.test.ts`, `fail-open-audit-write.test.ts`, `auth.test.ts`, `join-links.test.ts`, `account-resolver.test.ts`, `error-handler.test.ts`, `oidc-error-sanitizer.test.ts`) — 151 tests, all passing. I also ran `tsc --build` across `packages/backend`, `packages/shared`, and `packages/frontend`; the errors that surface are pre-existing on `main` (confirmed by stashing this change's diff and re-running — identical error set in unrelated test files: `connectionHealth.test.ts`, `teams.test.ts`, `facilitator-*.test.ts`, `SessionLobbyPage.test.tsx`, etc.). None of this change's own files introduce a new type error.

## Minor observations (non-blocking)

- **`teams.ts`'s inline transaction block and `withAuditTransaction` are now two implementations of the same pattern**, differing only in the `ROLLBACK` failure-swallowing guard noted above. This is acceptable — `teams.ts` wasn't in this change's scope and rewriting it to consume the new helper would be scope creep the design correctly didn't take on — but it's worth naming for whoever next touches `teams.ts`, so the divergence is a known fact rather than something a future reader has to rediscover.
- **The `SET LOCAL statement_timeout` cost (running on every transaction even when `auditInsert` no-ops) is real but negligible**, exactly as design.md's D2 mechanics section states. I re-derived this independently rather than taking the document's word for it: a session-parameter `SET LOCAL` involves no disk I/O or lock acquisition, so the added round trip is genuinely cheap. Agreed with the design's own framing — not a concern.

## On my own standing concerns (per my persona's success criteria)

- **Boundaries:** the fail-open/transactional split is a real architectural boundary — one is Redis/timer-shaped, one is Postgres-transaction-shaped — and the code keeps them in separate modules with no cross-contamination. Good.
- **Operability:** Decision D7's `AuditWriteError` classification is a genuine, shipped observability improvement (an accurate `errorClass` on `auth.callback_error` where none was possible before). Confirmed in `oidc-error-sanitizer.ts` and `error-handler.ts` directly, not just claimed in prose.
- **Growth fit:** the shared helpers (`writeFailOpenAuditRow`, `withAuditTransaction`) are the right level of abstraction for "company scale, not internet scale" — parameterized enough to cover this change's seven events without inventing a generic event-bus or plugin system nobody asked for.

No further action requested from the implementation team on this review.
