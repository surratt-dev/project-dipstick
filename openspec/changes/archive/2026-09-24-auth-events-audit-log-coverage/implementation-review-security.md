# Implementation Review — Security

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope:** `packages/backend/src/auth/errors.ts`, `audit-write-transaction.ts`, `fail-open-audit-write.ts`, `audit-write-timeout.ts`, `account-resolver.ts`, `error-handler.ts`, `oidc-error-sanitizer.ts`, and the call sites in `routes/auth.ts` and `routes/join-links.ts`, reviewed against `design.md` Decisions D2–D7 and my own design-stage findings (F2, F3) recorded in `design-review-security.md`.

**Verdict: Approved.** The three areas I flagged at design time — `AuditWriteError`'s classification path, the transactional fail-safe mechanism, and the `previousRole` CTE — are implemented as designed, with no deviation that reopens a gap I'd already accepted as closed. I checked the actual code and the actual tests, not just the design document's account of them; the tests substantiate the specific claims I care about (rollback actually happens, the client error message never carries raw database content, no new call site skips an authorization check). Findings below are informational, not blocking.

---

## 1. `AuditWriteError` classification (`errors.ts`, `mapAuthError`, `sanitizeOidcError`)

This is the finding I'd have pushed back hardest on if it were wrong: an unclassified `AuditWriteError` reaching `mapAuthError`'s default branch would tell an incident responder "sign-in failed" when the actual story is "our own database rejected an audit write," which is exactly the misattribution D7 exists to prevent, and exactly the kind of signal loss that makes an incident six weeks long instead of six hours.

**Verified correct:**

- `AuditWriteError.message` (`errors.ts:44-48`) is the fixed string `"Audit log write failed"` — never built from `cause`. `causeClass` is derived from `cause.constructor.name`, never from `cause.message`. This means a Postgres error that happened to echo back part of a query (theoretically possible, e.g. a constraint-violation message including a column value) cannot reach the client or the log via this path. I checked `oidc-error-sanitizer.test.ts`'s canary test directly (`packages/backend/src/auth/__tests__/oidc-error-sanitizer.test.ts:213-220`) — it constructs an `AuditWriteError` wrapping an `Error` whose message contains a random canary token and asserts the token never appears in the sanitizer's serialized output. That's the right test for the right property; I'd have written the same one.
- `mapAuthError` (`error-handler.ts:28-34`) routes `AuditWriteError` to a new `internal_error` category with a static, generic client-facing message. It does not reuse `authentication_failed` (which would carry "sign-in"/credentials framing, still a misattribution) or `provider_unavailable` (which would misname the IdP as the failing party — a different kind of misattribution, but one I'd have flagged too, since it points incident response at the wrong system). `error-handler.test.ts:27-46` confirms the category and confirms the message does not contain "credentials."
- `sanitizeOidcError` (`oidc-error-sanitizer.ts:93-100`) returns `errorClass`, `message`, `stack`, `causeClass` unredacted for `AuditWriteError` — correctly, since none of those fields can carry IdP- or user-supplied content for this class, unlike a real OIDC error where `message`/`error_description` are redacted by design.
- The client only ever receives `authError.message` (the static string), never `err.message`/`err.stack`/`causeClass` — those go to `request.log.error` only (`routes/auth.ts:516-521`). I traced this through the redirect construction at `routes/auth.ts:538`: only `authError.category` and `authError.message` are interpolated into the `/auth/error` URL. No path from `AuditWriteError`'s internals to the browser exists.
- `AuthErrorPage.tsx`'s `isRetryable` correctly includes `internal_error` — a database hiccup is transient and worth retrying, unlike `authentication_failed`'s implication of a credential problem the user can't fix by clicking "Try Again" alone (they can, and it's a reasonable UX default here since retry costs nothing, but the category distinction is what makes that a considered choice rather than an accident).

**Scope boundary I checked deliberately:** D7 states `resolveOrCreateAccount`'s own UPSERT failure is deliberately *not* wrapped as `AuditWriteError` — only the audit `INSERT` and the `db.connect()` call are. I confirmed this in `withAuditTransaction`: `domainWrite`'s errors propagate unwrapped (`audit-write-transaction.ts:79-99`, the outer `catch (err)` rethrows `err` as-is, only the inner `catch (auditErr)` around `auditInsert` wraps). This is the right line to draw — a raw Postgres error from the UPSERT was already a pre-existing, unclassified failure mode before this change (nothing new introduced, nothing regressed), and conflating it with the audit-write failure mode would blur the exact distinction D7 is trying to sharpen. `audit-write-transaction.test.ts`'s "propagates a domainWrite failure unwrapped" test confirms this holds in practice, not just in the helper's comments.

**One thing worth naming, not blocking:** `join-links.ts`'s two call sites (`join.link_created`, the direct-path half of `join.link_redeemed`) still surface `AuditWriteError` as a plain, unclassified Fastify 500 — D7 states this asymmetry explicitly as accepted, not equalized, and `join-links.test.ts`'s tests (5.4/5.5/6.6/6.7) assert the plain-500 behavior directly rather than silently passing. I'd have flagged this if it were an oversight; it isn't — it's a named, tested, deliberate scope boundary, and building OIDC-shaped error handling into a file that's never needed it for a single failure class is proportionate restraint, not a gap.

## 2. Transactional fail-safe mechanism (`audit-write-transaction.ts`, call sites in `auth.ts`/`join-links.ts`)

My design-stage question here was: does joining the audit write to the domain write's transaction create any new way to end up in an *inconsistent* state — an authorization decision made, a domain effect applied, but no durable trail, or worse, a domain effect applied without ever having been authorized because the transaction machinery changed evaluation order.

**Verified correct:**

- Authorization is unchanged and unaffected. In `join-links.ts`'s `POST /api/teams/:teamId/join-links`, the facilitator-permission check (`memberResult`/`userResult`/`canCreate`, lines 21-63) runs entirely before `withAuditTransaction` is ever called (line 76) — the transaction wraps only the already-authorized write. Same pattern in `GET /api/join/:token`: the link-validity checks (not-found/revoked/expired, lines 148-183) and the unauthenticated-redirect gate (line 186) all happen before the transaction opens (line 218). `withAuditTransaction` is a persistence-and-audit mechanism; it does not sit in the authorization path anywhere, and I confirmed this by reading the call sites directly rather than trusting the design doc's characterization.
- Every mutating query that used to run directly against `db.query` still runs with the same SQL, same parameters, same `ON CONFLICT` idempotency gates — I diffed `join-links.ts` and `auth.ts`'s `executeJoinFlow` against `main` (`git diff main`) and confirmed the domain-write SQL is byte-for-byte unchanged; only the surrounding transaction plumbing and the appended audit `INSERT` are new. This is the property I most wanted true: a change billed as "audit coverage" should not quietly touch the authorization-relevant queries it wraps.
- Fail-closed behavior on audit failure is real, not asserted-and-hoped. `audit-write-transaction.test.ts` proves: (a) an audit `INSERT` failure wraps as `AuditWriteError`, rolls back, and the domain write does not persist (rollback is asserted via the mock's call log, not inferred); (b) a `db.connect()` failure short-circuits before either write runs; (c) the `SET LOCAL statement_timeout` mechanism actually frees the connection before `ROLLBACK` is issued (the "statement_timeout cancellation" test at line ~104, which asserts ordering — INSERT's rejection resolves before ROLLBACK is issued — not just that both eventually happen). This is the fix for the Engineer review's Finding 1 (the original, incorrect claim that `AUDIT_WRITE_TIMEOUT_MS` bounded the transactional group's latency), and I verified the corrected mechanism is what's actually running, not just documented as fixed.
- No new bypass path: the only way `withAuditTransaction`'s domain write commits is via `COMMIT` after both `domainWrite` and (if applicable) `auditInsert` succeed. There's no branch where a caught error leads to returning a success value — every `catch` block either rethrows or is the `finally`'s `client.release()`. I looked specifically for a "fail open" branch that might have been copy-pasted from `fail-open-audit-write.ts` into this file by mistake, since the two mechanisms sit side by side in the same PR; they are correctly kept distinct — `withAuditTransaction` never swallows a write failure the way `writeFailOpenAuditRow` intentionally does for its own group.
- `join.link_redeemed`'s two call sites (`join-links.ts` direct path, `auth.ts`'s `executeJoinFlow`) both gate the audit row on the same `ON CONFLICT DO NOTHING` / `RETURNING id`-emptiness check that already gated the structured log before this change — the transactional wrapping doesn't change *when* the event fires, only how durably it's recorded when it does. Confirmed by reading both call sites directly (`join-links.ts:227-230`, `auth.ts:821-826`).
- Structured-log-after-commit reordering (Engineer Finding 3) is in place at all four transactional call sites, confirmed by reading the code, not just the comments claiming it: `auth.ts:357-380` (first_access_created/role_claim_mapped), `auth.ts:839-846` (join.link_redeemed via executeJoinFlow), `join-links.ts:117-122` (join.link_created), `join-links.ts:245-252` (join.link_redeemed direct path). This matters from a security-auditability standpoint specifically because a structured log claiming an event happened when the durable record was rolled back is a false positive in exactly the trail Success Criterion 4 depends on — I'd have flagged this as a real finding if any of the four had been missed, since it would silently reintroduce the "log says X happened, the durable record disagrees" failure mode the whole change exists to close.

**Residual risk, already named honestly by the design and not something the implementation should have fixed:** the coupled-fate cost of D3 (an `audit_log`-table failure blocks account creation and privileged-role logins, not just administrative actions) is a real, accepted trade-off, not a bug. I raised the narrower gap (a table-isolated failure `/health/ready` wouldn't catch) at design time as F2; it's tracked as issue #131 rather than fixed in this change, which is the correct disposition for something that's an observability gap, not a defect in this diff.

## 3. `previousRole`-capturing CTE (`account-resolver.ts`)

My concern at design time (and the reason this was called out specifically for this review) was cross-user leakage: does the CTE that captures the pre-update `global_role` value risk exposing one user's role history in another user's audit row, or otherwise read data it isn't scoped to.

**Verified correct — this is not a cross-user leak, and I checked the actual predicate to be sure:**

```sql
WITH prior AS (
  SELECT global_role FROM users WHERE oidc_subject = $1 AND oidc_issuer = $2
)
```

`$1`/`$2` are the exact same `(oidc_subject, oidc_issuer)` pair used in the `INSERT ... VALUES ($1, $2, ...)` and the `ON CONFLICT (oidc_subject, oidc_issuer)` clause immediately below it (`account-resolver.ts:137-151`) — the same identity pair that anchors the UPSERT itself. The CTE cannot resolve to any row other than the one the UPSERT is about to touch: `(oidc_subject, oidc_issuer)` is the documented, comment-affirmed identity match key for this table (line 118: "Identity match key is (oidc_subject, oidc_issuer) only"), and that pair is a unique constraint the `ON CONFLICT` clause depends on for correctness independent of this change. There is no scenario — race condition, malformed claim, or otherwise — where this CTE reads a *different* user's `global_role`, because it is parameterized identically to the write it accompanies, not independently derived. This holds even under concurrent authentication from two different users: each request's CTE and UPSERT share one parameter set, scoped to that request's own claims.

The resulting `previousGlobalRole` value is:
- `null` for a new user (`is_new_user` true) — correctly distinguished, not conflated with "no change."
- The account's own prior value for a returning user — this is the account's own historical data being surfaced back to an operator investigating that same account, which is the entire point of Decision D4 (Success Criterion 4's "did an EM's role ever get misapplied" question). This is not a new category of sensitive data exposure; `global_role` values are already written to `audit_log` today for the current-role case, and this only adds the immediately-prior value for the same account, in the same row.
- Never a raw IdP claim value — `mapRoleClaimToGlobalRole`'s allowlist gating (which rejects attacker-controlled claim strings *before* they reach the UPSERT's `$5` parameter) is unchanged by this diff, and the CTE reads a stored, previously-validated `global_role` column value, not a raw claim. This preserves the exact "raw claim values never reach the audit trail" property `mapRoleClaimToGlobalRole`'s existing comment states, which I'd have flagged hard if the CTE had somehow bypassed it — it doesn't, since it never touches `claims` at all.

Tests confirm the shape (`account-resolver.test.ts`'s new `previousGlobalRole / optional client parameter` describe block): null-for-new-user, correct value for returning user, and confirmation the UPSERT statement text actually contains `WITH prior AS` (not just that the mock returns the right shape regardless of the real query). I'd have wanted a test asserting the CTE's `WHERE` clause uses the same `$1`/`$2` placeholders as the outer UPSERT specifically — the current test only checks the SQL text contains the CTE, not that its parameterization is tied to the same identity. This is a minor test-completeness gap, not a shipped defect (I read the actual SQL string and confirmed the parameterization myself), and I'm not blocking on it — noted for whoever next touches this file.

## Other items checked while in these files

- **`writeFailOpenAuditRow`/`withTimeout` extraction** (`audit-write-timeout.ts`): pure extraction, confirmed byte-for-byte against the pre-change `session-invalidation-audit.ts` content via `git diff`. No behavior change, no new risk surface. Re-export from `session-invalidation-audit.ts` keeps existing importers working.
- **`role_claim_mapped`'s allowlist discipline is unaffected**: `PERMITTED_GLOBAL_ROLES` gating and the "never log a rejected claim value" comment (`account-resolver.ts:82-90`) are untouched by this diff — I checked this specifically since it's the property that keeps attacker-controlled input out of compliance-relevant records, and it would have been an easy thing to regress while restructuring the surrounding function.
- **No secrets or claim values appear in any new `metadata` JSON payload** — I read every new `INSERT INTO audit_log` call site (`auth.ts` x3, `join-links.ts` x2) and confirmed the `metadata` objects carry only `oidcSubject`, `globalRole`/`previousRole`, `correlationId`, `linkId`, `expiresAt` — all either already-audited fields or this application's own mapped vocabulary, never a raw claim.
- **Provider-agnostic constraint** (per this project's standing guidance that OIDC support isn't Entra-only): confirmed nothing in this diff branches on IdP identity, tests a provider-specific claim shape, or assumes Entra's token format. `actor_global_role` comes from `users` table state; `previousRole`/`globalRole` are this codebase's own enum values; `oidcSubject`/`oidcIssuer` are pre-existing generic fields. This matches design.md's own stated check on this point, and I re-verified it against the code rather than taking the design doc's word for it.

## Summary

No blocking findings. The implementation matches design.md's Decisions D2–D7 faithfully, including the corrections made during design review (Engineer Findings 1, 2/4, 3, 6; my own F2/F3), and the test suite backs the specific claims that matter from a security standpoint — rollback actually happens, redacted-vs-unredacted fields are correct and canary-tested, authorization checks are untouched, and the CTE's parameterization ties it to the same identity as the surrounding write. The one non-blocking note is the account-resolver test suite could more precisely pin the CTE's parameter binding rather than just its SQL text, for whoever next modifies that query.
