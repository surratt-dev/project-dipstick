## Why

This is the third link in a deliberate chain: `websocket-connection-reauthorization` (#27) named the HTTP-side `session_invalidated`/`token_refresh_*` gap in its own Non-Goals rather than absorbing it — that became #30. `http-auth-audit-log-coverage` (#30) closed `session_invalidated`'s gap at all four of its call sites and, in turn, named the much larger remaining gap — every other event in `auth.ts`, and all of `join-links.ts`'s events — in its own Non-Goals rather than absorbing it. That became #132, this issue. Eleven events across two files (thirteen call sites, once `auth.ts`'s duplicate `executeJoinFlow` join-redemption path is counted alongside `join-links.ts`'s) are `emitAuditEvent`-only today: a structured pino log line, which `audit-logger.ts` itself documents as the operational alert path, not the durable record. BRD SEC-12 frames the audit log as the mechanism for post-hoc incident reconstruction; SEC-13 requires "user authentication (login, logout, failure, expiry)" and "session lifecycle (creation, join, close, facilitator changes)" without qualification; SEC-15 requires that record live somewhere the application can't modify or delete — a guarantee a log line alone doesn't provide, and one that `docs/deployment.md`'s own Logging section already names these eleven events as being at risk from (a future transport-level filter can drop them silently, with zero indication anything was lost).

Why now, specifically: same answer as the two changes before this one — there is no scheduled security review or customer gate forcing this. It's being picked up because it's a fully-scoped, well-understood gap, sitting adjacent to work already done twice in this exact file, and it's cheaper to close now than to let a fourth exploration re-derive the same call-site inventory from scratch.

## What Changes

Grounded in `exploration-notes.md`'s per-event severity/frequency pass (Decision D1's lens, reapplied). Seven events get a durable `audit_log` row; four stay log-only, deferred with a tracked follow-up rather than a silent Non-Goals sentence.

**Get a DB row:**
- `auth.success` — SEC-13's "login" category, fires once per completed sign-in.
- `auth.session_created` — fires in the same breath as `auth.success` (same call site, right after `request.session.regenerate()`); the cleanest match for SEC-13's "session lifecycle (creation...)" category, and not in either prior change's Non-Goals list only because nobody had named it until this exploration — brought in now rather than deferred a third time on the same file.
- `auth.first_access_created` — the rarest event in this entire set (once per account, for the system's lifetime). High-significance, no volume concern.
- `auth.role_claim_mapped` — fires whenever a login resolves a non-default `global_role` from an IdP claim. This is the event that lets anyone answer, two years from now, "did an EM's role ever get misapplied, and when" — the durable record my own no-manager-participation success criterion (Champion's Success Criterion 4) ultimately depends on being able to reconstruct. Gains a `previousRole` field (see design.md) so that answer doesn't depend on diffing consecutive rows.
- `auth.idp_logout_failed` — rare (only fires when the IdP's own end-session call throws), operationally meaningful (a dangling IdP-side SSO session an incident responder would want to find).
- `join.link_created` — low-frequency, gate-keeper action restricted to facilitators/EMs/admins; same "access-granting administrative action" shape as `team.manager_established`, which already has a row.
- `join.link_redeemed` — grants team membership, the access-granting event of the three `join.*` names. **Covers both real call sites behind this one event name**: `join-links.ts`'s `GET /api/join/:token` (already-authenticated path) and `auth.ts`'s `executeJoinFlow` (through-auth path, invoked from `/auth/callback` when a join token rode through the OIDC state round-trip). Treating this as "join-links.ts's event" and missing the `auth.ts` half would reproduce the exact gap Decision D3 of the precedent change closed for `session_invalidated`'s fourth call site — named explicitly here so it isn't rediscovered during implementation. `actor_global_role` is resolved differently at the two call sites, stated explicitly rather than left implicit: `executeJoinFlow` gains a new parameter threaded from its caller's already-resolved `user.globalRole` (a free pass, no lookup); `join-links.ts`'s `GET` handler has no such value in scope anywhere in the handler and issues a new `SELECT global_role FROM users WHERE id = $1` (see design.md Decision D5).

**Stay log-only, deferred with a tracked issue (not just a Non-Goals bullet):**
- `auth.authorization_initiated` and `auth.callback_received` — both fire once per login *attempt*, reachable by unauthenticated, potentially hostile traffic (anyone can hit `/auth/login`), unlike every event above (each of which only fires after a real IdP round trip or an already-authenticated request). A synchronous write here is a write an attacker gets to trigger for free, and — separately — any added latency at this exact step lands on first-session onboarding, already the highest-friction session anyone runs (OIDC login plus learning the ritual at once). Neither a volume nor a latency number is obtainable today (`docs/deployment.md` states no log transport is configured anywhere in this codebase; issue #3's reachability-check request was deferred for the same reason). Per the exploration's own recommendation, "no data obtainable" is itself treated as the reason to hold the conservative default rather than guess.
- `auth.failure` — not named in either prior change's Non-Goals, and SEC-13's most on-the-nose "failure" match of anything in this set, so stated here explicitly rather than missed a third time. Two of its three call sites (missing `state`; expired/invalid `state`) share `authorization_initiated`/`callback_received`'s unauthenticated-reachability profile above; its third (the catch-all for any thrown error, including `MissingClaimError`) fires only after real IdP work already happened — a different profile the deferred follow-up should evaluate separately rather than assume the same answer applies uniformly.
- `join.link_rejected` — reachable via a bare, unauthenticated `GET /api/join/:token`; whether its real-world traffic is human-scale (expired links) or scanning-scale (token-guessing) determines which side of the `team.access_grant_mismatch` (log-only) / `team.role_change_denied` (audited) line it falls on, and that number isn't obtainable today either.
- **Tracked as GitHub issue #156**, opened as part of this change, matching the #27→#30→#132 pattern exactly rather than leaving these four as a sentence nobody re-reads.

**Mechanism, stated as a choice (see design.md for the full reasoning):**
- `auth.success`, `auth.session_created`, `auth.idp_logout_failed` — no Postgres write anywhere nearby in the call path, the same situation `session_invalidated` was in. These reuse (via a shared, parameterized helper — not a third copy) the fail-open/timeout mechanism `session-invalidation-audit.ts` established: a single bounded timeout across both round trips, fail-open, `auth.audit_write_failed` as the detectability signal.
- `auth.first_access_created`, `auth.role_claim_mapped`, `join.link_created`, `join.link_redeemed` (both call sites) — a Postgres write is already in flight, moments before the emit, in the same function. These join that existing write in one transaction (the pattern already established by `team.manager_established`/`session.draft_created`/`action_item.status_changed`), not the bare-INSERT-plus-timeout mechanism built for a Redis-only event. This is a deliberate departure from copying `session-invalidation-audit.ts` as the default template just because it's the newest example in the file.
- `team_id` is populated (not NULL) on all `join.*` rows — every call site already has an unambiguous candidate (`link.team_id` or the route's own `:teamId` param) in scope, unlike `session_invalidated`'s call sites, which had none. It is NULL on the other five events (`auth.success`, `session_created`, `first_access_created`, `role_claim_mapped`, `idp_logout_failed`) — these are account-level events with no single team in scope, a genuine architectural absence rather than a punt.
- `auth.ts`'s `executeJoinFlow` gains `userId` on its two `join.link_rejected` structured-log emissions (it's already in scope there, unlike `join-links.ts`'s pre-session-check branches, which structurally have none) — a small, adjacent fix while this file is already open, matching the precedent's own `sourceIp` addition to `session_invalidated`. `auth.idp_logout_failed`'s structured log similarly gains `sourceIp`, matching the sibling fix `session_invalidated` already received in the same handler.
- The transactional group's rollback-and-rethrow is caught by `GET /auth/callback`'s existing catch block for two of its four call sites (`auth.first_access_created`/`auth.role_claim_mapped`'s transaction, and `executeJoinFlow`'s `join.link_redeemed` transaction, invoked from within the same handler) — the same catch block every `auth.failure` branch already shares, built to classify and sanitize OIDC-library errors, not Postgres ones. Left alone, a rolled-back audit write would fall into that machinery's generic "unrecognized error" fallback: redacted diagnostic detail, and a message that says "sign-in failed" when the actual cause is this application's own database. A new `AuditWriteError` class (design.md Decision D7) wraps the audit `INSERT`'s thrown error — and, per design review, a failed `db.connect()` too (a new failure mode this change introduces by checking out a pooled client in `/auth/callback` for the first time) — before rethrow, following the existing `MissingClaimError` special-casing pattern, so `mapAuthError`/`sanitizeOidcError` recognize it explicitly instead. `AuthErrorCategory` gains a fifth value, `internal_error`, for this case, treated as retryable the same as `provider_unavailable`. `join-links.ts`'s own two call sites (`join.link_created`, and the direct-path half of `join.link_redeemed`) have no equivalent catch block; a rolled-back audit write there surfaces as an ordinary Fastify 500, not a redirect — a real asymmetry between the two `join.link_redeemed` call sites' failure UX, named here rather than equalized, since building OIDC-shaped error handling into a file that has never needed it is out of proportion with what this change is instrumenting.
- The transactional group's four call sites share one implementation, not four independent copies: a shared `withAuditTransaction` helper (design.md Decision D2) owns the connect/`BEGIN`/domain-write/audit-`INSERT`/`COMMIT`/`ROLLBACK`/`release` skeleton, the `db.connect()`-and-audit-`INSERT` `AuditWriteError` wrapping, and a `SET LOCAL statement_timeout` on the audit `INSERT` (design.md Decision D3) that gives the 500ms figure a mechanism that actually bounds the transactional group's rollback path — design review (Engineer) found the original wording didn't hold, since a hung `INSERT`'s follow-up `ROLLBACK` queues behind it on the same connection; the fix makes Postgres itself cancel the query, freeing the connection promptly, rather than relying on a client-side race that never resolved the underlying query. Each of the four call sites' existing structured `emitAuditEvent` calls (`first_access_created`, `role_claim_mapped`, `join.link_created`, `join.link_redeemed` ×2) move to fire only after the transaction commits, matching `team.manager_established`'s own existing ordering — otherwise a rolled-back transaction could still produce a structured log line claiming the event happened (design review, Engineer Finding 3), reproducing this change's own reason for existing.

**No new admin-configurable surface, no new interval, no new on/off switch.** This instruments existing emit sites; it does not introduce a new mechanism.

## Capabilities

### New Capabilities

None. This instruments existing authentication- and join-event-logging capabilities; it does not introduce a new domain of behavior.

### Modified Capabilities

- `auth-error-handling`: the "Authentication event logging" requirement's scenarios for `auth.success`, `auth.session_created`, `auth.first_access_created`, `auth.role_claim_mapped`, and `auth.idp_logout_failed` are updated to state the new DB-row guarantee, field shape (including `role_claim_mapped`'s new `previousRole` field), and transactional-vs-fail-open mechanism for each. A new requirement documents the fail-open/timeout write path shared by `auth.success`/`auth.session_created`/`auth.idp_logout_failed`, mirroring the existing "Audit log write failures fail open" requirement's shape. `auth.authorization_initiated`, `auth.callback_received`, and `auth.failure` remain explicitly log-only, stated as a deliberate scope boundary rather than left silent. "Distinct error messages for authentication failure modes" and "OIDC library error sanitization" are also updated: a new `AuditWriteError` class and a fifth `AuthErrorCategory` value (`internal_error`) mean a rolled-back transactional-group audit write is classified and logged distinguishably from an OIDC error, rather than falling into the existing sanitizer's generic "unrecognized" fallback.
- `join-link`: a new requirement establishes that `join.link_created` and `join.link_redeemed` (both call sites) are durably recorded in `audit_log`, in the same transaction as the state change each accompanies, with `team_id` populated, `actor_global_role` resolved per call site (a parameter pass at `executeJoinFlow`, a new lookup at `join-links.ts`'s `GET` handler), and the two `join.link_redeemed` call sites' asymmetric failure UX on rollback named explicitly. `join.link_rejected` remains explicitly log-only, cross-referenced to issue #156.

## Impact

- **Code:** `packages/backend/src/routes/auth.ts` (six of its thirteen `emitAuditEvent` call sites gain a DB row: `auth.success`, `auth.session_created`, `auth.first_access_created`, `auth.role_claim_mapped`, `auth.idp_logout_failed`, and `executeJoinFlow`'s `join.link_redeemed` call site), `packages/backend/src/routes/join-links.ts` (`join.link_created` and its `join.link_redeemed` call site), `packages/backend/src/auth/account-resolver.ts` (capturing the prior `global_role` value for `role_claim_mapped`'s new `previousRole` field), `packages/backend/src/auth/audit-logger.ts` (no change to `AuditEventName` itself — all seven event names already exist). A new shared module generalizes `session-invalidation-audit.ts`'s fail-open/timeout mechanism for reuse by the three non-transactional events, rather than a third hand-copied implementation.
- **Data:** No schema migration. `audit_log` (migration `8_audit_log.sql`) already has the columns this needs; `operation` is unconstrained `TEXT`.
- **Latency:** A bounded, fail-open DB round trip is added to three already-terminating paths (`auth.success`/`session_created`'s redirect, `idp_logout_failed`'s fallback response). Four writes join an existing in-flight transaction rather than adding a new round trip. No change to any pre-authentication or hot in-session path — that boundary is the entire reason `authorization_initiated`/`callback_received`/`failure`/`join.link_rejected` are deferred rather than included.
- **Operational reliability of `audit_log` (Decision D3's real cost, addressed rather than left as an accepted-on-faith tradeoff):** no uptime SLA or historical availability number exists for `audit_log`, or for Postgres generally, anywhere in this codebase — stated plainly rather than invented. What does exist and already applies to this exact failure mode: `/health/ready` (`packages/backend/src/routes/health.ts`) checks Postgres reachability directly and returns `503` when it's down, and `docs/deployment.md`'s Kubernetes section wires that into the liveness/readiness probe — so a *full* Postgres outage, the scenario that makes `audit_log` unreachable, already surfaces as a failing readiness probe in production today, independent of anything this change adds. What that doesn't cover: a failure isolated to the `audit_log` table specifically (a lock, a constraint violation, a permissions problem scoped to that one table) while the rest of Postgres answers fine — no monitoring specific to that narrower slice exists, and this change doesn't add one. This narrower gap is tracked as GitHub issue #131 (design review, Security F2), not left as an untracked observation — this change's own new signals (`auth.audit_write_failed` for three more events, and `errorClass: "AuditWriteError"` on `auth.callback_error`) are named on that issue as concrete inputs for whoever builds the alert/dashboard it calls for. See design.md Decision D3 for the full reasoning, including the request-latency correction made during design review (Engineer Finding 1: the original 500ms bound didn't hold for the transactional group's rollback path; a `SET LOCAL statement_timeout` fix makes it hold in practice) and the one concrete detectability improvement this change does add (Decision D7, now also covering `db.connect()` failures).
- **SEC-15:** its write-only-destination guarantee is a property of the `audit_log` table's existing database permissions, unchanged by this change — none of the seven new call sites touch table-level grants, and this change's job is writing rows to a destination that already carries that property, not establishing it.
- **Explicitly out of scope, named here so "done" isn't overread once this ships:**
  - `auth.authorization_initiated`, `auth.callback_received`, `auth.failure`, and `join.link_rejected` — tracked as GitHub issue #156, opened as part of this change, pending the volume and latency numbers named above.
  - Whether `role_claim_mapped` should also fire on a role's *reversion* to the default (`engineer`) — today it fires only on a non-default mapping, so a reversion is visible only as an absence of rows, never a row of its own. This is a change to when an existing event fires, not to whether an existing emission gets a row, and is a separate question from this change's scope. Tracked as GitHub issue #157, alongside #156 (design review, Security F3).
  - `join.link_redeemed` always inserting `team_memberships` with `role = 'participant'` regardless of the joining user's `global_role` (an EM redeeming a join link lands with a participant-shaped row) — a mismatch this change makes durably visible for the first time (see design.md), but not this change's job to fix. Evaluating or correcting the mismatch itself is its own question for the join-link feature.
  - Who signs off on field shape (`userId`/`sourceIp`/`team_id` completeness) from the perspective of the person reconstructing an incident under pressure — flagged in exploration-notes.md as a real, unassigned gap; not something this proposal can resolve by naming a role unilaterally.
