## Context

This closes issue #132, itself named as a recommended follow-on in `http-auth-audit-log-coverage`'s own Non-Goals (which closed `auth.session_invalidated`'s gap), itself named as a follow-on from `websocket-connection-reauthorization`'s Non-Goals (issue #30 → #27). `exploration-notes.md` already did the per-event grounding this design builds on: every `emitAuditEvent(` call site in `routes/auth.ts` and `routes/join-links.ts` was read and re-verified directly against the code, not inherited from either prior change's event list (which itself turned out to be missing `auth.failure` and `auth.session_created`, and to undercount `join.link_redeemed`/`join.link_rejected` by treating `join-links.ts` as the only file involved when `auth.ts`'s `executeJoinFlow` duplicates two of the three `join.*` event names on a separate, through-auth code path).

This design does not re-derive that grounding. It makes the Design-stage calls exploration-notes.md explicitly declined to make: which of the eleven events get a row (proposal.md's Decision, restated here with the reasoning), what mechanism each uses, and what each row's fields are.

**Constraint carried forward from standing project guidance:** this auth layer must remain provider-agnostic (Entra is the primary configured IdP today, not the only one this code may assume). Checked against every field this design adds: `actor_global_role` comes from this application's own `users` table; `previousRole`/`globalRole` are this codebase's own mapped vocabulary (`engineer`/`engineering_manager`/`application_admin`), never a raw IdP claim value (raw claim values are explicitly excluded from audit records today — `account-resolver.ts`'s `mapRoleClaimToGlobalRole`, by design, since they're attacker-controlled input); `oidcSubject`/`oidcIssuer` are already-audited fields with no new provider-specific shape introduced. No part of this design branches on IdP identity.

**Two mechanisms are needed, not one — this is the central technical fact this design has to get right rather than default on.** `session-invalidation-audit.ts` (the direct fail-open/timeout precedent) exists because `auth.session_invalidated` fires from a Redis operation with no Postgres transaction anywhere nearby to join. That is true of three of this change's seven in-scope events (`auth.success`, `auth.session_created`, `auth.idp_logout_failed`) and not true of the other four (`auth.first_access_created`, `auth.role_claim_mapped`, `join.link_created`, `join.link_redeemed`), each of which fires immediately after a Postgres write — `resolveOrCreateAccount`'s UPSERT, `INSERT INTO join_links`, `INSERT INTO team_memberships` — already in flight in the same function. For that second group, the closer, already-shipped precedent in this codebase is `teams.ts`'s `establishManagerAssociation` (`team.manager_established`): `client.connect()` → `BEGIN` → domain write → `INSERT INTO audit_log` in the same transaction → `COMMIT`/`ROLLBACK` on failure, `client.release()` in `finally`. Decision D2 below states which group each event is in and why; Decision D3 states the real cost of the transactional choice honestly rather than presenting it as strictly better.

## Goals / Non-Goals

**Goals:**
- Give seven events (`auth.success`, `auth.session_created`, `auth.first_access_created`, `auth.role_claim_mapped`, `auth.idp_logout_failed`, `join.link_created`, `join.link_redeemed`) a durable `audit_log` row, using whichever of the two mechanisms above genuinely fits each event's call-site shape — not defaulting to the newer, more visible one.
- Cover both real call sites behind `join.link_redeemed` (`join-links.ts`'s direct path, `auth.ts`'s `executeJoinFlow` through-auth path) so this doesn't reproduce the exact "N of N+1 call sites covered" gap Decision D3 of the precedent design existed to close for `session_invalidated`.
- Give `auth.role_claim_mapped` a `previousRole` field so Success Criterion 4's "did an EM's role ever get misapplied, and when" question is answerable directly from a row, not only by diffing consecutive rows for a `userId`.
- State explicitly, as decisions rather than silent gaps, which events are deferred and why, with the deferral tracked as a real, filed issue (#156) rather than a Non-Goals sentence alone — the same discipline the two prior changes in this chain established.
- Reuse existing machinery: `resolveActorGlobalRole` where the actor's role isn't already known locally; the already-generic parts of `session-invalidation-audit.ts` (`withTimeout`, `AuditWriteTimeoutError`) for the fail-open group, rather than a third hand-copied timeout mechanism.

**Non-Goals:**
- `auth.authorization_initiated`, `auth.callback_received`, `auth.failure`, `join.link_rejected` — deferred, tracked as issue #156. Not designed here beyond the scope statement in proposal.md.
- Whether `auth.role_claim_mapped` should also fire on reversion to the default role (`engineer`). This is a change to the event's firing condition, not to whether an existing emission gets a row — out of scope for an audit-coverage change. Named in Risks below so it isn't mistaken for something this design silently fixed.
- Correcting `join.link_redeemed`'s `role = 'participant'` hardcoding regardless of the joining user's `global_role` (an EM redeeming a join link lands with a participant-shaped membership row). This design makes that scenario durably visible for the first time (it gets a real `audit_log` row with the EM's actual `global_role` in `actor_global_role`), which is a genuine improvement over today's log-only state, but fixing the mismatch itself is a join-link feature question, not this change's.
- Any admin-facing configuration surface. No interval, threshold, or on/off switch is introduced.
- Building or wiring a monitoring/alerting consumer for `auth.audit_write_failed` or any other `AuditEventName`. Same accepted, stated gap as the precedent's own Non-Goals — this design doesn't newly claim to close it.
- Cancelling a hung Postgres query when `withTimeout` times out for the **fail-open group** — same accepted limitation as the precedent's Decision D5/Risks. (The **transactional group** is a deliberate exception, not an oversight: Decision D3, revised during design review, does cancel a hung audit `INSERT` via a Postgres-level `statement_timeout`, because for that group the alternative — a client-side timer racing an `INSERT` that keeps occupying the connection a subsequent `ROLLBACK` needs — was found not to bound request latency at all. This Non-Goal still stands for connection-level or network-level hangs, and for the fail-open group's writes, neither of which this design cancels.)

## Decisions

### Decision D1: Scope — seven events get a row; four are deferred to issue #156

**Choice:** `auth.success`, `auth.session_created`, `auth.first_access_created`, `auth.role_claim_mapped`, `auth.idp_logout_failed`, `join.link_created`, and `join.link_redeemed` (both call sites) get a durable `audit_log` row. `auth.authorization_initiated`, `auth.callback_received`, `auth.failure` (all three call sites, uniformly — see rationale), and `join.link_rejected` (all five call sites) remain log-only.

**Rationale, applying exploration-notes.md's per-event lens:**
- The seven in-scope events share a property none of the four deferred ones have: every one only fires after either a completed IdP round trip (`auth.success`, `auth.session_created`, `auth.first_access_created`, `auth.role_claim_mapped`), an already-authenticated request (`join.link_created`, both `join.link_redeemed` call sites), or a failure that happens after successful authentication and local session teardown (`auth.idp_logout_failed`). None is reachable by an unauthenticated, potentially hostile request the way `authorization_initiated`/`callback_received`/`join.link_rejected` are (`GET /auth/login` and `GET /api/join/:token` both accept arbitrary unauthenticated traffic), and none shares `auth.failure`'s two pre-authentication branches' profile.
- `auth.failure` is treated as a single deferred unit rather than split by call site (its third, post-IdP-round-trip catch-all branch has a materially different reachability profile than its first two). Splitting one event name's DB-row treatment by call site, the way this design does for `session_created`/`success` sharing a mechanism group, is a reasonable thing for issue #156 to consider — but doing it here, for an event this proposal doesn't otherwise touch, would be scope creep into a question the deferred issue exists to hold open. Stated as a single deferred unit, not decided piecemeal.
- `auth.session_created` was not named in either prior change's Non-Goals — nobody had inventoried it until this exploration. It is brought into scope here rather than deferred a third time on the same file: it shares `auth.success`'s exact call site and mechanism group, so including it costs nothing beyond what `auth.success` already requires, and SEC-13's "session lifecycle (creation...)" category is otherwise unrepresented by anything in this change's scope without it.
- `join.link_rejected`'s deferral is not a severity judgment (a blocked join attempt against a security boundary is exactly the kind of thing SEC-12 wants reconstructible) — it's an unresolved volume question. `docs/deployment.md` confirms no log transport exists today to pull a real number from, so proceeding on a guess in either direction would be worse than holding the conservative default and revisiting once observability exists.

**Alternative considered:** Include `auth.failure`'s catch-all branch (line 442) only, splitting the event by call site now rather than deferring the whole event. Rejected — the catch-all branch's `auditFields` object is built inline in the same `catch` block as the two pre-auth branches, and giving one branch a DB row while its siblings stay log-only under the identical event name is exactly the "three of four `reason` values audited" shape Decision D3 of the precedent design existed to close, not reproduce. If issue #156 wants to split treatment by branch, it should do so as a stated decision with the full event in view, not as a side effect of this change reaching for the branch that happened to be easiest.

### Decision D2: Two mechanisms, assigned by whether a Postgres write is already in flight nearby

**Choice:**
- **Fail-open, bounded-timeout group** (`auth.success`, `auth.session_created`, `auth.idp_logout_failed`): no Postgres write occurs anywhere else in these call paths. These reuse the already-generic parts of `session-invalidation-audit.ts` — `withTimeout`, `AuditWriteTimeoutError`, `AUDIT_WRITE_TIMEOUT_MS` — via a new, parameterized write function rather than a third hand-copied timeout implementation.
- **Transactional group** (`auth.first_access_created`, `auth.role_claim_mapped`, `join.link_created`, `join.link_redeemed` at both call sites): a Postgres write is already in flight, moments before the emit, in the same function. These join that write's transaction, following `teams.ts`'s `establishManagerAssociation`/`team.manager_established` pattern (`client.connect()` → `BEGIN` → domain write → audit `INSERT` → `COMMIT`, `ROLLBACK` + rethrow on any failure, `client.release()` in `finally`) rather than the fail-open pattern built for a Redis-only event.

**Mechanics — fail-open group:** `session-invalidation-audit.ts`'s `withTimeout`/`AuditWriteTimeoutError`/`AUDIT_WRITE_TIMEOUT_MS` are extracted, unchanged, into a new small shared module (`packages/backend/src/auth/audit-write-timeout.ts`); `session-invalidation-audit.ts` imports them from there instead of defining them locally, so its own tested behavior is unchanged by this refactor. A new module, `packages/backend/src/auth/fail-open-audit-write.ts`, exports:

```ts
export async function writeFailOpenAuditRow(params: {
  operation: AuditEventName;
  userId: string;
  actorGlobalRole: string;
  actorIp: string;
  teamId: string | null;
  metadata: Record<string, unknown>;
  log: FastifyBaseLogger;
  failureAuditFields: Record<string, unknown>; // merged into auth.audit_write_failed's payload
}): Promise<void>
```

`actorGlobalRole` and `teamId` are typed, required parameters, not resolved or defaulted inside the helper itself — every caller passes both explicitly (see "a real optimization this generalization makes visible," below, for how each caller obtains `actorGlobalRole`; every call site in this group passes `teamId: null`, stated above). This snippet and tasks.md's task 1.2 describe the same signature; reconciled here after an earlier revision of this document omitted both fields from the snippet while the surrounding prose already described them (BA review, Finding 3).

**Type fix (Engineer review, Finding 5):** `operation` is typed `AuditEventName` (imported from `audit-logger.ts`), not `string`. Every existing `emitAuditEvent` call site is checked against this union at compile time specifically to catch a typo'd operation name before it becomes a silent wrong value in an unconstrained `TEXT` column; typing this parameter `string` would have quietly reopened that exact class of bug for the one write path this change generalizes into a multi-event function. Costs nothing, closes a real gap.

This resolves `actor_global_role` via `resolveActorGlobalRole` only when the caller doesn't already have it — see below, two of the three events in this group already do. `team_id` is a parameter defaulting to `null`; every call site in this group passes `null` explicitly (none of these five has a team concept — login and logout are account-level, not team-scoped, a genuine architectural absence, not a punt the way `session_invalidated`'s NULL was for `explicit_logout`). On any failure (explicit error or timeout), it emits `auth.audit_write_failed` via `emitAuditEvent`, merging `failureAuditFields` with `{ failureMode: "error" | "timeout", sourceIp: actorIp }` — generalizing the existing signal's shape rather than hardcoding `authSessionId`/`reason`, which only `session_invalidated` and (now) `idp_logout_failed`/`session_created` have.

**A real optimization this generalization makes visible:** unlike `session_invalidated`, two of this group's three events already have the actor's `global_role` in scope without a lookup. `auth.success` and `auth.session_created` both fire after `resolveOrCreateAccount` has already returned `user.globalRole` in the same handler — `writeFailOpenAuditRow`'s caller passes it directly, skipping the `resolveActorGlobalRole` SELECT entirely for these two. Only `auth.idp_logout_failed` needs the lookup (`SessionData` carries no `globalRole` field — verified against `session-store.ts`), matching `session_invalidated`'s existing need. This directly serves the first-session-latency concern raised in exploration-notes.md: `auth.success`/`session_created`'s write is now one bounded round trip (the INSERT alone), not two.

**Mechanics — transactional group, via one shared helper, not four hand-copied blocks (Engineer review, Finding 6):** `teams.ts`'s inline `client.connect()`/`BEGIN`/domain-write/audit-`INSERT`/`COMMIT`/`ROLLBACK`/`release()` shape is the right mechanics, but this change adds four more call sites reproducing it, not one — the same "third hand-copied timeout mechanism" instinct that ruled out a second fail-open implementation applies equally here. A new shared helper, `withAuditTransaction` (`packages/backend/src/auth/audit-write-transaction.ts`), captures the skeleton once:

```ts
export async function withAuditTransaction<T>(
  domainWrite: (client: PoolClient) => Promise<T>,
  auditInsert: (client: PoolClient, domainResult: T) => Promise<void>,
): Promise<T> {
  let client: PoolClient;
  try {
    client = await db.connect();
  } catch (connectErr) {
    // No transaction was ever opened — nothing to roll back. This is a new
    // failure mode this change introduces (Engineer review, Finding 2/4): today,
    // none of these call sites check out a pooled client at all. Wrapped as
    // AuditWriteError for the same reason the audit INSERT itself is (Decision
    // D7) — from an incident responder's perspective, "couldn't get a DB
    // connection to write the audit row" and "the audit row write itself
    // failed" are the same story: this application's own database
    // infrastructure, not the IdP.
    throw new AuditWriteError(connectErr);
  }
  try {
    await client.query("BEGIN");
    const domainResult = await domainWrite(client);
    try {
      // Fixed internal constant, not request-derived — string interpolation
      // here carries no injection risk despite SET not accepting bind
      // parameters. See Decision D3 for why this exists and what it fixes.
      await client.query(
        `SET LOCAL statement_timeout = ${TRANSACTIONAL_AUDIT_STATEMENT_TIMEOUT_MS}`,
      );
      await auditInsert(client, domainResult);
    } catch (auditErr) {
      throw new AuditWriteError(auditErr);
    }
    await client.query("COMMIT");
    return domainResult;
  } catch (err) {
    await client.query("ROLLBACK").catch(() => { /* connection is already lost; nothing more to do */ });
    throw err;
  } finally {
    client.release();
  }
}
```

Each of the four call sites supplies its own `domainWrite`/`auditInsert` closures — `resolveOrCreateAccount(claims, log, client)` for `auth.ts`'s account-resolution transaction, the `join_links`/`team_memberships` `INSERT ... RETURNING` for the other three — but the connect/begin/commit/rollback/release mechanics, the `db.connect()`-failure wrapping, and the statement-timeout mitigation (Decision D3) are written once and used four times, not reproduced four times with four independent chances to miss a `release()` or a `ROLLBACK`. `resolveOrCreateAccount` (`account-resolver.ts`) is still extended to accept an optional `client` parameter exactly as before — `withAuditTransaction`'s `domainWrite` callback is what passes it. `auditInsert` closures internally decide whether to issue an `INSERT` at all (e.g., `role_claim_mapped`'s closure no-ops when the role is the default; `join.link_redeemed`'s closure no-ops when `ON CONFLICT DO NOTHING` suppressed the membership insert) — `withAuditTransaction` itself doesn't need to know a given transaction produced no audit row, it just commits the domain write alone in that case, matching each event's existing firing condition exactly.

**A deliberate, minor cost of using one shared mechanism instead of per-call-site special-casing:** the `SET LOCAL statement_timeout` statement executes on every transaction this helper opens, even the (common) case where `auditInsert`'s closure no-ops — e.g., every repeat login by a default-role engineer, where no `role_claim_mapped` row is written at all. This is a negligible added round trip (a session-parameter change, no disk I/O, no lock contention) accepted as the cost of one correct mechanism over four call sites each deciding independently whether it applies.

**Structured-log ordering, made explicit rather than left as an implicit assumption (Engineer review, Finding 3):** today, `auth.ts`'s `first_access_created`/`role_claim_mapped` structured `emitAuditEvent` calls fire immediately after `resolveOrCreateAccount` returns, and `join-links.ts`'s `join.link_created` structured log fires immediately after its `INSERT ... RETURNING` resolves — both unconditionally, before any transaction concept exists in this code path. Once this design wraps each of these four events' domain write and audit `INSERT` in `withAuditTransaction`, **those existing structured-log calls move to fire only after `withAuditTransaction` returns successfully (i.e., after `COMMIT`), not at their current source position.** Leaving them at today's position would mean a rolled-back transaction (Decision D3 — the whole point of the transactional group) still produces a structured log line claiming the event happened, for a domain write and audit row that were both just undone. That is precisely the "log says X happened, the durable record disagrees" failure mode this entire change exists to close — reproduced by this change itself if the reordering isn't made explicit. This is not a new invention: `teams.ts`'s `establishManagerAssociation` already does this correctly today — its `emitAuditEvent(request.log, "team.manager_established", ...)` call sits *after* the `try`/`catch`/`finally` transaction block, not inside it — this design's four new transactional call sites are brought into line with that existing, correct precedent, not given novel treatment. Stated here as its own decision, and in Migration Plan steps 3/5/6 and tasks.md, precisely because — as the Engineer review notes — it's the kind of thing that's obvious once pointed out and easy to leave in place by default otherwise (the diff looks smaller if you don't move it).

**A newly-introduced failure mode, addressed rather than left implicit (Engineer review, Finding 2/4):** before this change, `GET /auth/callback` never checked out a pooled client — every DB access went through `db.query` directly, and `db.connect()` failing outright (pool exhaustion, connection refused) was not a failure mode this handler could hit. `withAuditTransaction` introduces up to two `db.connect()` calls in the same request (the account-resolution transaction, and — when a join token is present — `executeJoinFlow`'s `join.link_redeemed` transaction, opened sequentially after the first commits, never concurrently). As shown above, a `db.connect()` failure is wrapped as `AuditWriteError` the same as an audit-`INSERT` failure, so it does not fall back into `mapAuthError`'s default `authentication_failed` branch — the exact misattribution Decision D7 exists to fix. On pool sizing: `packages/backend/src/db.ts` constructs `new Pool({ connectionString: config.DATABASE_URL })` with no `max` configured, so `pg`'s default (10) applies. This change does not increase the number of pooled connections *available* to `/auth/callback` at any point in time — it changes one existing `db.query` call (which itself already borrows a connection from the pool for the duration of that query) into a `db.connect()`/held-client span that spans two sequential statements (the UPSERT, then the audit INSERT) before releasing, and adds a second such span, sequential not concurrent, when a join token is present. Stated honestly rather than assumed: no login-concurrency number is available in this codebase today (the same "no data obtainable" situation D1/proposal.md already name for the deferred events) to compute whether the default pool size is adequate under a real concurrent-login burst; this is judged acceptable for an internal tool at today's scale, and is the same kind of operational-headroom question that would surface as elevated `db.connect()` latency or `AuditWriteError` volume before it became an outage — worth revisiting if either signal appears, not a number this design can responsibly invent.

**Alternative considered (both groups defaulting to `session-invalidation-audit.ts`'s shape):** Rejected for the reasons exploration-notes.md's open question 3 already named — it would mean an `audit_log` outage never blocks `resolveOrCreateAccount`'s login-critical UPSERT, `join_links`'s creation, or `team_memberships`'s insert, which sounds safer in isolation, but produces exactly the silently-thinning-trail failure mode this whole change exists to close for the highest-significance events in the set (`first_access_created` fires once per account, ever; `role_claim_mapped` is Success Criterion 4's evidentiary record). See Decision D3 for why the transactional group's real cost is accepted anyway, deliberately, rather than assumed away.

**Alternative considered (both groups defaulting to the transactional shape):** Rejected for `auth.success`/`session_created`/`idp_logout_failed` — there is no Postgres write in these call paths to join; forcing one into existence solely to give the audit row a transaction to ride along in would be new machinery for no state-consistency benefit (there's no second write these rows need to stay atomic with), and would take on the transactional group's coupled-fate cost (D3) for zero atomicity gain in return.

### Decision D3: The transactional group's real cost, stated honestly

**The trade-off:** joining the audit `INSERT` into the domain write's transaction means an `audit_log` failure — a DB error, a constraint violation, a connection-pool exhaustion — rolls back the domain write too. Concretely: if the `audit_log` table is unreachable at the exact moment a user is authenticating for the first time, `auth.first_access_created`'s transactional coupling means their account is *not* created, and the login fails, rather than succeeding with a silently-missing audit row. The same is true, at smaller but real scale, for `role_claim_mapped` (every login by a facilitator/EM/admin — a bounded but non-trivial population, not ordinary engineer traffic) and for both `join.*` events (a facilitator's join-link creation, or a user's team-join attempt, fails outright).

**Why this is accepted rather than avoided:** `team.manager_established` already established this exact coupled-fate precedent for an analogous administrative/access-granting action, and the four events in this group are the same shape — one-time-per-account (`first_access_created`), bounded-population-per-login (`role_claim_mapped`), or gate-kept/one-time-per-join (`join.link_created`, `join.link_redeemed`) actions, none of them ordinary high-volume traffic. An `audit_log` outage blocking these specific actions, rather than letting them proceed with a silently thin audit trail, is the more defensible failure mode for events this significant — the same reasoning that made `team.manager_established`'s coupling acceptable applies here, not a novel risk this design introduces without precedent.

**What bounds the blast radius, corrected to actually hold (Engineer review, Finding 1 — High):** the original version of this decision claimed `AUDIT_WRITE_TIMEOUT_MS` (500ms) bounds request latency for the transactional group the same way it does for the fail-open group, via `withTimeout` racing the audit `INSERT`. That claim does not hold, and shipping it unexamined would have been exactly the kind of implicit, undocumented assumption this design process exists to catch. The mechanism is different enough to matter: `pg` processes queries on a single `Client`/`PoolClient` strictly in submission order over one connection — it does not pipeline. If `withTimeout` "loses" the race against a hung `INSERT`, the caller's `await` resolves early with `AuditWriteTimeoutError`, but the `INSERT` itself is still outstanding on the wire, still occupying that connection's one command slot. The transaction's `catch` block's `await client.query("ROLLBACK")` — which the request is synchronously waiting on before it can build its response — queues behind that still-pending `INSERT` and is not bounded by `AUDIT_WRITE_TIMEOUT_MS` at all; it's bounded by whatever eventually resolves the original hung command, which could be far longer than 500ms. The fail-open group doesn't share this problem (no follow-up query is issued on the same connection after a timed-out one), so its 500ms bound is accurate as originally stated — this correction applies only to the transactional group.

**The fix — a real mechanism, not a corrected sentence:** the transactional group's `withAuditTransaction` helper (above) does not race the audit `INSERT` with a Node-side timer at all. Instead, immediately before issuing the `INSERT`, it runs `SET LOCAL statement_timeout = <TRANSACTIONAL_AUDIT_STATEMENT_TIMEOUT_MS>` (400ms — deliberately shorter than `AUDIT_WRITE_TIMEOUT_MS`, so Postgres's own cancellation ordinarily resolves the query before any Node-side timer would even be relevant). `statement_timeout` is enforced by the Postgres server itself: if the `INSERT` doesn't complete in time, Postgres cancels it server-side and returns an error to the client for that exact statement — the connection's command slot is freed as part of that response, not left occupied indefinitely. `client.query(INSERT)` then rejects with a real Postgres error at ~400ms, `withAuditTransaction`'s wrapping `catch` converts it to `AuditWriteError`, and the subsequent `ROLLBACK` executes against a connection that is no longer waiting on anything — because the query that would have blocked it has already been resolved by Postgres, not abandoned by the client. `SET LOCAL` scopes the setting to the current transaction only (it does not leak to later transactions on a recycled pooled connection), and is issued fresh, right before the `INSERT`, on every call.

**What this bounds, and what it honestly still doesn't:** with this mechanism, the ordinary case (a hung or slow `INSERT` due to lock contention, disk pressure, or a genuinely unreachable `audit_log` table) resolves in ~400ms plus a small margin for the `ROLLBACK` and `release()` that follow — comfortably within the 500ms figure this design has always quoted, and for a reason that now actually holds under trace-through, not by assertion. The residual gap, named honestly rather than papered over: `statement_timeout` cancellation depends on Postgres being able to deliver its cancellation response back to the client over the same connection. A *network-level* partition between the application and Postgres (as opposed to a query-level hang on an otherwise-reachable server) could still leave `client.query(INSERT)` waiting past 400ms with no response arriving at all — a materially rarer and more catastrophic failure class than "a slow or lock-contended query," and one no purely client-side or purely statement-level mechanism can bound without also introducing a lower-level connection/socket timeout (`pg`'s own `statement_timeout`/`query_timeout`/`connectionTimeoutMillis` pool options, which is a separate, connection-lifecycle decision this design doesn't need to make to close Finding 1 — this fix already narrows the previously-open-ended "any hung query" risk down to the network-partition case specifically, which is a real, accepted, and now-precisely-named residual, not an unbounded one glossed over as bounded).

**Operational reliability posture, answered directly rather than assumed (Exec review):** the honest answer to "how reliable is `audit_log` today, actually" is that no uptime SLA or historical availability number exists for it, or for Postgres generally, anywhere in this codebase — inventing one here to make this decision sound more grounded than it is would be worse than saying so plainly. What does exist, and already applies to this exact failure mode without this change adding anything: `/health/ready` (`packages/backend/src/routes/health.ts`) checks Postgres reachability directly (alongside Redis) and returns `503` when it's down; `docs/deployment.md`'s Kubernetes section wires this into the liveness/readiness probe. A *full* Postgres outage — the scenario that makes `audit_log` unreachable — already surfaces as a failing readiness probe today, in production, independent of this design. That is existing infrastructure this design leans on, not new monitoring being claimed on its behalf.

What that posture does not cover: a failure isolated to the `audit_log` table specifically — a lock, a constraint violation, a disk-quota or permissions problem scoped to that one table — while the rest of Postgres answers normally would not trip `/health/ready`, yet would still trigger this group's rollback for every affected request. No monitoring specific to that narrower slice exists today, and this design does not add one — building that consumer remains out of scope (Non-Goals), unchanged.

**Tracked, not left as a "worth watching" sentence (Security review, F2):** this narrower gap — an `audit_log`-table-isolated failure that `/health/ready` wouldn't catch — is a concrete instance of an already-filed, codebase-wide gap: GitHub issue #131, "No monitoring consumer exists for any `AuditEventName` signal, including the new `auth.audit_write_failed`," filed by the precedent change and still open. Rather than restate the gap here as a fresh, undirected observation, this design names its own specific new signals as first-class candidates for #131's fix, and that naming is recorded on the issue itself, not only in this document: the fail-open group's `auth.audit_write_failed` emissions (three more events' worth of volume than #131's original scope), and Decision D7's `AuditWriteError`/`errorClass` addition to the existing `auth.callback_error` log line — both concrete, greppable signals that a table-isolated `audit_log` failure would now produce, where #131 already names "prioritize `auth.audit_write_failed`... first" as suggested scope. This change does not build the alert or dashboard — that stays #131's job, not this change's — but it does not leave the specific gap this design's own D3 accepts as an unaddressed, unowned sentence either.

One concrete, in-scope improvement this design does add, as a direct byproduct of closing Decision D7's gap below: the existing `request.log.error({ event: "auth.callback_error", ... })` line at `GET /auth/callback`'s catch block — already emitted today, unconditionally, on every callback failure — will carry an accurate, unredacted `errorClass: "AuditWriteError"` for this failure mode instead of folding it into `sanitizeOidcError`'s "unrecognized class" branch. Before this change, a Postgres error was structurally impossible in this call path, so no comparable signal existed at all; after this change, an operator (or a future alert rule — none exists today, and building one remains out of scope, per Non-Goals) has an accurate, greppable signal for exactly this failure mode where none existed before. This is a real, added detectability improvement, not a promise about uptime, and it does not change that Decision D3's coupling itself is accepted, not mitigated.

### Decision D4: `auth.role_claim_mapped` gains a `previousRole` field, captured within the same transaction

**Choice:** `resolveOrCreateAccount`'s UPSERT is extended with a CTE that captures the pre-update `global_role` value in the same statement, before the update applies:

```sql
WITH prior AS (
  SELECT global_role FROM users WHERE oidc_subject = $1 AND oidc_issuer = $2
)
INSERT INTO users (oidc_subject, oidc_issuer, display_name, email, global_role)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (oidc_subject, oidc_issuer)
DO UPDATE SET display_name = EXCLUDED.display_name, email = EXCLUDED.email,
              global_role = EXCLUDED.global_role, updated_at = NOW()
RETURNING id, oidc_subject, oidc_issuer, display_name, email, global_role,
          (xmax = 0) AS is_new_user,
          (SELECT global_role FROM prior) AS previous_global_role
```

`ResolvedUser` gains a `previousGlobalRole: string | null` field (`null` for a brand-new user — there is no prior value, which is a different, already-distinguishable case via `isNewUser`). `auth.role_claim_mapped`'s `audit_log` row includes `previousRole` in `metadata` whenever it fires (i.e., only for returning users with a non-default current role — the event's existing firing condition is unchanged).

**Rationale:** exploration-notes.md is explicit that this is the event Success Criterion 4 (no manager has participated, no exception made) ultimately depends on being reconstructible against. Reconstruction-by-diff (comparing consecutive rows for a `userId`) technically works but requires an investigator to already know to do that, and produces no answer at all for a `userId` with only one row on file. A single query (`WHERE operation = 'auth.role_claim_mapped' AND metadata->>'previousRole' != metadata->>'globalRole'`, or simpler, `metadata->>'previousRole' = 'engineering_manager'`) directly answers "did this account's role ever change into or out of EM," which is the shape of question Success Criterion 4 actually poses. The CTE adds no extra round trip — it's computed in the same statement already running.

**What this does not fix, named so it isn't assumed solved, and tracked rather than left as a Risks-section sentence alone (Security review, F3):** a role's *reversion* to the default (`engineer`) still emits nothing — `role_claim_mapped`'s firing condition (`user.globalRole !== "engineer"`) is unchanged by this decision. `previousRole` makes each row that *does* fire more informative; it does not make the event fire on cases it doesn't fire on today. This bears directly on Champion Success Criterion 4 ("did an EM's role ever get misapplied, and when"): a `role_claim_mapped` row showing `engineering_manager` with no subsequent row is structurally indistinguishable from "still an EM, hasn't logged in recently" versus "was demoted, no trace of when." Filed as GitHub issue #157, alongside #156, applying the same discipline this design already applies to the four deferred events — not resolved here, since it changes when an existing event fires, a larger surface than an audit-*coverage* change's stated scope, but not left unowned either.

### Decision D5: `join.link_redeemed` covers both call sites identically; `team_id` is populated, not NULL

**Choice:** `join-links.ts`'s `GET /api/join/:token` handler and `auth.ts`'s `executeJoinFlow` both get the identical transactional treatment for their `join.link_redeemed` emission (only when `INSERT ... RETURNING id` actually returns a row — the existing `ON CONFLICT DO NOTHING` idempotency gate is unchanged and continues to gate the audit write the same way it already gates the structured-log emission). `team_id` is populated from `link.team_id` — already in scope, unambiguous, at both call sites — on every row this change adds under `join.link_created` or `join.link_redeemed`. This is a deliberate departure from `session_invalidated`'s uniform-NULL convention (Decision D4 of the precedent design): that NULL was forced by `middleware.ts`'s call sites having no candidate at all and `auth.ts`'s logout site having an ambiguous one (multiple active sessions). Neither condition holds for any `join.*` call site.

**Rationale:** Treating "join-links.ts's events" literally and missing `auth.ts`'s `executeJoinFlow` half would reproduce, exactly, the shape of gap Decision D3 of the precedent design existed to close for `session_invalidated`'s fourth call site — a plausible, easy-to-make mistake this design closes explicitly by naming both call sites in the same decision rather than one per file.

**`actor_global_role` resolution differs by call site, stated explicitly rather than left as a hedge (BA review, Finding 2):** "already resolved earlier in the same handler, no additional lookup where it's already in scope" is not a uniform fact across `join.link_redeemed`'s two call sites — it is true at one and false at the other, and the fix is different at each:
- `auth.ts`'s `executeJoinFlow` does not currently know the joining user's `global_role` — it receives only `userId: string` as a parameter. Its caller, `GET /auth/callback`, already has the full resolved `user` object in scope at the call site (`auth.ts:385`), including `user.globalRole`, resolved moments earlier for `auth.success`'s emission. `executeJoinFlow` gains a new required parameter, `actorGlobalRole: string`, and the call site passes `user.globalRole`. This is a free parameter pass, not a lookup — it costs nothing beyond a signature change.
- `join-links.ts`'s `GET /api/join/:token` has no such value in scope anywhere in the handler — verified directly: the handler reads only `session.userId`, never a role. This call site issues a new `SELECT global_role FROM users WHERE id = $1` (using `session.userId`) before writing the `join.link_redeemed` audit row — a genuine additional lookup, not a pass-through. **Connection scoping, pinned down explicitly rather than left to task-time judgment (Architect review, Finding 5; BA review, Finding 2):** this `SELECT` runs on the plain pool (`db.query`), *before* `withAuditTransaction`'s `db.connect()`/`BEGIN` opens — not on the checked-out transaction client. The resolved role has to be available when the `auditInsert` closure runs inside the transaction, and it's a read with no correctness dependency on the pending `team_memberships` INSERT; running it on the plain pool ahead of `db.connect()` avoids holding it on a connection a subsequent rollback would tear down before the value was ever used, and keeps it out of the transactional span's own (already time-boxed, Decision D3) work.
- `join-links.ts`'s `POST /api/teams/:teamId/join-links` (`join.link_created`) is unaffected by this clarification — it already resolves `userRole` via an existing query earlier in the handler (the facilitator-permission check) and needs no change.

These are two different fixes behind one event name, not a single settled fact — stated here explicitly, and in the delta spec, so tasks.md doesn't carry it forward as a "check before assuming" item into implementation.

### Decision D6: Adjacent small fixes, scoped in while these files are already open

**Choice, matching the precedent's own `sourceIp`-while-already-touching-the-file precedent (D5 of `http-auth-audit-log-coverage`):**
- `auth.idp_logout_failed`'s existing structured-log `emitAuditEvent` call gains `sourceIp: request.ip` (already in scope two lines away; its sibling `session_invalidated` emission in the same handler already has it).
- `auth.ts`'s `executeJoinFlow` gains `userId` on its two `join.link_rejected` structured-log emissions (it's already resolved as a parameter at that point in the function, unlike `join-links.ts`'s pre-session-check branches, which structurally have none available).

Neither of these is a DB-row change — `join.link_rejected` remains log-only per Decision D1 — these are field-completeness fixes to the existing structured logs, cheap enough to include while these exact call sites are already being read and touched for this change, and left undone they'd be the same shape of small, easy-to-miss gap this codebase has already corrected once (`auth-audit-correlation-fields`, closing a `sourceIp`/`correlationId` completeness gap on three sibling events in this same file).

### Decision D7: `AuditWriteError` — distinguishing the transactional group's own-infrastructure failures from an OIDC error

**Problem (BA review, Finding 1):** `auth.first_access_created`/`auth.role_claim_mapped`'s transaction (Decision D2/D3) and `executeJoinFlow`'s `join.link_redeemed` transaction both rethrow, unwrapped, into `GET /auth/callback`'s existing `catch (err: unknown)` block — the same block every `auth.failure` branch already shares, built to classify OIDC-library errors (`mapAuthError`, `error-handler.ts`) and sanitize them before logging (`sanitizeOidcError`, `oidc-error-sanitizer.ts`). Neither function recognizes a raw Postgres error today, because before this change nothing in this call path could throw one. `mapAuthError` falls to its default branch — category `authentication_failed`, message "An unexpected error occurred during sign-in...". `sanitizeOidcError` falls to its "unrecognized class" branch — `message` and `stack` redacted. Net effect: the exact failure mode Decision D3 spends a full section accepting surfaces to whoever is debugging it as a generic, redacted "sign-in failed" error, destroying the one piece of information — the actual Postgres error — an incident responder needs to tell "the IdP had a problem" apart from "our own database had a problem." This directly undermines SEC-12 for the failure mode this design's own D3 decision creates.

**Choice:** wrap the audit `INSERT`'s thrown error — and only that INSERT's error, not `resolveOrCreateAccount`'s own UPSERT failure, which is a separate, pre-existing failure mode this change doesn't newly create and isn't scoped to fix (a raw Postgres error from that UPSERT could already reach this same catch block before this change, for the same reasons any pre-existing database-backed write in this handler could) — in a new `AuditWriteError` class (`packages/backend/src/auth/errors.ts`, alongside `MissingClaimError`), before the transaction's `ROLLBACK`/rethrow. **Widened scope (Engineer review, Finding 2/4 — Medium):** `withAuditTransaction`'s `db.connect()` failure (see Decision D2's mechanics) is wrapped in the same `AuditWriteError` class, for the same reason. Before this change, `db.connect()` was not a failure mode this handler could hit at all — every DB access went through `db.query` directly. This design newly introduces up to two `db.connect()` calls per request (pool exhaustion or connection refusal is a real, if rare, thing to hit on what is likely one of this application's highest-traffic routes), and leaving that specific failure unwrapped would have reintroduced the exact misattribution this decision exists to fix, just triggered by the connection pool instead of the audit table. There is no `ROLLBACK` to perform in this case — no transaction was ever opened — so the wrapped error is rethrown immediately, without a rollback step:

```ts
export class AuditWriteError extends Error {
  readonly causeClass: string;
  constructor(cause: unknown) {
    super("Audit log write failed");
    this.name = "AuditWriteError";
    this.causeClass = cause instanceof Error ? cause.constructor.name : typeof cause;
  }
}
```

`message` is always the static string above — never built from the underlying Postgres error, which could in principle echo back query content — so it is always safe to log in full, unlike a genuine IdP error's message. `causeClass` (e.g. `"DatabaseError"`) gives an operator a bit more diagnostic value without that risk.

`mapAuthError` gains a branch: `AuditWriteError` → category `internal_error` — a fifth `AuthErrorCategory` value (`packages/shared/src/types/auth.ts`). Neither existing category fits honestly: `authentication_failed`'s "sign-in" framing is exactly the misattribution this decision exists to fix, and reusing `provider_unavailable` would misname the *identity provider* as the failing party when it's this application's own database. Message: "We couldn't finish signing you in due to a temporary internal problem. Please try again in a few moments. If this continues, contact your IT administrator." `internal_error` is treated as retryable, the same as `provider_unavailable` — `packages/frontend/src/pages/AuthErrorPage.tsx`'s `isRetryable` check gains this value.

`sanitizeOidcError` gains a matching branch: `AuditWriteError` → `{ errorClass, message: err.message, stack: err.stack, causeClass: err.causeClass }`, nothing redacted — mirroring `MissingClaimError`'s existing treatment, since neither class's `message`/`stack` ever carries identity-provider- or user-supplied content.

**Scope of this fix:** this closes the gap only where it's reachable — inside `GET /auth/callback`'s catch block, which is where `auth.first_access_created`/`role_claim_mapped`'s transaction (task 3.1) and `executeJoinFlow`'s `join.link_redeemed` transaction (task 6.2, invoked from within the same try block at `auth.ts:385`) both rethrow into, whether the underlying failure was the audit `INSERT` itself or the `db.connect()` call that would have opened the transaction. `join-links.ts`'s two call sites (`join.link_created`'s transaction, task 5.1; the direct-path half of `join.link_redeemed`'s transaction, task 6.1) have no equivalent catch block — Fastify's default error handler responds with a plain 500 regardless of whether the thrown error is `AuditWriteError` or anything else. `AuditWriteError` is still thrown at these two call sites too (for the same reason it's used everywhere else — distinguishing an audit-log failure from the accompanying domain write's own failure, should this file later gain error-shape-aware handling), it just isn't consumed by any sanitizer there today. This asymmetry — a classified, retryable redirect at the through-auth path; a plain, unclassified 500 at the direct path — is named here and in the delta spec, not equalized: building OIDC-shaped error handling into a file that has never needed it is disproportionate to what this change is instrumenting.

**Alternative considered:** carry the same information on the existing `authentication_failed` category via a new response field instead of adding a category value. Rejected — `AuthErrorCategory` is a small, closed union the frontend's `isRetryable` check switches on directly; overloading an existing value's meaning silently (making some `authentication_failed` responses retryable and others not, based on a field the frontend would need new logic to read) is worse than adding one clearly-named value the type system enforces everywhere it's handled.

## Risks / Trade-offs

- **[Risk] The transactional group's coupled-fate cost (Decision D3) means a sustained `audit_log` outage blocks new-account creation (`first_access_created`) and privileged-account login (`role_claim_mapped`), not just the administrative actions the precedent (`team.manager_established`) accepted this cost for.** → **Accepted, not mitigated, for the reasons D3 states** — including D3's own reliability-posture paragraph, which grounds this acceptance in what's actually known about `audit_log`/Postgres operational coverage today rather than an assumed-safe blast radius. Decision D7 improves this failure mode's *detectability* (an accurate `AuditWriteError` signal in the existing `auth.callback_error` log line, where none existed before, now also covering `db.connect()` failures), which is a real improvement but does not change that the coupling itself is accepted, not mitigated. The narrower, table-isolated slice of this risk that `/health/ready` wouldn't catch is tracked as issue #131 (Security review, F2) — see D3 — rather than left as an untracked "worth watching" sentence. If `audit_log` write failures for this group turn out to correlate with real incident reports of "I can't sign in," that's a signal this design's D2/D3 alternative (fail-open for this group too) should be revisited — not evidence the reasoning here was wrong at the time, but a real cost worth watching for.
- **[Risk] `role_claim_mapped`'s reversion-to-default blind spot is unchanged by this design — a role dropping back to `engineer` still produces no row at all, visible only as an absence, never as an event of its own.** → **Named, and tracked, not fixed (Decision D4, Security review F3).** Anyone querying this trail for Success Criterion 4 needs to know that "no reversion row exists" doesn't mean "no reversion happened" — it's structurally unrepresentable today. Filed as GitHub issue #157, alongside #156; not fixed here because it changes when an event fires, a larger surface than this change's stated scope.
- **[Risk] `join.link_redeemed`'s durable row makes an existing mismatch (an EM landing in `team_memberships` with a participant-shaped row) visible for the first time, which could read as this design endorsing or normalizing it.** → **Mitigation:** stated explicitly in this design's Non-Goals and in proposal.md's Impact section — this change makes the scenario reconstructible; it does not evaluate or fix it. A future reader of this design.md should not infer the mismatch was considered acceptable, only that fixing it wasn't this change's job.
- **[Risk] Deferring `auth.authorization_initiated`/`callback_received`/`failure`/`join.link_rejected` a third time, even with issue #156 filed, still leaves those four events' actual coverage decision unresolved indefinitely if #156 never gets prioritized.** → **Mitigation:** issue #156 states its own fallback (proceed on the qualitative reasoning, or treat "no data obtainable" as itself the answer) so it doesn't stall waiting on a number that may never exist — see the issue text.
- **[Risk] `withTimeout`'s abandoned-query-keeps-its-connection limitation (same as the precedent's own accepted risk) still applies to the fail-open group exactly as it always did — no change there.** → **Accepted, same as the precedent, unchanged by this design.** For the transactional group specifically, this risk is substantially narrowed, not merely restated, by Decision D3's `SET LOCAL statement_timeout` fix (Engineer review, Finding 1): a hung audit `INSERT` inside a transaction is now cancelled by Postgres itself at the (shorter) statement-timeout bound, freeing the connection so `ROLLBACK`/`release()` proceed promptly, rather than waiting indefinitely on whatever eventually resolves the original query. The residual risk for the transactional group is narrower and different in kind — a network-level partition between the application and Postgres, not an ordinary query-level hang — and is named explicitly in Decision D3 rather than folded into this general bullet as if unchanged. Full query cancellation for the fail-open group, and connection-level (as opposed to statement-level) timeouts for both groups, remain out of scope (Non-Goals), same as the precedent's own stated limitation.
