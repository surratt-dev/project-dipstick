## Why

Right now, once an open or in-progress action item is misassigned — its owner left the team, wrap-up assigned it in a hurry, or the team decided out loud to redistribute an overloaded engineer's backlog — there is no way to fix it. The item sits with an owner who can't or won't act on it, forever, because the only owner-write path that exists today (`ACTION-002`) is locked to the session's own `wrap_up` phase. VOTE-004 (`requirements/design/REST API Contract.md`, GitHub issue #108) closes that gap: `PATCH /api/v1/action-items/:actionItemId/owner`, a facilitator-only, session-scoped endpoint that reassigns an action item to a new active team member at any point in a facilitator's active session, not only during wrap-up.

This is a narrow, general-purpose reassignment primitive, not the richer facilitator UX (a visual "owner has left" indicator, an active-engineer picker) the pre-session review use case ultimately wants — that UI is issue #68, and it consumes this endpoint once it exists. Landing #108 does not change anything a facilitator experiences in a live session yet; it lays the server-side contract #68 will call. That distinction matters enough to say plainly here: nobody should treat this change shipping as "facilitators can now fix misassigned items" internally, because they can't, until #68 gives them a way to invoke it.

From where I sit, this is also a small but real test of something I care about more than this one endpoint: whether the tool can encode intent precisely enough that a team that has never talked to me uses it correctly without my help. Two of this application's protective boundaries — no manager holds an accountable ritual artifact, and a facilitator's write authority is earned by actively running a session, not held standing — run directly through this contract's validation rules. Getting the "new owner must be an active, non-EM participant" check exactly right, and reusing (not reinventing, not loosening) the session-scoped facilitator-authorization pattern this codebase already shipped and reviewed once for `VOTE-002`, is what keeps this a safe, boring primitive instead of a quiet crack in either boundary.

## What Changes

- Add `PATCH /api/v1/action-items/:actionItemId/owner` (VOTE-004), authorized to the action item's currently-facilitating facilitator only — the same session-scoped `EXISTS` check (`sessions.facilitator_id = $1 AND team_id = $2 AND status = ANY(ACTIVELY_FACILITATING_STATUSES)`) `VOTE-002` already ships in `action-items.ts`, reused rather than re-derived. There is no owner-or-facilitator fork here as there is in `VOTE-002` — only a facilitator may call this endpoint, full stop.
- New-owner validation cascade, in order: the target cannot be the calling facilitator themselves (`422`); the target user must exist (`404` otherwise); must have a `team_memberships` row for this team (`404` otherwise); and that membership must be active (`removed_at IS NULL`) and `role = 'participant'` — not soft-removed, not an Engineering Manager (`422` otherwise). Checked precisely against `role = 'participant'`, not "membership exists," so a facilitator cannot reassign an item to an EM.
- Reassigning an item to its own current owner is accepted as a `200` no-op — `action_items.updated_at` is bumped, and no `action_item_history` row is written — mirroring the same-status no-op pattern `VOTE-002` already established for status updates. **Unlike** `VOTE-002`'s no-op, this one still writes an `audit_log` row (`metadata.no_op = true`), because this no-op can repeatedly reset a staleness signal other people rely on, with otherwise zero record that it happened (design.md Decision D6, amended following security review).
- A **required** `sessionId` request-body field (`422` if missing), validated independently against the item's team and the same active-session status set using `VOTE-002`'s Decision D11 rule exactly, but required here rather than optional as it is for `VOTE-002` — this endpoint's governing use case has no out-of-session path and records the reassignment session unconditionally, unlike `VOTE-002`'s own use case, which explicitly supports an out-of-session status update. Server-side derivation of `sessionId` is still declined for the reason `VOTE-002` already established (see design.md Decision D4).
- A resolved action item cannot be reassigned: `409 Conflict`, matching `VOTE-002`'s "resolved is terminal, unhedged" precedent — **correcting** the current contract text, which lists this case as an undifferentiated `403` alongside "not a facilitator." Distinct codes for distinct facts (an auth failure vs. a state conflict) so a future facilitator UI (#68) can tell a caller which one happened instead of showing one generic error.
- A caller with zero relationship to the item's team gets `404`, indistinguishable from a nonexistent `actionItemId`; `403` is reserved for a caller with some relationship (team member, or has ever facilitated a session for this team) who isn't a currently-authorized active facilitator — applying `VOTE-002`'s already-reviewed Decision D12 anti-enumeration ordering to this endpoint's structurally identical URL shape (no `teamId` in the path).
- Every accepted, non-no-op reassignment writes `action_item_history` (new nullable `previous_owner_id`/`new_owner_id` columns, additive migration, `previous_status`/`new_status` populated with the item's own unchanged current status) and `audit_log` (`operation = 'action_item.owner_reassigned'`), in the same transaction as the owner update — following `VOTE-002`'s established dual-write pattern exactly.
- Every accepted reassignment (no-op included) bumps `action_items.updated_at`, so a newly-reassigned owner's staleness clock starts clean rather than inheriting whatever staleness the item accrued under its prior owner.
- No WebSocket broadcast — confirmed, not merely omitted. No event named or shaped for an owner change exists in this codebase's catalog, and none is added here. Whether a live reassignment should be visible to the room during a session is named as an open question for #68, not decided in this change.
- Correct two stale references in `openspec/changes/team-membership-removal/README.md` that describe VOTE-004's active-participant constraint as still undesigned/blocking — it will no longer be true once this change ships.
- Add a one-sentence cross-reference to `action-item-status-management`'s existing `action_item_history` requirement, scoping it to status-change rows only, since this change's reassignment-only rows are a distinct requirement of a different capability.
- Add "Corrected by `reassign-action-item-owner`" notes directly under VOTE-004's section in `requirements/design/REST API Contract.md`, in this document's existing correction-note style, for the 403→409 resolved-item fix, the `sessionId` description wording, and — added after design review — a full rewrite of the stale `global_role`-based `Authorization` line to match `VOTE-002`'s own corrected precedent (session-scoped mechanism, no `global_role` gate).
- A `status != 'resolved'` guard, with a `rowCount` check, on the final owner-update statement — added after design review, since this change is what turns `action_items` into a two-writer table for the first time, and a concurrent `VOTE-002` resolve racing this reassignment must not be able to commit an owner change against an item that's resolved by the time this endpoint's write lands (design.md Decision D11).

**Out of scope, named and carried forward to #68, not silently dropped:** the trigger taxonomy (departed owner, quiet misassignment correction, load-balancing, in-room volunteer handoff) and which of those should feel visible-to-the-room versus quiet; batch/multi-item reassignment; the UI copy and presentation for the distinct error codes this endpoint returns; and whether the "no broadcast" fact is acceptable UX for the social/collaborative trigger cases. None of these change this endpoint's contract.

**Accepted limitations, named plainly:** this endpoint validates the new owner's structural *eligibility* (active, non-EM, not the caller), not their *availability* — someone on leave without a membership change is accepted today, and that is not modeled here. Authorization requires an active session for the team, exactly like `VOTE-002` — a facilitator noticing a stale assignment between sessions cannot correct it until their next live session for that team; this is the same accepted trust-boundary precedent applied consistently, not a new problem this change introduces, and it is not widened here. And because nothing in this codebase's application code yet sets `team_memberships.removed_at`, the endpoint's own namesake scenario — reassigning away from a departed owner — cannot occur organically through any production code path today; this change's validation is fully correct and buildable regardless, since reassignment already has other legitimate, reachable uses (misassignment correction, load-balancing), and manual/QA verification of the "not an active participant" path requires a raw `UPDATE team_memberships SET removed_at = ...` fixture, matching the existing pattern in `ws-pubsub-integration.test.ts`, not an end-to-end removal flow. Finally, this route has no request-schema validation layer — an inherited gap, not one this change introduces (`VOTE-002`'s own handler has none either) — so a missing or malformed `newOwnerUserId` (not a well-formed UUID, or absent from the body entirely) is not given a stated status code by this proposal; it is accepted as a pre-existing gap in this codebase's request-validation approach, named here rather than left for a future reviewer to discover.

**Two non-blocking follow-ups, named after design review, deliberately not built as part of this change:**

- **A global Fastify error handler.** (Security review Finding 5, `design-review-security.md`.) `packages/backend/src/app.ts` registers no `setErrorHandler`, and no global Fastify error handler exists anywhere in `packages/backend/src`. A malformed `newOwnerUserId` bound to a parameterized query against a `uuid`-typed column throws a raw Postgres driver error (`invalid input syntax for type uuid`) that propagates as an unhandled exception, which Fastify's default handler turns into a `500` carrying the underlying error message — a pre-existing exposure this endpoint inherits identically to `VOTE-002`'s own `resolutionNote`/`status`/`sessionId` fields, not a new one it introduces. Worth a follow-up ticket for a global error handler that maps unexpected exceptions to a generic `500` without leaking the underlying error, closing this for every write endpoint in the file at once — not a per-endpoint fix bolted onto this change.
- **Shared request/response types for `VOTE-002` and `VOTE-004` together.** (Engineer review Finding 5, `design-review-engineer.md`.) Neither `ReassignActionItemRequest` nor `ReassignActionItemResponse` are added to `packages/shared/src/types/action-item.ts` by this change — consistent with `VOTE-002`'s own precedent of an inlined Fastify route generic and an ad hoc response object literal, not a regression this change introduces. But it's a second data point on the same gap in this codebase's shared-types principle, which otherwise covers domain entities but not mutation endpoint bodies/responses. Worth a follow-up ticket to backfill shared types for both endpoints together, so a third mutation endpoint doesn't repeat the inline pattern a third time.

## Capabilities

### New Capabilities
- `action-item-owner-reassignment`: server-side authorization and validation rules for `PATCH /api/v1/action-items/:actionItemId/owner` — facilitator-only, session-scoped authorization; the new-owner eligibility cascade (self-facilitator, existence, membership, active-non-EM-participant); the same-owner no-op; the resolved-item precondition; the 404-vs-403 enumeration-safety ordering; and the `action_item_history`/`audit_log` records a real reassignment produces.

### Modified Capabilities
- `action-item-status-management`: its "every real status transition is recorded in `action_item_history`" requirement gains one sentence scoping it to status-change rows only, since owner-reassignment rows are a distinct requirement of the new `action-item-owner-reassignment` capability, not a status transition.

## Impact

- **Backend**: new route handler in `packages/backend/src/routes/action-items.ts` (the existing action-item write-path home; `VOTE-002`'s `ACTIVELY_FACILITATING_STATUSES` constant stays file-local and is reused, not exported), a new `AuditEventName` member (`action_item.owner_reassigned`) in `packages/backend/src/auth/audit-logger.ts`.
- **Database**: one additive migration (next in sequence after migration 9) adding nullable `previous_owner_id uuid NULL REFERENCES users(id)` and `new_owner_id uuid NULL REFERENCES users(id)` to `action_item_history`, plus a `CHECK` constraint enforcing symmetric nullability of the two columns. No changes to `action_items`, `team_memberships`, or any existing column.
- **Documentation**: `requirements/design/REST API Contract.md` gets a correction note under VOTE-004 (403→409 for resolved items; `sessionId` corrected from optional to required, with updated field description; and, added after design review, the stale `global_role`-based `Authorization` line rewritten to state the actual session-scoped mechanism, matching `VOTE-002`'s own corrected entry); `openspec/specs/action-item-status-management/spec.md` gets the one-sentence cross-reference; `openspec/changes/team-membership-removal/README.md` gets its two stale VOTE-004 references corrected to a forward pointer.
- **No frontend, no WebSocket changes.** #68 (facilitator UI) and any live-visibility decision are explicitly out of scope and unaffected in shape by this change's own decisions.
- **Issue tracker**: closes #108 (VOTE-004). Does not close #68, which remains open and unscheduled, consuming this endpoint once picked up.
