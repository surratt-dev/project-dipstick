## Context

Framed from my (Devon Calloway, Internal Champion) perspective, grounded in exploration (`exploration-notes.md`) and its two review passes (`explore-review-ba.md`, `explore-review-facilitator.md`), both of which are already reconciled into that document's decisions rather than left as open questions here.

`ACTION-002` is the only place `action_items.owner_id` can change today, and it only runs during a session's `wrap_up` phase. There is no way to reassign an item once wrap-up has closed — which is exactly when the "owner left the team" scenario this endpoint is named for, and the misassignment/load-balancing scenarios facilitators actually hit, get noticed: during pre-session review, mid-session, or between sessions from the trend dashboard. `VOTE-004` (issue #108) is a pre-existing, complete contract in `requirements/design/REST API Contract.md` — this change implements it as documented, with two corrections stated below rather than silent adoption or silent divergence.

`action-item-status-management` (`VOTE-002`, already shipped and reviewed) is the direct sibling of this endpoint: same table family, same facilitator-authorization shape, same enumeration-safety concerns. Every decision below either reuses `VOTE-002`'s already-litigated pattern directly or states explicitly why this endpoint's shape requires something new. That reuse is deliberate, not merely convenient — the more this endpoint's authorization model diverges from `VOTE-002`'s, the more a future reader has to hold two different "when can a facilitator write to this table" models in their head at once.

This is not a review of the ritual's core structural constraints (simultaneous reveal, no-manager participation, facilitator-from-another-team, topic-default restorability, cross-person comparison) in the sense of the vote/reveal mechanics — but the no-manager-participation constraint (BRD FR-9.5) does touch this endpoint directly, through the new-owner eligibility check, and is treated as load-bearing throughout: if that check is ever implemented as "any team member" instead of "role = 'participant' specifically," a facilitator could hand an accountable action item to an Engineering Manager, which is a crack in the no-manager wall even though it isn't the voting wall.

**Picking this up as Solution Architect (Ingrid Sollenberger), incorporating two independent design reviews.** `design-review-engineer.md` (Marcus Oyelaran) and `design-review-security.md` (Tomás Ferreira) both came back with overlapping findings, resolved once each below rather than answered twice: a real concurrency gap this change introduces by making `action_items` a two-writer table for the first time (D11, new); a documentation gap in the REST API Contract's `Authorization` line that both reviews independently caught and that this document's own D3 incorrectly implied was already handled (Migration Plan, D3 amendment); under-specified `applyTimingFloor` coverage inherited from `VOTE-002` but never stated for this endpoint (D2 amendment); an audit-trail blind spot on the same-owner no-op path that both D6 and D9, individually reasonable, produce in combination (D6/D10 amendment); and two smaller implementation-guidance items threaded into D5 and tasks.md. Each is resolved as a stated decision below, not left as an open question.

## Goals / Non-Goals

**Goals:**
- Ship a facilitator-only, session-scoped `PATCH /api/v1/action-items/:actionItemId/owner`, reusing `VOTE-002`'s authorization pattern, anti-enumeration ordering, and resolved-item-is-terminal precedent exactly, rather than re-deriving equivalent-but-different versions of each.
- Make the no-manager-participation constraint and the facilitator-only privilege structurally precise: `role = 'participant'` checked exactly, not "membership exists"; session-scoped authorization, not a global facilitator flag.
- Give this reassignment a durable, auditable trail (`action_item_history` + `audit_log`) using the smallest additive schema change that doesn't corrupt `action-item-status-management`'s existing "one row = one status transition" assumption for any of its own consumers.
- Correct, in place, the two spots where the current contract/documentation is wrong or stale rather than leaving corrections to accumulate in this change's own artifacts only.

**Non-Goals:**
- The facilitator-facing reassignment UI (issue #68) — the visual "owner has left" indicator, the active-engineer picker, any live-vs-quiet distinction for the four realistic triggers (owner departed, misassignment correction, load-balancing, in-room volunteer handoff). This change ships the contract #68 will call; it does not decide how #68 should look or feel.
- Modeling new-owner *availability* (parental/medical/sabbatical leave) — this endpoint validates structural eligibility only. Adjacent to `team-membership-removal`'s territory if ever addressed; not bolted onto this endpoint speculatively.
- Widening the authorization trust boundary to admit an off-session administrative correction. This endpoint's authorization inherits `VOTE-002`'s exact session-scoped trust boundary, on purpose — see Decision D1.
- A live WebSocket broadcast of the reassignment. No event exists for this in the catalog; none is added. Whether one should exist is a #68-era UX question, not resolved here.
- Backfilling `action_item_history` writes for `ACTION-002`'s existing wrap-up owner edits (the still-open OQ-8). A different endpoint's write path; out of this change's scope, named forward instead of silently left inconsistent.

## Decisions

**D1 — Authorization: reuse `VOTE-002`'s session-scoped facilitator check exactly; no owner-or-facilitator fork.**

`VOTE-002`'s `ACTIVELY_FACILITATING_STATUSES = ['lobby', 'pre_session', 'active', 'wrap_up']` constant and its `EXISTS (SELECT 1 FROM sessions WHERE facilitator_id = $1 AND team_id = $2 AND status = ANY(...))` query, both file-local to `packages/backend/src/routes/action-items.ts`, are reused verbatim for this endpoint's authorization gate. This endpoint lands in the same file — `action-items.ts` already frames itself as the action-item write-path home, and one file holding one authorization story (rather than a second, subtly-different copy of the same predicate) is the stated convention this codebase already follows for `VOTE-002` itself.

Unlike `VOTE-002`, there is no owner-authorized path here at all — reassignment is a privileged action, not something the current owner can do to themselves. The branching is therefore simpler: authorized-facilitator-or-nothing, not owner-or-facilitator.

*Accepted limitation, stated plainly rather than discovered later:* because authorization requires an active session for the team, a facilitator who notices a stale assignment between sessions — from the trend dashboard, from memory, from a Slack message — cannot correct it until their next live session for that team. This is `VOTE-002`'s existing accepted trust-boundary precedent (its own Decision D10), applied consistently to a sibling endpoint, not a new problem this change introduces. *Alternative considered:* widen the authorization model to admit an off-session administrative correction path. *Rejected:* doing so here would mean `VOTE-002` and `VOTE-004` diverge on when a facilitator may act — a worse outcome than the inconvenience, and if the product wants an off-session correction capability, that is a distinct authorization-model proposal revisiting both endpoints together, not something bolted onto this one as a side effect of adding a new route.

**D2 — Anti-enumeration ordering: adopt `VOTE-002`'s Decision D12 directly.**

This endpoint's URL (`PATCH /api/v1/action-items/:actionItemId/owner`) carries no `teamId`, structurally identical to `VOTE-002`'s status-update URL. The current contract's error table states `403` directly for "Not a facilitator" with no relationship-based `404` boundary — reading like it was drafted before `VOTE-002`'s D12 pattern existed in this codebase. Applying D12 here is not a fresh judgment call; it is the same already-litigated precedent applied to a URL shape D12 was designed to generalize to. Sequence: load the item by ID alone (`404` if missing) → evaluate the caller's relationship to the item's team, broader than write-authorization (owner is not applicable here since there's no owner path, so: any `evaluateTeamAccess` grant, or has ever facilitated a session for this team, regardless of status) → `404` if no relationship at all, indistinguishable from "doesn't exist" → `403` if some relationship exists but the caller isn't currently an authorized active facilitator per D1.

*Alternative considered:* keep the contract's flatter `403`-only table. *Rejected:* it reopens the same `actionItemId`-existence enumeration oracle `VOTE-002`'s D12 already closed once for a structurally identical URL; there is no stated reason for this sibling endpoint to reintroduce a gap its neighbor already fixed.

*Amended following Security review Finding 1 (`design-review-security.md`):* correct status-code ordering is only half of `VOTE-002`'s actual anti-enumeration control. Its shipped handler also calls `applyTimingFloor` — documented in its own file header as a "BLOCKING design requirement" — at every short-circuit return that precedes the mutation: the item-not-found `404`, the no-relationship `404`, the invalid-`sessionId` `422`, and the not-authorized-facilitator `403` (`action-items.ts` lines 80, 114, 134, 165). This is not incidental to D2's purpose; it's the other half of it. Distinct status codes and identical response bodies close the *content* side of the enumeration oracle this decision is about; without an equivalent timing floor, the same information leaks back out through response latency, since the branches above do measurably different amounts of database work (a bare item lookup, vs. item lookup + `evaluateTeamAccess` + an "ever facilitated" query, vs. + the facilitator-authorization query). **Decision:** this endpoint SHALL call `applyTimingFloor` at the same four branch points, using the same helper `VOTE-002` already ships in the same file (`packages/backend/src/content/timing-oracle.ts`). This is stated explicitly here — not left to be inferred from the fact that both handlers share a file — because "the neighboring handler already does it" is exactly the kind of assumption that quietly stops being true the day someone edits one handler without the other. See tasks.md 2.2/2.3/2.4/2.5, each of which now names its own `applyTimingFloor` call rather than leaving it implicit in a neighboring task.

**D3 — Resolved-item precondition: `409`, not `403`; corrects the contract in place.**

The contract's error table lists `403` for both "Not a facilitator" and "resolved action items cannot be reassigned" — an authorization failure and a state-precondition failure collapsed into one status code. `VOTE-002` already litigated this exact class of question (its Open Question 3: "Resolved is terminal... a `409`, unhedged") and there is no stated reason for this sibling endpoint to depart from that precedent. Adopting `409` here, and correcting the contract document itself — not only this change's own design.md — matches this codebase's existing house style for this exact situation (`VOTE-002`'s own `global_role`-based `Authorization` line, fully rewritten to describe its actual session-scoped mechanism when it shipped; the `session-lifecycle-transitions` correction under `SESSION-005`; `websocket-specification`'s Appendix D correction): a one-paragraph "Corrected by `reassign-action-item-owner`" note added directly under VOTE-004's section, dated, not a silent edit. See tasks.md for the exact task.

*Clarified following both reviews (`design-review-engineer.md` Finding 2, `design-review-security.md` Finding 3):* the sentence above originally read "the `global_role` correction on this same issue's contract entry," which both reviewers independently — and correctly — read as claiming VOTE-004's *own* `Authorization` line had already been corrected. It hadn't; that phrasing named `VOTE-002`'s entry as a precedent for the correction-note *style*, not as evidence this endpoint's own stale `Authorization` line was already fixed. It wasn't a considered decision to leave VOTE-004's line wrong — it was an editing error in this document, now corrected. See the Migration Plan's third correction, below.

Check ordering: the resolved-item `409` is evaluated before the new-owner validation cascade (D5), mirroring `VOTE-002`'s own resolved-terminal check positioned ahead of its body-content validation. A caller who both targets a resolved item and supplies an invalid new owner is told the item is resolved, not that their new owner is invalid — fixing the new owner wouldn't have helped them anyway.

**D4 — `sessionId`: REQUIRED for this endpoint (corrected from an earlier optional draft), validated by `VOTE-002`'s Decision D11 rule; server-side derivation still declined.**

*Corrected during BA review (`propose-review-ba.md`, Finding 1):* an earlier draft of this decision made `sessionId` optional "for consistency" with `VOTE-002`'s Decision D11, without checking whether D11's own reason for optionality travels with it. It doesn't. `VOTE-002`'s optionality is grounded in its own governing use case ("Update Action Item Status"), which explicitly names an out-of-session path ("...or, if supported, outside of a session") and hedges its session-recording language accordingly ("(if applicable)"). This endpoint's governing use case ("Reassign an Action Item When an Owner Leaves the Team") has no such path: its precondition requires an active session unconditionally, and its postcondition states without hedge that the reassignment session is recorded in the item's history. Sibling-consistency is a good default, but it stops being a good default the moment the sibling's own stated reason for its shape is a scenario this endpoint doesn't have. That's copy-paste residue, not a considered decision, and it's worth naming plainly rather than quietly fixing.

**Decision:** `sessionId` is REQUIRED in the request body for this endpoint. Its absence SHALL be rejected with `422` — the same code its invalidity already produces under D11's rule, since a missing session and an invalid one are the same practical fact from the caller's perspective (this reassignment cannot be attributed to a session). When present, it is validated exactly per D11: `SELECT status FROM sessions WHERE id = $1 AND team_id = $2`, rejected `422` unless a row is found with `status` in `ACTIVELY_FACILITATING_STATUSES`. The contract's current "Current session context, for history attribution" phrasing is corrected to state the field as required, not optional, matching `VOTE-002`'s qualifier style otherwise.

This closes the gap against the use case's unconditional postcondition without reopening the "assume a single qualifying session per team" question: the client's own UI already knows which session it's acting in, because the use case's own precondition means a facilitator can only reach this action from inside a live session in the first place. Server-side derivation remains declined for the reason already litigated: deriving it would require assuming "exactly one qualifying active session per team can exist at a time" — a guarantee neither endpoint's authorization query enforces today and that no uniqueness constraint on `sessions` backs at the database level. Re-litigating that assumption for both endpoints to enable derivation is a bigger authorization-model question than this change was filed to answer, and doing it only here would leave `VOTE-002` and `VOTE-004` with two different session-attribution models.

*Alternative considered:* keep `sessionId` optional, and instead explicitly override the use case's postcondition (state that a reassignment's `session_id` MAY be `NULL` when omitted, as a deliberate, named divergence). *Rejected:* overriding a use case's stated postcondition should be reserved for cases where honoring it is actually costly to the caller. It isn't here — this endpoint is only ever reachable from inside a live session, so the caller's own UI already holds the value; requiring it costs nothing real and closes the gap outright instead of documenting around it. The smaller, more honest fix is to require the field.

*Ordering note, not a new decision:* `sessionId` validation (including the new missing-field `422`) still runs where it always has in this check sequence — before the resolved-item precondition (D3) and before the new-owner cascade (D5), unchanged from `VOTE-002`'s own shipped order. A request against a resolved item that also has a missing or invalid `sessionId` is therefore rejected `422` for the session reason, not `409` for the resolved reason — the mirror image of D3's new-owner-vs-resolved precedence, where the resolved check wins because it runs first. See `specs/action-item-owner-reassignment/spec.md` for the corresponding scenario (BA review Finding 3).

**D5 — New-owner validation cascade: self-facilitator check first (cheap, no DB round-trip), then existence, then membership, then active-participant-non-EM.**

Full ordered sequence (see `specs/action-item-owner-reassignment/spec.md` for the normative scenarios):

1. `newOwnerUserId === callerId` → `422`, checked first since it requires no database access.
2. `newOwnerUserId` doesn't exist in `users` → `404`.
3. `newOwnerUserId` exists but has no `team_memberships` row at all for this team → `404` ("membership never existed").
4. `newOwnerUserId` has a `team_memberships` row for this team, but it's soft-removed (`removed_at IS NOT NULL`) or `role = 'engineering_manager'` → `422`.

The 404-vs-422 split in steps 3–4 mirrors the same distinction `team-membership-removal`'s (stub) partial-unique-index comment draws between "never a member" and "soft-removed member" — consistent with how membership state is already reasoned about elsewhere in this codebase, not a new distinction invented for this endpoint. Step 4's `role = 'participant'` check is exact, not "any membership" — this is the enforcement point for the no-manager-participation constraint (BRD FR-9.5): a facilitator SHALL NOT be able to reassign an item to an Engineering Manager by way of a loosely-written membership check.

*Implementation note, following Security review Finding 4 (`design-review-security.md`):* the steps 3/4 membership lookup MUST be its own query — `SELECT role, removed_at FROM team_memberships WHERE user_id = $1 AND team_id = $2`, with no `removed_at` filter in the `WHERE` clause — and MUST NOT reuse `evaluateTeamAccess`'s query shape as a shortcut. `evaluateTeamAccess` (already imported in this file) `LEFT JOIN`s `team_memberships` with `AND tm.removed_at IS NULL` baked into the join condition itself; reusing that shape here would silently fold a soft-removed member into "no row," misclassifying step 3's `404` as if the membership never existed and never reaching step 4's `422` at all. This is an implementation pitfall, not a design alternative — it would quietly break the exact 404-vs-422 distinction this decision draws. See tasks.md task 2.7 for the corresponding warning.

**D6 — Same-owner reassignment is a `200` no-op for the business record, but not for the audit trail.**

Reassigning an item to its own current `owner_id` is accepted: `action_items.updated_at` is bumped, and no `action_item_history` row is written — the identical shape `VOTE-002` already established for a same-status update, on the reasoning that this is the same class of request (an update to a value that doesn't change anything observable in the item's own history). This determination happens only *after* the new-owner cascade (D5) and the resolved-item precondition (D3) both pass, so a no-op request isn't exempted from validation an ordinary reassignment would have to satisfy.

*Amended following Security review Finding 2 (`design-review-security.md`):* the original draft of this decision also skipped the `audit_log` write on the no-op path, matching `VOTE-002`'s precedent exactly. That's the wrong precedent to copy verbatim for this one field. `VOTE-002`'s same-status no-op can't be used to manipulate anything another person relies on — a status that doesn't change is inert. This endpoint's no-op *can*: D9 bumps `updated_at` unconditionally, no-op included, and `updated_at` is the pre-session review screen's staleness signal (proposal.md's Context names it as the motivating consumer). A facilitator — or a retried/double-submitted client — can call this endpoint repeatedly with `newOwnerUserId` set to the current owner and reset that signal on demand, with, under the original draft, zero record anywhere that it happened. Skipping `action_item_history` on a no-op remains correct (nothing about the item's ownership changed, and that table's job is recording ownership transitions); skipping `audit_log` for the same reason is not, because `audit_log`'s job — see D10 and `VOTE-002`'s Decision D13 — is not "record what changed" but "record that a privileged action was exercised." A privileged action was exercised here, repeatedly, resettable at will, with a real effect on a signal other people act on. That is precisely the "permission exercised in a suspicious pattern" case audit logging exists to make reconstructable. See D10 for the resulting shape.

**Decision, restated:** the no-op path writes `action_items.updated_at` only (no `action_item_history` row) but SHALL write an `audit_log` row and its `emitAuditEvent` counterpart, distinguished from a real reassignment by `metadata.no_op = true`.

*Alternative considered:* reject same-owner reassignment as a non-reassignment (`422`, "new owner is the same as the current owner"). *Rejected, unchanged from the original decision:* treating a status no-op and an owner no-op differently at the `action_items`/`action_item_history` layer, with no stated product reason, remains an inconsistency a future reader would have to puzzle out. This amendment narrows the departure from `VOTE-002`'s precedent to the audit layer specifically; it does not reopen no-op acceptance itself.

**D7 — `action_item_history` schema: additive nullable owner columns (Option A), with an enforced symmetric-nullability invariant.**

`previous_status`/`new_status` on `action_item_history` are `NOT NULL` (migration 2), and `action-item-status-management` treats this table as strictly a status-history table today: one row per accepted transition, both status columns always populated. A reassignment doesn't change status, so a literal reuse of those columns alone would require writing `previous_status = new_status = <the item's unchanged current status>` on a reassignment row — workable, but only if the table also gains a way to say "this row is about ownership, not status."

Adopted: add `previous_owner_id uuid NULL REFERENCES users(id)` and `new_owner_id uuid NULL REFERENCES users(id)` to `action_item_history` (one additive migration, next in sequence after migration 9). Keep `previous_status`/`new_status` `NOT NULL` as-is, written to the item's unchanged current status on a reassignment-only row. `changed_by_user_id`/`session_id`/`changed_at` are all reused as-is. This is the smaller diff against a table an already-shipped, reviewed endpoint depends on; a grep across `packages/` and `openspec/` confirms no existing consumer beyond `VOTE-002`'s own write path and tests assumes "one row = one status transition," so nothing is corrupted by widening the table's meaning.

*Alternative considered:* a separate `action_item_owner_history` table. *Rejected:* doubles the write-path surface (two tables, two transactions to coordinate) and two places to query "what happened to this item" for no benefit proportional to the cost — this table already carries `changed_by_user_id`/`session_id`/`changed_at`, which a second table would have to duplicate.

**Enforced invariant, not a comment:** a `CHECK` constraint, `CHECK ((previous_owner_id IS NULL) = (new_owner_id IS NULL))`, is added in the same migration — cheap, catches a malformed insert at the database boundary regardless of which code path writes it in the future, matching this codebase's existing appetite for narrative, well-commented migrations (migration 7's comment block is the house style to match). A second invariant — "a reassignment-only row's `previous_status` and `new_status` SHALL be equal" — is stated as an application-level SHALL in `specs/action-item-owner-reassignment/spec.md`, not a database `CHECK`: this codebase's endpoint that could violate it (this one) is the only call site that will ever write a non-null-owner-column row, and a `CHECK` comparing two enum columns for equality only when a third condition holds is more constraint complexity than the actual corruption risk justifies today. A future endpoint that wants to change status and owner in the same write would need a corresponding schema/spec update first — this is a boundary this change draws deliberately, not an oversight.

**Cross-reference, not a one-sided note:** `action-item-status-management/spec.md`'s "every real status transition is recorded" requirement gets one added sentence (this change's delta spec) scoping it to status-change rows only, so a future reader of that spec alone — without ever opening this capability's spec — still learns that a row with non-null owner columns is governed elsewhere.

**D8 — No WebSocket broadcast: confirmed, not tentative.**

`action_item_status_updated`'s payload is scoped strictly to `previousStatus`/`newStatus`; no event named or shaped for an owner change exists anywhere in this codebase's catalog or in `websocket-specification`'s corrected Event Registry, and Appendix D's broadcast-exclusion table doesn't list `VOTE-004` at all — read as an artifact of the contract predating `VOTE-002`'s actual implementation, not a considered exclusion. This change adds no event. Whether the room should see a reassignment happen live — plausible for the "team decided together, out loud" trigger cases, moot for the quiet-correction ones — is a `websocket-specification`-governed UX judgment for whichever change eventually builds #68, not something this change should half-build by speculatively adding an event nobody has designed a consumer for.

**D9 — Staleness clock: every accepted reassignment bumps `action_items.updated_at`, no-op included.**

If a reassignment doesn't touch `updated_at`, an item that sat untouched for three sessions and gets reassigned to a brand-new owner shows up already red on that owner's first session holding it, for no fault of their own — undermining trust in the pre-session review screen's staleness signal for a reason invisible to the new owner. This is the same reasoning `VOTE-002`'s same-status no-op already applies: the recorded fact of ownership (or a re-confirmed one, in the no-op case) changing is what should reset the clock, not only a status change.

*Cross-reference:* because this decision resets the staleness clock on the no-op path too, the no-op path is the one this design gives a real, repeatable ability to affect a signal other people rely on — which is exactly why D6 is amended to require an `audit_log` record for it. This decision (bump the clock, no-op included) and D6's amendment (audit the no-op, no-op included) are a matched pair, not independent choices; see D6 for the reasoning.

**D10 — Audit event name: `action_item.owner_reassigned`, matching `VOTE-002`'s `audit_log` dual-write pattern — extended, per D6's amendment, to also fire on the no-op path.**

`action_item.status_changed` (`VOTE-002`'s audit event, Decision D13) is the direct precedent: an `emitAuditEvent` structured-log call plus an in-transaction `audit_log` row, same shape (`actor_user_id`, `actor_global_role`, `actor_ip`, `operation`, `team_id`, `metadata` JSON). This change adds `action_item.owner_reassigned` to `AuditEventName` in `packages/backend/src/auth/audit-logger.ts`, with `metadata` carrying at minimum `action_item_id`, `previous_owner_id`, `new_owner_id`, `session_id`.

Per D6's amendment, the no-op path writes the same `audit_log` row and `emitAuditEvent` call as a real reassignment, with two differences: `metadata.previous_owner_id` and `metadata.new_owner_id` are equal (both the item's unchanged owner), and `metadata` carries an additional `no_op: true` field so a reader of the audit trail — or tooling built against it later, e.g. to flag repeated staleness-clock resets on the same item as a suspicious pattern — can tell "ownership actually changed" from "a facilitator re-confirmed the existing owner" without inferring it from two equal IDs. The no-op path's `UPDATE action_items SET updated_at = NOW()` and its `audit_log` `INSERT` are wrapped in the same lightweight transaction (open, `UPDATE`, `INSERT`, commit) so the staleness-clock reset and its audit record can't diverge — a failed audit write should not silently leave an unrecorded reset in place. Only the `action_item_history` row is skipped on the no-op path, per D6; that table's job is recording ownership transitions, and none occurred. Mechanical beyond the no-op extension — recorded here for completeness against D7's schema decision.

**D11 — Concurrency: a `WHERE status != 'resolved'` guard on the final `UPDATE` closes the two-writer race this change introduces on `action_items`, without introducing row-level locking.**

*Following Full Stack Engineer review Finding 1 (`design-review-engineer.md`).* Before this change, `action_items` had exactly one write path (`VOTE-002`'s status `PATCH`), so a race against itself was the only possible interleaving. This change adds a second concurrent writer to the same row's `owner_id` (and reader of its `status`), and the existing pattern both endpoints share — read the row via a plain `SELECT` before opening a transaction, make every business-rule decision against that snapshot, then `UPDATE ... WHERE id = $1` unconditionally inside the transaction — has no guard against the row changing between the snapshot read and the commit.

The interleaving that matters: facilitator A resolves the item via `VOTE-002` while facilitator B (or a second tab) reassigns it via this endpoint at nearly the same time. B's pre-transaction snapshot (task 2.2) still reads `status = 'open'`, passes the resolved-item precondition (D3), and B's `UPDATE` — unconditional today — then commits an owner change against a row that is, by commit time, actually resolved. That violates the "resolved is terminal, unhedged" invariant D3 exists to enforce, and it writes a `previous_owner_id` into `action_item_history` that no longer reflects the truth at the moment of the write.

**Decision:** the final `UPDATE action_items SET owner_id = $1, updated_at = NOW() WHERE id = $2` (task 2.9) gains an `AND status != 'resolved'` guard, and the handler checks the update's `rowCount`. A `rowCount` of `0` means a concurrent writer resolved the item between this handler's snapshot read and its own commit attempt — a late-discovered instance of the exact same conflict D3 already returns `409` for, so it is handled identically: roll back, return `409`, write neither `action_item_history` nor `audit_log`. This closes the invariant violation with a one-clause addition to a statement this change was already writing, with no new lock primitive and no restructuring of the "validate against a snapshot, then write" shape both endpoints already use.

*Alternative considered:* `SELECT ... FOR UPDATE` on the item row at load time (task 2.2), holding the lock for the handler's duration. *Rejected, for now:* the item load happens before authorization and before most of the validation cascade; turning it into a locking read would mean holding a row lock across several subsequent DB round-trips (relationship check, `sessionId` validation, facilitator-authorization query, new-owner cascade) for the full duration of a not-yet-authorized request — a meaningfully larger blast radius (a slow or malicious caller holds a lock other facilitators may need in order to resolve the same item) than the specific race this decision needs to close. The `WHERE`-guard protects the one invariant that actually matters (resolved is terminal) at the exact moment it matters (the final write), without paying that cost. If `action_items` grows a third concurrent writer, or the residual risk below turns out to matter in practice, promoting this to `SELECT ... FOR UPDATE` (or a serializable transaction) is the natural next step — not precluded by this decision, just not taken preemptively.

**Residual risk, named rather than silently accepted:** this guard closes the resolved-vs-reassign race specifically — a terminal-state correctness invariant — but does not serialize two concurrent *reassignment* writes against the same item (facilitator A and facilitator B both reassigning the same open item to different new owners within the same short window). In that interleaving both writes still succeed, since the guard only checks `status`, not `owner_id`; whichever commits last determines the final `owner_id`, and the later-committing write's `action_item_history` row records `previous_owner_id` from its own pre-transaction snapshot, which may no longer match the true immediately-prior owner if the two writes interleaved. This is a lost-update on a mutable assignment field, not a violation of a stated invariant (there is no "reassignment is terminal" rule, unlike `resolved`), and two facilitators reassigning the same item within the same window is a materially rarer and lower-consequence event than a resolve/reassign race. Not fixed here — the `WHERE status != 'resolved'` guard is scoped deliberately to the one invariant this design treats as load-bearing, not generalized into full write serialization for a race with no stated product harm today.

## Risks / Trade-offs

- **[Risk]** The `team_membership_role = 'participant'` check, if ever loosened to "any membership exists" in a future refactor, would let a facilitator reassign an item to an Engineering Manager — a crack in the no-manager-participation constraint even though it isn't the voting wall → **Mitigation:** D5 states the check precisely as a SHALL against `role = 'participant'`, not membership existence, and `specs/action-item-owner-reassignment/spec.md` has a dedicated scenario ("An Engineering Manager cannot be reassigned an item") pinning this down as an independently-tested case, not defense-in-depth left implicit.
- **[Risk]** A future endpoint reading `action_item_history` for "count of status transitions" or similar trend tooling could misread a reassignment-only row (equal `previous_status`/`new_status`) as a no-op status update → **Mitigation:** D7's cross-reference sentence in `action-item-status-management/spec.md` states the disambiguating rule (check `previous_owner_id`/`new_owner_id` non-null first) directly in the spec a future implementer of such tooling is most likely to read, not only in this capability's own spec.
- **[Risk]** Diverging this endpoint's authorization, enumeration-safety, or session-validation shape from `VOTE-002`'s, even slightly, would leave two different "when can a facilitator write here" models for a future reader to reconcile → **Mitigation:** D1, D2, and D4 each state explicitly that they reuse `VOTE-002`'s mechanism rather than approximate it, and name the one structural difference (no owner-path fork) as the only deliberate divergence.
- **[Risk]** This change makes `action_items` a two-writer table for the first time; a `VOTE-002` resolve racing this endpoint's reassignment could otherwise commit an owner change against an item that's actually resolved by commit time, violating the "resolved is terminal" invariant → **Mitigation:** D11's `WHERE status != 'resolved'` guard plus `rowCount` check on the final `UPDATE`, treating a late-discovered conflict identically to the already-known-resolved `409` case. **Accepted, named residually:** the same guard does not serialize two concurrent *reassignment* writes to the same item — a lost-update on `owner_id` itself remains possible under that narrower, lower-consequence interleaving; see D11's residual-risk paragraph.
- **[Risk]** The endpoint's own namesake scenario — reassigning away from a departed owner — cannot occur organically in production today, since no application code sets `team_memberships.removed_at` yet (`team-membership-removal` is a stub, not blocking, per exploration §3) → **Mitigation:** stated as an accepted, named limitation in proposal.md rather than left for a reviewer or QA engineer to discover later; manual/QA verification of the "not an active participant" `422` path uses a raw `UPDATE team_memberships SET removed_at = ...` fixture, matching the existing pattern in `ws-pubsub-integration.test.ts`, not an end-to-end removal flow. This does not block the endpoint's own correctness — reassignment has other legitimate, already-reachable uses (misassignment correction, load-balancing) that exercise the same validation path today.
- **[Risk]** Leaving `openspec/changes/team-membership-removal/README.md`'s two references to this exact constraint uncorrected would create a false blocker for whoever picks that change up next, reading as if VOTE-004's constraint is still undesigned → **Mitigation:** tasks.md includes an explicit task to rewrite both bullets to a forward pointer, not left as a note only visible in this change's own exploration notes.
- **[Risk]** `ACTION-002`'s wrap-up owner edits remain unrecorded in `action_item_history` (the still-open OQ-8) — once this change ships, the table will contain owner-history rows for reassignments made after wrap-up but not for edits made during it, an inconsistency in what "the item's owner history" means depending on which endpoint touched it → **Mitigation:** named explicitly here and in proposal.md as a pre-existing, separate gap this change does not resolve (a different endpoint's write path), with a pointer that OQ-8's eventual answer can reuse this change's owner-column shape instead of inventing new ones. Not fixed here — extending scope to `ACTION-002` is exactly the kind of adjacent scope creep this change should not absorb.

## Migration Plan

One additive migration, next in sequence after migration 9 (`9_draft_session_and_facilitator_expiry.sql`): adds `previous_owner_id uuid NULL REFERENCES users(id)` and `new_owner_id uuid NULL REFERENCES users(id)` to `action_item_history`, plus `CHECK ((previous_owner_id IS NULL) = (new_owner_id IS NULL))`. No existing column, index, or constraint on `action_item_history` or `action_items` changes shape. No backfill is required — every existing row has both new columns `NULL`, which is a valid, correctly-typed status-change row under the new schema. Deploy is purely additive; rollback is a normal migration revert (drop the two columns and the constraint), with no data-loss risk since no pre-migration data depends on the new columns.

`requirements/design/REST API Contract.md`'s existing `VOTE-004` section is reconciled, not replaced: a "Corrected by `reassign-action-item-owner`" note is added directly under it (matching the `global_role`, `session-lifecycle-transitions`, and `websocket-specification` correction precedents already in that document) stating three corrections, not two:

1. The `403`→`409` resolved-item correction (D3).
2. The `sessionId` description wording fix, optional→required (D4).
3. **Added following both reviews (`design-review-engineer.md` Finding 2, `design-review-security.md` Finding 3):** a full rewrite of the `Authorization` line. It currently reads *"Authorization: `global_role = 'facilitator'` only. The facilitator must have an active session for the team this action item belongs to."* `global_role = 'facilitator'` is a real, distinct enum value (`user_role`, migration 1) — this is not a typo, it describes a materially weaker, standing authorization model than the session-scoped `EXISTS` check this design actually implements (D1), and the code never checks `users.global_role` at all. The rewritten line matches `VOTE-002`'s own corrected contract entry precedent exactly: it states the session-scoped `EXISTS` mechanism precisely, notes there is no owner-authorized fork here (unlike `VOTE-002`), and cites this design's Decision D1 by name.
