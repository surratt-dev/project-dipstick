# Task Ordering & Dependency Review — Ingrid Sollenberger (Solution Architect)

Scope of this pass: does tasks.md's ordering respect the dependencies design.md establishes, and does any task assume something a later task actually introduces? This is not a re-review of the design decisions themselves (D1–D11) — those are settled and I incorporated the prior review rounds into design.md already. This is strictly a sequencing check, cross-referenced against the current state of the codebase where that's verifiable (migrations directory, `action-items.ts`, `audit-logger.ts`).

## Finding 1 (blocking-if-unaddressed): Task 2.8 forward-references the `AuditEventName` addition that Task 2.11 introduces

Task 2.8 (same-owner no-op) requires writing an `audit_log` row with `operation = 'action_item.owner_reassigned'` and calling `emitAuditEvent(logger, "action_item.owner_reassigned", ...)`. But `"action_item.owner_reassigned"` is not a valid `AuditEventName` literal until Task 2.11 adds it to the union type in `packages/backend/src/auth/audit-logger.ts` — I confirmed by reading that file that `AuditEventName` is a closed TypeScript string-literal union (`"auth.authorization_initiated" | ... | "team.manager_established" | ...`), not an open string or a DB-level enum. There's no schema-level constraint on `audit_log.operation` (migration 8 defines it as plain `TEXT NOT NULL`, no `CHECK`), so this isn't a database migration-ordering problem — but it is a real source-ordering problem: an implementer working tasks.md front-to-back would hit a type error writing 2.8's code, because the literal it needs doesn't exist as a valid `AuditEventName` value until two tasks later.

Task 2.11's own phrasing compounds this — it bundles "add `action_item.owner_reassigned` to `AuditEventName`" (a one-time source edit) together with "`INSERT INTO audit_log`" (a per-request runtime action) under one task, framed as both happening "in the same transaction." Only the second is transactional; the first is a type declaration that has to exist before *either* 2.8 or 2.11's runtime code compiles. That framing is what let the forward reference slip through — it reads as scoped to the real-reassignment path alone, when it's actually a prerequisite for the no-op path three tasks earlier.

**Recommendation:** pull the `AuditEventName` addition out of 2.11 into its own task positioned before 2.8 — either fold it into 2.1 (route scaffolding) as a first sub-step, or insert a new 2.1a ("Add `action_item.owner_reassigned` to `AuditEventName` in `audit-logger.ts`, ahead of any call site") immediately after 2.1. Then 2.8 and 2.11 both simply *use* the literal rather than one of them silently depending on the other introducing it out of order.

## Minor, non-blocking observation

Tasks 2.9–2.11 share one transaction (open → guarded `UPDATE` → history insert → audit insert), and 2.9's rollback path is spelled out explicitly ("roll back the transaction and return 409" on `rowCount = 0`). There's no equivalent explicit "commit the transaction" checklist item for the success path before 2.12 returns. This is very likely implicit to any implementer and I'm not asking for a task split over it, but since 2.9 was careful enough to spell out the failure branch, the success branch's commit could get the same one-clause treatment for symmetry. Not a sequencing defect — noting it only because tasks.md is otherwise unusually precise about transaction boundaries, and this is the one place the mirror-image statement is missing.

## Bottom line

Ordering is sound at the level that matters most — migration-before-route, and the check-ordering sequence in the route handler matches design.md's D2/D3/D4/D5 precisely, verified against the actual shipped anchor code, not just the design narrative. The one real defect is Finding 1: Task 2.8 depends on a type-level addition that Task 2.11 doesn't introduce until three tasks later. That's a genuine "later task introduces what an earlier task assumes" ordering bug and should be fixed by relocating the `AuditEventName` addition ahead of 2.8, not by re-explaining the dependency in place.
