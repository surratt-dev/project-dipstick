- [x] 2.5 Implement facilitator authorization: reuse `VOTE-002`'s existing `ACTIVELY_FACILITATING_STATUSES` constant and `EXISTS (SELECT 1 FROM sessions WHERE facilitator_id = $1 AND team_id = $2 AND status = ANY($3::text[]))` query verbatim (Decision D1). No owner-path fork — facilitator-or-nothing. **Apply `applyTimingFloor` before returning this `403`** (Decision D2's timing-floor amendment, following Engineer review Finding 3 and Security review Finding 1 — this is the one branch both reviews independently flagged as missing the call-out VOTE-002's own shipped handler makes at its equivalent branch, `action-items.ts` line 165).
- [x] 2.6 Implement the resolved-item precondition: if the item's current `status` is `resolved`, reject with `409` (Decision D3) — evaluated before the new-owner validation cascade (2.7), so a resolved item with an also-invalid new owner is rejected for the resolved reason. - [x] 2.7 Implement the new-owner validation cascade, in this exact order (Decision D5): (a) `newOwnerUserId === callerId` → `422`, no DB round-trip; (b) `newOwnerUserId` doesn't exist in `users` → `404`; (c) no `team_memberships` row for this team → `404`; (d) membership exists but `removed_at IS NOT NULL` or `role = 'engineering_manager'` → `422`. Check (d) precisely against `role = 'participant'`, not "membership exists" (no-manager-participation constraint, BRD FR-9.5).
  - **(b)'s query should also select `display_name`** (`SELECT id, display_name FROM users WHERE id = $1`): the fetched row is reused as the source of the response's `ownerDisplayName` field for both the no-op path (2.8) and the real-reassignment path (2.12), so neither needs a separate join (Engineer review Finding 4).
  - **Implementation note, following Security review Finding 4:** the (c)/(d) membership lookup MUST be its own query — `SELECT role, removed_at FROM team_memberships WHERE user_id = $1 AND team_id = $2`, with no `removed_at` filter in the `WHERE` clause — and MUST NOT reuse `evaluateTeamAccess`'s query shape as a shortcut. `evaluateTeamAccess` `LEFT JOIN`s `team_memberships` with `AND tm.removed_at IS NULL` baked into the join condition itself; reusing that shape here would silently fold a soft-removed member into "no row," misclassifying step (c)'s `404` as if the membership never existed and never reaching step (d)'s `422` at all.
- [x] 2.8 Implement the same-owner no-op (Decision D6, amended per Security review Finding 2): if `newOwnerUserId` equals the item's current `owner_id` (after 2.6/2.7 both pass), open a lightweight transaction that (a) runs `UPDATE action_items SET updated_at = NOW() WHERE id = $1 RETURNING updated_at` and (b) writes an `audit_log` row (`operation = 'action_item.owner_reassigned'`, using the `AuditEventName` literal added by 2.1a; `metadata.no_op = true`, `previous_owner_id` and `new_owner_id` both equal to the unchanged owner) — commit both together; no `action_item_history` row is written. - [x] 2.9 Open a database transaction for the real-reassignment path (after 2.6–2.8): `UPDATE action_items SET owner_id = $1, updated_at = NOW() WHERE id = $2 AND status != 'resolved' RETURNING updated_at` (Decision D9 — `updated_at` bumped on every accepted reassignment, no-op included; **Decision D11 — the `status != 'resolved'` guard closes the race against a concurrent `VOTE-002` resolve, following Engineer review Finding 1**).
