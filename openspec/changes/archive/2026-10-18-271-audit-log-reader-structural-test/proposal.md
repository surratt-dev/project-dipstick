# Proposal: 271-audit-log-reader-structural-test (#271)

*Framed by Devon Calloway (Internal Champion). Builds on `exploration-notes.md`; section 0 and section 8 there are the live position. The explore reviews are history. Revised after the propose reviews (`propose-review-ba.md`, `propose-review-exec.md`) and again after the design reviews (`design-review-engineer.md`, `design-review-security.md`, resolved in `design.md`); see "Review resolution" below.*

## Why

The "Audit visibility guard" in `team-content-access` says audit rows for admin topic-configuration reads and denials must never reach team members or engineering managers. Today that rule holds by reviewer memory. The one non-admin reader, `fetchConnectionRecoveries` in `routes/content.ts`, is pinned by a string assertion in `content.test.ts`, but nothing stops a new reader from appearing with `operation LIKE 'session.%'` or no operation filter. Security review #208 recorded this as D-5: "visibility guard enforced by review only", worth an automated source scan once #264 landed. #264 is closed, so the precondition is met.

Why I care, in participant terms: people stop speaking honestly in a Health Check if they believe admin or diagnostic data about them can be surfaced. So this test protects the ceremony, not only compliance. A constraint that lives in the heads of the people who reviewed #208 does not survive them. I want the build to carry it, and I want the failure message to teach a developer who has never heard of #208, so I am not the help desk.

## What Changes

- Add a structural test, `packages/backend/src/routes/__tests__/audit-log-reader-structural.test.ts`, and a pure scanner helper at `routes/__tests__/helpers/audit-log-reader-scanner.ts` (TypeScript AST plus a small SQL tokenizer). `template-writer-scanner.ts` is not refactored; three of its helpers (`literalText`, `functionLabel`, `enclosingFunction`) gain an `export` keyword, no behavior change.
- The scanner reads string and template literals in `packages/backend/src` only (via `productionSources()`), ignores comments, and finds every **touch** of `audit_log`: `audit_log` in a SQL table position (after FROM, JOIN, INTO, UPDATE, TRUNCATE, TABLE, ONLY, COPY, MERGE, LOCK, or a FROM-list comma; whole word, case-insensitive when unquoted) other than as the target of a **writer**. A writer is a column-listed `INSERT INTO audit_log (...)` whose row source is `VALUES` or a SELECT that does not itself read `audit_log` (an `ON CONFLICT` or `RETURNING` tail is fine); the existing INSERT...SELECT in `auth/fail-open-topic-audit.ts` is a writer. Touches: SELECT, JOIN, subquery, CTE, INSERT without a column list, a self-reading INSERT...SELECT, UPDATE, DELETE, TRUNCATE, COPY, MERGE, LOCK. Any other `audit_log` string in code (a constant, an array of table names, error-message prose) is a non-inventoriable **tripwire** finding. The pass condition for writers is stated, not estimated: every production writer produces zero findings.
- The test holds an **inventory** (every touch, keyed by file plus enclosing function, each with a non-blank reason) in **two** classes held in two separate objects: `exact-match` (mechanically checked against a positive grammar: one flat single-table SELECT, a lone `operation = '<literal>'` conjunct, and a row-scope conjunct `team_id = ...` or `metadata->>'scopeId' = ...`) and `admin-only` (exempt from the filter check; reason names the constant and the route's admin guard; also carries `callers`, the files allowed to reference the function, which the test verifies, and `statements`, the number of touching statements). An UPDATE, DELETE or TRUNCATE touch has no class today and fails as unclassifiable; if one is ever legitimate, a reviewed change adds a class then.
- Failures: an uninventoried touch (even a correctly filtered one); a stale entry; a blank reason; an `exact-match` entry on a protected operation; an `admin-only` function referenced from a file not in its `callers`, or whose statement count changed; a statement that cannot be statically classified (precise boundary in design D4 and D5); a source file that does not parse, an empty source set, an unknown directory under `packages/`, or a non-`.ts` source under `packages/backend/src`; a `process.env`, `.skip`, `.only`, `skipIf` or `runIf` in the test or scanner source.
- Protected set, a short constant: any operation beginning `admin.` (case-sensitive, so the bare literal `admin.` counts) or `topic.config_` (fails closed on a future sibling denial row), plus the exact names `topic.config_list_denied` and `admin.topic_config_accessed`. `topic.configure` and bare `admin` are not protected.
- Today's inventory: `routes/content.ts#fetchConnectionRecoveries` (`exact-match`; serves the facilitator via session history; shows connection recoveries only), and `sessions/default-topic-maintenance.ts#readTemplateList` (two statements, one entry, `statements: 2`; the reorder statement is not verified because the entry is `admin-only` as a whole) and `#readTemplateHistory` (`admin-only`, `statements: 1`), both with `callers: ["routes/admin-default-topics.ts"]`.
- Docs and spec: a short extension procedure in the test header; one pointer sentence in `docs/deployment.md`; a MODIFIED delta on the "Audit visibility guard" requirement that keeps the original normative obligation verbatim and adds verification wording plus a link to the test (see Specs below).
- **Mitigates security review D-5, with named residual; it does not close it.** The filter-shape half of the guard becomes mechanical; the classification of whom a reader serves, readers the scanner cannot see, and scope and column correctness remain review. A task adds a one-line note on the archived #208 `design-review-security.md` saying exactly that. `Closes #271` on the PR closes the issue, not the risk. Also a stated deviation from the issue text: the issue says "allow-list"; this change uses an **inventory** (every touch listed, compliant readers included), so nobody should read the issue and expect compliant readers to be free. The issue's "route file" scope is deliberately widened to all of `packages/backend/src`, because R2 to R4 live under `sessions/`.
- No production code, migration, API, or facilitator-visible behavior changes. The `content.test.ts` pin stays unchanged; it pins the executed SQL, the new test pins the source. The test header says so too, so it survives archive: do not remove the pin as redundant.
- Effort bound: revised to about three days including review (tokenizer and positive grammar, caller check, 40 to 50 table-driven fixtures). If it grows past four, scope has drifted and I want to hear about it. This is up from two; the increase is security-driven and the executive stakeholder is asked to confirm it.

## Capabilities

### New Capabilities
- None.

### Modified Capabilities
- `team-content-access`: the "Audit visibility guard" requirement keeps its original obligation (no non-admin query selects `audit_log` by wildcard, prefix, pattern or `IN` list; every such query filters `operation` by equality on one named operation), and gains wording on how it is verified: the structural test mechanically checks the filter shape and inventory; classification of whom a query serves, and queries the test cannot see, are verified by review. The original behavioural scenario stays; one structural scenario is added. Details of the rules live in the test header, not the spec, so the spec does not need rewriting when the scanner changes. A test provides evidence for an obligation; it does not replace it.

## Constraints preserved

- No switch: no env var, skip flag or config can disable the test. A false positive is fixed in the scanner with a fixture, never by adding an inventory entry.
- Runs in the default backend `npm test` with no DB and no env vars, and that suite is the one CI runs (verified, task 5.1).
- Nothing here makes a protective rule optional; `admin.*` rows stay unreachable by non-admin readers.
- No performance-tool surface is added; no data is newly surfaceable.

## Known limits (stated in the test header)

- `admin-only` is trusted for what it returns and whom the route serves. The test does verify callers (by name, including string-literal keys and listed same-file wrappers; not computed keys or wrappers in other files) and statement count, but not an in-place edit of an existing admin-only statement, and not that a caller file really enforces `application_admin`. Reason quality (beyond non-blank) is human-review territory by decision.
- `exact-match` requires a scope conjunct but checks only its presence, not that the value is the caller's scope; it does not check selected columns.
- Entries are keyed by file plus function (labels from `functionLabel`, including `<module>` and `route GET /x`); duplicate labels in one file collapse to one key. Within an `exact-match` function every statement is judged; a mixed function is `admin-only` as a whole and unverified.
- **Approval is by convention, not enforcement.** The repo has no CODEOWNERS file (searched whole repo and `.github/`, which has only `workflows/`). New entries are reviewed by the Security Analyst role. This change does not claim an enforced gate and promises no review turnaround. Whether the `test` job is a required status check on `main` is stated in the PR; if it is not, the whole control is advisory.
- Scope is `packages/backend/src`, `.ts` only. `migrations-manual/` is out (operator-run, human-reviewed). A new migration that creates a view or function over `audit_log` is a known gap. A new package under `packages/` fails an assertion until the scan roots are extended on purpose. SQL assembled from fragments none of which spells `audit_log`, `.sql` files read at runtime, and a production module hidden under `__tests__` are blind spots.

One issue, not five, to respect the backlog concern. **Filed as #312.**
- **Open decision (owner: Brian Surratt as repository owner):** a CODEOWNERS entry for the test and scanner. Security asks for it now; it needs a team handle that no repo document names. Until decided, approval is by convention, as stated above.
- Residual risk if the protected set is ever descoped: an exact match on `admin.topic_config_accessed` would pass the filter check and be caught only by inventory review. The protected set is in scope here.
