# Design-Stage Security Review — websocket-connection-reauthorization (SEC-25/SEC-26/SEC-27)

**Reviewer:** Tomás Ferreira, Senior Application Security Analyst
**Scope:** design.md, proposal.md, the delta spec, verified against `packages/backend/src` (not assumed from prose) — `auth/middleware.ts`, `auth/session-store.ts`, `auth/audit-logger.ts`, `realtime/connection-registry.ts`, `realtime/websocket-routes.ts`, `realtime/ws-event-dispatcher.ts`, `realtime/staleness-signal.ts`, `routes/content.ts`, `routes/auth.ts`. Also read the archived `websocket-delivery-time-authorization` design.md in full, since this document is bound by its non-disclosure guarantee and its D7/D8 audit-logging precedent.

**Bottom line:** The core architecture (two independent mechanisms, reuse of the existing authorization functions, `STALE_SIGNAL_CLOSE_CODE`'s non-disclosure boundary preserved for SEC-25) is sound and I would not reopen D1, D2, D6, D7, or D8. I have one **blocking finding** (Finding 1: D4's recovery check is verified, against actual code, to be broken for the exact case SEC-26 exists to handle) and three **non-blocking-but-required-before-implementation** findings (Finding 2: the Redis write-race risk assessment doesn't hold under a common, security-recommended OIDC configuration; Finding 3: the D9 diagnostic trace has no reachable read path anywhere in this codebase, verified; Finding 4: the D9 diagnostic trace's own scoping reintroduces a narrower version of the disclosure it exists to prevent). None of these require reopening the headline two-mechanism/two-close-code architecture — all are corrections or additions within it.

## Finding 1 (Blocking): Decision D4's recovery check will never observe a genuine SEC-26 re-authentication, because the login flow it relies on regenerates the session ID

**Verified, not assumed:** `packages/backend/src/routes/auth.ts` line 196, in the `/auth/callback` handler: `await request.session.regenerate();`, with a comment explaining this is deliberate session-fixation prevention (Task 3 of an earlier change). This means the **only** flow the SEC-26 spec's "explicit re-authentication" language can mean — the client redirecting through `/auth/login` → IdP → `/auth/callback` — issues the client a **new** session ID and, per `@fastify/session`'s `regenerate()` contract, does not update the old session's Redis row in place.

Decision D4's recovery mechanism does the opposite of what this requires: at grace-period expiry, it "re-reads `SessionData` for the same session id from the Redis store" — the session ID `RegisteredConnection.sessionId` captured once, at WS registration time (Decision D3). If the client does exactly what the disclosed `reauth_required` signal asked of them — logs in again — the WS connection is checking a session row that `session.regenerate()` has already abandoned. The old row still holds the stale `tokenExpiresAt` (or is gone entirely, depending on `@fastify/session`'s regenerate-then-destroy-old ordering). Either way, D4's check reads it as "not recovered" and closes the connection with `REAUTH_GRACE_EXPIRED_CLOSE_CODE`, **every time**, regardless of whether the user re-authenticated successfully.

The mechanism does work for a narrower case the design doesn't distinguish from the one above: a **silent, same-session, threshold-triggered refresh** — `authMiddleware`'s existing `onRequest` refresh logic firing on some ordinary HTTP request the client's browser happens to make during the grace window, which mutates the *same* session row in place (no `regenerate()` call in that path). That case genuinely recovers under D4's check. But that's not "the client completed re-authentication" — it's "the client's browser happened to make an unrelated request while the refresh token was still valid to reuse." For the actual disclosed-to-the-user, "please re-authenticate" case — which is what fires when refresh has already failed definitively (`"revoked"`) or exhausted retries (`"transient_failure"`) — a fresh silent refresh on the *old* session is exactly what already failed once; the only path back to a valid token for that user is the explicit login, which this check cannot see.

**Why this is a security finding, not just a UX bug:** it fails closed, not open — I confirmed there is no path by which this bug grants continued access to someone who shouldn't have it. But it means the SEC-26 requirement text itself ("if the client completes re-authentication within the grace period, the connection remains open") is unsatisfiable by the described mechanism for the one case it names. A design document should not present D4 as settled ("this reuses the client's existing re-authentication flow... instead of inventing a new WebSocket control message") when the specific flow it names to reuse structurally defeats the check built around it. This needs one of: (a) the WS-side recovery check keyed by `userId` rather than the stale `sessionId`, checking whether *any* current, valid session exists for that user; (b) the explicit login flow additionally writing/aliasing the new session's tokens back under the old session ID for the grace window (awkward, and in tension with the fixation-prevention rationale `regenerate()` exists for); or (c) an explicit design acknowledgment that the "recovery" path only ever covers the same-session silent-refresh case, and the disclosed-prompt case is *always* a hard close requiring a brand-new WS connection after login — which is a legitimate design choice, but it isn't the one D4 currently describes, and Decision D7's "no close occurs on success" framing and the spec's own acceptance scenario should be corrected to match whichever choice is made.

## Finding 2 (Required before implementation): D3's "accepted narrow race" reasoning for the Redis write race does not account for refresh-token rotation with reuse detection

Decision D3's Risk 3 states two independent writers (an HTTP request's refresh and the new WS timer's refresh) can race on the same session's Redis row, and characterizes the worst case as "a wasted OIDC round-trip, not an authorization gap," because both writers only fire near the refresh threshold and both produce "valid, freshly-issued tokens."

That framing assumes the identity provider treats a refresh token as reusable within a short window. Many OIDC providers — and this is the security-*recommended* configuration for public and increasingly confidential clients — implement **refresh token rotation with reuse detection**: each refresh call consumes the current refresh token and issues a new one; a second concurrent call presenting the same (already-consumed) refresh token gets `invalid_grant`, and some providers respond to that reuse by revoking the entire token family as a compromise signal. I checked `packages/backend/src/auth/oidc-client.ts`: `refreshToken()` is a thin wrapper over `openid-client`'s `refreshTokenGrant`, with no code-level assumption either way — this is entirely a function of provider configuration, and the design does not state which configuration is assumed or verify which one is deployed.

If rotation-with-reuse-detection is in effect, the race is not benign:

- **HTTP side loses the race:** `authMiddleware`'s existing "revoked" branch (verified in `middleware.ts`) calls `request.session.destroy()` and returns 401 — a legitimate, still-authorized user is force-logged-out by a race this change introduces. Before this change there was exactly one writer per session, serialized by the request lifecycle; this change adds a second, independent writer on the same row, and that is a genuinely new failure mode, not a pre-existing one.
- **WS side loses the race:** the connection is sent a disclosed `reauth_required` and a 30-second grace timer starts on a token that was never actually invalid — and (per Finding 1) if the user reacts to that prompt by explicitly logging in, D4's check won't see it as recovered anyway.

This doesn't need distributed locking (I agree with D3 that that's disproportionate for this application's scale), but it does need: (1) explicit confirmation of whether the deployed IdP rotates refresh tokens with reuse detection — this is a one-line fact to establish, the same way D10 of the archived design named the Redis hardening assumptions explicitly rather than leaving them implicit; and (2) if it does, a cheap mitigation — e.g., the WS-side timer re-reads the session row immediately before calling the OIDC refresh and skips the call if `tokenExpiresAt` has already moved past the threshold since the timer was scheduled (catches the case where the HTTP side already won), which narrows the window without adding a lock.

## Finding 3 (Required before implementation): D9's diagnostic trace has no reachable read path — verified against the actual codebase, not assumed

Decision D9 states the `session.connection_recovered` audit event "becomes queryable through the same facilitator-role session-history/session-detail read path `content.ts` already serves — no new endpoint, no new live WS event type."

I checked this claim directly rather than accepting it: I grepped every file in `packages/backend/src` for a `SELECT`/read against the `audit_log` table. There is none. Every reference to `audit_log` in this codebase — `content.ts`, `em-views.ts`, `teams.ts`, `sessions.ts`, `facilitator-sessions.ts` — is a write (`INSERT INTO audit_log`), consistent with the archived design's own D7 correction that `audit_log` is a write-only authoritative record with no existing consumer. `content.ts`'s `GET /api/v1/teams/:teamId/sessions` handler (the endpoint D9 names) queries `sessions`, `session_topics`, and `votes` and serializes that into `FacilitatorContentView`/etc. — it has no `audit_log` join, no diagnostics field, nothing a `session.connection_recovered` row could surface through today.

This means Migration Plan step 5 ("confirm it surfaces through the existing facilitator session-history read path") is asking someone to confirm something that does not exist to confirm. Concretely, either:

- New backend work — a query against `audit_log` and a new field on an existing (or new) facilitator-facing response — is actually required, which is more scope than "no new endpoint" states and should be named as such in the Migration Plan and tasks; or
- Until that's built, the requirement text ("reaching facilitator-visible session history/diagnostics") is not met by anything this design specifies, and the diagnostic trace is, in practice, write-only data nothing exposes to a facilitator.

This isn't a request to design that read path here — same as the archived design correctly deferred Priya Nair's UX ownership rather than inventing it under pressure — but the current document should not claim the read path already exists when I can find no code that does this, and the acceptance criterion for this requirement should not be signed off against a "confirm" task that has nothing to confirm.

## Finding 4 (Worth naming, not blocking): scoping the D9 event to the SEC-26 case only reintroduces a narrower version of the disclosure it's meant to prevent

The delta spec's requirement text says the reconnect signal must be recorded "without disclosing which of the possible causes (periodic-sweep revocation, token-refresh grace-period expiry, or an ordinary network drop) produced it" — read plainly, this implies the signal should be recorded uniformly across all three causes, precisely so its presence carries no information.

Decision D9 doesn't do that. It explicitly scopes `session.connection_recovered` to the SEC-26 grace-period-recovery case only, and names the exclusion directly: "An ordinary network drop is a third, pre-existing case... but... is out of scope for this specific audit event." SEC-25 revocation closes, by construction, never get a recovery event either (a revoked user isn't expected to legitimately reconnect).

The consequence: once Finding 3's read-path gap is closed and this becomes visible to a facilitator in any form, the **presence or absence** of a `session.connection_recovered` row for a given reconnect becomes itself a distinguishing signal — "this participant's reconnect followed a token-refresh event" (row present) versus "this was an ordinary network blip" (row absent, silent). That's less sensitive than disclosing a SEC-25 revocation, and I'm not asking this be treated as equivalent to that — but it is exactly the kind of distinguishability the requirement's own scenario text rules out ("does not indicate whether the prior connection ended due to a periodic sweep, a refresh grace-period expiry, or a network drop"), and it sits in direct tension with the readiness-grid requirement two lines later in the same spec file, which insists on "one uniform treatment... no visual or data element... distinguishes which cause occurred."

If the intent is genuinely non-disclosing, the event needs to be recorded for **all three** reconnect causes uniformly (a generic "reconnect occurred," no cause field, for every deregister-then-reregister within the window) — not only for the SEC-26 case. If the SEC-26-only scoping is deliberate (e.g., because network-drop reconnects are considered out of this change's operational-visibility scope for cost reasons), the requirement text and its scenario should be narrowed to match, rather than stating a broader non-disclosure guarantee than the implementation delivers.

## Answers to the five specific questions raised

**1. Is D5 (two close codes, two modules) structurally sufficient?** For the literal question — does either mechanism ever disclose *another user's* authorization state — yes, structurally: both close codes and the `reauth_required` message are strictly keyed to `conn.userId`/`conn.sessionId` of the connection being acted on, and I traced no path where one connection's SEC-25/SEC-26 outcome touches another's signal. I specifically checked for a timing race where both timers fire near-simultaneously on the *same* connection (SEC-25 revoking while SEC-26's grace timer is independently about to expire) — whichever `.close()` call lands first wins, the second is a no-op against an already-closing socket, and I don't find a disclosure problem either order, since 4001 already discloses only "your own token," uniformly, regardless of whether SEC-25 would also have rejected the connection. One structural gap worth fixing, not a disclosure bug: the Migration Plan's `RegisteredConnection` extension (step 2) lists `sessionId`, `reauthSweepTimer`, `tokenRefreshTimer` as new fields cleared on deregister — it does not list a handle for D4's grace-period `setTimeout`. If SEC-25 deregisters a connection while a SEC-26 grace timer is independently pending, that timer isn't named as something `deregister` clears, and will later fire against an already-closed connection. Whether that's harmless depends on `ws`'s `.close()` behavior on an already-closed socket, which — per the archived design's own precedent of verifying `.send()`'s readyState behavior empirically rather than assuming — should be verified rather than assumed here too, and the timer handle should be added to the registry and cleared on deregister regardless.

**2. Does D4 introduce a new attack surface via the HTTP-level recovery reuse?** See Finding 1 above — the mechanism is broken, but it fails closed (over-closes connections, never grants access it shouldn't), so I don't classify it as an attack-surface expansion. It is not exploitable to extend access.

**3. Are D6 and D3's Risk 3 sound?** D6 (absolute lifetime untouched): yes — I verified `middleware.ts`'s existing refresh block touches only `encryptedAccessToken`/`encryptedRefreshToken`/`tokenExpiresAt`, never `sessionCreatedAt`, and D3's extraction is described as preserving that. Sound. D3's Risk 3 (the write race): not sound as written — see Finding 2. The "wasted OIDC round-trip, not an authorization gap" conclusion is correct only under an unstated assumption about the IdP's refresh-token rotation behavior.

**4. New audit-logging gaps relative to SEC-13/14 and the archived D7 pattern?** Yes, two: (a) the design specifies no audit event at all — not even the informal `logger.info` pattern `ws-event-dispatcher.ts`'s `isConnectionExpired` already uses for absolute-lifetime rejections — for a SEC-25 revocation close, despite this being at least as security-relevant as the `em.*`/`admin.*` events that do get real `audit_log` rows today; (b) it's unspecified whether the WS-side caller of the extracted `refreshSessionTokens` reproduces the HTTP side's `auth.session_invalidated` audit event on a `"revoked"`/`"transient_failure"` outcome, since that event is currently emitted adjacent to `request.session.destroy()` in the code being extracted, and the WS side has no `request.session` to destroy — the design should state explicitly what the WS-side caller does with both the audit event and the underlying Redis session row on that outcome, not leave it to be inferred from "identical audit events."

**5. Can `reauth_required`/4001 leak information about other users?** Not through the message itself (see Q1). Through the D9 audit trail once Finding 3's read gap is closed — yes, see Finding 4.

## Confirmed sound, not reopened

D1 (two independent mechanisms, no shared control flow) and D2's reuse of `evaluateSessionSubscriberAccess`/`evaluateTeamAccess` verbatim — correct, and I verified there is no third implementation of "is this user still authorized" introduced anywhere in this design. D6/D7's structural argument that in-flight vote state can't be lost because the backend never held it in the first place — verified against the SEC-16/SEC-22 exclusion already enforced in the archived change's vote-submission audit logging. D8's reveal-timing independence argument — correct; delivery-time authorization re-queries per-push with no caching, and nothing in this design gives it a reason to look at timer state on the connection object.
