## Context

`websocket-delivery-time-authorization` (archived 2026-09-07) closed the authorization gap at the moment an event is pushed: every content-access event is re-checked against the database at delivery time, no caching. Its design.md (Decision D8) named, deliberately, what it could not do — reach a connection that receives nothing. `session-lifecycle-transitions` (issue #26) removed the last reason that gap was theoretical: all four content-access events now fire from real, committed production writes, which means a facilitator sitting in a real quiet lobby with revoked access, or a participant whose token has expired mid-session, is now a live possibility, not a hypothetical the spec carried as a caveat.

This design closes that gap via two additive mechanisms — SEC-25/SEC-27 (periodic re-authorization) and SEC-26 (silent token refresh) — against the architecture the archived change already shipped: `ConnectionRegistry` (one registry, one place, both connection scopes), `evaluateSessionSubscriberAccess`/`evaluateTeamAccess` (the only authorization logic that runs against a connection, at any check point), `STALE_SIGNAL_CLOSE_CODE` (the non-disclosure guarantee for any close whose cause must not be revealed), and `authMiddleware`'s existing token-refresh/retry/revocation-distinction logic (the HTTP-side precedent for exactly the liveness problem SEC-26 has on the WS side).

Constraints inherited from the archived change and from the Internal Champion's exploration notes (repository-owner-confirmed 2026-09-09, see `exploration-notes.md`): two separate mechanisms, not one heartbeat; SEC-25 interval fixed at 5 minutes; SEC-26 grace period fixed at ~30 seconds, distinct from the backend's own ~15s automatic retry budget; in-flight client vote state must survive both mechanisms; a silent recovery must leave a facilitator-visible diagnostic trace without disclosing cause; none of the above may become an admin-configurable setting.

## Goals / Non-Goals

**Goals:**
- Close the SEC-25/SEC-27 gap: a connection whose authorization has lapsed (membership removed, EM promotion, role change) is detected and closed within a defined interval even if it receives no push.
- Implement SEC-26: keep an active WebSocket connection's underlying auth token live for up to the full 90-minute session ceiling via silent refresh, with an explicit, disclosed re-authentication prompt and grace period on failure.
- Preserve every non-disclosure guarantee the archived change established: a SEC-25 revocation close is indistinguishable from any other silent close; the SEC-26 own-token-expired signal is legitimately disclosed to that client only and never conflated with revocation.
- Preserve the 90-minute absolute connection lifetime as an untouched, separate axis.
- Preserve in-flight, composed-but-unsubmitted client vote state across both mechanisms.
- Leave a generic, non-disclosing diagnostic trace for facilitators when a connection silently recovers.
- Reuse, not re-implement: the same authorization functions, the same close-code, the same refresh/retry/revocation logic the codebase already has.

**Non-Goals:**
- Re-litigating D1–D10 of the archived design (transport, fan-out, delivery-time check placement, serializer reuse, CSWSH origin check). This is additive to that architecture.
- Designing the client-visible UX for the SEC-26 re-authentication prompt or the facilitator readiness-grid's treatment of a dropped/recovered tile. Both are named here as hard constraints on the signal's *properties* (disclosed vs. non-disclosed, uniform visual treatment) but the actual mockups are Priya Nair's (Facilitator SME) deliverable, tracked as an open question below — the same hard-gate pattern the archived change used for the staleness banner (`staleness-signal.ts`).
- A priority/role-aware re-authorization scheme for facilitator connections (shorter interval, longer grace period, etc.). Named as a deferred risk, not resolved here — see Risks.
- Any admin-facing configuration surface for the interval, the grace period, or a kill switch to disable either mechanism. Not a gap to fill later; deliberately absent, see Decision D9.
- **Retroactively adding `audit_log` rows to the pre-existing HTTP-side `auth.session_invalidated`/`auth.token_refresh_success`/`auth.token_refresh_failure` events.** Those events are `emitAuditEvent`-only (structured log, not a DB row) today, predating this change. Decisions D2 and D3b close this gap only for the *new* WS-triggered events this design adds; the HTTP-side gap is separate, unscoped work — worth its own tracking issue, not fixed here.

## Decisions

### Decision D1: Two separate mechanisms, not one combined heartbeat

**Choice:** SEC-25 and SEC-26 are implemented as two independent per-connection timers, in two separate modules, sharing no control flow.

**Rationale:** SEC-25's check is a fast, pure Postgres read — identical to what delivery-time already runs, cheap and safe to run every 5 minutes across the whole registry. SEC-26's check is potentially an OIDC round-trip with its own retry/backoff and a hard revoked-vs-transient distinction. Merging them into one loop would let a slow or degraded OIDC provider stall SEC-25's revocation-latency guarantee for every other connection on the pod. This was confirmed with the repository owner during exploration and is treated here as settled, not reopened.

**Alternative considered:** One combined interval that runs both checks per tick. Rejected for the failure-isolation reason above, and because it would force the two non-disclosure signal paths (STALE_SIGNAL_CLOSE_CODE vs. the new disclosed SEC-26 signal) to share a "send signal" function distinguished by a flag — exactly the shape that makes a wrong-flag bug possible later (named directly in exploration notes).

### Decision D2: SEC-25/SEC-27 — repeating per-connection sweep, reusing the delivery-time authorization functions verbatim

**Choice:** A new module, `packages/backend/src/realtime/connection-reauthorization.ts`, exports `scheduleReauthorizationSweep(conn, scope, id, registry)`, called from both WS route handlers in `websocket-routes.ts` at registration time, immediately after `scheduleForceClose`. It starts a `setInterval` at a fixed `REAUTHORIZATION_INTERVAL_MS = 5 * 60 * 1000` (module-local constant, not exported for override, not read from environment). Each tick calls `evaluateSessionSubscriberAccess(conn.userId, sessionId)` for session-scoped connections or `evaluateTeamAccess(conn.userId, teamId)` for team-scoped connections — the exact same functions delivery-time checks already call, with the exact same admin-path rejection rule `topic_history_update` delivery already applies for team scope. A `null` grant (or an admin-path grant on team scope) closes the socket with `STALE_SIGNAL_CLOSE_CODE`, clears the interval, and deregisters. `RegisteredConnection` gains a `reauthSweepTimer` handle, cleared on deregister the same way `forceCloseTimer` is.

**Rationale:** This is a sibling to the existing `scheduleForceClose` precedent — one timer per connection, cleared on deregister, no new authorization logic. `evaluateSessionSubscriberAccess`/`evaluateTeamAccess` already encode the dual `users.global_role` / `team_memberships.role` EM check; the sweep inherits that for free by calling the same function, which is the point — there must be no third implementation of "is this user still authorized."

**Scope — both session-scoped and team-scoped connections:** `ConnectionRegistry` already treats both connection kinds uniformly and BRD SEC-25 says "the connected client" without qualifying by type. A stale team-scoped trend-dashboard viewer is the same gap as a stale session lobby.

**Interval value — 5 minutes:** Reuses `TOKEN_REFRESH_THRESHOLD_S`'s (5 min) existing role in the codebase's mental model, well under the 1-hour fallback token-expiry assumption `middleware.ts` already uses when a provider omits `expires_in`, and cheap enough to run this often given the check is a pure Postgres read. Satisfies the adopted "≤ token expiry window" reading of SEC-25 with margin, and satisfies SEC-27 ("revocation must take effect within a defined interval") with the same number — not a second interval to source or justify separately.

**Alternative considered:** Scheduling the sweep as a single computed delay-to-next-check the way `scheduleForceClose` computes remaining time to absolute expiry. Rejected — SEC-25's check has no natural "next relevant instant" the way absolute-lifetime or token-expiry do; a flat repeating interval is simpler and matches the repository owner's confirmed framing ("a straightforward per-connection interval timer... since it's cheap").

**Added in this revision — explicit `audit_log` row on a revocation close (Security Analyst Finding 3):** a SEC-25 sweep failure is a genuine, security-relevant event — a live connection's access being cut off mid-session — and the first draft of this design let it fall into the same `emitAuditEvent`-only gap the archived change's Decision D7 already had to be corrected for once (`emitAuditEvent` is a structured-log emitter only; it is not, and was never meant to be, a substitute for an `audit_log` row — see this file's Context section). Before closing the socket, the sweep writes:

```sql
INSERT INTO audit_log (actor_user_id, actor_global_role, actor_ip, operation, team_id, metadata)
VALUES ($1, $2, NULL, 'session.access_revoked_live', $3, $4)
```
— `actor_user_id`: `conn.userId`. `actor_global_role`: resolved via `SELECT global_role FROM users WHERE id = $1`, the same pattern `facilitator-sessions.ts`/`content.ts` already use before their own inserts. `actor_ip`: `NULL` — this event fires from a background timer with no live HTTP request to source an IP from, and the column is nullable (verified against migration `8_audit_log.sql`). `team_id`: the session's team id (session-scoped) or the team id directly (team-scoped). `metadata`: `{ scope: "session" | "team", scopeId: id }` — no cause beyond "access was revoked," which is a server-side record only, never sent to the client, and does not weaken `STALE_SIGNAL_CLOSE_CODE`'s non-disclosure guarantee. `session.access_revoked_live` is a new `AuditEventName` (`audit-logger.ts`), added with the file's existing dual-write comment convention. Followed by the existing `emitAuditEvent` call as the structured-log counterpart, not a replacement for the INSERT.

### Decision D3: SEC-26 — extract `authMiddleware`'s refresh logic, drive it from a token-expiry-scheduled timer per connection

**Choice:** Extract the refresh/retry/revocation-distinction loop currently inlined in `authMiddleware` (`middleware.ts` lines ~51–123) into an exported function, `refreshSessionTokens(session: SessionData, sessionId: string, log: FastifyBaseLogger, source: "http" | "websocket"): Promise<RefreshResult>`, returning a discriminated result (`{ status: "refreshed"; session: SessionData }`, `{ status: "revoked" }`, `{ status: "transient_failure" }`, or `{ status: "no_refresh_token" }` — see below). `authMiddleware`'s `onRequest` hook calls this function; because it returns a new `SessionData` object rather than mutating its input in place, the hook now explicitly copies the returned `encryptedAccessToken`/`encryptedRefreshToken`/`tokenExpiresAt` fields back onto `request.session` on `"refreshed"`. This step is not optional plumbing: `@fastify/session`'s save-on-mutation dirty-tracking only fires when fields on `request.session` itself are assigned, not when the caller merely holds a returned object — so this is called out here as a required line in the extraction, not assumed to happen for free the way the original inline code got it implicitly. `TOKEN_REFRESH_THRESHOLD_S`, `REFRESH_RETRY_DELAY_MS`, and `REFRESH_MAX_RETRIES` become exported alongside `ABSOLUTE_LIFETIME_MS`, which already crosses this boundary for exactly the same reason. Both callers pass an explicit `source`, which `refreshSessionTokens` attaches to the `auth.token_refresh_success`/`auth.token_refresh_failure` audit events it emits (`source: "http" | "websocket"`) — the operational field needed to tell the two writers apart when reasoning about Decision D3a's race. The added `sessionId` parameter exists solely so the extracted function can reproduce the `sessionId: request.session.sessionId` field the current inline code's audit emits already include (`middleware.ts:72, 86, 111`) — `SessionData` itself carries no Fastify session id, so without this parameter the extraction would silently drop that field from every audit event it emits. `authMiddleware` passes `request.session.sessionId`; the WS caller passes `conn.fastifySessionId` — the same value Decision D3's next paragraph introduces for exactly this purpose.

`RegisteredConnection` gains a `fastifySessionId: string` field (renamed from a plain `sessionId`, which the original draft only flagged as a collision risk in prose without acting on it — this object already carries a domain-level `sessionId`, the Zoom/Health-Check session used as a `ConnectionRegistry` map key, and `conn.sessionId` next to that was a standing misread risk). It is captured from `request.session.sessionId` at registration so the WS-side mechanism can re-fetch current `SessionData` from the Redis-backed store by session id, independent of any live HTTP request object, via the store's existing `get` (`session-store.ts`'s `createRedisStore`), promisified and reused directly. Write-back does **not** reuse the store's generic `set()` — see Decision D3a.

`scheduleTokenRefreshMonitor` takes `(conn, scope, id, registry)` — the same shape as Decision D2's `scheduleReauthorizationSweep`, not `(conn, registry)` as an earlier draft had it — because the grace-period-expiry path (Decision D4) must call `registry.deregister(scope, id, conn)`, which has no signature omitting `scope`/`id`.

The per-connection timer is scheduled the same way `scheduleForceClose` computes delay from a known future instant: `tokenExpiresAt - TOKEN_REFRESH_THRESHOLD_S` seconds from now. On fire, it first re-reads current `SessionData` by `fastifySessionId` and re-checks the threshold before calling `refreshSessionTokens` — an HTTP request on the same session may already have refreshed it in the interim, and skipping an already-healthy session avoids an unconditional, redundant OIDC round-trip and refresh-token rotation every time that coincidence happens (this same re-check is also the adopted mitigation for Decision D3c's refresh-token-rotation race — see below). If already healthy, the timer reschedules against the current `tokenExpiresAt` and returns; otherwise it calls `refreshSessionTokens(session, conn.fastifySessionId, log, "websocket")`:

- On `"refreshed"`: writes the updated `SessionData` back via Decision D3a's conditional write and reschedules the next check against the new `tokenExpiresAt` — the connection never notices.
- On `"revoked"`, `"transient_failure"` (retries exhausted), **or a Decision D3a conditional-write rejection** (the session was destroyed elsewhere between this read and this write — treated identically to `"revoked"`): sends the client a disclosed `reauth_required` message (Decision D5) and starts the grace-period timer (Decision D4).
- On `"no_refresh_token"`: no-op, matching the HTTP path's existing behavior (today's inline `if (tokens.refreshToken) {...}` guard means nothing happens and the request proceeds on the existing token) — the monitor reschedules its next check at the same token-expiry-relative cadence rather than treating "no refresh token" as a failure.

**Stated invariant — one `tokenRefreshTimer` field spans three sequential phases (Engineer Finding 7):** `RegisteredConnection` gets exactly one `tokenRefreshTimer` handle, reused across the wait-for-expiry phase (this section), the grace-period phase (Decision D4), and back to a fresh wait-for-expiry phase after a successful post-grace reconnect registers. This is safe only because each phase's `setTimeout` is scheduled exclusively from inside the *previous* phase's own fire callback — never while a prior timer for the same connection is still pending — so the field is never overwritten while still holding a live handle. This is a real invariant to preserve during implementation, not an incidental detail: a future change that schedules a new phase from anywhere other than the prior phase's own callback (e.g., a retry path added later) would leak the old handle. Stated here explicitly, and as a one-line code comment at the field's declaration in `connection-registry.ts`, so it survives the extraction from this document into the implementation.

**Scope — both session-scoped and team-scoped connections:** Symmetric with Decision D2's reasoning for SEC-25 — a team-scoped dashboard viewer's token is exactly as capable of expiring mid-connection as a session-scoped participant's, and both connection kinds already share the same 90-minute absolute-lifetime bound uniformly. There is no principled reason to keep one connection kind's token alive and not the other's.

**Alternative considered:** Polling `tokenExpiresAt` on the same flat 5-minute cadence as SEC-25, rather than scheduling precisely against expiry. Rejected — token-expiry-relative scheduling directly mirrors `authMiddleware`'s own threshold check and `scheduleForceClose`'s pattern, and a flat poll would either check too late (missing the threshold window between polls) or force a much shorter, wasteful interval to compensate.

### Decision D3a: SEC-26 write-back uses a conditional, existence-gated write — a `destroy()` that runs first always wins

**Choice:** The generic `SessionStore.set()` `@fastify/session` uses (`session-store.ts`'s `set`, an unconditional `SETEX`) stays unconditional and untouched — the HTTP path depends on `set()` succeeding even when the key does not yet exist (the login callback's `regenerate()` + `save()` always writes to a brand-new key). `session-store.ts` instead exports a second, narrower function used only by the WS-side write-back: `conditionallyUpdateSession(sessionId: string, session: SessionData): Promise<boolean>`, implemented as a single atomic Redis command, `SET <key> <value> EX <ttl> XX` (ioredis: `redisClient.set(key, value, "EX", SESSION_TTL_SECONDS, "XX")`) — writes only if the key already exists, returns `false` with no write performed if it does not. Decision D3's `"refreshed"` write-back calls this instead of the generic `set()`. A `false` return means the session was destroyed by another writer (an HTTP-side `destroy()` — revocation or absolute-timeout) between this monitor's read and its write; the monitor treats this exactly as `"revoked"` (see Decision D3). It never retries the write or falls back to an unconditional `set()` — that would reproduce the exact resurrection bug this decision exists to prevent.

**Rationale:** Closes the race the Security Analyst's review identified: an unconditional `SETEX` from a stale, in-flight WS-side refresh could recreate a session key an HTTP-side `destroy()` (`DEL`) had already removed moments earlier, silently undoing a revocation. `SET ... XX` is atomic at the Redis level — there is no window between "the key still exists" and "write" for a concurrent `DEL` to land in. This guarantees `destroy()` wins permanently regardless of interleaving: if `destroy()` runs first, the WS write becomes a no-op; if the WS write runs first, `destroy()`'s unconditional `DEL` still removes it either way. Neither ordering can end in "resurrected."

**Alternative considered:** Read-verify-then-write (`GET` to confirm existence, then `SETEX`) — rejected as non-atomic; a `destroy()` could land in the gap between the verifying read and the write, reproducing the same race. Distributed locking — rejected as unnecessary; a single conditional command already provides the needed guarantee.

**Explicit scope statement (evaluated directly against the codebase, independent of what either review file discusses):** the specific ordering this decision closes is: an HTTP-side `destroy()` (`DEL`) runs to completion *before* a stale, already-in-flight WS-side write (an OIDC refresh that was already in progress when the revocation was discovered elsewhere) completes its own `SETEX`. I traced this scenario directly against `session-store.ts` and `middleware.ts` — it is real: before this decision, the WS-side write was unconditional, so a `DEL` that ran first would be silently undone by the later `SETEX`, resurrecting a destroyed session. Decision D3a's `SET ... XX` closes this specific ordering completely — a `DEL` that has already run means the key does not exist, so the later `XX` write is a guaranteed no-op regardless of how much earlier the `DEL` landed or how long the stale write had been in flight. This is a distinct race from Decision D3c below (refresh-token rotation reuse-detection): D3a is about which of two writes to the *same, still-valid* Redis key ends up persisted after a revocation; D3c is about the OIDC provider *rejecting* one of two concurrent refresh calls as invalid even though the user's session remains legitimate. Both are addressed, by different mechanisms, because they are different failure shapes.

### Decision D3b (new): WS-triggered SEC-26 revocation/exhausted-retry events also get explicit `audit_log` coverage

**Choice:** in addition to Decision D2's SEC-25 revocation-close audit write, `connection-token-refresh.ts` writes an `audit_log` row — not only the reused `emitAuditEvent` structured-log call Decision D3 already covers — when `refreshSessionTokens` returns `"revoked"`, when retries are exhausted (`"transient_failure"` after `REFRESH_MAX_RETRIES`), or when Decision D3a's conditional write is rejected (treated identically to `"revoked"`):

```sql
INSERT INTO audit_log (actor_user_id, actor_global_role, actor_ip, operation, team_id, metadata)
VALUES ($1, $2, NULL, 'session.token_refresh_failed_live', $3, $4)
```
— same field pattern as Decision D2's insert: `actor_user_id` = `conn.userId`, `actor_global_role` resolved via the standard lookup, `actor_ip` = `NULL` (background timer, no request), `team_id` from the connection's scope, `metadata: { scope, scopeId, failureType: "revoked" | "transient_failure" | "session_destroyed_concurrently" }` — no token values, ever, per SEC-16/SEC-22. `session.token_refresh_failed_live` is a new `AuditEventName`, same dual-write convention.

**Rationale:** the same gap Decision D2 closes for SEC-25, applied to SEC-26's own failure path — a WS connection's authentication definitively failing mid-session is security-relevant and should not be structured-log-only. Scoped narrowly to this *new* WS-triggered call site; the pre-existing HTTP-side `auth.token_refresh_failure`/`auth.session_invalidated` gap (also `emitAuditEvent`-only today, predating this change) is explicitly not retrofitted here — see this document's Non-Goals.

### Decision D3c (new): Refresh-token rotation reuse-detection can produce a false `"revoked"` classification under concurrent redemption — mitigated by a re-check, not eliminated, and named as a residual risk

**The problem (Security Analyst Finding 5):** Decision D3's original write-up characterized the WS-side/HTTP-side concurrent-refresh race as, at worst, "a wasted OIDC round-trip" — both writers producing valid, freshly-issued tokens. That framing silently assumes the identity provider treats a refresh token as reusable within a short window. Many OIDC providers instead implement **refresh-token rotation with reuse detection**: each refresh call consumes the current refresh token and issues a new one; a second, concurrent call presenting the same (already-consumed) refresh token gets `invalid_grant` — indistinguishable, from this codebase's error handling in `middleware.ts`, from an actual revocation. `packages/backend/src/auth/oidc-client.ts`'s `refreshToken()` is a thin wrapper over `openid-client`'s `refreshTokenGrant` with no code-level assumption either way — whether this race is possible is entirely a function of the deployed IdP's configuration, which this design does not currently state.

If the deployed IdP does rotate with reuse detection, a genuine race between the WS-side timer and an HTTP request refreshing the same session near-simultaneously means whichever call loses gets `invalid_grant` for a still-legitimate user: the HTTP side would call `request.session.destroy()` and force-log-out an active user; the WS side would send `reauth_required` and start a grace period for a token that was never actually invalid.

**Choice:** Adopt the mitigation Decision D3 already specifies for a different reason (avoiding redundant refresh calls) as the mitigation for this race too: before calling `refreshSessionTokens`, the WS-side timer re-reads current `SessionData` and re-checks it against `TOKEN_REFRESH_THRESHOLD_S`. This catches the common case — the WS-side timer was scheduled well in advance of firing, so if an HTTP-side refresh already won the race and updated `tokenExpiresAt` by the time the WS timer fires, the re-read sees the already-healthy session and skips calling `refreshSessionTokens` entirely, never presenting the now-stale refresh token to the provider at all. This narrows the race window to genuinely concurrent redemption (both sides read a still-stale session, both decide to refresh, before either has written back) — it does not eliminate that narrower window, and this design does not add distributed locking to close it further, for the same disproportionate-complexity reasoning Decision D3a's "Alternative considered" already applies to a related race.

**What is explicitly NOT resolved here, and is named as a residual risk (see Risks section) rather than silently accepted:** whether the deployed IdP actually rotates refresh tokens with reuse detection is an operational fact this design does not have and does not assume either way — verifying it, and re-assessing whether the residual concurrent-redemption window is acceptable at this application's connection volume once known, is named as a pre-implementation verification step (tasks.md Group 3), not resolved here.

### Decision D4: SEC-26 grace period — a server-side hygiene bound, not an in-place resume; recovery is carried by the client's next connection

**This decision replaces the original design's mechanism outright, not as a patch.** The Full Stack Engineer's review, confirmed directly against `packages/backend/src/routes/auth.ts` (~line 196), established that every successful OIDC login calls `request.session.regenerate()`, which allocates a brand-new session id and Redis key and never updates the old session's `SessionData` in place. The original mechanism — re-read `SessionData` for the same session id at grace-period expiry and check whether the client re-authenticated — can therefore never observe a successful re-auth: a user who completes OIDC login within the 30-second window is authenticated under a session id the grace-period check has no way to discover, because it is still looking at the old, now-orphaned one.

A second, independent fact rules out the originally-considered-and-rejected alternative ("a `reauth_complete` client-to-server WS message sent once the client's own re-auth completes") as well — not just the session-id mechanism. This application's re-authentication trigger (`AuthContext.tsx`, `AuthErrorPage.tsx`) is `window.location.href = "/auth/login"`: a full top-level page navigation to the OIDC provider and back through `/auth/callback`. That navigation tears down the page's JS execution context — and with it any open WebSocket object — before the user ever reaches the identity provider. There is no "same socket" left to send a completion message once re-login finishes, because that socket stopped existing when re-login started. Any mechanism premised on the original connection surviving through re-authentication is incompatible with how this application actually re-authenticates a user, independent of the session-id defect.

**Choice:** Accept, explicitly, that grace-period recovery is always a fresh reconnect, not a resumed connection, and design around that:

1. **The grace-period timer's only remaining job is bounding how long a connection with a known-failed token stays registered server-side** before this pod cleans it up — a hygiene/resource bound, not a recovery check. At expiry, it unconditionally closes the socket with `REAUTH_GRACE_EXPIRED_CLOSE_CODE` and deregisters — no re-read of any session state. In practice this timer rarely fires: the moment the client begins re-authenticating, the top-level navigation tears down the open connection, and the existing `socket.on("close", cleanup)` / `socket.on("error", cleanup)` handlers (`websocket-routes.ts`) already deregister it, typically well before the 30-second timer would. The timer exists for the client that never comes back, not for the client that does.
2. **Recovery is entirely carried by the new WebSocket connection the client establishes after completing re-authentication and reloading the app**, under its new session id. That registration *is* the recovery — there is nothing to re-check against the old connection, because the old connection's authorization was never in question, only its token's liveness; a freshly-authenticated connection is, definitionally, recovered.
3. **A short-lived Redis correlation marker lets the *diagnostic trail* (Decision D9) tell a grace-triggered reconnect apart from an ordinary fresh connect**, without depending on the old session id or on state local to one pod's `ConnectionRegistry`. When the grace period starts (`reauth_required` is sent), the WS monitor writes `dipstick:reauth-grace:{userId}` → `{ startedAt }` with a TTL equal to the grace period (30s), via the same shared Redis client `session-store.ts` and `auth.ts`'s own state/nonce flow already use. When any new WS connection registers (either scope) for a `userId` with a live marker, the registration handler deletes the marker (single-use) and treats this as a grace-period recovery for Decision D9. If the marker has expired or never existed, this is an ordinary connect.

**Rationale:** This gives up "silent, in-place" recovery because it was never achievable given how this application's re-authentication actually works — the original design's claim to it was unbuildable independent of the session-id defect alone. What the grace period still delivers, and does: the client is told in-band that it needs to re-authenticate (Decision D3's `reauth_required`); it is given 30 seconds of continued connection before server-side cleanup, matching BRD SEC-26's stated grace period; and a facilitator-visible diagnostic trail distinguishes this from an ordinary drop (Decision D9), without asserting a recovery guarantee the login flow cannot support.

**Security note (Security Analyst Finding 3):** the correlation marker is keyed by `userId`, read only for the `userId` the *new, already-authenticated* connection's own session resolves to — never a client-supplied identifier. A connection can only ever match its own marker; there is no lookup surface letting one user's connection probe or enumerate another user's grace-period state. A false-positive match (a coincidental fresh login by the same user within the same 30-second window, unrelated to any grace-expiry event) is possible but consequence-free: at most one extra, correctly-scoped, non-disclosing `session.connection_recovered` row in that same user's own session history — an accepted diagnostic imprecision, not a security issue.

**Note on Decision D7 (in-flight vote state):** D7's structural argument — the client's own in-memory compose state preserves the draft "exactly as it already must for an ordinary network blip" — holds for SEC-25 sweep passes and successful SEC-26 refreshes (neither ever closes the socket). It does **not** automatically hold for a SEC-26 grace-period-expiry-then-recovery, because recovery here means a full page reload (this decision), which clears in-memory JS state the same way closing the tab would — a materially different case from an ordinary network blip, which involves no page reload. This is a real gap in D7's coverage, newly surfaced by this redesign, called out here as an explicit boundary rather than left implicit: composed-but-unsubmitted vote state cannot be assumed to survive a SEC-26-triggered re-login without an explicit frontend persistence mechanism (e.g. `sessionStorage`), which is frontend-stage work outside this design's Migration Plan.

**Alternative considered:** Both alternatives named in the original write-up — re-reading the same session id, and a same-socket `reauth_complete` message — are ruled out for the reasons above, not merely deprioritized. A `userId`-keyed database lookup/scan (the Engineer review's alternative (b)) was also considered for the recovery-marker role and rejected in favor of the Redis TTL-keyed marker above: it needs no new index, self-expires without a cleanup job, and matches the shape of ephemeral, short-TTL state this codebase already keeps in Redis (`auth.ts`'s own OIDC `state`/`nonce` entries).

**Note on Engineer Finding 6 (grace-period recovery structurally unreachable for the `"revoked"` sub-case):** this finding was correct against the original mechanism (a same-session re-read could only ever observe a same-session silent refresh, never a `regenerate()`-based explicit login — meaning it silently worked for `"transient_failure"` but never for `"revoked"`, with no visible distinction between the two). It does not carry forward against this redesign: the new mechanism never attempts in-place recovery for *either* sub-case — `"revoked"` and `"transient_failure"` are both funneled into the identical grace-period-then-fresh-reconnect path (Decision D3), and recovery is uniformly "the client's next connection," regardless of which failure triggered the grace period. There is no longer a sub-case that silently behaves differently from the one the design describes.

### Decision D5: Two close codes, two modules, deliberately not unified behind one "send signal" function

**Choice:** `STALE_SIGNAL_CLOSE_CODE` (4000, existing) is the only code ever used for a SEC-25 revocation close and remains the only code for the existing subscription-rejection and absolute-lifetime paths — unchanged. A new, distinct code, `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (4001), lives in the new `connection-token-refresh.ts` module and is used only for the SEC-26 grace-period-expiry close. The two codes are sent by two different functions in two different modules; there is no shared "close with reason" helper parameterized by a disclosure flag.

**Rationale:** This is not the same kind of information. `STALE_SIGNAL_CLOSE_CODE` protects against telling a connection *why it lost access to something it wasn't entitled to know it lost* — a surveillance-adjacent leak if disclosed. SEC-26's grace-period closure is different in kind: the client was already, explicitly, told "please re-authenticate" via the `reauth_required` application-level message before the grace period even started (Decision D4) — the cause is not a secret from this client, it's a statement about that client's own token. Reusing 4000 here would not add any protection (nothing new is being disclosed — the client already knows), and would remove a debugging signal for no benefit. Keeping them as two codes, sent from two modules that do not share a parameterized helper, is the concrete implementation of the exploration notes' negative acceptance scenario: a SEC-25 revocation close must never be observably reachable through any code path that also knows how to send the SEC-26 signal.

**Alternative considered:** A single close-code enum with a `disclose: boolean` parameter threaded through one shared close helper. Rejected explicitly — exploration notes name this exact shape as the one that "makes it possible for someone to pass the wrong flag later."

### Decision D6: The 90-minute absolute lifetime is untouched by either mechanism

**Choice:** Neither the SEC-25 sweep nor a successful SEC-26 refresh writes to `RegisteredConnection.sessionCreatedAt`, and the SEC-26 refresh path's write-back to the Redis session store updates only `encryptedAccessToken`, `encryptedRefreshToken`, and `tokenExpiresAt` — the same three fields `authMiddleware`'s existing refresh already touches, never `sessionCreatedAt`.

**Rationale:** BRD SEC-26 states this outright ("must be enforced even if a valid token is present"). `authMiddleware`'s existing refresh already gets this right on the HTTP side (it never calls anything analogous to `request.session.touch()` inside the refresh branch — `touch()` is a separate, later call in the hook, extending the Redis key's sliding TTL, which is a different axis from `sessionCreatedAt`). The WS-side refresh must preserve the same separation: connection age is connection age, full stop; token liveness is an orthogonal axis this effort adds, not a replacement for the compensating bound Decision D8 of the archived design established.

### Decision D7: In-flight vote state — a structural property of what does and doesn't close the socket, not a new state-preservation mechanism

**Choice:** No server-side vote-draft storage is introduced. The backend already never receives a composed-but-unsubmitted vote value (SEC-16/SEC-22: vote values are never transmitted before lock-in) — so there is nothing for either mechanism to lose. The requirement is satisfied structurally by Decisions D2–D4: a successful SEC-25 pass and a successful SEC-26 refresh never close the socket at all. The only paths that close a connection are a genuine SEC-25 revocation, a SEC-26 grace-period expiry, or an ordinary network drop — and in every one of those cases, the client's own in-memory compose state (not tied to the socket's lifecycle) is what preserves the draft, exactly as it already must for an ordinary network blip today. This design does not add any new case where a connection is closed for a client that remains authorized and has a live token.

**Acceptance scenario (adopted, not server-side-only):** *GIVEN a participant has composed but not submitted a vote, WHEN a silent token refresh (SEC-26) or a periodic re-auth sweep (SEC-25, non-revocation case) completes on their connection, THEN the client's composed-but-unsubmitted vote value is not lost and the participant is not forced to re-enter it.* Satisfied by construction on the backend (no close occurs); the client-side requirement — don't clear compose state on socket close/reopen — is an explicit constraint this design places on the frontend implementation, not a UX decision left open.

### Decision D8: Reveal-timing independence is a stated property, not an assumed one

**Choice:** Concurrent SEC-25/SEC-26 timer state on a connection cannot introduce a seam in a `vote_revealed` push. Delivery-time authorization (`dispatchVoteRevealed` in `ws-event-dispatcher.ts`) re-checks `evaluateSessionSubscriberAccess` at the instant of push, independent of any periodic timer's current phase — a sweep or refresh mid-flight on the same connection does not gate, delay, or bypass that check. No change to `ws-event-dispatcher.ts` is needed or made by this design.

**Rationale:** Named explicitly per the exploration notes' instruction that "I assume this is fine" is not a substitute for a written, considered answer. The reasoning holds because delivery-time authorization was designed (D3 of the archived design) to be a live, per-push, per-candidate check with no caching — by construction, it cannot observe or depend on unrelated timer state on the same connection object; it only reads `conn.userId` and re-queries the database.

### Decision D9: A SEC-26 recovery leaves a diagnostic trace via the audit-log path, surfaced through a new facilitator-scoped read query — not a new live UI signal

**Choice:** When a new WS connection registers (session-scoped or team-scoped) and a live Decision D4 correlation marker (`dipstick:reauth-grace:{userId}`) exists for that connection's `userId` — i.e., this registration follows a SEC-26 grace period that was started, not a fresh, unrelated connect — the registration handler deletes the marker and writes:

```sql
INSERT INTO audit_log (actor_user_id, actor_global_role, actor_ip, operation, team_id, metadata)
VALUES ($1, $2, NULL, 'session.connection_recovered', $3, $4)
```
— **stated explicitly here, not gestured at, per the archived design's own Decision D7 having already been corrected once for exactly this "gestures at the pattern instead of stating the INSERT" gap.** `actor_user_id`: `conn.userId`. `actor_global_role`: resolved via the standard `SELECT global_role FROM users WHERE id = $1` lookup. `actor_ip`: `NULL` — this fires from the registration handler processing a WS upgrade, not from a context this design threads an IP through; nullable column, stated explicitly rather than left for an implementer to guess whether it's required. `team_id`: the session's team id (session-scoped) or the team id directly (team-scoped). `metadata: { scope: "session" | "team", scopeId: id }` — no other fields, no cause, no token detail. Followed by `emitAuditEvent(log, "session.connection_recovered", fields)` as the structured-log counterpart, per the file's existing convention — not a replacement for the INSERT above. `session.connection_recovered` is added to `AuditEventName` (`audit-logger.ts`) with the file's standard dual-write comment. This mechanism replaces the original design's `(userId, sessionId)`-pair-matched-against-`ConnectionRegistry`-history approach, which the Full Stack Engineer's review correctly identified as broken twice over: the old session id is never the one a real re-auth reconnects under (the same `regenerate()` fact Decision D4 addresses), and `ConnectionRegistry` holds no history of past deregistrations and would not span pods even if it did. The Decision D4 marker is Redis-backed and therefore correct across pods — the common case, since a reconnect commonly lands on a different pod behind the load balancer than the one that saw the grace period start.

This becomes queryable through the facilitator-role session-history/session-detail surface `content.ts` serves, but — correcting the original wording — this is **not** already-existing plumbing. `content.ts`'s facilitator-serving queries today read `sessions`/`session_topics`/`votes`, not `audit_log`; there is currently no `SELECT ... FROM audit_log` anywhere in the codebase (only `INSERT` call sites). Making this queryable means adding a new read query to `content.ts` and extending its response shape — real, scoped implementation work this Migration Plan now names explicitly (see below), not reused infrastructure.

**Non-disclosure guard on the new query, stated explicitly so it isn't discovered as a gap later:** this design also adds two other `audit_log` operations this change writes — `session.access_revoked_live` (Decision D2) and `session.token_refresh_failed_live` (Decision D3b) — into the same table. Neither is facilitator-visible; both exist for server-side security record-keeping only, and disclosing either would directly violate `STALE_SIGNAL_CLOSE_CODE`'s non-disclosure guarantee (a SEC-25 revocation cause) or unnecessarily expose a participant's authentication-failure detail. The new `content.ts` query this decision requires **must filter explicitly to `operation = 'session.connection_recovered'`** — never a wildcard or prefix match across `session.*` — so an implementer building "the facilitator session-history query" doesn't inadvertently join in the other two operations this same change introduces into the same table.

**Rationale:** BRD requires this reach "facilitator-visible session history/diagnostics" without requiring it be instantaneous or on-screen mid-session. Persisting it into the audit trail, readable via a facilitator-scoped history query, satisfies the requirement without adding a new piece of live UI chrome — consistent with the concern (Internal Champion's, standing) that the application should disappear into the background once a session is underway, not accumulate notification surface area with every infrastructure addition. A live, in-the-moment indicator on the readiness grid is left as an option for Priya Nair to pursue with mockups, not built here.

**Accepted trade-off (Security Analyst Finding 2 — naming the disclosure asymmetry as deliberate):** This event creates a mild, intentional asymmetry: an ordinary network drop leaves no trace, while a SEC-26 grace-period recovery leaves a permanent, facilitator-visible record tied to that specific participant's session history. Accepted because it delivers exactly the diagnostic value BRD SEC-26 asks for — letting a facilitator distinguish "this participant's token needed re-authentication" from ordinary session noise — while the event's own fields (`userId`, `sessionId`, nothing else) disclose only that a recovery happened, never *why* the token needed re-authentication (revoked vs. expired vs. transient failure remain indistinguishable from this event alone), preserving the non-disclosure boundary Decision D5 draws. This is a considered product/privacy call, not a scope gap being waved through.

**Scope note:** SEC-25 non-revocation sweep passes never close the connection (Decision D2), so there is nothing to "recover" from on that path — the diagnostic trace applies to the SEC-26 grace-period-recovery case specifically, which is the only mechanism this change adds that can legitimately close and reopen a still-authorized connection. An ordinary network drop is a third, pre-existing case (named in exploration notes for the readiness-grid's *visual* uniformity) but is not a SEC-25/SEC-26 mechanism this change owns, and is out of scope for this specific audit event.

**Alternative considered:** Emitting the trace as a live `session_state_change`-style WS push to the facilitator's own connection at the moment of recovery. Rejected for this pass — it would be a new client-visible signal needing its own UX review (the same gate the SEC-26 prompt itself needs), and the BRD's own wording ("session history or facilitator-visible diagnostics") is satisfied by the persisted, queryable form without that additional surface.

### Decision D9a: No interval, grace period, or mechanism-disable setting is exposed anywhere — including as an operational kill switch

**Choice:** `REAUTHORIZATION_INTERVAL_MS`, `TOKEN_REFRESH_THRESHOLD_S`, `REFRESH_RETRY_DELAY_MS`, `REFRESH_MAX_RETRIES`, and the 30-second grace period are all module-local or already-existing constants. None are read from environment variables, feature flags, or any admin-facing setting. There is deliberately no runtime toggle to disable either mechanism.

**Rationale:** Restated from exploration notes and applied here as a binding decision, not a preference: "the moment a re-authorization interval is exposed as something an administrator can tune, someone will eventually tune it to 'basically never.'" This applies equally to a well-intentioned operational kill switch — a flag meant only for incident rollback has a way of becoming the thing someone reaches for under a different kind of pressure. Rollback for this change is a standard code deploy rollback (Migration Plan, below), not a runtime flag.

## Risks / Trade-offs

- **[Risk] A facilitator's connection has a strictly higher blast radius than a participant's — losing it can stall the whole room, not cost one voter — and this design applies the identical interval, threshold, and grace period to both.** → **Mitigation:** Deliberately not resolved by inventing a role-aware timer in this pass (Decision D9a's reasoning applies equally to a per-role special case — it is itself a new place a future admin-configurability request could attach). Tracked as an explicit open question for a follow-on decision if production data shows this is a real, recurring problem, rather than pre-optimizing against a scenario that has not yet been observed.
- **[Risk] Extracting `authMiddleware`'s refresh loop into a shared function changes a code path every authenticated HTTP request already exercises.** → **Mitigation:** The extraction (Decision D3) preserves identical control flow, retry/backoff/revocation-distinction behavior, and audit events — the one new step, the explicit copy-back of `refreshSessionTokens`'s returned fields onto `request.session`, is named as a required line in the extraction (not assumed to happen implicitly, the way the original inline code got it for free) specifically so this doesn't silently regress HTTP-side persistence. Requires full existing `middleware.ts` test coverage to pass unmodified before this change is considered complete, plus new tests for the WS call site and the copy-back step itself.
- **[Risk — resolved by Decision D3a, not accepted as-is] The SEC-26 write-back to the Redis session store from a WS-side timer, running concurrently with a possible HTTP-side revocation or destroy, is a write race that did not previously exist (HTTP-only refresh had only one writer per session at a time, gated by the request lifecycle).** → This was originally assessed as "at worst a wasted OIDC round-trip" — that assessment was wrong. The Security Analyst's review traced the actual worst case: an unconditional `SETEX` from a stale, in-flight WS-side refresh can recreate a session key an HTTP-side `destroy()` has already deleted, silently resurrecting a session Postgres/the identity provider considers revoked — the exact class of gap SEC-25/26/27 exist to close, not reopen. **Mitigation:** Decision D3a — the WS-side write-back uses a conditional, existence-gated write (`SET ... XX`), never an unconditional `SETEX`; a `destroy()` that ran first always wins permanently, regardless of interleaving. This is a hard ordering guarantee that must be implemented alongside Group 1/Group 3 of tasks.md, not an accepted narrow race documented after the fact.
- **[Risk] A rolling deploy leaves pre-deploy connections in pods running old code without the new timers until they reconnect.** → **Mitigation:** `ConnectionRegistry` is already documented as per-pod, in-process, non-migratable — this is the existing operational model, not a new gap. Those connections remain bounded by the already-enforced 90-minute absolute lifetime regardless.
- **[Risk] SEC-25's sweep and SEC-26's grace-period expiry are fully independent timers (Decision D1) that could both decide to close the same connection at nearly the same moment.** → **Mitigation:** `ConnectionRegistry.deregister()` (`connection-registry.ts`) removes a connection from a `Set` by object identity; deregistering a connection already absent from the set is a no-op (`if (!set) return`, and `Set.delete()` on a value no longer present is itself a no-op) — so a second `deregister()` call for the same connection is safe. Closing a `ws` socket that is already closing/closed is likewise a documented no-op at the `ws` library level. Both close paths are therefore safe to race in either order without an explicit guard between the two modules. This should not be taken on faith: tasks.md's Group 4 negative-acceptance scenario is extended to assert a double-close/double-deregister on the same connection produces no error, no duplicate close-code send, and no duplicate audit write.
- **[Risk, residual — Decision D3c] If the deployed IdP rotates refresh tokens with reuse detection, a genuinely concurrent redemption of the same refresh token by the WS-side timer and an HTTP request on the same session can produce a false `"revoked"` classification for a still-legitimate user** — force-logging out an active HTTP request, or sending a WS connection an unnecessary `reauth_required` and grace period. → **Mitigation:** Decision D3c's re-check-before-refresh narrows the window (the common case, where one side already won before the other fires, is caught and skipped entirely) but does not eliminate genuinely simultaneous redemption. Not closed with a lock, for the same proportionality reasoning as D3a. Whether the deployed IdP's configuration makes this window practically reachable at this application's scale is an open operational fact to verify before/during implementation (tasks.md Group 3), not resolved by this document.

## Migration Plan

1. Extract `refreshSessionTokens` (now taking an explicit `sessionId: string` for audit parity and `source: "http" | "websocket"`) from `authMiddleware` in `middleware.ts`; export it and the three refresh-related constants alongside `ABSOLUTE_LIFETIME_MS`. Update `authMiddleware`'s call site to copy the returned `SessionData` fields back onto `request.session` (Decision D3). Add `conditionallyUpdateSession` to `session-store.ts` (Decision D3a). Verify existing `middleware.ts` test suite passes unmodified.
2. Extend `RegisteredConnection` (`connection-registry.ts`) with `fastifySessionId`, `reauthSweepTimer`, and `tokenRefreshTimer`; extend `deregister` to clear all three timer handles (not just `forceCloseTimer`).
3. Implement `connection-reauthorization.ts` (SEC-25/SEC-27), including the `session.access_revoked_live` audit_log write (Decision D2); wire `scheduleReauthorizationSweep` into both route handlers in `websocket-routes.ts`, alongside the existing `scheduleForceClose` call.
4. Implement `connection-token-refresh.ts` (SEC-26) with signature `scheduleTokenRefreshMonitor(conn, scope, id, registry)`, including the new `REAUTH_GRACE_EXPIRED_CLOSE_CODE`, the `reauth_required` `WsClientMessage` variant (add to `packages/shared/src/types/realtime.ts`), the `session.token_refresh_failed_live` audit_log write (Decision D3b), and the Decision D4 Redis correlation marker (`dipstick:reauth-grace:{userId}`) written on grace-period start and consumed at registration time. The grace-period timer itself performs no re-read of session state (Decision D4) — it unconditionally closes on expiry. Include the re-check-before-refresh step (Decision D3c) and, before this group is considered complete, confirm with whoever owns the OIDC provider configuration whether refresh tokens are issued with rotation and reuse detection — record the answer in this directory (not just in a task checkbox) since Decision D3c's residual-risk assessment depends on it. Wire `scheduleTokenRefreshMonitor` into both route handlers.
5. Add `session.access_revoked_live`, `session.token_refresh_failed_live`, and `session.connection_recovered` to `AuditEventName` (`audit-logger.ts`); add the marker-based recovery-detection check at registration time (Decision D4/D9) including its `audit_log` write; add a new read query and response-shape extension to `content.ts`'s facilitator session-history path for `session.connection_recovered` — this is new query logic, not existing plumbing (Decision D9).
6. New capability spec (`websocket-connection-reauthorization`); correct its "reconnect... recorded without cause" scenario to the SEC-26-recovery-only scope (Decision D9's scope note) rather than the three-way framing the first draft carried over unreviewed.

**Rollback:** Standard code-level rollback (revert the deploy). No feature flag exists to disable either mechanism independently (Decision D9a) — this is deliberate, not an oversight to fix later.
