## 4. SEC-26 Grace Period — Hygiene Bound, Not In-Place Recovery

**Depends on: Groups 1, 2, 3 (task 4.5 exercises the Group 2 SEC-25 sweep close path directly). The grace timer is a server-side cleanup bound; recovery is carried entirely by the client's next (fresh) connection (design.md Decision D4 — rebuilt after review found the original re-read-same-session-id mechanism unbuildable: `auth.ts`'s `/auth/callback` calls `request.session.regenerate()` on every login, and this application's re-authentication is a full top-level page navigation that tears down any open WebSocket before the identity provider is even reached — there is no "same connection" left to recover in place.**

- [x] 4.1 Add `REAUTH_GRACE_EXPIRED_CLOSE_CODE = 4001` in `connection-token-refresh.ts` — new, distinct, never reused by `connection-reauthorization.ts` or `staleness-signal.ts`.
- [x] 4.2 On grace-period start (task 3.4): write `dipstick:reauth-grace:{userId}` → `{ startedAt }` to Redis with TTL = the grace-period constant, via the same shared client `session-store.ts`/`auth.ts`'s OIDC state/nonce flow already use. Start a single `setTimeout` for the grace-period constant (task 3.1). No poll loop, no client-to-server control message.
- [x] 4.3 On grace-timer fire: **unconditionally** close with `REAUTH_GRACE_EXPIRED_CLOSE_CODE` and deregister — no re-read of any session state. Expected to rarely fire in practice: a client beginning re-authentication tears down the connection via the top-level navigation, and the existing `socket.on("close"/"error", cleanup)` handlers already deregister it, typically before this timer would.
- [x] 4.4 At WS registration time (both route handlers, either scope): check for a live `dipstick:reauth-grace:{userId}` marker for the connecting user. If present, delete it (single-use) and hand off to Group 5 for the `session.connection_recovered` audit write. If absent/expired, ordinary connect, no special handling. Added to both route handlers in `websocket-routes.ts`, alongside the existing `scheduleForceClose`/`scheduleReauthorizationSweep`/`scheduleTokenRefreshMonitor` registration-time calls. **Coordination note:** 4.4 and 5.1 describe one atomic registration-time sequence (marker detection/consumption, then the audit write for a marker match) split across two groups at the same call site in the same file. If picked up by different people, coordinate rather than treating them as independently schedulable — 4.4 landing without 5.1 produces working code that silently drops the audit trail for every recovery, not an obvious failure.
- [x] 4.5 Negative acceptance scenario (Decision D5): a connection closed via the SEC-25 sweep path (Group 2) receives `STALE_SIGNAL_CLOSE_CODE` and **no** `reauth_required` message, sent-then-withdrawn or otherwise observable — and no code path calls both `connection-reauthorization.ts`'s close and `connection-token-refresh.ts`'s signal for the same closure.
- [x] 4.6 Positive mirror scenario: a connection closed via grace-expiry (task 4.3) received `reauth_required` before the close, used `REAUTH_GRACE_EXPIRED_CLOSE_CODE` (never `STALE_SIGNAL_CLOSE_CODE`).
- [x] 4.7 Recovery scenario: a marker is written (task 4.2), a new connection registers for the same `userId` within the TTL window, and the marker is consumed exactly once — a second registration does not find a stale marker.
- [x] 4.8 Security-boundary test (Decision D4's security note): a connection cannot resolve or be affected by another user's marker — lookup is keyed strictly by the *new, already-authenticated* connection's own resolved `userId`, never a client-supplied identifier.
