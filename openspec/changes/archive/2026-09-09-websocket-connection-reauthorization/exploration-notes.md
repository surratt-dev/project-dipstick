# Exploration Notes: websocket-connection-reauthorization (SEC-25/SEC-26)

**Author:** Devon Calloway (Internal Champion / SME), explore stage, GitHub issue #27.

## What this is, and what it isn't

Issue #27 is the companion effort `websocket-delivery-time-authorization` (archived 2026-09-07) deliberately spun off rather than absorbed under time pressure — Decision D8 of that change's design.md names it directly. That change closed the delivery-time authorization window: once an event is pushed, the recipient's authorization is re-checked against the database at that instant, no caching, no exceptions. What it structurally cannot do is reach a connection that receives nothing. A facilitator sitting in a quiet pre-session lobby, or a participant who has voted and is just waiting for the reveal, can have their `team_memberships.removed_at` set, or their OIDC token expire, and nothing in the shipped system will notice until — or unless — an event happens to fire at them. That's SEC-25 (BRD line 596: re-authorize "at meaningful intervals, no less frequent than once per token expiry window") and SEC-26 (BRD line 598: token expiry/silent-refresh mid-connection, up to the 90-minute session ceiling, without interrupting the participant).

I want to be precise about scope going in, because the archived change's design.md is unusually disciplined about not letting adjacent problems bleed into a document that doesn't own them, and I intend to hold this one to the same standard:

- Not re-litigating D1–D10 of the archived design (transport, fan-out, delivery-time check placement, serializer reuse, audit logging, the CSWSH origin check, Redis hardening). Those are settled, built, and now firing from real production triggers as of `session-lifecycle-transitions` (issue #26 resolved — the spec's front-matter note now says so). This effort is additive to that architecture, not a redesign of it.
- Not choosing between "one combined heartbeat" and "two separate mechanisms" here — that's explicitly named as Design-stage work in the issue and in D8. I'll lay out the tradeoff below so whoever writes design.md isn't starting cold, but I'm not deciding it in this document.
- Not designing the client-visible UX for token-expiry re-authentication. That's a distinct signal from the existing staleness banner (see below) and belongs with Priya Nair the same way the generic staleness signal did.

## Grounded in what's actually built today

I read the current state of `packages/backend/src/realtime/` and `src/auth/middleware.ts` rather than working from the archived design's description of what it intended to build — the two mostly agree, but a few things are worth naming precisely because they change what "reuse" means for this effort:

- **`ConnectionRegistry` (`connection-registry.ts`) is genuinely one registry, one place.** Every socket — session-scoped and team-scoped — is a `RegisteredConnection` holding `socket`, `userId`, `sessionCreatedAt`, and a `forceCloseTimer`. There's already exactly one scheduled-closure precedent in this codebase (`scheduleForceClose` in `websocket-routes.ts`, wired to `ABSOLUTE_LIFETIME_MS`). A periodic SEC-25 sweep is a *sibling* to that pattern, not a new idea — reuse the registry, reuse the "one timer per connection, cleared on deregister" shape.
- **The registry does not currently hold what SEC-26 needs.** `RegisteredConnection` has no reference to the Fastify session id, the token expiry timestamp, or the refresh token. Token refresh lives entirely in `authMiddleware`'s `onRequest` hook (`middleware.ts`), which operates on `request.session` — a live HTTP request object a long-lived WS connection doesn't have. Extending `RegisteredConnection` with a session-id reference (so the mechanism can re-fetch current `SessionData` from the Redis-backed store — `session-store.ts`, keyed `dipstick:session:<id>`) is additive to the existing registry, and is the reuse the issue text is asking for, not a second tracking mechanism.
- **`STALE_SIGNAL_CLOSE_CODE` (4000) is a hard constraint, not a convenience.** `staleness-signal.ts` is explicit: every server-initiated close whose cause must not be disclosed — subscription rejection, the 90-minute force-close — uses the identical code, specifically so a client can't distinguish "you were revoked" from "you aged out" from "the network blipped." Any SEC-25 revocation-triggered close **must** reuse this code. If it doesn't, this effort quietly reopens the exact disclosure gap the archived change closed, one document later. I consider this load-bearing in the same way the no-manager rule is load-bearing elsewhere in this project: not a style preference, a guarantee.
- **`isConnectionExpired` / `isPastAbsoluteLifetime` already run on every delivery-time push**, checking `sessionCreatedAt` against `ABSOLUTE_LIFETIME_MS` before the event-specific grant check. This is the *compensating bound*, not SEC-25 itself — it catches total connection age, not a mid-window membership change. Nothing about this effort should touch that check's semantics; SEC-25's job is to close the gap *inside* the 90-minute window that this bound doesn't reach.
- **`evaluateSessionSubscriberAccess` and `evaluateTeamAccess` are the only authorization logic that should ever run against a connection, at any check point.** Delivery-time already calls these verbatim per candidate, per push. A periodic re-auth sweep is the same call, on a timer instead of on a push. There should be no third implementation of "is this user still authorized for this session/team." I'd flag it hard in review if I saw one.
- **The periodic sweep must re-derive EM status from both `users.global_role` and `team_memberships.role`, independently, exactly as the delivery-time check does.** This is not new scope — `evaluateSessionSubscriberAccess`/`evaluateTeamAccess` already encode this dual-signal check, per the shipped SEC-25 spec requirement (`openspec/specs/websocket-session-authorization/spec.md`, lines 109–131, 235) — but it needs to be named here, not just implied by "reuse the existing functions," because I described this mechanism as a *membership* re-check throughout an earlier draft of these notes and never said "role" once. That's exactly the kind of narrowing that produces a periodic-sweep test suite covering `removed_at` and never covering an EM-promotion-mid-connection scenario. Whoever writes acceptance scenarios needs both: a removed-membership case and an EM-promotion case, sourced from `global_role` alone and from `team_memberships.role` alone.
- **The periodic sweep is in scope for both session-scoped and team-scoped connections in the registry.** A stale team-scoped dashboard viewer — someone watching the trend dashboard after their team membership lapsed — is the same SEC-25 gap as a stale session lobby, not a separate concern. BRD SEC-25 says "the connected client" without qualifying by connection type, and `ConnectionRegistry` already treats both connection kinds uniformly; there's no principled reason for the sweep to only cover one.

## The core design tension, named but not resolved

SEC-25 (membership/role re-check) and SEC-26 (token liveness) sound like the same shape of problem — "periodically confirm this connection is still good" — and the issue itself asks whether they should be one heartbeat or two. I don't think that's a coin flip; the two checks have different blast radii and different failure semantics, and whoever designs this should reckon with the asymmetry rather than default to "obviously one loop":

- **SEC-25's check is a fast, pure read** against Postgres, identical to what already runs on every delivery-time push. Cheap, safe to run frequently, safe to run concurrently across the whole registry (the existing `Promise.all` pattern in `ws-event-dispatcher.ts` is the precedent).
- **SEC-26's check is potentially an OIDC round-trip with retries** — `authMiddleware`'s existing refresh logic has a retry loop and a `REFRESH_RETRY_DELAY_MS` backoff for transient failures, and a hard distinction between "revoked" (`invalid_grant` — kill the session now) and "transient" (retry, then kill if exhausted). That is not a check you want gating hundreds of session-scoped membership checks behind a slow or degraded identity provider. If these get merged into one interval loop, a slow OIDC provider shouldn't be able to stall SEC-25's revocation-latency guarantee for every other connection on the pod.

My instinct, not a decision: SEC-25 can piggyback on a straightforward per-connection interval timer (much like `scheduleForceClose`, but repeating) since it's cheap and matches how the rest of this codebase already treats per-connection timers. SEC-26 probably wants its own path — closer in spirit to `authMiddleware`'s existing refresh flow than to a lightweight poll — because it mutates session state (writes new encrypted tokens back to the Redis session store) and needs the same revoked-vs-transient handling `middleware.ts` already has, and duplicating that distinction badly here would be worse than not sharing a loop. Whoever designs this should treat "one mechanism vs. two" as a question about failure isolation and existing-code reuse, not just code volume.

## Where this touches the ritual directly

This is the part I actually care about most, and it's the reason I want to be consulted on this one rather than let it get waved through as "just infrastructure":

- **BRD SEC-26 itself protects the felt experience of the ritual, not just the security posture.** "Silent refresh... to maintain the connection for the full session duration without user interruption" is, in plain terms, a requirement that nobody gets kicked out of a Health Check session mid-vote because a token happened to expire at an inconvenient moment. A facilitator losing their live connection during a reveal, or a participant getting silently dropped right as they're about to lock in a vote, is exactly the kind of software-shaped friction that makes the ritual feel like a tool being run on people instead of a conversation they're having. Get the silent-refresh path right and nobody ever notices this effort shipped. Get it wrong and it's the first thing a team complains about.
- **The interval choice for SEC-25 needs to not become visible chatter.** I don't have a number to put on it — BRD only says "no less frequent than once per token expiry window" — but whatever's chosen should not itself introduce reconnect flicker or observable interruption on an authorized, healthy connection. The only participant who should ever notice this mechanism running is one whose access was actually revoked, and even then the experience should be the same silent no-more-events-then-close pattern the archived change already established, not a new distinguishable behavior.
- **Two different kinds of "telling the client something" are in play here, and they must not get conflated.** The archived change's non-disclosure principle (STALE_SIGNAL_CLOSE_CODE, the reveal-cause-silence pattern) exists specifically so a *revoked* connection never learns why it lost access — that's a surveillance-adjacent leak if disclosed. SEC-26, by contrast, explicitly *requires* telling a client "please re-authenticate" when silent refresh fails — but that's a statement about the client's own token, not about another user's membership status, and disclosing it isn't a ritual-integrity problem the way disclosing revocation cause is. Design needs to draw that line explicitly so an implementer doesn't either (a) over-apply non-disclosure and leave a legitimately-expired user stuck with no signal, or (b) under-apply it and let a revocation start looking distinguishable from an ordinary re-auth prompt.
- **A successful token refresh must not reset the 90-minute absolute-lifetime clock.** BRD SEC-26 says this outright ("must be enforced even if a valid token is present"), and it would be an easy, plausible-looking bug to write a refresh path that touches `sessionCreatedAt` the way `request.session.touch()` extends the sliding TTL on the HTTP side. The WS connection's absolute lifetime is connection age, full stop — token liveness is a separate axis this effort adds, not a replacement for that bound.
- **Don't let the interval, or the grace period BRD SEC-26 names for re-auth, become an admin-configurable setting.** Same principle I'd apply to the no-manager rule or the facilitator-from-another-team requirement: the moment a re-authorization interval is exposed as something an administrator can tune, someone will eventually tune it to "basically never," and the whole point of closing this gap evaporates quietly, with no single moment where anyone decided to weaken it.
- **The non-disclosure principle doesn't stop at the wire protocol — it has to hold on the facilitator's readiness grid too.** Priya Nair flagged this in review and she's right that I only reasoned about it from the closed-connection client's point of view. A connection can leave the registry for three different reasons — a SEC-25 revocation sweep, a SEC-26 refresh that failed past its grace period, or an ordinary network drop — and `STALE_SIGNAL_CLOSE_CODE` already guarantees the *departing client* can't tell which. But if the facilitator's own screen renders those three cases with any visible difference — the tile vanishes instantly versus greys out versus shows a distinct "reconnecting" state — then the room has been told something about *why* that person is gone, which is the same disclosure this project has already decided is unacceptable, just routed through a different screen. Design needs to specify one uniform on-screen treatment for "this participant's connection is no longer live," with no visual branch on cause. I'm naming the requirement, not the specific UI — that's Priya's call with mockups, same as the SEC-26 re-auth signal.
- **Whether the re-authorization timers can ever coincide with an active reveal broadcast has to be an explicit, written answer, not an assumed one.** Reveal simultaneity is the property the facilitator evaluates everything else against. My working assumption is that this is a non-issue, because delivery-time authorization already re-checks access at the instant the reveal event is pushed, independent of whatever periodic timer state a connection happens to be in — a SEC-25 sweep or SEC-26 refresh running concurrently shouldn't be able to introduce a seam in a push that's separately gated. But "I assume this is fine" is not the same as design.md stating it's fine and why. This needs to be written down as considered, with the reasoning, so nobody has to re-derive it under time pressure later.
- **A facilitator's connection has a different blast radius than a participant's, and I'm naming it here without resolving it.** Priya flagged this and she's right that nothing above addresses it: pacing is entirely facilitator-controlled — nobody else can advance a topic or trigger a reveal — so a facilitator losing their connection to a SEC-25 revocation, a SEC-26 grace-period expiry, or an ordinary drop doesn't cost the room one voter, it can stall the whole session. Whether that argues for a shorter re-auth interval, an earlier refresh attempt, or a longer grace period specifically for facilitator-role connections is a real question I don't have the standing to answer in an exploration doc — it trades off against the "don't let the interval become admin-configurable, don't let it become per-role special-cased into meaninglessness" instinct two bullets up. I'm marking this considered-and-deferred to Design rather than silently dropping it, per Priya's ask.
- **Whether a silent SEC-25/SEC-26 recovery leaves any trace for facilitator diagnostics is an open, not a closed, question.** Priya asked this directly: if a connection drops and silently recovers mid-session, she doesn't need to know *why* (that stays non-disclosed, correctly), but she may want to know a hiccup happened at all, so a team's later "why did the app glitch last time" doesn't catch her flat-footed. I don't think this is a hard requirement, but it shouldn't be a silent omission either — Design should make an explicit call on whether any reconnect-occurred signal reaches session history or the facilitator's own diagnostics, distinct from the never-disclosed cause.

## Decisions made during exploration (repository owner confirmed, 2026-09-09)

The open questions below split into two groups: numeric/mechanism choices the repository owner was able to confirm directly during exploration review, and UX/implementation-detail questions that genuinely need Design-stage work (client mockups, code structure) and stay open for whoever picks that up. Recording the confirmed ones here, at decision tier, so Propose and Design don't re-litigate them:

- **Two separate mechanisms, not one combined heartbeat.** SEC-25 gets a cheap, frequent per-connection interval timer (sibling to `scheduleForceClose`) running a pure DB read via `evaluateSessionSubscriberAccess`/`evaluateTeamAccess`. SEC-26 gets its own path modeled on `authMiddleware`'s existing refresh/retry/revocation-distinction logic. Reasoning stands as originally argued: a slow or degraded OIDC provider must not be able to stall SEC-25's revocation-latency guarantee for every other connection on the pod.
- **SEC-25 re-authorization interval: every 5 minutes.** Reuses the existing `TOKEN_REFRESH_THRESHOLD_S` (5 min) constant's role in the codebase's mental model, well under any realistic OIDC token-expiry window (confirmed: `middleware.ts` falls back to a 3600s/1hr assumption when the provider doesn't specify `expires_in`), and cheap enough to run this often given the check is a pure Postgres read identical to the delivery-time path. Satisfies the adopted "≤ window duration" reading of BRD SEC-25 with margin. Also satisfies SEC-27 ("access revocation must take effect on active WebSocket connections within a defined interval") — same interval, not a second number to source.
- **SEC-26 grace period: ~30 seconds, distinct from the backend's automatic retry budget.** `REFRESH_RETRY_DELAY_MS` (5000ms) × `REFRESH_MAX_RETRIES` (2) — roughly 15s — governs the backend's own silent, automatic refresh retries before giving up and notifying the client. BRD's "defined grace period... if the client does not complete re-authentication" is a distinct, additional window: time given to the *client* to complete its own re-auth flow after being notified silent refresh failed. These are not the same number reused; Design should implement them as two separate timers even though both derive from the same failure path.
- **In-flight client vote state: the acceptance scenario in the section below is adopted, not the server-side-only reading.** *GIVEN a participant has composed but not submitted a vote, WHEN a silent token refresh (SEC-26) or a periodic re-auth sweep (SEC-25, non-revocation case) completes on their connection, THEN the client's composed-but-unsubmitted vote value is not lost and the participant is not forced to re-enter it.* This is now a firm acceptance condition for tasks.md, not an open question.
- **A silent SEC-25/SEC-26 reconnect must leave a diagnostic trace for facilitators.** Not "user X was revoked" — that stays non-disclosed, correctly — but a generic "a reconnect occurred" signal should reach session history or facilitator-visible diagnostics, so a facilitator isn't caught flat-footed if a team later asks about a hiccup they noticed. Design owns exactly where this surfaces (session history entry vs. a dedicated diagnostics view); the decision that it must surface *somewhere* facilitator-visible is made.

## Decisions to make explicitly at Design stage, not leave open

Marcus's review is right that these were originally open questions wearing decisions' clothing. The in-flight-vote-state and diagnostic-trace decisions above have since been confirmed (previous section); the disclosure/non-disclosure negative scenario below still needs Design to specify the *implementation* that satisfies it:

- **The disclosure/non-disclosure line needs a testable negative scenario, not just the principle.** I've already stated the principle above (SEC-25 revocation stays indistinguishable via `STALE_SIGNAL_CLOSE_CODE`; SEC-26's own-token-expired signal is legitimately disclosed to that client only). Design.md needs to state the constraint on whatever Priya designs for the SEC-26 signal: the two code paths must not share a single "send signal" function that both closes call into with a flag distinguishing cause, because that shape makes it possible for someone to pass the wrong flag later. And it needs this as an explicit acceptance scenario: *GIVEN a connection is closed because a SEC-25 sweep revoked the user's access, THEN the client receives `STALE_SIGNAL_CLOSE_CODE` (4000) and nothing else — no SEC-26 re-auth-required signal is sent, sent-then-withdrawn, or otherwise observable on this path.*

## Open questions for whoever picks up Design

Genuinely UX/implementation-detail questions — not resolvable without client mockups or code-structure decisions, so they stay open rather than get a number invented for them:

1. Does the SEC-26 "notify the client that re-authentication is required" signal reuse any part of the existing staleness-signal client work, or does it need its own Facilitator-SME-reviewed UX, given it's a legitimately-disclosed signal rather than a deliberately-uninformative one? I'd guess the latter, but that's Priya's call to make with actual client mockups, not mine to assert here.
2. If a connection is silently closed and reopens — a SEC-25 sweep, a SEC-26 refresh that looked like a blip, or an ordinary network drop — does the participant's readiness state (locked-in or not) survive the reconnect cleanly on the facilitator's grid, with no flicker? Priya's right that this is broader than just the affected client's own composing state: a visible hiccup in the readiness grid during a live session erodes trust that the tool is showing the facilitator the truth in real time, independent of whether any vote data was actually lost.

## Feedback disposition

I incorporated every point from both reviews above — role/EM re-check scope, team-scoped connections, in-flight vote state, the disclosure negative scenario, the "no less frequent than" reading, the facilitator's readiness-grid view of the three failure modes, reveal-timing, facilitator blast radius, and diagnostic traces. Nothing here asked me to make a protective constraint optional, admin-configurable, or silent-by-default, so there's nothing to push back on — both reviewers were arguing for *more* rigor on the non-disclosure and ritual-integrity guarantees I already consider load-bearing, not less. The one place I deliberately held the line rather than just agreeing: I did not attempt to resolve the facilitator-blast-radius question or invent a priority-refresh scheme in this document, even though Priya asked good questions about it. Any concrete mechanism (earlier refresh, longer grace period, role-aware timers) is itself a new place where "admin-configurable" could sneak in, and I'd rather Design own that tradeoff deliberately than have me hand-wave a mechanism here that later gets treated as already-decided.

## Why I don't want this to sit too long

This gap stopped being theoretical the moment `session-lifecycle-transitions` wired real production triggers for all four events (issue #26, resolved). Before that, "a quiet lobby connection with revoked access" was a scenario that could only really happen with stubbed test triggers. Now every one of the four content-access events fires from a real commit, which means a real facilitator sitting in a real quiet lobby with revoked access, or an expired token, mid-session, is now a live possibility, not a hypothetical one the spec carried as a caveat. The 90-minute compensating bound (D8) keeps the outer edge closed, but the actual SEC-25 revocation-latency guarantee — someone loses access and the system notices within a meaningful interval, not "eventually, at the 90-minute mark" — isn't real yet. I'd rather this move to Design and Propose promptly than become the footnote D8's own risk register warned against.
