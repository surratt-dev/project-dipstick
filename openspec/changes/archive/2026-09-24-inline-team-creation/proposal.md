## Why

There is no `INSERT INTO teams` anywhere in production code today. Every team that exists in this application exists because a test fixture or the migration 4 seed inserted it directly — the application itself has never created one. That is not a missing nicety; per the use case's own design ("there is no standalone 'create team' screen"), team creation *is* session creation for a new team. Until this ships, no team that has never used the application can ever have its first Health Check, full stop, regardless of anything else that's been built. Closes #44.

This matters now because #153 shipped the existing-team picker and made the gap concrete rather than theoretical: `SessionCreationPage.tsx` has a picker and a confirm screen, but no "create a new team" affordance anywhere, and a facilitator with zero eligible existing teams — a state the use cases explicitly support — hits a dead end with no path forward. The `session-creation` capability's own purpose statement already names this as deliberately deferred scope: "the new-team variant of session creation... left for it to grow into later." This change is that growth.

It is also the first production code path that will ever read `topics.is_default` — nothing else in this codebase touches that column. Getting the default-topic-assignment mechanism right here matters more than an ordinary first-integration would, because the topic set assigned at this moment is locked until the team's first session completes: a wrong default is not a cosmetic bug, it is the team's Health Check baseline for every session and trend chart that follows.

## What Changes

- **New:** `POST /api/v1/teams` creates a team and its first session in a single transaction — team-name uniqueness validated case-insensitively and after trimming (normalized collision detection, backed by the existing `teams_name_unique` constraint as the server-side backstop), default topic set copied from the sentinel `__default_topics__` team's `is_default = true` rows into the new team's own `topics` rows, and a session created with `is_first_session = true` computed explicitly for this flow (not inherited from the existing-team `POST /draft` handler, which correctly hardcodes `false` for a different reason).
- **New:** the new-team flow skips `draft` status and lands the facilitator directly in `lobby` — unlike the existing-team flow's deliberate draft gate (ADR-007's "review team context before an irreversible action"), a brand-new team has no prior context to review, so the gate's rationale doesn't transfer. In its place: the submit control echoes the typed name back before firing ("Create team 'Platform Team' and open session room"), and the landing screen explicitly acknowledges that the team was created and its default topics were assigned.
- **Modified:** `SessionCreationPage.tsx`'s `Screen` union gains a third variant (`{ name: "new-team" }` or equivalent) for the team-name entry form, alongside the existing `picker` and `confirm` screens from #153 — one component with three screens, not a second page that can drift out of sync with the first. Backing out to the picker pre-submit is a client-side state transition only; nothing is created before the form is submitted, so it is always safe.
- **Modified:** the picker's empty-state copy changes from "no teams available" to language that points at the new-team option (e.g., "Don't see your team? Create one to get started") — once new-team creation ships, an empty eligible-teams list is no longer a dead end.
- **Named negative AC:** `POST /api/v1/teams` SHALL NOT insert a `team_memberships` row for the creating facilitator. The use case's Notes and Out of Scope are explicit on this point, and `teams.created_by_user_id` makes it easy for an implementer to reflexively add one anyway — that would manufacture a same-team-facilitator conflict the first time this same person tries to facilitate the team they just created.
- **Not in this change — formal prerequisite dependency:** `packages/backend/migrations/4_seed_data.sql` currently seeds six default topics (one per `entities-and-relationships.md` Topic Area); the Topic Management use case's Acceptance Criteria canonically enumerate twelve. Marcus confirmed directly that the twelve-item AC is correct and the seed migration is stale scaffolding, not an intentional simplification. I'm scoping the fix as a prerequisite change, filed as a stub at `openspec/changes/fix-default-topic-seed-data/` (a new migration replacing the six rows with the twelve AC-verbatim topics from `requirements/use cases/08 - Topic Management - Use Cases.md`'s AC, plus a regression test pinning the seeded prompts to those exact strings) — rather than folding it into this change, for the same reason the existing-team change shipped its `POST /draft` membership-check fix as its own deployable step ahead of the picker UI: this change's job is to build the copy mechanism correctly, not to also decide what canonical content it copies. Bundling them would make one change responsible for two independently reviewable claims ("the copy mechanism is correct" and "the twelve-topic list is correct"), and would block this change on a content decision that's already been made and just needs to be executed.

  **This change is formally blocked on `fix-default-topic-seed-data` merging before `inline-team-creation` merges.** That sequencing is not just documented intention: task 4.3/4.4 (see tasks.md) adds a real-data integration test that queries the actual seeded `topics` rows for the sentinel team and asserts the twelve AC-verbatim prompts, count, and ordering — a test that fails loudly against the current six-topic seed and can only pass once the prerequisite has actually landed. Whoever picks up this change is responsible for turning the `fix-default-topic-seed-data` stub into a real proposal and merging it first; the merge gate is enforced by that test, not by trusting task 1.1 to be read carefully.
- **Not in this change — explicitly named as carried-forward scope:** the use case's own Notes flag "what makes someone a 'member' of the new team vs. just a participant in one session" as unresolved, and it stays unresolved here — membership assignment happens at join time (Join Session via Link), not team creation, and this change is explicit that it does not add a `team_memberships` row for anyone. Whoever picks up the join-link flow next should not assume this question was silently answered by this change.
- **Not in this change — pre-existing gap, not introduced or closed here:** no production code path populates `session_topics` for a new session (traced across every route in `facilitator-sessions.ts`); `begin-voting` reads from it assuming it exists. This change assigns the team's `topics` configuration, which is a different table from the per-session `session_topics` snapshot — "assign the default topic set" does not mean "make the new team's first session playable end-to-end."
- **Requirements documentation correction, in this change's scope:** "Create Session for a New Team" in `requirements/use cases/02 - Session Setup - Use Cases.md` predates the draft/lobby split — its Postconditions still say "waiting for participants" and its Main Flow never mentions `draft` at all. The existing-team use case got a dated addendum when it gained the draft/lobby split (see its own "Addendum (draft-landing decision)"); this change writes the equivalent addendum for the new-team use case — Postconditions naming `lobby` explicitly, and a Main Flow note explaining why this flow intentionally skips `draft`, cross-referencing the existing-team flow's addendum — as part of this change's own work (tasks.md 8.1), the same way the existing-team change shipped its addendum as part of that change rather than as a tracked follow-up.

## Capabilities

### New Capabilities
- `default-topic-provisioning`: the mechanism that copies the canonical default topic set (sourced from the sentinel `__default_topics__` team's `is_default = true` rows) into a newly created team's own `topics` rows — a real row-copy, not a reference, matching this codebase's existing pattern of denormalizing topic data at each layer so a later edit can't rewrite another team's history. Covers ordering, `is_default` carried forward, and confirms "locked" is a derived state (no completed session yet) rather than a stored column, so no implementer adds a redundant `locked` boolean.

### Modified Capabilities
- `session-creation`: grows to cover the new-team variant explicitly named as deferred in its own purpose statement — the new-team form as a third screen in the existing picker/confirm state machine, `POST /api/v1/teams`, normalized team-name uniqueness validation, `is_first_session = true` as a named, explicitly-computed acceptance criterion for this flow, the `draft`-skip-to-`lobby` landing specific to new-team creation (inline name-echo confirmation in place of the draft gate, plus a landing acknowledgment that team creation and topic assignment succeeded), and the picker's empty-state copy update.

## Impact

- **Backend:** a new `POST /api/v1/teams` handler, added to `packages/backend/src/routes/facilitator-sessions.ts` alongside the existing `POST /draft` handler (design.md D3 — not `teams.ts`, which is the unrelated TEAM-005/TEAM-006 admin route file), implementing the team-insert + topic-copy + session-insert transaction, following the same transactional audit-write pattern established by `POST /draft` (`team.created_with_session` on success, `team.creation_denied_role` on a non-facilitator rejection). Relies on the new `teams_name_unique_normalized` functional index (design.md D4) as the server-side backstop, with the pre-existing `teams_name_unique` constraint (`2_create_tables.sql:23`) left in place.
- **Frontend:** `packages/frontend/src/pages/SessionCreationPage.tsx` (new `Screen` variant, form, submit control with name-echo, empty-state copy) and its landing target (new-team-specific acknowledgment copy on the session room / lobby view).
- **Database:** no new tables or columns. Formally blocked on the `fix-default-topic-seed-data` prerequisite change (stub filed at `openspec/changes/fix-default-topic-seed-data/`, see What Changes) merging before `inline-team-creation` merges — enforced by the real-data integration test in tasks.md 4.3/4.4, not just by sequencing intent.
- **Requirements documents:** "Create Session for a New Team" in `requirements/use cases/02 - Session Setup - Use Cases.md` gets a Postconditions/Main Flow addendum naming `lobby` and explaining the draft skip, written as part of this change (tasks.md 8.1) — not deferred as a follow-up.
- **No breaking API changes.** `POST /api/v1/teams` is a new endpoint; nothing existing calls it today.
