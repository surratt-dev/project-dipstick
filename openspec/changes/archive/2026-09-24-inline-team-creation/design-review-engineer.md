# Design Review — Full Stack Engineer (Marcus Oyelaran)

**Change:** `inline-team-creation` (#44)
**Reviewed:** design.md, proposal.md, tasks.md, specs/session-creation/spec.md, specs/default-topic-provisioning/spec.md, against the shipped #153 implementation (`facilitator-sessions.ts`, `SessionCreationPage.tsx`) and current schema (migrations 1–10).

## Verdict

Implementable as written, with one correctness gap that will produce an unhandled 500 in a real (if narrow) concurrency scenario, and one file-placement ambiguity that risks a wrong first move. Neither requires a design rework — both are fixable at the design level before implementation starts. Everything else — the transaction boundary, the `is_first_session` scoping, the topic-copy mechanism, the reuse of `POST /draft`'s patterns — is correct and consistent with how #153 actually shipped, not just with how it was designed.

I verified every SQL fragment quoted in design.md against the live schema (migrations 1–10) and the real `POST /draft` handler, not just against the prose. Two things design.md asserts as fact are correct: `session_status` already contains `'lobby'` as a first-class value (no enum work needed), and `topics_team_order UNIQUE (team_id, display_order, status)` cannot be tripped by the topic-copy INSERT, because the new team's `team_id` is unique to it — the constraint is scoped per-team, so copying six (or twelve) rows with distinct `display_order` values into a brand-new team can never collide with itself or anyone else.

## Findings

### 1. [Must-fix] The 23505 catch in D4/task 3.4 only matches the new index — an exact-duplicate race can still 500

D4 and task 3.4 both specify catching the uniqueness violation "matched on `err.constraint`" against `teams_name_unique_normalized` — mirroring `POST /draft`'s existing pattern at `facilitator-sessions.ts:340-343`:

```js
err instanceof DatabaseError &&
err.code === "23505" &&
err.constraint === "sessions_team_active_unique"
```

That pattern works for `POST /draft` because there is exactly one relevant unique constraint in play. Here there are two, and D4 deliberately keeps both: the pre-existing exact-match `teams_name_unique` (migration `2_create_tables.sql:23`) and the new normalized `teams_name_unique_normalized`. An **exact**-duplicate name violates both constraints simultaneously. PostgreSQL does not guarantee which constraint's violation is reported when two independent unique indexes are both violated by the same INSERT — in practice it's determined by index-check order (roughly creation/OID order), which means the older `teams_name_unique` is a live candidate to fire first for an exact-duplicate race, not just the new index.

Concretely: the spec's own "Scenario: Concurrent submissions for normalized-duplicate names" only exercises case/whitespace variants. Run the same race with two requests for the **identical** string "Platform Team" and there's a real path where the losing request's error has `err.constraint === "teams_name_unique"`, which the handler (as specified) doesn't check for — it falls through to `throw err`, and the caller gets a raw 500 instead of the 409/400-class collision response the spec requires ("not a generic server error").

The app-level pre-check (task 3.4's first half) closes most of this for sequential requests, but not for the concurrent case, which is exactly the case D4 exists to protect.

**Fix:** catch both constraint names (`err.constraint === "teams_name_unique" || err.constraint === "teams_name_unique_normalized"`), or — cleaner — treat any `23505` on the `teams` table's INSERT as the same collision response regardless of which named constraint fired, since both mean the same thing semantically ("a team with this name already exists"). Worth a one-line addition to D4 and task 3.4 rather than leaving it to be discovered in the concurrent-duplicate integration test in task 7.1.

### 2. [Must-clarify before implementation] `teams.ts` already exists and owns a different domain — task 3.1's two options aren't symmetric

Task 3.1 offers "`facilitator-sessions.ts` alongside `POST /draft`, or a new `teams.ts` route file — pick one and note the choice." The proposal's Impact section repeats this framing: "a new `teams.ts` route file — a design-stage decision," as if that filename is unclaimed.

It isn't. `packages/backend/src/routes/teams.ts` already exists — it's the TEAM-005/TEAM-006 route file: `GET /api/v1/teams/:teamId/members`, `GET /api/v1/teams/:teamId`, `PATCH /api/v1/teams/:teamId/members/:userId/role`, `POST /api/v1/teams/:teamId/managers`, plus ~150 lines of TEAM-006 sliding-window rate-limiting infrastructure. No route-path collision with `POST /api/v1/teams` (all existing routes there require `:teamId`), so it would technically compile and run either way — but that file is entirely about **team administration** (role assignment, EM/team association, admin-only rate-limited mutations), not session creation. Dropping the team+topic+session creation transaction into it mixes two unrelated domains in one file, and an implementer reading task 3.1 cold has no way to know `teams.ts` is already 1300+ lines of a different feature.

**Recommendation:** name this explicitly in the design rather than leaving it as an open choice discovered at implementation time. Given `facilitator-sessions.ts` already owns every other piece of the session-creation transaction machinery this change extends (`POST /draft`, the audit-write-in-transaction pattern, `GET /eligible-for-session`, the `DatabaseError`/`err.constraint` import), that file is the better home — it keeps the new-team creation flow next to the existing-team creation flow it's a sibling of, which is also the strongest argument against duplicating logic. If `facilitator-sessions.ts`'s length is a real concern, a new, distinctly-named file (e.g. `team-creation.ts`) is safer than reusing `teams.ts`'s name for an unrelated concern.

### 3. [Should-fix] Frontend error-state shape isn't addressed, and the existing `ConfirmError` type doesn't extend cleanly

`SessionCreationPage.tsx`'s current `ConfirmError` type is a two-member discriminated union (`membership_conflict` | `session_already_exists`) scoped entirely to the existing-team confirm screen, backed by a single `confirmError` state variable. The new-team screen needs at least two more error shapes — empty-name and name-collision (task 5.3) — that don't fit either existing member.

Design D1/D2 don't say whether the new-team screen reuses `confirmError`/`ConfirmError` (extending the union, which couples two screens' unrelated error vocabularies into one type) or introduces its own state (which is cleaner but means the "back to picker always safe, no leftover state" property has to be verified for two state variables instead of one — task 7.2's back-navigation test should assert no stale error renders on the *other* screen too, not just no request fired). Given D1's stated reason for a single component ("one gate, checked once") is about the *screen transition*, not about sharing error-state shape, I'd expect a new-team-scoped error state (e.g. `newTeamError: { kind: "empty_name" } | { kind: "name_collision"; message: string } | ...`), separate from `confirmError`. Worth one sentence in D1 or D2 settling this, since it's exactly the kind of small omission that produces a widened, harder-to-read union type if left to whoever implements it first.

Relatedly: the existing codebase's convention for a distinguishable, machine-readable rejection (`SessionAlreadyExistsResponse`, `RevealFailureResponse`, `TopicAdvanceBlockedResponse` — all typed response bodies with an `errorState` discriminant, defined in `@dipstick/shared`) is stronger than "a validation error naming the collision" (design.md D4's wording, spec.md's wording). The frontend needs to distinguish empty-name from name-collision reliably (task 5.3); a generic `{ error: { category, message } }` shape means doing that by string-matching `message`, which is exactly the "matched by message substring" anti-pattern this codebase's own comments (`facilitator-sessions.ts:298`) call out as the wrong approach on the backend side. Recommend a typed response (e.g. `TeamNameCollisionResponse { errorState: "team_name_collision"; providedName: string }`) added to `@dipstick/shared`, matching precedent, rather than leaving the exact shape to be improvised during implementation.

### 4. [Minor, non-blocking] Migration numbering coordination between this change and its prerequisite

Both `fix-default-topic-seed-data` and this change's task 2.1 will each add a new numbered migration file (next available today is `11_*.sql`). Since this change is formally blocked on the prerequisite merging first (D7/task 1.1), the numbering will naturally resolve in sequence *if the prerequisite actually lands first* — but nothing in tasks.md tells whoever picks up `fix-default-topic-seed-data` that its migration claims `11_*` and this change's `teams_name_unique_normalized` migration must therefore be `12_*`. Low risk given the hard merge-order dependency already exists for other reasons (D7), but worth a one-line note in task 2.1 ("confirm the next available migration number at implementation time — do not assume `11`") so nobody hand-writes `11_add_teams_name_unique_normalized.sql` while the prerequisite is still in flight on a parallel branch.

## What's correct and doesn't need to change

- **Transaction boundary (D3):** `BEGIN → INSERT teams → INSERT topics (copy) → INSERT sessions → audit INSERT → COMMIT` is the right shape and matches the established `client.query("BEGIN")` / catch-rollback-rethrow / `finally client.release()` pattern used by every other transactional handler in `facilitator-sessions.ts` (`POST /draft`, `/advance`, `/start`, `/begin-voting`, `/reveal`, `/topics/advance`). Partial failure at any step rolls back cleanly under that pattern — no state where a team exists without topics or a session exists without a team, as claimed.
- **`is_first_session = true` (D3):** correctly scoped as a new, independent literal in a new endpoint, not a change to `POST /draft`'s existing `false`. I checked every other reference to `is_first_session` in the file (`begin-voting`'s `firstSessionDescription` gating at line ~874) — this flows through correctly and is in fact the entire reason `first_session_description` will ever render for a first-time team, which the current codebase has never been able to exercise. Zero regression risk to the existing-team flow, since it's a separate code path entirely.
- **Default-topic copy (D5):** the `INSERT ... SELECT` against the sentinel `topics` rows is schema-safe — confirmed `topics_team_order UNIQUE (team_id, display_order, status)` cannot be violated by this copy (new team_id is unique to the copy, so no collision with itself or any other team), and the omitted `status` column correctly defaults to `'active'`, matching how the sentinel rows themselves were seeded in migration 4 (also without an explicit `status`).
- **No `team_memberships` row (D6):** verified against the real `eligible-for-session` query (`facilitator-sessions.ts` ~line 1834, `LEFT JOIN team_memberships ... WHERE tm.id IS NULL`) — a creator with no membership row will correctly reappear as "eligible" for their own newly-created team in a future session, exactly as the spec's last scenario claims. This isn't just asserted correctly, it's mechanically consistent with the query that will actually evaluate it.
- **Reuse vs. duplication:** this change reuses the real, shipped patterns from #153 — not an idealized version of them. `join_token` generation, the `err.constraint`-matched rollback-to-409 pattern, the audit-write-in-transaction shape, and the `Screen` union extension are all grounded in what's actually in `facilitator-sessions.ts` and `SessionCreationPage.tsx` today, not a stale description of #153. D1's rejection of a sibling `NewTeamCreationPage.tsx` is correct and consistent with how #153's own design avoided the equivalent draft/lobby split.

## Recommendation

Fix Finding 1 (constraint matching) and settle Finding 2 (file placement) explicitly in design.md before implementation starts — both are cheap to fix now and expensive to discover mid-implementation (Finding 1 specifically will surface as a flaky-looking integration test failure in task 7.1's concurrent-duplicate-name case, which is worse than catching it here). Finding 3 is worth a sentence for clarity but isn't going to block a competent implementer. Finding 4 is a note-to-self, not a design change.
