## 1. What this feature actually is, underneath the CRUD

The issue text frames this as "a `POST /api/v1/teams` endpoint plus a form." That framing undersells it in the same way the existing-team change's framing undersold *that* feature. Team creation here is not a generic admin CRUD operation — it is the **one-time moment that decides what a team's Health Check will measure for as long as that team exists.** The topic configuration assigned at this moment is locked until the team's first session completes (Topic Management, "Enforce Topic Customization Lock for First Session"). Get the default topic set wrong here, or get the "first session" flag wrong, and the team's inaugural session — the one that sets the tone for whether the ritual sticks at all — runs on bad data, silently.

This is also literally the only way a team enters the application. Per the use case's own Notes: *"there is no standalone 'create team' screen. Teams come into existence only when a session is being created for them."* That's a deliberate design choice worth respecting rather than "fixing" by adding a separate admin team-management screen as a side effect of this work — that would be scope creep past what either use case asks for, and it would create a second team-creation path that the facilitator-neutrality and default-topic-set rules would then need to be enforced against twice.

## 2. Confirmed: the production gap is exactly as described, and it's deeper than "no endpoint"

I verified the issue's claim directly. `grep -rn "INSERT INTO teams"` across `packages/backend/src` finds it only in test fixture files (`ws-pubsub-integration.test.ts`, `action-items-integration.test.ts`, two files under `routes/__tests__/`) and in `migrations/4_seed_data.sql`'s one-time system-team seed. No route file constructs a `teams` row. `SessionCreationPage.tsx` (the picker built for #153) has no "create a new team instead" affordance anywhere in its markup — confirmed by reading the whole file.

But the gap goes further than "the endpoint doesn't exist": **nothing in production code reads `topics.is_default` either.** I grepped for `is_default` and for the sentinel team id `00000000-0000-0000-0000-000000000001` across `packages/backend/src` (excluding tests) and found zero matches. The default-topic-set seed data has been sitting in the database, unused, since migration 4. This feature is the first thing that will ever read it. That raises the stakes on getting it right — nobody has exercised this data path before, so nothing has caught the problem in §3 yet.

## 3. Finding (blocking): the seeded default topic set does not match the canonical list in the requirements

This is the finding I most want on record before anyone writes a proposal.

`requirements/use cases/08 - Topic Management - Use Cases.md`, "Assign Default Topic Set to New Team," Acceptance Criteria, states explicitly and enumerates by name:

> "The default topic set contains all **twelve** topics: 'How easy is it to add features to production code?' (Finger), 'How easy is it to reason about production code?' (Finger), 'How would you rate the code under active development?' (Finger), 'How would you rate the code for the entirety of the project?' (Finger), 'Is the test suite effective?' (Finger), 'Is the test suite consistent?' (Roman), 'How would you rate the tests under active development?' (Finger), 'How would you rate the tests for the entirety of the project?' (Finger), 'Confidence in the pipeline' (Finger), 'Are you comfortable with the technology stack?' (Roman), 'How effective is pairing?' (Finger), and 'Project Trend' (Modified Roman — up/steady/down)."

`packages/backend/migrations/4_seed_data.sql` seeds exactly **six** topics under the sentinel team `00000000-0000-0000-0000-000000000001`: Production Code, Test Suite, Pipeline, Technology Stack, Pairing, Project Trend — one topic per `entities-and-relationships.md` Topic Area, not one topic per the twelve-item list above. The prompts don't match either (e.g., seed says *"How easy is it to add new features to the production code?"* — close but not identical wording to the AC's *"How easy is it to add features to production code?"*, and the AC's four distinct production-code questions collapse into the seed's single "Production Code" topic).

This is precisely the kind of drift Devon's persona exists to catch: **the "default topic set" is supposed to be a system-level constant, defined once, and both the requirements doc and the running database currently claim to be that constant, and they disagree.** If this feature just copies `is_default = true` rows as they exist today, it ships a default set that contradicts the requirements document's own acceptance criteria for the sibling use case this feature depends on. If it copies whatever the requirements doc says instead, the seed migration is stale and something needs to reconcile it (a new migration, ideally, so `is_default = true` in the database and the twelve-item AC agree before this feature reads either).

**Resolved (BA-confirmed):** Marcus confirmed this directly — he wrote both source documents this finding sits between. The twelve-item AC in the Topic Management use case is canonical; it's the direct output of facilitator interviews (the "active development" vs. "entirety of the project" split was deliberately elicited as two separate questions, not padding). The seed migration's six rows map one-to-one onto the five Topic Areas in `entities-and-relationships.md` plus Trend — an earlier-stage entity concept that was never reconciled against the finished twelve-item use case. This is scaffolding drift, not an intentional simplification, and the requirements AC does not need amendment.

**Concrete follow-up, to be scoped as a prerequisite to #44, not inside it:** a new migration that replaces the six `is_default = true` rows under `00000000-0000-0000-0000-000000000001` with the twelve AC-enumerated rows, using the AC's prompt text verbatim (not re-paraphrased) as the source of truth, and preserving `vote_type` per topic exactly as specified (Finger/Roman/Modified Roman). Pair it with a regression test asserting the seeded default topic set's prompts match the twelve AC strings verbatim, so this drift can't silently recur the next time migration 4 (or whatever supersedes it) is touched. #44 depends on the default set being correct; it doesn't own defining "correct" — that's Topic Management's use case. The proposal should call this out explicitly as a dependency/prerequisite change, following the same pattern as the existing-team change's `POST /draft` membership-check fix, which shipped as its own deployable step ahead of the picker UI.

## 4. Finding: `is_first_session` must not be silently inherited as `false`

`POST /api/v1/teams/:teamId/sessions/draft` (the existing-team endpoint, `facilitator-sessions.ts:198-380`) hardcodes `is_first_session = false` in its `INSERT INTO sessions` (line 309). That's correct *for that endpoint* — an existing team's draft session is not assumed to be its first. It would be actively wrong if reused unmodified for new-team creation: a brand-new team's inaugural session is *always* its first session, definitionally, and `is_first_session` is not a cosmetic flag. I traced its two real consumers:

- `begin-voting` (`facilitator-sessions.ts:874`): `firstSessionDescription: sessionRow.is_first_session ? firstTopicRow.first_session_description : null`. This is the onboarding copy that explains what "1" vs. "4" means on a topic — exactly the content a team that has never run the ritual before needs and a returning team doesn't. If this flag ships `false` for a new team's first-ever session, that onboarding context never renders, and nothing else in the system will ever get another chance to show it (only the first session reads it).
- Topic Management, "Enforce Topic Customization Lock for First Session": the lock is keyed off session completion history for the team, not this flag directly, but the flag is this application's only per-session record of "was this the first one" — worth confirming there's no second place that also needs to agree with it.

**Whatever creates the session record in this flow must compute `is_first_session = true` explicitly** (or, more robustly, derive it from "does this team have any prior session" rather than hardcoding a literal — a new team can only ever have zero prior sessions, so either is correct here, but deriving it is the more defensible pattern if this code path is ever reused). This needs to be a named acceptance criterion in the proposal, not an incidental detail of "reuse the draft-session code."

**Settled for propose:** both reviewers independently flagged this same point, converging on treating it as a standalone, named acceptance criterion — not something inherited by whichever code path implements team creation. Suggested AC text: *"The session created for a new team is recorded as that team's first session, and this determination does not depend on reusing logic written for the existing-team flow."*

The use case's own step 2 says the Facilitator "selects the option to create a new team rather than selecting an existing one" — this reads as one additional affordance on the *same* picker screen from #153, not a separate route the facilitator navigates to. `SessionCreationPage.tsx`'s `Screen` union type (`{ name: "picker" } | { name: "confirm"; team: EligibleTeam }`) is exactly the kind of discriminated-union state shape that a third variant (`{ name: "new-team" }` or similar) slots into cleanly — this is a strong signal for the propose stage that the two flows should live in the *same component*, extending the existing state machine, not a parallel page that has to stay in sync with it by hand. I'd flag it as a risk if the proposal instead builds `NewTeamCreationPage.tsx` as a sibling file — that's exactly the kind of "two components that can drift" pattern the existing-team change's own design.md called out and deliberately avoided (D6, "one shared component invoked two ways... not two components that can drift").

One nuance the use case doesn't address and #153 had to resolve for its own screen: what does the *empty* eligible-teams list look like once "create a new team" is always available? Today, `SessionCreationPage`'s empty state (lines 238–244) tells the facilitator there's nothing to do. Once new-team creation ships, that's no longer true — a facilitator with zero eligible existing teams can still always create a new one. The empty-state copy and the "create a new team" affordance's visibility need to be decided together, not left as "the button was already always going to be visible so the copy doesn't matter" — I'd want the empty-state message itself to point at the new-team option rather than reading as a dead end (see also `NoTeamPage.tsx`'s existing "you don't have a team yet" framing — a facilitator with zero team memberships hitting this flow for the first time is exactly the audience this use case's own Preconditions carve out: *"a newly granted Facilitator who hasn't yet been added to any team... is explicitly supported."*).

**Resolved: this needs to be a named AC, and the copy should invite new-team creation, not just tolerate it.** Both reviewers agreed independently. **Named AC for propose:** when the eligible-teams list is empty, the picker's message directs the facilitator to the "create a new team" option (e.g., "Don't see your team? Create one to get started") rather than stating only that no teams are available.

**New (from Priya's review): backing out of the new-team form pre-submit must be safe by construction, and this should be stated explicitly rather than left implicit.** Re-reading the use case's own Main Flow confirms it: step 4 (enter name) leads to step 5 (validate) and step 6 (create the team record) — nothing is created before submission. Because the new-team form is a third variant of `SessionCreationPage`'s existing `Screen` state union (not a separate route), navigating back to the picker is just a client-side state transition with no server-side side effect to unwind. **Named AC for propose:** "Navigating back from the new-team form to the picker before submission creates nothing and is always available."

## 6. Team-name uniqueness validation

`teams.name` already carries `CONSTRAINT teams_name_unique UNIQUE (name)` (`2_create_tables.sql:23`) — the database-level constraint already exists and has existed since the schema was first defined; it's just never been exercised by a real INSERT path. That gives the proposal an easy, low-risk validation shape to follow, matching this codebase's established pattern elsewhere (the `sessions_team_active_unique` partial index + `23505`-to-`409` translation in the existing-team change, `facilitator-sessions.ts:339-359`):

- Client-side/inline check is a UX nicety, not the enforcement point (consistent with every other constraint in this codebase — see §3 of the existing-team exploration notes, which I fully agree with and won't re-litigate: the server-side check is the actual constraint).
- Server catches the `23505` unique-violation on `teams_name_unique` specifically (matched on `err.code` and `err.constraint`, not a message substring — the established pattern) and returns a distinguishable validation error, not a generic 500.
- **Resolved: normalize (case-fold + trim), not exact match.** `teams_name_unique` is a plain `UNIQUE` constraint — `"Platform Team"` and `"platform team"` are different values to Postgres, and the use case doesn't define equality on its own. Priya has a concrete, real-world failure case from the physical version of the ritual: two teams independently signed up as "Platform" and "platform-team" weeks apart, undetected until she was staring at two near-identical rows in a spreadsheet trying to work out which session belonged to which team. That's exactly the continuity problem this application exists to solve — trend history and handoff context only work if "the team" is a single, unambiguous thing — and there's no admin screen anywhere in these use cases to merge or reconcile a near-duplicate after the fact. **Named AC for propose:** team-name uniqueness is evaluated case-insensitively and after trimming leading/trailing whitespace — "Platform Team" and "platform team" are treated as a collision. The existing `teams_name_unique` constraint stays as the server-side backstop, but the pre-check and the collision error message both need to reflect normalized equality, not raw-string equality.

## 7. Default topic set assignment — concretely, where the data lives and what "assignment" means

Setting aside the §3 content mismatch, the *mechanism* the Topic Management use case describes is already well-supported by the existing schema, and I want to name it precisely so the proposal doesn't reinvent it:

- **Source:** `topics` rows where `team_id = '00000000-0000-0000-0000-000000000001'` (the sentinel `__default_topics__` system team) and `is_default = true`, ordered by `display_order`.
- **Target:** new `topics` rows, one per default topic, with the new team's real `team_id`, `is_default = true` carried forward, same `display_order`, `prompt`, `vote_type`, `name`, and `first_session_description` copied verbatim — a straight `INSERT INTO topics (...) SELECT ... FROM topics WHERE team_id = '000...0001' AND is_default = true` is the natural shape, inside the same transaction as the team-row insert.
- **This is a copy, not a reference.** The Topic Management use case is explicit that "each team owns its own copy of the topic configuration — changes to one team's topics do not affect others," and separately that "if the canonical defaults change in a future application version, existing teams retain their assigned configuration." A foreign-key-style reference back to the sentinel topics would violate both properties the first time any team customizes a topic (which mutates a row a different team's session already depends on) — this has to be a real row-copy, matching how `session_topics` already denormalizes `topic_name`/`topic_prompt`/`vote_type` off of `topics` at the next layer down (`2_create_tables.sql:86-101`) for exactly the same "don't let a later edit rewrite history" reason.
- **What this feature does *not* need to build:** population of `session_topics` for the resulting session. I traced every route in `facilitator-sessions.ts` and found no production code path that inserts into `session_topics` at all — `begin-voting` reads from it assuming it's already populated, but nothing I can find populates it. That's a pre-existing gap in this codebase, not something #44 introduces or is responsible for closing. Worth a note in the proposal's Non-Goals so nobody assumes "assign the default topic set" also means "make the new team's first session actually playable end-to-end" — that second piece needs its own change, and may already be silently broken for the existing-team flow too. I'm flagging it here so it's visible, not asking this change to fix it.
- **Locked state:** the Topic Management use case says the new configuration is "marked as locked (not yet customizable)" at creation. Nothing in the current schema (`topics` table columns: `id, team_id, name, prompt, vote_type, display_order, status, is_default, first_session_description, created_at, updated_at, archived_at`) has a per-team lock flag — the lock is described in Topic Management's other use case ("Enforce Topic Customization Lock for First Session") as being derived from session-completion history, not stored as a boolean. So "marked as locked" in the Assign-Default-Topic-Set use case is describing an *emergent* state (no completed session yet ⇒ locked), not a column this feature needs to write. Worth confirming explicitly in the proposal so nobody adds a redundant `locked` column that can drift from the derived truth.

## 8. Ritual and constraint concerns specific to this feature

- **Facilitator-not-a-member-of-the-new-team: structurally true, not a runtime check.** The use case's AC frames this as something the application must prevent ("the Facilitator cannot create a team that they themselves are a member of and then use it as the session target"), but because the team doesn't exist until this flow creates it, there is no membership row to check against — the constraint is satisfied by construction, not by a guard clause. The one thing worth being deliberate about: this flow must **not** insert a `team_memberships` row for the creating facilitator as a side effect of `POST /api/v1/teams`. The use case's Notes are explicit ("The Facilitator who creates the new team is not added as a member of that team") and Out of Scope explicitly excludes "Assigning an Engineering Manager to the team at creation time." I'd want this as a named negative acceptance criterion in the proposal (not just an absence of a task to do the opposite) — precisely because a well-meaning implementer might reflexively add a `created_by` membership row the way `teams.created_by_user_id` might suggest, and that would quietly manufacture a same-team-facilitator conflict the very next time this same person tries to facilitate this new team.
- **Neutrality is trivially preserved here, but the *next* session for this team is where the real cross-team check matters.** This facilitator creates the team and its first session cleanly (no membership exists, no check needed). But once real engineers join via the join link and the team has members, the *second* session for this team goes through the ordinary existing-team flow (#153), where the facilitator-from-another-team enforcement (`facilitator-sessions.ts:257-289`) already applies correctly. No new work needed here, but worth stating in the proposal so it's clear this change isn't quietly creating a team that's exempt from that rule going forward — it isn't, the general mechanism just doesn't apply yet because there's no membership to conflict with.
- **No-manager-participation and simultaneous-reveal:** neither is touched by this feature. Team creation precedes any voting or participation; flagging their absence here only to confirm I checked, not because either is in play.

## 9. Resolved decisions and remaining open items for propose

Both reviews (Priya Nair, Facilitator; Marcus Delgado, BA — `explore-review-facilitator.md`, `explore-review-ba.md`) converged independently on nearly every point below. Where they converged, I'm treating the point as settled rather than re-opened; where either raised something new, I've folded it in as its own finding.

### Resolved

1. **(Was blocking, §3) Twelve-topic list vs. six-topic seed — resolved: the twelve-item AC is canonical.** See updated §3 above. Concrete follow-up: a prerequisite migration correcting `4_seed_data.sql` to the twelve AC-verbatim topics, plus a regression test pinning the seed to those exact strings. The proposal should scope this as a dependency/prerequisite to #44 — likely its own small change ahead of implementation — not solved inside #44 itself.

2. **(Was blocking, §9.6) Draft vs. lobby landing — resolved: skip `draft`, land directly in `lobby`.** Both reviewers independently confirmed my lean: for a brand-new team there is no prior-session context to review, so the draft gate's entire rationale (per the existing-team change's D6 decision — review team context before an irreversible action) doesn't carry over; it would be a screen that always renders empty. This is settled.

   **But that does not mean "no confirmation moment at all," and that's a real addition to the original finding.** The irreversible thing in this flow isn't opening the room — it's the team name itself. There's no rename path (confirmed — I searched for one while writing §5 and found none), and the name is entered in a free-text field rather than picked from a constrained list, so a typo here is worse than a wrong pick from the existing-team picker: it becomes the team's permanent identity across every future session, trend chart, and facilitator handoff. **Named AC for propose:** the submit control must echo the typed name back before the request fires — e.g. "Create team 'Platform Team' and open session room," not a bare "Submit." This satisfies the confirmation need inline, without reintroducing a `draft` status or an extra screen.

   **Also resolved, same finding: the session room needs to acknowledge that team creation succeeded.** Landing in an empty session room, seconds after typing a team name, with nothing on screen to confirm what just happened, reads as the confirmation having vanished rather than the flow being fast. **Named AC for propose:** on landing, the session room shows an explicit acknowledgment that the team was created and its default topics were assigned (e.g., "Team created. Default topics assigned. Share the link below to get started.") — new UI copy scoped to the *new-team* landing specifically, not a change to the existing-team room view. I'd also recommend (not requiring it block propose) read-only visibility into *which* topic set was assigned, given §3's finding that the seed data doesn't currently match the documented default — a facilitator running their first-ever session for a team is the person who most needs to trust what's in front of them, and the cost of a read-only list is low.

   **This is also a use-case documentation gap, not just an implementation footnote.** `requirements/use cases/02 - Session Setup - Use Cases.md`'s "Create Session for a New Team" predates the draft/lobby split entirely — its Postconditions still say "waiting for participants" and its Main Flow goes straight to the room, written before `draft` existed as a status at all. The existing-team use case got a dated "Addendum (draft-landing decision)" when it gained the draft/lobby split; this one never did. Flagging this as a task for the propose/sync stages — the use case needs an explicit rewrite (Postconditions naming `lobby` by name, plus a note cross-referencing the existing-team flow and stating why this flow intentionally skips `draft`) — not something to rewrite here, since that's the BA's document and the propose stage is where requirements changes get made deliberately rather than inherited from exploration notes.

No requirements change needed; carry forward as a one-line implementation note so nobody adds a redundant `locked` column that can drift from the derived truth.
