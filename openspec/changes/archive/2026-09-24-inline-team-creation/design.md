## Design Review Disposition

This design was reviewed by Marcus Oyelaran (Full Stack Engineer) and Tomás Ferreira (Security Analyst); their full reviews are retained at `design-review-engineer.md` and `design-review-security.md`. Every Must-fix and Medium finding is incorporated below (engineer Finding 1 → D4; engineer Finding 2 → D3; security F1 → D3; security F2 → D6). Minor/Low findings are incorporated where the fix is cheap (engineer Finding 3 → D2; engineer Finding 4 → D4; security F4 → D8, also reflected in specs/session-creation/spec.md); one (rate limiting, security F3) is explicitly considered and deferred with a stated reason rather than implemented — see D9.

## Context

`session-creation` (from #153) already has a working picker → confirm → create flow for existing teams, built as a single component (`SessionCreationPage.tsx`) with a discriminated `Screen` union (`{ name: "picker" } | { name: "confirm"; team: EligibleTeam }`). That component's own purpose statement explicitly defers the new-team variant. This design extends that same flow rather than building a parallel one, and defines the transaction that creates a team, assigns its default topics, and creates its first session as a single atomic unit.

Two things constrain this design more than a typical CRUD feature would:
1. **Team creation is a one-time, unrepeatable moment.** There is no rename path and no standalone team-management screen (confirmed absent by search). A typo in the team name is permanent. The topic configuration assigned here is locked until the team's first session completes.
2. **This is the first production code path that will ever read `topics.is_default`.** The mechanism has zero prior exercise in this codebase — every existing team was created by a test fixture or the seed migration.

## Goals / Non-Goals

**Goals:**
- Let a Facilitator create a brand-new team and its first session in one flow, reusing the existing picker/confirm component rather than a parallel page.
- Make team-name uniqueness, default-topic assignment, and `is_first_session` correct and structurally enforced — not dependent on the frontend behaving.
- Land the Facilitator directly in `lobby` with enough on-screen confirmation that the flow doesn't feel like it silently succeeded or silently failed.

**Non-Goals:**
- Fixing the six-topic vs. twelve-topic seed-data mismatch (`packages/backend/migrations/4_seed_data.sql`) — tracked as a prerequisite change, referenced but not implemented here.
- Populating `session_topics` for the new session (pre-existing gap affecting the existing-team flow too).
- Defining team-membership semantics at join time (member vs. participant) — carried forward as an open dependency for the join-link work.
- A standalone team-management/rename screen — deliberately out of scope per the use case's own design.

## Decisions

### D1: Extend `SessionCreationPage.tsx`'s `Screen` union with a third variant, not a new page

`{ name: "picker" } | { name: "confirm"; team: EligibleTeam } | { name: "new-team" }`. The alternative — a sibling `NewTeamCreationPage.tsx` — was rejected: it's exactly the "two components that can drift" pattern the existing-team change's own design.md (D6) called out and avoided for the draft/lobby view. One component, three screens, one gate (`canFacilitateSessions`) checked once.

### D2: New-team creation skips `draft` and lands directly in `lobby`, with an inline name-echo replacing the draft gate

The existing-team flow's `draft` status exists so a Facilitator can review *prior team context* before an irreversible action (ADR-007). A brand-new team has no prior context — the draft screen would always render empty, which is a screen that exists only to be skipped. Instead:
- The submit control on the new-team form echoes the typed name back (e.g., "Create team 'Platform Team' and open session room") rather than a bare "Submit" — this is where the real irreversible moment lives, since there's no rename path afterward.
- The `lobby` landing view shows an explicit acknowledgment that team creation and default-topic assignment succeeded (e.g., "Team created. Default topics assigned. Share the link below to get started.") — new-team-specific copy, not a change to the existing-team room view.

**Alternative considered:** reuse the `draft` gate for consistency with the existing-team flow. Rejected — it would render an always-empty screen and add a click with no decision behind it, which works against Devon's "the application should disappear into the background" concern more than it protects anything.

**Error-state shape (engineer review, Finding 3):** the new-team screen gets its own state variable, not an extension of `SessionCreationPage.tsx`'s existing `ConfirmError` union. `ConfirmError`'s two members (`membership_conflict`, `session_already_exists`) are scoped to the existing-team confirm screen's error vocabulary; the new-team screen's errors (empty name, name collision) are a different, unrelated vocabulary, and D1's rationale for one component ("one gate, checked once") is about the screen-transition gate, not about sharing error-state shape across screens. A new `newTeamError: { kind: "empty_name" } | { kind: "name_collision"; providedName: string }` state, reset on every transition into or out of the new-team screen, keeps the two screens' error handling independent and keeps task 7.2's back-navigation assertion ("no leftover state") simple to verify per-screen.

The backend's collision response is a typed body, not a message the frontend string-matches: `TeamNameCollisionResponse { errorState: "team_name_collision"; providedName: string }`, added to `@dipstick/shared` alongside `SessionAlreadyExistsResponse` and `RevealFailureResponse`. This matches the codebase's own established convention for machine-readable rejections and avoids the message-substring-matching pattern `facilitator-sessions.ts:298`'s comment already calls out as wrong on the backend side.

### D3: `POST /api/v1/teams` performs team-insert, topic-copy, and session-insert in one transaction

Mirrors the existing `POST /draft` handler's transaction pattern (`facilitator-sessions.ts`): `BEGIN` → `INSERT INTO teams` → `INSERT INTO topics (...) SELECT ... FROM topics WHERE team_id = '00000000-0000-0000-0000-000000000001' AND is_default = true` → `INSERT INTO sessions (..., is_first_session, session_number) VALUES (..., true, 1)` → audit row → `COMMIT`. A failure at any step rolls back all three — there is no state where a team exists without its topics, or a session exists without its team.

`is_first_session` is set to the literal `true` for this flow, not derived from a "does this team have prior sessions" query — a team that was just created in the same transaction can only ever have zero prior sessions, so the literal and the derived value are equivalent here, and the literal avoids a redundant read inside the same transaction. This is a **named, explicit assignment**, not inherited from `POST /draft`'s `false` (which is correct for that endpoint and would be wrong here if copied unmodified).

**Route file placement (engineer review, Finding 2):** `POST /api/v1/teams` is implemented in `facilitator-sessions.ts`, alongside `POST /draft` — not in `teams.ts`. `teams.ts` already exists (`packages/backend/src/routes/teams.ts`, TEAM-005/TEAM-006: role management, EM/team association, ~1300 lines with its own rate-limiting infrastructure) and is an unrelated domain — team *administration*, not team *creation*. `facilitator-sessions.ts` already owns every other piece of machinery this transaction extends: the `POST /draft` handler this endpoint is a sibling of, the audit-write-in-transaction pattern, the `DatabaseError`/`err.constraint` import, and `GET /eligible-for-session`. This is a correction to the proposal's and tasks.md's earlier framing of this as a still-open choice between two symmetric options — it is not; `teams.ts`'s name is claimed by a different feature and should not be reused for this one.

**Rejected-attempt auditing (security review, Finding F1):** this codebase's established convention is that a security-relevant rejection gets its own audit row, not just the success path — `POST /draft`'s facilitator-from-another-team rejection writes `session.draft_denied_membership_conflict`, and `join-links.ts` writes `join.link_rejected` for its own rejection class. `POST /api/v1/teams` follows the same convention: the `403` non-facilitator rejection writes `team.creation_denied_role`, identifying the actor, actor role, and actor IP (no team/session id exists yet at that point). The name-collision `409` does not get its own audit row — collision attempts are a business-rule miss on non-sensitive data (team names are visible to anyone who joins a session), not an authorization probe, and the volume of legitimate typo-retries would make a collision-specific audit row mostly noise rather than signal. This asymmetry is deliberate: audit the check that gates access, not the check that gates data shape.

### D4: Team-name uniqueness gets a normalized (case-insensitive, trimmed) database constraint, not just an app-level pre-check

Exploration settled that "Platform Team" and "platform team" must collide. The existing `teams_name_unique` constraint is a plain `UNIQUE (name)` — exact string match. An app-level pre-check (`SELECT ... WHERE lower(trim(name)) = ...`) alone has a real race: two concurrent requests for normalized-duplicate names (differently cased) both pass the pre-check and both insert successfully, because the exact-match constraint doesn't catch them. That reintroduces the exact failure mode Priya's "Platform" / "platform-team" story describes, just delayed instead of prevented.

This change adds its own migration (next available number to be confirmed at implementation time — see the numbering note below) creating a functional unique index: `CREATE UNIQUE INDEX teams_name_unique_normalized ON teams (lower(btrim(name)))`. The existing plain `teams_name_unique` constraint is left in place (harmless, strictly narrower than the new index) rather than dropped, since dropping it is not required to satisfy this change and removing a working constraint is unnecessary risk.

**Constraint matching on the INSERT (engineer review, Finding 1 — must-fix):** because both `teams_name_unique` and `teams_name_unique_normalized` are live on the same `teams.name` INSERT, an **exact**-duplicate name violates both simultaneously, and Postgres does not guarantee which constraint's violation is reported first for a concurrent exact-duplicate race — `err.constraint` can come back as either `teams_name_unique` or `teams_name_unique_normalized`, not deterministically the new one. The handler therefore does not match a single constraint name the way `POST /draft` matches `sessions_team_active_unique`; it treats any `23505` on the `teams` INSERT as the same collision response, regardless of which named constraint fired — both mean the same thing semantically ("a team with this name already exists"). Concretely: `err instanceof DatabaseError && err.code === "23505"` on that specific INSERT, translated to the `TeamNameCollisionResponse` (see D2). This closes the gap the original single-constraint match left open for the identical-string concurrent case, not just the case/whitespace-variant case the spec's scenario names.

**Collation note:** Postgres's `lower()` is collation-dependent — for locales where a single character can lowercase to a multi-character sequence, or where case-folding is context-sensitive, `lower()` can theoretically produce a result that a human wouldn't consider "the same casing" as the input. This application's target Postgres instance is not yet pinned to a specific non-default collation, and team names are short, facilitator-entered strings rather than high-volume user content, so this isn't treated as a blocking risk for this change. It is worth an explicit confirmation before shipping that the target instance's default collation (`en_US.UTF-8` or equivalent) doesn't produce a surprising `lower()` result for non-ASCII input, since a normalization bug in a *uniqueness* constraint fails in the least visible way possible — two teams that look distinct to Postgres but not to a human, which is exactly the failure mode this index exists to prevent.

**Alternative considered:** rely on the app-level pre-check alone, treating the exact constraint as "the" backstop, per the exploration notes' original framing. Rejected at design time — the race is real and this codebase's own established pattern (concurrent-session block, `POST /draft`'s membership check) is "the database is the actual enforcement point," not "the pre-check usually catches it." A normalized functional index is the structural fix consistent with that pattern.

**Migration numbering (engineer review, Finding 4):** `fix-default-topic-seed-data` (D7's prerequisite) also adds a new numbered migration. Since this change is formally blocked on that prerequisite merging first, numbering resolves naturally in sequence *if* the prerequisite lands first as required — but nobody should hardcode `11_add_teams_name_unique_normalized.sql`. Task 2.1 confirms the next available migration number at implementation time rather than assuming a specific one.

### D5: `default-topic-provisioning` is a copy, not a reference, and does not write a "locked" column

`INSERT INTO topics (team_id, name, prompt, vote_type, display_order, is_default, first_session_description) SELECT $new_team_id, name, prompt, vote_type, display_order, is_default, first_session_description FROM topics WHERE team_id = '00000000-0000-0000-0000-000000000001' AND is_default = true` — new rows, own `id`s, same content. No foreign-key-style reference to the sentinel rows exists anywhere; that would violate the Topic Management use case's explicit "each team owns its own copy" and "changes to the canonical defaults don't retroactively affect existing teams" requirements the moment either set of rows was edited.

"Marked as locked" (per the Topic Management use case's Postconditions) is **not** a column this change writes. The `topics` table has no lock flag; lock state is the emergent absence of a completed session, evaluated by whatever implements "Enforce Topic Customization Lock for First Session" (a separate, not-yet-built capability). This change's only obligation is to not add a redundant, driftable `locked` boolean.

### D6: Team creation does not insert a `team_memberships` row for the creating Facilitator

Stated as a negative requirement precisely because `teams.created_by_user_id` (already a NOT NULL column, populated regardless) makes it easy to reflexively also insert a membership row "since we're already recording who created it." The use case is explicit that the creator is not a member. No membership row, of any role, is inserted by `POST /api/v1/teams` for any user.

**Enforcement is by absence of code, not a schema-level guarantee (security review, Finding F2):** unlike D4's uniqueness fix, this invariant isn't expressible as a database constraint — "no row was ever inserted" has no `CHECK` equivalent. The only safety net is task 7.1's regression test asserting no `team_memberships` row exists after creation. Because this is a lower rigor standard than D4 applies to itself, that test is treated as security-critical, not an ordinary functional assertion: it must carry an inline comment at the test site naming D6 and the facilitator-from-another-team constraint it protects, matching this codebase's existing convention of commenting the specific risk a test or constraint guards against (`sessions_team_active_unique`, the TEAM-006 rate-limit block). The comment is what stops a future refactor from quietly weakening or dropping the assertion without anyone clocking the security implication — see tasks.md 7.1.

### D7: The seed-data mismatch and its fix are a prerequisite change, not part of this one — enforced by a real-data test, not just sequencing intent

See proposal.md's "What Changes." Design-level consequence: this change's default-topic-provisioning code has a hard runtime dependency on the sentinel team's `topics` rows being correct, but no code-level dependency on *how* they became correct — the `SELECT ... WHERE is_default = true` query is agnostic to whether it's reading six rows or twelve. This change can be implemented and unit-tested (with a controlled fixture) independently of the prerequisite migration's landing.

The prerequisite is named explicitly as `fix-default-topic-seed-data` (stub filed at `openspec/changes/fix-default-topic-seed-data/`), and this change's merge is formally blocked on it. That sequencing is not enforced by a task-list instruction alone: tasks.md 4.4 adds a second integration test — separate from 4.3's fixture-based unit test — that queries the *actual* seeded `topics` rows for the sentinel team against the real migrated test database and asserts twelve rows matching the AC-verbatim prompts, vote types, and ordering. That test is exactly the mechanism that fails loudly if this change ships ahead of its prerequisite, closing the gap the fixture-based test alone couldn't: the fixture in 4.3 asserts the copy mechanism works correctly *given* twelve-topic input, but is independent of what's actually seeded, so it can never catch a stale six-topic seed on its own. 4.3 and 4.4 together cover both claims — the mechanism is correct, and the mechanism is running against correct data.

### D8: Check ordering is a spec-level requirement, not just `tasks.md` list order (security review, Finding F4)

`POST /api/v1/teams` checks in a fixed order: authenticate (global middleware) → authorize role (`facilitator`) → validate name is non-empty → check normalized uniqueness. As designed, this bounds the endpoint's enumeration surface to "an already-authenticated facilitator can learn whether a normalized name is taken" — acceptable, since team names aren't confidential (visible to anyone who joins a session) and every caller who reaches the uniqueness check is already an authenticated facilitator.

That bound holds only if the ordering is real, not incidental. Previously it lived solely in `tasks.md`'s prose sequencing (3.2 before 3.3 before 3.4), which a plausible refactor (e.g., extracting a shared "validate the request body" helper) could invert without anyone noticing it was security-relevant — inverted, a non-facilitator authenticated user could probe name existence pre-authorization. This is now an explicit requirement in `specs/session-creation/spec.md` ("Check order is authenticate, then authorize, then validate, then check uniqueness"), matching how `POST /draft`'s own inline comment documents its check order as deliberate.

### D9: Rate limiting is a considered-and-deferred decision, not an unconsidered gap (security review, Finding F3)

TEAM-006's manager-association endpoint (`teams.ts`) implements fail-closed rate limiting (burst + daily + global) because it creates persistent relationship rows and was jointly signed off by the BA and Security as warranting it (the Q6 decision). `POST /api/v1/teams` is evaluated against the same bar and, for now, does not get rate limiting.

The reasoning: `POST /api/v1/teams` is gated to `facilitator` role only — a scarce, IdP-managed privilege, not self-service — and doesn't establish a cross-user relationship the way TEAM-006's endpoint does. Abuse of this endpoint requires an already-compromised facilitator credential, at which point rate-limiting team creation is a narrow mitigation against one specific abuse shape (bulk junk-team creation) rather than a control against the actual threat (the compromised credential itself, which can do worse things through other facilitator-gated endpoints this change doesn't touch). This is explicitly a judgment call, not a claim that internal/low-volume implies no threat model: a compromised facilitator credential is a real insider/lateral-movement scenario, and this decision should be revisited if `POST /api/v1/teams` ever lands in `teams.ts` (it doesn't, per D3) where TEAM-006's rate-limit infrastructure would be a low-marginal-cost reuse, or if facilitator role assignment becomes less scarce than it is today.

## Risks / Trade-offs

- **[Risk]** Shipping this change before the prerequisite seed-data migration lands, and having someone demo or test-verify it against the current six-topic seed → **[Mitigation]** The prerequisite is named as a formal merge dependency (`fix-default-topic-seed-data`, see D7) with its own stub artifact, and this change's own test suite includes a real-data integration test (tasks.md 4.4) that queries the actual seeded topics and fails if the prerequisite hasn't landed — not just a fixture-based test that would pass regardless (4.3, which covers the copy mechanism, not the seeded content).
- **[Risk]** A well-meaning future change adds a `locked` boolean column to `topics`, out of sync with the derived truth (no completed session) → **[Mitigation]** D5 states the non-goal explicitly; the eventual "Enforce Topic Customization Lock" capability's own spec should reiterate it.
- **[Risk]** The normalized-uniqueness functional index (D4) is a new migration touching a table with an existing constraint; a mistake here is schema-level and harder to walk back than an app bug → **[Mitigation]** additive-only migration (new index, no column/constraint drop), with a down-migration that drops only the new index.
- **[Trade-off]** Landing directly in `lobby` (D2) means a brand-new team's first session becomes joinable immediately with no facilitator review step — accepted because there is nothing yet to review, and the alternative (an always-empty draft screen) trades away UX clarity for a consistency argument that doesn't hold up.
