## Why

`websocket-staleness-signal` shipped `reauth-required` as a structurally distinct, legitimately-disclosed third connection-health state — but its own Non-Goals section deferred the state's actual client-visible content to this issue (#32) on purpose, and what's live today is a placeholder: `ConnectionStatusBanner.tsx` renders `<div role="status">{REAUTH_REQUIRED_TEXT}</div>` — text only, no button, no navigation wiring, sharing the identical passive ARIA treatment as the unrelated `unknown-reconnecting` state it was deliberately built to differ from. That gap matters because `reauth-required` is the one state in this machine where "do nothing, it resolves itself" is false: the connection is ending, unconditionally, in about 30 seconds, and staying on the page cannot prevent that. A passive, easy-to-miss banner turns a recoverable moment into a silent forced disconnect — worse for a participant mid-topic, and design.md's own Risks section for `websocket-connection-reauthorization` already names a facilitator's version of this as having a strictly higher blast radius. This is also the last open question blocking full confidence in the SEC-26 reauthorization effort: the backend built real disclosure discipline (two close codes, two modules, no shared "send signal" helper) that a placeholder `role="status"` div does not yet honor at the one point it meets an actual person.

## What Changes

- Replace the placeholder `reauth-required` rendering with new interactive content: a call-to-action button wired to the existing `window.location.href = "/auth/login"` pattern (`AuthErrorPage.tsx`'s "Try Again" button is the precedent), live from first render — not gated behind grace-period expiry, since the state is already terminal at message-receipt and there is no meaningful "phase two" to wait for. This is new interactive-element work in a component that currently has none for this state, not a copy swap.
- Elevate `reauth-required`'s accessibility and visual treatment above `unknown-reconnecting`'s: `role="alert"` (assertive) in place of the shared `role="status"`, persistent/non-auto-dismissing (or demotion to a small persistent badge, never to nothing), and a visually distinct register (color/weight/icon) — stopping short of a full modal. The concrete mock realizing this is a named, tracked deliverable, not prose guidance — citing GitHub issue #36 explicitly as the standing precedent for what "described in words but not settled against a mock" looks like on this exact class of decision on the sibling staleness banner.
- Define the copy as a required-content checklist rather than a blank page: no visible countdown or numeric grace-period value (backed by a CI-enforced rendered-output test asserting the string never matches a digit-plus-time-unit pattern, mirroring the existing `unknown-reconnecting` rendered-output-identity test), no cause disclosed beyond what SEC-26 already legitimately discloses, a plain statement that continuing requires leaving and returning to the page, and a tone register of "expected token-lifetime event," not an error. The literal sentence construction remains a Design/Priya Nair sign-off item; the checklist itself is settled here.
- **Resolve the vote-loss copy condition as a build-time-checkable acceptance condition, not a judgment call left open.** `vote-compose-recovery` (GitHub issue #31, PR #42) already shipped a tested `sessionStorage`-backed persist/restore module (`packages/frontend/src/realtime/voteDraft.ts`), but it is wired to nothing — the vote-compose UI it would protect does not exist in the codebase yet. This change's copy MUST include a plain-language statement that continuing discards an unsubmitted vote *unless*, at this change's implementation time (not at this Propose/Design sign-off, since the compose UI's own ship date is the variable), the vote-compose UI is confirmed to import `voteDraft.ts`'s persist/restore hooks — a single grep-checkable fact, not a subjective call. Whoever implements this change names who performs that check and when in `tasks.md`.
- **Resolve the reveal-window collision as an explicit, stated answer: accepted as rare, no special-case mechanism.** `reauth_required` landing in the few seconds around a reveal moment could, to a facilitator watching the grid, read as a desync rather than an unrelated auth event. The server-side truth of reveal timing is untouched by this change, and building a mechanism to detect or suppress this co-occurrence would require `connectionHealth.ts` or `ConnectionStatusBanner.tsx` to become reveal-aware — a special case this change deliberately declines, consistent with `websocket-connection-reauthorization`'s Decision D9a reasoning against cause-specific carve-outs. This is a considered, stated trade-off, not a silently unconsidered gap.
- Keep the CTA and copy identical for participants and facilitators — no role fork. `websocket-connection-reauthorization`'s Decision D2/D3 scope sections and Decision D9a's broad rationale both argue against role-differentiated treatment here; the facilitator's structurally different consequence of clicking "log in again" (resuming full facilitation control) is existing app behavior this prompt doesn't need to encode. A forward note for whoever scopes issue #33: a second, more insistent, facilitator-specific cue on the eventual dedicated readiness-grid control surface is a reasonable *additive* future affordance, not something this change builds or forks toward.
- **Make the facilitator's role-uniform treatment real, not asserted.** `FacilitatorReadinessGrid.tsx` today has its own independently-duplicated `reauth-required` rendering — its own placeholder text, its own `role="status"` div — separate from `ConnectionStatusBanner.tsx`, not a call into it. Left as originally scoped, this change would have touched `ConnectionStatusBanner.tsx` only and left that duplication (and the facilitator's higher-blast-radius placeholder experience) untouched, while claiming the facilitator already benefited from the change. This change now extracts the `reauth-required` rendering into one shared subcomponent that both `ConnectionStatusBanner.tsx` and `FacilitatorReadinessGrid.tsx` consume (design.md Decision D9), so the CTA, ARIA role, persistence, and copy work above apply to both surfaces by construction.
- Preserve the structural bounds already in place: `connectionHealth.ts` remains the sole implementation of the three-state machine (no fork, per that capability's existing "Single shared implementation" requirement); the disclosure-blind `connected`/`unknown-reconnecting` pair is untouched by any of the above; no grace-period value or interval becomes visible anywhere, including as an innocuous convenience.

## Capabilities

### New Capabilities
_None._ This change builds out content and behavior within an existing, already-shipped state; it does not introduce a new capability boundary.

### Modified Capabilities
- `websocket-staleness-signal`: the `reauth-required` branch of the "Uniform participant-facing rendered treatment" requirement changes from a fixed placeholder string to a defined content/CTA/ARIA contract, distinct from `unknown-reconnecting`'s plain/passive treatment. New requirements are added for the call-to-action, the vote-loss disclosure condition, and the no-reveal-special-casing bound. The existing "Pilot-readiness gate" requirement is extended to include this change's own mock-sign-off and usability-check items, so they cannot be marked resolved by copy guidance alone — mirroring the currently-open bar set by issue #36 for the sibling grid-marker treatment.

## Impact

- **Affected code:** New shared subcomponent (e.g. `packages/frontend/src/components/ReauthRequiredTreatment.tsx`) holding the `reauth-required` copy, CTA button, `role="alert"` region, and persistence behavior (design.md Decision D9). `packages/frontend/src/components/ConnectionStatusBanner.tsx` and `packages/frontend/src/components/FacilitatorReadinessGrid.tsx` are both updated so their `reauth-required` case renders this shared subcomponent — `FacilitatorReadinessGrid.tsx`'s own previously-independently-duplicated placeholder constant and markup are deleted, not left alongside it. `unknown-reconnecting`'s rendering in both files is untouched. No change to `packages/frontend/src/realtime/connectionHealth.ts` (the state machine, its triggers, and its cause-blindness are all out of scope and unmodified). No change to `AuthContext.tsx` or `AuthErrorPage.tsx` — both are reused as the established `window.location.href = "/auth/login"` pattern, not modified.
- **Affected specs:** `websocket-staleness-signal` (modified capability — delta spec at `specs/websocket-staleness-signal/spec.md`).
- **Dependencies:** None new. Reuses the existing OIDC login route, which is already provider-agnostic at this call site — the CTA does not need to know or care which IdP is configured, consistent with the project's standing multi-provider OIDC constraint.
- **Related, not touched:** `vote-compose-recovery`'s `voteDraft.ts` (issue #31/PR #42) — this change only reads that module's wiring status as an implementation-time gate on its own copy content; it does not wire `voteDraft.ts` into anything itself. Issue #33 (facilitator readiness-grid distinction between revocation and flakiness during reauth) remains untouched and out of scope, consistent with `websocket-staleness-signal`'s existing boundary.
- **Client-visible impact:** Participants and facilitators whose connection enters `reauth-required` now see an assertive, persistent, actionable prompt with a working "Log in again" button, instead of a passive, non-interactive placeholder string.
