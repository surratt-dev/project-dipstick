# Design: harden-team-creation-topic-copy (#215)

*Devon Calloway. Decision labels D1-D12 and conditions C1-C12 are from `exploration-notes.md`.*

## Context

Team creation (`POST /api/v1/teams`, in `facilitator-sessions.ts`) copies the template team's default topics into a new team inside one transaction, then locks topics and snapshots the first session's topics (`lockTeamTopics`, `snapshotSessionTopics`). The copy selects `is_default = true` for the sentinel team with no status filter and no position handling. `content.ts` TOPIC-002 builds `defaultTopicsNotActive` from a separate query that also ignores the template row's status. Migration 18 made `display_order` unique only among active rows (`topics_team_active_order`, partial index `WHERE status = 'active'`). See the proposal for the two resulting failures.

## Goals / Non-Goals

**Goals:** a single definition of the canonical default set used by both consumers; a copy that cannot fail on template position anomalies and never resurrects an archived row; a visible operator signal for a damaged template; unchanged behaviour for a healthy template.

**Non-Goals:** any ritual mechanic; repairing existing teams; F5 maintenance path; frontend or response-shape change; the write trigger.

## Decisions

### Shared predicate (D1, D6)

The canonical default set is a predicate, not a list: `team_id = <DEFAULT_TOPICS_TEAM_ID> AND is_default = true AND status = 'active'`. Both parts of `is_default` and `status` stay: a custom row on the template is a #188 violation and must not copy, and an archived row is a fault.

**Choice: one exported SQL fragment plus an equality test, not the test alone.** `packages/backend/src/sessions/default-topics.ts` already exists to share the sentinel id so "the SQL ... cannot drift". It gains an exported fragment builder with this pinned signature:

```ts
export function canonicalDefaultsWhere(alias: "dt" | "topics", paramIndex: number): string
// canonicalDefaultsWhere("dt", 2) === "dt.team_id = $2 AND dt.is_default = true AND dt.status = 'active'"
```

Contract: (a) `alias` is a closed union, `"dt"` (the `content.ts` template-side alias) or `"topics"` (the copy, which selects `FROM topics` unaliased). `"t"`, the team-side alias in `content.ts`, is deliberately excluded from the type, so the fragment cannot be applied to the team's own rows (the C6 hazard). (b) `paramIndex` must satisfy `Number.isInteger(paramIndex) && paramIndex >= 1`, checked at runtime; otherwise the function throws (guards a `$undefined` or `$NaN` typo and any non-literal caller). (c) The sentinel id is always a bound parameter at `$paramIndex`, never inlined; only the literals `true` and `'active'` are in the string. A comment in the module states that no value may ever be interpolated and that the alias is not to be widened to `string`. (d) Both consumers pass `$2` (team id is `$1`), the simplest contract. (e) A one-line unit test asserts the exact string above for `("dt", 2)` and one `("topics", 2)` case, plus the throw on `0`, `1.5`, `NaN`: the C7 equality test proves behaviour, not that the interpolation was well formed. (f) `default-topics.ts` was constants only; its header comment is updated to say it now also owns the canonical-default SQL (fragment and copy), still not a route. Rationale for the type being a union rather than a runtime regex: the compiler rejects a request-derived string at the call site, and the runtime check on the index covers the one numeric input.

Rationale: the bug exists because two queries drifted. A test alone detects drift after the fact; a shared fragment makes drift a one-line edit in one place, and the C7 equality test then guards the wiring (that both actually use it, and that the fragment is correct).

Alternatives considered: (a) a SQL view `canonical_default_topics`: rejected, it is a migration on a shared table path for a two-consumer problem, and the copy needs row ids/order that a view makes harder to test with scratch schemas; (b) a TypeScript helper that returns the rows and have both consumers use the rows: rejected, `content.ts` needs a left join against the team's rows in SQL, and fetching twice adds a race for no gain; (c) two copies of the predicate plus the test: rejected as above. Interpolating the fragment into SQL is safe because its inputs are a closed alias union and a validated integer, and the fragment holds no value.

The twelve default names are not in application code. They appear only in the invariants test (D8), labelled a baseline that F5 (#216) must update when it edits defaults.

### Copy with explicit positions (D2)

Replace the `INSERT ... SELECT` with an exported function in `default-topics.ts`, `copyCanonicalDefaults(client: PoolClient, newTeamId: string, sourceTeamId: string = DEFAULT_TOPICS_TEAM_ID): Promise<void>`, which the route calls on its transaction client. This is the seam that makes the duplicate-position case testable (see Risks): the route cannot be driven against a missing index, a function on one client can. `sourceTeamId` exists as a test seam only: it is bound as `$2` (never interpolated), defaults to the sentinel, and lets the duplicate test use a scratch team as the "template" so the real template is never touched. The route never passes it. The SQL inside is:

```
INSERT INTO topics (team_id, name, prompt, vote_type, display_order, is_default, first_session_description)
SELECT $1, name, prompt, vote_type,
       row_number() OVER (ORDER BY display_order, id), is_default, first_session_description
FROM topics WHERE <canonical predicate with $2>
```

Positions are 1..n regardless of template gaps or duplicates; the new team no longer depends on template position values. The tie-break on `id` is deterministic but arbitrary, and applies only between rows with equal `display_order`, which cannot exist in a healthy template, so non-duplicate rows are never reordered (C4). Healthy template: identical output to today. The new team's positions equal the template's literal numbers only when the template is contiguous from 1; relative order is the shared language, not the integers. `row_number()` computes positions explicitly, so it does not rely on `ORDER BY` fixing insertion order. The column list stays explicit (annotation columns excluded, topic-annotation Decision 9); a test checks each copied column (C11).

This also resolves the issue's alternative (skip duplicates or renumber): we renumber. With the status filter, the archived/active collision disappears; genuine duplicates among active rows can only occur if the unique partial index is missing (down-migration, hand restore, stale environment), and renumbering makes creation immune to that.

### Anomaly detection and signal (D3)

Semantics (V1-V4) are fixed in `proposal.md` "Anomaly semantics" and the provisioning delta spec; this section is mechanism only. In short: `non_contiguous_order` is computed over the distinct active default positions and must equal 1..m (nonzero start fires it, duplicates alone do not); `non_default_row` counts non-default rows of any status; `topicIds` is the capped (50) union of affected rows and may be empty for a position-only anomaly; one entry per request, no cross-request de-duplication (a persistent fault is intentionally noisy); read committed, so the anomaly read and the copy may see different states under a concurrent template edit, which is acceptable.

**Where it runs (S2/S6, decided).** After `COMMIT`, on the pool (`db.query`, not the transaction client), only on the success path. Reasons: a failed query inside the open creation transaction aborts it (`25P02` on every later statement) and a JS `try/catch` cannot recover that, so the read must not share the transaction; running it after commit means a failure cannot touch creation, and it logs only for requests that actually created a team (a 409 name conflict or a rolled-back empty-template creation writes no `template_anomaly`; the empty case already writes its own error-level entry naming the template). Rejected: before `BEGIN` (would log for requests that later fail, adding noise and ambiguity about "one entry per creation"); a `SAVEPOINT` (extra statements on the hot transaction for no benefit). Cost: the read observes post-copy state; under read committed that may differ from what the copy saw if an operator edits the template concurrently, which the proposal already accepts because the log is diagnostic. The `proposal.md` "Isolation" bullet is edited to match.

**Mechanism.** Two exports in a new sibling file `packages/backend/src/sessions/template-anomalies.ts` (next to `default-topics.ts`, not in the 2600-line route file): `readTemplateTopicFacts(db: Pool): Promise<TemplateTopicFact[]>`, one query returning `id, is_default, status, display_order` for every template row of any status (no names, no prompts); and pure `detectTemplateAnomalies(facts): { anomalies: TemplateAnomaly[]; topicIds: string[] }` implementing V1-V4. The route wraps the call after commit in `try/catch`; on failure it logs a single `request.log.warn({ templateTeamId, err code only }, "template_anomaly_check_failed")` (no SQL text, SF1) and carries on. If anomalies are found it emits one `request.log.warn({ templateTeamId, anomalies, topicIds, correlationId }, "template_anomaly")`.

**Log entry content (S1, S2).** Ids and codes only. `anomalies` is the closed four-value enum; `topicIds` are UUIDs taken straight from the `id` column, capped at 50. The entry never carries `name`, `prompt`, `first_session_description` or any other row text, and the message is the literal constant `"template_anomaly"` (values go in object fields, never into the message string); a unit test pins that the entry's keys are exactly those four plus the logger's own bindings. Key names reuse the existing `{ templateTeamId, correlationId }` keys of the empty-template error log so one log query covers both. **`correlationId` source:** on the success path there is no error envelope, so there is no minted id to reuse. The value is `request.id`, Fastify's per-request id, which pino's `request.log` already binds as `reqId` on every line of that request (`session.draft_created`, `team.creation_denied_role`, etc.), so the entry joins to the rest of the request's lines. A fresh `crypto.randomUUID()` is explicitly not used, because it would appear nowhere else. (The empty-template error path keeps its envelope `correlationId`, unchanged.)

The sink is the application log, the same surface as the neighbouring `request.log.error` calls. Creation continues. A healthy template emits nothing. No `audit_log` row (security-oriented, adds a write to every creation, and the empty-template path rolls back and could not write one), no metric (no pipeline for this route), no facilitator-facing field (D11). **Accepted limitation (security):** a warn-level log is only a signal if someone reads it, and no alert exists. A persistent fault being noisy is not the same as it being detected. An alert on `template_anomaly` is recorded as a follow-up for when a log pipeline exists (task 5.4), not built here. The control that does not depend on a reader is the CI invariants test.

**Test shape.** `detectTemplateAnomalies` is covered by a table-driven unit test: empty template, healthy, gap, nonzero start, duplicates only (must not fire `non_contiguous_order`), archived default, archived non-default (fires `non_default_row`), more than 50 affected ids (cap). Integration assertions of "exactly one `template_anomaly` entry" capture logs with the repo's existing pattern: build the Fastify app with `logger: { level: "info", stream: { write } }` and parse the lines, as in `packages/backend/src/teams/__tests__/template-constraint-violation.test.ts` (no new infrastructure).

### Zero active defaults (D4)

With the filter, the copy inserts zero rows when the template has no active defaults, and `snapshotSessionTopics` throws `NoActiveTopicsError` exactly as before. The catch issues `ROLLBACK` and replies HTTP 500, code `internal_error`, with the existing plain-language message, `correlationId`, and no template id. An error-level entry names `templateTeamId`. No new status or code (503 rejected: the envelope convention here is 500 `internal_error`, and a new code churns frontend and tests). This change adds a test pinning status, code, message, no ids in the body, no stack, no SQL text and no `NoActiveTopicsError` class name in the body (the error is thrown from the snapshot layer), and no persisted team/topic/session/audit rows (C3). A uniform `internal_error` is deliberate: a distinct code would tell any authenticated facilitator that the template is damaged.

### Restore list (D5)

`defaultTopicsNotActive` becomes: active template defaults (the shared predicate on `dt`) left-joined to the team's topics by name; filter `team_topic_status !== 'active'` as today. The status filter is on `dt` only, never on `t`. Consequences, tested both ways (C5, C6): template default archived, team has no copy: absent. Template active, team holds an archived copy: present with `isArchived: true`. Template archived, team holds an archived copy: absent (the case only arises under a data fault or after an F5 retirement, which owns its semantics). The name-only join remains, with its known duplicate wart (D10, separate issue); this change does not reshape the join.

### Declined: template write trigger

Scope item 3 proposed a `BEFORE INSERT OR UPDATE OR DELETE ON topics` trigger that raises for the template team unless a session setting (for example `app.allow_template_topic_write = 'on'`) is set. **Decision (Devon, recorded on #215, D9): declined for now.** Reasons:

1. **Not a security boundary.** Anyone able to run SQL can set the opt-in. The threat is a trusted operator's mistake, not an attacker; the API threat is closed by #188 and #214.
2. **Residual risk after this change is silent content drift by whoever holds write access to the database.** With the copy fixed there is no 500, no resurrected row, and reordered baselines are normalised. Structural drift (names, positions, statuses, extra rows) and, with the extended baseline, content drift (below) is caught more cheaply by the invariants test.
3. **Cost.** Seed migrations 4 and 11 write the template; a trigger must come in a later migration, and every future default-topic migration (including F5 and wording fixes) must know to opt in, with migration numbers assigned across parallel branches so a stale branch can land a seed edit without it. `db:migrate` runs `--no-single-transaction`, so `SET LOCAL` needs an explicit `BEGIN` or a plain `SET` leaks to the pooled connection. Test suites mutate the template directly (snapshot and restore in `finally`) and would each need the opt-in or a shared helper; `down` migrations and `migrations-manual` scripts too. It is a schema change on a hot shared table for a fault that needs an operator to commit.
4. **No sanctioned writer until F5 (#216).** The opt-in only means something if exactly one code path (the Application Administrator maintenance path, after authorization and audit) sets it. Added now it is a string people paste; added with F5 it has a design: one function that sets the flag, one audit row, one place to review.

**Residual risk named as a risk (S4).** The same write capability that permits an honest operator mistake also lets an insider, or anyone holding the database credential, silently change the prompts every future team receives; a changed prompt is persuasive content delivered to all new teams. The anomaly log cannot see this (it checks ids, statuses and positions only). Mitigation here: the invariants test baseline is extended to `prompt`, `vote_type` and `first_session_description` (D8, below), which makes prompt drift detectable. **Limit, stated plainly:** that test runs against the CI database, so it detects a bad migration or seed, not a bad edit made directly in production. Production-side detection of content tampering is not provided by this change and is accepted until F5 (#216) puts template writes behind an audited path.

**Open item for the pre-production security review (deferred, not blocking #215):** least privilege. If only migrations edit the template, the application's runtime database role should not hold `UPDATE`/`DELETE` on sentinel rows. This change does not know the runtime role's grants on `topics`; the review confirms them and whether row-level separation of the sentinel is possible. This is a better control than the declined trigger and costs no application code.

**Substitute:** the template invariants test (C8), run in CI on every merge: it fails if a seed migration violates the baseline, and it documents the canonical set. **Revisit trigger (a condition, not a note):** the decline is acceptable only because F5 reopens it. Task 5.2 adds concrete acceptance lines to #216: (i) every template write goes through one audited function, and (ii) that function writes one `audit_log` row per template write (FR-8.1 maintenance is the first point where such a row can be required); (iii) the write guard is reconsidered in that design. If #216 is dropped or reshaped so these lines are lost, this decision lapses and the trigger is to be reopened. **If the team later wants defence in depth first**, the minimum viable form is: a new migration numbered after all current seeds, opt-in via `SET LOCAL` inside an explicit transaction, one shared test helper, and header comments in migrations 4 and 11 pointing at the rule. I would not block it, and would not spend the complexity budget on it before F5.

### Template invariants test (D8)

New integration test, failure messages name the violated invariant: (a) active default count equals N and names equal the baseline list in the test; (b) active default positions are exactly 1..N; (c) zero default rows with status other than `active`; (d) zero non-default rows on the template; (e) zero memberships and sessions on the sentinel: a count kept so a failure message names the invariant, even though migration 23's CHECKs on sessions and memberships already enforce it at the database (this is an intentional duplicate, not a claim of non-duplication); (f) for each baseline name, `prompt`, `vote_type` and `first_session_description` equal the baseline (S4). For (f) the baseline holds, per topic, `{ name, vote_type, promptSha256, firstSessionDescriptionSha256 }` hashes rather than full prose, so the test file stays small and a diff shows only that content changed; the hashes are computed from the seeded text in migrations 4 and 11 and the existing requirements topic list, and an implementer who finds the prompt text is not in the requirements list falls back to hashing the migration-seeded text and notes that in the file header. The list lives in this test and the existing requirements topic list; no third copy of the prose. The test is the CI-time control only (see Declined, S4).

**Serialization (decided).** This test asserts an absolute baseline, and `default-topic-provisioning-integration.test.ts` swaps the template's default rows for a fixture set; Vitest runs files in parallel by default (`vitest.config.ts` sets no `fileParallelism`/pool option), so an unguarded invariants test would fail nondeterministically. Decision: a small shared test helper `withTemplateLock(fn)` takes a Postgres session-level advisory lock (a fixed bigint key constant in the helper) on a dedicated client, runs `fn`, and releases in `finally`. It is held by: the invariants test, every test that mutates the template (the existing provisioning test, plus the new tests that archive or add template rows: C1, C4/C11 template cases, C5-C7, C9), so they run one at a time across worker processes. Rejected: setting `fileParallelism: false` globally (slows the entire backend suite for a three-file problem); a separate Vitest project listing the template-mutating files (config churn, the list silently rots when a new file is added, whereas the helper is opt-in at the point of mutation and visible in review). Tests that only *create teams* against the template without mutating it do not take the lock; they must derive expectations from a snapshot taken in the same test (never from the baseline list), so a concurrent swap cannot fail them on it.

## Risks / Trade-offs

- **Parallel tests mutate the shared template** (#188 design Risks still apply). Serialized by `withTemplateLock` (D8 above). Tests that archive or reorder template rows reuse #188's snapshot-and-restore-in-`finally` helper, restoring `display_order` by negate-then-set because of the partial index. Do not write a second helper. That helper restores only by snapshot id and does **not** restore `name`, `prompt`, `is_default` or `first_session_description`: tests that insert extra template rows (an archived default, an active same-name row) must delete them in `finally`, and must not change those columns on existing rows. Template-mutating tests that create a team assert against a snapshot taken in-test, not the baseline.
- **Duplicate active positions: route-level testing is not possible, by design.** The row-level duplicate case needs `topics_team_active_order` dropped. `DROP INDEX` is transactional in Postgres, but only for the client that ran it: the route takes its own connection from the pool (`db.connect()`) and will not see an uncommitted drop or uncommitted duplicate rows, and `DROP INDEX` holds `ACCESS EXCLUSIVE` on `topics`, so an `app.inject` awaited while the test transaction is open blocks on that lock and hangs until timeout (it would look like flakiness, not a failure). Do not attempt it. The required duplicate test is therefore at function level on one client: `BEGIN; SET LOCAL lock_timeout = '2s'; DROP INDEX topics_team_active_order; insert two active default rows at the same position on a scratch team; copyCanonicalDefaults(client, newTeamId, scratchTeamId); assert the new team's positions are 1..n ordered by source id; ROLLBACK`, in a `finally` that always rolls back and releases the client. Rules: nothing but that client is awaited inside the transaction (no `app.inject`, no other pool use), so the lock window is milliseconds; `lock_timeout` makes a contended run fail fast rather than hang. **Guard:** the helper refuses to run (throws before issuing `BEGIN`) unless running under Vitest (`VITEST` set; not `NODE_ENV`, because the CI workflow sets `NODE_ENV=development`) and the `DATABASE_URL` host is `localhost` or `127.0.0.1`, because the lock must never be taken against a shared or production database. Before writing the test, the implementer checks `topics` for any other constraint or trigger (for example `(team_id, name)` uniqueness) that would reject two scratch rows, and picks distinct names if so. The route-level C4 cases that need no index drop still run through the route: gap {1,3,7}, nonzero start, and the archived/active collision at one position. The pure detector (`duplicate_active_order`) is covered by the table-driven unit test.
- **Regression assertion change (C9).** `template-team-creation-regression-integration.test.ts` currently compares against `is_default = true` rows of all statuses; update to active-only and compare positions as renumbered.
- **Restore regression risk.** A filter on the wrong alias (`t.status`) would hide the restore case; both directions are tested (C6).
- **Forward-only.** Teams created while the bug was live may hold a resurrected topic; see D7 check. Silent-case discovery only.
- **Snapshot order (C12).** The snapshot runs after the copy in the same transaction (`lockTeamTopics` then `snapshotSessionTopics`); a test asserts session topic order equals team topic order.

## Notes on specs and consumers

- The `topic-customization-lock` delta is ADDED, not MODIFIED: that spec holds only a non-normative implementation note about `defaultTopicsNotActive`, so there is no requirement header to modify. The ADDED requirement states that it supersedes the note where they differ. It is wording only; no access rule (TOPIC-002 arms, 403/404 codes, audit rows) changes.
- No UI consumer reads `defaultTopicsNotActive` today (`topic-management-screen` says the screen must not). C5-C7 protect the API contract. Facilitator-side FR-8.6 is served by the screen's own archived list; this change does not extend or claim to close it.

## Migration Plan

No migration, no data change, no flag. Deploy is a plain code release. Before merge: the D7 read-only query (pass criterion: count 0 proceeds; more than 0 means a remediation issue number is recorded in `tasks.md` before merge and Rachel is told in one line). The exact SQL, so the check is repeatable, is in `tasks.md` 1.2; in short, run inside `BEGIN READ ONLY`, count first, and list row ids only (not team names) if the count is above 0, since the output must not be pasted with team identifiers into a public issue. A remediation issue records whether any of the surviving rows have votes or session history attached, because a naive repair would then delete data and the pre-merge browser spot check (create a team, confirm twelve topics in order, archive one of the team's own defaults, confirm it appears under restore, restore it). Rollback is reverting the commit.
