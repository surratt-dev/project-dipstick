## Context

Sign-in today: an unauthenticated request to any route triggers `AuthContext.tsx`'s unconditional `401 → window.location.href = "/auth/login"`, which redirects to the IdP's authorization endpoint. Locally, the IdP is the `node-oidc-provider`-based stub in `docker/oidc/server.js`, and it presents its library-default `devInteractions` form — a generic username/password screen with no concept of "persona." The four seeded accounts (`participant-001`, `facilitator-001`, `manager-001`, `admin-001`) exist only in that stub's in-memory account store (`docker/oidc/server.js:8-33`); there is no corresponding row in `packages/backend/migrations/4_seed_data.sql`. Logging in as `manager-001` today produces an ordinary First Access user with no team memberships — the "Manager" label describes intent, not a guarantee.

`resolveOrCreateAccount` (`packages/backend/src/auth/account-resolver.ts:88-133`) already re-derives `users.global_role` from an ID token role claim (`OIDC_ROLE_CLAIM`, default `role`) on every login, allowlisted via `PERMITTED_GLOBAL_ROLES` to `engineer` / `engineering_manager` / `application_admin`. `isPrivateAddress()` (`config.ts:22-46`) is already the fail-closed, startup-time judgment call for "is the simulated IdP allowed to back this deployment" — `loadConfig()` calls `process.exit(1)` if `NODE_ENV === "production"` and `OIDC_ISSUER` resolves to a private/local address. Both are reused here rather than reimplemented.

Constraints carried forward from exploration (not re-litigated): none of the four load-bearing ritual rules (no-manager-participation, simultaneous reveal, facilitator-from-another-team, no individual-level data surfacing) are enforced anywhere near authentication, so this stays orthogonal to them by construction — but the implementation must keep it that way, not just the intent.

## Goals / Non-Goals

**Goals:**
- Eliminate manual account-id/password entry for local sign-in without adding any new bypass of the Authorization Code + PKCE exchange.
- Make `manager-001` and `admin-001` behave as their labels claim (real `global_role` values) using only the existing role-claim mechanism.
- Keep exactly one source of truth for "is the dev shortcut active," checked identically at initial sign-in and at post-logout redirect.
- Make the landing page unmistakably scaffolding — never a UX pattern a real user could confuse with the product.
- Fail closed and fast in production: no added latency, no new failure mode, no data access on the disabled path.

**Non-Goals:**
- Backend-minted sessions that skip the IdP round-trip (rejected — see Decisions).
- Seeding `facilitator-001` with a real `facilitator` global role (would require expanding `PERMITTED_GLOBAL_ROLES`, a role-assignment/session-participation decision out of scope here).
- Team-scoped facilitator fixtures for testing facilitator-from-another-team enforcement (separable local-dev fixture work; earns its own proposal if wanted).
- Bespoke multi-session-in-one-tab machinery for concurrent persona testing (browser contexts already isolate sessions; nothing to build).
- Any new or divergent audit-event shape for persona logins.

## Decisions

**D1 — `login_hint` passthrough + IdP-side auto-approve, not a backend-minted session.** The shortcut only ever decides which account the IdP's interaction screen auto-selects. `auth.ts` and `oidc-client.ts` are untouched: state generation, nonce, PKCE, the atomic `getdel` single-use state check, `sub`/`iss` claim validation, `session.regenerate()`, and all audit events fire exactly as they would for a manually-typed login. `login_hint` is a standard, inert OIDC parameter — a real IdP either cosmetically pre-fills a field with it or ignores it outright; it can never cause a real IdP to skip authentication. Alternative considered and rejected: have the backend mint a session directly from a `loginHint` and skip the IdP exchange. Rejected because it puts a live authentication bypass inside `auth.ts` itself — the security-relevant code all real logins share — rather than confining the shortcut to the throwaway stub container.

**D2 — Double gate on `/auth/dev-login-options`, evaluated independently.** The endpoint checks both `isPrivateAddress(config.OIDC_ISSUER)` AND `config.NODE_ENV !== "production"` explicitly, not one alone. `isPrivateAddress` is currently a private, unexported function in `config.ts`; making the endpoint call it directly requires exporting it (one word, `export`) — reusing the same already-trusted judgment, not reimplementing the private-address check inline in `auth.ts`, which would quietly defeat the point of this decision. Today these are equivalent in practice — production refuses to boot with a private-address issuer — but that equivalence is enforced by a different code path (`loadConfig`'s fatal exit) than this endpoint. If a future refactor of `loadConfig()` drops that exit, a single-gate endpoint would silently become the last line of defense without anyone knowing it depended on the invariant. Two independent checks that happen to agree today is cheap insurance against one being removed tomorrow unnoticed. On any gate failure: `404`, no body, no Redis/DB access.

`isPrivateAddress` is now load-bearing for two independent security purposes (the production-boot guard and this gate) rather than one. Its coverage is narrower than its name implies: IPv4 literals in the three RFC 1918 ranges plus the literal strings `localhost`/`127.0.0.1`/`0.0.0.0` — no IPv6 (`::1`, `fc00::/7`, `fe80::/10` all fall through to `false`), no DNS resolution of a hostname that resolves to a private address, no handling of decimal/octal/hex-obfuscated IPv4 literals. The fail-closed direction is the one that matters for both call sites (an unrecognized-as-private issuer causes production to refuse to boot, and causes this gate to 404), so this is not a defect in either use — but it means a future local stack configured with an IPv6 issuer or a DNS alias would silently never qualify for the dev shortcut, which fails safe but could be confusing to debug. This change adds a one-line comment at `isPrivateAddress`'s definition in `config.ts` stating its known scope, so the next reuse doesn't have to re-derive this by reading the implementation.

**D3 — Frontend timeout bounds the extra round-trip, in every environment.** `AuthContext.tsx` calls `/auth/dev-login-options` before its existing 401-redirect, for all users, since the frontend cannot know in advance whether the backend is gated off. A 300ms client-side timeout caps this: a miss behaves identically to a 404, proceeding straight to the existing `/auth/login` redirect. 300ms because this is a same-origin call to a server that either says "no" instantly (production, no I/O) or sits directly in the local dev stack — anything slower is itself a signal something's wrong, and production sign-in must never be made to wait on it.

**D4 — Manager/admin role via existing claim mechanism, not new seed infrastructure.** Per `openspec/specs/session-participation/spec.md`, the no-manager-participation check is `users.global_role = 'engineering_manager' OR team_memberships.role = 'engineering_manager'` — an OR, so `global_role` alone is sufficient to trigger the block. Adding a `role` claim to `manager-001` (`engineering_manager`) and `admin-001` (`application_admin`) in `docker/oidc/server.js` is the entire change; `mapRoleClaimToGlobalRole` does the rest on next login, re-evaluated every sign-in exactly as a real IdP's claim would be. Alternative considered and rejected: a new database seed script populating `team_memberships`/`global_role` rows directly. Rejected as more machinery than the two accounts that matter need, and as bypassing the claim-mapping code path this change should be exercising, not routing around.

**D5 — `facilitator-001` explicitly not seeded; landing page states the gap.** `facilitator` is not in `PERMITTED_GLOBAL_ROLES`. Closing that gap means either expanding the claim allowlist (changes what a real IdP's role claim is trusted to assert — a role-assignment decision, not a login-convenience one) or bespoke seed infrastructure the other three accounts don't need. Both rejected as scope creep. The Facilitator button is labeled by account id alone (not role name), with an inline caveat: "Role not seeded — signs in as a default user, not a Facilitator. Single identity; does not test cross-team facilitation (see docs)." Single source of truth for "is this persona unseeded": `/auth/dev-login-options` returns a `seeded: boolean` per option, and the frontend renders the caveat whenever `seeded === false` — the frontend does not hardcode a per-account-id list of which personas are unseeded, so the two sides cannot drift apart on the same fact.

**D6 — One gate, checked at both call sites.** Post-logout redirect target (persona landing page vs. generic form) branches on the same `/auth/dev-login-options` check as the initial 401-redirect, not a second independently-maintained "are we local" signal. Prevents the two call sites from drifting apart over time.

**D7 — Landing page is deliberately unpolished scaffolding.** Full-width banner in a non-product color treatment reading "LOCAL DEV ONLY — PERSONA LOGIN," four buttons labeled with role name and account id (Facilitator: account id + caveat only), a one-line note beneath the buttons stating that each button starts a normal sign-in and concurrent multi-persona testing requires separate browser profiles or incognito windows, a plain "Sign in manually" link to unmodified `/auth/login`, nothing else — no app navigation, no shared styling with any real screen. This is the inverse of the product's own design goal (session UI should disappear into the background); here, looking obviously like scaffolding is the point, so nobody mistakes it for a pattern worth carrying into a real environment or proposes it "for demos." The multi-persona note appears on the page itself, not only in `docs/local-development.md` — exploration-notes.md Decision 3 committed to both, on the reasoning that silence on the page (not missing functionality) was the actual gap; docs-only would be a silent narrowing of that decision.

**D8 — No new audit event path, but a boolean presence flag on the existing initiation event.** Because the callback path is unmodified, `auth.success`, `auth.first_access_created`, `auth.session_created`, etc. fire identically for persona-shortcut and manually-typed logins — no `via: "persona-shortcut"` field or equivalent on those events; the audit log shouldn't need a special case to describe a real OIDC assertion accurately, and a field that only ever fires in an unaudited environment isn't worth maintaining forever. `GET /auth/login`'s existing `auth.authorization_initiated` event does gain one field: `hasLoginHint: Boolean(loginHint)`, mirroring the identical `hasJoinContext: Boolean(joinToken)` boolean the same event already logs (`auth.ts:50-54`). This is not a new event and not a value exclusive to an unaudited environment — it's `false` on every production request as a structural fact, and it's the one forensic signal that would let an investigator reconstruct which sign-ins arrived via the persona shortcut if the weaker IdP-side auto-approve (see D11's context) were ever abused on a reachable non-production box. Narrow enough not to conflict with this decision's intent to keep the callback-path events persona-unaware.

**D9 — Landing page renders behind a new public client route, not inside `AuthProvider`.** `AuthContext.tsx` today does a hard `window.location.href = "/auth/login"` browser navigation from inside `fetchSession()`; `AuthProvider` is a pure context (`<AuthContext.Provider>{children}</AuthContext.Provider>`) and renders nothing conditionally — the "show nothing until authenticated" gating is `ProtectedRoute`'s job, and `ProtectedRoute` only wraps some routes (`/auth/error`, `/auth/loading`, `/join-error` sit outside it, per `App.tsx`). Two ways to land the persona landing page: (a) grow `AuthProvider` into rendering a full-page UI itself, branching on landing-page-vs-children; or (b) keep `AuthContext`'s existing, narrow responsibility — decide where to navigate — and add a new public client route that owns the landing page component.

This design adopts (b). `AuthProvider` wraps every route including `/auth/error` and `/join-error`; option (a) would mean the persona landing page could render on top of those pages too, unless something explicitly excluded it — and `/auth/error` already has a pre-existing, unrelated issue where today's unconditional redirect-on-401 can clobber it, which (a) would inherit and entangle with this change rather than leave alone. Option (b) is also less code and matches the existing pattern (`/auth/error`, `/auth/loading` are already public, `ProtectedRoute`-external routes).

Concretely: a new route `/auth/dev-login`, registered in `App.tsx` alongside `/auth/error` and `/auth/loading` (outside `ProtectedRoute`, no shared layout), renders the persona landing page component. `AuthProvider` sits inside `BrowserRouter` already (see `App.tsx`), so `fetchSession()`'s 401 branch can use React Router's `useNavigate()` for this specific case — a client-side transition to `/auth/dev-login` — while the existing miss/timeout path is left as the unmodified `window.location.href = "/auth/login"` hard navigation (required there regardless, since `/auth/login` is a backend route that issues its own redirect to the IdP). `AuthContext`'s job stays exactly what it is today: deciding where to navigate on 401, never what to render.

**D10 — The auto-approve interaction handler must resolve both the login and consent prompts.** `node-oidc-provider`'s `devInteractions` (the feature this change replaces) handles two interaction reasons, not one: `login` and `consent`. This client requests `offline_access`, which routes through the consent prompt on top of login — so today, a manual sign-in through the stub already clicks through two `devInteractions`-rendered screens. A handler that only auto-resolves `login` and falls through to a manual "allow access" consent screen technically satisfies "falls back to a form" but defeats the feature's actual goal: every persona button would still end on a manual click, not a one-click sign-in. The custom handler must call `provider.interactionFinished()` for both the `login` and `consent` interaction reasons when `login_hint` matches a known account id — either by resolving both in sequence within the same request flow, or confirming (and locking in with a test) that resolving `login` for this client auto-resolves `consent` as well. This is real implementation work — an interaction route that intercepts before `devInteractions`' own router, correct `interactionDetails()`/`interactionFinished()` sequencing, and a clean fallback — not a config flag flip.

**D11 — Bind the local OIDC container's port to loopback as part of this change; leave `postgres`/`redis` port bindings as a separately tracked, pre-existing issue.** `docker-compose.yml`'s short-syntax port mappings (`"4011:4011"` for `oidc`, and the same pattern for `postgres`/`redis`) publish on all host interfaces (`0.0.0.0`) by Docker's default, not loopback-only. This is pre-existing and independent of this change, and on a shared devbox, cloud dev VM, or any host with a routable interface, the mock IdP is already reachable by more than the developer who started the stack. D2's double gate protects the Dipstick *backend's* willingness to offer the shortcut; it does nothing for the IdP *container's* own network exposure, which has no gate of its own.

Today, someone reaching the exposed stub still has to submit a shared password through `devInteractions`' form. After D10's auto-approve handler ships, the same someone can authenticate as `admin-001` with a single unauthenticated `GET` carrying `login_hint=admin-001` — no credential of any kind, trivially embeddable in a link. This change is what removes that friction, so this change is where the mitigation belongs: `docker-compose.yml`'s `oidc` service port mapping changes from `"4011:4011"` to `"127.0.0.1:4011:4011"`. This is a one-line change with no functional cost — local development already reaches the stack via `localhost`, so binding host-only changes nothing about how a developer on the same machine uses it, and it directly closes the exposure this change amplifies.

`postgres` and `redis`'s equivalent port-binding exposure is real but pre-existing, unrelated to authentication, and out of scope for a login-convenience change — fixing it here would be scope creep into general `docker-compose.yml` network posture. It's named explicitly in Risks below as an accepted, tracked-separately gap rather than left implicit.

**D12 — `loginHint` is validated against the known seeded account ids before being forwarded; anything else is a `400`.** No length or character constraint was previously stated on `loginHint` before it becomes the OIDC `login_hint` authorization parameter. `openid-client`'s `buildAuthorizationUrl` uses standard `URLSearchParams` encoding, so there's no injection risk into the URL structure, and `login_hint` is inert for a spec-compliant IdP by construction (D1). Still, an unbounded string reflected into a redirect to a third-party endpoint doesn't need to be unbounded: `GET /auth/login` validates `loginHint`, when present, against the closed set of known seeded account ids (`participant-001`, `facilitator-001`, `manager-001`, `admin-001`) and returns `400` for anything else, rather than passing an arbitrary string through. This is cheap, removes an open question, and matches the closed, four-entry account set the local stub's own interaction handler (D10) looks up against.

## Risks / Trade-offs

- [A future refactor of `loadConfig()` removes the production-boot guard, and someone forgets `/auth/dev-login-options` implicitly depended on it] → Mitigated by D2: the endpoint checks `NODE_ENV` itself, redundantly, rather than trusting the guard transitively.
- [The `/auth/dev-login-options` pre-check adds latency or a new failure mode to production sign-in] → Mitigated by D2 (fast 404, no I/O) and D3 (300ms client timeout, fail-open to existing redirect).
- [The landing page looks polished enough that someone proposes reusing it in staging] → Mitigated by D7's deliberate visual distinctness; not a technical control, so this is a design-review checkpoint at implementation time, not something tests can enforce.
- [A contributor reads the Manager/Admin buttons as fully authoritative and misses the Facilitator caveat] → Mitigated by D5's inline, non-tooltip caveat text directly beneath the Facilitator button, plus `docs/local-development.md` stating the same gap.
- [`docker/oidc/server.js`'s new login_hint-aware interaction handler has a bug that silently accepts an unrecognized hint] → Falls back to the existing password form when `login_hint` is absent or unrecognized (explicit fallback branch, not a default-allow); this is local-only stub code with no production exposure regardless.
- [`postgres`/`redis`'s `docker-compose.yml` port mappings also publish on all host interfaces, the same underlying exposure D11 fixes for `oidc`] → Accepted as out of scope for this change: it's pre-existing, unrelated to authentication, and general `docker-compose.yml` network posture is a repo-wide concern, not a login-convenience one. D11 fixes `oidc` specifically because this change is what removes the credential-entry friction that made that exposure meaningfully worse; the same reasoning doesn't apply to the database and cache ports. Worth a follow-up change scoped to the repo's general port-binding posture.
- [Confirmed, not a live risk: `/auth/dev-login-options` returns 200 and the subsequent `/auth/login` redirect it implies then 404s] → Cannot happen at runtime. Both checks read the same in-process `config` object, computed once at boot (`loadConfig()`) and never mutated; `/auth/login` is also unconditionally registered regardless of environment. No window exists where the gate passes and the route it gates disappears.

## Migration Plan

No production migration — this change ships entirely in dev-gated code paths (`docker/oidc/server.js`, the double-gated `/auth/dev-login-options` endpoint, and frontend logic that fails open to today's behavior on any non-200/timeout) plus a `docker-compose.yml` port-binding change (D11) that only affects local Docker networking. No database schema changes. No feature flag needed: the existing `isPrivateAddress`/`NODE_ENV` gates are the flag. Rollback is a plain revert; nothing to migrate backward.
