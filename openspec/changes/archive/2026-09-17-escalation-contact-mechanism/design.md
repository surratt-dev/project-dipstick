## Context

Two escalation messages on the member management view ("Contact your admin," `MemberManagement.tsx:239-241` for TEAM-005 role-assignment and `:445-447` for TEAM-006 EM-association) currently satisfy the BRD's minimum-acceptable text but not FR-1.6a's actual requirement: a specific, resolvable contact path. This was a named, tracked gap at the time TEAM-005/006 shipped — Rachel Okonkwo's (VP Engineering) sign-off on TEAM-006 being admin-only was explicitly conditioned on this escalation path being built, not deferred — and both specs already document the gap in a "Preferred (not yet implemented)" / commented-risk form.

Exploration (`exploration-notes.md`) established the following as resolved fact, not open question, and this design treats them as fixed inputs:

- **No session-start blocking.** Neither escalation site gates session creation today (`sessions.ts` never queries role-assignment or manager-association state in the session-creation path). This change is a "resolve before your next session" affordance, not a gate, and must not become one — a blocking modal would also violate the passive-text constraint below.
- **[SUPERSEDES the two bullets below, and Decision 1] Stakeholder decision (2026-09-16): the Application Admin contact point is a single configured alias, not an enumerated roster.** The blocking pre-implementation gate this design originally carried (former Open Questions #1/#2 — real admin headcount, and reconfirming the July 2026 threat-model assumption against a full-roster disclosure) is resolved by eliminating the question rather than answering it: the contact point is one configured value (e.g. `APPLICATION_ADMIN_CONTACT_EMAIL`) — explicitly a mailing list / shared inbox / equivalent collection point, not an individual's personal email — set once per deployment, independent of how many real users hold `global_role = 'application_admin'`. This is the design's previously-rejected Option B, now adopted; see the rewritten Decision 1.
- **The zero-real-admin-roster edge case and the seed `System`-account exclusion concern are moot under the new design, resolved by elimination rather than by a fix.** Both were about a database query enumerating `global_role = 'application_admin'` users — `global_role` is still an IdP-asserted claim re-written on every login (`account-resolver.ts:118-130`) with no in-app promote/demote UI, and the seed sentinel `System` account (`00000000-0000-0000-0000-000000000001`) still exists and still holds that claim, but neither fact matters here any more, because this design no longer runs a query that could return zero rows or an unwanted `System` row. The equivalent question in the new design is not "how many real admins exist" but "is the configured contact-alias value set" — see Decision 4.
- **`mailto:` satisfies FR-1.6a's "email address."** It's the more actionable rendering of the same mechanism, not a weaker substitute requiring "equivalent mechanism" justification.
- **The two escalation sites are asymmetric**, not copies of each other: TEAM-005's authorized-actor set is Application Admin *or* an active EM for that team; TEAM-006's is Application Admin only. This shapes the decisions below.
- **A team can have more than one associated EM.** `team_memberships_active_unique` (migration 7) is a partial unique constraint on `(user_id, team_id) WHERE removed_at IS NULL` — unique per *user*-team pair, not per team. Nothing prevents two different users from each holding an active `engineering_manager` membership for the same team. `MemberManagement.tsx` already renders this as a list (`engineeringManagers.map(...)`, `:452` on) and `TeamMembersResponse.engineeringManagers` (`packages/shared/src/types/team.ts:73`) is typed `TeamMember[]`, plural. The TEAM-005 EM-fallback branch below must resolve for zero, one, or many EMs, not assume exactly one.

## Goals / Non-Goals

**Goals:**
- Every "you can't do this" escalation message on this view resolves to an actual, actionable contact — a `mailto:` link to the configured Application Admin contact alias, or (TEAM-005 with an EM present) the EM's existing on-page identity — never a dead end.
- The unconfigured (unset/empty) Application Admin contact-alias state renders a named, honest fallback instead of silently reintroducing the unhelpful pattern this change exists to eliminate.
- The rewritten task-4.3 test suite can only pass against a component that actually surfaces a mechanism — not against the old wording with cosmetic additions.

**Non-Goals:**
- No new interactive UI (request forms, "message an admin" flows, modals, notifications). This stays passive text, matching the existing `access-model-statement` pattern.
- No facilitator-continuity tracking (whether the next facilitator can see that escalation was already requested by someone else). Real gap, real complexity (its own data model and UI surface) — recommended as a separate follow-on issue.
- No general-purpose admin directory or admin-management UI. This surfaces just enough identity data to make the two escalation messages actionable.
- Does not reopen the TEAM-006 admin-only decision (Q2) — the TEAM-006 contact path resolves to Application Admin only, never to an EM, even though an EM may exist for that team in a display-only capacity elsewhere on the page.

## Decisions

### Decision 1: Application Admin contact is a single configured alias, not enumerated individual identities

**Superseded 2026-09-16 by stakeholder decision.** The original version of this decision added a backend code path exposing individual `users.global_role = 'application_admin'` identities (name + email, enumerated) to non-admin callers, gated by the "how many admins do we show, and is that too many named privileged accounts to make ambiently discoverable" tradeoff — Option A in the original exploration. That tradeoff no longer needs resolving: the stakeholder decision adopts **Option B** instead — a single configured contact address (e.g. an environment variable or app-config entry such as `APPLICATION_ADMIN_CONTACT_EMAIL`) — explicitly documented as a mailing list, shared inbox, or equivalent collection point, **not** an individual's personal email address. This sidesteps the headcount/blast-radius tradeoff entirely rather than answering it: there is no "how many named privileged accounts are ambiently discoverable" question to evaluate, because no individual identity is ever disclosed by this mechanism.

**What this removes from the design** (the original Decision 1/3/5 surface area):
- No `AdminContact` type and no roster query in `teams.ts` — there is nothing to enumerate.
- No seed `System`-account exclusion logic (Context, above) — there is no query for it to pollute.
- No viewer-state gating (see the rewritten Decision 5, below) — a shared alias isn't privileged, individual PII, so there's nothing to gate by caller authorization.
- No headcount-driven format-reconsideration trigger (the original Decision 3 asked "if headcount comes back large, revisit Option B") — Option B *is* the design now, unconditionally.

**What replaces it:** `GET /api/v1/teams/:teamId` (TEAM-003) gains a field carrying the configured contact value — see the rewritten Decision 5 for the exact shape and for the backend-vs-frontend placement judgment call. The legacy `GET /api/v1/teams/:teamId/members` endpoint remains explicitly out of scope, unchanged from the original rationale: it is unused by `MemberManagement.tsx` and marked `@deprecated` in `packages/shared/src/types/team.ts`.

**In-app request/message flow (Option D):** still rejected, rationale unchanged — this is a new messaging/notification system, not a contact-mechanism fix, and is a much bigger UI surface than the "disappears into the background" constraint tolerates.

### Decision 2: The two escalation sites get different contact-resolution logic, not one shared component

- **TEAM-006 (EM-association escalation):** always resolves to Application Admin contact. There is no EM fallback here by design — Application Admin is TEAM-006's only authorized actor (Q2, resolved), and pointing this contact at an EM would quietly reopen that decision.
- **TEAM-005 (role-assignment escalation):**
  - When the team has exactly one associated EM, the escalation resolves to that EM's identity — already fetched and rendered a few lines down on the same page (`em.email`, `MemberManagement.tsx:469`). No new backend call; this is read-reuse of data already on the page.
  - When the team has **more than one** associated EM, the escalation lists all of them, comma-separated, in the same single-inline-line, no-directory-layout visual register Decision 3 establishes for this feature — reused here for its *register* only. (There is no longer a multi-*admin* case for this to literally extend, since the Admin side is now a single static configured contact — Decision 1 — but the "don't let this become a list" rationale applies identically to multiple EMs.) This branch exists because the data model permits multiple active EMs per team (`team_memberships_active_unique` is per user-team pair, not per team; see Context) and `MemberManagement.tsx` already renders `engineeringManagers` as a list. Still no new backend call — the same on-page EM data is reused, just iterated instead of singular.
  - When the team has **no** associated EM (including the TEAM-005/TEAM-006 stacked case — a facilitator lacks role-assignment permission *and* no EM exists to fall back to), TEAM-005 falls back to the same Application Admin contact mechanism TEAM-006 uses.

These are kept as two separate code paths rather than one shared "escalation contact" component, because they have genuinely different authorized-actor sets and different fallback chains (TEAM-005: EM → Admin → unconfigured-contact fallback; TEAM-006: Admin → unconfigured-contact fallback only). A shared component would need a branch for "does this site have an EM fallback tier" anyway — that branch is the actual difference between the two requirements, and hiding it inside a shared component makes it easier to accidentally collapse the two paths later (e.g., a future edit that "simplifies" TEAM-006 into reusing TEAM-005's EM branch, which would reopen Q2). Implementers may still factor out shared rendering (the single-line `mailto:`-link markup) — the fork is in resolution logic, not necessarily in JSX.

*(This decision — the EM-reuse branch and the TEAM-005/TEAM-006 fork — is unaffected by the 2026-09-16 configured-alias decision and is carried forward unchanged except for the terminology update above: "zero-admin fallback" is renamed "unconfigured-contact fallback" throughout this document, since there is no longer an admin roster to be zero of.)*

### Decision 3: Rendering format — one inline line, no directory layout

The Application Admin contact renders as a single line of text in the same visual register as `access-model-statement`: one `mailto:` link to the configured contact alias (working draft: "Contact the Application Admin team at [mailto link]" — exact copy per task 1.3), no card, no bulleted or numbered list, no vertical stacking. Because the contact is now exactly one configured value rather than an enumerable roster, the original "comma-separated multiple entries" concern no longer applies to the Admin side — there is nothing to enumerate.

This single-inline-line, no-directory-layout register remains the applicable pattern for TEAM-005's multi-EM case (Decision 2): when more than one EM is associated, their names/emails still render comma-separated on one line. The moment that becomes a list with its own visual rhythm, it stops being passive text and becomes a directory — the exact UI-chrome outcome this change is supposed to avoid. Only the Admin-side enumeration this decision used to also govern has been removed; the underlying rendering-register rule is unchanged.

### Decision 4: Unconfigured Application Admin contact-alias fallback copy

When the configured contact value (`APPLICATION_ADMIN_CONTACT_EMAIL` or equivalent) is unset or empty, both escalation sites render:

> "No Application Admin contact is currently configured for this application. Contact your engineering leadership directly."

This reframes the former "zero real admins in the roster" question — a data question about a roster this design no longer queries — as a configuration question: is the value set? The fallback trigger is now a simple presence check on one config value, not a `COUNT(*)` over a filtered user query. Whether to additionally validate that the configured value looks like a plausible email address, versus trusting deployment-time configuration as-is, is a non-blocking implementation judgment call (see Open Questions) — not required for this decision to stand.

This is a placeholder for final review (see open questions) but is not itself a placeholder bug in the task-3.10 sense — it names the actual system state and gives a real, if generic, next step, rather than repeating "Contact your admin" with nothing after it.

### Decision 5: No viewer-state gating needed — the configured contact value is a required, always-present field

**Superseded 2026-09-16 by stakeholder decision.** The original version of this decision gated backend inclusion of Application Admin identity on the requesting caller's own authorization (`!canAssociateManagers`), because individually-named Application Admin identity was highest-privilege PII being exposed to non-admins for the first time, and had to be withheld from any caller who didn't specifically need it (security review Finding 1). **That gating no longer applies, and is removed.** A configured shared-inbox alias is not privileged, individual PII — it is the same address every employee is meant to be told to email, the moment any of them needs to. There is nothing left to gate: the field carrying the configured contact value is populated **unconditionally, for every caller**, admin and non-admin alike.

This actually resolves the tension the original decision had to argue its way around. The engineering review had recommended always populating `applicationAdmins` unconditionally, the same way `engineeringManagers` already is, to eliminate an entire class of conditional-population bugs — and the original Decision 5 explained at length why that instinct, correct for EM data, didn't transfer to Admin data (EM identity was already visible to every team member regardless of this change; Admin identity was new exposure, so unconditional population would have meant every request carried the full privileged roster whether needed or not). That argument depended entirely on Admin identity being sensitive per-caller exposure. It isn't, any more: the "no new exposure, so populate unconditionally" reasoning that already applied to `engineeringManagers` now applies to the Admin-contact field too, for the same reason. Gating logic, and the backend/frontend synchronization risk it existed to manage, are both removed rather than replaced.

**Type and shape.** No `AdminContact[]` type is needed. `TeamMembersResponse` gains a single field carrying the configured value:

```ts
applicationAdminContactEmail: string | null;
```

`null` means "not configured" (Decision 4's fallback trigger); a non-null string is the configured address, rendered as a `mailto:` link. Because there is no longer any viewer-gating, there is no "two possible causes of an empty value" ambiguity the original decision had to resolve for `applicationAdmins: []` (genuinely-zero-admins vs. caller-doesn't-need-it) — `null` here has exactly one meaning, and no runtime sentinel or required-vs-optional argument is needed to establish that.

**Backend vs. frontend placement — judgment call.** This value could in principle be read directly at the frontend build boundary (e.g. a Vite-injected `import.meta.env` value) instead of round-tripped through the backend response. This design keeps it backend-sourced, for consistency with how every other deployment-time configuration value in this codebase is already handled: `packages/backend/src/config.ts` is the single source of truth for env-derived config — `APP_ORIGIN`, `OIDC_ROLE_CLAIM`, etc. are all declared in its `optional` key list, read once at boot, and exposed to consumers via small getters (`getAppOrigin()`, `getAllowedOrigins()`) or, as here, via an API response field. There is no existing precedent anywhere in `packages/frontend` for reading configuration directly from `import.meta.env` or `process.env` — introducing one here would create a second, parallel configuration mechanism for a single string value, and would mean rotating the support alias requires a frontend rebuild and redeploy rather than a backend config/env change and restart. Backend-sourced wins on architectural consistency and operational ergonomics; there is no security reason to prefer either placement, since the value isn't secret. This is an architecture-consistency call, not a security one, and does not need further sign-off before implementation — flagged here so the reasoning is visible, not because it's still open.

### Decision 6: No new audit-log entry for non-admin reads of Application Admin contact data

`teams.ts` already writes an `audit_log` row (plus `emitAuditEvent`) whenever an Application Admin reads membership or team-detail data (`admin.membership_list_accessed`, `admin.team_detail_accessed`). The original version of this decision considered the inverse case — non-admin callers reading individually-enumerated Application Admin identity — and decided against adding an audit entry for it. That case (and the roster it referred to) no longer exists under the 2026-09-16 configured-alias decision, but the same conclusion holds, now on simpler and more clear-cut grounds — restated explicitly rather than silently dropped, per the instruction not to let a superseded decision just disappear:

**Decision (reaffirmed, simplified rationale): do not add an audit_log entry for this read.**

- The original rationale's core point — the existing audit convention targets privileged actors reading or changing *other people's* information, where an anomalous pattern is a real signal of misuse — still applies, and applies more cleanly now. There is no individual PII disclosure to weigh at all any more: the value returned is a static, org-wide-shared configuration string (a support alias), not personal contact information belonging to a specific human. Logging its reads would be auditing "the page was viewed" in an even more literal sense than the original rationale described — there is not even a roster whose *size or membership* could vary in a way worth tracking.
- This remains a GET read behind an existing, unaffected authorization gate (`is_member OR application_admin`), not a new access grant.
- The blast-radius concern that originally motivated raising this question at all (ambient over-exposure of a full privileged-account roster) is now moot by elimination (see Decision 1) — there is no roster whose exposure frequency needs mitigating, by audit logging or otherwise.

This remains a design-level call, not one requiring further security sign-off. If the organization's audit-logging policy later expands to cover general configuration-value reads, this should be revisited as part of that broader change, not special-cased here.

## Risks / Trade-offs

- **[Risk] A future edit collapses the TEAM-005/TEAM-006 resolution paths into one, silently reintroducing an EM fallback on TEAM-006 and reopening Q2.** → Mitigation: keep the two resolution functions/queries named and tested separately (see tasks.md and the delta specs' scenarios); the rewritten task-4.3 tests assert TEAM-006 never renders EM identity, only the configured Admin contact or the unconfigured-contact fallback. **Stated plainly (security review Finding 3, carried forward): this is enforced by code separation and tests, not by a structural authorization barrier.** Nobody gains data they weren't already authorized to see either way, since `engineeringManagers` is already rendered elsewhere on the same page regardless of which contact the escalation message shows — this is a copy/framing decision about which already-visible identity gets labeled "the person to contact," not an access-control boundary. The distinct-type protection Decision 5 originally described (`AdminContact[]` vs. `TeamMember[]`, a copy-paste substitution becoming a type error) still exists in a simpler form: the Admin contact is now a single `string | null`, so substituting `engineeringManagers[0]` (an object) for it is *more* obviously a type error than before, not less — but this is still a secondary, cheaper layer on top of code separation and tests, not a replacement for them.
- **[Resolved by elimination] The zero-admin query accidentally includes the seed `System` account.** No longer applicable — there is no roster query for the `System` account to pollute (Decision 1). The equivalent failure mode in the new design would be the configured contact value itself being accidentally set to something non-actionable (e.g. a placeholder or internal address); that is not a `System`-specific risk and isn't mitigated at the query layer, because there is no query — see the new unconfigured-alias risk below.
- **[Resolved by elimination] Real Application Admin headcount larger than assumed.** No longer applicable — there is no enumeration, so there is no headcount-driven readability or blast-radius question to evaluate (former Open Question #1, now closed; see Open Questions below).
- **[Resolved by elimination] The July 2026 security threat-model assumption ("internal, small user population," under which naming individual admins was judged acceptable) being stale.** No longer applicable — this design no longer names any individual admin, so the July precedent's scope question (one identity vs. a full roster) doesn't arise (former Open Question #2, now closed; see Open Questions below).
- **[New risk] The configured contact-alias value is left unset or misconfigured at deploy time**, and nobody notices until a facilitator hits the fallback message in production. → Mitigation: Decision 4's fallback copy names the actual state honestly rather than failing silently or rendering a broken `mailto:` link, so the failure mode is visible rather than a dead end. This is otherwise an operational concern, not a design gap — recommending (non-blocking) that deployment documentation / the eventual runbook note this as a required post-deploy configuration check.
- **[Trade-off] TEAM-005's EM-fallback path and Admin-fallback path are separate branches rather than a uniform "look up authorized contact" abstraction.** Slightly more code for a small feature, but keeps the TEAM-006/Q2 boundary explicit and testable rather than implicit in a shared function's branch logic (see Decision 2). Unaffected by the 2026-09-16 decision.
