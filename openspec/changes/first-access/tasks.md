# Tasks: First Access
**Change:** first-access
**Date:** 2026-07-05

Most of the first-access implementation is already in place. These tasks verify the existing code against the finalized requirements, close the two confirmed gaps, and add tests for acceptance criteria not yet covered.

---

## Implementation Tasks

- [ ] Task 1: Add missing-claims validation to the authentication callback — In `packages/backend/src/routes/auth.ts`, after extracting `claims` from `tokens.claims()`, add an explicit guard that checks whether `claims.sub` is absent or an empty string, and whether `claims.iss` is absent or an empty string. If either condition is true: do not call `resolveOrCreateAccount`, do not establish a session, emit an `auth.failure` audit event identifying the specific missing claim without logging any PII (no token values, no other claim values), and redirect the user to the auth error page with a generic message and a correlation ID. This validation must precede the call to `resolveOrCreateAccount` in the callback flow.

- [ ] Task 2: Implement server-side no-team redirect in the authentication callback — In `packages/backend/src/routes/auth.ts`, after `resolveOrCreateAccount` completes and after any pending join token is processed, query the user's current team memberships from the database. If the user has no active memberships, set `redirectUrl` to `/no-team`. If the user has at least one active membership, set `redirectUrl` to `/team/:teamId` (using the first membership's team ID). Remove the default `redirectUrl = "/"` fallback for the non-join-token case. The query must use `team_memberships` with `WHERE user_id = $1 AND removed_at IS NULL`, matching the same live-data pattern used in the `/auth/session` endpoint.

- [ ] Task 3: Add no-team guard to the `/no-team` route — In `packages/frontend/src/App.tsx` or in `packages/frontend/src/pages/NoTeamPage.tsx`, add a guard that reads the current session's `teamMemberships`. If the user has one or more active team memberships when navigating to `/no-team`, redirect them to `/team/:teamId` (using the first membership's team ID). The guard should render a loading state while the session loads, then apply the redirect. This covers the bookmark scenario: a user who joined a team and later navigates directly to `/no-team` must not see the no-team page.

- [ ] Task 4: Verify the `/no-team` route is not wrapped in any navigation-contributing layout — Read `packages/frontend/src/App.tsx` and confirm that the `/no-team` route definition does not include any `<Layout>`, `<AppShell>`, `<Shell>`, `<Navigation>`, or similar wrapper component. If the application has added such a layout component to other routes since this check, ensure the no-team route is explicitly excluded. Document the result of this verification in a comment adjacent to the route definition, so the exclusion is visible to future developers.

## Test Tasks

- [ ] Task 5: Add tests for missing-claims rejection to the backend auth route — In `packages/backend/src/routes/auth.ts`'s test suite (or a new integration test file for the callback route), add test cases for: (a) a token where `sub` is an empty string — assert no call to `resolveOrCreateAccount`, no session created, redirect to auth error, audit event emitted without PII; (b) a token where `iss` is an empty string — same assertions; (c) a token where `claims()` returns `null` or undefined — same assertions. Verify that no account record is created or modified in any of these cases.

- [ ] Task 6: Add tests for server-side no-team redirect in the callback — In the backend auth route test suite, add test cases for: (a) a new user with no team memberships after account resolution — assert redirect to `/no-team`; (b) a user with one or more team memberships after account resolution — assert redirect to `/team/:teamId`; (c) a user whose join token is processed during the callback and results in a team membership — assert redirect to the team or session URL, not `/no-team`. These tests should mock the team membership query and verify the redirect destination set on the reply object.

- [ ] Task 7: Add tests for the no-team guard (bookmark redirect) — In the frontend test suite, add test cases for `NoTeamPage` (or the route wrapper added in Task 3): (a) when the session has no team memberships, the no-team page content is rendered; (b) when the session has at least one team membership, the component redirects to `/team/:teamId` without rendering no-team content. Use `MemoryRouter` with the appropriate session mock.

- [ ] Task 8: Add a routing-layer test that the `/no-team` route renders no navigation elements — In the frontend test suite, add a test that renders the full `<App>` at the `/no-team` path (using `MemoryRouter` with an initial entry of `/no-team` and a session mock with no team memberships). Assert that no `<nav>`, no element with a navigation role, and no element matching known navigation class names or test IDs is present in the rendered output. This test exists specifically to catch regressions if a layout wrapper is added to the `/no-team` route in the future.

- [ ] Task 9: Verify existing account-resolver tests cover the sub/iss-only identity matching constraint — In `packages/backend/src/auth/__tests__/account-resolver.test.ts`, confirm there is a test asserting that when two identities share the same email address but have different `sub` values, two separate accounts are created. If this test does not exist, add it. Also confirm there is a test asserting that a returning user with the same `sub`/`iss` but a changed email is matched to the existing account with the email updated. If not present, add it. These tests verify the explicit prohibition on email-based identity matching.

- [ ] Task 10: Verify audit logging for first_access_created — In the backend auth route test suite, add or verify a test case asserting that when a new user completes authentication, the `auth.first_access_created` audit event is emitted with `userId`, `oidcSubject`, and `oidcIssuer`, and does not include display name, email, or any other PII fields. Verify that for returning users (isNewUser = false), this event is not emitted.

- [ ] Task 11: Add isNewUser constraint comment to resolveOrCreateAccount — In `packages/backend/src/auth/account-resolver.ts`, add a code comment on or immediately before the SELECT query that precedes the upsert. The comment must state: (a) that `isNewUser` is determined by this SELECT, not from the upsert result; (b) that in a concurrent scenario where two callbacks arrive simultaneously for the same user before any account exists, both may read `existing.rows.length === 0` and both may set `isNewUser = true`; (c) that this is a hard constraint on future work — before any feature that consumes `isNewUser` is merged, the SELECT-before-upsert pattern must be replaced with a pattern that derives `isNewUser` from the upsert result, or the consuming feature must treat duplicate firings as idempotent. This comment exists specifically so future developers encounter the constraint when working in this function, not only in documentation files.
