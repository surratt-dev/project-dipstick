## Context

Two capabilities shipped independently and never reconciled: `pre-session-action-item-review` (2026-09-15) built `SessionLobbyPage`'s Start Session control and `pre_session` review render, framing `SessionLobbyPage` as *the* trigger off `lobby`. `session-creation-existing-team` (2026-09-23) built `DraftSessionHost` as the facilitator's durable, refresh-safe home across the session lifecycle (`design.md` Decision D6), explicitly meant to "grow" into that role — but its `live-readiness-view` never got a Start Session control, and nothing anywhere navigates a live user to `SessionLobbyPage`. Confirmed by exploration (`exploration-notes.md` §1–§3): the join-link landing rule only redirects for `active`; `TeamPage` has zero session-awareness; `DraftSessionHost`'s `live-readiness-view` renders only static status text for `lobby`/`pre_session`. Net effect: no session created today can progress past `lobby` through any reachable UI path.

`SessionLobbyPage` cannot simply be deleted in favor of `DraftSessionHost` (exploration §4): `DraftSessionHost` is facilitator-only, team-scoped, authorized via `facilitator_id === caller` on `GET .../facilitator-state`. `SessionLobbyPage`'s `action-items-review` endpoint is authorized via `evaluateSessionSubscriberAccess`, deliberately serving facilitator *and* participants from one shared surface. These are different authorization shapes by design; `DraftSessionHost` cannot become the shared participant surface without forking that model, and reproducing `SessionLobbyPage`'s subscribe-before-fetch WebSocket ordering (a correctness-sensitive guarantee against stranding a participant mid-transition) inside `DraftSessionHost` is real work this change does not take on.

## Goals / Non-Goals

**Goals:**
- Give the facilitator a working `lobby → pre_session` trigger on the page they actually land on (`DraftSessionHost`), without relocating the dead end to the next status.
- Give Engineers a working landing on `/session/:sessionId` for every `SessionStatus` where a joining user should be kept with the in-progress session rather than redirected away from it (`lobby`, `pre_session`, `active`), decided once as a full enumeration rather than patched incrementally per status. Note: "kept with the session" describes the routing destination, not a claim that each status has distinct rendered content there today — `SessionLobbyPage`'s actual branch logic renders `pre_session` distinctly but collapses `active` (and, if ever routed there, `wrap_up`) into one generic "moved past the pre-session review" message (`SessionLobbyPage.tsx`, `branch.kind === "left"`). That content gap is real, pre-existing, and not fixed by this change — see the Named Follow-ups list in proposal.md.
- Make the facilitator's normal-use handoff from `DraftSessionHost` to `SessionLobbyPage` for the `pre_session` review read as one continuous product, not two.

**Non-Goals:**
- `TeamPage` session-awareness. Existing team members who are not following a fresh join link have no way to discover a forming session; this predates this issue and is out of scope here (see proposal.md).
- A `DraftSessionHost`-native render of the `pre_session` review. This change keeps the facilitator's review on `SessionLobbyPage`, reached via a navigate link from `DraftSessionHost`. Full consolidation is a named follow-up (see Open Questions).
- A facilitator-aware join-link redirect (a facilitator's own link always landing on `DraftSessionHost`). Separate routing logic gated on resolving facilitator identity before the redirect decision; not touched here.
- Presence signal ("N people have joined") and "Open the room" vs. "Start Session" differentiating copy beyond the alignment pass in this change.
- Any backend change. `POST /start`, `GET /action-items-review`, and join-redemption are unchanged; this is routing/wiring plus copy alignment only.

## Decisions

**D1 — `DraftSessionHost` gets a Start Session control, not a redirect to `SessionLobbyPage`, for the `lobby → pre_session` transition.**
`DraftSessionHost` is already facilitator-only by authorization (D6 of `session-creation-existing-team`), so no additional gating is needed. The control renders whenever `currentSessionState === 'lobby'`. On click, call `POST /api/v1/sessions/:sessionId/start`; on success, update `currentSessionState` to `'pre_session'` in local component state — the same in-place-update pattern `openTheRoom` already uses for `draft → lobby`, no navigation. On failure, show inline retry and remain on `lobby`, matching `openTheRoom`'s existing failure pattern.
*Alternative considered:* route the facilitator to `SessionLobbyPage` immediately upon reaching `lobby`, since that page already has the control. Rejected — it contradicts `DraftSessionHost`'s established role as the facilitator's durable home ("room to grow," D6), and would mean the facilitator bounces between two pages within a single lobby wait instead of one.

**D2 — A navigate link closes the transition, so D1 doesn't just relocate the dead end one status later.**
Whenever `currentSessionState` is `'pre_session'` or a later non-terminal status (`'active'`, `'wrap_up'`), `DraftSessionHost` renders a link/button navigating to `/session/:sessionId`. A genuinely terminal session (`'complete'`, `'abandoned'`) keeps the existing static status text with no link — that's not a new dead end, since nothing about those statuses is actionable. Without this, a facilitator who clicks Start Session lands on the exact same static "Session status: pre_session." text the page renders for every non-`draft` status today (confirmed in current render logic, `DraftSessionHost.tsx:184-208`) — a second dead end introduced by this change's own D1.

**D3 — The facilitator's `pre_session` review stays on `SessionLobbyPage`; consolidation is deferred, not silently accepted as permanent.**
The navigate link in D2 sends the facilitator to `SessionLobbyPage`, the same page `pre-session-action-item-review`'s Decision 3 already built the review UI on, authorized via the same `evaluateSessionSubscriberAccess` grant that already gives the facilitator standing there. Building a `DraftSessionHost`-native render instead means reimplementing WebSocket subscribe-before-fetch ordering — a correctness guarantee, not a copy-paste — inside a component that has no WebSocket subscription today. Not taken on by this change.
*Consequence accepted, not hidden:* the facilitator's `pre_session` review happens on a screen with a different heading/voice than `DraftSessionHost`, exercised in normal use (the navigate link, or a facilitator following their own join link) — not an edge case. D5 below narrows this gap without closing it.
*Alternative considered:* build the `DraftSessionHost`-native review now. Rejected for this change on scope/risk grounds — real, non-trivial work, not a documentation gap — but named explicitly as a near-term follow-up (see Open Questions), not deferred into the general backlog.

**D4 — `join-link`'s landing rule becomes a full seven-`SessionStatus` enumeration, replacing the existing requirement outright.**
`SessionStatus` has seven values (`draft | lobby | pre_session | active | wrap_up | complete | abandoned`, `packages/shared/src/types/session.ts`). The existing requirement only branches on `active`. A patch touching only `lobby`/`pre_session` would leave `wrap_up`, `complete`, and `abandoned` to be inferred by whoever implements it — exactly the kind of gap that becomes a guess. This change's delta spec carries a full replacement of the "Session-aware join link landing" requirement:
> If a session exists for the team whose status is `lobby`, `pre_session`, or `active`, the user SHALL be directed to `/session/:sessionId`. If the team's most recent session (if any) is in `draft`, `wrap_up`, `complete`, or `abandoned` status, or no session exists at all, the user SHALL land on `/team/:teamId`.
`SessionLobbyPage` already renders correctly for `lobby` (waiting message, no Start Session control for non-facilitators — `SessionLobbyPage.test.tsx` "6.4") and `pre_session` (full review UI) — this is a spec-level rule change with no new frontend rendering logic required for the Engineer path.
*`wrap_up` bucket assignment — resolved, not deferred.* `wrap_up` stays in the `/team/:teamId` bucket, alongside `draft`/`complete`/`abandoned`. Decided by Devon Calloway (Internal Champion), against `requirements/use cases/06 - Session Wrap-up - Use Cases.md` directly, rather than left as a checkpoint pointing at a persona who was never asked (see tasks.md 1.1's history). That use case does frame `wrap_up` as a genuinely active, observable phase — "Participants' views update to indicate the session is in wrap-up," and explicitly: "the application should make clear to participants that the session is in its closing phase, not that it is over." Taken alone, that framing would argue for bucketing `wrap_up` with `lobby`/`pre_session`/`active`, not with `complete`/`abandoned`.
But the use case describes an observer experience that does not exist on any join-link-reachable surface today. Tracing `SessionLobbyPage.tsx`'s actual branch logic: the `action-items-review` endpoint returns 200 only for `pre_session`; every other reachable status via its 409 response — `active`, `wrap_up`, `complete`, `abandoned` alike — collapses into one undifferentiated `branch.kind === "left"` render, the static string *"This session has moved past the pre-session review."* Routing a `wrap_up` joiner to `/session/:sessionId` today would not produce the "closing phase, not over" experience the use case calls for — it would show a sentence that is actively misleading (it implies the pre-session review is the only thing that happened, not that the session is nearly done), which is worse for ritual trust than landing on a page that simply says nothing about the session. `/team/:teamId` is silent on the session, not wrong about it; `/session/:sessionId`'s current `left` branch would be wrong about it.
This is therefore a content gap, not a routing gap: the real fix is a `wrap_up`-aware observer render (on `/session/:sessionId` or the existing `/session/:sessionId/live` surface), not a routing rule pointed at a page with nothing to show. That's out of scope for this change and named as a follow-up (proposal.md), bundled with the related `active`-content gap the BA review also flagged. If that observer render is built later, this bucket assignment should be revisited — `wrap_up` would then have a legitimate destination it currently lacks.

**D5 — Copy/layout reconciliation is scoped narrowly: label/heading alignment plus two small copy fixes, not a shared-component refactor.**
Given D1–D3 mean the facilitator *will* land on `SessionLobbyPage` in normal use, the existing heading/copy mismatch (`DraftSessionHost`: team-name heading, "The room is open. Session status: lobby."; `SessionLobbyPage`: "Session Lobby" heading, "Session {sessionId} — waiting for the facilitator to start.") stops being latent and becomes something this change's own decisions actively route a facilitator into. In scope:
- Align the Start Session control's label and the `lobby`-state heading/copy across both surfaces closely enough that landing on either reads as the same product mid-transition.
- Drop the raw `sessionId` from `SessionLobbyPage`'s Engineer-facing waiting copy; add a one-line reassurance ("The facilitator will start the session shortly").
Out of scope, named explicitly: a shared component for the `lobby` state (vs. independently-matched copy), the presence signal, and "Open the room" vs. "Start Session" differentiating copy.

## Risks / Trade-offs

- **[Risk] Copy alignment (D5) drifts again the next time either page is touched independently**, since the two surfaces remain separately implemented, not a shared component. → Mitigation: accepted for this change's scope; the shared-component question is named explicitly as future scope in Open Questions rather than silently deferred.
- **[Risk] The `DraftSessionHost` → `SessionLobbyPage` handoff (D2/D3) is a second page with its own load/subscribe sequence**, so a facilitator following the navigate link pays a second network round-trip and a possible flash-of-loading-state that a native render wouldn't have. → Mitigation: accepted as the cost of not duplicating correctness-sensitive WebSocket-ordering logic (D3); scoped as a near-term follow-up to remove once `DraftSessionHost` gains its own subscription.
- **[Trade-off] `TeamPage` remains session-blind (non-goal).** A team member not holding a join link still cannot discover a forming session through this change. → Accepted; named as a distinct, pre-existing gap for its own follow-up, not silently absorbed or silently dropped.
- **[Risk] The seven-status enumeration (D4) is a full requirement replacement, not a patch** — any future `SessionStatus` value added to the system must be deliberately slotted into this enumeration's two buckets, or it silently falls into whichever bucket its omission defaults to. → Mitigation: the requirement is written as an exhaustive two-bucket partition (not an allowlist with an implicit else), so a reviewer adding an eighth status has to touch this text to stay correct; flagged here so implementation and future reviewers know the enumeration is deliberately exhaustive.
