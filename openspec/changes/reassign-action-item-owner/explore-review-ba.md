## Overall read

Devon's exploration is careful and the code-reading is accurate everywhere I checked it — the `evaluateTeamAccess`/`ACTIVELY_FACILITATING_STATUSES`/D12 descriptions in Sections 3 and 5 match `action-items.ts` line for line, and the migration-2 schema references are correct. The instinct to *not* silently resolve the two contract/precedent conflicts (Sections 5, 6) and instead flag them for design.md is the right call and needs no rework from me.

Where I want firmer ground before this goes into proposal.md: one blocker-reversal that's well-reasoned but shouldn't be adopted without a documentation trail (Section 3), one schema decision that's specific about the happy path but not about its own failure mode (Section 4), and one "exhaustive" mapping (Section 7) that's missing two request-shape cases and a validation-order rule that its own sibling endpoint (`VOTE-002`) already had to solve. I also found one adjacent gap the notes never surface at all: `ACTION-002` already has a second, unreconciled owner-reassignment code path.

## 1. The "still blocked on team-membership-removal" claim (Section 3)

**What's in the notes:** The code evidence — `removed_at`/`role` already live and read by `evaluateTeamAccess`, nothing in application code ever sets `removed_at`, `TEAM-004` (member removal) removed from the contract — is accurate and I re-verified it independently. The conclusion ("not blocked for #108's scope; genuinely blocked only for #68") is well-supported and I agree with it on the merits.

**What's not yet buildable as stated:** this isn't a vagueness problem, it's a *traceability* problem, and it's the kind of thing that becomes a scope dispute later if left as an implicit conclusion in an exploration doc. Three concrete issues:

1. **The blocker isn't just "still blocked on" prose — it's structurally referenced in two places in issue #108**: the "Still blocked on" section *and* the References list, which tags `team-membership-removal/README.md` explicitly as "(blocking dependency)." Reversing a blocker that's been named twice in a filed issue, on the strength of one engineer's independent code read, is exactly the kind of decision that needs a visible sign-off trail, not just a note buried in exploration.md that says "I'd want this confirmed." Devon already asks for my confirmation (Section 3, penultimate paragraph, and Open Question 1) — I'm treating that as a live request, not a formality: **I concur with the reasoning**, with the scope caveat below made explicit in writing.
2. **The stub itself needs updating, or it will mislead the next reader.** `openspec/changes/team-membership-removal/README.md`'s "Scope to design when this change is picked up" section currently lists: *"Resolution of GitHub issue #23 (open action-item reassignment authorization — `VOTE-004`'s 'new owner must be an active participant' constraint is not designed) as a prerequisite or a bundled decision."* That sentence is already stale as of #108's own issue body (#23 is resolved, cited there as "RESOLVED — was blocked on #23, now closed"), and it will be doubly stale once this change designs and ships that exact constraint. **Suggested rewrite:** proposal.md for this change should include a task to edit the stub's README to remove that bullet (or replace it with a forward pointer: "VOTE-004's active-participant validation is now designed/shipped by `reassign-action-item-owner`; this stub's remaining scope is limited to the admin/EM removal-authorization model and mid-session removal effects"). Leaving stale scope text in a dependency stub is exactly the kind of gap that creates a false blocker for some *future* change that reads the stub and assumes #108 hasn't happened.
3. **The "not blocked" conclusion needs its scope boundary stated in proposal.md, not just in exploration notes.** Devon's own honest caveat (Section 3, "The one honest caveat") — that the *typical* departed-owner scenario is unreachable in production until something sets `removed_at` — is correct and important, but it's the kind of nuance that gets lost between exploration.md and proposal.md if it isn't carried forward verbatim. **Suggested acceptance condition for proposal.md:** state explicitly that (a) VOTE-004's server-side validation is fully buildable and correct today against the existing schema, and (b) the "owner has left the team" scenario this endpoint is *named* for will not occur organically in any live team until a member-removal write path exists, so manual/QA verification of the 422 "not an active participant" path will need a raw `UPDATE team_memberships SET removed_at = ...` fixture (matching the existing test-fixture pattern Devon found in `ws-pubsub-integration.test.ts`) rather than an end-to-end removal flow. This should not surprise a reviewer or a QA engineer six weeks from now.

**Bottom line:** the reasoning is sound enough to build on, but it needs to leave a paper trail (updated stub, explicit scope caveat in proposal.md) — not just a "confirmed with Marcus" line in exploration notes that nobody re-reads once this change is archived.

## 2. `action_item_history` schema approach — Option A (Section 4)

**What's in the notes:** Option A (additive nullable `previous_owner_id`/`new_owner_id`, same-status-pair convention for reassignment-only rows, documented in the migration comment) is well-reasoned as a *choice between two options*, and I agree Option A is the smaller, lower-risk diff against a table `action-item-status-management` already depends on. I checked for existing consumers that might already assume "one row = one status transition" (grep across `packages/`, `openspec/specs/`, `openspec/changes/`) — there are none beyond the VOTE-002 write path and its own tests, so Option A does not corrupt anything live today. That part of the analysis holds.

**What's still too soft to hand to an implementer:**

- **"Readers must learn a convention" is not an acceptance condition — it's a description of a risk the notes correctly identify but don't close.** A convention that lives only in a migration comment is exactly the kind of thing that erodes the first time someone writes a new query against this table without reading migration history. I want this stated as an enforceable invariant, not a comment: *"A row where `previous_owner_id` and `new_owner_id` are both non-null is a reassignment-only row and its `previous_status`/`new_status` values SHALL be equal by construction. VOTE-004 SHALL NOT be extended to also change status in the same write without a corresponding schema/spec update."* I'd want design.md to state whether this is enforced with a `CHECK` constraint (e.g., `CHECK ((previous_owner_id IS NULL) = (new_owner_id IS NULL))` at minimum) or left as an application-level invariant with a documented reason why a DB-level check wasn't worth it. Either answer is fine — leaving it unstated is not.
- **The notes' own "future reader" risk has a present-day sibling that wasn't checked.** Section 4 worries about "a future 'status change count' metric or the trend/audit tooling" misreading reassignment rows as status changes. That's speculative — but there's a non-speculative, *already-shipped* gap adjacent to it: see Section 5 below (`ACTION-002`). The schema decision for `action_item_history` can't be signed off as "specific enough" without deciding how it relates to that existing gap, because both are about the table's completeness as an owner-change audit trail.
- **The spec-boundary note (last paragraph of Section 4) is correct but needs to be a concrete task, not a suggestion.** I agree with "the existing `action-item-status-management` spec's 'every real status transition' requirement should get a note that a reassignment row is a distinct requirement of a different capability." Suggested rewrite for tasks.md: an explicit task to add one sentence to `action-item-status-management/spec.md`'s history requirement — e.g., "This requirement governs status-change rows only; owner-reassignment rows written by `VOTE-004` are a distinct requirement, see `reassign-action-item-owner` capability" — rather than leaving it as something "the new capability's own spec should say," which could be satisfied by writing it in only one of the two places and calling it done.

**Bottom line:** Option A is the right lean, but "additive nullable columns + a documented convention" needs to become "additive nullable columns + a stated invariant (constraint or explicit application-level rule) + a cross-reference edit to the existing spec" before it's buildable without a follow-up question. I agree this is Ingrid's call to weigh in on given her D12/Finding history, per Devon's own note.

## 3. The two contract-vs-precedent conflicts (Sections 5 and 6)

Devon handled both of these the right way procedurally — flagged, not silently resolved, with a documented lean and a request for explicit design.md treatment. I don't think either needs to be resolved differently than Devon leans; I think both need a firmer *process* commitment than "I'd bring it to review":

- **Section 5 (404-vs-403 enumeration boundary):** I agree the D12 pattern should win over the contract's flatter table, for the same reason D12 was adopted in the first place — this isn't a new judgment call, it's applying an already-litigated precedent to a URL shape (`actionItemId` with no `teamId`) that is structurally identical to VOTE-002's. **What I'd add:** this should not be a design.md footnote — it should be written as its own scenario set (mirroring `action-item-status-management/spec.md`'s "A caller with no relationship to the item's team cannot distinguish it from a nonexistent item" / "A user with some relationship... is rejected with 403" scenario pair) so the two behaviors have independent test coverage, the same way VOTE-002's did. A single sentence in design.md saying "apply D12" is not the same as spec'd, testable scenarios.
- **Section 6 (403 vs 409 for resolved items):** I agree with the 409 lean — "resolved is terminal, unhedged" was explicitly litigated for VOTE-002 (Open Question 3 in `action-item-status-management/spec.md`, confirmed on my re-read) and there's no stated reason for VOTE-004 to depart from it. **What I'd add:** if design.md adopts 409 here, the REST API Contract.md document itself should get a correction note in VOTE-004's section, in the same style as the `global_role` correction and Appendix D's reveal/topic-advance correction already in this document — i.e., a one-paragraph "corrected by `reassign-action-item-owner`" note directly under the endpoint definition, not just a change buried in this change's own design.md. This document is the thing engineers grep for `VOTE-004` against; if the correction only lives in this change's design.md, the contract stays wrong at its source indefinitely.

**Bottom line:** both leans are right; both need to land as spec'd scenarios plus a contract-document correction, not just a design.md decision line, to match how this exact class of contract error has been handled before in this codebase.

## 4. 404-vs-422 mapping for new-owner validation (Section 7) — not exhaustive

Section 7's four-case enumeration (user doesn't exist / no membership row / disqualified membership / self-facilitator) is correct as far as it goes, but "exhaustive and unambiguous" is not yet accurate. I found two request-shape cases it omits and one cross-cutting rule it doesn't state:

1. **`sessionId` validation is entirely unaddressed.** The request body's `sessionId` field ("Current session context, for history attribution") is structurally identical to `VOTE-002`'s own optional `sessionId` field — and `VOTE-002` already had to solve this exact problem as Decision D11: an optional `sessionId`, if present, is validated *independently* of owner/authorization checks, and rejected with `422` ("sessionId does not reference a session in an active state for this team") if it doesn't belong to the item's team or isn't in an actively-facilitating status (`packages/backend/src/routes/action-items.ts`, the `if (sessionId !== undefined)` block preceding the D10 authorization check). VOTE-004's contract text doesn't even carry VOTE-002's "Required when the update occurs within a session" qualifier — it just says "Current session context, for history attribution," with no stated rule for when it's required, what happens if it references a different team's session, or whether it's validated at all. This needs the same D11-shaped scenario VOTE-002 has, reused, not re-derived. **This is a real gap, not a nuance** — Section 7 calls its mapping exhaustive, and it isn't, because it only ever considers `newOwnerUserId`.
2. **`newOwnerUserId === current owner` is unaddressed.** Reassigning an item to its existing owner is not covered by any of the four cases (the current owner, by definition, already passes cases 1–3 as a valid active participant, and isn't necessarily the facilitator). Is this a no-op success (200, matching VOTE-002's own same-status no-op precedent), or should it be rejected as a non-reassignment (422, "new owner is the same as the current owner")? The contract is silent, the use case doc is silent, and Devon's mapping doesn't raise it. I'd want an explicit line in design.md — my lean, for consistency with VOTE-002's same-status no-op handling, is 200/no-op, but this is a real decision, not an obvious one, since unlike a status no-op it produces zero externally-visible signal that anything happened.
3. **Validation ordering across all of this is unstated.** When an action item is resolved *and* the supplied `newOwnerUserId` also fails validation, which error wins — the resolved-item check (403/409, per Section 6) or the new-owner check (404/422)? VOTE-002 answers this exact class of question with an explicit, ordered sequence of checks (existence/relationship → sessionId → authorization → state/transition validity → body validation), each with its own decision number (D10, D11, D12) and its own test coverage in `action-items.test.ts`. VOTE-004 needs the same explicit ordering stated in design.md before tasks.md is written, or the implementer will pick an order ad hoc and a later reviewer will have to reverse-engineer whether it was deliberate.

**Suggested rewrite of Section 7's opening line:** replace "maps cleanly to three distinguishable cases" with an explicit statement that the mapping covers `newOwnerUserId` only, and that `sessionId` validation, same-owner reassignment, and overall check ordering are separate, currently-open decisions that also need design.md treatment before the endpoint is buildable end-to-end.

## 5. Gap not raised in the notes: `ACTION-002` is a second, unreconciled owner-write path

The exploration notes treat `action_item_history`'s owner-column gap as new territory VOTE-004 introduces. It isn't quite — `ACTION-002` (`PATCH /api/v1/sessions/:sessionId/action-items/:actionItemId`, "Update Action Item (During Wrap-Up)") already allows changing `ownerUserId` during wrap-up, with its own, slightly different validation phrasing ("must be an active participant of the team," no explicit self-facilitator or EM carve-out named), and its contract note is explicit that **no `action_item_history` entry is written for these edits today**, flagged as an open question (Appendix C, OQ-8: "BA to confirm").

This matters for exactly the schema decision in Section 4: once VOTE-004 ships and writes owner-change rows to `action_item_history`, the table will contain owner-history rows for reassignments made *after* wrap-up but *not* for owner edits made *during* wrap-up via `ACTION-002` — an inconsistency in what "the item's owner history" means depending on which endpoint touched it, and one a future audit/trend feature could easily miss. This isn't something #108 needs to fix (`ACTION-002`'s behavior is out of this issue's scope, and OQ-8 predates it), but the proposal should say so explicitly rather than let it look like an oversight:

**Suggested addition to design.md:** one sentence noting that `ACTION-002`'s wrap-up owner edits remain unrecorded in `action_item_history` per the still-open OQ-8, that this is a pre-existing, separate decision this change does not resolve, and that OQ-8 should be revisited (by me) once `reassign-action-item-owner`'s history convention exists, since the answer to OQ-8 can now reuse the same owner-column shape instead of inventing a new one.
