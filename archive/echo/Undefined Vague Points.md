# Undefined/Vague Points in Engineering Health Check

## Ambiguous Definitions

### 1. "Senior Engineer" Role
- Line 37-41: Uses "senior engineer" but note clarifies it's "more about experience than title"
- **Issue**: No clear criteria for determining who qualifies as a facilitator
- **Recommendation**: Define minimum years of experience or specific competencies

### 2. Quorum Requirements
- Line 35: States "Effort should be made to keep a regular cadence" and mentions absence handling
- **Issue**: No specific quorum threshold defined (e.g., 50%, 75%, all members?)
- **Recommendation**: Specify minimum attendance percentage for valid session

### 3. Action Item Ownership
- Line 71: "a senior engineer on the team should take it as an action item"
- **Issue**: What if no senior engineer is present? What if multiple issues are identified?
- **Recommendation**: Define clear ownership and escalation process

### 4. Vote Scale Interpretation
- Line 67: "there is no middle ground" for finger votes (1-4)
- **Issue**: No guidance on what each number means (e.g., 1=very difficult, 4=very easy)
- **Recommendation**: Add explicit reference scale for each topic

### 5. Outlier Threshold
- Line 69: Facilitator "will take note of any outliers"
- **Issue**: What constitutes an outlier? Is it a statistical calculation or facilitator judgment?
- **Recommendation**: Define criteria (e.g., 2+ points from mean)

### 6. Spreadsheet Format/Storage
- Line 21, 59: References capturing results in a spreadsheet
- **Issue**: No standard template provided, no guidance on where it's stored, who has access, or how to analyze trends
- **Recommendation**: Provide a sample spreadsheet template

### 7. Roman Vote vs Finger Vote Decision
- Line 67: "depending on the topic"
- **Issue**: No clear guidance on when to use which voting method
- **Recommendation**: Create explicit mapping of topics to voting types

### 8. Frequency Adjustment Criteria
- Line 47: "You may find that meeting more or less frequently as fits their needs"
- **Issue**: No criteria for when to change frequency
- **Recommendation**: Define triggers for frequency changes

### 9. Handling Significant Conflicts
- Line 39: "If a significant conflict is raised, the team needs to work with its engineering manager"
- **Issue**: No definition of what constitutes "significant"
- **Recommendation**: Define threshold for escalation to management

### 10. First Session Timing
- Line 118: Suggests first session be "an hour long"
- **Issue**: How far into a team's formation should this start? New projects only?
- **Recommendation**: Define when to initiate the practice

### 11. Participant Preparation
- No guidance on whether participants should prepare or review topics beforehand

### 12. Post-Session Follow-up
- Line 117: Mentions tracking action items but doesn't specify:
  - Where they're tracked
  - Deadline for resolution
  - How to measure effectiveness

### 13. "Bikeshedding" Boundaries
- Line 53: Mentions "This is not a time for bikeshedding"
- **Issue**: No guidance on how to recognize or prevent bikeshedding discussions

### 14. Legacy vs Greenfield Scope
- Line 125-127: FAQ addresses this but leaves decision to each team
- **Issue**: No framework for teams to make this decision

### 15. Confidentiality/Reporting
- No guidance on whether results are shared outside the team
